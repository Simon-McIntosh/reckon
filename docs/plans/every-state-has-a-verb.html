§1 — Five findings, one shape

Four coordinators working four projects reported five separate problems on 2026-09-03 and 2026-09-04. They look unrelated — a stale process, a SLURM wait, a lane switch, an undeclared companion file, a mislabelled row — and they are one thing. In each, a run reached a state the command surface has no verb for, so a competent agent invented a manual workaround, and in three of the five the workaround was an operation the rest of the system actively guards against.

That last clause is what makes this urgent rather than tidy. A worker whose lane is exhausted can only be discarded and re-dispatched, so the surface pushes an operator toward deleting a resumable session — the exact act that cost another session five runs the same night, and the act a promotion guard was landed hours earlier to prevent. A gap in the verbs is not a missing convenience; it is a channel that routes careful people into the dangerous path.

§2 — A follower never runs code older than the fleet it watches

A crew follow process holds the module code it started with for its entire life. When a recovery sweep landed and was wired into that loop, every follower on the workstation had been started hours earlier, so not one of them called it. Two independent sessions were simultaneously unable to perform a recovery they had just gained, and neither could see that from the pane — one of them left a run blocked for five hours and forty-two minutes with its limit long lifted.

The failure is silent in the direction that costs work. A stale renderer draws a wrong column and somebody notices; a stale follower recovers nothing and is indistinguishable from a fleet with nothing to recover. Restarting is the known remedy, it works, and it is an operator habit with no bound check — which is the same class of control this repository has already watched fail twice in a day.

Three shapes, in the order they should be tried. The follower detects that the package it imported is older than the one on disk and re-execs itself in place, keeping its session registration and its stdout so a watching pane never sees a gap. Failing that, the watch seat publishes a version stamp each cycle and a follower reading a newer stamp re-execs. Failing both, the follower says once, in the pane, that it is stale and how to cycle it — which is strictly worse than the first two but strictly better than silence.

Done when a follower running while new crew code lands performs the new behaviour without an operator restarting it; when the transition costs no gap in the pane and no lost session registration; when a follower that cannot re-exec says so explicitly rather than continuing quietly; and when no skill text anywhere instructs a reader to restart a follower after a merge. Asserted by landing a change to the swept behaviour under a running follower and requiring the new behaviour, not by asserting that a re-exec function exists.

§3 — Waiting on an external job is a state, not a blocker

A worker that submits a cluster job and outlives its own turn has nowhere to put that fact. The manifest vocabulary has no state for waiting on an external condition, so the worker parks as blocked with prose naming the job. The follower then counts it in the blocked bucket beside genuine failures, a coordinator resumes it by hand when a separate watch fires, and the recovery sweep cannot help because nothing refused it.

Measured on four runs in one night: two parked on jobs that ran forty-two minutes and three hours, each needing a hand resume; two more lost their turn while backgrounding a poll and were indistinguishable from crashes. The second pair is the sharper half — a wait that ends in silence and a crash that ends in silence produce the same record, so the coordinator cannot tell a healthy long job from a dead worker.

The state carries what a resumer needs and nothing more: what is being waited on, how to ask whether it is finished, what finished means, and the brief to hand back on resumption. The follower gives it its own bucket, so a fleet with four healthy waits does not read as four failures. And the sweep that already resumes lapsed provider holds acts on it when the named condition turns terminal — the same actor, a second trigger, because the shape is identical: a run that stopped for a reason that has since gone away.

Done when a worker can declare in its manifest that it is waiting on a named external condition with a way to test it and a resume brief; when the follower renders that as a bucket distinct from blocked and from working; when the sweep resumes such a run once the condition reaches a terminal state and leaves it alone until then; when a run waiting on a condition that never terminates is surfaced by age rather than waiting forever; and when a crashed worker is still distinguishable from a waiting one. Asserted through the follower's own rendering and the sweep's entry point, with the condition test injected so no test submits a job.

§4 — A run changes lane without losing its identity

Moving a dispatched run from one backend to another costs stop, then discard, then a fresh dispatch — and that dispatch is refused twice on the way, once because the member is still in flight until the old pointer is gone, and once because the worktree path already exists. So the price of a lane switch is either a new node id, which breaks the node's identity across the ledger, or a manual worktree removal.

Both prices are paid in the currency this system spent the night protecting. A new node id makes one piece of work appear as two unrelated runs in the record. A manual worktree removal is the act that turned a ten-minute provider outage into an unrecoverable loss, and the act that a promotion guard now refuses to perform on a recoverable run. Meanwhile resume accepts no backend override, so a run whose lane is genuinely spent cannot be continued elsewhere at all — the one case where moving lanes is obviously right is the case with no verb.

Done when a dispatched run can be moved to another backend keeping its node id, its worktree and its ledger identity; when the move records both lanes and the reason, so the run's history shows where it ran rather than appearing to have always run on the second; when a move onto a held lane is refused with the hold named; and when a session that cannot follow the move — because the new backend is a different harness — is reported as starting fresh rather than silently losing its context. Asserted through the command a coordinator invokes, over a dispatched run, requiring the worktree path and node id to be unchanged afterwards.

§5 — A promotion can accept a path the node did not declare

A producer regenerated a declared JSON artifact and, in the same call, its companion image. The image was not in the write scope, so crew complete refused the promotion for changed paths outside the declared scope — and neither the scope-changed flag nor the boundary waiver lifts that particular refusal. The run's commit was already merged to the primary branch. There was no way to record it.

The two available exits are both wrong. Discarding the record throws away the account of work that is already in the tree, leaving a commit no ledger row explains. Leaving the pointer strands it as an unreconciled remainder that also blocks its member from further dispatch. A third exit exists but is undocumented and unsafe by construction: hand-editing the live pointer's declared paths, which this coordinator has done, and which makes the fence agree by rewriting the thing it checks against.

The fence is right to refuse by default — an undeclared write is how one worker silently overwrites another. What is missing is the deliberate, recorded exception every other fence here already has. Done when a promotion accepts a named path outside the declared scope with a stated reason; when the accepted paths and reasons land on the promoted ledger row so the exception is auditable; when accepting a path claimed by another live run is still refused, because that is a collision rather than a companion; and when a promotion with undeclared paths and no acceptance is refused exactly as it is today. Asserted through the completion entry point over a run whose commit touches one declared and one undeclared path.

§6 — The surface answers the question an agent is holding

The four sections above each add a verb. This one is about whether the next agent finds them. Every finding in this plan was discovered by an agent hitting a wall and improvising, not by reading a surface and choosing correctly, and several improvised around capabilities that already existed — a session id recoverable from a stream, a sweep already wired to a loop, a hold already ageing out. A capability nobody can find is indistinguishable from one that does not exist, which is this repository's oldest recurring finding wearing a different hat.

The unit of discovery is the moment of failure. An agent reads a refusal far more often than it reads a manual, so the refusal is where the verb belongs: a promotion blocked by an undeclared path names the acceptance flag, a dispatch blocked by a held lane names the probe and the sweep, a resume refused for a live process names the stop. Each of these is one sentence in a message that is already being printed.

Done when every refusal the crew surface emits names the verb that resolves it or states plainly that none exists; when the command help for each verb says which state it applies to rather than only what it does; when no two commands whose names differ by a word do unrelated things without saying so in the first line of help — the classification command and the sweep currently sit one word apart; and when an agent reading only refusals and help can reach every verb this plan adds. Asserted by collecting the refusal messages the surface can emit and requiring each to name a verb or an explicit absence.

§7 — A worker can find the worker it needs to talk to

Six coordinators were live on this workstation across four repositories on 2026-09-04, and no tool could say so. Every cross-session message this night was addressed by a name someone happened to remember, and every question of the form whose run is that was answered by reading another session's pointer files by hand — a boundary no coordinator should have to cross to learn who owns a run.

The cost is not hypothetical. This session told a nova coordinator to resume a run that belonged to a different nova coordinator — nova had two, s18-pta and s19-relaunch, and nothing surfaced that. They corrected it, and the correct answer was already on disk: the run's pointer named its session, its project and its repository. A peer separately guessed a run id from memory of dispatch order and got a microsecond timestamp wrong, because the only ways to learn one were to glob a config directory or parse a committed ledger.

The join already exists and the tool is a thin read. Every live pointer carries the coordinator's own session label, the project, the plan its node serves, and the repository in its worktree path. Grouping those four fields produces the directory directly, demonstrated against the live fleet before this section was written. What the pointer cannot supply is the harness address a message is sent to, which arrives on every cross-session message as its sender socket — so the tool reports the reckon-side identity it knows and the transport identity where it has seen one, and never invents the second from the first.

Done when one read answers, for a project or for the whole workstation, every live coordinator session with its project, its repository, the plans or sprint it is shipping, and its live node count; when a run can be resolved to its owning session without reading another session's files; when a node id rather than a run id is enough to identify a run, since the node id is the human handle and the run id carries a timestamp nobody can reconstruct; when the answer distinguishes a session that is dispatching from one whose runs are all terminal, because those want different messages; and when the transport address is reported only where it has been observed rather than derived from a name. Asserted through the read a coordinator calls, over pointers built the way dispatch writes them, including the two-coordinators-in-one-project case that caused the misaddressed instruction.

And the default is collaboration, not silence. A finding about another repository is worth more to the session working in it than to the one that found it, and this night's evidence is one-sided: every correction that mattered came from a peer measuring something the author could not see. A stale-base warning caught a merge misreading inherited ancestry as delivered work. A count of five-of-six dead-process claims holding unintegrated work stopped a data-loss predicate shipping. A measurement of zero file-writing tool calls corrected a loss claim in the other direction. Each arrived unbidden, and each was cheaper to send than to rediscover. So a coordinator that finds a defect touching a repository it does not own reports it to the session working there when one is live — as a finding, never as an instruction, and never as authority, since a peer cannot authorise work in a repository that is not theirs.

§ Decisions

How does a follower stop running stale code?

What shape moves a run between lanes?

One implementation behind two entry points, because the entry points answer different questions while the operation underneath is identical. A backend override on resume is the verb when a run is BLOCKED and its lane is spent - the live case being a run held by a usage limit resetting four days out, where resume never becomes available and a lane change is the only lawful move. A redispatch keeping the node id is the verb when a run is WORKING and the coordinator wants it elsewhere, which is how the gap was first reported. Underneath both are one act: relaunch this node's worker on a different backend, keeping its node id, its worktree and its ledger identity. Two implementations of that would be two code paths able to disagree about one run, which is this session's most repeated defect - a pointer and a stream disagreeing about a session, a CLI and an MCP surface disagreeing about a verb, a package attribute resolving to two objects by import order. Choosing a single entry point was rejected because each covers a state the other cannot: an override on resume cannot move a run that is still working, and a redispatch cannot answer a NEEDS-HELP brief inside the session that raised it.

§ Followups

The follower first, because every other fix here is invisible without it

§2 goes first and the ordering is not preference. Every section below it changes behaviour a follower executes, and a follower that holds stale code will not perform any of them - so landing §3, §4 or §5 before §2 means landing capabilities that the running fleet cannot reach, which is precisely the failure §2 describes. It has already happened once with the recovery sweep.

§3 and §4 are independent of each other and can run together. §5 is a small, self-contained change to the completion path and can run beside either. §6 goes LAST by construction: it asserts that every refusal names its verb, and it cannot be measured until the verbs §2 to §5 add exist.

Two decisions are open and only one blocks: the follower freshness mechanism should be settled before §2 is dispatched, since the three candidate shapes have different failure modes and the weakest is explicitly a fallback. The lane-change verb can be settled by the node that implements it, since both shapes are described and the third option is to share one implementation.
