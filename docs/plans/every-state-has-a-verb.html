§1 — Five findings, one shape

Four coordinators working four projects reported five separate problems on 2026-09-03 and 2026-09-04. They look unrelated — a stale process, a SLURM wait, a lane switch, an undeclared companion file, a mislabelled row — and they are one thing. In each, a run reached a state the command surface has no verb for, so a competent agent invented a manual workaround, and in three of the five the workaround was an operation the rest of the system actively guards against.

That last clause is what makes this urgent rather than tidy. A worker whose lane is exhausted can only be discarded and re-dispatched, so the surface pushes an operator toward deleting a resumable session — the exact act that cost another session five runs the same night, and the act a promotion guard was landed hours earlier to prevent. A gap in the verbs is not a missing convenience; it is a channel that routes careful people into the dangerous path.

§6 — The surface answers the question an agent is holding

The four sections above each add a verb. This one is about whether the next agent finds them. Every finding in this plan was discovered by an agent hitting a wall and improvising, not by reading a surface and choosing correctly, and several improvised around capabilities that already existed — a session id recoverable from a stream, a sweep already wired to a loop, a hold already ageing out. A capability nobody can find is indistinguishable from one that does not exist, which is this repository's oldest recurring finding wearing a different hat.

The unit of discovery is the moment of failure. An agent reads a refusal far more often than it reads a manual, so the refusal is where the verb belongs: a promotion blocked by an undeclared path names the acceptance flag, a dispatch blocked by a held lane names the probe and the sweep, a resume refused for a live process names the stop. Each of these is one sentence in a message that is already being printed.

Done when every refusal the crew surface emits names the verb that resolves it or states plainly that none exists; when the command help for each verb says which state it applies to rather than only what it does; when no two commands whose names differ by a word do unrelated things without saying so in the first line of help — the classification command and the sweep currently sit one word apart; and when an agent reading only refusals and help can reach every verb this plan adds. Asserted by collecting the refusal messages the surface can emit and requiring each to name a verb or an explicit absence.

§8 — The peer channel is advertised to the roles that cannot reach it

The worker prompt hands every node a peer-channel client and the client is composed as python -c 'from reckon.crew.dispatch import _peer_command; …' at reckon/crew/prompts.py:67 — a bare interpreter name with nothing guaranteeing the package is importable. Whether it works depends entirely on where the worker happens to be standing, because python -c puts the working directory on the import path. Measured 2026-09-08 on this host, one command, two locations:

Working directoryRoles standing thereResult
the assigned worktreefull-worktree roles imports, because the worktree is the package source tree
the delivery directoryread-only roles ModuleNotFoundError: No module named 'reckon'

So the channel is not broken in general, which is why it survived: the roles that exercise it most while implementing are the ones it happens to work for. It is broken precisely for the roles whose deliverable is a report and whose reason to speak to a peer is strongest, and those are the roles the prompt tells about it in the same words. A capability advertised where it cannot run is worse than an absent one, because the worker spends turns on it before discovering that.

The dependence on the working directory is the defect, not the missing path. An interpreter that can import the package is already in hand at composition time — the process composing the prompt is running from one — so the client can name it instead of hoping the worker's cwd supplies it. Naming it also removes a second latent failure that has not yet been measured: a worker whose python resolves to a different interpreter than the one reckon is installed into would fail from any directory at all.

Done when the composed peer-channel client runs from a working directory that is not the package source tree, proven by executing the exact advertised command from a delivery directory and getting the client's own usage rather than an import error; when the interpreter it names is derived from the composing process rather than resolved from the worker's environment, so no host path is written into the prompt text; when a full-worktree role's client keeps working unchanged; and when a test asserts the composed string does not begin with a bare interpreter name. Asserted by running the advertised command from both directory kinds and requiring the same outcome in each.

§ Decisions

How does a follower stop running stale code?

Deduced from the code rather than chosen: the follower already compares follower_code_stamp() against the stamp it started with at a bounded cadence (FOLLOWER_FRESHNESS_SECONDS) and re-execs itself through the sys.path root that supplied the imported package, carrying a reader checkpoint across the replacement so no transition is lost and its registration survives. Stamp-driven was rejected because the watch seat's reckon_version answers a different question, which producer a project's seat belongs to, and coupling follower freshness to it would make a follower's correctness depend on the producer having been re-armed. Announce-only is the fallback and is already the failure path rather than the mechanism: when os.execv itself fails the follower states that it is stale and prints the exact command to cycle it. The accepted cost is that a re-exec replaces the process, so anything holding the old pid loses it.

What shape moves a run between lanes?

One implementation behind two entry points, because the entry points answer different questions while the operation underneath is identical. A backend override on resume is the verb when a run is BLOCKED and its lane is spent - the live case being a run held by a usage limit resetting four days out, where resume never becomes available and a lane change is the only lawful move. A redispatch keeping the node id is the verb when a run is WORKING and the coordinator wants it elsewhere, which is how the gap was first reported. Underneath both are one act: relaunch this node's worker on a different backend, keeping its node id, its worktree and its ledger identity. Two implementations of that would be two code paths able to disagree about one run, which is this session's most repeated defect - a pointer and a stream disagreeing about a session, a CLI and an MCP surface disagreeing about a verb, a package attribute resolving to two objects by import order. Choosing a single entry point was rejected because each covers a state the other cannot: an override on resume cannot move a run that is still working, and a redispatch cannot answer a NEEDS-HELP brief inside the session that raised it.

§2 goes first and the ordering is not preference. Every section below it changes behaviour a follower executes, and a follower that holds stale code will not perform any of them - so landing §3, §4 or §5 before §2 means landing capabilities that the running fleet cannot reach, which is precisely the failure §2 describes. Two decisions are open and only one blocks: the follower freshness mechanism should be settled before §2 is dispatched, since the three candidate shapes have different failure modes and the weakest is explicitly a fallback. DESIGN PROPOSAL FOR crew follow, relayed by the imas-ambix session from two coordinators who hit the same gap independently today, and recorded here rather than acted on because both metered lanes are constrained. THE GAP: the follower reports transitions and nothing reports their ABSENCE, so a drained fleet is indistinguishable from a working one. Two measured failures on 2026-09-05: one coordinator sat with three terminal pointers unpromoted for hours because quiet read as done; another had two runs end with work outstanding and manifests still reading in_progress, discovered four hours later only when its lead asked what was in flight - a process that ends without emitting a terminal event produces no transition at all, so the follower is structurally blind to it. THE DISAGREEMENT IS THE USEFUL PART and the union is the design. One proposed firing when the alive-process count reaches zero, which closes the non-terminal pointer whose process is dead - the row no transition will ever announce. The other proposed firing when WORKING reaches zero rather than when all three counts do, and that is the sharper trigger: the ambiguity that costs is not finished versus still working, it is finished versus waiting on something I forgot. With blocked and unpromoted non-zero all afternoon, an all-three-zero trigger would never have fired for the coordinator who needed it most. Take working-hits-zero as the primary trigger and the alive-count payload with it: always carry all three counts, and where a non-terminal pointer has no live process, NAME it. ON NOISE, which was the lead's actual question: both coordinators independently proposed hysteresis rather than a timer, which is a good sign. Fire when working hits zero and do not re-arm until working has been non-zero again. One line per quiescence rather than per transition, no debounce interval to tune, and a fleet that drains, refills and drains again has genuinely reached the state twice, so both lines are wanted. A level with hysteresis, not an edge on every poll. This belongs to this plan because it is a state with no verb: the fleet reaches quiescence and nothing says so.
