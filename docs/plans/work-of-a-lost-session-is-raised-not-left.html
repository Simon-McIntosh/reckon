§1 — Why: work that nobody owns keeps the lane busy and the queue long

On 20 November the lead asked why the local lane had stopped draining. The lane was open with ten free slots and the admit service was passing every 25 seconds, yet the monitor showed nine ready requests and nineteen waiting. None of it was launchable, and part of the reason was work whose coordinator session no longer existed.

A census of the live pointers that morning found seven records owned by five sessions with no running process:

Two queued reviews of sessions 67139f13 and efd0ee8c had also been relaunched and refused on every pass for days, each attempt creating and removing a run. They were dropped by hand that morning. One was recomposed by the review reflex within minutes and refused again, because the duty belongs to a finished run that the lost session still owns; a week-long acknowledgement on that run is the only thing holding it now.

Finding the owner of a record took three hand steps. The pointer carries the session id; the scheduler job a session submits carries nothing, so job 1331989 was traced to its session through the worktree path in its working directory; and the session id was mapped to a peer name by reading the harness's own session files. Eight messages to seven peers then settled most of the nineteen waits in an hour, which is the evidence that the missing piece is the address, not the channel.

The same morning showed that a wait can be correct for days. The imas-codex coordinator answered that four requests waiting 48 to 81 hours were parked by design behind a benchmark the lead must rule on. So age alone is not a reason to remove a wait: the reason is that nothing can ever release it, or that nobody is left to act on it.

The lead ruled on 20 November: when a session has been lost for three days its reviews are dropped and its implement work is raised to the lead for adoption or retirement; a wait that cannot resolve is removed; and none of this may add load to an orchestrator's own loop.

§2 — A lost session is a derived fact, read once by the admit service

Deliverable. One Python function answers, for a coordinator session id, whether the session is lost and since when. A session is lost when no follower lease, session-host record or running coordinator process has existed for it for longer than a flight setting, lost_session.after_hours, whose default is 72. The answer is keyed on the last instant the session was heard, never on the age of its process, because a resumed session keeps its id for weeks. A session that has never registered a follower is dated from its oldest live record. The crew directory view carries the answer for every session that owns a live record: last_heard_at, lost and lost_since.

The admit service is the only caller that acts on the answer, and it reads it at most once per session per pass from state it already lists. No follower, hook, station tick or session command gains a read.

Done when. tests/test_a_lost_session_is_a_derived_fact.py passes, covering: a session whose last lease is 71 hours old reads live and one at 73 hours reads lost, each computed from the fixture's own instants; a session with a running coordinator process reads live whatever its lease age; a session whose coordinator process is ten days old and was never restarted, holding a lease renewed a minute ago, reads live; the setting moves the boundary; and the directory view returns the three fields for a lost and a live session. A second assertion in the same file counts the reads an admit pass makes over a fixture of 40 pointers across 6 sessions and requires the lost-session reads to number at most 6.

Negative control. With the function replaced by one keyed on process age, the ten-day-old process with a fresh lease must read lost, so that case fails.

§3 — A lost session's reviews retire, and no review is composed under it

Deliverable. A queued or awaiting-upstream request of role review whose session is lost is retired by the admit pass that finds it, leaving a discard record that names the lost session, the instant it was last heard and the rule. A finished run that owes a review and whose session is lost gets no review composed under that session, by the reflex or by recovery, so nothing is created to be refused. The duty is not forgotten: the run is carried into the decision §4 raises.

Done when. tests/test_a_lost_sessions_reviews_retire.py passes, covering: one admit pass retires a lost session's queued review and writes the discard record with those three facts; a second pass creates no run and attempts no launch for it; a finished run of a lost session with a review owed yields zero composed reviews across three reflex passes; a live session's identical records are untouched; and the pass's verdict record lists each retirement under a named key.

Negative control. With the session made live in the fixture, the same pass must retire nothing and the reflex must compose the review.

§4 — A lost session's implement work is raised as one decision for the lead

Deliverable. For each lost session that owns anything other than a review request, the admit service records exactly one open decision, readable through crew view decisions. The decision lists every record the session owns with its project, plan, section, phase and age, and the work each one holds back. A request §5 retires as stranded is retired whoever owns it and is not listed: the decision covers only records still live after that retirement. It is written once and updated in place as the list changes; it is never written again while it is open. Until it is answered, the session's implement requests launch nothing and its landing groups are skipped without a refusal being recorded on each pass.

The decision takes one of two answers per record. Adopt names a live session: the record's ownership moves to that session, so that session's follower hears the run and its obligations list it, and a queued request becomes launchable. Retire removes a request with a discard record, and for a run records its disposition without promoting it. A record the classifier already reads as promoted or landed elsewhere needs no answer: its pointer is retired by the pass with the reason recorded.

Done when. tests/test_a_lost_sessions_work_is_raised.py passes, covering: a lost session with one implement request, one blocked run and one finished run yields one decision naming all three, and ten further passes leave the decision count at one; an adopt answer moves ownership so the adopter's live view lists the run and the lost session's lists nothing; a retire answer leaves a discard record and no pointer; an already-promoted pointer of a lost session is retired without a decision; a stranded request of a lost session is retired with §5's reason and is absent from the decision; and a landing group containing a lost session's member is skipped with one recorded reason, not refused per pass.

Negative control. With the decision store emptied between passes, the test asserting a single decision must fail by counting more than one write.

§5 — A wait that cannot resolve is removed; an idle wait is reported to its owner

Deliverable. Every awaiting-upstream request is classed by what could release it, in Python, and the class is carried on the live view as wait_class:

ClassMeaningWhat happens
progressingan upstream section has a live run or a queued requestnothing

strandedan upstream it names can never land: the section id is absent from its plan, the plan is absent, or the plan is closed, superseded or abandoned with that section not donethe request is retired with a discard record naming the upstream and why it cannot land, and its owner's obligations carry the retirement once

A wait is never removed for its age alone. A request held with crew queue hold keeps its hold whatever its class.

Negative control. With the upstream plan's status moved from superseded back to active in the fixture, the retirement case must fail.

§13 — A review that changed no file releases cleanly

The release step resolves that text as a revision, fails, and the run is classified blocked or unreadable with “workspace release refused: manifest commit '…' does not resolve”. Five review runs of the power_convertor session on 19 and 20 November, a review of an mctb run and this plan's own content review all ended that way with their records stored. crew complete --gate not-run --wait then fails on “commits missing” unless an outcome is passed.

Deliverable. A review run whose record is stored and whose worktree holds no change releases its workspace and is recorded without a refusal, whatever its manifest writes where a commit would go, and crew complete for such a run needs no outcome text to stand in for commits.

Done when. tests/test_a_review_that_changed_nothing_releases.py passes, covering: a review run with a stored record, a clean worktree and each of the three observed spellings of an empty commits field releases and reads recorded, never blocked or unreadable; a review run whose worktree holds an uncommitted change is still refused, naming the change; and an implement run whose manifest names a commit that does not resolve is still refused.

§ Decisions

When a session has been lost for three days, are its implement requests dropped like its reviews, or raised to the lead for adoption?

Raise them. A dropped review is composed again by the reflex under a live session; nothing composes a dropped implement request again, so dropping it loses the work silently.

Is waiting work with no connection to anything that could release it removed?

The lead asked for stranded waits to be removed. A wait whose upstream can never land is removed. A wait whose upstream is only idle is reported to its owner, because the same morning a coordinator showed four multi-day waits that were parked by design.
