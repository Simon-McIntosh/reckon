§1 — Why: the shared record is the conflict

Across the five primary branches, 415 of the 1,086 merges from 12 to 26 September that changed plan or evidence HTML (38%) conflict when their recorded parents are replayed (crew pattern review §5), and three of the five coordinators surveyed on 2026-09-26 — s21, s23 and the imas-ambix coordinator — rank those conflicts among their largest wall-clock costs: "nearly every merge, always a mechanical union" (s21), "the single worst conflict generator" (s23) (§3). The cause is the default write scope: besides the paths a node declares, dispatch adds three shared paths — the plan's HTML file, the plan's cumulative evidence record, and the plan-wide figure directory docs/figures/<plan>/. The review's six study nodes declared six data directories disjoint from one another and were still each granted those same three paths (§9), so their merges produced an add/add conflict on the shared evidence record every time.

The practice of a worker authoring its own landing record is right and this plan keeps it (worker-authors-its-own-record); the append_evidence op already landed (a-landing-beat-needs-no-hand-edit §2). What changes is where that record is written: today both the evidence anchor and the plan comment are regions of files every other worker also edits.

§2 — A node's default scope replaces the shared paths with its own fragment

Deliverable. In place of the three shared paths, dispatch adds by default docs/evidence/fragments/<plan>/<node-id>.html for the node's evidence anchor and docs/figures/<plan>/<node-id>/ for its figures; a redispatch of the same node writes the same fragment, replacing its predecessor's. A coordinator may still declare a shared record explicitly, and dispatch then warns that it reintroduces the conflict. The worker prompt names the fragment as the write path for the evidence anchor and no longer names the shared record as one. Each node writes exactly one landing: line in its manifest in place of editing the plan.

Done when a test dispatching six dry-run nodes against one plan asserts that no two default scopes contain, or are contained in, the same path, and a prompt fixture shows the fragment path and no shared record among the write paths.

§3 — The record is composed at read time, and the plan comment goes through the versioned write

Deliverable. One function composes a plan's cumulative evidence record — at docs/evidence/archive/<plan>-landed.html or docs/evidence/<plan>-landed.html — as the record file's own content followed by its fragments in the order the ledger records their promotions; the SPA, read_plan and audit-doc all read through it. Promotion writes the run's landing: line as a comment on the node's plan section through the versioned edit_plan path, never through a git merge.

Done when the six study commits of the review — velocity 9afcdbe0, worker anatomy 11fb09a4, coordinator overhead 4413e78a, code depth 77876fa0, nova flapping e01ec2ad and nova readiness 9cf52140 — with each one's evidence anchor moved into its fragment and its plan edit moved into a landing: line, merge onto their base 457bbec7 with zero conflicts under docs/plans and docs/evidence by git merge-tree, and the composed record contains all six anchors.

✓ landed 2026-09-26 compose_landed_record — the composition function reads a record's own bytes and appends each fragment under docs/evidence/fragments/<plan>/ in the order the ledger records its promotion, resolving both record spellings. A node promoted twice contributes its fragment once, at its earliest promotion; a row for another plan never reorders this record; and a fragment merged before its run is promoted is composed after the ledgered ones rather than hidden. It writes no file and never re-renders the document, so a record with no fragments composes to its own bytes byte-for-byte. Composer only — the versioned landing: write and the SPA / read_plan / audit-doc readers are not in this node's scope. §3 composition landed

§4 — Records without fragments are unchanged

Deliverable. Composing a record that has no fragments returns the record file's own bytes, so no existing record is rewritten or re-rendered.

Done when a test over the current tree asserts that, for every existing docs/evidence/*-landed.html and docs/evidence/archive/*-landed.html with no fragments, the composed bytes equal the file's bytes.
