§1 — A short commit citation is resolved once per process

Why. _FollowerReloader in reckon/crew/follower_reload.py checks for a code move every FOLLOWER_FRESHNESS_SECONDS, which is 1.0 s (reckon/crew/follower_registration.py near line 554). Each check calls runs.follower_code_stamp(), which reaches checkout_trust.source_code_identity. For a git checkout that is _committed_reload_tree in reckon/checkout_trust.py: git ls-tree HEAD reckon skills, a second ls-tree for the catalogue blob, and one or two git mktree calls. So every follower starts several git processes a second. Each of them opens the repository's config and every pack index on GPFS, and the answer changes only when HEAD's commit changes.

What changes. The follower keys its identity on a cheap reading of where HEAD points: the stat of .git/HEAD, of the ref it names, and of packed-refs, all resolved without starting git. It re-derives the identity, with the same git calls as today, only when that key changes. Otherwise it returns the identity it holds. The key is read through the same .git resolution git uses, so a worktree checkout and a main checkout both read correctly. A checkout outside git keeps its content stamp path unchanged. A read that fails yields IDENTITY_UNKNOWN exactly as today, so a partial read never stands for an unmoved HEAD.

Done when. A new tests/test_a_follower_reads_its_identity_only_when_head_moves.py, working in a temporary git repository, shows four things. With subprocess.run counted, 20 identity reads against an unmoved HEAD start git only on the first read. A new commit touching reckon/ moves the key, and the next read re-derives and returns the new identity. A commit touching only a file outside reckon/, skills/ and the catalogue moves the key but leaves the identity equal. A key-read failure yields IDENTITY_UNKNOWN. Negative control: drop the key comparison so every read re-derives, and the first case fails while the others pass. The test files importing reckon.checkout_trust, reckon.crew.follower_reload or reckon.crew.follower_registration add no failure against the base revision, run in place on the fleet node with -n 6 --timeout 120, one arm at a time. After landing, once followers have reloaded, a 15 s strace -f -e trace=execve of one reckon follower records no git execve while HEAD does not move. The before and after counts are logged.

Write paths: reckon/checkout_trust.py, reckon/crew/follower_reload.py, reckon/crew/follower_registration.py, tests/test_a_follower_reads_its_identity_only_when_head_moves.py. Every log under the run directory starts with its revision and the literal command and ends in a bare EXIT= line. ruff check and ruff format --check are clean on those paths by delta.

§2 — The model catalogue has one memo, and it hands out copies

Why. The same follower opened and parsed docs/state/reckon/model-catalogue.yaml 86 times in 15 s, about six a second. The catalogue changes only when a commit changes it. It is read through flight.read_layer_file (reckon/flight.py near line 624) from at least ledger.resolve_name and ledger.lanes_declaring_model (reckon/ledger.py near lines 255 and 297), and the YAML parse costs CPU on every call. The reload tree's copy sits on node-local /tmp, but a checkout's copy is on GPFS.

What changes. The catalogue's parsed content is held in memory, keyed on the file's path, st_mtime_ns and st_size, and re-parsed only when that key changes. Callers receive a value they cannot mutate into the cache: either an immutable view, or a copy. The memo lives at the one read boundary every catalogue reader already passes through, not beside each caller. A missing file still reads as it does today.

Done when. A new tests/test_the_model_catalogue_is_parsed_once_per_stamp.py shows that 50 reads of an unchanged catalogue parse it once. Rewriting the file with a different size or mtime makes the next read return the new content. A caller mutating the returned value does not change what the next read returns. A deleted catalogue reads as it does today. Negative control: drop the stamp comparison, and the parse count case fails. The test files importing reckon.flight or reckon.ledger add no failure against the base revision, run in place on the fleet node with -n 6 --timeout 120, one arm at a time. After landing and a reload, a 15 s strace -e trace=openat of one reckon follower opens the catalogue at most once while it is unchanged. The before and after counts are logged.

Write paths: reckon/flight.py, reckon/ledger.py, tests/test_the_model_catalogue_is_parsed_once_per_stamp.py. Every log under the run directory starts with its revision and the literal command and ends in a bare EXIT= line. ruff check and ruff format --check are clean on those paths by delta.
