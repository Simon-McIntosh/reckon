§1 — A short commit citation is resolved once per process

Why. _resolve_commit in reckon/crew/recovery_review_subject.py (near line 240) remembers an answer only when the candidate is a full revision (_FULL_REVISION, near line 203). _stored_commit_answer (near line 214) returns empty for anything shorter. Manifests cite short shas, so the derivation that opts into cached=True (near line 347) starts git again for every citation on every follower pass. A commit object that resolved once stays resolved, so the repeated query buys nothing.

What changes. A citation that resolves is remembered under its tree and the candidate as written, whatever its length, in the bounded _RESOLVE_COMMIT_CACHE and the store behind recovery_watch._stored_commit_answer that the full revision already uses. A citation that does not resolve is remembered only against the reading of git_head._head_identity for that tree, so a commit that arrives later is asked about again once HEAD or its ref moves. strict callers keep asking git every time, as today. No second cache is added. This extends the one _resolve_commit already keeps.

Done when. A new tests/test_a_short_commit_citation_is_resolved_once.py, in a temporary git repository with subprocess.run counted, shows four things. Twenty cached=True resolutions of one short sha start git once. Twenty resolutions of a short sha naming no commit start git once while HEAD is unmoved. After a new commit moves HEAD, the next resolution asks git again. A strict resolution starts git on every call. Negative control: restore the full-revision-only guard in _stored_commit_answer, and the first case fails while the strict case passes. The test files importing reckon.crew.recovery_review_subject or reckon.crew.recovery_watch add no failure against the base revision, run in place on the fleet node with -n 6 --timeout 120, one arm at a time. After landing, once followers have reloaded, a 20 s strace -f -e trace=execve of one reckon follower records no git rev-parse for a citation it has already resolved. The before and after counts are logged.

Write paths: reckon/crew/recovery_review_subject.py, reckon/crew/recovery_watch.py, tests/test_a_short_commit_citation_is_resolved_once.py. Every log under the run directory starts with its revision and the literal command and ends in a bare EXIT= line. ruff check and ruff format --check are clean on those paths by delta.

§2 — The model catalogue has one memo, and it hands out copies

Why. ledger._identity_catalogue (reckon/ledger.py near line 248) caches the catalogue with lru_cache on ledger._file_identity, and hands every caller the same mapping. The design review confirmed on this checkout that a key written into one result shows up in the next. ledger.lanes_declaring_model (near line 297) bypasses that cache and calls flight.read_layer_file directly, which is where the follower's repeated catalogue opens come from. reckon/file_memo.py already owns stat-keyed memoisation: memoized (near line 358) keys on signature_from_stat and deep-copies on hand-out.

What changes. Every catalogue read in reckon/ledger.py goes through one file_memo.memoized read of the catalogue. _identity_catalogue and the catalogue's use of ledger._file_identity are deleted, and lanes_declaring_model reads through the same memo. A missing catalogue reads as it does today. Nothing is added to reckon/flight.py.

Done when. git grep -n "_identity_catalogue" over reckon returns nothing. A new tests/test_the_model_catalogue_has_one_memo.py shows four things. Fifty calls mixing resolve_name and lanes_declaring_model on an unchanged catalogue parse it once. Rewriting the file makes the next call read the new content. A caller mutating a returned value does not change the next call's answer. A deleted catalogue reads as it does today. Negative control: return the memo's stored object without the copy, and the mutation case fails. The test files importing reckon.ledger or reckon.file_memo add no failure against the base revision, run in place on the fleet node with -n 6 --timeout 120, one arm at a time.
