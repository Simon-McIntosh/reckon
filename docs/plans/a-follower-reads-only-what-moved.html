§1 — A short commit citation is resolved once per process

Why. _resolve_commit in reckon/crew/recovery_review_subject.py (near line 240) remembers an answer only when the candidate is a full revision (_FULL_REVISION, near line 203). _stored_commit_answer (near line 214) returns empty for anything shorter. Manifests cite short shas, so the derivation that opts into cached=True (near line 347) starts git again for every citation on every follower pass. A commit object that resolved once stays resolved, so the repeated query buys nothing.

What changes. The guard at recovery_review_subject.py near lines 205-209 keeps no abbreviation, because a ref name or an abbreviation can move. That reason holds for a ref name, and for an abbreviation only as ambiguity: a hex prefix names an object, so a later object sharing the prefix makes git refuse it rather than name another commit. So a candidate that is a hex string of at least 7 characters, and that resolved to a commit whose full id starts with it, is remembered under its tree and the candidate. It goes into the bounded _RESOLVE_COMMIT_CACHE and the store behind recovery_watch._stored_commit_answer, which the full revision already uses. A ref name, or any candidate that is not such a prefix, is still never kept. A citation that does not resolve is remembered only against the reading of git_head._head_identity for that tree. That reading covers HEAD and the ref it names, so a commit made in that worktree is asked about again. An object fetched without moving that ref is not, until the process restarts, and the section accepts that because a worker's commits always move its own HEAD. strict callers keep asking git every time, as today. No second cache is added: this extends the one _resolve_commit already keeps.

Done when. A new tests/test_a_short_commit_citation_is_resolved_once.py, in a temporary git repository with subprocess.run counted, shows four things. Twenty cached=True resolutions of one short sha start git once. Twenty resolutions of a short sha naming no commit start git once while HEAD is unmoved. After a new commit moves HEAD, the next resolution asks git again. A strict resolution starts git on every call. Negative control: restore the full-revision-only guard in _stored_commit_answer, and the first case fails while the strict case passes. The test files importing reckon.crew.recovery_review_subject or reckon.crew.recovery_watch add no failure against the base revision, run in place on the fleet node with -n 6 --timeout 120, one arm at a time. After landing, once followers have reloaded, a 20 s strace -f -e trace=execve of one reckon follower records no git rev-parse for a citation it has already resolved. The before and after counts are logged.

§2 — The model catalogue has one memo, and it hands out copies

Why. The follower opened docs/state/reckon/model-catalogue.yaml 86 times in 15 s. The trace has no call sites, so the section does not pick a culprit.
