The queue exists so that chosen work never waits on a coordinator. On 28 October it did the opposite four times, in three projects. Each case was measured from run records and the admission verdict log at ~/.config/reckon/crew/admission-verdicts.jsonl.

Five causes, each confirmed in the code:

  • Release waits for a whole pass. resolve_waits has three callers. _queue_validated_waits (dispatch.py:274) resolves a request once, when it is queued. The drain view (runs.py:2146) resolves an overdue request only to report it stuck, and moves nothing. The release step in admit_once is the only one that moves a waiting request once its upstream lands. Nothing runs that step when a section lands, so release latency equals the duration of whatever pass is in progress.
  • One serial loop does three jobs. admit_until_stopped runs land_once() and then admit_once(), one after the other. land_once bounds its measurements to one per pass, but not its landings. _land runs crew complete --land through srun with no timeout, once for every accepted delivery. Any slow landing delays every release and launch on the workstation.
  • A launch recomputes what queue time already proved. With no refusals left, a pass still takes 6.5 minutes. A py-spy sample at 20:20Z shows each launch inside plan_dispatch, then require_plan_reviewed, then review_coverage, re-parsing every stored review snapshot of the plan with BeautifulSoup. A plan with 55 stored reviews pays that on every launch. §18 caches readiness, not review coverage.
  • Some refusals have no lifter. held-on-claim lifts when the claim releases, and capacity refusals keep a back-off. A CompetenceLimit is now held until the request changes, but nothing tries a lane whose window fits. A park whose probe cannot change is never classed dead. And a delivered run with no review at its head leaves land_once without a record.
  • Nothing measures a stall where the queue is read. The verdict row records no pass duration, and no view reports how long an admissible request has waited. On 28 October the lead read an idle lane as a halted system, twice, before any record showed why.

The design that follows rests on five rules. Release is driven by the event that makes it possible, not by a pass. Release, launch and landing are separate stages, each with its own time budget, and none waits on another. Every refusal class names what lifts it, and a refusal nothing can lift is reported to its owner. A check that can run at dispatch or at a queue edit runs there, while the coordinator is present. And the queue's own liveness is recorded in the verdict row and the drain view, never as monitor lines.

§2 — A landed section releases its waiters within a minute

The resolve-and-move idiom has one owner. The lines in _queue_validated_waits (dispatch.py:274-283) that resolve a request's waits and move its pointer become one function in queue_admission, beside resolve_waits, that resolves a request's waits and moves its pointer. Every mover uses it: the queue-time check in dispatch, the release step in admit_once, and two new callers. Promotion calls it inline once its merge has landed, for the requests that wait on the section the promoted run delivered, and a discard calls it for the discarded run's dependants. The admission service runs the release step on its own tick, at most every 30 seconds and separately from launches and landings, so a release never waits behind either.

The readiness cache from §18 keeps its key. roadmap_snapshot.roadmap_project_generation carries no file-content signal, so a plan edited in place during a pass would no longer invalidate it. Stat-ing the plan files per lookup costs far less than the roadmap build the cache saves. The drain view's call site is section 7's to change, not this section's. Interface: no public definition is added, and the new function retires the duplicated idiom in dispatch.py.

Done when a new tests/test_a_landed_section_releases_its_waiters.py shows four things:

  • A request waiting on another section stays awaiting-upstream.
  • The release tick moves a request whose upstream landed by another route, a hand merge for one, within one tick.
  • A release that raises leaves the promotion landed and records the failure on the request.

§3 — Landing runs beside admission, bounded

The landing pass leaves the admission loop's critical path. admit_until_stopped stops calling land_once between passes. The admit service runs landing in its own worker thread instead, under its own lock, with at most one landing action in flight, so a slow landing delays only the next landing. Each tick takes at most one action: one measurement, or one crew complete --land. _land bounds its srun step by the landing measure's timeout and records a timeout as a refusal naming it. Each verdict row records its stage durations: release, launch and land seconds, and the start and end of the pass.

Interface: no CLI verb or option is added, because the fleet supervisor already runs the admit service and the worker lives inside it. The serial land_once call in admit_until_stopped is retired.

Done when a new tests/test_landing_runs_beside_admission.py shows four things:

  • An admission pass completes and releases a waiter while a landing it does not call is blocked on a patched _land.
  • A landing tick that finds three accepted deliveries runs one crew complete --land and leaves two for later ticks.
  • A _land step that exceeds its bound is stopped and recorded as refused with a guard naming the bound.
  • Each verdict row carries started_at, ended_at and per-stage seconds.

The negative control calls land_once from admit_until_stopped again, and the first arm must fail. A further arm shows that a landing worker that raises is restarted on the next tick and never stops the admission loop. The test files importing reckon.crew.queue_landing and reckon.crew.queue_admission add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/queue_admission.py, reckon/crew/queue_landing.py and the new test.

§4 — A launch reuses what queue time proved

A queued request already passed the dispatch gate when it was queued, and a-review-gate-judges-what-it-covers §10 records its section and contract digests. At launch, require_plan_reviewed compares those digests with the plan's present ones and returns at once when neither moved. When one did, it computes review_coverage through a memo keyed by the plan file's blob and the stored review records' identities, shared by every launch in one pass. A direct dispatch keeps its own full check.

§5 — A refusal at admission is routed or reported, never parked

When admission refuses a queued request with CompetenceLimit, the pass does not judge fit itself. It asks the picker for its ranked candidates for the node through picker.snapshot.candidates, whose _fit already runs the competence check per backend under the lifts in force. It takes the first candidate whose competence verdict passes, and moves the request there with move_queued_run, which already re-composes a launch on another backend. A lane the admission service may launch on is launched there in the same pass; any other lane leaves it queued on that lane with an obligation naming it. Only when no lane fits is the request held held-until-changed, with an obligation to the owning session. Its stored reason is the failure, as a-queue-holds-the-whole-plan §29 requires, and not the lane's last allowance. crew queue edit runs the context-fit check and the live-claim check on the edited request and refuses the edit there, while the coordinator is present. It also re-records the request's review contract through queue_admission.record_review_contract, folded from the review of the production wiring, so an edited request keeps the narrowed hold rather than falling to the dispatch gate's. Interface: the two edit-time refusals are the existing CompetenceLimit and ScopeConflict refusals, raised earlier, so no refusal family and no public definition is added.

Done when a new tests/test_a_refusal_at_admission_is_routed.py shows four things:

  • A request that fits no lane is held held-until-changed, with one obligation naming the shortfall in tokens.
  • A crew queue edit that grows a request past every lane's window is refused, naming the shortfall, and leaves the request unchanged.
  • A queue edit onto a path a live claim holds is refused, naming the holder.

The negative control skips the picker query, and the first arm must fail. §6 — A park whose probe cannot change is dead

A parked run is held by a wait probe until the probe reads a declared terminal value. When the probe's value has not changed across three supervisor sweeps, and no process of the run or of the work it waits on is alive, the park is dead. The supervisor reclassifies the run from parked to a dead-park state. The owning session receives one obligation naming the probe, its last value and the terminal value it expected. The repeating "terminal when the probe reports …" detail stops for it. The classification belongs to its owner, recovery_classification.classify_pointer: its waiting branch and the detail built around recovery_classification.py:1240-1265 are where a park is classed and its row is drawn. Obligations derive from that classification (obligations.py:610), so no obligation is written separately. The history the decision needs is written by the one per-sweep actor. resumption.sweep already calls the probe each sweep, and it records the observed value and its time on the run's pointer as wait_probe_history, keeping the last three entries. classify_pointer stays pure and reads that history from the pointer it is given. recovery_wait.py only validates a probe's shape and does not change. Liveness is read through process_liveness.process_alive and recovery_liveness._live_descendant, never a second process check. Interface: no public definition is added, and the repeated per-sweep detail for a dead park is retired.

Done when a new tests/test_a_park_that_cannot_change_is_dead.py shows three things:

  • A park whose probe reads a constant value with no live process is reclassified on the third sweep, with one obligation.
  • A park whose probe value is still moving, or whose waited-on process is alive, stays parked.
  • A probe that later reaches its terminal value releases the run as before.

The negative control removes the liveness clause, and the second arm must fail. The test files importing reckon.crew.recovery_classification add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/recovery_classification.py, reckon/crew/resumption.py and the new test.

§7 — The queue reports its own stalls where it is read

The drain view and each admission verdict row carry the age of the oldest request that is admissible but unlaunched while its lane has room. Nothing new is written to the monitor stream. When that age passes ten minutes, the pass records a stall verdict naming the request, the stage that held it and that stage's last duration. The stall reaches the request's own session through the existing needs-you rows in needs_you.needs_you_rows, once, until it clears, and not through a new obligations row. The drain view's own overdue computation at runs.py:2146 reads the recorded stall verdict in place of resolving waits a second time. A stall therefore names its cause in the record a coordinator already reads. Interface: the drain view's separate stuck rule is retired, the stall verdict is the one added kind, and no new row kind is added.

§8 — A delivered run always reaches a landing verdict

land_once already reads a commit entry that carries a subject or several revisions, through _delivered_revision (queue_landing.py:28). It already refuses an entry that names no revision, through _unreadable_entry_guard (queue_landing.py:52). Two exits still drop a delivered run. First, land_once continues past a run with no review at its head, or a stale one, with no record. Second, the crew complete --land step that land_once calls re-reads the raw entry in promotion_evidence.py (around lines 878 and 932) and refuses the same entries the pass accepted. This was measured on 28 October on a-link-that-orders-nothing-is-named and shc-locus-reapply-all-bindings.

A run with no review at its head is recorded awaiting-review in the same admission_landing record, with the review reflex's own state beside it: dispatched, or refused with its reason. The land step reads the delivered revision through queue_landing._delivered_revision. Interface: no public definition is added, and the second commit-entry reader in promotion_evidence.py is retired.

§10 — A landing measure is bounded by what it measures, and a timeout is retried

On 28 October the landing pass refused r-20261028T201333437803-a-queued-request-is-stamped-at-queue-time with landing measure unreadable: the population base arm exceeded its 600s bound. The run changes eight lines of reckon/crew/runs.py. The run's review carried no blocking finding, and its armed test passed. But nearly every test file imports runs, so the importer population is close to the whole suite. Under the fleet node's load that evening, that population takes longer than any fixed 600 s bound. The refusal is also sticky: since section 33 of a-queue-holds-the-whole-plan, a refused head is judged again only when the landing code or its review changes, and neither moves when the node is merely busy. The run would stay refused until a coordinator landed it by hand.

So the bound is sized from what is measured. Every arm records its elapsed seconds and file count in the Arm record, and so in the stored landing-measure/measurement.json, which today records neither. An arm's bound is then the larger of the configured floor and a multiple of the file count times the project's median seconds per file. The median is read across the project's stored measurements, and an arm with no history gets the floor. A refusal whose guard is a timeout or a base-checkout failure is environmental. It is retried on a bounded back-off, counted from the failure, with no code or review change required. A refusal whose guard is a measured regression, a blocking finding or a merge conflict stays as section 33 left it. Interface: no public definition and no refusal family is added. The fixed 600 s figure is retired as the sole bound.

Done when a new tests/test_a_landing_measure_is_bounded_by_what_it_measures.py shows four things:

  • An arm whose population last took 900 s is given a bound above 900 s, and an arm with no history gets the floor.
  • A refusal recorded for a timeout is judged again after its back-off with the code and review unchanged.
  • A refusal for an added regression is not judged again until the code or review moves.
  • The back-off doubles across repeated timeouts and is capped.

The negative control restores the fixed bound, and the first arm must fail. The test files importing reckon.crew.landing_measure and reckon.crew.queue_landing add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/landing_measure.py, reckon/crew/queue_landing.py and the new test.
