§1 — What stalled work on 28 October

The queue exists so that chosen work never waits on a coordinator. On 28 October it did the opposite four times, in three projects. Each case was measured from run records and the admission verdict log at ~/.config/reckon/crew/admission-verdicts.jsonl.

Five causes, each confirmed in the code:

  • Release waits for a whole pass. The only call that moves a request from awaiting-upstream to queued is the release step inside admit_once (queue_admission.py, the loop over resolve_waits). Nothing runs it when a section lands. So release latency equals the duration of whatever pass is in progress.
  • One serial loop does three jobs. admit_until_stopped runs land_once() and then admit_once(), one after the other. land_once bounds its measurements to one per pass, but not its landings. _land runs crew complete --land through srun with no timeout, once for every accepted delivery. Any slow landing delays every release and launch on the workstation.
  • A launch recomputes what queue time already proved. With no refusals left, a pass still takes 6.5 minutes. A py-spy sample at 20:20Z shows each launch inside plan_dispatch, then require_plan_reviewed, then review_coverage, re-parsing every stored review snapshot of the plan with BeautifulSoup. A plan with 55 stored reviews pays that on every launch. §18 caches readiness, not review coverage.
  • Some refusals have no lifter. held-on-claim lifts when the claim releases, and capacity refusals keep a back-off. A CompetenceLimit is now held until the request changes, but nothing tries a lane whose window fits. A park whose probe cannot change is never classed dead. And a delivered run with no review at its head leaves land_once without a record.
  • Nothing measures a stall where the queue is read. The verdict row records no pass duration, and no view reports how long an admissible request has waited. On 28 October the lead read an idle lane as a halted system, twice, before any record showed why.

The design that follows rests on five rules. Release is driven by the event that makes it possible, not by a pass. Release, launch and landing are separate stages, each with its own time budget, and none waits on another. Every refusal class names what lifts it, and a refusal nothing can lift is reported to its owner. A check that can run at dispatch or at a queue edit runs there, while the coordinator is present. And the queue's own liveness is recorded in the verdict row and the drain view, never as monitor lines.

§2 — A landed section releases its waiters within a minute

A new queue_admission.release_waiters(project, refs) resolves the waits of every awaiting-upstream request that names one of refs, and moves each satisfied one to queued. It uses the same resolve_waits and dead-section rule as the pass, with one readiness read for the call. Promotion calls it inline once its merge has landed, passing the plan and section the promoted run delivered; a discard calls it for the discarded run. The admission service also runs the release step on its own tick, at most every 30 seconds, separately from launches and landings, so a release never waits behind either.

Done when a new tests/test_a_landed_section_releases_its_waiters.py shows four things:

  • Promoting a run that delivers plan#s1 moves a request waiting on plan#s1 to queued with no admission pass run.
  • A request waiting on another section stays awaiting-upstream.
  • The release tick moves a request whose upstream landed by another route, a hand merge for one, within one tick.
  • A release that raises leaves the promotion landed and records the failure on the request.

The negative control removes the inline call, and the first arm must fail. The test files importing reckon.crew.queue_admission and reckon.crew.promotion add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. After landing, the coordinator records the interval from one promotion to its waiter's queued stamp on the live store, beside nova's 41 minutes. Write paths: reckon/crew/queue_admission.py, reckon/crew/promotion.py and the new test.

§3 — Landing runs beside admission, bounded

The landing pass leaves the admission loop. It runs as its own supervised loop, crew land --watch, under its own lock, so a slow landing delays only the next landing. Each tick takes at most one action: one measurement, or one crew complete --land. _land bounds its srun step by the landing measure's timeout and records a timeout as a refusal naming it. Both loops write their stage durations into their verdict rows: release, launch and land seconds, and the start and end of the pass.

Done when a new tests/test_landing_runs_beside_admission.py shows four things:

  • An admission pass completes and releases a waiter while a landing it does not call is blocked on a patched _land.
  • A landing tick that finds three accepted deliveries runs one crew complete --land and leaves two for later ticks.
  • A _land step that exceeds its bound is stopped and recorded as refused with a guard naming the bound.
  • Each verdict row carries started_at, ended_at and per-stage seconds.

The negative control calls land_once from admit_until_stopped again, and the first arm must fail. The fleet supervisor starts and restarts the new loop as it does the admit service. tests/test_cli_help_contract.py and the other help-contract tests cover the new verb. The test files importing reckon.crew.queue_landing and reckon.crew.queue_admission add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/queue_admission.py, reckon/crew/queue_landing.py, reckon/crew_run_commands.py, reckon/crew/fleet_supervisor.py and the new test.

§4 — A launch reuses what queue time proved

A queued request already passed the dispatch gate when it was queued, and a-review-gate-judges-what-it-covers §10 records its section and contract digests. At launch, require_plan_reviewed compares those digests with the plan's present ones and returns at once when neither moved. When one did, it computes review_coverage through a memo keyed by the plan file's blob and the stored review records' identities, shared by every launch in one pass. A direct dispatch keeps its own full check.

Done when a new tests/test_a_launch_reuses_what_queue_time_proved.py shows three things:

  • A pass launching three queued requests on one unchanged plan calls review_coverage zero times, counted through a patch.
  • After a plan edit, the same pass calls it once and reuses the result for the other two.
  • Each launch's verdict equals the verdict of a fresh direct dispatch at the same moment.

A timing arm, logged under the run's logs/, records the launch-gate seconds on reckon:a-queue-holds-the-whole-plan before and after, and the after figure is below a tenth of the before. The negative control drops the digest comparison, and the first arm must fail. The test files importing reckon.crew.routing and reckon.crew.plan_review add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/routing.py, reckon/crew/plan_review.py and the new test.

§5 — A refusal at admission is routed or reported, never parked

When admission refuses a queued request with CompetenceLimit, the pass asks the picker for a lane whose context window fits the node's estimate, among the lanes the request's session may use under the lifts in force. If one exists, the pass moves the request there with move_queued_run, which already re-composes a launch on another backend. A lane the admission service may launch on is launched there in the same pass; any other lane leaves it queued on that lane with an obligation naming it. Only when no lane fits is the request held held-until-changed, with an obligation to the owning session. Its stored reason is the failure, as a-queue-holds-the-whole-plan §29 requires, and not the lane's last allowance. crew queue edit runs the context-fit check and the live-claim check on the edited request and refuses the edit there, while the coordinator is present.

Done when a new tests/test_a_refusal_at_admission_is_routed.py shows four things:

  • A request whose estimate exceeds the local window but fits another lane under an active lift is moved to that lane in one pass, with no obligation.
  • A request that fits no lane is held held-until-changed, with one obligation naming the shortfall in tokens.
  • A crew queue edit that grows a request past every lane's window is refused, naming the shortfall, and leaves the request unchanged.
  • A queue edit onto a path a live claim holds is refused, naming the holder.

The negative control skips the picker query, and the first arm must fail. The test files importing reckon.crew.queue_admission and the module carrying crew queue edit add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/queue_admission.py, reckon/crew/queue_edit.py and the new test. The coordinator confirms the module that implements crew queue edit before dispatch and names it in the node's write paths.

§6 — A park whose probe cannot change is dead

A parked run is held by a wait probe until the probe reads a declared terminal value. When the probe's value has not changed across three supervisor sweeps, and no process of the run or of the work it waits on is alive, the park is dead. The supervisor reclassifies the run from parked to a dead-park state. It raises one obligation to the owning session naming the probe, its last value and the terminal value it expected, and stops reporting "matches no declared terminal state" for it.

Done when a new tests/test_a_park_that_cannot_change_is_dead.py shows three things:

  • A park whose probe reads a constant value with no live process is reclassified on the third sweep, with one obligation.
  • A park whose probe value is still moving, or whose waited-on process is alive, stays parked.
  • A probe that later reaches its terminal value releases the run as before.

The negative control removes the liveness clause, and the second arm must fail. The test files importing reckon.crew.recovery_wait add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/recovery_wait.py and the new test.

§7 — The queue reports its own stalls where it is read

The drain view and each admission verdict row carry the age of the oldest request that is admissible but unlaunched while its lane has room. Nothing new is written to the monitor stream. When that age passes ten minutes, the pass records a stall verdict naming the request, the stage that held it and that stage's last duration. The obligations view shows the stall to the request's own session once, until it clears. A stall therefore names its cause in the record a coordinator already reads.

Done when a new tests/test_the_queue_reports_its_own_stalls.py shows three things:

  • A request queued and admissible for eleven minutes on a lane with room yields one stall verdict naming the release, launch or land stage that held it.
  • The drain view reports its age.
  • A request held on a claim, or a lane with no room, yields no stall.

The negative control removes the room clause, and the third arm must fail. A check confirms no monitor-stream row is added. The test files importing reckon.crew.queue_admission and reckon.crew.runs add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/queue_admission.py, reckon/crew/runs.py and the new test.

§8 — A delivered run always reaches a landing verdict

Two exits from the landing path still drop a delivered run without a record. land_once continues past a run with no review at its head, or a stale one. And crew complete --land re-reads the manifest's raw commits entry, so it refuses an entry that carries a subject or several revisions, which land_once already parses. A run with no review at its head is recorded awaiting-review, with the review reflex's own state beside it: dispatched, or refused with its reason. The landing step reads the delivered revision through the parser land_once uses.

Done when a new tests/test_a_delivered_run_reaches_a_landing_verdict.py shows three things:

  • A complete run with no review at its head carries an awaiting-review landing record naming the reflex state.
  • A run whose last commit entry carries its subject lands through crew complete --land.
  • A complete manifest with no commits entry at all is refused with a recorded guard.

The negative control restores the silent continue, and the first arm must fail. The test files importing reckon.crew.queue_landing and the promotion modules the change touches add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. After landing, the coordinator replays the landing filters over the live pointers and records that no complete implement run lacks a landing record. Write paths: reckon/crew/queue_landing.py, reckon/crew/promotion_records.py and the new test.

§9 — A first dispatch reports what it wrote

A dispatch whose node waits on an unlanded section stores a new request. It then answers run … is already awaiting-upstream for this node, naming the run it has just created. nova read that as a duplicate on 28 October, and so did this plan's author, twice. The answer comes from _answer_existing_node_run, which a first dispatch reaches after its own _queue_validated_waits write. A first dispatch answers queued awaiting-upstream with its waits. Only a dispatch that finds a request it did not write answers already.

Done when a new tests/test_a_first_dispatch_reports_what_it_wrote.py shows three things:

  • A first dispatch of a waiting node answers with its new run id, phase awaiting-upstream and its waits, and no already.
  • A second dispatch of the same node answers already, naming the first run.
  • Exactly one pointer exists after both.

The negative control routes the first dispatch through _answer_existing_node_run, and the first arm must fail. The test files importing reckon.crew.dispatch add no failures against the base revision, and ruff check and ruff format --check pass on the changed paths. Write paths: reckon/crew/dispatch.py and the new test.
