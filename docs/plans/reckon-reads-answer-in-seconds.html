An agent that waits half a minute for a routine read stops using the tool. The lead asked, on 2026-09-25, for the reads to answer without a large pause.

§1 — What the reads cost today

Each tool body was called twice in one process on clu-2058, in fleet job 1277272, at 2026-09-25 about 08:40 local. That mirrors the resident MCP server's cold first call and warm second call.

The warm audit sits one second under the 30 s storage deadline. Under load it crosses the deadline and returns storage-slow. The roadmap and audit do not get faster when warm, so nothing is cached between calls.

S21's a-page-load-reads-each-file-once makes discovery parse each file once for the served web loader. This plan covers the MCP tools and must reuse that plan's memo rather than add a second cache.

§2 — Profile the three slow reads

This is an investigation. Its deliverable is docs/research/reckon-read-latency-profile.html. It profiles the warm audit, roadmap summary and discovery calls on the reckon project, for example with cProfile, and names the top five cumulative-time call sites of each by file and line at a named revision.

For each read it states:

  • whether the time is parsing, filesystem walking, git subprocesses or computation
  • which existing memo, such as reckon.file_memo, the S21 discovery memo or memoized, could carry it
  • the expected warm latency if it did

Done when: the report tabulates, for each of the three reads, its top five call sites with cumulative seconds, the category of each, and the reuse candidate. It records the profiling command and the revision. No product file changes.
