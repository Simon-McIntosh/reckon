When the lead's usage limit resets early, every coordinator session that stopped at the limit stays idle until someone tells it to continue. On 2026-10-21 the lead relayed the news through one session, which messaged the other eleven by hand (reckon-bc at about 14:27 UTC). A budget lift already reaches every session without anyone messaging it. This plan sends a limit reset down the same path: one durable record, folded by every project's producer into its watch stream, drawn once on every session's pane, and delivered by the session host as a notification that starts a turn in an idle session.

Why not detect the reset from the transcripts. A Claude Code transcript records a refusal as quotaLimits with a resetsAt epoch. At 14:23 UTC on 2026-10-21 this repository's coordinator transcript recorded a seven_day refusal with resetsAt 2026-10-22T18:00, and three minutes later the lead reported the limit reset. An operator's early reset leaves that stamp where it was, so the stamp cannot announce it. A scheduled five-hour reset needs no broadcast either: the harness already releases a session it stopped, as the usageLimitNote pairs wrap_up 08:15 and release 08:38 the same day show. The case this plan covers is the early, operator-applied reset, and only an announcement can carry that.

§1 — A limit reset is one durable record

Deliverable. reckon crew budget --announce-reset --reason "<why>" writes one record into a workstation-wide control document, <config-home>/limit-resets.json, written atomically under a monotonically increasing version in the same shape as budget-lifts.json. The store lives in a new module, reckon/crew/limit_reset.py, beside budget_lift.py and reusing its document helpers rather than copying them.

A record carries id, window (five_hour, seven_day or unspecified, from --window), reset_at (now by default, or --at <ISO-8601> for a reset the lead states a time for), announced_by (the user), session (the announcing session when known), reason (required), and scope (global by default, or session:<id> for a rehearsal that reaches one session). A reset is an instant, not a span, so the record has no end and nothing computes one.

Several sessions relaying the same news must write one record, not several: an announcement for a window that already has a global record whose reset_at is within ten minutes of it returns that record and writes nothing. reckon crew budget --list shows the resets of the last 24 hours beside the lifts.

Done when tests/test_a_limit_reset_is_one_record.py, in a temporary config home, finds:

  • an announcement writes one record carrying every field above;
  • an announcement without --reason is refused and writes nothing;
  • --at and --scope session:<id> are recorded as given;
  • a second announcement for the same window five minutes later returns the first record, and one 30 minutes later writes a second;
  • --list names a recent reset and omits one older than 24 hours.

The negative control removes the ten-minute rule, and the second case then writes two records. The test files that exercise crew budget or import reckon/crew/budget_lift.py add no failure against a base arm, both arms from git checkouts under the run's own scratch directory with the four follower variables unset, run in place on the fleet node with pytest -n 8. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. ruff check and ruff format --check add no findings. Write paths: reckon/crew/limit_reset.py (new), reckon/crew_run_commands.py and the new test.

§2 — Every pane draws a limit reset once

Deliverable. A producer sweep, a sibling of lift_watch.sweep in a new module reckon/crew/limit_reset_watch.py, runs on every producer poll, beside _sweep_lift_rows in reckon/crew/recovery_watch.py and under the same guard that only the project's registered producer writes the stream. It does not sit inside the document-change gate that call runs under (if sweep:). A reset announced with a future --at becomes due on the clock, not on a write, so a sweep that runs only when the document changes would never announce it. The sweep therefore keeps the pending resets' due instants in memory, rereads the document only when it changes, and on every poll appends the row for any reset whose instant has passed. For every record whose reset_at has passed and which it has not yet announced, it appends one row built through recovery_watch._watch_transition as a lift row is, with:

  • state limit-reset;
  • the session field empty for a global reset and naming the session for a scoped one, so the existing selection decides which panes see it;
  • the reset's id in a structured field;
  • a detail that reads plainly in the pane: usage limit reset (window five_hour) at 14:26 UTC, announced by <user>: <reason>; sessions stopped at the usage limit can continue their work.

The sweep's memory is a set of announced ids, kept across polls as the lift sweep keeps its own. A producer that has just (re)armed announces only resets whose reset_at lies within the last 60 minutes, so a restart never wakes the fleet with an old reset.

The pane's row policy in reckon/crew/ticker.py gains a branch for limit-reset. It draws the row once per pane through the shared claim the lift rows use, keyed on (pane, reset id, limit-reset), and it has no end row to pair. A pane that follows several projects therefore draws the reset once although every project's producer carries it. The follower module itself does not change.

Done when tests/test_a_limit_reset_reaches_every_pane.py, in a temporary crew and config home with two projects' producers, finds:

  • session A's pane, following both projects, draws the reset line exactly once;
  • session B's pane draws it exactly once;
  • a producer armed two hours after the reset appends no row for it;
  • a reset scoped to session B reaches B's pane and not A's;
  • a reset whose reset_at is still ahead appends no row until it passes, and then appends it on the first poll after it passes with the document unchanged in between.

The negative control removes the claim from the new branch, and session A's pane then draws the line twice. A second control runs the reset sweep only when the document changes, and the scheduled reset is then never announced. The test files importing reckon/crew/ticker.py, reckon/crew/lift_watch.py or reckon/crew/recovery_watch.py, plus the new file, add no failure against a base arm on the same terms as §1. tests/test_every_module_fits_a_worker_window.py passes at head. Write paths: reckon/crew/limit_reset_watch.py (new), reckon/crew/recovery_watch.py, reckon/crew/ticker.py and the new test.

§3 — A session without a pane learns of a reset on its next prompt

Deliverable. The coordinator obligations hook, reckon/hooks/coordinator_obligations.py, names a global reset whose reset_at lies within the last 60 minutes, in the context it already adds to each prompt. That is the horizon a re-armed producer uses, and the rule needs no memory of what the hook showed before. A session whose follower is down still learns of the reset on its next prompt. A session prompted twice inside the hour reads the line twice, which costs one line of context and no new state.

Done when a test in a temporary home finds the hook's added context naming a global reset 20 minutes old, and not naming one 90 minutes old nor a reset scoped to another session. The negative control drops the 60-minute horizon, and the hook then names the 90-minute-old reset too. The tests importing reckon/hooks/coordinator_obligations.py add no failure against a base arm on the same terms as §1. Write paths: reckon/hooks/coordinator_obligations.py and the new test.

  • First real use (followup). At the lead's next early reset the announcement is global, and the record lists the claim directory, which shows one claim per pane, and the command's reach report naming any session without a pane that was messaged by hand.

The listing before the announcement is the control: a claim present then would mean the count measured something other than this announcement. §5 — An announcement names the sessions it cannot reach

Deliverable. reckon crew budget --announce-reset reports its reach. It lists the sessions holding a live follower registration, whose panes will draw the row, and those that hold none, so the announcer messages only the second list. The registrations are the ones the follower already writes and the obligations hook already reads. The report is part of the command's output and of its JSON document, and writes nothing.

Done when a test in a temporary home with one session holding a live follower registration and one holding a stale one finds the report listing the first as reached and the second as not. The negative control treats every registration as live, and the second session is then listed as reached. The tests that exercise crew budget add no failure against a base arm on the same terms as §1. Write paths: reckon/crew/limit_reset.py, reckon/crew_run_commands.py and the new test.
