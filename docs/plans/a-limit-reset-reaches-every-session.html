§1 — A limit reset is one durable record

Deliverable. reckon crew budget --reset --group <group> --used --reason "<why>" records one reset event in the group's record in <crew-home>/budget-resets.json, through budget_reset.mark_used. Today that function changes nothing when no banked flag is available. It will record the event either way, and it will clear the flag only when one is available and the event is global, because an early reset applied to the account is the banked reset being spent. No new module, store or flag is added. --reason, --from, --clock and --session already exist on crew budget for --lift, and their help and validation extend to --reset --used.

An event carries:

  • kind used, as today;
  • id, new and stable, reset-<group>-<UTC stamp>, so a pane's claim can key on it;
  • detected_at, which is now, or the instant --from names (an ISO-8601 time or a duration) for a reset the lead states a time for;
  • clock, from --clock (five_hour or seven_day);
  • by, and reason, which --used now requires;
  • session, from --session. It is absent for a global event. A session-scoped event is a rehearsal that reaches one session and never clears a flag.

The consumed events that observe writes gain an id in the same form. Several sessions relaying the same news must write one event, not several. A global --used for a group and clock that already has a global event within ten minutes returns that event and writes nothing.

One public reader, budget_reset.recent_resets(session=None, now=None, horizon=...), returns the events of both kinds, across every group, that apply to a session (global, or scoped to it) and are no older than the horizon. §2, §3 and crew budget --list all read through it, and --list shows the last 24 hours' events beside the lifts.

Done when tests/test_a_limit_reset_is_one_record.py, in a temporary crew home, finds:

  • --used on a group with no flag writes one event carrying every field above;
  • with a flag available, a global --used clears it and records the event, and a session-scoped one records the event and leaves the flag;
  • --used without --reason is refused and writes nothing;
  • --from and --session are recorded as given;
  • a second global --used for the same group and clock five minutes later returns the first event, and one 30 minutes later writes a second;
  • recent_resets returns a global event and one scoped to the asking session, omits one scoped to another session and one older than the horizon, and returns a consumed event that observe wrote;
  • --list names an event from the last 24 hours and omits an older one.

tests/test_codex_banked_reset.py, which covers the flag, passes unchanged. The negative control removes the ten-minute rule, and the coalescing case then writes two events. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. ruff check and ruff format --check add no findings. §2 — Every pane draws a limit reset once

Deliverable. reckon/crew/lift_watch.py, which already folds lifts into each project's stream, gains the reset row family as a second entry point, sweep_resets(project, seen=None, now=None, ...). It shares the module's row builder, which goes through recovery_watch._watch_transition, and its _append_rows. It is a separate entry because it runs on a different trigger with a different memory. sweep runs on the poll's change gate and remembers the lifts in force. sweep_resets runs on the clock-driven block and remembers the event ids it has announced. An event stated with a future --from, or written to a store outside the gate's fingerprint, becomes due with no file the gate reads moving.

Each pass reads budget_reset.recent_resets with a 60-minute horizon. For every event whose instant has passed and whose id it has not yet announced, it appends one row:

  • state limit-reset;
  • the session field empty for a global event and naming the session for a scoped one, so the existing selection decides which panes see it;
  • the event id in the field a lift row carries its lift id in, so the pane's claim path is reached;
  • a detail that reads plainly in the pane: usage limit reset (claude-sub, seven_day) at 14:26 UTC, announced by <user>: <reason>; sessions stopped at the usage limit can continue their work. A consumed event reads detected from the window readings in place of the announcer.

The 60-minute horizon also bounds a producer that has just (re)armed, so a restart never wakes the fleet with an old reset. The call, _sweep_reset_rows in reckon/crew/recovery_watch.py, sits in the block guarded by WATCHER_SWEEP_INTERVAL_SECONDS, beside the three sweeps already there. It uses the guard _sweep_lift_rows uses, which lets only the project's registered producer write the stream, and it is best-effort like its neighbours. An event therefore reaches every stream within about 30 seconds. The lift family is not moved.

In reckon/crew/ticker.py, limit-reset joins LIFT_STATES, which routes it to _feed_lift. There it gets a case of its own, beside the grant and end cases. Today _feed_lift recognises only lift-granted and lift-ended exactly, and any other state falls to the baseline in-force path. That path drops a row whose group the pane has already drawn (if group and group in self._lift_groups), and it adds the group to that memory when it draws. The reset case takes the shared claim on pane, event id and limit-reset, and on a claim it appends the row. It neither reads nor changes _lift_groups, so a reset for a group with a lift in force is drawn, and the lift family's memory is left as the lift rows set it. The state also joins PANE_STATES under the existing word working, as lift-granted and lift-in-force do. The pane speaks seven words by design (tests/test_the_pane_speaks_seven_words.py, tests/test_ticker_row_is_one_transition.py), and a distinction stays in the event's own facts: the stage cell reads limit and the detail says usage limit reset. No word or hue is added. A reset has no end row to pair. take_lift_claim treats any transition other than in-force and ended as a plain exclusive create, so the follower module does not change. A pane that follows several projects draws the reset once, although every project's producer carries it. The renderer reads LIFT_STATES a third time, to set a row's stage cell to LIFT_STAGE (lift). A reset row's stage reads a word of its own, limit, so the row reads limit claude-sub reset rather than claiming to be a lift. The lift rows' stage is unchanged. The tests that read LIFT_STATES (tests/test_a_standing_lift_survives_a_follower_reload.py and tests/test_a_released_run_row_is_never_blank.py) pass unchanged, as do tests/test_follower_names_a_lift.py, which pins the lift stage word, and the two vocabulary tests named above.

Interface. §1 and §2 add budget_reset.recent_resets, lift_watch.sweep_resets, the state limit-reset and the stage word limit. The pane's seven state words are unchanged. They retire nothing, because the reset family runs beside the lift family rather than replacing any part of it. In exchange they add no module, no store, no command and no MCP view. The only options they touch are four existing crew budget options whose scope widens from --lift to --reset --used.
