§1 — One word for two situations with opposite remedies

The follower marks a run stalled when its stream has been quiet for the stall window, which is DEFAULT_WATCH_STALL_WINDOW in reckon/crew/node.py, fifteen minutes. Four coordinators reported on 2026-09-22 that the word covers a dead worker, which needs a resume, and a live worker in a long quiet step, which needs nothing. Each had to check the process and the stream by hand to tell them apart.

  • A live worker read as stalled. imas-efit-e3's run r-20260922T140247463532-rail-env-remaining-eighteen was flagged after 2,759 seconds of quiet while compiling under srun, then completed normally after 2h28m. nova-a9 saw the same on codex workers waiting on scheduler jobs inside their turn.
  • A dead worker read as nothing, then as stalled. nova-37's review died at 21:21:31 and surfaced as stalled only at 21:36. nova-37 found it at 21:28 by checking the pid. The process is observable at once. The stream silence takes fifteen minutes to become a fact.
  • A resume offer while the worker lives. nova-37 received a row reading ready to resume at 20:20:54 while the worker was alive and running its own probe. crew resume correctly refused, but the row read as an instruction.
  • A record the classifier cannot read is silent forever. nova-a9 met six manifests carrying a status word outside complete, blocked and failed. Each classified as unreadable and never emitted a terminal transition.

The stall census in the measurement plan §5 split 118 stall transitions from seven days by what was true at the stall.

So a stall is a dead worker in 97 of 118 cases, and reporting the death at once is where the value is. The session that wrote this plan met it twice in one night: two review workers died mid-thinking in the read-only sandbox at 22:50 and 23:20, and each surfaced as stalled fifteen minutes later. Live stalls are rare, but 9 of 12 finished without help, which is the condition §6 names. The census also found that r-20260922T140247463532-rail-env-remaining-eighteen completed after a resume, not without one, so that example stands only for the fifteen-minute false alarm.

imas-ambix-f6 also recorded the other side: past about twenty-two concurrent workers the lane degrades without any refusal, and three reviews stalled at almost exactly 900 seconds with no error record. The silence detector caught every one of them. So stream silence stays a signal. What changes is that the row says whether the process is alive, and a dead process is reported when it dies. The stall census in the measurement plan §5 supplies the seven-day split. How a worker's exit is recorded is owned by a-review-dies-where-nobody-is-looking. This plan owns only what the follower emits.

§2 — A worker's death is a row within one poll landed

Terms shared by §2 to §8

Non-terminal means the manifest's status is not in TERMINAL_MANIFEST_STATUSES in reckon/crew/reports.py (complete, blocked, failed), or no manifest exists. Recognised non-terminal means the status is in MANIFEST_STATUSES but not terminal, for example in-progress or waiting. Process gone means the pointer's recorded worker pid is not alive by the check record_process_alive in reckon/crew/runs.py performs, called at snapshot time. A pointer with no recorded pid is neither alive nor gone, and none of these sections fires for it. Newest stream means the stream file returned by reckon.crew.recovery.newest_stream(run_dir), the helper from worker-death-is-recorded §5, which returns the newest non-empty stream path and its mtime, or None, across stream.jsonl, resume-*.jsonl and lane-change-*.jsonl. §2, §6, §7 and §8 call that helper and wait for it to land. The run's time budget is the pointer's budget_seconds.

Precedence, so exactly one of these rows fires for a run on a given snapshot. With the process gone and a non-terminal manifest, the check runs in this order. If the manifest status is outside MANIFEST_STATUSES, §5 fires. Otherwise, if the newest stream's last record has type result, §8 fires. Otherwise §2 fires.

When the watcher's snapshot finds a non-terminal run whose process is gone and whose newest stream's last record is not a result, emit a transition for it on that snapshot, rather than waiting for the stall window. The row's state is the classifier's reading of what the dead worker left, which on the current main branch is interrupted, from the run phase that worker-death-is-recorded added to reckon/crew/node.py. Its reason names that the process exited. When §3 of a-dispatch-returns-without-its-worker has landed, the reason also carries the exit record's signal_name or exit_code and its last_record_type, which is what separates a kill from a worker's own exit.

Done when tests/test_watch_reports_death_at_once.py builds a live pointer whose pid is a process the test starts and then kills, whose manifest reads status: in-progress, and whose stream's last record is an assistant record. After the kill it runs one watcher snapshot and asserts one transition for that run whose reason says the process exited, with the elapsed quiet time under the stall window. A second case gives the stream a last record of type result and asserts that the reason is §8's and not this one. The negative control is executed and logged: with the new death branch deleted from the head, the first case's snapshot emits nothing for the run. The write paths are reckon/crew/recovery.py and that test.

§6 — A live worker with a running job is not stalled at fifteen minutes

The stall census settled this section's branch: of 12 stalls where the worker process was alive, 9 completed without a resume (§1's table). So the stall window for a run whose process is alive and has a live descendant process extends to the run's time budget, budget_seconds. A run with no live descendant keeps the fifteen-minute window. The census measured whether the worker process was alive, not whether it had a descendant. The descendant condition is a deliberate narrowing chosen here, because a live worker with no running child is the case a stall most often means is hung. A run past its time budget that is alive and quiet is surfaced by a-follower-keeps-your-work-in-view §2's needs-you line rather than by this window.

§7 — A working worker reads working within one poll

The follower's row state for a live run comes from the pointer's stored phase. The reducer in reckon/crew/recovery.py reads state = "dispatched" if phase == "starting" else "working". The stored phase advances only when something calls observe in reckon/crew/dispatch.py, which folds the stream into the pointer. The watcher's snapshot classifies pointers without calling it. So a worker that has been thinking and editing for an hour still renders dispatched, and no dispatched → working transition is ever emitted unless a coordinator happens to run crew observe. Measured in session ship-s20-20260923 on 2026-09-23: five of six runs dispatched at 06:48 CEST still read dispatched at 07:52, while each had written to its stream within the previous forty seconds. The imas-efit coordinator reported the same across nine live nodes in its own wave, and had to check each log by hand to establish that nothing had stalled. The watcher already computes the evidence that settles it, because the stall check beside the reducer reads the stream's age.

Derive the row's phase from the run's streams, not from the stored field. A non-terminal run whose newest stream, across stream.jsonl, resume-*.jsonl and lane-change-*.jsonl, contains at least one record whose type is assistant reads working. A stream's record types are system, assistant, user (which carries tool results) and result, and a worker's first assistant record is the first evidence it is doing work rather than starting. The newest stream is read through the helper that worker-death-is-recorded §5 adds to recovery.py. The watcher emits the dispatched → working transition on the first snapshot that sees such a record. The live MCP view's phase reads the same derivation, so the pane and the tool agree.
