§1 — One word for two situations with opposite remedies

The follower marks a run stalled when its stream has been quiet for the stall window, which is DEFAULT_WATCH_STALL_WINDOW in reckon/crew/node.py, fifteen minutes. Four coordinators reported on 2026-09-22 that the word covers a dead worker, which needs a resume, and a live worker in a long quiet step, which needs nothing. Each had to check the process and the stream by hand to tell them apart.

  • A live worker read as stalled. imas-efit-e3's run r-20260922T140247463532-rail-env-remaining-eighteen was flagged after 2,759 seconds of quiet while compiling under srun, then completed normally after 2h28m. nova-a9 saw the same on codex workers waiting on scheduler jobs inside their turn.
  • A dead worker read as nothing, then as stalled. nova-37's review died at 21:21:31 and surfaced as stalled only at 21:36. nova-37 found it at 21:28 by checking the pid. The process is observable at once. The stream silence takes fifteen minutes to become a fact.
  • A resume offer while the worker lives. nova-37 received a row reading ready to resume at 20:20:54 while the worker was alive and running its own probe. crew resume correctly refused, but the row read as an instruction.
  • A record the classifier cannot read is silent forever. nova-a9 met six manifests carrying a status word outside complete, blocked and failed. Each classified as unreadable and never emitted a terminal transition.

The stall census in the measurement plan §5 split 118 stall transitions from seven days by what was true at the stall.

So a stall is a dead worker in 97 of 118 cases, and reporting the death at once is where the value is. The session that wrote this plan met it twice in one night: two review workers died mid-thinking in the read-only sandbox at 22:50 and 23:20, and each surfaced as stalled fifteen minutes later. Live stalls are rare, but 9 of 12 finished without help, which is the condition §6 names. The census also found that r-20260922T140247463532-rail-env-remaining-eighteen completed after a resume, not without one, so that example stands only for the fifteen-minute false alarm.

imas-ambix-f6 also recorded the other side: past about twenty-two concurrent workers the lane degrades without any refusal, and three reviews stalled at almost exactly 900 seconds with no error record. The silence detector caught every one of them. So stream silence stays a signal. What changes is that the row says whether the process is alive, and a dead process is reported when it dies. The stall census in the measurement plan §5 supplies the seven-day split. How a worker's exit is recorded is owned by a-review-dies-where-nobody-is-looking. This plan owns only what the follower emits.

§2 — A worker's death is a row within one poll

When the watcher's snapshot finds a non-terminal run whose recorded process is gone, emit a transition for it on that snapshot, rather than waiting for the stall window. Liveness is read through record_process_alive, which is already folded into each pointer. The row's state is the classifier's reading of what the dead worker left, and its reason names that the process exited.

Done when tests/test_watch_reports_death_at_once.py builds a live pointer whose pid is a process the test starts and then kills, runs one watcher snapshot after the kill, and asserts a transition for that run whose reason says the process exited, with the elapsed quiet time under the stall window. The negative control is executed and logged: with the base revision the snapshot emits nothing for the run. The write paths are reckon/crew/recovery.py and that test.

§3 — A stalled row says alive or gone

Every row entering stalled carries the process state in its reason, in words: alive, quiet 46m or process gone, quiet 15m. The words carry the distinction without colour.

Done when two rendered stalled rows, one with a live process and one with a dead one, contain alive and process gone respectively, and neither contains the other's word. The write paths are reckon/crew/recovery.py, reckon/crew/ticker.py and tests/test_stalled_row_names_liveness.py.

§4 — A resume offer is not shown while the worker lives

A row that offers a resume, including the sweep's ready to resume, is emitted only when the run's process is gone. While it lives, the same row reads as a wait on the named condition.

Done when a test renders the sweep's ready-to-resume event for a run with a live process and asserts the row does not contain resume, and renders it for a dead process and asserts it does. The write paths are reckon/crew/resumption.py and tests/test_resume_offer_needs_a_dead_process.py.

§5 — An unreadable manifest names the word it could not read

When the classifier reads a manifest whose status word is outside the recognised set, emit a transition into unreadable whose reason quotes the word, as in status "in-progress" is not complete, blocked or failed. Validating the manifest when the worker writes it is owned by crew-runtime-positive-controls. This section only makes the existing case visible.

Done when a test writes a manifest with status: in-progress beside a pointer whose process is gone, runs one snapshot, and asserts one transition into unreadable whose reason contains in-progress. The write paths are reckon/crew/recovery.py and tests/test_unreadable_names_its_word.py.

§6 — A live worker with a running job is not stalled at fifteen minutes

This section waits on the stall census. If the census shows that stalls with a live process mostly completed without a resume, the stall window for a run whose process is alive and has a live descendant process extends to the run's time budget. A run with no live descendant keeps the fifteen-minute window. If the census shows the opposite, record the figure and close the section with no change.

Done when a test holds a live pointer whose worker process has a sleeping child, advances the clock past fifteen minutes, and asserts no stalled transition, then kills the child and asserts the stalled transition on the next snapshot. The write paths are reckon/crew/recovery.py and tests/test_stall_window_respects_a_child.py.

§7 — A working worker reads working within one poll

The follower's row state for a live run comes from the pointer's stored phase. The reducer in reckon/crew/recovery.py reads state = "dispatched" if phase == "starting" else "working". The stored phase advances only when something calls observe in reckon/crew/dispatch.py, which folds the stream into the pointer. The watcher's snapshot classifies pointers without calling it. So a worker that has been thinking and editing for an hour still renders dispatched, and no dispatched → working transition is ever emitted unless a coordinator happens to run crew observe. Measured in session ship-s20-20260923 on 2026-09-23: five of six runs dispatched at 06:48 CEST still read dispatched at 07:52, while each had written to its stream within the previous forty seconds. The imas-efit coordinator reported the same across nine live nodes in its own wave, and had to check each log by hand to establish that nothing had stalled. The watcher already computes the evidence that settles it, because the stall check beside the reducer reads the stream's age.

Derive the row's phase from the run's streams, not from the stored field. A non-terminal run whose newest stream, across stream.jsonl, resume-*.jsonl and lane-change-*.jsonl, holds an assistant or tool record reads working. The newest stream is read through the helper that worker-death-is-recorded §5 adds to recovery.py. The watcher emits the dispatched → working transition on the first snapshot that sees such a record. The live MCP view's phase reads the same derivation, so the pane and the tool agree.

Done when tests/test_working_reads_working_at_once.py writes a live pointer whose stored phase is starting and whose process is a live process the test starts. It then appends one assistant record to the run's stream, runs one watcher snapshot, and asserts a transition into working for that run. A second case puts the record only in resume-1.jsonl and asserts the same. A third asserts that crew(view="live") reports phase as working for the same pointer. The negative control is executed and logged: with the base revision's stored-phase reducer the first snapshot emits no transition and the test fails. The write paths are reckon/crew/recovery.py, reckon/mcp_views.py and that test.

§8 — A turn that ended without a manifest is a row at once

A print-mode worker whose turn ends has finished, whether or not it delivered. Its stream's last record is then a result record, and the process exits. Today that case is silent until the stall window: measured on the same session, the prior-art scout r-20260923T044719237479-follower-repair-reuse-map ended its turn at 06:50:30 CEST with a result record, a clean end of turn, right after writing Now let me verify the symbols with grep. It had written no report and its manifest still read in-progress. The row reached the pane at 07:05:49 as stalled: stream quiet for 901s, fifteen minutes late and naming the wrong cause. A resume at 07:06 recovered it.

When the watcher's snapshot finds a non-terminal run whose newest stream ends in a result record and whose manifest is not terminal, emit a transition on that snapshot. Its reason says the turn ended without delivering, as in turn ended, manifest in-progress, and its action is reckon crew resume. This is distinct from §2, where the process dies without a result record, and the two reasons must differ, because the remedies differ: a resume continues a turn that ended, while a death needs its cause read first.

Done when tests/test_ended_turn_is_a_row_at_once.py writes a live pointer, a manifest reading status: in-progress and a stream whose last record is a result record, with no live process. One watcher snapshot then emits a transition whose reason contains turn ended, with the quiet time under the stall window. A second case, whose stream's last record is an assistant thinking record with no result, emits the §2 death reason rather than this one. The negative control is executed and logged: at the base revision the first snapshot emits nothing for the run. The write paths are reckon/crew/recovery.py and that test.
