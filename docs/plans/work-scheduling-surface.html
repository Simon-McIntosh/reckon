§1 — The problem, measured on one project in one day

On 2026-09-18 the nova roadmap ranked cut-cell-current-attribution first in ready_now: it heads the sprint's critical path (45 worker-hours into uniform-cell-clip-and-coupling) and unlocks two further plans. It had no worker for the whole of sprint S19. In the same hours twelve runs were live, every one of them closing a plan already at 85 to 99 percent implementation, most of them record repairs raised by reviews. Six nova sprints were marked active, so the derived active sprint was S10, a one-plan sprint opened in August. Two S19 plans read 0 percent implementation after five landed nodes each, because nothing in the landing path advances a plan's impl. Reckon's own project shows the same shape: two active sprints, and four runs merged into main whose plans do not know it.

The ranking exists. Nothing downstream of it has teeth: dispatch never reads the critical path, nothing measures how many workers a path has, a record-repair followup competes equally with a capability followup for width, and a promotion does not require the plan to move. This plan gives the ranking consequences at each of those four points and puts the result on one screen per workstation.

§2 — One pushed sprint

The sprint status enum gains open: work remains and the sprint is not the one being pushed. active is reserved for exactly one sprint per project and means pushed. A new edit_plan op on the project resource, push with a sprint id, sets that sprint active and demotes the previously active sprint to open in the same write, so the invariant cannot be broken by a two-step edit. The roadmap derives active_sprint_id from the unique active row and reports open sprints in their own bucket. _derived_sprint_state stops returning active from member progress and returns in-progress, so an open sprint with shipped members no longer reads as state drift. The audit promotes multiple-active-sprints from warn to error and adds pushed-sprint-has-no-ready-work (warn) so a push onto a drained sprint is visible. Nothing moves between sprints: nova's S10, S12, S15, S16 and S18 keep every member and become open; reckon's S16 and S18 likewise once the lead names the push.

Done when: the enum, the derived state, the push op, the roadmap bucket, the audit codes and the reckon-sprint skill text all carry open; a test shows a push demoting the prior active sprint in one write; a test shows two active sprints failing the audit at error severity; nova's five sprints accept open through edit_plan.

§3 — Critical-path coverage

The roadmap emits coverage: for each open path, the plans on it, the live runs on those plans (from the project's live pointers), and whether the path's head is dispatchable. A finding critical-path-uncovered fires when the pushed sprint's critical path has zero live runs while its head plan is dispatchable; it is a warning whenever the project's live width is zero and an error when width is above zero, because then the lane is busy and the path is starved by choice. crew(view="flight") and the dispatch summary print coverage per open path. The follower's fleet counter gains a cp:N cell, delivered as its own node to the session that holds ticker.py.

The refusal is deliberately not in this plan's first landing. Five coordinators dispatch on this workstation, and a fence that refuses an off-path dispatch would bind all of them on one project's evidence; a coordinator mid-recovery would reach for the override reflexively and the finding would then measure nothing. The decision below locks the sequence: land the figure and the finding, read them across every mounted project for one day, then decide whether crew dispatch refuses off-path while the path is uncovered (with --off-path REASON recorded on the ledger row) or keeps reporting only.

§4 — Followup classes

A followup carries kind in {capability, measurement, record, repair}. Capability work changes what the code can do; measurement produces a receipt that decides something; record repairs correct prose, captions, receipts and anchors; repair fixes a defect a review or a gate found. The ready ordering ranks capability and measurement above record and repair within a plan; the drain ledger and the follower's counters report the four kinds separately; reckon-ship gains the rule that record repairs occupy at most one slot per plan while capability or measurement work on the pushed sprint is dispatchable. Existing followups are classified once by a migration that infers the kind from the title and body words (restore, correct, caption, receipt, anchor and the like read as record; measure, census, receipt-of read as measurement) and the audit reports unclassified followups at info severity so a project can finish the classification by hand.

§5 — Implementation must move when work lands

crew complete on an implement or test run with a passing gate compares the plan's impl at promotion against the value recorded on the run at dispatch. If unchanged, the promotion is refused with the two figures and the plan's remaining sections, unless --no-impl-change REASON is passed; the reason lands on the ledger row. The dispatch record therefore stores plan_impl_at_dispatch. Review, investigate and cleanup runs are exempt, as is a run whose failure classification is a negative result or correct refusal. This converts a coordinator habit into a check: two nova plans sat at 0 percent with five landed nodes each, and four reckon runs are merged with their plans unaware.

§6 — Portfolio flight

reckon flight --portfolio and crew(view="portfolio") list every mounted project on one screen: pushed sprint and its theme, critical path and its length, coverage of that path, live width by role, unreconciled runs, lane headroom and the newest lane reading. Rows sort by the pushed sprint's uncovered critical hours descending, so the project whose longest path is most starved reads first. The view reuses the roadmap and flight readers and adds no state file.

Landed 2026-09-18. reckon flight --project '*' composes the portfolio from every registered mount: one row per project carrying the pushed sprint and its theme, the critical path with its elapsed length, that path's coverage, live width by role, the unreconciled run count, and the newest lane reading with its age, sorted by uncovered critical hours descending. Coverage is counted from each project's live pointers whose process is alive and never from transition events, because a working run rewrites its manifest only when it finishes; the roadmap's own coverage field has not landed, so this view derives that figure locally and reuses the roadmap reader for the rest. reckon/mcp_views.py exposes it as portfolio_view with summary, detail and raw depths; naming it as a crew view needs one entry in the view list that reckon/mcp.py holds, and another node held that file. A real-mount read of all thirteen mounted projects answered in 155 s, so this read belongs on a compute partition rather than the login node. No state file is added.

Two surfaces publish active_sprint_id and compute it differently, so the audit reports its own disagreement

read_plan(project, "index").active_sprint_id and roadmap's field of the same name are computed two different ways, and the audit's active-sprint-mismatch finding is the artefact of that disagreement rather than a defect in any project's state. Reported from another project and reproduced here.

_derive_default_sprint_focus at reckon/project_state.py:1210 returns "the first sprint in composed order with unfinished plan work" and never consults the sprint's own status, so the record the push op writes is ignored and a closed sprint can be elected over the pushed one. _audit_sprint_findings at reckon/mcp.py:1436 then compares that election against status and emits the mismatch — a surface reporting the difference between two of its own readings as though it were news about the project.

Two causes, each independently sufficient, and one project demonstrates each. The reporting project elects a shipped sprint because one member slug does not resolve: an unresolved member has no status, str(status or "") is the empty string at line 1215, and the empty string is not in COMPLETED_STATUSES, so a dangling reference counts as unfinished work and silently pins the focus to whatever sprint holds it. Reckon has no dangling members and still misreports: active_sprint_id reads S12, whose status is done, while S16 and S18 both carry active. So the missing status check alone is enough, and the dangling-slug path is enough on its own elsewhere.

Measure. One derivation answers active_sprint_id for every reader, and it consults the status the push op records rather than inferring a focus from item completion. An unresolvable member is reported as a broken reference rather than counted as unfinished work, so a dangling slug surfaces as the wiring fault it is instead of silently electing a sprint. Falsify both independently: a project whose only active sprint is not first in composed order must elect that sprint, and a project with a dangling member in a closed sprint must report the dangling reference and still elect the active one.

Why it belongs here rather than in the roadmap plan: this plan owns the one-pushed-sprint invariant and the push op that maintains it, and the defect is that the invariant's own record is not read. The reporting project correctly declined to repair it from their side — their sprint resources are right, one active and pushed, and no change they can make clears the warning.
