§1 — Why: file claims serialised S27 behind single modules

Every worker runs in its own detached worktree, and crew merge builds the landing with git merge-tree, refusing only the paths that really conflict (reckon/crew/merge.py, refusing_conflicts). Yet dispatch, admission, widening and promotion all refuse a second claim on the same file unless that file is listed in docs/state/<project>/shared-write-paths.json. Every one of those checks reads the list through runs._shared_write_paths (called from dispatch_claims.py twice, promotion_scope.py twice, queue_admission.py twice and queue_edit.py), so a file is exclusive unless someone has thought to declare it shared.

On 7 and 8 November that default held S27's work in series behind single modules, while each queued node edited a different function:

  • reckon/crew/queue_admission.py held five queued sections behind one delivered-but-unlanded run, and later four more behind admission-loop §32;
  • reckon/crew/obligations.py held the monitor plan's §13 follow-up behind an unrelated §8 run, and §15 behind §13;
  • reckon/crew/dispatch.py and promotion.py held crew-state §2 behind six queued peer runs, which is why it was parked on 6 November;
  • reckon/crew/resumption.py held the monitor plan's §14 behind an unrelated resume change;
  • a run that claimed a plan's whole docs/evidence/fragments/<plan> directory blocked every other node of that plan, and §32 had to be dispatched on its brief alone to get past it.

As immediate relief the lead had eleven crew modules added to the shared list on 8 November (commit 5cf29445c8). This plan makes that the rule rather than a hand-maintained exception: a source or test file is shared unless it is declared exclusive, and exclusivity is kept only for paths a merge cannot reconcile.

§2 — A source or test file is shared unless it is declared exclusive

Deliverable. The project's write-sharing declaration gains a default. A file path under a declared shared root (for reckon, reckon/, tests/, scripts/ and skills/) admits concurrent claims unless it matches a declared exclusive pattern. Exclusive by default are the paths a textual merge cannot reconcile or that one writer owns: docs/plans/*.html, cumulative evidence records under docs/evidence/archive/, generated state under docs/state/, figure topic directories under docs/figures/, and pyproject.toml and uv.lock. A directory claim stays exclusive, as it is today, and a claim on a node's own evidence fragment file never conflicts with a claim on another fragment file. The existing explicit paths list keeps working, so a project that declares no roots behaves exactly as now.

The answer is computed in one place, the function every claim check already calls, so dispatch, admission, queue edit, widen and promotion agree. A refusal that remains names the exclusive pattern that caused it.

Done when a new tests/test_a_source_file_is_shared_by_default.py shows, with a temporary repository and crew home:

  • two dispatches whose write paths name the same file under a shared root both succeed;
  • a queued request whose path another live run claims is admitted, not held-on-claim, when the path is under a shared root;
  • the same two claims on docs/plans/x.html are refused, naming the exclusive pattern;
  • a directory claim is still refused against any path inside it;
  • a project whose declaration has no shared roots refuses exactly as before.

Negative control: the same test at the base revision refuses the first two cases. The test files importing reckon.crew.runs, reckon.crew.dispatch_claims, reckon.crew.promotion_scope, reckon.crew.queue_admission or reckon.crew.queue_edit add no failure against base, run one arm at a time with at most -n 4; a test that asserts the old exclusive default for a shared-root path is updated to the new contract and named in the manifest. Ruff adds no findings on the staged paths. Write paths: reckon/crew/runs.py, the four modules that call it (dispatch_claims.py, promotion_scope.py, queue_admission.py and queue_edit.py; dispatch.py and promotion.py only re-export the symbol), docs/state/reckon/shared-write-paths.json, and the new test.

§3 — A landing that conflicts sends its run back for a merge repair

Deliverable. Once two runs may edit one file, the second to land can meet a real conflict. Today crew merge refuses such a head; the lander (queue_landing._merge_conflicts, near reckon/crew/queue_landing.py:1554) records an admission_landing refusal naming the conflicted paths and appends an obligation row, but no repair round opens and no outcome names the conflict, so the run sits delivered and unlanded until a coordinator acts. After this section, a landing refused because refusing_conflicts named paths, whether by crew complete --land or by the admit service's lander, records a merge-conflict outcome on the run naming the conflicted paths and the main revision it met, and opens a repair round through recovery_repair_dispatch. The round's advice tells the worker to merge the current primary into its worktree, resolve the named paths keeping both changes' intent, re-run its own gate, and deliver again. A landing never discards either side and never lands conflict markers.

Done when a new tests/test_a_conflicting_landing_is_repaired.py shows, with a temporary repository and a bare remote:

  • two runs that edit different functions of one file both land, the second merging cleanly behind the first;
  • two runs that edit the same lines: the first lands, and the second is refused with a merge-conflict outcome naming the file and the main revision, and has a repair round opened whose advice names the file;
  • after that repair delivers a head that merges main, the second lands;
  • no landing leaves conflict markers in the tree.

Negative control: at the base revision the second, conflicting run is refused with no repair round opened. The test files importing reckon.crew.merge, reckon.crew.queue_landing or reckon.crew_run_commands add no failure against base, one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Write paths: reckon/crew/merge.py, reckon/crew/queue_landing.py, reckon/crew_run_commands.py, reckon/crew/recovery_repair_dispatch.py and the new test.

§5 — A fragments-directory claim never blocks a sibling node

Why. On 8 November run r-20261108T052434073237-oversized-node-reserved-lane-reproduced claimed the whole docs/evidence/fragments/work-is-never-stuck-behind-the-admission-loop directory, so every other node of that plan was refused at dispatch, and admission-loop §32 had to be dispatched on its brief alone. §2 keeps directory claims exclusive, so this blocker survives §2.

Deliverable. A claim on a plan's evidence-fragments directory is narrowed to the fragment files a node names or writes, and dispatch's default fragment path for a node is its own file, docs/evidence/fragments/<plan>/<node>.html. Two nodes of one plan never conflict on the fragments directory; two claims on the same fragment file still do.

Done when a new tests/test_a_fragment_claim_never_blocks_a_sibling.py shows with a temporary repository and crew home: a live run whose claim names a plan's fragments directory does not refuse a second node of that plan whose fragment is a different file; two nodes naming the same fragment file are refused. Negative control: at the base revision the first case is refused. The test files importing reckon.crew.dispatch_claims or reckon.crew.runs add no failure against base, one arm at a time with at most -n 4; ruff adds no findings on the staged paths.
