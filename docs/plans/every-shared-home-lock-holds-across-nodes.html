§1 — Why: most shared-home locks exclude only their own node

fcntl.flock is granted by the local kernel. On the GPFS home, a holder on one node therefore does not block a holder on another. a-plan-state-lock-holds-on-every-node measured this on 2026-11-13. It added reckon.node_exclusive_lock.exclusive_lock, whose POSIX record lock the file server holds, and measured that lock excluding across nodes. It moved only the plan-state locks onto it.

The same plan's census, every flock is accounted for, read every lock-taking flock under reckon/ at 7d8ca3f. Of 43 sites, 10 are node-local by design and 13 have their cross-node case decided by a lease. The other 20 guard shared state that a process on another node can reach, and nothing else decides that case. Among them:

  • the per-run pointer lock that keeps a resume and a promotion from interleaving;
  • the admit lock that launches a queued run once;
  • the landing-pass lock;
  • the ledger write lock;
  • the placement reservation.

Today the fleet node and the login node both run crew commands, and the admit service can run on either. That is not hypothetical. From about 13:10Z on 2026-11-13 until job 1291586 was cancelled at 07:42Z on 2026-11-14, a station and a local-lane admit service ran on both 98dci4-clu-2023 and 98dci4-clu-2001, and the two split one promotion queue. Two coordinator sessions had a crew complete --wait on clu-2001 refused because the run was "already being promoted by host 98dci4-clu-2023" (reported by the reckon monitor session).

The coordinator re-read the tree at 03b18d9 on 2026-11-14 and found 45 sites, two of them new:

  • review_records._index_lock, added the day before, guards the review store index. Its docstring says the lock "serialises against every other node's writer", which the census disproved for flock. This makes 21 shared-home sites.
  • watch_unit._seat_is_held probes a producer seat, which the host lease decides.

So new bare flock calls arrive faster than a census can follow them, and the first deliverable is a guard rather than a migration.

The coordinator also prototyped a migration on 2026-11-14. Its patch and logs are under ~/.cache/reckon-lock-proto/. Two measurements bear on the endpoints:

  • A record lock is dropped when its process closes any descriptor for the file. In probe-98dci4-clu-2001.log, a second process sees the lock held inside exclusive_lock. After the holder opened and closed the same file once more inside the block, the second process sees it free. A lock that guards a file the body also opens (the picker's holds log locks the very file it appends to) is therefore released mid-body. So is a lock whose file anything else in the process opens: a probe, a gc pass, a reader on another thread.
  • The cost is negligible. One exclusive_lock cycle on the GPFS home took a median of 0.10 ms (p95 0.11 ms), against 0.02 ms for flock alone, over 200 cycles.

§2 — A guard refuses any bare flock that is neither judged nor pending

Deliverable. A repository test, tests/test_every_shared_home_lock_holds_across_nodes.py, holds two tables. Each table entry keys one lock-taking flock call under reckon/ by file and qualified enclosing function, never by line.

  • The judged table records why a site is safe on one node: the lock file lives on one host, or a named lease decides the foreign-host case.
  • The pending table names the 21 shared-home sites from §1 that have not yet moved.

The test fails in three cases:

  • a site that is in neither table;
  • a table entry with no such call left;
  • an entry in both tables.

Its failure message names the cross-node lock as the remedy.

Done when.

  • The test passes on the delivered head.
  • The judged table carries every site the census and §1 found safe (24 calls at 03b18d9), keyed as they stand at the head.
  • The pending table carries the 21 sites.
  • Three negative controls are logged in the run directory, each with its failing output:
    • a scratch module under a temporary reckon/ tree with one bare flock is reported by file and function;
    • deleting one judged entry fails the test, naming that site;
    • adding an entry for a function with no flock fails the test, naming the stale entry.
  • The guard is declared among the project's census tests, so it runs inside the scoped gate command of every node that writes product source, not only in a full-suite run. The manifest shows a scoped gate command composed for a product-source node that carries the guard.
  • The new file passes ruff check and ruff format --check.

Write paths. tests/test_every_shared_home_lock_holds_across_nodes.py and docs/state/reckon/flight.yaml.

§3 — Run, queue, landing and ledger locks exclude across nodes

Deliverable. These seven locks take the cross-node lock:

  • in reckon/crew/runs.py: _pointer_lock, queue_dispatch and update_watch_registration;
  • reckon/ledger.py _ledger_write_lock;
  • reckon/crew/queue_landing.py land_once;
  • reckon/crew/admission/service.py _admit_lock;
  • reckon/crew/placement.py _reservation_hold_lock.

Each keeps the answer its callers get when the lock is held. A non-blocking pointer take still raises PointerLockHeldError, and a held landing pass still returns its busy result. Each site's row leaves the guard's pending table.

Done when.

  • The guard passes with these seven rows removed from pending.
  • For the pointer lock and the landing-pass lock, a test runs a holder in a second process that takes only the POSIX record lock on the lock file, not flock. The non-blocking take reports the lock held: the refusal for the pointer lock, the busy result for the landing pass. This is the half that excludes across nodes, measured in §1's predecessor and again in §6. The negative control is the same test run against the base revision, where the site takes only flock: it must fail, because the take sees the record-lock holder as free. The failing run is logged.
  • Each of the seven lock files is opened in reckon/ only through exclusive_lock. The manifest lists every other reference to each path (gc and pruning included) and states why none opens the file.
  • The focused tests that import the changed modules add no failures against the stated base.

Write paths. reckon/crew/runs.py, reckon/ledger.py, reckon/crew/queue_landing.py, reckon/crew/admission/service.py, reckon/crew/placement.py, the guard test file, and new test files under tests/.

§5 — Lane, budget and picker locks exclude across nodes

Deliverable. These five locks take the cross-node lock:

  • reckon/crew/budget_reset.py _locked;
  • reckon/crew/model_catalogue.py _refresh_lock;
  • reckon/crew/paid_lanes.py refresh_reserved_window and publish_document;
  • reckon/crew/picker/outcomes.py record_picker_hold.

Each keeps its held answer. A catalogue refresh that cannot take the lock still reads the snapshot on disk instead of fetching. The picker's holds log stops locking the file it appends to, because §1 measured that closing any descriptor for a record-locked file drops the lock. Its lock is a file that nothing else opens. Each site's row leaves the guard's pending table.

Done when.

  • The guard passes with these five rows removed from pending.
  • A test runs a holder in a second process that takes only the POSIX record lock on the picker's lock file. It shows that a hold recorded meanwhile does not reach the log until the holder releases, and then appears as one whole line.
  • A test runs a holder in a second process that takes only the POSIX record lock on the catalogue's lock file, and shows a refresh reading the snapshot rather than fetching.
  • The negative control for both tests is the same test run against the base revision. Each must fail there, because nothing at the base waits on a record lock: the hold is written while the holder holds, and the refresh fetches. Both failing runs are logged.
  • Each lock file is opened in reckon/ only through exclusive_lock, evidenced as in §3.
  • The focused tests that import the changed modules add no failures against the stated base.

Write paths. The five modules named above, the guard test file, and new test files under tests/.
