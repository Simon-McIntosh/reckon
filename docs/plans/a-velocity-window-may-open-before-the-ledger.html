§1 — A revision without the ledger reads as one with no runs

At main 3e4736687, reckon crew velocity --project reckon --since 2026-08-01 exits 1. The error is CalledProcessError from git show 69fb3c1e5…:docs/state/reckon/crew.json, raised inside recover_ledger_clocks at reckon/velocity.py:1191. The window's base commit is 69fb3c1e5, from 2026-07-30. docs/state/reckon/crew.json was first committed in af650745d on 2026-08-12, so the base has no such file. recover_ledger_clocks reads the ledger at the base only to learn which runs already existed. When the path is absent, the whole view aborts, although the true answer is that no runs existed.

The read at the head has the same defect. _read_ledger at reckon/velocity.py:708 looks up the blob with _blob_sha, which returns None for an absent path. It then calls git show unconditionally at line 719. So a window whose head predates 2026-08-12 fails in the same way. Every window will fail once the-ledger-is-one-file-per-run §4 deletes crew.json, because no head will have it from then on. That is why this plan blocks that section. _read_run_rows already copes with an absent runs/ directory, because git ls-tree prints nothing for one.

Remedy. Make _read_ledger (reckon/velocity.py:708) the one reader of the committed ledger at a revision. A revision whose tree has no crew.json then reads as a ledger with no runs:

  • _read_ledger reads the ledger's bytes through the module's existing batched reader read_blobs (reckon/velocity.py:395), which maps a missing object to None. A None means there is no ledger at that revision, and the function returns no records. _read_run_rows still supplies the per-run files.
  • recover_ledger_clocks stops parsing the ledger itself: the else-branch parse at reckon/velocity.py:1191 to 1192 goes. Keep the path assignment at line 1182, because the same function's git log search for a run's first appearance still uses it at line 1221. It takes the runs present at the base from _read_ledger(repo, base, project["project"], None), so a base with no ledger has no runs present and every candidate is searched.
  • For an absent ledger, the digest the snapshot reports is None, not the digest of an empty document. That follows the repository's convention that an unknown reading is None rather than a value that looks real (reckon/crew/window_reading.py:28). A reader can then tell a revision with no ledger from one whose ledger is empty.

Do not catch a failed git call. read_blobs reports a missing object as None but still raises when the cat-file process itself fails, and that failure must keep raising. No new public name is added. Once both reads go through _read_ledger, the section of the-ledger-is-one-file-per-run that deletes crew.json has one function to retire.

§2 — A long window's ledger search stays inside its git bound

§1's post-merge check did not exit 0. At main 440ce55a6, reckon crew velocity --project reckon --since 2026-08-01 gets past the base read that used to crash. It then fails with subprocess.TimeoutExpired after 180 seconds in the search recover_ledger_clocks runs at reckon/velocity.py:1217. A window whose base already has a ledger fails in the same way: --since 2026-09-01 at 534f6536e ended with the same timeout, with EXIT=1 after 410 seconds. The timeout is therefore older than §1: the crash hid it for windows that open before the ledger, and it already broke long windows. Both logs are under ~/.cache/reckon-velocity-window-check/.

The search is one git log --first-parent -p --unified=0 -G <every missing run id> origin..head -- crew.json runs/. run_git (reckon/velocity.py:149) bounds every git call at 180 seconds. The search has to generate the patch of every commit that touched crew.json in the window. Until per-run records landed, nearly every promotion rewrote that file at tens of megabytes, so a window reaching back into August or September asks git for hundreds of such patches.

Remedy. Most of the runs in these windows can only be placed by the crew.json search. Per-run files first appear on 2026-09-25 (e080ed967). The content review measured the runs without promotion_commits that also have no per-run file: 1,803 in the 2026-08-01 window and 1,446 in the 2026-09-01 window. So the search itself must stay inside the bound. Two changes, both in recover_ledger_clocks and its cache, with no public name added:

  • Search the ledger in slices. List the first-parent commits in origin..head that touch the ledger paths, with a plain path-limited git log --first-parent --format=%H that generates no patch. Run the existing -G search over consecutive slices of them, oldest first. Each slice drops the ids already placed from the expression.
    • Hold the slice size, a count of ledger-touching commits, in a module-level private constant, _LEDGER_SEARCH_SLICE_COMMITS. The search reads it at call time, so a test can set it to one with monkeypatch.setattr. Choose its value so that one slice's search finishes well inside run_git's 180-second bound on this checkout, and record the value and the measured worst slice time in the manifest.
    • After each slice, store the cache with head set to the slice's last commit. The cache's existing walked resume then carries a long window across slices.
    • A read interrupted after some slices resumes where it stopped. A repeated read of a window already walked runs no search at all.
  • Place runs with their own record file first. A run whose per-run file, docs/state/<project>/runs/<run_id>.json, is added in the range is placed at the adding commit. A path-limited git log --first-parent --diff-filter=A --name-only lists those additions without generating a patch. It records the same appearance fields the search records, but with its own source, first_primary_record_file_addition_upper_bound. promotion_clock_sources (reckon/velocity.py:2149) then reports the two mechanisms apart. Like the search's value, it is not promote_commit, so dispatch_to_explicit_promotion_seconds still excludes it. Only the ids left after that reach the sliced search.

Do not raise the timeout. If a single slice of one commit still exceeds the bound, report blocked with that commit and its measured time.
