§1 — Why: refusals that guard a form

A third of all dispatch and promotion attempts in the fortnight to 26 September were refused — 658 refusals against 1,264 successes, each costing 12 to 15 coordinator responses to recover (crew pattern review §5). The surveyed coordinators name five refusals that guard a form rather than the work (§3): the goal lint refusing a semicolon, "and", "then" or a quoted <path> inside one deliverable (s21 lost about eight dispatches); the watcher-required refusal after a follower's lifetime ends while runs are in flight; the impl-must-move refusal on corrective nodes, waived "about every other time" (s23); --outcome demanded on review runs; and verify-gate refusing a checkout two ledger commits past the merge. The review itself was refused for the done-when "… and the counts of TODO-FIXME, xfail and skip markers …", which named a marker to count. This plan narrows exactly these five; every other refusal is untouched here, and making each refusal name its discharge stays with an-orchestrator-can-discharge-a-refusal, which may proceed concurrently because the two plans change different conditions.

§2 — The contract lint refuses placeholders and two deliverables, not punctuation

Deliverable. In the goal and the done-when, the lint refuses an unresolved template placeholder: an angle-bracket token such as <node> that appears outside a quoted string and outside a code span, or a goal consisting only of a placeholder word. In the goal only, it refuses two deliverables: two clauses each with its own action verb and its own object ("write the census and update the plan"). It no longer refuses a semicolon, "and" or "then" that joins parts of one deliverable, one verb over several objects ("compare the base and the head"), or any word — "TODO" included — inside a done-when or inside quoted text; a quoted <path> is accepted.

Done when a table-driven test holds these pinned fixtures and passes: accepted — a single-deliverable goal with a semicolon, one with "and then", a goal quoting <path>, and this review's refused done-when verbatim; refused — the two brief defects s22 reported, copied from s22's dispatch record into the table as strings, and one authored two-deliverable goal. The refused side has three rows.

Evidence inputs (s22-coord's dispatch record, relayed 2026-09-26). Neither of s22's two defects was a goal-text split. Both are other validate_node properties, so their rows carry the role or budget the refusal depended on and must still refuse after the lint is narrowed:

  • Node window-plan-currency-audit, --role investigate. Its done-when ended with the sentence "Read only: change no file outside the reports directory, and run no test suite beyond targeted pytest selections needed to confirm a landed verdict." It was refused with "fully-specified: done-when matched execution measure 'pytest selections', but role 'investigate' declares execution_capable false; correct the role or pass an explicit execution override". It was redispatched as r-20260926T085450107836.
  • Node dispatch-records-the-pace-row, --time-budget 90m. It was refused with "bounded: budget 90m exceeds the resolved fence 60m; split the work rather than overrun it". It was redispatched at 60m as r-20260926T095413623438.

The accepted side's "goal quoting <path>" row may use s22's one observed false positive, node accepted-shared-path-is-not-a-conflict. Its done-when quoted the runtime message "cannot accept <path>: live run <peer> claims <claim>" and was refused as "fully-specified: '<path>' leaves the worker to infer intent". The review's own refused done-when survives only as the fragment quoted in §1 ("… and the counts of TODO-FIXME, xfail and skip markers …"), and the run store's refusals table holds no fuller copy. The row uses that fragment verbatim inside an otherwise complete done-when.

§3 — A session that armed a follower keeps dispatching

Deliverable. When the dispatching session appears in the project watcher's released-followers list (it armed a follower that has since expired) and the watcher process is live, dispatch proceeds and prints a warning whose text contains the exact attach command to re-arm. The watcher-required refusal remains for a session that has never registered a follower with the watcher.

Done when two tests pass — the expired-follower case proceeds with the attach command in its warning, and the never-registered case is refused — and a dry run shows the same outcome for each.

§4 — Bookkeeping follows the run

Deliverable. Three narrowings. A corrective run — one whose record carries attempt_kind resume or redispatch, or whose dispatch declares --repairs <run-id> naming a promoted run (a declaration this section adds) — promotes with impl_move recorded as exempt, so no operator passes --no-impl-change for it. A review run's --outcome becomes optional, defaulting to its stored review's total score and finding count. verify-gate accepts a checkout when the merged revision is an ancestor of the checkout's HEAD and none of the run's changed paths differs between the two.

Done when each of the three has a named test, including a verify-gate run on a checkout two ledger commits past the merge. After release, a week of coordinator transcripts is read for operator uses of --no-impl-change on corrective runs and --outcome on review runs, against the counts in the coordinator-overhead census; the target is zero, reported as a follow-up measure rather than a release gate.
