§1 — What the lead and three coordinators reported

The lead reported five defects in reckon crew follow from one pane on 2026-09-22, following the nova session s18-fable-20260922. The rows are scoped to a session while the trailing 5w· 1b· 5u figures count the whole project. A blocked or unpromoted run is shown once, so a coordinator must remember it. The grid goes ragged because model aliases have different widths. The from-and-to transition spends two state cells where the destination alone is what a reader acts on. Several cells always read –, and a cell reading 0mu is not decodable. Above all, followers go stale and are re-armed regularly.

Two coordinators answered a request for their experience the same evening, and their reports agree on the main cause. nova-a9 re-armed fourteen times in nine and a half hours and imas-efit-e3 nine times in eight hours. Every re-arm followed the host's Monitor expired after 30m notice, and neither saw a follower die on its own. Both first armings failed with exit 127, because the attach_line reckon emits is a bare reckon that is not on the Monitor shell's path. imas-efit-e3 lost three unpromoted runs for between 1h21m and 2h42m each because the transition was shown once, during a re-arm gap. nova-a9 found that observing a peer session caused the follower's recovery sweep to dispatch a review onto that peer's run from its own runtime.

Reading the code confirms three of the lead's points directly. The 0mu cell is the age of the oldest unpromoted run, printed as minutes followed by the bucket letter, from _age_cells in reckon/crew/ticker.py. The – cell is the generation rate, rendered as the absence marker whenever the transition carries no rate. The model cell is ten columns wide and deliberately lets a wider alias overflow, and the locally served lane's alias dsv4.1-flash is twelve. The session-scoped count helper landed on 2026-09-15, but the follow command at reckon/cli.py still calls format_watch_transition without session=, which is open work on a-scoped-follower-counts-its-own-session.

The sections below measure what the reports claim, so that the repair plans are sized from counts. Each is one node on the locally served lane, delivering one JSON data file under docs/research/data/ and a manifest. Every node runs as the implement role in a full worktree sandbox, because on this lane read-only workers die mid-thinking in 34 of 36 measured cases. No node changes source code.

§2 — Why followers go stale: a cause census

Count every way a follower stopped delivering over the last seven days, across the reckon, nova, imas-efit and imas-ambix projects, and attribute each stop to one cause. The inputs are the Claude Code transcripts under ~/.claude/projects/ for those four checkouts, the follower registrations under the crew config home, and the git history of the files follower_code_stamp in reckon/crew/runs.py hashes.

The causes to count are these. A host expiry is a notice reading Monitor expired after. An arming failure is a Monitor whose command exited 127 or printed command not found. A code reload is an in-place re-exec by _FollowerReloader in reckon/cli.py, whose frequency follows from how often any session edits reckon/cli.py or reckon/crew/*.py. A producer gap is a re-attach baseline burst after the project seat was released. Anything else is its own row, with an example.

Also record two facts about the host. The first is the parameter set of every Monitor tool call in the transcripts, stating how many passed persistent and whether those calls still met the thirty-minute expiry. The harness reference tells coordinators to pass persistent: true. The second is whether a worker launched by the follower's own recovery sweep is a child of the follower process, so that a host expiry which kills the follower also kills it. Answer that from the dispatch and resumption code with file and line, and look for a resumed run whose stream ends within a minute of an expiry notice.

Done when docs/research/data/monitor-staleness-census.json exists with one row per cause, each carrying a count, the pattern searched, the population searched and up to three quoted example lines with their transcript path. The positive control must hold: the imas-efit transcripts for 2026-09-22 yield at least nine expiry notices, because that coordinator reported nine. If fewer are found the matcher is wrong and must be fixed before any other count is reported. The file also states the number of Monitor calls that passed persistent, the number of expiries among them, the median interval between successive armings in one session, and a yes-or-no answer on sweep-launched workers with the file and line that decides it.

§2 landing record — the cause census

Landed. docs/research/data/monitor-staleness-census.json carries one row per cause over 2026-09-16–2026-09-23 across the reckon, nova, imas-efit and imas-ambix checkouts (1384 transcript directories, 1292 Monitor calls).

The positive control holds: the imas-efit transcripts for 2026-09-22 yield 17 expiry notices against the coordinator's reported nine. Every armed follower in the window falls into exactly one of three outcomes, a complete partition of 700 armings: 600 met the host's thirty-minute expiry, 100 ended early because the seat was released, and 0 failed to arm. On the host's parameters, 453 Monitor calls passed persistent and none of them met the expiry, while 730 non-persistent calls did; every one of the 453 predates the window, so not one of the 700 in-window armings carried the flag. The median interval between successive armings in one session is 30.23 minutes across 64 sessions.

Sweep-launched workers: yes as to parentage, no as to the kill. The sweep reaches subprocess.Popen at reckon/crew/dispatch.py:4585, which makes the worker the follower's child, but it passes start_new_session=True at reckon/crew/dispatch.py:4592, so the worker sits in its own process group and survives the follower's death.

Caveats. The code-reload row counts 198 commits touching reckon/cli.py or reckon/crew/*.py — the opportunity for a re-exec, not reloads observed, because the in-place re-exec leaves no banner a transcript distinguishes from prose. The .events streams carry time-of-day only, and the imas-efit stream holds no ticker rows at all, so producer gaps are derived from the transcripts; two baseline bursts are visible where the streams do carry rows.
