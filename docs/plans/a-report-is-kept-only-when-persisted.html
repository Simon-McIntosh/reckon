§1 — Why: 330 GB of reports nobody chose to keep

On 5 November the home filesystem hit its quota and was lifted temporarily. The crew reports store, ~/.config/reckon/crew/reports, held 330 GB, and two projects made up nearly all of it: imas-efit at 294.8 GB and nova at 35.0 GB, measured on 11 November. Of imas-efit's share, about 219 GB was .log and .out files and 49 GB was .nc and .h5 data. Copied base trees and builds made up most of the rest. Figures and HTML together came to under 2 GB.

So version control was never the cause. The store keeps everything a worker writes, indefinitely, whether or not anyone will read it again. Most plots are in-work items that matter for a day. The few that matter for longer are figures a plan cites or a reviewer will want again.

The lead's direction (2026-11-05 and 2026-11-11) is to turn the default around:

  • everything a run writes is working material and expires;
  • an item survives only when someone persists it, case by case, through a persist action in the SPA or the CLI;
  • persisted large data lives in the project's own store on /work, not in home.

The decisions below record the four choices. The open decision reports-bound-across-projects in the-crew-home-has-a-bound is answered by this plan.

Two things the move on 11 November found, which bind every section below:

  • Containment. Dispatch admission refuses a declared write path whose resolved form leaves the delivery roots (delivery_roots in reckon/crew/runs.py). So a reports project directory replaced by a symlink to /work would refuse every write a node declares beneath it. The move therefore links only settled child folders and leaves the project directory, and the folders reckon keeps writing (briefs, plan-review, code-review, portfolio-review), as real directories.
  • The retention sweep. Raw plan-review text is pruned inside plan-review, and a removal that meets a symlink where it expects a directory fails. That folder therefore stays a real directory.

§2 — A persisted item has a record and a home outside the crew home

Deliverable. A project's flight configuration names its persist root, a directory outside the crew home. Reckon carries no default path and no project name, so persisting without that setting is refused, and the refusal names the setting. Persisting an item does three things:

  • copies a figure, and optionally data files the caller names, from the reports store or a run directory into the persist root;
  • checks that each copy has the source's byte count and content hash;
  • appends one record to the project's persisted-items resource. This is a typed per-project state record, read and written through reckon/project_state.py (resource_path, _validate_resource, read_resource and write_resource) and its atomic write, and resolved against the project's mounted docs directory. An unmounted project is refused rather than given a path, so no new path rule is added.

Each record holds: the source path, the persisted path, its kind (figure or data), the figure a data file belongs to, the plan and section when the source can be attributed to one, who persisted it, when, the byte count and the hash. A read returns the records for a project, filterable by plan and kind. A second persist of the same source with the same hash returns the existing record, and writes nothing.

Done when a new tests/test_a_persisted_item_has_a_record.py shows, on a synthetic crew home and a temporary persist root:

  • Persisting a figure writes the copy and one record, and the copy's hash equals the source's.
  • Persisting it with two named data files writes three copies and three records, and both data records name the figure.
  • A project with no persist root configured is refused, with the setting's name in the message and nothing written.
  • A repeat persist of an unchanged source writes no second record.
  • A copy whose bytes are altered before the check is refused, and leaves no record.
  • A project that is not mounted is refused, and nothing is written.
  • A persisted figure attributable to a plan section carries that plan and section, and every record carries who persisted it and when.
  • A read filtered by plan returns only that plan's records, and a read filtered by kind returns only figures or only data.

The test asserts that the real crew home and docs state are untouched afterwards. Negative control: skipping the hash check makes the altered-copy case pass a corrupt copy and fail the test. Ruff adds no findings on the staged paths. Write paths: one new module under reckon/crew/, reckon/project_state.py (registering the resource type), the flight schema, and the new test.

§3 — Persisting is one action from the CLI, MCP and HTTP

Deliverable. The §2 operation is reachable from three surfaces:

  • a reckon crew persist verb taking a figure path and zero or more --data paths, figure-only by default;
  • a sub-path of the existing /crew HTTP route that the SPA can call. It is not a new top-level route;
  • the MCP crew tool, read-only: persisted items are a field of the existing records view, not a new view. The MCP persist action is deferred, because CrewArgs carries no action field and actions live on separate tools.

Both write surfaces call one Python function and return the same record shape. The SPA computes nothing about an item's retention: the server's listing of a plan's report items carries, for each item, its retention class (persisted, cited or working) and, for working items, the date it expires under §4. Both come from the one classifier §4 creates in reckon/crew/report_retention.py; the listing does not re-derive them.

Surface budget. The plan adds one CLI verb, one sub-route, a field on one existing view, two flight settings (the persist root and the staging root) and one refusal family (persisting with no persist root configured). Nothing is retired, because no existing surface persists anything a reader can later find.

Done when a new tests/test_persist_surfaces_agree.py persists the same synthetic figure through the CLI and the HTTP sub-route, each against its own temporary store, and shows the two returned records are equal apart from timestamps. It also shows the existing records view lists the persisted item. The served listing for a plan returns the persisted item as persisted, a report path cited in a plan document as cited, and an unreferenced report as working with an expiry date.

Tests covering CLI help, the verb registry and the MCP tool schema gain the new verb and the records field, and keep their base results otherwise. Negative control: routing the HTTP endpoint through a second implementation that omits the data records makes the agreement case fail. Ruff adds no findings on the staged paths. Write paths: reckon/crew_run_commands.py, reckon/mcp_views.py, reckon/serve.py and tests/test_persist_surfaces_agree.py.

§4 — An unpersisted report expires at its plan's close or after 30 days

Deliverable. The existing pass that removes report trees, _run_report_trees in reckon/crew/routing.py (run from garbage_collect by the hourly retention sweep, crew-state-stays-bounded §7), is extended with the rules below. No second pass is added. Its item rule replaces the run-tree rule for the reports store, so the 30-day run-tree rule can never remove a cited or persisted item first. _plan_review_raw_reports keeps its own rule for raw plan-review text.

One classifier. A new module, reckon/crew/report_retention.py, owns the judgement. Its one classify function returns an item's class (persisted, cited or working), its expiry and the reason. The pass calls it, and so does §3's listing, so the listing never shows an item as retained while the pass removes it. The citation scan reuses the existing document walk: iter_resources (reckon/resources.py) for the plan, research and evidence documents, _LINK_ATTR_RE for href and src targets, and audit_links / _link_record (reckon/doccheck.py) for extraction. No third document walk is written.

Expiry rule. A report item that is neither persisted nor cited expires at whichever comes first:

  • the moment its plan reaches a terminal status, when the item can be attributed to a plan. An item is attributed to a plan when its folder name equals the slug of a plan in its project, or when a ledger run of its project names that plan and has a report path inside the item. An item matching neither rule is unattributable and takes only the 30-day ceiling;
  • 30 days after the item's newest file was last written.

What counts as an item. An item is a child folder of a project's reports directory, or a file directly inside one.

What is kept. An item is kept for as long as any of these holds:

  • a §2 record persists something inside it;
  • its path, or the path of any file or folder inside it, appears in a plan, research or evidence document of its project. A plan usually cites a figure inside a run folder, not the folder itself, and either form keeps the whole item;
  • a live run pointer names it.

Reckon-written folders. plan-review keeps its own rule (_plan_review_raw_reports) and is never treated as one item. briefs, code-review and portfolio-review have no rule of their own, so each child of those folders is an item under the rules above, and none of the three folders is ever removed whole.

Moved folders. An item that is a symlink to a folder moved off home is expired by removing the folder it points to, after checking that the target lies under that project's staging root. The staging root is a second per-project flight setting beside the persist root, and names where moved working reports wait to expire. The symlink is removed last. The pass stops calling shutil.rmtree on a symlinked item, which today raises and leaves both the link and its target. The sweep never removes anything under the persist root, which holds only what §2 kept deliberately. A symlink pointing anywhere else, the persist root included, is reported and left alone, as is any symlink in a project with no staging root set.

Output. A dry run prints every candidate with its reason, its age and the rule that applies. --apply prints every removal.

Done when a new tests/test_an_unpersisted_report_expires.py shows, on a synthetic crew home with a mounted synthetic project:

  • An unreferenced item 31 days old is removed. A 29-day-old item attributed by folder name is kept until its plan closes, and is removed once it does. The same holds for a 29-day-old item attributed only through a ledger run's report path. A 29-day-old item that matches neither rule is kept whatever any plan's status. A 31-day-old item attributed to a plan that is still open is removed, because the 30-day ceiling applies whichever way the item is attributed.
  • Each of these is kept at 90 days: a persisted item; an item whose own path is cited in a plan document; an item cited only through a file inside it; one item cited only from a research document, and another only from an evidence fragment; and an item named by a live pointer.
  • No reckon-written folder is removed whole at any age. A 31-day-old unreferenced child of code-review is removed. The plan-review folder's contents are left to its own rule.
  • An expired symlinked item has its target and its symlink removed. A symlink whose target lies outside the permitted roots is kept and reported.
  • The dry run's candidate list equals the set --apply removes.
  • A 40-day-old run-keyed tree that holds a figure a plan cites is kept, where at the base revision _run_report_trees removes it.

Three negative controls:

  • dropping the citation check removes the cited item and fails the test;
  • matching citations against the item's own path only removes the item cited through a file inside it and fails the test;
  • dropping the target-root check removes the outside target and fails the test.

The test files that import reckon.crew.gc add no failure against the base revision, and the test asserts the real crew home is untouched.

Ruff adds no findings on the staged paths. Write paths: reckon/crew/report_retention.py (new); reckon/crew/routing.py, where _run_report_trees runs; reckon/crew/gc.py; the flight schema, for the staging-root field; and the new test.

After the node lands, the coordinator measures the real store. The node cannot do this step, because its write scope is the reckon repository and the settings live in other repositories.

  • Set the staging root in each moved project's own flight configuration: /work/projects/imas_gpu/crew-reports/imas-efit for imas-efit and /work/projects/imas_gpu/crew-reports/nova for nova. Each is committed in its own repository.
  • Run one dry run over the real reports store on the fleet node, under a 30-minute timeout. Record whether it finished and, per project, the count and bytes it would expire.
  • The dry run must report none of the moved imas-efit or nova folders as outside the permitted roots. Each moved folder is either a candidate, or kept with a citation, persist or live-pointer reason.

The record is committed as docs/evidence/fragments/a-report-is-kept-only-when-persisted/an-unpersisted-report-expires.html. The section is declared done only once that record shows the dry run finished inside its timeout.

§5 — The SPA shows retained figures and offers the persist action

Deliverable. The SPA gains a listing of a plan's report items under reports/<project>/, fed only by the §3 listing. This is a second root beside the committed docs/figures inventory that figure_rows already serves. Committed figures never expire, are always shown as retained, and are not changed by this section. In that report-item listing, a filter chooses one of retained (persisted or cited), working or all, and defaults to retained. Each working item shows its expiry date and a persist control. The control offers figure only, or figure with the data files the reader ticks from that item's folder, and calls the §3 endpoint. The item then reads as persisted without a page reload. Every class, date and count the surface shows comes from the §3 listing, and the surface computes none of them.

Done when a browser test against the served SPA on a synthetic project whose reports store holds one persisted, one cited and two working figures shows:

  • The default view lists exactly the two retained figures, and all lists four.
  • Persisting one working figure through the control moves it into the retained view, and leaves one §2 record in the temporary store.
  • Choosing figure-with-data and ticking one file leaves two records.

Every figure added or changed for the surface is rendered and inspected, as the figure review rule requires. Negative control: a listing payload whose classes are swapped makes the default view show the working figures and fail the test. The parity check that compares surfaces gains the retention class: a case shows it fails when the SPA's class for an item differs from the listing's. Write paths: docs/ui/plan.jsx, docs/_shared/dashboard.css, tests/test_crew_surface_parity.py and tests/test_the_report_listing_shows_retained_figures.py.

§6 — The existing backlog leaves home and is expired by §4

Deliverable. An operational record, carried out by the coordinator on 11 November at the lead's instruction. imas-efit's and nova's report trees are copied to the staging root /work/projects/imas_gpu/crew-reports/<project> and verified.

The original is removed only after a late-write copy and a second comparison both show 0 differences. Every action is printed to /work/projects/imas_gpu/_moves/crew-reports/. Nothing is deleted outright: the copies stay until §4 expires them.

§ Decisions

What happens to the existing 330 GB before the policy lands?

This frees home at once with nothing deleted, and leaves the deletion to a rule that has a test and a dry run.

When a figure is persisted, what happens to the data files behind it?

A figure from a long solver run cannot be rebuilt cheaply, so its data can be kept deliberately. The default keeps the 49 GB of .nc and .h5 in imas-efit from being persisted by reflex.

Where does persisted large data go?

Projects outside the GPU allocation can point elsewhere, and reckon keeps no project name or host path in code.

How long does a report nobody persisted stay in the crew home?

Slow plans keep their working evidence for a month, and the 30-day ceiling stops a long-lived plan from growing without bound. The lead asked in the same answer for an SPA filter for retained images, which is §5.

§7 — A node whose result can be drawn leaves a figure, and no prose report

The lead's direction of 22 November 2026: a worker's reflex is a graphical evidence trail of figures, plots and animations wherever the work supports one, and written evidence reports are composed only when a plan or a sprint closes. The fleet does the opposite. In the week to 21 November reckon recorded 746 landings, 965 commits whose subject begins docs(evidence), and 37 figure files. The composed worker contract explains it: one clause tells a node it "writes no figure and no evidence prose outside the landing fragment" unless its done-when names that artifact, and a later clause tells the same node to "use a figure wherever a spatial, plotted or sequential relationship is clearer" (both in reckon/crew/prompts.py). Workers obey the first and write a fragment of prose. The ask itself, and the manifest's figures: line that holds each named figure to a committed file, already exist; what is wrong is that the withholding clause is composed beside them, and that the rule is carried in four places that can drift apart.

Deliverable. The contract a worker is launched with says one thing about evidence, stated once and composed into every contract: draw a figure, or an animation where the result is a sequence in time, wherever the result is one a figure shows more clearly than prose, name it on the manifest's figures: line, keep prose to the landing line, and write an evidence fragment only for a negative result. No composed contract carries a clause that withholds a figure beside one that asks for it, and the worker protocol reference states the same rule.

Done when. tests/test_a_drawable_result_leaves_a_figure.py passes, covering: the contract composed for a node whose done-when states a measure asks for the figure and names the topic directory; the contract composed for a node whose done-when is a rename asks for none; no composed contract contains both a clause withholding a figure and a clause asking for one; and the worker protocol reference states the same rule in the same words. Changing the rule's text in its one place changes it in every composed contract, which a case asserts. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line. Write paths: reckon/crew/prompts.py, skills/reckon-build/references/worker-protocol.md and the new test.

Negative control. At the base revision, the third case must fail, with both clauses present in one composed contract.

§8 — A plan's evidence report is written once, at closure, and names its plan and sprint

A plan's landed record is the one written account of what its nodes delivered. A reader who opens one has to know which plan it records and which sprint that plan ran in, and should see the figures the nodes drew rather than a paragraph about each. Of the 226 landed records under docs/evidence/archive/ on 22 November 2026, all 226 name their plan in metadata, 9 name a sprint, and 59 embed a figure.

Deliverable. Closing a plan composes one evidence report for it. The report states the plan it records and the sprint that plan belonged to, each as a link, in its first visible block and in its metadata; it has one row per landed node carrying that node's landing line; and it embeds, under the node's row, every figure the node saved. No evidence report is composed for a plan while it is open.

Done when. tests/test_a_closed_plan_has_one_report_naming_its_plan_and_sprint.py passes, covering: closing a plan in sprint S9 with three landed nodes, two of which saved figures, yields one record whose metadata names the plan and the sprint, whose first block links both, which embeds both figures by project-absolute path beneath their nodes' rows, and which reckon audit-doc accepts; a landing on a plan that stays open composes no record; and closing a plan that belongs to no sprint composes the record with the sprint stated as none. The record is written where the plan's landed record already lives, and the composition adds no new refusal. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line. Write paths: reckon/project_state.py, reckon/evidence.py and the new test.

§11 — A measure stated as a count or in words still asks for a figure, in one directory

The re-review of §7 at head 9096b78bef (r-20261124T002326297129-review-of-a-report-is-kept-only-when-persisted) found two remaining gaps in the composed evidence rule. A done-when that states its measure as a count of an unnamed thing ("reduces 120 sequential calls to 3 batched ones") or in words ("halves the runtime") is still told "Your done-when states no measure", which is false and withholds the figure §7 asks for. And a brief-carried run reads two directories for one figure in one prompt: the manifest template places figures under docs/figures/<plan>/ while the location sentence composed for the same run gives docs/figures/<topic>/.

Deliverable. A done-when that states a measure, whether as a number with a unit, a count of anything, or a word of proportion or comparison such as halves, doubles or a tenth of, is composed with the clause asking for a figure. A done-when that states none, such as a rename, is still composed with none. Every prompt names one figure directory, the same in its manifest template and in its location sentence, for both carriers.

Done when. tests/test_a_measure_in_any_form_asks_for_a_figure.py passes, covering: done-whens reading "reduces 120 sequential calls to 3 batched ones", "halves the runtime" and "cuts the gate's runtime by 30 percent" each compose the figure-asking clause and not the no-measure clause; a rename-only done-when composes the no-measure clause; and for each carrier, every figure directory named in one composed prompt is the same path. The expectation for each done-when is written in the test, not read from the module's own pattern or constants. The tests that import the changed modules add no failure against a base arm run on all_debug. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. At main after §7 lands, the first two done-whens compose "Your done-when states no measure", and a brief-carried prompt names two different figure directories.
