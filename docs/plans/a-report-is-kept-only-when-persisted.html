§1 — Why: 330 GB of reports nobody chose to keep

On 5 November the home filesystem hit its quota and was lifted temporarily. The crew reports store, ~/.config/reckon/crew/reports, held 330 GB, and two projects made up nearly all of it: imas-efit at 294.8 GB and nova at 35.0 GB, measured on 11 November. Of imas-efit's share, about 219 GB was .log and .out files and 49 GB was .nc and .h5 data. Copied base trees and builds made up most of the rest. Figures and HTML together came to under 2 GB.

So version control was never the cause. The store keeps everything a worker writes, indefinitely, whether or not anyone will read it again. Most plots are in-work items that matter for a day. The few that matter for longer are figures a plan cites or a reviewer will want again.

The lead's direction (2026-11-05 and 2026-11-11) is to turn the default around:

  • everything a run writes is working material and expires;
  • an item survives only when someone persists it, case by case, through a persist action in the SPA or the CLI;
  • persisted large data lives in the project's own store on /work, not in home.

The decisions below record the four choices. The open decision reports-bound-across-projects in the-crew-home-has-a-bound is answered by this plan.

Two things the move on 11 November found, which bind every section below:

  • Containment. Dispatch admission refuses a declared write path whose resolved form leaves the delivery roots (delivery_roots in reckon/crew/runs.py). So a reports project directory replaced by a symlink to /work would refuse every write a node declares beneath it. The move therefore links only settled child folders and leaves the project directory, and the folders reckon keeps writing (briefs, plan-review, code-review, portfolio-review), as real directories.
  • The retention sweep. Raw plan-review text is pruned inside plan-review, and a removal that meets a symlink where it expects a directory fails. That folder therefore stays a real directory.

§2 — A persisted item has a record and a home outside the crew home

Deliverable. A project's flight configuration names its persist root, a directory outside the crew home. Reckon carries no default path and no project name, so persisting without that setting is refused, and the refusal names the setting. Persisting an item does three things:

  • copies a figure, and optionally data files the caller names, from the reports store or a run directory into the persist root;
  • checks that each copy has the source's byte count and content hash;
  • appends one record to a per-project persisted-items store under the project's docs state.

Each record holds: the source path, the persisted path, its kind (figure or data), the figure a data file belongs to, the plan and section when the source can be attributed to one, who persisted it, when, the byte count and the hash. A read returns the records for a project, filterable by plan and kind. A second persist of the same source with the same hash returns the existing record, and writes nothing.

Done when a new tests/test_a_persisted_item_has_a_record.py shows, on a synthetic crew home and a temporary persist root:

  • Persisting a figure writes the copy and one record, and the copy's hash equals the source's.
  • Persisting it with two named data files writes three copies and three records, and both data records name the figure.
  • A project with no persist root configured is refused, with the setting's name in the message and nothing written.
  • A repeat persist of an unchanged source writes no second record.
  • A copy whose bytes are altered before the check is refused, and leaves no record.

The test asserts that the real crew home and docs state are untouched afterwards. Negative control: skipping the hash check makes the altered-copy case pass a corrupt copy and fail the test. Ruff adds no findings on the staged paths. Write paths: one new module under reckon/crew/, the flight schema, and the new test.

§3 — Persisting is one action from the CLI, MCP and HTTP

Deliverable. The §2 operation is reachable from three surfaces:

  • a reckon crew persist verb taking a figure path and zero or more --data paths, figure-only by default;
  • the MCP crew tool, as an action, plus a view that lists persisted items;
  • a served HTTP endpoint the SPA can call.

All three call one Python function and return the same record shape. The SPA computes nothing about an item's retention: the server's listing of a plan's report items carries, for each item, its retention class (persisted, cited or working) and, for working items, the date it expires under §4.

Done when a new tests/test_persist_surfaces_agree.py persists the same synthetic figure through the CLI, the MCP action and the HTTP endpoint, each against its own temporary store, and shows the three returned records are equal apart from timestamps. The served listing for a plan returns the persisted item as persisted, a report path cited in a plan document as cited, and an unreferenced report as working with an expiry date.

Tests covering CLI help, the verb registry and the MCP tool schema gain the new verb and action and keep their base results otherwise. Negative control: routing the HTTP endpoint through a second implementation that omits the data records makes the agreement case fail. Ruff adds no findings on the staged paths. Write paths: the CLI module that registers crew verbs, the MCP crew tool, the served plan endpoints, and the new test.

§4 — An unpersisted report expires at its plan's close or after 30 days

Deliverable. The hourly retention sweep (crew-state-stays-bounded §7) reaches the reports store.

Expiry rule. A report item that is neither persisted nor cited expires at whichever comes first:

  • the moment its plan reaches a terminal status, when the item can be attributed to a plan. An item is attributed to a plan when its folder name equals the slug of a plan in its project, or when a ledger run of its project names that plan and has a report path inside the item. An item matching neither rule is unattributable and takes only the 30-day ceiling;
  • 30 days after the item's newest file was last written.

What counts as an item. An item is a child folder of a project's reports directory, or a file directly inside one.

What is kept. An item is kept for as long as any of these holds:

  • a §2 record persists something inside it;
  • its path, or the path of any file or folder inside it, appears in a plan, research or evidence document of its project. A plan usually cites a figure inside a run folder, not the folder itself, and either form keeps the whole item;
  • a live run pointer names it.

What is never removed. The four folders reckon writes into are swept only by their own existing rules, never as one item: briefs, plan-review, code-review and portfolio-review.

Moved folders. An item that is a symlink to a folder moved off home is expired by removing the folder it points to, after checking that the target lies under that project's persist root or the move's staging root. The symlink is removed last. A symlink pointing anywhere else is reported and left alone.

Output. A dry run prints every candidate with its reason, its age and the rule that applies. --apply prints every removal.

Done when a new tests/test_an_unpersisted_report_expires.py shows, on a synthetic crew home with a mounted synthetic project:

  • An unreferenced item 31 days old is removed. A 29-day-old item attributed by folder name is kept until its plan closes, and is removed once it does. The same holds for a 29-day-old item attributed only through a ledger run's report path. A 29-day-old item that matches neither rule is kept whatever any plan's status.
  • Each of these is kept at 90 days: a persisted item; an item whose own path is cited in a plan document; an item cited only through a file inside it; one item cited only from a research document, and another only from an evidence fragment; and an item named by a live pointer.
  • None of the four reckon-written folders is removed at any age.
  • An expired symlinked item has its target and its symlink removed. A symlink whose target lies outside the permitted roots is kept and reported.
  • The dry run's candidate list equals the set --apply removes.

Three negative controls:

  • dropping the citation check removes the cited item and fails the test;
  • matching citations against the item's own path only removes the item cited through a file inside it and fails the test;
  • dropping the target-root check removes the outside target and fails the test.

The test files that import reckon.crew.gc add no failure against the base revision, and the test asserts the real crew home is untouched.

A host measure follows: one dry run over the real reports store, under a timeout on the fleet node, records the count and bytes it would expire per project. It is committed as docs/evidence/fragments/a-report-is-kept-only-when-persisted/an-unpersisted-report-expires.html. Ruff adds no findings on the staged paths. Write paths: reckon/crew/gc.py, the new test and that fragment.

§5 — The SPA shows retained figures and offers the persist action

Deliverable. Where the SPA lists a plan's figures and report items, a filter chooses one of retained (persisted or cited), working or all, and defaults to retained. Each working item shows its expiry date and a persist control. The control offers figure only, or figure with the data files the reader ticks from that item's folder, and calls the §3 endpoint. The item then reads as persisted without a page reload. Every class, date and count the surface shows comes from the §3 listing, and the surface computes none of them.

Done when a browser test against the served SPA on a synthetic project with one persisted, one cited and two working figures shows:

  • The default view lists exactly the two retained figures, and all lists four.
  • Persisting one working figure through the control moves it into the retained view, and leaves one §2 record in the temporary store.
  • Choosing figure-with-data and ticking one file leaves two records.

Every figure added or changed for the surface is rendered and inspected, as the figure review rule requires. Negative control: a listing payload whose classes are swapped makes the default view show the working figures and fail the test. The parity check that compares surfaces gains the retention class. Write paths: the JSX component that renders a plan's figures, its CSS in docs/_shared/, and the new browser test.

§6 — The existing backlog leaves home and is expired by §4

Deliverable. An operational record, carried out by the coordinator on 11 November at the lead's instruction. imas-efit's and nova's report trees are copied to the staging root /work/projects/imas_gpu/crew-reports/<project> and verified.

Each settled child folder is then replaced by a symlink to its copy. A folder qualifies as settled when all of these hold:

  • it is not one of the four reckon-written folders;
  • it was unchanged for 7 days;
  • a fresh comparison lists no difference, and the file counts and byte totals match.

The original is removed only after a late-write copy and a second comparison both show 0 differences. Every action is printed to /work/projects/imas_gpu/_moves/crew-reports/. Nothing is deleted outright: the copies stay until §4 expires them.

Done when the swap log names every child folder of both projects as linked or kept, with the reason for each kept one. Negative control: the log shows at least one folder kept because it changed inside 7 days, so the settle check is seen refusing a folder rather than assumed to. du of each project's home reports directory, measured under a timeout, is recorded before and after. The record is committed as docs/evidence/fragments/a-report-is-kept-only-when-persisted/the-existing-backlog-leaves-home.html.

§ Decisions

What happens to the existing 330 GB before the policy lands?

This frees home at once with nothing deleted, and leaves the deletion to a rule that has a test and a dry run.

When a figure is persisted, what happens to the data files behind it?

A figure from a long solver run cannot be rebuilt cheaply, so its data can be kept deliberately. The default keeps the 49 GB of .nc and .h5 in imas-efit from being persisted by reflex.

Where does persisted large data go?

Projects outside the GPU allocation can point elsewhere, and reckon keeps no project name or host path in code.

How long does a report nobody persisted stay in the crew home?

Slow plans keep their working evidence for a month, and the 30-day ceiling stops a long-lived plan from growing without bound. The lead asked in the same answer for an SPA filter for retained images, which is §5.
