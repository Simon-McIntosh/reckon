§1 — Inventory the failures at head and name each root cause

The earlier plan Every Suite Failure Has An Owner cleared the fourteen standing failures it inventoried at dc52c8d and closed at impl 1.0. Since then the repository has taken many landings, and there is no current reading of the suite at head. A failure set is a property of a revision, not of the repository, so this section starts by measuring rather than by assuming the earlier inventory still holds.

This section is diagnosis only. It changes no source or test file. Its deliverable is the research record docs/research/suite-failures-at-head.html (reckon-type=research, plan-informs=the-suite-is-green-at-head), which later sections cite as their input.

Where it runs. The whole suite is heavy work and runs on SLURM compute, never on the login node. A worker already running inside the fleet allocation (SLURM_JOB_ID set, host not a login node) runs it in place; otherwise it submits to partition all_debug with --time at most 00:59:00. Either way TMPDIR=/tmp, one log per run, and the record names the host and job id the run used. The earlier plan measured that tests/test_crew.py completes in about 30 s on a compute node and stalls only on the login node, so a stall on compute is itself a finding to record. If the suite cannot finish in one one-hour job, split it by test file across jobs and name the split.

MeasureRequired evidence
Inventory at a recorded revisionThe record names the revision measured, the exact command and partition used, the total pass, fail, error and skip counts, and every failing or erroring node id. Each run's log path is recorded.
Grouped by cause, with evidenceEvery failing node id is assigned to exactly one cause group. Each group states its root cause in one sentence and cites the evidence for it: a traceback line, the commit that changed the behaviour or the assertion, or a reproduction command.
Stale assertion distinguished from defectEach group is classified as one of stale expectation (the behaviour changed on purpose and the test did not), product defect (the code is wrong), test isolation (the test reads or writes state outside the repository, depends on order, or depends on today's date), or environment (fails only because of the host). The record says which, and why. The earlier plan's locked decision still governs: when behaviour changed deliberately, the test moves to the shipped behaviour.
Repair scope per groupFor each group, the record names the files a repair would write and whether any two groups' repairs would touch the same file, so §2 can be cut into non-overlapping nodes.

§2 — Repair each cause group

One node per cause group identified in §1, each cut to exclusive write paths from the §1 record's repair-scope column. This section's nodes are authored once §1 has landed: the cause groups are not known until then, and cutting nodes before the diagnosis would repeat the mistake the earlier plan warned about, which is repairing several failures under one assumed cause.

No node disables, skips, xfails or deletes a failing test. Each repair either corrects a stale assertion to the shipped behaviour, with the cause named, or fixes the product defect the test found.

MeasureRequired evidence
Cause named before repairEach node's landing record repeats the §1 cause group it repairs and whether it moved the assertion or the behaviour.
Zero addedFailure sets compared by node id at the node's base revision and at its head, on compute; the group's failures are gone and no other node id moved from pass to fail.
Green at the integrated headAfter every §2 node merges, one full-suite run on compute at the merged head reports zero failures and zero errors, with its revision and log recorded in the cumulative evidence record.
