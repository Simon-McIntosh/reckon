§2 — Jev reads the session's own admission before it routes

Deliverable. The state rendered for Jev carries, for each lane with a router, the worker slots the router would grant this coordinator session, taken from the lane document's admission.sessions[session].worker_slots or, when the session is not listed, admission.new_session_worker_slots, in the order the global routing rules already define. That reading already exists as _lane_worker_allowance in reckon/crew/dispatch_plan.py, which the picker's snapshot calls (reckon/crew/picker/snapshot.py, behind its local-lane guard). This section extends that helper and that guard to carry the session's figure into the rendered state, and writes no second reader. The route question's guidance says that a lane granting the session no slot is not available to it now. When a route nonetheless lands on such a lane for an implement or test node at the exact or guided specification level, Jev is asked once more with that lane excluded. The second answer stands, and the record names both asks, so the decision is visible. Routine or open work keeps today's behaviour and is queued under §13 of the queue plan.

Under a lift, Jev routes with the lift in view instead of defaulting to the local queue. The lead's rule, given on 2026-10-15: a lift is not a free-for-all. Jev still chooses the lane, sending harder work to the metered lane as before. But a lift means the window is to be spent. With two full weekly resets in hand, or a deadline, the fleet scales at full width rather than queueing. While a lift governs a metered lane that serves the node (budget_lift.effective_budget names it), Jev decides with the lift in view, and no deterministic rule overrides its answer: the choice is a trade of cost, speed and quality that Jev weighs. Three things change. The rendered state names the lift on that lane, with its form and end. The route question's guidance says a lifted lane is meant to be spent: its burn and pace do not press it, and when the local lane is full, holding or queueing for it is no longer the default for work the lifted lane can serve. And review_excluded_backends does not exclude a lifted lane, so a review is offered the lifted lane's options, with guidance that a review should prefer the lane's cheaper models. When the local lane has a slot and no lift is in force, Jev routes exactly as it does today. This relies on a-window-paces-the-lane §17: until the budget preflight reads the lift, Jev sees a lifted lane as held at its reserve ceiling.

Done when a test renders a state in which the local lane is open lane-wide but grants the session no slot, with codex serving, and finds that a guided implement node is not left queued on the local lane; the same state with the session granted one slot routes as before; an open-specification node in the zero-slot state is still allowed to hold. The picker's and dispatch's test files show no added failure against base. Negative control: without the session figure in the rendered state, the zero-slot case must reproduce the 2026-10-13 queueing. Under a lift, in addition: a test renders the zero-slot state with an uncapped lift in force on codex. It finds that the rendered state names the lift on the codex lane, that the guidance carries the lifted-lane wording, and that a review node is offered the codex options with the cheaper-model guidance. Without the lift, the same review node is offered no codex option and the lift wording is absent. A replay through a stub picker that returns hold for a routine node shows the hold is recorded as Jev's own answer and not overridden. Negative control: with the lift removed from the rendered state, the review is offered no codex option.

§3 — A pick probe uses the inputs a dispatch would

Deliverable. reckon crew pick accepts the node fields that dispatch hands to the picker (write paths, negative control, estimated hours and section). These options mirror fields crew dispatch already takes and hands to the picker, so they restate existing inputs on a second command rather than add new interface, and they retire nothing because no option of crew pick carries them today. Its answer lists any of them the probe left out, so a coordinator can see that a hold may come from what the probe lacked. With every field supplied, a pick and a dry-run dispatch render the same node state for Jev.

Done when a test renders the node state from a pick and from a dry-run dispatch with the same fields and finds them equal; a pick that omits write paths names them in its answer. Negative control: a pick given fewer fields than the dry-run must render a different state and the equality test must fail.

§4 — A lane change keeps the run's recorded waivers

Deliverable. reckon crew redispatch carries the waivers recorded in the original run's dispatch_options (allow_unreviewed_plan, accept_directory_claim and the reason in comment) into the new launch and records them as carried, so moving a run to another lane is not refused by a gate the original dispatch had already answered. A waiver is never added by a redispatch, only carried. A queued run is moved by redispatch without being discarded, so the move does not race the admission pass, and a queued run that never launched is moved by re-composing its launch from the recorded node rather than refused for having no prompt. That recomposition already exists as _launch_queued in reckon/crew/queue_admission.py, which rebuilds the node with _node_from_pointer and forwards the pointer's dispatch_options to dispatch. The queued move extends that path with the new backend, and does not write a second one. The review reflex's retry asks the same question §2 asks before it re-queues on the lane that refused it.

Done when a test dispatches a node with --allow-unreviewed-plan against an uncovered plan, redispatches it to another backend, and finds it launched with the waiver recorded as carried; a node dispatched without the waiver is still refused on redispatch. Negative control: with the carry removed, the first case must be refused as on 2026-10-13.

§7 — A resume runs under the policy its run was dispatched with

Why. §4 made a lane change keep the run's recorded waivers. Reviewing it found that the two commands which move a run resolve its flight config differently. crew_redispatch in reckon/crew_run_commands.py reads the run's recorded dispatch_options.overrides, the --set values it was dispatched with, and resolves the flight config with them before calling change_lane. crew_resume resolves the flight config with an empty override tuple. That holds both for crew resume --backend, which reaches the same change_lane, and for a plain resume, which builds resume_plan from it. A run dispatched with an override that changes lane policy, a budget figure or a review exclusion therefore runs under a different policy once it is resumed or moved through resume than when it is moved through redispatch.

Deliverable. crew_resume resolves its flight config with the run's recorded overrides, as crew_redispatch does, through the same reading of dispatch_options.overrides. That reading becomes one helper both commands call, not a second copy. A run recorded with no overrides resolves as today.

Done when a test, with the config home pointed at a temporary directory, records a run dispatched with an override that changes a resolved flight value. Both crew resume --backend and a plain crew resume --print-only resolve the overridden value, and crew redispatch --print-only resolves the same one. A run with no recorded overrides resolves the base value on all three. The test files that import reckon/crew_run_commands.py give the same pass and fail ids at head as at base, apart from the new file. Negative control: with crew_resume passing an empty override tuple again, the resume cases read the base value; the control is logged under the run directory. Write paths: reckon/crew_run_commands.py and tests/test_a_resume_runs_under_its_dispatch_policy.py.

§8 — A queued run's admission reads its overrides through the same helper

Why. §7 gave crew resume and crew redispatch one reading of a run's recorded overrides, _recorded_dispatch_overrides in reckon/crew_run_commands.py. Its review found a third copy. _resolve_lane_config in reckon/crew/queue_admission.py reads the overrides by hand. A queued run's lane change never reaches it, because its callers pass a config already resolved. The admission pass does reach it, for a queued run's own launch, session-allowance and gate checks. It reads (pointer.get("dispatch_options") or {}).get("overrides") by hand. The copies agree today, but nothing keeps them in step.

Deliverable. One owner reads a run's recorded overrides: a public recorded_dispatch_overrides in reckon/crew/runs.py, beside read_pointer. Both modules can import it without a cycle, since queue_admission.py already imports runs. crew_run_commands.py drops its private _recorded_dispatch_overrides and calls the owner. _resolve_lane_config in queue_admission.py drops its hand read and calls the owner. Behaviour is unchanged.

Done when no module in reckon/ reads dispatch_options overrides except the owner. A test pins the owner for a record with overrides, a record with dispatch_options but no overrides, and a record with neither. A second test patches runs.recorded_dispatch_overrides to return a sentinel override.
