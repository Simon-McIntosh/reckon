The fleet allocation holds one node for every orchestrator and its workers, and its batch step runs reckon/crew/fleet_supervisor.py. That supervisor already starts one standing child, the health sampler, through start_health_sampler. On 2026-10-01 the lead decided that a project's telemetry ingest runs as a standing 60-second loop under this supervisor, rather than as a SLURM job on the GPU reservation. One ingest tick measures 0.29 s, about 0.5% of a core. This plan generalises the health sampler's pattern into services that a user config declares, so the supervisor runs any such loop without reckon naming the project that owns it.

§1 — Declared services start once, restart with backoff, and reload

A user config file, ~/.config/fleet/services.json, maps each service name to an argv list. The supervisor starts each declared service as its own-session child of the batch step. Each service holds a lock in the fleet runtime directory, so a reload or a second supervisor never starts a second copy. A service that exits is restarted with exponential backoff: 5 s at first, doubling to a 300 s cap, and reset after 10 minutes of steady running. A service is restarted only when it exits, never on a liveness timeout. A long tick is the service working: the consuming project measured a cold catch-up tick of 862 s after a fleet requeue. Each service's stdout and stderr are appended to a size-bounded log at ~/.local/state/fleet/services/<name>.log, which is on the shared filesystem, so a later reader can open the last ticks after the fleet node is gone; output never goes to DEVNULL. A service is started with the batch step's environment and needs no working directory of its own. On reload, a newly declared service starts, and a service removed from the file is stopped by the pid the supervisor recorded for it, never by a pattern. The supervisor never names a project. The first entry a consuming project will declare is ambix-ingest, whose argv runs that project's ingest every 60 s; that entry lives in the user's config, not in reckon.

Done when tests, run against a temporary runtime directory and a temporary config home, show five things. A declared service starts as its own session, with a lock held. A second start, or a reload, while it runs starts no second copy. A service that exits is restarted after the backoff and not before. A reload starts a newly declared service and stops a removed one by its recorded pid. The health sampler still starts as before. The negative control removes the lock check; the no-second-copy case must then fail.
