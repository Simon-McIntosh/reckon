A promoted run that is not merged reads as landed to every reader of the ledger, while its change reaches no one. Two defects combine to produce it. §1 removes the crash, and §2 makes any failure after promotion report itself.

§1 — The landing marker check reads a blob as bytes

Why. reckon/crew/merge.py's _run (near line 108) runs every git call with text=True, so git's output is decoded as UTF-8. _show (near line 211) returns git show <revision>:<path> through it, and the landing check reads each changed path at the base and the head through _show (callers near lines 274, 275 and 306). It splits each path into distinctive marker lines, so it can refuse a merge that dropped a change. A binary blob does not decode, so the check raises UnicodeDecodeError instead of comparing.

Deliverable. The landing check compares each changed path by blob identity first, and reads content only where it has to. git rev-parse <revision>:<path> gives a path's blob id without decoding anything, and the module already resolves object names this way (near lines 125, 133 and 345). A path whose merged blob equals the head's blob survived, or whose absence matches the head's when the change deleted it. Such a path needs no content read, whether it is text or binary.

Only a path whose merged blob differs from the head's is read, and then for the marker comparison it has today. If that content is not text, the merge altered a binary file the change carried, and the landing is refused naming the path. A content read that is still needed takes bytes, following the pattern reckon/crew/promotion_scope.py already uses near line 922, capture_output=True without text=True, and decodes only for a text path. _run stays a text call for every other git command.

One function in reckon/crew/merge.py owns this decision, and its docstring says what "survived" means for each kind. change_markers and surviving_change_refusals call it rather than each deciding. The survived block land() reports (near line 652) names each path's judgement, for example blob_identity beside paths and markers. A landing whose only change is binary then reports that it checked the blob, rather than markers: 0.

Done when tests/test_a_landing_reads_binary_files.py builds its temporary origin and checkout with the helpers that already exist: _write_origin_and_checkout in tests/test_one_call_lands_a_run.py (near line 34) and tests/helpers/git.py. If a helper must be shared, it moves into tests/helpers/ rather than being copied, and every environment-resolved directory points at temporary paths. The fixture's head adds a small binary file, one that contains a NUL byte and is not valid UTF-8, and edits a text file. The test holds all of these:

  • merge.land lands that head without raising, and the merged tree carries the head's blob for the binary path. merge.land is the function crew complete --land calls (reckon/crew_run_commands.py, near line 2474) and the one that runs the marker check. merge.land_merge, which crew merge calls, reads no blob content, so a test against it would pass on the unfixed code;
  • the landing's survived report names the binary path as judged by blob identity;
  • a merge candidate whose tree drops the binary file, or alters it, is refused by the landing check, naming that path;
  • the text file's marker check behaves as at base.

Negative control: read the binary path through the text _show again, and the first case raises UnicodeDecodeError. §2 — A land step that fails after promotion exits non-zero and says so

Why. _land_a_promoted_run (reckon/crew_run_commands.py, near line 2393) catches only merge_module.MergeError around the merge. Any other exception escapes the land step, even though the run is already promoted and released: the decode error in §1 is one, and an OSError or a git failure the merge module does not wrap would be others. The report never carries steps.land: {ok: false}. The standalone reckon crew merge verb (near line 65) has the same gap, because it converts only MergeError into a refusal. The session that hit the crash says the command exited 0. An uncaught exception from a click command normally exits 1, so that observation needs reproducing before it is explained.

Deliverable. First reproduce it. Make the merge raise a non-MergeError exception inside a crew complete --land call driven through click's CliRunner, against a temporary repository, and record the exit status and output the base produces. Then make every exception raised after promotion and before the land step reports success a failed land step. The command emits its JSON report with steps.land set to {ok: false, error: …}, naming the exception's type and message, and exits non-zero. The report also names the crew merge command that resumes the landing, as a MergeError refusal already does. crew merge reports such an exception as a refusal with a non-zero exit rather than a traceback.

One module-level function in reckon/crew_run_commands.py owns the mapping from a merge failure to a land refusal: its type, message, resume command and exit status. Today that mapping is written out at two sites: crew merge's MergeError handler (near line 77) and the promoted-land merge refusal handler near line 2485. Both call the new function and keep no catch of their own, so the sites cannot drift apart the first time one changes. The handler near line 2449 is not a merge failure. It catches a repository-resolution failure from merge_module.project_repository, reported before any merge or resume command exists, and keeps its own report, which has no resume key.

Two neighbouring handlers are not refusals and keep their own handling unchanged. The MergePushOutstandingError handler near line 2475 reports a landed merge whose push is outstanding: ok: true, steps.land.push_outstanding, and exit PUSH_OUTSTANDING_EXIT, pinned by tests/test_a_reviewed_head_lands_without_touching_the_index.py near line 352. The release-step handler near line 2524 records a push error under steps.release.push_error. It lives in crew_run_commands.py, beside its callers, rather than in reckon/crew/merge.py, so this section and §1 stay on disjoint files. Promotion and release are not rolled back: the report states that they happened, and that the merge did not.
