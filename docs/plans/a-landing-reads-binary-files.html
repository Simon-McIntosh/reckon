What happened. On 2026-10-20, power_convertor run r-20261020T134904187980-disruption-induced-voltages carried a 10 MB GIF, docs/figures/iter-disruption-induced-voltages/md-vs-vde.gif. reckon crew complete --land promoted the run (c639a8d7) and released it (efc56be5). That session landed the run by hand: git merge --no-ff 1dbb35aa made 726d539f, the gate passed at that head, and the tree was cleaned up.

A promoted run that is not merged reads as landed to every reader of the ledger, while its change reaches no one. Two defects combine to produce it. §1 removes the crash, and §2 makes any failure after promotion report itself.

§1 — The landing marker check reads a blob as bytes

Why. reckon/crew/merge.py's _run (near line 108) runs every git call with text=True, so git's output is decoded as UTF-8. _show (near line 211) returns git show <revision>:<path> through it, and the landing check reads each changed path at the base and the head through _show (callers near lines 274, 275 and 306). It splits each path into distinctive marker lines, so it can refuse a merge that dropped a change. A binary blob does not decode, so the check raises UnicodeDecodeError instead of comparing.

Deliverable. The landing check reads blobs as bytes. A path whose content at the base or the head is binary is compared by blob identity: the merged tree must carry the head's blob, or the base's when the change deleted the path. It is never split into lines. A text path is compared by marker lines exactly as it is today. _run stays a text call for every other git command. The blob read is the only call that takes bytes. Choose the narrowest test for "binary", such as a NUL byte or a failed UTF-8 decode, and name it in a docstring.

Done when tests/test_a_landing_reads_binary_files.py builds a temporary repository with every environment-resolved directory pointed at temporary paths. Its head adds a small binary file, one that contains a NUL byte and is not valid UTF-8, and edits a text file. The test holds all of these:

  • merge.land_merge lands that head without raising, and the merged tree carries the head's blob for the binary path;
  • a merge candidate whose tree drops the binary file is refused by the landing check, naming that path;
  • the text file's marker check behaves as at base.

Negative control: read the binary path through the text _show again, and the first case raises UnicodeDecodeError. The gate runs the new test with tests/test_a_reviewed_head_lands_without_touching_the_index.py, tests/test_one_call_lands_a_run.py and tests/test_crew_tool_carries_the_write_verbs.py, at base and at head, judged by delta. Each arm's log names its revision, ends in EXIT=, and lives under the run directory. baseline_suite and after_suite record failure_ids in the form tests/<file>::<name>. ruff check and ruff format --check add no findings on the paths staged. §2 — A land step that fails after promotion exits non-zero and says so

Why. _land_a_promoted_run (reckon/crew_run_commands.py, near line 2393) catches only merge_module.MergeError around the merge. Any other exception escapes the land step, even though the run is already promoted and released: the decode error in §1 is one, and an OSError or a git failure the merge module does not wrap would be others. The report never carries steps.land: {ok: false}. The standalone reckon crew merge verb (near line 65) has the same gap, because it converts only MergeError into a refusal. The session that hit the crash says the command exited 0. An uncaught exception from a click command normally exits 1, so that observation needs reproducing before it is explained.

Deliverable. First reproduce it. Make the merge raise a non-MergeError exception inside a crew complete --land call driven through click's CliRunner, against a temporary repository, and record the exit status and output the base produces. Then make every exception raised after promotion and before the land step reports success a failed land step. The command emits its JSON report with steps.land set to {ok: false, error: …}, naming the exception's type and message, and exits non-zero. The report also names the crew merge command that resumes the landing, as a MergeError refusal already does. crew merge reports such an exception as a refusal with a non-zero exit rather than a traceback. Promotion and release are not rolled back: the report states that they happened, and that the merge did not.

Done when tests/test_a_failed_land_exits_nonzero.py drives both commands through CliRunner against a temporary repository, with every environment-resolved directory pointed at temporary paths, and with merge_module.land_merge patched to raise a UnicodeDecodeError. The test holds all of these:

  • crew complete --land exits non-zero, and its JSON report carries steps.land.ok false, an error naming UnicodeDecodeError, and the resume command;
  • crew merge exits non-zero with that error in its output and no traceback;
  • a MergeError refusal reports as it did at base.

The base arm records what the unpatched code did, the reproduction asked for above. Negative control: narrow the handler back to MergeError, and the first case escapes the land step.
