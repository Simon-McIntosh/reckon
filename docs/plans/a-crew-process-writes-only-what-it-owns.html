§1 — Why: two writers acted on state that was not theirs

A hold transition left every run record rewritten and uncommitted. nova-39 reported on 7 November that nova's checkout held 356 modified run records, all written at 02:11:02 local. Each had the same change: the retired follow_on_paths key renamed to outside_scope_paths. They were written 1 min 44 s before nova commit a03fe0706, “chore(holds): close hold-codex-20261107011059”. record_hold_checks (reckon/ledger.py near line 3440) calls write (near line 2007). That brings every per-run file into line with its aggregate row, through normalize_outside_scope_paths (reckon/run_record.py near line 33), but _commit_state_write (near line 2438) is then given only the aggregate's path. The function's own comment says the run rows stay byte-identical across a hold transition; they do not when a row still carries the retired key. Reckon's own checkout had carried 1,319 such rewrites since hold close 916bd85724 on 24 October. Both were committed by hand as their own change, nova's at 274e2b00c and reckon's at ca3029c385, after each file was checked to differ from its committed JSON by that rename alone. Any commit made without a pathspec would otherwise have swept them in.

A session host followed a session it did not own. nova-39 reported the same day that its session host (record session-hosts/457425-270383021.json, owner 457774) held three follower children. One was for nova-8a's session 35a66cc6-f4f1-4358-8dbb-99c9333c7249 (pid 1042564, started 08:10:21Z), 5 s after nova-8a's own follower (pid 4035663) exited “settled”. nova-8a's host (2339302-329925366.json) held none. Two consequences followed:

  • nova-39's UserPromptSubmit and Stop hooks showed and blocked on 35a66cc6's obligations, including promoting nova-8a's run, which a coordinator acting on them would have landed for another session.
  • nova-8a's re-arm through _ask_session_host_for_follower (reckon/crew/dispatch_watch.py near line 770) returned True with nothing spawned. Its test is watch_state(...)["session_attached"], which any follower satisfies. Meanwhile the misplaced follower held the session's single-follower lock.

The pair then stayed with the wrong host. When nova-39 stopped 1042564, its host started a replacement, pid 1076196, within a minute, because the host's tick (reckon/crew/session_host.py near line 512) restarts a child that exits other than settled unless another host's live follower holds the pair (_foreign_live_follower, near line 460), and once 1042564 was gone none did. So the repair is to stop a host from being asked for a pair that is not its own (§3); a restart guard alone could not have prevented it, and a host cannot tell which sessions its owner holds, since one host serves both a Claude session id and a crew session name. nova-8a's own host, pid 2339833, alive and reading the same FIFO inode its record names, still listed no child after _rearm_session_follower, which returned False. The live follower held the session's lock throughout.

The host a request reaches is chosen from the caller's CLAUDE_PID (_session_host_owner, near line 583), while the request names a session. So a crew call made under one session's Claude process that names another's session asks the wrong host. _rearm_session_follower (near line 786) already refuses that case; the ask does not.

§2 — A hold transition commits every run file it rewrote

Deliverable. write in reckon/ledger.py (near line 2007) already knows which per-run files it rewrote: _keep_run_files_identical (near line 1899, called near line 2174) returns them as snapshots. Two changes use that list. First, write's own commit=True branch (near lines 2192–2200) passes those paths with the aggregate's to _commit_state_write, which closes the same leak for its other committing callers (reckon/crew_run_commands.py near line 3561, reckon/crew/promotion_records.py near line 1082, reckon/crew/routing.py near lines 3003 and 3130). Second, write keeps its int return and gains a keyword-only changed_paths list, filled from the same snapshots. record_hold_checks (near line 3440, reached in production from reckon/budget.py near line 1911), which commits under its own hold subject, passes that list to its _commit_state_write call. So no write leaves a run record rewritten and uncommitted. The inline comment before the aggregate load in record_hold_checks, which claims the run rows stay byte-identical, is corrected to what the code does.

Two negative controls: passing only the aggregate's path to _commit_state_write from record_hold_checks leaves the run record modified in the first case, and doing so in write's commit branch leaves it modified in the third. §3 — A host is asked to follow only its own session

Deliverable. The worker first reproduces, in a temporary crew home, how a follow request for one session reaches another session's host. It records the path it finds in the run directory: a review the reflex dispatches for another session's run, a resume, or another. Then _request_host_follower (reckon/crew/dispatch_watch.py), which composes the request line, writes none when the session it names is not _calling_session(), as _rearm_session_follower already refuses. Both writers of a follow request pass through it: the ask path, and a follower handing its pair to a waiting host (_hand_off_to_waiting_host, near line 870, reached from _hand_off_from_follower in reckon/crew_follow_commands.py near line 625). The ask then returns False, since no host attaches; _ask_session_host returns only a boolean (near line 746), and the ownership reason stays in _rearm_session_follower (near line 785), which already gives it. _ask_session_host_for_follower (near line 770) tests _session_host_child_pid (near line 695), the calling host's own census, instead of the session-wide attachment, so a re-arm reports True only when its own host runs the child.

§4 — The obligations hooks report only their own session

Deliverable. _session_from_followers (reckon/hooks/coordinator_obligations.py, defined near line 439 and called from locate_session near line 865) already returns a registration whose session equals the hook payload's harness session. But it walks read_followers in name order and returns the first registration whose follower descends from the caller's Claude process, before reaching the harness session's own. So another session's follower held by the caller's host is adopted as the caller's session. It instead scans every registration for the exact harness-session match first, and falls back to descent only when the harness session has none.

§5 — A re-armed host follows its session's live runs at once

Why. nova-4a reported this on 7 November, with the lead's go-ahead. When the Monitor running plugins/crew-host/bin/crew-host expires after 30 minutes and is re-armed, the new script waits silently on its FIFO for a first request before it execs reckon crew host --first-request (near lines 47–67). A follow request arrives only with a dispatch, so a session with live runs and no new dispatch shows an empty pane indefinitely. The lead saw this for about an hour, and several re-armed windows delivered no events while runs changed state. nova-4a's workaround was to write {"project":"nova","session":"<id>"} to the FIFO by hand on every re-arm.

Deliverable. On start, the script asks reckon which projects have live runs owned by its owner's session. If there is one, it execs the host at once with that project's request as the first request; each further project is written to the FIFO, so the host follows all of them. With none, it prints one line saying it is waiting for a dispatch, then waits as today. The session it asks about is its owner's own, the session §3 makes the only one a host may follow.

Done when a new tests/test_a_rearmed_host_follows_live_runs.py shows three things, running the script with a stubbed reckon and a temporary state directory: with one live run owned by the session, the host is started at once with that project's request; with live runs in two projects, the second is written to the FIFO; and with none, the script prints its waiting line and starts no host. Two negative controls: waiting on the FIFO before the live-run check leaves the first case with no host; and dropping the waiting line fails the third case. The test files covering plugins/crew-host add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. Write paths: plugins/crew-host/bin/crew-host and tests/test_a_rearmed_host_follows_live_runs.py. It reads §3's ownership rule, so it waits for §3.
