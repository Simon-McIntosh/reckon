§1 — Why: two writers acted on state that was not theirs

A hold transition left every run record rewritten and uncommitted. nova-39 reported on 7 November that nova's checkout held 356 modified run records, all written at 02:11:02 local. Each had the same change: the retired follow_on_paths key renamed to outside_scope_paths. They were written 1 min 44 s before nova commit a03fe0706, “chore(holds): close hold-codex-20261107011059”. record_hold_checks (reckon/ledger.py near line 3440) calls write (near line 2007). That brings every per-run file into line with its aggregate row, through normalize_outside_scope_paths (reckon/run_record.py near line 33), but _commit_state_write (near line 2438) is then given only the aggregate's path. The function's own comment says the run rows stay byte-identical across a hold transition; they do not when a row still carries the retired key. Reckon's own checkout had carried 1,319 such rewrites since hold close 916bd85724 on 24 October. Both were committed by hand as their own change, nova's at 274e2b00c and reckon's at ca3029c385, after each file was checked to differ from its committed JSON by that rename alone. Any commit made without a pathspec would otherwise have swept them in.

A session host followed a session it did not own. nova-39 reported the same day that its session host (record session-hosts/457425-270383021.json, owner 457774) held three follower children. One was for nova-8a's session 35a66cc6-f4f1-4358-8dbb-99c9333c7249 (pid 1042564, started 08:10:21Z), 5 s after nova-8a's own follower (pid 4035663) exited “settled”. nova-8a's host (2339302-329925366.json) held none. Two consequences followed:

  • nova-39's UserPromptSubmit and Stop hooks showed and blocked on 35a66cc6's obligations, including promoting nova-8a's run, which a coordinator acting on them would have landed for another session.
  • nova-8a's re-arm through _ask_session_host_for_follower (reckon/crew/dispatch_watch.py near line 770) returned True with nothing spawned. Its test is watch_state(...)["session_attached"], which any follower satisfies. Meanwhile the misplaced follower held the session's single-follower lock.

The pair then stayed with the wrong host. When nova-39 stopped 1042564, its host started a replacement, pid 1076196, within a minute, because the host's tick (reckon/crew/session_host.py near line 512) restarts a child that exits other than settled unless another host's live follower holds the pair (_foreign_live_follower, near line 460), and once 1042564 was gone none did. So the repair is to stop a host from being asked for a pair that is not its own (§3); a restart guard alone could not have prevented it, and a host cannot tell which sessions its owner holds, since one host serves both a Claude session id and a crew session name. nova-8a's own host, pid 2339833, alive and reading the same FIFO inode its record names, still listed no child after _rearm_session_follower, which returned False. The live follower held the session's lock throughout.

The host a request reaches is chosen from the caller's CLAUDE_PID (_session_host_owner, near line 583), while the request names a session. So a crew call made under one session's Claude process that names another's session asks the wrong host. _rearm_session_follower (near line 786) already refuses that case; the ask does not.

§5 — A re-armed host follows its session's live runs at once

Why. nova-4a reported this on 7 November, with the lead's go-ahead. When the Monitor running plugins/crew-host/bin/crew-host expires after 30 minutes and is re-armed, the new script waits silently on its FIFO for a first request before it execs reckon crew host --first-request (near lines 47–67). A follow request arrives only with a dispatch, so a session with live runs and no new dispatch shows an empty pane indefinitely. The lead saw this for about an hour, and several re-armed windows delivered no events while runs changed state. nova-4a's workaround was to write {"project":"nova","session":"<id>"} to the FIFO by hand on every re-arm.

Deliverable. The script stops waiting on the FIFO before it starts the host: it execs reckon crew host at once, with no first request. The host (crew_host, reckon/crew_follow_commands.py near line 2775, running reckon/crew/session_host.py's run near line 710) reads its owner's session on start, from the same environment _calling_session() reads. For each of its owner's sessions and each project, it asks the judgement the host already holds of whether a pair owes a pane, live_work_run (reckon/crew/session_host.py near line 312, through the _live_view seam near line 406), which delegates to population_has_live_work (reckon/crew/station_subscriber.py near line 250). It composes no scan or terminal set of its own, so a run owes a pane exactly when the follower would not settle on it. Those are the owner's current session and every session named in the children of the owner's previous session-hosts record whose entry carries owner_checked: true. That mark tells the owner's own sessions apart from a foreign pair a host kept wrongly, such as the nova-8a session 35a66cc6 that §1 records on nova-39's host. §3 makes _request_host_follower (reckon/crew/dispatch_watch.py) put owner_checked: true on the request line once its ownership guard has passed. §5 reads that mark and carries it through the host. Today parse_request (reckon/crew/session_host.py near line 193) returns only the project and session, and the child entries SessionHost.record() writes carry only project, session, pid and settled_at. §5 keeps the mark in both, so it reaches the child entry a later host reads. These are this section's two additions to the host's surface, with waiting_for_dispatch below, and neither can carry the other: the widened parse_request return is the only route for the mark from the request line into the child entry, and waiting_for_dispatch is the only field that names a live host with nothing to follow. Neither retires an existing field. An entry without it is skipped, which includes every record written before this fix. The host's own start-up adoptions are marked too, since they are drawn only from marked entries and the owner's current session. That record is keyed by the owner's pid and start time, which survive /clear while the session id does not, so a run dispatched before a /clear is still followed. The host reads that record before it writes its own. The key is session, the value _calling_session() returns. It is not session_id, which is empty on every live pointer and is what resumption._pointer_session (reckon/crew/resumption.py near line 753) reads. The host follows each project they name, exactly as if a request for that pair had arrived. With none, the host writes nothing to stdout, because its stdout is the pane and only its children speak there (crew_host's docstring). SessionHost.record() (reckon/crew/session_host.py near line 368) gains a waiting_for_dispatch field. It is true when the start-up scan finds no live run and false once a child starts. supervise already writes the record at start (near line 667), so the field is the only change there. The host then serves its FIFO as today. A first request, when one is given, is served as today.

Host 69000, owned by session 6f111d4a and fifteen days old, had held one (29401) for about 37 hours. When reckon-0f stopped the follower under reckon-a1's host and re-armed through its own, host 69000 started a new 404513fc follower (405039) within seconds. Its record, session-hosts/68551-241698294.json, listed children for both 6f111d4a and 404513fc when reckon-a1 and reckon-0f read it at about 22:40Z on 7 November; the record has since dropped the foreign child, after that follower exited. A process listing, reckon-a1's and 404513fc's host records and the run directory listing are kept in ~/.cache/reckon-follower-ownership/2026-11-07T2140Z-a1-holds-404513fc-follower.txt. §3 stops a new foreign request, including the follower's own hand-off (_hand_off_to_waiting_host, reckon/crew/dispatch_watch.py near line 870), which writes through _request_host_follower. §5 skips unmarked children only when a new host adopts its predecessor's record. Neither stops a running host from restarting a child it already holds. SessionHost.tick (reckon/crew/session_host.py near line 585) restarts every exited child that is not settled, on the backoff, and is held back only while _foreign_live_follower (near line 533) sees another live follower for the pair. So a host that took a foreign pair keeps restarting it for as long as the host lives.

Deliverable. A running unmarked child is left to run until it exits; the host does not signal it. The owning host no longer defers to such a child. Today _foreign_live_follower (near line 533) reads any live follower for the pair as already following it, so reckon-0f's own host declined to arm while host 69000's duplicate printed to another session's pane, and reckon-0f's pane stayed empty until it stopped the duplicate and wrote its request within the second before 69000 respawned it.
