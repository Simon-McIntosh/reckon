§2 — A review run promotes itself once its record is stored

Deliverable. A run in the review role promotes itself, with promoted_by: review-self on its ledger row, when all of these hold:

  • its manifest reads complete;
  • its worker and supervisor have exited;
  • the record it was dispatched to store is on disk with a status the readers act on.

This covers run reviews, plan reviews and code reviews. The review's record is its whole deliverable, so promoting the run reads nothing a coordinator would add. The reviewed run is untouched: its acceptance stays scoped to merged runs, as the lead ruled for a-review-is-sized-to-its-risk §4.

The promotion reuses the promotion call that accept_clean_review makes (reckon/crew/recovery_review_acceptance.py). It runs as a separate branch, for review-role pointers only, because that pass skips every review node (_is_review_node) to stop a chain of reviews of reviews. The skip stays in force for acceptance and for review dispatch. The new branch only promotes the review run itself and never dispatches a review of it, so no chain can start. A review run whose record is missing or unparsed is left for the coordinator, with the reason recorded.

Interface. promoted_by: review-self is one more value in the ledger's existing promoted-by vocabulary (reckon/ledger.py), beside review-acceptance. It stays distinct because it names a different act: a review run's own promotion, not acceptance of the run it reviewed. It retires a hand step: the live classifier's next action "promote the completed review run once its verdict is read" no longer appears for a run this branch promotes.

Done when tests/test_a_review_run_promotes_itself.py passes in a temporary crew home and repository:

  • A complete review run with an exited worker and a stored parsed record is promoted with promoted_by: review-self, and no longer counts as unreconciled at dispatch.
  • One whose worker pid is alive is not promoted.
  • One with no stored record is not promoted, and its reason is recorded.
  • An implement run is never promoted by this path.
  • The negative control, which drops the exited-worker condition, fails the live-worker case. It is logged under the run directory.
  • The existing tests that import recovery_review_acceptance pass.

Write paths: reckon/crew/recovery_review_acceptance.py, tests/test_a_review_run_promotes_itself.py.

§3 — A test-only change earns a light review

Deliverable. The tiers in review_tier (reckon/review_tiers.py) change for a run whose changed paths include test source but no runtime source. Such a run earns the light tier, not none. A weakened, skipped or deleted assertion is a change to what the suite protects, and only a reader can see it. A run that changes only plans, evidence, research, figures or state keeps none. A run that changes runtime source keeps today's light/full rule.

Done when tests/test_a_test_only_change_earns_a_light_review.py passes:

  • A run changing only tests/… is light.
  • A run changing only docs/… is none.
  • A run changing reckon/… and its test keeps the tier the current rule gives.
  • Existing tests that assert none for a test-only change are updated to the new tier, never deleted, each named in the manifest.
  • The test files that import review_tiers pass.
  • The negative control, which restores none for test source, fails the first case. It is logged under the run directory.

Write paths: reckon/review_tiers.py, tests/test_a_test_only_change_earns_a_light_review.py, plus the existing test files whose test-only assertion changes, each named at dispatch.

§4 — A manifest's evidence is checked before promotion

Deliverable. audit_manifest in reckon/crew/reports.py, which reckon crew check-manifest calls, gains two findings.

  • Gate logs. Every file named in test_logs must carry its literal command near its head and end with an EXIT=<n> line. Whether that command is abbreviated is judged by the existing gate-command reader gate_command_prose (reckon/crew/promotion_gate.py), which already classifies an angle-bracket placeholder in a recorded gate command, so the two judges cannot disagree. The EXIT= line is read through the reader that promotion already uses for a gate log's exit status, if one exists, and the manifest names it.
  • Plan labels. Added lines in production Python source (not under tests/) whose comment or docstring text carries a plan-section reference (§ followed by a digit) are refused. Each finding names the file and line.

A worker runs check-manifest before it finishes, so it sees these findings while it can still fix them. Test source is exempt from the plan-label check, because fixtures legitimately carry section identifiers as data. Both checks are new entries in audit_manifest's existing finding list. They open no new refusal family and add no option.

Done when tests/test_a_manifest_evidence_is_checked.py passes:

  • A gate log with no EXIT= line is a finding.
  • So is a log whose command reads pytest -q <five tests>.
  • So is an added production comment carrying §9.
  • An added test fixture string carrying §3 is not.
  • A well-formed manifest has no findings.
  • The test files that call audit_manifest or check-manifest pass.
  • The negative control, which drops the EXIT= check, fails its case. It is logged under the run directory.

Write paths: reckon/crew/reports.py, tests/test_a_manifest_evidence_is_checked.py, and reckon/crew/promotion_gate.py only if gate_command_prose needs a public name to be called from reports.py.

§5 — A producer seated on another node reads as live

Deliverable. freshness in reckon/crew/obligation_snapshot.py stops reading a producer on another node as absent. The snapshot it reads records no producer host: document_for writes the pid, its start time, the start instant and the code stamp. freshness is called with the document alone, from two sites in reckon/hooks/coordinator_obligations.py. So freshness gains the project, and both callers pass it. When the recorded pid is not running locally, it asks the existing owner of that judgement, reckon/crew/watch_unit.py, whether the project's seat names a foreign host whose stream is still fresh (_seat_names_a_foreign_host, _seat_stream_fresh). A yes counts as a live producer, and the hook then reports stale or fresh as usual. No new host comparison is written; if those helpers need a public name to be called from obligation_snapshot, they get one where they are. A seat on this host whose pid is dead, or a foreign seat whose stream is stale, still reads as no-producer.

Done when tests/test_a_remote_producer_reads_as_live.py passes:

  • A project whose seat names another host with a fresh stream is not no-producer.
  • The same seat with a stale stream is no-producer.
  • A local producer whose pid is dead is no-producer.
  • The test files that import obligation_snapshot or reckon/hooks/coordinator_obligations.py pass.
  • The negative control, which judges every producer by local pid, fails the remote-live case. It is logged under the run directory.

Write paths: reckon/crew/obligation_snapshot.py, reckon/hooks/coordinator_obligations.py, reckon/crew/watch_unit.py (a public name only), tests/test_a_remote_producer_reads_as_live.py.

§6 — A review record a reviewer wrote is checked before it finishes

Why. store_review in reckon/crew/review.py refuses a record whose status is outside RECOGNISED_REVIEW_STATUSES, because no reader acts on such a record. A reviewer can bypass it by writing the record straight into the review store. A peer session found one on 2026-10-13: the review of r-20261013T035012337867 wrote status: complete with an inline json.dump, and promotion would have read the run as unreviewed. Every reviewer passes check-manifest before it finishes, so that is where the check belongs as well.

Deliverable. audit_manifest in reckon/crew/reports.py, which check-manifest runs, re-validates each review record among a review run's write paths with the same status check store_review applies, and refuses the manifest naming the record, the status found and the accepted set. The check is one function both callers use, so the accepted set has one owner.

Done when a test writes a review record with status: complete at a review run's write path and check-manifest refuses it with that status named. A record written through store_review passes the same check. The test files importing reckon/crew/reports.py show no added failure against base. The negative control removes the audit-side call, and the hand-written case must then pass check-manifest. It is logged under the run directory. Write paths: reckon/crew/reports.py, reckon/crew/review.py and tests/test_a_hand_written_review_record_is_refused.py.
