reckon · fleet node operation

The fleet node stays in service

The fleet allocation, job 1281970, has run on 98dci4-clu-2002 since 8 October. Slurm drained that node at 08:11:39 CEST the same morning, six hours after the move onto it, with the reason Kill task failed. The node the fleet left, clu-2018, was drained the same way on 3 October, and the GPU serving node gpu-0003 was drained the same way on 17 October. Each time, the step or job that failed to die had been cancelled by this account. The previous plan moved the fleet and fixed what loaded the node; it left the mechanism that drains a node untouched. This plan removes that mechanism, repairs the migrate command so it can carry a second move, bounds each worker step's memory, measures what the watch producers cost, and then moves the fleet on a schedule of our choosing.

§1 — What drained three nodes, and what loads this one

A drain does not end a running job. It stops the scheduler placing new jobs on the node, and an administrator must resume the node after the last job leaves. The fleet job has no wall clock, so the drain itself costs nothing today. Two things make it matter. First, if the job ends or is requeued, it cannot return to this node. Second, an administrator servicing the node may end the job. The move is therefore not urgent. But it should not be needed every week, and at present it is.

The configuration explains the timing. KillWait is 30 s and UnkillableStepTimeout is 60 s. When a step is cancelled, slurmstepd signals every process in the step's cgroup, then SIGKILLs them. If any process survives the timeout, slurmd drains the node. The only process SIGKILL cannot end is one in uninterruptible sleep, which on this cluster almost always means a GPFS call or a GPU driver teardown. The job records 482 steps CANCELLED by 39486 against 5,606 completed. Each cancellation is one draw against that timeout. Every step that ends by cancellation rather than by its task exiting carries a chance of draining the node. The empty cgroups step_251, step_1080 and step_5531 are still present under the job.

The stop path in reckon/crew/dispatch_launch.py sends SIGTERM to the worker pid and, after the stop grace or the terminal-manifest grace, sends SIGKILL. Two cases are possible. If that pid is the srun client, the SIGKILL ends the client and the step is cancelled from outside. If it is the worker inside the step, the SIGKILL leaves the step's other processes to slurmstepd's kill. Either way, ending the step is the scheduler's kill rather than the task's own exit, and that is the event that drains. Which of the two it is, and which run step 251 belonged to, is §2's question.

§3 — A stopped worker ends inside its step

The step must end by its own task exiting, never by the scheduler's kill. The per-run supervisor already owns a worker's parentage, its stop signals and its exit record. It is started by _start_supervisor (reckon/crew/dispatch_launch.py:2078), its entry point is reckon/crew/supervisor_main.py:23, and its stop path is at dispatch_launch.py:2860–2884 and 2936–2963. So this section extends that supervisor and adds no new reaper or process.

For a worker placed as a step (its argv built by placement.step_prefix), the supervisor delivers the stop to the sandboxed worker. That means the processes below the sandbox's PID-namespace init, which are the step task's descendants other than the bwrap processes themselves. It never signals the task itself, and never the srun client or any process in its local subtree. Two probes on 18 October set both boundaries:

  • A signal to the client made Slurm cancel step 1281970.6508 in that second (§2).
  • A SIGTERM to the outer bwrap task, checked by its cgroup and start time, ended step 1281970.6958 as CANCELLED|0:15 in 3.02 s. The task died of the signal, and slurmstepd then tore down what was left in the step.

When the sandboxed worker exits instead, the namespace init exits with it. The task then returns an exit status rather than dying of a signal.

The supervisor reads the task's identity from a record its wrapper writes before it execs the sandbox: job, step, pid and start time. It confirms that the task belongs to the step from facts local to the kernel: the task's cgroup names the step, and its start time matches the record. scontrol listpids left out a just-started task in two probes, so it is not the check. The supervisor then waits for the client to exit by itself. The later escalation is SIGKILL to the same inner processes, still never to the task or the client, and never a cancel. The wait has no deadline shorter than a GPFS stall. If the worker outlives a long ceiling of at least ten minutes, the supervisor records the step's processes and their wait channels to the run directory and keeps waiting.

There is one case where the client is signalled: a step that has not started. srun --overlap can wait indefinitely for a step allocation, and a stop must still end such a run.

  • The wrapper execs the sandbox only after its record has been written (&& exec, not ; exec), and exits non-zero otherwise. So no worker runs inside a step that has no record.
  • Each placed step is named after its run id (srun --job-name), so Slurm itself can say whether the step exists. If no record has appeared 30 s after the first stop attempt, the supervisor asks the scheduler for a step of the fleet job carrying that name. Slurm lists a step only once it has been created, so no such step means the request is still pending. Only then does it signal the client, once, by pid alone, under its own sender reason. At that point the signal withdraws a pending request; it does not cancel a running worker. If the scheduler lists the step without a record, the client is not signalled. The supervisor records a refusal naming the step and keeps waiting.
  • A record that appears inside the window returns the stop to the inner path.

A step that ends normally can drain the node too. When the task exits, slurmstepd kills whatever is left in the step's cgroup under the same 60 s timeout. The probe therefore also checks that the sandbox's PID-namespace init holds the task open until every descendant has exited. If it does not, this section is re-planned; it is not patched with a second waiter.

Done when two things hold. First, a unit test proves that, for a step-placed worker, the stop path delivers only to processes below the sandbox init. It records no signal to the task or to any process in the srun client's local subtree.

Second, a probe on the fleet allocation stops a worker step whose process and child both ignore SIGTERM and would sleep 120 s against the 55 s stop grace. The step must end after the grace, through the SIGKILL to the inner processes, well before the sleep would have finished. When it does:

  • sacct reports the step as not CANCELLED, with a zero signal field in its ExitCode. That is COMPLETED, or FAILED carrying the worker's own exit status.
  • The sender receipts show the inner processes as delivered, and show no signal to the task or to the client.
  • The node's state is unchanged.

The negative controls are the two saved probes, step 1281970.6508 (the client signal) and step 1281970.6958 (the task signal). Both read CANCELLED, and neither is re-run.

§4 — The migrate command starts a second move

reckon fleet-node migrate reads the newest move-*/ledger.json, and once that ledger's next step is done it prints migration complete forever. Its census step is reachable only when no ledger exists, so the command can carry exactly one move. Measured 18 October: --dry-run printed migration complete while the fleet ran on a drained node. The fix: when the newest ledger is done, the next invocation begins a new move at census with a new move-<stamp> ledger, and --dry-run says so. This holds even when the fleet still runs on the job that move promoted, which is the case on 18 October: job 1281970 is both the promoted job and the drained one. Census and layout only read state and write records; stand-up is the first step that requests anything and needs its own invocation, so starting a census after a finished move costs nothing. The earlier ledger is kept untouched. In the same file pair, reckon fleet-node status replaces its warning that "the allocation ends when the drain completes". The replacement states that the scheduler places no new job on the node, that the allocation continues until it ends, and that the node returns only when an administrator resumes it. Neither change adds or retires an option: the first changes what the existing command does when its newest ledger is done, and the second replaces one string.

Done when tests in tests/ cover a completed ledger followed by a fresh census and the dry-run text in both states, and the status wording. The negative control is a ledger mid-move, at cutover, which must still resume that move rather than start a new one.

§5 — A rehearsal at the current head

The previous move needed a hand-written cutover-one.py because the cutover relay was broken on the night. Since then, §16 of the previous plan fixed the relay, and the code has moved for ten days. Run reckon fleet-node migrate --rehearse on a probe session in the fleet allocation at the head that §4 lands on. A finished rehearsal ledger answers rehearsal complete without running (fleet_migrate.py:708–716). rehearsals/probe-rehearsal/ledger.json already reads done, so the rehearsal uses a probe session named for this run (the name must start with probe-), passed with --session, whose ledger does not exist before it starts. Done when that new rehearsal ledger, created after dispatch, reaches its pass state with the probe's tab list and conversation id the same before and after, recorded in the evidence fragment. The negative control is a probe whose recorded tab is removed before the check, which must be refused.

The probe session has to exist before the first --rehearse call. The census refuses a name it cannot find in the local session census. It also refuses a session that lacks two tabs and a live Claude pane (fleet_migrate.py:722–734). So the node first writes a layout ~/.config/zellij/layouts/probe-<name>.kdl with two tabs, matching the probe of 8 October: conversation, running a Claude conversation that has one exchange, and shell. It then asks the node's supervisor to start the session with the request line session probe-<name> probe-<name> on the fleet request FIFO, the same relay the rehearsal's own start step uses (fleet_migrate.py:768–773). Starting through the supervisor puts the Claude pane outside the worker's sandbox, where its transcript can be written. Every call runs with the fleet's zellij socket directory (XDG_RUNTIME_DIR and ZELLIJ_SOCKET_DIR under /tmp/<uid>-fleet), because a plain shell sees every session as exited. When the rehearsal has passed, the node ends probe-<name> by name and removes both its layouts. It never uses a focus-relative zellij action.

A dispatched node cannot take these steps. Dispatch confines a node's writes to repository roots and delivery roots (_require_write_paths_in_authority, reckon/crew/dispatch_admission.py:1773). The layout and the rehearsal ledger live under the operator's home, in ~/.config/zellij/layouts/ and ~/.local/state/fleet/migration/rehearsals/. Comment c-s5-authority records the refusal. So §5 runs one of two ways, and the choice is the lead's. In the first, the operator takes the steps above from a plain ssh shell on the fleet node, with the fleet socket directory exported, and a worker then writes only the evidence fragment from the ledger. In the second, a reckon change first lets a node declare those two fleet-state paths. §5 is not dispatched until that choice is made.

§6 — A worker step carries a memory bound

The four processes killed on 17 October were not runaways. They belonged to two nova solver runs, r-20261017T073925596435-axis-facing-owner (steps 5614 and 5621) and r-20261017T102932384946-owner-cell-current (step 5700). Each step's stderr records Slurm's oom_kill event, and both runs were doing map solves at the 2,098-point size, which legitimately need 52–59 GB. The defect is placement, not leakage. The fleet allocation is 96 GB shared by every session and worker, so one such solve takes more than half of it. A second one, or the sessions' own growth, takes the whole job to its limit, and the OOM killer then picks the largest process anywhere in the job.

Every worker step is therefore placed with an explicit --mem, so undeclared work stays inside a share that leaves room for the sessions. placement.step_prefix (reckon/crew/placement.py:233) is the one owner of a step's options and carries the bound. fleet_node.placement_argv (reckon/crew/fleet_node.py:358) builds the same srun --overlap --jobid=… prefix for the migrate and place commands, so it is folded into step_prefix rather than given the bound separately. A node whose work needs more declares it through the existing dispatch --set override, recorded on the run, so no new option is added. The bound uses the memory vocabulary placement already has: memory_gb in placement.reservation_options, and DEFAULT_MEMORY with its environment override in fleet_node.py. A declaration above the fleet's per-node ceiling is placed in its own job on a *_debug partition rather than inside the fleet allocation. The decision worker-step-memory below locks a 24 GB default and a 48 GB ceiling. Done when a test shows the placed srun argv carrying the default and a declared bound, and a test shows a declaration above the ceiling routed to its own job. A probe step on the fleet allocation must also show its cgroup memory.max equal to the bound. The negative control is a probe allocating past its bound: its OOM event lands in the step's memory.events and not the job's.

§9 — A watch producer sweeps only when the crew home changes

§7 measured that one producer cycle, in watch_ticker (reckon/crew/recovery_watch.py), sweeps the whole fleet every second whether or not anything has moved. It lists every project's live/ before filtering (runs.py:705, runs.py:720), walks run directories, parses streams and calls the git shim. That is about 1,880 opens and 1,575 stats per cycle plus 1.25 git-shim calls, whatever the live pointer count. Five producers make roughly 9,000 GPFS opens a second.

The sweep runs only when the crew home changes. The change signal is inotify on live/, runs/ and the watch directory, or one mtime stat of each where inotify is unavailable on GPFS; the worker states which in the evidence. The per-live-run liveness probe stays on the fixed beat, because a process can die without touching a file. The listing filters to the producer's own project before it stats pointers.

Done when two things hold. A test drives a producer through quiet cycles and sees no directory walk and no git-shim spawn, then touches a pointer and sees exactly one sweep. Every input a gated sweep reads is covered by the change signal. That covers the budget-lift document and the classification inputs behind a reused snapshot. There is one test per input: it writes that input on a quiet beat and requires a sweep.

A 32 s strace is taken in a harness whose base revision reproduces the order of §7's figures. That positive control is several hundred openat per quiet cycle. On a quiet cycle the change must stay below a tenth of the base's openat, spawn no git, and make no more than half the base's stat calls. The stat target is half rather than a tenth because the change signal itself stamps each live pointer, stream and manifest. On 19 October, against a 30-pointer copy, the change measured 22 opens against the base's 418–471, and 99 stats against 297–334. A signal that stamps directories and lets the per-run stat ride the liveness probe would remove the per-pointer stat; that is a follow-on. The negative control is a cycle in which a pointer's mtime moves, which must sweep. A transition test must still deliver a run's death within one beat when no file moved. Because this changes load on the run trees that reckon serve also reads, the session owning that work is told before this section dispatches.

§10 — The code identity is read only when HEAD moves

Every long-running reckon process asks once a second whether reckon's code has moved: the followers, the producers, the MCP server and queue admission all reach source_code_identity (reckon/checkout_trust.py:389) through follower_code_stamp, on the FOLLOWER_FRESHNESS_SECONDS = 1.0 cadence (reckon/crew/follower_registration.py:444). Each read runs git ls-tree HEAD reckon skills, the catalogue's own read, and one git mktree per composed tree (_committed_reload_tree, checkout_trust.py:344). Measured on clu-2002 at 20:52 on 19 October, a 3.6 s sample saw 73 distinct git mktree processes. git mktree freshens an object that already exists by rewriting its mtime, so the identity tree's loose object (.git/objects/c0/8e3ea7…) had its mtime rewritten twice in three seconds. That is a metadata write to one shared GPFS inode, from every reading process on every node, every second, with no code having moved.

The identity is a function of what HEAD names, so it is memoised per source root against a stamp of the files HEAD resolves through: HEAD itself, the ref it names, and packed-refs, located once per root and including a worktree whose .git is a file. The git reads run only when that stamp moves. A read that failed is never memoised, so IDENTITY_UNKNOWN keeps the meaning it was given on 19 October. The content-stamp path for a package outside Git keeps its present behaviour.

Done when three things hold. A test reads the identity over many quiet ticks and sees no git spawn after the first. A test exists for each way HEAD moves (a commit, a branch switch, git pack-refs, a detached HEAD), each yielding the new identity on the next read. A failed read leaves the next read to run git. The negative control is a commit that touches nothing under reckon/ or skills/: the git reads must run and the identity must not change. A 30 s count on a quiet checkout, taken on the fleet allocation, compares the git processes one follower spawns: the base revision is the positive control, at least one a second, and the change must spawn none. Over the same window the identity object's mtime must not move.

§11 — A moved checkout is proved importable once

When the code identity moves, every long-running reckon process proves the new image loads before re-executing into it. It does so through reckon_imports (checkout_trust.py:707), which compiles and imports all 180 modules of the materialised reload tree in a throwaway interpreter. All of them prove the same immutable tree at the same moment. At 20:48 on 19 October, 16 such probes ran at once on clu-2002, blocked in D state on cxiBlockingMutexAcquire and cxiWaitEventWait, and the follower reported the import probe timed out after 30 s. One probe alone on the same node took 11.2 s of wall time and 3.4 s of CPU. In the preceding 24 hours, main's first-parent history moved reckon/ or skills/ 63 times, and each move starts such a herd. That herd followed the 20:47:09 merge. A 15-minute sample afterwards, with no code move, saw at most three probes at once: these were retries, each taking about 27 s. The retries stay in step with one another, because the retry gap (crew_follow_commands.py:221) carries no jitter.

Whether a tree imports depends on the tree and the interpreter, not on the process asking. The first process to prove a materialised tree records the verdict beside it, published by rename and keyed by the interpreter, and every later asker reads that verdict. Proofs of one tree are serialised by an exclusive lock in the tree's directory, so a second asker waits for the first's verdict rather than running its own. That wait is bounded by the probe's own 30 s timeout, because a follower's poll runs on its delivery path. A wait that reaches the bound with no verdict is answered as a timeout, which the follower already retries with jitter. A pass and an import failure are both recorded. A timeout is never recorded, because it says nothing about the code (see ImportProbeTimedOut), so the next asker under the lock probes alone. The retry gap gains jitter. A source checkout reloading under a content stamp has no immutable tree, so it keeps the per-process probe.

Done when the following tests pass:

  • Concurrent askers on one tree start exactly one probe subprocess, and all receive its verdict.
  • A timed-out probe records nothing, and the next asker probes.
  • A recorded failure is returned without probing again.
  • A new tree id is probed afresh.
  • A verdict recorded for another interpreter is not reused.

The measurement runs on the fleet allocation. Sixteen concurrent askers prove a freshly materialised tree. At the base revision, the positive control, sixteen probes run. At the change, one probe runs, and all sixteen answers arrive within 30 s. The negative control is a materialised tree carrying a module that fails to import. Sixteen concurrent askers must all refuse the reload, from one probe and the failure verdict it records, and none may re-execute into the tree. This section writes checkout_trust.py, as §10 does, so it dispatches after §10 lands.

§12 — A process table is read once per beat

At 02:07 on 20 October the imas-codex watch producer was using 90% of a CPU on clu-2002. Over 10 s it made 24,581 openat calls, 14,520 of which failed. A 5 s capture showed that 14,568 of its 15,019 opens were /proc/<pid>/environ, across 850 distinct processes. That is about 3.4 full reads of the node's process table a second, and 8,706 of the opens failed because the process belongs to root or another user. The reader is _processes_owning_run (reckon/crew/process_signal.py), reached from _env_scan_run_pid (reckon/crew/recovery_liveness.py). It runs once per beat for every run whose recorded pid has gone, and reads every process's environment each time. A process's environment changes only when it execs, so almost every re-read returns what the last one did.

The liveness read builds one index of the run marks it can see on each beat, and every run is answered from that index. An environment already read is reused until the process could have changed it. The key is the pid, the start tick and the executable identity, because an exec keeps the pid and the start tick but replaces the environment. The memo drops pids that have left the table. A process owned by another user is skipped by the owner of its /proc entry, without opening its environment. The stop path keeps its own check at signal time, the start-tick floor and the crew home, so a memoised reading never by itself selects a process to signal.

Done when the following tests pass:

  • A second beat over an unchanged process table opens no environment.
  • A new process is read once.
  • A pid reused by a new process is read afresh.
  • Another user's process is skipped without an environ open.
  • A reparented worker carrying the run mark is still found, both by the liveness read and by the stop path.
  • The existing tests for both modules have no added failures against the base, with paired logs.

The negative control is a process whose environment is read between its fork and its exec, and which then execs with the run mark. It must be found on the next beat, which a memo keyed on pid and start tick alone would miss. The measurement runs on the fleet allocation: a 10 s strace of a producer harness in which several runs need the scan. At the base revision, the positive control, each beat opens one environment per process for each such run. At the change, it opens no more than one per process started during the window.

§ Decisions

What default memory bound does a worker step carry, and above what declared size does a node leave the fleet allocation for its own job?

The job holds 96 GB and the sessions use about 35 GB. A 24 GB default leaves room for them. The 52–59 GB nova map solves go to their own debug-partition job, where a whole node serves them, instead of taking the fleet to the limit that failed on 17 October.

When does the fleet move off clu-2002?

Do not move now. The drain does not end the job, and the processes behind it have exited, so SDCC is asked to resume clu-2002 in place. A move happens only if SDCC asks for the node back, and then only after §3 and a passing §5 rehearsal, so the new node does not inherit the drain mechanism.
