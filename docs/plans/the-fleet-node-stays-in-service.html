reckon · fleet node operation

The fleet node stays in service

The fleet allocation, job 1281970, has run on 98dci4-clu-2002 since 8 October. Slurm drained that node at 08:11:39 CEST the same morning, six hours after the move onto it, with the reason Kill task failed. The node the fleet left, clu-2018, was drained the same way on 3 October, and the GPU serving node gpu-0003 was drained the same way on 17 October. Each time, the step or job that failed to die had been cancelled by this account. The previous plan moved the fleet and fixed what loaded the node; it left the mechanism that drains a node untouched. This plan removes that mechanism, repairs the migrate command so it can carry a second move, bounds each worker step's memory, measures what the watch producers cost, and then moves the fleet on a schedule of our choosing.

§1 — What drained three nodes, and what loads this one

A drain does not end a running job. It stops the scheduler placing new jobs on the node, and an administrator must resume the node after the last job leaves. The fleet job has no wall clock, so the drain itself costs nothing today. Two things make it matter. First, if the job ends or is requeued, it cannot return to this node. Second, an administrator servicing the node may end the job. The move is therefore not urgent. But it should not be needed every week, and at present it is.

The configuration explains the timing. KillWait is 30 s and UnkillableStepTimeout is 60 s. When a step is cancelled, slurmstepd signals every process in the step's cgroup, then SIGKILLs them. If any process survives the timeout, slurmd drains the node. The only process SIGKILL cannot end is one in uninterruptible sleep, which on this cluster almost always means a GPFS call or a GPU driver teardown. The job records 482 steps CANCELLED by 39486 against 5,606 completed. Each cancellation is one draw against that timeout. Every step that ends by cancellation rather than by its task exiting carries a chance of draining the node. The empty cgroups step_251, step_1080 and step_5531 are still present under the job.

The stop path in reckon/crew/dispatch_launch.py sends SIGTERM to the worker pid and, after the stop grace or the terminal-manifest grace, sends SIGKILL. Two cases are possible. If that pid is the srun client, the SIGKILL ends the client and the step is cancelled from outside. If it is the worker inside the step, the SIGKILL leaves the step's other processes to slurmstepd's kill. Either way, ending the step is the scheduler's kill rather than the task's own exit, and that is the event that drains. Which of the two it is, and which run step 251 belonged to, is §2's question.

§3 — A stopped worker ends inside its step

The step must end by its own task exiting, never by the scheduler's kill. The per-run supervisor already owns a worker's parentage, its stop signals and its exit record. It is started by _start_supervisor (reckon/crew/dispatch_launch.py:2078), its entry point is reckon/crew/supervisor_main.py:23, and its stop path is at dispatch_launch.py:2860–2884 and 2936–2963. So this section extends that supervisor and adds no new reaper or process.

For a worker placed as a step (its argv built by placement.step_prefix), the supervisor delivers the stop to the task inside the step and never to the srun client. §2 showed that a signal to the client makes Slurm cancel the step in that second. The worker chooses the delivery primitive and names it in the evidence. One candidate is scancel --signal=TERM addressed to the step id, which signals the task without cancelling the step; another is a signal srun forwards to its task without cancelling. The supervisor then waits for the client to exit by itself. A later escalation is SIGKILL delivered to the task the same way, still never a cancel. The wait has no deadline shorter than a GPFS stall. If the worker outlives a long ceiling, at least ten minutes, the supervisor records the step's processes and their wait channels to the run directory and keeps waiting.

A step that ends normally can drain the node too. When the task exits, slurmstepd kills whatever is left in the step's cgroup under the same 60 s timeout. The probe therefore also checks that the sandbox's PID-namespace init holds the task open until every descendant has exited. If it does not, this section is re-planned; it is not patched with a second waiter.

Done when two things hold. A unit test proves that the stop path, for a step-placed worker, delivers to the step's task and records no signal to the srun client. And a probe on the fleet allocation stops a worker step whose child ignores SIGTERM for 40 s: sacct then reports the step COMPLETED, the supervisor's record names the child, and the node's state is unchanged. The negative control runs the same probe through the old path, a signal to the srun client, and shows CANCELLED.

§4 — The migrate command starts a second move

reckon fleet-node migrate reads the newest move-*/ledger.json, and once that ledger's next step is done it prints migration complete forever. Its census step is reachable only when no ledger exists, so the command can carry exactly one move. Measured 18 October: --dry-run printed migration complete while the fleet ran on a drained node. The fix: when the newest ledger is done, the next invocation begins a new move at census with a new move-<stamp> ledger, and --dry-run says so. This holds even when the fleet still runs on the job that move promoted, which is the case on 18 October: job 1281970 is both the promoted job and the drained one. Census and layout only read state and write records; stand-up is the first step that requests anything and needs its own invocation, so starting a census after a finished move costs nothing. The earlier ledger is kept untouched. In the same file pair, reckon fleet-node status replaces its warning that "the allocation ends when the drain completes". The replacement states that the scheduler places no new job on the node, that the allocation continues until it ends, and that the node returns only when an administrator resumes it. Neither change adds or retires an option: the first changes what the existing command does when its newest ledger is done, and the second replaces one string.

Done when tests in tests/ cover a completed ledger followed by a fresh census and the dry-run text in both states, and the status wording. The negative control is a ledger mid-move, at cutover, which must still resume that move rather than start a new one.

§6 — A worker step carries a memory bound

The four processes killed on 17 October were not runaways. They belonged to two nova solver runs, r-20261017T073925596435-axis-facing-owner (steps 5614 and 5621) and r-20261017T102932384946-owner-cell-current (step 5700). Each step's stderr records Slurm's oom_kill event, and both runs were doing map solves at the 2,098-point size, which legitimately need 52–59 GB. The defect is placement, not leakage. The fleet allocation is 96 GB shared by every session and worker, so one such solve takes more than half of it. A second one, or the sessions' own growth, takes the whole job to its limit, and the OOM killer then picks the largest process anywhere in the job.

Every worker step is therefore placed with an explicit --mem, so undeclared work stays inside a share that leaves room for the sessions. placement.step_prefix (reckon/crew/placement.py:233) is the one owner of a step's options and carries the bound. fleet_node.placement_argv (reckon/crew/fleet_node.py:358) builds the same srun --overlap --jobid=… prefix for the migrate and place commands, so it is folded into step_prefix rather than given the bound separately. A node whose work needs more declares it through the existing dispatch --set override, recorded on the run, so no new option is added. The bound uses the memory vocabulary placement already has: memory_gb in placement.reservation_options, and DEFAULT_MEMORY with its environment override in fleet_node.py. A declaration above the fleet's per-node ceiling is placed in its own job on a *_debug partition rather than inside the fleet allocation. The decision worker-step-memory below locks a 24 GB default and a 48 GB ceiling. Done when a test shows the placed srun argv carrying the default and a declared bound, and a test shows a declaration above the ceiling routed to its own job. A probe step on the fleet allocation must also show its cgroup memory.max equal to the bound. The negative control is a probe allocating past its bound: its OOM event lands in the step's memory.events and not the job's.

§8 — Move the fleet off the drained node

Deferred under the locked decision move-timing: the fleet does not move unless SDCC asks for clu-2002 back instead of resuming it in place. If it does, once §3 and §5 have landed, move the fleet with reckon fleet-node migrate, from census to retire, in the same tabs, with coordinators resumed. The move is live in the sense the previous plan built: sessions keep their conversations and tabs, and in-flight workers finish or are resumed by run on the new node. A process cannot cross nodes, so a short quiesce window is unavoidable, and it is taken as late as possible. The retire step cancels job 1281970, which is irreversible and needs the lead's --confirm. Moving before §3 lands would carry the drain mechanism to the new node, which is what happened on 8 October. Done when the move ledger records every census session cut over and verified, and the new node's state is ALLOCATED without DRAIN after the first wave of worker stops. The negative control points the same state reading at a node already recorded as draining, such as gpu-0003 or the old clu-2002, and must report DRAIN. That shows the reading can see a drain without draining a node to prove it.

§9 — A watch producer sweeps only when the crew home changes

§7 measured that one producer cycle, in watch_ticker (reckon/crew/recovery_watch.py), sweeps the whole fleet every second whether or not anything has moved. It lists every project's live/ before filtering (runs.py:705, runs.py:720), walks run directories, parses streams and calls the git shim. That is about 1,880 opens and 1,575 stats per cycle plus 1.25 git-shim calls, whatever the live pointer count. Five producers make roughly 9,000 GPFS opens a second.

The sweep runs only when the crew home changes. The change signal is inotify on live/, runs/ and the watch directory, or one mtime stat of each where inotify is unavailable on GPFS; the worker states which in the evidence. The per-live-run liveness probe stays on the fixed beat, because a process can die without touching a file. The listing filters to the producer's own project before it stats pointers.

Done when two things hold. A test drives a producer through quiet cycles and sees no directory walk and no git-shim spawn, then touches a pointer and sees exactly one sweep. A 32 s strace of a producer against the fleet's copied live/ must also show per-cycle openat and stat counts below a tenth of §7's figures while no file changes. The negative control is a cycle in which a pointer's mtime moves, which must sweep. A transition test must still deliver a run's death within one beat when no file moved. Because this changes load on the run trees that reckon serve also reads, the session owning that work is told before this section dispatches.

§ Decisions

What default memory bound does a worker step carry, and above what declared size does a node leave the fleet allocation for its own job?

The job holds 96 GB and the sessions use about 35 GB. A 24 GB default leaves room for them. The 52–59 GB nova map solves go to their own debug-partition job, where a whole node serves them, instead of taking the fleet to the limit that failed on 17 October.

When does the fleet move off clu-2002?

Do not move now. The drain does not end the job, and the processes behind it have exited, so SDCC is asked to resume clu-2002 in place. A move happens only if SDCC asks for the node back, and then only after §3 and a passing §5 rehearsal, so the new node does not inherit the drain mechanism.
