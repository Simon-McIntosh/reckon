§5 — The station's node-local store

A new module reckon/crew/station_store.py owns one SQLite database in WAL mode under the node-local runtime root, never under the crew home. The root is the one reckon/crew/dispatch_watch.py's _session_host_runtime_root returns, made public so the station and the session host resolve a single directory. Only its first two candidates, $XDG_RUNTIME_DIR and then /run/user/<uid>, are shared by every process on a node. Its last, TMPDIR, differs per session: on clu-2068 on 2026-10-23 every session host read XDG_RUNTIME_DIR=/tmp/39486-fleet, while TMPDIR was /tmp for two of them and /dev/shm/39486-fleet-1291586 for a third. So a root reached only through TMPDIR is refused rather than opened as a per-session database. The stat identity stored for each pointer and stream is reckon/file_memo.file_signature's, so the station keys a file as every in-process memo does. The table holds that identity because the station's state must survive a restart, which file_memo's in-process map cannot. Tables:

  • pointers: path, stat identity, run id, project, session, phase and the fields the classifier reads;
  • streams: path, inode, consumed offset, the carried fold state, the folded observation;
  • events: id, time, project, audience (a session or every pane), run, kind, from, to, detail and duty, indexed on (audience, id) and (project, id);
  • cursors, obligations and station (heartbeat, code identity, started-at).

Events are written to one file per UTC day, attached for reads, and a file older than the retention window (seven days, a configuration value) is unlinked. A missing database is rebuilt from the crew home. The module reads the root's own mount type through reckon/host.py's _filesystem_type and refuses any type in _SHARED_FILESYSTEMS, because WAL needs shared memory that a network filesystem cannot provide across nodes. It also refuses a type it cannot determine, when _filesystem_type returns None because the mount table is unreadable: the guard fails closed, since it cannot prove such a root is node-local. It does not call host._is_node_local: that function accepts $XDG_RUNTIME_DIR and /run/user/<uid> by path prefix before it reads the mount type (reckon/host.py:190–192), and those are exactly the roots the store uses. Both refusals, a shared mount and a root reached only through TMPDIR, raise one error class defined in the module, naming the path and the reason. That error is the station's own, not a dispatch refusal, so it joins no entry of reckon/crew/refusals.py's D-coded registry. This section adds the module and retires nothing yet, because nothing reads the station until §7 and §8. The surfaces the station replaces are retired where they are named, in §7 and §12.

Done when unit tests show: a rebuild from a fixture crew home (three pointers, two streams) produces the same pointer and observation rows as an incremental build; a day partition older than the window is unlinked and its rows are gone; a root under a temporary $XDG_RUNTIME_DIR is refused once per type in host._SHARED_FILESYSTEMS, naming its type, with _filesystem_type patched to report that type, refused when it reports None, and accepted when it reports tmpfs; a root that resolves only through TMPDIR is refused; and a pointer whose file_memo.file_signature is unchanged is not re-parsed. The test files importing reckon/crew/refusals.py show no added failure against base. Negative controls: a store that writes events into one undated file must fail the retention test, and a store that checks the root through host._is_node_local must fail the shared-type case under $XDG_RUNTIME_DIR.

§6 — Ingest reads only bytes it has not read

The station's tick stats the live directory and each live pointer and stream. A pointer is parsed only when its file_memo.file_signature moved against the stored one. A stream is read only past its stored offset, up to the last whole record, and folded by _backends.observe_stream with the stored fold state as state; a stream whose inode changed, or whose current size is below its consumed offset, is folded from its start. Worker streams are append-only JSONL, so a rewrite is a truncate followed by fresh writes; a truncate a tick sees reads as that size test. A rewrite that grows back past the consumed offset between two ticks is caught by a 64-byte tail anchor: a stream that grew is read from 64 bytes before its consumed offset, and those bytes are compared with the copy stored beside the offset, a mismatch folding the stream from its start. The anchor misses a rewrite whose bytes at that position happen to be identical, which timestamped JSONL records make vanishingly unlikely, and it is not consulted for a stream that did not grow. It costs 64 bytes per grown stream. The stream's size at the last read is stored beside its consumed offset, and a stream whose size has not changed since is not read at all, so a trailing partial record is re-read only when more bytes arrive. station_store.ingest_stream (§5) checks only inode and size today, so this section adds the anchor. The classifier (recovery.classify_pointer) runs once per run whose classification inputs changed, keyed on recovery_watch._snapshot_reuse_key, the key the producer uses today. It composes recovery_memo._classification_inputs (the pointer, its log, the manifest, the run directory's records, the review-store candidates and the tree head) with the run's newest stream, which differs from the pointer's log once a resume or lane change writes beside it, and the run's promotion ledger row. A worker that finishes by writing its manifest moves neither its pointer nor its stream, so a key on those two alone would never see it deliver. Its liveness probe runs only where the pointer's launcher_host is this node. A verdict also moves with the clock and the process table, which no file identity records: a run that goes quiet must read stalled, and a worker can exit while its files stay still. So a run whose inputs did not move still takes the quiet-beat reading each tick, as recovery_watch._quiet_beat_snapshots does for the producer today: its liveness, for a run launched on this node, and its stall clock are read again. The full classifier runs when the run's inputs moved or its liveness reading moved, as _quiet_beat_snapshots calls _watch_snapshot when the liveness triple moved; otherwise only the stall clock is re-derived through recovery_watch._stall_reading, which acts on a dispatched or working run and reads it waiting when a pause reason explains the silence and stalled when none does.

The fold already exists in §5's station_store.ingest_stream; this section's new mechanism is the classification, so it is measured directly. Over three ticks of a fixture with three live runs, with recovery.classify_pointer and the liveness probe counted through patches: a tick where nothing changed classifies no run; a tick where one run's pointer or stream moved classifies exactly that run, once; a tick where only one run's manifest moved classifies exactly that run, once; a tick where a run's resume writes a new resume-1.jsonl beside its original stream classifies that run; a run launched on this node whose worker exits while every file stays still reads its new verdict on the next tick, while a run launched on another node is never probed, so its verdict moves only with its files or its stall clock, its liveness being read by the station on its own node; a working run silent past its stall window reads stalled without any file moving, and one whose silence a pause reason explains reads waiting; and the liveness probe is called only for runs whose pointer's launcher_host is this node, so a run launched on another host is classified without a probe. Negative controls: an ingest that ignores the stored offset must fail the bytes test; one that drops the carried fold state must fail the equality test on a stream whose rate depends on earlier records; a tick that classifies every run on every pass must fail the unchanged-tick count; a change key on the pointer and stream alone must fail the manifest-only tick; a station without the quiet-beat reading must fail the exited-worker and stall cases; and an ingest without the tail anchor must fail the case where a stream is truncated and rewritten past its consumed offset between two ticks.

§7 — One station per node replaces the per-project producers

reckon crew station runs one process per node, held by a lock under the node-local runtime root §5 resolves, for every mounted project on the node. It is the only writer of every table but cursors. Each subscriber (§8) writes its own row there and no other, and SQLite's WAL mode serialises those writes beside the station's. Each tick it ingests (§6), writes each transition once with the same row fields crew watch writes today plus its audience and duty, and refreshes its heartbeat. It is started where workers run: on the fleet node by the crew host when a session first dispatches, and by the fleet supervisor otherwise. crew watch becomes an alias that ensures the station, and the per-project seats, leases and the producer user units on the login nodes are retired once §12's cutover passes. This section adds the station verb and retires nothing immediately, because the per-project producers must run beside the station until §12's measured cutover shows it carries every row. §12 then removes the producer seat, its leases and its user units, and crew watch keeps only the alias.

The station is the only process that reloads onto new code. It reloads from a reload image materialised under the node-local runtime root, so no cross-node lease record is written.

§8 — A follower becomes a subscriber

crew follow keeps its arguments and its output format. It reads PRAGMA data_version each poll. That pragma moves only for commits to the main database, not for commits to the attached day files that hold the events (§5), so the station writes a generation counter in its station table, in the main database, in a commit made after every commit that adds event rows. The subscriber wakes on that. When the value moved, it selects the rows for its session and the broadcast rows after its cursor, renders them with the existing ticker painter and advances its cursor in the same transaction. A cursor is the pair of a station-wide event sequence number and the UTC day of the event it names, not a per-partition row id. The station assigns each event the next value from a counter in the main database, so one number orders events across every day file. The subscriber attaches the day files from its cursor's day through today, and attaches the new file at each UTC rollover. A cursor older than the oldest retained day file resumes at that file's first event and prints one line saying how many days were skipped. The subscriber's registration is its own row in cursors, in the node-local store, not a watch record under the crew home. The pane's checkpoint and history, which follow_checkpoint.checkpoint_path and history_path keep under runs.follower_dir in the crew home today, move into that same row's columns, so the poll path opens nothing under the crew home. The pane policy (ticker.PaneRowPath: arrival and settle holds, lift claims) runs in the station once per audience, so its decisions are made once and stored with the row. The follower computes no snapshot, reads nothing on GPFS, and does not reload: its code is a query and a painter. When the station's heartbeat is older than its stale window, the follower prints one line saying so and naming the command that restarts it.

§10 — The review reflex and settle run once, in the station

Today each follower runs resumption.sweep and settle detection on its own cadence. The sweep has two passes: a resume pass, which resumes runs whose provider hold or declared external wait has ended and writes the auto_resume stamp, and then the review pass, the review reflex (recovery_review_acceptance.dispatch_awaiting_reviews). The station runs the whole sweep, both passes, and settle detection for every session on the node, on the session's behalf, each on every change and on the station's own beat. The resume pass keeps the host rule runs.sweep_unfollowed_sessions applies today: a resume restarts a process on the host it runs on, so the station resumes only runs launched on its own host and leaves a run launched elsewhere to that host's station. resumption.sweep carries no host filter of its own, so the station supplies it. The beat is needed because all three expire on the clock: a hold or declared wait ends at its stated time, and a settle window expires REVIEW_SETTLE_SECONDS from the run's resume stamp (recovery_review_dispatch.review_settle_seconds_remaining), and a resumed worker that writes nothing produces no change at the moment the window passes.

Today the settle reader, review_settle_seconds_remaining, takes only the sweep's own auto_resume stamp. Every resume of a run whose tree yields a head, the advice door's included, already records the resume instant through resume_superseded_head (a run with no readable head has no head to review at, so there is nothing for its settle window to protect), and _latest_resume_at in the same module already returns the newer of the two stamps. This section makes the settle reader use _latest_resume_at, so a run resumed by a coordinator's crew resume --advice waits the same settle window an automatic resume does (old §81). The advice door writes nothing new, and auto_resume stays the sweep's own record.

A review is already dispatched once per run and head whatever the subscriber count, because dispatch_review_for_run refuses a pair already in flight. What the move buys is the sweep itself: today each subscriber runs resumption.sweep, and its reads of the fleet, on its own cadence. The follower's drain settle moves with it: today _check_settle samples the population every FOLLOWER_SETTLE_SAMPLE_SECONDS through _population_has_live_work, which lists and opens the live pointer directory, judging each population separately: the subscriber's own session and every session it has observed (settle_populations), each filtered by pointer owner. §13 — The station's tick reads only what changed

The cutover measure of §12 failed on cost, not on rows. Its run showed the station carrying every row of a recorded hour (100 of 100), and then measured the station alone over the fleet node's live pointers at 1,067–1,160 MB/min of reads against the bound of 20, and 57–92 % of one core against 5. The reads are page-cache traffic (read_bytes stayed at zero), and they scale with the live population: the same instrument over five live pointers read 126 MB/min.

The cause is not yet named, and this section names it before it changes anything. Both stream reads are built to be incremental: StationStore.ingest_stream in reckon/crew/station_store.py reads past its stored offset, and a fresh classification through recovery_watch._watch_snapshot resumes a grown stream from the offset its classification memo records (recovery_stream._observed_stream), re-reading from the first record only when the stream's inode or its head fingerprint changes, which steady append-only growth triggers neither of. The §12 run's tick probe measured a cold station tick over five live runs at 83 MB and the next ticks at 0.07 MB. But the same run measured the station over five live pointers on the fleet at 126 MB/min, and sixty warm ticks a minute at the 1 s interval read about 4 MB, while even one cold tick plus 59 warm ones reads about 87 MB. So the fleet's ticks are not warm, and the leading candidate is the classification path itself: a reuse key (recovery_watch._snapshot_reuse_key) or classification memo that does not hold from one tick to the next on live runs, for instance because an input it is keyed on (a run's manifest, its records, the review store or the tree head) moves every tick. A per-project refresh stage outside the classification is the other candidate. This section measures which.

The work is one change found by one measurement: take a per-path census of the bytes the station reads over a 60 s window on the fleet node, name the paths and the code reading them that make up most of the volume, and remove the dominant read so a steady-state tick reads only what changed since the last one. It does not change what a verdict says and retires nothing; §12 does that once this cost is inside its bound.

Done when: a census of one 60 s window of the station on the fleet node with at least 30 live runs, counting bytes per path through an instrument that sees every read the station process makes (a Python audit hook on open wrapping the returned file's reads, or strace -f -e trace=read,pread64,openat summarised by path), is recorded as a log in the run directory and names the paths making up at least 90 % of the bytes and the function reading each; a test in tests/test_the_station_reads_only_what_changed.py builds its own fixture crew home of at least five runs whose dominant input, the one the census names, totals at least 10 MB across its paths, moves that input between two ticks, and asserts through the same per-path instrument that the second tick reads under 1 MB from that input's paths, while the same test at the base revision reads at least the input's full size from them (the negative control, recorded as a test log); the same test asserts that every verdict classify_tick returns on that fixture equals the verdict a fresh recovery_watch._watch_snapshot classification returns for the same pointer and moment; over a 60 s window on the fleet node with at least 30 live runs, starting after the station has completed its first tick, measured with the instruments of docs/research/monitor-storage-load-rca.html §2, the station alone at its default interval reads under 20 MB/min and uses under 5 % of one core, with the census and the before and after figures recorded in the RCA; the test files importing the changed modules show no added failure against base in matched arms; and ruff check and ruff format --check on the staged paths add no finding.

§45 — The review store is indexed by its writers

Why. The review-store index is keyed on the store directory's identity, so any review written for any run marks the whole project's index stale. An update then lists the store and runs stat on every record. reckon's store held 7,563 records, and one full stat pass measured 5.6 s on the fleet node (0.74 ms per file on GPFS). The check runs once per duty item, per run and per session.

Prototype. ~/.cache/reckon-review-index/review_index_proto.py implements the design below on a synthetic store of 7,536 records across 93 runs. One record is written through the index, and then every run's records are read. Today's reader model made 700,755 record stats and 93 listings, taking 8.5 s on tmpfs, an estimated 519 s on GPFS for one session's pass. The writer-maintained index made 0 stats and 0 listings, taking 0.075 s. changed_since(0) named exactly the one run written, its digest moved, and a write that bypassed the index was still found by listing names alone.

Design. Each project's review store keeps one persisted index document inside the store directory on the shared home, beside the records, with its lock in the same directory, so a writer on any node advances the version every node reads. It does not live in the node-local cache, where a write from another node would never be seen.

  • Per record. An entry holds the record's run id, the SHA-256 of its bytes, its size, mtime and inode, and the store version at which it was last written.
  • Per run. A digest over that run's (name, hash) pairs. A reader caches what it derives from a run keyed on that digest, so an unchanged run costs one comparison and no read.
  • Per store. A monotonic version and a bounded change log of (version, run id), so the runs changed since a version a reader last saw are found without a scan. The document also records the store directory's mtime as of the last indexed write.
  • One writer path. One function in review_records writes a record atomically, hashes the bytes it wrote, and updates that record's entry, the run's digest, the version and the log, under a lock on the index. review._write_record, which the disposition writers already share, and the plan-review writes in plan_review.py that land in the same store all go through it.
  • Readers. review_entries_signature, _store_index and their callers read records by run id from the index, and so does the per-tick store path (_TICK_REVIEW_STORES), which today rebuilds from scratch through _build_store_indexes. They treat the version and the run digest as their freshness keys. They never list or stat the store on a read.
  • Foreign writes. When the store directory's mtime, which is shared across nodes, differs from the one the index recorded, something wrote outside the writer path. The reader then lists names only, hashes the names the index lacks, drops entries whose names are gone, and records the new mtime. It never stats every record.
  • Rebuild. A missing, unreadable or foreign-stamped index is rebuilt from one listing and one hash of each record, as today's index is.

When this node lands first, §35 routes its readers through this index instead. The node names in its manifest which of the two cases it met.
