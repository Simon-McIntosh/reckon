§1 — What fails, and what it costs

A coordinator can name a crew worker, send it an instruction, and be told the send succeeded. The worker receives nothing. Measured across every run on this workstation: 0 delivered messages in 3,949 worker streams, against a positive control of 11,939 in 244 interactive transcripts. The channel has never worked once.

An attempt census, recorded in the same session, confirms the zero from the coordinator’s side: 2,232 send attempts appear in interactive session transcripts, 0 arrive in any crew worker run stream, the control instrument finds 1,204 deliveries among interactive sessions, and 84% of the coordinators who attempted the channel stood down in their next turn believing it delivered — a fleet steered on a confirmation no worker ever saw. Each count sits beside the command that produced it, and the next-turn classification carries quoted evidence per class: A census of coordinator attempts to message a crew worker.

The full measurement, the process facts behind it, and the reason a coordinator reasonably believes the channel exists are in Messages to workers never arrive. This plan does not restate them.

The cost is not the undelivered message. It is that a coordinator makes a real decision on the strength of a false confirmation — judging a fleet steered, and standing down — which is the same failure shape as a guard that reports a protection it does not provide.

§2 — Two defects, separable and differently urgent

They are worth keeping apart, because one is cheap and self-contained and the other touches a contended surface.

The false clearance. Headless workers are advertised as interactive peers and accept sends that report success. A coordinator is told twice that the path is open. Closing this does not require the missing capability to exist — a refusal naming the working alternative is strictly better than a silent expiry, today.

The missing channel. Nothing can put an instruction in front of a worker that is still working. reckon crew resume --advice continues a session whose turn has ended and is refused while the process lingers, so it answers the stopped worker and not the working one. Until something answers the working one, the written recovery order contains a step no mechanism implements.

The second is why the first is dangerous: an advertised channel standing in for a capability the system genuinely lacks is what makes the substitution invisible.

§3 — Refuse the send at the layer that knows ✓ landed 2026-09-15

Reckon does not own the session listing or the send, but it already owns a proven interception point: the pre-tool hook that refuses a harness-native background-agent spawn in a crew-managed repository and composes the crew-dispatch re-route so the caller fixes it in one step rather than diagnosing a bare refusal.

The same shape applies here. When a send names a recipient that resolves to a live crew worker — matched against this host's live run pointers rather than against a name pattern, so a coordinator session that happens to share a node's name is not caught — refuse it, and name the channel that does work for that run's current state: resume when the run has stopped, the inbox of §4 when it is live.

Done when a send addressed to a live worker is refused immediately, the refusal names the run id and the working command, and a send to a genuine coordinator session is untouched. The falsifier is the second half: a guard that refuses peer messaging generally would pass a test that only checks the first, so the quiet half is written before the loud one.

Self-contained: a hook module and its settings wiring, plus tests. It touches nothing under reckon/crew/.

Landed. §4 — An inbox a working worker reads

A headless worker cannot be interrupted — its stdin is a consumed file and its approval gate has nobody behind it. But it can read. A coordinator writes a message into the run's own directory; the worker's prompt contract obliges it to read that directory at points where an instruction could still change what it does: before submitting a long job, before committing, between phases, and whenever it is about to report.

This is deliberately not an interrupt. Delivery is at the next checkpoint, which is the honest guarantee the process model can support, and the one the incident actually needed — the four workers were minutes away from submitting jobs, not mid-syscall. It inherits the properties the fleet already relies on: the message is a file, so it is durable across a turn boundary, auditable after the fact, and readable by a resumed session.

Done when a message written to a live run is quoted back in that worker's manifest, and when a run that received none says so rather than being silent about it. An unread inbox must be visible: a channel whose delivery cannot be distinguished from silence is the defect this plan exists to remove, and reproducing it one layer down would be worse than leaving it alone.

Contended. The prompt contract lives in reckon/crew/prompts.py, which is mid-repair under another coordinator. This section serialises behind that work rather than fencing around it.

§5 — Make the written instruction name a mechanism

Two documents tell a coordinator to message a worker and neither names how. The orchestration reference's recovery order says to message the worker when evidence exists but no report does; the workstation-wide order for a silent worker says the same. Both predate the measurement and both are read as authorising the channel that does not work.

Correct them to name the mechanism for the run's state, and record why the obvious-looking one is absent — an instruction that merely drops the step teaches nothing and will be re-invented.

Done when neither document contains an unqualified instruction to message a worker, and each names the command for the state it is describing. Note that the skill reference directories are symlinks into this checkout, so this is a repository edit fenced as one.

§6 — What is deliberately not proposed

Making the worker's permission mode match the coordinator's so the hold never fires. This would route around a permission decision rather than answer it, and it would make delivery depend on a coincidence of settings between two sessions — fragile, and wrong in the direction that matters.

Signalling the process, or writing to its descriptors. Its stdin is a consumed regular file and its stdout is the run's own event log; both are load-bearing for observation.

A second transport of any kind. The run directory is already the durable, audited, per-run surface both sides agree on.

§ Decisions

How far does this go?

Closing the false clearance is cheap and touches no contended file. Building the inbox gives the capability that is actually missing but waits on a surface another coordinator is repairing.

The guard closes the false clearance immediately and touches no contended file; the inbox supplies the capability that is actually missing, and without it the guard would refuse a send while leaving the coordinator with nowhere to go. Landing them separately keeps the cheap half from waiting on the expensive one.
