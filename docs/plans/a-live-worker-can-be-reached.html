§1 — What fails, and what it costs

A coordinator can name a crew worker, send it an instruction, and be told the send succeeded. The worker receives nothing. Measured across every run on this workstation: 0 delivered messages in 3,949 worker streams, against a positive control of 11,939 in 244 interactive transcripts. The channel has never worked once.

An attempt census, recorded in the same session, confirms the zero from the coordinator’s side: 2,232 send attempts appear in interactive session transcripts, 0 arrive in any crew worker run stream, the control instrument finds 1,204 deliveries among interactive sessions, and 84% of the coordinators who attempted the channel stood down in their next turn believing it delivered — a fleet steered on a confirmation no worker ever saw. Each count sits beside the command that produced it, and the next-turn classification carries quoted evidence per class: A census of coordinator attempts to message a crew worker.

The full measurement, the process facts behind it, and the reason a coordinator reasonably believes the channel exists are in Messages to workers never arrive. This plan does not restate them.

The cost is not the undelivered message. It is that a coordinator makes a real decision on the strength of a false confirmation — judging a fleet steered, and standing down — which is the same failure shape as a guard that reports a protection it does not provide.

§2 — Two defects, separable and differently urgent

They are worth keeping apart, because one is cheap and self-contained and the other touches a contended surface.

The false clearance. Headless workers are advertised as interactive peers and accept sends that report success. A coordinator is told twice that the path is open. Closing this does not require the missing capability to exist — a refusal naming the working alternative is strictly better than a silent expiry, today.

The missing channel. Nothing can put an instruction in front of a worker that is still working. reckon crew resume --advice continues a session whose turn has ended and is refused while the process lingers, so it answers the stopped worker and not the working one. Until something answers the working one, the written recovery order contains a step no mechanism implements.

The second is why the first is dangerous: an advertised channel standing in for a capability the system genuinely lacks is what makes the substitution invisible.

§3 — Refuse the send at the layer that knows ✓ landed 2026-09-15

Reckon does not own the session listing or the send, but it already owns a proven interception point: the pre-tool hook that refuses a harness-native background-agent spawn in a crew-managed repository and composes the crew-dispatch re-route so the caller fixes it in one step rather than diagnosing a bare refusal.

The same shape applies here. When a send names a recipient that resolves to a live crew worker — matched against this host's live run pointers rather than against a name pattern, so a coordinator session that happens to share a node's name is not caught — refuse it, and name the channel that does work for that run's current state: resume when the run has stopped, the inbox of §4 when it is live.

Done when a send addressed to a live worker is refused immediately, the refusal names the run id and the working command, and a send to a genuine coordinator session is untouched. The falsifier is the second half: a guard that refuses peer messaging generally would pass a test that only checks the first, so the quiet half is written before the loud one.

Self-contained: a hook module and its settings wiring, plus tests. It touches nothing under reckon/crew/.

Landed. A new pre-tool hook, reckon/hooks/worker_message_guard.py, refuses a SendMessage whose recipient resolves by exact identity to a live run pointer recorded on this host, naming the run id and the recovery-order command that reaches it, reckon crew resume --run <run-id> --advice "…". The match is host-local and identity-based (run id, node id, member, session, session id), never a name pattern, so a coordinator session that shares a node's name is untouched and a pointer launched on another host is never matched. reckon sync installs it beside the native-agent guard in a crew-managed repository's harness settings and removes both as one unit. §4 — An inbox a working worker reads

Superseded by §8. The checkpoint read below depends on the model remembering to look; §8 delivers through the harness hook instead, so this mechanism is not to be built. The text is kept as the record of the design it replaced.

A headless worker cannot be interrupted — its stdin is a consumed file and its approval gate has nobody behind it. But it can read. A coordinator writes a message into the run's own directory; the worker's prompt contract obliges it to read that directory at points where an instruction could still change what it does: before submitting a long job, before committing, between phases, and whenever it is about to report.

This is deliberately not an interrupt. Delivery is at the next checkpoint, which is the honest guarantee the process model can support, and the one the incident actually needed — the four workers were minutes away from submitting jobs, not mid-syscall. It inherits the properties the fleet already relies on: the message is a file, so it is durable across a turn boundary, auditable after the fact, and readable by a resumed session.

Done when a message written to a live run is quoted back in that worker's manifest, and when a run that received none says so rather than being silent about it. An unread inbox must be visible: a channel whose delivery cannot be distinguished from silence is the defect this plan exists to remove, and reproducing it one layer down would be worse than leaving it alone.

Contended. The prompt contract lives in reckon/crew/prompts.py, which is mid-repair under another coordinator. This section serialises behind that work rather than fencing around it.

§6 — What is deliberately not proposed

Making the worker's permission mode match the coordinator's so the hold never fires. This would route around a permission decision rather than answer it, and it would make delivery depend on a coincidence of settings between two sessions — fragile, and wrong in the direction that matters.

Signalling the process, or writing to its descriptors. Its stdin is a consumed regular file and its stdout is the run's own event log; both are load-bearing for observation.

A second transport of any kind. The run directory is already the durable, audited, per-run surface both sides agree on.

§8 — A message reaches a live worker at its next tool call

Why this replaces §7's mechanism. §4 and §7 deliver through the prompt contract: the worker is told to read its run directory at named checkpoints, so delivery depends on the model remembering to look. A prototype run on 2026-11-10 found a delivery path that does not. Claude Code runs a PostToolUse hook after every tool call, and a hook's hookSpecificOutput.additionalContext is placed in front of the model before its next step. reckon already emits additionalContext from a PreToolUse hook (the worker git guard, reckon/hooks/worker_git_guard.py), but registers no PostToolUse hook anywhere, so the registration path below is new. In the prototype, a headless claude -p session with a hook that read a scratch inbox directory received a message written there before its first tool call returned, and its final answer obeyed it (session 02f01c36-7b6c-4b2f-950b-db44c8c5a4f4; the script and its output are in Worker steering and anchored edit prototypes). The transport is still the run directory, so §6's refusal of a second transport stands; what changes is that the harness reads it, not the model.

The same prototype found the one defect the product must design out: the model issued three tool calls in parallel, three hook processes ran at once, and each delivered the same message. Delivery must claim a message atomically, so exactly one hook delivers it.

Deliverable.

  • A new hook, reckon/hooks/worker_inbox.py. Today a run home's hooks key is copied from the operator's settings (_seed_harness_entry in reckon/_worker_fence.py, near line 426), and the code that adds hook entries (install_hook_settings and configure_crew_guards in reckon/hooks/install.py) writes user-scope or repository settings, never a run home. That copy cannot carry the new entry: _seed_harness_entry returns at once when the run home's settings.json already exists (near line 436), and the seeding loop in seed_harness_home (near line 249) skips an entry whose operator source is absent, so an operator with no ~/.claude/settings.json gets a run-home settings.json only when the MCP-server step writes one (_seed_worker_mcp_settings, near line 317), and then with no hooks in it. The registration therefore goes in seed_harness_home itself, after the loop, for Claude-dialect runs: create the run home's settings.json when the loop produced none, then merge a PostToolUse entry running this hook through the checkout's interpreter, reusing the installer's merge so an entry already present is not duplicated. Every worker launched under the fence then carries it, whatever the operator's settings hold and whether or not the home was seeded before. It reads <run dir>/inbox/*.md, claims each message by renaming it (a rename that fails because another hook already claimed it is skipped), emits the claimed messages as additionalContext, and appends a receipt to <run dir>/inbox/receipts.jsonl naming the message, the delivery time and the tool call it followed. A hook that finds no run directory, or an empty inbox, exits silently in well under the hook timeout, because it runs after every tool call of every worker.
  • A coordinator verb, reckon crew tell --run <id> <message>, that writes one message file atomically into a live run's inbox and reports queued_for_next_tool_call, never delivered: delivery is proved only by the receipt. For a run whose process has ended it refuses and names crew resume --advice, the channel that reaches a stopped worker. For a live run whose own run home does not carry the inbox hook it refuses too, naming the reason. The test is the hook itself, read from the run home's settings.json, not the record's fenced flag: a fenced run launched before this section lands carries fenced: true but a home seeded without the entry, and nothing re-seeds a live run's home (seed_harness_home runs only at launch). An unfenced run (fenced: false, or no fenced key, as on a record written before the field existed) has no run home and is refused on the same test: such a run has no seeded home and so no hook, and reporting it queued would repeat §1's silent non-delivery one hop later. Until §9 lands it also refuses a live codex run for the same reason.
  • The worker-message guard (reckon/hooks/worker_message_guard.py), whose refusal today names only crew resume, also names crew tell when the addressed run is live.
  • The worker's manifest contract records messages received: a run that received a message quotes it, a run that received none says so, and the coordinator's view of a run shows messages written but not yet delivered.

Done when tests cover: a message written before a tool call is delivered once as additionalContext and leaves a receipt; three concurrent hook invocations deliver one message exactly once between them; an empty inbox and a missing run directory produce no output; crew tell on a live fenced Claude-dialect run writes the file, on an ended run refuses naming crew resume, and refuses naming the missing hook on a live run recorded fenced: false, on a live run whose record has no fenced key, on a live fenced run whose home was seeded without the entry, and on a live codex run; the new verb passes the CLI help-contract tests. a seeded Claude-dialect run home carries exactly one PostToolUse entry in each of three cases — the operator has no settings file, the operator's settings carry other hooks (which are kept), and the run home was already seeded without the entry — and this section writes nothing into a codex run home (§9 owns that); a worker manifest whose run directory holds a delivery receipt but which quotes no message is flagged by the manifest check, and one with no receipt must say no message was received; and the coordinator's run view lists a message written to the inbox and not yet claimed. Negative control: with the claiming rename replaced by a plain read, the concurrency test must fail. Live check, dispatched by the coordinator after the node lands: one read-only investigate node on the local lane, told a codeword through crew tell after it starts, quotes the codeword in its manifest, and its inbox holds the matching receipt; the section closes only on that run.

§9 — Codex workers receive the same delivery

What the prototype found (recorded in Worker steering and anchored edit prototypes). Codex 0.167 has hooks enabled by default and uses the same schema as Claude Code (hooks.json, PostToolUse, hookSpecificOutput.additionalContext), so §8's hook script is expected to work for codex unchanged; the prototype never got a codex hook to run (every attempt stopped at trust), so this section's node is the first to verify it. But codex runs a hook only after its definition has been trusted, and trust is recorded per hook in config as hooks.state.<key>.trusted_hash. An untrusted hook in a headless run is skipped without a word: two prototype runs with the hook declared in a project .codex/hooks.json and inline through -c hooks.PostToolUse=… both completed normally and delivered nothing. Codex also offers --dangerously-bypass-hook-trust.

codex queue is a false clearance. codex queue --thread <id> --message … against a running codex exec session printed Queued message … for thread … and exited 0, and the worker finished its turn without ever seeing the message. That is the shape §1 describes, in a different program. Nothing in reckon may use it as a channel to a live worker.

Deliverable. Under the locked codex-hook-trust decision, the codex launch carries §8's hook and the trust record for exactly that hook as -c overrides on its argv, composed by _CodexDialect — the route workers-spend-fewer-tokens-per-landed-node §5 takes for its MCP server, not yet built at the time of writing. This is narrower than the wording of the locked codex-hook-trust rationale, which speaks of a record in the run's CODEX_HOME: the trust exists only for the run's own codex process and is written nowhere. It keeps every constraint that decision states — only reckon's own hook is trusted, the user's codex config is never written, and the bypass flag is not used — and the lead has been told of the narrowing. No file in the run home is written for this: the codex dialect already seeds the operator's config.toml into every codex run home through its harness_home_files declaration (reckon/schema/flight-defaults.yaml near line 47), copied byte-for-byte by seed_harness_home and _seed_harness_entry (reckon/_worker_fence.py near lines 193 and 432) only when absent, and the fence's merge helpers are JSON-only with no TOML writer in the repository, so a file-based route would either do nothing on an existing home or need a new writer. Argv overrides leave that owner untouched, never reach the user's ~/.codex/config.toml, and cost no new public function.

The node's first step is to establish the override keys: the hook table (hooks.PostToolUse, as the prototype passed it) and the trust record (hooks.state.<key>.trusted_hash) — how the key is formed and how the hash is computed. The route already built for that is reckon's codex app-server client (BudgetProbe in reckon/_backends.py near line 1625, which already performs the initialize handshake and request/answer pairs): ask the app server to list hooks and record trust against a scratch CODEX_HOME, and read the resulting key and hash, falling back to the codex source only if the server exposes neither.

Done when argv tests show the hook and trust overrides present for a codex run and absent for every other dialect, and the user's codex config untouched; and the node, running on the codex lane where a codex home with credentials exists, makes two direct headless codex exec runs of the prototype's three-command task with an inbox message written before each, one with the argv the dialect composes and one with the same argv minus the trust override (built in the test, not by a production parameter): with trust, the message is claimed, a receipt is written and the final answer carries the codeword; without it the message stays unclaimed and no receipt is written. Both streams and receipts are kept as gate logs. Live check, dispatched by the coordinator after the node lands: one codex investigate node told a codeword through crew tell after it starts quotes it in its manifest, with a matching receipt; the section closes only on that run.

But reckon crew tell refuses every codex run at its dialect test (reckon/crew_run_commands.py near line 2554, which admits Claude-dialect run homes only), before the settings check is reached, so a coordinator cannot reach a codex worker through the verb and §9's live check cannot be run.

Deliverable. § Decisions

How far does this go?

Closing the false clearance is cheap and touches no contended file. Building the inbox gives the capability that is actually missing but waits on a surface another coordinator is repairing.

The guard closes the false clearance immediately and touches no contended file; the inbox supplies the capability that is actually missing, and without it the guard would refuse a send while leaving the coordinator with nowhere to go. Landing them separately keeps the cheap half from waiting on the expensive one.

How should codex workers be allowed to run reckon's inbox hook, given codex skips any hook that has not been trusted?

Codex skips any hook whose definition has not been trusted, so without trust codex workers cannot be steered at all. Recording trust for exactly reckon's own inbox hook in each run's private CODEX_HOME keeps the decision narrow: the user's ~/.codex/config.toml is never written, no other hook is trusted, and --dangerously-bypass-hook-trust (which trusts everything, and which the coordinator's safety classifier refuses) is not used. Claude-only steering was rejected because it leaves the codex lane, a third of implement runs, with no channel. Locked by the lead on 2026-11-10.
