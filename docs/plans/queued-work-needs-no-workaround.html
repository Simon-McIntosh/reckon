§1 — Why: coordinators spend their turns working around the harness

At 14:28Z on 2026-11-14 the router would have admitted 13 more local workers. 8 were running, and no request was queued. The lead asked every coordinator session to report the harness defects it had met in two days. 15 of 18 sessions answered, across reckon, nova, power_convertor, imas-codex and imas-efit. They reported 131 defects, logged one per line in ~/.cache/reckon-harness-defects/defects.md, each with the reporting session, the run ids, the refusal text and the workaround applied.

Most of the reports are not crashes. They are workarounds a coordinator applies by hand, every time:

  • Batch queueing bounces. One nova batch refused 5 of 5 entries. One imas-codex batch refused 9 of 11. The refusals were the 60-minute time-budget fence, which a batch entry cannot override, and fields that batch neither takes from the section nor accepts in an entry.
  • Obligations outlive their runs. Seven sessions renamed promotion-request files to .json.settled by hand. They did it because a promotion-failed, sweep-failed or worktree-held row stayed after the run was promoted, landed or discarded, and the stop hook refused every turn on it. crew ack did not hide such a row, and it refuses outright for a run with no pointer and no ledger row.
  • Reservations hold with no worker behind them. A repair round took its attempt's reservation and then held for coordinator advice. The advice it asked for was then refused for 30 minutes as "already has attempt 3 in flight". Reservations and promotion locks held by a pid on the old fleet node were never released after the fleet moved.
  • An automatic repair loop ran unbounded. One run was resumed 437 times overnight. Each round's worker rewrote its status as in-progress with "nothing remaining".
  • Manifest faults are caught at promotion, after the worker has gone. These include a status outside the recognised set, prose or short shas in suite revisions, "sha subject" commit citations, and gate commands naming an absolute /tmp tree that is gone by landing. Each needs a resume or a hand edit of an archived manifest.
  • A section already delivered still reads as ready. One wave dispatched a duplicate of a section another session had landed hours before. Under queue-ahead, this is what turns a deep queue into rebuilt work.

Two blockers were removed by configuration before this plan was written, and are not sections here:

  • The host flight layer raised fences.time_budget to 24h (dotfiles 4cd7481). The budget watchdog is off, so the ceiling only ever refused work.
  • reckon was linked into ~/.local/bin beside codex, so fleet-node shells and resumed workers find it.

Defects already owned by a live plan are left there, and are not restated:

  • MCP read deadlines: a-read-answers-inside-its-deadline.
  • The station's tick and wake latency: work-flows-to-the-lane §64, and the-monitor-reads-each-fact-once §13.
  • Index-lock retries: a-landing-never-waits-on-a-shared-index §10.
  • Reviews held by the roster cap: work-flows-to-the-lane §62.
  • Automatic landing: work-flows-to-the-lane §60.

Each section below names the defect ids it answers, so a reader can check the reports. Every section is independent of the others, and none declares write paths: a node's diff is its scope.

§2 — A batch entry takes every field a single dispatch takes

Why. Defects D1, D35, D76, D95 and D108. Batch entries are refused for over_fence, comment and local, which single dispatch accepts. The command-level --over-fence is silently ignored beside --batch. A batch cannot be dry-run. A priority can only be set after queueing, one request at a time. Durations such as 1h30m are refused. Coordinators fall back to one dispatch per section, which is what batch exists to replace.

Deliverable. A batch entry accepts every per-node option single dispatch accepts, including the over-fence reason, the steering comment, the local-lane choice and a queue priority. A command-level option given beside --batch applies to every entry that does not set it. --dry-run --batch validates every entry and prints one row per entry, writing no pointer and no run directory. A compound duration is accepted wherever a duration is.

Done when. Tests with a temporary repository and crew home show the following:

  • An entry carrying each of those four fields is queued with the same stored request as the equivalent single dispatch.
  • A command-level over-fence reason reaches every entry.
  • A dry-run batch prints a row per entry and leaves the crew home unchanged.
  • An entry with priority 5 is admitted before a same-session entry with none.
  • 1h30m stores as 90 minutes.

Negative control: the same entries against the base revision are refused with "unknown field(s)", and the failing run is logged. The gate runs on all_debug, and its log is written to the section's evidence fragment.

§3 — Every field a dispatch omits is taken from its section

Why. Defects D2, D36, D96, D110 and D120.

  • A batch entry naming only its section is refused with "no time budget is set; no specification level is declared", although the section carries effort hours and capability attributes.
  • A single dispatch with --plan and --section does not take the section's done-when.
  • A path pattern such as pf<n>-terminal-edge.json, or an HTML tag written as test data inside <code>, is refused as a placeholder that "leaves the worker to infer intent".

Deliverable. A dispatch, single or batch, that names a plan section and omits any of the following takes it from the section:

  • the done-when;
  • the time budget, from the section's effort hours;
  • the specification level, from its capability attributes;
  • the negative control, from the done-when's negative-control sentence.

A code span is exempt from the placeholder rule when its text reads as a path or filename pattern (it holds a / or a file extension around the bracketed token) or as an HTML tag written as test data. A code span whose bracketed token stands alone, such as <project>, is still a placeholder and still refused.

Done when. Tests with a temporary repository and crew home show the following:

  • A batch entry naming only project, plan, section, node and goal is queued, with done-when, budget, specification level and negative control equal to the section's.
  • A single dispatch omitting --done-when stores the section's.
  • A done-when naming pf<n>-terminal-edge.json or the tag <strong> inside code spans is accepted.
  • A done-when with a bare <n> in prose is still refused, and so is a code span holding only <project>.

Negative control: the section-only entry against the base revision is refused, naming the budget and specification level. The gate runs on all_debug, and its log is written to the section's evidence fragment.

§4 — A declared write path fences nothing

Why. The lead's directive of 2026-11-14: work is done in worktrees, and file claims are an unnecessary block. Defects D61 and D77. work-flows-to-the-lane §22 and §53 let a node that declares no write paths be dispatched and write anywhere outside the merge-unsafe patterns. A node that does declare them, which every batch entry does when its section carries a write-paths sentence, is still bound in three ways:

  • it is fenced to them;
  • a peer declaring an overlapping path is refused at dispatch;
  • promotion refuses any changed path outside them until the coordinator names each one with --accept-path.

One imas-codex landing had 15 such paths, and the scope it was compared against had been widened silently by an earlier attempt.

Deliverable. Declared write paths are advisory everywhere. No dispatch, queue admission, worker fence or promotion refuses or narrows a node because of a path it declared or did not declare. The only paths that still fence, claim or refuse are the project's merge-unsafe patterns: plans, generated state, cumulative evidence records, figure topic directories and dependency locks. Declared paths remain readable on the request, as a hint to the worker and the reviewer.

Done when. Tests with a temporary repository and crew home show the following:

  • Two nodes declaring the same source file are both queued and launched.
  • A node declaring a.py writes b.py under its fence, and is promoted with no --accept-path.
  • A node writing a figure topic directory that a live peer claims is still refused, naming the pattern.

Negative control: the first two cases against the base revision are refused (the scope conflict, and "changed paths outside its declared write scope"), and the failing runs are logged. The gate runs on all_debug, and its log is written to the section's evidence fragment.

§5 — Dispatch prints one JSON document, and a fresh request never reads as a duplicate

Why. Defects D12, D62, D88, D92 and D131.

  • Dispatch through a pipe printed nothing, or printed text before its JSON, while the run was created.
  • crew review prints "reckon: created run …" ahead of its JSON.
  • The first dispatch of a node waiting on an upstream answers queued: false and "already awaiting-upstream" for the request it has just created.
  • A landing that met an index lock ended in a Python traceback rather than a JSON refusal.

Deliverable. crew dispatch, crew dispatch --batch, crew review and crew complete write exactly one JSON document to stdout on every exit path, success and refusal alike, whether stdout is a terminal, a pipe or a file. Human-readable progress goes to stderr. A request created by the call reports itself as created, with its phase, and never as already present.

Done when. Tests run each verb as a subprocess with stdout piped, through success, refusal and a raised CrewError, and parse the whole of stdout as one JSON document. A test dispatches a fresh node behind an unlanded upstream and reads queued: true, the awaiting-upstream phase, and no "already". Negative control: the piped dispatch against the base revision does not parse, and the failing run is logged.

§6 — A section a run has delivered is not ready

Why. Defects D24, D84 and D119.

  • The roadmap listed an imas-standard-names section as ready three days after its run was promoted, its commits were on main and its tokens had shipped in a release.
  • A reckon wave dispatched a duplicate of a monitor-plan section that another session had already landed.
  • Two runs were promoted "passed" with no landing while their sections were declared done.

A deep queue only helps if nothing in it is already built.

Deliverable. The roadmap's ready set, batch dispatch and admission all treat a section's node as not ready while that node has a live, delivered, promoted or landed implementation run, and say which run holds it. The hold is per node: a section split on purpose into several nodes (as reckon-02 split a context-fit section into three) keeps its other nodes ready while one is in flight or landed. The roadmap reports a section declared done whose run never landed as a wiring finding, naming the run.

Done when. Tests with a temporary repository and crew home show the following:

  • A section whose only node has a promoted run is absent from ready_sections, and a section with a second node not yet queued stays listed.
  • A batch entry for the same node is answered as held by that run, not queued, while an entry for a second node of the same section is queued.
  • A done section whose run's head is not on the integration branch yields the finding.

Negative control: against the base revision, the promoted section is listed ready, and the failing run is logged.

§7 — A finished upstream releases its waiters

Why. Defects D13, D38, D107, D112 and D148.

  • A plan-level dependency on a plan whose sections are all done, but whose status is still active, parked its dependents until the upstream was closed by hand. Batch entries list such a dependency among their waits.
  • Dispatch refuses an input path that a declared upstream section will create.
  • A request routed to a metered lane is never launched once its upstream lands. A coordinator therefore cannot queue a chain whose sections only fit on codex.
  • A review run's pointer survived its promotion (pointer_removed: false). The release check counts any live pointer on a section as an unlanded run of it, so six requests waiting on every-shared-home-lock-holds-across-nodes §2 stayed held for 91 minutes after §2 landed. The promoted §2 row also recorded no plan slug.

Deliverable. A plan-level dependency is met once every section of that plan is done or descoped. An awaiting-upstream request may name an input that does not yet exist, and is refused only if the input is still absent when it is released. An awaiting-upstream request on a metered lane is launched by admission when its upstream lands, under that lane's own admission rule. A review run, or any run that already has a ledger row, never counts as an unlanded run of its section. A promotion that writes a review's ledger row removes its pointer, and every promoted row carries its plan slug.

Done when. Tests with a temporary repository and crew home show the following:

  • A request waiting on a plan whose sections are all done is released without the plan being closed.
  • A request naming a not-yet-existing input is queued, and is refused at release if the input is still missing.
  • A codex-routed awaiting-upstream request launches when its upstream lands.
  • A request waiting on a landed section is released while a promoted review pointer of that section is still live.
  • The ledger row a promotion writes for an implementation run carries its plan slug.

Negative control: against the base revision, the first request stays parked, and the failing run is logged.

§8 — Every obligation clears when its duty ends

Why. Defects D14, D31, D43, D47, D59, D90, D103, D114, D124, D125 and D149. Seven sessions saw promotion-failed, sweep-failed, review-in-flight or worktree-held rows after the run was promoted, landed, resumed or discarded. They saw this after work-flows-to-the-lane §52 landed, so its fix covers only part of the cases. The stop hook refuses every turn on such a row. crew ack returns success but leaves the row, and for a run with no pointer and no ledger row it refuses. One session's rows were served from a station snapshot two hours old. A sweep-failed row comes from the station's per-session failure list, which only that session's next completed sweep replaces, and the view adds each entry back without checking that its run still exists.

Deliverable. An obligation row is removed in each of these cases:

  • its run is promoted, landed, discarded or resumed out of the state that raised it;
  • its request is settled;
  • it is acknowledged.

The row disappears from the obligations view and the stop hook no later than the next station pass. crew ack accepts any run that still raises a row, whatever its pointer or ledger state.

Done when. Tests with a temporary repository and crew home raise each of the four row kinds, then settle the run each way above, and read the obligations view empty after one pass. A test acks a row for a run with no pointer and no ledger row, and reads it moved to acknowledged. A census of the live crew home, written to the section's evidence fragment, counts rows whose run has no live pointer or has landed; the count is zero one pass after the delivered head runs. Negative control: the settled-by-promotion case against the base revision still lists the row, and the failing run is logged.

§9 — A reservation or lock holds only while its holder is working on it

Why. Defects D7, D17, D39, D49, D50, D69, D75 and D116.

  • A repair round took its attempt's reservation and then held for coordinator advice, so the advice was refused as "attempt 3 in flight" until the reservation aged out 30 minutes later.
  • A parked run resumed itself with no event, and a manual resume was refused.
  • Reservations, promotion locks and resume marks held by pids that had exited, or that lived on the old fleet node, held until someone cleared them by hand.

Deliverable. No reservation, promotion lock or resume mark outlasts the work it guards:

  • A path that holds for coordinator advice holds no reservation.
  • A reservation, lock or mark whose holder is proven gone is released when the next reader finds it. On this host, gone means the pid is dead or its start time differs from the recorded one. On another host, gone means that host's own lease or heartbeat has expired. A live holder on another host still holds.
  • A coordinator resume with advice supersedes an automatic repair round that has not started its worker.
  • Every resume prints a transition row.

Done when. Tests with a temporary repository and crew home show the following:

  • An advice hold leaves no reservation on disk.
  • crew resume --advice during the hold is accepted.
  • A reservation naming a dead pid, and one naming a host whose lease has expired, are both released on read. One naming a host whose lease is fresh is kept.
  • A resume mark whose attempt has a result record does not hold review dispatch.
  • A coordinator resume with advice, sent while an automatic repair round holds its reservation without a worker, launches the coordinator's advice and records the repair round superseded.
  • Every resume, automatic or coordinator, writes one transition row a follower prints.

Negative control: the advice-hold case against the base revision refuses the resume, and the failing run is logged.

§10 — A repair round's advice carries every finding disposed into the run

Why. Defects D28 and D50.

  • Between 17:56Z on 13 November and 07:40Z on 14 November, run r-20261113T114341166779-vofa-candidates-vessel was resumed 437 times on the claude lane. Each round's worker rewrote its status as in-progress with checkpoint "nothing remaining".
  • Another repair round's advice named only the blocking dimension finding, and dropped four non-blocking findings folded into the node.

The 437-resume loop was fixed directly on 2026-11-14 (1e9c272ea7): a refusal written between two resumes had reset the round's attempt count, so the cap never fired. Its test is in tests/test_the_reflex_resumes_an_unpromoted_run.py. What remains is the dropped findings.

Deliverable. A repair round's advice carries every finding disposed into the run, blocking and folded alike, each with its id and text.

Done when. A test composes repair advice for a run with one blocking dimension finding and two non-blocking findings folded into its node, and reads all three ids and texts in the advice. Negative control: against the base revision the folded findings are absent, and the failing run is logged.

§11 — A manifest is refused while its worker is live for anything promotion would refuse

Why. Defects D30, D41, D42, D46, D74, D79, D80 and D129. Promotion refused delivered work because of the following manifest faults:

  • a status outside the recognised set;
  • commit citations written as "sha subject";
  • prose or short shas in suite arm revisions;
  • a baseline_suite: none for a test file that is new at the head;
  • a gate command naming an absolute /tmp tree that was removed before landing.

Each needed a resume, or a coordinator's hand edit of the archived manifest. That edit has no verb other than the status word.

Deliverable. The manifest check a worker runs before delivery refuses every condition that promotion would refuse, with the same reason. A test file absent at the base is a complete base arm with zero failures. A suite arm can be re-pointed by a coordinator through a verb that keeps the as-delivered file, as crew repair does for the status.

Done when. A table-driven test runs each fault above through both the manifest check and promotion's refusal, and reads the same reason from both. A test promotes a run whose only new test file has no base arm. A test re-points an arm through the verb and reads the as-delivered file kept. Negative control: against the base revision, the manifest check passes at least the prose-revision row that promotion refuses, and the failing run is logged.

§12 — A review is promoted only after it delivers, and no review run vanishes

Why. Defects D11, D29, D60, D65, D69, D104, D106, D113, D115 and D126.

  • Queued plan reviews moved to promotion-requested with no worker ever launched.
  • A plan review with an in-progress manifest was promoted, then relaunched as two scheduler steps.
  • A queued batch request and a composed review run disappeared, leaving no pointer, discard record or ledger row.
  • A delivered design review's findings could not be answered until its run was promoted by hand.
  • A code-mode health review was refused auto-promotion as review-self.
  • A record that passed crew check --review was unreadable at promotion.

Deliverable. A review run reaches promotion-requested only once its worker has delivered a manifest with a recognised terminal status, and a promoted run is never relaunched. A delivered review's report is stored, and its findings are answerable, without a hand promotion. A code-mode review promotes on its report. The record check and promotion read records the same way. Every request or run that leaves the crew home leaves a discard or failure record naming why.

Done when. Tests with a temporary repository and crew home show the following:

  • A review whose worker never launched stays queued.
  • An in-progress review is not promotable.
  • A delivered design review's findings are listed with ids before any promotion.
  • A code-mode review promotes.
  • A record stored under its plain name is accepted by promotion as by the check.

A census, written to the section's evidence fragment, takes every run id the last day's admission verdict log and dispatch records name, and finds for each one a live pointer, a ledger row or a discard or failure record. A run named in those logs with none of the three is a vanished run, and the census finds none. Negative control: the never-launched case against the base revision reaches promotion-requested, and the failing run is logged.

§13 — Landing judges added failures, and reads a finished review at the head

Why. Defects D34, D52, D58, D70, D72, D73, D93, D101, D123 and D130. Landing refused, or misbehaved, in these cases:

  • a red head whose only failure was the same id at the base;
  • a negative-control log that rightly records a failure;
  • an after-suite arm measured before a later commit that changed only documentation (--waive-suite-delta did not waive it);
  • an evidence-only node with no shell gate;
  • a review of the promoted head that had delivered but was still promotion-requested;
  • a review filing that demanded a numeric added_failure_count for a run with no suite.

A re-run crew complete without --wait answered duplicate: true and did nothing, and crew complete --dry-run submitted a landing measurement job and blocked on it.

Deliverable. Promotion and landing judge a suite by failures added against the base, not by exit status. A log cited as a negative control is required to record a failure. A commit after the after-suite arm that touches no path the suite imports does not invalidate the arm. A node whose done-when names no test lands on its declared evidence check. A delivered review of the asserted head counts, whether or not its own run is promoted yet. A repeated crew complete drives the queued promotion. A dry run submits no job.

Done when. Tests with a temporary repository and crew home land each case above, and read a dry run that writes nothing and starts no scheduler job. Negative control: the paired base-and-head failure case against the base revision is refused as red, and the failing run is logged.

§14 — A decision can hold only its sections, and a batch sees its own earlier ops

Why. Defects D5 and D25. No op scopes a decision to the sections it holds, so every open decision holds the whole plan and coordinators edit the HTML by hand. And close refuses in the same batch as the append_evidence that satisfies it, so one write becomes two.

Deliverable. edit_plan sets the sections a decision holds, and a batch's later ops see the effects of its earlier ones.

Done when. Tests drive both cases through the MCP edit tool against a temporary project and read the plan HTML. A decision scoped to §2 holds only §2 on the roadmap. A close batched after its evidence succeeds in one write. Negative control: the batched close against the base revision is refused at its op index, and the failing run is logged.

§15 — An edit op accepts the input forms its examples show

Why. Defects D98, D99 and D105. archived: true fails with a raw schema error while the string "1" works. A followup append requires written_at and written_by, which the reckon-edit examples omit. A sprint append refuses a committed plan until some state write registers it.

Deliverable. Boolean and string spellings of a flag are both accepted. A followup append defaults its author and date. A sprint append resolves any committed plan with valid metadata.

Done when. Tests drive the three cases through the MCP edit tool against a temporary project and read the written plan or sprint, one test per case. Negative controls, one per case, each run against the base revision and logged: archived: true fails with the schema error; a followup append without author and date is refused; a sprint append naming a committed plan with no state write is refused.

§ Followups

Review, then queue every section in one batch

§2–§15 are independent, and each removes one family of workaround. Once the content and design reviews are answered, queue them all in one batch, with priority to §4 (the lead's directive), §8, §9 and §2. Each delivered section is announced to the reporting sessions it answers.
