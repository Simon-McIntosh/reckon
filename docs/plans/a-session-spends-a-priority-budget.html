§1 — Why: priority is a per-request afterthought, and the queue cannot be read

The lead's direction of 2026-11-14 has four parts:

  • sessions submit work with a priority;
  • work dispatches in the order of its DAG;
  • the lane is shared fairly across sessions while staying full;
  • each session holds a priority budget, spends it as it chooses, changes it at any time to promote a run, and can inspect the queue through callables or MCP tools.

The coordinator read the admission order at 1ad29c422c. DAG order and fair share already hold:

  • a declared section wait parks its request until the upstream lands;
  • within a project, ready requests launch in roadmap order;
  • across sessions, each launch goes to the session with the fewest live runs on that lane;
  • delivered reviews go first;
  • a request waiting 30 minutes or more is aged forward.

Priority, budget and inspection do not hold:

  • Priority cannot be given at submission. Neither crew dispatch nor a batch entry accepts one. It is set afterwards, one request at a time, with crew queue reprioritise.
  • Priority is unbounded and has no cross-session meaning. Any session can mark every request at any value, so the number carries no information. It orders only a session's own requests and its project's sessions, and never trades against fair share. Nothing stops one session claiming the lane. Nothing lets a session spend a limited claim on the one run that matters.
  • Priority stops at launch. A prioritised run's review and its promotion request queue at default priority. A coordinator who wants a run landed first cannot say so to the review queue or the promotion queue.
  • The queue cannot be read as a queue. No view, MCP read or importable function lists the queued and awaiting requests in the order admission will launch them, with the reason for each place. A coordinator reconstructs it from crew view live and pointer files, and cannot see where its request stands against other sessions.

§2 — Each session holds a priority budget and spends it at submission or later

Deliverable. The flight configuration declares a per-session priority budget, a whole number of points.

  • A session gives a request a priority at submission, through crew dispatch, a batch entry or crew review. It changes that priority at any time before launch, through crew queue reprioritise.
  • The points a session has placed on its unlaunched requests never exceed its budget. A submission or change that would exceed it is refused, naming the budget, the points in use and the requests holding them. A request's points return to the budget when it launches, is dropped or is discarded.
  • Admission orders requests across sessions by priority first. Requests of equal priority are ordered exactly as they are today: delivered reviews first, then ageing, then fair share by live runs, then roadmap rank. The ageing rule still lifts any request that has waited past its bound, so a spent budget can move work ahead but cannot starve another session.

Done when. Tests with a temporary repository and crew home show the following:

  • A dispatch and a batch entry each carry a priority onto the stored request.
  • With a budget of 10, priorities of 6 and then 5 on two requests: the second is refused, naming 6 of 10 in use. After the first launches, the second is accepted.
  • Of two sessions, the one with more live runs but a priority-3 request has that request admitted before the other session's priority-0 request.
  • A priority-0 request older than the ageing bound is admitted before a fresh priority-3 request.

Negative control: the cross-session case against the base revision admits the session with fewer live runs first, and the failing run is logged. The gate runs on all_debug, and its log is written to the section's evidence fragment.

§3 — A run's priority carries to its review and its promotion

Deliverable. The priority a run held when it launched is inherited by the review composed for it and by its promotion request. Both queues order by it, ties falling back to their current order. A coordinator promotes a delivered run, so that its review and its promotion move ahead, by setting its priority through the same reprioritise verb, charged to the same session budget. The points return when the run lands or is discarded.

Done when. Tests with a temporary repository and crew home show the following:

  • A priority-4 run's review is admitted before a priority-0 run's review queued earlier.
  • Of two promotion requests, the priority-4 one is drained first.
  • Reprioritising a delivered run charges the session's budget, and landing returns the points.

Negative control: the promotion-order case against the base revision drains in request order, and the failing run is logged. The gate runs on all_debug, and its log is written to the section's evidence fragment.

§4 — The queue reads as a queue, from the CLI, MCP and Python

Deliverable. One read answers "where does my work stand". It is served as reckon crew view queue, as the MCP crew(view="queue"), and as an importable function that returns the same document. It lists every queued and awaiting-upstream request and every pending review and promotion. Each row carries:

  • its position in the order admission would launch it next;
  • its session, project, plan section and lane;
  • its priority;
  • how long it has waited;
  • the reason for its place, in the same words admission records on its verdict row;
  • for a request that cannot launch, the hold that stops it.

Each session's budget, the points in use and the points free appear beside the rows. The read filters by session and by project. It is derived in Python and computed by the same ordering that admission uses, so the view and the next admission pass cannot disagree.

Done when. A test queues requests from two sessions with different priorities, waits and holds, and reads the same order and reasons from the function, the CLI and the MCP tool. A test runs one admission pass and reads the request it launched at position 1 of the view taken just before. Negative control: a view that ordered by queue time alone fails the position-1 test, and the failing run is logged.
