§1 — An orchestrator has two halves and only one of them is automatic

Dispatch is reflexive. A coordinator reads a plan, cuts nodes, and sends them, and every part of that is prompted by the work itself. The return half is not. Work that comes back has to be merged, conflicts have to be resolved, a blocked run has to be unblocked and an unpromoted one has to be promoted — and nothing asks for any of it. The orchestrator is the only thing that knows those duties exist, which means they are discharged exactly as often as it remembers.

That is not a discipline problem to be solved by trying harder, and this plan does not propose a checklist. It proposes that the three duties which can be automatic become automatic, that the one which cannot be automatic be made visible in a form that prompts action, and that the signals all of this rests on be true. Each is separately measured below.

The orchestrator loop. The outbound half is prompted by the plan; the return half is prompted by nothing.

§2 — A finished run dispatches its own review

When a run reaches a terminal state with a manifest it is classified scoring, which means finished and awaiting an independent review. Promotion is correctly refused until that review exists. Nothing creates it.

The command is already composed. _review_dispatch_action at reckon/crew/recovery.py:145 builds the complete dispatch for the review a scoring run needs — project, plan, section, node id, goal, done-when, write path, time budget, session and --local — and returns it as a string for a person to read and retype. The system knows exactly what to run and prints it instead of running it.

What that costs, measured 2026-09-18 across this workstation. Six runs sat in scoring at one moment, four on reckon and two on nova, each waiting on a command already written out in full. Within one reckon session nine runs accumulated unreconciled across a working day, four of them with their code already merged to the main branch and the ledger not knowing it; the oldest had been waiting fourteen hours. The coordinator's own account when asked was two are being handled, seven are not.

The rule. A run entering scoring dispatches its own review to the local lane, as a reflex, without being asked. The sole exception is the local lane being unavailable, in which case the run is recorded as awaiting review with the lane's state as the reason, and the review dispatches when the lane returns. The dispatch is subject to the same admission checks as any other — scope, member, follower, context fit — because an automatic dispatch that bypasses admission is worse than a manual one that does not.

§3 — A plan is not released until something has read it back

A plan is written by one agent and executed by many. Between those two moments nothing checks that what was written says what its author meant, and the failure mode is not a typo — it is a sentence that reads differently to the executor than to the author.

Measured on this project, 2026-09-17 to 18. A decision was locked with the note spell out queued then there is no ambiguity. The coordinator read that as an instruction to render the whole word in the fleet counter, and cut a node accordingly. The lead had meant the bucket should be named queued so that its existing letter q decoded. The node did exactly what it was asked, the change merged, and every session on the workstation lost five columns of the reason clause on every row until it was reverted the following morning. A reader whose only job was to restate the decision in its own words before dispatch would have surfaced the divergence in one turn, at no cost to anyone.

The rule. When a plan is authored or materially revised, reckon-edit dispatches a rubber-duck review to the local lane: a read-only node whose deliverable is a restatement of the plan's intent, its decisions and its done-whens in the reviewer's own words, plus any place where two readings are possible. The orchestrator acts on the findings before the plan is released. An unreviewed plan is refused for execution — not warned about — because a warning at dispatch time is read by the same agent that skipped the review.

Two properties keep this cheap. The review is read-only, so it needs no worktree and no write scope beyond its own record. And it is bounded by the plan, not by the codebase: its input is one document, which is why it can run on the local lane in minutes while an implementation review cannot.

§4 — The inbox is a duty, and a total is not an inbox

The fleet counter renders four quantities in one grammar — 6w· 1b· 4u· 1q. Two of them are the orchestrator's inbox: a blocked run needs a decision, an unpromoted one needs merging, reviewing or recording. Two are work in progress and need nothing. All four look identical, so the pair that demands action does not stand out from the pair that forbids it.

Nothing re-raises the inbox. The follower emits on state change, so a run that became unpromoted at 03:00 produced one transition and is silent from then on. Its count persists on every subsequent row — always present, never new — and a figure that is always there stops being read.

And a total cannot show whether the inbox is being worked. Measured while draining this session: the coordinator cleared one blocked item and reported the count had moved from two to one. It had, on exactly one row, for a few seconds; a different run entered the same bucket moments later and the lead's screen read two throughout. The count was stable while its membership turned over completely. Worse, the two were not comparable in kind — one was a dead review correctly recorded, the other a healthy worker whose stream had been written 162 seconds earlier and which was misclassified by the placeholder-wait defect of §5.

The rule. The actionable cells carry identity or age, not only a total: the oldest item's age, and a count of items unchanged since the reader last saw a row. The orchestrator's duties are named where a coordinator reads them before dispatching rather than discovered when something breaks — an orchestrator dispatches and is bound to merge, resolve, unblock and promote what returns.

The classifier must read what a field says rather than that it exists.

§6 — What this plan does not own

The row's rendering — column widths, counter letters, colour, truncation — belongs to monitor-renders-what-it-is-given, and the findings in §4 and §5 are recorded there as well as here. This plan owns the obligation: what an orchestrator must do with a signal once it is true, and which of those duties stop being manual.

Removing a compensation the coordinator performs by hand belongs to work-does-not-fall-to-the-coordinator. The distinction is that that plan retires hand-work which should not exist; this one automates duties which should exist and currently depend on memory.

§ Decisions

Where does an unreviewed plan get refused — at dispatch of its first node, or at the ship invocation that reads it?

Enforced by code at the crew dispatch preflight, which is where every execution path already passes and where every other admission check already lives — scope, member, follower, context fit, budget. A refusal at ship would be a rule inside a skill, which is a rule an agent can skip; a refusal at dispatch is a rule the surface applies whether or not the agent knows it exists. Refusing at both would duplicate the check in a place that cannot enforce it, which is how two copies of one rule drift.

When the local lane was unavailable and then returns, does the backlog of awaiting-review runs dispatch all at once, or at a bounded rate?

Withdrawn as speculative rather than answered. The as-needed rule already settles it and leaves no backlog to have a policy about: a review dispatches when its run needs one, so an unavailable lane leaves runs awaiting review rather than a queue waiting to be drained, and when the lane returns each review dispatches at the moment something needs it. There is no separate drain and no rate to choose. The question was raised against a condition that does not hold, the local lane is serving, and encoding it as open made the plan read as blocked on a choice nobody needed to make.

/reckon-build an-orchestrator-is-bound-by-its-inbox §2

The mechanism, settled by the lead. Enforcement is code at the crew dispatch preflight, not prose in a skill. Three pieces.

1. The plan resource gains review state, which it does not have today. The only reviewed_at in the schema belongs to the project-level review singleton; there is no per-plan review record at all. The plan gains one, and the load-bearing field is not the timestamp: it is the plan version the review read. A review is current when that version equals the plan's current version, so any edit to a plan makes it unreviewed again by construction rather than by anyone remembering. A timestamp alone cannot express that, because a plan edited a minute after review is newer than its review and still reads as reviewed.

2. The preflight refuses. crew dispatch already refuses on scope, member, follower, context fit and budget; this joins them. A node whose plan has no current review is refused, and the refusal names the plan, the version reviewed and the version now.

3. The refusal dispatches the review rather than describing it. This is the trap §2 exists to close and it must not be re-dug here: _review_dispatch_action composes a complete command and returns it as a string, and the result is six runs waiting on a command the system had already written. The preflight refusal must therefore launch the plan review on the local lane, with the unavailable lane as the sole exception, and report that it has done so. A refusal that prints an instruction is the same defect wearing a different hat.

What the review checks is broader than a rubber-duck read. It reads the plan back in its own words and names any sentence with two readings — the failure that cost every session five columns this morning. It also audits the plan against reality: whether the implementation state of the code still matches what the plan claims, whether sections recorded as landed actually landed, and whether linked plans, and unlinked ones covering the same ground, have overtaken it. A plan that is internally coherent and describes a codebase that has moved is stale in the way that matters, and only a reader looking at both can say so.

Rollout is as-needed and there is no pause. Every plan must pass through review including the ones that already exist, but not as a backfill wave: a plan is reviewed the first time someone dispatches against it, which spreads the cost across the work that actually needs each plan and spends nothing on plans nobody touches. The first dispatch against an unreviewed plan costs one review; every dispatch after it costs nothing until the plan is edited again.

The largest risk to §2, measured before §2 was written. Making review dispatch automatic is worth nothing if the review then produces no record, and on 2026-09-17 to 18 five review runs on this project ended having done substantial work and written no review record at all. Two of them were attempts at the same node; one node needed four attempts before a record existed. An automatic reflex that fires into this failure rate manufactures runs rather than reviews.

The signature, and it is not an error. Comparing the five against reviews that succeeded, the discriminator is the terminal record's own text. Successes end with a conclusion or with nothing. Failures end mid-sentence, narrating work they were about to begin: Reading the helper implementations the module depends on, and Typos slipped in. Rewriting the driver carefully. Both carried subtype: success with is_error: false. Tool-use counts were 24 and 33 against 49 for both successes. This is the documented shape of a process ending with its turn, not a crash and not a lane fault.

Four mechanisms were proposed and measured away before this one. An oversized request: refuted, no request in any of the runs exceeded the window, maxima 165,846 and 98,918 against 480,000. Context exhaustion: refuted by the same figures. Lane saturation: one api_retry in a 25,048-record stream. A cumulative usage figure read as a single request: that was a misreading of the terminal record's own aggregate, and the falsifier was one row away, because a run that succeeded shows 14,023,168 by the same measure. Recording the dead ends matters as much as the finding, because each looked sufficient at the time.

The mitigation, and its evidence is thin on purpose. Every review brief now carries an instruction to write the record as soon as every dimension has a first score and refine it in place, on the reasoning that a thin record which exists is recoverable while a perfect one never written is indistinguishable from a crash. Two reviews delivered on their third attempt carrying it, and neither wrote early — both wrote at the end like every success before them. So the failure rate moved and the instructed behaviour did not, which means the correlation is unexplained and the instruction is not yet evidence of anything. It costs nothing to keep and should not be cited as a fix.

What §2 owes because of this. An automatic dispatch must record the review's absence as loudly as its verdict: a run whose review ran and produced nothing is not the same as one whose review never ran, and today both leave the parent in scoring looking identical. Until a review that writes nothing is distinguishable from one that was never dispatched, the reflex will quietly re-fire against the same node and the count will not move.

The peer opens by retracting their own finding, which is the part that makes the rest credible: they believed --stall-window made the watcher exit and release the project seat, raised theirs to six hours to prevent it, and then found that in follow mode the breaks sit inside for…else loops under while True — a stall emits one stalled event, adds the run to reported_runs, skips that poll's sleep and carries on. Root cause of the stale follower rows, and the honest scope: this is signal noise, not latency. Raised by the lead against a payload showing 28 registrations of which 2 deliver.

The mechanism, and the design being right is the point. A follower registration is an advisory flock on <watch>/<project>.followers/<session>-<hash>.lock, and liveness is whether that lock is held. That is correct by construction — the kernel releases the lock however the process ends, so a killed, crashed or expired follower cannot leave a registration claiming to deliver. The docstring says exactly this and it is the reason the seat is trustworthy. Nothing about liveness is wrong.

The defect is one missing line. Releasing the registration releases the lock; nothing unlinks the file. list_followers globs *.lock and returns a row per file. So the registry is append-only by construction: it holds one entry for every distinct session name that has ever followed the project, forever, and grows at roughly the rate sessions are created.

Scale, measured across the workstation. 72 registrations across six projects — reckon 28 (2 live), imas-codex 14 (2 live), imas-ambix 13 (1 live), nova 12, imas-standard-names 3, imas-efit 2. The oldest is dated 1 September, seventeen days back. Reckon accrues about 1.6 a day.

What this does NOT cost, stated because the opposite is the natural assumption. Listing 28 rows takes 0.028 s, and the only consumer in the codebase is watch_state at reckon/crew/runs.py:1823. Dispatch never calls it. So the accumulation does not contribute to dispatch latency and fixing it will not make dispatch faster; the entire cost is that a reader is handed 28 rows to find 2 facts.

Why it belongs on this section rather than in a tidy-up queue — the author anticipated it exactly. The comment above the liveness reason block reads: a dead row's only timestamp is when it attached, “so a dead row's only timestamp makes it look older and better established rather than stale — and a reader counting rows to ask ‘is this project covered’ is then answered by a registration that ended.” The known failure was then mitigated by attaching a not_live_because sentence to every dead row, rather than by not reporting rows that are not registrations. That is a compensation carried in the payload instead of the payload being right — the same shape as every other finding on this plan, and the reason a reader must currently decode 28 explanations to learn that 2 sessions are covered.

The obvious fix is wrong and the reason is worth writing down. Unlinking a dead file when a reader notices it races against the design: process A takes the lock on the dead file and unlinks it while process B opens the same path, creates a fresh inode and locks that — both then hold “the” lock for one session. The flock scheme is safe precisely because the path is stable, so sweeping on the read path trades a correct liveness signal for a tidy list.

The safe change, in two independent halves. First, the payload reports the registrations that deliver plus a count of those released, never the released rows themselves; followers_live already exists and is already correct, so this is a reporting change with no liveness risk at all. Second, a sweep by age removes files whose lock is free and whose mtime is older than a threshold, invoked from an explicit maintenance path where no concurrent registration is in flight — never from a read.

Falsifier, both halves. A project with N released and M live registrations reports M rows and the number N, for N of 27 and for N of 0. And the negative half, which is what makes the sweep safe: a registration released moments ago whose session is restarting is not swept, and a live registration is never swept whatever its age — a follower armed at 09:00 and still delivering at 18:00 must survive a sweep that removes rows half its age.

Two false signals found in one dispatch attempt, both fitting this section exactly, and the second is the worst signal defect recorded on this plan so far.

One: a discarded run renders as promoted. A dispatch died; its pointer was discarded with crew discard, which by its own help text removes a pointer without recording promoted evidence. The ticker then emitted abandoned → promoted for that run, and the unpromoted counter fell by one. The committed ledger holds zero rows for that run id against 1,072 rows in total, so nothing was promoted and no evidence exists. promoted in the ticker means the live pointer disappeared, not a record was written — and those are the two things an orchestrator most needs to tell apart, because one is work banked and the other is work erased. An orchestrator clearing a backlog by discarding would watch its inbox drain and its ledger stay still, with the display congratulating it at every step. Any transition into promoted must be evidenced by the ledger row it claims, and a pointer that vanishes without one is a distinct state needing its own word.

Two: a rollback that cannot succeed, and destroys the error that invoked it. reckon/crew/dispatch.py:3308. The except Exception path runs in this order: unwire peer channels, kill the spawned worker, _remove_worktree(...), shutil.rmtree(directory), pointer_path(run_id).unlink(), raise. But _remove_worktree refuses while a live pointer claims the path — and that pointer is deleted two lines later. So the removal always raises, the unlink and the bare raise are unreachable, and the original exception is replaced by a message about worktree removal naming the run the dispatch had just created. Every post-pointer dispatch failure therefore presents identically, masks its own cause, and leaves worker dead with worktree, pointer and run directory behind — which is the abandoned classification. Deleting the pointer before removing the worktree is a one-line ordering fix; preserving the original exception is the half that matters, because without it no operator can ever see why a dispatch failed.

The cost is concrete and runs the opposite way to the skeleton problem. A skeleton risks promoting work that should have been rejected. A stale review risks refusing work that is already correct: a coordinator reading finding 1 in good faith would have held a node whose defect had been repaired, and would have been right to, on the evidence available. What it asks of the field. reviewed_commits alone is not enough to catch this, because a reader must still compare. The comparison is cheap and mechanical once the field exists: a review is current when the commits it names are the commits the run landed and nothing has touched the reviewed paths since. Where they differ, the record should say so rather than leaving the reader to discover it by measuring, which is what happened here and only happened because the promotion was being untrust-checked anyway.
