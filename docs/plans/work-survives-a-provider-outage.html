§1 — A temporary outage became a permanent loss

On 2026-09-03 a five-node wave was dispatched on a metered lane at 19:34Z and every node was refused per-request on a spend limit within seconds. The refusal was temporary: the operator re-authenticated and the same lane was proved to serve at 19:44Z by a direct one-token probe. This occurrence cost minutes, and no artifacts — a figure corrected below, because it was overstated twice in opposite directions before it was measured. What the occurrence demonstrates is a sequence that is available on every metered lane and that a future refusal arriving a few turns later would make expensive.

The coordinator read session_id: null on each live pointer, concluded the runs could not be resumed, and promoted all five. Both halves of that conclusion were wrong, and nothing in the system said so. resume_plan already recovers a missing session id by calling observe and re-reading the stream, so a null in the pointer means only that observe has not run yet — never that a run is unresumable. And crew complete accepted each blocked run, returned ok=True, removed the pointer and released the worktree. The five session transcripts are still on disk, at 271 KB, 194 KB, 103 KB and two at 50 KB. They have nowhere to resume into.

This plan exists because that sequence is available to every coordinator on this workstation, on every metered lane, and because the loss reported success. The prior instance was the same day: a session promoted five refusal-killed runs and destroyed five resumable sessions; on the next denial a peer resumed instead and two came back working, one to completion. Twice in one day, two different sessions, identical mechanism.

§2 — A promotion that would destroy a resume path is refused

Promotion is the only route by which a run enters the committed ledger, and it is unconditional about evidence: a passing gate is refused unless it carries the check that produced it. It is silent about recoverability. A run classified blocked whose session is still recoverable is accepted without comment, and the operation that follows is irreversible.

The fix is the one this repository already applies to every other dangerous operation: refuse, and offer a recorded waiver. Promoting a blocked run whose session id is present in the pointer, or recoverable from its stream, is refused with a message naming crew resume. A coordinator who genuinely wants the promotion passes an explicit waiver, and the waiver and its reason land on the ledger row — so a deliberate discard is distinguishable afterwards from an accidental one, which is precisely the distinction the incident could not make.

Done when promoting a blocked run with a recoverable session is refused and the refusal names the resume command; when the same promotion succeeds with an explicit waiver and the ledger row carries the waiver and its stated reason; when a blocked run with no recoverable session promotes unchanged; and when a run with a passing gate is unaffected in every case. Asserted through the same crew complete entry point a coordinator invokes, over pointers and streams built the way dispatch writes them under a temporary configuration home, with the real configuration home asserted untouched afterwards.

§3 — The worktree outlives the promotion while the session lives

Releasing the worktree is what converted a recoverable outage into a loss. The session transcripts survived; the directory they had been oriented against did not, and a resume has no cwd. This is the more consequential half of the incident and it is separable from §2: even a deliberate, waived promotion should not strand a live session.

A session and its worktree are one recoverable unit, so the release must be conditioned on the session being unrecoverable rather than on the run reaching a terminal state. Where a session survives, the worktree is retained and the retention is recorded on the ledger row, so a later audit can find the trees that are deliberately held open and distinguish them from the stranded ones. The existing worktree audit already distinguishes clean-and-reachable trees from those holding unintegrated work; a retained-for-resume tree is a third category and must not read as either.

Done when promoting a run whose session is recoverable retains its worktree and records the retention; when promoting a run whose session is unrecoverable releases it as it does today; when a waived promotion retains the worktree unless the waiver explicitly discards it; and when the recorded retention is visible to whatever enumerates worktrees, so a retained tree is never reported as stranded. Asserted through the promotion entry point, and through the audit that reads worktrees, rather than through the release helper.

§4 — A missing session id is not evidence of an unresumable run

The coordinator's reasoning was sound given what it was shown. The live pointer said session_id: null; nothing said that value was merely unpopulated rather than absent, and nothing said the stream held it. resume_plan has recovered exactly this case for some time — if the record lacks a session id it calls observe and re-reads — so the capability existed and its existence was invisible at the moment of the decision.

This is the same defect family as the display work in fleet-monitor-legibility: a fact is recorded and its consumer discards it, or in this case never learns it can be derived. The remedy is that anything reporting on a terminal run reports recoverability as a derived answer rather than leaving a reader to infer it from a null. A coordinator asking observe about a dead run should be told whether it can be resumed, not handed a field it must know the internals to interpret.

Done when observing a dead run whose pointer carries no session id, but whose stream does, reports the run as resumable and names the recovered id; when a run with neither reports as not resumable and says which evidence was absent; and when neither answer requires the caller to read session_id directly. The negative must be asserted so the not-resumable answer stays reachable. Asserted through observe as a coordinator calls it.

§5 — The recovery order is carried by the tool, not by memory

The correct order after a per-request refusal is: inspect the worktree for committed and uncommitted work, resume the session, and reconcile only once resume is impossible. That ordering has been recorded in this workstation's guidance since the first instance and was not applied at the second, four hours later, by a different session. Guidance that must be recalled at the moment of an incident is a compensation, and this plan's §2 through §4 exist because compensations fail.

What the tool can carry is the ordering itself. A refusal-killed run is already classified blocked; that classification can name its own remedy, so the operator reads the recovery rather than deducing it. The same applies to the display: a blocked row whose session is recoverable is a different operational state from one that is not, and the pane currently renders them identically.

Done when a run blocked by a provider refusal carries its remedy in the record — the resume command, with the recovered session id — so the recovery is read rather than recalled; and when that remedy survives into the promoted ledger row, so a post-hoc reader of a discarded run can see what was available at the time. Asserted through the classifier entry point and the promotion path, from a stream carrying a real per-request refusal rather than a synthesised one.

§6 — Recovering the five runs already lost

The sessions are not gone. Every promoted ledger row retained its session_id, because crew complete ran observe on its way through — so the ids the coordinator believed were absent were written into the permanent record by the very operation that destroyed the resume path. All five transcripts are on disk, and every row retains base_sha 580fff9d, the commit each run was oriented against.

So recovery is mechanical rather than speculative: recreate each worktree at the recorded base sha, provision it as dispatch does — the environment and credential symlinks matter, since a forgetful command otherwise builds a second environment — and resume the session in that directory. The two single-turn sessions are not worth the ceremony and are better redispatched; the twenty-nine, twenty and thirteen turn sessions are where the value is. This section is owned by the S16 coordinator, who holds the write scope for those nodes and knows what each had established; it is recorded here so the recovery is not lost if that session ends.

SECTION 3 IS RESHAPED BY A PEER RCA THAT IS SHARPER THAN WHAT I AUTHORED, and it comes with a severity correction that must travel with it. THE SEVERITY FIRST, BECAUSE I REPEATED THE WRONG FIGURE. The five streams were measured for file-writing tool calls and carry Write 0, Edit 0, MultiEdit 0 and NotebookEdit 0 across all five, against nine Read calls and nineteen Bash calls on the three substantive runs. That agrees with the git status and the empty commit range taken before promotion. So there was never a work product: the transcripts were never endangered by promotion, and recreating the worktrees recovered a working directory rather than any artifact. The incident cost minutes. Both earlier framings were wrong in opposite directions - first unrecoverable loss, then sixty-four turns of orientation not lost - and neither survived measurement. The defect below is real and a refusal arriving a few turns later would make it expensive; the occurrence that exposed it was cheap. THE ROOT CAUSE IS NARROWER AND WORSE THAN PROMOTION CLOSES TREES. The release path is careful: it delegates to the gc classification and reclaims only trees classified integrated or disposable, withholding a dirty tree because nothing reclaims a worktree holding work that exists nowhere else, and an unintegrated one because removing it would destroy the only copy of that commit. Those verdicts are right, and they mean the catastrophic version of this cannot happen through promotion at all. THE DEFECT IS THAT THE ONE GUARD WHICH WOULD HAVE FIRED IS GUARANTEED FALSE AT THE MOMENT IT IS CHECKED. A tree is withheld as live-referenced when a live run pointer still claims it, and release runs only after the ledger append and the pointer delete have both succeeded - so the pointer whose existence would raise that verdict is removed one step before the classifier looks for it. The live claim list is empty by construction on every promotion-triggered release. The guard protects a tree from gc and gives promotion a free pass, which is the ninth instance in this repository of a capability that reads as protection while being unreachable. AND THE CLASSIFICATION ANSWERS THE WRONG QUESTION. It asks whether a tree holds work that exists nowhere else, which is a question about artifacts. It never asks whether a tree serves a session that could still continue, which is a question about capability. The five trees were clean at base, so integrated was the correct verdict about artifacts and simultaneously the wrong decision, because each was the working directory of a live resumable session. The vocabulary has no term for that state, and a state nothing can name is a state nothing can guard. FIVE FIXES, ADOPTED IN THE PEER'S ORDER OF VALUE PER LINE. One, release on a passing gate only, which becomes this section's primary measure: a passing gate is a closure and its tree is spent, while a failed or not-run gate is by definition a triage step whose node will be resumed, retried or reshaped. It keys on data promotion already holds, needs no new classification, composes with the section 2 guard rather than duplicating it, and would have withheld all five. Two, the waiver of section 2 retains the tree - a waiver means record this now, never and burn the working directory. Three, either classify before the pointer delete or pass the record being promoted into the inspection, so a live-referenced verdict is reachable in a test rather than dead code. Four, add the missing term, a clean tree whose record carries a session id and whose gate is not passing, with a withheld reason stating that removal leaves the session with no working directory. Five, report the consequence rather than the act: a released flag reading true is a true statement phrased as an accomplishment, and naming the session whose resume it forecloses puts the cost on the same line as the act.
