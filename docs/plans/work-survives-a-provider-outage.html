§1 — A temporary outage became a permanent loss

On 2026-09-03 a five-node wave was dispatched on a metered lane at 19:34Z and every node was refused per-request on a spend limit within seconds. The refusal was temporary: the operator re-authenticated and the same lane was proved to serve at 19:44Z by a direct one-token probe. This occurrence cost minutes, and no artifacts — a figure corrected below, because it was overstated twice in opposite directions before it was measured. What the occurrence demonstrates is a sequence that is available on every metered lane and that a future refusal arriving a few turns later would make expensive.

The coordinator read session_id: null on each live pointer, concluded the runs could not be resumed, and promoted all five. Both halves of that conclusion were wrong, and nothing in the system said so. resume_plan already recovers a missing session id by calling observe and re-reading the stream, so a null in the pointer means only that observe has not run yet — never that a run is unresumable. And crew complete accepted each blocked run, returned ok=True, removed the pointer and released the worktree. The five session transcripts are still on disk, at 271 KB, 194 KB, 103 KB and two at 50 KB. They have nowhere to resume into.

This plan exists because that sequence is available to every coordinator on this workstation, on every metered lane, and because the loss reported success. The prior instance was the same day: a session promoted five refusal-killed runs and destroyed five resumable sessions; on the next denial a peer resumed instead and two came back working, one to completion. Twice in one day, two different sessions, identical mechanism.

§3 — The worktree outlives the promotion while the session lives

The release is now conditioned on the session being unrecoverable rather than on the run reaching a terminal state, so even a deliberate, waived promotion does not strand a live session. A retained tree records its retention on the ledger row and reads as its own third category in the worktree audit — never as clean-and-reachable and never as holding unintegrated work — and a waived promotion still retains the tree unless the waiver explicitly discards it. 19 passed in 1.50 s with zero added ruff findings against a baseline of 10, asserted through the crew complete entry point and through the audit that enumerates worktrees rather than through the release helper. Full record: §3 landed (commit a1bf7da).

§4 — A missing session id is not evidence of an unresumable run

The coordinator's reasoning was sound given what it was shown. The live pointer said session_id: null; nothing said that value was merely unpopulated rather than absent, and nothing said the stream held it. resume_plan has recovered exactly this case for some time — if the record lacks a session id it calls observe and re-reads — so the capability existed and its existence was invisible at the moment of the decision.

This is the same defect family as the display work in fleet-monitor-legibility: a fact is recorded and its consumer discards it, or in this case never learns it can be derived. The remedy is that anything reporting on a terminal run reports recoverability as a derived answer rather than leaving a reader to infer it from a null. A coordinator asking observe about a dead run should be told whether it can be resumed, not handed a field it must know the internals to interpret.

Done when observing a dead run whose pointer carries no session id, but whose stream does, reports the run as resumable and names the recovered id; when a run with neither reports as not resumable and says which evidence was absent; and when neither answer requires the caller to read session_id directly. The negative must be asserted so the not-resumable answer stays reachable. Asserted through observe as a coordinator calls it.

§5 — The recovery order is carried by the tool, not by memory

The correct order after a per-request refusal is: inspect the worktree for committed and uncommitted work, resume the session, and reconcile only once resume is impossible. That ordering has been recorded in this workstation's guidance since the first instance and was not applied at the second, four hours later, by a different session. Guidance that must be recalled at the moment of an incident is a compensation, and this plan's §2 through §4 exist because compensations fail.

What the tool can carry is the ordering itself. A refusal-killed run is already classified blocked; that classification can name its own remedy, so the operator reads the recovery rather than deducing it. The same applies to the display: a blocked row whose session is recoverable is a different operational state from one that is not, and the pane currently renders them identically.

Done when a run blocked by a provider refusal carries its remedy in the record — the resume command, with the recovered session id — so the recovery is read rather than recalled; and when that remedy survives into the promoted ledger row, so a post-hoc reader of a discarded run can see what was available at the time. Asserted through the classifier entry point and the promotion path, from a stream carrying a real per-request refusal rather than a synthesised one.

§6 — Recovering the five runs already lost

The sessions are not gone. Every promoted ledger row retained its session_id, because crew complete ran observe on its way through — so the ids the coordinator believed were absent were written into the permanent record by the very operation that destroyed the resume path. All five transcripts are on disk, and every row retains base_sha 580fff9d, the commit each run was oriented against.

So recovery is mechanical rather than speculative: recreate each worktree at the recorded base sha, provision it as dispatch does — the environment and credential symlinks matter, since a forgetful command otherwise builds a second environment — and resume the session in that directory. The two single-turn sessions are not worth the ceremony and are better redispatched; the twenty-nine, twenty and thirteen turn sessions are where the value is. This section is owned by the S16 coordinator, who holds the write scope for those nodes and knows what each had established; it is recorded here so the recovery is not lost if that session ends.

§7 — A refused wave resumes itself

Everything above is defence. It refuses a promotion that would destroy a resume path, keeps the worktree alive, makes recoverability legible and names the remedy in the record — and after all of it, a human or a coordinator still has to notice the outage and type the command. That is the wrong shape for this failure, because the failure's defining property is that it happens while nobody is watching, on a lane that returns minutes later, to a session whose only need is the word continue. A recovery that requires attention is not a recovery; it is a second chance to make the same mistake, and this workstation used both of its chances today.

The trigger already exists and needs no provider polling. A refusal that names a reset time is dated by it, and a refusal that names none ages out of a declared shelf life — so the moment a held lane becomes eligible is computable from records already on disk, without spending a token to discover it. What is missing is the actor that acts on that moment.

The recovery is one idempotent command, and something already running calls it. A sweep takes a project, finds every run blocked by a provider refusal whose hold is no longer in force, whose session is recoverable and whose worktree is present, and resumes each with an advice naming the reset as passed and instructing it to continue from where it stopped. Being idempotent and safe to repeat is what lets the existing per-project watch producer invoke it on a cadence, so the capability becomes automatic without a new daemon and without the display process holding the logic itself. An operator can run the same command by hand, which is also how it is tested.

Four bounds keep the sweep from becoming its own hazard, and each is a measure rather than a hope. It resumes a given run at most once per hold, so a lane that refuses again produces no retry storm — a second refusal re-arms the hold and the sweep waits for that hold's own expiry. It skips a run whose write scope has since been claimed by another run, because resuming into a scope somebody else now owns is a collision it would be creating rather than recovering from. It skips a run whose worktree is absent and says so, since a resume with no working directory cannot start — that is the state §3 exists to prevent and the sweep must not paper over it. And it refuses to resume onto a lane whose hold is still in force, so the sweep can never be the thing that spends the last of a recovering quota.

Done when a sweep over a project resumes every run held by a lapsed provider refusal whose session is recoverable and whose worktree is present, one resume per run, each carrying a continue advice; when running the sweep twice in succession performs the resumes once and reports the second pass as nothing to do; when a run whose hold is still in force, whose scope is claimed elsewhere, or whose worktree is gone is skipped with its reason named rather than silently; when the sweep records what it resumed and what it skipped so an operator reading afterwards can see the recovery happen; and when the watch producer invokes it on a cadence so no attention is required. Asserted through the sweep's own entry point over pointers and streams built the way dispatch writes them under a temporary configuration home, from a real refused stream rather than a synthesised one, with the real configuration home asserted untouched. The once-per-hold bound is asserted by refusing the resumed run a second time and requiring the sweep to wait rather than retry.

§ Decisions

How strict is the refusal on promoting a recoverable blocked run?

Deduced from the code rather than chosen: the promotion path already refuses a recoverable blocked run and names --waive-resume-path REASON as the single override (reckon/crew/promotion.py, wired through reckon/cli.py), and the refusal was observed working in the field on 2026-09-04 when a peer coordinator was stopped from promoting exactly this state and had to state in writing why the session was safe to discard. Warn-and-proceed is refused by the incident that motivated the plan: five resumable sessions were destroyed by a promotion that read session_id null as a verdict, and a warning is the same prose rule wearing a checkmark. Refuse-absolutely is refused because a genuinely unrecoverable session must still be promotable, and an override that must be stated in writing is one visible deliberate step rather than a default. The accepted cost is that a waiver exists at all, recorded on the promoted ledger row.

What ends the life of a worktree retained for a resume that never comes?

Locked 2026-09-04 by the lead. A retained tree becomes reclaimable after a declared age and the existing worktree audit is what surfaces it, rather than a second cleanup path. The safety argument is that the audit already refuses to remove a dirty or unintegrated tree, so an age bound can only reclaim trees whose work has already landed - which is the property that makes a bound acceptable at all, since reclaiming a tree holding uncommitted work destroys it outright with nothing to recover from. Unbounded retention was rejected on measured cost: one sibling project carried 124 reclaimable trees, a fleet produced a 180,186-file storage alert in a single day, and three of nine live pointers were once held by terminal runs the oldest of which was a day old, because the explicit disposal never came. Keying the lifetime to the session transcript leaving disk was rejected because it hands the bound to the harness's own pruning, which reckon neither controls nor sees change. The accepted cost is that a resume wanted after the bound finds no working directory.
