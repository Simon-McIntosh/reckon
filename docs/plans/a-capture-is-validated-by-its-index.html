§1 — It died confirming what it had already written down

A capture node produced its entire deliverable — eight screenshots at two widths and a complete capture-index.json — and then failed with API Error: 400 deepseek-v4-flash is not a multimodal model. It had opened one of its own PNGs to check that it was populated.

It did not need to. The index it had just written carries every fact the check wants, as text scraped from the rendered DOM at capture time:

{ "capture": "evidence-banner-1374", "surface": "evidence-banner",
  "image": "evidence-banner-1374.png", "width": 1374, "height": 900,
  "populated": true, "rowCount": 3,
  "bannerText": "2 new evidence since you opened this list",
  "bannerShowCount": 1, "pendingEvidence": 2 }

So eighty minutes of correct work was lost to a step that added nothing. The brief said each file must exist carrying its recorded width and a row count above zero — which is index-based and text-only. What it never said was that opening the image is not part of the check, and the absence of a prohibition read as permission.

This is a lane-capability mismatch only because of that step. Without it a capture node is lane-agnostic; with it, a capture node can never complete on a text-only lane, and re-dispatching to the same lane fails identically at the identical point.

§2 — The index is the contract

State it positively and negatively, because only the negative half was missing: a capture is validated by reading its index and stat-ing the files the index names. A gate never opens an image. What an image would show that the index does not is nothing: the scraped text, the row counts and the dimensions are recorded when the page is live, by the code that rendered it, which is a better witness than a later reader squinting at a PNG.

This also makes the rule falsifiable in the useful direction. An index claiming a capture that is absent from disk, or claiming a row count of zero, must fail — those are the failures a capture gate exists to catch, and both are text.

Done when the capture gate validates from the index alone, demonstrated by running it on a lane with no multimodal capability and recording that it passes; and demonstrated able to refuse in two distinct ways, once against an index naming a file that does not exist and once against an index whose row count is zero, each recorded. State as a digit how many captures the gate reads and how many image bytes it opens, the second being zero.

§4 — Out of scope

This does not change how captures are produced, what is captured, or the browser harness. It does not address figure allocation or merge policy, which is a separate contract with its own plan.

It makes no claim that images are never worth looking at. A coordinator verifying a landing may open one, and one was opened here. The rule constrains what a gate may depend on, because a gate must run anywhere and a person may look at anything.

§ Decisions

Where do the index's recorded values come from?

Locked because it is what the working implementation already does and the alternative reintroduces the defect. Values scraped from the live DOM at capture time are recorded by the code that rendered the page; values derived later from the image require reading the image, which is the step that makes a capture node lane-dependent. The index is a witness statement taken at the scene rather than a reconstruction.
