§1 — Purpose, window and shared inputs

The lead asked for a review of the background dispatch pattern — coordinators running /reckon-build and dispatching workers through reckon crew to the local lane (clive, deepseek-v4.1-flash) and the codex lanes — over the roughly two weeks it has run at scale. The questions are whether it produces better work at a higher rate, where the bottlenecks are, whether the system is too heavy, whether workers receive too much context, whether nodes should be smaller, whether coordinators do too much or too little, and whether the code it produces is deep, reused and small in interface or shallow and reimplemented. The lead also suspects that recent local-lane work in nova (a Grad–Shafranov equilibrium solver) has been flapping: rewriting the same code back and forth so that readiness has gone backwards.

A survey of the five live coordinator sessions is held by the coordinator and is not a node. The six sections below are the measured studies. Each writes one data directory and, where a figure earns its place, one figure topic directory; the synthesis in §8 reads all six.

Window. The study window is 2026-09-12T00:00:00Z to the capture instant 2026-09-26T10:00:00Z. Every census filters to that closed interval so that the growing ledgers and streams cannot move its counts after the fact. Where a study compares against an earlier period it names that period explicitly.

Shared inputs (all read-only; absolute paths):

  • Committed run ledgers for the five mounted projects: /home/ITER/mcintos/Code/<repo>/docs/state/<project>/crew.json and the one-file-per-run records under docs/state/<project>/runs/, for reckon, imas-ambix, nova, imas-efit and imas-codex. The run store /home/ITER/mcintos/.config/reckon/crew/run_store.db (SQLite) indexes the same runs; its backend column is empty on recent rows, so read the backend from the payload.
  • Run directories /home/ITER/mcintos/.config/reckon/crew/runs/<run-id>/: stream.jsonl, resume-N.jsonl, manifest.md, stderr.log. Two stream schemas exist (message-style and thread.started-style); a parser must be proved on one known-healthy run of each before any absence is reported.
  • Durable review records under /home/ITER/mcintos/.config/reckon/crew/reviews/.
  • Coordinator session transcripts under /home/ITER/mcintos/.claude/projects/-home-ITER-mcintos-Code-<repo>/*.jsonl; a run record's node_definition.coordinator.runtime_session_id names the transcript that dispatched it where it was recorded.
  • Git history of each repository's primary branch, read with git -C <repo>.
  • Prior instruments to reuse rather than rewrite: the burn census in /home/ITER/mcintos/.cache/burn-census/ and the review census script /home/ITER/mcintos/.config/reckon/crew/reports/reckon/s21-coord/review-node-utility/review_metrics.py.
  • Baselines: docs/research/crew-fleet-rox-review.html (August 12–16), docs/research/dispatch-cost-measurement.html (to September 4) and docs/research/review-node-utility.html (September 25).

Execution. Workers run on the fleet allocation, where heavy work runs in place. Keep each census to at most four concurrent processes, put temporary files in /tmp, and never write to any repository other than the worker's own worktree. Every data directory holds the census script, its output JSON, the log of one complete run, and a short findings.md stating each headline figure with its denominator. Re-running the script must reproduce the JSON byte for byte.

§2 — Velocity: the rate of implemented work

Deliverable. A velocity census of work landed through crew across all five projects in the window, compared with the August baseline.

Method. Join ledger records to primary-branch history. Report per project and per day: promoted implement-class nodes (implement, documentation, test, cleanup) and review or investigate nodes separately, split by lane (clive; codex family; claude family; native); lines landed on the primary branch from git log --first-parent --numstat, split into source, tests, plan/evidence/research HTML, figures, and docs/state; the count of commits by class (product: feat, fix, refactor, perf, test; record: promote, release, record, docs(plans), docs(evidence); merges). Report latency as dispatch-to-completion and dispatch-to-promotion medians and p75, and attempts per landed node (resumes, redispatches, and repair nodes whose lineage or node id points at an earlier node). Report the ratio of record lines to product lines, the fraction of product lines deleted again within seven days (so that durable velocity is distinguished from gross), and landed product lines per worker-hour and per coordinator-hour of active dispatch. State the August figures the baseline document reports beside each comparable figure rather than re-deriving them.

Done when docs/research/data/crew-pattern-review/velocity/velocity.json carries every figure above with its denominator, the census script beside it reproduces it, findings.md states the headline figures, and one figure in docs/figures/crew-pattern-review-velocity/ plots durable product lines landed per day by lane.

Velocity census — landed in the worker tree, 2026-09-26

The fixed-window census covers 2,303 promotion records across five primary branches: 1,259 implement-class and 1,044 review/investigate records (2,268 logical nodes after retry links). It measures 299,492 source/test additions in 6,515 first-parent commits. Of 123,960 additions with seven days of follow-up, 3,706 were deleted within seven days (2.99%); 120,254 remain durable. The 175,532 later additions are right censored. The timed, matched mature cohort delivered 86,478 durable lines / 739.9025 worker-hours = 116.88 durable lines per worker-hour.

Record/product additions are 49.10 including the figures directory, 11.72 excluding figure support data, and 5.35 excluding the entire figure directory. This is stored output volume, not writing effort. The published August baseline is quoted with its different cohorts and clocks; it did not measure seven-day durability.

Census evidence, coverage gaps, figure and validation; compact JSON; findings and August comparison. Artifact commit 95b173b8d99858cdaddc58a4d5ecbe08557cd98e. The replay gate reproduces the external full JSON and compact repository JSON byte for byte and conserves counts and lines across all 450 project/day/lane cells. This landing does not close the section; coordinator synthesis and integrated verification remain separate.

§3 — Worker anatomy: where turns and tokens go

Deliverable. A census of how crew workers spend their turns and context, by lane and role, for runs dispatched in the window.

Method. From run streams, per lane and role, report medians and p90 of: first-request input tokens; assistant turns; turns before the first file edit; the share of tool calls that read plan, evidence or research HTML, AGENTS.md, skill files or manifests; the share of file edits by class (source, tests, plan/evidence/research HTML, figures, manifest and reports); the share of wall time spent inside gate or test commands; and the number of self-verification reads of files the worker itself just wrote. Report the sample size per cell and stratify by node outcome (promoted passed, promoted not-run, blocked, failed, discarded). Prove each stream parser on one named healthy run before relying on it.

Done when docs/research/data/crew-pattern-review/worker-anatomy/anatomy.json carries every figure above with its sample size, the census script beside it reproduces it, and findings.md states the headline figures including the share of worker effort spent on record-keeping (plan, evidence, figures, manifest) against product code.

§4 — Coordinator overhead: the cost of each landed node

Deliverable. A census of what coordinators spend per landed node, from their session transcripts, for the window.

Method. Identify coordinator sessions from run records (node_definition.coordinator) and their transcripts. Per session report: landed nodes; coordinator assistant turns, input tokens and output tokens per landed node; the tool-call mix by category (dispatch, crew reads and MCP views, git and merges, plan edits, reading worker diffs and gate logs, follower notifications); dispatch refusals by error code and promotion refusals by reason, with the coordinator turns between each refusal and the next successful attempt; and hand-committed worker diffs. From each primary branch, count merges in the window that touched docs/plans or docs/evidence and how many of them would have conflicted, re-derived with git merge-tree on the recorded parents.

Done when docs/research/data/crew-pattern-review/coordinator-overhead/overhead.json carries every figure above per session with totals, the census script beside it reproduces it, and findings.md ranks the five largest coordinator costs per landed node with their figures.

§5 — Code depth, interface width and reuse in reckon and nova

Deliverable. A structural assessment of the code the fleet has produced in reckon and nova, judged against the lead's stated preference: deep modules behind small interfaces, and no reimplementation of what already exists.

Method. Take four weekly snapshots of each primary branch (the commit nearest 12:00Z on 2026-09-05, 09-12, 09-19 and 09-26), extracted with git archive into /tmp. For reckon/ (with reckon/crew/ separately) and nova/, report per snapshot: source and test lines, module count, public function and class count, the function-length distribution, and for reckon the number of CLI commands, CLI options, MCP views and dispatch refusal codes. Run a clone census — duplicate blocks of six or more lines found by hashing normalised token windows — and report the clone share of source lines. Build a reimplementation census: every helper concept implemented in three or more places (for example ISO timestamp parsing, process liveness, atomic JSON writes, git subprocess wrappers, stream parsing, plan HTML reads), with file:line for every copy. Report pass-through functions (a body that only forwards its arguments) and modules whose public surface is large relative to their lines.

Done when docs/research/data/crew-pattern-review/code-depth/code-depth.json carries every figure above for all eight snapshots, the census script beside it reproduces it, and findings.md ranks the ten highest-value consolidation candidates, each naming its copies and one proposed single home, with the week-over-week trend in clone share and interface width stated for each repository.

§6 — Nova: is recent work flapping?

Deliverable. A verdict, with evidence, on whether nova's recent history shows flapping — the same code rewritten back and forth — and which lane and plan produced it.

Method. Weekly from 2026-08-15 to 2026-09-26 on nova's primary branch, report commits, lines added and removed under nova/ and tests/, the share of added lines deleted again within seven days, revert commits, and files and functions changed in three or more distinct weeks. Detect oscillation directly: the same constant, default, signature or test expectation set to a value and later set back. Attribute each commit to a crew run and lane through nova's ledger (/home/ITER/mcintos/Code/nova/docs/state/nova/crew.json) or its commit message, and state unattributed commits as such rather than guessing. Read the worst episodes as code, not as counts.

Done when docs/research/data/crew-pattern-review/nova-flapping/flapping.json carries the weekly figures and the per-commit attribution, the census script beside it reproduces it, findings.md presents the five worst flapping episodes with commit shas, what changed back and forth, and the lane and plan behind each swing, and it states a verdict on whether flapping rose during the local-lane period with the figures that decide it.

Nova history census delivered for review

The census at c29fb51e7820d712a4259eceff8e531585939fca covers 3,879 first-parent landings, including 633 source/test changes. Mature seven-day source churn is 9.27% before September 12 and 9.39% afterward; splitting at the first local code landing on September 5 instead gives 10.86% and 6.58%. Localized reversals exist, but the evidence does not establish a broad increase caused by the local lane.

§7 — Nova: readiness at weekly snapshots

Deliverable. A readiness trajectory for nova measured by running its own fast test lane and lint at weekly commits.

Method. For the primary-branch commit nearest 12:00Z on each Friday from 2026-08-22 to 2026-09-26, plus the current head, extract the tree with git archive into /tmp — never a worktree of nova and never a write to nova. Run nova's default fast lane (pytest with its configured -m 'not slow') against the main checkout's environment (/home/ITER/mcintos/Code/nova/.venv/bin/python, with PYTHONPATH set to the extracted tree, no sync), with a per-test timeout of 120 s and the same selection at every snapshot. Record collected, passed, failed, errored, skipped and xfailed counts; errors caused by the present environment rather than the snapshot's code are classified as such. Record ruff findings under nova's own configuration and counts of TODO/FIXME, xfail and skip markers.

Done when docs/research/data/crew-pattern-review/nova-readiness/readiness.json carries every count for every snapshot, each snapshot's complete pytest log is saved beside it, and findings.md states the readiness trend with its figures.
