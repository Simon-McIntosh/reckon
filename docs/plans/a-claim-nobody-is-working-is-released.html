§1 — Why: four kinds of run outlive their worker

A live pointer is a claim: it holds the run's paths, keeps the sections that wait on it waiting, and tells every reader that a worker exists. delivered-work-lands-without-a-coordinator made a promoted run with no live worker give up its pointer (its §21, §26, §27 and §29, all landed by 19 November). Three kinds of run fall outside the cases those sections cover, and a fourth reads as alive when it never started. Each was seen on the fleet on 18 and 19 November.

CaseWhat was seenWhy the landed rule does not reach itSection
The worker was recorded on a node that no longer hosts the fleetPromoted runs kept their pointers after the fleet moved node; a discard of each was undone on the next passThe worker's liveness reads as unknown, and unknown is kept§2
A journaled measurement runA run marked as measurement-only kept its pointer after its measurement was recordedIt is never promoted, so the promoted-run rule never tests it§3
A member of a landing groupOne member's pointer survived its group's landing and held the sections waiting on itThe group lands as one head; the member's own record shows no promotion§4
A resume whose step never startedA resume launched a 32-CPU overlapping scheduler step that never ran; the run read as alive, and stopping it left the scheduler client processes behindLiveness is read from the launcher, not from a turn having begun§5

The rule each section keeps from the landed work: a run showing a turn in progress is never released on an unknown reading. Only a run with no turn in progress may be released without proof that its worker is dead.

§2 — A run whose worker was on a previous fleet node gives up its claim

Why. The fleet moves node every few days. Every promoted run launched before the move then reads as liveness unknown for ever, and its pointer is never retired.

Deliverable. A promoted run whose recorded launcher host is not the node the fleet record names, and which shows no turn in progress, gives up its pointer on the next pass. A discard of such a run is not undone.

Done when. A test builds a temporary crew home holding three promoted runs recorded on a host other than the current fleet node: one with no turn in progress, one whose stream grew inside the turn window, and one recorded on the current node with a dead process. After one pass the first and third have no pointer and the second keeps its pointer. A discarded run of the first kind has no pointer after two further passes. Negative control: at the base revision the first run keeps its pointer. The existing release tests add no failure against the base. Tests run on all_debug with at most -n 4. Write paths: reckon/crew/pending_landing.py, reckon/crew/process_liveness.py, reckon/crew/promotion_release.py and tests/test_a_run_from_a_previous_fleet_node_is_released.py.

§3 — A measurement run gives up its claim when its measurement is recorded

Why. A measurement-only run is journaled, not promoted. Nothing retires its pointer, so its paths stay claimed after its record is written.

Deliverable. A measurement-only run whose record is stored and which has no live worker has no pointer after the next pass. One whose record is not yet stored keeps it.

Done when. A test builds a temporary crew home with two measurement-only runs, one with its record stored and no live worker, one without a record. After one pass the first has no pointer and its record is unchanged byte for byte; the second keeps its pointer. Negative control: at the base revision the first keeps its pointer. Tests run on all_debug with at most -n 4. Write paths: reckon/crew/landing_measure.py, reckon/crew/promotion_release.py and tests/test_a_recorded_measurement_run_is_released.py.

§4 — A landing-group member is released when its group lands

Why. Sections that wait on a group member wait on its pointer. When the group lands as one head and one member's pointer survives, those sections never start.

Deliverable. When a landing group's head is on the primary branch, every member's pointer is retired and every section waiting on a member is released. A group whose head is not on the primary branch keeps every member.

Done when. A test builds a temporary repository and crew home with a three-member group and one request waiting on each member. With the group head merged, one pass leaves no member pointer and all three requests released. With the head unmerged, every pointer and every wait is kept. Negative control: at the base revision the merged case leaves at least one member pointer. Tests run on all_debug with at most -n 4. Write paths: reckon/crew/pending_landing.py, reckon/crew/promotion_release.py and tests/test_a_landed_group_releases_every_member.py.

§5 — A resume that never started reads as not started, and a stop leaves no process

Why. A resume was reported on 19 November whose scheduler step asked for 32 CPUs inside the fleet job and never started. The run read as alive for as long as the client process waited, so nothing resumed it again, and stopping it left that client and its children running.

Deliverable. A resumed run reads as working only once its worker has begun a turn. A resume whose worker has not begun a turn within a stated bound reads as a failed launch, naming what it was waiting for. Stopping any run ends every process the launch started, and reports each pid it signalled.

Done when. A test launches a resume through a stand-in launcher that blocks before starting the worker: within the bound the run's classification is the failed-launch one and carries the launcher's own waiting reason, and it is offered for resume again. A second stand-in starts a worker that begins a turn: the run reads as working. Stopping the blocked run leaves no process from its launch tree alive, checked by pid, and prints each pid signalled. Negative control: at the base revision the blocked run reads as working, and the stop leaves the stand-in launcher alive. Tests run on all_debug with at most -n 4 and start no scheduler step. Write paths: reckon/crew/resumption.py, reckon/crew/process_liveness.py and tests/test_a_resume_that_never_started_reads_as_not_started.py.

§6 — The fleet holds no claim without a worker

Deliverable. A census of the live fleet after §2 to §5 have landed, beside the same census taken before.

Done when. The evidence record holds two censuses of every live pointer on the workstation, each row giving the run, its kind, its recorded host, whether a turn is in progress and the pointer's age. The census before landing lists at least one run of each kind in §1, or says which kind had none that day. The census taken at least six hours after the last landing lists no promoted, measurement-only or landed-group run older than one hour with no turn in progress, and no run reading as working whose worker has begun no turn. A census that read fewer pointers than the live directory holds fails as unread. Write paths: docs/evidence/archive/a-claim-nobody-is-working-is-released-landed.html.
