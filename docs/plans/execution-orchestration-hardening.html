A node cannot be dispatched into a repository other than the one holding its plan

reckon crew dispatch --repo <other> resolves the node's plan inside the dispatched repository and refuses with plan-unavailable when it is not there. That makes every cross-repository node undispatchable, even though the semantics are already coherent everywhere else: the plan is the semantic authority, and read_plan/edit_plan already accept checkout_path to separate the plan's checkout from the working one.

Measured while sweeping twelve mounted projects for a reckon-owned plan: four repositories hold work that plan authorises and none of it could be delegated, because the plan lives in reckon while the edits land in imas-efit, imas-ambix, nova and hanney. The obvious workaround is worse than the gap: pointing write paths at another checkout puts a worker outside the worktree that bounds its blast radius.

The repair is to let the plan resolve through its registered mount while the worktree still comes from --repo, so a cross-repository node keeps both its semantic authority and its isolation.

Re-run the gate at merge time, not only at the worker's base revision

A worker's gate runs against the base revision its worktree was branched from, so a contract landed after that base cannot bind it — the run is legitimately green and the merge turns the primary branch red. Measured 2026-08-25: 4d7fdf8 (09:55) introduced a contract asserting every registered crew verb is named in the ship skill or explicitly exempt; 4656c7a (09:58) registered reckon crew shadow from a worktree branched before it, passing its own full suite at 2357/2357; the merge c82cf57 (10:09) turned main red and a peer session caught it three minutes later. The repair was one sentence plus one registry row (a3c9f2b), but the class recurs whenever a contract and the code it governs land in the same window from different bases.

The durable fix is at integration, not in the worker: re-run the affected gate against the merge result before the coordinator pushes, so what is verified is the tree that ships rather than the tree the worker started from. Note the coordinator already performs a scoped audit at this moment (git show --stat against declared scope), so the hook exists — what is missing is executing the check at the integrated revision. Reported independently by two peer sessions as the merge-time analogue of a monitor that reports success because it never looked.

Dispatch payload must tell a session whether it holds the watcher seat

Reported by two independent orchestration sessions (nova-18 2026-08-25; a second session 2026-08-21, nine dispatched nodes). reckon crew dispatch returns watch.watcher_live, computed by project_watch_visibility (reckon/crew/runs.py) from three project-global facts — the advisory lock being held, the registering process alive, and observer_alive — with no comparison against the caller's identity. So a session that does not hold the seat receives watcher_live: true on every dispatch, satisfies the watcher requirement, and is never wake-capable, because wake delivery is session-local while the requirement is project-global.

The failure is silent by construction — no error, no refusal, no artifact, only work that quietly never notifies — and it sent both sessions to hand-rolled manifest-polling loops. reckon crew follow now supplies the missing capability, but a session cannot learn it needs follow rather than watch while the payload reports everything is fine; one of the two reported reading the skill's liveness guidance and still shipping polling loops, which is the argument against a documentation-only fix.

Proposed: add watch.seat_is_yours (boolean) beside watcher_live, turning an invisible condition into a branchable one. Cheap by inspection — the watch record already stores parent_pid and parent_start_time and project_watch_visibility already reads both to derive observer_alive; only the derived boolean escapes today. No new capture, no new record field, no lock-file format change: a comparison against the caller's own process using values already in scope.
