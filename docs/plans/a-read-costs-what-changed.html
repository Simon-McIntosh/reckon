§1 — Why a read now takes a minute, and a queued dispatch forty

reckon-reads-answer-in-seconds shipped on 25 September with warm reads under five seconds. On 2 November the same reads measured as follows on the fleet node, which is clu-2068, at 889c335354:

OperationMeasuredTarget
read_plan(view="summary"), one plan, fresh process83 s; the MCP call overran its 30 s deadline at 16.8 s CPUunder 5 s
edit_plan on a large plan36–52 s CPU; every write overran its 60 s deadline and still landedunder 5 s
Admission readiness read for one project, nothing changed since the last read26–55 s per callunder 5 s for the whole pass
One admission pass with 27 waiting requests1,250–2,980 s logged as launch_secondsunder 5 s

Three profiles were taken: a py-spy sample of the live admit service, and cProfile runs of _readiness_rows and of read_plan. They name six causes. Each was then confirmed in the code.

  • The memo dies with its process. file_memo.memoized keeps parses in process memory, and the parse is _plan_html.read_state through BeautifulSoup, about 0.15 s per plan. A fresh process re-parses all of them: 198 calls, 33 s, in one read_plan. Fresh processes are now the common case. An MCP current-code child is fresh after every landing. The admit service re-executes on every new code stamp, which happened about ten times on 2 November. The CLI and dispatch run fresh every time.
  • Validating the cache walks directories that hold nothing it covers. metadata_index._reuse_covered stats every recorded directory to prove the file set is unchanged. Of the 2,727 directories under docs/, 2,369 sit under docs/state/reckon, the stored review JSON. Together they hold two HTML files.
  • The validation runs again on every lookup within one request. One read_plan called _reuse_covered 21 times, giving 57,267 directory identities and 86,098 stat calls, 25 s on GPFS. A request scope exists, metadata_index._DISCOVERY_FILES, but the MCP read, the admission pass and dispatch do not enter it.
  • Each ref rebuilds the identity index. resources._canonical_identity_is_unique calls _directory_identity_index once for every ref it resolves. That is 18 calls and 30 s in one read_plan, coming from _section_dependency_rows, and once per section wait in roadmap._plan_section_deps.
  • A one-plan read composes the whole project. _store._add_north_star_diagnostic calls project_state.compose_project_state to learn the project's declared north stars, which costs 38 s of the 83.
  • The admission pass shares nothing across requests. queue_admission._readiness_rows keys its per-pass cache on the plan and refs asked about. The whole-project answer it caches depends on neither, so each distinct ref recomputes the project. It also calls read_state on the text of every plan in the inventory. That bypasses the file memo, so it is 216 BeautifulSoup parses and 34 s per call.

The shipped plan's measure was a warm read in one long-lived process. That measure still holds and still misses the cases that now dominate: a fresh process, a tree that has grown 2,369 directories of review records, and callers that never went through the memo. This plan's measure covers all three. Each section's done-when therefore counts operations on a synthetic store, deterministically, and §7 times the real store, cold and warm.

§2 — Every read enters the scopes that already exist, at one boundary

Why. The design review of 2 November found that the caches this plan's §1 measured as missing exist already. The slow paths simply never enter them:

  • metadata_index.discovery_file_scope shares one covered-tree observation within a read;
  • resources.resource_scan_scope (reckon/resources.py, near line 507) holds one identity index for every resolve inside it, and tests/test_a_slug_uniqueness_is_one_lookup.py asserts exactly that.

read_plan enters neither, which is why one call made 18 identity-index validations and 21 covered-tree validations. Separately, metadata_index.covered_name (near line 362) covers every HTML file anywhere, so the covered walk descends into the 2,369 review-record directories under docs/state/reckon/, which hold no documents.

Deliverable.

  • One boundary, entered on the right thread. Every MCP tool is registered through mcp_deadlines._deadline_tool (reckon/mcp_deadlines.py, near line 555; registration near reckon/mcp.py lines 3688–3720). That wrapper runs the tool body on a worker thread through loop.run_in_executor (near lines 365–367 and 438–449), which does not carry context variables, and both scopes are context variables. So the scopes are entered inside the callable the executor runs, around the tool body on its own thread. They are not entered in the async wrapper. The per-tool entry inside roadmap (reckon/mcp.py, near line 2224) is removed. Only read-only tools get the boundary scope: read_plan, roadmap, audit and the crew views, declared by a flag at registration. A scope opened by the wrapper cannot be closed by the body, and a nested entry joins the open region rather than opening a fresh one (metadata_index.py, near lines 105–107; resources.py, near line 518). So edit_plan is registered without the boundary scope and enters both scopes itself, twice: once around its reads before the write, and once around its reads after it (_review_owed_fields and _plan_readiness_fields, reckon/mcp_edit_plan.py, near lines 2247–2255). Its post-write reads therefore see the written file.
  • The covered walk skips the state records, not the figures. resources.INFRA_DIRS (near line 39) names the directories that hold no documents. It also names figures, whose images the covered set does include (metadata_index._FIGURE_DIR, near line 80). The covered walk and validation therefore skip the INFRA_DIRS directories other than figures. They read the constant, so a directory added to it is skipped too. covered_name's figure rule is unchanged. The committed review store under docs/state/<project>/reviews/ is read by its own readers, list_plan_reviews and review_coverage, which glob it directly, and this section does not change them. The pages the server serves from docs/state/<project>/ by path, such as the timeline and review pages, are still served.

Done when a new tests/test_a_request_validates_the_tree_once.py builds a synthetic docs tree with 40 plans, 5 figures under docs/figures/, and 2,000 directories of JSON under docs/state/<project>/reviews/. It calls each tool through its registered _deadline_tool wrapper, so the body runs on the executor thread as it does live. With os.stat and metadata_index._reuse_covered counted through patches, it shows seven things:

  • One call each of these stats fewer than 300 paths and validates the covered tree at most once, or for edit_plan at most twice (once before its write and once after). A tool that reads no document, such as crew(view=\"live\"), validates it zero times. The tools are: read_plan(view="summary"), an edit_plan set, roadmap(view="summary"), audit, and crew(view="live"). The test records each count, and the base revision's count for the same call, which exceeds 20,000 stats for read_plan.
  • Resolving 20 section refs in one read_plan builds the identity index once.
  • The 5 figures are still in the metadata index's rows and in the discovery listing.
  • An HTML file placed in a new subdirectory of docs/state/<project>/ does not appear in the discovery listing (read_plan with no slug), roadmap's plan set or audit's document set.
  • A stored review record added under the reviews tree still changes what edit_plan's review_owed reports, and the server still serves docs/state/<project>/timeline.html.
  • A plan added to docs/plans/ is seen by the next read.
  • Within one edit_plan call, a read after the write returns the written value.

Three negative controls each make one case fail:

  • entering the scopes in the async wrapper rather than on the executor thread fails the first case;
  • restoring the covered walk into docs/state/ fails the first case;
  • skipping every INFRA_DIRS directory, figures included, fails the third.

The test files importing reckon.metadata_index, reckon.resources, reckon.mcp_deadlines, reckon.serve and reckon.mcp add no failure against the base revision. ruff check and ruff format --check add no findings on the staged paths. Write paths: reckon/mcp_deadlines.py, reckon/mcp.py, reckon/mcp_edit_plan.py (where _edit_plan_tool enters the scopes around _uncovered_before_write and around its post-write reads), reckon/metadata_index.py and the new test.

§3 — A persisted answer carries the version of the code that made it

Why. The persisted parse already exists. metadata_index.discovery_state (reckon/metadata_index.py, near line 1521) returns each unchanged file's stored parse, record_discovery (near line 1616) writes it back, and _plan_html.reuse_parsed_state (reckon/_plan_html.py, near line 1579) seeds the in-process memo from it. serve.py (near line 1632) and _store.py (near line 2419) already use it. Two things are missing:

  • The stored entry carries only signature and digest (near lines 1566–1575), so a change to the parser does not invalidate it.
  • The read paths behind read_plan, edit_plan and admission do not seed from it, so a fresh process re-parses every plan. One read_plan made 198 read_state calls, about 33 s.

Deliverable.

  • One persisted-memo helper. metadata_index gains one function, beside _persisted_cache_path (near line 1805), the existing owner of persisted caches. It stores and returns a value for an identity together with the source digests of the modules that produced it, and treats an entry whose digests differ as absent.
  • The parse carries its parser's version. discovery_state and record_discovery use that helper with _plan_html's source digest, so a parser change invalidates every stored parse.
  • The read paths seed from it. The state read behind read_plan and edit_plan (_store._read_state) seeds the in-process memo from discovery_state through reuse_parsed_state before reading, as serve.py does. §6 does the same for admission.

Done when a new tests/test_a_persisted_answer_carries_its_code_version.py shows four things, with _plan_html.read_state counted through a patch:

  • A second simulated process, made by clearing file_memo, runs read_plan(view="summary") over a 40-plan store with zero parses of unchanged plans.
  • One edited plan is parsed once.
  • A changed _plan_html source digest, patched, makes every stored parse absent, so the next read parses each plan once.
  • A corrupt stored entry yields the parsed value, not an error.

Two negative controls each make one case fail. Leaving the code digest out of the helper's key fails the third case. Removing the seed from _store._read_state fails the first. The test files importing reckon.metadata_index, reckon._plan_html, reckon._store and reckon.serve add no failure against the base revision. Ruff adds no findings on the staged paths. Write paths: reckon/metadata_index.py, reckon/_store.py and the new test.

§4 — A request resolves its refs against one identity index

Why. resources._directory_identity_index keeps its built index in _INDEX_MEMO. To know whether that index is still current, it recomputes the directory listing through _identity_listing, which calls metadata_index._reuse_covered, on every call (reckon/resources.py, lines 789–856). The index itself is rebuilt only when the listing moves, so the cost is the validation, not the build. One read_plan made 18 such calls and spent 30 s in them.

Deliverable. Within the §2 request scope, _identity_listing is computed once per docs directory and every later call in the scope reuses it, so _directory_identity_index validates once per call however many refs it resolves. Outside a scope the behaviour is unchanged. A duplicate canonical identity is refused exactly as before.

Done when a new tests/test_a_request_resolves_refs_against_one_index.py resolves 20 section refs in one read_plan of a plan on a synthetic store. It counts calls to metadata_index._reuse_covered made from _identity_listing, through a patch. The count is 1 at the head; the test runs the same read on the base revision's code path and records 20 there. The test also shows that a duplicate canonical identity is still refused. The negative control computes the listing per call inside the scope, and the count case fails. The test files importing reckon.resources and reckon.roadmap add no failure against the base revision. Ruff adds no findings on the staged paths. Write paths: reckon/resources.py and the new test.

§6 — Every hot path reads plan state through the memo

Deliverable. Four changes, all in the admission, landing, dispatch and review paths.

  • One admission pass, one landing pass and one crew dispatch each enter discovery_file_scope and resource_scan_scope once, as §2's boundary does for an MCP call. Each closes them before any write.
  • queue_admission._readiness_rows seeds from discovery_state as §3 does, and takes each plan's section_declarations from the memoized read_state_and_text_file, not from read_state on the file's text.
  • Inside an admission pass, its whole-project read is cached on the project, its docs directory and the tree fingerprint only, so a pass computes each project once however many plans and refs its requests name. The bounded read outside a pass keeps its present key.
  • plan_review._snapshot_evidence stores its whole result — section digests, declarations and prose texts — through §3's persisted-memo helper. It is keyed by the snapshot's content digest with plan_review's and _plan_html's source digests. Today it parses each snapshot four times (reckon/crew/plan_review.py, near lines 315–331, 429–478 and 896–905):
    • through _section_digests, via read_state;
    • through _snapshot_declarations, via read_state again;
    • twice through _prose_texts, via _plan_html._structural_spans.
    With the helper, an unchanged snapshot is never parsed again by either parser, in any process.
