§1 — The mechanism: bind the check to the moment that always happens

Two coordinator sessions on one morning launched harness-native background-agent fleets in crew-managed repositories against an explicit codex-worker directive; the evidence and root causes are recorded in the native-agent-dispatch-bypass research record. The decisive causes were rule locality (the ban lives in a skill those sessions never load) and a binding rule with no bound check. The remedy follows the repository's own doctrine: put a runnable check at the moment that always happens. For this failure that moment is the spawn call itself — a host-harness pre-tool-use hook that sees every attempt to start a new background agent before it runs.

The guard changes nothing outside crew-managed repositories, never touches a session's own inline tools (reading files, running commands, and messaging or stopping already-running agents stay free), and refuses exactly the act that starts an unledgered worker: spawning a new background agent where the crew system owns worker execution.

§ Decisions

Does the guard hard-refuse new native background agents, or warn and allow?

Both sessions in the motivating incident had counter-signals available (a memory rule in one, general crew discipline in both) and rationalized past them; the reviewing session explicitly judged that a hard block would have caught its batch cleanly with a one-to-one re-route into crew dispatches and zero lost work. A warn is the same prose rule wearing a checkmark.
