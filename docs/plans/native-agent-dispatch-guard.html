§1 — The mechanism: bind the check to the moment that always happens

Two coordinator sessions on one morning launched harness-native background-agent fleets in crew-managed repositories against an explicit codex-worker directive; the evidence and root causes are recorded in the native-agent-dispatch-bypass research record. The decisive causes were rule locality (the ban lives in a skill those sessions never load) and a binding rule with no bound check. The remedy follows the repository's own doctrine: put a runnable check at the moment that always happens. For this failure that moment is the spawn call itself — a host-harness pre-tool-use hook that sees every attempt to start a new background agent before it runs.

The guard changes nothing outside crew-managed repositories, never touches a session's own inline tools (reading files, running commands, and messaging or stopping already-running agents stay free), and refuses exactly the act that starts an unledgered worker: spawning a new background agent where the crew system owns worker execution.

§2 — The hook

A self-contained hook script, shipped in this repository and wired as a pre-tool-use hook on the harness's agent-spawning tool. Behavior, in order:

  • Scope test: resolve the working repository; if it carries no crew management state (no docs/state/<project>/flight.yaml and no crew ledger), exit permissive — non-crew repos are untouched.
  • Waiver — crew-prepared in-harness run: if a live run pointer for this project has an in-harness launch awaiting attachment, allow the spawn and remind the caller to bind it with reckon crew attach. This keeps the legitimate native backend path alive.
  • Waiver — explicit override: an environment toggle set for the session allows the spawn; the refusal message names the toggle so the escape is always one visible, deliberate step, never a default.
  • Otherwise refuse, with a message that does the re-route for the caller: the matching reckon crew dispatch invocation shape for investigate/review work, and the watcher arming line. A refusal that teaches the correct call costs one retry; a bare "no" costs a diagnosis.

Done when: hook unit tests cover the four branches — non-crew repo passthrough, in-harness-awaiting-attach waiver, environment override, and the refusal message naming both the dispatch shape and the override; and a synthetic crew-managed temp repo proves the scope test reads only repository-local state.

§3 — Distribution: reckon-sync owns the wiring

reckon sync installs or refreshes the hook wiring into a crew-managed repository's harness settings the same way it owns CSS, mounts, and skill links — idempotently, with a clean removal path, and never touching a repository that is not crew-managed. The hook script itself stays in reckon so a fix lands once and reaches every synced repository on its next sync.

Done when: a sync run on a synthetic temp repository installs the wiring exactly once (a second run is a no-op, asserted byte-for-byte), and the removal path leaves settings as found.

§4 — Fix rule locality: the routing rule lands where the temptation occurs

One binding line in each skill a session can be holding when the spawn temptation arises — status, roadmap, sprint, and create — plus the repository agent guidance: in a crew-managed repository, investigation and review fan-out is reckon crew dispatch work (investigate/review roles); harness-native background agents bypass the run ledger, manifests, and calibration and are refused by the guard. The ship skill already carries the full rule and sits at a measured size ceiling; it gets a pointer at most, not a restatement.

Done when: each named skill file carries the line, phrased against the mechanism rather than any incident, and a contract test asserts its presence so the next skill rewrite cannot silently drop it.

§ Decisions

Does the guard hard-refuse new native background agents, or warn and allow?

Both sessions in the motivating incident had counter-signals available (a memory rule in one, general crew discipline in both) and rationalized past them; the reviewing session explicitly judged that a hard block would have caught its batch cleanly with a one-to-one re-route into crew dispatches and zero lost work. A warn is the same prose rule wearing a checkmark.

Locked 2026-09-03 by the lead. The spawn is refused in crew-managed repositories, with the two waivers §2 specifies: a crew-prepared in-harness run awaiting attachment, and an explicit environment override the refusal message names, so the escape is one visible deliberate step rather than a default. Warn-and-allow was rejected because it is the same prose rule wearing a checkmark: both sessions in the motivating incident had counter-signals available and rationalised past them, and this repository has already paid twice for warnings that were scrolled past. The reviewing session judged that a hard block would have caught its whole batch cleanly, with a one-to-one re-route into crew dispatches and zero lost work. The accepted cost is that a legitimate spawn pattern nobody anticipated is blocked until someone sets the override, which the refusal message states.

§ Followups

Ship the guard once the enforcement mode is locked

The enforcement-mode decision is user-owned: it changes the default behavior of every session in every crew-managed repository. §2–§4 are executable the moment it locks; the recommended choice is hard-refuse with waivers.
