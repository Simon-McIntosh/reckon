§1 — Why: four coordinators rebuilt power_convertor's real shape by hand

On 2026-10-21 the lead asked whether reckon can tell an agent where a project stands: its direction, its critical path, the work queued behind it and which task matters most. The test project was power_convertor, which has 17 plans, two open sprints and four coordinator sessions, and whose active sprint S3 promises a presentation in the week of 19 October. Its roadmap answered as follows.

8 of the 9 open plans are ready, 0 are blocked, and every plan's unlocks is empty.The plans declare 30 open sections and 16 cross-plan section edges in plan-section-depends-on. 11 of the 30 open sections wait on another open section.
The critical path is one plan, coil-supply-report-rebuild, at 35 h, and the five open paths are five single plans.From the stored edges, the effort-weighted section chain is iter-switched-terminal-transients#s6 (8 h) → coil-supply-report-rebuild#s4 (10 h) → #s8 (5 h). All four coordinators were asked how they chose their current node. Each said it was their own judgement, informed by peer messages, and that no tool ranked anything. They reconstructed blocking chains, file holds (who is writing switched_circuit.py now and who is next), the cross-plan sections that consume their output, and duplicated scope (shared-coil-supply-model#s6 and iter-switched-terminal-transients#s6 describe the same move of the integrated run). They did it by reading plan HTML, crew pointer files and each other's messages. One coordinator put it as "much of my time is relay messaging between sessions, because holds and cross-plan waits aren't in any shared view".

The information is mostly stored already. Sections carry data-effort-hours, declarations and cross-plan dependencies, and live runs carry their plan and section. The analyser builds its graph between plans. It adds plan-level depends_on refs and gate edges to that graph, but plan-section-depends-on entries only decide each plan's own section readiness and never reach it. Every cross-plan edge in power_convertor is of that third kind, so none becomes an unlocks, and a plan with any ready section reads ready. The measurement, the prototype that derived the section chain, and the code references are in docs/evidence/archive/a-project-reads-as-one-picture-landed.html. This plan makes the section the unit of the graph and derives the plan view from it. The answer contract the MCP serves it through is the-mcp-answers-the-question-asked.

§2 — The critical path runs through sections

One function in Python builds the section graph of a project. Its nodes are the open sections of every live plan, each weighted by its effort_hours scaled by the plan's progress where a section carries no finer figure. Its edges come from three sources. Plan-level depends_on refs and gate edges are already in the base graph between plans; they are carried down to the sections they name, reusing the code that reads them today. plan-section-depends-on entries, which the base reads only for section readiness, become edges for the first time, and that is the new work. Qualified refs (nova:plan#s5) resolve against the named mount and stay blocking until that project closes the section.

critical_path, open_paths, unlocks and the ready set are computed over that graph. A plan row keeps its fields, now derived from its sections: it is ready when a section is ready, its unlocks is the set of plans its open sections transitively unblock, and its share of the critical path is named. The section rows are served beside the plan rows rather than replacing them.

Done when: a synthetic three-plan fixture whose only cross-plan wiring is plan-section-depends-on, A#s2 → B#s3 → C#s1, reports a critical path naming those three sections in that order with their summed effort, and reports C in B's unlocks. The negative control is the same fixture against the base commit, where the path is a single plan and unlocks is empty, and the test must fail there. On power_convertor the critical path spans at least two plans and names iter-switched-terminal-transients#s6, recorded in the gate log with the head it ran at.

§3 — The ranking reads signals that differ between rows

Ready sections are ranked lexicographically. A section on the critical path to the active sprint's open work comes first. Next is the number of sections it transitively unblocks, then the sprint's remaining time where the sprint states an end or a dated goal, then its stuck signal (two or more attempts, or a run on it blocked for more than a day, which raises it so that it is seen rather than skipped). ROI and effort only break the ties those leave. Every ranked row carries a one-line reason naming the signal that placed it (not why, which names the MCP's why(ref) read), so a reader can disagree with a specific reason rather than with an opaque order.

When at least 80 % of a project's open plans share one ROI value, the roadmap emits an informational flat-priority-signal finding that names the share. That tells the lead the ROI field has stopped carrying information and is not being used to rank.

Done when: on a fixture where every plan is ROI high and effort M, the ranked order puts the section with the largest downstream reach first, and every row's reason names a signal other than ROI. On the base commit the same fixture returns plans in sprint and slug order, and the test fails there. power_convertor reports flat-priority-signal with its measured share (16 of 17 plans).

§4 — Work in flight sits on its section

Every live, queued and interrupted run resolves to plan#section. A section row carries its runs with one classification each, taken from the same function crew live calls, so the roadmap and the crew surface can no longer disagree about one run. It also carries the write paths those runs hold, as the dispatch scope claims already record them, and the queued dispatches waiting on those paths.

A section's blocking state is named by kind rather than collapsed into one boolean. The kinds are: dependency (an open upstream section), gate, run-blocked (a run's manifest reports blocked, with its blocker text), held-path (a write path claimed by another section's run), external-data (a gate whose measure names data not yet in the repository, such as the dummy-load recorder files) and decision.

Done when: a fixture live pointer with a plan and section appears on that section's roadmap row with the classification crew live gives it, and a fixture whose manifest reports blocked makes its section run-blocked and carries the blocker text. A parity test asserts that the roadmap's run state equals crew live's classification for every run in a fixture of mixed states; the interrupted-against-running pair measured on power_convertor is reproduced as its negative control and must fail on the base commit. Two fixture runs claiming one path report the holder and the queued run, in that order.

§5 — A wait nobody declared is a finding

Two wiring findings make the edges coordinators carry in messages visible. undeclared-wait fires when a section's blocked run, gate measure or open followup names another section ref (slug#sN or project:slug#sN) that the section's dependencies do not include. It names both refs and the text that mentioned them, so the repair is one section_depends_on.<sid> write. overlapping-scope fires when two open sections in different plans declare intersecting write paths in their briefs or dispatch history. That is the shape of shared-coil-supply-model#s6 and iter-switched-terminal-transients#s6, the same integrated run planned twice.

Both findings are warnings with an exact repair. Neither invents an edge: the analyser reports the suspected wait and leaves the decision to whoever owns the plan.

Done when: a fixture whose blocked manifest names B#s4 from a section with no edge to it emits undeclared-wait with both refs, and the same fixture with the edge declared emits nothing. Two fixture sections claiming one path emit overlapping-scope, and two claiming disjoint paths do not. On power_convertor the findings are listed in the gate log, and each is checked by hand as a true or false positive, with the count of each recorded.

§6 — A section can wait on a followup

The ref grammar gains slug@f-id, satisfied when that followup resolves. One coordinator's section really waited on f-tfcv-007 and could only declare the whole section that followup belonged to. PLAN-FORMAT.md, the published schema and the reckon-edit skill state the new ref in the same commit as the parser change.

Done when: a section declared to depend on X@f-1 is blocked while the followup is open and ready once it resolves, and a ref to a followup that does not exist is a dangling-hard-dependency finding. Both tests fail on the base commit, where the ref does not parse.

§7 — One brief an agent can act on

reckon.brief.project_brief(project, session=None, since=None) composes, from §2 to §5, the page a coordinator needs before choosing work. It runs to at most 6,000 characters of plain text plus the typed rows behind each line, and contains:

  • the active sprint's goal and its time left;
  • both completion percentages;
  • the critical path as sections, with hours, the runs on it and what holds its head;
  • the ten highest-ranked ready sections with their reason;
  • true blockers grouped by kind;
  • at-risk work: sections with repeated attempts, runs blocked more than a day, interrupted runs;
  • wiring findings, counted, with the top three shown;
  • when since is given, what changed after that cursor.

The brief is a composition, not a second analyser: every figure in it is read from the payload §2 to §5 produce. The CLI prints it as reckon brief --project, and the MCP surface serves it under the contract its own plan sets.

Done when: a fixture is built so that its critical-path head, its top-ranked ready section, its oldest blocked run and one undeclared wait are known in advance, and the brief names all four within 6,000 characters. The base commit has no brief and its plan-level analyser names a different head, so the test fails there. A second arm changes one fixture edge and requires the brief's critical-path line to change with it. On power_convertor the brief names the critical-path head, the run blocked since 2026-10-17 and the three ready sections with the largest reach. A parity test that every number in the brief equals its roadmap field stays as a guard against drift, not as the control.

§8 — Measured on power_convertor and two other mounts

The coordinators' questions are asked again through the new reads on power_convertor, nova and reckon itself. They are: what is critical, what is blocking a named section, who holds a named file, and what should run next. Each answer is compared with what the owning coordinator says is true, and the result goes to the cumulative landed record.

Done when: each question is answered by one call on each of the three mounts within its read deadline. Every disagreement with a coordinator is listed with its cause, as either a wiring fault in the plans or a defect in the derivation, and each derivation defect becomes a section of this plan or a new plan. Two controls make the measure able to fail. The same four questions put to the base commit on the same power_convertor snapshot must disagree with the coordinators at least on the critical path and the first-ranked item, as they do today. And a copy of the snapshot with one declared cross-plan edge removed must move the critical path, and must raise undeclared-wait when a blocker still names the removed edge.

§9 — A section can be descoped

A new declaration, descoped, with a required reason, counts as closed for close and for the critical path but not as done for impl, and is shown in history. Today a coordinator ticked a deferred section done with an explanatory comment, because close refuses any plan with a deferred section; the record then says something false. PLAN-FORMAT.md, the published schema and the reckon-edit skill state the declaration in the same commit as the parser change.

Done when: a plan whose only open section is descoped closes, its impl excludes that section, and a descoped declaration with no reason is refused. On the base commit the declaration is refused as unknown, and the test fails there.

§10 — A refused op names the path that works

set section_depends_on without a section id is refused, and two coordinators concluded from the refusal that the field could not be written. The refusal now names section_depends_on.<sid> and sections.<sid>.effort_hours, which already work.

Done when: the refusal text for a bare section_depends_on set names the keyed path, and the keyed write it names succeeds on the same fixture. On the base commit the refusal does not name it, and the test fails there.
