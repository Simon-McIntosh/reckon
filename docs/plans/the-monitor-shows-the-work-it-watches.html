§1 — Why: the pane is empty while work runs, and it never ends

The imas-codex coordinator session 6fe78f81 relayed this on 2026-10-12, at the lead's request. At 04:47Z on 98dci4-clu-2002 that session dispatched one review run, r-20261012T044739534705-review-portfolio-4dde24777e04. The host wiring was correct: crew host pid 2116694 started follower pid 2162620, and both write to the pane. The watch stream held the run's baseline row (04:47:43Z) and its dispatched → running row (04:47:56Z). After more than 12 minutes the lead's Monitor pane still read "Status: running · No output available".

The cause is the row policy shipped by a-follower-row-is-worth-a-wake (commits 089cd7741, 79d3a5458, contract 778219ba2). It delivers only a row that asks the coordinator for action, or news nobody caused, and never a start. So a session with work in flight shows nothing. The host also never exits on its own, because Claude Code would not restart it (reckon/crew/session_host.py, module docstring). So the pane stays "running" after the work has ended.

The lead's requirements, in their words: "it should not be overly verbose, but also not empty"; "I should be able to see all work active"; "the monitor should auto stop when there is no live work"; and "the monitor is for me too, I want to see what is going on". The pane has two readers, the coordinator and the lead. The policy that is right for waking the coordinator is not enough for the person watching.

A peer session's start, a bare re-announcement, an echo and a replay are still held, so nothing is added to a pane for work that is not its own.

§4 — The pane ends when no work is live

Deliverable. When the session has no live run, its follower child prints one idle line, no live work in <session> since HH:MM, and exits. "No live run" is the answer of _population_has_live_work(project, session=...) in reckon/crew_follow_commands.py, which already owns that judgement; it is not derived a second time. The idle line extends the final-line path crew follow --lifetime already prints. Today SessionHost.handle drops a request for a project and session already in its children, and tick restarts a keyed child on backoff without removing the key. So when a child settles, the host removes it from its census. The next request for that pair then starts a new child, and backoff never restarts a settled one.

The session host stays alive, and the pane's last line reads idle. When the session next dispatches, the request that dispatch already writes to the host's pipe starts a new follower child for that project and session. The new child replays nothing it has already printed and delivers the new run's start row. No turn is spent re-arming. The host itself still never exits on its own, because a plugin monitor that exits is never restarted in the session (decision pane-end). Claude Code therefore still lists the monitor as running, which this section accepts.

Done when tests/test_a_pane_settles_when_no_work_is_live.py passes over a temporary host state directory:

  • When the last live run of session S settles, the idle line is delivered once and the follower child exits, while the host process stays alive.
  • A follower that observes a peer session (--observe-session) whose run is still live does not settle. A peer session the follower does not observe never holds it open: the population it settles on is its own session plus the sessions it observes, not the whole project.
  • A later request for S starts one new child, which delivers the next run's start row and replays no row the settled child already printed.
  • Two requests for S arriving together start one child.

The existing session-host and follower tests pass. The negative control, which restarts a settled child immediately as today's backoff does, fails the first case. It is logged under the run directory.

Decision: how the pane ends.

  • Host exits. The host writes a closing "no live work" line and exits, so Claude Code shows the monitor as stopped. The next dispatch re-arms the monitor, which costs the session one turn per idle-to-busy transition.
  • Child settles. The follower child ends on a settled summary line, and the host stays and starts a new child when the session next dispatches. No turn is spent, but Claude Code still shows the monitor as running.

Write paths: reckon/crew/session_host.py, reckon/crew_follow_commands.py, tests/test_a_pane_settles_when_no_work_is_live.py.

§5 — The pane speaks seven state words, in pairs

Why. The pane prints whatever word each layer leaves behind: pointer phase, recovery classification, watch state and display alias. On 2026-10-12 it showed both completed_unpromoted and its alias unpromoted for one state. It also printed unpromoted → complete for a run moving forwards, and complete → unpromoted for a reviewed run that went back for fixes. The classifier grew a state for each incident: wait-aged, stopped, unwritten, exited-unfinished and others. Each is right for choosing a recovery action, and each was printed as its own word. Measured over every project's watch stream (11,408 runs, 39,042 transitions), the pane has used 19 state words in 143 distinct pairs. The dwell times show which ones carry no information for a reader:

  • dispatched: median 95 s, followed by working 6,307 times.
  • running: median 49 s, a duplicate of working.
  • promoted: median 3 s, re-announced 365 times.
  • stopped: median 30 s.
  • Awaiting review (median 784 s) and reviewed-awaiting-promotion (median 118 s) follow each other 2,937 times.

Deliverable. The pane uses exactly these seven words (lead's choice, 2026-10-12):

WordMeansInternal states it covers
queuedheld for a lane slotqueued
workinglaunched or runningdispatched, starting, running, working
waitingon a declared external waitwaiting, paused, wait-aged (an overdue wait keeps the word and carries the existing action marker)
haltedstopped short; a decision is neededblocked, needs-help, held, stalled, stopped, abandoned, failed, unreadable, unwritten, exited-unfinished, ended-without-manifest, launch-failed, refused-at-admission
deliveredthe worker finished; not yet landedscoring / completed_unpromoted, promotable / complete
landedpromoted or recordedpromoted, recorded
droppedleft without landingwithdrawn, discarded, departed

Every row is a pair drawn from these words. A run's first row reads new → working or new → queued, where new appears only on the left of a first row. A pair whose two words are the same is never printed. The reason clause, not the state word, names the specific cause: what a halted run asks, what a waiting run waits on, which review a delivered run is in. The internal classifications and their recovery verbs are unchanged. The mapping is one table, owned in one place, which every surface that prints a run's state reads: the row, the run counters and the roll-up of §3. It supersedes DISPLAY in reckon/crew/ticker.py in place, and DISPLAY is retired. The counter bucket labels _WAIT_CELL and _COUNT_FIELD are reconciled with the seven words. So is DISPLAY_HUE, which resolves each word's colour and is keyed today on the old alias words, so every one of the seven words resolves its own hue rather than the dim fallback. Replayed over the same history, this mapping prints 28,408 rows instead of 39,042, in 22 distinct pairs.

Done when tests/test_the_pane_speaks_seven_words.py passes:

  • Every classification and watch state the code can emit maps to exactly one of the seven words. The test enumerates them from the code's own vocabularies, so a new internal state without a mapping fails the test.
  • A rendered row's left and right words both come from the set, and a raw internal word such as completed_unpromoted never appears.
  • A same-word pair prints nothing.
  • A run's first row starts with new.
  • The run counters use the same words.
  • Each of the seven words resolves a hue in DISPLAY_HUE, so no rendered state word falls to the dim fallback.

The existing ticker and follower tests that assert today's words are updated to the new words, never deleted, and each is named in the manifest. The negative control adds an unmapped internal state, and the enumeration test must then fail. It is logged under the run directory.

Write paths: reckon/crew/ticker.py, tests/test_the_pane_speaks_seven_words.py, plus the existing test files whose expected words change, each named at dispatch. It runs after §2 and before §3, which renders states in its roll-up.

§6 — A pane's remembered states are pane words

Why. §5 maps every state a row draws to one of seven pane words, yet two panes on 2026-10-13 drew completed_unpromoted → delivered after reloading onto that code. A streamed row takes its left word from the state the grid remembers for the run. _seed_ticker_memory in reckon/crew_follow_commands.py fills that memory on attach and reload from the follower's remembered map, which merges the checkpoint with stored history, and both can hold producer states. The memory is copied into the grid unmapped, so a run live across a re-arm or a reload shows its raw state on the left. It recurs at every vocabulary change and at every attach that seeds from stored history.

Deliverable. The grid maps a remembered state to its pane word where it takes the memory in. A remembered state that is already one of the seven words maps to itself; _display_state in reckon/crew/ticker.py blanks delivered, halted, landed and dropped today, so the mapping handles them. No other path writes the grid's memory, so every left word a row draws is new on a run's first row or one of the seven.

Done when a test seeds a grid with a run remembered as completed_unpromoted and another remembered as working, renders a following transition for each, and finds the left words delivered and working. A second test seeds every internal state in PANE_STATES and each of the seven words, and finds each internal state's left word to be its pane word and each seeded pane word's left word to be that same word, delivered, halted, landed and dropped included. The test files importing reckon/crew/ticker.py or reckon/crew_follow_commands.py show no added failure against base. The negative control seeds the memory unmapped again, and the first test must then fail. It is logged under the run directory. Write paths: reckon/crew_follow_commands.py, reckon/crew/ticker.py and tests/test_a_remembered_state_renders_as_a_pane_word.py.

§7 — A standing line lists your runs that need you

Was §2 of a-follower-keeps-your-work-in-view, folded here on 2026-10-13.

Add a row kind to the follower, the needs-you line. It lists every run of the owning session whose state is in NEEDS_ACTION in reckon/crew/ticker.py, or is unpromoted, or needs help. Each entry gives the node, the state word and the time the run has held that state, as in needs you: 2 unpromoted pta-adopted-read-cost 1h21m, rail-worktree-uv-env 42m · 1 blocked fsa-repair 5m. The line is plain text and reads fully without colour.

An unpromoted run whose review is already stored is marked reviewed in its entry. imas-ambix-f6 lost the only repairable window this way: promotion deletes the pointer and its captured session, so a review read after promotion can no longer be answered by resuming its author.

Emit the line after any transition that changes the set, and again on a cadence whether or not the set is empty. When nothing needs the coordinator the cadence line reads yours: 4 working · nothing needs you. That makes the cadence line a heartbeat, which imas-ambix-f6 asked for, because a quiet pane must not look the same for a healthy follower and a dead one. The cadence defaults to ten minutes and is set with --remind. The line is composed in Python beside the fleet partition in reckon/crew/recovery.py, so the live MCP view can return the same list. The follower emits it from inside the generator _follow_watch_lines in reckon/cli.py, in its wait pass where _tick() is already called, because that code can yield to the pane. The on_poll hook cannot carry it: the path map in the measurement plan §4 found that _tick discards on_poll's return value, so nothing it produces reaches the reader.

Done when tests/test_follow_needs_you_line.py runs a follower over a fixture holding two sessions. The owning session has one unpromoted and one working run, and the other session has one blocked run. With the cadence set to one second, the needs-you line appears at least twice in three seconds, names the unpromoted run with its age, and never names the other session's blocked run. A second case with no owned run needing action asserts the cadence line still appears and reads that nothing needs the coordinator. An unpromoted run with a stored review record is marked reviewed. The negative control is executed and logged: with the cadence emission removed, the line appears at most once and the first case fails. §12 — The critical-path coverage cell, and why it waits

Was §10 of monitor-renders-what-it-is-given, folded here on 2026-10-13.

The counter block answers how much work is in flight and says nothing about which work. A fleet can read 7w all day while the plan on the critical path has nobody on it — measured on nova, 2026-09-18: the roadmap ranked the critical path first for a whole sprint while twelve runs closed plans already between 85 and 99 percent complete, and the path itself carried zero workers. A coverage cell on the row is what makes that visible where a coordinator already looks, rather than in a report nobody opens mid-wave.

This section owns the cell and not the figure, and the split is the project's rule rather than a preference here. The coverage figure is a derived fact a reader without a pane would also want, so it is computed once in Python and consumed by the surface. Deriving it a second time inside the renderer would be two implementations of one truth — the same defect with a longer fuse, because nothing fails when the copies drift.

The figure belongs to work-scheduling-surface §3 — roadmap coverage per open path, computed from live pointers whose process is alive rather than from transition events. That section is queued behind its own plan's push-status node because the two share reckon/roadmap.py. Its coordinator offered to let this cell read live pointers directly and to have §3 adopt the same helper afterwards. That offer is declined: it places the first implementation of a derived fact inside a renderer and then asks the owning module to follow it. Waiting costs a queue position and buys one derivation.

Done when the row carries a coverage cell for the critical path whose value comes from the roadmap's own derivation rather than from any figure computed in ticker.py, asserted against a fixture in which coverage and the working count disagree — they must differ, or the assertion passes on a renderer showing the wrong number.

§13 — The session host removes its FIFO when it ends

Was §9 of a-follower-lives-as-long-as-its-session, folded here on 2026-10-13.

Deliverable. When reckon crew host stops, because its owner ended or it was signalled, it removes the FIFO it was handed. The entry point removes the FIFO only when its owner ends before the first request; once it has become reckon crew host, nothing does, so every session that dispatched leaves one stale FIFO in the runtime directory. The entry point's own removal does not hold either. It runs only when the wait loop sees the owner gone, and the entry point traps no signal, so a monitor that Claude Code stops at session end exits before reaching it. Measured 2026-10-07: two sessions that never dispatched (Claude pids 2484216 and 2489693) ended and left their FIFOs behind with no entry point alive. So the entry point also removes its FIFO on TERM, HUP and INT. The host derives the path from its owner pair and the same runtime-directory order the entry point uses.

Done when a test in tests/test_session_host.py starts the host on a FIFO named for a fake owner, ends the owner, and finds the FIFO gone; a test in tests/test_session_host_plugin.py sends TERM to a waiting entry point and finds its FIFO gone; and the session-host census reports stale_fifos=0 after one session that dispatched and one that did not have both ended. Each test fails on the current code, which is its negative control: the host test because nothing removes the FIFO once the entry point has become reckon crew host, and the entry-point test because no trap removes it on TERM.

§14 — A run that changes state across a producer reload still wakes its session

§15 — A held request is retried without leaving the queue

Why. The pane flickers. The queue runner, admit_once in reckon/crew/queue_admission.py, retries each held request by deleting its queued pointer in _launch_queued and running a full dispatch, which the lane refuses and queues again. Every pass therefore emits a withdrawal, a dispatch and a queueing for a request whose state never changed, and the pane draws queued → dropped and dropped → queued each time. Measured on 2026-10-13: 445 of the project's 725 transitions in two hours, 61%, were this cycle, and one held plan review cycled 112 times.

Deliverable. Before it releases a queued pointer, admit_once asks the lane the two questions dispatch would ask, the lane gate (_dispatch_lane_gate in reckon/crew/dispatch.py) and the session's lane allowance. A request the lane would still hold is left exactly as it is: the same run id, phase queued, no event. Only a request the lane will admit is released and launched, as today.

A request that cannot launch is not retried every pass. The request that cycled 112 times was never waiting on the lane: its dispatch failed every pass with a CrewError because its brief file no longer exists, and each pass released it, failed and restored it. A request whose last attempt failed for a reason other than a lane hold keeps its queued pointer and its recorded failure and is not attempted again until something it depends on changes, such as its brief, its plan or its lane configuration, or until a bounded back-off elapses. Its first such failure is reported once to its session.

Done when a test runs admit_once over a queued request while the lane holds it, and finds the pointer unchanged and no transition appended to the project's event stream; with the lane open, the same request launches. A second case queues a request whose brief file is missing and runs admit_once three times: the first pass records the failure, and the next two leave the pointer unchanged and append nothing to the stream. The test files importing reckon/crew/queue_admission.py show no added failure against base. The negative control releases the pointer before the admission check again, and the held case must then find a withdrawal in the stream. It is logged under the run directory. Write paths: reckon/crew/queue_admission.py and tests/test_a_held_request_stays_queued.py.

§16 — The pane draws no round trip

Why. Even with §15, a run can leave a state and come back within seconds: a requeue, a lane change, a resume that is refused. The pane draws both halves, so a reader sees two rows that cancel each other.

Deliverable. A departure that does not come back within the window is delivered as it is today, so a real withdrawal still reaches the pane.

Done when a test feeds queued → withdrawn → dispatched → queued within the settle window for a run the pane shows as queued, and finds no row; the same departure with no return delivers its dropped row once the window passes. The test files importing reckon/crew/ticker.py show no added failure against base. The negative control removes the round-trip rule, and the first case must then show rows. It is logged under the run directory. This section runs after §6 and after the-suite-is-green-at-head §15, which also write ticker.py. §17 — A standing lift is not announced again on every restart

Why. On its first pass after it starts, reckon/crew/lift_watch.py emits a baseline row for every lift in force, and the pane draws each one as new → working, "lift in force". A producer restarts on every reload, so a standing lift is announced again each time. A peer pane measured it on 2026-10-13: the same codex-sub lift announced at 09:32:06, 09:35:57, 09:36:15, 09:37:26, 09:37:51 and 09:38:03 with no change between them. A baseline row is inventory of what already exists, not something that happened.

Deliverable. A pane draws a lift's grant and its end, and draws a standing lift once when the pane first sees it. A baseline row for a lift the pane already showed, or for one a reloaded watcher re-announces, draws nothing. Whether this is done in the lift watcher, by carrying which lifts it announced across a restart, or in the row policy, by holding a baseline lift row the pane already drew, is the node's to decide from the code.

Done when a test restarts the lift watcher with one lift standing and finds no new pane row, a new grant and an end each still draw one row, and a pane attached for the first time still shows the standing lift once. § Decisions

pane-end

A plugin monitor that exits is never restarted in the session. Claude Code starts one only at session start or plugin reload ('always'), or the first time a named skill runs ('on-skill-invoke'), and no hook, skill or CLI command can restart it. So 'host exits' would leave a resumed session with no pane. The host stays alive and the follower child settles on an idle line, and the next dispatch restarts the child through the host's request pipe at no turn cost. The cost is that Claude Code still shows the monitor as running.

Once a follower sweeps only its own session, who sweeps the runs of a session that has no follower?

(Locked on a-follower-keeps-your-work-in-view; carried here when that plan was folded in on 2026-10-13.)

Measured 2026-09-22 over seven days and four projects. A coordinator that is present re-arms fast: median 12 seconds, 471 of 587 gaps under a minute, 90th percentile 9.7 minutes. The tail, 99th percentile 5.2 hours and maximum 12.9 hours, is coordinators who were absent, and 13 expiries were never re-armed; three sessions were unattended at the census with pointers 24 to 26 hours old. A grace period of ten minutes, just above the 90th percentile, leaves a present coordinator's re-arm alone and sweeps the sessions nobody is watching, while the 99th percentile would have disabled the sweep exactly when it is needed. The coordinator's own session showed this the same night: its follower was down about two and a half hours during a usage-limit pause, and two finished runs received no review dispatch. No live pointer or registration named another host, so treating a foreign-host pointer as unknown costs nothing today. The watcher records itself as the writer of each sweep action, because no record today carries the sweeping session.

What replaces q for the waiting counter, given that the compact letters are a display contract readers have memorised?

(Locked on monitor-renders-what-it-is-given; carried here when that plan was folded in on 2026-10-13.)

None of the three offered options was taken. The counter spells the word queued rather than carrying any single letter, and the ambiguity disappears because a spelled word needs no mapping to learn. The decision also explains the letter it replaces: q was never arbitrary, it is the first letter of queued — a word the surface never showed anywhere. So the compact rule was intact all along and the display was withholding the term the rule was derived from, which is this sprint's subject rather than an exception to it. Spelling it out costs width in the one cell where the reader most needs certainty, and removes the collision with working without re-lettering a counter readers have used far longer.

When does the plugin monitor start?

A plugin monitor can start at session start ( always ) or the first time a named skill runs. Plan reviews dispatched from /reckon-create and /reckon-edit need a follower as much as /reckon-build runs do. (Locked on a-follower-lives-as-long-as-its-session; carried here when that plan was folded in on 2026-10-13.)

The first dispatch is what needs a follower, whichever skill or tool makes it. A skill list would miss review workers and any dispatch made through the CLI or MCP. The cost is one idle shell per interactive session, waiting on a node-local FIFO.

What does the host print to the pane?

(Locked on a-follower-lives-as-long-as-its-session; carried here when that plan was folded in on 2026-10-13.)

The pane stays the ticker it is today. Host status goes to its log and record, never to stdout, consistent with the rule that the stream carries worker transitions and fleet posture and nothing else.

What happens where no host is running?

(Locked on a-follower-lives-as-long-as-its-session; carried here when that plan was folded in on 2026-10-13.)

Codex sessions, -p sessions and sessions without the plugin have no plugin monitor, so the current mechanism stays for them unchanged.
