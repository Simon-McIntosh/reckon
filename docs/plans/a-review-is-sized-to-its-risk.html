§1 — Why: review became most of the work

On 2026-09-21 promotion began refusing any run that had not been reviewed, and the same morning the review reflex began dispatching a review for every finished run. Across the five mounted projects the share of promotions that were review or investigate nodes went from 25% (14–20 September) to 57% (21–26 September), promotions rose 77%, and source lines landed fell 27% (crew pattern review §4). Every surveyed coordinator ranks review round-trips — 20 to 60 minutes each, serial after the implement run — first or second among wall-clock sinks, and the imas-ambix coordinator measured one 20-minute edit taking five implement nodes and five reviews because each finding became its own repair node (§3).

Review is worth keeping where it pays: on source changes it catches real defects and leads to an observable repair about one time in eight. On documentation, evidence and measurement nodes it leads to a repair about one time in forty (review-node utility §6). This plan keeps the first and stops paying full price for the second.

§2 — Review tier by node class, declared in flight config

Deliverable. A review.tiers table in flight config, read by the review reflex and by promotion, that assigns every promotable node one of three tiers from its changed paths, role and diff size:

  • full — any change to runtime source outside tests/, and any node whose plan section is declared guard, fence or security work. Today's review, unchanged.
  • light — a source change under 50 changed lines at spec level exact. A read-only review with a ten-minute budget that answers two questions: does the diff do what the brief says, and does the negative control fail on the mutation it names.
  • none — tests-only, documentation, evidence, figures, plan text and measurement nodes. The integrated gate re-run and the negative control are the check; promotion records the tier as the reason no review exists.

Done when the tier is recorded on every promoted ledger row, a fixture set of one run of each class resolves to the declared tier in a test, and the velocity view (or the census script in docs/research/data/crew-pattern-review/velocity/) shows review and investigate nodes at or below 30% of promotions over a full week, with the seven-day deletion share of product lines no higher than the 2.99% measured on 12–19 September.

§3 — One repair per review round

Deliverable. When a review carries findings, the reflex (and any coordinator acting on it) composes exactly one repair node whose brief carries every finding of that review, as a numbered list, against the same write paths. A finding the repair declines is answered in its manifest with a reason.

Done when a test drives a stored review with three findings through the reflex and observes one repair dispatch naming all three, and over a week of ledger rows the count of repair nodes per finding-bearing review is at most one.

§4 — A clean review promotes without a coordinator beat

Deliverable. A run whose stored review scores at least 90, carries no finding, whose gate passed and whose verify-gate re-run passes at the merged head is promoted by the review's own completion, and the ledger row records that no coordinator beat was spent. Anything short of that returns to the coordinator exactly as today. This builds on the refusal landed by scoring-should-stop-a-promotion; it adds an acceptance path, not a bypass.

Done when a synthesised repository promotes a clean run end to end with no coordinator command after dispatch, a run whose review carries one finding is not promoted, and a run whose integrated gate fails is not promoted — three named tests.

§5 — The reflex reviews a settled head, once

Deliverable. The reflex dispatches a review only for a run that is terminal and has not been resumed within the last five minutes; a resume cancels a review still queued for the superseded head; and a review of an earlier head carries forward when the later commits change no path the review's tier covers (a relocation of a data file, a manifest correction), so a second full review is not demanded. Observed in the review that motivated this plan: three census runs were reviewed at heads their coordinator was already correcting, and each correction demanded a second review.

Done when tests show a resumed run's queued review is withdrawn, and a head change confined to paths outside the review tier's scope does not raise a review-missing obligation.
