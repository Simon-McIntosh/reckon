§1 — Why: review became most of the work

On 2026-09-21 promotion began refusing any run that had not been reviewed, and the same morning the review reflex began dispatching a review for every finished run. Across the five mounted projects the share of promotions that were review or investigate nodes went from 25% (14–20 September) to 57% (21–26 September), promotions rose 77%, and source lines landed fell 27% (crew pattern review §4). Every surveyed coordinator ranks review round-trips — 20 to 60 minutes each, serial after the implement run — first or second among wall-clock sinks, and the imas-ambix coordinator measured one 20-minute edit taking five implement nodes and five reviews because each finding became its own repair node (§3).

Review is worth keeping where it pays: on source changes it catches real defects and leads to an observable repair about one time in eight. On documentation, evidence and measurement nodes it leads to a repair about one time in forty (review-node utility §6). This plan keeps full review for runtime source and stops reviewing documentation, evidence and measurement nodes, which the integrated gate re-run checks instead.

§2 — A review tier derived from what the node changed

Deliverable. A review.tiers key in the shipped flight defaults (reckon/schema/flight-defaults.yaml), overridable in the host and project layers like every other flight key, and a resolver that assigns each finished run one tier at completion, from its actual changed paths, its changed-line count (added plus deleted) and its declared spec level:

  • full — the run changes runtime source, meaning package source outside tests/ plus the SPA the server delivers (docs/ui/, docs/_ui/, docs/_shared/ .js, .jsx, .css), the same classification the velocity census uses; or its plan or section declares capability risk elevated or critical (the existing plan-capability-risk field), which is how guard, fence and security work is marked. Today's review, unchanged.
  • light — the run changes runtime source by fewer than 50 changed lines at spec level exact or guided, with no elevated risk. A review dispatched with a ten-minute time budget that answers two questions — does the diff do what the brief says, and does the node's recorded negative-control log show a failure for the mutation it names — and stores its review record like any other. It reads; it does not re-execute. A light review that exceeds its budget escalates to a full review.
  • none — the run changes no runtime source: tests, plans, evidence, research data, figures, or any combination of them. Promotion runs verify-gate at the merged head, and the node's negative control where it declared one; the ledger row records the tier as the reason no review exists.

The tier is recorded on every run promoted after this lands; earlier rows are not backfilled.

Done when a fixture set — one run per tier, plus one none run for each path class (tests, plans, evidence, research data, figures) and one mixed tests-plus-plan run — resolves to its declared tier in a test; and, one week after landing, the velocity census re-run over the trailing seven days across the mounted projects shows review and investigate nodes at or below 30% of promotions, with the seven-day deletion share of product lines no higher than the 2.99% measured on 12–19 September.

§3 — One repair per review round

Deliverable. When a review carries findings, the reflex (and any coordinator acting on it) composes exactly one repair node for that review round, whose brief lists every finding and whose write scope is the union of the paths the findings name — declared at dispatch, so a finding outside the reviewed run's fence is granted rather than refused. The repair's own manifest answers each finding it declines, with a reason. A repair that fails or blocks may be redispatched as another attempt of the same round; that is not a second round.

Done when a test drives a stored review with three findings through the reflex and observes one repair dispatch naming all three; and over a week of ledger rows every finding-bearing review has exactly one repair round, and no finding is left without either a repair commit or a declined-with-reason answer.

§4 — A clean review promotes without a coordinator

Deliverable. When a review run completes with a stored record whose five-dimension total is at least 90 of 100 and which carries no finding, the review's completion handler promotes the reviewed run itself: it confirms the run's recorded gate passed, runs verify-gate against the primary branch's current head with the run merged, and on both passing promotes with promoted_by: review-acceptance on the ledger row. Anything short of that returns to the coordinator exactly as today. This adds an accepting branch to the refusal scoring-should-stop-a-promotion landed; it is not a bypass of it.

Done when a synthesised repository takes a clean run from its implement dispatch to promotion with no coordinator command in between; a run whose review carries one finding is not promoted; and a run whose integrated gate fails at the merged head is not promoted — three named tests.

§5 — The reflex reviews a settled head, and re-reviews only what changed

Deliverable. The reflex dispatches a review only for a run that is terminal and has not been resumed in the last five minutes. A resume withdraws a review still queued for the superseded head; a review already running when a resume lands finishes, and its verdict applies to the new head only under the rule that follows. When a reviewed run gains commits, the stored review carries forward if those commits change no runtime source path; if they do, the reflex dispatches a light review of those commits alone rather than a second full review of the run. The carry-forward is written to the run's record as satisfying the review requirement, never left as a silent absence.

Done when tests show: a resumed run's queued review is withdrawn; a data-file relocation after a review writes a carried-forward record and raises no review-missing obligation; and a later runtime-source commit dispatches a light review scoped to that commit.

§6 — The project's own suite is a standing gate

Why. Per-node gates run the tests a node's brief names. In nova the default test command stopped at collection and ran no test from 29 August to at least 19 September while nodes kept promoting (crew pattern review §8). Lighter per-node review is only safe beside a check that sees the whole project.

Deliverable. Project configuration declares its suite command and a whole-run budget; the coordinator's wave close runs that command once at the merged head, recording collected, passed, failed and errored counts on the sprint's evidence; and while the last recorded run failed to collect or exceeded its budget, promotions at tier none and light are held with the reason named, until a passing run is recorded or the lead waives it.

Done when reckon and nova each declare a suite command and budget; a synthetic project whose suite fails at collection holds a tier-none promotion in a test; and one real wave close in each of the two projects records its counts.
