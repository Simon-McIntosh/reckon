§1 — Why: two reviews stuck before launch after a landing

nova-39 reported this on 6 November, relayed and confirmed by reckon-e0. Two review runs that the follower composed on clive, r-20261106T151053449404-review-of-bank-solve-trace-head-1a40db649fa0 and r-20261106T152717322525-review-of-bank-compact-followups-a663fcd2e239, sat in phase starting with no pid for over 30 minutes. Their run directories held only brief.md, claim.json and classification.json: no attempt.json, worker.json, exit.json or stderr. The monitor drew them as halted, and neither appeared in the obligations, so the owed reviews were invisible. The pointers were already classified launch-failed by _stranded_launch (reckon/crew/recovery_liveness.py near lines 740–771, past STRANDED_LAUNCH_BOUND_SECONDS = 900 at line 62), but CLASSIFICATION_DUTY_KINDS (reckon/crew/obligations.py near line 53, read near line 1957) has no entry for that classification, so the obligations drop it.

Each was created about a minute after a reckon/ landing on main: 458f9827f9 at 15:09:26Z, then the first run at 15:10:53Z; 0004c5f682 at 15:20:34Z, then the second at 15:27:17Z. The station's review sweep runs in a daemon thread (reckon/crew/station.py near line 64). Its code reload calls os.execve (near line 384), which ends every thread at once, and followers (reckon/crew/follower_reload.py near line 514) and the admit service (reckon/crew/queue_admission.py near line 876) re-exec the same way. A re-exec between a dispatch writing its claim and launching its worker leaves exactly these leftovers.

A redispatch was then refused with “already in flight as run … pid 2082563”. Both node dispatch claims named the station, pid 2082563 with process start time 362172960, which still matched /proc: the station re-execs under the same pid, and its reload tree had moved from ed98a062 to 1ce850f368. _claim_holder_is_alive (reckon/crew/dispatch_claims.py near line 624) reads a claim as held while its pid and start time match, so the orphaned claim stays held until the station process exits, and crew discard of the run did not release it. reckon-e0 released both by renaming each to <name>.json.reclaimed-<run id>, as _reclaim_stale_node_dispatch_claim (near line 674) does. Any reckon/ landing can trigger this, so reviews composed near a landing are the ones at risk.

§2 — A re-exec never orphans an in-flight dispatch

Deliverable.

  • A node dispatch claim records its holder's exec identity beside the pid and start time: a nonce each process draws once per exec, which a re-exec draws afresh. _claim_holder_is_alive (reckon/crew/dispatch_claims.py near lines 624–652) reads a claim that carries an exec identity as stale when the holder's published identity differs, so a claim written before a re-exec is reclaimed by the existing _reclaim_stale_node_dispatch_claim. A claim carrying no exec identity, written by a holder that has not reloaded onto this code, is judged as today.

Done when a new tests/test_a_reexec_never_orphans_a_dispatch.py shows three things with a temporary crew home:

  • A claim written by a holder whose published exec identity has since changed, with pid and start time unchanged, reads as stale, and a new dispatch of the same node succeeds.
  • A claim whose holder's exec identity is unchanged still reads as held, as today.
  • A claim carrying no exec identity whose pid and start time match reads as held, as today.

Three negative controls, one per case: comparing only pid and start time makes the first case refuse the new dispatch; ignoring the claim's identity entirely makes the second case read stale; and treating a missing identity as a mismatch makes the third case read stale. The test files importing reckon.crew.dispatch_claims add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. Write paths: reckon/crew/dispatch_claims.py and the new test. The holder publishes its identity where its pid record already lives; the worker names that file in the manifest. The wait before re-exec is §5's.

§3 — A discard releases its run's dispatch claim

Deliverable. discard (reckon/crew/promotion.py near line 1987) releases the node dispatch claim of the run it discards, through _reclaim_stale_node_dispatch_claim, when that claim names the discarded run. A claim naming another run is left alone.

Done when a new tests/test_a_discard_releases_its_dispatch_claim.py shows two things with a temporary crew home: discarding a run whose claim names it releases the claim, so a dispatch of the same node succeeds; and a discard leaves a claim naming a different run in place. Two negative controls: skipping the release makes the first case refuse the dispatch; and releasing any claim for the node makes the second case lose the other run's claim. The test files importing reckon.crew.promotion add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Write paths: reckon/crew/promotion.py and the new test.

§4 — A run stuck before launch is reported as a launch failure

Deliverable. The classification already exists: _stranded_launch marks a pre-spawn pointer with no pid, worker record, stream or launch log past STRANDED_LAUNCH_BOUND_SECONDS as launch-failed. CLASSIFICATION_DUTY_KINDS gains an entry for it, so the obligations list it with the command that redispatches it, and the monitor draws it launch-failed rather than halted (reckon/crew/ticker.py, whose phase colours are near lines 193–205).

Done when a new tests/test_a_run_stuck_before_launch_is_reported.py shows three things with a temporary crew home: a pointer starting with no pid past the bound appears in the obligations as a launch failure carrying a redispatch command; the same pointer within the bound does not; and the ticker draws the first as launch-failed. Three negative controls: dropping the duty-kind entry leaves the first case absent from the obligations; lowering the bound to zero makes the second case report; and drawing every pid-less pointer as halted fails the third case. The test files importing reckon.crew.obligations or reckon.crew.ticker add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Write paths: reckon/crew/obligations.py, reckon/crew/ticker.py and the new test.

§5 — A service waits for its in-flight dispatches before it re-executes

Why. §1's cause: the station (reckon/crew/station.py near line 384), a follower (reckon/crew/follower_reload.py near line 514) and the admit service (reckon/crew/queue_admission.py near line 876) call os.execve while a thread of theirs may be between writing a dispatch claim and launching its worker. §2 makes the claim left behind read stale; this section stops leaving it.

Deliverable. Each of the three waits, for a bound, for a dispatch its own threads have in flight before it calls os.execve, and logs any it abandons at the bound with its run id.

Done when a new tests/test_a_reexec_waits_for_its_dispatches.py shows three things with a stubbed os.execve: a station reload with a dispatch in flight in its sweep thread waits for it before exec; a follower reload does the same; and the admit service does the same. A dispatch still in flight at the bound is logged with its run id in each. Three negative controls, one per service: calling os.execve without waiting makes that case exec with the dispatch in flight. The test files importing reckon.crew.station, reckon.crew.follower_reload or reckon.crew.queue_admission add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Write paths: reckon/crew/station.py, reckon/crew/follower_reload.py, reckon/crew/queue_admission.py and the new test.
