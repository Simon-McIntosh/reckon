§2 — A re-exec never orphans an in-flight dispatch

Deliverable.

  • A node dispatch claim records its holder's exec identity beside the pid and start time: a nonce each process draws once per exec, which a re-exec draws afresh. _claim_holder_is_alive (reckon/crew/dispatch_claims.py near lines 624–652) reads a claim that carries an exec identity as stale when the holder's published identity differs, so a claim written before a re-exec is reclaimed by the existing _reclaim_stale_node_dispatch_claim. A claim carrying no exec identity, written by a holder that has not reloaded onto this code, is judged as today.
  • The holder's identity is published where _claim_holder_is_alive can find it from the claim alone: each exec writes its identity to a per-pid file under the crew home's claims directory as soon as dispatch_claims is imported, which the station, a follower and the admit service do at start, so a re-exec overwrites the file before any claim from the old exec is judged. The check reads that file for the claim's pid; a missing file is judged as a claim with no identity. The claim record itself is built near lines 745–757.

Done when a new tests/test_a_reexec_never_orphans_a_dispatch.py shows three things with a temporary crew home:

  • A claim written by a holder whose published exec identity has since changed, with pid and start time unchanged, reads as stale, and a new dispatch of the same node succeeds.
  • A claim whose holder's exec identity is unchanged still reads as held, as today.
  • A claim carrying no exec identity whose pid and start time match reads as held, as today.

Three negative controls, one per case: comparing only pid and start time makes the first case refuse the new dispatch; ignoring the claim's identity entirely makes the second case read stale; and treating a missing identity as a mismatch makes the third case read stale. The test files importing reckon.crew.dispatch_claims add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. Write paths: reckon/crew/dispatch_claims.py and the new test. The wait before re-exec is §5's.

§3 — A discard releases its run's dispatch claim

Deliverable. discard (reckon/crew/promotion.py near line 1987) releases the node dispatch claim of the run it discards through the claim's own release path, _NodeDispatchClaim.release(), which unlinks it, when that claim names the discarded run. A deliberate discard is not a stale claim, so it leaves no .reclaimed- artifact. A claim naming another run is left alone.

Done when a new tests/test_a_discard_releases_its_dispatch_claim.py shows two things with a temporary crew home: discarding a run whose claim names it releases the claim, so a dispatch of the same node succeeds; and a discard leaves a claim naming a different run in place. Two negative controls: skipping the release makes the first case refuse the dispatch; and releasing any claim for the node makes the second case lose the other run's claim. The test files importing reckon.crew.promotion add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths.
