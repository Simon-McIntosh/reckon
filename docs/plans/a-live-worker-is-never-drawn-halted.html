§2 — A live worker's unreadable in-progress manifest is not unwritten

In recovery_classification, the arm that runs when alive is True first asks _absence_of_a_verdict_is_transient. That check holds the reading back within LAUNCH_WINDOW_SECONDS of dispatch and within MANIFEST_REWRITE_WINDOW_SECONDS of the manifest's own mtime. Past both windows, the arm sets manifest_unwritten = True when a present manifest carries no readable status and has a parse error. Two kinds of manifest reach that arm. One is unreadable because it is non-terminal and loosely written: a ;-joined list field, or a non-vocabulary status such as in-progress-placeholder. The other is a delivery that really is missing its verdict. A live worker is still writing the first kind, so it is not a missing verdict. The run must keep the classification its liveness and stream already give it, and the parse error must stay visible in the run's detail. The same motion evidence decides it as the orientation-write predicate: a proven-live worker, or for unknown liveness an assistant turn in the newest stream inside LOG_STALE_AFTER_SECONDS. Extend that predicate, or the arm beside it, so that a non-terminal or unreadable body of a run in motion is covered. Do not add a second motion rule. Once the worker has exited, the same manifest is still unreadable or unwritten and draws halted, because then it is the delivery.

Done when one new test file builds three fixture runs, each with a live pid (the test process), a newest stream carrying an assistant record, and a dispatch time and manifest mtime set outside both windows above (stated in the test, and derived from the window constants rather than written as literals): (a) status: in-progress with changed_paths: a.py; b.py, (b) status: in-progress-placeholder with the orientation keys, and (c) status: in-progress and a checkpoint. For all three, recovery.recover gives a recovery_classification whose ticker._pane_word is working, and the detail of (a) and (b) names the parse error. A process-gone arm of (a) and (b) still classifies unreadable or unwritten. Negative control: (a) and (b) at the base revision give pane word halted, recorded in the gate log. The tests covering recovery_classification and recovery_liveness add no failures against the base, and ruff check and ruff format --check add no findings on the staged paths. Write paths: reckon/crew/recovery_classification.py, reckon/crew/recovery_liveness.py and the new test.

§3 — A resumed attempt is read through its own records

A resume writes attempt-N.claim, then attempt-N-worker.json and worker.json. It moves the previous attempt's exit.json to attempt-(N-1)-exit.json, and when a coordinator has repaired the status it leaves status-repair.json beside the manifest. The current attempt is live when its claim or worker record is newer than the newest exit record and no exit record for attempt N exists. The supervisor on the launching host writes the exit record, so its absence crosses hosts in a way a pid probe does not. While that holds, a manifest status the coordinator wrote (its status-repair.json repaired_at is older than the claim) and the previous attempt's exit do not decide the run. It classifies starting until the current attempt's worker record exists, and working after. A manifest the current attempt writes is read as it is today. A terminal status the worker itself wrote still counts, and stays provisional while the worker is alive or, with liveness unknown, while its stream is in motion inside the stall window. A launch-failed attempt whose next attempt's claim already exists also classifies starting (reckon-a1's plan-review-of-an-mcp-failure-names-its-cause). Name in the manifest where the current attempt is resolved today. Extend that resolver rather than adding a parallel one. The guard that already owns this reading is _manifest_is_the_predecessor_attempts_report, which reads recovery_liveness._manifest_predates_the_current_attempt and _current_attempt_number. Two stored code reviews flagged its liveness narrowing at recovery_classification.py:72 as letting "the predecessor's blocked word govern a live resumed attempt". Reproduce the recorded case (r-20261023T012524464845-a-plan-write-refuses-the-bucket: repair at 12:14:30Z, attempt 4 launched 12:15:11Z, drawn halted at 12:25:51Z, exited 12:27:56Z) to find which of its three conditions failed, and fix that condition. If the guard itself is sound, the cause is elsewhere: say which in the manifest.

§5 — A wait that recovers from aged prints no row

wait-aged and waiting share the pane word waiting. The aging row is news, because the wait is overdue. The return to waiting is not, because nothing the coordinator must do has changed, yet it prints as waiting → waiting. The departure memory (RowPolicy._shown, _departures) never sees this pair: _hold_departure records nothing when the destination's pane word equals the shown word. What prints both halves is the same-word exemption same_word_row_is_news (_actionable_recovery(event) or declares_a_wait(event)), and declares_a_wait is true for both rows because each carries the wait declaration. That predicate reads one event alone, and the policy's per-run memory (_shown) holds only a pane word. So the row policy also records the shown row's wait facts (wait_overdue, condition, probe, terminal) beside the pane word it already keeps per run. The same-word check, still owned by same_word_row_is_news and its two call sites, is given that memory. A same-word row carrying a wait is news when it newly sets wait_overdue (true where the last shown row had it false or absent), or when its condition, probe or terminal differ from that row's. A row that only clears the overdue flag with the same facts is not news. Add no second same-word rule beside it. The aging row's wording is unchanged.

The producer emits at most one lift-granted and one lift-ended per lift id.

§9 — A producer off the fleet node gives up its seat

The fleet record ~/.local/state/fleet/record.json names the node every worker runs on. A producer whose host is not that node cannot probe a worker pid, so every liveness reading it publishes is unknown, and it still holds the seat that would let a producer on the fleet node start. At start and on each lease renewal, a producer whose host differs from the fleet record's node, and whose project's runs carry a launcher_host equal to that node, releases its seat and exits. The seat owner takes that decision, so it cannot disagree with the readers that already judge a foreign seat: watch_unit.live_foreign_seat / live_foreign_seat_host, watch_unit._record_producer_running, and runs.watch_host_lease / runs._seat_host_is_local. The fleet record is read through its existing owner, fleet_supervisor.RECORD_NAME (and the reader at dispatch_launch.py about line 2128), not by a new path literal. When it was started as a systemd user unit, it first disables that unit, so Restart=always does not bring it back every five seconds. The release is announced once on the stream, naming both hosts. With no fleet record, nothing changes.
