The fleet pane · five cells, and the measurement behind them

What Each Worker Cost, On Its Own Row

The monitor says which worker, what state, and how many are still running. It does not say what any of them cost. A coordinator choosing where to send the next node reads the pane, and then guesses — because the figures that would answer it are either unpopulated, unpriced, or reset on every restart. This plan puts wall time, model time, charged tokens, generation rate and a notional dollar figure on every row, accumulated across restarts, and fixes the three measurements underneath that currently cannot support them.

§1 — The vocabulary already exists and is not populated

Nothing in this plan invents a quantity. _backends.py's throughput_block already defines every figure the pane needs, and defines them with the distinction that matters: generation_seconds is time inside model requests, machine_seconds is elapsed − generation — the test runs, the SLURM waits, the tool execution — and tokens_per_second is deliberately generated over generation rather than over wall. Someone designed this correctly. The block is then populated on almost nothing.

That is a borrowed measurement and not a prerequisite: it is already readable, and no node here waits on that plan closing — the edge was authored as a hard dependency and removed once each node was checked against it individually. The one real coupling is that §7's fourth node writes ledger.py, which a concurrent session holds; that is a dispatch-time scope claim, enforced by the validator, rather than a relationship between plans. A cell reading a field populated on 3.4% of runs is blank on nineteen rows in twenty, and a reader takes a blank cell as a quiet worker rather than as an unrecorded one. Shipping the columns without the measurements would make the pane worse than silent: it would make it wrong.

The generation_seconds gap has a specific cause, and it is not difficulty. _backends.py sets it to None for codex on purpose, commenting that the harness “separates neither inference from tool wait nor the turn from the run, so claiming a generation span would be inventing one”. That is true of the exec stream it reads and false of the client rollout, which carries a timestamp on all 4,985 records of the file measured for this plan — and which crew/rollout.py already parses, in the same package, for quota. So the field is empty because the measurement reads the wrong file, with codex accounting for 2,280 of those 2,582 runs.

§2 — Five cells, between the effort cell and the counters

The cells sit after the model and effort pair and before the fleet counters. That placement is forced rather than chosen: everything before the reason must be fixed-width, because the pane clips its own right edge and the reason is the elastic tail. Putting the figures after the counters would let a width read one column too wide eat them silently.

The node column is shown narrowed above so the sample fits this page without wrapping; in the pane it keeps its full 36 columns and the five cells sit further right.

Widths are fixed and every cell is right-aligned, so the right edge never moves as figures change: wall 7, model 6, tokens 4, rate 4, dollars 5, single-space separators, 27 columns including the leading gap. MIN_WIDTH moves from 128 to 155. On the 208-column pane this workstation measures, the reason field goes from 79 columns to 52 — comfortably above the 12-column floor below which a clause is not worth reading. At the 180-column default it falls to 25, which still clears the floor; the ticker's own header anticipated this, noting that “the 52 at the default is what a later added column spends first”.

The wall-and-model pair is the cell that earns its width. A row showing much wall against little model is a worker sitting in a test suite or a SLURM queue, and a row showing the two close together is a worker actually thinking. That is legible at a glance from the two figures side by side and requires no arithmetic, which is the whole reason both are shown rather than one. The tokens cell counts total charged input including cache reads, plus output, because that is what the meter and the weekly quota charge; the rate cell is generated tokens over model seconds, which is the familiar generation rate. The two therefore do not divide into each other, deliberately: each answers its own question, and a rate computed over charged input would read in thousands and mean nothing a reader could act on.

An unmeasured cell renders a dim en-dash, never a zero. A zero and an unknown are different facts, and this fleet has large populations of both: 131 rows of one lane whose dollar figure must be suppressed, and 96.6% of runs with no model span. Rendering either as 0 asserts a measurement that was never taken, and a reader cannot tell it from a worker that genuinely spent nothing.

§3 — Cumulative means along the lineage chain, and never across a shadow

A worker restarted several times must show figures that add up rather than start over. Today nothing does, because log_path is repointed on every resume — stream.jsonl, then resume-1.jsonl, then resume-2.jsonl. One run measured for this plan holds eight such files under a single run id. Any figure read from log_path alone resets each time a coordinator answers a blocked worker, which is precisely the behaviour this plan exists to remove.

How a restart is recorded depends on which kind it was, and the three kinds are not interchangeable. A resume keeps the run id and adds a stream file. A redispatch and a lane change mint a new run id and chain to the old one. A shadow also mints a new run id and is not a further attempt at all — it is a separate measurement of a different configuration against the same node, run so the two can be compared. Folding a shadow into its primary destroys the comparison the run corpus exists to make.

Both lane-change rows are self-rooted, so they begin a chain rather than continuing one. So the accumulation branches on the kind and then reads the field that kind actually populates: 

durable(run)     := not (lineage and lineage["kind"] == "shadow")
accumulation_key := run_id                          if kind == "shadow"
                    lineage.root_run_id or run_id   otherwise

Durability names the exclusion rather than enumerating the inclusions, and that is not a style preference. An earlier draft of this predicate read lineage is None or kind == "redispatch", which silently dropped lane-change — a kind whose work does merge — and would have dropped every kind added after it. The accumulation key branches on kind explicitly for the same reason: root_run_id or run_id returns the right answer on all 37 rows today only because no shadow happens to carry that field, so it is correct by accident and folds a shadow into its primary the day one does.

This predicate is exported under a name and has two callers. The wave-cost row in crew-observability-truth §13 needs the same exclusion, because a wave's durable cost must not charge it for evidence that never merged; that section will call this predicate rather than restate it, since two copies of an exclusion rule is how the wave figure and the pane cell drift apart while both look correct.

§4 — A rate ledger, and the currency decision this reverses

The dollar figure is a notional cost computed from public API rates for the model actually served. It is not a claim about what any subscription was billed, and it deliberately does not try to be one. Its purpose is comparison: a coordinator deciding between lanes needs to know that one node's work would have cost four times another's, and a dimensionless weight cannot answer that across two different subscriptions.

This reverses a decision recorded in three places, and the reversal is deliberate and owner-approved. flight.yaml's per-backend rate comments state the rates are “used only to derive a dimensionless quota comparison between lanes — never a currency charged to this subscription”; the schema descriptions for input_rate_per_million and output_rate_per_million say the same; and dispatch-cost-per-durable-node §1b rules budget.cost_usd “never surfaced”. All three texts change in the same commit as the code, because a config comment that contradicts the behaviour is worse than no comment — the next reader trusts it.

Measured on this project's own 803 committed rows, the case is stronger than §1b's coverage figure suggests. 107 rows carry a numeric cost_usd, but only 64 — 8.0% — are genuinely metered: 48 on claude totalling $87.65 and 14 on claude-opus totalling $47.91. The other 43 are fabricated figures on the free local lanes, and they total $941.50. So 87% of every dollar this project has ever recorded was never charged to anyone, and all of it is attributed to the hardware that costs nothing per token.

The existing guard is not at fault and the distinction matters for what gets fixed. _label_unmetered_cost nulls and flags correctly on 89 rows, and the 43 survivors all fall between 2026-08-26 and 2026-09-03 while every correctly flagged row falls between 2026-09-05 and 2026-09-09 — no overlap, so they are residue from before the guard existed rather than a leak in it. That makes the 43 rows a backfill belonging to whichever plan owns ledger repair, not a defect for this one to fix, and it leaves the forward path clean. What it does not leave is a usable historical ranking: any comparison drawn over the committed corpus is poisoned by those rows until they are backfilled, which is a second and independent argument for a figure derived from declared rates rather than read from a record.

What §1b was right about survives intact, and it is the reason the figure must be computed rather than read. budget.cost_usd comes from the harness, which prices whatever model name it was told to speak. On the locally-served lane it therefore reports a real-looking figure for a model that was never billed: one deepseek run measured for this plan reports total_cost_usd: 34.34 with costBasis: "unknown", and across four ledgers that free lane totals the highest spend of any backend. A pane rendering that field raw ranks free hardware as the most expensive thing on the workstation. So the cell reads a figure derived from declared rates and measured tokens, never the harness's own.

The word “imputed” already means the opposite of what this plan needs it to mean, and the flag cannot be reused. Today budget.cost_usd_imputed marks a figure that was nulled because the lane is unmetered, and capabilities._cost_usd returns None whenever it is set. Under this plan an imputed figure is one that was computed from declared rates. Setting the existing flag on a computed figure would therefore make every surface reading through that helper discard the cost for exactly the lanes the plan exists to compare — a stable name whose referent has inverted, which is the failure this repository has spent a sprint removing. So the computed figure gets its own vocabulary, the existing flag keeps meaning precisely what it means now, and capabilities.py changes in the same commit as the derivation rather than a commit later. The prior-art scout found this; the plan had missed it.

The ledger has to be refreshable, and every rate has to carry its own date. Rates move; a rate written down once and never revisited is the fuse this repository already knows about under “a snapshot of a moving number”. So each rate is stored with an as_of date, a rate older than a declared staleness horizon reports its age rather than quietly pricing at last year's number, and a model with no declared rate stays explicitly unpriced rather than inheriting a neighbour's. Three backends carry rates today; the rest must either gain one or be visibly unpriced.

§5 — The receipt a coordinator reads before dispatching

The pane cell answers “what did this worker cost”. Choosing where to send the next node also needs “how much room is left, and until when”, and that is a per-lane fact rather than a per-row one. crew/rollout.py already produces most of it: RolloutReceipt carries cumulative tokens, the largest request, the context window, plan_type, and a QuotaReading per window holding window_minutes, used_percent and resets_at. The ledger already has a lane_receipt field to hold it. What is missing is the notional cost beside the quota, so the two can be read together.

So the receipt gains the imputed spend for the run, and the notional value of the headroom remaining in each window, each labelled with the window's own duration and its reset time. Every window is named from the payload rather than assumed — a five-hour figure is another provider's concept, and a surface that renders one for an account reporting only a weekly window is displaying state that account never sent.

One soundness limit travels with it and must be stated on the surface, not only here. rollout.py's own header records that the client's used_percent is quantised to whole percentage points, so a run consuming four tenths of a point is indistinguishable from one consuming nothing: per-run attribution from quota movement is not sound, while aggregates over many runs are. That is why per-worker spend is derived from token counts and rates, and quota is used only for the remaining-and-reset half. A receipt that presented both with equal confidence would misrepresent the weaker one, which is how a reader comes to distrust every figure on a surface once one of them proves soft.

§6 — What was refuted while designing this

Two candidate mechanisms failed measurement during design, and both are recorded because each would have shipped a plausible wrong number rather than an obvious one.

The first was this plan's own proposed rule for codex model time. The idea was to attribute each interval ending at a token_count event to model time, since such an event marks a completed request. Measured against one real rollout it yields 62 seconds of model time across a 20.03-hour span and 818 requests — 76 milliseconds per request, a 0.1% model share. Not credible, so the rule is wrong: those events evidently land adjacent to the record before them rather than at a request boundary. The workable direction is the inverse — bound the tool spans and subtract them from wall — and because the rule is not yet established, §7's first node carries a falsifier rather than an algorithm.

The second is that the codex rollout's cumulative token field is not monotonic. In the same file, info.total_token_usage.input_tokens reads 24,495,394 at its maximum and 744,077 at the end, because the counter resets at each of the file's three compacted markers. So reading the last value under-reports by 33×, and reading the maximum is wrong the moment a session compacts twice. Any cumulative codex figure must sum per-segment deltas across those boundaries. Both readings are wrong in different directions and neither announces itself.

A third field was checked and deliberately left alone. peak_input_tokens carries two different quantities depending on lane — a cumulative sum on codex against a per-request peak elsewhere, medians differing by two orders of magnitude — and a resumed run records one turn while the two blocks hold different values. Nothing in this plan reads it.

§7 — Execution order

The measurements come before the cells, because a cell reading an unpopulated field is worse than an absent cell. Nodes 1 and 2 are independent and open together; node 3 is independent of both. Node 4 follows node 1 because both write crew/rollout.py and a containing path claim is refused rather than merged. Node 5 follows 1–4, since it renders what they produce. Node 6 measures the merged head, which is the only place the combination can be measured at all.

A measure ranges over the corpus, never over a fixture, wherever the figure it asserts can go unmeasured. This plan's own fifth measure failed that test on first authoring: it asked that each cell carry a value or an explicit marker, which five dim dashes satisfy, and at the base revision all five cells are measured together on only 26 of 803 committed rows. A cell-by-cell corpus reading is the reason the figure is known at all — wall 89.4%, tokens 90.4%, model 16.1%, rate 15.8%, dollars 13.3%, and any cell at all on 98.1% of rows. So the fifth node now carries a coverage floor against the corpus and the first three carry the measurements that raise it. The general form, which cost a sibling section six passing-but-inert measures in one day: a derivation that can return unknown must be checked for whether it returns unknown on the whole corpus, because a fixture where it resolves proves only that it can resolve.

Every measure below is phrased with carries or does, never with can or supports. A measure phrased permissively is satisfied by a capability nobody exercises: a sibling section's gate read “every run can join a wave”, and it passed five tests against a field that was empty on 797 of 797 rows. Each measure below also ranges over a fixture population containing the cases where the property can actually fail — a resumed run, a redispatched run and a shadow — rather than over whatever the current inventory happens to hold.

§8 — What this plan does not do

No wave cell yet, and when it comes it will not carry the id. The wave field on the live pointer began defaulting mid-session: it went from empty on every pointer to 8 of 14 carrying the key, two with real ids, six holding the empty string and six predating it entirely, while the committed ledger still lacks it on 797 of 797 rows. So three populations coexist, and both absences — empty string and missing key — mean not-in-a-wave; neither may ever be grouped, or a rollup renders one plausible-looking wave containing every ungrouped node.

The id is wave- followed by 32 hex characters, 37 columns. That is wider than the node cell at 36 and wider than all five cells of §2 together at 27, so it cannot go in the grid. The precedent is already in the file: the owner cell is deliberately one glyph, its comment reading that a run id spelled in full “spends eighteen columns saying it” — an argument that applies roughly twice over at 37. So the pane will render a short per-pane wave index assigned in order of first appearance, exactly as Ticker.hue hands out node colours and for the same recorded reason: identity only has to hold within the pane a reader is watching. The full id stays on the transition record, where a reader correlating against a ledger row can use it. The grid gets the discriminator; the record keeps the identifier.

No change to Ticker._stats. A concurrent session needs that function for a fourth counter cell. The five cells sit between the effort cell and the counters precisely so the two changes touch different functions in one file, and the shared surface is Ticker.render, which is serialised by agreement rather than by refusal.

No SPA meter. Position, burn and projected exhaustion on one mark belong to burn-is-visible-before-it-bites, which is blocked on exactly the derivation this plan lands and will consume it rather than compute a second copy in JSX. No burn fence either: showing a reader where they stand is a different act from refusing a dispatch, and the fence belongs to the prerequisite plan.

No claim about subscription spend. The dollar figure is notional, computed from public rates, and is never presented as what an account was billed. A per-run figure derived from quota movement is explicitly out, for the quantisation reason in §5.

§ Decisions

What grounds the dollar figure?

A notional figure from public rates is consistent and comparable across two different subscriptions, which is the decision it has to support; it needs no plan price and makes no claim about actual billing. The harness figure is disqualified by measurement rather than by preference — it prices whatever model name it was told to speak, so the free local lane totals the highest spend of any backend and a ranking built on it inverts. A subscription share would require declaring each plan's price and would still not compare across providers.

Wall time, model time, or both?

The gap between the two is itself the signal: much wall against little model is a worker stuck in a test suite or a SLURM queue, and neither figure alone shows it. Wall alone hides the rate's denominator and cannot distinguish a slow worker from a busy one; model alone lets a twelve-hour node read forty minutes with nothing on the row saying how long it actually ran. The cost is eight columns of reason field, which the measured pane can afford.

How does a cell with no measurement render?

A zero asserts a measurement that was never taken, and this fleet has large populations of both facts at once — an unpriced lane really did spend nothing chargeable, while an unobserved run's tokens are simply unknown. Blank whitespace takes the right edge ragged, which is the defect the fixed grid exists to prevent.

§ Followups

Open the measurement nodes together, then the cells

§7 nodes 1, 2 and 3 are independent and open in one wave: the codex model span, the lineage accumulator and the rate ledger touch disjoint files and none depends on another's output. Node 4 waits on node 1 because both write crew/rollout.py. Node 5 waits on all four, since a cell reading an unpopulated field is the defect §1 measures.

Two constraints belong in every dispatch. The three decisions above are locked, so no node re-opens them. And the eleven test files asserting on a rendered line are fenced with ticker.py in node 5 rather than left outside it — a narrower fence lets a worker report a clean delta while the merged head is red, which has happened repeatedly on this file.
