§1 — Why: a row is a turn, and most rows ask for nothing

Each line the follower prints reaches the coordinating session as a notification, and each notification can open a turn. The session host from a-follower-lives-as-long-as-its-session keeps that stream open for the whole session, so the stream's density is now the main cost of watching a fleet. The lead reads the same lines in the same transcript, so a row that wastes the coordinator's turn also costs the lead attention.

On 2026-10-08 the lead asked for the stream to carry important transitions and to drop start-up flap and rapid transitions: a dispatch should not produce dispatched → working, a bare working and an exit row in quick succession. The measurement below is the case for doing that, read from every Claude Code transcript under ~/.claude/projects with a Monitor event notification since 2026-10-07 (14 sessions, 2,676 notifications, 3,128 rows) and from the producer streams under ~/.config/reckon/crew/watch/*.events since 2026-10-05 (6,825 transitions over 2,027 runs).

About three rows in five ask for nothing. The producer stream also shows the rapid transitions directly. A run reaches a settled state through a chain of rows written seconds apart: exited-unfinished → blocked within 2 s, blocked → wait-aged → blocked within 3 to 8 s, working → stopped → discarded within a median 18 s. The stream also carries rows whose state does not change at all (withdrawn → withdrawn, recorded → recorded, working → working). Session 9cf43820 received dispatched → working at 02:50:15 and then a bare working for the same run at 02:53:00. That was the replay of a follower its host had restarted at 02:52:42. Session 184d1501's first plugin batch at 02:34:36 replayed rows stamped 11:55 and 12:07 the day before.

The producer already says which rows ask for something. Every transition carries a recovery verb: observe on 2,125 of 2,125 rows into working and 268 of 275 into withdrawn, an empty verb on every terminal record, and promote, review, decide, resume, wait, investigate, repair or redispatch on every row that needs the coordinator. NEEDS_ACTION and SETTLED_STATES in reckon/crew/ticker.py draw the same line for the display. This plan reuses both and adds no new classification.

crew_follow's docstring in reckon/cli.py says every transition is delivered and that no option narrows to action states, because hiding a recovery hides the news a reader is waiting for. This plan keeps that guarantee in a different form. Every change that asks for action or reverses an action row the reader was shown is delivered, and only rows that ask for nothing and reverse nothing are held back. --all keeps the complete stream for a human pane.

The active plan a-follower-keeps-your-work-in-view proposes a needs-you line on a ten-minute cadence. Under host delivery that is a turn every ten minutes per session whether or not anything changed. Its owner should weigh this plan's measurement before building that cadence. Nothing here edits that plan.

§2 — One row policy decides what a follower delivers

Deliverable. A pure module, reckon/crew/row_policy.py, that takes one run's transitions in order, each with its observed_at, to_state and recovery, and returns the rows a reader should receive and when. It holds a run's change until the run has gone a settle window with no further transition. Twenty seconds covers every measured chain in §1, and no row is ever held more than two minutes from its first transition. When a change settles, the policy compares the settled state with the state this reader last judged for the run and classifies the net change:

  • Deliver when the settled state is in NEEDS_ACTION, or its recovery verb is anything other than observe or empty.
  • Deliver when the reader was shown an action row for the run and the run has since returned to working. That is the recovery the docstring protects.
  • Deliver when a run reaches a terminal state without the reader having been shown an action row for it, such as a working run withdrawn or discarded by another actor.
  • Hold back a start (dispatched or working with observe), a row whose state equals the judged state, a terminal state reached after the reader was shown the action row that led to it, and a run that appears and reaches a terminal state inside one settle window without asking for anything.

The judged state advances on every settled change, delivered or held back. A held-back change has been judged, and judging it again at the next attach is the replay this plan removes. The policy composes no text: it returns the event to render, so the ticker's row format and colours are unchanged. It is composed in Python because the live MCP view and an agent reading the stream need the same answer as the pane.

Done when tests/test_row_policy.py drives the policy with the measured sequences as fixtures and checks each one:

  • dispatched → working → complete → recorded, with the complete delivered before the recorded arrives, yields exactly one row, the complete.
  • working → exited-unfinished → blocked two seconds apart yields one row, the blocked.
  • blocked → wait-aged → blocked inside the window yields nothing after a delivered blocked.
  • A delivered blocked followed by working yields the recovery row.
  • dispatched → withdrawn → withdrawn yields nothing.
  • A run withdrawn from working with no action row delivered yields the withdrawn row.
  • A run that keeps changing state every ten seconds is delivered within two minutes of its first change.

A negative control is executed and logged: with the settle window set to zero and every change delivered, the first and third cases fail. The write paths are reckon/crew/row_policy.py and tests/test_row_policy.py.

§3 — The follower delivers through the policy

Deliverable. reckon crew follow passes every transition through the §2 policy before it reaches the pane, in the generator _follow_watch_lines in reckon/cli.py, so the same rows go to a session host's follower and to a Monitor fallback. A held row is released by the follower's wait pass when its window elapses, not only when the next transition arrives, so a lone completion is never stuck behind a quiet fleet. The judged state is persisted beside the existing delivered record that note_delivered writes through runs.write_delivered, so a restarted or re-armed follower resumes judging where the last one stopped. A new --all flag bypasses the policy and delivers every row as today, for a human tailing the stream in a pane. The docstring's every-transition paragraph is rewritten to state the guarantee §1 gives.

Done when tests/test_follow_settled_rows.py runs a follower over a fixture stream for one session and checks three things. The stream holds one run that goes dispatched, working, complete and recorded, and one that goes working, exited-unfinished and blocked two seconds apart. The pane receives exactly two rows, the complete and the blocked. With --all the same fixture delivers all six transitions. A completion with no later transition is delivered within the window plus one poll interval. The negative control is executed and logged: with the policy call removed, the first assertion fails with six rows. The write paths are reckon/cli.py and tests/test_follow_settled_rows.py.

§4 — An attach re-announces nothing the reader has judged

Deliverable. When a follower attaches, it draws no row for a run whose current state equals the state the reader last judged. That covers a session's first arming, a host restarting its child after backoff, an in-place reload and a Monitor re-arm. Runs that moved during the gap are passed through the §2 policy, so a run that completed while nobody watched is delivered and a run that merely started is not. A first attach with no judged record draws one summary line naming the session's run counts, then one row for each run in an action state. It draws no row per working run. Under session-host delivery the dim history burst that _follow_history_burst replays from the pane's stored history is not drawn, because the Claude transcript already holds those rows. The Monitor fallback keeps it.

Done when tests/test_follow_attach_is_quiet.py attaches a follower twice to a fixture holding one working run, one unpromoted run and one run that completed between the two attachments. The first attach draws one summary line and the unpromoted row. The second attach draws only the completion, and draws no bare working row. A host-delivered follower with a stored pane history draws no history row. The negative control is executed and logged: with the judged-state comparison removed, the second attach draws a bare working row and the test fails. The write paths are reckon/cli.py and tests/test_follow_attach_is_quiet.py.

§5 — Replay the measured week through the policy

Deliverable. A measurement that feeds every producer stream under ~/.config/reckon/crew/watch/*.events from 2026-10-05 to 2026-10-08 through the merged policy, one session at a time, and reports, per session and in total:

  • the rows today's follower would deliver and the rows the policy delivers;
  • every settled action state the policy held back, which must be none;
  • the longest delay between a transition into an action state and its delivery.

The report is written to the run directory and summarised in the landing record. It reads the streams and writes nothing beside them.

Done when the report shows at least half of today's rows removed, zero held-back action states, and no action row delayed more than two minutes. As a positive control, the same replay with the window at zero reproduces today's row count within 2%.

§ Decisions

Does a dispatch produce a row when its worker starts?

The lead's direction on 2026-10-08: dispatched → working rows are not needed. The dispatch call already returned the launch, and a launch that fails reaches stalled, launch-failed or withdrawn, which the policy delivers.
