§1 — Why: a row is a turn, and most rows ask for nothing

Each line the follower prints reaches the coordinating session as a notification, and each notification can open a turn. The session host from a-follower-lives-as-long-as-its-session keeps that stream open for the whole session, so the stream's density is now the main cost of watching a fleet. The lead reads the same lines in the same transcript, so a row that wastes the coordinator's turn also costs the lead attention.

On 2026-10-08 the lead asked for the stream to carry important transitions and to drop start-up flap and rapid transitions: a dispatch should not produce dispatched → working, a bare working and an exit row in quick succession. The measurement below is the case for doing that, read from every Claude Code transcript under ~/.claude/projects with a Monitor event notification since 2026-10-07 (14 sessions, 2,676 notifications, 3,128 rows) and from the producer streams under ~/.config/reckon/crew/watch/*.events since 2026-10-05 (6,825 transitions over 2,027 runs).

About three rows in five ask for nothing. The producer stream also shows the rapid transitions directly. A run reaches a settled state through a chain of rows written seconds apart: exited-unfinished → blocked within 2 s, blocked → wait-aged → blocked within 3 to 8 s, working → stopped → discarded within a median 18 s. The stream also carries rows whose state does not change at all (withdrawn → withdrawn, recorded → recorded, working → working). Session 9cf43820 received dispatched → working at 02:50:15 and then a bare working for the same run at 02:53:00. That was the replay of a follower its host had restarted at 02:52:42. Session 184d1501's first plugin batch at 02:34:36 replayed rows stamped 11:55 and 12:07 the day before.

The producer already says which rows ask for something. Every transition carries a recovery verb: observe on 2,125 of 2,125 rows into working and 268 of 275 into withdrawn, an empty verb on every terminal record, and promote, review, decide, resume, wait, investigate, repair or redispatch on every row that needs the coordinator.

The follower already filters. RowPolicy in reckon/crew/ticker.py holds the three noise pairs NOISE_PAIRS names (launch flicker, first-commit exit phantom, stall flap), folds same-state rewrites into the counter block, and collapses a launch's arrival into its first transition. PaneRowPath wraps it for the follower through follower_row_path, and replay_row_policy drives the same class for a measurement. transition_class sorts each kind into coordinator duty, observer context or counter, after the 2026-09-25 follower signal audit. That audit decided observer context should still print, as the rows a reader needs to follow progress, and crew-observability-truth reduced a launch to one dispatched → working row on 2026-10-04. The rows above are what that policy lets through. Starts, terminal echoes and attach re-announcements are observer context, and the gap replay (_follow_gap_rows) still let 446 bare rows through. This plan changes one decision in the existing policy: on the coordinator's pane, observer context is held back. It adds no second policy.

crew_follow's docstring in reckon/cli.py says every transition is delivered and that no option narrows to action states, because hiding a recovery hides the news a reader is waiting for. This plan keeps that guarantee in a different form. Every change that asks for action or reverses an action row the reader was shown is delivered, and only rows that ask for nothing and reverse nothing are held back. The producer's log keeps the complete stream for a human.

The active plan a-follower-keeps-your-work-in-view proposes a needs-you line on a ten-minute cadence. Under host delivery that is a turn every ten minutes per session whether or not anything changed. Its owner should weigh this plan's measurement before building that cadence. Nothing here edits that plan.

§2 — One row policy decides what a follower delivers

Deliverable. RowPolicy in reckon/crew/ticker.py holds back a row that transition_class classes as observer context instead of printing it, with two exceptions that print:

  • A recovery: the run leaves a state whose coordinator row this pane printed, for a non-terminal state such as working.
  • An unexplained end: the run reaches a state in SETTLED_STATES without this pane having printed a coordinator row for it since its arrival. SETTLED_STATES gains withdrawn and discarded, which a run also does not leave, so the one owner of "a state a run does not leave" covers them and HIDDEN_AT_ATTACH derives from it as before.

An arrival that resolves into an observer kind, the launch's dispatched → working, prints nothing. An arrival still sitting in dispatched at ARRIVAL_WINDOW prints as today. A kind outside COORDINATOR_KINDS counts as coordinator when its event's recovery_classification is in ACTIONABLE_RECOVERY_CLASSIFICATIONS in reckon/crew/recovery.py, the owner of "needs the coordinator", so working → exited-unfinished and its kin print without the audit's list being grown by hand. A coordinator row followed by another transition of the same run within a twenty-second settle window prints only the later row, so the measured chains (working → exited-unfinished → blocked in 2 s, blocked → wait-aged → blocked in 3 to 8 s) print once. The settle window is one module constant beside ARRIVAL_WINDOW; it is the only definition §2 adds, because a hold needs a length and the existing windows each belong to one named noise pair. No row is held more than two minutes from its first transition. A pane built with observer context shown keeps today's behaviour exactly, which replay_row_policy uses for §5's comparison. PaneRowPath writes its memory only for printed rows, as it does today, and a held-back observer row is held back again when a re-arm re-derives it.

Done when tests/test_row_policy_holds_observer_context.py feeds RowPolicy the measured sequences and checks each one:

  • arrival, dispatched → working, working → complete, complete → recorded prints exactly one row, the complete.
  • working → exited-unfinished → blocked two seconds apart prints one row, the blocked.
  • A printed blocked followed by blocked → working prints the recovery.
  • arrival then dispatched → withdrawn twice prints nothing.
  • A working run whose next row is working → discarded prints the discarded.
  • A run changing state every ten seconds prints within two minutes of its first change.
  • With observer context shown, the first sequence prints the rows it prints today.

A negative control is executed and logged: with the observer hold removed, the first case prints three rows and fails. tests/test_a_dispatch_is_one_row.py and tests/test_follower_prints_only_policy_rows.py assert today's launch row and are updated to the held-back behaviour in the same change; every other test that imports RowPolicy or PaneRowPath passes unchanged. The write paths are reckon/crew/ticker.py, tests/test_row_policy_holds_observer_context.py, tests/test_a_dispatch_is_one_row.py and tests/test_follower_prints_only_policy_rows.py.

§3 — The follower delivers through the policy

Deliverable. The follower, armed by a session host or the Monitor fallback alike, prints through §2's coordinator pane, and a held row whose settle window elapses is released by the follower's existing wait pass through PaneRowPath.flush, so a lone completion is never stuck behind a quiet fleet. No option is added to crew follow: a human who wants every row reads the producer's log, which already prints each one, so the full stream needs no second surface. The docstring paragraph of crew_follow that says every transition is delivered is rewritten to state the guarantee §1 gives and to name the producer's log as the full stream.

Done when tests/test_follow_settled_rows.py runs a follower over a fixture stream for one session holding two runs. The first goes dispatched, working, complete and recorded. The second goes working, exited-unfinished and blocked two seconds apart. The pane receives exactly two rows, the complete and the blocked. A completion with no later transition is delivered within the settle window plus one poll interval. A negative control is executed and logged: with the follower building its row path with observer context shown, the first assertion fails. The write paths are reckon/cli.py and tests/test_follow_settled_rows.py.

§4 — Find the path that re-announced a delivered run

Deliverable. An investigation of the 446 bare rows of §1. They carry no arrow, are re-announcements of a state already delivered, and got past _follow_gap_rows, which drops a run whose recorded state equals its current one, and past the RowPolicy.seed memory a re-arm restores. One measured case: session 9cf43820 received dispatched → working for dispatch-module-split-moved at 02:50:15 on 2026-10-08, then a bare working for the same run, stamped 02:50:15, at 02:53:00. Its session host had started a new follower child at 02:52:42. The investigation finds why that child re-announced the run, whether through a resume mode that fell back to a fresh baseline, a delivered record missing the run, or a seed the child never read. It counts how many of the 446 rows that path explains, by session and by delivery (host child restart, Monitor re-arm, in-place reload). §2 holds back a bare working row as observer context, but a bare unpromoted or blocked row is coordinator context and §2 does not stop it, so the path matters after §2 lands.

Done when the report written to the run directory names the function and branch that drew the 02:53:00 row, reproduces it in a logged command against a fixture follower whose delivered record holds the run at working, and gives the count of §1's bare rows that branch explains. The repair, if the report finds one owed, is added to this plan as a new section with that reproduction as its negative control.

§5 — Replay the measured week through the policy

Deliverable. A measurement that feeds every producer stream under ~/.config/reckon/crew/watch/*.events from 2026-10-05 to 2026-10-08 through the merged policy with replay_row_policy, one session at a time, and reports, per session and in total:

  • the rows today's follower would deliver and the rows the policy delivers;
  • every settled action state the policy held back, which must be none;
  • the longest delay between a transition into an action state and its delivery.

The report is written to the run directory and summarised in the landing record. It reads the streams and writes nothing beside them.

Done when the report shows at least half of today's rows removed, zero held-back action states, and no action row delayed more than two minutes. As a positive control, the same replay with the window at zero reproduces today's row count within 2%.

§ Decisions

Does a dispatch produce a row when its worker starts?

The lead's direction on 2026-10-08: dispatched → working rows are not needed. The dispatch call already returned the launch, and a launch that fails reaches stalled, launch-failed or withdrawn, which the policy delivers.
