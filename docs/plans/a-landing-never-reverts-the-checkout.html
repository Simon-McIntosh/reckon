§1 — Find what turned nova's checkout back below its landing commit

Why. On 2026-10-18 nova's lead asked reckon to root-cause and fix a promotion that committed its landing and then left nova's shared checkout holding a staged reversal of that same commit. The facts, as reported by the nova session that found it and as read from nova's repository the same evening:

  • Afterwards docs/plans/converged-forward-solve.html was staged as modified, with its index and working tree both at plan-version 395 and without the promotion's comment, while HEAD held 396 and the comment. Three files the commit added were staged as deleted and absent from disk while present in HEAD: docs/state/nova/reviews/run/r-20261018T145203666018-census-proposal-coverage/legacy-5ef79bad605b.json, docs/state/nova/reviews/run/r-20261018T145203666018-census-proposal-coverage/r-20261018T171142922335-review-of-census-proposal-coverage-f7ed7e9d8ef6.json and docs/state/nova/runs/r-20261018T171142922335-review-of-census-proposal-coverage-f7ed7e9d8ef6.json.
  • No .git/index.lock and no reckon process held the checkout afterwards. The next promotion re-synced the plan file but not the three deleted paths; the nova session restored those from HEAD with its lead's approval.
  • nova's .git/FETCH_HEAD is stamped 19:23:57.9, five seconds after the landing commit. It was written by that session's git pull --no-rebase, run in the same checkout from 98dci4-clu-2002 and followed by a git merge --no-commit that refused, citing those paths as local changes. The producer seat runs on 98dci4-srv-1006, on the same GPFS checkout.
  • That session's record of the two commands, with the pull's output cut to its last line by a tail -1: the pull printed Already up to date., and the reflog shows no entry from either command. The merge, run a second or two later, refused (Merge with strategy ort failed.) with all four paths on one line of tracked local changes, not as untracked files it would overwrite. Immediately after, git diff --cached --name-only listed all four as staged, the three new files as deletions. So the revert was complete by about 19:23:59, before either command wrote anything.
  • The run's directory under ~/.config/reckon/crew/runs/ holds no landing failure record. Its classification.json is stamped 19:24:01, and its live pointer is gone.

What the code shows. The reverted state is exactly what _restore_landing_writes (reckon/crew/promotion_scope.py:1672) leaves when it runs while HEAD still resolves to the commit before the landing. Its git restore --source=HEAD --staged --worktree (line 1700) returns a tracked path to that commit's content in both the index and the working tree. For a path the landing created, that restore fails, and _restore_one_landing_write finds no HEAD:<path> (line 1734), drops the index entry (line 1737) and unlinks the file (line 1741). Run after HEAD carries the landing commit, the same calls change nothing. So either a rollback read a HEAD that did not yet carry the commit that then landed, or another actor produced the same state. Three candidates, none confirmed:

  • reckon's own rollback running against the pre-landing HEAD. It is reached from a refused stage or commit in _commit_landing_writes (lines 1953 and 1980), from a refused review-record store in reckon/crew/promotion.py:1334, and from a refused release in reckon/crew/promotion_release.py:615 and :646. One way to reach it is a second promotion of the same run racing the first. The reverted run's ledger row carries promoted_by: review-self, so the review sweep's promote_review_run_itself promoted it (reckon/crew/recovery_review_acceptance.py:416). That sweep confines itself to one session only when its process holds a follower registration (_sweeping_session, reckon/crew/recovery_repair_dispatch.py:1000). Any other sweeping process handles every session's review runs, so two sweepers, for example on two hosts, can promote one review run at once.
  • A peer's git command acting on an index it read before the landing. git pull reads the index and HEAD before it fetches, and when HEAD has moved by the time the fetch returns it tries to fast-forward the working tree from the HEAD it started on ("fetch updated the current branch head").
  • Another path, in reckon or outside it, that restores files from a snapshot rather than from HEAD.

Whichever candidate §1 confirms must also explain one fact. 2321fba57 carries the landing's content, so the commit read its paths from the working tree before the revert. A git commit on the shared index holds that index's lock from reading its paths until after it moves HEAD, and git restore --staged needs the same lock. So if reckon's rollback is the actor, the commit and the restore did not contend for one lock. For example, the committing process used another index file, or two promotions of this run interleaved their stage, commit and rollback steps. The pull's printed Already up to date. does not rule out its fast-forward, because a pull prints it after fast-forwarding too, and the lines before it were cut.

Deliverable. A read-only investigation that writes docs/research/what-turned-a-landing-back.html and the script that reproduces its finding, scripts/reproduce_landing_reversion.py. It reads these sources: nova's HEAD reflog and the stamps on its .git files; the run directory of r-20261018T171142922335-review-of-census-proposal-coverage-f7ed7e9d8ef6; the logs of the producer, watcher and admission services on 98dci4-srv-1006 for 19:23 to 19:25; the nova session's own record of its pull and merge, which that session offered; and the promotion code above. From them it names the process and the call, with file and line, that changed nova's index and working tree after 2321fba57 landed. If the records cannot separate the candidates, it says which remain and names the record that would have separated them. §3 then adds that record wherever §2 does not already keep it.

It changes no product code.

§2 — A landing checks what it left at its paths and records every rollback

Why. Whatever §1 finds, nothing in reckon looked at nova's checkout after this landing, and no record says whether a rollback ran. A rollback's per-path report travels only on the exception _landing_refusal raises (reckon/crew/promotion_scope.py, LANDING_ROLLBACK_ATTRIBUTE), and the receipt it feeds is printed once to whoever ran the promotion. The ledger cannot hold it either, because the ledger row is one of the writes a rollback takes back. So the landing must check its own result and write what it did where it survives. A check made only at the instant a landing returns would not have seen this incident, though: the commit landed at 19:23:52 and the revert was complete about seven seconds later. So a landing also checks, before it stages, whether an earlier landing's paths have been staged back.

Deliverable. One owner first, then the checks. Promotion's other three landings call _commit_landing_writes (reckon/crew/promotion_scope.py:1916), from reckon/crew/promotion.py:751 and :1350 and reckon/crew/promotion_gate.py:960. The release-outcome commit in _record_release_on_ledger (reckon/crew/promotion_release.py:569) repeats that sequence inline instead (lines 611 to 650: stage, a no-change short-circuit, commit --only, rollback). It is routed through _commit_landing_writes with its own subject and body. _commit_landing_writes gains the release path's no-change rule: when staging leaves nothing changed at the paths, it returns without committing rather than refusing. The checks below are then written once, in _commit_landing_writes. Both build on the comparisons that file already owns, _path_differs_from_head (line 1482, HEAD against the working tree) and _path_has_a_staged_change (line 1747, HEAD against the index). The check after the commit extends those two to return the blob ids its report carries. The reversal check before staging needs one comparison neither computes, the staged blob against the blob the landing commit's parent held, and it is added beside them in the same file.

  • A check before every landing stages. Before it stages anything, a landing reads the paths staged in the shared index (git diff --cached --name-only). For each one it finds the newest commit that wrote that path. The path is a staged reversal when that commit is a reckon landing, with a promote( or release( subject, and the staged content is exactly what the path held in that commit's parent, or the path is staged as deleted and the parent did not have it. Every staged reversal is reported with the commit it reverses: on the landing result as landing_check.reversals, on the receipt, on stderr and in landing.json. It is reported and never repaired, because restoring it would write to an index other sessions share. Unstaged changes are not checked, because an uncommitted edit to a landed plan file is ordinary peer work. In nova's incident this check would have fired at the next promotion, at 19:37:06, naming 2321fba57 and all four paths.
  • A check after every landing commit. It catches a revert made inside the landing's own process. Once the commit returns success, read each written path's blob in HEAD, in the index and in the working tree, once. Every path that differs is reported: the landing result carries landing_check with ok and the mismatched paths, each with its three blob ids. The promotion's receipt carries that field, and the promotion prints the mismatched paths on stderr. A mismatch does not roll anything back and does not change the exit status, because the commit has landed and a re-promotion would duplicate it.
  • A record of every refusal and rollback. Every refused landing writes landing.json in the run's directory (run_dir(run_id)), one entry per attempt, appended rather than overwritten. An entry holds the attempt's time, the step that refused (stage, commit or review-record store), git's message, the HEAD each rollback read before restoring, and the rollback's per-path report. A successful landing appends its commit, the HEAD before it, and its landing_check. The write is best-effort: a run directory that cannot be written is reported on the receipt, and it does not replace the landing's own outcome.

Nothing else changes: the rollback still restores what it restores today, until §3.

§3 — The path §1 names can no longer leave a written path behind HEAD

Why. This is the fix at source nova's lead asked for. It is deferred until §1 names the mechanism, because the three candidates call for different fixes.

  • If reckon's rollback ran against the pre-landing HEAD, the rollback captures the HEAD the landing started on before it stages anything. It restores only while HEAD still resolves to that commit. When HEAD carries the landing commit, it restores nothing and reports the landing as committed.
  • If a peer's git command rewrote the index and working tree, reckon cannot stop that command. Then the fix is what reckon owns: §2's check sees the result, and the shared-checkout guidance names the command and the safe form.
  • If another reckon path restores from a snapshot, that path gets the same guard as the first case.

What §1 found, and what it adds. §1 names a second promotion of the same review run, running beside the first, as the leading candidate. Run at the landed HEAD, the rollback changes nothing, so it must have read the pre-landing HEAD while the first promotion's commit was still to come. §1 could not separate that from a path that restores files from a snapshot, because no record kept today would show the difference. promotion.complete already holds _pointer_lock for its whole span (reckon/crew/promotion.py:197, defined at reckon/crew/runs.py:316). But that lock is a blocking flock, and flock is node-local on this home, as measured in a-seat-held-elsewhere-is-not-restarted §8. So two promotions of one run on two hosts run at once: nova's producer seat on 98dci4-srv-1006 and a review sweep on 98dci4-clu-2002, both reaching complete through promote_review_run_itself (reckon/crew/recovery_review_acceptance.py:331). That makes the leading candidate a concrete, reachable interleaving, and it is the one this section removes. It is still not confirmed by a record. §2's landing.json now records the HEAD each rollback read, so a recurrence will confirm it or rule it out. If a recurrence shows a rollback with no second promotion behind it, the snapshot-restoring branch is planned then. This section adds no condition to the rollback. A guard that restored only while HEAD still resolved to the landing's starting commit would not have stopped this interleaving, because the second promotion's rollback read exactly that commit. It would also block a legitimate rollback after an unrelated peer commit moved HEAD.

Deliverable. A promotion holds a claim on its run that excludes other hosts as well as other processes, for its whole span. The claim is a HostLease (reckon/crew/host_lease.py) named for the run: it claims by an atomic link, names its holder's host, pid and job, and is taken over once its holder stops renewing. No new lock mechanism is written.

  • The promotion takes the lease before its first write (the ledger row, the plan comment or a review record) and releases it after its landing or rollback. It renews the lease while it runs, so a slow landing on a congested shared filesystem is not taken over mid-landing.
  • A promotion that finds the lease freshly held by another holder refuses at once without writing, naming the holder's host, pid and job.
  • A lease whose holder has stopped renewing past the stale window is taken over, and that promotion proceeds.
  • The node-local pointer lock stays for the pointer's own read-modify-write. promote_review_run_itself reaches complete, so it inherits the claim. A sweep that finds the lease held reports a refused self-promotion naming the holder, not an error.

Write paths. reckon/crew/promotion.py, reckon/crew/host_lease.py, reckon/crew/recovery_review_acceptance.py, and tests/test_one_promotion_of_a_run_at_a_time.py, which is new.

Negative control. At the base revision, a second promotion that does not share the first's node-local lock, as on another host, proceeds and writes. So the new test's cross-host case fails by id.
