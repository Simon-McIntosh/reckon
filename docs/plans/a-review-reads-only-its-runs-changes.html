§1 — Why: a review sized at 670k tokens for a few hundred lines of change

Run r-20261106T134041653278-stop-only-its-own-run-when-a-run-record-is-damaged (the-crew-home-has-a-bound §12) was resumed on 6 November with advice to merge origin/main into its worktree so it could reproduce a regression on the merge candidate; it did (fc7f245289 merge: incorporate current main) and then committed its fix. Its dispatch base is fc5a7fb2b2, and git diff fc5a7fb2b2..HEAD now spans 160 files, 122,334 inserted lines and 4.8 MB, nearly all of it main's own work. The review reflex refused to compose its review eight times, the last at 09:13:20Z on 7 November: “context-window-exceeded: estimated 670392 usable input tokens against a 230144 token window”, while the files the refusal names sum to under 50k tokens. The obligation row meanwhile read “the review reflex owns this dispatch” for 48 minutes (that misreport is the-monitor-shows-the-work-it-watches §114). Re-exec §3, queued behind this run, waits with it.

A run's changes are the commits it authored, not everything reachable from its head that its base lacks. After a mid-run merge the range that isolates the run's own work is origin/main...HEAD, the diff from the merge base of the head with the integration branch: on this run it gives 6 files and 320 insertions. The three-dot form off the dispatch base, <base>...HEAD, does not help, because the dispatch base is itself the merge base, so it returns the same 160 files as the two-dot range. The run's armed baseline keeps naming the dispatch base, which is correct for the suite measure; only what the review reads and is sized on is wrong.
