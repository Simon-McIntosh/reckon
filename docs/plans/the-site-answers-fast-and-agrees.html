§2 — A plan's progress is its sections' done share, weighted by effort

Why. §1's third row. Two readers of one plan report different figures, and the lead locked one measure for every surface (decision progress-measure below). The current rule in derive_impl_with_source (reckon/_plan_html.py), shipped by the-portfolio-reads-true §2, weights by effort only when every declared section has a record with hours, and otherwise counts. The lead's rule imputes instead.

Deliverable. One function computes a plan's progress, and every reader of a plan calls it:

  • The denominator is the sections declared done or implementable; deferred sections are excluded.
  • Each section weighs its record's effort_hours. A section with no hours takes the mean of the sections that have them. When none has hours, every section weighs the same, which is the count.
  • A plan with no declarations keeps its authored plan-impl.
  • impl_source reads computed when any hours were used, declarations for the count, and authored for the fallback.
  • The light reader that builds discovery rows derives from the declarations in its head metadata even when the document carries no section records, so discovery and the parse report the same figure.

Done when a test under tests/ parses temporary plans covering five cases:

  • All sections have hours: the effort-weighted share.
  • Partial hours: s1 done at 2 h, s2 implementable without hours, s3 implementable at 4 h. s2 is imputed 3 h, so progress is 2/9.
  • No hours: the count.
  • No declarations: the authored figure.
  • Declarations with no records: the light reader and the parse give the same value.

The negative control makes the light reader skip the declarations again, and the last case then fails. The test files importing reckon/_plan_html.py show no added failure against base. That includes tests/test_impl_derives_from_declarations.py, whose covered-case expectation this rule supersedes, so it is edited to the new rule. ruff check and ruff format --check add no findings on the changed Python files. Every log sits under the run directory and ends in EXIT=, and the suite runs on the fleet allocation, not the login node. Write paths: reckon/_plan_html.py, tests/test_impl_derives_from_declarations.py and the new test file.

§4 — A reader on another cache format never evicts the served one

Why. §1's first row. Every process that reads a project writes one shared file per project under ~/.config/reckon/cache/metadata-index/, named by project and docs path only. A process on another format version finds the file incompatible, rebuilds and overwrites it, and the next reader on the other version does the same. The served process pays 17 to 26 s each time.

Deliverable. One function owns the path of a persisted cache under _config_home()/cache/, and that path includes the writer's format, so processes on different formats keep separate files and none evicts another. All four caches that share the defect use it: the metadata index (_index_path in reckon/metadata_index.py), the git creation map (_git_creation_cache_path), the git last-modified map (_git_last_modified_cache_path, both in reckon/serve.py) and the compliance store (_store_path in reckon/compliance.py). A same-format reader still reuses its file as today.

Done when a test runs two writers with different format versions over one temporary project, alternating three times, for each of the four caches. Each writer's second and third reads reuse its own file without a rebuild. Nothing logs Ignoring incompatible metadata index or the other caches' equivalent rejection. The negative control removes the format from the shared path function, and the rebuild count then rises for all four. Tests importing the three changed modules show no added failure against base. Every log sits under the run directory and ends in EXIT=, and the suite runs on the fleet allocation, not the login node. ruff check and ruff format --check add no findings on the changed Python files. After the served process carries the change, a 20-minute watch of the cache directory and the server log records no incompatible-cache line. Write paths: reckon/metadata_index.py, reckon/serve.py, reckon/compliance.py and the test file.

§5 — A request is answered from the last computed result, never behind a recompute

Why. One Python process derives and serves. A cold discovery, a rollup (7 to 17 s), a compliance pass (2.2 to 2.7 s) or a velocity capture (10.5 s) holds the interpreter while it runs, and every other request, including trivial ones, waits beside it.

Deliverable. /_checks/<project> already recomputes outside the request path. _start_check_refresh and _spawn_check_refresh in reckon/serve.py start a niced child per project, single-flight through _CHECK_REFRESHES, which writes the store the route reads. That mechanism is generalised from one route to four: /_discover/<project>, /_projects/index.json, /_checks/<project> and /crew/velocity. No new module is added. Its interface is three functions, keyed by route and project:

  • compute, the child's entry point, which writes the route's stored result;
  • read the last result, which a request answers from, with the result's age in a response header;
  • spawn on change, single-flight per route and project, started when the route's inputs change.

A request waits only when no result exists yet. A result that changes is pushed over the existing /_changes/<project> stream. Retired: the inline computation of the three new routes on the request path, and the compliance-only names of the refresh machinery, which becomes the one generic instance.

Done when a test forces a cold recompute of a temporary project's discovery. While it runs, a trivial request answers in under 50 ms and the derived endpoint answers from the prior result with an age header. The negative control computes inline, and the trivial-request bound then fails. On srv-1006, after the served process carries the change, ten minutes of ordinary fleet activity are logged with §9's durations, and every derived endpoint answers under 1 s at the 95th percentile. Tests importing reckon/serve.py show no added failure against base, and the same ruff, log and allocation terms as §2 hold. Build it after §4 and §9 merge, since §9 supplies the durations this measures. Write paths: reckon/serve.py, a new module beside it for the recompute, and the test file.

§ Decisions

What does a plan's progress bar mean, everywhere it appears (plan list, graph, crew flow, fleet home)?

The lead chose the effort-weighted share. Where no section carries hours it falls back to the count. Where some do, the missing hours are imputed with the mean of the present ones. A figure derived from sections cannot drift the way a hand-set impl did (twelve of nova's thirty sectioned plans off by 25 points or more). Weighting by effort reads closer to the work left than a count does. The coordinator's own calls, which the lead can revisit: a plan with no declared sections keeps its authored impl , and every roll-up (graph endpoint, fleet home) applies the same weighting over member plans' hours.
