§2 — A plan's progress is its sections' done share, weighted by effort

Why. §1's third row. Two readers of one plan report different figures, and the lead locked one measure for every surface (decision progress-measure below). The current rule in derive_impl_with_source (reckon/_plan_html.py), shipped by the-portfolio-reads-true §2, weights by effort only when every declared section has a record with hours, and otherwise counts. The lead's rule imputes instead.

Deliverable. One function computes a plan's progress, and every reader of a plan calls it:

  • The denominator is the sections declared done or implementable; deferred sections are excluded.
  • Each section weighs its record's effort_hours. A section with no hours takes the mean of the sections that have them. When none has hours, every section weighs the same, which is the count.
  • A plan with no declarations keeps its authored plan-impl.
  • impl_source reads computed when any hours were used, declarations for the count, and authored for the fallback.
  • The light reader that builds discovery rows derives from the declarations in its head metadata even when the document carries no section records, so discovery and the parse report the same figure.

Done when a test under tests/ parses temporary plans covering five cases:

  • All sections have hours: the effort-weighted share.
  • Partial hours: s1 done at 2 h, s2 implementable without hours, s3 implementable at 4 h. s2 is imputed 3 h, so progress is 2/9.
  • No hours: the count.
  • No declarations: the authored figure.
  • Declarations with no records: the light reader and the parse give the same value.

The negative control makes the light reader skip the declarations again, and the last case then fails. The test files importing reckon/_plan_html.py show no added failure against base. That includes tests/test_impl_derives_from_declarations.py, whose covered-case expectation this rule supersedes, so it is edited to the new rule. ruff check and ruff format --check add no findings on the changed Python files. Every log sits under the run directory and ends in EXIT=, and the suite runs on the fleet allocation, not the login node. Write paths: reckon/_plan_html.py, tests/test_impl_derives_from_declarations.py and the new test file.

§5 — A request is answered from the last computed result, never behind a recompute

Why. One Python process derives and serves. A cold discovery, a rollup (7 to 17 s), a compliance pass (2.2 to 2.7 s) or a velocity capture (10.5 s) holds the interpreter while it runs, and every other request, including trivial ones, waits beside it.

Deliverable. /_checks/<project> already recomputes outside the request path. _start_check_refresh and _spawn_check_refresh in reckon/serve.py start a niced child per project, single-flight through _CHECK_REFRESHES, which writes the store the route reads. That mechanism is generalised from one route to four: /_discover/<project>, /_projects/index.json, /_checks/<project> and /crew/velocity. No new module is added. Its interface is three functions over one key per stored result. Discovery and the checks summary are keyed by route and project. The fleet rollup /_projects/index.json is keyed by route alone, because collect_projects reads every mount into one result. Velocity is keyed by project and the normalised query, as set out below.

  • compute, the child's entry point, which writes the route's stored result;
  • read the last result, which a request answers from, with the result's age in a response header;
  • spawn on change, single-flight per key, started when the route's inputs change. Changes in several projects therefore start at most one fleet-rollup child.

A request waits only when no result exists yet. A result that changes is pushed over the existing /_changes/<project> stream. A project-scoped result goes to that project's stream. A fleet-scoped result goes to every open stream as one fleet event naming its key: the rollup each time it changes, and a velocity key spanning every project once, when its computation completes. The refresh runs in a child process, which cannot reach the parent's streams, so the parent publishes its result: for each running child the parent keeps one waiter thread, and when the child exits having stored a fleet-scoped result, the waiter records that key's new version and wakes every open stream through the fleet watch's wake pipes. Handler._send_project_changes, when woken, compares each fleet key's version with the one it last sent and writes one fleet event for each that moved, even when its own project's rows are unchanged. watchProjectStateChanges in docs/ui/state-loader.js keeps calling its onChange callback as today and also dispatches each fleet event on window as a reckon-fleet event carrying the key. VelocityView in docs/ui/velocity.jsx listens for reckon-fleet while it shows the computing state, and re-requests when the event names the key it is computing. §6's home view consumes the same event. Retired: the inline computation of the three new routes on the request path, and the compliance-only names of the refresh machinery, which becomes the one generic instance.

Who starts each refresh. Four callers compute on the request or stream path today, and each moves behind a stored result. Handler._send_project_changes calls discover_plans inline for its first frame and for every later one; it reads the stored discovery instead and spawns only on a miss; spawning on a change belongs to _FleetChangeWatch alone, below, so one owner starts each change-driven refresh. /_checks/<project> calls compliance.project_checks on the request; it answers from the stored summary, and its pending-document spawn stays as that route's trigger. /_projects/index.json and Handler._serve_velocity compute on the request; each answers from its stored result instead. The rollup spawns on a miss or a change. Velocity spawns on a miss, and for the default window also when its stored result is older than the refresh interval; a result stored under an explicit window never changes. _FleetChangeWatch keeps its job of invalidating and waking streams, and it also calls spawn-on-change for the project whose inputs moved and for the fleet rollup's one key. It computes nothing itself.

The velocity key. A stored velocity result is keyed by project and by the normalised query (since, until, fields, limit and cursor), not by route and project alone. A request naming no window takes the moving default window, stored under one key per scope rather than one per interval. It is answered from the newest stored default-window result, with an age header, and spawns a refresh when that result's window ends more than the refresh interval, 15 minutes, before now; so a default-window request never waits behind a recompute, whenever it lands. A request naming since or until is keyed by its exact window. At most one computation runs for a velocity scope at a time, so a refresh still running is never started a second time. The all-project view took 605.8 s on the fleet node on 2026-10-19 (§8's evidence), so its first request also answers without waiting. The route returns 202 with the refresh started and a Retry-After header. VelocityView in docs/ui/velocity.jsx, which today fetches once per scope and window and treats any 200 as final, renders a computing state on a 202. It asks again after the stated interval until a 200 arrives, or at once when a fleet event announces that key's completion, and never renders a pending answer as an empty pane.

Done when a test forces a cold recompute of each of the four routes for a temporary project: discovery, the fleet rollup, the checks summary and velocity. Each route's case stubs that route's computation with a delay of at least 200 ms. While the recompute runs, the route itself answers in under 50 ms, from the prior result, with an age header. When the recompute finishes, the route answers with the recompute's own result, identified by a marker the stub writes into it, so a refresh that computes but stores nothing, or stores under another key, fails. Each case carries its own negative control, which computes that route inline under the same delay. The route's own answer then takes at least 200 ms, and the 50 ms bound fails. A velocity case asserts that two queries differing only in limit are stored and answered separately, and that a first all-project request answers 202 without waiting for the computation. A fleet-rollup case changes two projects at once and asserts that one rollup child runs; its negative control keys the rollup per project, and two children then run. A fleet-event case changes the stored rollup and asserts that a stream open on a temporary project receives one fleet event naming the rollup's key. A second case completes a first all-project velocity computation and asserts that the same stream receives one fleet event naming that velocity key. Both cases run the refresh in a child process, as production does, so the event reaches the stream through the parent's waiter. Their negative control publishes only per-project events, and both assertions fail. A test in the style of tests/test_spa_crew_cards.py asserts two things of VelocityView. It re-requests after a 202 and renders the computing state, not an empty pane. It also re-requests, without waiting out Retry-After, when a fleet event announces that the key it is computing has completed. Its negative control treats a 202 as final, and the re-request assertions fail. On srv-1006, after the served process carries the change, ten minutes of ordinary fleet activity are logged with §9's durations, and every derived endpoint answers under 1 s at the 95th percentile. Tests importing reckon/serve.py show no added failure against base, and the same ruff, log and allocation terms as §2 hold. Build it after §3 and §8 merge. §3 is the section before it in the chain that writes reckon/serve.py, and §8 makes the all-project velocity computation answer for every scope. §4, and §9, whose durations this measures, land earlier in that chain. Write paths: reckon/serve.py, reckon/change_streams.py, which holds _FleetChangeWatch once §16 lands, reckon/compliance.py, whose refresh entry point becomes the first instance of the generic one, docs/ui/velocity.jsx, docs/ui/state-loader.js and the test files.
