§1 — Where the local lane stands

clive is a site wrapper that execs an agent CLI against the local model catalog on the GPU cluster, resolving endpoint and credential itself so no secret passes through reckon. It is already a backend: reckon/_backends.py registers the command as an alias of the Claude dialect, and the host flight layer defines a clive backend pinned to deepseek-v4-flash at effort medium, defined but defaulted by nothing. The catalog currently publishes one live route, DSv4 flash on two H200s with a 512k context; GLM 5.3 is not yet served.

The lane has been measured once. Six controlled shadow pairs on 2026-08-26 put DSv4 flash against the incumbent on the same node, base and check: four passed, and on two the local model produced the better diff, keeping a test the incumbent dropped and writing twelve lines where the incumbent wrote twenty-nine. It ran about 2.3 times slower where both timings exist. Both failures were fence failures rather than capability failures: one worker never entered its worktree and wrote into the shared checkout, one did correct work and never wrote its manifest. The recorded verdict was read-only roles now, no repository write access until the declared worktree boundary is enforced. That verdict is the shape of this plan: the model is not the constraint, the harness around it is.

Meanwhile the incumbent has accumulated the evidence base the routing rules were waiting for. The ledgers across four mounted projects hold 2,201 promoted gpt-5.6-sol runs at medium and high effort, against the 58 runs the current effort priors were set from. The two questions this plan settles, local lane and default routing, are the same question asked of the same ledger.

§8 — Effort is not a dial on these models, and the harness pretends it is

Measured against the endpoint directly, 2026-09-02. The routing origin serves both releases and accepts the Anthropic Messages API. Asking each model the same question at four thinking budgets — none, 1024, 4096 and 16000 tokens:

Every call returned a thinking block, including the ones that requested no thinking at all, and the budget moved the depth by nothing on flash and by noise on GLM. So thinking is intrinsic to these checkpoints rather than gated by the API, and budget_tokens is accepted and ignored. The wrapper agrees: it declares SUPPORTED_CAPABILITIES="thinking" unconditionally for whichever release it selects.

The consequence for routing is that the local lane has no effort dimension at all — not the two levels one might expect, but zero. A pinned effort on the clive backend is a client-side fiction: it changes what the harness asks for and nothing the server does. Three things follow. The earlier reading that the lane had been "running with its reasoning switched off" at medium is retired for a second time and by a stronger instrument than the one that retired it first. The thinking_tokens counter the harness reports is not merely unreliable, it is measuring a request rather than a response — a smoke test that wrote its file correctly reported thinking_tokens: 0 while the endpoint emits thinking on every call. And a shadow pair that substitutes effort on a local model is not a controlled comparison of anything; only backend, model and prompt are real variables here.

So pin the local backends' effort to one declared value and stop treating it as a calibration axis, record in the flight comment that the server ignores it with this measurement as the reason, and keep the ledger's effort field as a record of what was requested rather than of what ran.

§2 — GLM 5.3 beside DSv4 flash

A second local model is a second backend entry, not a code change. When the catalog publishes the GLM 5.3 release, the host flight layer gains clive-glm with command: clive, the release id as its model (the wrapper accepts --model RELEASE and the dialect already passes the model through), a pinned effort, budget_check off because the local endpoint publishes no headroom, and session_reuse on. Until the release is live the entry is authored and marked unavailable by the availability probe; reckon flight already reports which backends resolve, so a down model reads as down rather than as absent.

Two properties are non-negotiable and both come from the effort-routing reference. Effort is pinned on every backend: the first clive run recorded effort: null, which is exactly the unpinned-backend-effort review finding, and an unpinned row cannot enter a calibration slice. Sessions never cross models: a roster member captures one session for one configuration, so DSv4 and GLM get distinct members.

Measured 2026-09-02, and it moves what this section can deliver. clive --list publishes exactly one route — deepseek-v4-flash · 2×H200 · fp4+fp8 · 492,288-token usable input — so GLM 5.3 is not served yet and its release id does not exist to be authored. Authoring a backend entry against a guessed id would be a fabrication, not a placeholder. What is executable now is the half that makes the entry safe to add the day the catalog publishes it: the availability probe is model-blind. reckon flight resolves availability in reckon/flight.py from command_found plus an optional auth_check argument vector, and both are properties of the wrapper. A clive-glm entry naming an unserved release would therefore report available, and its dispatch would fail inside the worker rather than at the refusal. The catalog is the authority the probe is missing, so this section's executable node teaches the probe to check the declared model against the backend's own catalog and to refuse a dispatch naming an unserved one.

§6 — Write access is gated on an enforced worktree boundary

The boundary is enforced without sandboxing children, for every backend. Dispatch takes one deterministic snapshot of every registered tree — path, HEAD, a SHA-256 porcelain digest — and promotion re-inspects exactly those roots under its existing lock, refusing a run that changed the main checkout or a peer worktree, naming the path and its owning tree, before ledger append and with the pointer left recoverable. A worktree registered after dispatch is not charged; the coordinator-owned plan resource is excluded. Five cases, each strict half paired with its negative. Full suite 2,672 passed / 0 failed, commit 0226835. What now stands before local write access is the six requalification pairs — a measurement, not a missing mechanism. Full record: §6 landed.

Original section text

The worktree-full tier resolves to the harness's no-sandbox mode because an OS sandbox is inherited by child processes and breaks the test runners a gate depends on. The consequence, verified in source and demonstrated by a local-model worker, is that the worktree boundary is the worker's obedience to its prompt: one edited the shared checkout with sixty-one tool inputs naming it and none naming its worktree. That is the declared-sandbox-is-advisory-isolation review error, and it gates write access for every backend, not only this one. It lives here because the local lane is what it blocks first.

Re-verified in source 2026-09-02. The claim still holds exactly as written: sandbox_write_roots in reckon/_backends.py returns None — unrestricted — for the worktree-full tier, and the codex dialect's _sandbox_flags emits --dangerously-bypass-approvals-and-sandbox for it, with the comment already in the file giving the reason: a sandbox is inherited by child processes and would break the test runners a gate depends on. §7 — Strengthen the harness around local workers, so the model comparison is a model comparison

Both local failures to date were harness failures: a worker that never entered its worktree, and a worker that did correct work and never wrote its manifest. A weaker model exposes harness gaps that a stronger one papers over by following the prompt more reliably, which means the harness is the first thing to fix and the last thing to blame on the model. It also means GLM 5.3 and DSv4 flash must be compared under the same harness, or a difference in obedience will be read as a difference in capability. GLM may well outperform DSv4 here; the harness has to be good enough for the ledger to show it.

Four strengthenings, each a check bound to a moment that always happens:

  • Orientation is verified before work starts. The composed prompt asks the worker to open its manifest with the worktree path, the base revision it sees, and its declared scope, and the first observation of the run compares them with the pointer. A mismatch is a blocked run within a minute rather than a stray write discovered at promotion; the §6 promotion check remains the backstop.
  • Delivery cannot be silent. fences.manifest_required already exists; when a run reaches a terminal event with no manifest, recovery derives a provisional one from the final message and the worktree diff, marks it derived so it never counts as delivered, and reports the gap on the run record. A correct diff with no manifest then becomes a repairable row instead of a lost node.
  • Infrastructure failures are classified, not charged. A malformed tool call, a truncated stream, or a wrapper error mid-turn is recorded as an infrastructure failure with a redispatch, and never enters the model's pass rate or trips the circuit breaker, exactly as the effort-routing reference already states for the spark lane. The dialect learns the wrapper's own error shapes from recorded streams.
  • The comparison is paired. Every GLM shadow is dispatched against a node DSv4 has also shadowed, at the same base, with the same check, under the same prompt and fences, so the two models' rows differ in one variable. The capabilities cache reports them as sibling configurations with fence failures counted beside capability failures, and a divergence in obedience shows up as a harness row before it is read as a model verdict.
  • A duration is legible against the load it was measured under. Found by running the programme rather than reviewing it. A §4 node blocked at its 25-minute fence with the work already committed, because the full suite it was told to run could not finish while four peer suites contended for the same machine; the untouched baseline alone took 814 s. Nothing in the run record distinguishes a slow model from a busy workstation, and every comparison this plan makes is a comparison of recorded durations. So record the load: at dispatch and again at completion, store the count of non-terminal runs in the same repository, and mark a fence overrun that coincided with a raised count as contended. The fence itself does not move — a bound that stretches under load stops being a bound, and the point is to make the confound visible rather than to excuse it.
  • A shadow's explicitly named effort override is detected and then not applied. Found while trying to run the local lane at the effort it should be measured at. reckon crew shadow --set backends.clive.effort=xhigh resolves the agent at the primary's effort and records lineage.configuration.substituted.effort as {primary: medium, shadow: medium, via: override} — a substitution the record asserts and the run did not make. roles.implement.effort=xhigh behaves identically. This is the same class the shadow programme has already fixed twice, one field further along: a configuration dimension that moves, or fails to move, without the record saying so truthfully. It is worse than an unsupported override, because an unsupported one refuses and this one agrees. Until it is fixed no candidate tier can be shadowed at any effort but its primary's, which blocks the whole qualification programme for a model whose whole point is that it needs a different effort from the incumbent. An override that cannot be honoured must refuse; one that is honoured must move the resolved value and say so.
  • A read-only node on this dialect cannot reliably deliver a file, and does not know it. Settled by investigation rather than argued. All three local read-only runs report permissionMode=plan at their stream's init event, and every ordinary-path Write in all three was denied — the census's manifest write included. The census delivered only because it retried the same content through Bash; both reviews stopped inside the plan workflow and ended end_turn believing they were finished. The discriminator is the tool sequence after a denial, not the role, the argv, the effort or the target root. A tier that silently withholds a node's declared deliverable is worse than one that refuses the dispatch, because the run looks successful from every angle except the missing file. Give the read-only tier a real boundary instead of a permission mode: the node must be unable to modify the repository under test and able to write the paths it declared, and a denied write must end the run loudly rather than be swallowed. This is not local-lane-specific — it governs every investigate and review node on the Claude dialect, the claude backend included.
  • Session reuse is fenced to the model and not to the effort. Found one command after the item above, by watching an argv. Re-dispatching a failed node to the same roster member at a different effort emitted --resume <prior-session> --effort xhigh: the roster stores sessions keyed by model alone, so the run inherited seventy minutes of the medium configuration's context while claiming to measure xhigh. The earlier fence that stopped sessions crossing models was right and is simply drawn one dimension too narrow — effort is part of the configuration a slice is keyed on, so a session carried across it confounds exactly the comparison the ledger exists to make, and does so invisibly because the run record shows only the effort it was launched with. Key the stored session on the resolved configuration rather than the model, so a changed effort starts clean and an unchanged one still reuses.
  • A shadow worktree path names its primary but not its candidate, so two models cannot be compared on one node at the same time. Found immediately on trying to do exactly that: the second shadow of a primary is refused with worktree path already exists, because the path is shadow-<primary-run>/<node> with nothing in it identifying which candidate is running. The qualification ladder's central act is putting two candidates against the same node at the same base, so the one measurement the programme most needs is the one the path scheme forbids. Include the candidate backend in the shadow worktree path, keeping the lineage-based reclamation that already reads a committed shadow record so the cleanup rule is unaffected. Sequential shadows of one primary do work and are the workaround, but they double the wall clock of every paired comparison and couple two measurements that should be independent.

Does the spark small-model lane stay configured for exact nodes?

Nine promoted spark runs in total, eight passed, none since 2026-08-25; the reckon project layer still routes exact nodes there; its weekly meter is at 45%.

Evidence first, routing second, for spark and for the local models alike. The spark return on experience is nine pilot runs (eight passed; the one failure was a malformed tool call classified as infrastructure, not a specification defect) at a 3.9-minute median and roughly 2.3 times cheaper output tokens than sol, but eight runs consumed about 60% of its dedicated weekly meter (about 41M input tokens, almost all cached context) and one run inherited a ten-turn sol session for 22.9M tokens before session reuse was fenced to one model. The lane buys latency and sol-budget relief, never fleet share, and nothing has routed there since 2026-08-25. So the live exact overlay in the reckon project layer is removed, the backend stays defined, and the lane earns routing back the same way the local models do: at least ten usable shadow pairs showing a gain on the same nodes, then a gated pilot, then a slice-lock. Orchestrators are steered to a cheaper lane only once the ledger shows the gain.

How does "use local workers" reach dispatch?

One declared local_backend key in the host layer names the local backend and dispatch --local resolves it, refusing when the key is unset or names an undeclared backend, so a request to use local workers fails loudly on a host with no local lane instead of silently running the incumbent. The skill text names the flag and a contract test pins it; the previous --set convention was a rule with no bound check.

When does the local lane get repository write access?

Reopened and re-locked by the lead on evidence that retires the original rationale. Three things changed since the first lock this morning. First, its own gate is half-satisfied: the §6 boundary check landed and a stray write into the main checkout or a peer worktree is now refused at promotion by test, so the incident the lock was built around — a local worker editing the shared checkout under an advisory sandbox — is caught by machinery rather than by withholding write access. Second, the failures attributed to the local lane were harness failures, not write failures: every ordinary-path Write in three read-only runs was denied because the Claude dialect maps that tier to --permission-mode plan, and a direct smoke test at worktree-full writes correctly on the first attempt. The lock was gating the wrong risk. Third, the incumbent codex account is quota-exhausted until 2026-09-08 and the claude subscription cannot absorb the fleet, so the local lane is not a candidate being evaluated at leisure — it is the only implementation lane available, and a lock that forbids using it forbids progress. The audit obligation is kept and strengthened rather than dropped: implementation nodes run on the local backend now, every one full-diff audited, with the §6 refusal as the enforced backstop and any stray write a refused promotion with evidence. The six controlled pairs remain owed as calibration, not as a gate.
