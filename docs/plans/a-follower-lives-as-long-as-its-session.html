§1 — Why: Claude Code owns the cap, and every re-arm costs a turn

A coordinator's follower runs inside the Monitor tool, and the Monitor tool ends every watch at thirty minutes. Claude Code 2.1.271 made that deliberate: its changelog reads "Changed Monitor watches to always have a deadline (at most 30 minutes; 10 in single-prompt -p runs) and notify Claude to re-arm, replacing the no-timeout persistent option". In the installed binary the cap is a server-side flag rather than a setting, so nothing reckon passes can lift it.

The shipped plan a-follower-outlives-its-monitor made the expiry survivable. The follower arms with --lifetime 29m, announces its own end one minute before Claude Code ends it, names the attach line in that final row, and replays the runs that changed during the gap when it re-attaches. Its census found 620 of 719 armed followers ending when Claude Code expired the watch. What is left is the re-arm itself: every 29 minutes the coordinator spends a turn arming the same command again, and a coordinator that misses the end row learns of it from a watcher-required refusal on its next dispatch.

The same gap affects review workers. /reckon-create dispatches a read-back review of each new plan and /reckon-edit leads to crew review-plan, so a session that only authors plans still dispatches runs whose results it must hear. A trigger tied to /reckon-build would miss them. In this plan the monitor starts with every session and does nothing until that session's first dispatch, from whichever skill or tool makes it, asks it for a follower.

Two names are kept apart below. Claude Code is the harness that runs monitors and enforces their deadlines. The session host is the reckon crew host process this plan builds, one for each Claude Code session.

§2 — What Claude Code offers instead: a monitor that lives for the session

Claude Code lets a plugin declare monitors in its manifest. The plugin documentation says such a monitor "runs in the background for the whole session", and the binary agrees: it launches the plugin's command with no deadline and stops it only when the session ends. Three constraints come with it, all read from the 2.1.289 binary and the plugin reference:

  • Claude Code never restarts a plugin monitor that exits. Whatever it runs must stay alive for the session and supervise its own children.
  • Plugin monitors load only from personal scope. A plugin directory under ~/.claude/skills/ loads in place as <name>@skills-dir with no install step, and a symlink there is followed; a project's .claude/skills/ loads the plugin but skips its monitors.
  • Claude Code rate-limits each plugin monitor. Lines arriving within 200 ms form one batch and one notification. When batches arrive faster than the limit allows, the excess batches are dropped and a later notice says how many were suppressed. The follower's baseline replay is one batch, and the session host adds no output of its own, so it spends none of that limit.

§9 — The session host removes its FIFO when it ends

Deliverable. When reckon crew host stops, because its owner ended or it was signalled, it removes the FIFO it was handed. The entry point removes the FIFO only when its owner ends before the first request; once it has become reckon crew host, nothing does, so every session that dispatched leaves one stale FIFO in the runtime directory. The host derives the path from its owner pair and the same runtime-directory order the entry point uses.

Done when a test in tests/test_session_host.py starts the host on a FIFO named for a fake owner, ends the owner, and finds the FIFO gone, and the session-host census reports stale_fifos=0 after a session that dispatched has ended.

§ Decisions

When does the plugin monitor start?

A plugin monitor can start at session start ( always ) or the first time a named skill runs. Plan reviews dispatched from /reckon-create and /reckon-edit need a follower as much as /reckon-build runs do.

The first dispatch is what needs a follower, whichever skill or tool makes it. A skill list would miss review workers and any dispatch made through the CLI or MCP. The cost is one idle shell per interactive session, waiting on a node-local FIFO.

What does the host print to the pane?

The pane stays the ticker it is today. Host status goes to its log and record, never to stdout, consistent with the rule that the stream carries worker transitions and fleet posture and nothing else.

What happens where no host is running?

Codex sessions, -p sessions and sessions without the plugin have no plugin monitor, so the current mechanism stays for them unchanged.
