§1 — Why: Claude Code owns the cap, and every re-arm costs a turn

A coordinator's follower runs inside the Monitor tool, and the Monitor tool ends every watch at thirty minutes. Claude Code 2.1.271 made that deliberate: its changelog reads "Changed Monitor watches to always have a deadline (at most 30 minutes; 10 in single-prompt -p runs) and notify Claude to re-arm, replacing the no-timeout persistent option". In the installed binary the cap is a server-side flag rather than a setting, so nothing reckon passes can lift it.

The shipped plan a-follower-outlives-its-monitor made the expiry survivable. The follower arms with --lifetime 29m, announces its own end one minute before Claude Code ends it, names the attach line in that final row, and replays the runs that changed during the gap when it re-attaches. Its census found 620 of 719 armed followers ending when Claude Code expired the watch. What is left is the re-arm itself: every 29 minutes the coordinator spends a turn arming the same command again, and a coordinator that misses the end row learns of it from a watcher-required refusal on its next dispatch.

The same gap affects review workers. /reckon-create dispatches a read-back review of each new plan and /reckon-edit leads to crew review-plan, so a session that only authors plans still dispatches runs whose results it must hear. A trigger tied to /reckon-build would miss them. In this plan the monitor starts with every session and does nothing until that session's first dispatch, from whichever skill or tool makes it, asks it for a follower.

Two names are kept apart below. Claude Code is the harness that runs monitors and enforces their deadlines. The session host is the reckon crew host process this plan builds, one for each Claude Code session.

§2 — What Claude Code offers instead: a monitor that lives for the session

Claude Code lets a plugin declare monitors in its manifest. The plugin documentation says such a monitor "runs in the background for the whole session", and the binary agrees: it launches the plugin's command with no deadline and stops it only when the session ends. Three constraints come with it, all read from the 2.1.289 binary and the plugin reference:

  • Claude Code never restarts a plugin monitor that exits. Whatever it runs must stay alive for the session and supervise its own children.
  • Plugin monitors load only from personal scope. A plugin directory under ~/.claude/skills/ loads in place as <name>@skills-dir with no install step, and a symlink there is followed; a project's .claude/skills/ loads the plugin but skips its monitors.
  • Claude Code rate-limits each plugin monitor. Lines arriving within 200 ms form one batch and one notification. When batches arrive faster than the limit allows, the excess batches are dropped and a later notice says how many were suppressed. The follower's baseline replay is one batch, and the session host adds no output of its own, so it spends none of that limit.

A throwaway probe plugin, linked as ~/.claude/skills/reckon-monitor-probe and loaded with /reload-plugins, measured the rest in a live session on 2026-10-07:

QuestionMeasured

Does the monitor know its Claude session? Yes: CLAUDE_PID and CLAUDE_CODE_SESSION_ID are set and match ~/.claude/sessions/<pid>.json.
Does reckon count its output as delivering? Yes: stdout is a socket, which delivery_mode_of classifies as stream.

The probe's diagnostic lines exist only to answer these questions. The monitor this plan builds prints nothing of its own: a reader sees the follower's ticker and nothing else, exactly as the follower prints it today.

§3 — The session host starts with every session and stays silent until asked

Deliverable. A plugin at plugins/crew-host/ in this repository, holding .claude-plugin/plugin.json, monitors/monitors.json and one shell entry point, bin/crew-host. The manifest declares one monitor with when: "always", whose command runs that entry point. The entry point:

  • identifies its owner as the Claude process named by CLAUDE_PID together with that process's start time from /proc. The pair stays the same across /clear, whereas the session id does not;
  • creates a FIFO named after that pair in the runtime directory ($XDG_RUNTIME_DIR, then /run/user/<uid>, then $TMPDIR), all of which are node-local, so waiting on it costs nothing on GPFS;
  • blocks reading the FIFO with a 60-second timeout, so a request is handled as soon as it arrives and the owner's liveness is re-checked on each timeout; it prints nothing;
  • on the first request, replaces itself with reckon crew host (same pid and same stdout). It never parses a request: it opens the FIFO once, read-write, reads exactly one line (bash reads a pipe a byte at a time, so it takes no more), and passes that line and the open descriptor to reckon crew host, which is the protocol's only reader. The descriptor stays open across the exec, so a request written in between waits in the pipe rather than being lost. It finds the checkout by resolving the entry-point script's own path with readlink -f and taking the directory that contains plugins/crew-host/bin/crew-host, then runs that checkout's .venv/bin/reckon, never a bare reckon from PATH;
  • exits silently when its owner is gone.

Done when a fresh interactive session with the plugin linked shows one idle shell process for that session and no output in its pane, and that process exits within a minute of the session ending.

§4 — reckon crew host supervises the session's followers

Deliverable. A crew host command, hidden from help because only the entry point runs it, that reads one JSON request per line from the FIFO descriptor it inherits. Each request names a project and a session. For each request it runs reckon crew follow --project P --session S with no --lifetime, under the rules below.

Prior art. reckon/crew/fleet_supervisor.py already serves a request FIFO and supervises children. It is not the owner here, for three reasons. It runs once per SLURM allocation, not once per Claude Code session, and does not exist on a login node. It starts each service as its own session leader with its output logged, whereas a follower must end with its session and write to that session's stdout. And a follower's lines reach the pane only when the follower descends from the plugin monitor that holds that stdout. The session host reuses its parts instead: fleet_supervisor.next_backoff for restarts, and dispatch._write_fleet_request for the client write in §5.

  • Output. Children inherit the host's stdout, so their lines reach the pane exactly as the follower prints them and their registrations read as delivering. Child stderr goes to ~/.cache/reckon/session-host/<claude-pid>-<start>.log on the shared home, where a later session can read it, and never to the pane. The session host itself writes nothing to stdout, at start, on a request, or on a restart.
  • One child per project and session. A request for a project and session already followed changes nothing and writes nothing. A request carries no observed sessions: observing another session's runs stays on today's Monitor path.
  • Restarts. A child that exits while its owner lives is restarted on the schedule fleet_supervisor.next_backoff already applies to declared services. The session host does not start or restart its own child for a project and session while a live follower it did not start holds that registration, so it never contends with a coordinator who armed one by hand. It never stops a child it already runs because another follower appeared.
  • The session host never exits on its own, because Claude Code would not restart it. It ends only when its owner is gone or it receives a signal.
  • Children end with the host. Every child is started with a parent-death signal. The session host checks every five seconds that its owner is alive, and on its owner's end or on SIGTERM or SIGHUP it stops every child and then exits.
  • Record. The session host records its pid, owner and children in one file under ~/.config/reckon/crew/session-hosts/, written on change only, so a census can attribute every crew follow it started.

Done when unit tests drive the host with a fake follower command and show: one child per project and session; a killed child restarted; a hand-armed live follower left alone; no stdout from the host itself; and no child surviving the host's SIGTERM or its owner's exit.

§5 — Dispatch asks the session host before it refuses

Deliverable. In reckon/crew/dispatch.py, between _ensure_watch_producer and _watcher_delivery_admission: when the launch kind is cli, a session is named, that session is not attached, and the calling Claude process (resolved the way _coordinator_runtime already resolves it) has a live session host, dispatch writes a request to its FIFO through _write_fleet_request with no wait, so a FIFO without a reader means no session host and falls back at once; that function's error text names the FIFO rather than the fleet. It then waits, for at most WATCHER_LOAD_BOUND_SECONDS (the bound _ensure_watch_producer already uses), until the session reads as attached. Then it reads the watch state again and admits as it does today. Without a session host, or when it does not attach the session within the bound, dispatch behaves exactly as it does now, with the attach line and the refusal. The dispatch payload gains a delivery field: "host" when the session host attached the session, "monitor" otherwise. When it reads "host", the payload carries no arming instruction. This plan adds two surfaces, the hidden crew host verb and the payload's delivery field, and retires none: the Monitor path stays the fallback for Codex sessions, -p sessions and sessions without the plugin.

Done when a test with a stub host shows a dispatch from an unattached session admitted with delivery: "host" and no refusal, and the same dispatch with no host still refused with the same refusal text as before this change.

§6 — reckon-sync links the plugin; reckon doctor checks it

Deliverable. reckon-sync links plugins/crew-host from the main checkout as ~/.claude/skills/reckon-crew-host, alongside the skill links it already makes, and refuses to link from a worker worktree, for the same reason the hooks installer refuses: a reclaimed worktree would leave the link resolving to nothing. reckon doctor reports whether the link exists, resolves, points at the main checkout, and passes claude plugin validate. The link is user-level, so one link serves every repository that runs reckon. Each running session picks it up at its next start or after /reload-plugins.

Done when reckon-sync run twice leaves exactly one link, claude plugin list shows reckon-crew-host@skills-dir as loaded, and reckon doctor flags a link that points into a worktree.

§7 — The skills say what the session host now does

Deliverable. skills/reckon-build/SKILL.md (the producer-and-follower section), references/orchestrator-harness/claude-code.md (arming the fleet watch, and what a session owns) and references/sprint-orchestration.md §15 and §17 say that on Claude Code with the plugin linked, dispatch arms the follower and nothing re-arms it. Where no session host runs, the Monitor tool stays the fallback: Codex sessions, sessions without the plugin, and -p sessions, in which Claude Code starts no plugin monitors. The fallback lifetime is --lifetime 29m, except in a -p session, where Claude Code ends a Monitor at 10 minutes and the lifetime is --lifetime 9m. The re-arm guidance moves under that fallback rather than being deleted, because those sessions still need it. The user-global ~/.agents/AGENTS.md rule on stopping a follower before re-arming it gets the same qualification.

Done when the three skill files and the global rule name session-host delivery first and the Monitor fallback second, with its -p lifetime, and no sentence still tells a coordinator on a host-delivered session to re-arm every 29 minutes.

§ Decisions

When does the plugin monitor start?

A plugin monitor can start at session start ( always ) or the first time a named skill runs. Plan reviews dispatched from /reckon-create and /reckon-edit need a follower as much as /reckon-build runs do.

The first dispatch is what needs a follower, whichever skill or tool makes it. A skill list would miss review workers and any dispatch made through the CLI or MCP. The cost is one idle shell per interactive session, waiting on a node-local FIFO.

What does the host print to the pane?

The pane stays the ticker it is today. Host status goes to its log and record, never to stdout, consistent with the rule that the stream carries worker transitions and fleet posture and nothing else.

What happens where no host is running?

Codex sessions, -p sessions and sessions without the plugin have no plugin monitor, so the current mechanism stays for them unchanged.
