§1 — Why: the cap belongs to the host, and every re-arm costs a turn

A coordinator's follower runs inside the Monitor tool, and the Monitor tool ends every watch at thirty minutes. Claude Code 2.1.271 made that deliberate: its changelog reads "Changed Monitor watches to always have a deadline (at most 30 minutes; 10 in single-prompt -p runs) and notify Claude to re-arm, replacing the no-timeout persistent option". In the installed binary the cap is a server-side flag rather than a setting, so nothing reckon passes can lift it.

The shipped plan a-follower-outlives-its-monitor made the expiry survivable. The follower arms with --lifetime 29m, announces its own end one minute before the host does, names the attach line in that final row, and replays the runs that changed during the gap when it re-attaches. Its census found 620 of 719 armed followers ending at the host's expiry. What is left is the re-arm itself: every 29 minutes the coordinator spends a turn arming the same command again, and a coordinator that misses the end row learns of it from a watcher-required refusal on its next dispatch.

The same gap affects review workers. /reckon-create dispatches a read-back review of each new plan and /reckon-edit leads to crew review-plan, so a session that only authors plans still dispatches runs whose results it must hear. A trigger tied to /reckon-build would miss them; the trigger this plan adopts is the first dispatch, from whichever skill or tool makes it.

§2 — What the host offers instead: a monitor that lives for the session

Claude Code lets a plugin declare monitors in its manifest. The plugin documentation says such a monitor "runs in the background for the whole session", and the binary agrees: it launches the plugin's command with no deadline and stops it only when the session ends. Three constraints come with it, all read from the 2.1.289 binary and the plugin reference:

  • The host never restarts a plugin monitor that exits. Whatever it runs must stay alive for the session and supervise its own children.
  • Plugin monitors load only from personal scope. A plugin directory under ~/.claude/skills/ loads in place as <name>@skills-dir with no install step, and a symlink there is followed; a project's .claude/skills/ loads the plugin but skips its monitors.
  • A burst above the host's rate is suppressed, not delivered. Lines arriving within 200 ms are batched into one notification, so the follower's baseline replay arrives as one batch.

A throwaway probe plugin, linked as ~/.claude/skills/reckon-monitor-probe and loaded with /reload-plugins, measured the rest in a live session on 2026-10-07:

QuestionMeasured
Does a skill trigger match a user-level skill? Yes: when: "on-skill-invoke:reckon-create" armed when /reckon-create ran.
Does the monitor know its Claude session? Yes: CLAUDE_PID and CLAUDE_CODE_SESSION_ID are set and match ~/.claude/sessions/<pid>.json.
Does reckon count its output as delivering? Yes: stdout is a socket, which delivery_mode_of classifies as stream.
Does it outlive the Monitor tool's 30-minute cap? Pending: heartbeats at 10, 20, 31 and 40 minutes, then a deliberate exit at 45.
What happens in other sessions? It armed in two peer sessions that ran /reckon-create; each printed one line and exited.

The probe's diagnostic lines exist only to answer these questions. The monitor this plan builds prints nothing of its own: a reader sees the follower's ticker and nothing else, exactly as the follower prints it today.

§3 — A host process starts with every session and stays silent until asked

Deliverable. A plugin at plugins/crew-host/ in this repository, holding .claude-plugin/plugin.json, monitors/monitors.json and one shell entry point, bin/crew-host. The manifest declares one monitor with when: "always", whose command runs that entry point. The entry point:

  • identifies its owner as the Claude process named by CLAUDE_PID together with that process's start time from /proc. The pair stays the same across /clear, whereas the session id does not;
  • creates a FIFO named after that pair in the runtime directory ($XDG_RUNTIME_DIR, then /run/user/<uid>, then $TMPDIR), all of which are node-local, so waiting on it costs nothing on GPFS;
  • waits on the FIFO, checking once a minute that its owner is alive, and prints nothing;
  • on the first request, replaces itself with reckon crew host (same pid and same stdout), resolving the interpreter from its own symlink-resolved location, so it runs the checkout that holds the plugin and never a bare reckon from PATH;
  • exits silently when its owner is gone.

Done when a fresh interactive session with the plugin linked shows one idle shell process for that session and no output in its pane, and that process exits within a minute of the session ending.

§4 — reckon crew host supervises the session's followers

Deliverable. A crew host command that, once exec'd by the entry point, reads one JSON request per line from the FIFO. Each request names a project, a session, and optionally observed sessions and a theme. For each request it runs reckon crew follow --project P --session S, with the request's --observe-session and --theme flags and no --lifetime, under these rules:

  • Output. Children inherit the host's stdout, so their lines reach the pane exactly as the follower prints them and their registrations read as delivering. Child stderr goes to a log under the run cache, never to the pane. The host itself writes nothing to stdout, at start, on a request, or on a restart.
  • One child per project and session. A repeated request is a no-op. A request adding observed sessions restarts that child with the union of observed sessions, and the follower's own replay covers the restart.
  • Restarts. A child that exits while its owner lives is restarted with backoff from 1 to 60 seconds. The host stands down for a project and session only when a live follower it did not start already holds that registration, so it never contends with a coordinator who armed one by hand.
  • The host never exits on its own, because the plugin host would not restart it. It ends only when its owner is gone or it receives a signal.
  • Children end with the host. Every child is started with a parent-death signal. The host checks every few seconds that its owner is alive, and on its owner's end or on SIGTERM or SIGHUP it stops every child and then exits.
  • Record. The host records its pid, owner and children in one file under the crew config home, written on change only, so a census can attribute every crew follow it started.

Done when unit tests drive the host with a fake follower command and show: one child per project and session; a killed child restarted; a hand-armed live follower left alone; no stdout from the host itself; and no child surviving the host's SIGTERM or its owner's exit.

§5 — Dispatch asks the host before it refuses

Deliverable. In reckon/crew/dispatch.py, between _ensure_watch_producer and _watcher_delivery_admission: when the launch kind is cli, a session is named, that session is not attached, and the calling Claude process (resolved the way _coordinator_runtime already resolves it) has a live host, dispatch writes a request to that host's FIFO and waits, within the existing watcher load bound, until the session reads as attached. Then it reads the watch state again and admits as it does today. Without a host, or when the host does not attach the session within the bound, dispatch behaves exactly as it does now, with the attach line and the refusal. The dispatch payload gains delivery: "host" or delivery: "monitor", so a coordinator can tell which one carried the run, and it carries no arming instruction when the host did. A reckon crew host request subcommand sends the same request by hand, which is how a coordinator adds an observed session.

Done when a test with a stub host shows a dispatch from an unattached session admitted with delivery: "host" and no refusal, and the same dispatch with no host still refused with the same refusal text as before this change.

§6 — reckon-sync links the plugin; reckon doctor checks it

Deliverable. reckon-sync links plugins/crew-host from the main checkout as ~/.claude/skills/reckon-crew-host, alongside the skill links it already makes, and refuses to link from a worker worktree, for the same reason the hooks installer refuses: a reclaimed worktree would leave the link resolving to nothing. reckon doctor reports whether the link exists, resolves, points at the main checkout, and passes claude plugin validate. The link is user-level, so one link serves every repository that runs reckon. Each running session picks it up at its next start or after /reload-plugins.

Done when reckon-sync run twice leaves exactly one link, claude plugin list shows reckon-crew-host@skills-dir as loaded, and reckon doctor flags a link that points into a worktree.

§7 — The skills say what the host now does

Deliverable. skills/reckon-build/SKILL.md (the producer-and-follower section), references/orchestrator-harness/claude-code.md (arming the fleet watch, and what a session owns) and references/sprint-orchestration.md §15 and §17 say that on Claude Code with the plugin linked, dispatch arms the follower and nothing re-arms it. The Monitor tool with --lifetime 29m remains the fallback where there is no host: Codex sessions, -p sessions, and sessions without the plugin. The re-arm guidance moves under that fallback rather than being deleted, because those sessions still need it. The user-global ~/.agents/AGENTS.md rule on stopping a follower before re-arming it gets the same qualification.

Done when the three skill files and the global rule name host delivery first and the Monitor fallback second, and no sentence still tells a coordinator on a host-delivered session to re-arm every 29 minutes.

§ Decisions

When does the plugin monitor start?

A plugin monitor can start at session start (always) or the first time a named skill runs. Plan reviews dispatched from /reckon-create and /reckon-edit need a follower as much as /reckon-build runs do.

The first dispatch is what needs a follower, whichever skill or tool makes it. A skill list would miss review workers and any dispatch made through the CLI or MCP. The cost is one idle shell per interactive session, waiting on a node-local FIFO.

What does the host print to the pane?

The pane stays the ticker it is today. Host status goes to its log and record, never to stdout, consistent with the rule that the stream carries worker transitions and fleet posture and nothing else.

What happens where no host is running?

Codex sessions, -p sessions and sessions without the plugin have no plugin monitor, so the current mechanism stays for them unchanged.
