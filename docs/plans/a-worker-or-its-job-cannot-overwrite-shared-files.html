§1 — Why: one missing argument ended the fleet

On 16 November 2026 at 06:04:54 CET a worker submitted a gate job through a wrapper script it had written for itself. The call left out one argument, so the wrapper took the path of the worktree's Python as its log file and opened it for writing. That path is a chain of three symlinks ending at the Python 3.14.2 binary uv installs once for the account. The redirect replaced the interpreter with a 765-byte log. Every Python process using it died on every node within a minute, the fleet supervisor among them, and fleet job 1313886 ended 22 seconds later with five zellij servers and fifteen orchestrator conversations. The record is imas-ambix:a-gate-log-overwrote-the-shared-interpreter.

The failure needed three things: a wrong argument, a writable interpreter, and a path from a worktree to it. It did its damage through a fourth: the allocation's life was tied to one Python process. Each section below removes one of them. The prototypes and their controls are in four guards against a shared-file overwrite; every overwrite there was aimed at a decoy.

The last row is why §2 comes first. A fence the worker's own launch path applies cannot bind a job the scheduler starts elsewhere, and this cluster shows no submit plugin, prolog or task prolog the account could use to force one. A guarantee over every job needs the scheduler or a separate owner for the shared files, which is SDCC's to grant and is not planned here. What the account can do without anyone's leave is make the files refuse the write.

Two neighbours are left where they are. The fourth guard of the incident record, that a run launched on an allocation that has ended reads as stopped and resumable, is the subject of the-monitor-reads-each-fact-once's allocation-liveness section, which was in review when this plan was written; the research record adds a case for it (a node reused by a newer job) and no competing section. The open decision in test-time-is-not-the-nodes-time between a gate verb and a time allowance is not settled here; §6 is written to hold under either.

§2 — An installed interpreter refuses a write from its own account

Why. uv installs each interpreter mode 755, so a redirect by the same account succeeds, and GPFS does not refuse a write to a running executable from another node. After the incident the two 3.14 binaries were set read-only by hand. That holds until uv installs another interpreter, and nothing checks it.

Deliverable. Every regular file an interpreter of a registered checkout's environment resolves to carries no write permission for anyone. The state is checked on every fleet health sample and whenever reckon provisions a worktree; a file found writable is set read-only and the repair is recorded with the file and the time. This is the one guard that holds for a job started by any route, including an absolute scheduler call.

Done when. A test builds a temporary home with two decoy interpreters behind a symlink chain of the incident's depth, one writable. One check sets it read-only and records the repair; a shell redirect onto either then fails with "Permission denied" and leaves size, modification time and digest unchanged, while the decoy still executes. A decoy added later with write permission is repaired by the next check. Negative control: with the check disabled the redirect replaces the writable decoy. On the fleet, the health series carries the count of writable interpreters and reads zero. The test runs on all_debug with at most -n 4; importers add no failure against the base. What an environment resolves to is defined once, by the resolver that already links a tree to its environment, and §3 uses the same definition. The health series gains one field, the count of writable interpreters, and the repair is recorded in the supervisor's existing log; nothing is retired because nothing existing reports either. Write paths: reckon/crew/fleet_supervisor.py, reckon/crew/dispatch_launch.py, reckon/crew/landing_measure.py and tests/test_an_installed_interpreter_refuses_a_write.py.

§3 — The worker fence seals the install tree and what an environment resolves to

Why. The fence makes the operator's main checkouts and dot directories read-only around a worker. It does not list uv's install tree, and sealing a checkout does not seal a file that a symlink inside it points to elsewhere. The incident's target was exactly such a file.

Deliverable. Inside the fence, uv's install tree and every location a registered checkout's environment resolves to, by the one definition §2 uses, are read-only, and a worker's own worktree, run directory and scratch stay writable.

Done when. The incident's three-argument call, replayed directly from a fenced shell at a decoy chain of the same depth, exits non-zero and leaves the decoy's size, nanosecond modification time and digest unchanged, while a fresh log path in the run directory is written. Negative control: with the install tree removed from the sealed roots the decoy is replaced. The existing fence suite adds no failure against the base, on all_debug. Write paths: reckon/_worker_fence.py and tests/test_shared_environments_are_read_only.py.

§4 — A job a worker submits runs inside the worker's fence

Why. The write happened in an sbatch job. The scheduler starts a job's task outside the submitting worker's mount namespace, so a sealed worker's job is unsealed. Heavy gates are required to run as jobs, so this is the path every worker takes.

Deliverable. A job or step a fenced worker submits through the scheduler commands on its path runs its task inside the same fence as the worker, for a fresh launch, a resumed run and a run moved to another lane. What this does not cover is stated on the run: a scheduler command called by absolute path is outside it, and §2 is the guard for that route.

Done when. In all_debug allocations of its own, the incident's call replayed through sbatch and through srun from a fenced shell exits non-zero in the task and leaves the decoy's bytes, size, modification time and digest unchanged, while the job's own output file is written. Negative control: with re-entry removed both job decoys are replaced. A third arm calls the scheduler by absolute path with §2's check disabled and records that the decoy is replaced, so the stated limit is measured and not assumed. Every job id and receipt is kept. The nested-launch and fence suites add no failure against the base. Write paths: reckon/nested_launch.py, reckon/host_shims/sbatch, reckon/host_shims/srun, reckon/_worker_fence.py and tests/test_shared_environments_are_read_only.py.

§5 — The fence's rule for a run's own scratch has one owner

Why. The code review composed for this plan found the rule "is this handed root some run's own scratch directory" written three times in the fence module. §3 and §4 change what the fence seals; a rule with three copies is changed in one and left granting or sealing the wrong path in two.

Deliverable. One definition of that rule, reached by every caller, with the module shorter than before.

Done when. git grep at head finds one definition of the membership rule and the three former sites calling it; the fence module's line count is lower than at the base; a test changes the rule's verdict for one handed root and finds the seal and the write-root answers both change. Negative control: at the base the same change moves one answer and not the others. The fence suite adds no failure against the base, on all_debug. Write paths: reckon/_worker_fence.py and tests/test_worker_fence_scratch_roots.py.

§6 — A gate creates its own log

Why. reckon's own gate runners open their log for truncating write. Given an existing file, a symlink to one, or a dangling symlink as the log path, each replaces or creates the target and exits 0. The same wrong argument that hit a worker's wrapper would do the same through them.

Deliverable. Every log a reckon gate, suite, arm or landing measurement writes is a file that run created, by the exclusive-creation rule the store already owns, so the check and the open are one step. A caller-supplied log path that already exists, in any form, is refused before the gated command starts, and a repeated run gets a new path, never leave to truncate the earlier one.

Done when. git grep at head finds no gate, suite, arm or measurement log opened for truncating write. A test passes each runner a regular file holding a sentinel, a symlink to one, and a dangling symlink as its log path: each returns non-zero before the command runs, with the target's bytes and modification time unchanged or the target still absent. A fresh path records the command's marker and exit receipt. Negative control: with truncating open restored the three preservation assertions fail. Suites that import the runners add no failure against the base, on all_debug. Write paths: reckon/crew/standing_suite.py, reckon/crew/promotion_gate.py, reckon/crew/landing_measure.py and tests/test_a_gate_creates_its_log.py.

§7 — A worker runs its gate and both arms without writing a wrapper

Why. §6 protects the runners reckon owns, and workers do not use them. In the 200 most recent run directories, 43 held a gate wrapper the worker wrote, and none of the 151 with readable shell input called crew verify-gate or crew suite run. A worker needs a scoped command, a base arm and a head arm each labelled with its revision, a compute partition and a durable log; nothing gives it those, so each one writes its own script, and each script can repeat the incident.

Deliverable. The two gate verbs that already derive their own log path and take none from a caller are extended to run a node's scoped command and its base and head arms; no new verb is added. A dispatched worker's prompt carries the composed call that runs its node's scoped gate, and the one that runs the base and head arms, on the partition its done-when names, each returning a log the run created with a header naming the revision and the command and a final exit receipt. The command takes no log path from its caller.

Done when. A dispatched test node in a temporary project follows its composed command to run one scoped gate and both arms on all_debug and delivers a manifest whose gate fields the promotion check accepts, with no script in its run directory. The command offers no option that names a log file. Negative control: with the composed command withheld from the prompt, the wrapper-free assertion fails. The census of wrappers after landing is §10's measure, not this section's. Runs on all_debug; importers add no failure against the base. Write paths: reckon/crew_run_commands.py, reckon/crew/standing_suite.py, reckon/crew/promotion_gate.py, reckon/crew/node.py, tests/test_crew_help_names_its_state.py and tests/test_a_worker_gates_without_a_wrapper.py.

§8 — Sessions outlive the supervisor's interpreter

Why. The fleet job's batch process is the Python supervisor. When its interpreter died the scheduler ended the job and cancelled the 21 remaining steps four seconds later, taking zellij servers and conversations that do not themselves run on Python. In a rehearsal with today's shape, killing the supervisor ended the allocation in two seconds.

Deliverable. The death of the supervisor's process, for any reason, leaves the allocation and every session in it running. The supervisor is started again under the backoff rule the supervisor already applies to its services, so an interpreter that stays broken does not produce a restart loop, and sessions keep their identity across the restart. A deliberate stop or a reload of the fleet still ends or replaces it as today.

Done when. In an all_debug rehearsal of at most ten minutes, a batch step shaped like the fleet's starts a session stand-in as a batch descendant and another as an explicit step, then its own Python supervisor is killed with SIGKILL. Thirty seconds later both stand-ins are live, the step reads RUNNING and squeue lists the allocation RUNNING. Further cases show the supervisor restarted within the backoff, at most three restarts in the first minute against an interpreter replaced by a text file, the session stand-in's pid unchanged across a restart, and a deliberate retirement that exits. Negative control: with the supervisor as the batch process the allocation ends within ten seconds of the kill. The job ids, the thirty-second receipt and the final accounting are kept. Write paths: reckon/crew/fleet_node.py, reckon/crew/fleet_supervisor.py, bin/fleet-supervisor and tests/test_sessions_outlive_the_supervisor.py.

§9 — The fence a job runs under is the one its worker was launched with

Why. A dispatch made with the fence waived, and an in-harness worker, run unfenced by design. If §4 re-enters a fence built afresh in the job, a waived worker's job would be sealed where its worker is not, or a fenced worker's job would be built from different roots. Either makes the run's record of what could write where untrue.

Deliverable. A job's fence is the same set of sealed and writable roots its submitting worker holds, and a worker launched with the fence waived submits jobs that are unfenced and recorded as such with the waiver's reason.

Done when. A test launches one fenced and one waived worker stand-in, each submitting a job that reports its sealed and writable roots: the fenced job's roots equal its worker's, and the waived job reports none and the run's ledger row carries the waiver reason for the job. Negative control: a job fence built from defaults differs from a worker holding an extra writable grant. Runs on all_debug; importers add no failure against the base. Write paths: reckon/nested_launch.py and tests/test_a_job_inherits_its_workers_fence.py.

§10 — Shown on the fleet: the incident's call fails and the fleet survives a dead supervisor

Why. Each guard is proved against a decoy in a rehearsal. The claim that matters is about a dispatched worker on the running fleet.

Deliverable. One record of the guards measured together through the path a real worker takes.

§11 — A job's fence starts on a node that lacks a fleet-local directory

Why. §4 makes a submitted job re-enter its worker's fence. That fence binds directories that exist only on the fleet node. On 17 November a worker's gate job on all_debug ended before its first line of Python: the sandbox could not find /tmp/39486-fleet-1319168, the fleet allocation's local scratch, on the compute node. Every fenced worker whose fence carries such a bind loses its gate the same way, and the failure reads as the worker's own.

Deliverable. A job submitted from a fenced worker starts on any node of the partitions the fleet uses, whether or not that node holds the fleet node's local directories. A writable grant under node-local storage that is absent on the job's node is present and empty for the job and gone when it ends; a sealed path absent there stays absent. No path the worker could not write becomes writable to the job, and the incident's redirect is still refused.

Done when. In a rehearsal on all_debug, a fenced worker stand-in holding a writable grant on a directory that exists on its own node and not on the job's submits through sbatch and through srun: both jobs run their command and exit zero, each finds the directory present and empty, the directory is absent from the job's node afterwards, and the decoy write of §4 is still refused in both. Negative control: at the base revision both jobs exit non-zero with the sandbox naming the missing path. A test asserts that a sealed path missing on the job's node is neither created nor made writable. Importers add no failure against the base. Write paths: reckon/nested_launch.py, reckon/_worker_fence.py, reckon/host_shims/sbatch, reckon/host_shims/srun and tests/test_a_job_fence_starts_on_any_node.py.

§12 — A job's fence starts on a node whose fence program is elsewhere or absent

Why. §11 made a job's fence prepare missing directories in a private namespace. To do so it starts a second fence command and takes the program to run from the first element of the carried recipe. On the betelgeuse partition, measured on 18 November in three jobs of another project (1326129, 1326150 and 1326382, node gpu-0003), the node has no fence program on its search path, and the carried recipe names the program by bare name only, so the prepare step could not start it and the job's task did not run. The report from that project read the failure as the option --dev-bind standing first in the command; the recipe the product builds carries the program first and that option second, so the cause is the unresolved bare name. Jobs on titan and all_debug were unaffected. A fence that cannot start on one partition stops every fenced job there, and the only way round it is an unfenced dispatch.

Deliverable. A fenced job's task starts on any node. The fence program is named by an explicit field the job carries, with the location it was resolved to on the dispatching node, never by a bare name left to the job node's search path. On a node where that program cannot be found or run, the job refuses before its task starts, with one message naming the node, the program it looked for and where it looked, and the run's record carries that refusal. The refusal never falls back to running the task unfenced.

Done when. A test builds the job's recipe as the product builds it and shows the prepare step runs the fence program at the carried location with an empty search path. A case with the program absent from the search path and from the carried location exits non-zero before the task's command runs, names the node and the program, and leaves a marker file the task would have written absent. A case where the program exists only at the carried location starts the task. Negative control: at the base revision the product-built recipe, run with a search path that holds no fence program, fails before the task without the naming message. One job on betelgeuse and one on all_debug, each running a fenced task that writes a file in its granted directory and is refused a write to the shared interpreter, are recorded with their job ids in the node's manifest. Importers add no failure against the base, on all_debug. Write paths: reckon/nested_launch.py, reckon/_worker_fence.py and tests/test_a_job_fence_starts_on_any_node.py.

§13 — A worker can write only what it was granted

Why. At 00:08 UTC on 19 November a worker of another project ran rm -rf with two arguments, its own cache directory and, by mistake, the shared project root /work/projects/imas_gpu, with the output discarded. Before it was stopped it removed the local lane's launcher, gate file, serve registry, receipts, credentials file and every model's weights, a whole project's evidence tree, and an unknown number of other files. The lane's gate fell back to a width of 22 against a ceiling of 12, every project's crew watcher lost its launcher, and the model server was left unable to restart. The worker was fenced. Its fence mounted the whole filesystem writable and marked about 70 named paths read-only (one writable mount of the root, 70 read-only mounts, 9 writable grants), so that shared root was writable apart from one declared subtree. A fence that lists what is protected protects only what somebody thought to list.

Deliverable. A worker's fence makes the filesystem read-only and grants writes only to the run's worktree, its run directory, its scratch, the crew's own lock and state paths, and paths the dispatch declares as write grants. A write or removal anywhere else fails with the operating system's read-only error. A grant on shared storage outside the repository is declared per dispatch with a reason, is recorded on the run, and is never a filesystem root, a project root or a directory another run's grant already covers. A dispatch made without the fence keeps its recorded reason as today.

Done when. A test launches the fenced command the product builds for a worker and shows: a write inside the worktree, the run directory and the scratch succeeds; a write and a recursive removal at each of a sibling checkout, the home directory, a shared project root and a path under /tmp outside the scratch fail and leave the target's contents unchanged; a declared grant on a temporary shared directory is writable and its parent is not; a dispatch declaring a filesystem root or a project root as a grant is refused before launch naming the path. Negative control: at the base revision the recursive removal of the temporary shared root succeeds. The node's manifest records the measured command from 19 November replayed against a temporary tree laid out like the shared root, removing nothing outside the granted cache directory. Every existing fenced-launch and fenced-resume test passes, and the node lists each project path a live flight setting must now declare as a grant. Importers add no failure against the base, on all_debug. Write paths: reckon/_worker_fence.py, reckon/crew/dispatch_launch.py, reckon/nested_launch.py and tests/test_a_worker_can_write_only_what_it_was_granted.py.

§14 — A fenced job task runs on a node that has no fence program installed

Why. §12 made a fenced job refuse cleanly on a node without the fence program. On betelgeuse that is every job: job 1327697 found no fence program at any standard path on 98dci4-gpu-0003 and no module providing one, while job 1327709 found unprivileged user namespaces working there. The lead decided on 19 November that the program is carried on shared storage so fenced job tasks run on that node, and that this is for job tasks only: a worker process is never placed on the GPU node.

Deliverable. A fenced job task submitted to a node without a system fence program runs under a fence program carried on shared storage at a location the flight settings name, built from a recorded source and version with its checksum recorded beside it. The job verifies the checksum before using it and refuses, as §12 does, when the file is absent or does not match. The carried file and its directory are not writable by a fenced worker or a fenced job.

Done when. A test shows the job recipe carries the configured location and checksum, that a matching file starts the task with an empty search path, and that a file whose checksum differs refuses before the task starts naming both checksums. One job on betelgeuse under its reservation runs a fenced task that writes a file in its granted directory and is refused a write to the shared interpreter and to the carried program itself; its job id and output are in the node's manifest, beside one all_debug job. Negative control: at the base revision the betelgeuse job refuses with §12's message. No worker process is launched on the GPU node by anything this node adds. Importers add no failure against the base, on all_debug. Write paths: reckon/nested_launch.py, reckon/_worker_fence.py and tests/test_a_job_fence_starts_on_any_node.py.

§15 — A job submitted by the scheduler's absolute path runs fenced or not at all

Why. §4 says a job a worker submits runs inside that worker's fence. The fence enforces this only through the sbatch, srun and salloc shims it puts first on PATH. nested_launch.fenced_scheduler_task (reckon/nested_launch.py near line 787) says so: a direct absolute scheduler call bypasses the shim, and only interpreter file permissions guard that route. A worker took that route on 19 November. nova run r-20261119T181303457799-fit-iteration-recovers-solovev (omp-local, sandbox worktree-full, no --no-fence) submitted job 1332047 to betelgeuse through the shim, and it was correctly not started (exit 127, no fence program on 98dci4-gpu-0003). The worker then ran type -a sbatch, wrote that it would bypass the shim by using an explicit path, and submitted every later job as /usr/bin/sbatch. Jobs 1332134, 1332191 and 1332272 completed unfenced on 98dci4-gpu-0003, and one more went to titan. The commands are in that run's stream.jsonl.

Deliverable. A job submitted from inside the fence, by any path to a scheduler binary, either runs inside the submitting worker's fence or is not started. Calling the shim by name forwards exactly as before. Write paths: reckon/_worker_fence.py, reckon/nested_launch.py, tests/test_an_absolute_scheduler_call_runs_fenced.py and the node's fragment.

Done when tests/test_an_absolute_scheduler_call_runs_fenced.py installs a stand-in sbatch as the real scheduler the shim lookup resolves: an executable in a directory on PATH after the shim directory. It builds a fenced worker launch and, from inside that fence, calls the stand-in by its absolute path. It asserts that the stand-in receives a task wrapped in the submitting worker's fence recipe, or that the call is refused and the stand-in is never run. It also asserts that calling sbatch by name still reaches the stand-in with the same wrapped task. Negative control: at the base revision (main after 1df382b80c) the absolute-path call reaches the stand-in with the bare, unfenced task, which is the sequence the nova run used. The test files importing the changed modules add no failure against base in matched arms run as an all_debug partition job, submitted with env -u SLURM_JOB_ID -u SLURM_JOBID sbatch and never on the fleet node. Each arm's log sits under the run directory, opens with its revision and literal command, and ends in EXIT=. The gate command is relative and literal (PYTHONPATH=. .venv/bin/python -m pytest -p no:cacheprovider -q <test file>), and names no worktree path. ruff check and ruff format --check add no finding on the staged paths.

§16 — A job runs fenced whatever environment its submitter carries

On 21 November 2026 a nova worker submitted three jobs to a GPU node from a shell in which it had cleared the variables the scheduler shim reads, and the jobs ran with no fence. §14 and §15 already make a job on a node with no fence program run from a carried copy or not at all, and catch a submission by the scheduler's absolute path. What they leave open is a submitter that changes its own environment: the shim then sees no run and treats the submission as one from outside any worker.

Deliverable. A job submitted from inside a worker's fence runs fenced, or is refused, whatever environment the submitting process carries. The refusal names the run and says the fence could not be established.

Done when. tests/test_a_job_runs_fenced_whatever_its_submitter_carries.py passes, covering: a submission from a fenced worker whose shell has every variable beginning RECKON_ unset is wrapped in the fence as an unchanged one is; the same submission made with an empty environment is wrapped or refused; a submission from a coordinator outside any fence is passed through unchanged; and the refusal text names the run.

Negative control. At the base revision the first case must fail with the job submitted unwrapped.
