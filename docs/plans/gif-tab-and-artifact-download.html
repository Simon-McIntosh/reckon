The served surface · two features the lead asked for, and the correction that makes one possible

Animations Get A Tab, Artifacts Get A Save

Forty-nine animations exist in one consuming repository and none of them can be browsed, because figure discovery globs two extensions and an animation is neither. The lead asked for an animation tab beside Figures and a save control on artifacts whose file is unambiguous. The tab is the easy half to describe and the impossible half to build as things stand: three separate hardcoded lists decide whether a tab renders, which canvas it opens, and which item it resolves, and each one fails silently and differently when a fourth kind becomes a fifth. This plan makes one declaration decide all three, then adds the two features on top of it.

§1 — Why this exists

The request came from a repository that has been producing animations all day. Measured in imas-ambix at 06:33Z on 2026-09-07: 49 files matching *.gif against 440 matching *.png or *.svg, spread across topic directories, all of them fetchable by URL and none of them listed anywhere a reader browses.

The count is moving, and that decides how this plan is verified. Three independent readings of the same tree gave 47, 48 and 49 within about two hours, and none was wrong: four animations landed during that window, the newest two in commit be9d45b at 08:25 local, while three live render nodes continued to produce more. So no fixed row count can be an acceptance criterion here — a gate asserting “47 rows” would have failed twice over during the conversation that specified it. Every count in this plan is therefore derived from the filesystem at assertion time and compared, never written down as a literal. This is the repository's own rule about recorded absolutes that move on their own, and this is the clearest instance of it the project has produced.

Two extension globs are the whole of the discovery defect, and they are owned elsewhere: a peer session holds reckon/figures.py and reckon/serve.py and has already landed animations as a distinct row kind. That work is a prerequisite in fact but not a blocker in bookkeeping, because the surface half below is demonstrable against the emitted kind the moment the server carries it.

Three lists decide one thing, and none derives from another

Registering a fifth artifact route today requires editing three places that have no structural relationship to each other. Each omission produces a working-looking surface rather than an error, which is why this is the load-bearing section and not a tidy-up.

§2 — One declaration behind every tab, proven by the new tab working

The three declarations above collapse into one, and the other two derive from it. The animation tab is not a separate deliverable from that collapse: it is how the collapse is demonstrated, because a fifth kind that renders, routes and resolves without three coordinated edits is the only evidence that one declaration now decides all three. Shipping the unification without a new kind would prove nothing, and shipping the tab without the unification is not possible.

The reader itself needs no new branch. An animation row is identical to a figure row in every field except its kind, so the existing figure reader path renders it once it is reachable; an <img> element animates a GIF natively, which is why no frame extraction, no imaging dependency and no contact-sheet convention appear anywhere in this plan.

Gate for this section, recorded when the measure runs: adding one entry to the single declaration makes a fifth tab render in the bar, open its own canvas rather than the home dashboard, and resolve its own item rather than defaulting to a plan lookup — with no other file edited. Its evidence is the three-way equality assertion, the resolved kind for an animation hash, and one real animation from the consuming repository rendering in its own tab.

§3 — A save control the server decides

The lead scoped this deliberately: a save control for figures and animations, where the artifact is one unambiguous file, and a visibly disabled control for plans, research and evidence, where what “download” should mean is an open question this plan does not answer. Every artifact reader is one component keyed by kind, so the control renders in all five places and is live in two.

Whether an artifact can be saved is a server fact, not reader chrome. The row carries a download field — an href, empty where there is no unambiguous file — and the control's enabled state is exactly that field's emptiness. The reader never names a kind. This follows the project's binding rule that the SPA renders rather than derives, and it passes that rule's own test: an agent, a CLI caller and an MCP read all want to know which file backs an artifact, so the value is a fact the server owes every consumer and not a detail of one surface. It is also what stops the two surfaces disagreeing later, which is the failure the rule exists to prevent.

The field is a single href rather than an href beside a boolean, because a boolean is a second source of truth for one fact and can contradict the href it sits next to — the same shape as the three lists in §1, reintroduced in the very field added to avoid them. A field cannot disagree with itself. It carries an empty string rather than a null because the sibling fields on that row already use empty strings for absence, and one nullable field among them would force every consumer to handle two falsy shapes for no gain.

Because absence is falsy, this section is correct and demonstrable before the server field exists: every control is disabled, which is the honest rendering of a server that reports no downloadable file. It lights up without a further edit when the field arrives. The enabled half is therefore measured at a merged head carrying both commits, never against this node's own worktree alone.

Gate for this section, recorded when the measure runs: the control is enabled for exactly those artifacts whose row carries a non-empty download, disabled for every other kind, and the enablement condition contains no kind name. Its evidence is a saved file from each live kind, the disabled state on the three document kinds, and a source assertion that no kind literal appears in the condition.

§4 — Out of scope

What downloading a plan, research doc or evidence record should mean, which the lead explicitly deferred: the artifact there is HTML served through a plan route, so a save could reasonably mean the source file an agent edits and which carries the semantic state, or the rendered page a reader is looking at. Those need different server work and the answer probably differs by kind, so the control is greyed and the question stays open rather than being settled by whichever was easier to build.

Also out of scope: the two extension globs and the animation row kind, owned by a peer session in reckon/figures.py and reckon/serve.py; frame extraction, playback controls and contact-sheet generation, all of which a natively animating <img> makes unnecessary; the download field on document rows, which comes from the inventory producer rather than figure discovery and which lights this plan's control up with no change to it; and case-insensitive globbing, measured unnecessary at zero .GIF files.

§ Decisions

Do animations appear in the Figures index, or in a tab of their own?

The lead asked for “an additional gif tab next to figures”. The alternative was proposed independently by a peer session working from a relayed version of the same request, and it is not a smaller version of this choice but a different product: folding animations into figure rows makes the tab impossible to build, because a row's kind is what a route resolves against. It would also mix 49 animations into 440 static figures in the one repository that has them, changing the character of an index the lead reads. The distinction cost one word in a peer's node brief and decided whether the surface work could exist.

Does the save control cover documents, and if not, is it hidden or shown disabled?

The lead's amendment: “skip the download question for the docs for now, grey the button out. only implement for figs and gifs where the downloaded artifact file is clear.” Greying rather than hiding keeps the affordance discoverable and makes the unanswered question visible instead of silently absent, and it means the later document decision changes a server field rather than the reader's layout.

What shape does the server-derived download fact take on an artifact row?

A boolean beside the href is a second source of truth for one fact and can contradict the href it sits next to — precisely the defect this plan's §1 exists to remove, reintroduced in the field added to avoid it; a field cannot disagree with itself. Null was rejected because the row's sibling fields already express absence as an empty string, so one nullable field forces consumers to handle two falsy shapes for nothing. Deriving from kind in the reader was rejected by the project rule that the SPA renders rather than derives, and by that rule's test: an agent, a CLI caller and an MCP read all want to know which file backs an artifact. The peer session that owns the producing code asked for the name rather than guessing it, which is why this is recorded as a decision and not an implementation detail.
