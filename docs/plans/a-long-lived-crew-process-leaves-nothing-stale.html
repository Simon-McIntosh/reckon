§1 — Why: two kinds of debris outlive their cause

Both were found during the storage incident of 2026-10-23 on the fleet node clu-2068, recorded in monitor-storage-load-rca §10. Neither added load. Each is state a long-lived crew process keeps after the thing it describes has gone.

A queued run is told to re-dispatch. The queued run r-20261023T135622629487-a-scope-refusal-names-the-paths-it-parsed was refused once at admission at 15:42:01Z with UnreconciledRuns, because a sibling run was still unpromoted. The sibling was promoted 46 s later. For the next two hours the obligations view still listed the run as queued-awaiting-session, with the next command reckon crew dispatch --allow-unreconciled-runs, and the stop hook repeated that duty every turn. Admission meanwhile re-tested the run 369 times, answering held-for-allowance. Three later ScopeConflict refusals, at 16:12, 16:51 and 17:55Z, each published reckon crew dispatch the same way. The refusal is kept in the pointer's failure field, and recovery_classification._queued_failure_remedy publishes whichever command the refusal text quotes. For a request already in the queue, a re-dispatch is never the remedy: it discards the request's place, and admission re-tests the request on every pass by itself.

A re-exec strands its children. At 18:12Z the admit service (pid 4098806) held three zombie children, started 2026-10-21 04:08Z, 2026-10-22 15:16Z and 18:08Z. Each led its own session and had exited 0. The imas-codex producer (pid 1527007) held four, started between 07:34 and 17:25Z, and the nova follower (pid 464271) one. All three parents replace their own image in place when reckon's code moves: queue_admission._reexec_into_current_code and follower_reload, both through os.execve. A child alive at that moment stays the process's child, but no object in the new image refers to it, so nothing ever waits on it. CPython reaps only children it holds a Popen for; a dropped Popen is reaped at the next subprocess call, measured on 3.14.2. The follower already hands its launched workers across the exec (dispatch_launch._export_launched_workers_for_reexec); every other child is left. A zombie holds only a process-table slot, but one is left per reload for the life of the process.

§2 — A queued run is never told to re-dispatch

Deliverable. In reckon/crew/recovery_classification.py, _queued_failure_remedy returns no remedy, which is the waiting reading, for a refusal that quotes a reckon crew dispatch invocation among its remedies. Such a refusal speaks to a dispatch about to be made. The request it was recorded against is already in the queue, and admission re-tests it on every pass. A refusal that names the session keeps its follower duty, and a refusal whose only quoted remedy is another command, such as the plan-review gate's reckon crew review, keeps that duty, because the session alone can clear it. Nothing changes in how admission records a refusal. An UnreconciledRuns refusal needs no duty of its own here: each run it names is already listed in the obligations view as its own unreconciled run, with that run's remedy.

§3 — A re-exec reaps the children it inherits

Deliverable. One helper in reckon/crew/process_signal.py, reap_inherited_children(). On its first call in a process image it records the process's children, read from the kernel's /proc/self/task/*/children, and leaves out every pid the image has adopted through the launched-worker handover. On every call it reaps each recorded pid with os.waitpid(pid, os.WNOHANG), and forgets a pid once it is reaped or the kernel answers ECHILD. A child the new image starts itself is never in the record, so its Popen keeps its exit status. An adopted worker stays with the follower's reaper, which owns it.

Three loops call it: the admission loop queue_admission.admit_until_stopped on each pass, the producer loop recovery_watch.watch_ticker on each tick, and the follower poll loop in reckon/crew_follow_commands.py on each poll. Each also calls it once before the image spawns anything; for the follower that is straight after _adopt_launched_workers_from_reexec.

Done when tests/test_a_reexec_reaps_the_children_it_inherits.py passes. A process starts a child, replaces its image with a script that calls the helper, and the child exits after the exec; the child is a zombie before the next call and gone after it. A child the new image starts and holds as a Popen still reports its own non-zero exit status from wait(). A pid handed over as a launched worker is not reaped by the helper. Each of the three loops reaches the helper on a pass, shown by patching it. Negative control: a helper that records no children leaves the inherited child a zombie, and the first case fails. The test files importing reckon/crew/process_signal.py, reckon/crew/queue_admission.py, reckon/crew/recovery_watch.py or reckon/crew_follow_commands.py show no added failure against base. ruff check and ruff format --check add no finding and no formatting change. Write paths: reckon/crew/process_signal.py, reckon/crew/queue_admission.py, reckon/crew/recovery_watch.py, reckon/crew_follow_commands.py and the new test file.
