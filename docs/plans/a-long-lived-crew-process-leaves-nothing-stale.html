§1 — Why: two kinds of debris outlive their cause

Both were found while attributing the storage incident of 2026-10-23 on the fleet node clu-2068, whose analysis is monitor-storage-load-rca §10. That section does not record these two findings; the evidence for them is stated below. Neither added load. Each is state a long-lived crew process keeps after the thing it describes has gone.

A queued run is told to re-dispatch. The queued run r-20261023T135622629487-a-scope-refusal-names-the-paths-it-parsed was refused once at admission at 15:42:01Z with UnreconciledRuns, because a sibling run was still unpromoted. The sibling was promoted 46 s later. For the next two hours the obligations view still listed the run as queued-awaiting-session, with the next command reckon crew dispatch --allow-unreconciled-runs, and the stop hook repeated that duty every turn. Admission meanwhile re-tested the run 369 times, answering held-for-allowance. Three later ScopeConflict refusals, at 16:12, 16:51 and 17:55Z, each published reckon crew dispatch the same way. The refusal is kept in the pointer's failure field, and recovery_classification._queued_failure_remedy publishes whichever command the refusal text quotes. For a request already in the queue, a re-dispatch is never the remedy: it discards the request's place, and admission re-tests the request on every pass by itself.

A re-exec strands its children. At 18:12Z the admit service (pid 4098806) held three zombie children, started 2026-10-21 04:08Z, 2026-10-22 15:16Z and 18:08Z. Each led its own session and had exited 0. The imas-codex producer (pid 1527007) held four, started between 07:34 and 17:25Z, and the nova follower (pid 464271) one. All three parents replace their own image in place when reckon's code moves: queue_admission._reexec_into_current_code and follower_reload, both through os.execve. A child alive at that moment stays the process's child, but no object in the new image refers to it, so nothing ever waits on it. CPython reaps only children it holds a Popen for; a dropped Popen is reaped at the next subprocess call, measured on 3.14.2. The follower already hands its launched workers across the exec (dispatch_launch._export_launched_workers_for_reexec); every other child is left. A zombie holds only a process-table slot, but one is left per reload for the life of the process.

§2 — A queued run is never told to re-dispatch

What already landed. Between 22:29Z on 2026-10-23 and 03:26Z on 2026-10-24, peer commits f1181e0e5, 0a976babc and 41325f022 taught recovery_classification._queued_failure_remedy to read a refusal by its stamped exception class. QueueFull and the whole ScopeConflict family (_wait_refusal_classes) now read as waits, and an UnreconciledRuns refusal publishes the first named run's own reconcile command through _unreconciled_runs_remedy instead of a re-dispatch. That clears the ScopeConflict case and the re-dispatch remedy.

Deliverable. One case remains. _unreconciled_runs_remedy publishes the first run the refusal named, whether or not that run is still unreconciled. At 15:42:47Z the named run was promoted 46 s after the refusal, and the duty kept naming reckon crew complete for a run that no longer needed it. The remedy now publishes the first named run that still has a live pointer, read through runs.read_pointer; when none does, _queued_failure_remedy returns no remedy for that refusal, which is the waiting reading, and admission re-tests the queued request on its next pass. It must not fall through to _remedy_command_stated_by: the UnreconciledRuns text quotes reckon crew dispatch --allow-unreconciled-runs, so a fall-through would publish the re-dispatch again. The remedy's detail also drops its closing advice to discard the queued run and dispatch it again, the action a queued run must never be told to take.

§3 — A re-exec reaps the children it inherits

Deliverable. No second reaper. reckon/crew/dispatch_launch.py already owns non-blocking reaping of this process's children: _reap_launched_workers, run by _worker_reaper_loop once _ensure_launched_worker_reaper starts it, waits only on the pids in _LAUNCHED_WORKERS. _adopt_launched_workers_from_reexec already runs at exactly the execve boundary to refill that registry. That adoption now also registers every child the process has when it runs, read through recovery_liveness._process_children(os.getpid()), the existing reader of /proc/<pid>/task/*/children, without a _LAUNCHED_WORKER_RUNS entry, so the reaper reaps them silently. It then starts the reaper. In a process that has just started there are no children yet, so the call registers nothing. A child the new image starts later is never registered, so its Popen keeps its own exit status.

The follower already calls the adoption at start-up in reckon/crew_follow_commands.py. The admission loop queue_admission.admit_until_stopped and the producer loop recovery_watch.watch_ticker call it once at start-up as well. The station tick that the-monitor-reads-each-fact-once §7 builds must make the same call, which is why this plan blocks that section. No public name is added: the change extends a private function and calls it from two more private loops.

Done when tests/test_a_reexec_reaps_the_children_it_inherits.py passes. A process starts a child, replaces its image with a script that calls _adopt_launched_workers_from_reexec, and the child exits after the exec; the child is gone within the reaper's poll interval. A child the new image starts afterwards and holds as a Popen still reports its own non-zero exit status from wait(). A launched-worker pid handed over through the environment keeps its run record. The admission loop and the producer loop each reach the adoption once at start-up, shown by patching it. Negative control: an adoption that skips the child scan leaves the inherited child a zombie, and the first case fails. The test files importing reckon/crew/dispatch_launch.py, reckon/crew/queue_admission.py or reckon/crew/recovery_watch.py show no added failure against base. ruff check and ruff format --check add no finding and no formatting change. Write paths: reckon/crew/dispatch_launch.py, reckon/crew/queue_admission.py, reckon/crew/recovery_watch.py and the new test file.
