§1 — Why: a codex review lost every race for a seat, and the queue drained at one launch a minute

On 14 November the lead ruled that nova's inverse-equilibrium-baseline §1 is reviewed on codex, the fast lane kept as an escape hatch for work the local lane should not carry. The review was refused seven times between 20:51 and 21:21 UTC: five times at the placement roster's cap (25 workers already occupy the placement reservation's roster, whose cap is 25) and twice at the reservation's cores bound (28 of 28 cores admitted). One reservation (reckon/crew/placement.py, RESERVATION_ROSTER_LIMIT) seats every lane's placed workers. The admit service launches a queued local request the moment a seat frees, while a dispatch named to a metered lane cannot queue at all, because admission launches only the local lane. So every freed seat went to local work first, and the codex request could win one only if a retry happened to land in the gap.

The queue itself drained slowly. The admission pass that ended at 21:14:17Z spent 1,046 s launching, its oldest admissible request had waited 22,959 s, and 15 requests were marked stalled. A one-minute profile of the admit service sampled nothing but _adjacent_live_peers: every launch parsed the Python files of every live peer to decide adjacency, again for each peer pair and each launch. Seats free only as fast as workers finish, and a request reaches a freed seat only as fast as a pass launches, so a slow pass costs the whole fleet.

Reviews and implementations also compete in one queue with nothing to keep their cadence matched. A delivered run waits on its review before it can land, so a review that queues behind a wave of implementations holds finished work. And the same evening the sweep filed a review-self promotion request on a review its coordinator had held, moving a request that never launched out of the queue for good.

§5 — A request for a named lane queues, and is admitted into the reserve ahead of the local queue

Why. §2 makes room, but a codex request still gets a seat only by being dispatched at the moment one is free. A coordinator should state the request once and have it run when room and the lane allow, as local work already does.

Endpoint. A dispatch naming a lane other than the local one, held only by the roster or cores bound, is stored as a queued request and launched by admission into the reserved seats ahead of local work, so no coordinator retries it. A named lane under a budget hold keeps its request queued with the hold named, and nothing is rebound to another lane without the coordinator. Once named-lane requests queue, the reserve is held only while one waits or a named dispatch met the bounds within the last pass, so local work fills every seat when no escape-lane work is waiting: the router reads about 0.43 requests per worker, so a standing reserve leaves local cards idle. A review is moved to another lane on its queued request under the same node id, because its reviewed run is derived from that id. This carries queued-work-needs-no-workaround §17, moved here on 14 November.

Done when. New tests, each failing at the base revision:

  • A codex dispatch held at the cores bound or the roster cap is queued, not refused.
  • A local dispatch that falls back to codex on context fit and meets the cap is queued, and its output names the context-fit shortfall.

§6 — Reviews and implementations are admitted at a matched cadence

Why. A delivered run lands only after its review, so a review queued behind a wave of implementations holds finished work, while a wave of reviews holds back new work. Both are wanted, at a similar cadence.

Endpoint. When reviews and implementations both wait, each admission pass shares the seats it fills between the two roles in proportion to how many of each wait, with neither role taking fewer than one seat in three. Fair use between sessions still applies inside each role. The share is a named constant, and each pass records, per role, how many it launched and the age of the oldest it left waiting.

Done when. New tests, each failing at the base revision: with nine implementations queued ahead of three reviews and three free seats, one pass launches at least one review and at least one implementation; and a pass's verdict row carries per-role launch counts and oldest-waiting ages. A case with only one role waiting fills every seat from it. The tests importing the admission package or reckon.crew.queue_order add no failure against the base on all_debug. A one-hour reading of live passes before and after, from admission-verdicts.jsonl, is recorded in docs/evidence/fragments/the-escape-lane-and-reviews-keep-pace/role-cadence.html as evidence, not as the gate. The share extends the deficit round-robin weighted_project_order already runs over project weights (reckon/crew/admission/ordering.py), applied within each project's slice, so the project fairness it protects stays intact. It is not a second interleaver applied after it. It is computed in ordering before the launch loop, not inside the loop. Write paths: the admission ordering this needs and the new tests.

§7 — An admission pass is bounded, and says what each launch cost

Why. One pass ran 1,046 s launching. A pass that runs long holds every freed seat until it ends, and its stalls hide which step was slow.

Endpoint. A pass launches until a stated time budget (60 s by default, from flight) is spent, then ends and lets the next pass continue, so freed seats are filled within one pass's budget. Each launch records its own duration and its slowest step on the verdict row. Both extend the instruments that exist: the pass already records release_seconds, waits_seconds and launch_seconds (_record_stage_timings in reckon/crew/admission/service.py), and the budget is one deadline read at the head of the launch loop in reckon/crew/admission/selection.py. It is not a check threaded through the loop's exit paths, and a request the deadline leaves stays queued untouched for the next pass.

Done when. A run's gate can name the command and partition its arms run with

Why. nova's inverse-equilibrium-baseline §1 (r-20261113T162733537202-known-answer-recovery, head a32993c90e) passed its codex review at 117 of 120 and cannot land. crew complete --gate passed --land --wait refused twice, at 22:23 and 22:46 UTC on 14 November, with suite-delta-refused naming command_matches_suite_command and the revision matches on both arms. The lead ruled this gate runs on the H200, and those arms exist (jobs 1315504 and 1315628, the same two files, one identical pre-existing failure each, zero added) but their command differs, so they can never match. --waive-suite-delta is read in promotion_records._evaluate_suite_delta only for added failures, after the missing-fields refusal, so no flag reaches a mismatched arm. Each refused landing took about twenty minutes, submitted an all_debug job, and exited 0 under --wait.

Deliverable. A run's gate can declare the command and the partition its arms run with: the coordinator states them at dispatch, or a project declares them for a section in flight, and the landing measures with that command on that partition and compares the run's arms against it. A waiver for missing or mismatched arms is read before the missing-fields refusal, records its reason and the arms actually held, and never waives added failures. A refused landing returns as soon as it refuses, submits no measurement job it will not read, and exits nonzero under --wait. A run whose reviewed head is already an ancestor of the primary branch, merged by hand on the lead's decision as nova's a32993c90e was in 814f91c4b, is recorded through a supported verb: it writes the run's ledger row naming the merge that carried it, releases its pointer, worktree and claims, records its section landed so its waiters are released, and retires any pending-landing record so the pointer cannot be resurrected. It runs no suite-delta measurement, because the head is already on the branch. Three nova sections wait on it.

A stranded launch of a queued request goes back to the queue

Why. On 14 November queued requests vanished with no pointer, no run directory, no discard record and no ledger row: r-20261114T211520851719-review-of-bpq-one-call-queues-a-plan-98da3bf8578e, reckon-1e's r-20261114T175044608704-full-the-monitor-shows-the-work-it--s138, and a reckon-1e review of the wave-4 §10 run. The admission pass's _release_stranded_launches (reckon/crew/admission/launching.py) takes a launch whose span outlived STRANDED_LAUNCH_BOUND_SECONDS with its claim holder gone, records a refusal, and calls dispatch_claims._release_launch_claim, which removes the pointer and then the whole run directory. That is right for a launch nothing queued, such as a review the reflex composes and will compose again, but a coordinator's queued request launched by admission has nothing that dispatches it again: its brief, steering and request go with the directory. The admission verdicts record released-stranded-launch for twelve runs between 17:34 and 22:06Z that day. A launch is stranded most often when the admit service re-executes mid-launch: _request_claim_restored_on_refusal restores the request only on an Exception, so a re-exec skips it (D180), and the services re-executed near each vanishing.

Endpoint. A stranded launch that admission launched from a queued request is written back as that request, queued under the same run id with its brief and steering kept and a back-off stamped, and its refusal record names the abandoned attempt rather than the run, so the slow original attempt is still refused at its reservation while the re-queued request's next attempt is not. A stranded launch with no queued request behind it is released as now. A discard recorded for the run still releases it. Nothing that held a queued request is removed without a record a reader can find.

Done when.
