§1 — What loaded the storage, and why it is reckon's to fix

On the night of 2026-09-23 to 24 the login node 98dci4-srv-1006 reported a load average of 143 while vmstat read 95–98% idle. The load was processes in uninterruptible wait on the GPFS client (cxiWaitEventWait), and a single stat on a file in home took up to 8.5 s. The evidence, the per-session attribution and the recovery are recorded in imas-ambix's research note login-node-storage-contention (§1, §3, §6 and §7). This plan carries the part that belongs to reckon.

Most of the waiting processes were crew processes that no live session owned: ten followers for one nova session from 2026-09-16, three imas-efit followers, six per-project producers between 21 hours and 3.5 days old, crew dispatch and crew complete loops running full-tree git status walks, and a nova wave script still dispatching seven hours after its session stopped. Two unbounded searches ran as well: a bfs over /work/projects/imas_gpu for 13 h 50 min, and a find / over every GPFS mount for 10 h 49 min. As the crew processes and the first search were stopped, load fell from 143 to 15 and stat from 8.5 s to under 0.02 s. The find / was still running through that recovery, so it was not sufficient on its own. The causes cannot now be apportioned against each other, and each is stated here as contributing, not as the cause. The design defects in this plan stand either way, because each is a process that outlived the attention that started it.

The filesystem's weakness is known and accepted. A healthy GPFS stat costs about 250 µs against 3 µs on local disk, and every read of a file another node has changed needs a token round trip. What made it fail was the shape of the workload: processes nobody was watching, polling shared state and walking whole trees. Every one of them was started by a session that later ended, and none of them noticed. That is a property reckon can give its processes, which is what this plan does.

§2 — A follower that never held the registration never checks its owner

In reckon/cli.py, _check_consumer (around line 1953) returns at once when registration is None or not registration.held. Only after that return does it compare os.getppid() against the recorded parent. So a follower that streams read-only, because another follower holds the session's lock, never checks its consumer at all. a-follower-outlives-its-monitor §7 addresses the holder's half of this, by making a holder whose consumer is gone release the lock. No plan yet covers the read-only half. Each Monitor expiry that is re-armed while an older follower holds the lock adds one more read-only follower that will never exit. The ten nova orphans were 6:21, 5:17, 4:47, 3:42, 3:03, 2:29, 2:19, 1:48, 1:16 and 0:45 hours old: one per re-arm.

The fix is to check the owner's liveness on every wait-pass tick, independent of the lock. That is the same cadence at which _check_consumer already runs. The owner is fixed once, at the follower's first start, and nothing afterwards rewrites it. It is the pid and start time of the process that armed the follower. It travels in a dedicated environment variable, RECKON_FOLLOWER_OWNER, set once when the follower is armed and passed unchanged across a reload's re-exec. It is not read from the registration record. It is not stored inside RECKON_FOLLOWER_REGISTRATION either, because _adopt_inherited removes that variable at adoption and acquire() rewrites the record it carries, so an owner kept there would be lost at exactly the adoption this fix must survive. The reason is a takeover hole the read-back found. A read-only follower retries the claim on every tick (reckon/cli.py, the takeover of a registration whose holder has gone). acquire() in reckon/crew/runs.py then rewrites the whole record from the claimant's current parent (parent = os.getppid()). If that parent is init, _check_consumer returns before comparing anything, and the orphan becomes a holder that never exits. So acquire() also records the armed owner from the environment rather than os.getppid(), and a recorded owner of pid 1 or below is treated as gone, not as a reason to skip the check. A follower whose owner is gone exits on the next tick after the owner dies, whether or not it holds the lock, and a holder releases the lock as it does today. a-follower-outlives-its-monitor §7's holder release currently reads the recorded parent. Because this section edits the same function, _check_consumer, that release reads this owner once this section lands, leaving one definition rather than two. This is a live change to a landed mechanism, so §7's test stays in this section's gate.

Done when tests/test_follower_checks_its_owner.py, a new file, covers three cases under a stub parent that stands for the owner. First, a holder and a read-only follower for one session both exit on the tick after the stub parent is killed; the assertion allows one tick of scheduling slack and no more. Second, a follower re-executed for reload still exits after the original parent dies. Third, the owner stays alive while the holder exits and a read-only follower takes over the registration. The test asserts the taken-over record still names the original owner. It then kills the owner and asserts the follower exits on the next tick. tests/test_orphaned_follower_releases.py, §7's landed test, still passes. A mutation that restores the early return for a non-holder must fail the new test, and so must one that makes acquire() record os.getppid() again. The write paths are reckon/cli.py, reckon/crew/runs.py and tests/test_follower_checks_its_owner.py.

Outcome — the owner check runs on every wait pass, holding the lock or not. Commit 796583a4 feat(crew): a follower whose owner has died ends, lock or no lock. _check_consumer no longer returns before it compares the owner, so a read-only follower ends on the tick after its own owner dies. runs.follower_owner() resolves the owner once, at the follower's first start, from RECKON_FOLLOWER_OWNER when an armer stamped one and from os.getppid() exactly once otherwise, holding the value from that read onward so a later re-parent cannot move it. _FollowerRegistration.acquire() writes that owner into the record instead of os.getppid(), and a recorded owner of pid 1 or below is treated as gone rather than as a reason to skip — which closes the takeover hole where an orphaned read-only follower inherits a released registration and becomes a holder naming init. A reloaded image is handed the same owner through the environment its execve receives.

One deviation from the done-when's first case, disclosed. The case asks for a holder and a read-only follower armed by one stub parent, both leaving after that parent is killed. Written that way the case cannot show the defect: the one owner's death makes the holder leave and free the registration, and the read-only follower then leaves by taking that registration over in the same tick it acquires it, so with the early return restored it still leaves. The mask is exactly the scheduling slack the done-when forbids. The gate therefore arms two stubs, one per follower, and kills the read-only follower's owner first while the holder's owner stays alive — the orphan's real condition, one re-armed Monitor behind another. Both halves are asserted: the registration still names the holder when the read-only follower goes, and the holder leaves on its own owner's death.

Measured. Read-only follower, owner's death to gone: 0.811, 0.839, 0.905 s; holder: 0.185, 0.242, 0.185 s, against the gate's two-second bound. The gate over both files: 7 passed in 26.8 s at load average 3.9. All three declared mutations fail it against this commit's source, each reverted with the file verified byte-identical afterwards: the restored early return alone leaves the read-only follower running past the bound (1 failed, 6 passed); acquire() recording os.getppid() alone fails the takeover record (1 failed, 6 passed); and deleting the reloader's carry alone fails the re-parented reload case while the earlier reload case stays green (1 failed, 6 passed). The two declared together give 2 failed, 5 passed. Two controls guard the window: a live owner leaves the follower running and still the holder past the same two seconds, and the reload case confirms the image replacement from the replacement's own command line rather than inferring it. Section 7's landed test stays green in the same invocation. The exit bound is derived from the measurement, not chosen to be comfortable. Review found the first version's five-second bound too weak: the wait pass polls every 0.1 s, so five seconds admits fifty passes, and a regression that asked about the owner once every fifty passes would satisfy it while leaving a follower alive nearly five seconds after its owner died. Two seconds is 2.2× the slowest read-only sample — room for interpreter teardown and node jitter, about twenty passes rather than fifty — and the same two seconds is what the live-owner control has to survive for the window to mean anything.

The reload case could not see the owner carry, so it has its own case. Review measured the gap: execve does not change a process's parent, so a replacement reading os.getppid() reads the owner while the owner is alive and the reload case passes with the carry deleted. The carry is the reason a replacement does not adopt whatever process stands above it, so the new case reads the owner where the parent is not the owner: a subreaper process is started above the arming stub, the follower is held still, the stub is killed, the follower is adopted by the live subreaper — asserted from the process table — and only then is its source stamp advanced and the follower resumed, so the replacement resolves its owner after the re-parent. From the carried owner it is the dead stub and the replacement leaves; from os.getppid() it is the live subreaper and it never would. Measured 1.193, 1.220 and 1.240 s from the replacement becoming live to the process leaving, bounded at three seconds because that window carries the replacement's own import cost.

§3 — A producer holds a lease, not a lifetime

Per-project crew watch producers are detached with start_new_session=True and ppid 1 by design, and nothing ends them. On the night they were 21 h to 3.5 days old. The imas-codex producer used 21% of a core for three days with no run to watch, and the reckon producer 37%. The sample project's producer had lost its registration, so crew unwatch answered "no registered watcher" and it could only be stopped by pid. A producer with no consumers is pure cost, and one with no registration cannot be managed at all.

The fix has three parts. Each live follower renews a lease on its project's producer, and a producer whose lease has not been renewed for the lease interval stated below exits cleanly. The producer writes its own pid into its registration atomically at start, and rewrites it if the file goes missing, so crew unwatch can always find it. An idle producer backs off its poll interval instead of spinning. A follower arming for a project whose producer has exited starts one, as it does today, so the lease costs nothing in availability.

The lease interval is ten minutes, and it can be set. The default is 600 s. RECKON_PRODUCER_LEASE_SECONDS overrides it, so a test can use a lease of a few seconds. The idle back-off doubles the poll interval on each idle poll, starting from the producer's existing base interval, up to a cap of 30 s. It returns to the base on the first poll that sees a live run. The producer writes its current interval into its registration as poll_interval_seconds, which is what the test reads. The lease is checked on every wake-up, and no sleep outlasts the lease's remaining time, so a producer exits within one second of its lease lapsing however far its interval has backed off.

Done when tests/test_producer_holds_a_lease.py runs in a temporary RECKON_HOME with RECKON_PRODUCER_LEASE_SECONDS set to 3. It shows a producer exiting after its lease lapses with no follower attached, and one staying up for three lease intervals while a follower renews. It shows crew unwatch stopping a producer whose registration file was deleted under it. It shows an idle producer's recorded poll interval growing to the 30 s cap. The negative control is executed and logged: with lease expiry removed, the unattended producer is still running after three intervals and the test fails. The login-node check, that a project with no follower for an hour has no producer running, is a post-merge acceptance recorded in §8, not part of this node's gate. Order and write paths: the producer spans the crew watch and crew unwatch commands in reckon/cli.py, its loop in reckon/crew/recovery.py, and its spawn in reckon/crew/dispatch.py. So this section runs after §2, which also writes reckon/cli.py, and after a-dispatch-returns-without-its-worker §3, which writes dispatch.py. The write paths are those three modules and that test.

Two items settle before release (read-back review-of-the-producer-lease, 2026-09-24). M2: a reader has no way to see a lease renewal happen. The follower writes lease_renewed_at (UTC) into the producer's registration on each renewal, and the test reads that field, as it reads poll_interval_seconds. M8: the write paths also need reckon/crew/runs.py, where registrations are written, and the ordering clause names both files this section shares with §2, reckon/cli.py and reckon/crew/runs.py. On the fleet, the producer launch also takes a-dispatch-returns-without-its-worker §10's spawn path, so this section runs after that one.

§4 — Polling reads what changed, never the whole tree

git status --untracked-files=all is issued from reckon/crew/dispatch.py:5524, reckon/crew/routing.py:355 and reckon/ledger.py:895. Inside loops that live for hours, it becomes a full filesystem crawl every few seconds, and on GPFS each crawl lands on every other client. During the event, one git status --porcelain took 64 s. Dispatch also snapshots the worktree after launch, and over more than 300 retained trees that held one S20 dispatch for 3 h (reported by reckon-c4). a-dispatch-returns-without-its-worker §3 removes the hold from the dispatch's own lifetime. This section removes the walk itself.

imas-codex-10 measured the other half: of 68 worktrees registered on imas-codex, 39 were integrated, 28 had landed, one was a superseded draft, and about none were doing anything. Nothing in the crew surface prices a retained tree: it is free to create and free to hold, and its cost lands later in some other session's git. A faster walk only moves the wall to a larger count.

The fix: every polling call site asks git only for what it needs. That is tracked changes with -uno, or a status scoped to the node's declared write paths where untracked files matter, since the declared paths are the only place a worker may legitimately create one. Dispatch also applies back-pressure. Before it creates a worktree, it counts the project's retained worktrees whose heads are integrated and clean, and it reaps them without force. Integration is necessary but not sufficient. In imas-codex-10's hand reap, 2 of 39 integrated trees held a worker's untracked logs, and a published plan comment cites those logs by name. So the reap first preserves untracked content to a durable location, verifies it by file count, and removes it. Only then does the tree remove without force, because it is now genuinely clean, not because a refusal was overridden. Above a stated ceiling of live unintegrated trees, it reports the count in the dispatch output rather than silently adding one more.

Where the reap puts what it preserves, and how it removes. Untracked content goes to <config-home>/crew/reaped/<project>/<worktree name>/, keeping its paths relative to the tree root. Before removal, the file count there is asserted equal to the count read from the tree. The existing remover, _remove_worktree in reckon/crew/routing.py, passes --force. The reap uses a non-forced removal instead, so a tree that is not clean after preservation is refused and reported, never removed.

Done when exactly one call site passes --untracked-files=all: the boundary read of the run's own worktree, which keeps the untracked read. No other call site passes it over any tree, the run's own included. A test counts the git status invocations one dispatch-and-complete cycle makes and asserts that each is scoped. A dispatch into a project holding integrated, clean worktrees leaves fewer of them than it found, and never removes a dirty or unintegrated one.

One read keeps its untracked files. The boundary check of a run's own worktree still reads untracked files across that whole tree, not only under its declared paths. A file a worker creates outside its declared paths is exactly the out-of-fence write the check exists to catch, and scoping it away would pass the violation silently. What this section removes is the untracked walk over every other registered tree. A case plants an untracked file outside the declared paths in the run's own worktree and asserts the boundary check still reports it. Order: this section lands after a-dispatch-returns-without-its-worker §3 and after S19's the-boundary-check-reads-two-trees §1, which reduces the set of trees read. This section's invocation count is then measured on that reduced set.

§5 — Every storage read has a deadline

The MCP server is the interface and stays the interface. What failed was that its reads had no bound. One read_plan held imas-ambix-af's server blocked on GPFS for over 30 minutes, and imas-ambix-b6 measured 1806 s for a single read before the harness gave up. A tool that blocks for half an hour on a slow filesystem is not degraded; it is absent, and it looks exactly like one that is working.

The fix: every tool call runs its filesystem work under a deadline (proposed: 30 s for a read, 60 s for a write). When the deadline passes, it returns a typed storage-slow result naming the path it was waiting on and how long it waited, so the caller can distinguish a slow filesystem from a missing plan. One blocked read must not block the server, so a second call to a different project still answers. The serialization point is the MCP server, not the HTTP one. The HTTP surface is already a ThreadingHTTPServer (reckon/serve.py). The observed block was in reckon mcp. On 2026-09-23, one session's server sat in GPFS wait (cxiWaitEventWait) inside a read_plan, and every later tool call timed out behind it. That is consistent with the FastMCP server in reckon/mcp.py running a synchronous tool function on its one event loop. The node first confirms that from the installed SDK and records the finding in its manifest. If it holds, the node moves each tool's filesystem work to a worker thread under the deadline, so the loop stays free. If the SDK already runs synchronous tools off the loop, the hypothesis is wrong, and the node does not move anything on its strength. It reproduces the block with the section's blocking filesystem stub instead. It names the point where the second call actually waited, whether a lock, a shared client or the loop, and records it in the manifest. It applies the deadline and the release at that point. Either way the done-when's concurrent read decides. A write whose deadline passes reports whether it reached the file, since a timed-out write that did land must not be retried blindly.

Done when tests/test_mcp_reads_have_deadlines.py, a new file, is backed by a filesystem stub that blocks on one path. It shows a read of that path returning storage-slow within its deadline, and a concurrent read of another path answering normally. The write case reports its landed state in both directions. The test sets the deadline through a parameter, so it runs in seconds, not at 30 s. The negative control is executed and logged: with the deadline removed, the blocked read does not return within the test's bound, and the concurrent read waits behind it. The write paths are reckon/mcp.py, reckon/_mcp_tools.py and that test. A change needed in another module is named in the manifest as a follow-on.

Landed — every registered tool now runs off the event loop under a deadline

The hypothesis holds, and it is measured from the installed SDK rather than assumed. The venv runs mcp 1.28.1, whose server/fastmcp/utilities/func_metadata.py ends call_fn_with_arg_validation with if fn_is_async: return await fn(...) / else: return fn(...) — a synchronous tool body is called inside the coroutine, on the one event loop, with no thread offload. The serialization point is therefore the loop itself, and tests/test_mcp_reads_have_deadlines.py reproduces it against the SDK: a blocking probe registered on a bare FastMCP serialises a second call, so the free call enters only after the blocked one exits.

Each tool is registered as an async adapter (_deadline_tool) that runs the unchanged synchronous wrapper on a worker thread under a deadline — 30 s for a read, 60 s for a write, overridable through RECKON_MCP_DEADLINE_SECONDS. Passing the deadline abandons the thread rather than cancelling it (a blocked filesystem call cannot be interrupted) and returns a typed storage-slow result naming the path it was on and how long it waited, so a slow filesystem is distinguishable from a missing plan. A write result also carries landed, so a timed-out write that did reach its file is not retried blindly. Signatures are copied with annotations resolved, so the published argument model is unchanged and the synchronous wrappers stay directly callable.

§6 — An orphan is a process whose owner is dead

ppid 1 does not identify an orphan. A worker is reparented to init whenever its dispatch exits, and so are zellij servers and system services. imas-codex-0d's ppid-1 list this morning had 16 processes, none of them orphans. Selecting by the crew session id in ps output is closer, but a grep for it matches the shell running the check: its bash -c argv holds the whole script source, so bracketing the pattern is not enough when the same phrase appears in an echo or a comment. imas-ambix-f6 and imas-codex-0d each measured such a self-match. Every one of these selectors reads as authoritative and is wrong in some case.

The fix is to make ownership a recorded fact rather than an inference. Every process reckon starts carries its owner in its environment: the crew session id and the owning session's pid. That covers followers, producers, dispatch and complete loops, workers and their review nodes. reckon crew census reads that from /proc/<pid>/environ, which an argv grep cannot fake. It excludes its own ancestry by pid and lists every process whose owner is gone, with age, state, wait channel and working directory. With --apply it stops exactly the pids it listed, printing each one, and reports what it spared and why. Producers are owned by their lease (§3), not by a session.

Done when the census, run on the login node after a working day, lists zero reckon processes whose owner is dead. A test plants one owned and one ownerless stub, plus a stub whose argv contains the session id but whose environment does not, and the census lists exactly the ownerless one and never its own shell.

A swept pointer is completed, never discarded. This rule is imas-codex-10's. Any automated sweep of stale live pointers, the census's --apply included, completes each one with a failure classification, for example --gate failed --failure-classification infrastructure-failure with a --no-commit reason naming the sweep. It never uses crew discard. Both free the member, but only completion leaves a ledger row, so a discarded run disappears from every later count of what failed and why. A case sweeps one stale pointer and asserts that a ledger row exists for it, carrying the classification.

§7 — The skills say what a session owns and when it ends

Guidance cannot replace §2–§6, but three failures were instruction failures, and they recur until the skills name them. The reckon-ship skill and the Claude Code harness reference gain the following:

  • One follower per session, stopped before it is re-armed, and a session-end step that runs reckon crew census for its own session.
  • No backgrounded dispatch loop or wave script. A wave is a sequence of dispatch calls in the coordinator's own turns, so it ends when the session does. A nova wave7.sh kept dispatching for seven hours after its session stopped.
  • A search names its subtree or absolute path and is bounded on the producer side, with timeout or -maxdepth. | head is not a bound: it limits the output, and a search that finds nothing is exactly the one that then walks the whole tree. That is how find / -name wall.h5 | head ran for 10 h 49 min. A brief names the absolute data path rather than describing the file, since a described file is what sends a worker searching.

A backgrounded tool call is silent from its two-minute boundary until it dies, so its owner has usually moved on. The harness offers no heartbeat for that. The host dashboard in imas-codex's host-dashboard-covers-every-agent-process carries it instead, as a per-session list of long-running background processes.

Done when the three rules above are in the reckon-ship skill and the Claude Code harness reference, each beside the measurement that motivates it.

§9 — A dispatch holds while the lane is paused

During the engine relaunch of 2026-09-23 to 24, the local lane was paused by a message to every session, and holding relied on each coordinator reading it. A follower's automatic review sweep reads no messages, so until this section lands it dispatched anyway. nova-cc's sweep did exactly that and had to be stopped by hand. imas-ambix's local-lane-admission-control §11 makes the router enforce a pause declared in its gate file. The contract below names that file; lane.json only republishes the pause. This section is reckon's half: a pause declared in the gate file is a fact dispatch reads, not a message it must be told.

What a paused dispatch returns. It is neither a launch nor a refusal. The result is ok: false with error: "lane-paused" and exit status 75, the conventional temporary failure. A caller that branches on the error can tell it from a refusal and retry after the pause. No pointer and no worktree are created. The result names the gate file and its paused field, and carries the file's reason when one is present. A paused gate with no reason is valid, and the result then carries none. The sweep shows the run as waiting on the lane pause, a state with no pointer. It is deliberately not called held, because held already names a live run that has a pointer.

The contract, from imas-ambix local-lane-admission-control §11 (merged at imas-ambix bc8fd549, in imas_ambix/agent/router.py). The authority is the gate file /home/ITER/mcintos/public/imas-ambix/router-gate.json, a JSON object. Its paused is a JSON boolean, and its optional reason is a string. The router re-reads it about once a second. imas-ambix agent pause --reason X writes paused: true with the reason, and agent resume writes paused: false. lane.json mirrors that fact as router_generation_gate.paused and .reason, but only when refreshed. It can be stale when the router is down, and it carries no paused key until the router is restarted onto the pause code. So dispatch reads the gate file, never lane.json. The read has a deadline of 5 s: a single stat on this filesystem took 8.5 s on 2026-09-23. Each result carries a lane_gate object stating the row that applied. The rule is:

  • no gate path declared in flight config: the dispatch proceeds, and lane_gate.state is not-declared. This is a host or backend with no router;

§11 — A live producer reads only what changed since its last poll

The defect. §3 ends a producer that nobody uses. §4 stops whole-tree git status walks. Neither covers a producer that is legitimately alive, and that producer is itself expensive. The per-poll cost comes from the design, not from a bug.

Measured on 2026-09-24 at about 21:15 on the fleet node (clu-2058, job 1277272). One reckon crew watch --project reckon producer (pid 853019) served one follower and nine clive workers. It held 60–66% of a core continuously for more than 13 minutes, while the rest of the 28-core node sat 86–98% idle.

The mechanism, read from the code. watch_ticker (reckon/crew/recovery.py, the loop that serves watch_follow with transitions=True) polls every poll_interval=1.0 second. It skips the sleep entirely whenever a poll yields events. On every poll it rebuilds the whole fleet from nothing:

  • list_live re-reads every pointer file;
  • _watch_snapshot, called per run, re-reads the manifest;
  • observe_log (reckon/_backends.py) re-opens the run's stream.jsonl and parse_events JSON-decodes every line from the start;
  • _commits_beyond_base spawns a git rev-list --count in the worktree.

The streams are append-only and 1–2 MB each, so the cost per poll grows with every worker's transcript, and is paid once a second forever. A 10-second py-spy sample splits the time as follows:

  • 51.5% in parse_events ← observe_stream ← observe_log;
  • 26.8% in crew_watch;
  • 9.6% in parse_events ← crew_watch;
  • 4.1% in the dialect's observe fold.

An 8-second strace counted 43,302 read, 4,314 openat, 1,500 getdents64 and 16 subprocesses. Each git exec first walks about ten EasyBuild PATH entries. On the login node these reads land on GPFS home, which is how a producer turns into storage load for everyone.

The fix: state is carried forward, and work is gated on change.

  1. Incremental stream reads. The producer keeps a cursor per run holding the stream's inode, byte offset and parsed events so far. Each poll parses only the complete lines appended since the offset; a partial trailing line waits for the next poll. It re-parses from zero only when the inode changes or the size drops below the offset, which means the stream was replaced or truncated. The dialect's observe fold then runs over the cached events. At 4% of the cost it can stay a full fold, and it becomes incremental only if a measurement says so.
  2. Stat-gated snapshots. A run whose pointer, manifest, stream and exit-record mtimes and sizes are all unchanged reuses its previous snapshot. Only the time-derived fields (quiet seconds and stall) are recomputed, and those come from the stat. A stat is the only storage touch an unchanged run costs.
  3. Git keyed by head. The commits-beyond-base count is cached against the worktree's resolved HEAD sha, read from .git without a subprocess. It is recomputed only when the head moves. The executable is resolved once per process, not once per exec.
  4. One reader, many consumers. The producer publishes its folded snapshot, and crew(view="live") and the follower read that, not the streams. That way a coordinator's MCP read never re-parses nine transcripts.

The 1-second base interval stays, because a stat per run per second is cheap. §3's idle back-off still applies when no run is live.

  • the bytes parsed per poll equal the bytes appended since the last poll. The producer records this as bytes_parsed_last_poll in its registration;
  • a poll over unchanged runs parses zero bytes and spawns no subprocess;
  • a truncated or replaced stream is re-read from zero and observed correctly;
  • the transitions it yields are identical to the full-recompute path over the same sequence of files.
