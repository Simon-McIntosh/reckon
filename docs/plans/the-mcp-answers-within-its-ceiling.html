The MCP answers within its ceiling

Three coordinators running sprints on the compute node on 2026-09-24 each fell back from the reckon MCP tools to bash and jq, for the same two reasons. Some answers were too large for the transport. Others were too coarse for the question. The rule in reckon-build is that every routine read is an MCP call. This plan makes that rule something the tools can actually carry.

§2 — A sprint summary names its pending plans

A coordinator asks the summary view one question: which of this sprint's plans are still open, and which of them can start. Today, a sprint-scoped summary returns only counts. So the coordinator either asks for detail, which overflows, or parses the sprint HTML. The summary should carry one compact row for each pending plan in the sprint. Each row gives the slug, the status, impl, whether the plan is ready, the ids of whatever blocks it, and the ids of its sections still declared implementable. It carries no prose.

Done when:

  • A test builds a synthetic project whose sprint holds one shipped plan, one ready plan and one blocked plan. It asserts that roadmap(project, sprint=X, view="summary") lists exactly the two pending plans, carrying those fields.
  • The shipped plan is absent from the list. This is the negative case.
  • A summary read without sprint is byte-identical to its output before the change.
  • The recorded length of roadmap(project="reckon", sprint="S22", view="summary") at the integrated head is under 20,000 characters.

§3 — No read overflows the transport

An answer too large for the transport does not arrive at all. The coordinator gets nothing it can act on, and a second call fails the same way. Every MCP read tool (roadmap, read_plan, crew, audit) should measure its serialised answer against a response budget. The budget is configurable, defaulting to 80,000 characters. An answer over the budget comes back bounded, with a truncated block that says what was left out and which arguments would narrow the read (narrow_with), instead of the overflowing whole. An answer within the budget is unchanged.

Done when:

  • Tests size synthetic fixtures over the budget for roadmap detail, crew scopes and crew live. For each, they assert that the serialised answer is within the budget and carries a non-empty truncated.narrow_with.
  • A fixture under the budget returns exactly what it did before the change.
  • The declared mutation is applied: the budget check is removed. The over-budget tests are then observed to fail, and the log of that run is recorded.

§4 — A crew read returns the fields it was asked for

The fields argument is accepted by crew(view="live") and then ignored. crew(view="runs") honours fields, but it refuses the three fields coordinators check first. After this section:

  • live rows carry exactly the requested fields plus the run id.
  • runs accepts log_age_seconds, commits_beyond_base and manifest_reported_status, drawing them from the same classification live already computes.
  • An unknown field is still refused, and the refusal names the accepted set.

Done when: tests assert all three behaviours on a synthetic config home with two live runs. The live-view test fails when the projection is removed. That failure is observed and its log is recorded.

Outcome — a crew read returns the fields it was asked for. Commit 39dee90a feat(crew): honour requested fields on the live view projects a narrowed live read to the requested fields plus run_id, and widens the accepted field set with log_age_seconds, commits_beyond_base and <manifest_reported_status so runs accepts them from the same classification live computes.

Measured

  • All three behaviours asserted on a synthetic config home with two live runs, head 39dee90a against base a130260c: crew(view="live", fields=["classification","node"]) returns rows whose key set is exactly {run_id, classification, node}; an unknown field is refused naming the accepted set; and a runs read with source="live" returns the three fields equal to classify_pointer for the same pointer, populated from a real git worktree and log file. 3 passed.
  • The declared negative control is executed and logged: removing the fields projection from the live arm makes the projection test fail, the row key set growing from three to the whole classification.
  • No new lint findings in the three edited files against base a130260c (21 against 22 at base).

§5 — A single-run read answers in two seconds

crew(view="runs", run_id=…) hit the 30-second storage-slow guard for a run that is one directory on disk. A lookup by run id should read that run's pointer and its ledger row, and nothing else.

Done when:

  • The slow call is first reproduced, and its cause is named with a measurement (which files it opens, and how many).
  • A test with a synthetic ledger of 2,000 rows asserts that the run-id path opens no more than a small fixed number of files, and says what that number is.
  • A recorded timing of the same call against this host's reckon project, at the integrated head, is under 2 s.

§6 — A plan can be read one section at a time

Reading a single section today means pulling the whole plan or parsing HTML in bash. read_plan(view="section", section="s3") should return that section's heading, its plain text, its HTML, its declaration and the comments anchored to it. Discovery search should match the plans whose body text contains the query, not only sprint rows.

Done when:

  • Tests on a synthetic plan assert the section payload for a present section.
  • An absent section is refused with a named error.
  • A search whose term appears only in a plan's body returns that plan.
  • The section view of a real reckon plan at head is recorded, and its length is recorded beside the length of the raw view.

§7 — A section's declaration and position can be written alone

edit_plan should accept set section_declarations.<id>. It should also accept an op that inserts a new section before the structured-state regions, so that adding a § no longer means anchoring on unrelated prose.

This section waits on section-contract-and-computed-impl §1. That plan turns a section into a typed record. The S22 coordinator plans to dispatch it next, and it writes the same parser and op table. The gate below holds this section closed until that record lands, so the two are not built against each other.

Done when:

  • Tests assert that a dotted declaration set changes one key and preserves the rest.
  • An inserted section lands before the first data-reckon region, with the plan still passing reckon audit-doc.
