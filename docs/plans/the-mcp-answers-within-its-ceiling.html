The MCP answers within its ceiling

Three coordinators running sprints on the compute node on 2026-09-24 each fell back from the reckon MCP tools to bash and jq, for the same two reasons. Some answers were too large for the transport. Others were too coarse for the question. The rule in reckon-build is that every routine read is an MCP call. This plan makes that rule something the tools can actually carry.

§2 — A sprint summary names its pending plans

A coordinator asks the summary view one question: which of this sprint's plans are still open, and which of them can start. Today, a sprint-scoped summary returns only counts. So the coordinator either asks for detail, which overflows, or parses the sprint HTML. The summary should carry one compact row for each pending plan in the sprint. Each row gives the slug, the status, impl, whether the plan is ready, the ids of whatever blocks it, and the ids of its sections still declared implementable. It carries no prose.

Done when:

  • A test builds a synthetic project whose sprint holds one shipped plan, one ready plan and one blocked plan. It asserts that roadmap(project, sprint=X, view="summary") lists exactly the two pending plans, carrying those fields.
  • The shipped plan is absent from the list. This is the negative case.
  • A summary read without sprint is byte-identical to its output before the change.
  • The recorded length of roadmap(project="reckon", sprint="S22", view="summary") at the integrated head is under 20,000 characters.

Landed 2026-09-25 at 20258e3a, base a130260c. A sprint-scoped summary now carries pending_plans: one compact row per pending plan, with the slug, the status, impl, readiness, the blocking ids and the implementable section ids. The row is projected from the report already and carries no prose. Section ids come from the plan file when the inventory row carries none, because the MCP inventory whitelist drops the plan's declaration — without that fallback the column would report a false zero for every plan. The no-sprint summary is unchanged, proven byte-for-byte against the base tree, and the shipped plans stay absent because they are already terminal. Measured: the S22 summary is 8,294 characters over 45 pending rows, against the 20,000-character bound; the gate is 6 passed and the existing roadmap suite is unchanged at 78 passed. §3 — No read overflows the transport

An answer too large for the transport does not arrive at all. The coordinator gets nothing it can act on, and a second call fails the same way. Every MCP read tool (roadmap, read_plan, crew, audit) should measure its serialised answer against a response budget. The budget is configurable, defaulting to 80,000 characters. An answer over the budget comes back bounded, with a truncated block that says what was left out and which arguments would narrow the read (narrow_with), instead of the overflowing whole. An answer within the budget is unchanged.

Done when:

  • Tests size synthetic fixtures over the budget for roadmap detail, crew scopes and crew live. For each, they assert that the serialised answer is within the budget and carries a non-empty truncated.narrow_with.
  • A fixture under the budget returns exactly what it did before the change.
  • The declared mutation is applied: the budget check is removed. The over-budget tests are then observed to fail, and the log of that run is recorded.

Landed 2026-09-25. Commit 9e02b5f6 adds one post-deadline response boundary for all four registered MCP reads. It measures compact serialised characters against RECKON_MCP_RESPONSE_CEILING (default 80,000), returns values that fit without changing them, and replaces an oversized value with a bounded truncated receipt carrying omitted counts and actionable narrow_with arguments. Crew recovery writes are outside that read boundary.

The focused MCP gate passes 80 tests. The synthetic over-budget fixtures measured 11,883 characters for roadmap detail, 8,398 for crew scopes, 28,383 for crew live, and 13,150 for both read-plan and audit before the repair. Removing the common budget call makes all five oversized cases fail while three controls remain green. At the committed head, the real S22 roadmap detail is 307,123 characters before bounding and a 322-character receipt after it. The inherited I001 at reckon/mcp.py:51 is gone; that file has 18 lint findings against 19 at the base, with none in the new module or test.

Evidence: response-budget landing record.

§6 — A plan can be read one section at a time

Reading a single section today means pulling the whole plan or parsing HTML in bash. read_plan(view="section", section="s3") should return that section's heading, its plain text, its HTML, its declaration and the comments anchored to it. Discovery search should match the plans whose body text contains the query, not only sprint rows.

Done when:

  • Tests on a synthetic plan assert the section payload for a present section.
  • An absent section is refused with a named error.
  • A search whose term appears only in a plan's body returns that plan.
  • The section view of a real reckon plan at head is recorded, and its length is recorded beside the length of the raw view.

Outcome — one section can be written without replacing its neighbours. Commits 25845dc8 and 0b3cd08c accept set section_declarations.<id>, validate the value against implementable, deferred and done, and changes only the addressed declaration. If that id has an opt-in typed section record, its duplicated status moves with the declaration so the record remains schema-consistent.

The new insert_section state operation accepts an id, a title and an authored HTML body. Its version-checked write places the generated h2 block immediately before the first structured-state collection. A data-reckon="section" element is adjacency metadata, not an insertion boundary: the scan skips every such record, so the new heading lands after the last typed section record and before gates, decisions, followups or comments. The op travels from application to the locked write in a request-local effect list tied to the exact validated state object; validation_diagnostics remains state and can never execute an insertion.

Four authored-fragment refusals are asserted by name: an existing id returns section id 's2' already exists; a body containing an h2 returns insert_section body must not contain another h2; a section[data-reckon] returns insert_section body must not contain structured plan state; and a plan-* meta returns insert_section body must not contain plan metadata. Each refusal leaves the file byte-identical.
