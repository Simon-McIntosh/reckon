§2 — A plan with section declarations derives its impl from them

Deliverable. When section records cover every declaration, impl stays the effort-weighted figure it is today, with impl_source: computed as now (reckon/_plan_html.py:1128). When they do not, impl is derived from the declarations by count (done over done plus implementable, deferred excluded) and the parsed state says so with a third value, impl_source: declarations, added to the schema's enumeration (reckon/_schema.py:112) and to the values the plan-review reader documents (reckon/crew/plan_review.py:122); the authored meta stands only for a plan with no declarations, with impl_source: authored. A plan with an implementable declaration therefore never reads 1.0. reckon audit-doc reports impl-meta-stale (warn) when the meta on disk differs from the derived figure by more than 0.01, so a reader of the file and a reader of the server agree once the next write lands. Every caller of derive_impl_from_sections is moved with it: both impl_source assignments in reckon/_plan_html.py (lines 1125 and 2234), the reader at line 1939, and the authoring refusal at reckon/_store.py:2606, which keeps refusing an authored impl only in the covered case, so a coordinator's impl write on a partially recorded plan is still accepted and the audit flags it stale. The section adds one schema value and one audit code; nothing retires, because no existing value or code reports a figure derived from declarations.

§7 — A section gate holds its sections, not the plan

The roadmap reports a plan blocked when any of its execution gates is unpassed, including a gate whose gated_sections names one later section. In reckon/roadmap.py, the readiness pass builds gate_blockers from unpassed_gate_blockers(execution_gates(plan)) and lets any entry clear is_ready and set is_blocked, whatever sections the gate names. Measured on 2026-10-10: this plan and the-codebase-is-reviewed-between-nodes both read effective_status: blocked while their first sections were running, each because of a gate on one later section (comment c-gate-blocks-plan-1010). The wiring rules in the reckon-create and reckon-edit skills recommend a gate over a plan-level depends_on because a gate holds only the section it names. The roadmap undoes that, so the advice produces the misreport it was meant to avoid.

Deliverable. A gate whose gated_sections is non-empty holds those sections only. A gate that names no sections holds the whole plan, as it does today. A plan that declares no implementable section outside the sections its unpassed gates name is held by those gates, and that includes a plan with no section declarations at all. A gate holds only its sections when the plan declares at least one implementable section that no unpassed gate names. This keeps tests/test_roadmap.py::test_gate_verdict_blocks_and_releases_downstream_sections_without_status_edit true as written: its plan gates deployment and release, declares no sections, and reads blocked. One function beside execution_gates in reckon/roadmap.py splits a plan's unpassed execution gates into the ones that hold the plan and the ones that hold only some of its sections. All three readers that today pass unpassed_gate_blockers(execution_gates(plan)) into effective_status call it instead: the roadmap's readiness pass, the served plan composition in reckon/serve.py (which the plan page and fleet index read), and the MCP plan view in reckon/mcp_views.py. Only plan-holding gates enter gate_blockers and the blocker list effective_status reads. Section-holding gates are reported in a separate field on the same row, each with the sections it holds. Nothing retires, because no reader scopes a gate to its sections today.
