§1 — A page waits for the whole derived fleet, and a restart forgets it

The discovery repair removed the quadratic parse, and warm /_discover fell below 1.5 s at load average 8 to 12. The operator restarted reckon.service at 20:18 CEST on 2026-09-23 to pick up that plan's §7. The site was then unreachable for about 5.5 minutes, and afterwards /_discover/imas-efit did not answer within 120 s and /crew took 27 s. The login node stood at load average 169. The operator's requirement, in their words: lazy load the plans and thumbnails with only metadata loaded quickly on startup or refresh, make refresh lightning quick and also unnecessary, and keep the site in sync automatically.

Five causes, each measured or read from the code on 2026-09-23:

  • The server listens only after it has watched every tree. main calls start_fleet_change_watch before serve_forever, and each _ProjectChangeWatch walks its tree with os.walk. py-spy dump at 20:20 put the main thread in _watch_tree, at islink, with 10 of 13 trees done, and the port refused every connection until the walk finished.
  • Every cache lives in process memory. The per-file parse memo, the discovery cache and the git-history memo start empty after a restart, so the first request for each project re-reads every plan, evidence and figure file from the shared filesystem.
  • One response carries everything, and nothing paints before it. /_discover/<project> returns every row together with the roadmap, the ready set, readiness state, live crew runs, git creation times and review state. That is 5.5 MB for nova, and the SPA renders nothing until the whole response arrives.
  • A change means a full reload. /_changes/<project> emits only a content digest, and the SPA answers each event by fetching the whole /_discover payload again.
  • Thumbnails are full-size figures. The figure list draws each row's image at 50 by 34 pixels from the original file. Loading lazily defers the download but does not shrink it.

§3 — A metadata index survives a restart and answers in milliseconds

The server keeps one metadata index per mounted project on disk, under the configuration home's cache directory. Each row carries the fields a list needs: slug, href, type, title, status, sprint, archived, created and edited stamps, and figure dimensions. It also carries the stat identity of the file the row came from. At startup the index is read, and each file is re-parsed only when its stat identity differs from the recorded one, so a restart costs stat calls rather than reads. The change watch updates the rows of the files it reports. A new endpoint /_index/<project> serves the rows and nothing derived: no roadmap, no readiness, no live runs.

§12 — A served log keeps the home it started under

Why. Measured 2026-10-21: one run of tests/test_cross_node_writes_refresh_the_index.py::test_an_open_stream_receives_the_added_row_and_stays_open alone, from the main checkout, added two /_changes/sample lines to the live served log (83 such lines before, 85 after). Every unfenced test run leaves such lines in the log the lead reads, the coordinator's population arms included. The same per-call resolution lets a test process rotate the operator's log. The servers that leak are bare ThreadingHTTPServer objects a test builds itself around serve.Handler (tests/test_cross_node_writes_refresh_the_index.py near line 206), which never pass through the served entry point, so a binding made only there would not reach them.

§13 — A changed directory re-scans only itself

Why. Measured on the live service on 2026-10-22, right after it re-executed at 20:18:50 UTC with every project's persisted index on disk: /_index/reckon did not answer within 120 s, and py-spy caught its request thread in _walk_covered (reckon/metadata_index.py). The served read reaches it like this. /_index/<project> calls _served_index_rows (reckon/serve.py), which calls index_rows with revalidate left false. On a process cache miss, which every read after a restart is, index_rows hands build_index no covered set, and build_index walks the whole tree. The persisted file set and its directory identities are consulted only on the revalidate path, through _reuse_covered, and even there any one moved directory sends the read back to a full walk. reckon's docs/ holds 2,514 directories, and docs/state/reckon alone 9,983 files, of which 2 are HTML. Crew records under it change every few minutes.

Deliverable. The shared covered-set reuse, _reuse_covered, stops being all or nothing, and every reader of the covered set goes through it: a build with no covered set handed in, which is the cache-miss read that serves /_index, the revalidate path, and the discovery signature that /_discover and the change stream read through _covered_files_for_project and _covered_files. When a persisted index exists, the covered set comes from it. Directories whose recorded identity is unchanged keep their persisted files. Only the directories whose identity moved are scanned, together with any new subdirectory found in them, and a recorded directory that no longer exists drops its files and its descendants. The build then persists the identity of every directory it covers, the unchanged ones as recorded and the scanned ones as observed, so the next cold read starts from the whole shape. The full walk stays for a project with no persisted index. The covered set this produces is the one a full walk would produce, because a directory's identity moves whenever an entry is added to it or removed from it.

Done when a new tests/test_a_changed_directory_rescans_only_itself.py builds a temporary tree of nested directories with HTML files, persists its index, clears the process cache to stand in for a restart, and reads through index_rows with revalidate false, the served path. It proves, each with its own control: (1) a file added to one deep directory, of a type the index does not cover, leaves the rows unchanged, and the read scans exactly that directory, counted with a spy on os.scandir.
