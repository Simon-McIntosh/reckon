§1 — Two surfaces, one project, two answers

Reckon stores two facts about plan scheduling in two places each, and different read paths consult different copies. Nothing reconciles them, so a caller's answer depends on which function they happened to call, and the audit's own findings are in part a report of reckon disagreeing with itself rather than of anything wrong in the project being audited.

The first fact is which sprint a plan belongs to. It is written as <meta name="plan-sprint"> on the plan, and again as an entry in that sprint resource's items[]. roadmap picks a plan up from the scalar; the audit checks membership against the item list. A plan carrying only the scalar is therefore scheduled and missing at the same time.

The second fact is which sprint is active. roadmap reports the sprint whose stored status is active, which is what the push op maintains. read_plan(project, "index") instead calls _derive_default_sprint_focus in reckon/project_state.py, which walks composed order and returns the first sprint holding any unfinished item. That walk never reads sprint status at all, so the op's own record is ignored and a closed sprint can be elected.

§2 — The legacy aggregate is not the cause, and this must be recorded

The obvious suspect is the superseded aggregate at docs/state/<project>/index.json, which is still on disk and still contains sprint rows. It is not being read, and a session that assumes it is will repair the wrong file. This was checked on imas-ambix rather than assumed.

That aggregate lists sprints S0 through S23 and contains no S24, S25 or S26 at all, and its stored active_sprint_id is S17. Both roadmap and the audit report S24, S25 and S26, and both treat S24 as the pushed sprint. A reader of the frozen file could not produce those answers, so neither surface is reading it. The migration marker at docs/.reckon/project-state-migration.json confirms format: distributed, status: complete, and the composed read path returns source_format: "distributed".

So both copies of both facts live inside the distributed store. That is worse than a stale legacy file, because there is no obviously-retired artifact to delete and no reader is doing anything wrong. It also means the fix cannot be "finish the migration" — the migration is complete.

The frozen aggregate is still a trap for the next reader, and §4 disposes of it separately from the defect proper.

§3 — What was measured

All of the following were read from live projects on 2026-09-23, from the stores and the source rather than from a plan's description of itself.

ObservationWhere
A plan declaring plan-sprint=S24 and absent from S24's items[] appears on S24's critical path at 4.2 h and is simultaneously reported plan-sprint-missing-item. imas-ambix, local-lane-admission-control
Three further plans declared a sprint whose item list never held them, so live work at impl 0.92 and 0.83 was invisible to every sprint-scoped roadmap for weeks. imas-ambix S17
The inverse also occurs: a plan held as a member of one sprint while its own scalar named a different one. imas-ambix, mast-machine-configuration-map
read_plan(index) elected a shipped sprint as the active one, because a member slug that does not resolve has no status and str(status or "") is not in COMPLETED_STATUSES. imas-ambix, elected S1 against pushed S24
The same election picked a done sprint with no dangling members at all, purely because status is never consulted — so the two causes are each independently sufficient. reckon, elected S12 while S16 and S18 both carry active

The last row carries a second finding that belongs to whoever schedules reckon rather than to this plan: two sprints hold active simultaneously, which the audit reports at error severity as multiple-active-sprints and which is its only blocking finding. Two actives cannot arise from the push op, which promotes and demotes in one versioned write; they arise from a bare set on status. That matters here because a derivation that reads status is only as good as the invariant behind status, so §5 covers the write as well as the read.

§4 — The repair

The shape of the fix is that each fact gets one authority and every surface resolves through it. Which copy becomes authoritative is the decision below, and it is not obvious in both cases, so it is recorded rather than assumed.

For membership, one record must derive from the other rather than both being authored. Whichever direction is chosen, the composed read must expose a single answer and the audit must stop comparing two independently-authored copies. While both remain writable, a session that sets one and not the other creates a plan that is scheduled and missing at once, which is the failure mode that hid live work for weeks.

For the active sprint, the composed read must consult stored status rather than walking composed order. The push op already maintains the invariant that makes this well defined; the derivation simply does not read it. Where the invariant is broken and two sprints carry active, the read has no correct answer and must say so rather than choosing — a deterministic pick makes the violation survivable, and a violation that is survivable stops being maintained.

Independently of both, an unresolvable member slug must be reported as a broken reference rather than silently counted as unfinished work. That single line is what let a shipped sprint win an election, and the same latent behaviour will distort any future reader that counts unfinished items.

Finally the frozen aggregate should be made unmistakable — moved, renamed, or given a refusal on read — so that a session investigating a membership question cannot mistake it for the store. It is correctly ignored today and it cost one session a detour anyway.

§5 — Done when

A plan's sprint membership has exactly one authored record, and a plan that names a sprint is either a member of it or reported as an error — never both scheduled and missing. roadmap and the audit return the same membership for every plan in a project, demonstrated on a project that currently disagrees.

read_plan(index) and roadmap return the same active_sprint_id, that value is the sprint whose stored status is active, and a project with no active sprint or with more than one gets an explicit answer rather than an elected one. A regression test covers a closed sprint appearing earlier in composed order than the pushed one, and a second covers a sprint carrying a dangling member slug: the first must not be elected, and the second must be reported as a broken reference while the pushed sprint is still returned.

Writing status directly cannot create a second active sprint; the path that can maintain the invariant is the only path that can change it.

Neither test may read its expected value from the constant the code under test reads — the circular-assertion shape already recorded against the telemetry spine.

§ Decisions

Which record is authoritative for sprint membership — the plan's scalar, or the sprint's item list?

What should the composed read return when the one-pushed-sprint invariant is broken and two sprints carry active?

What happens to the superseded per-project index.json now that the migration is complete?

§ Followups

Settle the three authority decisions before any code moves

All three decisions in this plan change what the repair IS, not merely how it is written, so none of the sections can be dispatched until they are locked. The membership one is the load-bearing choice: whichever record becomes derived stops being writable, and callers that set it today will need to change.

The active-sprint half has a measured constraint worth carrying into the decision. Reckon's own state currently violates the one-pushed-sprint invariant, with S16 and S18 both marked active, which the audit reports at error severity as its only blocking finding. That is not a hypothetical for the ambiguity decision, it is the live condition the read must answer in today.
