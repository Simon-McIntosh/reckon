§1 — Why: 125 kills nobody can date

Fleet job 1313886 ran for 2.7 days under a 96 GiB limit and the scheduler recorded 125 out-of-memory kills against it. It was not memory that ended it: a gate log overwrote the shared interpreter (imas-ambix:a-gate-log-overwrote-the-shared-interpreter). But a node that sits at its limit and loses a process every half hour is a defect of its own, and its successor held 57 GB of 144 GB after fifteen hours. The measurements are in what fills the fleet node's memory.

§2 — Every memory kill is dated and the series outlives the job

Why. 125 kills happened and not one can be placed in time, so none can be tied to what was running. Every other section here is steered by what kills what.

Deliverable. Each one-minute health sample carries the job's memory in use, its limit and its cumulative kill count, so a kill is dated to the minute it happened, and the process table saved nearest to a kill is kept with it. A change in the count becomes an obligation naming the minute and the largest processes at that sample.

Done when. A test feeds the sampler a stand-in cgroup whose kill count rises from 3 to 5 between two samples and finds the second row carrying 5, an event dated to that sample, and a retained process table for it; an unchanged count raises nothing. Negative control: with the count field absent the event is not raised and the test fails. In a rehearsal allocation of 2 GiB on all_debug, a stand-in that allocates past the limit produces a dated event within two minutes. The test runs on all_debug with at most -n 4; importers add no failure against the base. Write paths: bin/fleet-health, reckon/crew/fleet_supervisor.py, tests/test_fleet_health.py and tests/test_a_memory_kill_is_dated.py.

§3 — Test processes on the fleet node are counted, and the count is zero

Why. Worker gates are the largest verified user of the node's memory that should not be there at all. A worker that runs its test command directly runs it in the fleet allocation; nothing places it elsewhere and nothing sees it. This section waits on the composed gate command of a-worker-or-its-job-cannot-overwrite-shared-files §7, which gives a worker a gate that runs on a partition; this section measures that it does.

Deliverable. Each health sample counts the test-runner processes inside the fleet allocation and their resident memory, by the run that started them, apart from a focused run within the stated light bound. A count above zero is an obligation for the owning run's coordinator naming the run and the command.

Done when. A test gives the sampler a process table holding two test-runner trees under two runs, one focused run inside the light bound and one non-test service whose command line contains the word pytest as an argument: it counts two trees with their bytes, attributes each to its run, and counts neither the focused run nor the service. Negative control: a matcher on command text alone counts the service and fails. Over 24 hours on the live fleet after the composed gate command has landed, the count is zero in at least 99 % of samples, against 12 trees and 12.4 GB in the reference sample. Runs on all_debug; importers add no failure against the base. Write paths: bin/fleet-health, reckon/crew/fleet_supervisor.py and tests/test_fleet_test_processes_are_counted.py.

§4 — Session scratch is not charged to the job's memory

Why. The supervisor points each session's scratch at /dev/shm, which is memory. Every file a session writes there is charged to the job as if it were a process, and one session held 1.59 GB of it. A coordinator that extracts a few source trees into its scratchpad can push the job over its limit and kill a peer's dispatch.

Deliverable. A session's scratch lives on the node's local disk. Each session's use is sampled, a session over the configured bound is an obligation for that session naming its largest directory, and the total is kept below a stated share of the disk. The bound and the share are flight settings with stated defaults of 2 GiB a session and half the disk.

Done when. A test starts two session stand-ins under the supervisor's scratch preparation: both scratch paths resolve on the local disk and none under /dev/shm; one writes past its bound and is reported with its largest directory while the other, which writes nothing, reads zero and is not reported. Negative control: with the path left on /dev/shm the first assertion fails. On the fleet node after landing, the sessions' bytes under /dev/shm read zero for every session started since, against 1.60 GB before. Runs on all_debug; importers add no failure against the base. Write paths: reckon/crew/fleet_supervisor.py, bin/fleet-health, the flight schema files with their generated JSON, and tests/test_session_scratch_uses_bounded_node_tmp.py.

§5 — The node's local disk is in the health series

Why. A full local disk drained the previous node's allocation of new work, and §4 moves more onto that disk. The series samples memory every minute and the disk never.

Deliverable. Each health sample carries the local disk's total, used and free bytes and its free inodes. Free space under a stated reserve is an obligation naming the largest entries by owner, and admission holds new launches while it lasts. The reserve is a flight setting with a stated default of 8 GiB.

Done when. A test samples two temporary mounts of different known sizes and finds each row carrying its own mount's figures, equal to an independent reading within one block; a mount under the reserve raises the obligation and one above it does not. Negative control: a sampler that reads one mount for both rows fails the per-mount equality. On the fleet node the series carries the four fields for an hour with no gap. Runs on all_debug; importers add no failure against the base. Write paths: bin/fleet-health, reckon/crew/fleet_supervisor.py, reckon/crew/admission/service.py, the flight schema files with their generated JSON, and tests/test_fleet_health_records_node_tmp.py.

§6 — A sampler outside the allocation keeps writing when the job ends

Why. The sampler runs inside the allocation it watches, so its last row is written before the event that matters most. The series for job 1313886 ends a minute before the job did, and a second analysis of the same failure read that as a blind hour.

Deliverable. A reader that runs outside the fleet allocation records, each minute, whether the fleet job is running, on which node, and its state as the scheduler reports it, in the same durable series, and writes one row naming the end state and reason when the job ends.

Done when. In a rehearsal on all_debug, a stand-in fleet job is cancelled and the outside reader writes a row within two minutes naming the job, its node, its end state and the scheduler's reason, after the in-job sampler's last row. A test drives the reader against recorded scheduler answers for a running job, an ended job and an unreadable scheduler: the first two produce their rows and the third writes a row marked unknown, never an end. Negative control: with the outside reader stopped, no row follows the in-job sampler's last. Importers add no failure against the base. Write paths: bin/fleet-health, reckon/crew/fleet_node.py and tests/test_a_sampler_outlives_the_fleet_job.py.

§7 — Dispatch, admission and the station can be profiled without writing live state

Why. The three largest processes on the node have never been profiled to completion. A read-only admission pass stopped at its lease write, a read-only station pass retried a refused write until it was cancelled, and a one-entry dispatch control ran into its job's time limit. What allocates 47 GB in a dispatch is still not known; the one completed profile, an eight-entry batch, peaked at 4.3 GB resident and 1.9 GB traced with the store read four times for 24,212 rows.

Deliverable. Each of the three commands completes one pass against a copy of the crew home in a temporary directory, writing nothing outside it, and reports its peak resident memory, its traced peak, its ten largest allocation sites, and the bytes read and rows decoded from each store. The report is one record per command, kept with the revision and the input's digest.

Done when. On rigel, each of the three passes exits zero inside 30 minutes against the same copied home and writes its record; the listing and digests of the real crew home are identical before and after. A one-entry and an eight-entry dispatch are both recorded, so the cost of a batch is told from the cost of a process. Negative control: a pass pointed at the real crew home is refused before its first write. The records are the baseline for §8 and §9. Importers add no failure against the base, on all_debug. Write paths: scripts/profile_control_pass.py, reckon/crew/admission/service.py, reckon/crew/station.py and tests/test_a_control_pass_profiles_without_live_writes.py.

§8 — A batch dispatch holds a bounded amount of memory

Why. A single crew dispatch --batch was seen at 47 GB, half the old job's limit, and a coordinator queueing a plan can run several. Queueing work should not be what kills the node.

Deliverable. Peak resident memory of a batch dispatch does not grow with the number of entries beyond a stated amount per entry, and stays under 4 GB for a batch of forty entries on this workstation's stores. The requests it stores are the same as before.

Done when. On §7's harness and input, an eight-entry and a forty-entry batch are profiled before and after: the forty-entry peak is under 4 GB and within 1 GB of the eight-entry peak, and each run's stored requests equal the base's. Negative control: at the base revision the forty-entry peak exceeds the eight-entry peak by more than 1 GB, or the section records that it does not and closes on the absolute bound alone. Runs on rigel; importers add no failure against the base, on all_debug. Write paths: reckon/crew/dispatch_batch.py, reckon/crew/dispatch_plan.py and tests/test_dispatch_batch_memory_profile.py.

§9 — The admission service does not grow with its age

Why. The admission service went from 0.07 GB to 6.1 GB in its first hour in the saved tables, was seen at 35 GB, and stood at 11.4 GB twenty-five minutes after a start on 17 November. Until that night it was restarted by every landing, which hid the growth; with one reload a window it now lives long enough to matter. The station's retained memory is owned by the-monitor-reads-each-fact-once and is not part of this section.

Deliverable. The admission service's resident memory after two hours of passes is within 20 % of its memory after fifteen minutes, and under 4 GB at this workstation's population. Its launch and release decisions are unchanged.

Done when. On §7's harness, the service runs 100 consecutive passes against the copied home: resident memory after the hundredth pass is within 20 % of that after the tenth and under 4 GB, and every pass's decisions equal the base's. Negative control: at the base revision the hundredth-pass figure exceeds the tenth by more than 20 %. On the live fleet, the process tables saved over the six hours after landing show the service under 4 GB at every sample. Runs on rigel; importers add no failure against the base, on all_debug. Write paths: reckon/crew/admission/service.py, reckon/crew/admission/selection.py and tests/test_the_admission_service_holds_steady_memory.py.

§10 — A declared service that outgrows its limit restarts alone

Why. When any process pushes the job past its limit the kernel chooses the victim, and it has chosen peers' dispatches and the station. A limit on a service's whole process tree is not available to this account: the job's cgroup is root-owned and creating a child is refused. What is available was shown in a rehearsal: with an address-space limit on each of two stand-ins, the one that outgrew it failed its own allocation and was restarted while its peer kept its pid; with no limit, both were killed at the job's limit.

Deliverable. Each service the supervisor runs may declare a memory limit, applied to the service's own process as an address-space limit when the supervisor starts it. A service that reaches it fails and is restarted under the supervisor's existing backoff, the event is recorded with the service and its limit, and no other service is affected. A service that declares none is started as today. What this does not bound, the service's child processes, is stated on the record. A limit on the whole tree needs SDCC to delegate a memory cgroup to the job, and is not planned here.

Done when. In a 2 GiB rehearsal allocation on all_debug, the supervisor runs two stand-in services, one declaring a 768 MiB limit and allocating past it: that one is restarted and its event recorded, the other's pid is unchanged, and the job's kill count does not move. Negative control: with no limit declared both are killed and the count rises by two. A test asserts a service with no declared limit is started with none. The existing supervisor suites add no failure against the base. Write paths: reckon/crew/fleet_supervisor.py, the fleet service configuration schema the supervisor reads, and tests/test_fleet_supervisor_service_memory_bound.py.

§12 — The node sampler runs the script the checkout holds

Why. The supervisor starts the node sampler once and re-executes itself whenever the code moves. Each re-execution starts a sampler from the current script, which finds the lock held and exits, so the sampler from the allocation's first minute keeps running the script it was started with. On 17 November the sampler started on 16 November at 07:00 was still writing the 16-column series after 138 re-executions: none of the columns §2 to §5 landed that day was being sampled, the disk sample of §5 was never published, and every reader on another host reported the disk as unreadable and launches as held when admission was holding nothing.

Deliverable. After the supervisor re-executes on moved code, the running sampler is the one started from the script the checkout then holds, with at most one sampler at any time and no more than two missed samples across the handover. The series file is carried over, widened to the current columns with its earlier rows kept. A reader that finds no published disk sample reports the sample as missing under the run or service that owes it, and reports launches as held only when admission is holding them.

Done when. In a rehearsal on all_debug, a supervisor stand-in starts a sampler from one script, the script gains a column, and the supervisor re-executes: within two sampling periods exactly one sampler runs, its script is the new one, the series holds the earlier rows and new rows carrying the added column, and at most two samples are missing. A test drives a reader with no published disk sample while admission's own verdict is open: the row names its owner and does not say launches are held. Negative control: at the base revision the first sampler is still the one running after the re-execution and the added column is never written. On the fleet node after landing, the series carries the columns of §2 to §5 within two re-executions. Importers add no failure against the base. Write paths: reckon/crew/fleet_supervisor.py, bin/fleet-health, reckon/crew/obligations.py and tests/test_the_sampler_runs_the_current_script.py.

§13 — A tree left in the crew scratch root with no owner is reclaimed

Why. The crew keeps its temporary trees on the fleet node's local disk under one scratch root. A landing measurement that is stopped before it finishes, as every service restart can do, leaves its base tree behind, and so does a run whose worker ended without cleaning up. The node's sweep keeps that root whole while live runs write inside it, so nothing removes these. On 18 November at 00:11 UTC the disk went under its reserve and held new launches; three landing trees of 0.2 to 1.3 GB, the oldest seventeen hours untouched and none with a process inside or a run pointer, were removed by hand to bring it back.

Deliverable. An entry in the scratch root that belongs to no live run and no running measurement, and has not been touched for a stated time, is removed without a coordinator, with its path, size, age and the reason recorded. An entry that belongs to a live run, has a process inside it, or was touched inside that time is left alone. The time is a flight setting with a stated default of two hours. The disk-reserve obligation of §5 names such entries apart from live runs' scratch.

Done when. A test builds a scratch root holding five entries: a landing tree untouched past the time with no owner, one with a process whose working directory is inside it, one untouched for less than the time, a live run's directory, and a directory of a run whose pointer is gone and which is untouched past the time. After a pass only the first and the last are gone, each removal is recorded with its size and age, and the other three are byte-identical. Negative control: with the ownership check removed the live run's directory is deleted and the test fails. On the fleet node over 24 hours after landing, no entry without an owner is older than twice the time. Runs on all_debug; importers add no failure against the base. Write paths: reckon/crew/landing_measure.py, reckon/crew/fleet_supervisor.py, the flight schema files with their generated JSON, and tests/test_unowned_scratch_is_reclaimed.py.
