Run and session identity · one read, three roots

Ask For a Run by Name

A run's identity is spread across three filesystem roots with three naming schemes, and nothing joins them. A coordinator who wants to resume a worker must know a microsecond-precision run id it cannot reconstruct, read a session field that reports null while the answer sits in the run's own stream, and reimplement a path-mangling rule to find the transcript that proves recovery is possible. This plan adds one read that answers all of it from the node id a human actually knows, and reports how it knows.

§1 — Why this exists

Every failure below was measured on this workstation on 2026-09-03 and 2026-09-04, in one sprint's execution.

Refused cleanly, but the id had to be re-derived from a directory listing.
“Can this refused run be resumed?” The live pointer's session_id reads null until an observe folds it in, while the id has been in the run's own stream since its first turn. Five runs read as unresumable, were promoted as infrastructure failures, and had their worktrees released. The ids were recoverable the whole time; only the working directory was lost.
“Is that blocked run mine or another session's?” The config home is workstation-global and the ledger is per-repository, so no single call spans both. Answered four times across three sessions by parsing another session's pointer file directly — a boundary no coordinator should have to cross to read a label.
“Does the transcript still exist?” Transcripts live at ~/.claude/projects/<worktree path with separators replaced>/<session-id>.jsonl. The mangling rule was reimplemented by hand to prove five transcripts survived. A rule held in one caller's head is a rule the next caller gets wrong.
“What did that node do?” Promoted runs leave the live pointer entirely; their record is one of 539 entries in docs/state/reckon/crew.json. Every such question was answered by a Python one-liner walking data.runs. The existing ledger and records views return the whole slice rather than the rows asked for.

§2 — A runs view on the existing crew tool

The MCP surface is deliberately one crew tool over eight views rather than eight tools (reckon/mcp.py, _crew). This adds a ninth view rather than a tool, and it stays a read: it launches, resumes and promotes nothing, exactly as the read/action split requires.

crew(project, view="runs", …) takes filters and returns compact rows. node is the important one, because a node id is the handle a human holds while a run id is machine identity — a caller should never have to type a timestamp. newest_per_node collapses a node's attempt history to its latest run, which is what “resume the fleet-index run” means. The filters are node, plan, section, session, member, classification, resumable and newest_per_node; source selects live, ledger or all, defaulting to all so a promoted run and a live one answer from one namespace with a source field distinguishing them.

Rows are compact by default because the existing views are too large to read: in one session roadmap returned 176,051 and 87,603 characters and read_plan at view="raw" returned 104,439, each exceeding the response ceiling and forcing a detour through a spill file, while crew(view="live") returns all twelve follower records on every call regardless of the question. The default row is fifteen short fields; fields opts into more and limit bounds the answer.

§3 — A session has a provenance, and an absence is stated

Call the resolver, never reimplement it. resolve_session (reckon/crew/recover.py) consults the live pointer, the run's own stream and the promoted ledger row in order and returns the source that answered. Where none has an id it returns a stated absence naming all three as consulted, because not yet observed and genuinely absent are different facts and a bare null expresses neither. The runs view calls it so that the query and crew resume can never disagree about the same run.

The ledger source is the one that gets forgotten. A promoted run has no pointer at all, and its session is still answerable from its committed row. Any implementation that reads only the pointer and the stream will report a promoted run as sessionless, which is a false negative on exactly the runs a later audit asks about.

resumable is the join, and its negative form is the useful half. A run is resumable when a session id is present or recoverable, its worktree exists, and its process is not alive. Each condition lives in a different root, which is why no caller can compute it today. The reason string matters more than the boolean: resumable: false, resumable_reason: "worktree released by promotion" is the sentence that was needed at 19:41Z and had to be derived by hand from a release result that reported only worktree_released: true.

Gate for this plan, recorded when the measure runs: against a synthesised config home carrying one pointer with no session field, one promoted ledger row with no pointer, and one run whose only session evidence is its stream, the runs view answers all three with the same session ids and sources that crew resume resolves, and reports a stated absence for a fourth run that genuinely has none. Its evidence is the two named test files passing plus one recorded run of the view against this workstation's real config home, with the row count, the distribution of session_id_source values and one resumable: false reason written into the execution record.

§4 — Workstation scope, because the roots have different spans

The config home is workstation-global while the ledger is per-repository, so “what is running on this machine” and “what has this repository recorded” are different questions against different roots. crew recover answers the first for one project only, and a fresh session inheriting a fleet it did not dispatch needs it for all of them. scope takes project, the default, or workstation, which enumerates live pointers across every project in the config home and labels each row with the project and repository that owns it — including projects whose repository is not the working directory. A row from another project is data, never something to act on: the view is read-only and the label is what lets a coordinator tell a peer's run from its own without reading the peer's files.

§5 — Out of scope

No action verbs: this view resumes, promotes, discards and stops nothing, because reads belong to MCP and actions to the CLI. No change to the run-id format — the timestamp is fine as machine identity once nobody has to type it. No new store: the four roots stay where they are and this joins them, because a fifth copy of a run's identity would be one more thing to disagree. The promotion guard that consumes session_id_source and peak input belongs to work-survives-a-provider-outage and is not built here; this plan informs it and will be wired to it once both land, rather than each growing its own join.

§ Decisions

Is this a new MCP tool or another view on crew?

The surface was deliberately collapsed to one crew tool over eight views rather than eight tools, and its docstring says so. A second tool covering the same subject splits the surface and invites the two to answer differently, which is the defect this plan exists to remove.

How does a row resolve its session id?

Reading the pointer alone is the measured defect: it reported null for five runs whose ids were in their streams. Reimplementing the walk creates a second authority that can drift from the resume path, and the whole value of the field is that a query and a resume agree about the same run.

How is a run with no discoverable session represented?

A bare null cannot distinguish not yet observed from genuinely absent, and a coordinator read one as a verdict on five runs and promoted them. The distinction is the whole reason the field is worth reporting.

What does a row return by default?

Three existing reads exceeded the response ceiling in one session and had to be answered through a spill file. A query whose default answer cannot be read is a query nobody uses, and the callers that need everything already have records.

§ Followups

Land the view, then its provenance, then its span

All three nodes write reckon/crew/query.py, so they are one serial lane on one roster member in section order: the view and its filters first, then session provenance and the resumability verdict, then workstation scope. Each lands with its named test and the third carries the recorded run against this workstation's real config home for the gate.
