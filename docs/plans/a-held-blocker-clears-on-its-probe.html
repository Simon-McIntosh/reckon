§1 — A held blocker names a probe, and the probe clears it

a-sprint-closes-on-completable-work made held a kind of blocker: a claim that nothing in the sprint can reach the work. That plan's §4 sets and clears a held blocker by hand and defers the executable check to a separate plan; this is that plan. Two locked decisions on a-sprint-closes-on-completable-work constrain it. probe-execution-boundary: a plan names a probe by id, and the probe is Python in this repository, reviewed and tested like any other code. It is never inline in a plan document and never evaluated in the surface. who-clears-a-held-blocker: clearing records a reason, so a cleared hold stays distinguishable from one that was never held.

Done when a held blocker can name a probe id that resolves to a registered Python callable. Evaluating a held blocker runs its probe against the blocker's declared subject. When the probe reports the subject arrived, the blocker is cleared with the probe's id and its finding recorded as the reason. A probe id that resolves to nothing is reported, never treated as clear. A test in a temporary repository shows all three: a probe that reports arrival clears its blocker with the reason recorded, a probe that reports absence leaves it held, and an unknown probe id is reported. The negative control is the base, where no held blocker can name a probe.

§2 — A cleared held blocker releases a plan stored as blocked

From the §1 worker. A plan persisted with the legacy status blocked stays blocked on the roadmap after its held blocker clears. reckon/roadmap.py synthesizes an unrecorded blocker for that status, so the clear that §1 records never reaches the plan's readiness.

Done when the node first shows the defect reproduces at main. Then a plan whose only blocker is a held blocker cleared by its probe reads ready on the roadmap, and a plan stored as blocked with no blocker resource keeps reading blocked. A test covers both. The negative control is main, where the first case reads blocked.

§3 — A cleared blocker reports its clear even after its probe is withdrawn

From the §1 review (score 96). In evaluate_held_blocker the already-cleared early return sits after the registry lookup. A blocker cleared while its probe was registered therefore raises "unknown held blocker probe id" once that probe leaves the registry, instead of reporting the clear it already recorded, and no test exercises that path.

Done when a cleared blocker reports its recorded clear whatever the registry now holds. An uncleared blocker with an unknown probe id is still refused. A test covers both, and the negative control is main, where the first case raises.

§4 — A graph target reads readiness from the one computation

From the §2 review (score 97). resolve_graph_target in reckon/roadmap.py (about line 1893) builds its own readiness list, whose membership still requires _status(plan) in _AUTHORISED_STATUSES. A plan released by §2 therefore appears in the roadmap's ready_now but is absent from a graph target's ready set. One readiness fact now has two computations, and only one was updated.

Done when a graph target's ready set is derived from the same readiness the roadmap's ready set uses, so a plan released by a cleared hold appears in both. A test builds a graph whose member is such a plan and asserts it is ready in both views. A second test covers §2's untested partial-clear case, one blocker cleared and one still holding, and asserts the plan stays blocked in both. The negative control is main, where the graph view omits the released plan.
