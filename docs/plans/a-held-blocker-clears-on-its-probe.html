§1 — A held blocker names a probe, and the probe clears it

a-sprint-closes-on-completable-work made held a kind of blocker: a claim that nothing in the sprint can reach the work. That plan's §4 sets and clears a held blocker by hand and defers the executable check to a separate plan; this is that plan. Two locked decisions on a-sprint-closes-on-completable-work constrain it. probe-execution-boundary: a plan names a probe by id, and the probe is Python in this repository, reviewed and tested like any other code. It is never inline in a plan document and never evaluated in the surface. who-clears-a-held-blocker: clearing records a reason, so a cleared hold stays distinguishable from one that was never held.

Done when a held blocker can name a probe id that resolves to a registered Python callable. Evaluating a held blocker runs its probe against the blocker's declared subject. When the probe reports the subject arrived, the blocker is cleared with the probe's id and its finding recorded as the reason. A probe id that resolves to nothing is reported, never treated as clear. A test in a temporary repository shows all three: a probe that reports arrival clears its blocker with the reason recorded, a probe that reports absence leaves it held, and an unknown probe id is reported. The negative control is the base, where no held blocker can name a probe.
