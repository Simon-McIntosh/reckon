Design fidelity · the drift and the check that would have caught it

Read It Against The Canvas

The lead read the landed surface and found six faults in one sitting: three views that cannot scroll, prev-and-next dead across every artifact kind, a reader whose panels are saturated where the canvas is light, a full-screen mode that changes the measure and does not fill the screen, a figure viewer with no caption and no zoom, and a sprint diagram whose cards carry less than the layout already computes. Each is a small correction. What they share is the reason: every node implemented from its plan's prose, the prose paraphrased the canvas, and nothing ever compared the result to the canvas itself.

§1 — What drifted, and what did not

Two of the six reports were already closed by commits the reading predates, and separating them matters because it tells us the difference between drift and staleness.

§2 — Every routable view scrolls

One defect in four places. docs/ui/graph.css declares .r-graph { flex: 1; overflow: auto } and carries no min-height rule at all; a flex child with overflow:auto and no min-height:0 grows to its content instead of scrolling, so the view runs off the bottom of the window. crew.css has the two min-height: 0 declarations that fixed exactly this for the Crew surface, and graph.css is now the only stylesheet in the tree with the flex-and-overflow pair and no min-height. The reader shares the fault for research, evidence and figures.

The fix is the rule the shell plan already stated and applied too narrowly: every flex ancestor between the app root and a routable view carries min-height: 0. The measure is the one that generalises, because a per-view assertion is what let this recur.

§3 — Prev and next work for every kind

The readout reads 0 / 0 on a plan that is one of many, and the arrows do nothing, on all four kinds. That is a stronger fault than the off-by-one recorded against the reader chrome: a 0 / 0 means the ordered list the index rendered never reaches the reader at all, rather than reaching it and being counted wrongly. The earlier symptom — a readout of 2 / 3 while standing on the third item — is the same defect seen through a fixture that did publish a list, and this section supersedes that node rather than sitting beside it.

The canvas is unambiguous about the contract: prev, next and the readout all read one list, published by the index at render time, including its status filter and its sort. Deriving it again inside the step handler is named in the plan as the way it silently breaks. So the fix is a single published queue, keyed by kind, and the measure must exercise a populated list of each kind rather than only plans — the kinds are exactly where it was not exercised.

§5 — Full screen fills the screen, and the measure stops moving

Two things, one of which departs from the canvas on the lead's instruction and is recorded as such. The canvas grows the measure from 760px to 820px on entering full screen; the lead's direction is that the measure stays constant at the larger of the two, so a document does not reflow when the chrome disappears. Reflowing text is the most disorienting thing a reading mode can do at the moment it is entered, and the canvas's own reason for growing the measure — that full screen buys width — is satisfied by simply using the wider measure throughout.

The second is not a deviation but an unmet requirement: full screen must show only the document. The canvas drapes a fixed inset-zero pane over the entire shell, topbar included, because every control in that bar navigates away from what is being read. The landed surface leaves chrome visible, so the mode buys neither width nor quiet.

§8 — The canvas becomes a measure

The six corrections above are worth little on their own, because nothing would stop the next surface node from paraphrasing the canvas again. The canvas is an executable document that carries its own values — measures in pixels, token names, padding, opacity, the fields a card prints — so a test can read them out of it and compare them against the implementation. That turns “truthful to the handoff” from an intention into a check that fails.

It cannot compare everything, and pretending otherwise would produce a brittle test nobody trusts. It compares what the canvas states numerically or by token: the reader measures, the toggle's font size and padding and opacity, the card ground and border tokens, the fields each card and metadata row prints, and the presence of the column labels. Where the implementation deviates deliberately — as the constant measure of §5 does, on the lead's instruction — the deviation is declared in one place with its reason, and the check asserts the declared set matches the actual set. An undeclared deviation fails; a declared one is visible to the next reader instead of being rediscovered by them.

§9 — Out of scope

The two reports already closed: the endpoint enumeration reaching the Graph tab, and the cone drawing plan edges only. The served-HTTP browser harness fault stays foreign-owned under its own plan; every measure here uses the file-URL harness, which works on this host. § Decisions

Does the reader measure grow when full screen is entered, as the canvas has it?

The lead's direction, and a deliberate deviation from the canvas recorded as one. Reflowing the text at the moment a reading mode is entered is the most disorienting thing that mode can do, and the canvas's stated reason for the growth — that full screen buys width — is served by using the wider measure throughout.

How is fidelity to the handoff held?

Restating in prose is what produced the drift: six nodes each measured against a sentence about the canvas rather than the canvas. Review by eye is what caught it, four surfaces late, and depends on someone looking. The canvas carries its values in a machine-readable form, so a check can compare them and fail.

Where does a figure's caption come from?

The capture indexes this sprint produced already record a description beside each recorded width, so the text exists. A filename dressed as a caption is worse than an absent one: it looks like a description and carries no information, which is the same defect as a flat line standing in for an empty series.

Does the published-queue work supersede the readout off-by-one node, or sit beside it?

A readout of zero of zero means the list never reached the reader; the off-by-one was the same defect seen through a fixture that did publish one. Two nodes against one cause would have one of them pass by accident.
