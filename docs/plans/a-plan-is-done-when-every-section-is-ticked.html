§1 — Why: landing rewrites the design, and the rewrite costs a review

A section lands today through collapse_section. The op replaces the section's authored body with a landed card: a badge, a one-line summary and a link to the full record. That has three costs, all measured on 2026-10-07 while landing one section of a-follower-lives-as-long-as-its-session.

  • The design a reader needs is gone from the plan. The deliverable and done-when a later node reads move out of the page and survive only in the evidence record.
  • The rewrite owes a review. The collapse moved the document unit's digest, so the next build owed a content review. That review's one finding was the card's own link.
  • The card's link was dead. evidence_anchor was written verbatim as the href, and the skills' example passed a bare anchor. Commit c14913bd repaired the link; the rewrite remains.

The lead's proposal: stop collapsing. Each plan opens with a linked todo list, one item per section, ticked when the section lands. Ticking never owes a review. Every section must have an item, and a plan reaches done only when every item is ticked.

§2 — What exists: the todo list is already stored, and already outside the review

Almost everything the proposal needs is already in the plan's state. What is missing is a reader that shows it, two controls that enforce it, and a landing beat that stops rewriting the body.

§3 — The plan read carries its todo list

Deliverable. One derivation function in reckon/_plan_html.py, called by both readers at their own boundary. One reader is the typed read (read_plan summary and detail), which reaches the plan through _store.read_plan and read_state_and_text_file, never parse_plan, and is rendered by reckon/mcp_views.py. The other is the plan payload the SPA fetches from reckon/serve.py's /plan/<project>/<slug>, which builds on parse_plan. Each reader holds the plan text, which the headings need, and passes it to the one function. It yields a todos list with one entry per authored section, in document order: the section id, its heading text, the in-page link #<id>, and its declaration. A ticked entry also carries its closing record: the section comment whose id is c-close-<id>, which the landing beat writes in the same call as the tick (§7). It is selected by that id, never by recency, because promotion appends its own section comments after the close. The same module gains the one predicate the later guards read, next to derive_impl_from_sections: the sections still open, meaning declared implementable or deferred. The list is a separate read-only field rather than more fields on sections. sections holds the stored, schema-validated typed records that round-trip into the HTML, and narrative sections have none. Nothing new is stored.

§9 — A deferred section blocks only the work that names it

Deliverable. Under §6 a plan holding a deferred section stays open, so a dependency that waits for the whole plan to reach done would wait for ever. The roadmap's readiness judges a dependency by the sections it needs. In reckon/roadmap.py, a whole-plan dependency on a plan (plan-depends-on: other) is satisfied when that plan is complete, or when at least one of its sections is done and none is left implementable, read through the implementable part of §3's open-section predicate, which also lists deferred sections. Two cases are uncertain, and no fixed rule settles them (decision below): a plan whose sections are all deferred, so nothing in it was built, and a plan with an authored heading that carries no declaration, found by §3's authored_section_headings because the declaration map cannot see a heading it lacks. In both, the dependency reads blocked by default, and the roadmap reports it in a judgment_required block, in the same shape as the existing schedule_override block. The block names the dependent, the target, the reason and the sections concerned, so the orchestrator decides: build or un-defer the section, or narrow or remove the dependency. The reckon-build skill names the block beside schedule_override as something the coordinator reports and decides before dispatch. A section dependency (other#sN) is satisfied when that section's declaration is done, as well as by the existing completed-plan and passed-gate routes, and never while the section is deferred or implementable. Today _section_satisfied reads no declaration at all, so a ticked section satisfies nothing until its plan is complete or its gates have passed.

Done when tests on a fixture project find the following, with plan A having §1 done, §2 deferred and status active. A plan depending on A is ready. A plan depending on A#s1 is ready. A plan depending on A#s2 is blocked, and the blocker names A#s2. A plan depending on an all-deferred plan is blocked and appears in judgment_required with the reason deferred-only. A plan depending on a plan with an undeclared heading is blocked and appears there with the reason undeclared-heading. A plan depending on a plan that still has an implementable section is blocked as today, and one depending on a plan that declares no sections stays blocked until that plan is complete. The first two fail on the current code, which waits for A to be complete; removing the judgment_required report fails its two tests. Those are the negative controls.

§ Decisions

Does a deferred section count as ticked when a plan is set to done?

A deferred section is one the author chose not to build in this plan. If it blocks done, authors are pushed to delete sections they mean to come back to.

A deferred section is not ticked, so a plan holding one stays open. The deferral blocks only the work that names that section: a section dependency on it stays blocked, and a whole-plan dependency is judged by the rule in §9. When nothing in the target was built, the case falls under the uncertain-dependency decision.

When does a whole-plan dependency clear if nothing in the target was built?

The lead favoured blocking when the target's only work is deferred, and asked that it not be fully deterministic. The orchestrator is told that something is blocked and makes the call. An all-deferred target, or one with an undeclared heading, holds its dependent by default and is reported in judgment_required, where the coordinator decides to build or un-defer the section, or to narrow or remove the dependency.
