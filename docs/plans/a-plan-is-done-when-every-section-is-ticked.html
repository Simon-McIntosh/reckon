§1 — Why: landing rewrites the design, and the rewrite costs a review

A section lands today through collapse_section. The op replaces the section's authored body with a landed card: a badge, a one-line summary and a link to the full record. That has three costs, all measured on 2026-10-07 while landing one section of a-follower-lives-as-long-as-its-session.

  • The design a reader needs is gone from the plan. The deliverable and done-when a later node reads move out of the page and survive only in the evidence record.
  • The rewrite owes a review. The collapse moved the document unit's digest, so the next build owed a content review. That review's one finding was the card's own link.
  • The card's link was dead. evidence_anchor was written verbatim as the href, and the skills' example passed a bare anchor. Commit c14913bd repaired the link; the rewrite remains.

The lead's proposal: stop collapsing. Each plan opens with a linked todo list, one item per section, ticked when the section lands. Ticking never owes a review. Every section must have an item, and a plan reaches done only when every item is ticked.

Almost everything the proposal needs is already in the plan's state. What is missing is a reader that shows it, two controls that enforce it, and a landing beat that stops rewriting the body.

§3 — The plan read carries its todo list

Deliverable. A plan's typed read (read_plan, view summary and detail) carries a todos list derived in Python. It has one entry per authored section, in document order, each with the section id, its heading text, the in-page link #<id>, and its declaration. A ticked entry also carries its closing record: the section comment whose id is c-close-<id>, which the landing beat writes in the same call as the tick (§7). The record is selected by that id, never by recency. Promotion appends its own section comments under the same author, so the newest comment is often a review or landing: line written after the close. Nothing new is stored: the list is derived from the headings, the declarations and that one comment.

Done when a test reads a fixture plan with three sections (one done with a c-close- comment followed by a later promotion comment, one implementable, one deferred) and finds three entries in document order with those states, the done entry carrying the c-close- comment rather than the later one. It fails on the current code, which has no todos field. A second test ticks a section through set section_declarations.<id> and finds the plan's review fingerprint unchanged. That already holds today, so its negative control is a declared mutation: digest with keep_declarations=True, so the declarations enter the fingerprint, and the test must fail.

§4 — The SPA shows the todo list at the top of the plan

Deliverable. The plan view renders the todos field from §3 above the first section, as a checklist. Each item links to its section's heading, a ticked item shows its closing comment, and a deferred item reads as deferred rather than open. The SPA renders the field and derives nothing.

Done when a module test of the plan view renders a payload carrying three todos and finds three links to #s1, #s2 and #s3 above the first heading, with the done item checked. With the render removed, the test fails; that is its negative control.

§5 — Every section has a todo item

Deliverable. reckon audit-doc reports section-without-todo for an authored section heading with no declaration, and todo-without-section for a declaration naming no heading. A plan write that would leave either is refused by edit_plan. The census comes first: count the live plans that would fail today, and state the count in the evidence, because closing this guard turns every existing gap into a refusal at that plan's next write.

Done when the census of every mounted project's live plans is recorded with its count. A test writes a plan with an undeclared heading and finds the audit error and the write refusal, and a second test finds the reverse case. Both fail on the current code, which checks neither; that is their negative control.

§6 — A plan reaches done only when every todo is ticked

Deliverable. A write that sets a plan's status to shipped or done is refused while any declaration is implementable or deferred, and the refusal names those sections. A deferred section is not ticked (decision below), so a plan holding one stays open; §9 keeps that from blocking work that does not depend on the deferred section. The census comes first here too: count the plans already at a terminal status with an implementable or deferred declaration, and state the count.

Done when the census is recorded with its count. A test sets a plan with one implementable section to done and finds the refusal naming that section, and a second does the same with one deferred section. After the section is ticked, the same write succeeds. Both refusal tests fail on the current code; that is their negative control.

§7 — The landing beat ticks instead of collapsing

Deliverable. The landing beat in skills/reckon-build/SKILL.md, its coordinator reference and skills/reckon-edit/SKILL.md becomes three ops: append_evidence, a set of the section's declaration to done, and a closing comment with the id c-close-<section> carrying the result and a link to the evidence, all in one call. collapse_section stays available but no skill uses it, and the section body stays as authored. The two docstrings in reckon/crew/review_lifecycle.py that describe a landed plan as collapsed are reworded to the declaration, which is what that code already reads.

Done when the skill-contract test applies each skill's documented landing examples to a fixture plan and finds the section's body unchanged, its declaration done, its c-close- comment present, and the plan's review fingerprint unchanged. With a collapse put back in the examples, the test fails; that is its negative control.

§8 — Retire the pre-collapse fingerprint form

Deliverable. Once no stored plan review depends on it, remove the pre-collapse form from plan_review._fingerprint_forms. A change to the fingerprint's shape makes every plan owe a review at its next build, so this section starts with a census of the stored review sidecars. It runs only when that census shows the change orphans no review, or orphans a number the lead accepts. Deferred until §7 has landed and the plan-review session's open edits to reckon/crew/plan_review.py have merged.

Done when the sidecar census is recorded, the form is removed, and a test shows a plan whose collapsed card is unchanged keeps its review. The display path in reckon/mcp_views.py, which reads landed cards for plans already collapsed, is left unchanged.

§9 — A deferred section blocks only the work that names it

Deliverable. Under §6 a plan holding a deferred section stays open, so a dependency that waits for the whole plan to reach done would wait for ever. The roadmap's readiness judges a dependency by the sections it needs. In reckon/roadmap.py, a whole-plan dependency on a plan (plan-depends-on: other) is satisfied when that plan is complete, or when none of its sections is left implementable: every section is done or deferred. A section dependency (other#sN) is satisfied when that section's declaration is done, as well as by the existing completed-plan and passed-gate routes, and never while the section is deferred or implementable. Today _section_satisfied reads no declaration at all, so a ticked section satisfies nothing until its plan is complete or its gates have passed.

Done when tests on a fixture project find the following, with plan A having §1 done, §2 deferred and status active. A plan depending on A is ready. A plan depending on A#s1 is ready. A plan depending on A#s2 is blocked, and the blocker names A#s2. A plan depending on a plan that still has an implementable section is blocked as today. The first two fail on the current code, which waits for A to be complete; that is their negative control.

§ Decisions

Does a deferred section count as ticked when a plan is set to done?

A deferred section is one the author chose not to build in this plan. If it blocks done, authors are pushed to delete sections they mean to come back to.

A deferred section is not ticked, so a plan holding one stays open. The deferral blocks only the work that names that section: a whole-plan dependency clears once no section is left implementable, and a dependency on the deferred section itself stays blocked.
