§1 — Why: promotions queue on one index and rescan the tree

On 2026-10-22 at about 21:45 CEST four sessions were promoting runs on clu-2068 at once. One crew complete of a plain review run ran past a five-minute bound and was killed; its retry then rolled back with fatal: Unable to create '.git/index.lock': File exists, because every promotion stages its landing writes in the main checkout's single index while peers do the same. The handoff from the monitor session records three promotions failing their landing step the same way earlier that day. Three py-spy samples of a peer's promotion, taken seconds apart, sat in:

  • ledger._indexed_data parsing JSON for promotion_checks._landing_preconditions;
  • routing._repository_tree_snapshot running git over the whole tree for the boundary check;
  • reports._committed_paths_added_since running git for the PNG-twin check.

The analysis is in monitor-storage-load-rca §3.

§2 — A landing commits through its own index

The promotion's landing writes are staged into a temporary index (GIT_INDEX_FILE under the run's scratch, seeded from HEAD), committed with git commit-tree, and published with git update-ref refs/heads/main <new> <old>, which fails when main moved. A failed compare is retried against the new head, up to a bound, and the main checkout's working tree is brought up to the published commit for the landed paths only. The main checkout's .git/index.lock is never taken.

Done when a test runs four promotions at once against a temporary repository and all four land as four commits, with no index lock taken in the shared checkout (asserted by holding .git/index.lock open for the whole test) and the shared checkout's tracked files matching HEAD afterwards. Negative control: today's staging path must fail with the held lock.

§3 — Promotion checks read only what moved

The ledger index is loaded once per promotion and shared by every check that reads it. The repository-boundary check reads the paths the run's commits touch, not a snapshot of the whole tree. The PNG-twin check reads the run's own commits since its base, not every path added since an older base.

Done when, on a fixture of 2,000 ledger rows and a repository of 5,000 files, a promotion calls the ledger loader once and runs no git command over the whole tree (counted by wrapping the git runner), and the existing promotion tests pass. Negative control: a boundary check that snapshots the whole tree must fail the git-call count.

§4 — A promotion lands in under a minute with peers promoting

Measure on the fleet node: three promotions of completed review runs started together.

Done when each lands in under 60 s wall clock, none rolls back, and the timings and the git log are recorded in the RCA. Negative control: the same measure on the code before §3 and §5 shows the multi-minute promotions and at least one lock collision, or the measurement records that the collision did not reproduce and how often it was tried.

§5 — A promotion's commit retries a held index lock and never leaves writes staged

Why. reckon-e0 relayed this on 6 November from nova-39. At 07:45:02Z nova-39 ran crew complete --no-commit on review run r-20261106T064850727420-review-of-bank-solve-trace-1e446dd29abe-figure while a peer promotion ran in the same checkout. The commit step failed with “File exists” on .git/index.lock. landing.json records step commit, head b97d2301f, and rollback: false for both paths. So two forward writes stayed staged in the shared index: the plan file at plan-version 169 and the new docs/state run JSON. The run stayed unpromoted, and the CLI's only sign was the tail line “landing writes could not be restored” (reckon/crew/promotion_scope.py near line 2158). A plain retry a minute later promoted it and landed 31dfb3564. For that minute, any commit in the checkout that named no paths would have swept in a half-landed plan. Crew-runtime-positive-controls §39 says a failed landing commit leaves nothing staged, and scoring-should-stop-a-promotion §17 says a landing write waits out a briefly held lock. After a failed commit the step does call _restore_landing_writes (near line 2419), but _restore_tracked_landing_write declines to clear a path the index still stages while the lock is held (near lines 1845–1846), so the write stays staged. Neither the commit nor the restore waits for the lock. §2, which removes the shared index from landings, is descoped, so this section closes the gap within the shared index.

Deliverable.

  • The commit step in _commit_landing_writes retries on .git/index.lock the way crew merge does, with the same bound and backoff.
  • When the commit fails, the restore in _restore_landing_writes waits for the lock with the same bound, then unstages the forward writes and restores their tracked content.

Done when a new tests/test_a_promotion_commit_survives_a_held_index_lock.py shows three things on a temporary repository:

  • With .git/index.lock taken after staging and before git commit runs, through a stub at that boundary, and held for less than the commit's bound, the promotion commits and lands. Staging already waits out a held lock (_stage_landing_writes, near lines 2295–2302), so a lock taken before staging measures that retry rather than the commit's.
  • With the lock held past the commit's bound and released one second after the commit step gives up, the promotion fails, its restore is observed to retry while the lock is still held, and it leaves nothing staged and the plan file as it was at HEAD.
  • With the lock held past both bounds, the refusal names every path still staged and the remedy, as today.

One negative control per arm: removing the retry makes the first case fail; and removing the restore's wait leaves the second case's paths staged. The test files importing reckon.crew.promotion_scope add no failure against the base revision. Ruff adds no findings on the staged paths. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. Write paths: reckon/crew/promotion_scope.py and the new test.
