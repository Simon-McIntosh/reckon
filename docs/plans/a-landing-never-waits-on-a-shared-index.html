§1 — Why: promotions queue on one index and rescan the tree

On 2026-10-22 at about 21:45 CEST four sessions were promoting runs on clu-2068 at once. One crew complete of a plain review run ran past a five-minute bound and was killed; its retry then rolled back with fatal: Unable to create '.git/index.lock': File exists, because every promotion stages its landing writes in the main checkout's single index while peers do the same. The handoff from the monitor session records three promotions failing their landing step the same way earlier that day. Three py-spy samples of a peer's promotion, taken seconds apart, sat in:

  • ledger._indexed_data parsing JSON for promotion_checks._landing_preconditions;
  • routing._repository_tree_snapshot running git over the whole tree for the boundary check;
  • reports._committed_paths_added_since running git for the PNG-twin check.

The analysis is in monitor-storage-load-rca §3.

§2 — A landing commits through its own index

The promotion's landing writes are staged into a temporary index (GIT_INDEX_FILE under the run's scratch, seeded from HEAD), committed with git commit-tree, and published with git update-ref refs/heads/main <new> <old>, which fails when main moved. A failed compare is retried against the new head, up to a bound, and the main checkout's working tree is brought up to the published commit for the landed paths only. The main checkout's .git/index.lock is never taken.

Done when a test runs four promotions at once against a temporary repository and all four land as four commits, with no index lock taken in the shared checkout (asserted by holding .git/index.lock open for the whole test) and the shared checkout's tracked files matching HEAD afterwards. Negative control: today's staging path must fail with the held lock.

§3 — Promotion checks read only what moved

The ledger index is loaded once per promotion and shared by every check that reads it. The repository-boundary check reads the paths the run's commits touch, not a snapshot of the whole tree. The PNG-twin check reads the run's own commits since its base, not every path added since an older base.

Done when, on a fixture of 2,000 ledger rows and a repository of 5,000 files, a promotion calls the ledger loader once and runs no git command over the whole tree (counted by wrapping the git runner), and the existing promotion tests pass. Negative control: a boundary check that snapshots the whole tree must fail the git-call count.

§4 — A promotion lands in under a minute with peers promoting

Measure on the fleet node: three promotions of completed review runs started together.

Done when each lands in under 60 s wall clock, none rolls back, and the timings and the git log are recorded in the RCA. Negative control: the same measure on the code before §3 and §5 shows the multi-minute promotions and at least one lock collision, or the measurement records that the collision did not reproduce and how often it was tried.

§5 — A promotion's commit retries a held index lock and never leaves writes staged

Why. reckon-e0 relayed this on 6 November from nova-39. At 07:45:02Z nova-39 ran crew complete --no-commit on review run r-20261106T064850727420-review-of-bank-solve-trace-1e446dd29abe-figure while a peer promotion ran in the same checkout. The commit step failed with “File exists” on .git/index.lock. landing.json records step commit, head b97d2301f, and rollback: false for both paths. So two forward writes stayed staged in the shared index: the plan file at plan-version 169 and the new docs/state run JSON. The run stayed unpromoted, and the CLI's only sign was the tail line “landing writes could not be restored” (reckon/crew/promotion_scope.py near line 2158). A plain retry a minute later promoted it and landed 31dfb3564. For that minute, any commit in the checkout that named no paths would have swept in a half-landed plan. Crew-runtime-positive-controls §39 says a failed landing commit leaves nothing staged, and scoring-should-stop-a-promotion §17 says a landing write waits out a briefly held lock. After a failed commit the step does call _restore_landing_writes (near line 2419), but _restore_tracked_landing_write declines to clear a path the index still stages while the lock is held (near lines 1845–1846), so the write stays staged. Neither the commit nor the restore waits for the lock. §2, which removes the shared index from landings, is descoped, so this section closes the gap within the shared index.

Deliverable.

  • When the commit fails, _restore_landing_writes (near line 1749) runs its git restore --source=HEAD --staged --worktree call through the same helper and bound, so it unstages the forward writes and restores their tracked content once the lock frees. No second wait loop is added.

  • With .git/index.lock taken after staging and before git commit runs, through a stub at that boundary, and held for less than the commit's bound, the promotion commits and lands. Staging already waits out a held lock (_stage_landing_writes, near lines 2295–2302), so a lock taken before staging measures that retry rather than the commit's.
  • With the lock held past the commit's bound and released one second after the commit step gives up, the promotion fails, its restore is observed to retry while the lock is still held, and it leaves nothing staged and the plan file as it was at HEAD.
  • With the lock held past both bounds, the refusal names every path still staged and the remedy, as today.

One negative control per arm: removing the retry makes the first case fail; and removing the restore's wait leaves the second case's paths staged. The test files importing reckon.crew.promotion_scope add no failure against the base revision. Ruff adds no findings on the staged paths. §6 — A main-checkout index that lags HEAD is surfaced

Why. On 8 November a landed file was reverted by the next ordinary commit in the main checkout. The interrupted-landing pass merged r-20261108T172213739428-where-a-review-takes-its-range as e741b27a9d, and the reflog records a real fast-forward at 19:13:24. That merge added docs/evidence/fragments/a-review-reads-only-its-runs-changes/where-a-review-takes-its-range.html. Six later commits by landings and peers kept the file, all made through path-scoped commits. At 19:19:38 a coordinator ran git add <plan> && git commit in the main checkout, and that commit (2754cbd2dc) recorded the fragment as deleted. The working tree still held the file byte for byte, so the checkout's index was the only stale copy. Some writer between the fast-forward and that commit left the index without a path HEAD carried. The note was restored at 55c6b25d56. Which writer did it is not known: the fast-forward updates the index, and the six intervening commits were made by promotion, release and peer plan writes.

Why the writer is not chased. The candidates do not fit. land_merge fast-forwards with git merge --ff-only (reckon/crew/merge.py near line 749), which writes the index for the paths it lands, so it would not leave a landed path missing. _commit_landing_writes commits with git commit --only -- <targets>, and its rollback touches only its own targets (reckon/crew/promotion_scope.py near lines 1754–1930 and 2505–2518). Both wholesale git read-tree calls in reckon (reckon/crew/routing.py near lines 1541 and 1599) run inside _save_and_release_worktree on a worktree, the first through a scratch GIT_INDEX_FILE, never on the main checkout's index. Peer sessions also run git in the main checkout, and nothing records which process wrote the index between 19:13:24 and 19:19:38. The writer cannot be recovered after the fact, so this section makes the condition visible when it happens.

Deliverable. The obligations view reads the main checkout of each mounted project for one condition: the index lacks a path that HEAD carries while the working tree still holds that file. These are the paths git diff --cached --name-only --diff-filter=D HEAD lists that also exist on disk and that the checkout does not ignore. A deliberate git rm --cached leaves the same shape, and usually adds the path to .gitignore, so the reader cannot tell the two apart for certain. When any such paths are present, every session working that project sees a notice, not a blocking duty, naming the paths. The notice says that a plain git commit would record them as deleted, and offers the path-limited restore git reset -q -- <paths> if the removal was not intended. That command resets only those index entries to HEAD and touches neither the working tree nor other entries. The first time each lag is seen, the reader appends one line to a log under the crew home, giving the time, the paths and HEAD, so a later occurrence can be matched to its writer. The reader never changes the index itself.

Done when a new tests/test_a_landing_leaves_the_index_at_head.py shows four cases with a temporary repository standing in for the main checkout and a temporary crew home. First, after a commit adds a file and the index entry is then removed while the file stays on disk, the obligations view lists the notice naming that path and its restore command, and the log holds one line for it; a second read of the view leaves the log at one line. Second, with an index matching HEAD, no notice appears. Third, a staged deletion of a file also removed from disk, which is an ordinary intended deletion, raises no notice. Fourth, a path untracked with git rm --cached and listed in .gitignore raises no notice. Negative control: dropping the detector leaves the first case with no notice while the index still lacks the path. The test asserts the real crew home is untouched. The test files importing reckon.crew.obligations add no failure against the base revision, run one arm at a time with at most -n 4, with logs under the run directory. Ruff check and ruff format --check add no findings on the staged paths. Write paths: reckon/crew/obligations.py and the new test.

§10 — A lander clears an index lock whose holder is proven gone

Why. On 14 November an empty .git/index.lock dated 11:54:40 sat in the shared checkout for more than 16 minutes with no git process on the fleet node holding it. Every reckon crew merge refused after eight attempts ("the checkout's index.lock stayed held"), so no landing reached main until the file went. A git process killed while holding the lock leaves it behind, and the lander waits on a lock that no live process will ever release. The lead asked that this can never block landings again, and chose the lander clearing a proven-stale lock over reporting it for a person.

Deliverable. When _run_waiting_out_a_held_index_lock (and the merge and promotion paths that use it) finds the lock still held past its retries, it judges the lock stale only when all of the following hold. The lock file is at least ten minutes old. Its size and mtime have not moved across the whole retry window. And no process on this host has the file open, read from /proc/*/fd. The checkout is written from other hosts too (§5 and §9 record promotions on nova-39 and clu-2068), so host-local absence alone cannot prove a holder is gone. A live writer on any host grows or touches the lock as it writes the index, so a still, empty lock ten minutes old has a hung or dead holder. The residual risk is a writer on another host that has taken the lock and has written nothing to it for ten minutes, which no git index operation does. A stale lock is removed, the attempt is retried once, and one line naming the lock's age and that it was removed goes to the landing's own record. A lock any process holds, one younger than the bound, or one whose size or mtime moved, refuses as today, with its age in the message.

Done when. A new test tests/test_a_lander_clears_a_stale_index_lock.py covers four cases. A temporary repository with an index lock aged eleven minutes, unchanged and held open by no process, is merged by crew merge, and its record names the removal and the age. The same lock held open by a live child process refuses, and the file survives. A lock whose mtime is touched during the retries refuses and survives. A lock aged five minutes refuses and survives. At the base revision the first case refuses. Removing the mtime condition fails the third case, and removing the holder check fails the second. The test files importing reckon/crew/merge.py or reckon/crew/promotion_scope.py add no failure against the base, run on the all_debug partition (env -u SLURM_JOB_ID -u SLURM_JOBID sbatch --partition=all_debug) one arm at a time with at most -n 4. Each log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. Ruff check and ruff format --check add no findings on the staged paths. Write paths: the module that defines _run_waiting_out_a_held_index_lock, reckon/crew/merge.py, and the new test.

§13 — A landing commit retries a lock released before it looked
