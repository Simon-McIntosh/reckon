§1 — What the fallback does

apply_backend_placement wraps a launch in the declared scheduler. When a reservation is published it emits srun --overlap --jobid=<id>, so the worker becomes a step inside an allocation somebody already holds. When no reservation is published it falls through to [scheduler, *options] with no job id — a bare srun, which does not join anything. It asks the scheduler for a new allocation, and it does so once per worker.

That is the precise inversion of what placement exists for. The design holds one reservation and runs many steps inside it; the fallback holds one allocation per step. A fleet of twenty workers asks for twenty allocations, and on a cluster where each carries a core and memory request, most of them queue. The dispatch reports nothing unusual, because from its point of view the wrapping was applied.

The file's own test currently pins this behaviour rather than refusing it: test_an_unheld_reservation_leaves_the_declared_wrapping_unchanged asserts that an unheld reservation yields srun --partition=all <argv> with no --overlap. It is an accurate description of what the code does and it is the thing to replace.

§2 — Why it has not bitten yet, and why that expires

One project declares a placement today, and the session that declares it publishes a reservation first, so the fallback is never reached. The protection is a habit, not a mechanism: nothing in the code requires the reservation to exist before the declaration takes effect.

Host-layer placement removes the habit. A declaration in ~/.config/reckon/flight.yaml applies to every project on the workstation, and a project that has published no reservation of its own reaches the fallback on its first dispatch. Reservations became per-project keyed on 2026-09-23, so a named project deliberately does not inherit the host-global record — which is correct, and which means the fallback is exactly the path an unprepared project takes.

§3 — The refusal

A declared placement with no readable reservation must refuse the dispatch rather than mint. The refusal names the reservation path it looked for, the project it looked for it under, and the ensure line that would hold one, so the reader's next command is in the message. Minting is never the safe default: a wrapping that silently changes from “join the fleet's allocation” to “take an allocation of your own” is a different operation wearing the same configuration.

Done when. A backend declaring placement with no readable reservation refuses, and the refusal names the path, the project and the ensure line. No allocation is requested on that path — asserted against a fake scheduler that records what it was asked for, so the assertion is that the request set is empty rather than that some flag is absent. The replaced test states the refusal in its name. A backend declaring no placement is untouched.
