§1 — What the fallback does

apply_backend_placement wraps a launch in the declared scheduler. When a reservation is published it emits srun --overlap --jobid=<id>, so the worker becomes a step inside an allocation somebody already holds. When no reservation is published it falls through to [scheduler, *options] with no job id — a bare srun, which does not join anything. It asks the scheduler for a new allocation, and it does so once per worker.

That is the precise inversion of what placement exists for. The design holds one reservation and runs many steps inside it; the fallback holds one allocation per step. A fleet of twenty workers asks for twenty allocations, and on a cluster where each carries a core and memory request, most of them queue. The dispatch reports nothing unusual, because from its point of view the wrapping was applied.

The file's own test currently pins this behaviour rather than refusing it: test_an_unheld_reservation_leaves_the_declared_wrapping_unchanged asserts that an unheld reservation yields srun --partition=all <argv> with no --overlap. It is an accurate description of what the code does and it is the thing to replace.

§2 — Why it has not bitten yet, and why that expires

One project declares a placement today, and the session that declares it publishes a reservation first, so the fallback is never reached. The protection is a habit, not a mechanism: nothing in the code requires the reservation to exist before the declaration takes effect.

Host-layer placement is what will remove the habit, and it has not happened yet: ~/.config/reckon/flight.yaml carries no placement key at the time of writing, so nothing at the host layer reaches the fallback on this workstation today. That makes this plan preventive rather than urgent — and it is the reason to land it before that host-layer declaration is made, not after. Once made, a declaration there applies to every project on the workstation, and a project that has published no reservation of its own reaches the fallback on its first dispatch. Reservations became per-project keyed on 2026-09-23, so a named project reads only its own record and does not fall back to the host-global one. That keying is why the fallback is exactly the path an unprepared project takes, and it is also why this plan cannot be implemented on its own: a shared reservation has to be readable by a project that did not publish it. Retiring the keying belongs to the fleet shares one allocation, which this plan blocks; the two land together or neither works.

§3 — Hold one, then place into it

Placement resolution now reaches ensure_reservation before any wrapping. A dispatch that finds no readable reservation holds the shared allocation, publishes it to the one unkeyed host-global record, and runs its worker as a step inside it. A dispatch under another project joins that allocation, and a recording scheduler sees exactly one allocation request across both. The hold runs under a file lock that is atomic between processes, so four racing processes ask for one allocation. The liveness probe is three-valued, so an unaskable scheduler waits and re-asks rather than reading as absent. § Decisions

What should a declared placement do when no reservation is readable?

Minting and ensuring are different operations and only minting is the defect. A dispatch finding no reservation holds the shared allocation once, publishes it, and places itself inside it; every follow-on worker finds that record and joins rather than asking for one of its own. Refusing would make the fleet wait on a human for something the machine can do correctly, and ensure_reservation already probes liveness and starts nothing when an allocation is held. The guard that makes it safe is idempotence under a race: serialise the ensure and decide on the liveness probe, never on the absence of a record, because a second allocation held beside a live one is the same per-worker minting arriving by a slower route.

§ Followups

Hold the shared reservation when none is readable, then place into it

Replace the fallback that prefixes a bare srun with a call that holds the shared reservation, publishes it to the host-global record, and places the worker into it as a step. ensure_reservation already probes liveness and returns already-held; what is missing is the call from placement resolution. This cannot land alone: against today's per-project keying the record it publishes is read by no other project, so it pairs with the keying retirement in the fleet shares one allocation. Serialise the hold across processes, not merely within one, and decide on the liveness probe rather than on the absence of a record. Replace test_an_unheld_reservation_leaves_the_declared_wrapping_unchanged, asserting exactly one allocation request across two dispatches against a recording scheduler.
