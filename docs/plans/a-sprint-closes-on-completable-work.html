§1 — A sprint can be unable to finish and unable to close

Two kinds of unfinished work look identical to the sprint machinery today. The first is waiting on another plan, or on a person, and someone can act on it now. The second is waiting on something no work in the sprint can reach — a reservation that has not come through, an upstream release, thirty days of data that have not elapsed. Both read as blocked, and either keeps a sprint open.

That produces the two failures this plan exists to prevent, and they pull in opposite directions. A sprint pinned open by a condition nobody can satisfy stops the horizon advancing, so the next sprint's work sits behind a wall that has nothing to do with it. And the obvious remedy — close the sprint and let the item go with it — is worse, because a completed container is where work goes to become invisible. A plan at impl 1.0 or a closed sprint is excluded from pending_work, ready_now and every open path, so an item carried into one is not tracked, it is hidden, and the paper trail makes it look tracked.

The distinction is not about how long the wait is. It is about whether any work in this sprint could end it. A prerequisite plan in the same sprint could; an external condition could not.

§2 — Held is a kind of blocker, not a new dependency type

Reckon already parses blocking rows carrying a kind, of which explicit exists today. This adds one more: a blocker declaring that what the item waits on is outside the sprint's reach. It is deliberately the smallest change that expresses the distinction — no new relationship field, no change to depends_on, which stays plan-to-plan, and no new document type.

A held blocker states what is being waited on in prose and carries no verdict machinery of its own in this plan. It is set and cleared by a person or a coordinator. That is deliberate: the executable half is a separate plan, and building the closure rule first means the vocabulary of conditions is learned from use rather than guessed at.

Done when a plan carrying a held blocker is reported by roadmap as held rather than merely blocked, distinguishable by a caller reading the payload without inspecting prose; the existing explicit-blocker behaviour is unchanged, asserted by a case that would fail if held rows were treated as explicit ones; and the count of plans in each state is stated as a digit for a fixture carrying both.

§3 — Closable means nothing completable remains

The rule is one sentence: a sprint is closable when every incomplete item is held. One item that is merely blocked, or ready and undone, keeps it open, because someone could still act on it.

On close, held items move to the advancing sprint carrying their blocker. They are not archived, not resolved, and not left behind in the closed one. When what they wait on arrives, the blocker clears and they become ready wherever they now sit.

Done when closing a sprint whose incomplete items are all held succeeds and moves them to the advancing sprint; closing one carrying a single un-held incomplete item is refused, naming that item; and the refusal is demonstrated once rather than only the success, because a closure rule never shown to refuse cannot be told from one that always closes.

The falsifiable test is the one this repository already trusts. After the close, call roadmap(project) and require every moved item to appear in pending_work. If it does not, the mechanism hid the work rather than carrying it, which is the precise failure the whole design exists to avoid. Assert it as a membership check over the returned set rather than as a count, because a count agrees by coincidence.

landed 2026-09-15

Closing a sprint is now a gated operation on the sprint resource itself: setting its status to a completed status runs a closability check against the composed state and refuses, naming the offending plan, while any incomplete item is not held by a blocker of kind held. §4 — What this does not do

It does not evaluate anything. A held blocker is set and cleared by hand here, and the executable probe that would clear it automatically is a separate plan, constrained by the decision recorded below so that it cannot be built as arbitrary code in a document.

It does not change depends_on, add a document type, or alter how plan-level dependencies are resolved. It does not decide how long a sprint may stay open, which is a scheduling question and not a correctness one.

It does not license closing a sprint whose work is merely unstarted. Held is a claim about reachability, and a held blocker whose subject someone in the sprint could actually deliver is a mislabelled one — the same defect as a test asserting a value it cannot observe.

§ Decisions

When a held blocker becomes machine-evaluated, where does the evaluating code live?

Locked ahead of the work it constrains, because it is the one genuinely risky choice and it is not actually open. The plan names a probe by id; the probe is Python in this repository, reviewed and tested like any other code. Inline code in a plan document is a code-execution surface fed by a file anyone may edit. Evaluation in the surface is refused by this repository's own binding rule that the SPA renders and does not derive: a probe evaluated in the browser is invisible to the CLI, to MCP and to every agent, so a human and an agent reading the same project would disagree with no way to notice.

Before probes exist, who may clear a held blocker, and does clearing it require evidence?

Locked on this repository's established pattern rather than on preference, and deliberately cheap to reverse once probes exist. Every other fence here records its waiver at the moment it is exercised: a dispatch waiving an unreconciled backlog records the exact backlog on the new run, and one dispatched without a delivering follower records the arming command and the unattached session. A held blocker cleared with no reason recorded is indistinguishable afterwards from one that was never held, which destroys the signal this plan exists to create - the distinction between work someone can act on and work nothing in the sprint can reach. The reason is also what makes the clearing auditable by the next session, which is the case that matters, since whoever cleared it is usually gone by the time anyone asks why the sprint closed. anyone-no-reason-required was rejected because it optimises the one moment that is already cheap, the clearing, at the cost of every later reading. The requirement is a recorded reason and not evidence: demanding evidence before probes exist would make the boundary unclearable and pin sprints open, which is the first of the two failures this plan names.
