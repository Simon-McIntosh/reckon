§1 — What is measured, and what was already repaired

The fleet has no cap and has never had one. The fleet review established that nothing in the code limits concurrent workers, that the de-facto ceiling is the registered roster under per-member serialisation, and that the wave barrier was “the most expensive artificial serialization: max-of-wave wait vs mean run time idles ~45% of worker-time at 3-wide.” That finding landed: the dead concurrency key is gone, the execution skill now says a wave is a reporting snapshot rather than a barrier, and the landing freeze explicitly exempts dispatching an unrelated ready node.

This plan does not re-open any of that. It starts from what the repaired contract still cannot answer, measured on a session executing a plan under it:

Running at 1 was locally correct and globally wrong. Correct, because the three sections that session shipped all wrote reckon/crew.py, reckon/cli.py, skills/reckon-ship/SKILL.md and tests/test_crew.py, and three contract tests bind the skill text to the CLI surface in both directions, so a second lane would have collided and left the suite red between landings. Wrong, because that judgement was reached by a coordinator reading test bodies by hand, and nothing in the system could have reached it — or contradicted it.

Both unmodelled gates have the same character, and it is the character this repository keeps finding: the data is already on disk and nothing derives the answer. Claimed paths are in every live pointer. Sprint order is built at reckon/roadmap.py line 392. Neither reaches the decision it should govern.

§3 — A per-project claim registry, and the planner that reads it

The registry already exists implicitly. The claimed-path set for a project is the union of node.write_paths over its live pointers, and list_live(project=…) already returns them. No new store, no new lifecycle: a claim lives exactly as long as its pointer, crew complete releases it, and a dead run holds its claim until the reconciliation machinery already built for that purpose clears it.

What is missing is that dispatch makes the coordinator retype it. --peer <node>=<paths> feeds the scoped property check, but the peers are supplied by hand, from memory, for data already on disk. Three deliverables:

  • Derived peer scopes. Dispatch reads live claims for the same project and repository root and refuses a declared-path collision before worktree creation, naming the owning run — the shape MemberInFlight and the unreconciled-backlog refusal already use. --peer becomes an override, not the source.
  • A read view. crew(project, view="scopes") returns path → owning run and node, so a wave can be planned before anything is submitted.
  • A lane planner. Given candidate nodes with declared paths plus the live claims, return the conflict graph and an ordered lane assignment. This is the half that matters: a refusal bounces the coordinator back to re-plan, while a partition hands it the wave.

Containment, not string equality. reckon/ and reckon/crew.py must conflict. Normalise to repository-relative POSIX paths and compare by prefix; key the registry on project and resolved repository root, which dispatch already does for the member guard. A claim in one repository means nothing in another, which is why the registry is per project.

Derivation groups are the failure this will hit first, and it has already been observed. A node adding one fence key had to claim reckon/_flight_schema.py and docs/_shared/flight.schema.json as well as the reckon/schema/flight.yaml they both regenerate from. A registry keyed on declared paths cannot know that, so a second node touching a generated file would be judged disjoint and would collide. The registry therefore needs a per-project source → generated map, and claiming a source claims its outputs. This is the real content of making the registry per project rather than global.

A claim is a declaration, not a fence, and the plan must not oversell it. The sandbox is worktree-full; a worker can write outside its declared scope. The registry prevents declared collisions only. Its complement is the post-hoc git show --stat audit against declared scope that verification already performs, and the two together are the whole guarantee.

The guard fires only where it refuses, never where a coordinator would ask. Probed adversarially against three live claims immediately after the refusal landed: --dry-run validated a node claiming reckon/roadmap.py while a live run held exactly that path, and validated a parent directory containing it, and validated a string-prefix sibling — all three identically, all ok. The cause is one line of placement: _raise_live_scope_conflict is called from dispatch and not from plan_dispatch, so the dry-run path never reads live claims.

This is consistent with the member guard and the budget hold, which are also dispatch-only, and for a pure refusal that placement is right. It is wrong for this one, because this section's purpose is to sequence before launch and the dry-run is the surface on which a coordinator asks whether a wave is safe. A planning surface that answers yes for a path dispatch would reject is worse than no planning surface: it is confidently wrong at exactly the moment the answer is being trusted. The repair is not to move the refusal, which would make a dry-run fail rather than report, but to have the dry-run report the conflicts it would hit while still exiting zero.

Done when two candidate nodes whose declared scopes overlap by containment are refused before any worktree exists with a message naming the owning run and the conflicting path; a dry-run against a live claim reports that conflict with the owning run while still validating the node, demonstrated by a test that holds a claim and dry-runs against it; a node claiming a declared source is judged to conflict with a node claiming its generated output; the planner returns a lane assignment for a candidate set whose partition matches a hand-computed expectation on the three-node case in §1; and the scopes view reports the live claim map without mutating a pointer.

§4 — Ready is not a queue, and saying so exposes the horizon

The seam is one line. reckon/roadmap.py computes readiness from dependency blockers, explicit blockers, gate blockers and cycle membership. Sprint status and sprint order are built in the same function and used only to sort the result and to exclude closed sprints. So ready_now answers are this plan's prerequisites met and is read as should this be started now, which is how five sprints come to contribute to one ready set.

It is already causing two agents to contradict each other in writing. One session reported a plan as deliberately held behind an earlier sprint; roadmap reported the same plan ready with no dependencies, no explicit blockers and no gates. Both were right about different questions. The hold was true and had nowhere in the model to live: sprint-item blocked_by would have rendered it as blocked, which is a defect state and not what a queued plan is, and the deferred bucket only fills for unauthorised or undispatchable plans, which is why it is empty.

Deliverable: a second, derived axis. Keep dependency readiness exactly as it is and add schedule readiness beside it, with the deferred rows carrying a computed reason naming the sprint they sit behind. Derived, so it cannot drift — the same property that makes feeds_sprints trustworthy. “Held behind an earlier sprint” stops being prose in a transcript and becomes a field, and two readers can no longer disagree.

Two constraints, and the first is written in the file already. The comment above _AUTHORISED_STATUSES explains why draft counts as authorised: withholding readiness for a labelling reason “produces a queue of implementable work that reads as blocked.” The identical trap applies here, which is why deferred rows must stay distinct from blocked ones, carry their reason, and keep appearing in the ordered roadmap. Nothing may disappear; it only stops claiming to be startable. Second, the rule must key on sprint order and open work rather than the active label, because the label cannot currently be evaluated: S5, S9 and S12 are all active, active_sprint_id names S5, and the work landing most recently was in S13, which is still planned.

What the rule reveals is the more valuable half. Applied strictly, schedule readiness would defer almost everything behind S5, because the project has five sprints open at once. That is not an argument against the field — it is the field doing its job, and the only honest reading is that the sprint horizon is five deep and nobody could see it. Choosing how wide the horizon should be is a decision below, not something this plan may settle on its own.

Done when a plan whose sprint sits behind an earlier sprint holding open work is reported schedule-deferred with a reason naming that sprint while remaining dependency-ready and still listed in the ordered roadmap; the two axes are separately readable so neither question is answered with the other's data; and the reported horizon depth for this project matches a hand count of sprints holding open work.

§5 — The seam that opens once lanes are wide

Two constraints only bite above one lane, so they belong here rather than in §3.

The coordinator re-arms once per event. The project watch exits on the first live pointer to turn terminal, which is exactly right for one lane and wrong for several: at N lanes the coordinator spends N arm-and-wake cycles on N events it could have drained as a stream. A follow mode that emits one event per terminal run, ending when the fleet empties, turns the wait into a queue the coordinator drains.

Worse than inefficient at width: the watch has no memory, so it re-fires on a run it already reported. Measured on a five-lane wave. A scout finished, the watch exited naming it, the coordinator re-armed before promoting it, and the watch exited immediately on that same run again — because the only thing that clears a terminal pointer from its view is promotion. So the oldest unpromoted run masks every later event, and a coordinator that re-arms while holding any backlog is woken by history rather than by news. At one lane this is invisible, because the coordinator promotes before re-arming. At five it is a busy loop that hides the four runs still working.

Follow mode therefore needs a memory, not only a stream: it emits each run once and then keeps waiting, rather than re-reporting whatever terminal pointer happens to be oldest. That also removes the ordering trap where the coordinator must promote in the order the watch happens to surface, instead of the order the work argues for.

The arming decision shipped its reporting half and not its enforcing half, and the difference was measured. Dispatch returns watcher_live, which is exactly the right fact at exactly the right moment — and it was returned false twice in one session and ignored both times, once because the coordinator armed a watch with a shell ampersand that the harness was not waiting on, and once because it simply did not look. Two workers then finished unnoticed and were found only when the lead asked whether anything was still alive. A field a coordinator may ignore is the same mechanism as a rule it may skip, which is the argument this plan's parent made before it.

Deliverable: dispatch refuses to start work into an unwatched project. No live watcher for the project, no dispatch — the same guard class as the unreconciled backlog and the member collision, fired at the same moment for the same reason, and needing no capability from the host harness at all. --no-watch is the recorded override for a genuinely synchronous one-off, so the escape hatch is explicit and lands on the run.

The three fences then compose into one invariant with no gap a coordinator can fall through: work cannot start unwatched, more work cannot start while finished work sits unreconciled, and a session cannot end with runs outstanding. Each is a refusal at a moment somebody is provably present, and none of them depends on anyone remembering anything.

Follow mode is what makes the refusal cheap rather than nagging. A watch that exits on the first event has to be re-armed between every landing, and that re-arm window is precisely where both failures above happened. One watch that streams an event per terminal run and ends when the fleet empties covers a whole wave, so the invariant holds for the duration of the work rather than between interruptions. Arming with no coordinator action at all remains host-local — a settings hook on the dispatch call for this harness — and stays in the harness reference, because a refusal that works everywhere is worth more than an automation that works in one place.

Integration is the real ceiling, and it is one coordinator wide. Audit, merge, promote, plan-write, push are strictly serial in one session: one git index, one plan version, one ledger version. Two sprints can be shipped concurrently by two sessions — sprint state is already distributed per sprint resource, so there is no contention there — and what remains shared is the run ledger and the primary branch, both version-paired, so the failure mode is retry rather than corruption. What is missing is a stated rule for who pushes, and a retry that does not surprise the loser.

A resumed run is invisible to observation, in three ways with one cause: nothing in the run record points at the current attempt. All three were measured on this plan's own first node, which stopped at its scope fence, was answered, and was resumed in the same session.

What was readWhat it saidWhat was true
the manifest, by a freshly armed watchblocked, fired instantlythat blocker had already been answered; it was written before the resume

Each reading is individually defensible and together they make a working run look finished, stalled and already-reported at the same time. A coordinator that trusts any one of them stops watching a live worker. The hazard is not confined to resume: any redispatch of a node id that has run before inherits the stale manifest, and it worsens with lanes, because every stale artifact in the fleet is a false wake-up competing with the real ones.

A fourth reading has the same cause and blocks the repair outright. crew resume refuses a run whose record carries no captured session id, telling the caller to observe it first. The session id was in the stream from the worker's first turn; only observe folds it into the record, so answering a stuck worker requires a preparatory command whose sole purpose is to copy a value that already exists. It cost one call here because the error names the fix precisely, and it is still a reader trusting a stored field that a single other command maintains — the same shape as the three above.

The fix is one concept, not four patches. An attempt is the unit: resuming or redispatching starts a new one, and the record names its stream, resets its phase, carries a counter a manifest must beat to be read as fresh, and captures the session id when the stream first reports it rather than when someone asks. Every reader then asks the same question — what does the current attempt say — instead of four readers each trusting a different stale field.

Stopping a watch needs its own command, for the same reason arming did. There is no way to stop a watcher except by finding and signalling its process, so the coordinator reaches for a general-purpose process killer — four times in this session. The pattern given to pkill -f matches the command line of the shell running it, so it kills its own shell before the intended target; that cost one lost resume here, and on a workstation carrying eleven workers across three projects a broader pattern would have killed another session's fleet. No skill mentions this and none should have to: the machinery for signalling a known process precisely already exists in this codebase, verifying the recorded start time so pid reuse cannot redirect the signal, and it is what crew stop already uses for workers. A watcher deserves the same, so the dangerous general-purpose form is never the only way to do an ordinary thing.

Done when a dispatch into a project with no live watcher is refused before any worktree exists, naming the arming command, while --no-watch dispatches and records the waiver on the run; a watcher records its parent and declines to register when it is orphaned, so a watch nothing is waiting on stops counting as live; one command stops the registered watcher for a project by verified pid and start time, reaching no other project and no worker; follow mode emits one event per terminal run over a multi-run fleet, never emits the same run twice, and ends when the last pointer is reconciled; a resumed run reports the current attempt's stream as its log, a non-terminal phase while its process is alive, and a watch that does not fire on the previous attempt's manifest, all three demonstrated by one test that resumes a blocked run and asserts the watch waits while the stream stays fresh; and two concurrent sessions promoting runs into the same ledger both succeed, with the contended write retried rather than failed, demonstrated by a test that runs the two promotions concurrently.

§6 — Peers are named so they can be avoided, never so they can be asked

The dispatch contract already introduces workers to each other, and then forbids contact. Every worker prompt carries a block naming its concurrent peers and their paths, under the heading that tells it never to touch them and to request a scope change instead. A peer is presented as a hazard. It is never presented as the one process on the machine that already knows the answer to the question the worker is about to guess at.

The common case is adjacent scope, not shared scope. One node owns the module where a function is being designed; another owns the caller. Their files are disjoint, so no exclusivity rule is violated and no conflict is detectable — and the second node still has to know the first one's signature. Today it guesses, or it stops. Executing the plan that produced this one, three consecutive nodes each needed the previous node's names, and the coordinator resolved it by writing the names into every node contract by hand. That works and it does not scale past one coordinator's attention.

One distinction governs the whole section, and relaxing it would undo the merge invariant. Communication carries shared knowledge. Exclusivity governs shared writes, and stays exactly as strict as it is now: two workers that agree perfectly still produce two divergent commits to one file, and reconciling those is the orchestrator's job. So a channel may settle an interface, a name, a call signature, an ordering, or the answer to “have you already moved that”. It may never hand a path from one live scope to another — that remains a coordinator decision, because the coordinator owns the claim registry that makes it safe.

Deliverable: a peer channel, on by default for adjacent nodes. Adjacency is computable from §3's conflict graph — nodes whose declared scopes are near-missing rather than overlapping, plus nodes a coordinator names explicitly. For those, dispatch wires the channel and tells each worker who its peers are and how to reach them, in place of a block that only says what not to touch.

Blocking, never polling — the same lesson, one level down. A worker that polls an inbox spends its own time budget on the failure this repository has already paid for twice. A peer read blocks until a reply arrives or a bounded wait expires, reusing the watch mechanism rather than inventing a second waiting style, and a timeout degrades to the existing NEEDS-HELP: report so an unanswered question still reaches the coordinator.

The transport is per launch kind, and only one of them exists today. An in-harness worker inherits the host harness's own inter-session messaging, which is why this is worth doing at all. A CLI-spawned worker is a separate process with no channel, so it needs a file-backed mailbox in its run directory — the same durable-delivery shape the manifest already uses, for the same reason: a message that exists only in a process is lost when the process ends.

Done when two concurrently dispatched adjacent nodes exchange a question and an answer without coordinator involvement, evidenced in both run directories; a peer read that receives no reply within its bound produces a NEEDS-HELP: report naming the unanswered question rather than expiring silently; a worker attempting to take a path held by a live peer claim is still refused; and the channel is wired without the coordinator naming it, for a node pair whose adjacency §3 computed.

§7 — Two dispatch targets, because they optimise different things

A sprint and a dependency closure are not competing units, they are opposite optimisations, and this session measured both. A sprint concentrates work on one area — and therefore on one set of files, which is why the two plans inside one sprint collided on four paths while pairs drawn from different sprints were disjoint. A closure follows dependency edges rather than topic, so it picks up disjoint work naturally and crosses repositories without trying.

SprintEndpoint closure

Nothing about a closure is stored except the name of its endpoint. Depth, the ready frontier, feeds N, the critical path, shipped-of-total and the repository set are all reads over depends_on, and average width is arithmetic over two of them. Realisable width is the lane partition from §3 applied to the frontier. A handle lives on the endpoint plan itself, so it cannot dangle: delete the plan and the handle goes with it.

The one interaction to settle deliberately. A closure ignores sprint order by construction — that is the point of shipping an outcome quickly — while §4's window will mark part of that closure deferred behind an earlier sprint. Shipping a closure is therefore an explicit override of the schedule window, recorded like any other, and the view states its cost: how many of its members the window would have deferred. Two mechanisms that disagree silently are worse than either alone.

Done when a ship target resolves an endpoint handle to its transitive closure across every mounted repository the closure reaches, with no membership stored anywhere; the closure reports ready, realisable, average width and critical path from derived state alone; an open decision inside the closure refuses the ship until it is locked or explicitly deferred; and shipping a closure whose members the schedule window would defer records that override on the run rather than proceeding silently.

§ Decisions

Where are candidate write paths declared, so a wave can be planned before launch?

Planning a wave needs paths one step earlier than dispatch, where they are currently invented per node. The coordinator knows its own nodes; it does not know another plan's.

Locked 2026-08-24 by the lead. The coordinator knows its own candidate nodes, which is enough to partition the wave it is about to run, and it needs no plan-authoring change to start. Section-declared scope was rejected on maintenance rather than capability: scopes written into plan HTML rot as code moves, and nothing verifies them, so the project would be hand-maintaining a second map of itself. The accepted limit is that a wave manifest cannot answer whether a plan nobody is running would collide.

Where does the per-project source-to-generated map live?

Claiming a schema source must claim its generated artifacts, or two nodes will be judged disjoint and collide on a regenerated file. The map is per project because the derivations are.

Locked 2026-08-24 by the lead, against the recommendation of a flight-config layer. A source-to-generated map is a fact about repository structure, and the project resource already carries the other one - the scope policy naming what a repository owns, excludes and routes elsewhere. Putting it in flight config would buy layered resolution and per-host override for a fact that has no reason to vary by host, at the cost of blurring runtime routing with repository structure. The accepted limit is a single unlayered answer per project.

How wide is the schedule horizon that schedule-readiness enforces?

Strictly applied to a project with five sprints open, an earliest-open-sprint rule defers nearly everything. The width is a policy choice about how much work may be in flight, not a derivation.

Locked 2026-08-24 by the lead. The window makes how much work may be in flight an explicit policy number rather than a consequence of the rule's shape. Earliest-open-sprint was rejected because with five sprints holding open work it would defer almost everything behind S5 on the day it shipped, which reads as the tool breaking rather than the horizon being five deep. Every-active-sprint was rejected because the active label cannot currently be evaluated - S5, S9 and S12 are all active while active_sprint_id names S5 - making it a two-step change gated on a sprint cleanup. The accepted cost is that N must be justified.

How do two sessions shipping two sprints share the primary branch?

Sprint state is already per-sprint, so the contention is the run ledger and the primary branch. Both are version-paired, so this decides who waits, not whether anything is lost.

What makes two nodes adjacent enough to be wired together by default?

Too narrow and the channel is never on when it would have helped; too broad and every worker is handed a roster of peers it has no reason to talk to. Overlapping scope is already refused, so adjacency is about near-misses.

Locked 2026-08-24 by the lead. An import or call edge captures the actual reason two workers need each other: one owns the definition and the other the caller, which is the case measured on three consecutive nodes whose names the coordinator had to write into every node contract by hand. Shared-parent-directory was rejected as too coarse in a flat package, where every node touching the same directory becomes every other node's peer. Same-plan-or-section was rejected because it misses the cross-plan case entirely, which is the case that prompted the section. All-concurrent-peers was rejected as a roster with no signal in it. The accepted cost is static analysis, and that the edge computation is language-specific.

What is stored for a dependency graph?

The view needs a stable short handle for quick dispatch, but stored membership rots the moment a plan joins the DAG later.

Locked 2026-08-24 by the lead. Stored membership was rejected because a hand-picked list silently misses a plan that joins the DAG afterwards, which is the same rot an authored sprint edge has and the reason feeds_sprints is derived. No handle at all was rejected on ergonomics: the lead wants a short quick-dispatch target, and typing the endpoint slug each time is friction on the pattern the graph exists to make fast. A handle carried on the endpoint plan cannot dangle, because deleting the plan deletes the handle, and it costs one meta field exactly parallel to the sprint one.

When is a sprint the dispatch target and when is a closure?

Both were measured this session: two plans inside one sprint collided on four files, while pairs drawn across sprints were disjoint.

Locked 2026-08-24 by the lead on measured behaviour rather than preference. A sprint concentrates work on one area and therefore on one set of modules, which buys coherent review and clean closure at the cost of width; a closure follows dependency edges rather than topic, so it selects disjoint work and crosses repositories naturally, buying latency to one outcome without closing any region. Retiring either would lose the property the other provides. The sprint keeps lifecycle ownership so plan and sprint accounting stay in one place; the closure is a selection lens over the same plans and owns no state.

What happens when a closure spans plans the schedule window defers?

A closure ignores sprint order by construction, which is its purpose. The schedule window added this session will mark part of most closures deferred.

Locked 2026-08-24 by the lead. Letting the window win would defeat the whole reason for shipping a closure, since the fast path to an outcome almost always reaches past the current sprint. Ignoring the window silently is worse than either: two mechanisms disagreeing without saying so leaves the coordinator following whichever it read last. Recording the override keeps both honest and makes the cost visible at the moment of choosing, exactly as the unreconciled-runs waiver does.

Does an unresolved decision inside a closure block shipping it?

roadmap computes dependency, explicit and gate blockers today and never reads decisions, so an open decision costs nothing and can be scrolled past.

Locked 2026-08-24 by the lead. A decision that only displays is a warning with no adjacent cost, and this repository has already paid twice for warnings that were scrolled past. Making it refuse gives an open decision a price, which is what causes it to be answered. Explicit deferral is what stops the mechanism deadlocking: a decision the lead judges non-blocking is said so once and recorded, rather than being worked around silently.

§ Followups

Start with the claim registry, because it is the gate that already cost a session its parallelism

§3 is first on evidence rather than preference: the file-scope gate is what forced a three-node wave into one lane while fifteen members sat idle, and it is the only one of the three gates with no representation at all in the model. It also needs no new store — the claims are already in the live pointers and already expire with them. Take the derived peer scopes and the containment rule before the planner, since a refusal that names the owning run is useful on its own and the planner is only worth building once the comparison it depends on is trusted. §4 can run in parallel with it: roadmap readiness shares no file with the dispatch guard. §6 follows §3, since the channel is wired from the adjacency §3 computes. Settle scope-declaration-site before the planner and schedule-horizon-width before §4 lands, because both change what the deliverable is rather than how it is written.

Two defects in the watcher guard, both found by using it within the hour and both recorded before repair. FIRST, a bootstrap deadlock: crew watch on an empty project exits immediately with no_live_pointers, and dispatch refuses when no watcher is live, so the first dispatch of any wave can never have one. Correcting an earlier claim recorded in this section. It says reckon cannot portably detect a watcher the harness is not waiting on, because it cannot know how the host launched the process. That is true of which primitive launched it and false of the property that matters, which is whether anything will observe the process exit. A watch backgrounded with a shell ampersand outlives the shell that spawned it and is reparented to init, so its parent id becomes 1; a harness-launched background command keeps a living parent that reaps it. Orphaning is therefore a direct test rather than a proxy, and it is POSIX rather than host-specific. Deliverable, and it belongs with follow mode because both are watch semantics on the same module: crew watch records its parent id in the lock and declines to register as the project watcher when it is orphaned, and watcher_live requires that recorded parent to still be alive, so an orphaned watcher stops counting and dispatch refuses again. Accepted limit, stated rather than hidden: this proves something is waiting on the process, not that the something is a coordinator, so nohup, systemd and disown all read as orphaned. Flagging them is correct, because none of them can wake a coordinator either.
