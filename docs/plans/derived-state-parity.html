Surface parity · the derivations that exist in only one language

One Derivation, Every Surface

The surface sprint taught four surfaces to derive state the stored files do not carry: a sprint's real completion, every dependency endpoint rather than only the named ones, a live cross-project rollup, and a schedule anchored at now. All four were implemented in JSX, so they are visible to a human with a browser and invisible to every agent, every CLI call and every MCP read. This plan moves each derivation into Python, makes the surface a consumer of it, and adds the check that fails when the two disagree.

The failure this produces is the one this repository keeps rediscovering: two implementations of one truth, and no check that they agree. It has already cost a session tonight in three unrelated places — a stale renderer drawing a wrong column, a stale follower recovering nothing, and a session field read from one of three possible sources. A derivation implemented twice is the same defect with a longer fuse, because nothing fails when the copies drift; the surface simply starts telling a different story from the tool, and whichever reader is wrong does not find out.

§2 — Sprint state derives once, and drift is reported everywhere

The rule is the surface's, and it is right: a sprint's state comes from member completion, and where the stored file disagrees the disagreement is reported rather than silently resolved, because resolving it hides a real inconsistency the sprint skill should repair. That rule belongs in roadmap, which is what every agent already reads for sprint order and readiness. Each sprint row gains derived_state and, when it differs from the stored value, state_drift naming both. docs/ui/sprint.jsx then reads those fields instead of recomputing them, and its was <status> flag renders whatever the payload reports.

§3 — An endpoint is enumerable without a handle

An endpoint is a plan with prerequisites that nothing depends on. The surface finds them structurally and renders named and unnamed alike; the graph read requires an authored handle, so the set an agent can address is a subset of the set a human can see, and the difference is invisible from either side. roadmap(project) gains an endpoints list — every endpoint with its closure membership, depth, shipped fraction, repositories spanned and open-decision count, each carrying its handle or null. The named-handle read keeps its exact current contract; this adds enumeration beside it, so /reckon-ship graph:<handle> still refuses an unnamed endpoint rather than inventing a target, and the surface's needs plan-graph-handle chip and an agent's refusal now name the same missing precondition.

§4 — The rollup is a read, not only an HTTP payload

reckon/fleet_index.py computes the one cross-project view in the system and nothing outside the HTTP handler can call it. An agent asking “which projects are moving, and how far along is each” has no answer, while the fleet home answers it in a glance. The module gains a CLI reader (reckon fleet) and an MCP view, both returning the same rows collect_projects serves, so the three surfaces answer from one computation. It stays read-only and cross-project: it mutates nothing and it is the one place where a row from another repository is legitimate data rather than something to act on.

§5 — The schedule is computed once

The schedule is the most valuable of the four and the most thoroughly stranded: twenty-six references in one JSX module, answering “when does this chain finish” for a browser and nobody else. It is also the derivation an orchestrator most wants, because it is what turns a dependency graph into a wave plan. It moves to Python as a function over the same inputs the surface uses — plan wall-clock hours, depends_on, edited stamps for landed work, live run dispatch times — and returns bars, best-fit lanes and the chain's far end. roadmap reports the far end and the lane count; the full bar list is available through the schedule read for callers that want it, and docs/ui/crew.jsx renders the payload rather than recomputing it.

Gate for this plan, recorded when the measure runs: for this repository, the sprint state, endpoint set, rollup rows, lane count and chain far end that the SPA renders are equal to what roadmap and the new reads return, compared field for field by the §6 check rather than by inspection. Its evidence is that check passing plus one recorded run of each new read against this checkout, with the endpoint count, the rollup row count, the lane count and the far-end figure written into the execution record.

§6 — The check that makes parity hold

Moving the four derivations is worth little on its own, because nothing would stop the next surface node from inventing a fifth. Parity needs a bound check, and the check has to compare the surfaces rather than assert about one of them: for a single fixture project, render the surface, call each read, and require the rendered values and the returned values to be equal. It is the only form that fails when a copy drifts, which is the failure mode this whole plan is about — and it is the reason the four nodes above each assert against the other surface's result rather than against a literal, because a literal in both places drifts silently in step.

The check also names what parity does not mean: geometry stays in the surface. Card sizes, gaps, edge routing and lane heights are presentation and have no agent-side counterpart. What must agree is state and derived fact — a sprint's completion, an endpoint's membership, a project's counts, a chain's far end.

§7 — Out of scope

Presentation stays in the surface: the DAG geometry helper, card and lane dimensions, edge routing, colour and the capture harness are not moved and have no agent-side counterpart. No new store and no caching layer — each read computes from the same discovery and ledger inputs the surface uses today, and a cache would be a fifth place for the truth to differ. The plan-state write path is unchanged; every read here is read-only. Whether the SPA should degrade when a derivation is unavailable is a surface question for a later plan, not a parity question.

§ Decisions

Where does a derivation live when both a surface and an agent need it?

A mirror is two implementations of one truth, which is the defect being fixed rather than a way of fixing it. Leaving it means an agent and a human reading the same project disagree with no way to notice. Python is where the CLI and MCP already read, and the surface already consumes payloads for everything else.

When derived sprint state disagrees with the stored file, which wins?

Resolving it silently hides an inconsistency the sprint skill should repair, and the surface already made that choice deliberately. Keeping only the stored value is what leaves an agent reading planned for a finished sprint.

What form does the parity check take?

Literals in two places drift silently in step and the test keeps passing, which is exactly the failure being guarded. Only a comparison between the surfaces fails when one copy changes.

Does layout geometry move to Python as well?

No agent reads a card width or an edge path, so moving geometry would add a payload nobody consumes and couple the surface's visual design to a server release. The line is whether a reader without a browser has a use for the value.
