§1 — Why: every crew store grows without a bound

Measured on clu-2068 on 2026-10-22 (monitor-storage-load-rca):

  • live pointers average about 44 KB and reach 94 KB, though a reader needs a few hundred bytes of them; picker_selection alone is 33 KB, then unreconciled_override 9 KB, argv 8.6 KB, admit_request 6.7 KB;
  • ~/.config/reckon/crew/runs/ holds 17,159 run directories in one directory;
  • crew/watch/ holds 252 MB of event logs, reckon's alone 92 MB, with no rotation, and stale .lock.registration.*.tmp files from crashed registrations back to 2026-10-07;
  • reload images sit on GPFS under crew/reload-trees/ with cross-node lease records.

Every reader of these pays for their size, and every scan pays for their count. This plan bounds each one. It is independent of the station except where a section says so.

Measured again on clu-2068 on 2026-10-23: runs/ holds 17,341 directories, of which 40 have a live pointer and none a queued entry; 8,861 are review runs. By last change, 533 are under a day old, 1,170 one to three days, 2,285 three to seven, 3,124 one to two weeks, 6,004 two to four weeks and 4,225 older than thirty days. A random sample of 200 held 3.1 GB, which puts the directory at about 270 GB. The largest holders in the sample were each codex run's own download of the codex plugin catalog under codex-home/cache/ and codex-home/plugins/, per-run tool caches under cache/ (matplotlib, xdg, numba), stream.jsonl, resume-*.jsonl and baseline-tree.tar.

crew gc already prunes a ledgered run directory older than thirty days whose stream-derived figures are on its ledger row (the retention_days pass in reckon/crew/gc.py). Three things keep that from bounding the directory: no unit or timer runs it, so it prunes only when an operator remembers; it judges runs against one project's ledger, so a run another project dispatched is never judged; and it keys on the directory's age rather than on whether anything can still need the run. It is also too slow to schedule as built: a dry run of crew gc --project reckon on 2026-10-23 printed nothing and was killed at its ten-minute limit, and when sampled it was running git status --untracked-files=all inside one of the checkout's 48 worktrees.

The committed run records under docs/state/<project>/runs/ are a different store, owned by history-persists-as-detail-washes-out; this plan bounds the crew home. The one-off reclaim of the crew home's other backlogs stays with the-crew-home-has-a-bound §5.

§2 — A live pointer carries only live facts

Dispatch-time detail that no live reader consults moves from the pointer into a file in the run's directory, written once at dispatch. The first six fields are picker_selection, admit_request, argv, competence, peer_scopes and unreconciled_override. The pointer keeps a path to that file. Every reader of a moved field reads it through one accessor in reckon/crew/runs.py that falls back to the pointer, so pointers written before the change still read.

Measured 2026-10-27: moving those six left a test dispatch's pointer at 15.7 KB, and production pointers at 11.8 to 28 KB. The content reviews of 2026-11-02 measured which fields carry the weight on the live pointers of that day: suite_evidence reaches 158 KB, dispatch_options 31 to 41 KB (it also holds a nested copy of picker_selection), and peer_channel 7 to 9 KB. With every field below moved, 25 of that day's 57 pointers stayed at or above 8 KB, the largest at 11.4 KB, most of the remainder being node; the same simulation over the 114 live pointers of 2026-11-05 left the largest at 18 KB, so the live population's size moves with what other work adds to a pointer. So the moved set is: the six above; dispatch_options, moved when the request launches, since a queued request launches from it and queue_admission.py and queue_edit.py read it until then; suite_evidence, which _record_suite_evidence in queue_landing.py writes and no module reads, though three cases in tests/test_the_landing_pass_measures_and_lands.py read it off the pointer and move to the accessor with it; peer_channel; and the dispatch-time fields directive, authority, pace, watch, lane_advisory and final_message. node stays whole on the pointer, because the board reads it for every live run (_crew_rows in reckon/serve.py). The lead decided on 2026-11-05 that the bound is 12 KB. It applies to what this section controls, a pointer written by a test dispatch, because the live population grows with fields other work adds.

The readers are taken from an ast walk of reckon/ and tests/, not from a list written here. On 2026-11-02 the moved fields were read in queue_admission.py, queue_edit.py, dispatch.py, dispatch_claims.py, dispatch_plan.py, dispatch_sessions.py, dispatch_peer.py, dispatch_picker.py, promotion.py, promotion_checks.py, recovery_wait.py, recovery_watch.py, model_catalogue.py, reckon/run_record.py, reckon/pace_report.py and reckon/hooks/native_agent_guard.py. The section runs as three nodes in order. The first re-applies the six-field move preserved at commit 31091b24c on branch preserve/dispatch-detail-moves-off-the-live-pointer, with the nested picker copy and every reader of those six routed through the accessor. The second moves the small dispatch-time fields and peer_channel. The third moves dispatch_options at launch and suite_evidence; its readers are the queue's own modules, so it is dispatched with --after on the queue owner's pending runs on those files rather than through a section wait, which would hold the first two nodes as well. No node of this section keeps a write claim while blocked; a blocked node is discarded and dispatched again.

Done when: an ast walk of reckon/ and tests/ finds no read of a moved field on a live pointer except through the accessor; a pointer written by a test dispatch is under 12 KB and carries none of the moved fields; after the third node lands, a pointer written by a real dispatch carries none of them; the sizes of the live crew home's pointers when the third node finishes are recorded as a table in its committed evidence fragment, naming the largest fields that remain, as information rather than a pass condition; tests that read each moved field pass for a pointer of the new shape and one of the old; and a promoted ledger row still carries every field it carried before. Negative control: an accessor without the fallback must fail the old-shape test.

§3 — Only a run something can still need keeps its directory

A run's directory is kept while something can still need it, and retired once nothing can. Something needs it while the run has a live pointer or a queued entry; while it has no terminal ledger row, being neither promoted nor discarded, and so may still be resumed; while a review of it is owed or in flight; and while the figures derived from its stream are not yet on its ledger row. Once none of those holds, the directory is removed after a grace window declared in flight config, one day by default, so that a reader holding a path to it does not lose it mid-read. Nothing is archived. The run's durable facts are its ledger row, its committed run record and its evidence fragment, and they outlive the directory. Research that needs a worker's stream copies it as evidence before the window closes. Review runs are runs, and the same rule retires them.

The rule extends the retention pass in reckon/crew/gc.py, which already withholds a run whose derived figures are missing. It replaces that pass's thirty-day directory age with the test above and adds no second sweep. With finished runs retired, runs/ holds the runs in flight and about a day of finished ones, a few hundred entries. That is why the dated subdirectories this section first proposed are dropped, and why runs.run_dir keeps one location.

Done when: in a temporary crew home, a dry run of the sweep over fixture runs in seven states lists only the last of them for removal. The states are live, queued, unpromoted, promoted with a review owed, promoted with derived figures missing, promoted and reviewed inside the grace window, and promoted and reviewed past it. The real run removes exactly that one and leaves the other six, and each removal is printed with its path and size before it happens. Negative control: the predicate reduced to directory age alone must fail on the unpromoted fixture, whose directory is older than thirty days.

§4 — The old event logs are retired

Once the station has taken over (the-monitor-reads-each-fact-once §12), the per-project .events logs, their .followers lease directories, the seat locks and the stale registration temporaries are compressed into one dated archive under the crew home and removed. The sweep names every path it removes and refuses any whose mtime is within the last hour.

Done when, in a temporary crew home seeded with a copy of those files, the sweep's dry run lists the paths with sizes, the real run removes exactly that list, and the copy's crew/watch/ holds under 1 MB afterwards. The live crew home is swept once, after the test passes, with its dry-run listing read first. Negative control: a log written within the hour must be refused and left in place.

§5 — Reload images live on node-local storage

When only the station reloads (the-monitor-reads-each-fact-once §7), the reload image cache moves to the node-local runtime root and the cross-node lease records in checkout_trust (_record_lease_node, _prune_must_keep's host branch) are deleted, because no image is shared between nodes any more.

Done when the reload tests pass with the cache under a temporary runtime root, the cache path is never under the crew home, and the lease-record functions are gone. Negative control: a cache resolver returning the crew-home path must fail the path test.

§6 — A worker's harness caches leave with the worker

Why. §1's sample found that the bulk of a codex run's directory is caches its harness built for that one process, kept for as long as the directory lives. One is the codex plugin catalog under codex-home/cache/ and codex-home/plugins/, which every codex run downloads afresh. The other is the cache/ tree a worker's tools fill (matplotlib, xdg, numba). Nothing reads either after the process ends.

Change. When an attempt's process exits, the code that writes that attempt's exit record (_supervisor_exit_record in reckon/crew/dispatch_launch.py) removes those caches before it returns. Nothing removes them at any other time, so a running attempt, including a later attempt of the same run, is never touched; a resumed codex attempt downloads the catalog again, as every codex run does today. The harness session files a resume needs, codex-home/sessions/ (named by RUN_HOME_SESSIONS in reckon/crew/rollout.py), are kept until §3 retires the directory.

Done when: a fixture run whose directory holds both caches and a sessions tree, put through the exit path, keeps the sessions tree and has neither cache; a fixture that has not exited keeps everything; a run whose first attempt has exited and whose second is running keeps the second attempt's caches through any later read of the first attempt's exit record; the removed paths and their sizes are on the exit record. Negative control: a removal that also takes codex-home/sessions/ must fail the resume fixture. Write paths: reckon/crew/dispatch_launch.py and a new test file. Every log is under the run directory.

§7 — The retention sweep runs on its own, across every project

Why. §3 says which directories may go, and §1 shows that a rule nobody runs bounds nothing: the thirty-day pass has existed while 4,225 directories older than thirty days accumulated.

Change. An hourly user timer, the same arrangement as reckon-paid-lanes.timer, runs the §3 sweep over every project in mounts.json, judging each run directory against the ledger of the project that dispatched it. Each pass removes at most 500 directories, so one pass stays short on shared storage, and the first passes reclaim the existing backlog at that rate. A pass appends its removals to one log under the crew home, which rotates at a fixed size, and writes nothing when there is nothing to remove. A directory no mounted project's ledger records is left to crew gc's existing unledgered-directory pass. The pass runs the run-directory retention alone, not the rest of gc, and runs no git command, because gc's worktree checks are where §1's dry run spent its ten minutes.

Done when: one pass over a temporary crew home holding finished runs for two projects, each ledgered in its own project, removes both; a second pass with nothing left writes no log line; a pass over 1,200 removable fixtures removes 500 and leaves 700 for the next; a pass whose fixture checkout carries worktrees starts no git process; and the unit files install the timer at an hourly interval. Negative control: a pass that reads only the first project's ledger must leave the second project's run in place and fail.

§8 — A run's scratch leaves with the run, on the host that made it

Why. Measured on clu-2068 on 2026-10-23 at about 14:05Z: 107 run scratch directories under /tmp/reckon-crew-scratch/ hold 9.7 GB. 62 of them belong to promoted runs with no live pointer, 1.3 GB, and a peer on imas-ambix counted 16 GB across 104 directories going back to 2026-10-20. Reading each promoted run's release record shows three ways the scratch survives:

  • 29 runs record scratch_removed: true and their directory is still there. r-20261020T202608740663-shc-gap-docs-regen recorded 5,014 bytes removed while the worker's files from 22:55 to 23:11 remain, so the release removed a same-named path somewhere other than the node-local tree the worker wrote.
  • 16 runs record scratch_removed: false.
  • 13 review and plan-review runs have no release block at all, so a review's promotion never removes its scratch. Two are from today: r-20261023T093727181057 and r-20261023T114328877933.

Change. A directory named for a run is that run's scratch on whichever host it sits, whoever made it: ensure_worker_scratch is reached from the launch supervisor, from the session that composes a launch, a resume or a lane change, and a step-placed worker writes under the same path on its own node. So the rule is kept by run, not by host. A release removes the copy on its own host through remove_worker_scratch in reckon/crew/dispatch_launch.py, the timestamp-stem siblings included, records which host that was, and never reports a copy it did not remove. Every other copy is removed on its own host by a settling pass: it takes each directory under the scratch root that is named for a run with no live pointer, whose run directory records that the run ended (its exit record or a discard marker), and that no process holds, and removes it the same way, with no age wait. The live pointers and run directories are read from the crew home, which every host shares, so no project's ledger is consulted. §3 retires a finished run's directory after its retention grace, so a copy on a host that runs nothing for that long can outlive its record. The settling pass therefore also takes a directory named for a run that has neither a live pointer nor a run directory, and removes it under the orphan sweep's age rule (SCRATCH_GRACE_SECONDS), after the same holder check. Every run-named copy is then removed by a pass that runs, either at once by its run's end record or after the grace once that record is gone. Directories not named for a run keep today's handling by garbage_collect_orphan_scratch. The settling pass is a function of its own in reckon/crew/gc.py, not the garbage_collect_scratch survey, and it runs from three callers, so that every host which can hold a copy runs it: the launch path in reckon/crew/dispatch_launch.py, before it makes a new worker's scratch; the step wrapper (_STEP_TASK_WRAPPER in the same module) when a step-placed worker starts, since a node that only runs steps never launches; and §7's hourly retention_sweep, which calls that pass and nothing else of gc, extending the pass §7 landed. The hourly caller runs only where install_retention_timer has installed the timer, which is the lead's decision and not part of this node; the launch and step callers do not depend on it. Review and plan-review promotions must reach the same release as an implementation run. The completion paths in reckon/crew/promotion.py, reckon/crew/promotion_records.py and reckon/crew_run_commands.py call _release_after_promotion (reckon/crew/promotion_release.py), yet 13 review runs carry no release block, so the node first reads the promoted records of those runs and the paths that promoted them, names the route that skipped the release or ran it without recording it, and puts that route through the same release. Four of the 62 promoted runs whose scratch survived fit none of the three records in the list above; the node reads those four too and names their route. The names and the evidence go in the fragment.

Done when: in a temporary crew home and scratch root, a release on its own host removes that host's copy and its timestamp-stem sibling and records scratch_removed: true naming the host; a release on a host holding no copy reports nothing removed; on a second host a worker launch, and separately a retention_sweep pass, remove the copy of a run that has no live pointer and whose run directory records its end, whatever the copy's age; a copy of a run that still has a live pointer, or that a process holds, is left; a run-named copy whose run has no live pointer and no run directory is removed by the settling pass once its ctime passes the orphan grace, and left before then; a step starting on a third host removes a finished run's copy there; the fragment names, with the record paths it read, the route that let review promotions skip the release and the route of each of the four unexplained survivors, and a case drives a review promotion through the named route, which leaves the scratch and no release block at the base and removes it with a release block at the head; and a promoted review run's scratch is removed by its promotion. Negative control: a settling pass that keeps the orphan sweep's age wait leaves the fresh copy of a finished run in place and must fail the second-host case. Write paths: reckon/crew/dispatch_launch.py, reckon/crew/promotion.py, reckon/crew/promotion_release.py, reckon/crew/promotion_records.py, reckon/crew_run_commands.py, reckon/crew/gc.py and tests/test_a_runs_scratch_is_removed_on_the_host_that_made_it.py. A skipping route found in any other module is named in the fragment and reported as a blocker rather than worked around. Every log is under the run directory, and the evidence fragment quotes each gate's command and summary line.

§10 — A retention pass finishes inside its slot

Why. On 5 November reckon-f8 ran the retention pass as a dry run (python -m reckon.crew.gc --limit 100000, no --apply) from the main checkout on clu-2068. It was killed at its 1,800 s timeout with empty stdout, while ~/.config/reckon/crew/runs held 20,003 run directories (563 GiB). Two phases are candidates:

  • _retention_ledger_records, which reads every mounted project's ledger through its index;
  • _run_directory_retention_report, which judges each run directory on GPFS.

The installed pass uses --limit 500, and the limit counts only offered rows, so withheld rows do not stop it. A slow phase means an hourly pass may never finish inside its hour, and the reaper §7 installs would then reap nothing. That run shared the node with parallel censuses and a 1.65 TB copy, so the cost is not yet attributed.

Deliverable. First measure the pass on a quiet window, with per-phase timings, and name the slow phase in the manifest. Then bound the pass's work: --limit counts every judged directory, not only offered ones, and the pass resumes from a cursor persisted after the last directory it judged, so a run of permanently withheld directories at the head of the sorted list (review owed, a derived figure missing) is passed over once per cycle rather than consuming every pass's budget; each phase reads its inputs once per pass; and the pass prints its progress and per-phase timing to stderr as it goes, so a killed pass still leaves a record while stdout keeps the one JSON report that main() and crew retention-sweep emit. A pass of 500 directories finishes in under five minutes on the real store.

Done when a new tests/test_a_retention_pass_is_bounded.py shows five things on a synthetic crew home of 2,000 run directories:

  • --limit 100 judges at most 100 directories however many are withheld.
  • With the first 300 sorted directories permanently withheld, consecutive passes of --limit 100 reach a prune candidate behind them by the fourth pass.
  • A pass interrupted part-way has already printed its progress.
  • Every pass prints one timing line per phase to stderr, naming the phase and its seconds, and its stdout still parses as one JSON report.
  • A pass over 2,000 directories in one project calls flight.resolve once, counted through a patch, rather than once per judged directory as _run_directory_grace_seconds does now.

Then a host measure on a quiet window: a timed dry run with --limit 100000 on clu-2068 records each phase's seconds and names the slowest phase, and one dry run with --limit 500 finishes in under five minutes. Both runs' printed timings are committed as docs/evidence/fragments/crew-state-stays-bounded/a-retention-pass-finishes-inside-its-slot.html, which the manifest cites. Two negative controls: counting only offered rows again makes the first case fail, and resetting the cursor at the start of every pass makes the withheld-head case fail. The test files importing reckon.crew.gc add no failure against the base revision. Ruff adds no findings on the staged paths. Write paths: reckon/crew/gc.py, the new test and that fragment.

Ledger caches are shared per repository and pruned by the sweep

Why. On 11 November ~/.cache/reckon held 139 ledger caches, 31.8 GB, a mean of 229 MB each and the largest about 460 MB: 58 built on 10 November and 25 more by 04:00Z on 11 November. ledger._run_index_path keys the cache by the resolved path of one checkout's ledger, so every worker and review worktree builds its own full copy from the 781 MB run store. That is a large GPFS write, and a full read, per worktree. Pruning exists only in crew gc --apply (gc._orphan_ledger_indexes), which nothing ran: 56 caches (16.6 GB) whose checkout was gone were still on disk until the coordinator pruned them by hand. The same root held 7,871 picker-budget-view-*.json files (79 MB), dating from 8 October on.

Deliverable. One ledger cache per repository and projection version, keyed by the repository's common git directory and the ledger's path inside the tree, so worktrees of one checkout share it. A worktree whose ledger differs from the shared one reads through, rather than building its own full copy. The retention sweep of §7 prunes orphaned ledger caches, and picker view files older than seven days, on its own schedule, printing every removal.

Done when a new tests/test_ledger_caches_are_shared_and_pruned.py shows, with a temporary repository, two worktrees and a temporary cache root, that both worktrees resolve one cache path and a second reader builds nothing; that the retention sweep removes a cache whose repository is gone and a picker view file older than seven days, and keeps a fresh one and one a live process holds. Gate logs and importer receipts are kept under the run directory and cited in the node's fragment. Negative control: at the base revision the two worktrees resolve two paths and the sweep removes neither. Matched importer arms run as a partition job and add no failure; ruff check and ruff format --check add no finding on the staged paths.

The run store retires old runs out of its hot tables

Why. ~/.config/reckon/crew/run_store.db was 781 MB on 11 November, holding 21,485 runs and their details, with no age-based retention: rows leave only when a project is reset. Followers and the station page through it on every pass (94% of one follower's reads that morning), so its size multiplies every read.

Deliverable. The retention sweep moves runs that ended more than thirty days ago, and that nothing can still need (no live pointer, open review or open queue request), out of the hot runs and run_details tables into a separate archive file beside the store, so the store's own pages shrink. That archive keeps the fields the ledger and velocity views read. Each sweep pass moves at most a fixed batch of rows (2,000 by default) so it stays inside §10's bound, and an archived run is never re-imported by import_ledger. No full VACUUM runs inside the hourly sweep, because rewriting the 781 MB store on GPFS blocks every reader for the whole rewrite. Compaction is incremental (PRAGMA incremental_vacuum with a bounded page count per pass). Readers of current state touch only the hot tables.

Done when a new tests/test_the_run_store_retires_old_runs.py shows, on a temporary store, that a run ended 31 days ago with nothing needing it leaves the hot tables while its ledger and velocity fields stay readable; that a run with an open review or queue request stays; and that the hot tables' page count falls after the sweep. Negative control: at the base revision the old run stays in the hot tables. Matched importer arms run as a partition job and add no failure; ruff check and ruff format --check add no finding on the staged paths. After landing, the coordinator records the live store's size and row counts before and after one sweep in this node's evidence fragment, which outlives the run directory.
