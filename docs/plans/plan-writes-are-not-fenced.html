§1 — A lost update that advances the version counter

The plan HTML is the store. Two writers reach it: edit_plan, which refuses on a stale expected_version, and the landing write a promotion performs to append its own record. Only one of them is fenced.

Measured in this project on 2026-09-15. An edit_plan appended a comment and returned "Updated … to version 399". A crew complete was in flight on the same plan. Afterwards:

CheckResult

the appended comment, working treeabsent

git status on the planclean

Exactly one comment was lost — the one written inside the promotion's window — and the follow-up git commit reported nothing added to commit, because the working tree already matched a HEAD that did not contain the edit.

A lost update that moves the version is undetectable by construction. Every surface a reader consults agreed the write had landed: the tool returned a new version, the file carried that version, git was clean, and the next reader sees a higher number and concludes it holds the later state. Recovery happened only because the author was still in the session and still held the text.

§2 — The same boundary, seen from the other side

Half an hour later the identical pairing surfaced in the direction that is protected: an edit_plan at expected_version 407 was refused because a promotion had moved the plan to 408, with both numbers named in the refusal. One conflict announced, one lost update silent, same two components, same afternoon.

That is the asymmetry stated as a measurement rather than an argument, and it is why the repair is not "add a check to the landing path" in the abstract: the fence already exists and one caller does not pass through it.

§3 — Two workers appending to one plan, six times

The imas-efit S13 coordinator reports the same boundary from a third direction. Two workers appending landing blocks to the same plan and its evidence archive conflict on every merge — on the plan-version meta, on duplicate section headings, and on duplicate element ids. They wrote reports/ship-s13/resolve_both.py, which keeps both sides, bumps plan-version to max+1 and prefixes duplicate ids, and used it six times across 27 landings.

Their proposal is that the merge helper become a convention, since the landing append already is one. This plan declines that framing, and the reason is the plan's whole thesis: a helper that reconciles both sides makes the unfenced write permanent and correct-looking. It removes the conflict, which is the only signal that two writers reached the same file — and §1 is what that looks like when the signal is already absent.

The conflicts are not the defect. They are the one place the defect currently announces itself.

§4 — Why the obvious fences are each wrong

Three repairs suggest themselves and none survives its own consequence, which is why this plan carries a design decision rather than a node.

  • Fence the landing write on expected_version too. Correct, and it converts a silent loss into a refused promotion — at the moment a worker's work is being recorded, with the coordinator's attention elsewhere. A refused promotion is recoverable and a lost comment is not, so this is an improvement; it is not obviously the right one.
  • Serialize: no plan edit while a promotion is in flight. This is what this session adopted by hand after losing the comment, and it works. It is also a rule with no check, which this project has repeatedly found to be a rule that decays — and it does not help two workers, who cannot see each other.
  • Make the append commutative so both writes survive by construction, as the S13 helper does at merge time. This removes the conflict rather than the race, and §1 shows the race producing silent loss with no conflict to remove.

The choice between them is a design decision about who is inconvenienced when two writers meet, and it is the lead's rather than a coordinator's.

§5 — What a repair must demonstrate

Whatever shape is chosen, the measure is the same and it is not "no conflicts". The falsifier reproduces §1 directly: a comment appended while a promotion is in flight on the same plan is either present afterwards, or its loss is reported. Silence with an advanced version counter is the failure, and a repair that produces fewer conflicts while still permitting it has not addressed this plan.

The positive control matters as much: the same test asserts that an ordinary sequential edit_plan still succeeds and still advances the version. Without it a fence that refuses everything passes the falsifier.

Landed 2026-09-18 (commit 36330a4). The write path now holds a per-file lock across the version check and the replacement, and a comment append whose base revision moved under it is merged by section and id rather than refused, so both writers survive the meeting; a write that disagrees about anything other than the comments is still a real conflict and still raises. The falsifier does fail at the base revision, and in the shape this plan measured rather than in a near one: two writers rendezvoused at the render step both passed their version check, the landing writer's own replace call moved the other writer's rendered file into place (AssertionError: a comment was discarded on the meeting: ['c-edit'] at version 1; outcomes {'edit': FileNotFoundError(2, 'No such file or directory'), 'landing': 1}), so one comment was gone, the other writer's replace found no temporary file left, and the counter read 1 for two landed writes. The same test carries the positive control: a sequential append after the meeting still lands and still advances the version, so a sequential edit is not caught by the fence. Measure: the focused cohort covering the plan-write path ran 1 failed / 181 passed at the base revision and 1 failed / 183 passed at the change, the single failure pre-existing at the base and unrelated (tests/test_north_star_write.py::test_north_star_is_the_only_plan_set_field_added), so the delta is zero added and two passing. Full record: §5 landed.

§ Decisions

When a plan edit and a promotion's landing write meet, who is inconvenienced? Fencing the landing write refuses a promotion at the moment a worker's result is recorded; serializing is a rule with no check and cannot help two workers; a commutative append removes the conflict but not the race that produced a silent loss with no conflict at all.

The failure that cost data was a lost update whose version counter advanced, so nothing raised a conflict and nothing could be noticed. Only the commutative append removes that case outright. It does not remove the race, and the plan is right to say so, but it changes the residue from a lost update into an append ordering question, which is benign for comments and severe for nothing. Fencing the landing write converts the silent loss into a refusal at the most expensive moment there is, as a worker's result is being recorded — and that shape was measured on 2026-09-17, when a promotion that refused after writing the plan left its run unpromotable and dirtied the plan so the next dispatch refused on the dirt while naming a section that was fine. Serializing cannot help writers who cannot see each other, which is the actual topology: five coordinator sessions ran concurrently on this workstation that evening in separate processes with no shared lock, so the check that would enforce it is a distributed lock under a simpler name. The accepted costs are that this is the largest of the three changes and that the meaning of the version counter has to be revisited as part of it, since a counter that advances on a lost update is itself part of what went wrong.

§ Followups

Lock who-loses-a-race before any node is cut

This plan deliberately carries no implementable node yet. All three candidate repairs are defensible and they differ in who is inconvenienced when two writers meet — a promotion refused at the moment a worker's result is recorded, a rule with no check that cannot help two workers who cannot see each other, or a commutative append that removes the conflict while leaving the race that produced a silent loss with no conflict at all.

Dispatching before the choice is locked would build one of three and discover the objection afterwards. The evidence the decision needs is in §1 through §4: a measured lost update whose version counter advanced, the same boundary refusing correctly in the other direction half an hour later, and a second coordinator hitting it six times in 27 landings.

One thing that should not wait: the S13 coordinator's resolve_both.py is in use and works. It should stay available and should not be promoted to a convention, because a helper that reconciles both sides removes the conflict, and the conflict is currently the only place this defect announces itself.
