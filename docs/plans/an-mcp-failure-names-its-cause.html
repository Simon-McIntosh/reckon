§1 — Why: the servers every session leans on fail, and say the wrong thing when they do

Every coordinator and worker reaches reckon's plan and crew state through the reckon MCP server, and the IMAS projects reach their graph through imas-cx. When either fails, a session falls back to the CLI or stops. The lead reported both as recurrent on 2026-10-08, and asked for a way to find the cause of each failure, not only a fix for the current one.

Claude Code writes one log per server connection under ~/.cache/claude-cli-nodejs/<cwd>/mcp-logs-<server>/<timestamp>.jsonl. Reading every such log from the seven days to 2026-10-08 (3,815 reckon connections and 1,652 imas-cx connections, across main checkouts and worker worktrees) gives these failure signatures:

The reckon server's recurrent failure is not in those logs, because it is a tool result rather than a lost connection. Transcripts under ~/.claude/projects since 2026-10-01 hold 180 storage-slow results in 32 sessions: 84 from read_plan, 51 from roadmap, 42 from crew and 3 from edit_plan. The label claims the filesystem was slow. On 2026-10-08 a stat of the plan whose read_plan had just timed out took 3 ms, while reckon roadmap --project reckon from the CLI took 87 s wall and 44 s of CPU on a node with load average 31. _run_under_deadline in reckon/mcp.py runs each tool body on a worker thread under a 30 s read deadline and abandons it at the deadline. An abandoned body that is busy computing keeps its thread and its share of the interpreter, so the next call competes with it. A deadline that cannot tell computing from waiting reports both as storage. The shipped plan reckon-reads-answer-in-seconds brought warm reads to seconds. Every session and every worker now starts its own server, so a read is warm only after that server has answered once.

The environment is not stale. reckon doctor on 2026-10-08 reported the reckon environment matching its lockfile and its editable install pointing at the main checkout, so a resync would not have prevented any of these failures. The launches themselves are the problem: every one runs uv run, which syncs before it starts the server.

Each worker sandbox also starts its own servers. On 2026-10-08 the fleet node carried about twenty imas-codex serve processes of about 610 MB resident each, roughly 12 GB of a 120 GB allocation, most of them in workers that never called the graph.

§2 — reckon doctor names every MCP failure's cause

Deliverable. reckon doctor gains an MCP connections check that reads Claude Code's MCP connection logs and reports, per server, how many connections it saw and how many failed, grouped by cause. The census is a function in a new module reckon/mcp_census.py that takes an explicit window, a start and an end instant; the doctor block calls it for the seven days ending now. Each cause carries its count, newest occurrence, one example log path and the kind of working directory it failed in: main checkout, worker worktree or temporary directory. The causes are the signatures in §1's table, matched by a table of patterns in the same module. A failure no pattern matches is reported as unclassified with its first line rather than dropped, because the next unknown cause is the one this check exists to surface. It also counts storage-slow tool results per tool over the same window: it enumerates transcript files through transcript_index in reckon/velocity.py, the owner of locating Claude Code transcripts, and reads their tool-result blocks itself, because no existing reader parses tool results. The check adds no command and no option: it is one more block in reckon doctor's existing report, and an agent that wants the figures for another window calls the census function. It reads and never writes, and its runtime is bounded by naming the log directories it walks.

Done when tests/test_mcp_census.py builds a fixture log tree holding one connection per signature in §1 plus one clean connection and one unmatched failure. It asserts that every signature lands in its cause with the right count, the unmatched failure is reported as unclassified, the clean connection counts as a success, and the doctor block prints the census function's figures. A negative control is executed and logged: with the pattern table emptied, every failure reports as unclassified and the test fails. Run against the real log tree on the fleet node for the window 2026-10-01T01:00:00Z to 2026-10-08T01:00:00Z, the census function reproduces §1's imas-cx CONNECTION_CLOSED count within 5%. The write paths are reckon/mcp_census.py, reckon/cli.py and tests/test_mcp_census.py; the transcript count calls reckon/velocity.py and changes nothing in it.

§3 — A reckon MCP timeout says whether it was computing or waiting

Deliverable. _run_under_deadline in reckon/mcp.py measures the thread CPU time its body has spent at the moment the deadline expires, beside the wall time, and the timeout result carries both with a cause of computing or waiting. The message and hint name that cause. For computing, they say the call was abandoned while it was still working, and give the CLI command that answers without a deadline. The error value stays storage-slow so no existing caller's branch changes.

Done when a test in tests/test_mcp_deadline_names_its_cause.py runs one body that spins the CPU past a short deadline and one that sleeps past it. The first reports computing and the second waiting, each with wall and CPU seconds. A negative control is executed and logged: with the CPU measurement removed, the first case reports waiting and the test fails. The write paths are reckon/mcp.py, reckon/_mcp_tools.py and tests/test_mcp_deadline_names_its_cause.py.

§4 — Measure where a reckon read spends its time

Deliverable. A measurement of read_plan (summary view of one plan), roadmap (summary view of the reckon project) and crew (live view) as an MCP server answers them: cold, the first call of a fresh server, and warm, the third call. Each is reported with wall time, process CPU time and the top functions by cumulative time from a profile. It runs on the fleet node under its ordinary load, records that load, and compares the warm figures with the claim reckon-reads-answer-in-seconds shipped. The report is written to the run directory and ends with the change it recommends, which becomes a new section of this plan if it is reckon's to make.

Done when the report gives cold and warm wall and CPU seconds for all three reads, names the functions that dominate the slowest one, and says whether the warm path still answers within the deadline. A positive control is part of the measurement: a call against a fixture project of three plans answers in under a second on the same node.

§5 — reckon doctor flags any MCP launch that would sync or resolve from its working directory

Deliverable. reckon doctor reads every stdio MCP server registered for Claude Code: the user-scope entries in ~/.claude.json and the .mcp.json of each mounted project. It flags a launch that runs uv run without --no-sync, or that names no absolute --project and so resolves its project from whatever directory the session started in. A worker's worktree is the case that fails. For each flagged launch it prints the corrected command, uv run --no-sync --project <checkout> …. The checkout is written so it names no single user's home: through a variable Claude Code expands in MCP configuration, such as ${HOME} or a project-specific variable with a default. A launch whose arguments carry a literal /home/<user> path is flagged too. Doctor exits non-zero when any launch is flagged. The existing environment-drift check stays beside it, because a launch that no longer syncs depends on the shared environment being kept current, which is already every agent's job. reckon edits no other project's .mcp.json. Those edits belong to their repositories and are recorded as followups naming each one.

Done when tests/test_doctor_mcp_launch.py gives doctor a fixture user config and two fixture projects. One project launches with uv run imas-codex serve, one with uv run --no-sync --project ${HOME}/Code/imas-codex imas-codex serve, and the user-scope reckon entry launches with uv run --project /home/someone/Code/reckon reckon mcp. Doctor flags the first project, and flags the user-scope entry twice (it syncs, and it names one user's home). It prints a corrected command for each, passes the second project, and exits non-zero. A negative control is executed and logged: with the --no-sync check removed, the user-scope entry is flagged only for its path and the test fails. Every reckon sync and reckon doctor test that reads a config resolves it under a temporary home, and the test asserts the real ~/.claude.json is untouched. The write paths are reckon/cli.py and tests/test_doctor_mcp_launch.py.

§7 — A worker starts only the MCP servers its work uses

Deliverable. A dispatched worker's harness starts the reckon server and no project MCP server unless the project asks for one. The run's harness home is seeded by _seed_harness_entry in reckon/_backends.py, the one writer of that home, so the seeded settings.json carries the setting that disables the project's .mcp.json servers. A project whose workers query a server names it under a worker_mcp_servers list in its flight configuration, which the seeding reads, and the seeded settings file in the run's harness home is the record of the servers it enabled. No dispatch option is added. The surface this retires is the implicit default under which every worker inherits every project server, the default that started about twenty imas-codex servers on 2026-10-08. A worker that needs the graph is no worse off. One that does not stops paying about 610 MB of memory and a launch that fails in a third of worktrees.

Done when tests/test_worker_mcp_servers.py seeds a fixture run's harness home for a project with no worker_mcp_servers and finds the project's servers disabled and reckon enabled. For a project listing imas-cx it finds imas-cx enabled in the seeded settings file, which is the record of the servers the run enabled. A negative control is executed and logged: with the settings write removed, the project server reads enabled and the test fails. The write paths are reckon/_backends.py and tests/test_worker_mcp_servers.py.

§8 — A retried reckon read waits for the copy already running

Deliverable. A call to the reckon MCP server with the same tool and arguments as a body _run_under_deadline has abandoned but which is still running waits on that body rather than starting a second one. A coordinator that retries a roadmap after a timeout then gets the first body's answer when it finishes, instead of two copies competing for the interpreter. A call with different arguments is not affected. A write is never joined: it always runs its own body under its own deadline.

Done when a test in tests/test_mcp_retry_joins_running_read.py issues a spinning read twice, the second after the first's deadline expired, and observes one body execution and both calls answered from it. A read with different arguments starts its own body, and a write is never joined. A negative control is executed and logged: with the join removed, two body executions are observed and the test fails. The write paths are reckon/mcp.py and tests/test_mcp_retry_joins_running_read.py, and this section runs after §3, which edits the same file.

§9 — A one-plan read stops walking the corpus

Deliverable. §4's profile found a read_plan summary of one 13 kB plan still running at 180 s, on 2026-10-08 on the fleet node at load 31 to 59. Its 90 s profile shows 26,858 posix.scandir calls (32.8 s of self time) driven by recursive globs. These come from resources._scan_resources and iter_resources (seven scans of 7.5 s each), from _store._resolve_html_file through resources.resolve_resource (41.7 s), and from _store._add_north_star_diagnostic through project_state.compose_project_state (34.4 s, run twice). A read about one named plan resolves that plan's path without a corpus scan. Whatever it needs from the rest of the corpus, such as the north-star diagnostic, it takes from a result memoised on the scanned directories' own stat identity, which reckon/file_memo.py already provides for file reads, rather than from a fresh recursive glob per call. Every read that changes keeps the answer it gives today.

Done when tests/test_one_plan_read_is_not_a_corpus_scan.py counts os.scandir calls during a read_plan summary of one plan in fixture projects of 5 and of 60 plans. The count is the same for both sizes, and the summary payload equals the one today's code returns for the same fixture. A negative control is executed and logged: with the direct path resolution reverted, the 60-plan count exceeds the 5-plan count and the test fails. A logged warm call on the fleet node answers the summary of this plan within the 30 s read deadline. The write paths are reckon/resources.py, reckon/_store.py and tests/test_one_plan_read_is_not_a_corpus_scan.py; a change needed in reckon/project_state.py is named in the manifest before it is made.

§10 — A fenced worker can read the crew live view

Deliverable. §4 found that crew(view="live") fails inside a worker's fence after about 20 s with [Errno 30] Read-only file system on ~/.config/reckon/crew/watch/<project>-<hash>.lock. The live view takes an advisory lock under crew/watch before reading, and the fence mounts the config home read-only. A read of the live view takes no lock it would need to create or write. Where it must order itself against a writer, it opens the lock read-only, or reads without it and reports the snapshot's age. The read-only fence is unchanged.

Done when a test in tests/test_live_view_reads_under_a_read_only_home.py builds a fixture crew home, makes its watch directory read-only, and calls the live view, which returns the fixture's runs with no error. A negative control is executed and logged: with the read path's lock acquisition restored to its current form, the call raises the read-only error and the test fails. The write paths are the module that takes the lock for the live read, which the node names in its manifest before editing, and tests/test_live_view_reads_under_a_read_only_home.py.

§ Decisions

What form should every MCP launch take?

Keep uv in the launch, but with --no-sync and an explicit --project, so no launch writes the shared environment or resolves its project from the session's working directory. The path must not name one user's home: the launch lines are shared with other users, so they are written through variables Claude Code expands rather than a literal /home/<user> path.
