§1 — Why: the servers every session leans on fail, and say the wrong thing when they do

Every coordinator and worker reaches reckon's plan and crew state through the reckon MCP server, and the IMAS projects reach their graph through imas-cx. When either fails, a session falls back to the CLI or stops. The lead reported both as recurrent on 2026-10-08, and asked for a way to find the cause of each failure, not only a fix for the current one.

Claude Code writes one log per server connection under ~/.cache/claude-cli-nodejs/<cwd>/mcp-logs-<server>/<timestamp>.jsonl. Reading every such log from the seven days to 2026-10-08 (3,815 reckon connections and 1,652 imas-cx connections, across main checkouts and worker worktrees) gives these failure signatures:

The reckon server's recurrent failure is not in those logs, because it is a tool result rather than a lost connection. Transcripts under ~/.claude/projects since 2026-10-01 hold 180 storage-slow results in 32 sessions: 84 from read_plan, 51 from roadmap, 42 from crew and 3 from edit_plan. The label claims the filesystem was slow. On 2026-10-08 a stat of the plan whose read_plan had just timed out took 3 ms, while reckon roadmap --project reckon from the CLI took 87 s wall and 44 s of CPU on a node with load average 31. _run_under_deadline in reckon/mcp.py runs each tool body on a worker thread under a 30 s read deadline and abandons it at the deadline. An abandoned body that is busy computing keeps its thread and its share of the interpreter, so the next call competes with it. A deadline that cannot tell computing from waiting reports both as storage. The shipped plan reckon-reads-answer-in-seconds brought warm reads to seconds. Every session and every worker now starts its own server, so a read is warm only after that server has answered once.

The environment is not stale. reckon doctor on 2026-10-08 reported the reckon environment matching its lockfile and its editable install pointing at the main checkout, so a resync would not have prevented any of these failures. The launches themselves are the problem: every one runs uv run, which syncs before it starts the server.

Each worker sandbox also starts its own servers. On 2026-10-08 the fleet node carried about twenty imas-codex serve processes of about 610 MB resident each, roughly 12 GB of a 120 GB allocation, most of them in workers that never called the graph.

§2 — reckon doctor names every MCP failure's cause

Deliverable. reckon doctor mcp reads Claude Code's MCP connection logs for a window (default seven days, --since to change it) and reports, per server, how many connections it saw and how many failed, grouped by cause. Each cause carries its count, newest occurrence, one example log path and the kind of working directory it failed in: main checkout, worker worktree or temporary directory. The causes are the signatures in §1's table, matched by a table of patterns in a new module reckon/mcp_census.py. A failure no pattern matches is reported as unclassified with its first line rather than dropped, because the next unknown cause is the one this command exists to surface. It also counts storage-slow tool results per tool from the transcripts for the same window. --json emits the same report for an agent. The command reads and never writes, and its runtime is bounded by naming the log directories it walks.

Done when tests/test_mcp_census.py builds a fixture log tree holding one connection per signature in §1 plus one clean connection and one unmatched failure. It asserts that every signature lands in its cause with the right count, the unmatched failure is reported as unclassified, the clean connection counts as a success, and the JSON and text outputs agree. A negative control is executed and logged: with the pattern table emptied, every failure reports as unclassified and the test fails. Run against the real log tree on the fleet node, the census reproduces §1's imas-cx CONNECTION_CLOSED count within 5% for the same window. The write paths are reckon/mcp_census.py, reckon/cli.py and tests/test_mcp_census.py.

§3 — A reckon MCP timeout says whether it was computing or waiting

Deliverable. _run_under_deadline in reckon/mcp.py measures the thread CPU time its body has spent at the moment the deadline expires, beside the wall time, and the timeout result carries both with a cause of computing or waiting. The message and hint name that cause. For computing, they say the call was abandoned while it was still working, and give the CLI command that answers without a deadline. The error value stays storage-slow so no existing caller's branch changes. A second call with the same tool and arguments, made while an abandoned body for it is still running, waits on that body rather than starting another, so repeated retries cannot stack copies of one expensive read.

Done when a test in tests/test_mcp_deadline_names_its_cause.py runs one body that spins the CPU past a short deadline and one that sleeps past it. The first reports computing and the second waiting, each with wall and CPU seconds. A third case issues the spinning call twice inside the deadline window and observes one body execution, not two. A negative control is executed and logged: with the CPU measurement removed, the first case reports waiting and the test fails. The write paths are reckon/mcp.py, reckon/_mcp_tools.py and tests/test_mcp_deadline_names_its_cause.py.

§4 — Measure where a reckon read spends its time

Deliverable. A measurement of read_plan (summary view of one plan), roadmap (summary view of the reckon project) and crew (live view) as an MCP server answers them: cold, the first call of a fresh server, and warm, the third call. Each is reported with wall time, process CPU time and the top functions by cumulative time from a profile. It runs on the fleet node under its ordinary load, records that load, and compares the warm figures with the claim reckon-reads-answer-in-seconds shipped. The report is written to the run directory and ends with the change it recommends, which becomes a new section of this plan if it is reckon's to make.

Done when the report gives cold and warm wall and CPU seconds for all three reads, names the functions that dominate the slowest one, and says whether the warm path still answers within the deadline. A positive control is part of the measurement: a call against a fixture project of three plans answers in under a second on the same node.

§5 — reckon doctor flags any MCP launch that would sync or resolve from its working directory

Deliverable. reckon doctor reads every stdio MCP server registered for Claude Code: the user-scope entries in ~/.claude.json and the .mcp.json of each mounted project. It flags a launch that runs uv run without --no-sync, or that names no absolute --project and so resolves its project from whatever directory the session started in. A worker's worktree is the case that fails. For each flagged launch it prints the corrected command, uv run --no-sync --project <absolute checkout> …, and exits non-zero. The existing environment-drift check stays beside it, because a launch that no longer syncs depends on the shared environment being kept current, which is already every agent's job. reckon edits no other project's .mcp.json. Those edits belong to their repositories and are recorded as followups naming each one.

Done when tests/test_doctor_mcp_launch.py gives doctor a fixture user config and two fixture projects. One project launches with uv run imas-codex serve, one with uv run --no-sync --project /abs/path imas-codex serve, and the user-scope reckon entry launches with uv run --project /abs/path reckon mcp. Doctor flags the first project and the user-scope entry, prints a corrected command for each, passes the second project, and exits non-zero. A negative control is executed and logged: with the --no-sync check removed, the user-scope entry passes and the test fails. Every reckon sync and reckon doctor test that reads a config resolves it under a temporary home, and the test asserts the real ~/.claude.json is untouched. The write paths are reckon/cli.py and tests/test_doctor_mcp_launch.py.

§6 — Find why imas-cx exits with os error 2 in imas-ambix worktrees

Deliverable. An investigation of the 576 imas-cx launches that died 40 ms after start with error: No such file or directory (os error 2), all in imas-ambix worktrees, where imas-ambix's .mcp.json runs uv run --project /home/ITER/mcintos/Code/imas-codex imas-codex serve --no-embed. Two hypotheses were tested on 2026-10-08 and do not reproduce: a working directory deleted before launch, and a missing TMPDIR. Both ran cleanly. The investigation reproduces the failure inside a worker's fence (the bind mounts, CLAUDE_CONFIG_DIR, TMPDIR and UV_OFFLINE=1 a dispatched worker carries), or finds the path uv could not open from strace or uv's verbose output. It names the cause and the owning repository of the fix.

Done when the report names the file uv failed to open, shows the failure reproduced on demand and absent under a changed condition that differs in one variable, and names the repository and file whose change removes it. Census figures in the report come from §2's command where it has landed, or from a recorded count otherwise.

§7 — A worker starts only the MCP servers its work uses

Deliverable. A dispatched worker's harness starts the reckon server and no project MCP server unless the node asks for one. Dispatch already writes each run's own harness home under CLAUDE_CONFIG_DIR, so the worker's settings there disable the project's .mcp.json servers by default. A --mcp <name> dispatch option enables a named one for a node whose work queries it, and the run record carries the servers it enabled. A worker that needs the graph is no worse off. One that does not stops paying about 610 MB of memory and a launch that fails in a third of worktrees.

Done when a dispatch test reads the harness settings written for a fixture run with no --mcp option and finds the project's servers disabled and reckon enabled. With --mcp imas-cx it finds imas-cx enabled, and the run record names it. A negative control is executed and logged: with the settings write removed, the project server reads enabled and the test fails. The write paths are the dispatch module that writes the harness home, which the design review names, and a new test file.
