§1 — Why: the servers every session leans on fail, and say the wrong thing when they do

Every coordinator and worker reaches reckon's plan and crew state through the reckon MCP server, and the IMAS projects reach their graph through imas-cx. When either fails, a session falls back to the CLI or stops. The lead reported both as recurrent on 2026-10-08, and asked for a way to find the cause of each failure, not only a fix for the current one.

Claude Code writes one log per server connection under ~/.cache/claude-cli-nodejs/<cwd>/mcp-logs-<server>/<timestamp>.jsonl. On 2026-10-08 a stat of the plan whose read_plan had just timed out took 3 ms, while reckon roadmap --project reckon from the CLI took 87 s wall and 44 s of CPU on a node with load average 31. _run_under_deadline in reckon/mcp.py runs each tool body on a worker thread under a 30 s read deadline and abandons it at the deadline. An abandoned body that is busy computing keeps its thread and its share of the interpreter, so the next call competes with it. A deadline that cannot tell computing from waiting reports both as storage. The shipped plan reckon-reads-answer-in-seconds brought warm reads to seconds. Every session and every worker now starts its own server, so a read is warm only after that server has answered once.

The environment is not stale. reckon doctor on 2026-10-08 reported the reckon environment matching its lockfile and its editable install pointing at the main checkout, so a resync would not have prevented any of these failures. The launches themselves are the problem: every one runs uv run, which syncs before it starts the server.

Each worker sandbox also starts its own servers. On 2026-10-08 the fleet node carried about twenty imas-codex serve processes of about 610 MB resident each, roughly 12 GB of a 120 GB allocation, most of them in workers that never called the graph.

§16 — A timed-out write still in flight is not reported as not landed

Why. On 2026-10-15 two edit_plan state writes returned storage-slow with landed: false and the message "The write did not reach its file." One was on a-seat-held-elsewhere-is-not-restarted, plan version 25; the other on a-held-session-routes-to-a-serving-lane, version 13. Both had landed. Read back about 20 s later, each file carried the new section declaration, the closing comment and the evidence entry, and the plan version had advanced. The result's hint says to retry once storage recovers, so a caller following it would have written each landing twice. The cause is in reckon/mcp_deadlines.py. A body that outlives its deadline is abandoned, not cancelled, and keeps running on its thread. _landing_state polls the file only for _landing_grace_seconds() and answers False when the grace ends with the file unchanged, even though the body is still running and may yet write it. That answer passes through StorageSlowResult in reckon/_mcp_tools.py as "did not reach its file".

Deliverable. A write's landed is False only when its body has finished, by returning or raising, and the file is unchanged. When the grace ends with the file unchanged and the body still running, landed is None. The message then says the write is still in flight and may yet land. The result's hint, today the fixed _STORAGE_SLOW_HINT ("Retry once the storage recovers"), becomes an instruction to read the resource back and resubmit only what is missing. A write reporting landed: False keeps the retry hint. True keeps its meaning: the file changed within the grace. The landing check reads the abandoned body's future, which _InflightBody already holds, rather than a second record of whether the body ended.

Done when a test drives the write deadline with three bodies. One writes its file after the landing grace and while the result is composed: it reports landed: None with the in-flight wording and a hint that says to read the resource back, not to retry. One finishes without writing: it reports landed: False. One writes within the grace: it reports landed: True. No real plan or crew home is written. The test files that import reckon/mcp_deadlines.py or reckon/_mcp_tools.py show no added failure against base. For the negative control, answer False whenever the grace ends with the file unchanged: the first body must then report landed: False. The control is logged under the run directory. Write paths: reckon/mcp_deadlines.py, reckon/_mcp_tools.py and tests/test_a_write_in_flight_is_not_reported_unlanded.py.

§ Decisions

What form should every MCP launch take?

Keep uv in the launch, but with --no-sync and an explicit --project, so no launch writes the shared environment or resolves its project from the session's working directory. The path must not name one user's home: the launch lines are shared with other users, so they are written through variables Claude Code expands rather than a literal /home/<user> path.
