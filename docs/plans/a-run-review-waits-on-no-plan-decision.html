§1 — Why: two run reviews held five hours on design decisions

On 6 November two queued reviews of delivered runs, r-20261106T161252641125 (review of r-20261103T080731600837, section a-dry-run-must-resolve-what-the-real-call-resolves §4) and r-20261106T162114428730 (review of r-20261103T082706369314, section an-orchestrator-can-discharge-a-refusal §10), sat at queue positions 1 and 2 for about five hours while the local lane ran two workers against a published allowance of 43. Every admit pass recorded the same verdict for both: held-by-gate, “waiting on readiness:reckon:<plan>#<section>”. Neither plan's section had changed; each plan carries open decisions with no choice (member-repository-requirement on the first, discharge-surface-shape and undischargeable-row-disposition on the second), which only the lead locks.

The wait comes from _validated_batch_waits in reckon/crew/queue_admission.py (near lines 2322–2358, added in b34d800ad7). For every queued request it reads its own section's verdict, and when the section is held by a gate or decision blocker it appends readiness:<section key>. It does this for every role. A gate or open decision says new work on the section must not start; a review reads code that a run has already written and judges it, and nothing it does depends on how the decision is settled. Holding it parks a finished run's landing behind a design question for as long as that question stays open. The obligation rows for both requests also read “waiting for a lane slot” while the pass said held-by-gate; that mismatch is work-is-never-stuck-behind-the-admission-loop §29's, and this plan does not touch it.

§2 — A queued review is not held on its section's gates or decisions

Deliverable. In _validated_batch_waits (reckon/crew/queue_admission.py), the own-section readiness wait is appended only for a request whose TaskNode.role is not review. A review request keeps every other wait it has: its explicit --after runs, its section's authored waits from section_wait_refs, and its plan's depends_on. Implementation, investigation and every other role keep the readiness wait exactly as now. No new helper and no new parameter: the condition sits on the existing if read_own_verdict and node.plan and node.section branch.

Done when a new tests/test_a_run_review_waits_on_no_plan_decision.py shows two things with a synthesised temporary repository whose plan section carries an open decision, calling _validated_batch_waits directly: a request node with role="review" on that section gets no readiness: ref; and a request node with role="implement" on the same section gets readiness:<project>:<plan>#<section>. Negative control: removing the role condition makes the review node receive the readiness ref.
