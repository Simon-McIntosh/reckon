The Boundary Check Reads Two Trees

Measured 2026-09-23. Every dispatch records a snapshot of every git worktree registered in the repository (dispatch.py _repository_tree_snapshot(repo_root)), and every promotion takes it again over the same roots (promotion.py). Each tree costs one git status --porcelain=v1 -z --untracked-files=all (routing._tree_state). The snapshot exists to refuse a promotion when a run changed a tree other than its own. The review run r-20260923T172710072463-third-read-back-of-the-ledger recorded 312 trees at dispatch. The same walk runs under crew follow and on dispatch's post-launch path. Two followers with a 29-minute lifetime ran for 3 h 36 m and 2 h 07 m, because the deadline is checked between polls and one poll sat inside a walk. That run's crew complete was still running after three hours, starting a new git status in a different retained worktree about every 30 seconds while peer commits were nearly idle. That 30 seconds per tree reflects a degraded shared filesystem. The same morning one tree cost about 3.3 seconds, which is still about 17 minutes per snapshot at 312 trees, paid once at dispatch and again at promotion. The cost grows with how many worktrees exist in every session, not with anything the run did. Per-run ledger files do not remove it.

The design. A fenced worker cannot write outside its own worktree and run directory once the fence also protects the other runs' worktrees. For such a run, a boundary check over the other 310 trees looks for a write the operating system already refused. So the check for a fenced run reads two trees: the run's own worktree and the main checkout. The main checkout is kept as a second line behind the fence, because a write there goes live for every session. An unfenced run, launched with --no-fence, keeps the full registry scan, because nothing stopped it from writing elsewhere. Reducing how many worktrees are registered helps too, but it is cleanup rather than a fix, and each session does it for its own promoted runs.

Order. §1 waits on two changes to other plans, recorded as gates. a-dispatch-returns-without-its-worker §3 moves the dispatch snapshot into the per-run supervisor, writes it to <run_dir>/tree-snapshot.json, and makes promotion read its baseline from there. a-worker-cannot-write-your-home §3 adds the worktree root to the fence's protected set, keeping the run's own worktree writable. §1 then lands on top of both, in dispatch.py, promotion.py and routing.py, which the S20 session owns until its §3 has merged.

§1 — A fenced run's boundary check reads its own worktree and the main checkout

Measure. When a run's launch plan composed the fence, every path that reaches routing._repository_tree_snapshot or routing._tree_state records and compares exactly two trees for it: the run's own worktree and the repository's main checkout. That includes the supervisor's snapshot, promotion's re-snapshot, dispatch's post-launch path, and whatever crew follow reaches through its sweeps. This section starts by listing every caller of those two functions and the entry point that reaches it, with the list recorded in the manifest. The run record carries whether the fence was composed, and the promotion reads that record, not the current default. A run launched with --no-fence, or recorded before this change, keeps the full scan of every registered worktree. The refusal a promotion gives when the main checkout changed unexpectedly is unchanged.

Falsifier. In a temporary repository with 50 registered worktrees, driven through the crew complete entry point with a git shim on PATH that counts status calls: a fenced run's snapshot holds 2 trees and its promotion makes 2 status calls, while an unfenced run's snapshot holds 51 trees and its promotion makes 51. With the same shim, one dispatch of a fenced run and one poll of crew follow over it each make at most 2 status calls for that run. The per-tree cost no longer depends on how many worktrees are registered, so a follower's lifetime deadline is not held for hours inside a single poll. A fenced run whose worker wrote into the main checkout is still refused at promotion, naming the tree. The negative control sends the fenced branch through the full scan, and the fenced run's count must then read 51.

§2 — The saving is measured on real runs

Measure. For fenced runs promoted at the merged head, the evidence record gives the registered tree count, the number of trees each snapshot read, and wall time from dispatch to worker start and from crew complete start to its commit. These are compared with the same figures for runs promoted before the change. Tree count is the primary figure, since per-tree cost depends on filesystem load on the day.

Falsifier. At least three fenced runs at the merged head each record 2 trees read, against a registered count above 100. An unfenced run in the same window records the full count. A run whose record reads 2 trees while its launch plan composed no fence is a defect in §1, and the evidence names it.

Its base is the later of those two merges, and the S20 session is told before it dispatches, because it writes dispatch.py and promotion.py. §2 is recorded from the first fenced promotions at the merged head.
