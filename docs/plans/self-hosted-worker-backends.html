§1 — The gap, measured

Reckon can route a node to any backend whose command it knows how to translate, and it knows two: codex and claude. What it cannot do is tell that command where to send its requests. A backend declares ten keys — launch, command, model, effort, sandbox, session_reuse, time_budget, budget_check, auth_check, name — and none of them carries an endpoint, a base URL, or a credential. The launcher confirms it: the subprocess.Popen call in reckon/crew/dispatch.py passes no env=, so every worker inherits whatever environment the dispatching process happened to hold.

That is the whole obstacle. It is not a model problem and not a protocol problem — both were measured and both are fine. The consequence is that a self-hosted endpoint can only be reached by mutating the orchestrator's own environment, which is global, invisible in the run record, and impossible to vary per node. A wrapper script does not rescue it either: dialect selection matches on the command's basename, so a backend declaring command: clive is refused with no launch translation for command 'clive' before anything launches.

§1.1 — What the local endpoint actually does

The GPU job serving the candidate has been running for over five days on the reserved H200 node against an unlimited partition. Probed directly, it publishes one model at a 524,288-token context and answers on both protocol dialects Reckon knows how to drive. The decisive capability is tool use: given an Anthropic-shaped tool schema it returns a well-formed tool_use block with stop_reason: tool_use and correctly extracted arguments, which is the minimum an agent loop requires and the thing that cannot be assumed of a self-hosted model.

Those last two rows have to be read together, and the order they were measured in matters. The bare “Say PONG” probe carried no tools and no system prompt, and its essay looked like a model that would not respect a fence — which would be disqualifying, because fences are how Reckon keeps a worker safe: exclusive write scope, a manifest at a named path, a time budget. Adding a tool schema and a concrete task reversed it. Given a job, the model emitted a well-formed call, consumed the result, and answered with the single number asked for and nothing else.

So the honest reading is that a bare-prompt probe measures the wrong thing for this purpose, and the loop test measures closer to the right one. Neither settles the question that actually decides adoption, which is whether fence adherence holds over a twenty-minute autonomous node rather than one turn. Nothing short of a real dispatch tests that, which is what §3's end-to-end measure and the §4 pairs exist to do.

§2 — A backend may name its environment

Add one optional key to the backend schema: a map of environment variable names to string values, merged over the dispatching process's environment when the worker is spawned. It is user data in exactly the sense command and model already are — the schema fixes no variable names, encodes no provider vocabulary, and ships no defaults. That is what keeps the shipped layer provider-neutral while letting a host layer name a machine on its own network.

The authored shape is a plain mapping of name to value — environment: {VARIABLE: value} under a backend entry, one nesting level, not a list of name/value pairs. That is pinned here rather than left to the implementation because §3 writes this YAML by hand and every later host and project layer inherits the spelling.

Expansion happens where the backend is selected, not when the config is read — and the first implementation got this wrong in a way worth recording, because the specification asked for it. The done-when below requires an unset reference to raise a typed error naming the variable, which is right for a backend a call actually routes to and wrong for every other caller: expanding eagerly at whole-config resolution made one unresolved reference in one defined-not-defaulted backend a hard failure for every dispatch in the project, including dispatches routing to an entirely different backend. A concurrent session's work stopped on it within a minute of the config landing.

The precedent to follow was already there: a backend whose command is absent reports command_found: false as an availability finding and breaks nothing. An unresolvable environment reference belongs in that same shape. The check itself was not wrong — it fired correctly, on callers who had nothing to do with what it was checking. A fence with the wrong blast radius is invisible in a single-session test, which is exactly how it passed: it was validated from a shell that happened to have the variable exported.

Values expand ${VAR} against the dispatcher's environment, so a credential can be referenced rather than written down. That is not a nicety here: the host flight layer is mode 0644 while the credential this plan needs lives in a 0640 group-restricted file, so writing the literal would widen who can read a secret. The expansion form keeps it out of the file entirely. A literal value is still permitted: the host flight layer is uncommitted user data by construction, so a literal there is no more exposed than the file the credential already lives in. The expansion exists so that the choice is available, not to forbid the simpler form.

The change touches the schema definition, the layered resolution that merges backend entries, the LaunchPlan that carries an invocation, and the one Popen call site. Merging over the inherited environment rather than replacing it matters: a worker still needs PATH, HOME and the harness variables its CLI reads.

Done-when: a backend declaring an environment map resolves through reckon flight with its values shown and the layer that supplied them; a dispatched worker's process environment contains those values merged over the inherited environment; ${VAR} expands from the dispatcher's environment and an unset variable is a stated configuration error rather than an empty string; the schema regenerates byte-identically from its source; and the existing suite passes with no new failures against the base revision.

§2.1 — No provider key is not the same as no secret

The governing constraint on this work is that it must run without API keys: the two agent CLIs authenticate through their own logins, and a local endpoint needs no account, no per-token billing, no quota and no rate meter. That is the property worth protecting and it holds completely — it is most of the adoption case in §5.

It does not follow that the endpoint takes no credential, and measurement says it does. The server was started with an API key, so a request with no header, an empty bearer, or a bearer of no-auth or anything is refused with 401. The local wrapper's no-auth fallback exists for a keyless server and this is not one. Removing the requirement means restarting a job that has been serving for days and leaving a cluster-reachable port open, which is a decision about a shared host rather than a configuration detail.

So the right distinction is between a provider credential — costed, metered, per-account, and genuinely absent here — and a host-local access token, which is present and is only an access control. The consequence for this section is ergonomic rather than architectural, and it is why the credential decision was re-locked: requiring an exported variable would make every fresh session, cron context and service unit configure a secret before the backend works, which reintroduces exactly the key-management burden the no-key principle exists to avoid. A reference to a file whose own permissions guard the token removes that step, and removes the secret from configuration at the same time.

§3 — Wire the local endpoint, defined and not defaulted

With §2 landed, the candidate enters the host flight layer as a backend with a pinned model, a pinned effort, and its environment naming the endpoint. It is defined and nothing routes to it: no role selects it, no by_spec_level mapping resolves to it, and only an explicit override or a shadow run reaches it. This is rung two of the qualification ladder that crew-effort-routing established, and it is the rung the lead asked to have in place immediately — the option exists in configuration from this point, while live routing stays shut until §4 produces evidence.

Effort must be pinned even though the local server has no reasoning-effort vocabulary of its own, because an unpinned backend inherits the user's interactive CLI preference and the ledger then cannot see what actually ran. The endpoint publishes no account-limit surface, so budget_check stays off and its headroom reads unknown; under the locked posture, unknown never holds a wave. That is correct here for a stronger reason than usual — a reserved GPU node has no quota to exhaust.

Done-when: reckon flight resolves the backend with its endpoint and pinned effort attributed to the host layer; no role and no specification-level mapping resolves to it, demonstrated by a dry-run dispatch that selects the incumbent; and one node dispatched explicitly to it completes end-to-end through the crew path — worktree created, prompt delivered, manifest written at its named path, run observable and promotable.

§4 — Shadow qualification against the incumbent

A shadow re-runs a committed node at its recorded base revision, inheriting the primary's effort, sandbox and time budget and substituting only the backend, model and launch. It is never merged. That control is what makes the comparison mean something, and it was hardened deliberately: the one Luna pair that had to be discarded was discarded because its budget and effort had drifted from its primary's, not because the model failed.

The evidence floor is ten usable pairs. The candidate starts at zero, as Terra still does. Node selection must span the mechanical work the lane would actually receive — nodes whose done-when is a runnable named check, not a prose measure — because a pass rate over hand-picked easy nodes measures the picking, not the model.

Ten pairs is a feasibility threshold and not an inferential one, and this section must not be read as though it were. The audit in §7 computed the powered depth: at the measured live base rate of 93.305%, detecting a ten-percentage-point difference at 80% power needs 161 pairs, so ten is 6.21% of it. What ten controlled pairs can establish is that a candidate is not catastrophically broken — that it holds fences, writes manifests, and passes checks at all. What they cannot establish is that it is as good as the incumbent. §5's recommendation is bounded by that and says so, rather than quoting a rate the sample cannot support.

Done-when: at least ten controlled shadow pairs are committed with lineage recording backend, launch and model as the only substituted dimensions; each pair reports its gate verdict against the primary's own named check, worker minutes, and tokens; the pass rate and median worker time are stated beside the incumbent's for the same nodes; and every infrastructure failure — a run dying with no diff and no manifest — is classified as such rather than counted against the model.

§5 — Verdict and adoption recommendation

The checkpoint renders a verdict including a negative one. Three outcomes are possible and all three are results: the candidate clears the success threshold over ten usable pairs and earns a gated pilot under the small-model lane's eligibility rules; it fails and the backend stays defined but unrouted, with the failure mode recorded so the question is not re-asked from scratch; or it cannot produce ten usable pairs, which is a statement about the harness rather than the model and names what blocked them.

The adoption case is worth stating plainly because it is large and it is what makes the qualification worth paying for. A reserved local node has no weekly meter, no rate limit, and no per-token cost. The incumbent's dedicated small-model lane was measured at roughly a dozen runs per week before its meter drained; a local endpoint has no such ceiling, so if the model can hold a fence, the constraint on fleet width stops being budget and becomes the roster. That is a different operating regime, not a cheaper version of the current one.

Done-when: a durable record states the pass rate over usable pairs against the incumbent's on the same nodes, median worker minutes for both, the classified infrastructure-failure count, and one of the three verdicts above with its reasoning; and every routing decision the read changes is locked on this plan.

§6 — The failure denominator is contaminated

Every verdict in §4 and §5 is a ratio, and the denominator is currently wrong. Across the three mounted ledgers, 1,281 usable records carry 1,192 passed and 89 failed — a 93.1% pass rate. Reading the 89 shows they are not one population. gate: failed is the only word available for at least six distinct outcomes, and only the first of them says anything about the worker:

What actually happenedObserved outcome textWhat it indicts
The named check ran against a delivered diff and failed “the change makes units_agree compare by pint dimensionality … wrong in general” The worker, or the specification
The worker refused correctly at a fence “refused correctly: 3 pre-existing untracked plots lie outside the migration roots” Nothing — this is the fence working
The node's own fences were malformed “blocked by a coordinator-side fence defect: the fenced receipt path lay outside the read-only sandbox roots” The coordinator that wrote the node
The run died producing nothing No diff and no manifest The transport
A check failed on a pre-existing condition “full suite on integrated 279b6f1: 1826 passed, 5 failed” The tree the worker was given
An experiment returned the negative result it was built to be able to return “GENERALIZATION NOT HELD … this is the phase working as intended” Nothing — it is a result

Twenty-three of the 89 carry no commit at all, and the sample above is drawn from them. One reads “nova MIGRATED and parity-verified … 225 compared / 225 matched / 0 mismatches” and is recorded as a failure. The doctrine already draws the most important line — a run that dies with no diff and no manifest is an infrastructure failure, redispatched without indicting the specification and excluded from the lane's circuit breaker — but nothing in the record stores which kind a failure was, so no reader and no reducer can apply it.

This belongs to this plan rather than to a followup because the candidate's verdict is computed from exactly this denominator. Two consequences are concrete. A candidate's measured pass rate is depressed by whatever share of its failures were refusals, malformed nodes or bad trees, and there is no reason to expect that share to be equal between a candidate and the incumbent it is compared against. And the small-model lane's circuit breaker closes a lane on two consecutive gate failures — which, on this vocabulary, two correct refusals would trip.

The fix is a classification stored beside the verdict, supplied when a run is promoted with a failing gate, and consumed by the ledger reducer so that pass rates are computed over the one class that measures the worker. The historical 89 are classifiable from their recorded outcome text, which is what makes the existing corpus usable rather than merely the runs from here on.

Done-when: promoting a run with a failing gate requires a classification from a closed set, refused with the set named when it is absent; the ledger reducer reports pass rate over the work-rejected class with the other classes counted separately, in the same shape as the existing measurement exclusions; all 89 historical failures across the three mounted ledgers are classified from their recorded outcome text, with the per-class counts stated and any record fitting no class reported by run id rather than forced into one; the recomputed pass rate is stated beside the pooled 93.1%; and the existing suite passes with no new failures against the base revision.

§7 — The gate is an assertion, not a measurement

§6 found the failure classes pooled into one word. The audit that produced §4's powered-depth figure found something upstream of that and worse: nothing in the record establishes that a gate verdict was ever measured. Tracing the promotion path, promotion::complete accepts the caller's gate string and passes it to ledger::build_record, which validates that it is one of three words and stores it. No manifest is read, no named check is re-run, no evidence is consulted. Across the whole corpus, 0 of 1,534 records carry a gate command, an exit code, a log path, or an evidence digest.

The consequence is precise, and it is not that coordinators are dishonest. It is that a verdict is unfalsifiable after the fact: a reader cannot tell an audited pass from a rubber-stamped one, and the two are worth different amounts. The audit ranked eleven weaknesses by direction of bias and nine of them inflate a candidate's apparent pass rate. That is the dangerous direction — the errors push toward adopting a model that has not earned it.

Three of the nine are structural rather than statistical, and they are what this section fixes. The named check is not identifiable, so nothing prevents a pair being scored on a different check from its primary's. Control is recorded but not enforced: capabilities::derive_capabilities branches on lineage.kind and never reads lineage.configuration, so the one confounded shadow in the corpus is pooled with the one controlled one. And node choice is discretionary — crew shadow accepts any eligible committed run id, with no sampling frame recorded, which is how both existing shadows came to target a single primary.

This is folded here rather than handed off because it is the same plan's own question. §5 cannot render a verdict on evidence whose provenance is absent, and the fold is converging rather than creeping: each layer's blocker has been narrower than its parent's and the write scope has stayed inside the ledger and promotion modules.

Done-when: a run promoted with a passing gate carries the check that produced it — command, exit status, and a log path or digest — with a passing verdict refused when they are absent, asserted by a test; a single accessor derives whether a shadow was controlled by comparing the recorded primary and shadow configurations, is the only place that predicate exists, and is consulted by both completion and capability derivation so a confounded row is never pooled with a controlled one, asserted by a test over the two existing shadow records; qualification depth counts distinct primary run ids rather than shadow rows; and the existing suite passes with no new failures against the base revision.

§ Decisions

Which protocol dialect drives the self-hosted endpoint?

The server answers on both. Reckon selects its launch translation from the command's basename, so the dialect choice is the choice of which CLI the backend names.

Tool use was verified end-to-end on the Anthropic surface, and that is also the surface the existing local-model wrapper drives, so it is the path with a demonstrated working hookup rather than an inferred one. The choice is cheap to revisit: because the dialect follows the command name and the endpoint follows the environment map, adding the other dialect later is a second backend entry in configuration and no code at all. One caution belongs in the record — the endpoint rejects the x-api-key header and accepts only bearer authorisation, so the credential variable must be the one the CLI sends as a bearer token.

How does a credential reach a worker's environment?

The host flight layer is user data and is not committed to any repository. The credential for this endpoint already sits in a file on a group-readable project path.

Re-locked in the same session on evidence that changed the question, and stated rather than done quietly. Two things were measured after the first lock. The endpoint is keyed: no header, an empty bearer, a bearer of 'no-auth' (the local wrapper's own fallback) and a bearer of 'anything' all return 401, so only the specific token the server was started with is accepted and a keyless path does not exist without restarting a five-day job and opening a cluster-reachable port. And the exposure asymmetry is real rather than theoretical: the host flight layer is mode 0644 while the credential lives in a 0640 group-restricted file, so the literal form this decision previously permitted would widen who can read a secret. That retires 'literal permitted' as the default. Expansion from the dispatcher's environment stays correct but carries an ergonomic cost that works against the project's own principle of needing no key management: every fresh session, cron context and service unit must export the variable first or the backend is unavailable. A third form answers both -- a reference to a file whose own permissions guard the secret, read at the point of selection. The token never enters configuration and never needs exporting. Literal and variable forms remain accepted; the file form is what this plan uses and what the documentation should show first.

If the candidate qualifies, does it enter the existing small-model lane gate or its own?

The small-model lane's eligibility rules were written around a metered backend: keep dispatches token-lean, never plan a wave that assumes the lane can absorb it. A local endpoint has no meter, so the budget half of those rules does not apply while the competence half still does. Deferred until §4 produces a verdict — there is nothing to route if it does not qualify.
