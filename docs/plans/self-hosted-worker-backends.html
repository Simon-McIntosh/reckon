§1 — The gap, measured

Reckon can route a node to any backend whose command it knows how to translate, and it knows two: codex and claude. What it cannot do is tell that command where to send its requests. A backend declares ten keys — launch, command, model, effort, sandbox, session_reuse, time_budget, budget_check, auth_check, name — and none of them carries an endpoint, a base URL, or a credential. The launcher confirms it: the subprocess.Popen call in reckon/crew/dispatch.py passes no env=, so every worker inherits whatever environment the dispatching process happened to hold.

That is the whole obstacle. It is not a model problem and not a protocol problem — both were measured and both are fine. The consequence is that a self-hosted endpoint can only be reached by mutating the orchestrator's own environment, which is global, invisible in the run record, and impossible to vary per node. A wrapper script does not rescue it either: dialect selection matches on the command's basename, so a backend declaring command: clive is refused with no launch translation for command 'clive' before anything launches.

§1.1 — What the local endpoint actually does

The GPU job serving the candidate has been running for over five days on the reserved H200 node against an unlimited partition. Probed directly, it publishes one model at a 524,288-token context and answers on both protocol dialects Reckon knows how to drive. The decisive capability is tool use: given an Anthropic-shaped tool schema it returns a well-formed tool_use block with stop_reason: tool_use and correctly extracted arguments, which is the minimum an agent loop requires and the thing that cannot be assumed of a self-hosted model.

That last row is not a joke at the model's expense; it is the reason this plan qualifies rather than adopts. A model that elaborates when asked to be terse is a model that may not respect a fence, and fences — exclusive write scope, a manifest at a named path, a time budget — are how Reckon keeps a worker safe. The shadow ladder in §4 is what converts that worry into a number.

§2 — A backend may name its environment

Add one optional key to the backend schema: a map of environment variable names to string values, merged over the dispatching process's environment when the worker is spawned. It is user data in exactly the sense command and model already are — the schema fixes no variable names, encodes no provider vocabulary, and ships no defaults. That is what keeps the shipped layer provider-neutral while letting a host layer name a machine on its own network.

Values expand ${VAR} against the dispatcher's environment, so a credential can be referenced rather than written down. A literal value is still permitted: the host flight layer is uncommitted user data by construction, so a literal there is no more exposed than the file the credential already lives in. The expansion exists so that the choice is available, not to forbid the simpler form.

The change touches the schema definition, the layered resolution that merges backend entries, the LaunchPlan that carries an invocation, and the one Popen call site. Merging over the inherited environment rather than replacing it matters: a worker still needs PATH, HOME and the harness variables its CLI reads.

Done-when: a backend declaring an environment map resolves through reckon flight with its values shown and the layer that supplied them; a dispatched worker's process environment contains those values merged over the inherited environment; ${VAR} expands from the dispatcher's environment and an unset variable is a stated configuration error rather than an empty string; the schema regenerates byte-identically from its source; and the existing suite passes with no new failures against the base revision.

§3 — Wire the local endpoint, defined and not defaulted

With §2 landed, the candidate enters the host flight layer as a backend with a pinned model, a pinned effort, and its environment naming the endpoint. It is defined and nothing routes to it: no role selects it, no by_spec_level mapping resolves to it, and only an explicit override or a shadow run reaches it. This is rung two of the qualification ladder that crew-effort-routing established, and it is the rung the lead asked to have in place immediately — the option exists in configuration from this point, while live routing stays shut until §4 produces evidence.

Effort must be pinned even though the local server has no reasoning-effort vocabulary of its own, because an unpinned backend inherits the user's interactive CLI preference and the ledger then cannot see what actually ran. The endpoint publishes no account-limit surface, so budget_check stays off and its headroom reads unknown; under the locked posture, unknown never holds a wave. That is correct here for a stronger reason than usual — a reserved GPU node has no quota to exhaust.

Done-when: reckon flight resolves the backend with its endpoint and pinned effort attributed to the host layer; no role and no specification-level mapping resolves to it, demonstrated by a dry-run dispatch that selects the incumbent; and one node dispatched explicitly to it completes end-to-end through the crew path — worktree created, prompt delivered, manifest written at its named path, run observable and promotable.

§4 — Shadow qualification against the incumbent

A shadow re-runs a committed node at its recorded base revision, inheriting the primary's effort, sandbox and time budget and substituting only the backend, model and launch. It is never merged. That control is what makes the comparison mean something, and it was hardened deliberately: the one Luna pair that had to be discarded was discarded because its budget and effort had drifted from its primary's, not because the model failed.

The evidence floor is ten usable pairs. The candidate starts at zero, as Terra still does. Node selection must span the mechanical work the lane would actually receive — nodes whose done-when is a runnable named check, not a prose measure — because a pass rate over hand-picked easy nodes measures the picking, not the model.

Done-when: at least ten controlled shadow pairs are committed with lineage recording backend, launch and model as the only substituted dimensions; each pair reports its gate verdict against the primary's own named check, worker minutes, and tokens; the pass rate and median worker time are stated beside the incumbent's for the same nodes; and every infrastructure failure — a run dying with no diff and no manifest — is classified as such rather than counted against the model.

§5 — Verdict and adoption recommendation

The checkpoint renders a verdict including a negative one. Three outcomes are possible and all three are results: the candidate clears the success threshold over ten usable pairs and earns a gated pilot under the small-model lane's eligibility rules; it fails and the backend stays defined but unrouted, with the failure mode recorded so the question is not re-asked from scratch; or it cannot produce ten usable pairs, which is a statement about the harness rather than the model and names what blocked them.

The adoption case is worth stating plainly because it is large and it is what makes the qualification worth paying for. A reserved local node has no weekly meter, no rate limit, and no per-token cost. The incumbent's dedicated small-model lane was measured at roughly a dozen runs per week before its meter drained; a local endpoint has no such ceiling, so if the model can hold a fence, the constraint on fleet width stops being budget and becomes the roster. That is a different operating regime, not a cheaper version of the current one.

Done-when: a durable record states the pass rate over usable pairs against the incumbent's on the same nodes, median worker minutes for both, the classified infrastructure-failure count, and one of the three verdicts above with its reasoning; and every routing decision the read changes is locked on this plan.

§ Decisions

Which protocol dialect drives the self-hosted endpoint?

The server answers on both. Reckon selects its launch translation from the command's basename, so the dialect choice is the choice of which CLI the backend names.

Tool use was verified end-to-end on the Anthropic surface, and that is also the surface the existing local-model wrapper drives, so it is the path with a demonstrated working hookup rather than an inferred one. The choice is cheap to revisit: because the dialect follows the command name and the endpoint follows the environment map, adding the other dialect later is a second backend entry in configuration and no code at all. One caution belongs in the record — the endpoint rejects the x-api-key header and accepts only bearer authorisation, so the credential variable must be the one the CLI sends as a bearer token.

How does a credential reach a worker's environment?

The host flight layer is user data and is not committed to any repository. The credential for this endpoint already sits in a file on a group-readable project path.

Refusing literals would buy no real secrecy while making the common case awkward: the flight layer is uncommitted by construction, so a literal there is no more exposed than the credential file it would be copied from. Expansion is what makes the safer form available for anyone who wants it, and it is the form this plan uses. The failure mode worth guarding is silent rather than loud — an unset variable expanding to an empty string would present as an authentication error from the server, so §2 requires it to be a stated configuration error instead.

If the candidate qualifies, does it enter the existing small-model lane gate or its own?

The small-model lane's eligibility rules were written around a metered backend: keep dispatches token-lean, never plan a wave that assumes the lane can absorb it. A local endpoint has no meter, so the budget half of those rules does not apply while the competence half still does. Deferred until §4 produces a verdict — there is nothing to route if it does not qualify.

§ Followups

Land the environment map, wire the endpoint, and run the shadow wave

§2 is the enabling change and everything else waits on it. §3 is configuration only once §2 lands, and the lead has asked for it to be in place immediately as a defined-not-defaulted option. §4 and §5 are the qualification the ladder requires before anything routes there.
