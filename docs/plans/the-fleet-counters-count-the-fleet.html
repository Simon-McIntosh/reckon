§4 — A re-arm continues the stream it left

The lead reported on 2026-09-25 that re-arming the follower every 30 minutes is fine, but every re-arm loses the history. A batch of rows arrives under one common timestamp, and the transitions that happened while no follower was attached never appear, which leaves a gap. The S23 coordinator's own follower reproduced it at 10:36:51–52 that day: after a re-arm it replayed twelve rows for runs already in flight, each stamped with the attach time.

Cause, at revision b453d763. The follower already has a resume path, but its checkpoint travels only through an environment variable handed across an in-place process reload (_take_follower_checkpoint, reckon/cli.py:1702). A re-arm is a new process with no checkpoint, so _follow_watch_lines (reckon/cli.py:2098–2112) takes the other branch, and two defects follow:

  • It emits watch_stream_cursor's baseline: one row per live run, stamped now. That is the common-timestamp batch.
  • It starts reading the producer's stream at the file's current end, so every line written between the old follower's exit and the new one's start is skipped. That is the gap.

After this section, a re-arm is a continuation.

  • The follower persists its checkpoint durably, per project and session, in the follower directory, and rewrites it atomically as it delivers. The checkpoint holds the stream path, enough of the stream's identity to tell a replaced or truncated file from the same one, the byte offset after the last line delivered, and the state last reported for each run.
  • A new follower for the same session reads that checkpoint. It seeks to the offset, delivers every line written since, each with the time the stream recorded, and then continues live. It emits no baseline. When nothing moved, the re-arm prints nothing.
  • When the checkpoint cannot be continued, because the stream was replaced or truncated, the follower falls back to state. It emits only runs whose state differs from the checkpoint's reported state, each stamped with the run's own recorded transition time, never the attach time.
  • A session's first arming has no checkpoint and emits the baseline, stamped per run. The baseline's state must match what the live stream would say. In the lead's capture, runs that had been working for over twenty minutes replayed as dispatched. A run whose stream has advanced past its start renders working.
  • Every row's age is computed from the run's recorded start.
  • The pane keeps its history across a re-arm. The lead reported on 2026-09-25, after the checkpoint landed, that each re-arm still opens an empty Monitor pane. The checkpoint stops the replayed baseline and fills the gap, but the rows the previous arming showed, and their times, are gone from view, and a coordinator cannot track its work without them. So the follower keeps a per-session log of the rows it rendered: each row's rendered text and original timestamp, beside the checkpoint, capped by default at the most recent 100 rows or 4 hours, whichever is smaller, both configurable in flight config. On a re-arm, before the gap lines, it re-emits that history as one burst of rows exactly as they were first rendered, with their original timestamps. Monitor batches lines written within 200 ms into one notification, so the history costs one notification per re-arm rather than one per row. The re-emitted rows are the log's rows, never a re-derived baseline, so no run is re-announced in a state it did not hold at that time. The burst is framed and marked as history, so a restored abandoned or process gone row is never taken for a new event or acted on:
    • It opens with one header line naming the span, for example ── history 12:31–14:00 · 37 rows ──.
    • Each history row is rendered dim, with its text and columns otherwise identical to its first rendering. A leading glyph was considered and rejected, because it would shift every column.
    • It closes with one separator line naming the re-arm time, for example ── re-armed 14:13 · live below ──. Every row after that line is news.
    S21's and S22's coordinators asked for the marking on 2026-09-25, because before this fix every re-arm replayed about twenty current-state rows that read as new transitions.

The work is folded in from a-follower-outlives-its-monitor §4, whose falsifier this section's done-when extends. The S22 coordinator agreed on 2026-09-25, and that plan's section declarations and evidence stay with S22.

§6 — The state cell carries the action; the reason is plain text

On 2026-09-25 the lead flagged that the reason clause repeats a label the state already implies, and that the label adds nothing. Rows read abandoned … recover: the process is gone …, stalled … investigate: stream quiet for 905s, blocked … ! resume: the worker process is gone …, unreadable … repair: the manifest at …. Worst is resume: ready to resume: …, where label and text say the same word twice. The text after the label is the useful part.

After this section:

  • The coordinator's action (resume, recover, investigate, repair, inspect, promote, review) moves into the state cell as <state> · <action>, for example blocked · resume. The ! urgency prefix becomes the state cell's colour and its word, not a glyph in the text.
  • The reason clause carries only the explanation. It never begins with a label and never repeats a word already in the state cell.

Done when:

Landed in 4cec02e2. §8 — A transition reads as an aligned arrow; the action has its own column

On 2026-09-25 the lead reviewed the row after §6 and §7 landed and found it still wrong. The state · action cell reads as a transition: a flicker renders dispatched · recover and then abandoned · recover, and a live run renders working · observe, so an action appears where no action is owed. Truncated node names still run into the next cell, for example hook-stop-mode-si…t-without-followerunpromoted · review, and a follower that reloads mid-stream leaves old-format rows above new ones. The lead's words: if the transition is worth showing, it takes a right arrow, every row centres on that arrow, there is room on both sides, text never runs into it, and entries are never ragged.

The transition is worth showing. dispatched → abandoned seconds after launch is exactly how a coordinator recognises the launch flicker, and working → blocked says more than blocked alone.

After this section:

  • Transition cell. The previous state is right-aligned in a fixed width, then → in one fixed column on every row, then the new state left-aligned in a fixed width. At least two spaces separate the cell from its neighbours. A row with no previous state (a first arming's inventory, or a history row that had none) leaves the left half and the arrow blank and keeps every column. Both widths come from the widest state word the classifier emits.
  • Transitions chain. The previous state printed on a row is the state the pane last showed for that run, never the producer's own from_state. So a run's rows always form a chain in which each row's left side is the previous row's right side: dispatched → abandoned, then abandoned → working. The lead flagged a pair rendered as dispatched → abandoned then dispatched → working. The second row's left side came from the producer, whose own record had skipped the abandoned state the pane had shown, so two separate transitions read as one contradictory story. The follower already keeps the last reported state for each run (reported), and the history log carries it across a re-arm, so the chain holds across re-arms as well.
  • No same-state rows. A row is printed only when the new state differs from the state the pane last showed for that run. The census found 293 same-state rows in one day: completed_unpromoted → completed_unpromoted 183, complete → complete 88, blocked → blocked 22. None is a transition. A change in the reason alone, for the same state, updates nothing on screen.
  • No action word; an attention column instead. The action (resume, recover, investigate, promote and the rest) is a function of the new state, so printing it beside the transition adds a word that reads as a third state: dispatched → abandoned recover was the lead's example. The row prints no action word and retires the state · action form from §6. What the coordinator does need is whether this event owes it anything. So the row opens, after the time, with a one-character attention column: ! when the new state owes the coordinator an action (blocked, stalled, abandoned, failed, needs-help, a completion awaiting promotion or review), blank otherwise. The state-to-action mapping is documented once, in the ticker's module docstring and the skill, not repeated on every row. The reason clause stays plain text explaining what happened.
  • Name column. A node name is truncated to leave at least two spaces before the transition cell. No cell ever touches the next.
  • Column order. The lead set the reading order on 2026-09-25: the time, then whether it needs you, then the model and effort the task runs on, then what the task is and what happened to it, then how long it has been going, then the fleet posture. So the row is, left to right: time, attention, model, effort, role, node name, transition (from → to), elapsed, counter block, reason clause. Every column has a fixed width with at least two spaces of gutter. Model and effort move from after the state to the third and fourth columns.
  • One format per pane. A follower that reloads onto new code mid-stream re-emits nothing, and marks the switch with one dim line such as ── ticker format updated ──, so a reader knows why the rows below look different.

What landed. New module reckon/crew/follow_checkpoint.py persists one checkpoint per project and session in the follower directory — stream path, device and inode (replacement), recorded byte offset (truncation), and the last reported state per run — written atomically (temp sibling, fsync, os.replace). _follow_resume_plan in reckon/cli.py selects one of three modes: baseline (first arm, unchanged), continue (seek to the recorded offset and deliver only the lines written since, carrying the stream's own timestamps and their state — no re-derivation), and restart (a replaced or truncated stream is re-read from its start and filtered to runs whose state differs from the checkpoint's). A continuation emits no baseline; a re-arm with nothing new prints nothing.

Both declared mutations were applied and observed to fail, logs recorded in the run directory: the re-arm ignores the durable checkpoint (4 failed, 1 passed) and replayed rows are stamped with the attach time (1 failed, 4 passed).
