§2 — Measure the counters against the fleet

This is an investigation. Its deliverable is docs/research/fleet-counters-against-the-fleet.html. It pairs each counter line the producer and follower emitted on 2026-09-24 for project reckon with the live classification at the same instant, reconstructed from run pointers, manifests, stream mtimes and worker.json pids. It then classifies every disagreement as one of three kinds:

  • stale: the counter was not recomputed when the fleet changed;
  • scope: the counter covers a different set of runs than the rows do;
  • classification: the counter faithfully counts a wrong state, such as a phantom abandoned run.

It names the function that computes the counter and the events that trigger a recompute. It also reproduces the refused-dispatch promoted row in a synthetic config home, and names the code path that turns a vanished pointer into that word.

Done when:

  • The report tabulates at least 50 counter observations with their disagreement class and the figure behind it.
  • It states the fraction of observations that disagree, per class.
  • It cites the counter's computing function and recompute trigger by file and line at a named revision.
  • The promoted reproduction is recorded as a command with its output.
  • No product file changes.

§3 — Counters and terminal words follow the classification

The counter should be recomputed from the same classification the rows use, whenever any run's classification changes. A pointer that disappears should be called promoted only when a ledger row for that run exists. Otherwise the follower should call it withdrawn, with the refusal named when the dispatch recorded one.

§4 — A re-arm continues the stream it left

The lead reported on 2026-09-25 that re-arming the follower every 30 minutes is fine, but every re-arm loses the history. A batch of rows arrives under one common timestamp, and the transitions that happened while no follower was attached never appear, which leaves a gap. The S23 coordinator's own follower reproduced it at 10:36:51–52 that day: after a re-arm it replayed twelve rows for runs already in flight, each stamped with the attach time.

Cause, at revision b453d763. The follower already has a resume path, but its checkpoint travels only through an environment variable handed across an in-place process reload (_take_follower_checkpoint, reckon/cli.py:1702). A re-arm is a new process with no checkpoint, so _follow_watch_lines (reckon/cli.py:2098–2112) takes the other branch, and two defects follow:

  • It emits watch_stream_cursor's baseline: one row per live run, stamped now. That is the common-timestamp batch.
  • It starts reading the producer's stream at the file's current end, so every line written between the old follower's exit and the new one's start is skipped. That is the gap.

After this section, a re-arm is a continuation.

  • The follower persists its checkpoint durably, per project and session, in the follower directory, and rewrites it atomically as it delivers. The checkpoint holds the stream path, enough of the stream's identity to tell a replaced or truncated file from the same one, the byte offset after the last line delivered, and the state last reported for each run.
  • A new follower for the same session reads that checkpoint. It seeks to the offset, delivers every line written since, each with the time the stream recorded, and then continues live. It emits no baseline. When nothing moved, the re-arm prints nothing.
  • When the checkpoint cannot be continued, because the stream was replaced or truncated, the follower falls back to state. It emits only runs whose state differs from the checkpoint's reported state, each stamped with the run's own recorded transition time, never the attach time.
  • A session's first arming has no checkpoint and emits the baseline as today, stamped per run.
  • Every row's age is computed from the run's recorded start.

The work is folded in from a-follower-outlives-its-monitor §4, whose falsifier this section's done-when extends. The S22 coordinator agreed on 2026-09-25, and that plan's section declarations and evidence stay with S22.

Done when:

  • A test with a synthetic config home and producer stream does the following in order:
    • arms a follower and delivers transitions;
    • ends the follower at its lifetime;
    • writes more transitions while nothing is attached;
    • re-arms with no environment checkpoint, as a fresh process would.
    It asserts that the second follower emits exactly the gap transitions, in order and with their stream timestamps, and no row for a run whose state did not change.
  • A re-arm with no intervening transition emits no line.
  • A test that replaces the stream between the two arms asserts that only changed runs are emitted, each stamped with its recorded time, and that no already-running run renders as dispatched.
  • Two declared mutations are applied and each is observed to fail, with its log recorded:
    • the re-arm ignores the durable checkpoint;
    • replayed rows are stamped with the attach time.
  • The tests leave the real follower directory under the user's config home untouched, and assert it.

The fence is the follow loop in reckon/cli.py, a new module holding the durable checkpoint, and the test. reckon/crew/runs.py joins it only if the stream's identity cannot be read without it.

§5 — The unpromoted count says what each run needs

The u counter says a run is unpromoted but not why. On 2026-09-25 the lead saw 3u while one of the three had no review at all. The reflex had reviewed only the run's first completion, and a resumed worker's new head sat idle for about ten minutes.

After this section, the follower emits a standing line, only when the set of unpromoted runs or their review state changes. It never repeats on a cadence: the lead rejected a heartbeat on 2026-09-25 because a signal that repeats gets ignored. Pending duties reach the coordinator every turn through the hooks in an-orchestrator-cannot-forget-its-obligations. The line names each of the session's unpromoted runs with its age, and says whether an independent review is in flight or the coordinator is needed.

The work is folded in from a-follower-keeps-your-work-in-view §2, whose falsifier is this section's done-when. Re-reviewing a resumed run's new head is reflex logic in reckon/crew/recovery.py, which S21's review-reflex node carries or which follows it. It is not part of this section.

Done when:

  • A test with three unpromoted runs asserts the standing line names all three with their ages. It labels the two with live reviews as review in flight and the one with no review as needs you.
  • The declared mutation, dropping the review-in-flight check, is observed to fail. The log is recorded.

§6 — The state cell carries the action; the reason is plain text

On 2026-09-25 the lead flagged that the reason clause repeats a label the state already implies, and that the label adds nothing. Rows read abandoned … recover: the process is gone …, stalled … investigate: stream quiet for 905s, blocked … ! resume: the worker process is gone …, unreadable … repair: the manifest at …. Worst is resume: ready to resume: …, where label and text say the same word twice. The text after the label is the useful part.

After this section:

  • The coordinator's action (resume, recover, investigate, repair, inspect, promote, review) moves into the state cell as <state> · <action>, for example blocked · resume. The ! urgency prefix becomes the state cell's colour and its word, not a glyph in the text.
  • The reason clause carries only the explanation. It never begins with a label and never repeats a word already in the state cell.

Done when:

  • A render test over every classification that carries a remedy asserts that no reason clause matches ^!?\s*\w+:, that the state cell contains the action word, and that the reason clause's first word differs from every word in the state cell.
  • A ready to resume case renders one resume, not two.
  • The declared mutation, restoring the label prefix, is observed to fail. The log is recorded.

§7 — A queued run keeps the ticker aligned

The lead reported on 2026-09-25 that a queued worker makes the ticker ragged. The coordinator's own follower showed the same misalignment from several causes:

  • The counter block gains a fourth bucket (q) only while a run is queued, so it changes width.
  • The elapsed cell mixes 0m, 15m, 0:14, 39:50 and 1:10:25.
  • Optional trailing cells (–, 0mb, 0mu) appear and vanish, and one row ran a cell into its text: 0mbinvestigate:.

After this section:

  • The counter block has a fixed width. Every bucket the fleet can show (w, b, u, q) always renders, with zero dimmed.
  • Elapsed uses one format, 57m or 1h33m, right-aligned to a fixed width.
  • Every optional cell keeps its column when empty, and a cell is always separated from the text by at least one space.

Done when:

  • A property test renders rows for every state, with and without a queued run in the fleet, and elapsed values from 0 s to 30 h. It asserts that the reason clause starts at the same column in every row, and that no cell abuts the text.
  • The declared mutation, rendering q only when non-zero, is observed to fail. The log is recorded.
