Why this plan exists

Four faults were measured on 2026-09-19 while a coordinator drained two sprints, and every one of them was caught by a person reading a run directory rather than by the runtime. The lead's ruling is that a check which always runs beats an instruction an agent has to remember, so each fault becomes a control in code, with a skill carrying at most a pointer to the command that exercises it. The record of this plan is docs/evidence/archive/crew-runtime-positive-controls-landed.html.

  • The nova watcher unit ran for seven hours without the backend directory on its PATH. Every wait-lift it issued launched clive, died at exec, and left a 0-byte resume-N.jsonl every two minutes (twelve of them on one run) while the pointer kept reading working. Parks lifted only when a person resumed from a shell that had the path.
  • A second project had no watcher process at all for an hour; its dispatches were admitted because a session follower was armed, and a follower cannot lift a wait. Both runs sat in phase starting with complete manifests.
  • A worker parked with RUNNING listed under wait_terminal, so a healthy watcher would have lifted the park on every tick while the job ran, and the worker would have re-parked each time.
  • A run's tests: prose claimed a passing gate while its structured suite record carried exit status 1; promotion refused correctly, but only because the coordinator read the manifest.

§1 — The backend binary is resolved before any launch, and the watcher execs an absolute path ✓ landed 2026-09-19

The launch plan in reckon/crew/dispatch.py hands subprocess.Popen an argv whose first element is a bare backend name and inherits the caller's environment, so whether the launch can happen at all depends on whoever started the process. Resolve the backend executable with shutil.which at the moment a launch plan is built, for dispatch, resume and every watcher lift, and store the absolute path in the plan; when resolution fails, refuse before writing any pointer or stream file, naming the binary and the PATH that was searched. reckon crew watch resolves every backend its project can route to at startup and refuses to arm when one is missing, so a watcher that cannot lift is never a watcher that reads as armed.

Done when. A dispatch, a resume and a watch started with the backend directory removed from PATH each refuse with the binary name and the searched path, and a launch plan built with it present carries an absolute executable; both are pinned by tests that manipulate the environment of the call, not the test process.

Landed 2026-09-19. The plan is resolved where it is built, at the dispatch, resume and member-move sites, and crew watch resolves every backend its project can route to before it takes the seat. §2 — A worker that exits before its first stream record is a launch failure, recorded once ✓ landed 2026-09-19

The launched-worker reaper knows the child exited; nothing reads that exit against the stream. A run whose stream file is empty when its process is gone is a launch failure, not a worker turn: record it as a lane record with the exit status, the stderr tail and the argv, move the pointer to a state the follower renders distinctly from working, and stop the lift loop after one such failure until an operator resumes or completes the run. The follower row shows the failure count and the last cause; the flight and drain views count it under an infrastructure classification rather than leaving the run invisible in a working bucket.

Done when. A synthetic backend that exits immediately produces exactly one launch-failure record and one distinct follower row for a run whose watcher would otherwise have retried every tick, the two-minute retry does not fire again, and a real resume from a repaired environment clears the state; pinned by tests on the reaper and the lift path.

Landed 2026-09-19. A run whose stream is empty when its process is gone gets one record on the run — exit status, argv, stderr tail — and a pointer in launch-failed, which the automatic lift refuses until a person resumes or completes the run; the hand-typed resume is deliberately left ungated so the person who repaired the environment can clear it. The control that makes the emptiness check mean anything runs the same spawn and reaper on a backend that writes a turn first and asserts no record appears; with the guard removed that control fails, which is how the guard was shown to be the thing the record rests on. §3 — Watcher liveness is read from the watcher process, and a follower never satisfies it

Done when. Landed 2026-09-19 — the --ensure half only. reckon crew watch --ensure renders a systemd user unit for the project and reconciles it in three ways: no unit gets written and started, an unchanged unit that is already active starts nothing and says so, and a rewritten unit is restarted onto its new definition, so the command a refusal names is safe to run against a watcher that is already up. §4 — A wait stanza is validated when written and a lift that re-parks on the same output is a defect

The wait reader in reckon/crew/recovery.py already refuses a no-op probe. Extend it: a wait_terminal value the probe prints while the awaited job is still queued or running (RUNNING, PENDING, WAITING, or any token the probe emits from a branch guarded by a live squeue result) is refused at manifest read with the offending token named, and a lift whose resumed worker re-parks with an identical probe output inside one tick is classified as a wait-key defect on the run and not lifted again until the manifest changes.

Done when. The 2026-09-19 stanza (RUNNING under wait_terminal beside a squeue probe) is refused by the reader with the token named, the re-park loop is detected on a synthetic run after one cycle, and both are pinned by tests beside the existing no-op probe test.

Landed 2026-09-19. The measured run r-20260919T111944475334-cco-review-repairs declared a squeue probe and, under wait_terminal, RUNNING — the token that probe prints on the branch it takes while the job is still queued. The declaration therefore read terminal on every sweep of a job that had not started, and the watcher wrote resume-1 through resume-30, most of them 0-byte streams. Two halves close it, both in the reader.
