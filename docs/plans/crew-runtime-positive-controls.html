Why this plan exists

Four faults were measured on 2026-09-19 while a coordinator drained two sprints, and every one of them was caught by a person reading a run directory rather than by the runtime. The lead's ruling is that a check which always runs beats an instruction an agent has to remember, so each fault becomes a control in code, with a skill carrying at most a pointer to the command that exercises it. The record of this plan is docs/evidence/archive/crew-runtime-positive-controls-landed.html.

  • The nova watcher unit ran for seven hours without the backend directory on its PATH. Every wait-lift it issued launched clive, died at exec, and left a 0-byte resume-N.jsonl every two minutes (twelve of them on one run) while the pointer kept reading working. Parks lifted only when a person resumed from a shell that had the path.
  • A second project had no watcher process at all for an hour; its dispatches were admitted because a session follower was armed, and a follower cannot lift a wait. Both runs sat in phase starting with complete manifests.
  • A worker parked with RUNNING listed under wait_terminal, so a healthy watcher would have lifted the park on every tick while the job ran, and the worker would have re-parked each time.
  • A run's tests: prose claimed a passing gate while its structured suite record carried exit status 1; promotion refused correctly, but only because the coordinator read the manifest.

§1 — The backend binary is resolved before any launch, and the watcher execs an absolute path ✓ landed 2026-09-19

The launch plan in reckon/crew/dispatch.py hands subprocess.Popen an argv whose first element is a bare backend name and inherits the caller's environment, so whether the launch can happen at all depends on whoever started the process. Resolve the backend executable with shutil.which at the moment a launch plan is built, for dispatch, resume and every watcher lift, and store the absolute path in the plan; when resolution fails, refuse before writing any pointer or stream file, naming the binary and the PATH that was searched. reckon crew watch resolves every backend its project can route to at startup and refuses to arm when one is missing, so a watcher that cannot lift is never a watcher that reads as armed.

Done when. A dispatch, a resume and a watch started with the backend directory removed from PATH each refuse with the binary name and the searched path, and a launch plan built with it present carries an absolute executable; both are pinned by tests that manipulate the environment of the call, not the test process.

Landed 2026-09-19. The plan is resolved where it is built, at the dispatch, resume and member-move sites, and crew watch resolves every backend its project can route to before it takes the seat. A refusal names the binary and the searched PATH and precedes every write; on the resume path that ordering was false as found, because the pointer was mutated with the context fit before the plan was built, and the reorder is pinned by comparing the pointer's bytes across the refusal. The path is made absolute without being canonicalised — resolving a launcher installed as bin/codex symlinked to codex.js recorded codex.js, which is a name no dialect matches, so the run could no longer read its own stream. Three cases outside the new files caught that; the linked launcher now has its own. §1 landed.

§2 — A worker that exits before its first stream record is a launch failure, recorded once ✓ landed 2026-09-19

The launched-worker reaper knows the child exited; nothing reads that exit against the stream. A run whose stream file is empty when its process is gone is a launch failure, not a worker turn: record it as a lane record with the exit status, the stderr tail and the argv, move the pointer to a state the follower renders distinctly from working, and stop the lift loop after one such failure until an operator resumes or completes the run. The follower row shows the failure count and the last cause; the flight and drain views count it under an infrastructure classification rather than leaving the run invisible in a working bucket.

Done when. A synthetic backend that exits immediately produces exactly one launch-failure record and one distinct follower row for a run whose watcher would otherwise have retried every tick, the two-minute retry does not fire again, and a real resume from a repaired environment clears the state; pinned by tests on the reaper and the lift path.

Landed 2026-09-19. A run whose stream is empty when its process is gone gets one record on the run — exit status, argv, stderr tail — and a pointer in launch-failed, which the automatic lift refuses until a person resumes or completes the run; the hand-typed resume is deliberately left ungated so the person who repaired the environment can clear it. The control that makes the emptiness check mean anything runs the same spawn and reaper on a backend that writes a turn first and asserts no record appears; with the guard removed that control fails, which is how the guard was shown to be the thing the record rests on. The reaper's raw wait status is converted to an exit code, so an exit of 127 records 127 and not 32512. The drain reading counts the run among the actionable ones under its own classification, which it did not before: the state had been given a classification and then left out of the set the count reads, so the run occupied a lane and read as invisible — the same defect one layer over. What is still carried is narrower and is a width question rather than a correctness one: the fleet counter's fixed four-bucket block has no bucket of its own for an infrastructure fault, so the number a reader sees is under blocked. §2 landed.

§3 — Watcher liveness is read from the watcher process, and a follower never satisfies it

watcher_state in reckon/crew/runs.py already binds liveness to a registered process, yet a dispatch was admitted with no watcher for its project because a session follower was armed. Make the dispatch and resume preconditions read watcher_live alone; a follower contributes to delivery, never to the watcher requirement. Add reckon crew watch --ensure, which starts or restarts the project's watcher as a user service with the resolved absolute executable and the environment it needs baked into the unit, writes the unit name into the watcher registration, and is idempotent; dispatch names that command in its refusal when the project is unwatched.

Done when. A dispatch into a project with a live follower and no watcher process is refused naming the ensure command; --ensure on a host with no unit starts one whose /proc/<pid>/environ carries the resolved backend directory; a second --ensure reports the existing unit and starts nothing; pinned by tests with a fake service manager.

§4 — A wait stanza is validated when written and a lift that re-parks on the same output is a defect

The wait reader in reckon/crew/recovery.py already refuses a no-op probe. Extend it: a wait_terminal value the probe prints while the awaited job is still queued or running (RUNNING, PENDING, WAITING, or any token the probe emits from a branch guarded by a live squeue result) is refused at manifest read with the offending token named, and a lift whose resumed worker re-parks with an identical probe output inside one tick is classified as a wait-key defect on the run and not lifted again until the manifest changes.

Done when. The 2026-09-19 stanza (RUNNING under wait_terminal beside a squeue probe) is refused by the reader with the token named, the re-park loop is detected on a synthetic run after one cycle, and both are pinned by tests beside the existing no-op probe test.

Landed 2026-09-19. The measured run r-20260919T111944475334-cco-review-repairs declared a squeue probe and, under wait_terminal, RUNNING — the token that probe prints on the branch it takes while the job is still queued. The declaration therefore read terminal on every sweep of a job that had not started, and the watcher wrote resume-1 through resume-30, most of them 0-byte streams. Two halves close it, both in the reader. First, _wait_terminal_names_a_live_state refuses RUNNING/PENDING/WAITING in any case and, separately, any token the probe text emits from a branch guarded by a non-empty squeue result — so a probe that invents its own wording for the live state is read out of its own text rather than matched against a vocabulary. The refusal names the offending token in the reason the follower already renders, so the repair needs no second reading of the probe. Second, the wait's signature is derived from what the declaration asks for — condition, probe, terminal and resume brief — rather than from the manifest file's modification time, so a worker that re-parks by rewriting its manifest no longer mints what the lift loop reads as a new condition; and a declaration that already lifted the run and has come back unchanged is marked as a wait-key defect on the run, rendered in classify_pointer with the repair named, so the lift loop stays stopped until the declaration changes. The decision the reader makes is drawn in the accompanying figure. §4 landed.

§5 — Skills carry the pointer, not the rule

Replace the recovery prose in skills/reckon-ship that tells a coordinator to export the backend directory and restart watcher units by hand with one line naming reckon crew watch --ensure, and state in the skill that a dispatch refused as unwatched is repaired by that command. Remove any instruction the code now enforces.

Done when. The skill carries the command and no longer carries the manual recipe, and reckon audit-doc passes on the plan and record.

§6 — A dispatch resolves its repository from the project mount, never from the caller's directory

Measured 2026-09-19 an hour after this plan was written: two reckon nodes dispatched from a shell whose working directory was the nova checkout received worktrees under the nova repository, because --repo defaults to the enclosing repository of the caller. One worker oriented, found none of its write paths, and blocked; the other was stopped before it could act. The dispatch already knows the project's mount (authority.plan.repository); when the resolved repository root is not that mount, refuse before creating a worktree, naming both paths and the --repo flag, and when --repo is absent take the mount rather than the shell. The same rule binds resume, member add and complete, each of which writes a checkout it resolves the same way.

Done when. A dispatch for project A run from project B's checkout with no --repo creates its worktree under A's mount; one run with --repo naming B is refused naming both roots; both pinned by tests with two temporary mounts.

§7 — A node that writes a check declares the negative that check fails against

Three checks were landed this week that ran, reported success, and could not fail for the reason they were written. A persistence guard compared one tensor-spline fit against its own evaluation, so its residual was zero by construction; it passed on all twenty archived states whose stored flux disagreed with their stored field by up to 2.2e-2 Wb. A receipt test held the two caption counts of a figure to its receipt but not the per-axis bars the renderer draws, so a figure built from a retired capture passed the gate that exists to catch exactly that. A panel test asserted a shared level array across two panels whose fixtures were written on one grid, so the assertion reproduced itself. Every one was found by an independent reviewer rather than by the runtime, and in each case the author's own gate was green.

The remedy is not more review. A node whose deliverable is a guard, an assertion or a test declares, in its done-when, the mutation that must turn it red, and its manifest carries that mutation's log beside the passing one. Dispatch refuses a node whose write paths include a test file when no negative is declared, the same way it refuses a missing specification level; promotion refuses a passing gate on such a node when the manifest carries no red log for the declared mutation. The two logs are the positive and negative control of one measurement, which is the standard this repository already holds physics evidence to.

Done when. A dispatch declaring a test path without a negative is refused, naming the field; a promotion of such a node without a red log is refused, naming the declared mutation; both pass when the pair is present, and the refusal messages name the discharge. Pinned by tests that exercise the refusal and its discharge on a fixture node.

A launch-failed run has no bucket of its own in the fleet counter

Reported by the launch-resolution node. The counter block is a deliberately fixed four-bucket width (working, blocked, unpromoted, queued), so a launch-failed run's number sits under blocked and reads to a coordinator as a triageable stop rather than an infrastructure fault. The drain reading does count it under its own classification, so it is not invisible, only mis-bucketed. Decide with the monitor plan's owner whether a fifth bucket is worth the column width, or whether the blocked bucket's reason clause should name the launch failure, and implement whichever is chosen.
