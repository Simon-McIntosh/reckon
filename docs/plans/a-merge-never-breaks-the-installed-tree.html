§1 — Why: one conflicting merge reached every follower on the workstation

On 2026-10-08 the lead saw this line in a follower pane, between ordinary rows: reckon crew follow deferred its reload: the new image does not import (SyntaxError: invalid syntax); keeping the current image, retrying when the code changes. Every producer and follower runs from the main reckon checkout and re-execs when its code changes. Before it re-execs, it imports the new code and refuses to load code that does not import, a guard added in 2bafddb13. The guard worked: no follower or producer died. What it caught was this:

23:57:29A coordinator session, building another plan, ran git merge --no-ff a44b5105f in the shared reckon checkout. Its branch predated the split of reckon/crew/recovery.py merged at 19:04, and the merge stopped: Automatic merge failed; fix conflicts.
23:57:29Git wrote <<<<<<< markers into reckon/crew/recovery.py in the working tree, which is the code every reckon process imports.
23:57The producers for reckon, imas-codex, imas-ambix, nova and RabbitPy each logged deferred its reload … SyntaxError, and so did the followers, whose panes showed the line.
23:57:46The session ran git merge --abort. It confirmed import reckon.crew.recovery worked again, and the tree was clean by 23:58.

For those 25 seconds, any reckon command that imported recovery.py from the checkout, such as a crew verb, a hook or a restarting MCP server, would have failed with the same SyntaxError. Another session saw it and asked who owned the merge. The cause is the place, not the merge: a conflicting merge is routine in a worktree, but a main checkout here is also the installed program. Nothing stops a coordinator from starting one there. The worker git guard (reckon/hooks/worker_git_guard.py) is already registered as a PreToolUse Bash hook for every session, but it applies only inside a crew run and lets every coordinator command through.

The same log shows two other moments when the tree briefly did not import: an ImportError at 06:42 during the CLI split, and a nova unterminated string literal. Neither is a merge conflict, and this plan does not address them; the reload guard covered both.

§2 — The git guard refuses a merge that would conflict in a main checkout

Deliverable. reckon/hooks/worker_git_guard.py gains a second rule that applies to every session, coordinator or worker. A git merge whose target repository is a main checkout, not a linked worktree, is first predicted with git merge-tree --write-tree --no-messages HEAD <commit> in that repository. When the prediction reports conflicts, the merge is refused before it runs. The refusal names the conflicted paths and the remedy: resolve the merge in a scratch worktree, commit it there, and fast-forward the checkout to it. A merge with no predicted conflict runs as before, as does any merge in a linked worktree or one the prediction cannot answer, such as an unknown revision. The guard reuses the module's existing command split and target resolution and its existing PreToolUse registration, so no install step changes. The module docstring states both rules. It adds no public definition and no refusal family beyond this one message.

Done when tests/test_merge_guard_refuses_a_conflicting_merge.py builds a temporary repository with a main checkout and a branch that conflicts with it on one file, and feeds the hook a coordinator payload, with no RECKON_RUN_ID, for git merge --no-ff <branch> run in the main checkout. The hook denies it, naming the conflicted file. Afterwards the checkout's file still matches HEAD and MERGE_HEAD does not exist. The same payload for a branch that merges cleanly is allowed, as is the conflicting merge issued from a linked worktree. The negative control is executed and logged: with the merge rule removed, the conflicting payload is allowed and the test fails. The tests importing reckon.hooks.worker_git_guard pass. The write paths are reckon/hooks/worker_git_guard.py and tests/test_merge_guard_refuses_a_conflicting_merge.py.
