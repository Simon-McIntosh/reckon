§1 — A signal with no consequence is not a check

Measured in imas-codex on 2026-09-01, and the numbers are the whole argument. Its test.yml workflow runs a bare whole-tree uv run pytest on every push to main and on every pull request. No path restriction, no continue-on-error, failure fatal to the job. Over the last 120 runs:

2026-08-270913
2026-09-0104552
total05465

Zero successes. A collection error had aborted the whole suite since 2026-08-25 — a week in which the default test command ran no tests at all — and CI was red on every push throughout. The detection was never missing. What was missing is that being red had no consequence: sessions kept dispatching, promoting and merging, and a 20-test regression was introduced inside that window and stayed invisible for two hours despite a red main.

This is reckon's problem rather than the consuming repository's, because the moment a change becomes a claim is crew complete. That is where a gate can refuse, and it is the one place every project's sessions pass through. Two sibling reckon plans already established the halves either side of it: run records became committed evidence, and a finished worker stopped being silent. This closes the gap between knowing and mattering.

§2 — Judge by delta, never by absolute redness

This constraint is load-bearing and was learned by counter-example, not derived. The first proposal was that crew complete refuse to promote while the tree's suite is red. That version would have blocked all fifteen nodes of the session that was repairing the outage — including the node whose own work made the redness visible in the first place.

A gate that fails closed on the fix for the problem it detects is worse than no gate: it converts a detected fault into a stalled repository, and the only way out is to disable the gate, which then stays disabled. So the measure is not is the suite green but did this node add a failure.

Reckon's consuming repositories already carry this pattern for lint, which is the precedent to follow rather than invent: a contributor is told to judge their own commit by delta because a file may carry pre-existing findings that are not theirs to fix in passing, and what they owe is adding none. The same shape applies here. A node inherits whatever the tree was already failing; it owes an empty delta.

§3 — The escape hatch is mandatory, and it is a record rather than a switch

A gate with no waiver becomes a gate that gets deleted the first time it is wrong, and it will be wrong: an infrastructure failure, a flaky test, a deliberate red-to-green migration landing in stages. So the waiver ships with the gate, not after it.

It should follow the form reckon already uses for exactly this situation rather than a new one. crew dispatch refuses on an unreconciled backlog and accepts an explicit flag that records the waived backlog on the new run; a synchronous one-off may dispatch unwatched and the waiver is written onto both the live run and its promoted ledger record. The properties that make those acceptable are the ones needed here: the waiver is explicit rather than a default, it demands a reason rather than a boolean, and it is recorded on the ledger row so a waived promotion is distinguishable forever from a clean one. A waiver nobody can count is indistinguishable from no gate.

§4 — A separate finding with a different fix: cancelled runs have no conclusion

Of those 120 runs, 65 were cancelled — more than the 54 that failed. The workflow sets concurrency.group to ${{ github.workflow }}-${{ github.ref }} with cancel-in-progress: true. That is right for a pull request, where a superseded commit's result is genuinely uninteresting, and wrong for main, where each commit's result IS the record.

With several agent sessions pushing in quick succession — roughly twenty pushes in one evening from two sessions — main CI structurally cannot finish. So for the majority of pushes there was nothing to read, not merely something unread. This is tracked here to be handed on, not fixed here: it is a workflow policy in the consuming repository, its fix is one conditional expression, and it is separate from the gate because only one of the two problems is about attention. A promotion gate reading a CI conclusion must nonetheless treat cancelled as absence of evidence rather than as a pass, which is why the two findings touch.

§5 — Deliverables

  • A promotion-time measure of whether the promoting node added a suite failure, computed against a stated baseline rather than against green.
  • A refusal on a non-empty delta, carrying the added failures' ids so the operator sees what to fix rather than that something is wrong.
  • An explicit waiver requiring a reason, recorded on the promoted ledger record so waived promotions remain countable and auditable.
  • Absence of evidence treated as absence rather than as a pass — a cancelled, missing or never-run suite is not a clean delta.
  • A regression proving the gate would have refused a known-bad promotion, and a second proving it would NOT have blocked the fifteen nodes of the session that repaired the outage.

§ Decisions

What is the baseline a promotion's failure delta is measured against?

Who executes the suite whose delta the gate reads?

Does the gate apply to every project by default, or opt in per project?

§ Followups

Build the delta-measured promotion gate with its waiver

Three decisions are open and each changes the implementation, so lock them before dispatching: what the delta baseline is, who executes the suite, and whether the gate defaults on. The measured incident in §1 and the counter-example in §2 are the inputs and do not need re-deriving. Sprint placement is a proposal, not a decision: this plan was authored from imas-codex by the session that measured the incident, and S9 was chosen because its theme produced the signal this plan gives consequence to. A reckon session should confirm or rebalance it.
