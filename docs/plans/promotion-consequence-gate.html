§1 — A signal with no consequence is not a check

Measured in imas-codex on 2026-09-01, and the numbers are the whole argument. Its test.yml workflow runs a bare whole-tree uv run pytest on every push to main and on every pull request. No path restriction, no continue-on-error, failure fatal to the job. Over the last 120 runs:

datesuccessfailurecancelled
2026-08-270913
2026-09-0104552
total05465

Zero successes. A collection error had aborted the whole suite since 2026-08-25 — a week in which the default test command ran no tests at all — and CI was red on every push throughout. The detection was never missing. What was missing is that being red had no consequence: sessions kept dispatching, promoting and merging, and a 20-test regression was introduced inside that window and stayed invisible for two hours despite a red main.

This is reckon's problem rather than the consuming repository's, because the moment a change becomes a claim is crew complete. That is where a gate can refuse, and it is the one place every project's sessions pass through. Two sibling reckon plans already established the halves either side of it: run records became committed evidence, and a finished worker stopped being silent. This closes the gap between knowing and mattering.

§2 — Judge by delta, never by absolute redness

This constraint is load-bearing and was learned by counter-example, not derived. The first proposal was that crew complete refuse to promote while the tree's suite is red. That version would have blocked all fifteen nodes of the session that was repairing the outage — including the node whose own work made the redness visible in the first place.

A gate that fails closed on the fix for the problem it detects is worse than no gate: it converts a detected fault into a stalled repository, and the only way out is to disable the gate, which then stays disabled. So the measure is not is the suite green but did this node add a failure.

Reckon's consuming repositories already carry this pattern for lint, which is the precedent to follow rather than invent: a contributor is told to judge their own commit by delta because a file may carry pre-existing findings that are not theirs to fix in passing, and what they owe is adding none. The same shape applies here. A node inherits whatever the tree was already failing; it owes an empty delta.

§3 — The escape hatch is mandatory, and it is a record rather than a switch

A gate with no waiver becomes a gate that gets deleted the first time it is wrong, and it will be wrong: an infrastructure failure, a flaky test, a deliberate red-to-green migration landing in stages. So the waiver ships with the gate, not after it.

It should follow the form reckon already uses for exactly this situation rather than a new one. crew dispatch refuses on an unreconciled backlog and accepts an explicit flag that records the waived backlog on the new run; a synchronous one-off may dispatch unwatched and the waiver is written onto both the live run and its promoted ledger record. The properties that make those acceptable are the ones needed here: the waiver is explicit rather than a default, it demands a reason rather than a boolean, and it is recorded on the ledger row so a waived promotion is distinguishable forever from a clean one. A waiver nobody can count is indistinguishable from no gate.

§4 — A separate finding with a different fix: cancelled runs have no conclusion

Of those 120 runs, 65 were cancelled — more than the 54 that failed. The workflow sets concurrency.group to ${{ github.workflow }}-${{ github.ref }} with cancel-in-progress: true. That is right for a pull request, where a superseded commit's result is genuinely uninteresting, and wrong for main, where each commit's result IS the record.

With several agent sessions pushing in quick succession — roughly twenty pushes in one evening from two sessions — main CI structurally cannot finish. So for the majority of pushes there was nothing to read, not merely something unread. This is CLAIMED, not merely handed on: an earlier version of this section recorded it as pending hand-off, which was the exact shape of work that falls between two plans and is never done — and a reckon plan can name an imas-codex workflow file but cannot change it, so there was no hand to hand it to. imas-codex’s hidden-suite-failures plan now owns it explicitly (6c924f83), and also records that this gate is reckon’s so no second one is built there. It stays separate from the gate because only one of the two problems is about attention, and because it is a policy decision rather than a defect repair — more runs reaching a conclusion consumes more minutes, and cancel-in-progress is genuinely correct for pull requests. A promotion gate reading a CI conclusion must nonetheless treat cancelled as absence of evidence rather than as a pass, which is why the two findings touch.

That seam can fail silently and deserves stating as a rule rather than a caveat. The naive reading is “not failure, therefore fine” — and with 65 of 120 runs cancelled that admits the majority of pushes on a measurement that never happened. That is absence-as-permission arriving inside the mechanism built to prevent absence-as-permission. It bites hardest on one specific choice below: if the delta baseline is taken as the previous promotion’s CI result, the previous promotion is disproportionately likely to have been cancelled by the next push, so that option inherits the worst of the cancellation problem rather than a random sample of it. Any conclusion-reading implementation must fail closed on absence.

§4a — Three absences a gate would read as permission

The cancellation seam above is not the only one, and they share a shape worth naming once so an implementation can check itself against all three. Each is a state that is not a failure and is also not a pass, which a naive reading admits:

absencereads asactually means
exit 2 collection errora configuration nuisanceno test in the tree ran
cancelled CI runnot failure, therefore finethe measurement never completed
skipped modulethe suite collected, so it ranthe check never executed

All three were measured in one repository on one day. The third is the subtlest and arrived while this plan was being written: a conditional import intended to keep a check alive “wherever the dependency is available” skipped the module whole, because in the repository the check guards that dependency is never available. A conditional guard is only a guard if its condition is sometimes true where it runs — and the argument for making it conditional was correct-sounding with an unmeasured premise, which is a different and harder failure than aiming an instrument wrongly.

The consequence for this gate is a hard requirement rather than a caution: whatever the gate reads must distinguish ran-and-passed from was-skipped and from never-measured. A gate satisfied by “the suite collected” would pass today in a repository whose own layout check collects zero tests. Any measure that cannot tell those apart inherits at least one of the three absences, which would place absence-as-permission inside the mechanism built to prevent it.

§5 — Deliverables

  • A promotion-time measure of whether the promoting node added a suite failure, computed against a stated baseline rather than against green.
  • A refusal on a non-empty delta, carrying the added failures' ids so the operator sees what to fix rather than that something is wrong.
  • An explicit waiver requiring a reason, recorded on the promoted ledger record so waived promotions remain countable and auditable.
  • Absence of evidence treated as absence rather than as a pass, covering all three forms in §4a — a collection error, a cancelled run and a skipped module are each distinguishable from ran-and-passed, and none is a clean delta.
  • A regression proving the gate would have refused a known-bad promotion, and a second proving it would NOT have blocked the fifteen nodes of the session that repaired the outage.

§ Decisions

What is the baseline a promotion's failure delta is measured against?

The ledger already records base_sha for every run, so the baseline is reproducible from committed state and needs no new store. The previous-promotion option inherits the cancellation problem stated in §4, and a worker-captured pre-change run makes the baseline self-reported by the party being judged.

Who executes the suite whose delta the gate reads?

Extends the existing refusal of a passing gate promoted without check evidence rather than adding a second measurement path, and costs no promotion-time wait; the gate running the suite itself was measured at about 487 s per promotion, roughly two hours of serial waiting over one fifteen-node session, and reading CI inherits a 65-of-120 cancellation rate. The worker's before and after counts must be recorded with command, exit status and log path so the evidence is auditable, and their absence is a refusal.

Does the gate apply to every project by default, or opt in per project?

A project with no declared suite command has nothing to measure. Default-on with absence treated as refusal would block every promotion in such a project, and default-on with absence treated as a pass contradicts §4. The gate arms when a project declares its suite command in flight config.

§ Followups

Build the delta-measured promotion gate with its waiver

Three decisions are open and each changes the implementation, so lock them before dispatching: what the delta baseline is, who executes the suite, and whether the gate defaults on. The measured incident in §1 and the counter-example in §2 are the inputs and do not need re-deriving. Sprint placement is a proposal, not a decision: this plan was authored from imas-codex by the session that measured the incident, and S9 was chosen because its theme produced the signal this plan gives consequence to.
