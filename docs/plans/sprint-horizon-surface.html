§1 — A 48-hour strip with a live now-line

The planning horizon is one to two days. The screen must therefore show today and tomorrow, with hour resolution and a cursor at the current instant, and must stop offering horizons that only make sense for a calendar.

Retire the 4w, 8w, 6m and all settings. The strip spans a fixed 48 hours anchored on the current local day boundary, marks the today/tomorrow division, and carries a now-line that advances without a reload. Sprints are not drawn as calendar bars at this zoom — whole-day starts/ends cannot place a bar meaningfully inside 48 hours, and drawing one anyway is the defect being removed. What the strip carries instead is the work that genuinely has a timestamp: completed runs, live runs, and the now-line.

The anatomy below is the whole screen, and the proportions are the point — the strip is a thin band and the table is the page.

Done when: the served Sprints screen offers no horizon longer than 48 hours; a now-line is present and its position is derived from the current instant rather than from M.today; and the now-line advances without a page reload. Evidence is a rendered capture plus a source-contract assertion that the retired horizon keys are absent.

§2 — The all-sprints state table

This section answers the complaint that there is no way to see all sprints at once, and it is the primary object on the screen. One row per sprint, carrying every field the lead named: status, implementation, ordering, blocked or delayed work, and which sprints are active.

The data already exists. A peer session landed the composition at merge d5d876f, so GET /_discover/<project> now carries a derived sprint_order, per-sprint metrics (item_count, by_effective_status, mean_impl, current_work) and a review findings block. This section is therefore wiring and layout, not new server work, and it must consume those fields rather than recompute them client-side.

Ordering is derived, never authored. The row order is sprint_order from the server, with a natural-id fallback when it is absent. A sprint's position in the list is a claim about dependency order, so reading it from an authored field would let the display disagree with the graph.

Disagreement about which sprint is active is shown, not resolved. This project currently reports active_sprint_id: S6 while S6 carries status planned, and S9 and S12 both carry active — so the stored pointer names a sprint that is not active and misses two that are. Another project reports four simultaneously-active sprints as its designed mode. The table badges every sprint carrying active and surfaces the conflict with the pointer as a visible badge. Silently picking one is the failure this badge exists to prevent, and a peer's merge already established that treatment — preserve it.

Blocked and delayed are flags, not statuses. A sprint holding blocked items shows a blocked flag with its count; a sprint whose ends date has passed while items remain open shows a delayed flag. Neither replaces the status column, because an active sprint with blocked work is both things at once and the current kanban loses exactly that distinction.

Done when: every sprint in the project appears as a row carrying status, an implementation figure, its derived order position, and blocked/delayed/active flags; the order matches the server's sprint_order under assertion; and a project whose stored active pointer disagrees with its active set renders the conflict badge. Evidence is a rendered capture against live state plus assertions on order and conflict rendering.

§3 — Make the page scroll

The surface cannot be scrolled to its foot. .r-sprint-surface combines flex: 1 with overflow: auto, which makes the scroll container a flex child sized by its parent rather than by its content, so content below the available height is unreachable rather than merely below the fold. The repair belongs with the layout work because the two new elements in §1 and §2 change the page's height profile, and a taller page makes the defect worse rather than incidental.

The fix is to establish one intentional scroll container for the view and to state which element owns scrolling, rather than to add a second overflow and hope the cascade resolves it. That statement is the deliverable as much as the behaviour is: the plan sprint-scope-and-surface has a locked decision recording that this cascade has no stated ownership boundary, and this section must not make that worse.

Done when: the full content of both surfaces is reachable by scrolling at a viewport height that previously truncated it, demonstrated by a rendered capture at a constrained viewport that reaches the last element; and the view declares exactly one scroll owner.

§4 — Retire the kanban for what-runs-next

The board's three columns are keyed on one field the §2 table shows in full, and the keying is lossy: blocked maps into doing, so blocked work renders as work in progress. Removing it costs nothing that §2 does not already carry better.

What replaces it is the question the board was being used to answer badly: what should run next. That is a derived answer the roadmap already computes — the ready set, with each row's reason — and rendering it directly is both smaller and more honest than three columns a reader must infer an ordering from.

Two cautions carried from a peer's consumer report. Ready work is a set of concurrent lanes rather than a sequence, so a rank column would invite serialising work that should fan out — show the lanes, not a ranking. And a landed row must be demoted rather than deleted, so a reader can see what closed without it competing with open work.

Done when: the board surface is gone from the Sprints screen; the replacement renders the ready set with a per-row reason and no rank column implying a sequence; blocked work is visually distinct from in-progress work; and no orphan CSS for the retired component remains. Evidence is a rendered capture plus a source assertion that the retired component and its selectors are absent.

§5 — See a new plan without reloading the site

A new plan currently appears only after a full page reload, and the reason is explicit in the source rather than emergent: docs/ui/shell.jsx:217 wires the refresh control to window.location.reload(). Discovery is read once into window.STATE at hydration and never revalidated, so the refresh control has no cheaper mechanism to call.

The deliverable is a client-side refresh that refetches discovery and re-renders from the new payload, without re-executing the page. It must be triggerable explicitly by the control that exists today, and it must not become a busy poll — the surface already polls live crew runs every three seconds and adding a second unconditional interval over a 699 KB payload would trade one complaint for a slower one. Revalidation that can return “unchanged” cheaply is what makes this affordable, and the discovery cache measured at twenty milliseconds warm is what makes it fast.

Done when: a plan file created while the page is open becomes visible without a page reload; the refresh path performs no full document navigation, asserted rather than observed; and the added steady-state request cost is stated as a measured figure rather than assumed negligible.

§6 — Stop charging ten seconds for a reload

This section owns the client-side half of the reload cost measured in §0, which no other plan covers. surface-latency-and-legibility §2 owns the cold-scan half and is separately blocked on a decision contradiction; the two do not overlap.

Three costs, each independently removable:

  • React and ReactDOM are fetched as .development.js builds from a remote CDN. Development builds are unminified and carry warning machinery; production builds are a fraction of the size. Serving them locally also removes two remote origins from the critical path, which matters more than the byte count on a network that does not reach unpkg quickly.
  • 240,579 bytes of JSX are transformed in the browser on every load, by a compiler that is itself fetched from that same CDN. The transform result is identical for every visitor and every reload.
  • Google Fonts adds two further remote origins, which a peer's own measurement already flagged as making a published build not self-contained.

The repository's stated architecture is a constraint on the fix, not a casualty of it. AGENTS.md describes the SPA as compiled in-browser with no build step, and that property is worth keeping: it is why a plan author can edit a component and reload. So the acceptable shapes are ones that remove the client cost without introducing an authoring build step — for instance transforming and caching server-side, since the server already serves these files — and the unacceptable shape is one that requires a build before a local edit is visible. reckon build already produces a self-contained static bundle, so the transform capability may already exist in the tree; establishing that is the section's first task, not an assumption.

Done when: a served page load fetches zero third-party origins and performs zero in-browser JSX transformation; first-load and reload wall-clock are reported before and after against the same project on the same host; and editing a component followed by a reload still shows the change with no build command run. The last clause is the one that keeps the fix from costing more than it saves.

§ Decisions

What replaces the gantt and the kanban on the Sprints screen?

The server already composes derived sprint_order , per-sprint metrics and a review findings block, so all candidate shapes are wiring rather than new data. The planning horizon is one to two days.

Locked by the lead 2026-08-26. The table answers the all-sprints complaint directly and degrades gracefully at any window width, while the strip carries the one thing a table cannot express — the current instant. The two-day grid was rejected on a measured property of the data rather than on taste: sprint items carry whole-day dates only, so most rows could not be placed by hour and the grid would read emptier than the data actually is. Rescaling the existing timeline was rejected as partly cosmetic, since it preserves the bar-per-sprint metaphor the lead had already called useless.

Does the kanban board survive in any form?

The lead judged it to add limited value. Its three columns are keyed on a single field the state table renders in full, and the keying folds blocked into doing .

Locked by the lead 2026-08-26 as part of the screen-shape selection. Keeping it as a secondary tab preserves a lossy view of data shown losslessly elsewhere, and the column mapping actively misreports blocked work as in progress. The ready set is the question the board was being used to answer, and the roadmap already derives it.

May the fix for the client-side reload cost introduce an authoring build step?

AGENTS.md describes the SPA as pure client-side React with JSX compiled in-browser and no build step, and that property is why a component can be edited and reloaded. Removing the in-browser transform is the largest single win available in §6, so the two pull against each other.

Locked at authoring, and it is a constraint rather than a mechanism: it forbids an outcome, not a technique. Server-side transform with caching satisfies it because the server already serves these files, and reckon build already produces a self-contained bundle, so the capability may exist in the tree. Accepting a build step was rejected because the edit-and-reload loop is the reason the architecture was chosen and losing it would cost more than the ten seconds being recovered. If the constraint turns out to be unsatisfiable, that is a finding to bring back through the dissent flow rather than a licence to quietly add a build.

When the stored active-sprint pointer disagrees with the set of sprints carrying active, which wins?

Measured in this project: active_sprint_id names S6, whose status is planned , while S9 and S12 both carry active . Another project reports four simultaneously-active sprints as its designed mode, so this is not a data defect to be normalised away.

Locked at authoring, consistent with the treatment a peer already merged at d5d876f . Either resolving rule produces a screen that is confidently wrong: the pointer currently names a sprint nobody is working in, and declaring the pointer legacy discards a field other surfaces still read. A conflict that is displayed gets fixed; a conflict that is resolved silently becomes permanent.

§ Followups

Rebuild the Sprints screen: 48-hour strip, all-sprints table, scroll, ready set, live refresh, client load

Six sections, and the order is not arbitrary. §3 comes early because both new elements change the page's height profile and the scroll defect gets worse as the page grows, so fixing it after §1 and §2 means fixing it twice. §2 is the largest single win and is pure wiring over fields a peer already merged at d5d876f — the derived sprint_order, per-sprint metrics and the review block — so it must consume them rather than recompute anything client-side. §4 is safe to run beside §2 only if the ready-set replacement lands in a different file than the table.

§5 and §6 are independent of the whole surface group and of each other, and neither touches sprint.jsx, so they can run concurrently with the rest. §6 carries a hard constraint from its locked decision: it may not introduce an authoring build step, because the edit-and-reload loop is why the architecture was chosen. If that turns out to be unsatisfiable, bring it back through the dissent flow rather than adding a build quietly.

Two cautions for whoever executes. Do not key anything on the derived active sprint — this project's pointer names a planned sprint while two others carry active, and the conflict badge exists to show that rather than resolve it. And any rendered-browser gate is only trustworthy on a quiet host: an earlier run on this surface lost its gate to DevTools stalls under a foreign load that held the box at 60–130, and the correct response was to record the evidence as owed rather than fake a capture.
