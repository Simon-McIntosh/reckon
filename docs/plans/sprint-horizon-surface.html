Original §6 framing, retained

This section owns the client-side half of the reload cost measured in §0, which no other plan covers. surface-latency-and-legibility §2 owns the cold-scan half and is separately blocked on a decision contradiction; the two do not overlap.

Three costs, each independently removable:

  • React and ReactDOM are fetched as .development.js builds from a remote CDN. Development builds are unminified and carry warning machinery; production builds are a fraction of the size. Serving them locally also removes two remote origins from the critical path, which matters more than the byte count on a network that does not reach unpkg quickly.
  • 240,579 bytes of JSX are transformed in the browser on every load, by a compiler that is itself fetched from that same CDN. The transform result is identical for every visitor and every reload.
  • Google Fonts adds two further remote origins, which a peer's own measurement already flagged as making a published build not self-contained.

The repository's stated architecture is a constraint on the fix, not a casualty of it. AGENTS.md describes the SPA as compiled in-browser with no build step, and that property is worth keeping: it is why a plan author can edit a component and reload. So the acceptable shapes are ones that remove the client cost without introducing an authoring build step — for instance transforming and caching server-side, since the server already serves these files — and the unacceptable shape is one that requires a build before a local edit is visible. reckon build already produces a self-contained static bundle, so the transform capability may already exist in the tree; establishing that is the section's first task, not an assumption.

Done when: a served page load fetches zero third-party origins and performs zero in-browser JSX transformation; first-load and reload wall-clock are reported before and after against the same project on the same host; and editing a component followed by a reload still shows the change with no build command run. The last clause is the one that keeps the fix from costing more than it saves.

§8 — A browser gate must say why it could not start a browser

✓ landed 2026-09-01 A failed probe now reports which of three start failures occurred instead of a bare timeout: ceiling-exhausted, sandbox-denied or navigation-never-completed, carrying the browser's stderr and the inotify count against the limit. Gate passed 7/7, each classification asserted from an injected condition rather than by exhausting the shared host ceiling — which would have inflicted the outage this section exists to prevent. A preflight refuses to start a probe when an AF_INET socket cannot be created and names the worker role as the likely cause. Record: §8 landed (commit 6979f98). Owed: the four test_build.py cases that spend 75 s each producing no assertion should use this classifier to skip on an unavailable browser rather than fail opaquely.

Every rendered gate in this plan depends on starting a headless browser, and when the host cannot start one the harness reports a bare timeout. A timeout is indistinguishable from a code defect, so the worker reads it as its own failure, retries once inside its fence, and stops. That is not a hypothetical reading of the code: four nodes across two sessions spent their time budgets on it in a single afternoon, each concluding independently that its own change might be at fault.

The mechanism, measured. fs.inotify.max_user_instances is 128 per user. A browser needs at least one instance. Leaked browsers hold theirs forever because no parent survives to reap them, so once roughly 128 accumulate, every subsequent inotify_init in the account fails with Too many open files and no browser can start again — for any session, until someone kills processes by hand. The observed state was 328 leaked browser processes holding all 128 instances, aged 3.9 to 4.6 hours, spawned in one 20-minute window in batches of about ten, which is the signature of a single full-suite run leaking every browser it opened. Reaping them restored usage to 52 of 128 and browsers started immediately.

This section is not the leak. The leak is a separate defect and it is already fixed: the harness now signals the process group with SIGKILL rather than politely asking a browser that has already missed its deadline, and the cleanup path no longer swallows the probe's failure. What remains unfixed is the diagnosis. The code stopped leaking hours before the outage ended, because a fix that does not clean up what the old code already produced leaves the symptom running at full strength. During that window the failure was invisible in exactly the wrong way: the suite reported test failures, so every reader looked at the tests.

Two deliverables, and the first is the one that matters. The harness must distinguish the host could not start a browser from the page did not become ready, and say which. On a startup failure it reports the browser's own stderr and the inotify instance count against the ceiling, and it fails fast rather than consuming a navigation deadline it cannot meet. Second, it should decline to leave stale profile directories behind — 1.3 GB of them had accumulated under the per-user runtime directory, which is a scarce shared allocation.

There are three start failures, not one, and the investigation found the third. A browser can fail to start because the per-user inotify ceiling is full; because the sandbox denies socket creation outright, which returns EPERM on AF_INET in about 0.14 s with a crashpad setsockopt error and is instantly distinguishable; or it can start cleanly and then never complete a navigation, which is the unresolved host fault. Each needs a different response — wait and retry, use a different worker role, or stop and report — and today all three arrive as the same bare timeout.

Done when: the harness classifies a failed probe into ceiling-exhausted, sandbox-denied or navigation-never-completed and reports the browser's own stderr with the inotify count against the limit; tests assert each classification from an injected condition rather than by exhausting the real host, since exhausting a shared ceiling to prove a message would inflict the outage this section exists to prevent; a preflight refuses to start a probe at all when an AF_INET socket cannot be created, naming the role as the likely cause; and a completed run leaves no profile directory behind. The negative case is the point — a gate that cannot run must be loud about the reason, because the alternative cost four nodes, two sessions and four hours, with every one of them independently blaming its own code.

The server already composes derived sprint_order , per-sprint metrics and a review findings block, so all candidate shapes are wiring rather than new data. The planning horizon is one to two days.

Does the kanban board survive in any form?

The lead judged it to add limited value. Its three columns are keyed on a single field the state table renders in full, and the keying folds blocked into doing .

Locked by the lead 2026-08-26 as part of the screen-shape selection. Keeping it as a secondary tab preserves a lossy view of data shown losslessly elsewhere, and the column mapping actively misreports blocked work as in progress. The ready set is the question the board was being used to answer, and the roadmap already derives it.

May the fix for the client-side reload cost introduce an authoring build step?

AGENTS.md describes the SPA as pure client-side React with JSX compiled in-browser and no build step, and that property is why a component can be edited and reloaded. Removing the in-browser transform is the largest single win available in §6, so the two pull against each other.

Locked at authoring, and it is a constraint rather than a mechanism: it forbids an outcome, not a technique. Server-side transform with caching satisfies it because the server already serves these files, and reckon build already produces a self-contained bundle, so the capability may exist in the tree. Accepting a build step was rejected because the edit-and-reload loop is the reason the architecture was chosen and losing it would cost more than the ten seconds being recovered. If the constraint turns out to be unsatisfiable, that is a finding to bring back through the dissent flow rather than a licence to quietly add a build.

When the stored active-sprint pointer disagrees with the set of sprints carrying active, which wins?

Measured in this project: active_sprint_id names S6, whose status is planned , while S9 and S12 both carry active . Another project reports four simultaneously-active sprints as its designed mode, so this is not a data defect to be normalised away.

Locked at authoring, consistent with the treatment a peer already merged at d5d876f . Either resolving rule produces a screen that is confidently wrong: the pointer currently names a sprint nobody is working in, and declaring the pointer legacy discards a field other surfaces still read. A conflict that is displayed gets fixed; a conflict that is resolved silently becomes permanent.
