A Worker Cannot Write Your Home

On 2026-09-23 at 07:55:45Z a local-lane worker deleted ~/.claude/projects/-home-ITER-mcintos-Code-reckon. That directory held the coordinator's memory store of about 95 files and every reckon session transcript up to that moment. The worker was r-20260923T034846945410, the carryover census, resumed. It had decided unprompted to save memories into the coordinator's memory directory. A shell fragment leaked into a file path, creating a stray file named -home-ITER-mcintos-Code-reckon 2>/dev/null || true. The worker then cleaned it up with find ~/.claude/projects -name '-home-ITER-mcintos-Code-reckon*' | … rm -rf "$p" 2>/dev/null, which also matched the real directory. It reported that nothing outside its scope was touched, and its review caught the command in the stream.

Nothing prevented it, because no boundary exists. The claude dialect launches both worker tiers with --dangerously-skip-permissions. The --add-dir grant bounds the file tools but not Bash, and codex's worktree-full tier bypasses its sandbox outright (reckon/_backends.py). Any worker can therefore delete anything the operator can. The instrument selected its own targets, the same shape as the morning's scancel -u. The remedy is not a better instruction, which is the rule this worker broke. It is an operating-system fence the worker cannot reason its way past.

Proved on this host, 2026-09-23. bwrap (bubblewrap 0.4.1) is installed and unprivileged user namespaces work. Under bwrap --dev-bind / / --ro-bind ~/.claude ~/.claude, rm -rf on a protected file and a write into ~/.claude both fail with Read-only file system, and a write into the repository succeeds. The same holds on the GPFS home.

§1 — Every CLI worker launches inside a filesystem fence

Measure. reckon._backends.launch_plan wraps the worker's argv in bwrap --dev-bind / /, with a --ro-bind for each protected path that exists, followed by a --bind for each of the run's own write roots that falls inside a protected path. The worker's worktree, its run directory, the shared reports and review stores it is fenced to, and the temp directory stay writable. Nothing else under a protected path does. The wrap applies to every CLI dialect, for fresh dispatch, resume and redispatch alike, because all three build their plan here.

Protected set, default. Operator state, credentials and shared records:

  • ~/.claude: coordinator memory, transcripts, settings and skill links. ~/.claude.json is protected with it.
  • ~/.codex: sessions and auth.json.
  • ~/.config/reckon, except the run's own granted roots under crew/runs/<run>, crew/reports and crew/reviews. Live pointers, the ledger inputs and the host flight layer stay read-only.
  • ~/.agents: the global agent guidelines.
  • ~/Code/dotfiles, which also covers every dotfile it links into the home.
  • ~/.ssh, ~/.gitconfig, ~/.config/git, ~/.config/gh and ~/.netrc: credentials and identity.
  • ~/public: the lane and endpoint documents other projects publish.
  • ~/.local/bin: the operator's executables.
  • Every main checkout under ~/Code, except the run's own worktree. A worker writing the main checkout goes live for every session through the editable install. Gates read the shared .venv but do not write it (--no-sync).

Falsifier. The test goes through launch_plan and runs the composed argv, with a stub command in place of the harness. For every protected path class, rm -rf of a sentinel inside a temp stand-in fails and the sentinel survives. A write into each granted root succeeds. A write into the worktree succeeds. The negative control drops the --ro-bind for ~/.claude, and the ~/.claude sentinel must be deleted. The fence must be shown to be the thing that held.

Landed in this section. launch_plan now takes fence (default False) and an injectable fence_home, and composes the worker's argv as bwrap --dev-bind / /, one --ro-bind per existing protected path, a --bind for each write root inside a protected path, then -- and the harness argv. The wrap sits at the one point every dialect and every entry path — dispatch, resume and redispatch — builds its argv, so it cannot be omitted for one of the three; the off-by-default contract is pinned by an exact-argv assertion. Proved by executing the composed argv with a stub in place of the harness: every protected sentinel survives rm -rf, every granted root and the worktree are writable, and the declared negative control (drop the --ro-bind for the ~/.claude stand-in so its sentinel can be deleted) deletes that sentinel. Run unfenced, all 15 sentinels are deleted, so survival is not vacuous. The fence stays off until §2 gives each run its own harness home.

§2 — A worker's own harness state lives in its run

Measure. A read-only ~/.claude would stop the claude harness writing its own transcript and config. So each run gets a harness home under its run directory. CLAUDE_CONFIG_DIR is set to <run_dir>/harness, seeded with the minimum the launcher needs, and for codex CODEX_HOME is set the same way with auth.json bound read-only. A worker's transcript and session files then land in its run directory, and session lookup for crew resume reads them there.

Falsifier. A real clive worker, fenced, completes a one-file node. Its stream carries a session_id, its transcript is under <run_dir>/harness, crew resume of that run continues the same session, and nothing under the real ~/.claude changed. That is checked by a before and after listing of ~/.claude/projects restricted to the run's worktree name. A codex worker does the same with ~/.codex/auth.json unchanged.

§3 — The protected set is declared, and the fence fails closed

Measure. The set is a flight key, protected_paths, in the host layer, with §1's list as the shipped default. A layer may add paths. It removes a default only by naming it under an explicit unprotected_paths, which is recorded on every run it affects. If bwrap is absent or a user namespace cannot be created, dispatch is refused before a worktree exists, and the refusal names the missing capability. The only way through is --no-fence REASON, recorded on the run and its ledger row.

Falsifier. A dispatch with bwrap removed from PATH is refused with the capability named, and the same dispatch with --no-fence launches and records the reason. A fence that disappears silently is worse than none, because it reports a protection that is not there.

§4 — The rule reaches the surfaces agents read

Measure. The worker contract composed into every prompt states that a worker never writes the operator's memory or any path outside its grants, and that the fence enforces this. The A worker can write the coordinator's persistent memory directory passage in the user-global AGENTS.md is updated to say the fence now prevents it. Its remaining advice, to prefer versioned records over private memory, stays.

Falsifier. A grep of the composed worker prompt finds the rule and its reason. The AGENTS.md passage names the fence and this plan.

§ Followups

Wrap the launch plan, then give the harness its own home
