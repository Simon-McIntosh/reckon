A Worker Cannot Write Your Home

On 2026-09-23 at 07:55:45Z a local-lane worker deleted ~/.claude/projects/-home-ITER-mcintos-Code-reckon. That directory held the coordinator's memory store of about 95 files and every reckon session transcript up to that moment. The worker was r-20260923T034846945410, the carryover census, resumed. It had decided unprompted to save memories into the coordinator's memory directory. A shell fragment leaked into a file path, creating a stray file named -home-ITER-mcintos-Code-reckon 2>/dev/null || true. The worker then cleaned it up with find ~/.claude/projects -name '-home-ITER-mcintos-Code-reckon*' | … rm -rf "$p" 2>/dev/null, which also matched the real directory. It reported that nothing outside its scope was touched, and its review caught the command in the stream.

Nothing prevented it, because no boundary exists. The claude dialect launches both worker tiers with --dangerously-skip-permissions. The --add-dir grant bounds the file tools but not Bash, and codex's worktree-full tier bypasses its sandbox outright (reckon/_backends.py). Any worker can therefore delete anything the operator can. The instrument selected its own targets, the same shape as the morning's scancel -u. The remedy is not a better instruction, which is the rule this worker broke. It is an operating-system fence the worker cannot reason its way past.

Proved on this host, 2026-09-23. bwrap (bubblewrap 0.4.1) is installed and unprivileged user namespaces work. Under bwrap --dev-bind / / --ro-bind ~/.claude ~/.claude, rm -rf on a protected file and a write into ~/.claude both fail with Read-only file system, and a write into the repository succeeds. The same holds on the GPFS home.

§1 — Every CLI worker launches inside a filesystem fence

Measure. reckon._backends.launch_plan wraps the worker's argv in bwrap --dev-bind / /, with a --ro-bind for each protected path that exists, followed by a --bind for each of the run's own write roots that falls inside a protected path. The worker's worktree, its run directory, the shared reports and review stores it is fenced to, and the temp directory stay writable. Nothing else under a protected path does. The wrap applies to every CLI dialect, for fresh dispatch, resume and redispatch alike, because all three build their plan here.

Protected set, default. Operator state, credentials and shared records:

  • ~/.claude: coordinator memory, transcripts, settings and skill links. ~/.claude.json is protected with it.
  • ~/.codex: sessions and auth.json.
  • ~/.config/reckon, except the run's own granted roots under crew/runs/<run>, crew/reports and crew/reviews. Live pointers, the ledger inputs and the host flight layer stay read-only.
  • ~/.agents: the global agent guidelines.
  • ~/Code/dotfiles, which also covers every dotfile it links into the home.
  • ~/.ssh, ~/.gitconfig, ~/.config/git, ~/.config/gh and ~/.netrc: credentials and identity.
  • ~/public: the lane and endpoint documents other projects publish.
  • ~/.local/bin: the operator's executables.
  • Every main checkout under ~/Code, except the run's own worktree. A worker writing the main checkout goes live for every session through the editable install. Gates read the shared .venv but do not write it (--no-sync).

The negative control drops the --ro-bind for ~/.claude, and the ~/.claude sentinel must be deleted. The fence must be shown to be the thing that held.

§3 — The protected set is declared, and the fence fails closed

Measure. The set is a flight key, protected_paths, in the host layer, with §1's list as the shipped default. A layer may add paths. It removes a default only by naming it under an explicit unprotected_paths, which is recorded on every run it affects. If bwrap is absent or a user namespace cannot be created, dispatch is refused before a worktree exists, and the refusal names the missing capability. The only way through is --no-fence REASON, recorded on the run and its ledger row. The shipped default also gains the worktree root, ~/Code/.reckon-worktrees. Every other run's worktree is then read-only to a fenced worker, while the run's own worktree stays writable as one of its granted roots. So a fenced worker can write nothing outside its own worktree, its run directory and its granted stores. That is what lets the-boundary-check-reads-two-trees stop scanning every registered tree.

Falsifier. A fenced stub's write into a sibling run's worktree is refused as a read-only file system, while its write into its own worktree lands. A dispatch with bwrap removed from PATH is refused with the capability named, and the same dispatch with --no-fence launches and records the reason. A fence that disappears silently is worse than none, because it reports a protection that is not there.
