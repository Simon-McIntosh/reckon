§1 — The roster serves two needs with one object

Measured, during a sprint run by two coordinators at once. One announced that codex-g, codex-h and sandbox-fix were free, then took two of them; the other lost two dispatches to the collision and had to re-register. Neither did anything the documentation forbids — the execution skill states plainly that members are cheap and that a coordinator raises concurrency by registering more.

The prose is right and the collision happened anyway, which locates the defect in the mechanism. The roster is being asked to serve two needs that want opposite things:

NeedWhat it wantsWhat it is forced to use
Concurrency — N workers now, identity irrelevantanonymitya shared list of names
Continuity — the worker that remembers this attempta stable namethe same shared list

Both coordinators needed the first and were made to shop in the second. Dispatch refuses only on a non-terminal live pointer, so idle is observable while another coordinator is about to use this is not. There is no signal for intent, so collision is the designed outcome rather than bad luck.

Half the mechanism already exists, and the roster has no lifecycle at all. --member is already optional: 34 of 136 recorded runs carried no member and still captured a session_id on the run record. Meanwhile crew member exposes exactly add and list — there is no remove and no reap, so the roster only grows. It stood at 16 members accumulated across three dates, 6 of which had never captured a session.

§2 — Ephemeral by default, named on purpose

Deliverable. A dispatch that names no member provisions its own, scoped to the dispatching session id — which cannot collide, because the session is the namespace. The ephemeral captures its session like any member, so a follow-up inside the same scope still reaches a worker that remembers the attempt. Named members remain, unchanged, for deliberate continuity across sessions.

Reaping is what keeps the roster honest, and the delay is not a tuning knob — it is the continuity window. An ephemeral is reaped when it holds no live pointer and has received no dispatch for the configured interval. Set it too short and the follow-up dispatch that should have reused a warm session gets a cold one; too long and the roster accumulates exactly as it does today.

The property that makes reaping cheap rather than lossy: run records already carry session_id, so removing a roster row does not destroy the worker's context — the committed ledger keeps the handle, and a member can be re-registered against a session found there. Reaping discards an index entry, not the thing it indexes. That is already true of the data model and needs no change to become true.

Done when two concurrent coordinators dispatching without naming members never contend, asserted by a test that runs concurrent dispatches and requires distinct members and zero refusals; a follow-up dispatch inside the reap window reuses the same session id; and an ephemeral idle past the window is gone from member list while its session id is still recoverable from the ledger.

§3 — A node whose measure is execution, routed to a role that cannot execute

Measured on the same sprint. Three suite runs were dispatched with --role review. That role is configured execution_capable: false and resolves to the read-only sandbox tier, under which the shared uv cache is not writable and uv run dies before pytest collects. The runs reported 34 failures and 10 errors, all environmental. The same suite under an execution-capable role at worktree-full reports 1991 passed, 0 failed, 0 errors.

The cost was not the failed runs — it was the diagnosis. The error surfaces as a cache permission problem two runs downstream of the decision that caused it, and reads as infrastructure. It sent one coordinator into the sandbox-tier translation code and produced a confident, wrong explanation before the role configuration was checked.

The seven-property contract validated this node as well-formed, because every property it checks is about the node in isolation. Nothing cross-references the node's stated measure against whether its resolved role can execute anything, so a contradiction between the two is expressible and passes.

Deliverable: dispatch refuses a node whose done-when describes execution when the resolved role declares execution_capable: false, exiting as a not-dispatchable node-contract failure naming both the measure and the role — the same class as any other malformed node, and repaired the same way, by correcting the request.

The detection has to be honest about being a heuristic. A done-when is free text, so this cannot be a proof. The refusal must therefore name what it matched and stay overridable, because a false refusal that cannot be bypassed is worse than the error it prevents. What makes it worth having anyway is the asymmetry: a false refusal costs one corrected flag, while the miss costs a wrong diagnosis of the sandbox.

Done when a node whose measure names running a test suite is refused against an execution_capable: false role with a message naming both, the same node dispatches cleanly against an execution-capable role, and an explicit override is accepted and recorded on the run so a deliberate exception is auditable rather than silent.

§ Decisions

How does a coordinator get a worker when it does not care which one?

Members are documented as cheap and unlimited, yet two coordinators still collided over a shared free list, because dispatch refuses only on a non-terminal pointer and there is no way to signal intent to claim.

Locked by the lead 2026-08-24. Documenting the protocol was tried implicitly and failed: the execution skill already states that members are cheap and that concurrency is raised by registering more, and a coordinator that had read it still drew from a pool it had itself announced as free. A rule with no mechanism behind it is guidance, and this one is contended by construction because intent is invisible between sessions. Scoping an auto-provisioned member to the dispatching session removes the shared resource rather than adding etiquette around it.

What does dispatch do when a node's measure implies execution but its role declares it cannot execute?

A done-when is free text, so matching it against execution intent is a heuristic and will sometimes be wrong in both directions.

Locked 2026-08-24 on the cost asymmetry. A false refusal costs one corrected flag at the moment of dispatch; a miss costs a run that fails for an unrelated-looking reason two steps downstream, and in the measured case produced a confident wrong diagnosis of the sandbox before anyone checked the role. A warning does not help because the failure it predicts is already being read as infrastructure noise. Silent rerouting was rejected outright: it makes the resolved routing differ from the requested routing with nothing in the record saying so, which is the same class of invisible mismatch this plan exists to remove. The override keeps a deliberate exception possible and auditable.

§ Followups

Provision members instead of shopping for them, and refuse a node its role cannot run

Auto-provisioning comes first because it removes a shared mutable resource rather than adding etiquette around one — scope the member to the dispatching session so collision is unrepresentable, and let the reap window double as the continuity window, since a follow-up inside it should still reach a warm session. Reaping is safe because the committed ledger already keeps every run's session id, so removing a roster row discards an index entry rather than the context it points at. Then the execution-fit refusal, which is a heuristic over free text and must therefore name what it matched and stay overridable, because a false refusal that cannot be bypassed is worse than the error it prevents.

The sibling defect was measured three times in the session that fixed the first one, and the third instance changes what §3 should cover. All three are one shape — a node fenced out of a file it structurally requires: tag-field-on-resources fenced from the schema artifact it generates, execution-fit-refusal fenced from reckon/crew.py where dispatch validation lives, and idle-member-reaping fenced against a peer list that was already stale. The workers refused correctly every time; the third was caught only by hand at dry-run. That exposes something auto-provisioning does not fix: it removes contention between coordinators, but a single coordinator fencing its own concurrent nodes off each other's files is unchecked, because the --peer list is supplied by the same coordinator that got the scope wrong and is therefore no independent check. A node's required scope is derivable from the files it is asked to change far more reliably than from a hand-written peer declaration. Recorded here rather than folded, because it widens §3 rather than fitting inside it. Full record: execution evidence.

A mechanical gap found by walking into it twice: crew resume cannot widen a node's write scope. The fence lives in the run record's write_paths; advice is prose delivered to the worker and changes nothing about what it is permitted to touch. So a node blocked on a wrong fence stays blocked no matter how the advice is worded, and the worker is right to keep refusing — its recorded scope is the authority, not the message. The coordinator's natural move on a scope block is exactly the one that does not work. I resumed execution-fit-refusal twice with progressively wider prose while its recorded scope stayed at two paths, burning two turns before reading the worker's own brief, which had already diagnosed it and recommended a serialized re-dispatch owning all four paths. That is what landed. Two candidate repairs, and the second is cheaper: let resume accept a scope change and record it, or have resume refuse when the advice implies paths outside the recorded fence, naming re-dispatch as the remedy. Either removes a silent no-op from the recovery ladder. Recorded here because it is the same family as this plan's other two defects — the tooling accepting an instruction it cannot honour and reporting nothing.
