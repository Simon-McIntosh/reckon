The reader refused it as a probe that cannot fail: “it names nothing outside the worker — no job id, pid, port or path” (reckon/crew/recovery_liveness.py near lines 1003–1008). That is false: the job id is in the argument. _wait_probe_reference_kind (reckon/crew/recovery_wait.py near line 683) splits an argument into words only when the command is one of _WAIT_PROBE_SHELL_COMMANDS (near line 668, bash sh zsh dash ksh), so a python3 -c string is one opaque token. Even split by _wait_probe_shell_words (near line 744), which splits only on whitespace and ; | & ( ), the comma-joined list ['squeue','-h','-j','1306915'],... stays one word, and stripping its edges leaves no word equal to -j.

The run was classified unreadable, whose recovery verb is repair (reckon/crew/recovery_vocabulary.py near line 88), with next action “repair the waiting declaration”. But crew view obligations for the session returned count 0 with unreconciled_runs 1: RECOVERY_CLASSIFICATION_DUTY_KINDS (reckon/crew/obligations.py near line 64) lists only needs-help. The follower delivered nothing, the session sat idle from 11:52Z until the lead asked at about 19:40Z, and the awaited Sirius job ended in TIMEOUT and OOM at 15:17Z unseen. nova-8a resumed the run with a sacct argument-vector probe.

§4 — A run parked on a live scheduler job is never drawn producer-gone

Why. nova-8a reported this on 6 November, on the same run after it was re-parked with a valid probe: ["sacct","-n","-X","-P","-j","1307334","-o","State"]. At 21:28:51 the follower moved it from waiting to halted with “the producer is gone — no process of the run is alive and the probe 'RUNNING' has not changed for 1188s — with no scheduler job alive”, while sacct reported job 1307334 RUNNING for 20 minutes on sirius. _producer_gone_verdict (reckon/crew/recovery_classification.py near line 535) asks the scheduler only when _wait_probe_job_id (near line 487) finds a job id, and that reader recognises one only when the probe's command is squeue. A sacct probe names no job to it, so a value that stays RUNNING, the expected steady state of a long job, reads as a producer gone. It is a second job-id reader beside the one §2 corrects.

Deliverable. _wait_probe_job_id (reckon/crew/recovery_classification.py near line 487) is deleted, and its two callers (near lines 517 and 566) read the job id from §2's reader, which already parses its glued and bare-digit forms. So a sacct probe, an squeue probe and an interpreter probe all name their job, and _scheduler_job_alive asks the scheduler about it. A run whose named job the scheduler still lists keeps waiting, however long its probe value stands still.
