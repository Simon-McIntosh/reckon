§1 — Why: a refused wait left a session idle for eight hours

nova-8a reported this on 6 November. Run r-20261106T084812488886-polygon-near-band-quadrature (nova session 35a66cc6-f4f1-4358-8dbb-99c9333c7249) parked waiting on Slurm job 1306915 with this probe:

wait_probe: ["python3","-c","import subprocess; p=subprocess.run(['squeue','-h','-j','1306915'],...); print('PENDING' if p.stdout.strip() else 'TERMINAL')"]

The reader refused it as a probe that cannot fail: “it names nothing outside the worker — no job id, pid, port or path” (reckon/crew/recovery_liveness.py near lines 1003–1008). That is false: the job id is in the argument. _wait_probe_reference_kind (reckon/crew/recovery_wait.py near line 683) splits an argument into words only when the command is one of _WAIT_PROBE_SHELL_COMMANDS (near line 668, bash sh zsh dash ksh), so a python3 -c string is one opaque token. Even split by _wait_probe_shell_words (near line 744), which splits only on whitespace and ; | & ( ), the comma-joined list ['squeue','-h','-j','1306915'],... stays one word, and stripping its edges leaves no word equal to -j.

The run was classified unreadable, whose recovery verb is repair (reckon/crew/recovery_vocabulary.py near line 88), with next action “repair the waiting declaration”. But crew view obligations for the session returned count 0 with unreconciled_runs 1: RECOVERY_CLASSIFICATION_DUTY_KINDS (reckon/crew/obligations.py near line 64) lists only needs-help. The follower delivered nothing, the session sat idle from 11:52Z until the lead asked at about 19:40Z, and the awaited Sirius job ended in TIMEOUT and OOM at 15:17Z unseen. nova-8a resumed the run with a sacct argument-vector probe.

nova-8a also asked that crew check --manifest refuse the probe when the manifest is written. It already does: audit_manifest (reckon/crew/reports.py near line 2576) runs _wait_declaration_refusal on a waiting manifest. A worker that ran it would have met the same misleading reason, which §2 corrects, so no separate section is needed.

§2 — A job id inside an interpreter's code string is read, or named as unread

Deliverable. _wait_probe_reference_kind splits the code string an interpreter is given with -c (python, python3 and versioned python3.N, perl, ruby, node with -e) on whitespace and on , [ ] ( ) ;, then strips quotes from each word's edges, so the §1 probe yields the words squeue, -h, -j, 1306915 and the flag rule reads the job id. The split is exposed as one function that returns the job id a probe names, so §4 reads job ids through it. A probe it still finds no reference in keeps its refusal, but the refusal then says that the probe runs an interpreter whose code string named no job id, pid, port or path the reader recognises, and names the argument-vector shape (["squeue","-h","-j","<id>"] or a sacct vector) instead of saying the probe names nothing.

Done when a new tests/test_an_interpreter_probe_names_its_job.py shows three things: the §1 probe, verbatim, is accepted as naming job 1306915; ["python3","-c","print('pending')"] is still refused; and that refusal's text names the interpreter and the argument-vector shape. Three negative controls: reading interpreter strings as one token makes the first case refuse; splitting on whitespace alone, as _wait_probe_shell_words does, makes the first case refuse; and restoring the old refusal text fails the third case. The test files importing reckon.crew.recovery_wait or reckon.crew.recovery_liveness add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. Write paths: reckon/crew/recovery_wait.py, reckon/crew/recovery_liveness.py and the new test.

§3 — An unreadable run is a duty of its session

Deliverable. RECOVERY_CLASSIFICATION_DUTY_KINDS in reckon/crew/obligations.py gains an entry keyed by the unreadable classification, the key the map is read by (recovery_classification, near lines 1903 and 1954), so a run classified unreadable with a refused wait declaration is listed among its session's obligations with its next_action and the refusal text, and the follower emits a row for it. A run already owed under another duty kind is not listed twice. exited-unfinished, the other classification whose verb is repair, is out of scope: such a run is already owed as turn-ended-early. This edits the same map as a-reexec-never-orphans-a-dispatch §4, which adds launch-failed, so it waits for that section to land.

§4 — A run parked on a live scheduler job is never drawn producer-gone

Why. nova-8a reported this on 6 November, on the same run after it was re-parked with a valid probe: ["sacct","-n","-X","-P","-j","1307334","-o","State"]. At 21:28:51 the follower moved it from waiting to halted with “the producer is gone — no process of the run is alive and the probe 'RUNNING' has not changed for 1188s — with no scheduler job alive”, while sacct reported job 1307334 RUNNING for 20 minutes on sirius. _producer_gone_verdict (reckon/crew/recovery_classification.py near line 535) asks the scheduler only when _wait_probe_job_id (near line 487) finds a job id, and that reader recognises one only when the probe's command is squeue. A sacct probe names no job to it, so a value that stays RUNNING, the expected steady state of a long job, reads as a producer gone. It is a second job-id reader beside the one §2 corrects.

Deliverable. _wait_probe_job_id reads job ids through the reader §2 exposes, so a sacct probe, an squeue probe and an interpreter probe all name their job, and _scheduler_job_alive asks the scheduler about it. A run whose named job the scheduler still lists keeps waiting, however long its probe value stands still.

Done when a new tests/test_a_run_parked_on_a_live_job_keeps_waiting.py shows three things with the scheduler query stubbed: a waiting run with the §4 sacct probe, no live process and a value unchanged past WAIT_PRODUCER_GONE_SECONDS is not producer-gone while the stub lists job 1307334; the same run is producer-gone when the stub lists no job; and the §1 interpreter probe names job 1306915 to _wait_probe_job_id. Two negative controls: restoring the squeue-only reader makes the first case producer-gone; and skipping the scheduler query makes the second case keep waiting. The test files importing reckon.crew.recovery_classification add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Write paths: reckon/crew/recovery_classification.py and the new test. It reads the reader §2 adds, so it waits for §2.
