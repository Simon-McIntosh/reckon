§1 — Why: a pair reckon reported as controlled had copied its answer

reckon crew shadow re-runs a promoted node at its original base on a second backend, so the two arms can be compared as a matched pair. That is the lead's test of Jev's lane against codex. Reckon records two verdicts on a shadow's ledger row. shadow_controlled, from ledger.shadow_controlled, reads only the recorded configuration: a pair is controlled when nothing but the backend, its model and its launch differ. shadow_contaminated, written at promotion by promotion_scope._shadow_stream_contamination through ledger.shadow_primary_read, records whether the shadow's tool calls read the primary's landed commit or a file that commit changed. A contaminated row is excluded from calibration by ledger.measurement_exclusion_reason, but the two verdicts never meet: pair_shadow_arms in reckon/capabilities.py reports a pair as controlled from configuration alone.

On 2026-10-16 nova ran a clive shadow, r-20261016T165229949973-xpoint-cell-owner, of the promoted codex primary r-20261016T145650209779-xpoint-cell-owner, with no configuration override. Its stream shows three channels to the primary's result:

  • Reckon's records of the primary. 138 references to the primary's run directory under ~/.config/reckon/crew/runs/, and 10 references to its review records under ~/.config/reckon/crew/reviews/nova/, all inside output it read from that run directory rather than files it opened.
  • The project's main checkout. The shadow ran git log --oneline 4e852a31e..HEAD in /home/ITER/mcintos/Code/nova. It then copied the primary's 37 prototype files from that checkout into its own worktree with cp -n. The primary had already landed, so main held its result.
  • Its own name. The shadow's worktree path is shadow-r-20261016T145650209779-xpoint-cell-owner-clive-…, so the primary's run id is in the first line of its prompt.

The shadow's first real commit was chore(equilibrium): adopt the node's existing X-point owner prototype. It then blocked at the decision the primary had reached, quoting the primary's numbers. The configuration predicate called the pair controlled, so outcome evidence would have credited clive with a diagnosis it copied. nova recorded the shadow as correct-refusal and is holding further shadow arms until this plan lands.

nova's row carries both verdicts at once: shadow_contaminated: primary_changed_path_read and shadow_controlled: True. The scan caught the copied files, yet the pair still reads as controlled. The scan also does not look for the primary's run directory, review records or worktree. Those hold the primary's reasoning and its numbers, not its landed files. The fix has two halves. Detection (§2) joins the two verdicts and widens the existing scan to those paths. Prevention (§3, §4) removes the cheap channels: the primary's name and reckon's records of it. The main checkout and git history still hold a landed primary's result. Closing those is a design choice with real costs, held as the decision in §5.

§2 — A shadow's reads of its primary make the pair uncontrolled

Deliverable. The existing contamination scan is widened, and its verdict is joined to the control verdict. No second scanner or record is added.

  • promotion_scope._primary_read_targets also returns the primary's run directory (through runs.run_dir), its review record paths (through review.review_path) and its worktree when its row names one. It takes the primary's ledger row, which _shadow_stream_contamination already looks up from the lineage's primary_run_id. That lookup and this function are the one place a primary's readable paths are resolved, and §4's fence calls the same pair.
  • ledger.shadow_primary_read returns a new reason for each of those kinds: primary_run_directory_read, primary_review_read and primary_worktree_read. They are written to the existing shadow_contaminated field. The scan still runs when the primary cites no commit, because a primary that landed nothing still has a run directory to read.
  • A contaminated row is not controlled. The predicate behind both the stored shadow_controlled field and pair_shadow_arms returns false when shadow_contaminated is set. The paired report names the reason a pair is uncontrolled, whether configuration or contamination with its reason.

Write paths. reckon/ledger.py, reckon/capabilities.py, reckon/crew/promotion_scope.py, tests/test_crew_shadow_contamination.py and one committed fixture, tests/fixtures/shadow_contamination/xpoint-cell-owner-calls.jsonl.

Done when tests/test_crew_shadow_contamination.py shows the following, with tool calls in both stream dialects:

  • A shadow whose calls read the primary's run directory, a primary review record or the primary's worktree gets the matching reason. A call reading only the shadow's own worktree and run home gets none.
  • A row with shadow_contaminated set has shadow_controlled false, and pair_shadow_arms reports the pair uncontrolled with the contamination reason.
  • The existing tests in that file pass unchanged.
  • The committed fixture holds the tool-call records of r-20261016T165229949973-xpoint-cell-owner's stream, copied from its run directory so the control survives crew gc. It still yields primary_changed_path_read, and its run-directory calls yield primary_run_directory_read when scanned on their own.
  • The negative control lets the control predicate ignore shadow_contaminated, and the contaminated-pair assertion must then fail.
  • The test files importing ledger.py, capabilities.py and promotion_scope.py show no added failure against the base revision, and ruff format --check exits 0 on the written paths.

§4 — The fence hides a primary's records from its shadow

Deliverable. When the launched run is a shadow, fence_argv in reckon/_worker_fence.py masks the primary's records. Today fence_argv is composed only by launch_plan in reckon/_backends.py, which receives no lineage, project or ledger. The paths are resolved in the crew layer and handed down. Each caller that launches a run reads the lineage. For a shadow, it looks up the primary's ledger row by the lineage's primary_run_id, as _shadow_stream_contamination does, and passes that row to promotion_scope._primary_read_targets, the function §2 extends. The callers are first launch in reckon/crew/dispatch.py, session launch in reckon/crew/dispatch_sessions.py and resume in reckon/crew/resumption.py. Each passes the resolved paths to launch_plan as a plain sequence of paths to hide, and launch_plan hands them to fence_argv. _backends.py gains no ledger parameter and no crew import. The fence mounts an empty tmpfs over the primary's run directory, and over the primary's worktree when that still exists. It binds /dev/null over each of the primary's review record files present at launch. The masks are composed from the shadow's lineage, so they apply on launch, resume and redispatch alike. Each mask comes before any writable grant that contains it, following the existing ordering rule in fence_argv, and the shadow's own run directory and worktree stay writable.

Write paths. reckon/_worker_fence.py, reckon/_backends.py, reckon/crew/dispatch.py, reckon/crew/dispatch_sessions.py, reckon/crew/resumption.py and tests/test_a_fence_hides_the_primary.py.

Done when a fenced stub launch of a shadow (bwrap on this host) lists the primary's run directory as empty, and reads each of the primary's review records as empty. The same stub can still write its own run directory and worktree. A resume of the shadow composes the same masks as its launch, and a non-shadow launch composes none. The negative control drops the masks for a shadow, and the empty-listing assertion must then fail. The test files importing _worker_fence.py show no added failure against the base revision. ruff format --check is clean on the written paths.

§5 — A paired dispatch launches both arms from one base

Why. §3 and §4 remove the shadow's cheap routes to its primary. A shadow dispatched after its primary has landed can still find the result in the project's main checkout or in git history, because main holds the merge. That is the channel the xpoint-cell-owner shadow copied from. The lead locked shadow-isolation-scope as paired-dispatch: both arms start from one base before either lands, so there is no landed result to find. Masking the main checkout was rejected because git show main:<path> stays open and tools that read the checkout would break. Detection alone was rejected because it spends a run on every breach. crew shadow keeps working for a promoted primary.

Deliverable. reckon crew dispatch gains --pair-backend <backend>. One call dispatches the node twice at one base revision. The primary arm is routed as any dispatch is. The shadow arm runs on the named backend and is configured from the primary arm's resolved agent through _shadow_dispatch_config in reckon/crew/dispatch.py, as crew shadow configures one today. Both run ids are allocated before either arm launches. The shadow arm's record carries the existing shadow lineage, kind: "shadow" with primary_run_id and worktree_component, so §2's scan, the control predicate and pair_shadow_arms read it unchanged. The primary arm's record names its partner as paired_shadow_run_id. Its configuration comparison is built from the primary's live dispatch, not from a committed ledger row, so shadow_source's refusal of an uncommitted primary does not apply.

Each arm's fence hides the other. Neither partner can be read from a store at launch. The primary of a paired dispatch has no ledger row until it is promoted. A shadow lineage publishes no launch pointer (claim_published = not shadow_lineage in dispatch.py), and its record is written only at the end of its own dispatch. So the paired dispatch allocates both run ids, creates both run directories and fixes both worktree paths before either arm launches. It composes each arm's masks from its partner's allocated run id and worktree path, resolved through promotion_scope._primary_read_surfaces, the function §2 added, and passes them to launch_plan as §4 does. A resume or redispatch of either arm composes the same masks from the partner run id its own record names.

Write paths. reckon/crew/dispatch.py, reckon/crew_dispatch_commands.py, reckon/crew/promotion_scope.py and tests/test_a_paired_dispatch_hides_each_arm.py.

Done when a paired dry run reports two arms at one base revision, the shadow arm's lineage naming the primary arm's run id and the primary arm's record naming the shadow's. A fenced stub launch of each arm (bwrap on this host) lists its partner's run directory as empty and can still write its own run directory and worktree. The primary arm's composed masks name the shadow's run directory, and an unpaired dispatch composes none. A dispatch without --pair-backend resolves exactly as it does at base. Negative control: dropping the primary arm's masks makes its empty-listing assertion fail, logged under the run directory. The test files importing reckon/crew/dispatch.py show no added failure id against the base revision. ruff check and ruff format --check add no findings on the changed Python files.

§6 — A paired arm does not land before its partner finishes

Why. §5 starts both arms before either lands, but they finish at different times. If the first arm to finish were promoted, main would hold its result while the second arm was still working, and the second arm could copy it from the main checkout as the xpoint-cell-owner shadow did.

Deliverable. reckon crew complete refuses to promote a paired arm while its partner is non-terminal. The refusal names the partner's run id and phase. It is one _require_* check defined in reckon/crew/promotion_checks.py. It is registered in the lambda list that reckon/crew/promotion.py passes to _require_independently, beside _require_worker_stopped_before_promotion. A run is paired when its lineage is a shadow lineage naming a live primary, or when its record names a paired_shadow_run_id. Once the partner is terminal, either arm promotes as it does today. A shadow of an already-promoted primary, dispatched through crew shadow, is not held.

Residual. Both worktrees share the repository's object store, so an arm could still reach its partner's commits through git. §2's scan reports a read of the partner's worktree or commit as contamination, so such a pair reads as uncontrolled rather than passing silently.

Write paths. reckon/crew/promotion_checks.py, reckon/crew/promotion.py and tests/test_a_paired_arm_waits_for_its_partner.py.

Done when promoting a paired arm whose partner's pointer is working is refused, naming the partner, and nothing is merged. The same promotion succeeds once the partner's pointer is terminal. A shadow of a promoted primary, and an unpaired run, promote unchanged. Negative control: with the check removed from the composed list, the working-partner promotion is not refused and the test fails, logged under the run directory. The test files importing reckon/crew/promotion_checks.py show no added failure id against the base revision. ruff check and ruff format --check add no findings on the changed Python files.

§ Decisions

Beyond detection and hiding reckon's records, how should a shadow be kept from its primary's landed result?

A paired dispatch removes the landed result rather than hiding it: both arms start from one base before either lands, and the fence hides each arm's records and worktree from the other. Masking the checkout leaves git history open and risks breaking tools that read it; detection alone spends a run on every breach. It matches how nova's lead wants deep nodes run.
