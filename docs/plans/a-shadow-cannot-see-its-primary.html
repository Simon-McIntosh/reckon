§1 — Why: a pair reckon reported as controlled had copied its answer

reckon crew shadow re-runs a promoted node at its original base on a second backend, so the two arms can be compared as a matched pair. That is the lead's test of Jev's lane against codex. The pair is reported as controlled by ledger.shadow_controlled, which reads only the shadow's recorded configuration: it is controlled when nothing but the backend, its model and its launch differ. Nothing checks what the shadow could read.

On 2026-10-16 nova ran a clive shadow, r-20261016T165229949973-xpoint-cell-owner, of the promoted codex primary r-20261016T145650209779-xpoint-cell-owner, with no configuration override. Its stream shows three channels to the primary's result:

  • Reckon's records of the primary. 138 references to the primary's run directory under ~/.config/reckon/crew/runs/, and 10 to its review records under ~/.config/reckon/crew/reviews/nova/.
  • The project's main checkout. The shadow ran git log --oneline 4e852a31e..HEAD in /home/ITER/mcintos/Code/nova. It then copied the primary's 37 prototype files from that checkout into its own worktree with cp -n. The primary had already landed, so main held its result.
  • Its own name. The shadow's worktree path is shadow-r-20261016T145650209779-xpoint-cell-owner-clive-…, so the primary's run id is in the first line of its prompt.

The shadow's first real commit was chore(equilibrium): adopt the node's existing X-point owner prototype. It then blocked at the decision the primary had reached, quoting the primary's numbers. The configuration predicate called the pair controlled, so outcome evidence would have credited clive with a diagnosis it copied. nova recorded the shadow as correct-refusal and is holding further shadow arms until this plan lands.

The fix has two halves. Detection (§2) makes every report honest whatever channel a shadow used, so it comes first. Prevention (§3, §4) removes the cheap channels: the primary's name and reckon's records of it. The main checkout and git history still hold a landed primary's result. Closing those is a design choice with real costs, held as the decision in §5.

§2 — A shadow's reads of its primary make the pair uncontrolled

Deliverable. When a shadow run is promoted, reckon scans its stream for tool inputs that name a path outside the shadow's own reach. That means the primary's run directory, any of the primary's review records, the primary's worktree, or the project's main checkout outside its .venv. Reckon records the result on the shadow's ledger row as lineage.isolation. The record holds a verdict, clean or breached, and for a breach each kind of path read with its count and first example. ledger.shadow_controlled returns false unless the isolation verdict is clean. The paired report in reckon/capabilities.py (pair_shadow_arms) names the reason a pair is uncontrolled, whether configuration or isolation. A row with no isolation record reads as isolation unmeasured and is not controlled. That follows the existing rule that lineage with no recorded configuration is not controlled, because a pair whose isolation was never measured cannot be claimed as matched.

The scan reads both stream dialects through the backend module's existing stream reader (reckon/_backends.py), so a codex shadow is scanned like a claude one. The main checkout is the project's repository root as reckon resolves it for dispatch. The instrument is deliberately conservative: the worker contract already says to work only in its own worktree, so any main-checkout read outside .venv breaches isolation. The breach names the path, so a reader can judge a benign one.

Write paths. reckon/ledger.py, reckon/capabilities.py, the shadow branch of promotion in reckon/crew/promotion.py (beside _write_shadow_patch), one new module reckon/crew/shadow_isolation.py holding the scan unless the design review names an owner to extend, and tests/test_a_shadow_reads_nothing_of_its_primary.py.

Done when tests with synthetic streams in both dialects show the following. A shadow whose stream reads only its own worktree and run home is clean and controlled. Reading the primary's run directory, a primary review record, the primary's worktree or the main checkout each gives breached with that kind named, and the pair is not controlled. A read of the main checkout's .venv stays clean. A row without lineage.isolation reports isolation unmeasured and is not controlled. Run on the retained stream of r-20261016T165229949973-xpoint-cell-owner, the scan reports breached, naming the primary's run directory, its review records and the main checkout. That run is the positive control. The negative control makes shadow_controlled ignore isolation, and the breached pair must then read as controlled and fail its test. The test files importing ledger.py, capabilities.py and promotion.py show no added failure against the base revision. ruff format --check is clean on the written paths.

§3 — A shadow's worktree path and prompt do not name its primary

Deliverable. shadow_worktree_session in reckon/crew/routing.py names a new shadow's worktree session from its candidate backend and its recorded unique component, without the primary's run id. Records written before the change still resolve to their existing paths through _shadow_worktree_records, so gc and promotion find old shadow worktrees. Nothing in a shadow's composed prompt names the primary's run id.

Write paths. reckon/crew/routing.py, the shadow branch of reckon/crew/dispatch.py if the component is composed there, and tests/test_a_shadow_worktree_hides_its_primary.py.

Done when a shadow dry run's worktree path and composed prompt contain no occurrence of the primary run id. A ledger row in the old naming, with and without a worktree component, still resolves to its original worktree path. The negative control restores the primary id in the session stem, and the dry-run assertion must then fail. The test files importing routing.py show no added failure against the base revision.

§4 — The fence hides a primary's records from its shadow

Deliverable. When the launched run is a shadow, fence_argv in reckon/_worker_fence.py masks the primary's records. It mounts an empty tmpfs over the primary's run directory, and over the primary's worktree when that still exists. It binds /dev/null over each of the primary's review record files present at launch. The masks are composed from the shadow's lineage, so they apply on launch, resume and redispatch alike. Each mask comes before any writable grant that contains it, following the existing ordering rule in fence_argv, and the shadow's own run directory and worktree stay writable.

Write paths. reckon/_worker_fence.py, the launch composition in reckon/crew/dispatch_launch.py that passes the shadow's lineage to the fence, and tests/test_a_fence_hides_the_primary.py.

Done when a fenced stub launch of a shadow (bwrap on this host) lists the primary's run directory as empty, and reads each of the primary's review records as empty. The same stub can still write its own run directory and worktree. A non-shadow launch composes no masks. The negative control drops the masks for a shadow, and the empty-listing assertion must then fail. The test files importing _worker_fence.py show no added failure against the base revision. ruff format --check is clean on the written paths.

§5 — How far a shadow's isolation reaches beyond reckon's records

§3 and §4 remove the shadow's cheap routes to its primary. A shadow dispatched after its primary has landed can still find the result in the project's main checkout or in git history: the worktree shares the main repository's object store, and main contains the merge. That is the channel the xpoint-cell-owner shadow actually copied from. §2 detects it after the fact and refuses to call the pair controlled, but it does not stop the run from spending its budget on a contaminated attempt. The three ways forward differ in cost and in what they ask of the coordinator. They are held as the decision shadow-isolation-scope. This section stays deferred until it is locked, and is then rewritten as the chosen option's build.

  • Detection only. Keep §2–§4 and accept that a shadow of a landed primary may be breached. This costs nothing more. A breached pair is reported as uncontrolled, but its run is spent.
  • Mask the main checkout. The fence also hides the main checkout's working tree from a shadow, keeping its .venv and .git. That stops the copy nova's shadow made, but not git show main:<path>. It may also break any tool the worker starts that reads the main checkout, such as the reckon MCP server reading plans through the mounts.
  • Launch both arms together. A paired dispatch starts the primary and the shadow from one base at the same time, before either lands, and the fence hides each arm's records and worktree from the other. Nothing has landed for either arm to read. nova's lead asked for paired arms on deep nodes, and nova reports that this suits its workflow. It needs a dispatch-time pairing, because crew shadow today requires a promoted primary to copy the configuration from.

Beyond detection and hiding reckon's records, how should a shadow be kept from its primary's landed result?

Recommended: a paired dispatch removes the landed result rather than hiding it, and it matches how nova's lead wants deep nodes run. Masking the checkout leaves git history open and risks breaking tools that read the checkout. Detection alone keeps every report honest but spends a run on each breach.
