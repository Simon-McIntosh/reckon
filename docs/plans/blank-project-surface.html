§1 — The symptom, and what it rules out

Reported 2026-09-02: the reckon home page loads, and selecting the nova project shows a blank page. Nothing renders — not an error banner, not an empty state, not a partial shell.

Every request the surface makes succeeds. Measured against the running server at 127.0.0.1:8765 on the day of the report:

GET /nova/200—
GET /_discover/nova2001 814 583

GET /nova/state/nova/projection.json404—

The server log records the whole sequence completing: the shell's modules are fetched, the projection.json probe 404s, the loader falls back to index.json and gets it, and discovery returns. Then nothing appears. So the fault is downstream of transport and downstream of parsing, in the client-side render — and the 404 is a documented fallback path, not by itself the failure.

Two properties narrow it further and both must be explained by whatever root cause is proposed. First, it is project-specific: the home page renders, so the shell mounts. Second, nova carries the largest payload of the mounted projects measured that day — 1.81 MB of project state against 1.30 MB for imas-codex and 0.74 MB for reckon — so a data-shape fault and a scale-dependent fault are both live hypotheses, and size alone is not evidence for either.

§2 — Root cause

Identify the exact failing code path: the module, the expression, and the value that reaches it. A render that produces an empty document has a concrete first throw, and that throw is the deliverable — not a plausible story about one.

The repository already carries machinery for evaluating the surface without a live browser: tests/spa_module_eval.py, tests/spa_render_capture.mjs, and tests/spa_browser_harness.py, alongside roughly thirty test_spa_*.py suites. Use them rather than building a parallel harness.

The investigation must state, with evidence: which module throws, on which field of which payload, and why nova reaches it while at least one other mounted project does not. A root cause that does not explain the project-specificity is incomplete.

§3 — Repair

Make the nova project surface render its content. The repair follows the finding from §2 and is scoped to the fault that finding names.

A surface that cannot render its data must not fail silently. Whatever the specific fault, the repaired surface either shows the content or shows a legible failure — a blank document is not an acceptable outcome for any input, because it is indistinguishable from an unreachable server and sends the reader to the wrong diagnosis.

§4 — A blank surface becomes a caught failure

The defect reached a user because nothing in the suite asserts that a project surface renders anything at all. Close that: a check that fails when a mounted project's surface produces an empty render.

Host constraint. Headless-Chrome HTTP navigation is not dependable on this workstation — that is the subject of rendered-evidence-on-this-host, and browser-gated checks here have timed out for reasons unrelated to the code under test. The guard must produce its verdict without depending on a capability this host has not demonstrated, or it will read as red when it is merely unable to run.

The check runs against payload shapes that reproduce the reported failure, so that reverting the §3 repair turns it red. A guard that passes both before and after the fix is not a guard.

§ Decisions

What produces the render verdict in §4?

Settled by the §2 finding: the mechanism must be able to observe the fault that was actually found, and must run on a host whose headless-browser navigation is unproven.
