§1 — What a coordinator must remember, the follower should keep saying

The follower reports each run's state once. That is right for news and wrong for obligations. A run that is blocked, unpromoted, stalled or abandoned needs the coordinator until it is answered, and the one row announcing it scrolls away within minutes. Four coordinators said the same on 2026-09-22, and each compensated by calling the live view filtered to their own session before every decision. imas-efit-e3 counted about fifteen such calls in eight hours and still left three runs unpromoted for between 1h21m and 2h42m.

The trailing figures do not help, because they count the whole project while the rows are the reader's own. nova-37 read 6w·3b·3u at 19:47 and looked for three blocked runs that all belonged to another sprint. The count repair is owned by a-scoped-follower-counts-its-own-session, whose last node passes the session at the follow command's call site. This plan depends on it.

Two open sections of older plans describe the same obligations and move here, because this plan carries their dispatchable specification. The repeated inbox of an-orchestrator-is-bound-by-its-inbox §4 becomes §2, and the wave drain line of crew-observability-truth §13 becomes §3. The age cells that section's inbox work added to the row are removed by a-monitor-row-reads-at-a-glance §4 once the needs-you line carries each run's age beside its name.

Every coordinator also asked for the same two pushes, in nearly the same words. The first is a standing list of their own runs that need them, restated rather than shown once. The second is a line saying their own fleet has stopped working, because a quiet pane after a wave looks the same whether work is running or finished.

§2 — A standing line lists your runs that need you

Add a row kind to the follower, the needs-you line. It lists every run of the owning session whose state is in NEEDS_ACTION in reckon/crew/ticker.py, or is unpromoted, or needs help. Each entry gives the node, the state word and the time the run has held that state, as in needs you: 2 unpromoted pta-adopted-read-cost 1h21m, rail-worktree-uv-env 42m · 1 blocked fsa-repair 5m. The line is plain text and reads fully without colour.

An unpromoted run whose review is already stored is marked reviewed in its entry. imas-ambix-f6 lost the only repairable window this way: promotion deletes the pointer and its captured session, so a review read after promotion can no longer be answered by resuming its author.

Emit the line after any transition that changes the set, and again on a cadence whether or not the set is empty. When nothing needs the coordinator the cadence line reads yours: 4 working · nothing needs you. That makes the cadence line a heartbeat, which imas-ambix-f6 asked for, because a quiet pane must not look the same for a healthy follower and a dead one. The cadence defaults to ten minutes and is set with --remind. The line is composed in Python beside the fleet partition in reckon/crew/recovery.py, so the live MCP view can return the same list. The follower emits it from inside the generator _follow_watch_lines in reckon/cli.py, in its wait pass where _tick() is already called, because that code can yield to the pane. The on_poll hook cannot carry it: the path map in the measurement plan §4 found that _tick discards on_poll's return value, so nothing it produces reaches the reader.

Done when tests/test_follow_needs_you_line.py runs a follower over a fixture holding two sessions. The owning session has one unpromoted and one working run, and the other session has one blocked run. With the cadence set to one second, the needs-you line appears at least twice in three seconds, names the unpromoted run with its age, and never names the other session's blocked run. A second case with no owned run needing action asserts the cadence line still appears and reads that nothing needs the coordinator. An unpromoted run with a stored review record is marked reviewed. The negative control is executed and logged: with the cadence emission removed, the line appears at most once and the first case fails. The live view returns the same list, asserted by comparing the two outputs over the fixture. The write paths are reckon/crew/recovery.py, reckon/cli.py and tests/test_follow_needs_you_line.py.

§3 — A drain line says when your own fleet stops working

When the owning session's working and queued runs reach zero, emit one drain line. It says either that the session's fleet is drained, or that nothing is working and names how many runs still need the coordinator. Emit it once per change into that state, never on a cadence, because the needs-you line already repeats.

Done when a test moves the owning session's last working run to unpromoted and asserts exactly one drain line naming one run that needs the coordinator. A peer session's working run in the same fixture does not prevent the line. Moving the run on to promoted produces exactly one further drain line saying the fleet is drained. The write paths are reckon/cli.py and tests/test_follow_drain_line.py.

§4 — Observing another session is read-only

nova-a9 and nova-37 both found that a follower armed with --observe-session ran the recovery sweep over the observed session's runs. In one case it dispatched a review onto a peer's run from the observing session's runtime. The sweep a follower runs must act only on the owning session's runs. _sweep_lapsed_holds in reckon/cli.py calls sweep in reckon/crew/resumption.py with the project alone; pass the owning session and filter the candidate runs by it. The path map in the measurement plan §4 names the exact lines.

A run whose session has no follower then has no sweeper. That is the decision below, and the implementing node follows its locked choice.

Done when tests/test_follow_sweep_is_session_scoped.py runs a sweep through a follower for one session over a fixture where both that session and an observed session each own one run whose hold has lapsed. Only the owning session's run is resumed, asserted through a stub launcher that records its calls. The negative control is executed and logged: calling the sweep without the session resumes both and the test fails. The write paths are reckon/cli.py, reckon/crew/resumption.py and that test.

§ Decisions

Once a follower sweeps only its own session, who sweeps the runs of a session that has no follower?

The coordinator recommends the project watcher. It already holds the project seat, it is a user service that outlives any session, and the runs of a session that ended still hold scope claims that block every other session's dispatch.

the-monitor-under-measurement#s7

Coordinator recommendation, not yet locked: the project watcher sweeps a session once it has had no live follower for a grace period, records itself as the sweep's writer on every run it acts on, and treats a session whose pointers name another login node as unknown rather than orphaned. The lead asked on 2026-09-22 that this rest on measurement, so the decision stays open behind gate g-afkywiv-sweep-ownership-measured. The grace period is the measured 99th percentile re-arm gap rounded up to five minutes, not the fifteen minutes first proposed. If the measurement finds no unattended sessions and no cross-session sweep actions, the recommendation weakens and the alternative option should be reconsidered.
