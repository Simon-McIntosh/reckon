§1 — Why: ceremony sized for features, applied to every edit

A 12-line fix costs about 35 minutes of worker time and a 20-minute review before promotion, against about 10 minutes inline (s22); one imas-ambix feature that was a 20-minute edit took five implement nodes and five reviews, about 2.5 hours. Writing and committing a followup only so a goal can cite it costs 5–10 minutes each (s23). The median node now takes 44 minutes to complete and 83 to promote, against 9.8 minutes per run in August, and the fleet adds 5.35 record lines for every product line (crew pattern review §4). The survey is clear that the delegation discipline for product code stays — every coordinator would keep the worktree, the gate and the negative control — so the lever is the ceremony around a small node, not whether a small node exists (§10).

§2 — A finding or a followup is a brief

Deliverable. A review finding, or an open followup, dispatches as a brief attached to the plan and section it already belongs to, using the stored-brief carrier that a-worker-can-take-a-brief adds: no new plan text, and no commit-before-dispatch beat. The brief records the finding id so the repair links back to the review that raised it.

Done when a stored review finding dispatches as a repair node with no plan write in between, the promoted row carries the finding id, and the review it came from shows the finding answered.

§3 — A small node records one landing line

Deliverable. A node whose diff is under 50 changed lines, or which changes no product code, writes one landing: line in its manifest — what changed and the measure's figure — and no evidence prose and no figure unless its done-when names one. Promotion carries that line into the plan. The worker prompt says so, and says that data outputs above 300 KB belong in the run directory rather than the repository.

Done when a small-node prompt fixture contains the one-line rule and the size bound, and over a week of small nodes the record-to-product line ratio is at most 1.0 (from 5.35 fleet-wide).

§4 — What a coordinator may commit directly

Deliverable. A declared, closed list of edits a coordinator commits itself, each recorded on the ledger as a coordinator commit: correcting a recorded sha, heading or path; the mechanical union of an HTML or JSON conflict; a manifest path repair; plan and sprint state. Product source and tests are never edited inline, and a .py merge conflict is resolved only in a scratch worktree. This writes down what s23 and s22 already do, and holds the line s21 learned from an outage.

Done when the build skill states the list in one table, and the coordinator-overhead census shows hand-committed worker diffs classified by list entry.

§5 — Exact write paths by default

Deliverable. Dispatch warns on a directory-wide claim over a shared tree such as tests/ and proposes the exact files the brief names; a directory claim stays possible when the coordinator confirms it. The imas-ambix coordinator lost about 30 minutes to its own over-broad tests claim blocking a peer.

Done when a dry-run with a tests claim returns the warning and the proposed files, in a test.

§6 — Measure the small-change path end to end

Deliverable. One week after §2–§5 land, measure the median time from a review finding to the landed repair, for repairs under 50 changed lines.

Done when the figure is recorded with its sample size, against a target of 30 minutes.
