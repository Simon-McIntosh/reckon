§1 — Why: Jev is shown the node's requirement but no evidence it can weigh against it

On 2026-10-16 the lead directed, through the nova coordinator, that coordinators trust Jev and stop routine lane overrides. Jev is to be given the full context, including the orchestrator's own reading of a node's difficulty and openness. It is to balance the node's needs against lane congestion, subscription drawdown and recent throughput per lane and model, and to learn from its previous decisions. The next one or two deep nodes are to run as a matched pair, Jev's lane against codex.

Evidence came from two nova sessions. One covered 64 implement runs on nova's converged-forward-solve plan; the other covered 22 dispatches in nova's S24, and its author has since withdrawn its proposal of a deterministic difficulty floor. Read against the run records and this repository's picker code on 2026-10-16, the evidence locates the defect in what Jev is shown, not in what it is asked:

§2 — The orchestrator's difficulty assessment reaches Jev, and the run records the requirement Jev weighed

Why. A coordinator's reading of a node's difficulty travels only inside --comment prose. Openness already has a structured carrier, --spec-level. Difficulty has none for a brief node, and for a section node the coordinator cannot say that it reads the node as harder or easier than the section declared. The resolved requirement is not stored on the run either, so §3 has nothing to condition on.

Deliverable. reckon crew dispatch accepts a repeatable --assess KEY=VALUE, where KEY is a capability requirement key the capability schema declares (reasoning, verification, risk, context, tool_autonomy). VALUE is validated against that key's declared values, and an undeclared key or value is refused by name. The assessment travels on the pick request and renders as node.orchestrator_assessment beside node.capability. It does not replace the declared capability (decision assessment-beside-declared). The questions' instructions name it as the coordinator's own reading, to be weighed with the declared capability. The run's node_definition records capability as the section routing resolved it, and orchestrator_assessment when one was given. Both are stored on the explicit and fallback routes as well as on a Jev route.

Write paths. reckon/crew_dispatch_commands.py, reckon/crew/dispatch_picker.py, reckon/crew/picker/types.py, reckon/crew/picker/__init__.py, reckon/crew/picker/templates/questions.jinja, reckon/crew/dispatch.py and tests/test_orchestrator_assessment_reaches_jev.py. Extend PickRequest and build_state; add no second request type.

Done when a dry-run dispatch with --assess reasoning=deep --assess risk=critical renders a state whose node.orchestrator_assessment is {"reasoning": "deep", "risk": "critical"} and whose node.capability is the section's declared capability unchanged. --assess risk=extreme and --assess colour=red are each refused, naming the key and the accepted values. A dispatch with no --assess renders no orchestrator_assessment key. A promoted run record built through the ledger's record builder carries node_definition.capability equal to the section routing's capability, on a picker route and on an explicit --backend route. The negative control removes the write to node_definition.capability, and the explicit-route assertion must then fail. The test files importing any written module show no added failure against the base revision.

§3 — Jev's outcome evidence is read at the node's requirement

Why. _candidates_scan counts gate outcomes per lane and model filtered by role and spec level alone, so a deep, critical node is shown the same history as a one-constant fix. That history is shaped by which nodes went where. Jev cannot learn from previous decisions when the decisions it sees are pooled across every difficulty.

Deliverable. Each candidate keeps its existing outcomes counts and gains an outcomes_at_requirement block. The block counts the same gate vocabulary over the rows whose recorded requirement (§2's node_definition.capability reasoning and risk) equals the request's, and carries review_total_median and wall_seconds_median over those rows. Rows that recorded no requirement count under unrecorded. They are never matched by default, so history written before §2 reads as unknown rather than as a match. The figures come from the same single pass over the rows. The glossary gains one entry defining the block, and the instructions tell Jev that these counts are the history at this node's difficulty, not a calibrated ranking.

Write paths. reckon/crew/picker/snapshot.py, reckon/crew/picker/types.py, reckon/crew/picker/prompts.py, reckon/crew/picker/templates/questions.jinja and tests/test_outcomes_at_requirement.py. §4 and §5 also write snapshot.py, so the three run one at a time, §5 first.

Done when a test builds ledger rows for two lanes: lane A passes four standard-reasoning rows and fails two deep-critical rows; lane B fails one standard row and passes three deep-critical rows. A pick request for a deep, critical node shows A's outcomes_at_requirement as 0 passed / 2 failed and B's as 3 passed / 0 failed, with the pooled outcomes unchanged. A row with no recorded requirement is counted under unrecorded only. The rendered state carries the block, and its glossary entry is present. The negative control drops the requirement filter, so both lanes' blocks equal their pooled counts and the assertion on A must fail. The test files importing snapshot.py or prompts.py show no added failure against the base revision. A test patches _candidates_scan to count its calls and finds exactly one per pick, so the new block adds no second pass over the rows.

§4 — A coordinator's move off Jev's pick counts against that pick, not for the lane it landed on

Why. A run that Jev routed to clive and a coordinator then moved to codex is credited to codex as if codex had been chosen for it. Its lineage records the move, and nothing that builds Jev's evidence reads that lineage. Jev therefore never sees that a coordinator disagreed with it, and the lane the moves land on collects outcomes it was never picked for.

Deliverable. A row whose lineage records a lane change away from the backend its picker_selection chose is a move. Its outcome is removed from the receiving candidate's outcomes and outcomes_at_requirement, and counted instead under that candidate's moved_in in the same gate vocabulary. The candidate Jev chose gains moved_off, the number of its picks a coordinator moved away within the window, at the request's requirement when §3's block is present. The glossary defines both. Jev's own pick and probabilities stay on the moved run's picker_selection unchanged.

Write paths. reckon/crew/picker/snapshot.py, reckon/crew/picker/types.py, reckon/crew/picker/prompts.py and tests/test_a_move_counts_against_the_pick.py. This section runs after §3.

Done when a test builds three rows: one Jev-routed clive run that stayed on clive and passed; one run whose picker_selection chose clive, whose lineage moves it to codex with a reason, and which failed; and one codex run that Jev routed there and that passed. The clive candidate reads 1 passed and moved_off 1. The codex candidate reads 1 passed and moved_in 1 failed. A row with a lane change but no picker selection (an explicit route that was later moved) counts under its final lane as today. The negative control ignores lineage, and the codex candidate must then read 1 passed / 1 failed with no moved_in. The test files importing snapshot.py show no added failure against the base revision.

§5 — A candidate's stale flag follows one rule, the one the glossary states

Why. Two readers in one pick judge one reading differently. budget_view marks a group's reading expired once its age passes the flight's evidence_shelf_life_minutes, whatever its source, and the candidate's stale flag follows that. lane_context._budget_block, which feeds the return-time block, marks only a ledger reading stale. With the host shelf life at 5 minutes and the paid-lanes document republished on a similar cadence, a metered lane routinely reads stale beside a local lane that reads served. That is an asymmetry in evidence, not a fact about the lanes. The candidate also carries no budget_source, so Jev cannot see which kind of reading it is being told is stale.

Deliverable. One function judges a reading's staleness from its source. An account-surface reading is never stale by age. A paid-lanes document reading is stale past the shelf life the document publishes (suggested_shelf_life_seconds), and past the flight's shelf life when it publishes none. A ledger reading is stale past the flight's shelf life. The candidate's stale and the return-time block both call that function, and the candidate carries budget_source. The glossary's stale entry states the three cases. Where the ceiling gate acts only on a fresh reading, it keeps acting only on a fresh one under the new rule.

Write paths. reckon/crew/picker/snapshot.py, reckon/crew/picker/lane_context.py, reckon/crew/picker/prompts.py and tests/test_one_staleness_rule.py.

Done when a test builds one document reading 345 s old from a document publishing a 900 s shelf life, under a flight shelf life of 5 minutes. The candidate and the return-time block both read stale: false with budget_source document. The same reading at 1,000 s reads stale in both. A ledger reading at 400 s reads stale in both. An account-surface reading at any age reads fresh in both. The negative control restores the source-blind expiry in budget_view, and the candidate's flag must then disagree with the return-time block at 345 s. The test files importing snapshot.py or lane_context.py show no added failure against the base revision.

§6 — Codex worker time is measured from its rollout receipt

Why. The lead's direction asks Jev to weigh recent throughput per lane and model. A codex run's worker_seconds is the run's wall time on a normal finish and absent on a stalled one. The stream measures take worker time from event timestamps (cached_stream_timestamp_bounds in reckon/_backends.py), and a codex stream's events carry none: none of 83 codex streams under the crew home has a timestamp field. Nova's codex-lane implement runs this month record stream_events on 6 of 108. So codex throughput is either wall time or unknown, while clive's is measured. Codex's own measurement exists elsewhere: the client rollout receipt carries generation_seconds and machine_seconds, which _apply_receipt_to_throughput folds into a live throughput block. No promoted codex row in nova this month carries machine_seconds, so the receipt does not reach the committed record.

Deliverable. At promotion, a codex run whose stream carries no event timestamps takes its worker_seconds from the client rollout receipt's machine_seconds, through the same receipt reader _apply_receipt_to_throughput is fed from. It records worker_seconds_source rollout_receipt, and the promoted throughput block carries the receipt's generation_seconds and machine_seconds. A stalled codex run whose receipt covers it is measured the same way. A run with no readable receipt falls back as today. Claude-format streams are unchanged.

Write paths. reckon/crew/promotion_checks.py, reckon/crew/promotion.py and tests/test_codex_worker_time_is_measured.py. First confirm from a real codex run of this week that its rollout receipt is readable at the moment promotion runs: under a fenced run, the rollout lives in that run's own harness home. Cite that run in the test's docstring. If no real run's receipt is readable at promotion, report blocked with what was found, rather than measuring something else.

Done when a test promotes a fixture codex run whose stream and rollout receipt are copied in shape from a real codex run, with content trimmed. It finds worker_seconds equal to the receipt's machine_seconds and worker_seconds_source rollout_receipt, on a normal finish and on a stalled one. A codex fixture with no receipt still records wall_fallback, and a claude-format fixture still yields its existing figure. The manifest reports the figure the new path gives for one real codex run of this week, beside that run's recorded wall time. The negative control removes the receipt branch, and the codex fixture must then record wall_fallback. The test files importing promotion_checks.py show no added failure against the base revision.

§7 — The outcomes report sets a primary run beside its shadow arm

Why. The lead asked for a matched comparison of Jev's lane against codex on the next deep nodes. reckon crew shadow runs the second arm, and its committed row names its primary in lineage.primary_run_id. The outcomes report excludes shadow rows, so neither the coordinator nor Jev can read the pair as a pair.

Deliverable. reckon crew pick --outcomes gains a paired_arms block. It has one entry per committed shadow row whose primary is committed, giving each arm's lane, model, route mode, gate, review total, wall seconds, worker seconds and worker-seconds source. A shadow whose primary is not committed is listed under unpaired with the missing primary named.

Write paths. reckon/crew/picker/outcomes.py and tests/test_paired_arms_are_reported.py.

Done when a test builds a primary row and a shadow row naming it, plus a shadow row naming a primary absent from the ledger. The report pairs the first two with both arms' figures and lists the third under unpaired. The existing outcome counts, which exclude shadow rows, are unchanged. The negative control drops the lineage join, and the pair must then be absent. The test files importing outcomes.py show no added failure against the base revision.

§ Decisions

Does the orchestrator's difficulty assessment sit beside the section's declared capability in Jev's state, or replace it for the pick?

Jev sees the section's declared capability and the coordinator's assessment side by side and weighs any disagreement; outcome history stays keyed on the declared, reviewed requirement. Chosen by the lead on 2026-10-16.
