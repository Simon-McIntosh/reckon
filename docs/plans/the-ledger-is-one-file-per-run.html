The Ledger Is One File Per Run

Measured 2026-09-23. The run ledger, docs/state/reckon/crew.json, is one file of 14.5 MB and 300,870 lines. It holds 1,429 promoted runs (11 MB; median row 6 KB, largest 65 KB), 391 roster members and 22 holds. ledger.append_run reads all of it, appends one row and writes all of it back, retrying from the top when a concurrent write intervenes. So a promotion's cost grows with history and every session promoting in the project queues on one file. Five crew complete processes from three sessions were observed waiting behind one another for more than ten minutes each. 184 commits touched the file in one day. Session capture writing onto roster members also left it uncommitted under a peer twice in the same day, which blocked every session's member add.

The decision is locked on history-persists-as-detail-washes-out (committed-export-scope, by the lead). Each promoted run is its own committed file, and those files are the record. The SQLite store at ~/.config/reckon/crew/run_store.db, today a shadow nothing reads, becomes an index derived from the files, which can be deleted and rebuilt with no loss. Git stays the durable, distributed transport, and a promotion never rewrites another run. The earlier plan's database-as-store direction is superseded by this one, while its rotation and detail-horizon work stays there.

§1 — A promotion writes one new file and touches no other

Measure. ledger.append_run writes docs/state/<project>/runs/<run_id>.json, holding the same record it appends today, and commits that one path. It never reads or rewrites another run's file. It refuses when a file for that run already exists, so promoting a run twice is still refused. The index is updated after the file commits, and a failed index write never fails the promotion.

Falsifier. Two promotions in two processes started together both land, and neither retries. Each commit's file list names exactly one run file. A third promotion of an existing run id is refused, naming the file. The negative control makes append_run rewrite a shared file, and the two concurrent promotions must then show a retry or a conflict.

§2 — Every reader reads the files, and the index is disposable

Measure. ledger.load and every reader of the run list, including recovery, calibration, the census tools and the MCP views, read the per-run files. Keyed questions go through the index when it exists and fall back to the files when it does not.

Falsifier. Every existing test that reads runs passes against a project holding only per-run files. A reader's answer is identical with the index present, deleted, and rebuilt from the files. The negative control makes a reader ignore the files when the index is absent, and that reader must return nothing.

§3 — The existing ledger is split once, row for row

Measure. A one-time migration writes each row of every mounted project's crew.json runs list to its own file. It moves members to docs/state/<project>/crew/members.json and holds to crew/holds.json, then removes runs from the old file. It runs as its own commit per project, with nothing else in it.

Falsifier. For every mounted project, the row count before equals the file count after, and the canonical JSON of each row equals its file byte for byte. A second run of the migration changes nothing. A dry run prints the counts without writing.

§4 — The roster is a small file that dispatch does not churn

Measure. The roster lives in crew/members.json. Dispatch, observe and promotion never write session fields onto a member. That comes from new-work-gets-a-new-worker §3, and this section depends on it. A roster file changes only on member add or member remove.

Falsifier. Across a dispatch, an observe and a promotion of one run, crew/members.json is byte-identical before and after, while the run's own file carries its session. The negative control restores session capture onto the member, and the roster file must then change.

§ Followups

Write, then read, then split; the roster follows the session fix

§1 and §2 land before §3, so the split finds a writer and every reader already speaking per-run files. §3 is its own commit per project, sequenced when no peer holds uncommitted work in docs/state. §4 waits on new-work-gets-a-new-worker §3. reckon/ledger.py is on every session's promotion path, so each node's gate includes a real promotion through the merged tree before it is merged.
