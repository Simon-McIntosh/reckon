The Ledger Is One File Per Run

Measured 2026-09-23. The run ledger, docs/state/reckon/crew.json, is one file of 14.5 MB and 300,870 lines. It holds 1,429 promoted runs (11 MB; median row 6 KB, largest 65 KB), 391 roster members and 22 holds. ledger.append_run reads all of it, appends one row and writes all of it back, retrying from the top when a concurrent write intervenes. So a promotion's cost grows with history and every session promoting in the project queues on one file. Five crew complete processes from three sessions were observed waiting behind one another for more than ten minutes each. 184 commits touched the file in one day. Session capture writing onto roster members also left it uncommitted under a peer twice in the same day, which blocked every session's member add.

The design follows the lead's choice of per-run files, locked on history-persists-as-detail-washes-out as committed-export-scope. Each promoted run is its own committed file, and those files are the record. The SQLite store at ~/.config/reckon/crew/run_store.db, today a shadow nothing reads, becomes an index: the promotion updates it after the file is written, it is never committed, and when it is missing it is rebuilt from the files. Git stays the durable, distributed transport, and a promotion never rewrites another run. The earlier plan's database-as-store direction is superseded by this one.

What a file holds. A run file holds the complete record the promotion builds today, every field including the wide fields named in run_store.DETAIL_FIELDS. A file written by §1's writer carries no store_write (see §1). A file written by §3's split keeps the row exactly as it was committed, so a historical row that carries store_write keeps it. This plan does not strip detail. Washing detail out once its derived values exist stays with history-persists-as-detail-washes-out's rotation work, which will then act on these files instead of on one shared file. Keeping the full record means §3's split loses nothing and every reader finds the fields it reads today.

Where the files live. Every path below is relative to the state directory that ledger.ledger_path(project) already resolves, through _run_ledger_root and the mount registry, to the project's owning checkout. Written out for reckon, that is docs/state/reckon/. Run files are runs/<run_id>.json, the roster is crew/members.json and holds are crew/holds.json. A run file is never moved, renamed or deleted once committed. Its content changes only when history-persists-as-detail-washes-out's rotation removes detail fields from it.

One serialisation. A single function writes every run file: json.dumps(row, sort_keys=True, indent=2, ensure_ascii=False) plus a trailing newline. §1's writer and §3's split both call it, so every run file is exactly the serialiser's output for its own row, whichever path wrote it.

Order. §2 (readers) lands first, then §1 (writer), then §3 (split), then §4 (roster and holds). Readers go first because between the writer landing and the split, a project holds both old rows in crew.json and new run files. A reader that knew only one of the two would miss runs.

§1 — A promotion writes one new file and touches no other

Measure. ledger.append_run writes runs/<run_id>.json through the one serialiser. It never opens another run's file. The promotion commit that crew complete already makes (promote(<run>): <verdict>) stages that one run file in place of crew.json. append_run itself does not commit. It refuses when its own target path already exists, or while crew.json still holds a runs row with the same id, naming whichever it found. Until §3 has run, the second check scans crew.json's bytes for the run id without building the run list. Only when the id occurs does it parse the document, to confirm that the match is a top-level runs row rather than an id nested inside another run's record. So §1 removes the rewrite and the retry queue, leaves a byte scan, and §3 removes the scan. §3 is queued as soon as §1 merges and runs when no peer holds uncommitted work in docs/state. Once §3 has emptied the old list, the path check is the whole guard.

The index write moves after the file. The run file no longer carries store_write. After the file is written, the promotion updates the index once and reports the outcome in its return payload and output. A failed index write never fails the promotion. failed_store_write_count is replaced by index lag: the number of run files whose id is absent from the index as it stands, computed without rebuilding it. Every failed index write adds one to it, and a rebuild returns it to zero. Where no index exists, the lag is reported as no index, not as a number. So a failed index write stays visible without being written onto the record, and index lag never claims a failure it cannot see: it measures how far the index trails the files, whatever the cause.

Falsifier. Two promotions of different runs, run through append_run in two processes started together against a temporary project, both land. Neither re-reads or rewrites the other's file. Neither repeats its write because of the other. Waiting on git's own index lock is allowed and does not count as a retry. Each promotion commit's file list contains exactly one file under runs/ and does not contain crew.json. A third promotion of an existing run id is refused, naming the file. A failed index write leaves the promotion landed and moves index lag from zero to one, and a rebuild returns it to zero. The negative control makes append_run rewrite one shared file, and the two concurrent promotions must then show a repeated write or a conflict.

How should an integrated gate re-run persist after run rows leave crew.json?

The current function loads the aggregate ledger, patches the matching run, writes the aggregate document, imports the ledger into the index, and commits the ledger path. Code evidence favors preserving the committed report with a per-file route.

The integrated-gate report is the only durable record of whether a promoted run's gate still holds at the merged head, and verify-gate exists to write it. Retiring the in-place update would delete that evidence to save one targeted read and write, which the one serialiser already makes cheap.
