§1 — Why: the reads the coordinator calls first do not answer

On 2026-10-10 the MCP roadmap(project="reckon") and audit(project="reckon") calls each failed with storage-slow at their 30 s deadline (reckon/mcp_deadlines.py:44), and the CLI roadmap took 69 s on a compute node. Every reckon skill starts from those two reads. The read-latency health review (~/.config/reckon/crew/reports/reckon/health-review-1010/health-tool-latency/) profiled them cold and warm, the warm call modelling the resident MCP server:

ReadColdWarmShipped warm median (reckon-reads-answer-in-seconds)
roadmap86.95 s12.45 s1.33 s
audit246.29 s18.10 s0.914 s
discovery118.74 s2.18 s

The figures were taken while seven sibling review nodes shared the CPUs, so they overstate a quiet node; what the profile attributes does not depend on that. Dropping the 104 shipped plans from a copy of the corpus did not make roadmap faster, so plan count is not the cause. Four causes are:

  • A read takes the project's write lock. recover_project_state_transactions (reckon/project_state.py:1951) runs on the read path and takes an exclusive flock on docs/.reckon/locks/reckon-transactions-recovery.lock; in a read-only tree the read dies with EROFS after 42 s of work.
  • The warm roadmap re-walks the covered tree on every call: 8,200 scandir and 5,728 stat calls, 6.5 s of 12.45 s, through _walk_covered (reckon/metadata_index.py:423), although every parse was a memo hit and the index already carries a walk-skip for an unchanged tree (_reuse_covered, line 215) that should have answered the call.
  • The warm audit spends 6.4 s in nine git subprocesses. The git-date answers are already cached in process, keyed on HEAD (_GIT_CREATION_CACHE and _GIT_LAST_MODIFIED_CACHE, reckon/serve.py:1279 and 1316), but finding HEAD is itself an uncached git rev-parse per lookup (_git_head, line 1244).
  • A cold audit parses plans 1,192 times from six call sites. Each reader is memoised, but under its own kind (section_authored at reckon/roadmap.py:184, readiness_state at reckon/serve.py:2067, and read_state_and_text), so one unchanged file is parsed once per kind.

§2 — A read takes no write lock

Deliverable. The read path checks for a transaction journal without a lock and calls recover_project_state_transactions only when one exists. A read in a tree with no journal opens no lock file and creates none. Recovery of an existing journal keeps its exclusive lock.

Done when tests/test_a_read_takes_no_lock.py builds a temporary project, makes its docs/ tree read-only, and asserts a project-state read returns the plans with no OSError and no lock file created; with a journal file present in a writable copy, the read recovers it. The negative control is executed and logged: with the journal check removed, the read-only read raises EROFS and the test fails. Write paths: reckon/project_state.py, tests/test_a_read_takes_no_lock.py.

§3 — A warm roadmap takes the walk-skip the index already has

Deliverable. The metadata index already skips _walk_covered when every recorded directory identity matches (_reuse_covered, reckon/metadata_index.py:215-240; _dir_identity, 490; the persisted dir_stamps, 748 and 783), and the MCP path reaches it through index_rows(..., revalidate=True) (reckon/mcp_views.py:1180). The profile nonetheless shows a warm roadmap entering _walk_covered twice. The node first establishes, with a counting wrapper, which reader on the roadmap path reaches the walk and why _reuse_covered does not answer it (a reader that bypasses index_rows, or a stamp that never matches), records that cause in its manifest, and fixes it in that reader or in metadata_index.py. It adds no second directory-identity map.

Done when tests/test_warm_roadmap_does_not_walk.py runs the roadmap read twice in one process on a temporary project and asserts, through a counting wrapper, that the second call enters _walk_covered zero times; after a plan file is added, the third call walks and reports the new plan. The negative control is executed and logged: with _reuse_covered forced to decline, the second call walks and the test fails. Write paths: reckon/metadata_index.py, reckon/roadmap.py, reckon/mcp_views.py, tests/test_warm_roadmap_does_not_walk.py.

§4 — Git HEAD is resolved once per commit, not once per lookup

Deliverable. The node first confirms, from a warm-audit profile, which of the nine git processes are rev-parse HEAD calls from _git_head (reckon/serve.py:1244) and which are date queries the in-process maps (_GIT_CREATION_CACHE, _GIT_LAST_MODIFIED_CACHE) should have answered. It then memoises _git_head on the identity (mtime and inode) of the repository's HEAD file and the ref file it names, so a warm read with no new commit starts no git process, and, if date queries remain, extends those two maps rather than adding a layer in front of them.

Done when tests/test_git_head_is_resolved_once.py calls the creation and last-modified lookups three times each for one path in a temporary repository and asserts, through a counting wrapper on the subprocess call, no git process after the first pair; after a new commit, the next call starts one and returns the new date. The negative control is executed and logged: with the HEAD memo keyed on nothing, every call starts a process and the test fails. Write paths: reckon/serve.py, tests/test_git_head_is_resolved_once.py.

§8 — One read scans the resource tree once, and warm reads reuse it

Why. §7 found the warm reads' residual time in _scan_resources and iter_resources in reckon/resources.py. Each call walks the tree with rglob("*.html") and identifies every file, hashing its content. The scan's cache (_SCAN_SCOPE) lasts for one read only. Within a read the scan is entered again, four times for roadmap and ten for audit, because callers pass different include_archived, include_legacy and ignore_invalid flags, and each combination is a separate scope key. This section fixes the roadmap and discovery reads, which open a scope. The audit walks and parses by its own route: §12 moves its walk and §13 its parse.

Deliverable. One walk per read, in reckon/resources.py. Inside a resource_scan_scope, the scan runs once with the widest include_archived and include_legacy flags, and each caller's view is filtered from that one result. Every caller reached inside a scope passes ignore_invalid=True, so that flag needs no filtering; a strict caller outside a scope keeps its own scan and its raise. Reusing identification across reads is §10. Memo hits keep their defensive copy. No new public function or option is added.

Done when a test counts walks: one read whose callers ask for different include_archived and include_legacy combinations walks the tree once, and each caller receives exactly the resources its flags select. The test files importing reckon/resources.py show no added failure against base. The negative control keys the scope on each flag combination again, and the one-walk case must then fail. It is logged under the run directory. The figures are re-measured by §6, not by this node. Write paths: reckon/resources.py and tests/test_a_warm_read_scans_the_tree_once.py.

§11 — A cold read parses each plan once

Why. §9 found the cold reads spending 70 to 90% of their time re-parsing plan HTML. A cold roadmap enters read_state 4.6 times per plan file across 176 files. Three readers each build their own BeautifulSoup and run soupsieve selection over it:

  • read_state_and_text_file in reckon/_plan_html.py, the memo the metadata index also reads through;
  • parse_plan and its _parse_plan_uncached in _plan_html.py;

parse_meta is a regex parse that builds no soup, and it is left as it is. §5 made one parse serve the roadmap, discovery and index readers, but these three soup-building kinds remain separate.

Deliverable. Within one read, a plan file's soup is built once and shared by the three soup-building readers, through the file memo §5 introduced, keyed on the file's identity, so each derives its value from that one parse. No reader's output changes. No new public function or option is added.

The audit's own parse route is §13. The three readers' outputs are equal to their outputs before the change for the same corpus. The test files importing the three readers' modules show no added failure against base. The negative control gives one reader its own parse again, and the parse-count case must then fail. It is logged under the run directory. Write paths: reckon/_plan_html.py, reckon/project_state.py, reckon/file_memo.py, reckon/_store.py (only if a caller must pass the shared document) and tests/test_a_cold_read_parses_each_plan_once.py.

§12 — The audit walks through the shared scan

Why. §7 found warm audit at 4.91 s against its 3 s target, with ten tree walks per read. A content review of 2026-10-13 found why §8 and §11 cannot reach it:

  • _audit in reckon/mcp.py walks the tree itself, with sorted(docs_dir.rglob("*.html")) and direct identify_resource calls, outside iter_resources and any scan scope.
  • It parses plans through _audit_plan_state, whose compute path is _plan_html.from_html, a soup builder of its own.

Deliverable. _audit opens one resource_scan_scope around the whole read and takes its resources from iter_resources inside it, so the audit shares §8's one walk and §10's reused identification. Sharing §11's parse in _audit_plan_state is §13. The audit emits invalid-resource-path findings from the ResourceCollision its own loop catches, and a scan with ignore_invalid=True drops those files silently. So the scan inside a scope records each file it drops with its collision reason, and the audit reports its invalid-resource-path findings from that record. The audit's output is therefore unchanged. No new public function or option is added.

Done when a test counts walks for one audit read of a temporary corpus: the tree is walked once. The audit's findings for that corpus are equal to its findings before the change. The test files importing reckon/mcp.py's audit show no added failure against base. The equal-findings case includes a corpus with an invalid resource path. Two negative controls are logged under the run directory, one for each half. The first restores the audit's own rglob walk, and the walk-count case must then fail. The second has the scan drop invalid files without recording them, and the equal-findings case must then fail, because the audit loses its invalid-resource-path finding. This section runs after §8 and §10, because it also writes resources.py. Write paths: reckon/mcp.py, reckon/resources.py (the record of dropped files) and tests/test_the_audit_shares_the_scan.py.
