§1 — Why: the reads the coordinator calls first do not answer

On 2026-10-10 the MCP roadmap(project="reckon") and audit(project="reckon") calls each failed with storage-slow at their 30 s deadline (reckon/mcp_deadlines.py:44), and the CLI roadmap took 69 s on a compute node. Every reckon skill starts from those two reads. The read-latency health review (~/.config/reckon/crew/reports/reckon/health-review-1010/health-tool-latency/) profiled them cold and warm, the warm call modelling the resident MCP server:

ReadColdWarmShipped warm median (reckon-reads-answer-in-seconds)
roadmap86.95 s12.45 s1.33 s
audit246.29 s18.10 s0.914 s
discovery118.74 s2.18 s

The figures were taken while seven sibling review nodes shared the CPUs, so they overstate a quiet node; what the profile attributes does not depend on that. Dropping the 104 shipped plans from a copy of the corpus did not make roadmap faster, so plan count is not the cause. Four causes are:

  • A read takes the project's write lock. recover_project_state_transactions (reckon/project_state.py:1951) runs on the read path and takes an exclusive flock on docs/.reckon/locks/reckon-transactions-recovery.lock; in a read-only tree the read dies with EROFS after 42 s of work.
  • The warm roadmap re-walks the covered tree on every call: 8,200 scandir and 5,728 stat calls, 6.5 s of 12.45 s, through _walk_covered (reckon/metadata_index.py:423), although every parse was a memo hit.
  • The warm audit spends 6.4 s in nine git subprocesses whose answers the persistent git-date cache would have held, but that cache sits under ~/.config/reckon/cache and is skipped when it cannot be written.
  • A cold audit parses plans 1,192 times from six call sites; two of them, read_authored (reckon/roadmap.py:173) and _read_readiness_uncached (reckon/serve.py:2070), read and parse the file themselves instead of through the path-keyed memo, 63 s between them.

§2 — A read takes no write lock

Deliverable. The read path checks for a transaction journal without a lock and calls recover_project_state_transactions only when one exists. A read in a tree with no journal opens no lock file and creates none. Recovery of an existing journal keeps its exclusive lock.

Done when tests/test_a_read_takes_no_lock.py builds a temporary project, makes its docs/ tree read-only, and asserts a project-state read returns the plans with no OSError and no lock file created; with a journal file present in a writable copy, the read recovers it. The negative control is executed and logged: with the journal check removed, the read-only read raises EROFS and the test fails. Write paths: reckon/project_state.py, tests/test_a_read_takes_no_lock.py.

§3 — The covered-tree walk is memoised on the tree's identity

Deliverable. _walk_covered keeps its result in reckon/file_memo.py, keyed on the stat identity (mtime and inode) of each covered directory, so a warm call whose directories have not changed issues one stat per directory and no scandir. A file added, removed or renamed in a covered directory changes that directory's mtime and re-walks it.

Done when tests/test_covered_walk_is_memoised.py walks a temporary tree twice and asserts, by counting calls through a patched os.scandir, that the second walk issues none; after a file is added to one directory, the third walk re-scans that directory alone and returns the new file. The negative control is executed and logged: with the memo key ignoring directory mtime, the added file is missing and the test fails. Write paths: reckon/metadata_index.py, reckon/file_memo.py, tests/test_covered_walk_is_memoised.py.

§4 — A git answer is asked once per process

Deliverable. The git-date lookups behind the audit and roadmap (_run_git and the creation and last-modified caches in reckon/serve.py, lines 1116 to 1468) read through an in-process memo keyed on the repository's HEAD and the path, in front of the persistent cache under ~/.config/reckon/cache/git-creation/ they use today, so a resident server asks git once per revision and a fenced or read-only home still benefits. The persistent cache stays the second level.

Done when tests/test_git_dates_are_asked_once.py calls the lookup three times for one path in a temporary repository with the persistent cache directory read-only and asserts, through a counting wrapper on the subprocess call, one git invocation; after a new commit, the next call asks again. The negative control is executed and logged: with the memo key omitting HEAD, the post-commit call returns the stale date and the test fails. Write paths: reckon/serve.py, tests/test_git_dates_are_asked_once.py.

§5 — Every plan read goes through the parse memo

Deliverable. read_authored (reckon/roadmap.py:173) and _read_readiness_uncached (reckon/serve.py:2070) read through read_state_and_text_file, the path-keyed memo the other readers use, instead of reading and parsing the file themselves. The other four call sites the profile names are checked and routed the same way where they bypass it.

Done when tests/test_every_plan_read_is_memoised.py runs one cold audit of a temporary project holding ten plans and asserts, through a counting wrapper on read_state, at most ten parses, against six per plan before. The negative control is executed and logged: with read_authored restored to its own read, the count exceeds ten and the test fails. The roadmap and audit tests pass, their list built at dispatch from the head tree. Write paths: reckon/roadmap.py, reckon/serve.py, reckon/project_state.py, tests/test_every_plan_read_is_memoised.py. This section runs after §2, which writes project_state.py, and after §4, which writes serve.py.

§6 — The reads are measured inside their deadline

Deliverable. A measurement node, run after §2 to §5 are promoted: the health review's profiler (health-tool-latency/scripts/profile_reads.py) runs roadmap, audit and discovery on the live reckon corpus on a compute node with no other reckon worker on it, cold and warm, five times each, and records the medians.

Done when the log under the run directory records warm medians of at most 2 s for roadmap and 3 s for audit, and a cold roadmap under the 30 s MCP deadline, beside the §1 figures; and roadmap(project="reckon") through the MCP server, restarted on the promoted code, returns without storage-slow. The negative control is the base revision measured the same way in the same session, which must exceed the deadline for the comparison to count. Write paths: the run's own log directory.
