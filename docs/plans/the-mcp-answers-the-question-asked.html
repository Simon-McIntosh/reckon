§1 — Why: the reads are bounded by refusal, so agents read the files instead

the-mcp-answers-within-its-ceiling shipped on 2026-10-07 with the measure "nobody falls back to jq over a saved file". On 2026-10-21, roadmap(project= "power_convertor", view="detail") returned response_over_budget at 141,346 characters for a 17-plan project, and the session asking saved the CLI's 214,910-byte report and read it with Python. The default summary fits, but it drops the ordered ready list and every section-level blocker, which are the parts a coordinator calls it for. roadmap(project="reckon") did not answer at all: it hit storage-slow at the 30 s deadline.

A census of the five power_convertor coordinator transcripts over the three days to 2026-10-21 measures the gap. The script, its input transcripts and its verbatim output are in docs/evidence/archive/the-mcp-answers-the-question-asked-landed.html.

The fallback counts are regex matches on commands, so they are upper bounds. Even halved, they show coordinators reading reckon's state by hand about twice as often as through the MCP; taken as measured, it is four times. The four coordinators named what sent them there. The summary roadmap returns a one-plan critical path and no ordered ready list. crew live rows carry no section, and asking for section is refused as an unknown field. read_plan's section_blocking reports a done section as waiting because it reads the target plan's status. One run reads interrupted in the roadmap and running in crew live. And raw or section reads of the two largest plans come back over budget.

The cause is one design choice applied everywhere. A view serializes the analyser's internal record (a pending_work row has 45 keys, and every dependency ref is a nine-field object repeating the target plan's status), and the transport ceiling is then enforced after the fact by refusing. Views are named after stores (live, ledger, records, runs, scopes) rather than after questions. The crew tool alone takes 57 parameters across 19 read views and 12 actions. The MCP modules are 11,803 lines and the roadmap analyser another 3,798.

This plan inverts that: decide the question, design the smallest answer that settles it, and let the size follow from the design. Work owned elsewhere is not restated here. Read latency is a-read-answers-inside-its-deadline §45 and §46. Verb folding and the single crew tool are the-crew-surface-is-one-tool-and-a-few-verbs, landed, including crew complete --dry-run listing every refusal. Serving current code is every-plan-write-goes-through-edit-plan. The section graph and the brief are computed by a-project-reads-as-one-picture.

§2 — A default read fits by construction

Paging already exists and is extended, not reinvented. paginate() in reckon/mcp_views.py (near line 2406) returns a page with its total and a cursor. roadmap_view already takes cursor and limit and pages wiring_findings (near lines 3471 to 3496). The views that still serialise whole records are brought under paginate() and compact summary rows instead of being refused: roadmap view=detail, read_plan raw and section on large plans, and crew view=findings, which was over budget at limit=20 on 2026-10-21.

The size contract lives where code can enforce it. One table in reckon/mcp_budget.py maps each view to the most characters a default call may return, beside response_ceiling and serialised_characters. The budget module reads it to label an answer, and the test reads it to hold every view to its row. A docstring does not carry it. The runtime ceiling stays as a guard, but a default call that reaches it is a defect in that view.

Surface: one table; no parameter, view or refusal is added.

Done when: a test calls every view of every reckon MCP tool with only its required arguments against a synthetic project of 60 plans and 400 sections. It asserts that each answer is within its row of the table and that none returns response_over_budget. The control is the size failure itself, not the table's absence. On the base commit roadmap view=detail against the same fixture, and against power_convertor (141,346 characters on 2026-10-21), returns response_over_budget; the gate log records that base arm before the change and the in-contract answer after it.

§3 — A row is compact and names its section

A fields request parameter already travels end to end on the crew tool. reckon/mcp.py passes fields and since into serve_crew_view (near lines 2174 and 2189), and project_live_rows in reckon/crew/query.py (near line 174) projects live rows. This section widens that owner rather than adding a vocabulary. Every list view routes its rows through the one projection, with one field vocabulary for the fields views share, and asking a view for a field it lacks is refused naming the fields it has, as live does today.

Rows follow two rules. A reference is a string in the one grammar, [project:]plan[#section][@run|@f-id], never an expanded object, and an empty or null field is omitted. Every row about a run (live, runs, obligations, directory) carries section, taken from _run_row as a-project-reads-as-one-picture §4 extends it. A row-level dependency reports the dependency's own state (the section's declaration, or the followup's status), never the containing plan's status.

Surface: one projection serves every list view. The existing fields parameter reaches more views, and no new parameter is added.

Done when: a fixture run dispatched for P#s4 reads section: "s4" in each of the four views, and fields=["section"] is accepted by all of them. A section ref whose target section is done but whose plan is in progress reads satisfied, with the section's declaration as its state; this is the section_blocking case power_convertor hit, and it fails on the base commit. The serialized power_convertor roadmap shrinks, measured before and after in the gate log.

§4 — One call explains any ref

A new read_plan view, view="why", takes any ref in the grammar and answers within its row of the §2 table with:

  • what the thing is and its state;
  • what it waits on, transitively, each wait with its kind from a-project-reads-as-one-picture §4;
  • what waits on it;
  • which runs and sessions are working on it now, and which paths they hold;
  • its last five events.

This is the question a coordinator otherwise answers by reading a plan, then a pointer file, then messaging a peer. The sessions measured above asked it in every one of their reports.

Surface: one value of read_plan's existing view parameter. No new MCP tool is added, and no CLI verb is added until a caller is named.

Done when: on a fixture where section A waits on B, B is held by a running run, and a followup on A is open, read_plan(view="why", section="A") names the wait on B, B's run and its held path, and the followup, all inside its contract. A ref that does not resolve is refused with the nearest refs that do. On the base commit the view is refused as unknown, and the test fails there.

§5 — One derivation per fact, held by a parity check

Each of four facts already has, or is given, one owner that every surface reads:

  • a run's classification: classify_pointer in reckon/crew/recovery.py, reached through partition_live_runs as a-project-reads-as-one-picture §4 extends it;
  • a section's readiness: _section_scoped_edges and _section_satisfied in reckon/roadmap.py;
  • a plan's progress: the one progress figure already served to every surface;
  • the active sprint: the value derived once, as work-scheduling-surface §10 requires.

The surfaces disagree today where a reader bypasses the owner, as read_plan's section_blocking does with the plan status. Each bypass is replaced by a call to the owner.

Parity is held by the two guards that already exist, extended rather than joined by a third. tests/test_producer_shares_the_classifier_verdict.py already holds one run verdict across producer snapshots and transitions, and gains roadmap, crew live and read_plan as readers. tests/test_surface_parity.py already compares what the SPA renders with what is returned, and gains section readiness, progress and active sprint from the /_discover payload.

Done when: both extended guards run one fixture with runs in every classification and sections in every declaration, and assert that the surfaces agree on all four facts. They are run against the base commit first, and the disagreements found there are listed in the gate log as the negative control.

§7 — A read can ask what changed

since already exists on the crew tool as a time bound: reckon/mcp.py passes it to serve_crew_view, and the velocity view takes since and until. The brief, crew live and the roadmap take the same parameter, with the same meaning, an ISO time, rather than a new opaque cursor. Each response carries observed_at, the time to pass next. A coordinator that polls state today re-reads the whole of it each time; that is the 588 pointer-file reads above.

The change set reads two existing timestamped sources; neither is a new store. A section's declaration and readiness changes come from the plan files' git history, which _plan_history in reckon/velocity.py already reads, each change carrying its commit time. A run's classification changes come from the project producer's transition stream (~/.config/reckon/crew/watch/<project>-<key>.events), whose rows carry their time. Wiring findings are not part of the change set, because they are recomputed on every read and have no history. A since older than the oldest retained transition is answered in full with full: true, never as if nothing had changed.

Surface: the existing since parameter reaches three more reads; no cursor, store or refusal is added.

Done when: on a fixture repository, a read with the observed_at of a previous read returns the one section whose declaration moved in a commit between the two, together with each section waiting on it whose readiness moved because of it (in the fixture, one dependent becomes ready), and exactly the one run whose classification changed in the fixture's transition stream. An unchanged project returns an empty change set with a new observed_at. A since older than the stream's oldest row returns the full answer with full: true. On the base commit the three reads refuse or ignore since, and the test fails there.

§8 — The surface is re-measured from the transcripts

reckon/mcp_census.py already counts MCP connection failures and storage-slow results. It gains three counts: per-tool and per-view outcomes, Bash fallbacks by class (pointer and crew JSON reads, plan HTML parsing, CLI reads), and fallbacks per coordinator-day, all over the same explicit window. Its first run is over §1's window and the five transcripts the evidence record names. That run is the before figure, so the before and after figures come from one instrument; §1's one-off counts stay beside it for comparison, and a difference between the two is explained in the gate log.

Done when: the census's own run over a three-day window that starts after §2 to §7 land shows plan-HTML and pointer-file fallbacks per coordinator session-day down by at least half against the census's own run over §1's window, and fewer than 5 % of roadmap results not ok. A coordinator session-day is one distinct pair of a session id and a calendar day (UTC) on which that session made at least one reckon MCP call or one fallback command; both runs divide by that count. Each window must hold at least ten coordinator session-days. A window with fewer is extended a day at a time, up to seven days, and a window still below ten is recorded as not measurable rather than passed. §1's one-off figures are context only, never the bar. A shortfall is recorded with the transcripts' own account of why each fallback happened, and each cause becomes a section here. Three controls guard the instrument, so a parser that sees nothing cannot pass as a reduction. A synthetic transcript built from records copied out of the after window, carrying known commands of every fallback class, must be counted exactly. The run over §1's window must report a non-zero count for every class §1 found. And the after run must count non-zero reckon MCP calls and non-zero Bash commands in every session-day it divides by; this proves it read that window without requiring the fallbacks the plan exists to remove to persist.

§9 — A newer config does not break an older reader

On 2026-10-21 a landing (c0eb31713, 10:12) added budget.advisory_pace_groups to the flight schema, and the shared config (~/.config/reckon/flight.yaml, a symlink into dotfiles) began to carry it. Every process still running older code then failed every flight read with budget.advisory_pace_groups: Extra inputs are not permitted. The power_convertor coordinator's crew MCP calls failed at 09:51Z, and an edit_plan answer of this session's lost its review_owed to the same error. The cause is one line: every model in reckon/_flight_schema.py is generated with extra = "forbid". A config read by long-running servers, producers and workers of several ages must not let the newest key break the oldest reader.

Reading becomes forward-compatible and authoring stays strict. When flight config is loaded to run, a key the running code does not know is ignored and reported in a flight_unknown_keys warning on crew(view="flight"), never raised. A typo is still caught where the config is written. The existing reckon flight verb (reckon/project_setup_commands.py, near line 415) gains one option, --check, which validates the resolved config strictly and refuses unknown keys as today's loader does; the schema's own test stays strict as well. The generator setting that produces the models changes once, so a regenerated schema keeps the behaviour. Surface: one option on an existing verb and one warning field.

Done when: loading a fixture config carrying a key the schema lacks succeeds, and the key appears in the flight view's warning. reckon flight --check on the same file still refuses it, naming the key. On the base commit the load raises Extra inputs are not permitted, and the test fails there.

§10 — A moved checkout serves every call on current code

The MCP server's stale-code guard (_refuse_when_stale in reckon/mcp.py) answers a call on the current code only after that call has failed. A tool switches to the persistent child interpreter for good only once it has failed once (_SERVE_ON_CURRENT_CODE). So a call that succeeds on stale code returns the old behaviour silently: after a landing, a session's roadmap keeps answering as it did before the commit until something breaks. Two failures also escape the guard. A raised exception while the child is still cold is re-raised raw, without the two stamps or the reconnect remedy a returned failure gets. And a failure embedded in an otherwise successful answer, such as review_owed_error on an edit_plan write, is never seen as a failure.

Once the checkout has moved and is trusted, every call of every tool is served by the warm child, not only those that failed: one import per commit, which the guard already pays. A raised failure while the child is cold returns the same stamped answer as a returned one, naming the reconnect remedy. An answer carrying a configuration or schema error in an embedded field, on a moved checkout, is re-run on current code like a failed one. After this lands, a reconnect is owed only when a tool's signature changes in a way the client cannot survive, which the guard already detects and names.

Done when: with a fixture server whose loaded stamp differs from a trusted checkout, a successful call of a tool that never failed is served by the child, and its answer carries the child's stamp. A raised failure while the child is cold returns a structured answer with both stamps and the remedy, not a raw error. An edit_plan answer whose review_owed_error names a schema error is re-run on current code. On the base commit the first call is served by the stale image and the second raises raw, so the test fails there. An unmoved checkout serves in-process as today; that is the control.
