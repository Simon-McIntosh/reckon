§1 — Why: the reads are bounded by refusal, so agents read the files instead

the-mcp-answers-within-its-ceiling shipped on 2026-10-07 with the measure "nobody falls back to jq over a saved file". On 2026-10-21, roadmap(project= "power_convertor", view="detail") returned response_over_budget at 141,346 characters for a 17-plan project, and the session asking saved the CLI's 214,910-byte report and read it with Python. The default summary fits, but it drops the ordered ready list and every section-level blocker, which are the parts a coordinator calls it for. roadmap(project="reckon") did not answer at all: it hit storage-slow at the 30 s deadline.

A census of the five power_convertor coordinator transcripts over the three days to 2026-10-21 measures the gap. The script, its input transcripts and its verbatim output are in docs/evidence/archive/the-mcp-answers-the-question-asked-landed.html.

The fallback counts are regex matches on commands, so they are upper bounds. Even halved, they show coordinators reading reckon's state by hand about twice as often as through the MCP; taken as measured, it is four times. The four coordinators named what sent them there. The summary roadmap returns a one-plan critical path and no ordered ready list. crew live rows carry no section, and asking for section is refused as an unknown field. read_plan's section_blocking reports a done section as waiting because it reads the target plan's status. One run reads interrupted in the roadmap and running in crew live. And raw or section reads of the two largest plans come back over budget.

The cause is one design choice applied everywhere. A view serializes the analyser's internal record (a pending_work row has 45 keys, and every dependency ref is a nine-field object repeating the target plan's status), and the transport ceiling is then enforced after the fact by refusing. Views are named after stores (live, ledger, records, runs, scopes) rather than after questions. The crew tool alone takes 57 parameters across 19 read views and 12 actions. The MCP modules are 11,803 lines and the roadmap analyser another 3,798.

This plan inverts that: decide the question, design the smallest answer that settles it, and let the size follow from the design. Work owned elsewhere is not restated here. Read latency is a-read-answers-inside-its-deadline §45 and §46. Verb folding and the single crew tool are the-crew-surface-is-one-tool-and-a-few-verbs, landed, including crew complete --dry-run listing every refusal. Serving current code is every-plan-write-goes-through-edit-plan. The section graph and the brief are computed by a-project-reads-as-one-picture.

§2 — A default read fits by construction

Every view declares a size contract in its docstring: the most characters it returns for a call that names no narrowing argument. It meets that contract by its shape, not by a post-hoc check. A list returns its highest-ranked rows up to a declared count, the total, and a cursor for the rest. A nested structure returns its summary line and a ref the caller can expand. The ceiling in mcp_budget stays as a guard, but a default call that trips it is a defect in that view, and the test suite treats it as one.

Done when: a test calls every view of every reckon MCP tool with only its required arguments against a synthetic project of 60 plans and 400 sections, and asserts that each answer is within its declared contract and that none returns response_over_budget. On the base commit at least roadmap view=detail fails it. The same assertion runs against power_convertor, and the result is recorded in the gate log.

§3 — A row is compact and names its section

Rows follow three rules:

  • A reference is a string in the one grammar, [project:]plan[#section][@run|@f-id], never an expanded object.
  • An empty or null field is omitted.
  • Every list view accepts fields with one shared vocabulary for the fields views share.

Every row about a run (live, runs, obligations, directory) carries section. A row-level dependency reports the dependency's own state (the section's declaration, or the followup's status), never the containing plan's status.

Done when: a fixture run dispatched for P#s4 reads section: "s4" in each of the four views, and fields=["section"] is accepted by all of them. A section ref whose target section is done but whose plan is in progress reads satisfied, with the section's declaration as its state; this is the section_blocking case power_convertor hit, and it fails on the base commit. The serialized power_convertor roadmap shrinks, measured before and after in the gate log.

§4 — One call explains any ref

A new read, why(ref), takes any ref in the grammar and answers within 4,000 characters with:

  • what the thing is and its state;
  • what it waits on, transitively, each wait with its kind from a-project-reads-as-one-picture §4;
  • what waits on it;
  • which runs and sessions are working on it now, and which paths they hold;
  • its last five events.

This is the question a coordinator otherwise answers by reading a plan, then a pointer file, then messaging a peer. The sessions measured above asked it in every one of their reports.

Done when: on a fixture where section A waits on B, B is held by a running run, and a followup on A is open, why("A") names the wait on B, B's run and its held path, and the followup, all inside the contract. A ref that does not resolve is refused with the nearest refs that do. The CLI reckon why prints the same answer.

§5 — One derivation per fact, held by a parity check

Three facts are served by more than one derivation today, and the copies disagree. A run's classification is the fourth; a-project-reads-as-one-picture §4 gives it one derivation and a parity test between the roadmap and crew live, and this section extends that same test rather than building a second one. The four facts are:

  • a run's classification;
  • a section's readiness;
  • a plan's progress;
  • the active sprint.

Each gets one owning function, and every surface reads that function: the MCP tools, the CLI and the SPA payload. A parity test compares the surfaces against each other on one fixture, rather than asserting a literal on each side, because literals on both sides drift together without failing.

Done when: the parity test from a-project-reads-as-one-picture §4 is extended to one fixture with runs in every classification and sections in every declaration, and asserts that roadmap, crew live, read_plan and the /_discover payload agree on all four facts. It is run against the base commit first, and the disagreements it finds there are listed in the gate log as the negative control.

§6 — The brief is the default answer

roadmap(project) with no view returns the project brief that a-project-reads-as-one-picture §7 composes: text first, typed rows behind it. The existing summary, detail and raw views remain for callers that name them. Each ranked row in the brief carries the ranking's own reason field; the brief does not call §4's why(ref), so this section does not wait on §4. The reckon-roadmap and reckon-status skills lead with the brief and describe the other views as drill-downs.

Done when: a default roadmap call on the fixture returns the brief within its contract, and a call naming summary is unchanged. The fast path of reckon-roadmap and of reckon-status each names the brief as the first read. A test reads both fast paths and asserts that each names the brief before any other roadmap or read_plan view. On the base commit neither fast path mentions a brief, so the test fails there for both skills.

§7 — A read can ask what changed

The brief, crew live and the roadmap accept a since cursor and return only what changed after it: sections whose declaration or readiness moved, runs that changed classification, and findings that appeared or cleared. Every response carries the cursor for the next call. A coordinator that polls state today re-reads the whole of it each time; that is the 588 pointer-file reads above.

Done when: on a fixture, a read with the cursor from a previous read returns exactly the one section whose declaration moved in between, and an unchanged project returns an empty change set with a new cursor. A cursor the server cannot resolve is refused with cursor-expired and the instruction to read in full, never answered as if nothing had changed.

§8 — The surface is re-measured from the transcripts

reckon/mcp_census.py already counts MCP connection failures and storage-slow results. It gains three counts: per-tool and per-view outcomes, Bash fallbacks by class (pointer and crew JSON reads, plan HTML parsing, CLI reads), and fallbacks per coordinator-day, all over the same explicit window. Its first run is over §1's window and the five transcripts the evidence record names. That run is the before figure, so the before and after figures come from one instrument; §1's one-off counts stay beside it for comparison, and a difference between the two is explained in the gate log.

Done when: the census's own run over a three-day window that starts after §2 to §7 land shows plan-HTML and pointer-file fallbacks per coordinator session-day down by at least half against the census's own run over §1's window, and fewer than 5 % of roadmap results not ok. A coordinator session-day is one distinct pair of a session id and a calendar day (UTC) on which that session made at least one reckon MCP call or one fallback command; both runs divide by that count. §1's one-off figures are context only, never the bar. A shortfall is recorded with the transcripts' own account of why each fallback happened, and each cause becomes a section here. Two controls guard the instrument. A synthetic transcript carrying known commands of every fallback class must be counted exactly, and the census's run over §1's window must report a non-zero count for every class §1 found, so that a parser that sees nothing cannot pass as a reduction.
