§1 — Why this exists

Plans are repo-local and committed, so the record of how a plan was implemented should be too. But a run has two natures that must not share a home: while a worker is in flight its record changes every few seconds and is worthless once the run ends; once complete, the record is durable evidence. Storing either in plan HTML is wrong — every progress tick would bump the server-owned version counter and fight optimistic concurrency.

The three-tier split, and why ~/.config/reckon/state/<project> being a symlink into the repository gives the durable half its properties for free, are recorded in Agent Fleet Orchestration §5.

§2 — Deliverables

The committed ledger. <repo>/docs/state/<project>/crew.json, written beside index.json so it inherits the existing symlink and is server-written and git-committed. It holds the team roster — member id, harness, role, long-lived session id, created date — and one record per completed run: run id, plan, section, node, member, resolved model and effort, dispatched and completed timestamps, commit SHAs, gate verdict, manifest path and outcome. Machine-written JSON, matching index.json's convention; humans tune YAML, machines record JSON.

Ephemeral live pointers. ~/.config/reckon/crew/live/<run-id>.json holding project, repository root, worktree, the backend's machine-readable log path, manifest path, process id and start time. Never committed, and never the sole home of a durable fact.

Promotion. reckon crew complete --run R --gate <verdict> --commit <sha> appends the finished record to the owning repository's ledger and deletes the pointer, in that order, so an interruption leaves a recoverable pointer rather than a lost record. Ledger writes are version-paired the same way index.json writes are, so two orchestrators cannot clobber each other.

Orphan recovery. reckon crew recover classifies every live pointer: process alive and log fresh means running; process dead with a terminal event in the log means completed-but-unpromoted, and it reports the manifest path so the record can be promoted; process dead with no terminal event means genuinely abandoned. It reports and repairs; it never force-removes a worktree, matching the conservative cleanup posture already in the fleet script.

Session reuse through the roster. A member registered with a null session captures its id from the backend's first run and persists it, so subsequent nodes and every escape-hatch resumption reach the same long-lived session. Members are per project so a repository's team is committed with its plans.

Record what makes effort measurable later. Effort is currently an asserted letter with no external referent, and the ledger is what makes it falsifiable — but only if the right fields are captured from the first run. Record per node: dispatch and completion timestamps, the agent configuration that ran it, changed-line counts from the scoped diff, tests added, the gate outcome, and an explicit flag when a node's scope was widened mid-flight. That last field is the one easy to omit and impossible to reconstruct: a scope-changed run measures neither the estimate nor the worker, so it must be excluded from calibration rather than silently averaged in. Report measured worker-time per plan against its declared effort so the spread is visible. Do not change the effort weights here — effort-calibration owns the unit migration and the calibration loops; this plan owns capturing the data they need.

The read tool. One new MCP tool, crew(project, view="flight"|"live"|"ledger"|"summary"), read-only, holding the MCP surface at five tools. It accepts checkout_path and follows the same worktree-routing contract as read_plan, so a worker inside a worktree reads its own checkout's ledger rather than the registered main one.

§3 — Evidence gates

MeasureRequired evidence
Round-trip A dispatch writes a pointer; completion promotes it into the repository ledger and removes the pointer. Recorded before-and-after file listings plus the resulting git status showing the ledger as the only changed state file.
Nothing transient is committed A test asserting no live-pointer path resolves inside any repository working tree, and that an in-flight run leaves the working tree clean apart from the worker's own scoped files.
Interruption is recoverable A killed run leaves a pointer that recover classifies as completed-but-unpromoted, reporting the manifest path; promotion then succeeds. All three classifications exercised by test.
Concurrent writes are safe A test proving two interleaved ledger writes both survive — version-paired, no lost update.
Session reuse A member registered with a null session captures an id on first run, and a second node against that member demonstrably resumes the same session.
Worktree routing crew(..., checkout_path=…) reads the worktree's ledger, not the registered main checkout's. Verified against a real worktree.
Calibration inputs captured A completed run record carrying dispatch and completion timestamps, agent configuration, changed lines, tests added, gate outcome, and the scope-changed flag, with a test proving that flag is settable and defaults false. Measured worker-time per completed plan reported against its declared effort with the observed spread stated.
Suite green Full reckon suite passes; new-test count recorded.

§ Decisions

Where does run state live?

Plans are repo-local and committed; their implementation record arguably should be too. But in-flight state churns too fast to commit.

A repository owns every durable fact about its own implementation, exactly as it owns its plans; reckon holds only the pointer that lets one view aggregate across mounted projects. Plan HTML was rejected because every progress tick would bump the version counter and fight optimistic concurrency.
