§1 — Why: the queue is a tenth of the work the plans declare

On 21 November 2026 the lead saw the local lane drain to no running work while the monitor showed 14 requests waiting, the oldest five days old, and asked whether sessions dispatch at full plan width and whether a batch over a plan is the default.

A count over every mounted project at 20:40Z that day, reading each live plan's section declarations against the live requests:

That is 298 declared sections and 28 requests. Some of the 298 are held for good reason: an unreviewed plan, an open decision, a plan no live session owns. The count does not separate those, and nothing in reckon does either, which is the first gap. The second is that the call which queues a whole plan exists (§2) but nothing makes a session use it, so full width depends on each session remembering a rule. The third is that no dispatch records whether it came as a whole plan, so the question the lead asked cannot be answered from the records.

Of the 18 requests waiting at the same time, 7 waited on sections nobody was building, 3 to 25 days old. Two of those were in the phase that says their upstream can no longer land. The lost-session plan reports an idle wait once and removes a wait it classes as stranded; these two were classed idle, so they were reported and left.

§2 — Dispatching a plan with no section already queues every implementable section

This section is not built here. It was delivered on 14 November 2026 by building-a-plan-queues-all-of-it §2 (commit 74fd70f0e7, covered by tests/test_a_plan_dispatch_queues_every_section.py): reckon crew dispatch --project P --plan SLUG --session S with no section queues one request for every section the plan declares implementable, with its waits. The first draft of this plan proposed it again because its author did not find the earlier plan; the count in §1 stands, and what it shows is that the call exists and is not being used. §4 and §7 are what make it used.

§3 — A request records the width it was dispatched at

The lead asked on 21 November 2026 whether sessions dispatch at full plan width. The question could not be answered from the records: a stored request does not say whether it came from a call naming its whole plan, a batch file or one section.

Deliverable. The request record every dispatch already writes carries one more field, beside the ones that say how the request was launched and admitted, giving the width it was queued at: whole plan, batch file or single section. The live view can be read by that field.

Done when. tests/test_a_request_records_its_dispatch_width.py passes, covering: a request from a whole-plan call, one from a batch file and one from a single-section call each carry their own value on the pointer and on the ledger row written at promotion; and the live view filtered by that field returns exactly the matching requests. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. On main after b3d730c8e1 the first case must fail with the field absent.

§4 — One answer says whether a plan may be queued, and an owner is told when theirs is not

Three things need to know whether a plan's sections may be queued: the owner's obligations, the admit service (§7) and the wait that queues its upstream (§8). The whole-plan dispatch already decides it once, when a coordinator calls it. This section makes that decision one named answer that all three read, so a plan is never queued by one and reported held by another.

Deliverable. One read answers, for a plan, whether its implementable sections may be queued now and, if not, the single reason from a fixed list: its review round is unanswered, an open decision holds it, a coordinator holds it, or its project has switched service queueing off. The whole-plan dispatch refuses and skips by that same answer. A session that the existing plan-coordinator resolution names as a plan's coordinator carries one obligation, of a new kind in the session obligations it already has, for each of its plans that may be queued and has an implementable section with no request; the obligation names the plan, the count and the whole-plan command.

Done when. tests/test_one_answer_says_a_plan_may_be_queued.py passes, covering: a reviewed plan with five implementable sections of which two have requests answers "may be queued" and its coordinator carries one obligation naming three; the command the obligation names, run in the test's own crew home, clears it; a plan with an unanswered review finding, one with an open decision and one under a coordinator's queue hold each answer with that reason and raise no obligation; and the whole-plan dispatch of each of those three is refused with the same reason text the read gives. The read over a fixture of 300 plans completes in under two seconds. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. On main after b3d730c8e1 the first case must fail with no obligation raised.

§5 — Withdrawn: retiring a wait that cannot land is already built

This section is not built. The first draft asked for a blocked wait to be retired. The design review of 21 November 2026 showed that the admit pass already retires a wait it classes as stranded and writes the discard record with its reason. The two six-day-old requests that prompted the section were classed idle, not stranded, because their upstream section sits in a live plan and could still be built; under the lead's decision of the same day that case is resolved by queueing the upstream, which is §8.

§6 — The waiting count is shown by the class each wait already carries

The admit pass already stamps every waiting request with a class: its upstream has a run on its way, nothing is building toward it, or it can never resolve. The pane and the lane document each show one waiting count that adds the classes together, so a drained lane beside 14 waits, the oldest five days old, read as a queue with work in it.

Deliverable. The two places that count waiting requests, the queue view and the lane document, give the count by the recorded class with the age of the oldest in each, and the pane renders what they give. Neither recomputes a wait's class. A lane with no running work and at least one wait that nothing is building toward is drawn as a fault naming the upstream plans.

Done when. tests/test_the_waiting_count_is_shown_by_class.py passes, covering: three waits stamped advancing and two stamped idle give both counts with their oldest ages in the queue view and in the lane document, and the pane row rendered from them shows both; a lane with no running work and two idle waits renders the fault and names their two upstream plans; a queue with only advancing waits renders no fault; and a wait whose stamp is changed between two reads changes the count with no other input. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. On main after b3d730c8e1 the first case must fail with a single waiting count given.

§7 — The admit service queues every plan that may be queued

The lead decided on 21 November 2026 that the queue must fill and drain unattended: reckon itself queues reviewed plans, and a coordinator audits and lands the work without having to start it.

Deliverable. On each pass the admit service calls the existing whole-plan dispatch for every plan that §4's answer says may be queued and that has an implementable section with no request. A request filed this way is recorded as queued by the service, under the plan's coordinator when the existing resolution names a live one and under the service's own identity otherwise. A project switches this off with one flight setting; a coordinator keeps a plan out of it with the queue hold that already exists. This section adds one flight setting and one value of the width field from §3, and no new command or refusal.

Done when. tests/test_the_service_queues_a_plan_that_may_be_queued.py passes, covering: a reviewed plan with three implementable sections and no request has three requests after one pass, each recorded as queued by the service, and no more after a second; a plan §4 answers "may not" gets none; a project with the setting off gets none; a plan with a live coordinator has its requests filed under that session, and one with none has them filed under the service identity and raised by the lost-session decision as any other unowned work is. On the fleet node at the node's head revision, the median duration of ten consecutive passes with the setting on is within two seconds of the median of ten with it off, both read from the service's own pass readings. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. On main after b3d730c8e1 the first case must fail with no request filed.

§8 — A wait on a section nobody is building queues that section

At 20:40Z on 21 November 2026 seven stored requests, 3 to 25 days old, waited on sections that were declared implementable and had no request. The lead decided the same day that such a wait is resolved by queueing its upstream.

Deliverable. When the admit pass stamps a wait as one nothing is building toward, and the upstream section's plan may be queued by §4's answer, the pass queues that section through the same call §7 uses, whatever the project's service setting, and the rule then applies to what that section waits on. Where the plan may not be queued, the wait's idle report gives §4's reason.

Done when. tests/test_an_idle_wait_queues_its_upstream.py passes, covering: a request waiting on an unqueued implementable section has that section queued after one pass and is released once it lands; a chain of three such sections is queued to its root in one pass; an upstream in a plan with an unanswered review is not queued and the waiter's idle report gives that reason in the words §4's read gives; and a wait shaped as the two imas-codex requests of 15 November (phase blocked on an upstream nobody is building, in a live plan) has its upstream queued. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. On main after b3d730c8e1 the first case must fail with the upstream still unqueued after the pass.

§9 — A session takes on an unowned plan only inside a sprint it works in

The lead ruled on 21 November 2026 that unowned plans are taken on, but not as a free-for-all: a session takes one only within the sprints in which it already coordinates a plan, and the other live sessions in the repository are told. A plan's coordinator is already derived from who dispatched it, so taking a plan on is dispatching it; no second ownership record is added.

Deliverable. A whole-plan dispatch by a session of a plan that the existing resolution gives no live coordinator is accepted only when the plan's sprint is one in which that session already coordinates a plan, and is otherwise refused naming the sprint. When it is accepted, every other live session in the project is shown one row naming the plan and the session that took it. A whole-plan dispatch of a plan with a live coordinator behaves as it does today. This section adds one refusal and one row, and no new command or record.

Done when. tests/test_a_plan_is_taken_on_within_a_shared_sprint.py passes, covering: a session coordinating a plan in a sprint dispatches an unowned plan of that sprint, its requests are queued, the resolution then names that session as the plan's coordinator, and a second live session in the project receives the row; the same session's dispatch of an unowned plan in a sprint it coordinates nothing in is refused naming that sprint and queues nothing; and a dispatch by the service identity (§7) is not subject to the rule. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. On main after b3d730c8e1 the second case must fail with the plan's sections queued.
