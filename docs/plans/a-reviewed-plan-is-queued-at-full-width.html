On 21 November 2026 the lead saw the local lane drain to no running work while the monitor showed 14 requests waiting, the oldest five days old, and asked whether sessions dispatch at full plan width and whether a batch over a plan is the default.

That is 298 declared sections and 28 requests. Some of the 298 are held for good reason: an unreviewed plan, an open decision, a plan no live session owns. The count does not separate those, and nothing in reckon does either, which is the first gap. The second is that crew dispatch queues one section unless a coordinator writes a batch file, so full width depends on each session remembering a rule. The third is that no dispatch records whether it came as a whole plan, so the question the lead asked cannot be answered from the records.

Of the 18 requests waiting at the same time, 7 waited on sections nobody was building, 3 to 25 days old. Two of those were in the phase that says their upstream can no longer land. The lost-session plan reports an idle wait once and removes a wait it classes as stranded; these two were classed idle, so they were reported and left.

§2 — Dispatching a plan with no section queues every implementable section

Deliverable. A dispatch that names a plan and no section queues one request for every section of that plan declared implementable that has no live request, in one call. Each request takes its goal, write paths, waits and negative control from its section. A section that cannot be queued is refused by name with its reason and does not stop the rest. A dispatch that names a section behaves as it does today.

Done when. tests/test_a_plan_dispatch_queues_every_implementable_section.py passes, covering: a plan with four implementable sections, one of which already has a live request, queues exactly the other three; a section whose declared wait has not landed is stored awaiting its upstream and not launched; a section with no done-when is refused naming that section while the others are queued; a second identical call queues nothing and returns the existing requests; and a call naming one section queues that section alone. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line. The tests importing the dispatch command module add no failure against the base on all_debug.

Negative control. On main after 130892970e the first case must fail with the call refused for want of a section.

§3 — A request records the width it was dispatched at

Deliverable. Every stored request records whether it was queued by a call that named its whole plan, a batch file or a single section, and the crew view of live work can be read by that field. The figure the lead asked for, how many requests of each kind each session made in a period, is one read.

Done when. tests/test_a_request_records_its_dispatch_width.py passes, covering: a request from a whole-plan call, one from a batch file and one from a single-section call each carry their own value on the pointer and on the ledger row written at promotion; and the live view filtered by that field returns exactly the matching requests. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. On main after 130892970e the first case must fail with the field absent.

§4 — A reviewed plan with unqueued sections is an obligation on its owner

Deliverable. A session that owns a plan whose review round is answered, with at least one section declared implementable and no live request for it, carries one obligation per such plan. The obligation names the plan, the count of unqueued sections and the single command that queues them. A plan with an unanswered review, an open decision holding its sections, or no owning live session raises nothing on that session and is listed, with its reason, in the project's read of unqueued work.

Done when. tests/test_an_unqueued_reviewed_plan_is_an_obligation.py passes, covering: an owned, reviewed plan with three unqueued implementable sections raises one obligation naming three and the command, and the command run in the test's own crew home clears it; a plan whose newest review has an unanswered finding raises none and is listed as awaiting its review; a plan with an open decision is listed as held by that decision; a plan owned by no live session is listed as unowned; and a plan every one of whose implementable sections has a request raises none. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line. The read over a fixture of 300 plans completes in under two seconds.

Negative control. On main after 130892970e the first case must fail with no obligation raised.

§5 — A request whose upstream can no longer land is retired

At 20:40Z on 21 November 2026 requests r-20261115T224010678540-iter-facility-protected-backup and r-20261115T224009612484-plant-signal-search-and-read had sat for 5.9 days in the phase that says their upstream can no longer land, each with the detail "nobody is building" their upstream section. The lead decided on 20 November that a wait which cannot resolve is removed. These were classed idle, so the pass reported them once and left them.

Deliverable. A stored request in the phase that says its upstream can no longer land is retired by the admit pass, with a discard record naming the upstream and why it cannot land, unless a coordinator holds the request. A request waiting on a section nobody is building, whose upstream could still land, keeps the idle report it has today.

Done when. tests/test_a_blocked_wait_is_retired.py passes, covering: a request shaped as the two above is retired on the next pass and its discard record names its upstream; the same request under a coordinator's queue hold is kept; and a request whose upstream is declared implementable with no request is kept and reported idle once. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line.

Negative control. On main after 130892970e the first case must fail with the request still stored after the pass.

§6 — The waiting figure separates waits that are advancing from waits nothing is building toward

Deliverable. Wherever the monitor and the crew views give a count of waiting requests, they give two: those whose upstream has a run on its way, and those nothing is building toward, with the age of the oldest in each. A lane with no running work and a non-zero second count draws that count as a fault, naming the plans to dispatch.

Done when. tests/test_the_waiting_figure_is_split.py passes, covering: a queue of three advancing waits and two that nothing builds toward renders both counts with their oldest ages in the pane row and in the live view; a lane with no running work and two such waits renders the fault and names the two upstream plans; and a queue with only advancing waits renders no fault. Each arm's log sits under the run directory and carries its revision, its literal command and a closing EXIT= line. The rendered row is read through the pane's own renderer, not from its inputs.

Negative control. On main after 130892970e the first case must fail with a single waiting count rendered.
