A worker knows it is on compute

Since 2026-09-24 the reckon fleet has run as a SLURM job on a compute node. Nothing in reckon/ knows it: the package does not reference a single SLURM_ variable. Every compute-node rule lives in prose that workers must remember. Workers have already broken each rule at least once.

§2 — One probe answers "am I inside the allocation"

A new module, reckon/host.py, exposes host_facts(). It returns the following, each with the source it was read from:

  • in_allocation: true only when /proc/self/cgroup names the job's cgroup. The environment alone is not enough.
  • job_id
  • step_id
  • node
  • the filesystem type of /tmp and of the home directory
  • whether /tmp is node-local

When SLURM_JOB_ID is present but the cgroup does not name the job, the probe reports in_allocation: false with the reason environment-inherited-outside-the-job-cgroup. The module reads files and calls statfs only. It runs no scheduler command, so it costs nothing on the login node.

Reuse, not a third reader. reckon/crew/summary.py already finds the process's own cgroup: SELF_CGROUP_PATH, LOGIN_CGROUP_ROOT, _user_slice_dir and read_login_slice. reckon/crew/placement.py already has occupying_the_reservation, which answers whether the process is inside the held job. host_facts() composes those two rather than parsing /proc/self/cgroup again. placement.py is claimed by S21, so this node reads it but does not edit it. The S21 coordinator pointed out this reuse on 2026-09-24.

Done when:

  • Tests feed fixture cgroup files and a stubbed statfs. They assert the four cases: inside the job cgroup, environment-only, no SLURM at all, and a GPFS home beside an xfs /tmp.
  • The environment-only case reads false. This is the negative control, and the test is observed to fail when the cgroup check is replaced by the environment check.
  • One recorded call on clu-2058 inside job 1277272 reads in_allocation: true.
  • No test reads the real /proc or real filesystems.

§3 — A nested launch is refused where it would fan out

This section adds reckon/nested_launch.py, plus thin shims named srun, sbatch and salloc under reckon/host_shims/. Placed first on a worker's PATH, a shim behaves as follows:

  • Inside the allocation (per §2), it refuses with exit status 97. The message names the job and node, says the command should run directly, and names the one discharge: RECKON_ALLOW_NESTED_LAUNCH=1, together with --overlap --ntasks=1 for srun.
  • Outside the allocation, it execs the real binary with the argv unchanged. The real binary is found on PATH after the shim directory is removed.

The shim never launches anything itself and never guesses a corrected command line.

An explicit single-task step always passes. Some work deliberately runs a step into the held fleet job. For example, the imas-ambix fleet-view probes run srun --overlap --jobid=<fleet job> from the login node. So an srun whose argv carries --overlap together with either an explicit --jobid or --ntasks=1 (or -n 1) execs the real binary unchanged, even inside the allocation. Only the implicit form, which inherits the job's task count, is refused. The login node is never inside the allocation, so nothing launched from it is refused. The shims reach only a worker's PATH (§4). Nothing here changes the system srun.

Done when:

  • Tests install a fake real srun that records its argv and assert three cases:
    • inside the allocation, the refusal happens with status 97 and the fake is never invoked;
    • outside it, the fake is invoked with identical argv;
    • with the override set, the fake is invoked.
  • Removing the in-allocation check makes the refusal test fail. That failure is observed and its log is recorded.
  • sbatch and salloc are covered by one parametrised case each.
  • Inside the allocation, srun --overlap --jobid=<id> true and srun --overlap -n 1 true each invoke the fake with identical argv, while plain srun true is refused.

§4 — Workers receive the shim and the facts

Dispatch should prepend reckon/host_shims to every worker's PATH when the dispatching process is inside an allocation. The worker contract should state the host facts in one line: the node, the job, that /tmp is node-local, and that logs a later reader needs belong on GPFS. This way the rule reaches every backend, not only the local lane.

Trigger: this section is deferred until no live run claims reckon/crew/dispatch.py or reckon/crew/prompts.py. Today the S21 coordinator claims the first, and the S22 coordinator's next wave claims the second. The contract wording is shared with followup f-tllitd-worker-turn-endings on the-local-lane-is-the-default, and is landed with its owner rather than beside it.

Done when: a dispatch test inside a fixture allocation shows the shim directory first on the worker's PATH and the host line in the composed prompt. The same test outside an allocation shows neither.

§5 — The suite carries its own bounds

pyproject.toml should declare pytest-timeout and pytest-xdist as development dependencies, with a default per-test timeout of 300 s in the pytest configuration. Then:

  • A test that hangs fails with a timeout instead of stalling the run.
  • -n gives each worker its own basetemp.

No test file changes in this section. The suite-repair plan owns the tests themselves.

Done when:

  • uv.lock is updated beside pyproject.toml.
  • A throwaway test outside tests/ that sleeps 10 s fails with a timeout under -o timeout=2. The recorded run shows it.
  • pytest -n 4 tests/test_doccheck.py passes, and that run is recorded too.
  • git diff --stat names only pyproject.toml and uv.lock.
