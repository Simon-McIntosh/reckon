§1 — Why: a run promoted as landed whose code was not on main

On 6 November every coordinator landing printed, after its merge had reached origin/main, the refusal “the reviewed head landed and was pushed, but the worktree was withheld: its HEAD is not reachable from the integration revision, so removing it would destroy the only copy of that commit” (reckon/crew_run_commands.py near lines 3380–3389, with the reason from reckon/crew/gc.py near line 97). The admit service's lander hit the same refusal at 17:24:38Z for run r-20261106T140731148709 after its head 11f880b126 had been merged at 17:21:15Z (43035e72bd). The merge and push were confirmed each time; only the release's judgement of the worktree is wrong, so every landed run leaves its worktree behind for crew gc and every landing exits 1.

A first reading of that incident blamed the lander for not merging. It was wrong: the coordinator's own merge landed the head while the lander was measuring its candidate (17:19:33–17:24:16Z), and the lander's refusal is the post-merge release refusal. §2 and §4, written on that reading, are descoped.

§2 — A promotion with --land ends with the head on the remote, or says it did not

Deliverable. The worker first reproduces, from the run's landing.json and the --land path in reckon/crew_run_commands.py, why the land step left 11f880b126 unmerged while the promote and release commits were written, and names the cause in the manifest. Then --land is made to end in one of two states: the reviewed head is an ancestor of the remote branch, checked by reading the remote after the push, or the command exits non-zero naming the step that failed and the commits left unpushed. Promote and release commits are never left on the local branch without a push attempt that is reported. A --land killed after it has pushed its promote and release commits and before its merge is not left looking landed: either the promotion record is written only after the merge reaches the remote, or the next landing pass finds a promoted run whose head is not on the remote branch and finishes the merge.

Done when a new tests/test_a_landing_is_on_main_when_it_says_so.py shows three things with a temporary repository and a bare remote: a successful --land leaves the reviewed head an ancestor of the remote branch; a land step whose merge is forced to fail exits non-zero naming the merge step and leaves no unreported local commits; a push forced to fail exits non-zero naming the unpushed commits; and a --land killed between its promotion and its merge ends, after the next landing pass, with the reviewed head an ancestor of the remote branch. Three negative controls, one per case: skipping the merge after promotion makes the first case's head absent from the remote; swallowing the merge failure makes the second case exit zero; swallowing the push failure makes the third case exit zero; and leaving a killed landing unfinished makes the fourth case's head absent from the remote. §5 — A plain complete refuses a head that is not on the primary branch

Why. nova-39 and nova-8a reported on 8 November, relayed by reckon-0f, that a plain crew complete (without --land) promotes a run as passed without checking that its head is on the primary branch. In nova-8a's case crew merge --run had been refused; crew complete still promoted, then deleted the live pointer, which left crew merge --run unable to find the run. The ledger then reads landed work that main does not carry, the state §2 exists to prevent.

Deliverable. A plain crew complete --gate passed on an implementation run, that is a run for which _is_review_run (reckon/crew/recovery_review_delivery.py, re-exported from reckon/crew/recovery.py near line 198) is false, whose reviewed head is not on the remote primary branch refuses, naming the head and the branch, and leaves the pointer and ledger untouched. The remote is read through its owner, reckon/crew/merge.py: _remote_head (near lines 614–621) already reads what the remote branch carries with one git ls-remote, and _is_ancestor already answers ancestry; the port-443 retry compute nodes need (_port22_refused, _port443_env) lives today only in _push_and_confirm (near lines 670–686), so §5 extends _remote_head, and the fetch it adds, to retry over that route the same way. §5 adds one function to merge.py that fetches the remote head's commit over that same route when it is not present locally and answers, through _is_ancestor, whether a head is on it; an unreachable remote and a missing branch are distinct answers. It is not a fifth ancestry convention: it calls _is_ancestor. The plain-complete path in reckon/crew_run_commands.py calls it, and §7 calls the same function. An unreachable remote or a missing branch refuses and names that cause. A head fast-forwarded on local main but not pushed is refused by the ancestry answer against the remote head. A landing measure runs on a compute partition

Why. On 10 November at 19:00Z the fleet node 98dci4-clu-2023 had a load average of 139 at 87% user CPU. Eleven nova processes running about ten cores were pytest workers of nova's equilibrium suite (tests/test_warmup_finite_admission.py, tests/equilibrium/test_solve_vertical_pin.py and others), started in a /tmp/reckon-crew-scratch/landing-base-* tree whose parent was reckon's own admit service (crew admit --lane clive). The landing measure (reckon/crew/landing_measure.measure_run) runs every arm, at base, at head and its repeats, as a plain subprocess on the fleet node, and the lander wraps its crew step in srun --overlap inside the fleet job (queue_landing._crew_step). So a project's heavy suite competes for the fleet allocation's 28 cores with every orchestrator and worker. The workstation rule is that heavy work runs on a SLURM partition: all_debug (1 h limit, 14 idle nodes at the time) or rigel (no limit, 66 idle).

Deliverable. A landing measure whose project declares a measurement partition in its flight config runs each arm as its own SLURM job on that partition (srun --partition=<p> --time=<bound>, not --overlap in the fleet job). The arm builds its tree on the job's node from the revision (git worktree or git archive into that node's /tmp), because the fleet node's scratch is node-local. It writes its log to the run directory on GPFS and removes its tree on exit. A project with no partition declared keeps today's in-place behaviour, recorded on the measurement as such. Reckon, nova and every other project whose suite is heavy declare all_debug, with rigel as the fallback for an arm whose bound exceeds an hour.

Done when a new tests/test_a_landing_measure_runs_on_its_partition.py shows, with the runner and srun patched to record their argv: a measure for a project whose flight declares all_debug launches every arm through srun naming that partition and a time bound, never --overlap; each arm's command builds its tree from the named revision and writes its log under the run directory; an arm whose bound exceeds an hour names rigel; and a project with no partition declared runs in place, with the measurement recording that.
