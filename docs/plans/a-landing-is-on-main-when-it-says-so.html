§1 — Why: a run promoted as landed whose code was not on main

On 6 November every coordinator landing printed, after its merge had reached origin/main, the refusal “the reviewed head landed and was pushed, but the worktree was withheld: its HEAD is not reachable from the integration revision, so removing it would destroy the only copy of that commit” (reckon/crew_run_commands.py near lines 3380–3389, with the reason from reckon/crew/gc.py near line 97). The admit service's lander hit the same refusal at 17:24:38Z for run r-20261106T140731148709 after its head 11f880b126 had been merged at 17:21:15Z (43035e72bd). The merge and push were confirmed each time; only the release's judgement of the worktree is wrong, so every landed run leaves its worktree behind for crew gc and every landing exits 1.

A first reading of that incident blamed the lander for not merging. It was wrong: the coordinator's own merge landed the head while the lander was measuring its candidate (17:19:33–17:24:16Z), and the lander's refusal is the post-merge release refusal. §2 and §4, written on that reading, are descoped.

§2 — A promotion with --land ends with the head on the remote, or says it did not

Deliverable. The worker first reproduces, from the run's landing.json and the --land path in reckon/crew_run_commands.py, why the land step left 11f880b126 unmerged while the promote and release commits were written, and names the cause in the manifest. Then --land is made to end in one of two states: the reviewed head is an ancestor of the remote branch, checked by reading the remote after the push, or the command exits non-zero naming the step that failed and the commits left unpushed. Promote and release commits are never left on the local branch without a push attempt that is reported.

Done when a new tests/test_a_landing_is_on_main_when_it_says_so.py shows three things with a temporary repository and a bare remote: a successful --land leaves the reviewed head an ancestor of the remote branch; a land step whose merge is forced to fail exits non-zero naming the merge step and leaves no unreported local commits; and a push forced to fail exits non-zero naming the unpushed commits. Three negative controls, one per case: skipping the merge after promotion makes the first case's head absent from the remote; swallowing the merge failure makes the second case exit zero; and swallowing the push failure makes the third case exit zero. The test files importing reckon.crew_run_commands or reckon.crew.merge add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. Write paths: reckon/crew_run_commands.py and the new test; any change the cause needs in reckon/crew/merge.py or reckon/crew/queue_landing.py is named in the manifest.

§3 — A withheld worktree is reported as a release outcome, not a landing

Deliverable. An investigation, not a repair. Reading the code alone, the post-merge release cannot find the worktree's HEAD unreachable: the guard near reckon/crew_run_commands.py line 3283 admits only a worktree whose HEAD is the reviewed head or its ancestor, the merge confirms that head on the branch (near line 3312), and _release_after_promotion then runs (near line 3337). Yet every landing on 6 November ended with that withheld reason, for example run r-20261106T121146659138, whose release.json reads it after its head 08e404d598 reached origin/main. Several of those runs' worktrees are still on disk.

The worker calls _inspect_workspace on two of those retained worktrees exactly as _release_run_workspace (reckon/crew/promotion_release.py near line 396) does, with the same repo, claims and ref, and records every input and the classification. It also records which release produced each release.json, the promotion-time one or the post-merge one. It names the cause in an evidence note and writes the repair as a section of this plan, with the repair's write paths. It edits no product source.

Done when the evidence note at docs/evidence/fragments/a-landing-is-on-main-when-it-says-so/the-withheld-release-cause.html shows, for two retained worktrees, the exact _inspect_workspace arguments, the classification it returned, and which release wrote the recorded reason. The note states the cause in one sentence that the inputs support, and the plan carries a new implementable section for the repair. Every command is logged under the run directory, starting with its revision and the literal command and ending in EXIT=. The negative control is the same call on a worktree whose HEAD is not on main, which must return the withheld classification. Write paths: the evidence note and this plan.

§4 — Every landing the lander attempts appears in its pass record

Deliverable. The admit service's pass record carries one landing row for every run its lander promoted or tried to promote in that pass, with the outcome and, for a refusal, the step that refused. A promotion that happens after a pass has deferred the run is recorded in the pass that performed it.

Done when a new tests/test_every_landing_reaches_its_pass_record.py shows two things with a stubbed landing: a pass whose lander promotes a run records a landing row naming it and its outcome; and a pass whose lander's promotion is refused at release records the refusal and its step. Two negative controls: dropping the row for a promotion makes the first case find none; and recording only landed outcomes makes the second case find none. The test files importing reckon.crew.queue_landing add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Write paths: reckon/crew/queue_landing.py and the new test.
