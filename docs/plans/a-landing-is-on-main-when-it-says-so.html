§1 — Why: a run promoted as landed whose code was not on main

On 6 November every coordinator landing printed, after its merge had reached origin/main, the refusal “the reviewed head landed and was pushed, but the worktree was withheld: its HEAD is not reachable from the integration revision, so removing it would destroy the only copy of that commit” (reckon/crew_run_commands.py near lines 3380–3389, with the reason from reckon/crew/gc.py near line 97). The admit service's lander hit the same refusal at 17:24:38Z for run r-20261106T140731148709 after its head 11f880b126 had been merged at 17:21:15Z (43035e72bd). The merge and push were confirmed each time; only the release's judgement of the worktree is wrong, so every landed run leaves its worktree behind for crew gc and every landing exits 1.

A first reading of that incident blamed the lander for not merging. It was wrong: the coordinator's own merge landed the head while the lander was measuring its candidate (17:19:33–17:24:16Z), and the lander's refusal is the post-merge release refusal. §2 and §4, written on that reading, are descoped.

§2 — A promotion with --land ends with the head on the remote, or says it did not

Deliverable. The worker first reproduces, from the run's landing.json and the --land path in reckon/crew_run_commands.py, why the land step left 11f880b126 unmerged while the promote and release commits were written, and names the cause in the manifest. Then --land is made to end in one of two states: the reviewed head is an ancestor of the remote branch, checked by reading the remote after the push, or the command exits non-zero naming the step that failed and the commits left unpushed. Promote and release commits are never left on the local branch without a push attempt that is reported. A --land killed after it has pushed its promote and release commits and before its merge is not left looking landed: either the promotion record is written only after the merge reaches the remote, or the next landing pass finds a promoted run whose head is not on the remote branch and finishes the merge.

Done when a new tests/test_a_landing_is_on_main_when_it_says_so.py shows three things with a temporary repository and a bare remote: a successful --land leaves the reviewed head an ancestor of the remote branch; a land step whose merge is forced to fail exits non-zero naming the merge step and leaves no unreported local commits; a push forced to fail exits non-zero naming the unpushed commits; and a --land killed between its promotion and its merge ends, after the next landing pass, with the reviewed head an ancestor of the remote branch. Three negative controls, one per case: skipping the merge after promotion makes the first case's head absent from the remote; swallowing the merge failure makes the second case exit zero; swallowing the push failure makes the third case exit zero; and leaving a killed landing unfinished makes the fourth case's head absent from the remote. The test files importing reckon.crew_run_commands or reckon.crew.merge add no failure against the base revision, run one arm at a time with at most -n 4. Ruff adds no findings on the staged paths. Every log is under the run directory, starts with its revision and the literal command, and ends in EXIT=. Write paths: reckon/crew_run_commands.py and the new test; any change the cause needs in reckon/crew/merge.py or reckon/crew/queue_landing.py is named in the manifest.

§5 — A plain complete refuses a head that is not on the primary branch

Why. nova-39 and nova-8a reported on 8 November, relayed by reckon-0f, that a plain crew complete (without --land) promotes a run as passed without checking that its head is on the primary branch. In nova-8a's case crew merge --run had been refused; crew complete still promoted, then deleted the live pointer, which left crew merge --run unable to find the run. The ledger then reads landed work that main does not carry, the state §2 exists to prevent.

Deliverable. A plain crew complete --gate passed on an implementation run, that is a run for which _is_review_run (reckon/crew/recovery_review_delivery.py, re-exported from reckon/crew/recovery.py near line 198) is false, whose reviewed head is not on the remote primary branch refuses, naming the head and the branch, and leaves the pointer and ledger untouched. The remote is read through its owner, reckon/crew/merge.py: _remote_head (near lines 614–621) already reads what the remote branch carries with one git ls-remote, and _is_ancestor already answers ancestry; the port-443 retry compute nodes need (_port22_refused, _port443_env) lives today only in _push_and_confirm (near lines 670–686), so §5 extends _remote_head, and the fetch it adds, to retry over that route the same way. §5 adds one function to merge.py that fetches the remote head's commit over that same route when it is not present locally and answers, through _is_ancestor, whether a head is on it; an unreachable remote and a missing branch are distinct answers. It is not a fifth ancestry convention: it calls _is_ancestor. The plain-complete path in reckon/crew_run_commands.py calls it, and §7 calls the same function. An unreachable remote or a missing branch refuses and names that cause. A head fast-forwarded on local main but not pushed is refused by the ancestry answer against the remote head. A complete with --gate failed or --gate not-run records work that is not to land and promotes as before. The refusal sits in the plain-complete path, not in the guard list promotion.complete_dry_run shares with crew merge --run (merge.require_promotable_head, near lines 157–180), because crew merge --run must still land an unmerged head. It adds one refusal family, registered in DISPATCH_REFUSAL_REMEDIES (reckon/crew/refusals.py) with the cause in its detail, not one family per cause. The coordinator lands such a run with crew complete --land or merges it first.

Done when a new tests/test_a_plain_complete_refuses_an_unmerged_head.py shows, with a temporary repository and a bare remote as origin: a plain complete on an unmerged head refuses, names the head and branch, and leaves the pointer and the ledger unchanged; a plain complete on a head already on the branch promotes as before; a --land complete on an unmerged head is unaffected by the refusal; a crew merge --run on an unmerged head still lands it, with a negative control in which the guard placed in the shared dry-run list refuses that merge; a head fast-forwarded on local main but not pushed, so that local main is ahead of the bare remote, is refused, with a negative control in which reading local HEAD promotes it; a --gate failed complete on an unmerged head promotes as before; a composed review run, whose pointer carries the reviewed node's off-branch head (reckon/crew/recovery_review_dispatch.py near line 641), promotes as before with --gate passed and runs no fetch, with a negative control in which keying the guard on the gate alone refuses it; and an unreachable remote refuses naming the failed fetch; a reachable remote that carries no primary ref refuses naming the missing ref, with a negative control in which reading that empty answer as promotable promotes it. Negative control: at the base revision the first case promotes and removes the pointer. The test files importing reckon.crew_run_commands or reckon.crew.promotion add no failure against the base revision, one arm at a time with at most -n 4, logs under the run directory starting with the revision and command and ending in EXIT=. Ruff check and ruff format --check add no findings on the staged paths. Write paths: reckon/crew/merge.py, reckon/crew_run_commands.py, reckon/crew/refusals.py and the new test. §6 also writes promotion.py and waits on this section.

§6 — A --land promotion records a landing only once the head is on main

Why. Measured on 9 November at about 14:02Z. crew complete --land on run r-20261109T114801835790-a-launch-span-is-dated-and-bounded (head 177d706c49) committed its promotion, 7b71afeb13, which wrote the ledger row as passed and the plan comment. Then the pointer-removal guard in reckon/crew/promotion.py (near line 189) raised run ... changed while promotion ran: the repair reflex had resumed the same run as attempt 4 after its review was promoted, so the pointer's attempt and phase had moved. The merge never ran. The ledger and the plan read the run as landed and the monitor shows landed, while origin/main carries none of its commits (its refusal family D24 is absent from reckon/crew/refusals.py on main). §5 closes the plain-complete route to that state; this is the --land route.

Deliverable. A promotion with --land whose merge does not run after its ledger row and plan comment are committed, the pointer guard included, keeps the pointer and marks it pending_landing_repair, the mechanism §2 landed: pending_landing.finish_pending_landings (reckon/crew/pending_landing.py near line 185) already finishes a promoted run whose head is not on the primary branch on the next landing pass, and crew complete already routes the flag (reckon/crew_run_commands.py near line 3217). So the run is landed by the existing recovery rather than a second one, and §6 adds no refusal family. The live-worker check (_require_worker_stopped_before_promotion, reckon/crew/promotion_checks.py near lines 787–845) already refuses a promotion that starts while a turn runs; the measured resume began after that check passed, because promotion holds _promotion_lock (_pointer_lock("promotion-<run>"), reckon/crew/promotion.py near line 161) while the resume takes the run's own pointer lock (reckon/crew/resumption.py near line 217). _pointer_lock (reckon/crew/runs.py near lines 453–462) takes a blocking flock(LOCK_EX) only, so §6 gives it a non-blocking mode, and a resume takes the run's promotion lock first in that mode (LOCK_NB), before the pointer lock it already takes in mark_resume_launching; that is the order promotion uses (with _promotion_lock(run_id), _pointer_lock(run_id), near line 2072), so the two cannot deadlock. If the promotion lock is held, the resume refuses rather than waits.

Done when a new tests/test_a_landing_record_waits_for_the_merge.py shows, with a temporary repository and crew home: a --land promotion whose pointer changes between the ledger write and the merge, simulated by a patched resume, keeps the pointer marked pending_landing_repair, and the next finish_pending_landings pass lands the head on the branch; a resume of the run attempted while its promotion lock is held refuses and leaves the pointer unchanged; an undisturbed --land promotion lands as before. Negative control: at the base revision the first case removes the pointer and leaves a passed row for a head that is not on the branch, which no landing pass then finishes. The test files importing reckon.crew.promotion add no failure against the base revision, one arm at a time with at most -n 4, logs under the run directory starting with the revision and command and ending in EXIT=. Ruff check and ruff format --check add no findings on the staged paths. Negative control for the resume case: at the base revision the resume proceeds while the promotion lock is held. Write paths: reckon/crew/promotion.py, reckon/crew/promotion_records.py, reckon/crew/resumption.py, reckon/crew/pending_landing.py, reckon/crew/runs.py and the new test.
