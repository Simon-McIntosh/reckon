§1 — Run state is pull-only, so completion is silent

Dispatch is fire-and-forget and nothing closes the loop. A worker that finishes writes a manifest and exits. A worker that blocks writes a manifest and exits. A worker that dies writes nothing. In all three cases the coordinator learns only by looking, and if it does not look, the node stays finished-and-unnoticed for as long as the session lasts.

Measured in the session that produced this plan. Two nodes completed and sat unpromoted for 55 minutes, their worktrees held, their commits unmerged. Both had overrun their time budget by a wide margin and nothing reacted. They were discovered only because the lead asked what was running.

§2 — The existing rule is prose, and prose is what failed

The execution skill already says to arm a watch at dispatch, and states the reason plainly: a node dispatched with nothing waiting on it is a node you will discover by accident. That rule was followed correctly on roughly eight dispatches in the same session and skipped on two, with no signal at either moment that the two were different.

That is the same shape as the member collision this sprint already fixed, and it failed the same way. The documentation was right, a coordinator that had read it did the wrong thing anyway, and nothing caught it — because a rule whose only enforcement is the reader's attention is enforced exactly as well as the reader is attentive, which is not a property anyone should design around.

The lesson is already written down twice in this repository from two separate incidents. Writing it a third time is not the repair.

The deliverable is a guard on dispatch, because dispatch is the one moment the coordinator is demonstrably awake and able to act. A coordinator asking to start new work while finished work sits unreconciled is not busy — it is present, and it is about to make the backlog worse.

The mechanism class already exists and needs no invention. Dispatch refuses a member that holds a non-terminal live pointer, raising a typed error that names the owning run. The same check, over the same pointer directory, can refuse a wave while the project holds runs classified completed_unpromoted or blocked past a threshold.

Three properties keep it from becoming an obstruction, and they matter more than the check itself:

  • Threshold, not instant. A node finishing seconds before an unrelated dispatch is normal concurrency, not a backlog. The refusal fires only once a run has been terminal and unpromoted long enough that nobody is plausibly mid-beat on it.
  • Nameable and actionable. The refusal prints the runs and their next_action lines, so clearing it is a paste rather than an investigation — the same standard the tag audit was held to.
  • Overridable and recorded. A coordinator with a genuine reason to leave work unreconciled says so explicitly and the override lands on the run record, exactly as the execution-fit refusal already does.

Done when a dispatch into a project holding a run terminal-and-unpromoted past the threshold is refused with a message naming each such run and its resolving command; a dispatch made while a run finished moments ago is not refused; the explicit override dispatches and records itself on the run; and a test asserts all three without reading or writing any pointer directory outside its own temporary home.

§4 — The half a refusal cannot reach

A dispatch-time guard catches the coordinator who keeps working. It cannot catch the one who stops. A session that dispatches two nodes and then ends leaves them exactly as stranded as before, and that is the case where the work is most likely to be lost entirely rather than merely delayed.

The closure fence in the execution skill already requires a drain before a closing report, but it drains followups — it says nothing about runs whose manifests are written and whose commits are unmerged. A session can satisfy the drain completely while leaving two finished nodes on disk.

Deliverable: extend the drain to run state. Before a closing report the coordinator reconciles every live pointer, and the ledger it already writes gains a second count alongside foldable-remaining: unreconciled runs, which must read zero for the same reason. A run left deliberately — handed to another session, or genuinely still working — is recorded with that reason, in the same closed-set style the followup dispositions already use.

Done when the closing ledger reports an unreconciled-run count derived from the live view rather than from memory, and a session ending with a nonzero count and no recorded reason is visible as such in its own artifact.

§5 — The coordinator that waits by asking again

Measured while this plan was being executed, which is how it was found. The coordinator armed a correct watch at dispatch and then asked the same question every turn anyway, ending with eight overlapping background watches on one run. The lead saw a screen of poll noise before the single real signal arrived. Nothing was lost, and that is the point: the loop worked and was still unusable.

This is the third case at the same seam, and the first two do not reach it. §3 catches the coordinator who keeps dispatching. §4 catches the one who stops. Neither catches the one who waits, because waiting badly produces no refusal, no stranded run and no missing artifact — only noise, which no fence measures.

The cause is the same shape as §2. The execution skill's own watch recipe is a poll loop, and it never says how many watches a wait needs. The host harness reference already records that this host re-invokes the session when a backgrounded command exits, so the capability was present and unused. A recipe the coordinator retypes per dispatch is a recipe it can get wrong once per dispatch.

Deliverable: one command, one watch, for the whole fleet. reckon crew watch --project <project> blocks until the first live pointer in that project reaches a terminal manifest or its stream goes quiet past a resolved window, then exits printing that run's id, classification and next_action. A per-run watch scales with the fleet and reproduces the noise it is meant to prevent, so the watch is project-wide and there is exactly one. Every crew command that leaves live pointers behind returns the arming line and whether a watcher is already live, so is the fleet watched stops being a question the coordinator answers from memory.

The recorded pid is not the liveness signal. Reading it misled this session, and an in-harness run has no pid at all. Stream quiet is both simpler and correct for every launch kind.

Arming without the coordinator acting at all is host-local, and stays quarantined. Reckon can reduce the wait to a single line and report whether it is live; only the host harness can arm that line unprompted, which for this host means a settings hook on the dispatch call. That belongs in the harness reference beside the wake-on-completion capability it depends on, never in the portable skill.

Done when the watch exits on the first terminal run in a project naming its classification and resolving command, exits on a stalled stream without waiting out any time budget, cannot reach two live watchers for one project, and reports its live state back through the dispatch payload; the execution skill's recipe is replaced by that one command; and the harness reference carries the host-local arming form.

§ Decisions

Where does the guard against unreconciled finished work fire?

The detection already exists in the live view. The question is what consumes it, given that the coordinator who needs telling is the one not looking.

Locked 2026-08-24 on measured failure rather than preference. The skill rule already exists and already gives the reason; it was followed on about eight dispatches and skipped on two in one session, with no signal distinguishing them, which is the same way the member-collision rule failed earlier in the same sprint. Restating it a third time repairs nothing. A background promoter was rejected for a stronger reason than cost: promotion is the moment a human or coordinator judges the gate, audits the scoped diff and decides the verdict, so automating it would replace a judgement with a default and produce a ledger full of unexamined passes. Refusing at dispatch keeps the judgement where it belongs and fires it exactly when someone is there to make it.

How many watches does a wave need, and who arms them?

Nothing currently arms a watch; the skill asks the coordinator to. Executing this plan produced eight overlapping watches on a single run, so the question is both how many and who.

Locked 2026-08-24 by the lead on measured noise. A per-run watch scales with the fleet, so an eight-node wave owes eight wake-ups for events nobody needed separately, and it is the form that produced the incident. Project-wide is one process whatever the fleet size, and it exits on the first event that matters. Reckon spawning the watcher itself was rejected on a hard constraint rather than preference: in this host the wake primitive is a harness-launched background command exiting, and a process Reckon detaches is not one the harness watches, so it would run forever and wake nobody. What Reckon can own portably is the single command plus the report of whether it is live; arming it with no coordinator action is host-local and belongs in the harness reference as a settings hook.

§ Followups

Make the signal that already exists load-bearing, at both ends of the loop

Nothing here needs new detection. The live view already classifies a finished-and-unpromoted run, computes how far past its budget it has drifted, and prints the command that clears it — and nothing reads any of it. Start with the dispatch refusal, because it reuses the guard class that already refuses a member holding a live pointer and fires at the one moment the coordinator is provably awake; keep it thresholded so ordinary concurrency is untouched, nameable so clearing it is a paste, and overridable with the override recorded on the run. Then extend the closure drain from followups to run state, because a refusal at dispatch cannot reach a session that simply stops, and that is the case where finished work is lost rather than delayed.
