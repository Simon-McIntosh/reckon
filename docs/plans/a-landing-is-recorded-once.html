§1 — Why: one landing is written four times

A section that lands is recorded in a fragment the worker writes, a landing line copied to the plan, an anchor the coordinator splices into the plan's landed record, and the run record the promotion writes. The landing line and the run record carry what happened and how it was checked; the other two restate them in prose.

The research document What per-node evidence costs measured this. Over the 30 days to 2026-11-14, 3,873 of 24,788 commits touched docs/evidence. A worker spends a median 7.1% of its run writing the fragment, and 489 of 1,923 fragments were opened by an agent afterwards. A prototype overview built without reading any fragment kept 47 of 60 sampled fragment claims with every sentence sourced; the 13 it lost were durations, pass counts, hashes and identifiers.

Plan landed-record-at-closure ruled in October that a node makes one write and the landed document is built once at closure. The per-node fragment later returned as a requirement. This plan restores that ruling and adds the two things the lead asked for: a figure where a section has something to show, and one concise sourced overview at closure. The lead adopted the plan on 2026-11-15 and settled both decisions below: a per-node fragment is optional, and the records already on disk stay frozen in place. §6 states the optional fragment.

§2 — A node with something to show leaves a figure

Deliverable. A node whose result is a measurement, a comparison or a rendered surface writes one figure in the figure directory its dispatch claims for it under docs/figures/<plan>/ and names it on a figures: line in its manifest. A node with nothing to show names none; there is no quota. The worker contract states this rule, and the manifest check holds a named figure to it.

Done when a new test file shows, in a temporary repository: a manifest naming a figure that the run's commits carry under the plan's figure directory passes the manifest check; a manifest naming a figure the commits do not carry is refused, naming the path; a manifest naming a figure outside docs/figures/ is refused; a manifest naming a figure committed under another plan's figure directory is refused; a manifest with no figures: line passes; and the composed implementation prompt states the rule. Negative control: with the new check removed, the missing-figure manifest passes. The test files that import the manifest check add no failure against the base revision, and ruff check and ruff format --check add no finding on the staged paths.

§3 — A closing plan gets one sourced overview

Deliverable. The existing reckon evidence synthesize command writes a plan's closure overview as that plan's landed record, at the path a close already requires; there is no second command and no second document. Anchors already appended to a plan's record are kept beneath the overview. The overview is built from the plan's sections and done-whens, its section landing comments, its committed run records, its stored reviews and the figures its runs named. It reads no fragment. The overview holds, in order: one paragraph per section giving what the section set out to do, its landing line verbatim, and the measured result; one table with one row per landed node; every named figure with its caption; and totals for runs, attempts per landed section, review findings and their disposal, and worker hours against declared effort. A section with no landing gets one sentence giving its declaration and that nothing landed. Every factual sentence and every table row carries its source: a commit, a run id, a gate command with its exit status, a gate log path, or a figure path.

Done when a new test file shows, over a temporary repository with a ledger, one figure and a three-section plan of which two sections landed: the overview carries one paragraph per section and each quotes that section's landing comment; no factual sentence lacks a source element; a node with three attempts renders one table row that states three attempts; the gate command, its exit status, the tests-added count and the suite failure count held on a run record each appear in the overview with that run's id as source; the section that did not land renders one sourced sentence stating its declaration and no landing line; the figure appears with a project-absolute src and its caption; a marker string placed only in a fragment file does not appear in the overview; and the overview passes reckon audit-doc. Negative controls: a renderer that emits a sentence with no source fails the second case, one row per run fails the third, a renderer that omits the run record's figures fails the fourth, and a renderer that skips an unlanded section fails the fifth. The test files that import reckon.evidence add no failure against the base revision, and ruff adds no finding on the staged paths.

§4 — A plan does not close over a section with no landing line

Deliverable. Without fragments, the landing line is the only prose account of a section. The close operation refuses a plan that holds a section which states a done-when, is declared done, and has neither a landing comment nor a run record, and names each such section. A section that states no done-when, such as a section giving the plan's reasons, is outside the rule. The rule applies only to a section marked done after it lands (lead ruling 2026-11-15): measured against the store on that day it would otherwise have refused 27 of 172 open plans over 49 sections that were already done. A section already done when the rule lands is exempt, and stays exempt however its plan is later edited.

Done when a new test file shows: closing a plan whose done sections each have a landing comment succeeds; closing one with a done section that states a done-when and has neither a landing comment nor a run record is refused and the refusal names the section; adding the comment lets the same close succeed; and a done section that states no done-when and has no comment does not stop a close. Negative controls: with the check removed, the second close succeeds, and a check that ignores whether the section states a done-when refuses the fourth. A section that was already done when the rule landed, with a done-when and no landing, does not stop a close, and a section marked done afterwards with no landing does. The new refusal is also run against the live store of every mounted project, and it refuses no open plan as that store stands; the log is in the node's run directory. The test files that import the close operation add no failure against the base revision.

§5 — A closing sprint gets one page

Deliverable. Closing a sprint writes one page with a row per member plan (status, sections landed, runs, worker hours and the plan's headline result) and the figures those plans' overviews carry. Every link on the page resolves.

Done when a new test file shows, over a temporary project with a three-plan sprint: the page has three rows whose counts equal those in each plan's overview; a plan with no overview is listed with its status and no broken link; every href and src on the page resolves to a file in the repository; and the page passes reckon audit-doc. Negative control: a row linking a plan with no overview fails the third case. The test files that import the sprint close add no failure against the base revision.

§6 — A per-node fragment is optional

Both decisions are settled: a per-node fragment is optional, and the fragments and landed records already on disk are left in place, frozen.

Deliverable. An implementation node is no longer required to write a per-node evidence fragment, and a landing no longer splices one into the plan's landed record. A node leaves its landing line, its run record, its gate log and any figure §2 asks for. A node may still write one fragment at its own fragment path when it has a negative result or a mechanism that does not fit a landing line; the worker contract says when that applies, and a routine landing writes none. Where a landed node wrote a fragment, the closure overview links it from that node's row and reads nothing from it; this section adds that link to the overview §3 built. The worker contract, the build skill and its references, and the edit, create and sprint skills state this, and none of them requires a per-node fragment or asks for a per-landing splice. Fragments and landed records already on disk stay readable where they are; nothing rewrites, moves or removes them.

Done when a new test file shows: the composed implementation prompt presents the fragment as optional and names the two cases it is for; a manifest with a landing line and no fragment passes the manifest check; a manifest with a landing line and a fragment at the node's own fragment path also passes; a promotion of a run without a fragment succeeds and records the landing; a section ticked with a close comment that links no evidence anchor is accepted; a closure overview for a plan where one node wrote a fragment links that fragment from that node's row and contains none of its text; and an existing fragment still renders through the served page. The gate log quotes, before and after, each skill passage that today requires a fragment or a per-landing splice (in the build skill and its worker-protocol, sprint-orchestration and coordinator references, and in the edit, create and sprint skills), and each after-text states the fragment as optional and asks for no splice. Negative control: with the mandatory fragment clause restored to the prompt, the first case fails. The test files that import the prompt composer or the manifest check add no failure against the base revision, and ruff check and ruff format --check add no finding on the staged paths.

The closing page's tests fail on a miscounted row and on a link to a plan with no document

Why. The review of the node that landed §5 (101, no added failure) left two findings on the strength of its tests. The sections-landed count on the closing page is asserted only for member plans whose every section is declared done, so a page that counted declared sections in place of landed ones would still pass. And the control that was run for §5 dropped a table row, so the page's rule for when a row carries a link, which is that a member plan with no document is not linked, is asserted and was never shown to fail.

Deliverable. The closing page's tests fail when a member plan's row shows a count of declared sections in place of landed ones, and fail when a row links a member plan that has no document.

Done when. The closing-page test file holds a member plan on which the two counts differ, one section declared done that has neither a landing comment nor a landed run beside sections that landed, whose row is asserted to show the landed count; that assertion is shown to fail when the count is taken from the declarations. It also holds a member plan with no document, whose row is asserted to carry no link. Negative control: with the check that withholds a link for a member plan with no document removed, that case fails, and that run is logged. The test files that import the overview module add no failure against the base revision, each arm run on rigel.

What becomes of the 1,923 fragments and 213 landed records already on disk?

Lead decision 2026-11-15: freeze the existing fragments and landed records in place.

Should any node still write a per-node fragment?

Lead decision 2026-11-15: a fragment is optional, for a negative result or a mechanism that does not fit a landing line.
