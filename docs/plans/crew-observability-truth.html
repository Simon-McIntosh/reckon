§1 — Why this is its own plan

Over one execution session the fleet display was wrong in five distinct ways, and in every case a person noticed before the tooling did. The lead twice identified a dead worker by looking at GPU utilisation while the ticker reported it running; a peer session watched six finished runs display as 6 working for 38 minutes, and later two more for 13 and 6 minutes, finding each by stat-ing a manifest rather than by being told. Three of those defects were fixed inside clive-local-workers §7, because that is where they were found. Two were not, and they have no owning plan at all — which is the condition this plan exists to end, since a defect named only in a followup is hidden work by the project's own rule.

The reason to separate them is that they are not about local workers. §7 of that plan is titled strengthen the harness around local workers, so the model comparison is a model comparison, and it has been absorbing crew-wide observability work because the local lane happened to expose it. That was correct while the lane was blocked; it is now obscuring both subjects. The qualification questions belong there. Whether the display tells the truth belongs here.

The producer-orphans RCA is the evidence base for §2. It closed two of its three defects; this plan owns the third.

§2 — The registry disagrees with the machine, and the guard trusts the registry

Measured 2026-09-03. crew list returned watcher pid: None, seat_held: None, watcher_live: None for the reckon project while reckon crew watch --project reckon was running as pid 85432, had been since 07:33:13, and had emitted four transitions in the preceding twenty minutes. The registry and the process table were both readable and they disagreed.

This is not a display nicety. watcher_live and session_attached are the fields crew dispatch reads to decide whether to refuse with watcher-required. A guard whose whole purpose is to stop work being dispatched into a fleet nobody is listening to is deciding on a value that can be wrong in either direction: it can refuse a dispatch whose producer is alive, or admit one whose producer is gone.

The likely mechanism, stated as the next thing to check rather than as a finding: the registry is a written record guarded by a seat lock, and the binding between that record and the process is one-way. The arming path already carries a comment describing the opposite failure — a producer whose supervisor died keeps appending real transitions while holding the seat, so the stale record outlives every session that cared. Both failures together suggest the record and the process have no reliable binding in either direction, and that a liveness answer should be derived from the process rather than read from a file that hopes to describe it.

§4 — What a person should be able to read off the pane

The three sections above are individual defects. This one is the standing obligation they violated, written down so a future change can be checked against it rather than against taste. Twice in one session the honest signal was outside the tool: GPU utilisation, and a manifest on disk. Both times the pane asserted the opposite.

  • A count of working runs means work is in progress. Not that pointers exist. A run whose process is gone, or whose manifest is terminal, is not working, and the display must not add it to that bucket.
  • Activity is generation, not bytes. A stream file's mtime advances on tool progress and system records; one measured run carried 30,461 records of which 156 were assistant turns while it sat blocked on a ten-minute wait. Liveness derived from mtime called that healthy, and so did the orchestrator reading it.
  • The pane says which code produced it. Already landed as the producer version stamp; recorded here because it is part of this obligation rather than a separate courtesy.
  • A wrong answer is worse than no answer. Where a signal cannot be derived honestly, report it as unknown. Absence of evidence has been mistaken for evidence three times in this fleet's short history — a budget signal, a manifest, and a watcher — and every instance cost more than a stated unknown would have.
  • A surface never drops the discriminating value. The obligation above governs a signal that cannot be derived; this one governs a signal the record already holds. Three times in one day the value that would have settled a question existed and the surface discarded it: a reset time parsed out of a rejection into resets_at: null, a manifest status dropped by a reader that returned eight other keys, and a reason truncated before the clause naming its predicate. In none of these was the cost a wrong answer — it was an unanswerable question, which is more expensive, because a wrong answer can be contradicted by a measurement and an absent one sends its reader to look somewhere else. A partial result is the worst form: eight keys and no status is indistinguishable from a manifest whose author omitted the status, so it manufactures a plausible wrong answer, and plausible wrong answers are the ones that survive review.

§6 — A transition names the label it last emitted, not the state it was in

Every run's first transition is labelled dispatched regardless of what it actually was. The arrival branch of the transition fold appends {**current[run_id], "state": "dispatched"} as a literal, discarding whatever the snapshot computed; subsequent polls then compare against that stored label. So from_state is the last emitted label rather than the state at evaluation, and a pane reading dispatched → X learns nothing about the phase the run was in when X was decided.

This is not cosmetic, because it makes the ticker unusable as evidence about the detector itself. A peer session reasoned that a dispatched → stalled event proved the pre-fix stall gate could evaluate a dispatched run, and therefore that widening the gate was not the fix for their case. The event is in fact fully reachable under the old gate: the run arrives and is labelled dispatched, its phase later advances to working so the state == "working" gate does fire, the quiet exceeds the window, and the transition is emitted with the stale label as its origin. The inference was sound given what the pane shows and wrong given what the code does, which is the defect — a display that cannot be reasoned from is worse than one that is merely sparse.

The same event carried a second, independent defect. That run was not stalled; it was finished, with a complete manifest, a landed commit and a clean worktree, and the last assistant turn 914 seconds before the event. The detector read the quiet correctly and then chose the wrong verdict, because it consulted elapsed silence and not the terminal manifest sitting beside it. Terminal manifests are checked before the stall gate in the current code, so this needs its own reproduction: either the manifest was unreadable to the classifier at that moment, or the ordering does not hold on the path the producer takes. Reproduce before repairing.

MeasureRequired evidence
An origin state is realA transition's from_state is the state the run was actually in at the previous evaluation, so a first transition from a run already working reports working rather than dispatched. Asserted against a fold whose first observation is a mid-flight run.
A terminal manifest outranks silenceA run whose manifest is terminal is never reported stalled, whatever its quiet interval. Asserted by reproducing the recorded case first, then fixing it.

§5 — A spent lane should be known before dispatch, and should hand over rather than refuse

The exhaustion was visible all along and nothing asked. On 2026-09-03 the codex account hit its usage limit with a reset eight days out. Every unnamed dispatch kept resolving to it, because default_backend named it, and crew preflight reported it clear. The cause is one missing flag: budget_check was set on codex-spark, codex-luna and codex-terra and not on codex — the highest-volume lane in the fleet at 372 promoted runs, and the one backend a pre-flight could not probe. Without it a pre-flight can only believe what earlier runs recorded, and no run had yet recorded the refusal because the parser that reads a usage-limit event into a budget signal landed afterwards. Enabling the flag changed the answer immediately: the same pre-flight now returns held: true naming codex.

That fixes visibility and leaves the second half open. Today a held backend refuses: crew preflight exits 3 and crew dispatch returns budget-hold. Refusing is correct when a human is watching and wrong when the point is unattended execution — the fleet stops on a condition the configuration could have routed around, and a person has to notice and edit default_backend by hand, which is what happened here and cost most of a session's dispatches.

Let a lane declare where its work goes when it is spent. An ordered fallback, resolved at dispatch when the primary is held, with three properties that keep it from becoming the next silent wrong answer:

  • The substitution is recorded on the run, naming the lane asked for, the lane used, and the hold that caused it — so a calibration slice never attributes a fallback run to the backend the caller named. This is the same reasoning that made a shadow record its substituted configuration.
  • A fallback is declared, never inferred. A backend with no declared fallback still refuses, because guessing a substitute is how a metered account gets spent by a caller who never chose it.
  • Unknown never triggers it. A backend reporting no headroom is not held and therefore never falls back, preserving the rule that absence of a signal is not evidence of exhaustion.

Two related gaps belong with it. roles.<role>.by_spec_level can set effort but nothing maps a spec level to a backend for the Claude lanes, so "route an open node to the frontier tier" is expressible only as a per-call --set — a rule with no bound check, which is this sprint's own thesis. And the host layer briefly carried two claude-opus definitions, added independently by two sessions; YAML takes the last key silently, which dropped budget_check and left the frontier tier with no headroom visibility at all. Nothing validated the collision.

§6 — A spend limit is a block, because a block is the only state that can be triaged

Directed by the lead on 2026-09-03, immediately after the outage recorded in §4 and §5. A provider refusal must surface as blocked. Not as a completion, which is what the harness reports and what let five deaths pass unnoticed for ten minutes. And not as a failure, which is what the coordinator had to reconcile them as, because it was the only reconciliation available.

Blocked is not a nicer word for failed; it is the state with the affordances the situation needs. Three of them, and no other state has all three. It reaches the coordinator, because blocked is a bucket the follower prints while a failure at starting is not. It is resumable in the same session, so the worker keeps the context it had when it stopped. And it holds a reason, which for this condition is an unusually good one: the account, the limit kind, and a reset timestamp. A spend limit is the most triageable stop a fleet can suffer — it says exactly what is wrong and exactly when it stops being wrong — and the fleet currently converts it into the least triageable thing there is.

Phase and failure classification are different axes, and this needs both. Classifying the refusal as an infrastructure failure is correct for the ledger: it keeps the model's pass rate clean, which is the rule the harness section already states. But classification is what the record charges at reconciliation, not what the coordinator sees while the condition holds. Recording infrastructure-failure and showing blocked are complementary, and today only the first exists.

What it cost, measured on one run of the five. The merged-head verification node had already launched both suite runs and was waiting on them; its manifest read in-progress and its run directory held two suite logs, an attribution map naming the three code-bearing candidate commits, and per-test ledgers at both revisions. It hit the limit three times, said it would wait for the settle notification rather than poll further, and stopped. Killed rather than blocked, none of that could be resumed: the artifacts survived only because they had been written incrementally, and a fresh node had to be handed them as a lead to re-confirm rather than a result to use. Four other runs were redispatched from scratch for the same reason.

The coupling with clive-local-workers §14 is not incidental. That run was waiting on test suites, generating almost nothing, and hit a spend ceiling anyway. A budget denominated in generation would not have charged it for the wait, and a refusal that blocks rather than kills would have let it collect the result it was minutes away from. The two changes address the same waste from opposite ends.

Asserted against the five streams recorded 2026-09-03, and as a negative against a genuine completion and a genuine crash, neither of which may become blocked.

§7 — Health is read from work, probed when stale, and the probe writes back

Directed by the lead on 2026-09-03, after this session held a wave for four hours on a reset the provider stated and did not honour. Two questions: can health be known without hitting the endpoint, and should a probe update the log rather than be a separate reading someone has to remember to take. Yes to both, and the answer is a ladder rather than one instrument, because the rungs answer different questions.

Rung one is free and already flowing: every served request returns rate-limit telemetry as a byproduct. A fleet doing work continuously reports its own headroom — utilisation, the window, and whether the request was served, warned or rejected — without a single extra call. This is the non-endpoint check, and for the routine case it beats a probe precisely because nobody has to decide to take it. What is missing is not the signal but its age: the budget record keeps the reading and not the moment, so a thirty-minute-old rejection and a five-second-old one are indistinguishable to the reader.

Rung two costs no tokens and is already declared in the schema, for nothing. BackendConfig.auth_check exists as an argument vector run to test whether a backend is authenticated, as an exit status — described in the schema as how a provider-specific credential check reaches reckon without reckon knowing any provider. All nine backends report no auth_check declared. Declaring it gives a credential check for free. It must not be mistaken for a quota check: an authenticated account can be spend-limited, so this rung answers can I reach the provider and never will it serve me.

Rung three is a one-token request, and it is the only rung that answers the question a dispatch actually asks. Measured: four output tokens, under half a cent, a definitive verdict. Cheap enough to use freely, and still not the routine path, because rung one already covers the routine case at zero cost. A probe is the tie-breaker for when the log is too old to trust and a decision turns on it.

The recorded refusal is rung zero, and it is authoritative only about the past. A refusal proves a lane was spent when it was recorded. Its stated reset is a claim about the future, and this session measured one wrong by three and a half hours. Holding until a stated reset is therefore not a recovery strategy; probing on an interval is.

What ties the ladder together is that every rung writes to one log. The budget record is the single thing the pre-flight reads, and today only run streams write it. A probe that reports to its caller and not to the record leaves the next reader to probe again, which is how a cheap check becomes an expensive habit. So a probe's result lands in the same record with its own timestamp and provenance, and the pre-flight's answer names which rung it came from and how old it is.

§ Decisions

Where does a liveness answer come from?

The registry and the process table disagreed in a measured case. Deriving from the process on every read is truthful but costs a scan; reconciling the record on read keeps the cheap path and repairs drift; keeping the record authoritative is what produced the defect.

Locked 2026-09-03 by the lead. The record stays as the cheap path and every read checks it against the process table, repairing drift in place without taking the seat lock. This is the only option that satisfies all three of §2's measures at once: deriving on every read is truthful and satisfies the first two but leaves the stale record for the next reader to trip over, failing 'a desync is repaired, not merely reported'; leaving the record authoritative is the mechanism that produced the measured defect, where crew list reported watcher_live None while pid 85432 had been emitting transitions for twenty minutes. The accepted cost is that a read now performs a process check, and that the reconciliation path must never take the seat lock, so observing still cannot deny an arming.

What should gc do when the named project's checkout is not the enclosing repository?

It currently scans the enclosing repository silently. Refusing is safest but blocks a legitimate cross-checkout call; resolving from mounts is convenient but changes existing behaviour for callers relying on the default.

Locked 2026-09-03 by the lead. With no --repo a named project resolves the checkout registered in mounts rather than the current directory, which makes the measured failure impossible: three different projects returned byte-identical counts from the reckon checkout, and nova's 124 reclaimable worktrees were reported as zero. Refusing unless the cross-pairing is stated was rejected as the default because it turns every legitimate cross-checkout call into two steps and would leave §3's third measure declared and undelivered. The refusal survives where it belongs, on an explicit --repo that disagrees with the named project's registered checkout, which is §3's first measure. The accepted cost is a behaviour change for any caller relying on the enclosing-directory default.

Which Anthropic tier is the default, and how is the other reached?

Asked by the lead on 2026-09-03 while the codex account was spent. Measured over this session's ledger: claude-sonnet-5 passed 8 of 8 at a 228-second median, claude-opus-5 passed 2 of 2 at 753 seconds. Sonnet is 3.3 times faster with four times the sample and both are clean, so speed decides the common case. The case for reserving opus is specific rather than general: on two nodes it caught traps its specification did not name — that writing a literal exhausted headroom would be silently downgraded by budget.py's own _is_known and hold nothing, reproducing the defect it was fixing, and that summing per-event usage undercounts generation 67-fold in a way that looks entirely plausible. Sonnet's contribution was different in kind: it declined to add an exception type and explained why, and it corrected a wrong diagnosis of mine mid-implementation. The coordinator has already set default_backend to the sonnet lane, so this ratifies or reverses a change already made rather than proposing an untried one. Note the coupling: reaching opus by specification level is not expressible until by_spec_level can name a backend, which is a measure of this same section.

Locked 2026-09-03 by the lead. This ratifies default_backend already pointing at the sonnet lane and puts the frontier tier where the evidence says it earns its cost rather than everywhere: on open-level nodes, the least-specified work, which is where opus caught two traps its specification did not name. Sonnet is 8 of 8 at a 228-second median against opus 2 of 2 at 753 seconds, so speed decides the common case on the larger sample. Reaching opus explicitly per dispatch was rejected because it leaves 'route an open node to the frontier tier' as a rule with no bound check, which is this sprint's own thesis about what decays. Opus as default was rejected as paying 3.3 times the wall clock on every node for depth the larger sample does not show is needed. The accepted coupling is that this choice is not fully expressible until §5's by_spec_level-names-a-backend measure lands, and degrades to per-dispatch selection until it does.

Ceded by the peer session that owns the promotion path, measured here before accepting it. Six of 486 committed run records store commits: ['none'] — a one-element list whose element is the literal string none.
