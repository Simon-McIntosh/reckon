§1 — Why: the surface holds a coordinator to duties it will not let it clear

Measured on 2026-10-21 by one reckon coordinator running five plans through about twenty runs. Each item cost a hand step that the obligations hook or the monitor then reported as the coordinator's to clear.

  • The stop hook demands a review the queue cap refuses. Three times (moved-checkout-serves-every-call at 16:40Z, a-finishing-write-offers-its-close at 16:56Z, review-waits-for-its-repair at 19:36Z) the hook blocked the turn with review-missing and printed the dispatch command, and that exact command returned queue-full: the session already held 2 queued runs, at its cap of 2. Each was cleared only by a hand crew ack.
  • A queued review waits behind implementation. The session's queue held an implementation node queued at 16:08Z ahead of a review queued at 16:33Z. With the session's share at 0 slots, the review that unblocks a landing waited behind new work for about half an hour, and no verb reorders a session's queue.
  • An obligation stays on the head a resume replaced. After crew resume --reopen of a-newer-flight-key-is-ignored-at-load (16:43Z) and the-critical-path-runs-through-sections (17:08Z), and after plain resumes of three more runs, the hook kept listing review-missing and promotable-stale for the replaced heads. They were acknowledged by hand six times.
  • The review reflex races the reopen. The reflex queued a review of the-critical-path-runs-through-sections at daf10d2 at 17:07Z; the coordinator reopened the run at 17:08Z and discarded the queued review by hand, since it would have scored a head being replaced.
  • A queued run changes its id while it waits. the-critical-path-runs-through-sections was dispatched as …160638960523 and launched as …161245050192; a-brief-carries-its-domain-rules went through …160852144811, …161828762522 and …170216319822 and launched as …170434451667; a-regenerated-path-is-charged-as-written went from …170639960137 to …173243033733. The monitor printed each retired id as dropped, and crew discard on the id the dispatch returned failed with no live run.

§2 — A review is never refused by its session's queue cap, and launches before implementation

A review of a delivered run is what lets that run land, so it is the last dispatch a cap should refuse. Reviews are exempt from the per-session queue cap, and among one session's queued runs a review launches before an implementation node queued earlier. The cap still bounds implementation.

Done when: a fixture session holding its cap of queued implementation nodes dispatches a review and gets it queued, not queue-full; with one slot free, that review launches before the earlier implementation nodes; and a further implementation dispatch is still refused queue-full, which is the control. On the base commit the review is refused queue-full, so the test fails there.

§3 — An obligation follows the run's current head

A resume replaces the head a review or a promotion would read. From the moment a complete run is resumed until it delivers again, its review-missing and promotable-stale duties for the prior head are withdrawn, and a review queued for that head is withdrawn rather than launched, recorded as superseded by the resume. When the run delivers again, the duties return for the new head.

Done when: a fixture complete run owing a review is resumed and its obligations list no review-missing or promotable-stale for the old head; a review queued before the resume is withdrawn and recorded as superseded; after the run delivers a new head, review-missing names the new head. A run that is not resumed keeps its duties, which is the control. On the base commit the old duties persist, so the test fails there.

§4 — A queued run keeps one id from dispatch to launch

The id a dispatch returns is the one a coordinator records, cites and later acts on. Admission retries and the launch reuse it rather than minting a new one, so crew observe, crew discard and the ledger all answer for the id the dispatch printed, and the monitor never reports a run that launched as dropped.

Done when: a fixture dispatch that is queued, retried by admission twice and then launched carries the same run id throughout; crew discard on that id while queued succeeds; the watch stream carries no dropped transition for it. On the base commit the launched run has a different id, so the test fails there.

§5 — A run built on a held chain tip may write its holder's paths

Why. Reported by nova-47 (session s21-nova) on 2026-10-22. Two follow-on nodes, contour-chain-added-failures and root-polish-owned-line-search, were dispatched with --base e9444fd44, the chain tip of the held run r-20261021T005136987306-read-correction-path, deliberately building on its unlanded 38 commits to resolve that run's 19 added gate failures. The admit service retried both for over 90 minutes and refused each with ScopeConflict on the holder's claimed paths (nova/equilibrium/contour_tree.py, nova/equilibrium/fixed_points.py), naming the holder as stopped with unreachable commits — promote or recover it. The holder could not be promoted, because the follow-ons exist to make it promotable. The coordinator worked round it by widening the holder and resuming it with both tasks, discarding the two queued runs.

Change. The exception is relational: it depends on the base of the dispatch under admission, which claim_disposition in reckon/crew/node.py never sees, since it judges one pointer at a time. So the exception lives in the conflict check _raise_repository_scope_conflict in reckon/crew/dispatch_claims.py, which is given the two facts it lacks today. The dispatch passes its resolved base revision into the check. Each _RepositoryScopeClaim carries the holder's run id, its head revision and whether its process has stopped as fields, read from claim_disposition, whose ClaimDisposition gains a stopped flag beside binding (it already tells the two cases apart, but only in its reason text). The check passes over a binding claim when its holder is stopped and the dispatch's base is the holder's head. The ancestry test reuses one of the existing helpers (_revision_is_ancestor in reckon/crew/promotion_scope.py or _is_ancestor in reckon/crew/merge.py) rather than adding a fourth. The admitted stacking is recorded on both pointers through the pointer writer in reckon/crew/runs.py, and the registry row _live_scope_claims builds for the holder's claim lists the stacked runs it admitted. The claim stays binding for every other dispatch. Promoting or discarding the holder while a stacked descendant is live is not refused, since the descendant's worktree carries the holder's commits. Instead, the promotion result in reckon/crew/promotion.py and the discard result in reckon/crew/runs.py read the stacking recorded on the holder's pointer and name each descendant still live. No refusal family is added.

Done when: a fixture held run with unlanded commits admits a dispatch based on its chain tip that writes its claimed path, and refuses one based on main with ScopeConflict; both pointers record the stacking, and the scopes view's row for the holder's claim names the stacked run while still reading binding; promoting the holder while its descendant is live succeeds and its result names the descendant. On the base commit the stacked dispatch is refused ScopeConflict, so the test fails there.

§6 — A manual admission pass says what it decides, inside a bound

Why. Reported by nova-47 the same night: a manual reckon crew admit (no options; --project is not accepted) emitted nothing for 5 minutes and was killed by timeout 300, so the coordinator could not tell whether it was waiting or working, nor what it decided. The decisions it makes are written to admission-verdicts.jsonl, which is where the coordinator diagnosing the case above had to read them.

Change. reckon crew admit --once already returns its pass's verdicts as JSON and records them through _record_pass_verdicts; the silent form is the bare verb, which is the service loop in admit_until_stopped (reckon/crew/queue_admission.py) and discards each pass's result after recording it. The loop now writes each pass's result to stdout as one JSON line, the same rows admission-verdicts.jsonl records, so a caller sees every decision as it is made. The help text of crew admit in reckon/crew_run_commands.py says that the bare form loops until stopped and that --once is the single manual pass, and states how long one pass may take. No option is added.

Done when: a fixture bare crew admit driven for two passes over two queued runs, one admitted and one refused on scope, prints one JSON line per pass naming both runs and their verdicts with the refusal's detail, matching the rows admission-verdicts.jsonl records for the same passes; --once output is unchanged; the help text names the loop and the single pass. On the base commit the bare loop prints nothing, so the test fails there.
