§1 — Why: the lane sat empty and no read said so

On 2026-10-22 at about 08:50Z the lead found power_convertor's local lane at one request in flight of twelve, with 38 worker slots free, headroom 10 and an empty router queue. The derived flow drew seven lanes with one in flight. Nothing was queued or held. Coordinators were not dispatching. Three sections were implementable, dependency-ready and gate-clear with no run:

  • iter-switched-terminal-transients#s13, never dispatched;
  • iter-dummy-load-validation#s4, held for a lead decision that the plan's own rule already answered;
  • shared-coil-supply-model#s9, a peer coordinator's, first on the project's 27-hour critical path (s9 → iter-switched-terminal-transients#s6 → coil-supply-report-rebuild#s4 → #s8).

No read surfaced any of it.

  • roadmap(view="summary") carries no section readiness. view="detail" with limit=3 was refused at 110,833 characters, and view="raw" at 124,408, against an 80,000-character ceiling.
  • crew(view="directory") lists coordinators that have live runs, so a coordinator that is idle on a ready section does not appear at all.
  • The derived flow draws a ready plan with no run as a grey "predicted" bar, identical to a plan waiting on a prerequisite.

The coordinator found the set only through reckon roadmap --json-output and a hand-written join of pending_work[].ready_sections and implementable_sections, minus live runs. Owners were found by messaging peers. Within ten minutes of the join, four more runs were in flight, the critical-path head among them.

The pieces exist. a-project-reads-as-one-picture §2 puts sections on the critical path, and its §4 puts runs and blocker kinds on each section row. crew's directory, scopes and live views hold sessions, runs and claims, and the-mcp-answers-the-question-asked §3 is adding the section to every run row. What is missing:

  • the coordinator session behind a section that has no run: the plan names its accountable person in plan-owner, and the ledger records a session per run, but nothing joins the two for a section with no run;
  • the "ready, no run" set as its own bounded answer;
  • the critical path read link by link;
  • one bounded join of every coordinator's runs, sections, held paths and queued runs;
  • the lane's admission share on the same answer.

That last list is this plan. Two neighbours are covered elsewhere and are not repeated here: why(ref) is the-mcp-answers-the-question-asked §4, and the ranked brief is a-project-reads-as-one-picture §7.

§2 — A plan's coordinator is derived from the ledger, beside its recorded owner

Two ownership facts already exist, and this section joins them instead of adding a third.

  • The person. The plan's <meta name="plan-owner"> names who is accountable. It is read as it stands and never overwritten.
  • The session. Every ledger run row carries session, the crew session that dispatched it, beside session_id, the worker's own harness session (reckon/ledger.py:162-165, reckon/run_record.py:538-539). _live_review_runs (reckon/crew/obligations.py:467) already filters live pointers by that session, but only those with a review in flight, so it is a precedent for the field, not a function to reuse.

A plan's coordinator is the dispatching session of its most recent dispatched run, live or in the ledger, within a configured staleness window. A run is matched to its plan by the row's plan field, and, where that is null because the run was dispatched from a brief (reckon/run_record.py:489), by its plan_link. A run carrying neither is matched by the plan its node id names: a plan review's node plan-review-of-<slug> names <slug>, and a run review resolves through the run it reviews. A run matched by none of these belongs to no plan. The window is a configuration value, never a literal in code. With no such run it is unowned, reported as itself and never guessed. The answer carries both facts: the plan-owner person and the coordinator session by its id; no surface resolves a session to a peer name today, so none is claimed. It also says whether that session is live, and an ended session reads as ended. A later dispatch by another session takes the plan over, and the ledger already holds the earlier sessions as history. No claim store is added. The resolver is one new function that reads the committed ledger rows and the live pointers, takes each run's dispatching session, and keeps the most recent match per plan; it does not reuse _live_review_runs, which sees only live pointers with a review in flight.

Done when, on a fixture built from power_convertor's run ledger as committed at 2026-10-22T08:50Z, each named plan resolves to the coordinator its most recent matching row names:

  • shared-coil-supply-model, iter-switched-terminal-transients and tf-co-wound-tape-validation each resolve to the session the test pins as a literal, read from the fixture rows by hand; the gate log names, for each plan, the row that decided it and which of plan, plan_link or the node id matched, so the expectation never comes from the derivation under test;
  • a plan given no ledger rows in the fixture to unowned;
  • each plan's plan-owner reported beside its coordinator.

Unit test: a plan dispatched by session A and then by session B resolves to B, with A in the ledger's history. Negative controls:

  • a resolver that returns unowned for every plan must fail the fixture test;
  • one that ignores dispatch order must fail the A-then-B test.

§3 — The ready-idle set extends the ready-set view

ready_set_view (reckon/mcp_views.py:1128) already projects ready sections from the canonical roadmap. This section extends it instead of adding a second projection. Each ready row gains three fields:

  • its live run, or none, read from the section rows a-project-reads-as-one-picture §4 carries;
  • its coordinator and plan-owner from §2;
  • a critical-path flag.

The view also gains closable plans, each naming its open closure blockers. The ready-idle set is that view filtered to rows with no live run. It is a filter argument on the existing view, not a new view or a new refusal family, and it pages with the view's own paging. Interface budget: no view is added. The lossless-report recipe that two skills carry as a stopgap is retired by §7.

Done when, on a fixture reconstructed from power_convertor's state at 2026-10-22T08:50Z, the filtered view names the three sections of §1 with their coordinators. It also names jt60sa-coil-circuit-model and tf-co-wound-tape-validation as closable, all in one call under the MCP ceiling. Negative control: a section given a live run in the fixture must leave the filtered set, and the test must fail if it stays.

§4 — The critical path reads link by link, on its existing rows

The roadmap's critical_path.sections rows (a-project-reads-as-one-picture §2) gain a primary state and the full list of what holds each link. The primary state is the first that applies, in this order:

  1. in flight, with its run id;
  2. ready-idle, with its coordinator;
  3. gated, with its gate id;
  4. waiting, with the ref it waits on.

The holds list carries every open gate and every unmet wait, so a link both gated and waiting reads as gated with both in its holds. The head link is reported first, and an idle head is said so in words. These are fields on rows that already exist, and that plan's §7 brief quotes them. Interface budget: no view or refusal family is added.

Done when the 08:50Z fixture reads shared-coil-supply-model#s9 as ready-idle with its coordinator named, and iter-switched-terminal-transients#s6 as gated, with holds g-istt-6 and shared-coil-supply-model#s9. Negative controls: giving s9 a live run must turn its primary state to in flight, and a holds list that drops either of s6's two holds must fail the test.

§5 — The board extends the coordinator directory

reckon/crew/directory.py owns the coordinator read model (_run_row, _observed_transport), and crew(view="directory") serves it. The board is that view, extended with three things:

  • each run row names its plan#section, from the-mcp-answers-the-question-asked §3;
  • each coordinator row carries its held write paths, with the binding verdict the scope check's own data gives, and its queued runs with their queue positions;
  • a coordinator that is coordinator (under §2) of a plan with ready-idle sections in §3's filtered view appears with those sections, even when it has no run, which is the case the directory misses today.

The board joins existing owners and derives nothing itself. Interface budget: no crew view is added; directory gains fields. Agents read it to coordinate without messaging: which files a peer holds, which section a peer is on, and which of its sections a peer has left idle.

Done when the directory for power_convertor lists every live run of every coordinator with its section and held paths, and lists a coordinator that has ready-idle work but no run. It stays bounded at workstation scope because the directory view gains a limit and a cursor: today reckon/mcp_views.py:3805-3813 returns the directory early with neither, so the change caps the row count and pages the rest. Negative control: a coordinator whose only plan has no ready section and no run must not appear, and the test must fail if it does.

§6 — The lane share lives on the lanes view alone

crew(view="lanes") already attaches the parsed lane document to each lane row (_attach_lane_document, reckon/mcp_views.py:724). The document is parsed once, by read_lane_document in reckon/crew/lane_document.py:303, and reckon/crew/obligations.py:553 (_published_worker_slots) already reads the calling session's published share. This section extends the lanes view with that share and the session's live run count, through that function, together with the document's observed_at. That is the one carrier. The directory and the ready-set view do not copy the figures; they name the lanes view as where to read them. A full lane queues a dispatch centrally, so the figures inform the order of dispatch, never whether to dispatch. Interface budget: no view is added.

Done when crew(view="lanes", session=...) carries the session's share and live runs with the document's observed_at, and a stale document reads as stale rather than as current. Negative control: a lane document older than its own publication period must be marked stale, and the test must fail if it is read as fresh.

§ Decisions

Which tool serves the board and the ready-idle set?

Split by what each fact describes, as the coordinator of the-mcp-answers-the-question-asked proposed on 2026-10-22, and across existing views only: no new view is added. The board (§5) extends the directory view, and the lane share (§6) extends the lanes view, because they are facts about coordinators, runs, claims and the lane. The ready-idle set (§3) and the link-by-link critical path (§4) are facts about sections, so they are fields on the roadmap's existing ready-set and critical_path rows, where a-project-reads-as-one-picture §4 already put runs and blocker kinds, and that plan's §7 brief quotes them. The roadmap serves plans and sections, and crew serves runs and coordinators: one derivation per fact.
