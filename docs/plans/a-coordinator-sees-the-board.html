§1 — Why: the lane sat empty and no read said so

On 2026-10-22 at about 08:50Z the lead found power_convertor's local lane at one request in flight of twelve, with 38 worker slots free, headroom 10 and an empty router queue. The derived flow drew seven lanes with one in flight. Nothing was queued or held. Coordinators were not dispatching. Three sections were implementable, dependency-ready and gate-clear with no run:

  • iter-switched-terminal-transients#s13, never dispatched;
  • iter-dummy-load-validation#s4, held for a lead decision that the plan's own rule already answered;
  • shared-coil-supply-model#s9, a peer coordinator's, first on the project's 27-hour critical path (s9 → iter-switched-terminal-transients#s6 → coil-supply-report-rebuild#s4 → #s8).

No read surfaced any of it.

  • roadmap(view="summary") carries no section readiness. view="detail" with limit=3 was refused at 110,833 characters, and view="raw" at 124,408, against an 80,000-character ceiling.
  • crew(view="directory") lists coordinators that have live runs, so a coordinator that is idle on a ready section does not appear at all.
  • The derived flow draws a ready plan with no run as a grey "predicted" bar, identical to a plan waiting on a prerequisite.

The coordinator found the set only through reckon roadmap --json-output and a hand-written join of pending_work[].ready_sections and implementable_sections, minus live runs. Owners were found by messaging peers. Within ten minutes of the join, four more runs were in flight, the critical-path head among them.

The pieces exist. a-project-reads-as-one-picture §2 puts sections on the critical path, and its §4 puts runs and blocker kinds on each section row. crew's directory, scopes and live views hold sessions, runs and claims, and the-mcp-answers-the-question-asked §3 is adding the section to every run row. What is missing:

  • the owner of a section that has no run, because nothing records plan ownership;
  • the "ready, no run" set as its own bounded answer;
  • the critical path read link by link;
  • one bounded join of every coordinator's runs, sections, held paths and queued runs;
  • the lane's admission share on the same answer.

That last list is this plan. Two neighbours are covered elsewhere and are not repeated here: why(ref) is the-mcp-answers-the-question-asked §4, and the ranked brief is a-project-reads-as-one-picture §7.

§2 — A plan has one owner, and the owner is a recorded fact

An idle section has no run, so no session can be read off it. Ownership is defined at the plan, in three tiers, with the tier recorded beside the answer.

  • Declared. A coordinator session claims a plan when it first dispatches a node of it. The claim is written to the project's state store beside the run ledger, not into the plan HTML, because the plan file is the team's and the claim is a session's. The claim holds until the session releases it, a later dispatch on the plan by another session takes it over, or the plan closes. A takeover keeps the earlier claim in its history.
  • Derived. With no claim, the owner is the session that dispatched the plan's most recent ledger run within a stated staleness window. The window is a configuration value, never a literal in code.
  • Unowned. Neither exists. That is reported as itself, never guessed.

The owner is reported as the session id, plus the session's peer name where the directory can resolve one. The answer never claims a liveness it has not checked: an owner whose session ended reads as ended.

Done when every pending plan in a project resolves to declared, derived or unowned, with its tier. Tests: a plan dispatched by session A and then by session B resolves to B, declared, with A in its history. A released claim falls back to derived. A plan with no ledger rows reads as unowned. Negative control: dropping the takeover rule leaves A as owner, and the first test must fail.

§3 — The ready-idle set is one bounded answer

A read returns every section that is implementable, dependency-ready and gate-clear with no live run, plus every plan whose dependency readiness reads closable. One derivation per fact: readiness and runs are read from the roadmap payload's section rows (a-project-reads-as-one-picture §4), never recomputed here.

Each row carries:

  • the plan#section ref;
  • the owner and its tier from §2;
  • the section's effort;
  • what it unlocks downstream;
  • whether it is a critical-path link.

Rows sort critical-path first. The answer is bounded by construction: one compact row per idle section, paged by limit and cursor like every other read, never refused for size. A closable plan row names its open closure blockers, such as deferred sections or open gates, so its owner knows whether a close or a descope decision is owed.

Done when, on a fixture reconstructed from power_convertor's state at 2026-10-22T08:50Z, the answer names the three sections of §1 with their owners, and names jt60sa-coil-circuit-model and tf-co-wound-tape-validation as closable, in one call under the MCP ceiling. Negative control: a section given a live run in the fixture must leave the set, and the test must fail if it stays.

§4 — The critical path reads link by link

Each link of the critical path carries one state:

  • in flight, with its run id;
  • ready-idle, with its owner;
  • gated, with its gate id;
  • waiting, with the ref it waits on.

The head link is reported first. An idle head is the most expensive idle work in a project, and the answer says so in words. This is the per-link state reckon-a1 named as a small extension. It lives here, not in a-project-reads-as-one-picture §7's rows, so each fact has one reader. §7's brief may quote it.

Done when the 08:50Z fixture reads shared-coil-supply-model#s9 as ready-idle, owner named, and iter-switched-terminal-transients#s6 as gated on g-istt-6 and waiting on that s9. Negative control: giving s9 a live run must turn its state to in flight, and the test must fail if it does not.

§5 — The board: what every coordinator is doing, with ids

One bounded read, at project or workstation scope, returns a row per coordinator session. Each row carries:

  • its runs: run id, node, plan#section, phase and age;
  • the write paths it holds, with each claim's binding verdict as crew(view="scopes") states it;
  • its queued runs, with their queue positions;
  • the plans it owns under §2, with their ready-idle sections from §3.

A coordinator that is idle on owned ready work is on the board even with no run, which is the case the directory misses today. The section on each run row comes from the-mcp-answers-the-question-asked §3, and the claims from the scope check's own data. Nothing is re-derived. Agents read the board to coordinate without messaging: which files a peer holds, which section a peer is on, and which owned sections a peer has left idle.

Done when the board for power_convertor lists every live run of every coordinator with its section and held paths, and lists a coordinator that owns ready-idle work but has no run. The answer stays bounded at workstation scope through paging. Negative control: a coordinator whose only plan has no ready section and no run must not appear, and the test must fail if it does.

§6 — The lane on the same answer

The board and the ready-idle answer carry the local lane's admission figures, as the lane document publishes them: worker slots, headroom, waiting and the oldest wait, plus the calling session's share and how many runs it holds. The answer states facts and computes nothing new from them. A full lane queues a dispatch centrally, so the figures inform the order of dispatch, never whether to dispatch.

Done when both answers carry the figures with the document's observed_at, and a stale document reads as stale rather than as current. Negative control: a lane document older than its own publication period must be marked stale, and the test must fail if it is read as fresh.
