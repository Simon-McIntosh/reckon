Why. A B300 router is expected to serve about 80 concurrent local requests, against today's gate of 12. On 15 November one fleet node (96 GB, 28 cores) carried every coordinator, the station, the admit service and every worker, and failed at gate 12. The fleet job reached 95 of 96 GB and recorded 136 OOM kills. The admit service restarted six times in under an hour, and the station's tick took two to six minutes. The measured costs that set the scale:

About 230 omp-local workers at 0.4 GB is about 90 GB, which does not fit on one fleet node beside the coordinators, so workers have to run on more than one node. The reckon MCP server today speaks stdio only, so each worker that uses it starts its own copy. The installed MCP library (1.28) also offers a network transport that one server can serve many clients through. Workers can already be placed as scheduler steps on a reservation. This plan sets the endpoints that let the lane run at 80 without the fleet node failing, and keeps MCP use open to workers that need it.

§1 — A queued request holds no process until it holds a slot

Deliverable. A request starts its worker's harness only when the router has a slot for it, and admission never launches past the router's published worker slots. A request waiting for a slot holds no process and no memory. The number of live workers at a full lane stays within the router's published worker slots plus two. Whether a queued or held request holds a process today has not been measured; the node's first record is that census at the base revision.

Done when. A test with a temporary crew home and a stand-in router of width 4 queues 20 requests and reads, at every admission pass, no more live workers than the router's worker slots plus two, and no process for any request still queued. A measure on the fleet node over one hour at a full lane reads the live worker count against the published worker slots every five minutes, and every reading is at most the slots plus two. A census at the base revision records, for every queued and held request, whether a process exists for it. Negative control: a mutation that starts a queued request's worker before it holds a slot turns the test red; the failing run, the census and the measure are logged to docs/evidence/fragments/work-scales-to-eighty-across-nodes/s1.html.

§2 — One MCP server per node serves every worker that uses it

Deliverable. On each node that runs workers, a declared MCP server runs once and serves every worker on that node whose MCP set names it. A worker connects to it rather than starting its own copy. The server's resident memory does not grow with the number of workers it serves.

Done when. A test starts 5, then 40 stand-in workers on one node whose MCP set names the reckon server and reads one reckon server process serving all of them, each worker's tool call answered. The server's resident memory serving 40 workers, read every ten minutes for one hour, has a median no more than 0.5 GB above its median serving 5 workers over the same length of time. Negative control: at the base revision the test reads one server per worker; the failing run and the measure are logged to docs/evidence/fragments/work-scales-to-eighty-across-nodes/s2.html.

§3 — A node declares the MCP set it needs

Deliverable. The flight names MCP sets, each a list of servers. A plan section or a brief may name one set for its node, and the node's worker connects to exactly that set, on every backend. A node that names no set connects to none. The set a worker connected to is recorded on its run.

Done when. Tests with a temporary flight declaring two sets read a node naming the first connected to exactly its servers, a node naming the second connected to exactly its servers, and a node naming none connected to no server, on a Claude, a Codex and an omp launch, with the connected set recorded on each run. Negative control: at the base revision a node naming a set is refused or connected to servers outside it; the failing run is logged to docs/evidence/fragments/work-scales-to-eighty-across-nodes/s3.html.

§4 — Workers run on compute nodes while coordination stays on the fleet node

Deliverable. A dispatched worker can run on a compute node rather than the fleet node. It reads and writes run state on GPFS and its scratch on that node's local disk. The fleet node keeps the coordinators, the station, the admit service and their MCP servers. A worker on a compute node delivers, is reviewed and lands exactly as one on the fleet node does.

Done when. A rehearsal places 20 workers on a compute node through the scheduler, and each delivers a manifest, passes its review and lands. The rehearsal reads the fleet node's memory before and during the run, and the readings differ by less than 2 GB. A test reads a worker on a compute node writing no file under the fleet node's local scratch. Negative control: at the base revision the rehearsal's workers run on the fleet node, and its memory rises by about 0.4 GB per worker; both are logged to docs/evidence/fragments/work-scales-to-eighty-across-nodes/s4.html.

§5 — The station's tick stays under 30 seconds at 230 live runs

Deliverable. The station completes a tick in under 30 seconds with 230 live runs across the mounted projects, and its resident memory stays under 2 GB, so obligations and the monitor stay current at the target scale.

Done when. A measure against a crew home populated with 230 live runs, run on all_debug, records 20 consecutive tick durations and the station's resident memory after each, and every tick is under 30 seconds and every reading under 2 GB. Negative control: the same measure at the base revision records ticks over 30 seconds; both are logged to docs/evidence/fragments/work-scales-to-eighty-across-nodes/s5.html.

§6 — The lane holds 80 concurrent requests for an hour

Deliverable. With §1 to §5 landed, the local lane holds about 80 concurrent requests for an hour across at least two nodes, served by at least 175 live worker processes, with no OOM kill in any fleet job and every admission pass under 30 seconds.

Done when. A record of a one-hour window, against the B300 router or a stand-in router of width 80, reads the router's in-flight count every five minutes with a median of at least 72, a count of live worker processes across the nodes of at least 175 at every reading whether the router is the B300 or a stand-in, zero OOM kills in each node's memory events, every admission pass under 30 seconds, and every queued request still present or launched at the window's end. Negative control: the same window at a revision before §1 lands records OOM kills or a median below 72; the record is docs/evidence/fragments/work-scales-to-eighty-across-nodes/s6.html.
