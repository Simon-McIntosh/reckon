§5 — Build the typed router

Build the router in reckon from §4's design note. It turns a node's declared needs and the live state of every lane into one typed selection: family, model, effort, the probabilities and confidence behind it, the pinned Jev version, the orchestrator's comment, and a fallback reason when one applies. The selection is recorded on the run and its ledger row. It replaces per-model backends with one backend per provider and adds a dispatch field for the orchestrator's free-form comment. Old backend names resolve, with a warning, for one transition period, so that no peer's dispatch breaks mid-flight. The router never falls back silently. This section's node shapes and done-whens are written from §4's design note, and its gate holds it until that note exists.

The lead's direction (2026-10-02, second instruction). "We need this working quickly." Jev's prompts are Jinja templates, after imas_codex/llm/prompt_loader.py in imas-codex, so that live facts are injected at call time: burn rate and window position for each metered lane, local-lane worker slots and congestion from lane.json, and recent successes and failures per model from the ledger. The state is concise and only what the judgment needs: the lead's words are "do not overwhelm the typesafe model". Return time is a routing input (the lead, 2026-10-02): the state carries, per candidate, the distribution of recorded run times by effort and node size (median and 90th percentile of wall_seconds from the ledger), and the local lane's current load (running, waiting, headroom, tokens per second), so that Jev weighs how soon a job of this size would return on each lane. The node run-time-profile derives these figures in a module of their own, and the picker renders them. Development is iterative: each replay and dogfood round feeds the next revision of the templates. Straightforward, well-defined work (specification level exact, or a node needing no decision) goes to the local lane, and this rule lives in the candidate filter and the template, not only in Jev's judgment. Metered lanes are paced so that a window is not spent in its first days.

Nodes, in order.

  1. Prototype (picker-prototype, dispatched under §4 because §4's replay runs through it, and so it lands before §4's gate): a reckon/crew/picker/ package holding the Jinja templates, the state builder, the candidate filter, the OpenRouter client for Jev and the typed selection. A reckon crew pick command prints one selection for a described node without dispatching anything, and a replay mode runs at least 50 ledger dispatches through it. The replay is §4's evidence.
  2. Shadow recording (picker-shadow): every dispatch asks the router and records its selection on the live run and on its ledger row as one key present on every row, null when the router was not asked. No lane changes.
  3. Routed dispatch (picker-routes-dispatch): an opt-in dispatch mode in which the router's selection names the backend, with the orchestrator's free-form comment passed verbatim. Below threshold, or when Jev is unreachable, it falls back to the deterministic default and records why.

The first cut chooses among the existing backend names, each of which is one (family, model) pair, so no peer's configuration changes. Consolidating to one backend per provider is a later node, opened only once routed dispatch has run here.

§6 — Prototype and dogfood the router

The router is proven on reckon's own work before it becomes anyone's default. Three stages, each leaving its own evidence:

  1. Replay, inside §4's done-when: recorded dispatches go through the questions, with no live effect.
  2. Shadow: every live reckon dispatch also asks the router, and records its pick, probabilities and confidence beside the lane actually used, without acting on it. This runs for at least one week or 100 dispatches, whichever is longer.
  3. Dogfood: one coordinator session routes its own dispatches through the router, using orchestrator comments, with a recorded switch back to deterministic routing.

Measures, each compared with deterministic routing over the same period: run success rate; metered spend per promoted run; dispatches to a refused or logged-out model (target zero); router latency per dispatch; fallback rate; and the confidence distribution.

Done when: the shadow and dogfood stages each publish those measures from their run records. The router becomes the default only if the dogfood stage shows a success rate no lower, spend no higher, and zero dispatches to a refused or logged-out model. Otherwise the plan records the negative result and what to change.

Compressed by the lead (2026-10-02). "Prototype extensively and then dogfood here to ensure working. Once live, message all other sessions and switch over." The switch therefore happens once the dogfood stage here meets three conditions. First, at least six of this session's dispatches are routed, with zero to a refused or logged-out model. Second, every routed run carries its recorded selection on its run record and ledger row. Third, one deliberate fallback (Jev unreachable, or confidence below threshold) is recorded with its reason. At the switch, every live coordinator session is messaged with how to route and how to switch back. The week-long shadow comparison above continues after the switch, as the measure that can reverse it.

§8 — Picker iteration: return time, latency and honest replay figures

The §4 prototype picks in 19.6 s end to end, while the Jev call itself takes 350 ms; the rest is the competence and context checks reloading the ledger once per candidate. Its state does not yet carry return time. Two nodes, split by file so they run in parallel. picker-return-time adds reckon/crew/picker/lane_context.py, which renders per candidate the median and 90th-percentile run time for a job of this size from run_time_profile, the budget reading's source and age (a ledger-only reading past its shelf life is marked stale), and the local lane's load from local_lane_load. It also measures the state bound against a real five-key congestion block. picker-latency shares one ledger read and one budget snapshot across all candidates of a pick, with a target median of 3 s or less per pick. It also corrects the replay summary, whose Jev-latency median counts rows that made no call and whose refused-pick count is zero by construction.

This work sits in a section of its own because §5's record cannot move from deferred to implementable through any edit path: state writes are refused on disagreement, and text writes cannot touch a structured-state region.

§ Decisions

Who decides the model for a dispatch?

The lead, 2026-10-02: "we want the model and the family to be picked. the router should handle everything, the orchestrator should be able to write free form comments to pass onto jev". The router picks family and model. The orchestrator influences the pick only through a free-form comment carried verbatim in Jev's state, never by naming a lane. Rejected: a coordinator override as the primary control, which reproduces today's per-name routing; and a picker with no orchestrator input, which discards context only the orchestrator has. Whether a hard override survives as a recorded emergency switch is settled by §6's dogfood evidence, not assumed.

§ Open questions

What is "jev" in "the use of jev via my OpenRouter account"? It might be a tool, a library, an OpenRouter feature such as its automatic router, or a typing slip. §4's scope depends on the answer.

Jev is TypeSafe's flagship model and the first System One model (the lead, 2026-10-02). It returns typed answers with probabilities over a JSON state, and §4 designs the router's judgments with it.
