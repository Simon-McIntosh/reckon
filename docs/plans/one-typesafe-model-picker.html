The lead's direction (2026-10-02): one lane per provider (claude, clive, codex), and a router that picks both the family and the model for every dispatch and handles the whole choice. The orchestrator does not pick. It may write a free-form comment, which the router passes on to the model making the judgment. That model is Jev, TypeSafe's flagship and first System One model, which returns typed answers with probabilities rather than generated text. Code keeps every hard constraint; Jev supplies the semantic judgment of which family and model fit the node. This is a significant redesign. The typesafe-ai skill and the live TypeSafe docs guide it; the skill was installed on 2026-10-02 as a Claude Code plugin and is invoked as /typesafe:typesafe-ai. The router is prototyped and dogfooded on reckon's own dispatches before it becomes anyone's default (§6).

It overlaps the-local-lane-is-the-default (route by backend and model, local by default), a-window-paces-the-lane and advise-the-lane-never-force-it. This plan is sequenced after the first and is meant to absorb the routing parts of all three, which the design section reconciles explicitly.

§4 — Jev as the router: design the judgments

Design the router's judgments with Jev, following the typesafe-ai skill and the live docs at docs.typesafe.ai.

What the docs establish (read 2026-10-02).

  • Model: Jev 1.13 (jev-1.13.0). The jev-latest alias moves when a release ships, so the router pins the version.
  • API: one call to POST https://api.typesafe.ai/v1/systemone answers many typed questions over one JSON state.
  • Choice: takes up to 255 options, and returns the chosen option, the full probability distribution and a confidence.
  • Parallelism: questions in one request run in parallel and cannot see each other's answers.
  • Limits: 64k tokens per request, of which 32k is for the state plus the longest question; 40 requests a second.
  • Price: $0.042 per million tokens, so cost is negligible beside any lane it routes to.
  • Routing patterns: intent routing, confidence-gated routing, function calling, speculative fan-out, and skill suggestion over a 182-item catalog. All of them keep hard constraints in code and gate actions on confidence.

The starting design this section must settle.

  • Candidate set. Code assembles it: every family and model the flight config declares, minus any that is refused, logged out, held on budget, too small for the node's context, or behind a paused gate. Jev cannot choose an option it is not shown, and §2 measured that a budget reading alone admits a refused model.
  • State. The node contract (role, specification level, capability requirements, goal, done-when, estimated context); the orchestrator's free-form comment, verbatim; and a lane snapshot per candidate. The snapshot carries availability, window utilisation and burn multiple, reset time, local-lane worker slots, and recent outcomes for that model on similar nodes.
  • Questions, in one request. A family Choice; a speculative model Choice per family, of which code reads only the chosen family's; and whatever gating Nouls the design needs. Compare this with a single Choice over every (family, model) pair.
  • Confidence and fallback. Code takes the minimum confidence across the answers it consumes, as in the function-calling cookbook. Thresholds are set by consequence: a metered lane needs more than the local lane. Below threshold, the router falls back to the deterministic default, loudly and on the record.
  • Access (settled by the lead, 2026-10-02). Jev is reached through the lead's OpenRouter account with the key in OPENROUTER_API_KEY_RECKON, read from reckon's gitignored .env and never logged. OpenRouter's public model list (read 2026-10-02) carries one TypeSafe entry, typesafe/jev-router, priced as variable. Its chat-completions surface is not obviously the typed System One API, so the probe in this section must establish which call returns a typed Choice with its probability distribution, and record a redacted request and response for it. If no call through OpenRouter returns a distribution, the probe says so, and the design uses whatever typed answer the surface gives, with confidence derived and labelled as such.

Done when: a design note names every question with its type, instructions and criteria; the exact state schema, including the orchestrator-comment field; the candidate filter; the confidence threshold for each consequence; the fallback; the pinned Jev version; and the credential path. In addition, a replay of at least 50 recorded dispatches from the ledger through those questions reports Jev's family and model picks with their confidence, beside the lanes those runs actually used and their outcomes.

§5 — Build the typed router

Build the router in reckon from §4's design note. It turns a node's declared needs and the live state of every lane into one typed selection: family, model, effort, the probabilities and confidence behind it, the pinned Jev version, the orchestrator's comment, and a fallback reason when one applies. The selection is recorded on the run and its ledger row. It replaces per-model backends with one backend per provider and adds a dispatch field for the orchestrator's free-form comment. Old backend names resolve, with a warning, for one transition period, so that no peer's dispatch breaks mid-flight. The router never falls back silently. This section's node shapes and done-whens are written from §4's design note, and its gate holds it until that note exists.

The lead's direction (2026-10-02, second instruction). "We need this working quickly." Jev's prompts are Jinja templates, after imas_codex/llm/prompt_loader.py in imas-codex, so that live facts are injected at call time: burn rate and window position for each metered lane, local-lane worker slots and congestion from lane.json, and recent successes and failures per model from the ledger. The state is concise and only what the judgment needs: the lead's words are "do not overwhelm the typesafe model". Straightforward, well-defined work (specification level exact, or a node needing no decision) goes to the local lane, and this rule lives in the candidate filter and the template, not only in Jev's judgment. Metered lanes are paced so that a window is not spent in its first days.

Nodes, in order.

  1. Prototype (picker-prototype, dispatched under §4 because §4's replay runs through it, and so it lands before §4's gate): a reckon/crew/picker/ package holding the Jinja templates, the state builder, the candidate filter, the OpenRouter client for Jev and the typed selection. A reckon crew pick command prints one selection for a described node without dispatching anything, and a replay mode runs at least 50 ledger dispatches through it. The replay is §4's evidence.
  2. Shadow recording (picker-shadow): every dispatch asks the router and records its selection on the live run and on its ledger row as one key present on every row, null when the router was not asked. No lane changes.
  3. Routed dispatch (picker-routes-dispatch): an opt-in dispatch mode in which the router's selection names the backend, with the orchestrator's free-form comment passed verbatim. Below threshold, or when Jev is unreachable, it falls back to the deterministic default and records why.

The first cut chooses among the existing backend names, each of which is one (family, model) pair, so no peer's configuration changes. Consolidating to one backend per provider is a later node, opened only once routed dispatch has run here.

§6 — Prototype and dogfood the router

The router is proven on reckon's own work before it becomes anyone's default. Three stages, each leaving its own evidence:

  1. Replay, inside §4's done-when: recorded dispatches go through the questions, with no live effect.
  2. Shadow: every live reckon dispatch also asks the router, and records its pick, probabilities and confidence beside the lane actually used, without acting on it. This runs for at least one week or 100 dispatches, whichever is longer.
  3. Dogfood: one coordinator session routes its own dispatches through the router, using orchestrator comments, with a recorded switch back to deterministic routing.

Measures, each compared with deterministic routing over the same period: run success rate; metered spend per promoted run; dispatches to a refused or logged-out model (target zero); router latency per dispatch; fallback rate; and the confidence distribution.

Done when: the shadow and dogfood stages each publish those measures from their run records. The router becomes the default only if the dogfood stage shows a success rate no lower, spend no higher, and zero dispatches to a refused or logged-out model. Otherwise the plan records the negative result and what to change.

Compressed by the lead (2026-10-02). "Prototype extensively and then dogfood here to ensure working. Once live, message all other sessions and switch over." The switch therefore happens once the dogfood stage here meets three conditions. First, at least six of this session's dispatches are routed, with zero to a refused or logged-out model. Second, every routed run carries its recorded selection on its run record and ledger row. Third, one deliberate fallback (Jev unreachable, or confidence below threshold) is recorded with its reason. At the switch, every live coordinator session is messaged with how to route and how to switch back. The week-long shadow comparison above continues after the switch, as the measure that can reverse it.

§ Decisions

Who decides the model for a dispatch?

The lead, 2026-10-02: "we want the model and the family to be picked. the router should handle everything, the orchestrator should be able to write free form comments to pass onto jev". The router picks family and model. The orchestrator influences the pick only through a free-form comment carried verbatim in Jev's state, never by naming a lane. Rejected: a coordinator override as the primary control, which reproduces today's per-name routing; and a picker with no orchestrator input, which discards context only the orchestrator has. Whether a hard override survives as a recorded emergency switch is settled by §6's dogfood evidence, not assumed.

§ Open questions

What is "jev" in "the use of jev via my OpenRouter account"? It might be a tool, a library, an OpenRouter feature such as its automatic router, or a typing slip. §4's scope depends on the answer.

Jev is TypeSafe's flagship model and the first System One model (the lead, 2026-10-02). It returns typed answers with probabilities over a JSON state, and §4 designs the router's judgments with it.
