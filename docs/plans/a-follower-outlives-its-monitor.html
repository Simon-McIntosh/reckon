§1 — The follower does not go stale; the host ends it

Four coordinators reported on 2026-09-22 how their followers stopped, and every stop had one cause. The Claude Code host ends a Monitor at thirty minutes and announces it only with its own Monitor expired after 30m with N events delivered notice. The Monitor tool's timeout_ms is capped at 1,800,000, and it has no persistent parameter, although the harness reference tells coordinators to pass persistent: true.

The census in the measurement plan §2 confirms this over seven days and four projects. Of 719 armed followers, 620 ended at the host's expiry, 86 when the project seat was released, 12 on an exit-127 arming failure and 1 on another script failure. The follower also replaced itself in place 198 times when reckon's own source changed. The persistent parameter did once work: 453 calls passed it and none met the expiry. The last such call was at 13:40 UTC on 2026-09-15, and the Monitor tool has not offered it since, which is when every follower started dying at thirty minutes.

The expiry costs three things, and only the first is visible. The next dispatch is refused with watcher-required, because the session has no delivering follower. The first arming often fails outright, because attach_line names a bare reckon that is not on the Monitor shell's path, and a Monitor that dies in under a second looks like a quiet fleet. And the re-arm hides the runs that changed during the gap, which is the costly part.

The hiding is two mechanisms together, both in the source. On attach the follower emits one baseline row per live run, and _row_is_stale_inventory in reckon/cli.py drops every baseline whose state is in SETTLED_STATES in reckon/crew/ticker.py. That set holds completed_unpromoted, failed and abandoned, which are the states that need the coordinator. Separately, _follow_watch_lines reports a run only when its state differs from the last one reported, so a run is shown once. imas-efit-e3 lost three unpromoted runs this way for 1h21m, 2h07m and 2h42m. The cause census in the measurement plan §2 supplies the seven-day counts.

§3 — The follower announces its own end before the host does

Add a --lifetime option to reckon crew follow, taking a duration. When the lifetime is about to elapse, the follower prints one final line and exits cleanly, releasing its registration. The line is marked as the follower's end rather than a fleet event, names the attach line to re-arm with, and lists the owning session's runs that need the coordinator. The host's notice then arrives after a line the reader can act on, and the registration is released rather than left to be discovered dead.

This is the one deliberate exception to the rule that the stream carries only worker transitions and fleet posture, because the end of the stream is the one fact about the follower a reader must act on.

Done when a test runs the follower with --lifetime 3s over a fixture holding one unpromoted run of the owning session, observes exit status 0 within five seconds, and asserts the last line names the absolute attach line and that run's node. Without the option the follower is asserted to keep running past five seconds. The write paths are reckon/cli.py and tests/test_follow_lifetime.py.

§4 — A re-attach replays the gap instead of hiding it

Persist each session's last delivered state per run, keyed by session, in the follower registration directory named by follower_dir in reckon/crew/runs.py. Write it whenever the follower delivers a row. When a follower attaches for a session that has a persisted record, emit the owning session's runs whose state differs from the record, as ordinary transitions from the recorded state. Emit no row for a run whose state is unchanged. Emit one header line first saying the follower re-attached, how many live runs it found and how many changed since the recorded time.

The replayed state is the classifier's current reading, never the pointer's stored phase. Measured on the session that wrote this plan: each re-arm's baseline labelled four runs that had been streaming for 27 minutes as dispatched, and left out both of the session's finished, unpromoted runs.

Remove completed_unpromoted, failed and abandoned from the set the human path suppresses, because those rows are what the reader must see. A run already promoted stays suppressed.

Three terms in this section are pinned to one reading. Suppressed set means the human path's own filter, _row_is_stale_inventory in reckon/cli.py. The SETTLED_STATES constant in reckon/crew/ticker.py keeps its value. Its only consumer is settled_at_attach, called by that filter alone, so the filter's derivation changes and the constant's name keeps describing states that are settled rather than states that are hidden. The record is a separate sidecar file in follower_dir, named for the session: <session>.delivered.json. It lives outside the flocked registration file, so writing it never contends with the registration lock, and follower_state does not expose it. A run that differs from the record includes a live run the record does not name at all, for example one dispatched while no follower was attached. Such a run is replayed as a transition from dispatched, so the header's count and the replay count the same population. Delivers a row means a row actually written to the pane, never a row generated and then suppressed. Live run means every live pointer the owning session holds, including unpromoted, failed and abandoned ones, so the header counts the same population the replay reports.

Done when tests/test_follow_replays_the_gap.py runs a follower for a session, stops it, moves one owned run from working to unpromoted and leaves a second owned run unchanged, then attaches a new follower. The new follower's first line is the header, the unpromoted run appears once as a transition from working, and the unchanged run does not appear. The negative control is executed and logged: with the base revision's baseline filter the unpromoted run does not appear and the test fails. The write paths are reckon/cli.py, reckon/crew/runs.py, reckon/crew/ticker.py and tests/test_follow_replays_the_gap.py.

§7 — A follower whose consumer is gone releases its registration

The S19 coordinator measured this from 05:20 to 05:40 CEST on 2026-09-23, in session ship-s19-20260922. A follower that had re-executed itself to reload changed source ran as python3 -c "… from reckon.cli import main; main()" crew follow … (pid 475686). When the host expired its Monitor and killed the Monitor's shell, that process survived, was reparented to init, and kept the flock on its session's registration file in the directory named by follower_dir in reckon/crew/runs.py. _follower_liveness correctly read the registration as not live, because its recorded parent_pid had exited. A freshly armed follower for the same session could not take the registration over, because the orphan still held the lock, so it streamed read-only. Every dispatch from the session was refused watcher-required for about twenty minutes. Re-arming did not help. A SIGTERM to the orphan repaired it within about twenty seconds.

A follower whose consumer has gone delivers to nobody, so holding the registration serves no reader. The follower checks its own consumer on each existing wait pass in _follow_watch_lines. The consumer is the parent process recorded at registration as parent_pid and parent_start_time. The consumer is gone when os.getppid() no longer equals the recorded parent_pid, or when the recorded parent_pid's current start time no longer equals the recorded parent_start_time. That second clause is a pid-reuse guard, the same (pid, start time) match the observer already applies to the recorded parent in reckon/crew/runs.py. A re-parent to init or to a subreaper satisfies the first clause. When the consumer is gone, the follower releases the registration and exits with status 0. It must print nothing on this path, and §3's end line is deliberately not reused, because nobody reads its output any more.

§8 — A reloaded follower keeps its lifetime deadline

Measured in session ship-s20-20260923 on 2026-09-23, the first time §3 was used. The follower was armed at 11:53 CEST with --lifetime 29m. Four commits to reckon then landed on the main branch while it ran. The host expired its Monitor at 30 minutes with no follower-end line delivered. The cause is in reckon/cli.py. The follower re-executes itself when reckon's source changes, passing its original arguments through os.execv, --lifetime 29m included. The new image anchors its deadline at its own start (started_at = clock()). So every reload restarts the 29 minutes, and during an active sprint the deadline falls after the host's cap. That is exactly when the final line matters, because code is landing.

The deadline is an absolute time fixed at the first arming. The follower passes it to its replacement image, for example as an environment variable holding the UTC epoch the lifetime ends at, and the replacement uses it in place of its own start. A reload never extends a lifetime.

Done when tests/test_follow_lifetime_survives_reload.py sets RECKON_HOME to a temporary directory and arms a follower with --lifetime 6s. It forces one reload about three seconds in, through the same trigger the follower uses for a source change, and observes the follower-end line and exit status 0 within eight seconds of the original arm, not the reload. The negative control is executed and logged: with the deadline not carried across the reload, the follower is still running eight seconds after the original arm. The write paths are reckon/cli.py and that test.

Outcome — a reload no longer restarts the lifetime. Commit bc229de1 feat(crew): carry a follower's lifetime deadline across its reload fixes the deadline at the first arming and hands it to the replacement image in the environment, which survives os.execv. The replacement reads how much of the original arming is left and spends it; it never writes a new deadline, so a reload cannot extend an arming, and a reload that arrives after the deadline ends the follower at once.

Carrying the instant in the environment rather than an argument keeps the arming's identity separate from any one image: a fresh arming by the host inherits nothing and arms from its own start, while a replacement of an armed follower continues that arming.

§9 — A watcher does not re-read every stream on every poll

Measured on 2026-09-23 at about 11:45 UTC, after imas-ambix-b6 reported that watchers were most of the login node's CPU. Five project watchers were running, for nova, imas-efit, reckon, imas-codex and imas-ambix. Averaged over their lifetimes they used 48, 48, 42, 26 and 15 percent of a core, about 60 percent of the node's four-core quota, while agent processes used about 12 percent. py-spy dump of the nova watcher placed its main thread in watch_ticker, then list_live, then _watch_stream_snapshots, then _watch_snapshot, then classify_pointer, then _background_wait_signal in reckon/crew/recovery.py, which calls observe_log, observe_stream and parse_events in reckon/_backends.py. There it read a run's stream whole with read_text and decoded every event with json.loads. It does that for every live pointer on every poll, so a watcher's cost is roughly the live pointers multiplied by their stream sizes (several megabytes each), once a second, whether or not anything changed.

The stream-derived facts a watcher needs are recomputed only when a stream has changed. A stream's parsed result is kept against its path, size and mtime, and reused while all three match. When the file has only grown, only the appended bytes are parsed. The classification result must be identical to a full re-parse.

The same parse is the dominant cost of a page load. Measured by reckon-e4 at about 17:31 local on 2026-09-23, after the discovery repair (56e13e11) removed the file-parse cost. Six py-spy samples during a /_discover/nova request all sat in one chain: discover_plans, _attach_ready_set, build_roadmap, partition_live_runs in reckon/mcp_views.py, then classify_pointer. From there it read streams by three paths: _stream_budget through observe_log and parse_events; _admission_refusal in recovery.py, through its own json.loads; and _budget_timing through _stream_completion_stamp and _terminal_stream_data in reckon/crew/promotion.py, then parse_events. Warm /_discover times tracked live-pointer count and commit rate: 49 s for reckon and 95 s for nova, against 1.3 s for imas-codex and 5 s for imas-efit. The same request varied between 1.6 s and 95 s. So the cache sits below classify_pointer and serves every caller, and all three reading paths go through it. A cache that only the watcher's call site consults leaves the page load as it is.

Done when tests/test_watch_stream_parse_is_cached.py builds a live pointer whose stream holds 20,000 events in a temporary RECKON_HOME. It runs ten watcher snapshots with the stream unchanged, counting stream parses through a counter the test installs, and asserts at most one full parse. It then appends one event and asserts the next snapshot parses only the appended bytes. After every snapshot it asserts the classification equals a full re-parse's. The same test then calls partition_live_runs ten times over that unchanged pointer and asserts that the stream is read in full at most once across all three reading paths, including _admission_refusal's. A second measure is stated as numbers: CPU time for those ten snapshots, and the wall time of one warm discover_plans call over a temporary project holding 30 such pointers, each at the base revision and at the head. The negative control is executed and logged: with the cache disabled, the parse count is ten and the test fails. The write paths are reckon/_backends.py, reckon/crew/recovery.py, reckon/crew/promotion.py and that test. The fix runs in recovery.py's serial chain, and after a-dispatch-returns-without-its-worker's sections that write promotion.py.
