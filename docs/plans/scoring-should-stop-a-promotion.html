§1 — The reviewer works, and only an error path asks for it

The independent review is built and it is good. reckon/crew/review.py carries the schema, parser and durable store; prompts/review.md carries the checklist; dispatch_review_for_run composes and launches the review a scoring run has already specified for itself; and tests/test_scoring_dispatches_its_review.py pins the behaviour, including that an unavailable lane is recorded rather than swallowed. 147 reviews are stored across four projects, and they are thorough: a sample reproduces the node's gate first-hand, replays the declared mutation at head and at base, diffs the landed scope against the declared write paths, and scans the added lines for banned labels.

None of that fires on a healthy run. The classification scoring is defined as complete-but-unreviewed — the record's own words are "no independent review is attached" — and two facts follow from where it is read:

  • The reflex is reachable only through reckon crew recover, whose docstring describes it as classifying pointers left by an interrupted session. A coordinator on the ordinary path goes dispatch → observe → complete and never calls it. The second entry point, dispatch_awaiting_reviews, is written and documented as "the reflex's entry point" and has no caller and no test.
  • reckon crew complete promotes a run in scoring without refusing. The classification names the missing review and nothing consults it at the moment the run becomes committed evidence.

Measured 2026-09-21 on imas-ambix. A five-node wave plus two earlier nodes were dispatched, verified by hand, and promoted. The project holds three stored reviews, the newest from 2026-09-17: not one node of that sprint was reviewed, and its committed ledger carries zero review-role runs. Every node was promoted past a classification that existed to stop it. The same coordinator ran recover twice — at the start of each resumed session, when the runs were still running — so the only trigger fired at the only times it could do nothing.

This is the failure the review module was written to prevent, stated in its own docstring: "a promoted run today carries a gate the worker wrote itself, which is why gate pass sits at 1.00 on every lane in the committed ledger and cannot separate one lane from another." The gate remains self-scored not because the second opinion is missing, but because the only door to it is marked recovery.

Promotion passes beside the scoring state rather than through it. The reviewer exists, is tested, and sits on a branch a healthy run never takes.

§2 — Promotion refuses a run that was never reviewed

Make the classification load-bearing at the one moment it matters. A passing implement run whose pointer classifies as scoring is refused by reckon crew complete, naming the review that is missing and the command that produces it — the same shape as the refusals that already guard the negative control, the declared scope and the impl move.

The middle column is the whole design constraint, and an earlier revision of this section got it wrong. It first reported ancestry as yes for all four, because it asked about the promote(...) commits. Those are ancestors of main by construction — promotion wrote them there. Asking about the revision that was actually promoted gives no for both failing nodes. So: if promotion records its own promote commit as the revision, the ancestry half of the sweep is a tautology and can never fail, for any failure mode. It must record the run's head.

Two distinct failure modes, and the sweep needs both paths live.

  • Never merged. The work is not an ancestor and the content is absent. Both instances above are this. It fails on the ancestry half — but only when ancestry is measured on the right sha.
  • Merged then dropped. The work is an ancestor and the content is still absent, because a merge conclusion committed an index that reverted it. This is the hazard the user-global rules describe. It passes ancestry and fails on the content marker, which is why the marker half is not redundant.

The removal case sits inside the second mode and is the quietest of all: where the change deleted something, a marker-present check finds nothing wrong, so the assertion has to require the removed marker's absence. bench-single-owner is exactly that shape.

One mode has an instance and the other is prophylactic, and the section says which rather than implying both. The second mode was looked for rather than assumed: across the last 40 merges of the repository where both instances arose, every path the branch changed since the merge base and main did not was compared against the merge result.

The zero is trustworthy because the instrument was aimed before it was believed: a detector that skipped every merge returns the same number, so the 38-of-40 comparison count is reported beside it, the two skips are merges with no branch-only path at all, paths both sides changed are excluded as genuine conflict resolutions rather than counted, and the same comparison was shown to fire on a known-absent case as a positive control. So the merges that happened were faithful, and both real instances are mode 1. The content-marker half is what catches what actually happens here; the ancestry half guards a case this repository has not produced. Both stay, and neither is described as the other.

The prospective and retrospective checks are not two spellings of one idea, and the difference decides what each must declare. The retrospective scan compares the merge result against the branch's whole content for a path, so it is symmetric by construction: a dropped addition and an undone deletion are the same measurement — the merge does not match the branch here — and neither needs its own case. The prospective sweep cannot do that, because at promotion time there is a revision and a target head but no branch to diff against wholesale. It asks whether a marker is present, which means it has to be told in advance whether presence or absence is the passing answer. That asymmetry is the entire reason the removal assertion exists, and it is a property of the cheaper check rather than an oversight in it.

Both controls are built and fire: a merge dropping an added file and reverting an edited one, and a merge restoring a file the branch deleted and a line the branch removed. Should it ever be cheap for the sweep to diff against the promoted head wholesale, it becomes symmetric too and the removal assertion falls out of it — a larger change than the one specified here, and the marker form works today.

§2g — One gate per kind of work, selected by what the run produced

§2f widens one gate. That is the substrate and not the design: a single rubric asked of every node is either too loose for code or too heavy for a report. An implementation and an investigation fail in different ways, so they need different reviews and different gates. The design below is shaped by three constraints together — catch as much as possible, stay quick enough to be reflexive, and run at high concurrency on the free lane.

Selection is by artifact, never by role name. That is the lesson of §2f: a role is a routing label a coordinator chose, while what a run wrote is a fact. A run that changed a tracked source file gets the implementation profile whatever its role was called. A run that changed only a report gets the investigation profile. The two are not exclusive: a run that wrote source, a test and a figure is judged by three profiles.

§3 — The reflex fires on the path a healthy run takes

Give dispatch_awaiting_reviews the caller its docstring already assumes. The sweep is idempotent by construction — a run whose review is stored or in flight is left alone — so it is safe to call from a cadence rather than from a repair.

The natural site is the follower's existing periodic sweep, which already resumes runs whose external wait has ended: a session watching its own fleet is exactly the thing that should notice a run has entered scoring. Calling it there means the review is dispatched by the same mechanism that tells the coordinator the run finished, rather than by the coordinator remembering.

The refusal path stays as designed: a scope, member, follower, context-fit or budget refusal is reported against the run and the sweep continues to the rest of the fleet. A sweep that stops at the first refusal would make one unavailable lane look like a quiet one.

The sweep must waive the unreconciled-runs fence, or it deadlocks on the very runs it exists to clear. A run awaiting review is an unreconciled run, and once it passes the grace window the fence refuses new dispatches for the whole project until the backlog is reconciled — while the reconciling action for each of those runs is the review dispatch the fence is refusing. Measured 2026-09-21 on imas-ambix: three runs in scoring, each carrying a next_action that was its own review dispatch, and that dispatch refused with exit 6 naming those same three runs as the reason. The remedy was the thing the fence blocked.

So the reflex passes --allow-unreconciled-runs, and the waiver it records is honest rather than a loophole: the backlog genuinely must remain, because clearing it is what the dispatch does. A review run must also never itself count toward that backlog for its own source run, or the second review of a wave is refused by the first. Both properties need a test, because both failures look like an idle fleet rather than an error.

Landed 2026-09-21, and it immediately exposed a defect of its own: the reflex dispatches a generic brief. The composed done-when is, verbatim, "the review for <run> stores a parsed record scoring all 5 dimensions in the range 0..20" — no reachability items, no inverse-direction control, no propagated findings. None of the clauses that produced today's value.

Every review that found something real today was hand-written: the role-spelling disagreement between the two exemptions, the two fail-open holes in the prescription judgement, the substituted negative control. Each brief named specific things to check. Set against the four-node measurement in §2g — where a reviewer found a defect once and three more instances came only from writing it into the next brief, and one round returned exactly the two items its brief named and nothing else — the consequence is exact: the brief bounds what a review finds, so automating the dispatch while leaving the brief generic scales the weakest version of the review rather than the review.

This is the same substitution, pointed at this plan's own repair. status: parsed stood in for the record is complete; a green gate stood in for the change is correct; and now a review was dispatched stands in for a review was asked anything. The reflex is correct and incomplete, and the incompleteness is invisible precisely because the reviews still come back scored.

So the composed dispatch must carry the profile, not the generic line. §2g's per-kind profile is selected from the run's own changed paths, which the reflex already has; the accumulated findings are one further sentence. Until it does, an automatic review is weaker than the manual one it replaced, and the ledger cannot tell them apart.

A discarded run renders as a promotion, which is the costliest false positive this plan can produce. At reckon/crew/recovery.py:3423 every departed pointer is reported promoted, with no ledger check:

for run_id in (item for item in known if item not in current):
    changes.append((departed, str(known[run_id]["state"]), "promoted"))

A pointer departs for several reasons — promotion, crew discard, manual removal — and the follower calls them all the same. This plan's whole claim is that a promotion cannot happen without a stored review, so a reader watching the ticker see review-of-… abandoned → promoted after a discard concludes the gate was satisfied. Measured on imas-ambix 2026-09-21: nothing was promoted, the ledger carried zero rows for that run and no review record existed. The ledger being right does not help a reader watching the stream, which is what the follower is for. The distinguishing fact is available at render time — a promotion writes a ledger row and a discard does not.

And a reflex review can produce nothing and still wedge the roster. A reflex-dispatched review ran ten seconds, ended exit_code: 0, outcome: success, and wrote no manifest, no review record and no final output; the pointer classified abandoned. It had auto-created a roster member, and a member is released by promotion — which that run can never reach — so crew member add stays blocked until the roster write is committed by hand. A failed automatic review therefore costs manual repair rather than nothing, which is the opposite of what a reflex is for. §4 — A review that is quick enough to be reflexive

A review nobody waits for is as useless as one nobody asks for. The checklist in prompts/review.md is thorough and it must stay discriminating while finishing in a few minutes, because a reflex that adds half an hour to every landing will be waived away.

The second is not bureaucracy, it is the lesson this repository's own fleet taught on 2026-09-21: three of four workers in one wave skipped a step that was declared in their prompt and absent from their measure. The hit rate is the argument for the feature. Reported from imas-efit, 2026-09-21: seven solver merges, every one of which the coordinator had hand-read the diff of before merging and promoted. The claim this plan rests on is therefore not that unreviewed work is bad — it is that coordinator self-audit is measurably not a substitute for it, which is a stronger and more falsifiable claim.

None of the three defects was in the diff's correctness, and that reshapes §4's checklist. All three were in what the diff did not reach, and a reviewer reading only the changed lines would have missed every one:

  • An absence. A test rail authored three days earlier was never registered — its own listfile said the directory was not yet reachable and named the missing add_subdirectory line. Eleven merges later a grep found three self-references and no wiring. Nothing in any diff was wrong; the defect was a line never added. The rail in question was the one written to catch a silently disconnected mechanism, so the rail written to detect disconnection was itself disconnected.

A Fortran change carried a second saddle's psi; the review traced it into C++ and found the boundary value stamped over every X-point node, discarding the exact quantity the carrier transports — with a comment two lines below acknowledging that secondary X-points sit at a different psi. Both files were correct in isolation.

So the checklist's strongest item is reachability, not correctness. Recovered by opening the cited line, the finding is one of the sharpest of the sprint: the test builds its expected argument vector from the same constant the production code uses to build the real one, so it compares the code against itself. Remove a field from that constant and the expectation moves with it — green suite, and the probe silently stops reading a field the plan requires. A second helper in the same file does it again with another constant. That is a gate written by the thing it gates, one level down from the defect this plan opened on.

Two repairs, and the cheaper one is a heuristic worth having only because the better one is not free. Checked against this workstation's whole review store: of 498 findings, 3 (0.6%) do not end in terminal punctuation, median length 396 characters, tenth percentile 225 — and the shortest finding anywhere is exactly the 46-character truncation. So "reject a finding that ends without terminal punctuation and names no concrete input" costs almost nothing in false positives and catches this. The sound repair is to make parsed mean the parse consumed the whole output, landing a cut-off record as partial, because that fixes the claim rather than one symptom of it.

§5c — A review describes a revision, and nothing records which

Acting on a review invalidates it, and the guard cannot tell. The healthy cycle is: the review finds defects, a worker repairs them, the run promotes. At that moment the stored review describes code that no longer exists — and §2's refusal is satisfied by any complete stored review, so the repaired run promotes on the strength of a record of the thing it was repaired from. The guard reads the presence of a review as evidence about the code being promoted. It is evidence about a revision, and the two stopped being the same revision at the first repair.

The revision is recorded. It is recorded under five different names, and the parser knows none of them. An earlier revision of this section claimed no stored review records the revision it read. That was wrong, and it was wrong in the way this page keeps warning about: it was read off parse_review's output rather than off the store. Counted across the 151 stored reviews on this workstation:

The repair is therefore standardisation, not invention. Adopt one of the names already in the store — reviewed_base_sha with reviewed_head_sha, because the pair distinguishes the base from the landed head where a single commit list does not, and because this repository already writes it — put it in the schema, treat a record lacking it as incomplete on the same principle that governs an absent dimension, and have §2's refusal compare it against the commits being promoted. A timestamp comparison is the tempting cheap version and it is wrong: it answers which was written first, not which revision was read.

A recheck destroys the review it rechecks. The store is one file per reviewed run — review_path(project, reviewed_run_id) — and store_review renames atomically into that path. So a second review of the same run does not sit beside the first; it overwrites it, with its findings. The author caught this with three rechecks in flight against the paths holding their originals, whose eleven findings and scores of 79, 86 and 89 are the measurement this plan's §5 rests on. Copying them aside is not a fix.

A review record has now been lost, not nearly lost. Recorded 2026-09-21: node-probe's round-two review — score 94 at revision f12261e8, carrying the unreachable-job-bound finding that the round-one repair had introduced — was overwritten by the round-three recheck before its author could copy it aside. The finding survives only because it had already been acted on. The store's own record of why the third repair was needed no longer exists.

And the interim naming failed for a reason worth keeping. The surviving records were first set aside under a round number, which was wrong within minutes because nobody knew the count in advance. Rekeying them by the revision each reviewer read — <run>.at-<sha>.json — is the same shape as the reviewed_base_sha normalisation above: accumulation by construction, rather than by someone remembering to copy a file before each recheck lands.

Third form: a stored verdict revised in place, with nothing recording the move. Measured on imas-ambix 2026-09-21 — same reviewer, same reviewed revision 7adfc3a30700, the same four findings on the same files and lines, and the evidence dimension revised from 18 to 15 twenty-four minutes later, taking the total from 90 to 87. Not a recheck and not a second reviewer. A reader sees 87 and cannot know it was ever 90.

If a reviewer reconsiders its own evidence that is good behaviour and should not be stopped — but it has to be visible. It already corrupted a real row: a coordinator read the 90, acted on its four findings, and promoted the review run with an outcome stating "scored 90 at 7adfc3a3". That ledger row now contradicts the store it cites. The findings being identical was luck; a revision changing which findings existed would have left a coordinator acting on a record that no longer said what it read.

This is the hard argument for §2g's refusal to gate on a score. That section rejects thresholds because a threshold invites tuning — a soft reason. The hard one is that a threshold would be non-deterministic: the same run, at the same reviewed revision, is promotable at 12:40 and not at 13:00, with nothing in the record explaining the difference. It is worse than staleness, because staleness at least leaves a revision to compare against; here the revision is identical and the verdict moved underneath it.

And whatever consults a review must record what it read. Today's gate checks status == "parsed" and writes that a review was attached, without naming which record it saw. Recording the figure consulted and the record's modification time on the row makes a later disagreement detectable rather than silent — the same discipline as recording the revision a review read, one level up.

Key the store by the reviewing run instead, and superseding falls out. An append-only history makes "which review is current" a revision comparison — the one whose recorded head matches the commits being promoted — rather than a filesystem accident, and the superseded ones stay readable as what was found and when. That last part is not sentiment: the case for the whole mechanism is those eleven findings, and a store that silently overwrites them destroys its own evidence.

Why this is the same defect as every other one on this page. A complete review is a true statement standing in for the one that was needed. It is the discriminator of §5b run on our own guard: what would make this field wrong while it still printed the same value? — a review that is complete, parsed, stored, and about different code.

The head key is now granted, read and fenced by one head. Three surfaces decide what a review's head key means and each was correct on its own while they disagreed: the reflex composed the reviewer's write path from review_path(project, run_id) alone, so a reviewer told to write the head-keyed path was refused it; the classifier read the newest record on disk rather than the review of the head it was classifying; and promotion could refuse a record the other two accepted. Each now resolves the head from the run's own tree and passes it through: _review_dispatch_fields grants the head-keyed path beside the legacy one and _review_dispatch_argv emits both as --write-path; _stored_review reads through one selector that names the head; and _review_for_promotion delegates to the same selector, so the gate and the classifier cannot drift. A legacy record carrying no revision pair is accepted when the head it describes — reconstructed by git rev-list -1 --before=<timestamp>, not by comparing timestamps — equals the head the promotion asserts, with no waiver; and a refusal names two revisions as a disagreement rather than one revision twice. The remedy a refusal prints now cites resolved commit shas, and prose in a manifest's commits field yields either a value that resolves or no value at all, never one that fails.

§5d — A repair can introduce the defect it was repairing

§5c says a promotion must refuse a review that predates the head. That fence is necessary and it is not sufficient, and the difference was measured rather than reasoned.

The case. An imas-ambix node was reviewed at 86 with two findings, repaired, and re-reviewed at 94. Both original findings were confirmed fixed and the recheck read f12261e8, the current head — so a staleness check passes it, correctly. The recheck nonetheless carried one finding, and the repair had caused it: a declared fifteen-second bound on a scheduler call that no production path can reach, because the caller hands its own ten-second timeout down two frames. A knob that does not do what it says — the same class as the defect being repaired, reintroduced one layer up by the fix.

Had that node been promoted against its original verdict after a hand-check of the repair — which is what happened for four earlier nodes that day — the new defect would have shipped with a review on the row saying 86. So the second fence is its own rule: a repair is not promotable against a review whose findings it changed. The review that matters is the one that read the repair, and a staleness comparison cannot supply it because the stale review is not the problem — the superseded one is.

And the store destroys exactly the record that proves this. Verified here against the imas-ambix store: the recheck overwrote the original at 09:15, one minute before a hand-made copy was taken for unrelated reasons.

§5i — A review's triage expires when the module gets its first caller

The call-site emission turned out to be load-bearing input to severity, not an audit field, and nobody designed it that way. On its first use outside this session a reviewer emitted CALL_SITES: none and triaged all four of its findings as follow-on — including one that reads as serious on its face: a compressed roll aborts the entire ingest pass, so a directory holding serve.jsonl beside serve.jsonl.2.gz ingests nothing at all.

That triage is correct today, because nothing in production constructs the reader. It becomes wrong the moment the wire node lands. So a finding's severity is a function of the call-site count at the time of review, and a review's triage therefore expires when the module gets its first caller — and nothing re-triages on that event. A gate that refuses on blocking findings will silently change its verdicts once callers exist, without any review being re-run and without anything recording that the ground moved.

This is the same defect as the stale review in §5c, one level up: there the record described a revision that no longer exists, here the record describes a reachability that no longer holds. Both are records that were true when written and become false without being touched, and the call-site count is what makes the second one detectable: a stored review carrying call_site_count: 0 against a module that now has callers is a mechanical comparison, not a judgement. That is the re-triage trigger, and it costs one query.

The reviewer also read the plan unprompted, and that should not be encouraged. Its finding cites the plan file and line to check whether the absence of callers was intended — which is the adjudication §5f deliberately placed outside the reviewer. The brief asked only for the count. It is worth knowing reviewers will reach for the plan, and worth not building on: a reviewer that reads the plan is a reviewer the plan can mislead, and the count-versus-intent comparison belongs in a gate where both halves are visible and neither is supplying the other's context.

Done when a stored review's call_site_count is compared against the module's current caller count at promotion, and a run whose reviewed count was zero while callers now exist is refused with both figures named, asserted with a synthesised record and a tree that gained a caller after it was written; and the refusal names re-review rather than a waiver, because the finding severities themselves are what went stale.

§6 — A reviewer that can see the figure

The text reviewer reads a diff. It cannot open a rendered figure, and the figure rules this repository enforces are visual ones: legible at a glance, high data-ink, no gradients or decorative fills, text that clears contrast on its background, and — the rule most often broken — never an image of what is naturally a table.

A separate figure-review role reads the rendered artifact and judges it against those rules. It reports defects and obvious failures, and it has exactly one thing it may write: the figure's caption. A caption is the one part of a figure that is prose about the image rather than the image itself, and it is the part most often left as a restatement of the title. Everything else the reviewer finds is flagged for the node that drew it, on the same flag-never-fix rule the text reviewer follows: a reviewer that redraws becomes a second author with no reviewer, and its findings stop being falsifiable because the evidence moved.

This role requires a lane that can read an image. That is a capability requirement, not a preference: a text-only lane cannot serve it at all, and routing it to one would produce a confident review of a file the reviewer never saw. The role therefore declares the requirement and dispatch refuses a lane that does not meet it, in the same way a context-fit refusal already rejects a node too large for its window. Which lane satisfies it is a runtime routing choice and is deliberately not fixed here.

The trigger is narrow on purpose: a node is figure-reviewed when its landed diff touches an image under a figures directory. Most nodes never are, so the cost falls only where a figure exists.
