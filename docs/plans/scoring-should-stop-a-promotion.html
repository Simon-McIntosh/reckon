§1 — The reviewer works, and only an error path asks for it

The independent review is built and it is good. reckon/crew/review.py carries the schema, parser and durable store; prompts/review.md carries the checklist; dispatch_review_for_run composes and launches the review a scoring run has already specified for itself; and tests/test_scoring_dispatches_its_review.py pins the behaviour, including that an unavailable lane is recorded rather than swallowed. 147 reviews are stored across four projects, and they are thorough: a sample reproduces the node's gate first-hand, replays the declared mutation at head and at base, diffs the landed scope against the declared write paths, and scans the added lines for banned labels.

None of that fires on a healthy run. The classification scoring is defined as complete-but-unreviewed — the record's own words are "no independent review is attached" — and two facts follow from where it is read:

  • The reflex is reachable only through reckon crew recover, whose docstring describes it as classifying pointers left by an interrupted session. A coordinator on the ordinary path goes dispatch → observe → complete and never calls it. The second entry point, dispatch_awaiting_reviews, is written and documented as "the reflex's entry point" and has no caller and no test.
  • reckon crew complete promotes a run in scoring without refusing. The classification names the missing review and nothing consults it at the moment the run becomes committed evidence.

Measured 2026-09-21 on imas-ambix. A five-node wave plus two earlier nodes were dispatched, verified by hand, and promoted. The project holds three stored reviews, the newest from 2026-09-17: not one node of that sprint was reviewed, and its committed ledger carries zero review-role runs. Every node was promoted past a classification that existed to stop it. The same coordinator ran recover twice — at the start of each resumed session, when the runs were still running — so the only trigger fired at the only times it could do nothing.

This is the failure the review module was written to prevent, stated in its own docstring: "a promoted run today carries a gate the worker wrote itself, which is why gate pass sits at 1.00 on every lane in the committed ledger and cannot separate one lane from another." The gate remains self-scored not because the second opinion is missing, but because the only door to it is marked recovery.

Promotion passes beside the scoring state rather than through it. The reviewer exists, is tested, and sits on a branch a healthy run never takes.

§2 — Promotion refuses a run that was never reviewed

Make the classification load-bearing at the one moment it matters. A passing implement run whose pointer classifies as scoring is refused by reckon crew complete, naming the review that is missing and the command that produces it — the same shape as the refusals that already guard the negative control, the declared scope and the impl move.

A refusal that cannot be overridden becomes a reason to stop using the tool, so it carries an explicit waiver that records why on the promoted row, exactly as --no-impl-change and --accept-path do. An unreviewed promotion then remains possible and remains visible, which is the difference between a discipline and an obstacle.

A review run must be exempt in the CLASSIFIER, not only at promotion, and this is the defect that would make the reflex unbounded. Measured 2026-09-21 on imas-ambix: a completed review run classifies as scoring exactly like the node it reviewed, and its own next_action reads --node review-of-review-of-node-probe. Reviews therefore require reviews, without limit. Today that is a cosmetic oddity because nothing acts on the classification; with §3's sweep wired it becomes a fleet that never drains, each review dispatching another. Exempting the role only at the promotion boundary would leave the sweep recursing, so the exemption belongs where the classification is computed.

§2c — A promotion asserts landed work that never landed

§2 makes promotion refuse a run with no review. This section is the same command refusing a different false statement, and it is the worse of the two: crew complete writes a durable "passed" whose truth depends on a merge that is a separate, later, unverified act. Nothing checks that the act happened.

Measured on imas-ambix, 2026-09-21, and verified from this checkout. Four nodes carry promote(...): passed commits on main. All four commits are ancestors of main. Two of them assert work that is not in the tree:

Which sha you ask about decides whether the defect is visible at all.

Nothing is lost — both worktrees are clean and hold their commits — but the ledger asserts five of five landed against a tree carrying three, the live pointers are gone because promotion deleted them, and no surface reports the gap. The coordinator who produced it did not notice across two nodes.

The middle column is the whole design constraint, and an earlier revision of this section got it wrong. It first reported ancestry as yes for all four, because it asked about the promote(...) commits. Those are ancestors of main by construction — promotion wrote them there. Asking about the revision that was actually promoted gives no for both failing nodes. So: if promotion records its own promote commit as the revision, the ancestry half of the sweep is a tautology and can never fail, for any failure mode. It must record the run's head.

Two distinct failure modes, and the sweep needs both paths live.

  • Never merged. The work is not an ancestor and the content is absent. Both instances above are this. It fails on the ancestry half — but only when ancestry is measured on the right sha.
  • Merged then dropped. The work is an ancestor and the content is still absent, because a merge conclusion committed an index that reverted it. This is the hazard the user-global rules describe. It passes ancestry and fails on the content marker, which is why the marker half is not redundant.

The removal case sits inside the second mode and is the quietest of all: where the change deleted something, a marker-present check finds nothing wrong, so the assertion has to require the removed marker's absence. bench-single-owner is exactly that shape.

One mode has an instance and the other is prophylactic, and the section says which rather than implying both. The second mode was looked for rather than assumed: across the last 40 merges of the repository where both instances arose, every path the branch changed since the merge base and main did not was compared against the merge result.

Searching for a merged-then-dropped instance, with the instrument checked first.
merges scanned40
merges with branch-only paths actually compared38
branch-only paths checked220
merges dropping branch-only content0

The zero is trustworthy because the instrument was aimed before it was believed: a detector that skipped every merge returns the same number, so the 38-of-40 comparison count is reported beside it, the two skips are merges with no branch-only path at all, paths both sides changed are excluded as genuine conflict resolutions rather than counted, and the same comparison was shown to fire on a known-absent case as a positive control. So the merges that happened were faithful, and both real instances are mode 1. The content-marker half is what catches what actually happens here; the ancestry half guards a case this repository has not produced. Both stay, and neither is described as the other.

The prospective and retrospective checks are not two spellings of one idea, and the difference decides what each must declare. The retrospective scan compares the merge result against the branch's whole content for a path, so it is symmetric by construction: a dropped addition and an undone deletion are the same measurement — the merge does not match the branch here — and neither needs its own case. The prospective sweep cannot do that, because at promotion time there is a revision and a target head but no branch to diff against wholesale. It asks whether a marker is present, which means it has to be told in advance whether presence or absence is the passing answer. That asymmetry is the entire reason the removal assertion exists, and it is a property of the cheaper check rather than an oversight in it.

Both controls are built and fire: a merge dropping an added file and reverting an edited one, and a merge restoring a file the branch deleted and a line the branch removed. Should it ever be cheap for the sweep to diff against the promoted head wholesale, it becomes symmetric too and the removal assertion falls out of it — a larger change than the one specified here, and the marker form works today.

Write paths. reckon/crew/promotion.py, and a new test file.

Done when a promotion records the run's own head as the promoted revision — asserted directly, because recording the promote commit instead makes the next clause unfalsifiable — and a sweep asserts both halves against the target head: the promoted revision is an ancestor, and a marker the change introduced is present. The sweep reports a promotion whose work is not an ancestor, asserted against a synthesised repository in that state, and one whose ancestry passes while its marker is absent, asserted against a second repository reproducing exactly that pair, so neither failure mode rests on the other's test; a promotion whose content did land reports nothing, asserted, because a check that fires on the healthy case is a check nobody keeps; and the negative half is covered too — a change whose purpose was a removal is asserted by requiring the removed marker's absence, since a dropped deletion is as silent as a dropped addition. Promotion does not merge: the assertion is a later sweep, not a side effect of landing.

§2g — One gate per kind of work, selected by what the run produced

§2f widens one gate. That is the substrate and not the design: a single rubric asked of every node is either too loose for code or too heavy for a report. An implementation and an investigation fail in different ways, so they need different reviews and different gates. The design below is shaped by three constraints together — catch as much as possible, stay quick enough to be reflexive, and run at high concurrency on the free lane.

Selection is by artifact, never by role name. That is the lesson of §2f: a role is a routing label a coordinator chose, while what a run wrote is a fact. A run that changed a tracked source file gets the implementation profile whatever its role was called. A run that changed only a report gets the investigation profile. The two are not exclusive: a run that wrote source, a test and a figure is judged by three profiles.

Profiles. Each names the failure it exists to catch, taken from what reviews have actually found here rather than from what seemed thorough.
ProfileSelected when the run changedIts one decisive check
implementation a tracked source path Reachability. Does the new path execute under a registered test, does a value survive the boundary it crosses, does a log line offered as evidence gate the thing it is offered for. Three of three defects found on imas-ambix were things the diff did not reach.
test a tracked test path The declared mutation is the applied one. Two of two multi-part nodes here declared one control and applied a different, adjacent one. Replay the declaration; require red for the stated reason; require the replay to run rather than die in collection.
investigation only an untracked report or no path Citations resolve and say what is claimed. Re-open a sample of the report's anchors; require an absence claim to carry a positive control, since an absence and an unaimed instrument return the same empty result.
document a plan, evidence or prose path Every number is traceable and none of it rots. A recorded absolute that moves on its own is a fuse; a pointer to a renamed anchor is worse than none.
figure an image under a figures directory It is not a picture of a table, and its labels clear contrast. §6 owns this one; it needs a lane that can read an image.
repair anything, when the run closes another run's findings What the repair introduced. Measured across three repair pairs: 11 of 11 findings closed, and 5 new found, 2 of them created or left unprotected by the repair itself. Roughly a fifth of repairs need this.

Gates are element checks, not score thresholds. A threshold invites tuning and turns a review into a number to beat; the score stays, for calibration and lane comparison, and gates nothing. A promotion is refused when a selected profile has no stored review, or when the stored review is missing an element the profile requires. That also makes the refusal legible: it names the profile and the missing element rather than a figure.

The dimensions are per profile, and one of the current five is already ink. Measured over twelve reviews on imas-ambix, correlation against total: evidence 0.86, durability 0.84, goal_fidelity 0.69, scope_discipline 0.51, fit 0.53. fit never leaves 16–19 and has the smallest spread on the page — it carries almost no ranking information and should be dropped or redefined. scope_discipline scores similarly by correlation and must be kept: its shape is one 15 against everything else 18–20, so it is a rare-fire detector behaving correctly, and retiring it on correlation would remove the wrong one. A flat dimension is ink; a silent one may be a detector.

What keeps the load down. One review per run per selected profile, never one per file. Each profile reads a bounded set and is refused the rest, as §4 already requires. Profiles that do not apply cost nothing — most runs select one. The free lane carries 64 concurrent, so a twenty-node wave reviews inside a single ten-minute window rather than serially; concurrency is what makes a per-kind review cheaper than one heavy rubric, not more expensive.

Done when profile selection is computed from a run's changed paths and asserted for each of the six against a synthesised run, including a run selecting more than one and a run selecting none; each profile's required elements are declared in one place that the prompt and the parser both read, asserted by the falsifier that already pins prompt against schema; a promotion is refused naming the profile and the missing element rather than a score, asserted per profile; the review role stays exempt; and the wall time of one wave's reviews is recorded against the ten-minute bound with its concurrency, because a design justified by concurrency has to show it.

§3 — The reflex fires on the path a healthy run takes

Give dispatch_awaiting_reviews the caller its docstring already assumes. The sweep is idempotent by construction — a run whose review is stored or in flight is left alone — so it is safe to call from a cadence rather than from a repair.

The natural site is the follower's existing periodic sweep, which already resumes runs whose external wait has ended: a session watching its own fleet is exactly the thing that should notice a run has entered scoring. Calling it there means the review is dispatched by the same mechanism that tells the coordinator the run finished, rather than by the coordinator remembering.

The refusal path stays as designed: a scope, member, follower, context-fit or budget refusal is reported against the run and the sweep continues to the rest of the fleet. A sweep that stops at the first refusal would make one unavailable lane look like a quiet one.

The sweep must waive the unreconciled-runs fence, or it deadlocks on the very runs it exists to clear. A run awaiting review is an unreconciled run, and once it passes the grace window the fence refuses new dispatches for the whole project until the backlog is reconciled — while the reconciling action for each of those runs is the review dispatch the fence is refusing. Measured 2026-09-21 on imas-ambix: three runs in scoring, each carrying a next_action that was its own review dispatch, and that dispatch refused with exit 6 naming those same three runs as the reason. The remedy was the thing the fence blocked.

So the reflex passes --allow-unreconciled-runs, and the waiver it records is honest rather than a loophole: the backlog genuinely must remain, because clearing it is what the dispatch does. A review run must also never itself count toward that backlog for its own source run, or the second review of a wave is refused by the first. Both properties need a test, because both failures look like an idle fleet rather than an error.

Two blockers, both found by §2's worker, and the reflex is unsafe to turn on until each is closed. Neither was visible when this section was written.

The sweep would dispatch a review of a review, without limit. classify_pointer in reckon/crew/recovery.py returns scoring for a completed review-role run and composes a review of that run as its own next_action — there is no role exemption in that function. §2 exempted the review role at the promotion boundary, which is the right place for promotion and the wrong place for this: the sweep never reaches promotion. So wiring the sweep before the classifier is exempted turns one landed node into an unbounded chain of reviews reviewing reviews, each one a real dispatch against a real member. This is the reason §3 cannot be a one-line caller.

The reviewer runs on the lane that did the work. _review_dispatch_argv ends in a hardcoded --local, and dispatch_review_for_run passes local=True, so a review composed for a local-lane run is dispatched to the local lane. That contradicts both governing statements: background-agent-fitness-and-dispatch-scope §1 asks for scored reviews "on lanes other than the one that did the work", and the ruling in force requires every local-lane promotion to sit behind "a short review on a metered lane". A reviewer sharing the worker's lane is also the weaker instrument on the merits — the gate and the review then come from the same model, which is a smaller version of the defect this plan exists to fix, where the gate and the diff come from the same worker.

Neither is a hard-coded lane name in the repair. Which lane reviews is a runtime routing choice; what the code must express is that the review resolves a lane different from the run's own, with the choice left to flight config. A fixed --local and a fixed --backend codex are the same mistake with different defaults.

One defect is already there to fix, and as of 2026-09-21 it is still there. The sweep's own refusal accumulator in dispatch_awaiting_reviews appends a generator expression rather than the report — reckon/crew/recovery.py:523, verified at that line after the classifier exemption landed — so a refused review is recorded as an unreadable object and json.dumps raises on the CLI's emit path. It has never been exercised because the function has no caller; giving it one exposes it. An earlier revision of this paragraph said it "is repaired here" before any node had touched it, which an independent review caught: a claim written ahead of the work, sitting in the section that warns about records outliving what they describe.

The two role exemptions disagree, and the test written to hold them together cannot fail. recovery._pointer_role accepts either spelling — the record root, falling back to node.role — and its docstring states dispatch writes both. promotion._require_review_waiver reads record.get("role") at the root only. So a record carrying its role under node.role is review-role to the classifier and not review-role to the promotion guard: the classifier exempts it from scoring while the promotion boundary demands a review it will never get. The agreement test builds both records with the root spelling, so it passes without ever reaching the disagreement.

The repair is to read the role through one accessor, not to widen the second reader. Two spellings with two readers is how they drifted; a third reader would be the same defect again. The agreement test must construct its record with the role under node.role only, since that is the spelling neither side was tested against.

Where the cadence actually lives. There is no reckon/crew/follow.py. The follower's periodic work is _sweep_on_cadence inside _follow_watch_lines in reckon/cli.py, which calls reckon.crew.resumption.sweep and nothing else. Adding the review pass to sweep itself therefore gives the reflex three callers at once — the follower's cadence, crew resume-ready, and the MCP sweep action — from one site, and keeps the follower's own code unaware of reviews.

Write paths. reckon/crew/resumption.py, reckon/crew/recovery.py, tests/test_review_reflex_sweep.py (new).

Done when a run entering scoring while a follower is armed has its review dispatched without any command being issued, asserted; the sweep run twice over the same fleet dispatches exactly one review per run, asserted; a refusal on one run leaves the others dispatched, asserted; and dispatch_awaiting_reviews has the test coverage it currently lacks entirely.

A review is evidence about a revision, and acting on it invalidates it. The ordinary loop is: review finds defects, worker repairs them, run promotes. After the repair the stored review describes code that no longer exists, so the promotion attaches a verdict reached on different bytes. Measured 2026-09-21: a node reviewed at 89 with five findings repaired all five and added three commits; its stored review still reads as that run's review, and nothing anywhere compares the two revisions.

The schema already carries commits_read, and the reviewer that produced this record left it null — so even the detectable case was not detected. Two properties follow. The reviewer must record the revision it read, and a null there is an unparseable review rather than a scored one, because a verdict whose subject is unknown cannot be checked against anything. And promotion must compare that revision against the run's head: equal promotes, moved is reported, and the coordinator either re-reviews or records why the repair does not need one. Silently attaching a stale verdict is worse than having no review, because it reads as independent evidence and is not.

Classifier exemption landed. §4 — A review that is quick enough to be reflexive

A review nobody waits for is as useless as one nobody asks for. The checklist in prompts/review.md is thorough and it must stay discriminating while finishing in a few minutes, because a reflex that adds half an hour to every landing will be waived away.

Two changes, in tension, and both required. Bound the work: the reviewer reads the goal, the done-when, the declared paths, the manifest and the diff — it does not re-derive the implementation, re-run the full suite, or review code the node did not touch. Enumerate the verdicts: every checklist item carries an explicit verdict, and the reviewer's own done-when requires that every item has one.

The second is not bureaucracy, it is the lesson this repository's own fleet taught on 2026-09-21: three of four workers in one wave skipped a step that was declared in their prompt and absent from their measure. A reviewer asked for a summary will skip items in exactly the same way, and a clean summary is indistinguishable from a thorough one. Per-item verdicts make the skipping visible; a summary hides it.

Completeness for promotion stays the five dimensions, and this is a cross-project constraint rather than a preference. _review_is_complete (reckon/crew/recovery.py) is what separates promotable from scoring, and it tests the five dimension scores. There are 147 reviews already stored across four projects and live scoring runs in other sessions right now; folding item verdicts into that predicate would mark every one of them incomplete and — once §2's refusal is in the installed code — refuse promotions in projects this plan never touched. So the item verdicts are recorded and their absence is named, exactly as an absent dimension is named today, and the aggregate is withheld rather than taken over the items that happen to be present. That is what "rejected rather than scored over fewer items" asks for, and it is the half that makes skipping visible; requiring them is the prompt's job, in the reviewer's own done-when, where it binds new reviews without rewriting the meaning of old ones.

One stale line to correct in passing. reckon/crew/review.py's module docstring still reads "Nothing here is wired into dispatch, promotion, recovery or the ticker". That was true when it was written and is now false — promotion.py, dispatch.py and recovery.py all call into it. The file is inside this section's fence, so the sentence is corrected here rather than left to mislead the next reader.

The checklist items are the five read targets the prompt already enumerates — goal, done_when, declared write paths, manifest, diff — not the five scored dimensions, which carry their verdicts as SCORE lines today. The per-item verdict is therefore a new emitted line, and rejecting a review that omits one is a parser change: reckon/crew/review.py is inside the fence for that reason. The falsifier that pins the prompt against the schema is tests/test_review_scoring.py::test_prompt_is_read_from_disk_at_call_time_and_names_every_dimension; extending it to the checklist items is an edit to that file.

Write paths. reckon/crew/prompts/review.md, reckon/crew/review.py, tests/test_review_scoring.py, tests/test_review_prompt_contract.py (new).

Done when a parsed review carries a verdict for every checklist item and a review missing one is rejected by the parser rather than scored over fewer items; the falsifier that already checks the prompt names every schema dimension is extended to the checklist items; and the median wall time of the reviews dispatched in §5 is recorded against a stated bound.

What one review was worth, measured before this plan was implemented. The first independent review dispatched on imas-ambix, 2026-09-21, took about ten minutes on a free lane and returned two defects with file, line and reproduction. The second is an inert parameter — a card reader accepting a timeout it never passes on, demonstrated by calling it with a fifty-millisecond timeout against a two-second command and measuring 2.07 seconds. The first is worse and is the reason this section exists:

The node was required to map card indices through SLURM_STEP_GPUS, "asserted against a fixture where the two differ". It did exactly that, and its gate was green. The reviewer read the launch path instead of the fixture and found that the serve is submitted with sbatch and runs its engine inline in the batch step — no srun anywhere in the generator — and SLURM does not set that variable for a batch step. The measure was satisfied and the code could never work in production. A coordinator had hand-verified the same node and passed it.

That is the failure a self-scored gate cannot catch by construction, because the gate and the fixture were written by the same worker from the same misunderstanding. It also bounds what a done-when can do: a measure naming a fixture tests the fixture, and only a reader who goes to the call site tests the claim. Ten minutes of a lane that costs nothing bought a defect four hand-verifications had already passed over.

§5 — Dogfood: this plan's own back half is reviewed

From this section onward, every node of this plan is promoted only with a stored review, produced by the machinery §2 and §3 have just wired. The plan therefore tests its own repair with the only evidence that counts — whether the thing works when something real depends on it.

This is also the first measurement of §4's bound. The reviews dispatched here are the sample: their wall times, their findings, and how many of those findings a human would have wanted are what say whether a reflexive review is worth its latency. A wave in which every review returns clean and fast is a result; so is one in which reviews are slow enough to be waived, and that result must be recorded rather than absorbed.

Done when every node from this section on carries a stored, parsed review at promotion with no waiver used; the review wall times are recorded with their median; and any finding a review raised that the coordinator acted on is named, because a review that never changed an outcome has not yet earned its place.

§5b — What the reviews actually caught, and what that means for the checklist

The hit rate is the argument for the feature. Reported from imas-efit, 2026-09-21: seven solver merges, every one of which the coordinator had hand-read the diff of before merging and promoted. Six independent reviews were dispatched against that work; the first to land returned three defective, two overstated, two real. Five of seven carried something the coordinator missed on work it had personally audited. The claim this plan rests on is therefore not that unreviewed work is bad — it is that coordinator self-audit is measurably not a substitute for it, which is a stronger and more falsifiable claim.

None of the three defects was in the diff's correctness, and that reshapes §4's checklist. All three were in what the diff did not reach, and a reviewer reading only the changed lines would have missed every one:

  • An absence. A test rail authored three days earlier was never registered — its own listfile said the directory was not yet reachable and named the missing add_subdirectory line. Eleven merges later a grep found three self-references and no wiring. Nothing in any diff was wrong; the defect was a line never added. The rail in question was the one written to catch a silently disconnected mechanism, so the rail written to detect disconnection was itself disconnected.
  • A crossing. A Fortran change carried a second saddle's psi; the review traced it into C++ and found the boundary value stamped over every X-point node, discarding the exact quantity the carrier transports — with a comment two lines below acknowledging that secondary X-points sit at a different psi. Both files were correct in isolation.
  • A structure. A write inside an if with the logging call outside it, so a stale buffer is re-logged on the ordinary path. The diff reads fine line by line.

So the checklist's strongest item is reachability, not correctness. Does the change's new path execute under any registered test; if the node offers a log line as evidence, does that line's emission point gate the thing it is offered as evidence for; does a value cross a module or language boundary intact. In the reported case the node's own record claimed "the line's presence is itself the gate on the carrier" and the reviewer showed it gates the recording rather than the publish — and the publish branch had never executed, because both available rails converge on the same mode.

The discriminator worth writing into the prompt, because it generalises every instance in this plan. Before a field is allowed to carry a conclusion, ask what would make it wrong while still printing the same value. A review status of parsed survives a skeleton review. A fresh stream mtime survives a worker writing nothing useful. A plan-slug meta survives on a document that is not a plan. A dry-run ok survives a dispatch that cannot run. The five dimension scores survive a reviewer that skipped four of the five things it was told to read — which is the whole reason §4 requires a verdict per item.

§5c — A review describes a revision, and nothing records which

Acting on a review invalidates it, and the guard cannot tell. The healthy cycle is: the review finds defects, a worker repairs them, the run promotes. At that moment the stored review describes code that no longer exists — and §2's refusal is satisfied by any complete stored review, so the repaired run promotes on the strength of a record of the thing it was repaired from. The guard reads the presence of a review as evidence about the code being promoted. It is evidence about a revision, and the two stopped being the same revision at the first repair.

The revision is recorded. It is recorded under five different names, and the parser knows none of them. An earlier revision of this section claimed no stored review records the revision it read. That was wrong, and it was wrong in the way this page keeps warning about: it was read off parse_review's output rather than off the store. Counted across the 151 stored reviews on this workstation:

So staleness is detectable today and nothing looks, which is a materially different repair from adding a field. This plan's author ran the comparison by hand the moment they read the right key, across three imas-ambix runs: read a9b217c4 against head f12261e8; d7f17110 against 25a92fe0; d917d12c against 3e677eb6. Three of three stale, every one repaired past its review, exactly as the paragraph above predicts.

The repair is therefore standardisation, not invention. Adopt one of the names already in the store — reviewed_base_sha with reviewed_head_sha, because the pair distinguishes the base from the landed head where a single commit list does not, and because this repository already writes it — put it in the schema, treat a record lacking it as incomplete on the same principle that governs an absent dimension, and have §2's refusal compare it against the commits being promoted. A timestamp comparison is the tempting cheap version and it is wrong: it answers which was written first, not which revision was read.

A recheck destroys the review it rechecks. The store is one file per reviewed run — review_path(project, reviewed_run_id) — and store_review renames atomically into that path. So a second review of the same run does not sit beside the first; it overwrites it, with its findings. The author caught this with three rechecks in flight against the paths holding their originals, whose eleven findings and scores of 79, 86 and 89 are the measurement this plan's §5 rests on. Copying them aside is not a fix.

A review record has now been lost, not nearly lost. Recorded 2026-09-21: node-probe's round-two review — score 94 at revision f12261e8, carrying the unreachable-job-bound finding that the round-one repair had introduced — was overwritten by the round-three recheck before its author could copy it aside. The finding survives only because it had already been acted on. The store's own record of why the third repair was needed no longer exists.

And the interim naming failed for a reason worth keeping. The surviving records were first set aside under a round number, which was wrong within minutes because nobody knew the count in advance. Rekeying them by the revision each reviewer read — <run>.at-<sha>.json — is the same shape as the reviewed_base_sha normalisation above: accumulation by construction, rather than by someone remembering to copy a file before each recheck lands.

Key the store by the reviewing run instead, and superseding falls out. An append-only history makes "which review is current" a revision comparison — the one whose recorded head matches the commits being promoted — rather than a filesystem accident, and the superseded ones stay readable as what was found and when. That last part is not sentiment: the case for the whole mechanism is those eleven findings, and a store that silently overwrites them destroys its own evidence.

Why this is the same defect as every other one on this page. A complete review is a true statement standing in for the one that was needed. It is the discriminator of §5b run on our own guard: what would make this field wrong while it still printed the same value? — a review that is complete, parsed, stored, and about different code.

§5d — A repair can introduce the defect it was repairing

§5c says a promotion must refuse a review that predates the head. That fence is necessary and it is not sufficient, and the difference was measured rather than reasoned.

The case. An imas-ambix node was reviewed at 86 with two findings, repaired, and re-reviewed at 94. Both original findings were confirmed fixed and the recheck read f12261e8, the current head — so a staleness check passes it, correctly. The recheck nonetheless carried one finding, and the repair had caused it: a declared fifteen-second bound on a scheduler call that no production path can reach, because the caller hands its own ten-second timeout down two frames. A knob that does not do what it says — the same class as the defect being repaired, reintroduced one layer up by the fix.

Had that node been promoted against its original verdict after a hand-check of the repair — which is what happened for four earlier nodes that day — the new defect would have shipped with a review on the row saying 86. So the second fence is its own rule: a repair is not promotable against a review whose findings it changed. The review that matters is the one that read the repair, and a staleness comparison cannot supply it because the stale review is not the problem — the superseded one is.

And the store destroys exactly the record that proves this. Verified here against the imas-ambix store: the recheck overwrote the original at 09:15, one minute before a hand-made copy was taken for unrelated reasons.

Without that copy the store would now assert node-probe was always a 94 with one finding, and the repair would have no evidence it ever needed to happen. The two records answer different questions — the original says what was wrong, the recheck says whether it is still wrong and what the fix cost — and a store keyed by reviewed run can only hold one of them.

So keying by the reviewing run is not an improvement, it is the precondition for both fences. Records accumulate by construction; supersedes becomes a field rather than a convention; the revision each record read is unambiguous without the parser having to learn all five spellings of §5c; and "which review is current" is a revision comparison. The .first-review.json files now sitting in the store are evidence of the defect, not a naming convention to adopt — the store should do this itself.

§6 — A reviewer that can see the figure

The text reviewer reads a diff. It cannot open a rendered figure, and the figure rules this repository enforces are visual ones: legible at a glance, high data-ink, no gradients or decorative fills, text that clears contrast on its background, and — the rule most often broken — never an image of what is naturally a table.

A separate figure-review role reads the rendered artifact and judges it against those rules. It reports defects and obvious failures, and it has exactly one thing it may write: the figure's caption. A caption is the one part of a figure that is prose about the image rather than the image itself, and it is the part most often left as a restatement of the title. Everything else the reviewer finds is flagged for the node that drew it, on the same flag-never-fix rule the text reviewer follows: a reviewer that redraws becomes a second author with no reviewer, and its findings stop being falsifiable because the evidence moved.

This role requires a lane that can read an image. That is a capability requirement, not a preference: a text-only lane cannot serve it at all, and routing it to one would produce a confident review of a file the reviewer never saw. The role therefore declares the requirement and dispatch refuses a lane that does not meet it, in the same way a context-fit refusal already rejects a node too large for its window. Which lane satisfies it is a runtime routing choice and is deliberately not fixed here.

The trigger is narrow on purpose: a node is figure-reviewed when its landed diff touches an image under a figures directory. Most nodes never are, so the cost falls only where a figure exists.

Write paths. reckon/crew/figure_review.py (new), reckon/crew/prompts/figure-review.md (new), reckon/crew/recovery.py, tests/test_figure_review.py (new).

Done when a node whose diff adds or changes an image under a figures directory has a figure review dispatched and no other node does, asserted; the role is refused on a lane that cannot read an image, with the refusal naming the capability rather than the lane; the reviewer's only write is the caption, asserted by diffing its commit; a figure that is a table of text is flagged rather than accepted, asserted against a fixture that is one; and the repository's lint and test gates pass.

§ Decisions

What happens when a passing run has no stored review?

A warning is read once and then never; a refusal with no override becomes a reason to stop using the tool. A recorded waiver keeps the unreviewed promotion possible and keeps it visible, which is what separates a discipline from an obstacle — and the waiver rate is itself the measurement of how much the reflex is needed.

May the figure reviewer change the figure?

A reviewer that redraws becomes a second author with no reviewer, and its findings stop being falsifiable because the evidence moved. The caption is the exception because it is prose about the image rather than the image, it is the part most often left as a restatement of the title, and rewriting it cannot disguise a defect in what it describes.
