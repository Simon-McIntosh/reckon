§1 — Why: four modules each fill most of a worker's window

On 7 October the picker held §6 of the fleet moves to a new node, the sprint's critical path, with context-window-exceeded. Its node writes reckon/crew/dispatch.py and reckon/cli.py. The context-fit check (_context_fit_verdict in reckon/crew/routing.py) counts every write-path file whole at 3.5 bytes per token, on top of a launch-context floor of 50,392 tokens. The local lane's window is 230,144 tokens. Those two files come to 253,906 tokens before any instruction is loaded, so the node cannot fit and no later edit to it can either.

The four largest are also the four most-written files in the repository. Each is listed in docs/state/reckon/shared-write-paths.json as co-claimable, because independent nodes keep editing unrelated regions of the same file. That is the signature of a module holding several concerns, and it is why nearly every node lands in at least one of them. A node writing any two of the four is refused on the local lane. It is then routed to a metered lane or held, as §6 was.

§8 — How every split is done, and in what order

A split is a pure move. Every definition moves with its source unchanged. The only new lines are imports, plus, in the original module, the imports that keep from <original> import <name> working for every name some other file imports from it today. The original module stays as that import surface and keeps whatever the map leaves in it. No signature, name, default or behaviour changes, and no public name is added beyond the new module paths. A produced module never imports the original at module level. An unavoidable back-reference uses the function-level import this codebase already uses for cycles.

What a move must repoint. A test that patches a moved name on the original module patches nothing once the caller lives elsewhere. A test that reads the original file's text by path reads the wrong file. The map's census names both kinds, and the move node repoints each one to the module that now holds the name, with its declared write paths covering those tests. A failure the census missed shows up in the suite measure, not silently.

Names. A produced module is a sibling of the original, named for the one concern it holds, as the rest of the package is. A name never carries a part number, a version or the word core. When a produced module holds one concern, the move also removes the original's entry from docs/state/reckon/shared-write-paths.json, or narrows its reason to what stays in it.

Peers. These are the files every concurrent session writes. A move is dispatched only when crew(view="scopes") shows no live claim on the module, and it is reviewed, merged and pushed in one sitting so the window in which a peer can start from the old layout is short. A peer whose worktree predates the split gets a conflict on its edits to a moved definition, and it re-applies them to the definition's new home. Its edits to code left in the original module merge as before.

Verification. The worker's gate is the move check, the guard and the tests its census named. The coordinator measures the whole suite at the base and at the merged head before pushing, because a moved name can break an importer no census anticipated. The review reads the move check's receipt and every line that is not a move. It does not re-read the moved bodies.

Order. §2 goes first, since every split is checked by its instruments. §3 and §4 follow, because together they bring §6 of the fleet move inside the local lane. Then §5 and §6, then §7. Two moves run at the same time only when their maps name disjoint test files. The map nodes are read-only and can run ahead of their moves.

§ Decisions

How large may a source module be, in the context-fit check's estimated tokens?

The lead asked that a file too large for a 200k context be split. A quarter of that window is the largest bound under which a node writing three modules and their tests still fits the local lane after the 50,392-token launch floor. At 40,000, five more files would need splitting for no measured hold: tests/test_crew.py at 49,747, and the ledger, the server, routing and budget, between 41,000 and 44,000. At 60,000, a node writing three modules at the bound is refused. Produced modules target 40,000 so the bound is not met again within weeks.

After a split, where do callers import moved names from?

Keep the original as the import surface. Four sessions are writing these files today, and code in their worktrees imports from the original paths. Repointing every importer would turn each split into a change to dozens of files that conflicts with all of them. Re-imports add no definition and no public name. Tests that patch a moved name still have to be repointed, because a patch on the import surface does not reach the module that calls the name. That cost is counted by each map's census.
