Build identity · a tag that was never meant to name a release

Only A Version Tag Sets The Version

Five wheel-build tests fail in this repository, and have been failing at every revision measured today. The cause is not the build and not the tests: one recovery tag, created to preserve work during an incident, satisfies the pattern the version machinery uses to find release tags, because its name ends in the commit sha it rescued and that sha contains digits. Any future rescue tag will do the same. This plan constrains what may name a version so the class cannot recur, rather than deleting the tag that happens to be here now.

§1 — Why this exists

Measured 2026-09-04 by a merged-head verification that ran the full suite at two revisions. Five of its failing ids are wheel-build failures present identically at base 85dc0f4 and at head 19c24fc1, so they belong to neither the wave under test nor any work in it.

The repository carries four tags. Three name releases — v0.2.0, v0.2.0rc24, v0.2.0rc25. The fourth is rescue/spec-level-names-a-backend-957c042, created to hold work during an earlier incident. Version is derived dynamically (hatch-vcs over setuptools_scm, [tool.hatch.version] with source = "vcs"), and the default describe pattern admits any tag containing a digit. The rescue tag's name ends in the short sha it rescued, 957c042, which contains four. So it is offered to the version parser, which cannot read a version out of it, and the build fails.

Two facts decide the remedy. The tag is on the remote, so deleting it rewrites state every clone and CI checkout shares. And the commit it points at is already an ancestor of main, so it protects nothing that is not already safe — deleting it would lose no work but would also fix nothing durable, because the next incident that mints a rescue tag reproduces the failure exactly. The recovery convention is sound and worth keeping; what is wrong is that a name chosen to describe a rescue is being read as a release identity.

§2 — Constrain what may name a version

Version derivation reads only tags shaped like this project's releases. The three existing release tags must continue to resolve exactly as they do today, including the release-candidate forms, and any tag outside that shape must be invisible to the version machinery rather than an error from it. The mechanism is a matching constraint in [tool.hatch.version.raw-options] — a describe pattern, a tag regex, or both, whichever the installed resolver honours; the node establishes which by measuring rather than by assuming, since the two options are honoured at different layers.

The measure is the part that matters: the malformed tag must be present in the repository while the build succeeds. A build that passes only once the tag is gone has tested the deletion, not the fix.

Gate for this plan, recorded when the measure runs: with rescue/spec-level-names-a-backend-957c042 still present, the wheel builds and reports a version derived from the newest release tag, and the five previously failing wheel-build ids pass. Its evidence is the recorded version string before and after, the five ids named individually, and one build run against a synthesised tag of the same malformed shape to show the fix covers the class and not one string.

§3 — Out of scope

Deleting or renaming the rescue tag, which is repository-owner authority over shared remote state and which this plan deliberately makes unnecessary; if the lead removes it later for tidiness, the fix still holds and the class stays covered. The rescue-tag convention itself, which did its job and is not the defect. Release publishing, owned by a shipped plan. And the version scheme: the three existing release tags keep resolving exactly as they do now, because changing what a version means is a different decision from choosing which tags may express one.

§ Decisions

Constrain the tag pattern, or delete the offending tag?

Deleting fixes today and nothing after it: the next rescue tag reproduces the failure, and the tag is on the remote so the deletion mutates state every clone shares. Renaming the convention makes a recovery mechanism carry a constraint belonging to the build. Constraining the pattern is a declared change in one project file that reaches every checkout and CI, and it covers the class.

Is the malformed tag present while the fix is measured?

A build that passes only once the tag is gone has measured the deletion rather than the fix, and would pass identically with no fix at all. The tag's presence is the condition under which the assertion means anything.
