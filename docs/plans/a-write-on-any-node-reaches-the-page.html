§1 — What is wrong, measured

The served page stops seeing new documents once work moves off the login node. Measured 2026-10-15 on imas-ambix. Two research documents were written and committed from the fleet node 98dci4-clu-2002, and they did not appear in the SPA. The server on the login node 98dci4-srv-1006 was healthy: /_server reported its code current, and /_discover/imas-ambix already listed both documents. But /_index/imas-ambix, the rows the page lists documents from, held 885 rows, and its newest research row was dated 2026-10-09. A single touch -c of a docs file on the login node brought it to 890 rows within five seconds, both documents included.

The cause is that only one of the server's three derived views has a cross-node backstop. _invalidate_tree_views drops three views of a tree together: the discovery reuse window, the cached discoveries and the in-process metadata index. Two mechanisms trigger it. One is the _FleetChangeWatch thread, which uses inotify. The other is the per-stream inotify watch inside the /_changes/ handler. inotify on GPFS reports only writes made on the same node. Discovery survives this, because its reuse window (_SERVED_SIGNATURE_TTL_S, 60 s) re-walks the tree when it lapses. The code says this is deliberate: the window "only backstops writes the kernel does not report, notably a write from another login node on the shared filesystem". metadata_index.index_rows has no such window. It answers from its cache until invalidate_tree is called, and only an inotify event calls it. An open page's change stream likewise waits on inotify alone, so it is never told.

This is now the normal case, not an edge. Since agent sessions moved to the fleet allocation, every plan, evidence and research write comes from a compute node. So the page's document list freezes at the last login-node write, and every open page's live updates stop. Restarting the server only hides the fault until the next write.

§2 — A docs tree's derived views get a cross-node backstop, and open pages are told

Scope. This covers the three views _invalidate_tree_views drops for one docs tree (the discovery reuse window, the cached discoveries and the metadata index), plus the open change streams for that tree. Other served views, such as the cross-project fleet index (reckon/fleet_index.py, read at serve.py:844), are outside it. The node checks whether the fleet index also misses a cross-node write and reports the answer in its manifest; it does not change it.

The change. _FleetChangeWatch gains a cross-node change detector for each mounted docs tree, beside its inotify watch. When the detector sees a change the kernel did not report, it does what an inotify event does: it calls _invalidate_tree_views(root, changed_at=...). It also wakes the open change streams. Today each /_changes/ stream builds its own _ProjectChangeWatch(docs_dir) (serve.py:2782) and blocks on its inotify descriptor, and nothing connects it to the fleet watch. So _FleetChangeWatch gains a subscription. A stream registers one wake pipe for its tree when it opens and removes it when it closes. The fleet watch writes one byte to every pipe registered for a tree whenever it sees a change to that tree, whichever source reported it. The stream's wait selects on that pipe beside its own inotify descriptor. It then runs the same settle, invalidate and row-diff path it runs today, so its change event keeps its shape. There are two sources of change, the per-stream inotify watch and the fleet watch, and one path that handles both.

The detector reuses the owners that already exist, because it runs on a login node over GPFS. A full discovery walk "costs seconds on a shared filesystem", so the detector must not be a walk on a timer. It reads two signals, each through an existing owner:

  • A fast signal, every 10 s by default. First, directory identities, through metadata_index._reuse_covered. It already compares the persisted directory stamps (_load_dir_stamps, _dir_identity) to decide whether an entry was added or removed, and that is the question the detector asks. Second, git state, through _head_identity (serve.py:1291), extended to include the stat identity of .git/index. It already resolves HEAD and its ref through _common_git_directory, so a linked worktree resolves correctly. With .git/index added, it changes on every add, commit, merge and pull from any node. Single-file reads go through _file_identity (serve.py:1262).
  • A slow signal, every 60 s by default. It runs only for a tree that has an open change stream, or that was read in the last ten minutes. It is the stat signature of every covered file, from _walk_discovery_signature (serve.py:1659) over metadata_index._covered_files. That walk already drives discovery, so the detector forks no second loop over the covered set. It catches an uncommitted in-place edit from another node, which changes no directory and no git file. A tree nobody is reading pays nothing.

Both intervals are environment-configurable beside RECKON_DISCOVERY_REUSE_S. A detector pass that raises an OSError is logged and treated as no change, so a storage stall never takes the watch thread down.

Why not index_rows(revalidate=True) on each request. That owner already exists for a reader with no watch, but it rereads the bytes of every covered file on every /_index request: about 900 GPFS reads per page load for imas-ambix. It also wakes no open stream, so an open page would still never be told. The detector costs stat calls only, only while a tree has readers, and pushes the change to streams.

What is not changed. The inotify paths stay and stay first, so a local write is still seen in about 0.25 s. The discovery reuse window stays as it is. The metadata index's cache and its revalidate mode are untouched; the detector only decides when invalidate_tree is called. No public name is added except the two environment variables. Nothing existing can absorb them, because the reuse window governs discovery walks and not these signals.

Deployment. The node does not restart the served process. The coordinator restarts it on the login node with reckon service restart after the merge, and then takes the live measure below.
