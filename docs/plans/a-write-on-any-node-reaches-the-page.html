§1 — What is wrong, measured

The served page stops seeing new documents once work moves off the login node. Measured 2026-10-15 on imas-ambix. Two research documents were written and committed from the fleet node 98dci4-clu-2002, and they did not appear in the SPA. The server on the login node 98dci4-srv-1006 was healthy: /_server reported its code current, and /_discover/imas-ambix already listed both documents. But /_index/imas-ambix, the rows the page lists documents from, held 885 rows, and its newest research row was dated 2026-10-09. A single touch -c of a docs file on the login node brought it to 890 rows within five seconds, both documents included.

The cause is that only one of the server's three derived views has a cross-node backstop. _invalidate_tree_views drops three views of a tree together: the discovery reuse window, the cached discoveries and the in-process metadata index. Two mechanisms trigger it. One is the _FleetChangeWatch thread, which uses inotify. The other is the per-stream inotify watch inside the /_changes/ handler. inotify on GPFS reports only writes made on the same node. Discovery survives this, because its reuse window (_SERVED_SIGNATURE_TTL_S, 60 s) re-walks the tree when it lapses. The code says this is deliberate: the window "only backstops writes the kernel does not report, notably a write from another login node on the shared filesystem". metadata_index.index_rows has no such window. It answers from its cache until invalidate_tree is called, and only an inotify event calls it. An open page's change stream likewise waits on inotify alone, so it is never told.

This is now the normal case, not an edge. Since agent sessions moved to the fleet allocation, every plan, evidence and research write comes from a compute node. So the page's document list freezes at the last login-node write, and every open page's live updates stop. Restarting the server only hides the fault until the next write.

§2 — A docs tree's derived views get a cross-node backstop, and open pages are told

Scope. This covers the three views _invalidate_tree_views drops for one docs tree (the discovery reuse window, the cached discoveries and the metadata index), plus the open change streams for that tree. Other served views, such as the cross-project fleet index (reckon/fleet_index.py, read at serve.py:844), are outside it. The node checks whether the fleet index also misses a cross-node write and reports the answer in its manifest; it does not change it.

The change. _FleetChangeWatch gains a cross-node change detector for each mounted docs tree, beside its inotify watch. When the detector sees a change the kernel did not report, it does what an inotify event does: it calls _invalidate_tree_views(root, changed_at=...). It also wakes the open change streams. Today each /_changes/ stream builds its own _ProjectChangeWatch(docs_dir) (serve.py:2782) and blocks on its inotify descriptor, and nothing connects it to the fleet watch. So _FleetChangeWatch gains a subscription. A stream registers one wake pipe for its tree when it opens and removes it when it closes. When no fleet watch is running, as in a test server that never calls start_fleet_change_watch, _FLEET_WATCH is None and the registration does nothing: the stream waits on its own inotify watch alone, exactly as it does today. The fleet watch writes one byte to every pipe registered for a tree whenever it sees a change to that tree, whichever source reported it. The stream's wait selects on that pipe beside its own inotify descriptor. It then runs the same settle, invalidate and row-diff path it runs today, so its change event keeps its shape. There are two sources of change, the per-stream inotify watch and the fleet watch, and one path that handles both.

The watch knows each tree's project and the state root. _FleetChangeWatch is built today from mounts.values() (serve.py:4017), tree paths only. The owners below are keyed by project and state root, so start_fleet_change_watch passes the project-to-tree mapping, and main() passes the state root it already resolves. The watch keeps each tree's project beside its path.

The detector reuses the owners that already exist, because it runs on a login node over GPFS. A full discovery walk "costs seconds on a shared filesystem", so the detector must not be a walk on a timer. It reads two signals, each through an existing owner:

  • A fast signal, every 10 s by default. First, directory identities. The watch loads each tree's persisted directory stamps with metadata_index._load_dir_stamps once when it arms the tree, and keeps them in memory. It learns that the index was rebuilt from the persisted index file itself: it keeps that file's _file_identity, and when a pass finds it changed, it reloads the stamps from the file. A rebuild is lazy and runs only when a later reader asks for the index, so between a detection and that rebuild the persisted stamps are still the old ones. So when a pass finds a directory whose identity differs from its cached stamp, the watch replaces the cached stamp with the identity it has just read before it invalidates. One change therefore fires the invalidation once, and the next pass is quiet until something changes again. The git signal works the same way: the watch keeps the last git identity it read and replaces it when the signal fires, and so does the slow signal with its last signature. A fast pass then calls only _dir_identity on each directory and compares it with the cached stamp, the same comparison _reuse_covered makes. It does not call _reuse_covered itself, which reads and parses the persisted index file twice per call: 36 reads every 10 s across 18 mounted trees. Second, git state. The detector's git identity is _head_identity (serve.py:1291) paired with the _file_identity of the index file in the repository's git directory, _git_directory(repo_dir) / "index". A mounted tree is a docs directory with no git directory of its own, so repo_dir is the tree's parent, docs_dir.parent, as the served index already takes it (serve.py:1588). _head_identity already resolves HEAD and its ref through _common_git_directory, so a linked worktree resolves correctly, and the index file changes on every add, commit, merge and pull from any node. _head_identity itself is not changed: _git_head memoises the resolved commit on it and promises that an unchanged checkout starts no git process, so adding the index file there would start a git rev-parse on every index write. Single-file reads go through _file_identity (serve.py:1262).
  • A slow signal, every 60 s by default. It runs only for a tree that has an open change stream, or that was read in the last ten minutes. The watch owns that read time: the /_index/<project> handler (serve.py:3282) and the /_discover/<project> handler (serve.py:3358) each stamp their tree's last read on the watch as they answer. _invalidate_tree_views does not clear the stamp, so a change does not make a tree look unread. It is the signature _walk_discovery_signature (serve.py:1659) computes over metadata_index._covered_files: the covered file count and the newest mtime. An edit sets its file's mtime to the time of the write, so the edited file becomes the newest and the signature changes; an edit that preserves an older mtime on purpose is not seen. That walk already drives discovery, so the detector forks no second loop over the covered set. It catches an uncommitted in-place edit from another node, which changes no directory and no git file. A tree nobody is reading pays nothing.

Both intervals, and the ten-minute window that counts a tree as recently read, are environment-configurable beside RECKON_DISCOVERY_REUSE_S. A test can therefore shorten the window instead of waiting it out. A detector pass that raises an OSError is logged and treated as no change, so a storage stall never takes the watch thread down.

Why not index_rows(revalidate=True) on each request. That owner already exists for a reader with no watch, but it rereads the bytes of every covered file on every /_index request: about 900 GPFS reads per page load for imas-ambix. It also wakes no open stream, so an open page would still never be told. The detector costs stat calls only. The fast signal stats every mounted tree's directories and git files on every pass; the slow signal's per-file stats run only while a tree has readers. It also pushes the change to streams.

What is not changed. The inotify paths stay and stay first, so a local write is still seen in about 0.25 s. To keep that true, the detector's passes run on a thread of their own that _FleetChangeWatch starts beside its event loop, not inside that loop. The loop's untimed select over the inotify descriptors is left as it is, so a slow pass over GPFS never delays an inotify event. Both threads call _invalidate_tree_views and write to the wake pipes, so the pipe registry is guarded by one lock. The discovery reuse window stays as it is. The metadata index's cache and its revalidate mode are untouched; the detector only decides when invalidate_tree is called. No public name is added except the three environment variables. Nothing existing can absorb them, because the reuse window governs discovery walks and not these signals.

Deployment. The node does not restart the served process. The coordinator restarts it on the login node with reckon service restart after the merge, and then takes the live measure below.

Done when: tests/test_cross_node_writes_refresh_the_index.py passes against a served process in which every inotify watch on the tree is replaced by one that never fires, which is how a write from another node looks. That is both the fleet watch's own _ProjectChangeWatch and the one each /_changes/ stream opens, so a stream can be woken only through its subscription pipe. It asserts each of the following. A new document added to a mounted tree appears in /_index/<project> within one fast interval, with the interval set to 1 s for the test. A commit that changes an existing document's bytes refreshes its row within one fast interval. An in-place edit with no commit refreshes its row within one slow interval while a change stream is open, and is not detected when no change stream is open and the tree has not been read for ten minutes, the slow signal's own activation rule. With no stream open, the same edit is detected within one slow interval after a /_index/<project> request, and a detection does not clear that read stamp. An open /_changes/<project> stream receives a change event carrying the added row, through its subscription pipe. Closing the stream removes its pipe from the fleet watch. One detected change invalidates the tree once: the fast passes after it, with nothing else changed and before any reader rebuilds the index, do not call _invalidate_tree_views again, and a rebuild that rewrites the persisted index file reloads the cached stamps without firing. A change to the tree's git index file with HEAD unchanged fires the detector, and leaves _head_identity unchanged, so _git_head starts no git process for it. A detector pass that raises OSError leaves the watch thread running. Every existing test in tests/test_changes_push_rows.py and tests/test_agent_readers_use_the_index.py still passes. The manifest records, for the imas-ambix tree on GPFS, the stat count and wall time of one fast pass and one slow pass, measured on the node the worker runs on. The manifest states whether the cross-project fleet index (reckon/fleet_index.py) also misses a cross-node write, quoting the request and the rows that show it. The declared negative control disables the detector, and the new-document test must then fail.

Live measure, taken by the coordinator after the restart: a document committed on the fleet node appears in /_index/imas-ambix on the login node within 15 s, with no touch on the login node.
