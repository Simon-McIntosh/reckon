Why this plan exists

Every worker this fleet has ever run was a child of the coordinator on the login node, and the login node gives one user a slice of memory far smaller than the machine. That slice is the fleet's real ceiling, and it is not a throughput ceiling: it kills processes.

So the machine is nearly empty while our slice is full, and three workers running a solve can exhaust it between them. Five hundred and twenty-nine processes have already been killed this way. The served model is not what stops us: one observed operating point is about 450 tokens a second in aggregate at roughly twenty-five concurrent workers, which is a rate under a load and not a measured ceiling. It is quoted here only to show that the serve was still delivering at a concurrency the login slice cannot host, and it is deliberately not offered as the sizing figure section 5 needs, which is a curve rather than a point. The slice binds on memory, so it has no fixed worker count of its own to compare against.

Nothing in reckon knows about the scheduler. A search of the package and the skills for srun, sbatch or SLURM returns nothing; workers are launched with subprocess.Popen in reckon/crew/dispatch.py and charged to whoever started the coordinator. What already runs under the scheduler is the model serve, and the per-node gates that briefs ask for by hand. This plan moves the worker itself.

Three preconditions were measured before the plan was written, one on each partition a worker might use. From a compute node on all_debug and again from one on rigel, the served model answers on 98dci4-gpu-0003:18810 and its router on :18802; the worktree root, the crew state directory, the backend binary and the shared project environment are all visible; and TMPDIR already resolves to /tmp rather than to node-local /run/user. Capacity is not scarce either: all carries no time limit with 3,084 idle cores across 97 idle nodes, against all_debug's one-hour ceiling.

The external lanes screen as reachable from a compute node, which is what keeps this from becoming a local-only pattern. Measured once, from one rigel node on 2026-09-19: TCP 443 opened to api.openai.com, chatgpt.com and api.anthropic.com; an unauthenticated GET completed an HTTP exchange with api.openai.com and api.anthropic.com, each answering 401, while chatgpt.com was tested only at the port. State the strength of that plainly: it shows something at those addresses speaks HTTP from a compute node, and it does not show which party replied, since a gateway or an edge can answer 401 as readily as the provider, nor anything about the authenticated traffic a lane actually carries. It is a screening result that makes the plan worth writing; section 7 is where the question is answered, by running a real node on an externally served backend. Alongside it: both the codex and claude launchers resolve on the node’s path, no proxy variable was needed, and the two lane credentials inspected (~/.codex/auth.json and ~/.claude/.credentials.json) are files on the shared home rather than environment secrets, so those two travel with the filesystem the worker already needs.

§1 — One worker under one allocation, on the local lane, before anything else changes

A backend gains an optional placement describing how its launch is wrapped. When a placement is declared, the launch plan built in reckon/crew/dispatch.py prefixes the resolved argv with the scheduler invocation rather than replacing it, so the resolved absolute executable, the environment, and the stdin, stdout and stderr paths that section 1 of the positive-controls plan established are carried through unchanged. Everything reckon writes stays on the shared filesystem, so a worker under an allocation is indistinguishable downstream from one on the login node.

Prototype first, on one run. This section is not finished by a design; it is finished by a single real local-lane node that ran to completion under an allocation and was promoted through the ordinary path. The details that only a real run will settle, and which the section must record as it finds them: whether the wrapper is srun held open for the worker's life or a batch job the coordinator polls, what the worker costs in cores and memory as measured rather than guessed, and how a queued allocation is distinguished from a slow worker. The size of this section is one node and no more: the three failure shapes, an allocation refused, pre-empted, or stopped at a time limit, are section 2's subject and are not produced here, which also settles that a time limit need not be exercised on a partition that has none. A design document is not a deliverable; what the run teaches is recorded in the evidence anchor, and the cost it measures is this worker on this node rather than the sizing curve section 5 needs.

Done when. One local-lane implement node dispatched with a placement runs on a compute node, writes its stream, manifest and reports to the same paths, and is promoted without any special handling; the run record names the job id beside the pid; and the section states the measured cost of that worker in cores, memory and queue wait.

Files, and what this section mints. The launch plan and the reaper are in reckon/crew/dispatch.py; the run record the job id must appear in is written by reckon/crew/runs.py for the live pointer and reckon/crew/promotion.py for the ledger row, and the section states which of the two it chose and why; the backend schema the placement field joins is in reckon/flight.py. Those four plus a test file are the grant. The field is optional in one specific sense fixed here rather than later: its absence means today’s login-node launch, so nothing changes for a backend that does not declare it, and section 6 changes which backends declare one rather than changing what absence means. Indistinguishable downstream means the paths and the formats are unchanged; the record gains the job id as a new field beside the pid, which is an addition rather than a difference in shape.

Outcome — mechanism landed, the proving run still owed. Commit 740e4065 lands the wrap in reckon/crew/dispatch.py: a backend's declared placement is resolved against the same PATH the launch searches and prefixed onto the already-resolved argv, so the absolute executable, the environment and the stream paths are carried through; a backend declaring none is returned untouched. The field is declared in the schema source and validated with the backend definition, and it survives resolution into the resolved configuration. Commit 09e27b83 puts the field in reckon/schema/flight.yaml as a PlacementConfig — the scheduler executable, its option strings and the probe that answers which job the launch became — and regenerates reckon/_flight_schema.py and docs/_shared/flight.schema.json from it with the repository's own generator, so the field validates under the same forbids-unknown-keys rule as every other backend key rather than being stripped before the model sees it. The job id is read through the placement's own declared probe and recorded beside the pid on the run record; reckon/crew/promotion.py is the module chosen to carry it onto the committed ledger row, because that row is the durable record a later attribution reads while the live pointer is removed by the same promotion. A run declaring no placement records the key absent rather than zero, so an unplaced run stays distinguishable from a placed one whose scheduler never answered. Not done, and now the coordinator's rather than this node's. No placed worker has run on a compute node from this work, so the partition and job id, the measured cores and peak memory, the queue wait, and whether a queued allocation is distinguishable from a slow worker are unmeasured. The measure here is the mechanism and its cases; the proving run is one dispatch a coordinator owns, because a worker that dispatches a worker does not fit a fence. It is a command rather than a design, and it is written out in this node's manifest under follow_ons.

§2 — Liveness and reaping follow the job, because a pid on another host is not a process

Every liveness answer in the crew reads a pid on the coordinator's own host. Under an allocation the worker's pid belongs to a compute node, so the existing reads become false in a specific and dangerous direction: a live worker looks dead. The classifier, the reaper that section 2 of the positive-controls plan built, and the launch-failure record all need the job as their subject. This is the plan's critical-risk section because a wrong answer here is either a duplicated worker or a silently abandoned one.

Done when. A placed run reports live while its job is running and terminal when the job leaves the queue, decided from the job rather than from a pid; a job that never starts is recorded once as a launch failure with its scheduler reason, the way an unresolvable binary is; a job killed for time or memory is classified distinctly from a worker that failed, since the remedy differs; and the payload log, not the step's exit status, decides whether the work ran, which two jobs proved necessary on 2026-09-19 by reporting COMPLETED while their payloads aborted.

Files. The classifier and the liveness reads are in reckon/crew/recovery.py and reckon/crew/runs.py; the reaper, its once-only guard and the launch-failure record are in reckon/crew/dispatch.py; the lift path that must not resume a job-placed run is in reckon/crew/resumption.py. Those four plus a test file are the grant, and this section is dispatched with them named because it is the critical-risk one.

§3 — One standing allocation the whole workstation shares, and Slurm is its queue

A job per worker mints a reservation per worker. That was measured to be fast — the proving run's allocation started in zero seconds on all — and speed was the wrong axis to judge it on. The objection is that every worker becomes its own reservation against the scheduler, so raising the fleet's concurrency means submitting more reservations rather than sizing one, and nothing about the arrangement is shared between the sessions that run on this workstation. The lead's design is one standing allocation with a generous core count, held once, that every session places workers into.

The pattern was measured before this section was written, on 2026-09-19. An allocation is held with no shell attached (salloc --no-shell), which returns a job id and keeps the resources without occupying a terminal: job 1274057, 8 cores and 32 GB on one node. Workers then run inside it as steps (srun --jobid=<id>), each appearing under its own step id, and the distinction that decides the whole surface is how the step asks for its share.

Step asks withWhat happenedWhat it means for reckon

So the design follows from the measurement rather than from a preference: workers are placed as exact steps, the allocation's size is the fleet's concurrency, and raising concurrency is one change to one allocation rather than a change to how dispatch behaves. Reckon does not implement a queue, which is the part of this section most likely to have been built unnecessarily.

Files, and what the surface looks like. The allocation is a durable shared resource of the same kind as the model serve and the project watcher, so it is managed the same way rather than invented afresh: an ensure command in reckon/cli.py and reckon/crew/runs.py that holds the allocation if it is absent, reports it if it is present and starts nothing, mirroring reckon crew watch --ensure; its identity published where every session reads it rather than held in one session's memory, the way the served model publishes its endpoint; and the placement in reckon/crew/dispatch.py resolving that published id rather than taking one on the command line. Those three plus a test file are the grant.

Done when. One allocation is held by the ensure command and a second call reports it and starts nothing; two workers dispatched from two different sessions both run as steps inside that one allocation, which is the property the shared design exists for and which a single-session test cannot show; a worker dispatched when the allocation is full waits for a slot rather than being refused, and is reported as waiting for capacity rather than as slow, which section 2 owes the surface anyway; and the policy is stated for an allocation that expires under workers and for a worker that outlives it.

§4 — The workspace contract: what a worker needs visible, and what must never be node-local

Three preconditions were measured from both partitions and hold today, but nothing in reckon asserts them, so a placement into a partition that lacks one would fail in a way that reads as a worker defect. The worker needs the worktree root, the crew state directory, the backend binary and the shared project environment, all of which sit on the shared filesystem; it needs the served model and its router reachable; and it must never be handed a path under /run/user, which is node-local tmpfs and has already cancelled a job in zero seconds with an empty log when an output path pointed there.

Done when. A placement is refused before launch when any declared requirement is not visible from the target partition, naming the path or the endpoint, pinned by a test with a synthesised unreachable requirement; and the refusal names the node-local case explicitly, because that one fails silently rather than loudly.

Files, and which side refuses. The requirement set is declared with the backend in reckon/flight.py and checked coordinator-side in reckon/crew/dispatch.py before a worktree or a pointer exists, with the refusal text composed in reckon/crew/node.py as the other pre-launch refusals are. Coordinator-side is the choice because a node-side check would need the node to start, which is the thing being refused. The credential path each lane needs belongs to this requirement set from the outset rather than being added by section 7.

§5 — The ceiling moves from a slice of memory to the roster, and the roster must know it

Today the honest bound on concurrency is the 64 GiB slice, which nothing reads and which announces itself only as a killed process. Once workers are charged to jobs, the roster is the only bound left, as the abandoned local-workers plan already said it should be. The roster then has to be sized against something real: the partition's admitted cores, the served model's measured aggregate, and the coordinator residue that stays on the login node however much moves off it.

Done when. The fleet surface reports the bound that is actually binding, and a dispatch that would exceed it is refused naming which bound and its measured value; the login slice's oom_kill counter is read and surfaced rather than discovered, so a slice under pressure says so before it kills anything.

Files, and the instrument that can actually warn. The bound is reported by the fleet surface in reckon/crew/summary.py and reckon/crew/ticker.py and enforced at the admission check in reckon/crew/dispatch.py. The oom_kill counter cannot warn before a kill, since it only increments on one; what warns is memory.current against memory.max, and the allocation-stall counter beside them, which stood at 2,912,593 while the kill count was 529. The surface reads those and reports the kill count only as history.

§6 — The prototype ladder, and only then the default

The lead's instruction is to prototype on the local lane first and settle the details individually before the design is fixed. That makes the ladder part of the plan rather than a habit: one worker under an allocation, then a small wave of independent nodes, then a wave with a peer-scoped merge, and only then a change to what a dispatch does by default. Each rung records what it measured and what it changed, and a rung that finds a detail the previous rung hid is the ladder working rather than a setback.

Done when. Each rung has run and is recorded with its measurements; the default placement changes only after the wave rung; and the section states what would send the fleet back to login-node launches, so the change is reversible on a stated condition rather than on an argument.

§7 — Every lane is placeable, not only the local one

The reason to move workers is a memory slice, not a model, so a placement that quietly serves only the locally hosted lane would trade one ceiling for a narrower fleet. All four lanes this project routes to were measured reachable from a compute node before the plan was written, and the credentials for each are files on the shared home rather than environment secrets, so nothing about placement is inherently local. What remains is to keep it that way by construction: placement is a property of the backend rather than a property of the local one, an externally served backend carries the same placement fields as the local one, and a dispatch is never silently rerouted to a different lane because of where it would run.

Done when. A placed dispatch to an externally served backend runs on a compute node and reaches its provider, demonstrated on one real node rather than by a port check; the placement configuration is asserted to carry no lane-specific branch, so adding a backend needs no placement code; and a placement whose partition cannot reach a backend's provider is refused before launch naming the backend and the endpoint, the way an invisible path is, rather than failing as a worker error. The credential path each lane needs is part of the workspace requirements of section 4, so a lane whose credentials do not travel is refused rather than discovered mid-run.

Files. The placement fields are on the backend schema in reckon/flight.py, the lane-agnostic launch is in reckon/crew/dispatch.py, and the reachability refusal shares the pre-launch site and the refusal text of section 4 rather than adding a second one. This section extends no other section’s requirement set: the credential paths are in section 4 from the outset.
