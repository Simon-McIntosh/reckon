Why this plan exists

Every worker this fleet has ever run was a child of the coordinator on the login node, and the login node gives one user a slice of memory far smaller than the machine. That slice is the fleet's real ceiling, and it is not a throughput ceiling: it kills processes.

So the machine is nearly empty while our slice is full, and three workers running a solve can exhaust it between them. Five hundred and twenty-nine processes have already been killed this way. The served model is not what stops us: one observed operating point is about 450 tokens a second in aggregate at roughly twenty-five concurrent workers, which is a rate under a load and not a measured ceiling. It is quoted here only to show that the serve was still delivering at a concurrency the login slice cannot host, and it is deliberately not offered as the sizing figure section 5 needs, which is a curve rather than a point. The slice binds on memory, so it has no fixed worker count of its own to compare against.

Nothing in reckon knows about the scheduler. A search of the package and the skills for srun, sbatch or SLURM returns nothing; workers are launched with subprocess.Popen in reckon/crew/dispatch.py and charged to whoever started the coordinator. What already runs under the scheduler is the model serve, and the per-node gates that briefs ask for by hand. This plan moves the worker itself.

Three preconditions were measured before the plan was written, one on each partition a worker might use. From a compute node on all_debug and again from one on rigel, the served model answers on 98dci4-gpu-0003:18810 and its router on :18802; the worktree root, the crew state directory, the backend binary and the shared project environment are all visible; and TMPDIR already resolves to /tmp rather than to node-local /run/user. Capacity is not scarce either: all carries no time limit with 3,084 idle cores across 97 idle nodes, against all_debug's one-hour ceiling.

The external lanes screen as reachable from a compute node, which is what keeps this from becoming a local-only pattern. Measured once, from one rigel node on 2026-09-19: TCP 443 opened to api.openai.com, chatgpt.com and api.anthropic.com; an unauthenticated GET completed an HTTP exchange with api.openai.com and api.anthropic.com, each answering 401, while chatgpt.com was tested only at the port. State the strength of that plainly: it shows something at those addresses speaks HTTP from a compute node, and it does not show which party replied, since a gateway or an edge can answer 401 as readily as the provider, nor anything about the authenticated traffic a lane actually carries. It is a screening result that makes the plan worth writing; section 7 is where the question is answered, by running a real node on an externally served backend. Alongside it: both the codex and claude launchers resolve on the node’s path, no proxy variable was needed, and the two lane credentials inspected (~/.codex/auth.json and ~/.claude/.credentials.json) are files on the shared home rather than environment secrets, so those two travel with the filesystem the worker already needs.

§2 — Liveness and reaping follow the job, because a pid on another host is not a process

Every liveness answer in the crew reads a pid on the coordinator's own host. Under an allocation the worker's pid belongs to a compute node, so the existing reads become false in a specific and dangerous direction: a live worker looks dead. The classifier, the reaper that section 2 of the positive-controls plan built, and the launch-failure record all need the job as their subject. This is the plan's critical-risk section because a wrong answer here is either a duplicated worker or a silently abandoned one.

Done when. A placed run reports live while its job is running and terminal when the job leaves the queue, decided from the job rather than from a pid; a job that never starts is recorded once as a launch failure with its scheduler reason, the way an unresolvable binary is; a job killed for time or memory is classified distinctly from a worker that failed, since the remedy differs; and the payload log, not the step's exit status, decides whether the work ran, which two jobs proved necessary on 2026-09-19 by reporting COMPLETED while their payloads aborted.

Files. The classifier and the liveness reads are in reckon/crew/recovery.py and reckon/crew/runs.py; the reaper, its once-only guard and the launch-failure record are in reckon/crew/dispatch.py; the lift path that must not resume a job-placed run is in reckon/crew/resumption.py. Those four plus a test file are the grant, and this section is dispatched with them named because it is the critical-risk one.

§2b — The stall verdict already has liveness in scope and does not read it

§2 says liveness must follow the job. Before that can be true it has to follow anything, and today it follows a quiet stream. In classify_pointer (reckon/crew/recovery.py) the variable alive is read from the row three lines above the stall branch and used for another case; the stall verdict never consults it:

alive = row.get("process_alive")          # in scope
...

    wait = _stall_wait_reason(pointer)

So a worker running a long test cohort — no stream output, live pid — is declared stalled. Measured three times on 2026-09-21, quiet windows of 901, 904 and 1578 seconds, every one a worker that was alive and went on to deliver; one had already written its manifest and committed. The comment above the branch reasons about "an alive worker sitting in a bounded wait" while the code never establishes aliveness. Each misfire cost a reconciliation and invited the interruption of working work.

This is the substitution the member guard closed, now in the surface that decides whether to interrupt a worker rather than whether to admit one: a quiet stream standing in for a hung process. A recognised wait already pauses rather than stalls; a live process in an unrecognised long operation should too. The distinction that matters is not which waits we can name, but whether anything is running.

And it is why §2's premise is load-bearing rather than tidy. Today's liveness is a host-local os.kill on a recorded pid. Under a placement the worker's pid is on another node, so that call answers about the wrong process — this plan's own words, a pid on another host is not a process. The job id is the handle that survives the move, which makes fixing the stall now and following the job later one repair at two depths.

Measured on this cluster by the imas-ambix coordinator, and recorded because it decides whether §2's premise holds. pam_slurm_adopt sits in the account stack of /etc/pam.d/sshd rather than the session stack, so an ssh connection to a node where the account holds an allocation is authorised but not adopted into the job cgroup: /proc/self/cgroup reads a user slice while the job cgroup holds only the job's own pids. An srun --overlap --jobid step is a real job step and does land in the job cgroup. So containment and reaping follow a placed step and do not follow an ssh session — the premise is safe for the mechanism this plan uses and false for the one it does not. Also measured: the compute node's user slice carries no cpu.max, so the four-core ceiling is a login-node drop-in that does not exist there, and placement buys the ceiling escape even without containment.

Done when a quiet stream with a live process is not reported stalled, asserted with a synthesised pointer whose stream is older than the window and whose pid is alive; a quiet stream with a gone process still reaches a terminal verdict, asserted, so the repair does not blind the check it fixes; liveness that cannot be established — no pid, or a pointer whose recording host is not this one — is reported unknown and does not stall, asserted separately for both; and one placed step prints /proc/self/cgroup showing the job cgroup, settling the containment premise by observation rather than by the account-stack inference above.

Liveness is necessary and it is not sufficient, because a process can be alive and the lane can be the reason it is producing nothing. Measured 2026-09-21 by a peer session sampling the locally served pool three times over one minute: running=30 against a computed ceiling of concurrent_requests=22, waiting=0. Nothing was queueing; the pool was serving 36% over its own document's figure. It does not refuse under that load, it degrades — two runs last emitted a line about their own output coming out garbled before going quiet, and no stream carried an is_error record at all.

So stalled is being emitted for two conditions whose correct operator responses are opposite: this node is stuck, resume it and this fleet is over its ceiling, let it drain. Resuming into the second does not work and the evidence is direct — one node stalled, resumed and stalled again, each attempt spending a turn to arrive at the same place.

A stream census separates the bands cheaply, and one candidate discriminator is already dead. Over 250 runs in one day's shared store, a peer found four runs with exactly one turn, zero tool use and a single text block whose content is the diagnosis — verbatim, API Error: Connection refused and Prompt is too long. That shape is mechanically detectable and its text can go straight into the verdict; "prompt is too long" in particular is an admission refusal that currently dissolves into the generic abandoned bucket, which is where a coordinator's sizing error goes to be forgotten. A second band — real turns, real tool use, nothing produced, no error text — is the degradation signature, and it is the one that cannot be told from a node defect without the lane counts. A third candidate, the share of turns emitting only thinking, looked strong on that band at 31–36% until the same census over known-healthy runs returned 33–35%: indistinguishable, and dead. §3 — One reservation we hold, steps that never queue, and a limit we own

A job per worker mints a reservation per worker. That was measured to be fast, the proving run starting in zero seconds, and speed was the wrong axis: the objection is that concurrency then means submitting more reservations rather than sizing one, and nothing is shared between the sessions on this workstation. The design is one reservation held once, private to us, that every session places workers into as steps.

Measured on 2026-09-19, and the step form decides everything. An allocation is held with no shell attached (salloc --no-shell), which returns a job id and keeps the resources without occupying a terminal. Workers then run inside it as steps under their own step ids. The cluster queue sees one entry for the reservation and never sees a step.

What the two step forms do, measured
Step asks withBehaviour
--exactthe allocation is a quota: four two-core steps ran in an eight-core allocation and a fifth waited 61 s for a slot
--overlapnothing is enforced: six steps each asking 4 GB ran inside an 8 GB allocation, and two steps then held 5 GiB of real memory each, 10 GiB inside 8 GB, and both survived

The choice is --overlap, and the reason is what a worker is. A worker is a thin client that spends nearly all its life blocked on the served model, so reserving cores exactly for one prices an idle process and would need fifty to a hundred cores to host the concurrency the serve already supports. Under --overlap the reservation is a place to run rather than a quota to queue behind: a step launches in under a tenth of a second against the 0.13 s the reservation itself costs once, and no worker ever waits on another. The concurrent limit is then ours, held in the roster, which this project already calls the only concurrency authority, and sized from dispatch experience rather than from a core count.

What follows, stated rather than left implicit. Because nothing is enforced, the failure this plan escapes does not vanish; it moves. On the login node the bound was a 64 GiB slice we did not choose, which announced itself by killing 529 processes. Inside the reservation the bound is the node's real memory and the number is ours, so oversubscribing far enough brings the kills back on a larger machine. That makes the sizing input memory per worker against reserved memory, measured across a real wave, and makes cores the cheap axis precisely because the workers are blocked on the network. The roster limit is a real limit rather than a formality, and the reading to watch while raising it is resident memory across the wave.

Files, and what the surface looks like. The reservation is a durable shared resource of the same kind as the model serve and the project watcher, so it is managed the same way rather than invented afresh: an ensure command in reckon/cli.py and reckon/crew/runs.py that holds the reservation if it is absent and reports it if it is present, mirroring reckon crew watch --ensure; its job id published where every session reads it rather than held in one session's memory, the way the served model publishes its endpoint; and the placement in reckon/crew/dispatch.py resolving that published id rather than taking one on the command line. No admission queue is written: Slurm does not provide one under --overlap and the roster already is one.

§4 — The workspace contract: what a worker needs visible, and what must never be node-local

Three preconditions were measured from both partitions and hold today, but nothing in reckon asserts them, so a placement into a partition that lacks one would fail in a way that reads as a worker defect. Done when. The stall word is a threshold comparison, so it is uninformative in both directions

Three measurements in one day, one display, and they do not agree about what stalled means — because the word carries no fact beyond a comparison against DEFAULT_WATCH_STALL_WINDOW. A worker thinking and a worker that has exited emit the identical reading, so the status is uninformative in both directions rather than merely noisy. That is worse than a false positive, because the prior feels most earned at exactly the moment it is wrong.

  • Five workers resumed wrongly in one session on a stalled reading that was the threshold, not a fault — each resume spending a turn to arrive back where it started.
  • One true positive at 902s against the 900s window, which is as close to a pure artefact as a reading can look: the process was gone, the manifest never completed, and treating it as the artefact would have left a dead run classified as working.
  • One near-miss in the other direction: a coordinator wrote “I am reading it as a display artefact until a process check says otherwise” and was one turn from skipping the check that sentence named. How large is the standing reservation, and what does the roster admit against it?

Measured 2026-09-19. Under --overlap nothing is enforced, so the reservation is a place to run and the limit is the roster's. Compute nodes on the all partition are 28 cores with 128 GB or 36 cores with 192 GB, so a reservation lives within one node rather than spanning the 503 GB the login host carries. Workers are blocked on the served model almost all the time, so cores are cheap and memory is the axis that binds, exactly as it did in the 64 GiB login slice that killed 529 processes. The serve was observed delivering about 450 tokens a second at roughly twenty-five concurrent workers, so twenty-five is the concurrency worth hosting. Per-worker resident memory has not been measured across a wave; the only figure in hand is a single nova solve at 24.6 GB, which is a test process rather than a worker.

Lead ruling 2026-09-20: hold 32 cores and 128 GB on a 36-core node, cap the roster at 25, and adjust the cap from the first wave's measured per-worker resident memory. Matches the concurrency the serve already delivers throughput for, leaves headroom on the node, and is the cheapest shape to start from and to reverse.
