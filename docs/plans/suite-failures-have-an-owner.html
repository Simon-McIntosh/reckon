§1 — A standing failure with no owner taxes every measurement after it

This repository's suite carries failures that no plan claims. They are not regressions and nobody introduced them today; they simply sit there, and the cost is paid by every session that has to prove it did no harm. Because absolute green is unavailable, no claim of the form the suite passes can be made, so every node must instead measure its base and its head and compare failure sets by node id. That is the correct discipline and this plan does not propose weakening it — but it doubles the verification cost of every landing, and a coordinator who forgets it reports a red suite as a defect in the change under review.

Measured 2026-09-09 at dc52c8d: 14 failing node ids. Counted by running the three files that hold them; the two in tests/test_crew.py were verified individually because that file cannot complete in a bounded run (see §4).

One caution the inventory itself demonstrates, and it is why every row above is stamped with a revision. An earlier reading of this same population counted 20 rather than 14, because it included six failures in tests/test_crew_promotion.py observed at a different base, 69db659. At dc52c8d that file passes clean. So a failure set is a property of a revision and not of the repository, and an inventory quoted without its revision is worse than none — it sends someone hunting a failure that is not there. Re-measure before acting on any row here, and record the revision beside the count when you do.

What is deliberately not proposed. Not disabling, not xfail-ing, and not deleting. The repository's own guidance is that a failing test that runs is a high-value signal and a disabled one is worth nothing, so the disposition of every row below is diagnose and fix, or correct a stale expectation, with a stated cause either way. A row closed by making it invisible is not closed.

§4 — Two failures already diagnosed, and a file that cannot be run whole

The diagnosis, carried forward from the session that met them. Both test_dispatch_refuses_work_above_the_selected_configuration_horizon and test_cli_competence_refusal_has_typed_dry_run_parity assert on a refusal's reason and recommendation without the remedy clause — Resolve with reckon crew dispatch once for each smaller node. — that was added deliberately at e68a84a, an ancestor of the base at which they were observed failing. So the expectation is stale and the behaviour is the intended one. These two are the cheapest rows on the board and they are the reason this plan is not speculative.

The file cannot be run whole, which is a second finding rather than an obstacle to the first. tests/test_crew.py does not complete in a bounded run in this environment; it stalls partway, and its output is block-buffered when redirected, so the stall presents as silence rather than as a failure. Both diagnosed rows above were therefore verified by running the two node ids individually. A file that cannot be run whole cannot produce a trustworthy delta for anything inside it, so every future change touching it is measured against a subset chosen by hand — which is precisely the condition that lets a real regression hide. The file is also the largest in the suite by a wide margin, and the repository already splits crew tests across many test_crew_*.py siblings, so the seam that would fix it exists and has simply never been finished.

§5 — What closing this buys, stated so it can be checked later

The point is not a green badge. It is that a delta becomes readable from one run instead of two, and that a coordinator reading a red suite stops having to decide whether the red is theirs. Two consequences are worth stating as claims rather than hopes, because both are measurable afterwards.

Verification cost. Every node landed today paid for a base run and a head run of the same files, purely to establish that a pre-existing failure was pre-existing. If the standing set is empty, the base run is unnecessary for any file whose failures were in it, and the saving is one full run per node touching those files.

A guard's fallout stops being ambiguous. When a fail-open guard is closed, the failures it exposes are legitimate and must be judged on their merits — but that judgement currently starts by separating the exposed failures from the standing ones. With no standing set, an exposed failure is unambiguously the guard's, which is the difference between reading a fallout count and re-deriving it.

§ Decisions

When a test's expectation and the shipped behaviour disagree, and the behaviour was changed deliberately, which side moves?

The two diagnosed failures in §4 assert a refusal's text without a remedy clause added on purpose at e68a84a. Updating the test blesses whatever shipped; reverting the behaviour blesses whatever was asserted first. The choice sets the default for every future instance of this shape, of which the ledger six may contain more.

Locked to match the measure this plan already authored, because the two were in conflict and a plan whose measure presumes an unlocked decision cannot be dispatched against. The evidence is one-sided on the instance: the remedy clause was added deliberately at e68a84a, it tells an operator what to do about a refusal rather than merely that one happened, and reverting it would remove a working affordance to satisfy an assertion written before it existed. The pin is what makes this safe as a default rather than a licence: the clause becomes asserted in its own right, so a future removal fails loudly instead of quietly narrowing what a refusal says. Case-by-case was rejected as a default because it is what the repository already does implicitly, and it is why two stale expectations sat red long enough to become someone else's red base. Recorded as a coordinator lock rather than a lead lock, and cheap to reverse: it governs which side of a disagreement moves, and the instances it governs are all test-side edits.
