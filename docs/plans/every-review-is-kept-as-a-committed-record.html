§1 — Why: reviews cost lane time, and the record of them is not kept

Over 5 and 6 October the local lane ran 456 plan reviews (48.7 run-hours) and 130 code reviews (21.5 run-hours) beside 100 build runs (83.4 run-hours), counted from the committed ledgers of reckon, imas-ambix, imas-codex and nova. Plan reviews outnumbered builds 4.5 to 1, and reviews of both kinds took about 46% of the lane's run-hours. The imas-ambix session imas-ambix-d2 measured the same pattern for 6 October between 00:00 and 07:50 UTC: 95 plan reviews against 38 build nodes, a median of 5.3 minutes each after the 600 s settle window, and a median authored-prose change of 1.3% behind each re-review. A rule that reviews only a new section, or a section changed by at least 30% of its own words, would have run 15 of those 96 reviews and kept all 4 new sections. Its scripts and data are in ~/.cache/imas-ambix-plan-review-evidence/; the wider measurement over 308 stored reviews is in plan-review cycles.

When a revision earns a review is owned elsewhere. Sections §21–§23 of a plan is reviewed before it is built take authored comments and followups out of the fingerprint, cover a unit while its prose stays within review.plan_change_threshold of its reviewed text measured cumulatively, and surface a delivery that failed to store. This plan does not restate that rule. An earlier revision of it did, as a classifier and an answer-check, and those sections were withdrawn in favour of §21–§22 on 2026-10-06 (the earlier text is in commit 91c0f1ab7). Later that day the lead retired the plan-review sweep. Plans are now reviewed when they are written and before they are built, never swept, and the dispatch gate stays the backstop (§25–§27 of the same plan). That retired this plan's author hold too, which existed only to keep the sweep away from a plan mid-rewrite.

What this plan owns is the record. A promoted plan-review run's ledger row carries review: null and one outcome sentence. The findings, answers, fingerprints and unit digests exist only in the host configuration directory, ~/.config/reckon/crew/reviews/<project>/, which is not versioned and not shared with any other clone. Its record timestamp is when the record was stored, not reviewed: 92 records of one plan carry one stamp from a batch import. Answering a finding rewrites the record in place. The nova directory holds 2.5 GB that is not review records at all: copied worktrees, a 627 MB tree.tar, a .git and a .codex left by one September session that used the store as a working directory. Two further faults sit beside the store: a reviewer reports one instance of a finding type per round where it could report the class (83% of duplicate_owner findings follow a review that raised the same type), and the review of a run dispatched with --brief cannot be dispatched at all.

§8 — Every delivered plan review becomes a record

Why. Measured on 2026-10-07 against each project's origin/main, many delivered plan reviews have no committed record. A delivered review is a report directory carrying a report.md with rubric and finding lines. It counts as recorded when a record matches it by review run id, or by plan, fingerprint and rubric. Unrecorded: reckon 240 of 390, nova 49 of 139, imas-ambix 53 of 190, imas-codex 39 of 172, imas-ink 0 of 18. There are two causes. First, the staging path is plan-<slug>.v<N>.json (plan_review_path), with an .at-<blob8> sibling only when the plan bytes differ. Repeated reviews of the same bytes at one version therefore share one file. The three delivered design reviews of a-brief-should-not-cost-what-it-names at version 2 (4, 5 and 6 October) left one record. Second, store_delivered_reviews runs only when the gate or a read reaches the plan, so a plan nobody builds keeps its reviews as report files. §5's import read the host store, so neither kind reached the committed tree. Nothing is lost yet: the reports stay on the host, and raw-report retention withholds any report that has no committed record.

Deliverable. Two changes, as two nodes. (1) A delivered plan review is stored under a path its own review run owns, so two reviews of one plan version never share a staging file. The new name stays inside the plan-<slug>.v<N>.at-*.json family that plan_review._candidate_paths already globs, so the version-keyed readers see every round without a reader change. The change belongs in plan_review_path and store_plan_review, and adds no second store. (2) scripts/import_host_reviews.py also imports every delivered report that no record carries. It parses the report through the parser _store_delivered_report uses and commits it through review.store_committed_review, keyed by the report directory's run id. The import across projects commits into their repositories, as §5's did.

Done when, node (1): a test stores two delivered reviews of one plan version with identical plan bytes, reads both back by review run id, and finds both through _candidate_paths. The negative control writes the second review to the version path, and that test turns red. Done when, node (2): the import's dry run lists, per project, the delivered reports no record carries; after the import is merged, that count is zero in every project when measured against origin; a second pass imports zero; and a test with a delivered report and no stored record fails when the import skips report directories. §10 — A disposition or an answer written after promotion is not shadowed

Why. Since §3, the run-review reader review.stored_record reads a committed record before its staging copy. crew dispose (review.record_dimension_disposition) writes back to whichever file that reader selects. Before promotion that is the staging copy, so a disposition recorded before promotion lives only in staging, and promotion commits a copy without it. After promotion the writer modifies the committed file in the working tree and leaves it uncommitted. Plan-review answers are not affected: read_plan_review picks the newest candidate by modification time, so an answer written to staging after promotion stays visible (checked by the review of 7 October). Measured on 7 October in imas-codex, on run r-20261007T101030801011-names-arm-recall, where promotion dropped a disposition recorded a minute earlier:

  • 10:56:22Z: crew dispose --dimension evidence wrote {"evidence": "exempted"} to the staging record.
  • 10:57Z: promotion committed the review record without dimension_dispositions.
  • After that, review.stored_record returned the committed copy, and the sub-floor duty could not be retired.

Promotion has the matching gap: it commits the staging copy it reads, so a disposition written to a sibling staging file at the same head is left behind.

Deliverable. One node, in reckon/crew/review.py, reckon/crew/plan_review.py and reckon/crew/promotion.py.

  • (1) Promotion carries dimension_dispositions, responses and response_events from every staging copy of the record at the committed head into the committed record.
  • (2) A disposition written to a committed record is committed through _commit_state_write, as promotion commits, rather than left as a modified tracked file in the checkout. A record with no committed copy is written to staging, as now.

Done when a test promotes a run review whose staging copy carries a disposition and reads the disposition back from the committed record through stored_record; it fails when promotion stops carrying dispositions. A test disposes after promotion and finds the committed record's change in a commit, not merely modified in the working tree; it fails when the commit is removed.

§ Decisions

Where do review records live?

Committed. A review is evidence about a plan, and the plan, its ledger and its evidence are already versioned and travel with the repository. The host store is invisible to other clones, has no history, timestamps records with the store time and rewrites them on every answer. A host database would carry the same faults. Promotion already commits every review run, so the record travels in an existing commit.

Is a review discarded once the work it reviewed lands?

Keep. Every measurement that led to this plan read history: the 83% same-type recurrence, the per-section change figures behind §22's threshold, the store-time defect. §22's threshold is a measured choice and must be re-measured on history. The lead's rubric rule counts a finding type declined across three or more plans, which spans plans and time. Plans cite the review behind a ruling. A record is about 4 KB. What gets discarded is the raw report text and run scratch, which the record already distils.
