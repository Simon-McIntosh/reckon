§1 — Why: reviews cost lane time, and the record of them is not kept

Over 5 and 6 October the local lane ran 456 plan reviews (48.7 run-hours) and 130 code reviews (21.5 run-hours) beside 100 build runs (83.4 run-hours), counted from the committed ledgers of reckon, imas-ambix, imas-codex and nova. Plan reviews outnumbered builds 4.5 to 1, and reviews of both kinds took about 46% of the lane's run-hours. The imas-ambix session imas-ambix-d2 measured the same pattern for 6 October between 00:00 and 07:50 UTC: 95 plan reviews against 38 build nodes, a median of 5.3 minutes each after the 600 s settle window, and a median authored-prose change of 1.3% behind each re-review. A rule that reviews only a new section, or a section changed by at least 30% of its own words, would have run 15 of those 96 reviews and kept all 4 new sections. Its scripts and data are in ~/.cache/imas-ambix-plan-review-evidence/; the wider measurement over 308 stored reviews is in plan-review cycles.

When a revision earns a review is owned elsewhere. Sections §21–§23 of a plan is reviewed before it is built take authored comments and followups out of the fingerprint, cover a unit while its prose stays within review.plan_change_threshold of its reviewed text measured cumulatively, and surface a delivery that failed to store. This plan does not restate that rule. An earlier revision of it did, as a classifier and an answer-check, and those sections were withdrawn in favour of §21–§22 on 2026-10-06 (the earlier text is in commit 91c0f1ab7).

What this plan owns is the record. A promoted plan-review run's ledger row carries review: null and one outcome sentence. The findings, answers, fingerprints and unit digests exist only in the host configuration directory, ~/.config/reckon/crew/reviews/<project>/, which is not versioned and not shared with any other clone. Its record timestamp is when the record was stored, not reviewed: 92 records of one plan carry one stamp from a batch import. Answering a finding rewrites the record in place. The nova directory holds 2.5 GB that is not review records at all: copied worktrees, a 627 MB tree.tar, a .git and a .codex left by one September session that used the store as a working directory. Two further faults sit beside the store: a reviewer reports one instance of a finding type per round where it could report the class (83% of duplicate_owner findings follow a review that raised the same type), and the review of a run dispatched with --brief cannot be dispatched at all.

§4 — Reviews are kept after their work lands

Deliverable. A lifecycle derived in Python from the record and the plan, never stored on the record: open (a blocking finding is unanswered), answered, superseded (a later full review of the same subject exists), and landed (the reviewed section has collapsed, the plan has shipped, or the reviewed run is promoted). The gate, the sweep, the obligations view and the SPA's default view read only the hot set, open and answered but not landed. The look-back views read the archive: finding-type recurrence, declined recurrence across plans (declined_recurrence), and how often a later review contradicts an earlier one. One of them replaces the throwaway scripts behind §1's figures (edit_size.py and section_change.py): the existing crew(view="plan-review") gains a per-day summary reporting, per plan, the reviews run, the authored-prose change behind each re-review and how often §22's threshold fired. No view is added, because that view already returns a plan's stored reviews and the summary is a fold over the same records. It reads each record's reviewed bytes from the object store, so re-measuring the threshold is a query rather than a script someone has to remember.

What is discarded is what the record already distils: the raw report text and a review run's scratch, after review.raw_report_retention_days (default 30) on the host.

Done when each lifecycle state is derived in a test from fixture records; a plan shipping moves its reviews to landed without any record being rewritten; declined_recurrence reads the committed archive; the per-day summary reproduces §1's per-section figure for 6 October from the imported records; and the raw-report retention runs on the host with its removals printed.

§5 — Import the host store, and set aside what is not a record

Deliverable. A one-shot migration script, scripts/import_review_store.py, dry run by default and --write to act. It is a script rather than a CLI command because it runs once per host and should not join the command surface's 317 options. For each project it parses every file under the host store. Each one matching the plan-review or run-review shape becomes a committed record, timed from its run id and deduplicated by subject, reviewed sha and review run id. Everything else is listed by path, size and modification time, then moved, not deleted, to a quarantine directory outside the store. From then on a guard in the store's writer refuses anything that is not a record. The 2.5 GB in nova is the known case. Deleting quarantined content is a lead decision taken on the printed inventory.

Done when the dry run's inventory is recorded with counts and bytes per project; the imported count per project equals the recognised records; the store holds records only; and a test shows the guard refusing a non-record write.

§6 — A review of a brief-carried run names its brief

Deliverable. _review_dispatch_fields in reckon/crew/recovery.py copies the reviewed node's plan and section and never its brief, so the review of a run dispatched with --brief composes a node with no authority, and dispatch refuses it as not-dispatchable. This was measured on 2026-10-06 for plan-review-cycles. The composed review carries the reviewed run's stored brief as its authority when the reviewed node names no plan, and the review-missing obligation's command is then dispatchable as printed.

Done when a test composes the review of a brief-carried run and the dispatch dry run validates it.

§7 — An author can hold a plan out of review while rewriting it

Deliverable. §22's threshold already leaves small edits unreviewed; a hold is for a rewrite that will cross it several times before it settles. The hold uses the existing set op on a new path, review_hold, whose value carries the holding session, an expiry and a reason, and whose null value releases it; no new op is added. It is written as a plan-review-hold meta and read through the same exclusion set as the other server scalars in reckon/crew/plan_review.py (PLAN_METADATA_SCALARS), not through a list of its own. While a plan is held, the sweep skips it, crew review-plan refuses and names the holder, and the gate refuses a build of it. Release reviews at once, with no settle wait, whatever §22 says is uncovered. A hold lapses at its expiry, two hours by default, and the holder's own edits renew it.

Done when a test drives the hold through the sweep, the verb, the gate, release and expiry.

§ Decisions

Where do review records live?

Committed. A review is evidence about a plan, and the plan, its ledger and its evidence are already versioned and travel with the repository. The host store is invisible to other clones, has no history, timestamps records with the store time and rewrites them on every answer. A host database would carry the same faults. Promotion already commits every review run, so the record travels in an existing commit.

Is a review discarded once the work it reviewed lands?

Keep. Every measurement that led to this plan read history: the 83% same-type recurrence, the per-section change figures behind §22's threshold, the store-time defect. §22's threshold is a measured choice and must be re-measured on history. The lead's rubric rule counts a finding type declined across three or more plans, which spans plans and time. Plans cite the review behind a ruling. A record is about 4 KB. What gets discarded is the raw report text and run scratch, which the record already distils.
