§3 — A hold lifts once per condition

Deliverable. §2's investigation named two guards that failed. Its report is ~/.config/reckon/crew/reports/reckon/one-live-worker/second-launcher/report.md.

First, the wait sweep's once-only stamp. sweep in reckon/crew/resumption.py lifts a hold unless the live pointer's auto_resume slot reads back the hold's signature, and _stamp_resumption_trigger writes that slot by rewriting the whole pointer. The sweep resumed the nova run at 02:25:08Z and stamped it. The resume's own launch then rewrote the pointer from a snapshot taken before the stamp, so 70 s later the next sweep lifted the same hold again (recovery log lines 7668 and 7669).

Second, the launch backstop. _launcher_refusal refuses only when a pid the run's records name is alive (record_process_alive in reckon/crew/runs.py). The second worker ran under ppid 1 with no attempt record, so nothing named it.

A hold is lifted at most once per condition. The sweep already appends one line per sweep to its append-only recovery log (recovery_log_path in reckon/crew/resumption.py), whose resumed list carries one entry per lift with the resumed run's id and hold signature. §2 found the two lifts there, lines 7668 and 7669. Before lifting, the sweep checks that log for a line already naming this run and this hold signature, and treats the pointer's auto_resume slot as a cache of it, not as the authority. A whole-pointer rewrite cannot drop a line from the log. No new record is added and nothing is retired: the log the sweep already writes becomes the one it reads.

Done when tests/test_a_hold_lifts_once.py rewrites a fixture run's pointer from a snapshot taken before the sweep's stamp, between two sweeps of an unchanged hold, and the second sweep resumes nothing. The negative control is executed and logged: with the log check removed, the second sweep resumes the run again and the test fails. The write paths are reckon/crew/resumption.py and tests/test_a_hold_lifts_once.py.

§4 — A live worker session refuses a second launch

Deliverable. The launcher guard is resume_plan in reckon/crew/dispatch_sessions.py, with _launcher_refusal in reckon/crew/resumption.py as the sweep's mirror of it, held word for word by a parity test. Both refuse only when a pid the run's records name is alive (record_process_alive in reckon/crew/runs.py). §2 found the second worker running under ppid 1 with no attempt record, so nothing named it.

The second worker was claude -p --resume 00ba9ff6… under ppid 1. Its supervisor was gone and wrote no attempt record, so no pid on the run named it. But its argv carried the run's worker session id, and that is how §1's ps listing found it. Both guards already take liveness from one owner, record_process_alive in reckon/crew/runs.py, and both call it directly: resume_plan in reckon/crew/dispatch_sessions.py and _launcher_refusal in reckon/crew/resumption.py. local_liveness in reckon/crew/recovery.py calls it too and so reads the same answer. That owner gains one more read, a private helper in the same module. When every pid the record names is dead and the record names a worker session, it walks /proc the way _pipe_reader_pids already does, for a live process owned by this user whose argv carries that session id as a whole element, excluding the caller and its ancestors. Both predicates have owners it calls rather than rewrites: the whole-element session match is the test _launched_prior_session in reckon/crew/dispatch_launch.py applies to a launch argv, and the bounded ancestry is _ancestor_processes in reckon/crew/dispatch_accounting.py. A hit reads alive. A live run never reaches the walk, so it costs nothing extra. Its reach is the host it runs on, the same reach the pid probe has.

No public definition is added and no refusal changes: both guards fire their existing live-process refusals, whose fixed text reads identically on both doors as tests/test_dry_run_predicts_the_launcher.py requires. No claim, lease or renewal is added, and nothing changes at the launch site.

Done when tests/test_a_live_session_refuses_a_second_worker.py builds a fixture run whose recorded pids are dead and starts a live child process whose argv carries the run's session id as one element. A resume through resume_plan, and the sweep through _launcher_refusal, are both refused with their existing live-process refusals. Once the child exits, both admit. A live process whose argv carries a different session id refuses neither. The negative control is executed and logged: with the session read removed, the first case is admitted and the test fails. The write paths are reckon/crew/runs.py and tests/test_a_live_session_refuses_a_second_worker.py.
