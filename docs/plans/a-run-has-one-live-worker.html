§4 — A live worker session refuses a second launch

Deliverable. The launcher guard is resume_plan in reckon/crew/dispatch_sessions.py, with _launcher_refusal in reckon/crew/resumption.py as the sweep's mirror of it, held word for word by a parity test. Both refuse only when a pid the run's records name is alive (record_process_alive in reckon/crew/runs.py). §2 found the second worker running under ppid 1 with no attempt record, so nothing named it.

The second worker was claude -p --resume 00ba9ff6… under ppid 1. Its supervisor was gone and wrote no attempt record, so no pid on the run named it. But its argv carried the run's worker session id, and that is how §1's ps listing found it. Both guards already take liveness from one owner, record_process_alive in reckon/crew/runs.py, and both call it directly: resume_plan in reckon/crew/dispatch_sessions.py and _launcher_refusal in reckon/crew/resumption.py. local_liveness in reckon/crew/recovery.py calls it too and so reads the same answer. That owner gains one more read, a private helper in the same module. When every pid the record names is dead and the record names a worker session, it walks /proc the way _pipe_reader_pids already does, for a live process owned by this user whose argv carries that session id as a whole element, excluding the caller and its ancestors. Both predicates have owners it calls rather than rewrites: the whole-element session match is the test _launched_prior_session in reckon/crew/dispatch_launch.py applies to a launch argv, and the bounded ancestry is _ancestor_processes in reckon/crew/dispatch_accounting.py. A hit reads alive. A live run never reaches the walk, so it costs nothing extra. Its reach is the host it runs on, the same reach the pid probe has.

No public definition is added and no refusal changes: both guards fire their existing live-process refusals, whose fixed text reads identically on both doors as tests/test_dry_run_predicts_the_launcher.py requires. No claim, lease or renewal is added, and nothing changes at the launch site.

Done when tests/test_a_live_session_refuses_a_second_worker.py builds a fixture run whose recorded pids are dead and starts a live child process whose argv carries the run's session id as one element. A resume through resume_plan, and the sweep through _launcher_refusal, are both refused with their existing live-process refusals. Once the child exits, both admit. §7 — Stopping a live attempt keeps its uncommitted work

Why. In r-20261107T052438443051-line-arm-screen-rows, crew stop ended a repair round mid-turn. Deliverable. Before it signals, terminate writes the worktree's uncommitted changes to stopped-attempt-<n>.diff in the run directory: tracked changes as git diff HEAD, plus the names of untracked files. The path goes in the result crew stop prints, and in the attempt's exit record. A clean tree writes no file and says so. A worktree that cannot be read is named in the result, and the stop still proceeds.

Write paths: reckon/crew/dispatch_sessions.py and the new test tests/test_a_stop_keeps_the_attempts_uncommitted_work.py. §7 waits on §6, which also writes dispatch_sessions.py.

§8 — A widen says when its paths take effect

Why. nova-39 reported on 7 November that crew widen on r-20261107T133413665344-bank-warm-stall returned ok and listed all three paths under write_paths, while the run's worker still could not write them. A running worker's mounts are fixed when bwrap starts it, so no change to the run's claim reaches that worker. The new paths reach only the next attempt. The widen's result (crew_widen, reckon/crew_run_commands.py near line 1658, through claims.widen_claim) says none of this, so a coordinator reads ok as a fixed fence. In that run the read-only tree itself came from the duplicate launch §5 refuses, which no widen can repair.

Deliverable. The widen result carries a takes_effect field. When a worker of the run is alive, as record_process_alive reads it, the field names that worker's attempt and pid and says its mounts are unchanged, so the paths apply from the next attempt. When no worker is alive, it says the next resume or launch mounts them. The text names the field the fence is built from at launch, so a reader knows what was changed.

Write paths: reckon/crew_run_commands.py, reckon/crew/claims.py and the new test tests/test_a_widen_says_when_it_takes_effect.py.

Done when. The defect is reproduced first, in a temporary crew home, through the two paths widen_claim lets through. One is a self-widen, with RECKON_RUN_ID naming the run and a --reason, beside a live stand-in worker. The other is a coordinator's widen of a stopped run. Each returns ok with the paths listed and no word on when they apply, and both outputs are recorded in the gate log. A coordinator's widen beside a live worker is already refused (reckon/crew/claims.py near line 106) and stays refused. The new test then shows three cases:

  • a self-widen beside a live worker names that attempt and its pid, and says its mounts are unchanged;
  • a widen of a stopped run says the next attempt mounts the paths;
  • the field the fence is read from at launch carries the widened paths after the call.

Negative controls: dropping the liveness read makes the first case read as the second; leaving the fence's source field unwidened fails the third. The armed suite command passes at the head, judged by delta against the dispatch base with the new test copied into the base tree. The test asserts that the real crew home is untouched.
