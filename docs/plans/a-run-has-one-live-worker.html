§1 — Why: two workers closed one run, and the second lost its commits

The nova S21 coordinator reported this on 2026-10-08 for run r-20261008T004428659638-cfs-compile-rows-cpu-seconds on the local lane. The worker declared a wait on one of the three all_debug jobs it had submitted (job 1281974). The sequence after that:

Time (CEST)Observed
04:24:05job 1281974 finished
04:24:54the wait sweep resumed the run automatically (resume 2, session 00ba9ff6-0d9b-4cdc-92c9-16ad2a255d38)
04:25the follower reported the run blocked: the worker process is gone with no recorded exit
about 04:26the coordinator's own crew resume was refused: still has a live process
05:06the manifest closed status: complete, saying a second live session shared the worktree and resume id 00ba9ff6 and rewrote the fragment and manifest; its commits line omitted the first five of the run's eight commits
until about 05:13pid 4069224, claude -p --resume 00ba9ff6…, cwd the run's worktree, ppid 1 and 47 minutes old, kept running in its worker_stop hook, then exited by itself

So two launches drove one worker session in one worktree. The live-process check that refused the coordinator's resume did not stop the second launch, and one of the two had lost its supervisor (ppid 1). A run's manifest is its record of what landed, and a second writer that rewrites it from a partial view drops commits a coordinator would then never promote. The coordinator repaired this run by hand.

§2 — Find the second launcher

Deliverable. An investigation of run r-20261008T004428659638-cfs-compile-rows-cpu-seconds. It reads the run directory under ~/.config/reckon/crew/runs/, its attempt and resume records, its stream and stderr logs, the session-host and follower records, and the nova watch log. It names every launch of session 00ba9ff6 between 04:24 and 05:13 by the code path that started it, for example the wait sweep in reckon/crew/resumption.py, a recovery reflex, a repair resume or a coordinator command. It names the check that should have refused the second launch, and why it did not. It also says why the follower read the first worker as gone while a claude -p --resume process for that session was alive with ppid 1. The report and its logs are written to ~/.config/reckon/crew/reports/reckon/one-live-worker/second-launcher/.

Done when the report lists each launch with its timestamp, process id, parent and the function that issued it, each backed by a quoted line from a named log file. It names the guard that admitted the second launch, by file and line, and the condition under which it admits one. It states whether that condition can be reproduced with a fixture run whose recorded worker pid is alive under a different parent. A repair section is then added to this plan with that reproduction as its negative control.
