§2 — A node is gated on the sections it builds

Deliverable. The dispatch-time plan-review gate judges coverage for the units the node builds: its own section, and the document unit only when the document-level text that changed is text the node reads as its contract (the summary, decisions and gates). A node building a covered, unchanged section is admitted while other sections owe a review. The refusal still names every uncovered unit, so a coordinator sees the debt, but it refuses only the nodes that build an uncovered unit. The coverage predicate is plan_review.review_coverage; the change is in how the dispatch gate reads it, not a second predicate.

Done when a test builds a plan with sections s2 and s3, stores a content review covering both, edits s3, and finds that a dispatch building s2 is admitted while a dispatch building s3 is refused naming s3. The test files importing the dispatch gate's module show no added failure against base. Negative control: with the gate reading every unit again, the s2 dispatch must be refused, and the test must fail.

§3 — An edit a finding asked for is covered by that finding's review

Deliverable. When a finding is answered --acted and the next edit to the plan changes only the section the finding anchors, by less than the word-share threshold the coverage predicate already applies (review.plan_change_threshold, 0.30; review.review_need_threshold is the review-need judge's probability cutoff, not a word share), the stored review covers that section at its new digest. The answer records the edit's commit, so the coverage carries its evidence. Edits beyond the anchored section, or beyond the threshold, still owe a review as today. This is the burst rule the reckon-create skill already states ("a burst of fixes earns at most one more, scoped review"), applied at the gate.

Done when a test stores a review with one finding anchored in s5, answers it acted, edits s5 by 1 % of its words, and finds s5 covered; an edit of the same size to s4 leaves s4 uncovered; an edit of 30 % to s5 leaves s5 uncovered. Negative control: with the answered-finding rule removed, the 1 % edit to s5 must read as uncovered.

§4 — A review run is promoted on its record, not on a gate command

Deliverable. Promotion of a run in the review role reads the stored review record as its evidence: the record's status, its findings and the report path. It does not require the manifest's tests line to be an executable command. The executable-gate check stays in force for every other role. The-review-loop-runs-without-hand-steps §2 already promotes a review run once its record is stored, so this section extends that rule to the hand promotion path, and the two cannot disagree.

§9 — A plan is reviewed when it is written, and ordering never re-opens it

The review that matters is the one the writing session reads while it still knows how to fix what it wrote. A review owed later, to a plan its author has left, blocks work and wakes a coordinator who has no context. On 27 and 28 October, admission held or refused launches on PlanReviewMissingError in at least 17 verdicts, on two plans that had been reviewed. In each case a later edit had re-opened a unit. The most common such edit was a section-wait or dependency change, which the document unit's digest counts as authored state.

Review happens at write time: the session that edits a plan composes and answers its review before it leaves the plan. §12 puts that rule in the skills. The producer's self-composing review (a-queue-holds-the-whole-plan §21) is the backstop for a writer that stopped early. This section makes the coverage predicate match that rule: ordering and bookkeeping never earn a review. Section waits (plan-section-depends-on), plan dependencies (depends_on, after, blocks, informs), effort figures and section declarations leave the document unit's digest. Decisions, gates, the summary and section prose stay, because they are the contract a node builds against.

Done when a new tests/test_a_plan_is_reviewed_when_written.py shows these things:

  • On a plan whose stored review covers every unit, changing one section's waits, the plan's depends_on, its effort and one section declaration leaves every unit covered.
  • Changing a decision's choice or a gate's measure uncovers the document unit.
  • Changing a section's prose uncovers that section.

The test files importing reckon.crew.plan_review add no failures against the base revision. Live-store arm: on reckon's live plans, the coverage predicate before and after the change uncovers no unit on any plan whose only change since its review was ordering or bookkeeping. The count of such plans is recorded in the gate log. The negative control keeps section waits in the document digest, and the first arm must fail. §10 — A queued request is checked for review once

Today a queued request is gated twice: at dispatch, and again at every admission pass, by _plan_review_owed in reckon/crew/queue_admission.py. The admission check reads the request's section and the document unit, so an edit anywhere in the plan's contract holds every queued request of that plan until a new review is answered, even though each request carries the done-when it was dispatched with. That second check is what turns one edit into a stalled queue.

A request is checked for review when it enters the queue, and after that only while its own contract has an unreviewed change. Its contract is what §2 gates on: its section and the document text it reads as its contract (the summary, decisions and gates). The request records the digests of both at queue time. Admission holds it only while one of those has changed since it was queued and no stored review covers the new text. The hold lasts only until the writer's write-time review (§9) covers that text. A change to another section, an ordering or bookkeeping edit, and a contract change already reviewed never hold it. So a queued request and an identical fresh dispatch get the same answer, and a properly reviewed plan's queue flows. A coordinator who wants a queued node to build edited section text changes the request with crew queue edit, which is what the build skill already teaches.

Done when a new tests/test_a_queued_request_is_checked_once.py shows these things:

  • A request queued against a covered section stays admissible after another section of the same plan is edited, and after its section's waits are changed.
  • It is held after a decision is changed and the change is uncovered, and released once a review covering it is stored, with no further dispatch.
  • It is held after its own section's text changes and the change is uncovered, and released once a review covering that text is stored.
  • The request records its section and contract digests at queue time.
  • A fresh dispatch and the queued request give the same verdict at every step.

The test files importing reckon.crew.queue_admission add no failures against the base revision. The negative control holds the request on any uncovered unit of the plan, and the other-section arm must fail. Write paths: reckon/crew/queue_admission.py, reckon/crew/node.py and the new test.

§11 — A run that a review does not block lands without a coordinator

The landing pass accepts a review only when it carries no finding of any severity (_review_accepts_promotion in reckon/crew/recovery_review_acceptance.py). On 27 and 28 October it refused 54 runs on that guard, across six projects, and landed none on 28 October. Of the 54, 52 carried no blocking finding. Every one of them waited for a coordinator. A run whose owning session had gone idle waited indefinitely: power_convertor's vs1-fdu-count-citation held a claim for about a day.

The same days show why a review alone is not enough. The coordinator's importer arms found real regressions in three runs whose reviews raised nothing blocking (a-queue-holds-the-whole-plan §19, §22 and §27). Each regression was in a test file outside the run's own tests.

A run lands without a coordinator when four things hold:

  • Its review is complete and carries no blocking finding. The score total sets no floor. On the live store, clean reviews scored from 78 to 118, and a floor at 90 % of the maximum would still have refused 28 runs that their reviewers did not block, among them vs1-fdu-count-citation at 92. One stored total also disagreed with its own dimension scores, reading 5 against a sum of 98. The reviewer controls the gate through severity, and the armed command, the importer population and the clean merge carry the safety.
  • Its armed command adds no failure at its head.
  • The test files importing any production module it changed add no failure at its head. Each added failure is re-run alone three times at base and head before it counts, so a flake is not a regression.
  • It merges cleanly.

The pass measures those test files with the bounds the landing pass already applies: a wall-clock timeout, one run per pass and a stored measurement per head. Non-blocking findings are recorded on the run as exempted, with the reason "non-blocking, noted at landing", and they do not hold the landing. The pass lands any session's run, so an idle owner does not hold work back. A run with a blocking finding, or an added failure that survives its isolated re-runs, goes to its review repair round as it does today.

Done when a new tests/test_a_run_a_review_does_not_block_lands.py shows these things:

  • A run whose review carries two non-blocking findings and a total below 108, and whose arms add nothing, is landed by one pass, with both findings recorded as exempted.
  • A run with a blocking finding is not landed.
  • A run whose importer population adds a failure that persists alone is not landed, and its obligation names the test.
  • A run whose added failure passes alone three times out of three at both revisions is landed.
  • A run owned by a session idle for a day is landed like any other.
  • A run whose head conflicts with the primary branch is not landed, its obligation names the conflicting paths, and nothing is written to the branch.

The negative control restores the any-finding rule, and the first arm must fail. Write paths: reckon/crew/recovery_review_acceptance.py, reckon/crew/queue_landing.py, reckon/crew/landing_measure.py and the new test.

§12 — The skills say a plan is reviewed by the session that writes it

§9 makes ordering and bookkeeping never re-open a review, and §10 lets a reviewed plan's queue flow. Both rest on one practice the skills must teach: the session that writes a plan reviews it before it leaves. That session still holds the context to fix what a finding names. A coordinator reaching the plan later does not.

skills/reckon-create/SKILL.md and skills/reckon-edit/SKILL.md each state the rule once. When an authoring burst ends, the writer composes one content review, answers every finding (fixing the plan, or declining with a reason) and only then leaves the plan. The edit a finding asked for is covered by that finding's review (§3), so answering does not start another round. skills/reckon-build/SKILL.md no longer tells a coordinator to compose a content review before dispatch. It dispatches the sections of a reviewed plan, and when a review is owed it hands the plan back to its writer or lets the producer's backstop compose it. It does not waive the gate.
