§1 — Why: one plan's first wave waited through three reviews and was then waived

On 2026-10-13 a coordinator in power_convertor opened the first wave of jt60sa-coil-circuit-model: five implementation nodes over §2–§5. The plan needed a design review, and two content reviews followed it. Every finding was answered as acted on, and each review was right: between them they caught a regression that could not identify a quiet coil, a transfer function treated as a coupling, a propagator that cannot predict the currents it was asked for, and a wrong supply-model entry point. The gate around them cost more than they did.

The gate's refusal named the uncovered sections correctly, but it applied them to every node of the plan, including nodes whose own sections were covered, and it counted an edit made in answer to a finding as new, unreviewed content.

The same session met three further defects at the edges of the review loop:

  • Promoting the design review run r-20261013T073603575731 by hand was refused with changed paths outside its declared write scope: docs/state/power_convertor/flight.yaml. The run was read-only. That file was changed by f454a1d, the commit the run was dispatched against, not by the run.
  • Promoting the second content review run r-20261013T080129089121 was refused because its manifest's tests line was a prose summary (snapshot plan.html == worktree … == HEAD — diff clean), and a passing gate needs an executable command with an exit status and a log. The review itself was sound. It was promoted as --gate not-run so that its record would be stored.
  • A dispatch dry-run's health_review block printed the compose command reckon crew review --project power_convertor --around jt60sa-coil-circuit-model. Run as printed, it refused with plan 'jt60sa-coil-circuit-model' names no implementable section write paths (reckon/crew/plan_review.py:2491), because that plan's write paths are carried on the dispatch flags, not in the plan.

§2 — A node is gated on the sections it builds

Deliverable. The dispatch-time plan-review gate judges coverage for the units the node builds: its own section, and the document unit only when the document-level text that changed is text the node reads as its contract (the summary, decisions and gates). A node building a covered, unchanged section is admitted while other sections owe a review. The refusal still names every uncovered unit, so a coordinator sees the debt, but it refuses only the nodes that build an uncovered unit. The coverage predicate is plan_review.review_coverage; the change is in how the dispatch gate reads it, not a second predicate.

Done when a test builds a plan with sections s2 and s3, stores a content review covering both, edits s3, and finds that a dispatch building s2 is admitted while a dispatch building s3 is refused naming s3. The test files importing the dispatch gate's module show no added failure against base. Negative control: with the gate reading every unit again, the s2 dispatch must be refused, and the test must fail.

§3 — An edit a finding asked for is covered by that finding's review

Deliverable. When a finding is answered --acted and the next edit to the plan changes only the section the finding anchors, by no more than the review-need threshold (review.review_need_threshold), the stored review covers that section at its new digest. The answer records the edit's commit, so the coverage carries its evidence. Edits beyond the anchored section, or beyond the threshold, still owe a review as today. This is the burst rule the reckon-create skill already states ("a burst of fixes earns at most one more, scoped review"), applied at the gate.

Done when a test stores a review with one finding anchored in s5, answers it acted, edits s5 by 1 % of its words, and finds s5 covered; an edit of the same size to s4 leaves s4 uncovered; an edit of 30 % to s5 leaves s5 uncovered. Negative control: with the answered-finding rule removed, the 1 % edit to s5 must read as uncovered.

§4 — A review run is promoted on its record, not on a gate command

Deliverable. Promotion of a run in the review role reads the stored review record as its evidence: the record's status, its findings and the report path. It does not require the manifest's tests line to be an executable command. The executable-gate check stays in force for every other role. The-review-loop-runs-without-hand-steps §2 already promotes a review run once its record is stored, so this section extends that rule to the hand promotion path, and the two cannot disagree.

Done when a test promotes a review run whose manifest carries a prose tests line and whose record is stored with a recognised status, and finds it promoted as passed; the same run with no stored record is refused; an implement run with a prose tests line is still refused. Negative control: with the review-role branch removed, the first case must be refused as today.

§5 — A run is charged only with what it changed

Deliverable. The promotion's write-scope check compares the run's own commits against its recorded base, so a path changed by the base commit itself is never charged to the run. The first step is to find which comparison the check makes today. On 2026-10-13 it charged a read-only review with docs/state/power_convertor/flight.yaml, which only f454a1d, the run's base, had changed. Then fix it at the one place the diff is taken.

Done when a test dispatches a read-only run against a base commit that itself changed a path outside the run's scope, makes no commit, and promotes it without --accept-path; a run that does change an out-of-scope path is still refused naming it. Negative control: a comparison taken from the base's parent must charge the base's path and fail the test.

§6 — A printed review command runs as printed

Deliverable. The dispatch's health_review block composes its command from the write paths of the dispatch that printed it (--around <path> for each), not from the plan, when the plan declares no section write paths. A printed remedy that refuses when run is a refusal moved one step later.

Done when a test dry-runs a dispatch against a plan with no section write paths, takes the printed compose_command, runs it, and finds a review composed for those paths. Negative control: the plan-slug form must be refused with the existing message.

§7 — Follow-on study: how often the gate refused a covered section

Before §2 and §3 land, measure the size of the problem across the fleet, not only in the one plan that surfaced it. From the dispatch refusals and the allow_unreviewed_plan flags recorded on runs over the last fourteen days, count the refusals in which the built section was covered, and the waivers whose recorded reason says so. Report the count per project, and the median delay from the first refusal to the dispatch that went through. The positive control is the four refusals in §1, which the count must include. It is a read-only investigation node, and its result is recorded in this plan before §2 is dispatched.
