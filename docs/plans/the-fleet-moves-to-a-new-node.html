reckon · fleet node operation

The fleet moves to a new node

The fleet allocation, job 1277272, runs on 98dci4-clu-2018, which Slurm has drained since 3 October 15:54 UTC with the reason Kill task failed. The job has no wall clock and a drain does not end it, so nothing forces the move today. But the node leaves service the moment the job ends, an administrator may end it to service the node, and the causes of its load would follow the fleet to any new node. This plan first fixes what loaded the node, then builds the tooling a move needs, then moves every session into the same tabs on a new node and resumes the coordinators where they stopped.

§1 — What is moving, and what was decided

The evidence is in what-loaded-the-fleet-node. A census taken on 7 October at 03:54 UTC (~/.local/state/fleet/migration/census-20261007T035424Z/) lists what the move must carry:

  • Five zellij sessions with 13 Claude panes: ambix-fleet (tabs ids, map, alembic), codex-fleet (jt-60sa, map-jev), efit-fleet (recon and a shell tab), nova-fleet (a shell tab plan, then S22, S21) and reckon-fleet (Jev, lane-unpub, depth, hooks, plan review). Every pane's conversation transcript is on shared storage, so every pane can be resumed by its id.
  • The crew runs live at the time of the move. Each runs as a step of job 1277272, launched from a supervisor process inside its coordinator's pane tree.
  • Two declared services under the fleet supervisor, imas-ambix agent ingest and imas-ambix agent publish-watch, plus the health sampler. Followers and per-project watch processes belong to their sessions and restart with them.

The model-serving lane, its router, the embedding service and the graph database run as their own jobs on GPU nodes. They are not on the fleet node and are not touched by anything here.

Four choices were made by the lead on 7 October and are locked below: fix first and then migrate; halt the coordinators as late as possible, letting background work run until the cutover; restart each session in the same tabs on the new node; and drive the move from a login node, never from the node being vacated.

§2 — The sampler names what stalled the node

reckon/bin/fleet-health saves a process table only when this user's thread count, its Python process count or available memory crosses a threshold. The failed kill that drained the node and the D-state storm two hours later crossed none of them, and are therefore unattributable. The sampler gains two triggers, the node-wide D-state count and the one-minute load, each with a threshold overridable by environment variable like the existing three. The table it saves gains, per process, its thread count and its wait channel, and the processes in D state are listed whoever owns them, because a stall is often in another user's process or a kernel thread. A snapshot stays rate-limited to one per ten minutes.

  • A test drives one sampling pass against fixture readings for each new trigger and finds a snapshot written with the thread-count and wait-channel columns present; a pass below every threshold writes none.
  • The three existing triggers fire exactly as before, shown by the same fixture harness.
  • No test reads the real /proc or writes under the real state directory.

§3 — A fleet process gets a bounded thread pool

Every heavy Python process on the node opened a thread pool as wide as its 28 cores: an imas-codex serve process holds 57 threads, a pytest process 55 to 61. The allocation's environment therefore sets OMP_NUM_THREADS, OPENBLAS_NUM_THREADS, MKL_NUM_THREADS, NUMEXPR_NUM_THREADS and VECLIB_MAXIMUM_THREADS to one declared default, chosen in the thread-cap decision, unless the variable is already set. The setting goes where every process on the node inherits it: the batch script that fleet_node.generate_hold_script writes, which is what starts the supervisor, the zellij servers, the panes and every worker, and reckon/bin/fleet-claude for a pane started some other way. A process that needs more threads raises its own variable.

Done when:

  • The generated hold script exports each variable with the declared default, and keeps a value already set in the submitting environment; tests assert both.
  • fleet-claude exports the same defaults without overriding a value already set; a test runs it with a stub claude and reads the environment the stub received.
  • One recorded measurement on the new node, after §10, shows a numpy import holding fewer threads than the 28-wide pool measured on clu-2018.

§4 — The supervisor collects every child

fleet_supervisor._reap_finished_children runs only between FIFO requests, and requests are rare, so an exited child can stay defunct for days: an imas-ambix service child started on 2 October is still a zombie under the supervisor. Collection must not depend on a request arriving. The supervisor collects exited children on a bounded interval, or on SIGCHLD, while still never racing the synchronous wait that the session start performs on its own child.

Hazard for the worker: tests/test_fleet_supervisor.py has been measured starting the operator's declared imas-ambix services and leaking them. The gate for this section runs with the services configuration pointed at a temporary directory, and the worker scans its own processes for leaked services after the run.

Done when:

  • A test starts a short-lived child under the serving loop with no request arriving, and finds it collected within the bound.
  • The existing session-start tests still pass, showing the synchronous wait is not raced.

§5 — A declared service runs once across nodes

A declared service is kept to one copy by a lock in the supervisor's runtime directory, which is node-local /tmp. During a move two supervisors run on two nodes, and the second would start a second imas-ambix agent ingest and publish-watch writing the same shared outputs. The supervisor gains a lease on shared storage beside the fleet record: a service's lease names the host, the pid and the job that hold it, and the holder renews it on a short interval. A supervisor on another host starts the service only when no lease is held or the lease has gone stale past a bound several times the renewal interval. Releasing a service, on stop or on shutdown, removes its own lease and never another host's. The node-local lock stays, because it is what guards one node against two copies.

Done when:

  • A test with two supervisor instances, two runtime directories, two host names and one shared state directory starts one copy of a declared service, and the second instance reports the holder.
  • A stale lease is taken over, and a fresh one is not; the staleness bound is a named constant.
  • The test points the services configuration at a temporary directory and starts no real service.

§7 — The worker reservation can be moved

Workers are placed by the shared reservation record, which names the job every worker step joins. ensure_reservation replaces that record only when its job has left the queue, so it cannot be pointed at a new allocation while the old one still runs. The existing reckon crew placement command gains a replacement flag that names its target job explicitly, refuses a job that is not running or is not this user's, records the job it replaced, and prints both. Steps already running in the old job are untouched; every later dispatch and resume places into the new one. It is a flag on a command that already owns the record, not a new command.

§8 — One command carries the move

reckon fleet-node migrate is one entry point that owns the move's ordered steps. A module beneath it holds the sequence and a ledger under ~/.local/state/fleet/migration/<started-at>/ on shared storage. Each invocation reads the ledger, runs the next step, records what it did and stops at the next checkpoint, where the operator confirms before the move goes on. So ordering and resumption belong to the module, not to the operator: a driving session that is lost is replaced by one that runs the same command and continues from the last recorded step. --dry-run prints the next step's actions and changes nothing, --session NAME limits a cutover step to one zellij session, and --confirm is required before the old job is cancelled.

§10 — Stand the new node up in standby

The new allocation is held before anything stops, so the halt in §11 is as short as possible. A supervisor publishes the fleet record when it starts, and cx attaches wherever that record points, so a new supervisor that published at once would send the next attach to a node with no sessions on it. The migrate command's stand-up step therefore starts the new supervisor in standby: it serves requests, but publishes no fleet record and starts no declared service until the migrate command promotes it at cutover. Until then every attach still reaches the old node. The second rehearsal of §9 runs on the standby node.

Done when:

§11 — Quiesce, as late as possible

Coordinators keep working, and their workers keep running, until the cutover is ready to start. Then, in order:

  1. Hold every launch with reckon crew gate --pause (§6), giving the move as the reason.
  2. Message every coordinator pane: reach a checkpoint, launch nothing, record your state in your plan, and reply with your live runs and whether you stopped mid-task. Panes are interactive sessions, which receive peer messages; workers are not, and are never messaged. A session's messaging socket lives in its node's runtime directory, so a peer is reachable only from a session on the same node: measured on 7 October, a login-node session listed one peer and none of the 13 fleet panes. The halt messages are therefore sent by a session on the old fleet node, or the migrate command sends them from a step there.
  3. Let running workers finish and land. A run that cannot finish within the halt window is recorded in the ledger with its resume path and left unpromoted, because promoting an unfinished run destroys its resume path.
  4. Take the final census. For each pane the ledger records whether it was halted mid-task, and the continue prompt it will receive.

A resumed conversation still shows its earlier background tasks and monitors as running, but their processes ended with the old node. The continue prompt says so, names the new node, and asks the coordinator to re-arm what it needs before it continues from its plan.

Done when: the fleet gate is held, every coordinator pane has replied or is recorded as idle, no worker step of job 1277272 is running except those recorded as parked, and the final census is in the ledger.

§15 — A worker's hooks run under reckon's interpreter

reckon/hooks/install.py binds the obligations hook to the checkout's own .venv/bin/python, and states that the worker stop hook "is standard-library only and keeps its bare script command". It no longer is: worker_stop.py imports reckon._timestamps, which needs datetime.UTC from Python 3.11. A bare command resolves python3 through the worker's PATH, and a worker launched from a non-interactive shell on a compute node finds the system Python 3.9. Measured on 7 October: every worker this plan dispatched over ssh to the fleet node ended its turn with ImportError: cannot import name 'UTC' from 'datetime' (/usr/lib64/python3.9/datetime.py) in its stop hook, which is non-blocking, so two workers stopped with work uncommitted or unreported and had to be resumed. The worker git guard is launched the same way and imports reckon, and a guard that cannot import fails open. The move drives steps from a login node into other nodes' shells, so this must hold before it.

Every hook a worker runs is launched by the checkout's own interpreter, as the obligations hook already is, both in the installed user settings and in each fenced worker's harness settings. The docstring states the rule that now holds.

§ Decisions

Fix the defects and build the tooling first, or move now by hand?

The node is stable and the job has no wall clock, so the move can wait for tooling that makes it repeatable, and the new node should not inherit the old one's load.

When are coordinators halted?

Work continues until the cutover is ready; the new node is stood up and rehearsed before anything stops.

How are sessions restored on the new node?

Each session restarts in the same tabs, in the same order, each Claude pane resumed by its conversation id. Tabs closed before the final census are not restored.

Where does the session driving the move run?

On a login node, because every pane on the old node ends at its cutover, a driver there included.

Move by a second allocation with a per-session cutover, or by requeueing job 1277272?

The job is requeueable and has already been requeued twice after node failures (clu-2058, then clu-2020), each time resurrecting its panes on the next node. A planned requeue keeps the job id, so the fleet and reservation records stay valid, but every session and worker stops at once and there is no way back. A second allocation lets sessions move one at a time and keeps the old node until the last one has moved.

Sessions move one at a time and the old node stays until the last has moved, so any step can be rolled back; the requeue path stays the fallback if the new-node tooling fails.

What default caps a fleet process's compute-library thread pool?

Eight threads per compute-library pool leaves numerical tests headroom while cutting the 28-wide pools that multiplied the thread count.

What size is the new allocation?

The current job holds 28 cores and 120 GB. The hold command's defaults are 26 cores and 96 GB, which leave two cores and GPFS headroom to the system so slurmd keeps answering under load.

At 26 cores and 96 GB the job's own OOM killer acts before the node runs out, so a peak like 6 October's 99.5 GB kills the largest test process rather than risking a NODE_FAIL that ends every session.
