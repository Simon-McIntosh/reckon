§1 — Why: one module is over the bound, and the next lane change adds to it

tests/test_every_module_fits_a_worker_window.py holds every production module under 50,000 tokens, measured by reckon.crew.routing._tokens_for_bytes, which the test imports. Its allowlist is empty, so an offender fails the test for every node whose gate runs it. A module that size also cannot be handed whole to a local-lane worker, whose usable window is 230,144 tokens and which must also hold the node's tests and brief.

At f5e88d284, reckon/budget.py is 180,363 bytes, which is 51,533 tokens. It was already 50,293 tokens before 6ebe65ba4, which added the purchased-credit lift, so the overflow is accumulated growth rather than one change. The test's two other offenders, reckon/crew/review.py and reckon/ledger.py, are outside this plan.

Two lane-and-model-routing sections also edit the file. §46, which shows each metered lane's burn, has been delivered and is under review, and it merges first. §48, which can make a lane's pace advice rather than a hold, adds to the file and waits for this split. The finished plan for the same test, every-module-fits-a-worker-window, set the method, in its §8: move code by capability, never by line count.
