§1 — The rule

On 2026-10-22 the lead ruled that new plans may not carry a deferred-work bucket, and that its language is to be purged from every reckon surface. All additional work is either written as its own plan section, or handled directly by the agent dispatching the job, through the instructions or prompt it gives a worker. Nothing is parked in a list that no roadmap reads.

Today reckon writes that bucket in three places, and its own label for it is the term follow-on:

  • Reviews. A finding's severity is blocking or follow-on (reckon/crew/review.py, FINDING_SEVERITIES, near line 155; reckon/crew/review_lifecycle.py, NON_BLOCKING_SEVERITIES, near line 74). The repair reflex skips the second kind (reckon/crew/repair.py, near line 162), so a finding with that label is recorded and then left.
  • Worker manifests. A worker lists work it found outside its fence under follow_ons (reckon/crew/prompts.py, near line 840). At promotion, reckon/crew/reports.py (near line 2797) turns each entry into a plan followup, and reckon/ledger.py records the paths they name as follow_on_paths.
  • Plans and skills. Plan sections carry a paragraph headed with the term, and six files under skills/ teach it.

A census on 2026-10-22 found the term in 19 production files (78 occurrences), 6 skill files (27) and 45 test files (236). The sections below replace each use with the two routes the rule allows, keep old records readable, and refuse new writes of the term. Older plan text stays as written, because it is history.

§2 — A review finding is blocking or non-blocking

Deliverable. A finding's severity is blocking or non-blocking. The review prompts (reckon/crew/prompts/review.md, reckon/crew/prompts/figure_review.md) teach those two words. FINDING_SEVERITIES and NON_BLOCKING_SEVERITIES name them, and so does every refusal or report message that names a severity, in reckon/crew/reports.py, reckon/crew/repair.py, reckon/crew/findings.py and reckon/crew/review_lifecycle.py. repair.follow_on_findings takes a name for what it returns, such as non_blocking_findings.

The prompts say what a non-blocking finding is for, in the two dispositions crew dispose already records, from the closed set DIMENSION_DISPOSITION_KINDS = ("folded", "exempted") (reckon/crew/review.py, near line 3426). folded names the node that carries the work. That is either the next dispatch, whose prompt the coordinator writes the work into, or the node a new plan section dispatches. exempted states why the finding is not acted on. A new section is answered by folding into its node, so no disposition kind is added and the closed set is unchanged. A stored review that says follow-on still reads as non-blocking. The reader maps the old word on the way in and never writes it back.

§4 — A plan write carrying the bucket's language is refused

Deliverable. The plan store refuses a write that adds the term follow-on, or its plural, to a plan's prose. That covers a new plan through edit_plan's create, a new section through insert_section, a text-mode edit, and a section body. The refusal names the rule, that additional work is a section or a prompt, and quotes the offending fragment. The term inside a <code> element is a citation of a symbol, not a bucket, so it is allowed. Text already in a plan is not refused by a text-mode edit. That route supplies an old_html and new_html pair, and only the fragment the edit adds is checked, so editing an old plan stays possible. The other routes check the whole value they are given. An insert_section, a created plan's section body and an append_evidence body are new text in any case. A set of sections.<id>.body passes the whole new body to the check (reckon/_store_section_ops.py, near line 143) with no prior body to compare. Re-setting a legacy body whose prose already carries the term is therefore refused, and the refusal names text mode as the way to edit that section. reckon audit-doc reports the term in prose as a warning on any plan.

The check extends the one existing predicate for authored plan bodies: _forged_plan_structure and _refuse_forged_body_structure (reckon/_store.py, near lines 899 and 924). Today every structured path already reaches it. insert_section and append_evidence call it. reckon/_store_section_ops.py's _refuse_forged_structure imports it for section-body writes. Plan creation with a section body appends through _queue_authored_section (reckon/_store.py, near line 3371) as a section_insertions effect, which the write path applies through _insert_authored_section and so through the predicate. Only the text-mode write does not reach it. This section calls the same predicate from the text-mode path, so every authoring path refuses the same fragments through one check. No second check is written. The prose it reads, with <code> and <pre> left out, comes from the one reader that already drops those subtrees: reckon/doccheck.py's _prose_text (near line 384). audit-doc and the store both use it. reckon/_plan_html.py's section_prose is not used, because its output keeps the text inside <code> and <pre> (its skip set is only script, style and head), and changing it would move every review digest. If the store cannot import doccheck without a cycle, the subtree-dropping rule moves to reckon/_plan_html.py beside section_prose, and doccheck imports it from there, so one copy remains.

On the interface: the refusal is one more reason the shared predicate reports, so it adds no refusal family code. Each authoring path raises it through its own existing channel, so no caller sees a new error code. edit_plan's create and insert_section raise OpError, which surfaces as op_error. The text-mode write keeps ValueError, which surfaces as text_edit_error (reckon/_store.py, near line 1979). The predicate returns the offending fragment, and each path raises it in its own channel. The refuser composes every refusal as f"{subject} must not contain {forged}" (reckon/_store.py, near line 928), and its existing reasons are bare labels. For this case the reason it returns is the rule itself, together with the quoted term: for example the term "follow-on" in prose; additional work is a plan section or an instruction in the dispatching prompt. The existing message format then names the rule and quotes the fragment, with no new message path. The audit-doc check is one new warning kind. It retires nothing, and this section is where it is accounted for.

Done when tests/test_a_plan_write_refuses_the_bucket.py holds all of these:

  • a section inserted with the term in its prose is refused, naming the rule;
  • a plan created through edit_plan with the term in a section body is refused, through op_error;
  • a text-mode edit that adds the term in prose is refused through text_edit_error, naming the rule;
  • a set of sections.<id>.body carrying the term is refused, naming the rule;
  • an append_evidence whose body carries the term is refused, naming the rule;
  • the same section with the term only inside <code> is accepted;
  • a text edit to a plan whose older text carries the term, which adds none, is accepted;
  • audit-doc warns on a plan carrying the term in prose.

Negative control: remove the check, and the first case is accepted. The gate runs the new test with every test file that drives edit_plan's create, insert_section or text mode, at base and at head, judged by delta.
