§1 — The rule

On 2026-10-22 the lead ruled that new plans may not carry a deferred-work bucket, and that its language is to be purged from every reckon surface. All additional work is either written as its own plan section, or handled directly by the agent dispatching the job, through the instructions or prompt it gives a worker. Nothing is parked in a list that no roadmap reads.

Today reckon writes that bucket in three places, and its own label for it is the term follow-on:

  • Reviews. A finding's severity is blocking or follow-on (reckon/crew/review.py, FINDING_SEVERITIES, near line 155; reckon/crew/review_lifecycle.py, NON_BLOCKING_SEVERITIES, near line 74). The repair reflex skips the second kind (reckon/crew/repair.py, near line 162), so a finding with that label is recorded and then left.
  • Worker manifests. A worker lists work it found outside its fence under follow_ons (reckon/crew/prompts.py, near line 840). At promotion, reckon/crew/reports.py (near line 2797) turns each entry into a plan followup, and reckon/ledger.py records the paths they name as follow_on_paths.
  • Plans and skills. Plan sections carry a paragraph headed with the term, and six files under skills/ teach it.

A census on 2026-10-22 found the term in 19 production files (78 occurrences), 6 skill files (27) and 45 test files (236). The sections below replace each use with the two routes the rule allows, keep old records readable, and refuse new writes of the term. Older plan text stays as written, because it is history.

§2 — A review finding is blocking or non-blocking

Deliverable. A finding's severity is blocking or non-blocking. The review prompts (reckon/crew/prompts/review.md, reckon/crew/prompts/figure_review.md) teach those two words. FINDING_SEVERITIES and NON_BLOCKING_SEVERITIES name them, and so does every refusal or report message that names a severity, in reckon/crew/reports.py, reckon/crew/repair.py, reckon/crew/findings.py and reckon/crew/review_lifecycle.py. repair.follow_on_findings takes a name for what it returns, such as non_blocking_findings.

The prompts say what a non-blocking finding is for, in the two dispositions crew dispose already records, from the closed set DIMENSION_DISPOSITION_KINDS = ("folded", "exempted") (reckon/crew/review.py, near line 3426). folded names the node that carries the work. That is either the next dispatch, whose prompt the coordinator writes the work into, or the node a new plan section dispatches. exempted states why the finding is not acted on. A new section is answered by folding into its node, so no disposition kind is added and the closed set is unchanged. A stored review that says follow-on still reads as non-blocking. The reader maps the old word on the way in and never writes it back.

Done when tests/test_a_finding_is_blocking_or_non_blocking.py holds all of these:

  • a review report whose findings say non-blocking is stored and read with that severity, and the repair reflex composes no repair from it;
  • a stored record whose findings say follow-on reads as non-blocking;
  • neither review prompt, and no message the review modules emit, carries the old word.

Negative control: restore the old word in FINDING_SEVERITIES alone, and the stored-record case fails. The gate runs the new test with every test file the census lists for the severity, at base and at head, judged by delta. A test that asserts the old word in emitted output is updated to the new word. A test fixture that stores the old word stays, because it proves old records still read. Write paths: reckon/crew/review.py, reckon/crew/review_lifecycle.py, reckon/crew/repair.py, reckon/crew/findings.py, reckon/crew/reports.py, reckon/crew/recovery_repair_dispatch.py (which calls the renamed follow_on_findings twice and emits the old word in two messages), reckon/crew/prompts/review.md, reckon/crew/prompts/figure_review.md, tests/test_a_finding_is_blocking_or_non_blocking.py, docs/evidence/fragments/additional-work-is-a-section/a-finding-is-blocking-or-non-blocking.html. Other test files the change breaks are granted from the failure ids the worker reports.

§3 — Work outside a worker's fence returns to its coordinator

Deliverable. The worker manifest field follow_ons becomes outside_scope: the work a worker found but was fenced out of. The worker prompt (reckon/crew/prompts.py, near lines 762 and 840) asks for that field and states the rule. The coordinator answers each entry with a plan section or with an instruction in the next dispatch's prompt. Promotion no longer turns entries into plan followups: reckon/crew/reports.py's conversion (near line 2797) is removed. The entries reach the coordinator instead, on the promotion report and on the run's ledger row, as work it must answer.

The ledger key follow_on_paths becomes outside_scope_paths (reckon/ledger.py, reckon/run_record.py, reckon/run_store.py, reckon/crew/promotion.py), and so do its readers in reckon/crew/recovery_repair_dispatch.py, reckon/crew/recovery_watch.py and reckon/crew/dispatch_peer.py. A manifest or ledger row written before the change still reads, through the old key, mapped on the way in.

Done when tests/test_work_outside_scope_returns_to_the_coordinator.py holds all of these:

  • a manifest with outside_scope entries promotes with no plan followup written, and its entries appear on the promotion report and the ledger row;
  • a manifest written with the old key reads the same way;
  • the worker prompt carries the new field and the rule, and not the old word.

Negative control: restore the followup conversion, and the first case finds a followup written. The gate runs the new test with every test file the census lists for the manifest field and the ledger key, at base and at head, judged by delta. The two comment-only sites the census found outside every list also take the new wording: reckon/crew/promotion_release.py (near line 131) and reckon/crew/promotion_records.py (near line 126). Write paths: the modules named above, those two, tests/test_work_outside_scope_returns_to_the_coordinator.py, docs/evidence/fragments/additional-work-is-a-section/work-outside-scope-returns-to-the-coordinator.html. §4 — A plan write carrying the bucket's language is refused

Deliverable. The plan store refuses a write that adds the term follow-on, or its plural, to a plan's prose. That covers a new plan through edit_plan's create, a new section through insert_section, a text-mode edit, and a section body. The refusal names the rule, that additional work is a section or a prompt, and quotes the offending fragment. The term inside a <code> element is a citation of a symbol, not a bucket, so it is allowed. Text already in a plan is never refused. Only the fragment a write adds is checked, so editing an old plan stays possible. reckon audit-doc reports the term in prose as a warning on any plan.

The check extends the one existing predicate for authored plan bodies: _forged_plan_structure and _refuse_forged_body_structure (reckon/_store.py, near lines 899 and 924). Today two paths reach it. insert_section and append_evidence call it, and reckon/_store_section_ops.py's _refuse_forged_structure imports it for section-body writes. Plan creation through edit_plan and the text-mode write do not reach it. This section calls the same predicate from those two paths as well, so all four authoring paths refuse the same fragments through one check. No second check is written. The prose it reads, with <code> and <pre> left out, comes from the reader that already owns that: reckon/doccheck.py's _prose_text (near line 384) for audit-doc, and reckon/_plan_html.py's section_prose (near line 474) for the store. Neither is copied.

On the interface: the refusal is one more reason inside the forged-body refusal family, so it adds no family code. The audit-doc check is one new warning kind. It retires nothing, and this section is where it is accounted for.

Done when tests/test_a_plan_write_refuses_the_bucket.py holds all of these:

  • a section inserted with the term in its prose is refused, naming the rule;
  • the same section with the term only inside <code> is accepted;
  • a text edit to a plan whose older text carries the term, which adds none, is accepted;
  • audit-doc warns on a plan carrying the term in prose.

Negative control: remove the check, and the first case is accepted. The gate runs the new test with every test file that drives edit_plan's create, insert_section or text mode, at base and at head, judged by delta. Write paths: reckon/_store.py, reckon/_store_section_ops.py, reckon/doccheck.py, tests/test_a_plan_write_refuses_the_bucket.py, docs/evidence/fragments/additional-work-is-a-section/a-plan-write-refuses-the-bucket.html.

§5 — The skills and references state the rule

Deliverable. The six skill files that teach the bucket teach the rule instead: skills/reckon-build/SKILL.md, its references worker-protocol.md, sprint-orchestration.md, coordinator-reference.md and conditional-guidance.md, and skills/reckon-edit/SKILL.md. Each one states that work found beyond a node becomes a plan section, or an instruction in the next dispatch's prompt. Each one names the non-blocking severity and the outside_scope field from §2 and §3. None carries the old term in prose. tests/test_skill_contracts.py gains a case that fails on the term in any skill file's prose.

Done when that case passes over skills/. Its negative control, restoring one old sentence, fails it. tests/test_skill_contracts.py passes at head and adds no failure against base.
