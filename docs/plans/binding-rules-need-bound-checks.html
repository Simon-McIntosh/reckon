§1 — The repository already diagnosed this about itself

Two sessions shipping in this repository on the same day hit two unrelated defect classes, and both turned out to be violations of rules that are already written down, already binding, and already argued. Nobody had to be persuaded of either rule. Nothing checked either one.

The user-space guidance says so in as many words, in the section that governs naming: a rule without a check decays. It then does something about it — it pairs each ban with a runnable command bound to a moment that always happens, which for that section is git add. The AI-attribution rule holds in practice for the same reason: it carries a one-line grep and a moment to run it at. The rules that decay here are precisely the ones with prose and no command.

This plan takes the two classes measured on 2026-08-25 and gives each a check bound to a moment. It is not a proposal to write more rules. Both rules already exist.

§2 — The two measured instances

Both were found by work colliding with them, not by review. That is the signature of this class: the rule reads as obviously correct, the violation passes every gate, and the cost lands on whoever touches the file next.

Every [tool.X] namespace in pyproject.toml must resolve to something the project declares, and one did not. tests/test_declared_tooling.py enumerates each configured namespace against the declared sets and fails on any that resolves to nothing, with a companion case pinning the red-before-green demonstration so the check cannot pass by never firing. ruff>=0.16.4,<0.17 is now declared and resolves. §4 — An assertion must state a contract, not a snapshot ✓ landed 2026-09-15

A closed-set assertion and a legitimate exact-value assertion look identical to a linter, so the mechanism chosen is not static at all: perturb the thing the assertion observes with one benign extra member and see which assertions break. A contract survives the addition; a snapshot does not. scripts/check_snapshot_assertions.py carries the four recorded instances and the later object-substitution instance as self-contained specimens and reports the census as numbers: 4 of 5 snapshot instances flagged, 0 of 4 carve-outs, every case guarded by a positive control that passes before its perturbation is applied. It names its bound moment — staging a change that adds, edits, or pins an exact-value assertion, the same moment the naming bans bind to — and tests/test_snapshot_assertion_shape.py re-runs the same census in the suite.

The one miss is kept explicit rather than promised away: literal-token membership survives an additive member, so perturb-and-observe does not catch every implementation-text pin. The four flagged instances remain unrepaired in the tree; §5 scopes repair out of this plan, so it needs a plan of its own. §5 — Out of scope

Writing more rules. Both rules exist and are well argued. If a check cannot be built for one of them, the honest outcome is a recorded negative result, not a stronger restatement of the prose.

Repairing the four recorded instances. All four were repaired the day they were found, in the plans that hit them. This plan owns the mechanism that would have caught them, not their remediation.

Other repositories. The configured-versus-declared gap plausibly exists wherever a project configures a tool it does not declare, and this plan does not survey for it. A check that lands here can be carried outward later by whoever owns that sweep.

The general form for this plan: a check whose enforcement depends on how it was invoked is not a bound check, and the invocation that disables it is the one worth testing.
THE PROPOSED REPAIR HAS A WORKING IMPLEMENTATION IN A SIBLING REPOSITORY, which turns it from a recommendation into a transcription. The imas-codex-b8 session checked its own equivalent gate on hearing this finding and reported the result. imas-codex carries requires_isn = pytest.mark.skipif(not _isn_available(), ...), structurally the same construction as this repository's requires_linkml. Run under the bare-interpreter form - .venv/bin/python -m pytest, no uv run - its ISN-dependent grammar tests report 25 PASSED rather than skipped. The only difference is what the predicate resolves: theirs resolves an IMPORT, with imas_standard_names and imas_standard_names.grammar both find_spec to a module; ours resolves a CONSOLE SCRIPT on PATH through shutil.which. That is the whole defect stated as a contrast. An import answers whether the dependency is usable by the code under test, which is the question the gate exists to ask. shutil.which answers whether this shell's PATH happens to be arranged the way uv arranges it, which is a question about the invocation rather than about the environment. Two repositories, the same construction, and only one of them asks the question it means to. So the repair is not a design decision to be weighed: change the predicate to resolve the generator modules rather than the console scripts, or have the regeneration script import them so PATH stops being load-bearing. A sibling repository proves the shape works under exactly the invocation that defeats ours. One sharpening from that session worth keeping in the general rule. A guard that skips is indistinguishable from a guard that passes in every summary line anyone reads, which is why two sessions independently concluded the assertion was absent while looking directly at it. A missing check is at least discoverable by looking for it. So: a skip on a dependency the project itself declares is a broken environment and should be an error rather than a skip, because the only honest states are enforced and failed.

A SECOND MEASURED INSTANCE OF A RULE THIS REPOSITORY WROTE FROM ITS OWN INCIDENT, UNDETECTED FOR EIGHT DAYS. Reported by a peer session auditing S16 plans, and it is the cleanest specimen of this plan's thesis yet: the rule is stated, the incident that produced it is recorded, the remedy is documented, and nothing fires.

The rule. AGENTS.md carries A test must not encode the current date as its own named section, written from a measured failure on 2026-08-25: an archive dry-run test asserted the literals "145d" and "176d", ages derived from its own fixture dates and frozen into strings. It passed its node's gate, passed the full suite twice, and turned main red at midnight with nobody touching the code. Two workers in another session were blocked on it before anyone noticed, because the failure surfaced in their gate rather than in ours.

The second instance. On graph-derived-schedule, a plan recorded at impl 1.0, one of five declared measures cannot re-run green: fixture stamps fixed at 2026-09-02 to 09-04 are rendered against a 60-hour retention filter and the live wall clock. It has been red since approximately 2026-09-06 and was attributed to nothing, because no one re-ran a measure on a plan already recorded as landed.

The discriminator that identifies it as the clock rather than the logic is the one the AGENTS.md section asks for and it is already present in the file: the sibling test that supplies an explicit clock passes. Same code path, same fixture, different source of now.

Why it belongs here rather than on the plan that carries it. The defect is not that someone wrote a dated test. It is that a rule with a measured incident behind it, a named section, and a stated tell — a literal that would have to be edited on a future date to keep the test true — still has nothing that fires. Eight days of red is the measure of what the gap costs, and the cost is paid by whoever next runs that suite rather than by the author.

The check is mechanical and cheap, which is the argument for writing it. A scan for a wall-clock read (datetime.now, date.today, time.time) reaching an assertion in the same test, and for date or duration literals in expected values, with an allow-list for tests that inject an explicit clock. That is the same shape as the path-scan check in §2 rather than the perturbation in §4 — the fourth distinct check shape recorded on this plan, which continues to be evidence that the thesis is about the missing binding rather than about any one technique.

A neighbouring instance from the same audit, recorded because its repair generalises differently. That is the §4 snapshot family — a test asserting the shape of a whole object when its subject is one property of it — and the same shape as a test asserting a field is ABSENT and failing the day the field legitimately arrives, four of which were repaired here in one night on 2026-09-08. Two measures on one plan, two different check shapes, neither caught by impl 1.0.
