§1 — The repository already diagnosed this about itself

Two sessions shipping in this repository on the same day hit two unrelated defect classes, and both turned out to be violations of rules that are already written down, already binding, and already argued. Nobody had to be persuaded of either rule. Nothing checked either one.

The user-space guidance says so in as many words, in the section that governs naming: a rule without a check decays. It then does something about it — it pairs each ban with a runnable command bound to a moment that always happens, which for that section is git add. The AI-attribution rule holds in practice for the same reason: it carries a one-line grep and a moment to run it at. The rules that decay here are precisely the ones with prose and no command.

This plan takes the two classes measured on 2026-08-25 and gives each a check bound to a moment. It is not a proposal to write more rules. Both rules already exist.

§2 — The two measured instances

Both were found by work colliding with them, not by review. That is the signature of this class: the rule reads as obviously correct, the violation passes every gate, and the cost lands on whoever touches the file next.

ClassThe rule that already forbids itWhat was measuredWhy review never caught it
A snapshot asserted as a contract “any recorded absolute that moves on its own … State the delta or derive the figure; a snapshot of a moving number is a fuse.” Four instances in one day across four unrelated files and two sessions: a byte-equality assertion on seven stylesheet placeholders, literal implementation strings inside two components five workers were rewriting, a positional source scan standing in for a rendering contract, and a closed exact-key-set assertion on a served payload that broke when two fields were added on purpose. It passes when written. Its author sees green; the next person to touch the file sees red and cannot tell a regression from a superseded requirement.
A tool configured but never declared The pre-stage protocol is literally uv run ruff check --fix . and uv run ruff format . pyproject.toml carries a real [tool.ruff] block with a considered extend-exclude; the dev dependency group is linkml and pytest only; ruff is absent from the project environment as both executable and module. Every clean lint either session has ever recorded here came through a user-level install resolved by absolute path. It fails open. The documented command could never run, and the protocol appeared to work for exactly as long as everyone happened to have a user-level install on PATH.

The second one is the more alarming of the two, because a configured tool is a stated guarantee. A tool that is merely absent announces itself the first time someone reaches for it; a tool that is configured and absent implies a guarantee the environment does not provide, and the configuration is what stops anyone looking.

§3 — Declared tools must match configured tools

This half is a set comparison and needs no environment. Every [tool.X] namespace in pyproject.toml must be satisfied by something the project declares: a runtime dependency, a dependency group, or [build-system].requires. Measured against the current tree, three namespaces exist and exactly one fails.

Configured namespaceResolves throughVerdict
[tool.hatch.*][build-system].requires — hatchling, hatch-vcssatisfied
[tool.pytest.*]dependency-groups.devsatisfied
[tool.ruff]nothingunsatisfied

The namespace-to-distribution mapping is not always the identity — hatch resolves through two differently-named distributions — so the check needs a small explicit alias table rather than a string match, and an unknown namespace should fail loudly rather than be assumed satisfied.

Done when a test enumerates every configured namespace, resolves each against the declared sets, and fails on any that resolves to nothing; the check is shown to fail on the current tree before the declaration is added and to pass after; and uv run ruff check resolves.

§4 — An assertion must state a contract, not a snapshot

This half is genuinely harder, and pretending otherwise is how it would get a check that fires on the wrong things. A closed-set assertion and a legitimate exact-value assertion look identical to a linter. The existing guidance already carves out cases where the exact figure is correct and must be kept — a measurement that stops someone undoing the code, runtime state described in the past tense, tool codes and dependency pins — and a naive pattern match would flag every one of them.

The promising mechanism is not static at all: it is to perturb and observe. A test that pins a closed set is detectable by adding a benign extra member to what it observes — one additional field on a payload, one additional file in a listing — and seeing which assertions break. A contract survives the addition; a snapshot does not. That is a property of the assertion's shape rather than of its text, which is exactly the distinction no grep can make.

The cost is that it needs somewhere to inject the benign member, and the injection has to be honest — a field nothing consumes, added in one place, reverted after. Whether that is worth its machinery is the open decision below.

Done when the chosen mechanism is shown to flag at least three of the four instances recorded in §2 when run against their pre-repair revisions, and to flag none of the carve-out cases the guidance already names.

§5 — Out of scope

Writing more rules. Both rules exist and are well argued. If a check cannot be built for one of them, the honest outcome is a recorded negative result, not a stronger restatement of the prose.

Repairing the four recorded instances. All four were repaired the day they were found, in the plans that hit them. This plan owns the mechanism that would have caught them, not their remediation.

Other repositories. The configured-versus-declared gap plausibly exists wherever a project configures a tool it does not declare, and this plan does not survey for it. A check that lands here can be carried outward later by whoever owns that sweep.

§ Decisions

How should a check tell a closed-set snapshot from a legitimate exact-value assertion?

Four instances in one day across two sessions makes the class real. But the guidance's own carve-outs — a measurement that stops someone undoing the code, runtime state in the past tense, tool codes and version pins — are exactly what a text-matching check would flag, so a noisy check would be worse than none.
