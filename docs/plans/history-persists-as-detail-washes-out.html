§1 — One file, parsed whole, by everything that asks anything

The run ledger is a single JSON document. Measured at authoring: 4,311,619 bytes holding 818 run records, 236 roster members and 16 holds, with 542 non-merge commits touching it. Every question anyone asks of run history — what a member last ran, which runs are unreconciled, what a configuration's competence horizon is, whether a node's write scope collides with a live claim — is answered by parsing all of it.

That is affordable today and it is the wrong shape for three reasons, each of which is already costing something measurable:

  • Every read is a full read. Seven modules reach the store: the ledger module itself, promotion, dispatch, routing, the CLI, the MCP surface and the native-agent guard. A question about one run costs the whole document. There is no index, so there is no cheaper answer available even in principle.
  • Nothing can age out. A JSON array has one lifetime for every field in it. Detail worth keeping for a week — the per-run stream pointers, the gate check payload, the suite observation — is kept for the same duration as the summary rows that are worth keeping forever, because the file has no mechanism to hold them for different durations. So the only available retention policy is deleting whole rows, which is exactly the policy that makes a historical figure permanently unrecoverable.
  • Concurrent appends are a text merge. Eleven live runs promoting into one array is a read-modify-write race resolved by git on indentation. It has already produced a 41-row append rendering as 35,000 changed lines when the indentation did not match, and 44 rows landing in four untracked foreign checkouts when a cross-repository dispatch wrote to the worker's tree rather than the project's registered one.

The derivation that reads it is the sharpest illustration. A capabilities derive takes 26.3 s, of which 99.7% is computation over 502 stream files totalling 3.68 GB — 195 times the ledger's own size. Reading the ledger alone costs 0.09 s. The corpus is being re-read because the figures derived from it are not stored, which the companion work is fixing; once they are stored, the remaining cost is entirely the shape of the store they are stored in.

§2 — What the store is, and what washing out means

An embedded SQLite database in the crew config home, one file, no server, already in the standard library. Three properties are the whole reason for choosing it over the current one:

  • An append is an append. A promoting run inserts one row under a transaction. It does not read, rewrite or serialise the other 825. The concurrent-promotion race disappears rather than being defended against.
  • A question can be asked without reading everything. Indexed on run id, member, node, project and completion time — the five keys every current reader scans linearly for.
  • Rows can hold their fields for different durations. This is what makes rotation possible at all, and it is the property a single JSON array cannot have at any size.

The split is measured, not proposed. Over the 826 rows present at authoring — 2.81 MB of row payload across 54 distinct fields — thirteen fields carry 78.3% of the bytes and the other forty-three carry 21.7%. One field, the node contract re-stored on every run, is 43.7% by itself. So the durable row and the detail hanging off it are not a design preference imposed on the data; they are where the data already divides.

What that buys, stated as a figure rather than as a direction. Today's file is 5,300 bytes per run. The durable half is 737, a 7.2× reduction, so the permanent record of 10,000 runs is 7.4 MB. That is larger than today's 4.38 MB file, and saying otherwise would be the wrong claim: the win is not that permanent history is smaller in absolute terms, it is that the part that grows without bound grows 7.2× more slowly, and that the part which does not need to be permanent stops being permanent. Deleting a run's gate-check payload after its horizon does not delete that the run happened, what it cost, or what it produced — which is everything a long-horizon measurement reads.

Three tables, and the two the current file conflates. The ledger today is one document holding runs, roster members and holds together; 826, 236 and 16 of them. Members and holds are small, mutable and read on every dispatch, while runs are large, immutable once written and read in bulk — opposite access patterns sharing one lock and one parse. They become their own tables, which is most of why a dispatch stops paying for the run history it never looks at.

§3 — The swap is hot, because reads and writes flip independently

There is no quiet window in this, and asserting there was one was wrong. The reason it is safe to do live is specific to how this codebase deploys: the CLI is current on every invocation. A promotion happens in a freshly started reckon crew complete process, so there is no population of long-lived writers holding stale code, and therefore no window in which some writers use the new store and some use the old. The cold surfaces — the served docs process and the MCP — are readers, and a stale reader reading the file that is still being written is correct rather than dangerous.

So the swap runs as expand, dual-write, verify, cut over one reader at a time, and only then contract. At every stage both stores hold the same rows, which is what makes every stage individually reversible by changing which one is read.

Verify is a standing measurement, not a one-off. "Demonstrated stable" has to be a number or it is a feeling. The check reads both stores and asserts row-for-row identity — same run ids, same field values, same count — and runs on every promotion, which is cheap because it is one indexed count and one digest. What is wanted before any reader is cut over is a stated count of promotions with zero divergences, and coverage of every shape that has historically diverged: a shadow run, a refused run, a resumed run, and a cross-repository dispatch, since that last one is the case that stranded 44 rows in checkouts nobody was reading.

Cut over the most expensive reader first, not the safest. The derivation is the one whose failure is loudest and most contained: a wrong capability verdict shows up immediately as a refused or wrongly-admitted dispatch, and is undone by pointing one reader back. Cutting over the cheap readers first buys confidence about the case that was never in doubt.

§4 — The committed file does not go away; it becomes the export

The 542 commits are the point. That file is not only a store, it is the transport by which run history reaches another checkout, another host, and the reader who has no crew config home at all. A SQLite database cannot be merged by git, so retiring the committed file is a separate decision from adopting the database, and conflating them is what would have forced a quiet window.

Keeping both is not a compromise, it is the shape the split already wants: the database is the local, queryable, rotating store holding full detail; the committed file is the durable narrow export — the same summary half that never ages out — written whenever it changes. That export is small, it merges line-by-line because it is one row per run in a stable order, and it is reconstructible from the database at any time, which is what makes the contract stage reversible.

§5 — Rotation is the last switch, and it is gated

Everything above is reversible because both stores hold everything. Rotation is the one step that is not: a washed-out field is gone. So it is enabled last, after the cutover has held, and it inherits the same invariant the reaper is being given for run directories — nothing is removed before the figures derived from it exist. The retention work and the record-at-promotion work in the companion plan are prerequisites in the strict sense: without them, rotation deletes detail whose derived value was never computed, and the row becomes permanently unmeasurable. One row in the current corpus has already crossed that line.

§ Decisions

How long is per-run detail kept before it washes out (§2)?

Open. The run directories the detail points at are currently reaped at 30 days, so a detail horizon longer than that keeps pointers to files that are gone. by-count holds a fixed number of recent runs regardless of elapsed time, which is the option that behaves the same in a quiet week and a busy one.

What does the committed file carry after cutover (§4)?

Open. durable-rows is the narrow permanent half, which is what makes the export small enough to merge line-by-line. everything keeps today's content and today's merge cost. retire makes cross-checkout history unavailable to any reader without the config home and is listed to be rejected explicitly rather than by omission.

§ Followups

Expand and dual-write before anything reads the database — §3

Execution order is forced by the reversibility argument rather than by preference: the expand and dual-write stages must both hold before the equality check can measure anything, and the check must report a stated count of clean promotions before any reader is cut over. The two prerequisite sections in dispatch-cost-per-durable-node — the retention invariant and the per-run figures recorded at promotion — gate §5 only; §3's earlier stages do not wait on them. Both decisions are open and neither blocks the expand stage.

Two gaps to close before the later stages, both recorded now because neither fails anything today.

  • The durable declaration is 10 fields; §2 measured 43. Nothing is lost at expand, because the detail table holds everything else — but rotation deletes detail, and 33 fields this plan calls permanent are currently on the wrong side of that line: the agent configuration, role, specification level, commits, changed lines, tests added, lineage, worker seconds and the two derived figures among them. The declaration must reach 43 before rotation is enabled, and because rotation is the one irreversible step, this is the gap with real teeth.
  • A recorded store failure is invisible where an operator looks. append_run returns the outcome on its payload and promotion does not forward it, so a shadow that has been silently failing for a week reads exactly like one that has been working. The dual-write stage cannot be believed without it — the equality check would compare a file against a store nothing has been writing to.
