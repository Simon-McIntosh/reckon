The roadmap decides what can run from each plan's sections classified implementable, its gates, its decisions and its dependency edges. A followup contributes none of those. Its schema carries a title, a body, a one-line invocation, a status and author fields, and no section, gate, effort or edge. So work written into a followup cannot appear in ready_now, cannot be dispatched as a section, cannot be held by a gate and carries no effort. On a shipped plan it does not appear at all. The build skill already says that same-plan work becomes a section and a followup is only a pointer to another plan. On 2026-10-01, 102 of the 129 open followups on reckon's plans broke that rule, because nothing checks it. This plan adds the check, at both the read side and the write side, and then clears the 102.

§1 — What the roadmap cannot see today

Reckon reads followups in exactly two places. continuation_present in reckon/_store.py accepts an open followup as the continuation a landing write must name. _dispatchability in reckon/roadmap.py counts a plan with an execution gate as dispatchable only while it has some open followup. Nothing else that decides readiness, order or effort reads them.

On 2026-10-01 the coordinator of S22 classified every open followup on docs/plans/*.html by the plan and section its invocation line names. The classifier was a heuristic over the prompt and recommends_skill fields, so a few rows may be misfiled:

§2 — One predicate names a followup that hides work, and the roadmap reports it

Write one function that takes a parsed plan and one open followup and answers whether the followup is a pointer or hides work. It is a pointer when its invocation names a different plan (a bare slug other than the host, or project:slug in another mount) or a sprint, or when it names its own plan together with a section the plan's section_declarations classify implementable. Anything else hides work. That covers an invocation naming its own plan with no section, with a section that is done or unclassified, or naming nothing parseable. The function returns the reason as one of a small fixed set of words, so a reader can tell the cases apart.

The roadmap calls this function for every open followup on every plan it inventories, including completed plans, and reports each one that hides work as a wiring finding of severity warn. The finding names the plan, the followup id and the reason. There is one implementation: the finding and §3's refusal import the same function, and no surface re-derives it.

Done when a test builds plans in a temporary docs directory, one for each case: a pointer to another plan, a pointer to the plan's own implementable section, a followup naming a done section, a followup naming no section, and a followup on a shipped plan. It asserts the predicate's answer and reason for each, and that the roadmap's findings list exactly the three that hide work. Run against reckon's own docs/plans, the finding count is recorded beside §1's 102, and every disagreement with §1's heuristic is listed by followup id with the reason. The negative control makes the predicate accept a followup that names its own plan with no section; the no-section case must then fail.

§3 — The write path refuses a new followup that hides work

Appending a followup through edit_plan, or through the HTTP patch path, is refused when §2's predicate says the new followup hides work. The refusal names the reason and the remedy: add the work as a section of this plan, or create a new plan when this one is complete, and point the followup at it. Resolving, superseding and reading an existing followup are never refused, because those are how §4 clears the backlog.

This closes a guard that has been open, so measure what rests on it before writing the refusal. Flip the check on in a scratch tree and count the failing tests and the callers that append followups: crew.followup_ops_from_manifest, the promotion path, and test fixtures that append a followup to a plan with no sections. That count goes in the manifest. A caller that appends work as a followup is repaired to write a pointer or to stop appending. A fixture is changed only where it encodes the old behaviour, not to make the gate pass.

Done when a test appends each of §2's five cases through edit_plan and asserts that the three that hide work are refused with the reason word, the two pointers are written, and resolving an existing followup that hides work succeeds. The negative control removes the check from the append path; the followup-naming-no-section case must then be written rather than refused. The gate covers every test file that appends a followup, found by a text search of tests/ for the append op and for followup_ops_from_manifest.

§4 — The open followups that hide work become sections, plans or pointers

The coordinator works through §2's finding list, because plan state is the coordinator's to write. Each row is disposed in one of four ways:

  • Same-plan work on a live plan becomes a section classified implementable. The followup is resolved with an outcome naming the section.
  • Work on a complete plan moves to a live plan that owns it, as a section there. If no plan owns it, a new plan is created. The followup is resolved with an outcome naming where the work went.
  • A followup that is really a pointer, but is written against its own plan, is rewritten as a resolved followup plus a new one that points at the right place.
  • Work that is already done or no longer wanted is resolved with an outcome saying so and citing the commit or the reason.

The coordinator of the session that wrote a row decides its disposition, or is told of it before its plan changes. s22-coord converts its own fifteen first. Rows from sessions that have ended are disposed by the coordinator running this section.

Done when the roadmap's finding from §2 lists zero followups that hide work on reckon's plans, or each remaining row is named here with the coordinator that holds it. A table in this plan's landed record shows every row's disposition and where its work went.

§5 — Order of work

§2 lands first, because it is read-only and gives §4 its worklist from the server instead of from a heuristic. §3 and §4 then proceed side by side. The refusal applies only to new appends, and §4 only resolves and adds sections, so neither waits on the other. s22-coord's fifteen are converted at once, before §2 lands, because they are known now.

§ Decisions

How far should the followup fix go?

The audit found 102 open followups that hide work, 15 of them s22-coord's.

A rule without a check decays, and 87 violations from other sessions show it already has. Making followups schedulable would add a second unit of work beside sections, so the fix keeps followups as pointers and checks that they are.
