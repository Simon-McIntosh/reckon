A held dispatch waits its fair turn

When the lane has no room, a dispatch today returns to its coordinator, which retries on its own schedule. A freed slot goes to whichever coordinator happens to retry next, so a session that dispatches a lot keeps winning, and nothing records who is waiting. This plan gives held dispatches a queue that admits them in fair-share order: the sessions using least of the lane go first.

§1 — Context

The local lane's router already publishes a fair share for each coordinator session: admission.sessions[<session>].worker_slots in the lane document, beside new_session_worker_slots and the lane-wide worker_slots. _lane_worker_allowance in reckon/crew/dispatch.py reads that share, most specific first. When the share is zero or less, dispatch raises LaneHeld, a kind of LanePaused: nothing is created, the node stays ready, and the caller is expected to retry.

So the fairness exists at the moment of admission, but not across the wait. Each held coordinator polls on its own. When a slot frees, the next coordinator to retry takes it, whatever the shares say, and a busy session that retries often keeps taking freed slots. Held work is also invisible: the follower's q column counts the router gate's waiting requests, not reckon's held dispatches, and no view lists them.

§4 — One drainer launches queued work

The drainer is the one new loop. It is declared in the fleet services configuration and run by the fleet supervisor. The supervisor already starts each declared service exactly once behind its host lease and restarts it with backoff, so the drainer takes no lease of its own. On a cadence it reads the lane document and the queued pointers. Whenever the router grants room to a session with queued work, it admits the highest-ranked entry by launching that run through the same dispatch path a coordinator uses, so the queued pointer becomes the dispatched run. A launch that fails leaves the pointer queued with the failure recorded. That shared path does not do this by itself. On a refused or failed spawn it rolls back through _release_launch_claim (reckon/crew/dispatch_claims.py), which unlinks the pointer and removes the run directory. A post-spawn failure with no manifest is marked launch-failed (reckon/crew/dispatch_launch.py). The drainer therefore keeps the queued pointer's content before it launches. On either outcome it writes the pointer back as queued, with the failure and its time recorded on it, so a failed attempt never destroys the request.

Done when:

  • A test with a lane document that opens one slot finds the highest-ranked queued run launched and no other.
  • Two drainers racing over the same queued pointers launch each run once.
  • A paused fleet gate launches nothing, and a launch failure leaves the run queued with the failure recorded.
  • The drainer is declared through the fleet services configuration, and the coordinator's follower sees the run's phase leave queued for the launch phases, starting then working, as it reports a run its coordinator launched itself.

Entry point. The declared service runs a new verb, reckon crew admit --lane <lane>, which repeats its admission pass on a cadence until it is stopped; --once runs a single pass, which is what the tests drive. No existing command launches a queued dispatch, so nothing is retired or merged into it: reckon crew drain is the session-closure report, and reckon crew recover --dispatch-reviews launches reviews for scoring runs. The interface grows by one verb with two options. The node ships the verb and a test that declares it in a temporary services configuration. Declaring the service on a workstation is an operator step taken after the merge.

§6 — A re-queue racing its own discard queues afresh

On the re-queue path runs.queue_dispatch selects the existing queued pointer, then takes its pointer lock and reads it again. A discard that removes the pointer in between makes that read raise no live run, so a dispatch racing the discard of its own queued entry errors instead of queueing afresh.

§12 — A queued dispatch is accepted, up to the session's share

Why. When the local lane holds a dispatch, it is stored as a queued run, and the reckon-admit-local fleet service launches it when a slot frees. The CLI reports it as a refusal anyway. The LanePaused branch in reckon/crew_dispatch_commands.py prints "ok": false and "error": "lane-paused" and exits 75, which is exactly what a paused gate prints, although a paused gate queues nothing. The only difference is that the queued case also carries a run_id and a position. On 2026-10-13 orchestrators in several sessions read this as "the local lane is full" and stopped dispatching, leaving ready work unqueued while the lane was the thing the queue exists to keep full. Nothing limits how much one session may queue either. A coordinator told to keep dispatching could put a whole plan in the queue ahead of every other session.

Deliverable. A dispatch the lane queues reports success. It sets ok and queued to true, carries the run_id, position and the hold's reason, and exits 0. A paused or unreadable gate keeps its refusal: lane-paused, exit 75, no run id. A session may hold at most its share of queued runs. That share is the lane document's admission.fair_share, kept between 2 and 8, and taken as 2 when the document publishes none. A dispatch past the cap is refused before anything is written, with queue-full and exit 75, and the refusal names the session's queued count and its cap. The count is taken under the queue's own lock, so two concurrent dispatches from one session cannot both pass it. A repeat dispatch of a node that is already queued updates its pointer and is never refused by the cap. The admission pass relaunching a queued run is not counted against it either.

Done when tests dispatch through the CLI while the lane holds and find each of these:

  • a queued dispatch exits 0 with ok and queued true, and its run id names the queued pointer;
  • a paused gate still exits 75 with lane-paused, and no pointer is written;
  • a session already at its cap is refused queue-full, and nothing is written;
  • at the cap, a repeat dispatch of an already-queued node updates that pointer;
  • the cap follows the published share: 1 gives 2, 3 gives 3, 12 gives 8, and an absent share gives 2.

tests/test_a_crew_verb_ok_reads_its_outcome.py passes. The test files importing reckon/crew_dispatch_commands.py or reckon/crew/runs.py show no added failure against base. There are two negative controls, both logged under the run directory. Reporting a queued dispatch as the refusal again must fail the success case, and removing the cap check must fail the queue-full case. Write paths are reckon/crew_dispatch_commands.py, reckon/crew/dispatch.py, reckon/crew/runs.py and tests/test_a_queued_dispatch_is_accepted.py. §6 also writes runs.py, so whichever of the two is dispatched second waits for the first to land.

§13 — A Jev hold queues for the local lane

Why. When Jev holds a node, it is usually waiting for the local lane. Its hold criterion says that routine or deferrable work should hold for the local lane, rather than spend a pressed metered lane, whenever local is not admitting. A hold today raises BudgetHold and exits 3, writing only a picker-hold record. The coordinator must remember to re-dispatch, and the admit service never sees the node. Every Jev hold recorded for reckon on 2026-10-13 offered the local lane as its only serving lane, with review-excluded-backend and in-harness-backend removing the rest. A queued request on that lane is exactly what those holds were waiting for. The same hold also stalls the queue itself. The admission pass relaunches a queued run through the same dispatch, so Jev is asked again, and at 10:10 that day nine queued imas-codex reviews carried BudgetHold: picker selected hold as their last failure. They were being put back after every pass rather than launched. A hold also skips node validation, because dispatch in reckon/crew/dispatch.py validates only after the route is resolved, so a malformed node is held where it should be refused.

Deliverable. When Jev holds and one of its offered candidates is on the local backend, dispatch validates the node before anything else and refuses a malformed node as not-dispatchable. A valid node continues on that local candidate. The lane allowance then decides: the node launches if the lane has room, and otherwise it is queued and reported as §12 specifies, under the same cap. The picker-hold record is still written, marked as queued with the run id, so the outcome history keeps Jev's choice. A hold that offered no local candidate stays a budget-hold, as today.

Done when tests stub the picker to return a hold and find each of these:

  • with a local candidate offered and room on the lane, the node launches on local;
  • an admission pass relaunching a queued run that Jev holds, with a local candidate offered and the session granted a slot, launches the run instead of putting it back;
  • with no local candidate offered, the dispatch exits 3 with budget-hold and nothing is queued;
  • a node failing validation exits 2 with not-dispatchable and nothing is queued.

The test files importing reckon/crew/dispatch.py or reckon/crew/picker/outcomes.py show no added failure against base. For the negative control, re-raise the hold before the local continuation; the queued case must then fail. The control is logged under the run directory. §14 — A node is queued once, even while it is being admitted

Why. The admission pass unlinks a queued pointer before it calls dispatch, so that the run's own write-path claim cannot refuse its launch. Until the launched run writes its own pointer, nothing on disk names that node at all. runs.queue_dispatch deduplicates only against pointers in the queued phase, so a dispatch arriving in that gap queues a second copy. On 2026-10-13 an imas-efit session queued review-of-west-iron-map-contraction-f8939ef9b726 (run r-20261013T074129767920). The pass dropped that pointer at 07:47:53Z and launched r-20261013T074756779667 at 07:48:23Z. In between, at 07:48:16Z, the coordinator saw no run for the node and dispatched again, which queued r-20261013T074816818235. That copy then cycled through the queue beside its working twin until the coordinator discarded it at about 08:00Z. Nothing refused the duplicate at any point. Once launched, a queued pointer never conflicts with the working run's path claim, because it holds no worktree.

Deliverable. A node is queued at most once per session while any run of it is queued, being admitted, or in flight. The admission pass leaves a handover record that queue_dispatch reads, from before it unlinks the pointer until the launched run's pointer exists or the request is put back. A dispatch arriving during the handover, or while a non-terminal run of the same project, session, plan, section and node is live, is not queued again. It is answered with the existing run's id and phase, and nothing new is written. That answer is built at the queue_dispatch call site in reckon/crew/dispatch.py, which today reports only run_id and position. A run that is not queued has no position, so the answer must not look one up in the admission order. A dispatch that matches a queued pointer on session, node, plan and section is the re-queue that updates that pointer in place, so the scope check must not refuse it for colliding with the pointer's own claim. On 2026-10-13 such a re-dispatch, made to add a review's unreconciled waiver, was refused with scope-conflict against exactly that claim, because the scope check runs before the same-node match.

Done when tests find each of these:

  • a dispatch made while the admission pass holds the handover for that node writes no second pointer and reports the run being admitted;
  • a dispatch of a node whose run is working writes no queued pointer and reports the working run and its phase;
  • after a failed launch puts the request back, a dispatch updates that one pointer;
  • a re-dispatch of a queued node whose write paths are claimed by that pointer updates it in place, with no scope conflict;
  • a different node from the same session still queues, and a different node claiming the same path is still refused.

The test files importing reckon/crew/runs.py or reckon/crew/queue_admission.py show no added failure against base. For the negative control, ignore the handover record; the first case must then write a second pointer. The control is logged under the run directory. Write paths are reckon/crew/runs.py, reckon/crew/queue_admission.py, reckon/crew/dispatch.py and tests/test_a_node_is_queued_once.py. This section runs after §11, §12, §13 and the-monitor-shows-the-work-it-watches §15, which also write these files.

§15 — A queued plan review is stored when it delivers

Why. A composed plan review's report directory carries dispatch.json, which names the crew run that ran it. Promotion joins the finished run to the review through that file (_plan_review_crew_run_id in reckon/crew/review.py, read by _plan_review_record_for_promoting_run in reckon/crew/promotion_checks.py). When the compose is queued, dispatch.json records status: lane-paused and run_id: null. When the admission pass later launches the request, it does so under a new run id, and nothing writes that id back. The run delivers its report and promotes, but the join finds no run and the review is never stored. On 2026-10-13 the content review of this plan queued as r-20261013T080553093117, launched as r-20261013T080918804954, delivered at 10:18 and promoted with stored: false. It was stored only because a later build dispatch of the plan swept unstored deliveries. Every queued plan review in the fleet takes the same path, and a review that is never stored keeps its plan's build gate shut.

Deliverable. A plan review that queued and was later launched is joined to the run that produced it and stored when that run is promoted, with its times taken from that run. A review that launched directly is joined exactly as before.

§16 — A failed launch does not block its node's next launch

Why. A run's worktree path is named for its session and node, so every attempt to launch one node in one session reaches for the same path. _create_worktree in reckon/crew/routing.py fails with worktree creation failed: … already exists when an earlier attempt left its tree there. A launch that exits before writing any stream record can leave exactly that tree behind. Every later admission retry of the node then fails on the existing path, so the request cycles through the queue and never launches. On 2026-10-13 in imas-codex, attempt r-20261013T071559249836 exited at launch with 0 stream records. Its tree blocked review-of-shs-registry-worklist-7e73ce74bc5e until the coordinator checked the tree was clean and unused and removed it by hand, after which the review launched. The evidence is on §4.

Deliverable. A launch of a node whose path holds a tree left by an earlier attempt goes ahead when that tree is disposable, and is refused by name when it is not. A tree is disposable when the attempt that made it has no live pointer, its worktree is clean, and its head has no commits beyond the base it was created at. Such a tree is released through the existing whole-tree release before the new one is created. A tree with commits, uncommitted changes or a live owner is never removed, and the refusal names the attempt and the reason.

Done when tests over temporary repositories find each of these:

  • a launch whose path holds a clean, commit-free tree from an attempt with no live pointer releases that tree and launches;
  • a tree holding a commit beyond its base is kept, and the launch is refused naming the attempt and the commit;
  • a tree with uncommitted changes is kept and refused the same way;
  • a tree whose attempt still has a live pointer is kept and refused.

The test files importing reckon/crew/routing.py show no added failure against base. For the negative control, treat every existing tree as not disposable; the first case must then fail on the existing path. The control is logged under the run directory. Write paths are reckon/crew/routing.py and tests/test_a_failed_launch_does_not_block_its_node.py.

§17 — A queued repair keeps its unreconciled waiver

Why. §10 found that a review queued on a held lane loses its unreconciled waiver. The admission pass rebuilds the waiver only from the queued request's dispatch_options (options.get("allow_unreconciled_runs") in reckon/crew/queue_admission.py), and the review paths passed the override without recording it there. Repairs have the same defect. dispatch_repair_for_run in reckon/crew/recovery_repair_dispatch.py passes unreconciled_override=True with no dispatch_options. A repair queued on a held local lane is therefore relaunched without the waiver and refused with UnreconciledRuns, which names the run the repair exists to fix. reckon-cd found this as a follow-on of the §10 review on 2026-10-13.

Deliverable. A repair queued while the lane holds carries its unreconciled waiver in dispatch_options, so the admission pass relaunches it with the same exemption it was dispatched with. This follows the pattern §10 used for reviews.

Done when a test queues a repair of a delivered run older than the grace while the lane holds, admits it, and finds it launches rather than failing UnreconciledRuns. A non-repair implementation node dispatched in the same state is still refused. The test files importing reckon/crew/recovery_repair_dispatch.py show no added failure against base. For the negative control, drop the waiver from dispatch_options; the queued repair must then fail UnreconciledRuns. The control is logged under the run directory. Write paths are reckon/crew/recovery_repair_dispatch.py and tests/test_a_queued_repair_keeps_its_waiver.py.

§ Decisions

Where does the drainer run?

The lane is shared across projects, so one drainer per lane, declared as a fleet service under its host lease, stays fair without cross-project coordination and survives a node move.

What measures a session's use of the lane?

It matches the router's per-session share and needs no new accounting; the count is taken again after every admission, so sessions converge and then alternate.

Which lanes queue a held dispatch?

The local lane is where the router publishes fair shares and where contention happens; a metered lane's hold is a budget window and keeps holding as today.
