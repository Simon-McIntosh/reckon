§1 — Why: every review reads one node or one plan, and nothing reads between them

reckon reviews work at two points. Before a build, a plan gets a content review and a prior-art and depth review (reckon/crew/prompts/plan_review.md, plan_design_review.md). After a node lands, its diff gets an independent review (reckon/crew/prompts/review.md). Both are bounded to their subject by design: the landed-node review is told "Do not review code the node did not touch" (review.md:29-45). The crew-pattern review of 2026-09-26 measured the result: work that is better-verified, not better-designed, because nothing owns the codebase between nodes (orchestrator-crew-pattern-review §1).

§2 — The design: one skill, three modes, and a reviewer that starts from what is already known

Is a standing health review busy work? It is when it generates findings from nothing, because the measured yield of review is already low where the subject is small: 12.9% of source-change reviews and 2.4% of docs reviews led to an observable repair (review-node-utility §3). It is not when it starts from the 847 follow-ons a month that are recorded and dropped, ranks them by recurrence, and proposes at most one treatment that deletes code or closes a recurring finding. The design below holds those three properties: known findings first, one treatment per review, and a yield the lead can read, with a stated rule for turning the reflex off.

A skill, not a coordinator node pattern alone. A node pattern written into reckon-build would add a second concern to a skill that the-crew-contract-fits-one-read is trying to shrink, and would leave plan and sprint health with no entry point. So:

  • /reckon-review <target> is one skill whose mode follows from its target: a path or --around <plan> selects code mode; a plan slug selects plan mode; a sprint id or project selects portfolio mode. A lead or a coordinator calls the same skill.
  • Code mode composes one read-only review node through a crew verb (§6), reads it back, and dispatches at most one treatment node. Plan mode audits a plan's currency against the code and its overlap with other live plans. Portfolio mode proposes close, merge, retire and re-sprint dispositions and applies them through reckon-edit and reckon-sprint, recording the round in the sprint review resource that already exists (docs/state/reckon/review.html, last written 2026-09-01).
  • reckon-build gains one step, not a procedure: in a plan build's first wave, run /reckon-review --around <plan> once, in parallel with the plan's own nodes (§9).

Reuse map. Findings already live in committed review records (docs/state/reckon/reviews/run/, from every-review-is-kept-as-a-committed-record); dispositions already have a writer (reckon crew dispose, fold or exemption, today scoped to a sub-floor dimension); review composition already has a verb (reckon crew review-plan); the instruments exist as reckon/clones.py, reckon/interface_counts.py and the velocity view. This plan adds one reader, extends one writer and one verb, and adds one prompt and one skill.

§3 — Every stored finding is readable by the path it names

Deliverable. One derived reader over the committed run-review and plan-review records of a project (docs/state/<project>/reviews/run/** and reviews/plan/**), served as the crew MCP view crew(project, view="findings", path=<prefix>) and as reckon crew ledger --view findings [--path <prefix>]. Each row carries the finding's path and line, its severity, its text, the review run id, the reviewed run id, the reviewed head sha, and its disposition (open until §4 records one). Rows are grouped by repository-relative path with a recurrence count, the number of distinct reviews naming that path. A finding whose path is not inside the repository (a report, a manifest, a store path) is kept with scope: artefact and left out of recurrence, because 254 of the 847 follow-ons name such paths. The reader is a new module beside reckon/crew/review.py rather than an addition to it (3,264 lines); it reads records through the existing record readers in that module and adds no store. It adds one MCP view and one value of an existing CLI option, and retires nothing, because no reader of findings by path exists: today the only way to ask is a full scan of 3,200 records.

Done when tests/test_findings_read_by_path.py builds a temporary project holding three committed run-review records: two naming reckon/a.py (one blocking, one follow-on) and one naming a report path. It asserts that the view for prefix reckon/ returns both reckon/a.py rows with recurrence 2 and disposition open, that the report row carries scope: artefact and adds no recurrence, and that the CLI form prints the same rows as JSON. The negative control is executed and logged: with the reader filtered through repair.blocking_findings, the follow-on row is missing and the test fails. tests/test_ledger.py passes, holding the MCP surface at five tools. Write paths: reckon/crew/findings.py, reckon/mcp.py, reckon/crew_run_commands.py, tests/test_findings_read_by_path.py.

§4 — A finding carries a disposition, so a later review does not re-find it

Deliverable. reckon crew dispose takes --finding <n> beside --run: the index of a finding in that run's newest review record, as §3's rows print it. The closed set is unchanged: a fold names the node the finding went into, an exemption names why it is not being acted on. The entry is written to the same record the dimension disposition already rewrites, and §3's reader reports it. --dimension and --finding are mutually exclusive and one is required. The verb's refusals stay the store's own. This extends one writer; it adds one option and no verb.

Done when tests/test_dispose_a_finding.py stores a review with two follow-on findings, runs reckon crew dispose --run <id> --finding 1 --kind fold --node fix-a, and asserts §3's reader reports finding 1 as folded:fix-a and finding 0 as open; an exemption with no reason, and a call naming both --dimension and --finding, each exit non-zero and write nothing (the record's bytes are unchanged). The negative control is executed and logged: with the finding branch writing to the dimension slot, the reader reports finding 1 open and the test fails. The existing dispose tests pass. Write paths: reckon/crew_run_commands.py, reckon/crew/review.py, tests/test_dispose_a_finding.py. This section runs after §3, which it reads through.

§5 — The health rubric reads known findings first and proposes at most one treatment

Deliverable. reckon/crew/prompts/health_review.md, a rubric for a read-only review of a neighbourhood of code rather than of one diff. The brief the composer (§6) hands it names the neighbourhood's modules, the open §3 findings for those paths with their recurrence, the four interface figures from reckon/interface_counts.py, the clone pairs reckon/clones.py reports inside the neighbourhood, and the neighbourhood's modules that no entry point reaches. The rubric has six items, each with a verdict line: known_findings (group the open findings into defect classes and say which recur), duplicate_capability (a census by capability, not text, across the neighbourhood and the package: every implementation of one capability, each with path:line), unreached, interface_growth (surface added in the last 14 days without anything retired), width (modules over the worker-window bound) and test_debt (duplicated helpers and source-text assertions in the neighbourhood's tests). It emits FINDING lines in the plan-review grammar with a class, then exactly one TREATMENT line: a single goal, its write paths, a done-when with a negative control, and its expected line delta, chosen only from treatments that delete code, narrow an interface, wire or delete unreached code, or close a finding recurring in two or more reviews; or TREATMENT: none — <reason>. A finding already in the brief is cited by its §3 row, never re-reported as new.

Done when tests/test_health_review_parses.py parses a fixed reviewer output through the parser §6 installs and asserts six verdicts, the classed findings, one treatment with write paths and a done-when, and the TREATMENT: none form; an output with two TREATMENT lines, or a treatment naming no write path, is refused by name. The negative control is executed and logged: with the one-treatment check removed, the two-treatment output parses and the test fails. Write paths: reckon/crew/prompts/health_review.md, tests/test_health_review_parses.py. The parser is §6's; this section's test lands with §6.

§6 — One review verb composes a code review around a plan or a path

Deliverable. reckon crew review-plan becomes reckon crew review. Its existing options keep their meaning under --plan, and two subjects are added: --around <plan> and --path <path> (repeatable). For a code subject the verb resolves the neighbourhood: the production modules named by the plan's implementable sections' write paths, or the named paths, plus every production module one import away in either direction, read from the reachability instrument nothing-lands-unreached §2 delivers. It composes the §5 brief and dispatches one read-only review node through the ordinary dispatch path, writing to a report directory under the crew reports root, and stores the parsed result as a review record keyed by the neighbourhood so §3 can read it. The parser lives beside the plan-review report parser. review-plan stays as a hidden alias that prints a one-line deprecation to stderr until §7 moves its callers; §7 removes it, so the verb count is unchanged once the plan lands.

§7 — The /reckon-review skill

Deliverable. skills/reckon-review/SKILL.md, a short core of at most 1,500 words in the shape of the reckon-build core. It resolves the mode from the target and runs one loop per mode. Code: compose with reckon crew review --around|--path, read the stored result with crew(view="findings"), prototype the treatment's change against the code to confirm it is real, then either dispatch it through reckon-build's dispatch with write paths disjoint from any live claim, or record why not, and dispose every finding it read: fold into the treatment or a plan section, or exemption with a reason. Plan: run §8's rubric on one plan and the existing content and design reviews; apply what it proposes through reckon-edit. Portfolio: run §8's rubric on a sprint or the project, apply close, merge and re-sprint dispositions through reckon-edit and reckon-sprint, archive a retirement with plan-archived, and record the round in the sprint review resource. A merge or retirement of a plan another live session is building is proposed, never applied. The skill states the busy-work rule of §2 and the stop rule of §10, and every reckon-* skill that names review-plan names review instead, which removes §6's alias.

Done when tests/test_skill_contracts.py discovers reckon-review beside the other reckon skills, and asserts its body is at most 1,500 words; the cited-command test the-crew-contract-fits-one-read §5 delivers passes with the new skill in its corpus; grep -rn "review-plan" skills/ reckon/ returns no hit outside the alias removal's own changelog-free code; and reckon crew review-plan --help exits non-zero. §8 — The portfolio rubric proposes a disposition for every live plan

Deliverable. reckon/crew/prompts/portfolio_review.md and the composer branch reckon crew review --sprint <id>, --portfolio (every non-shipped plan of the project), or --plan <slug> --rubric currency. The brief carries, for every non-shipped plan in scope, the figures the portfolio health review computed by hand: status, stored and derived impl, sprint and sprint membership, days since its last commit, open section declarations and followups, and the roadmap's ready or blocked verdict. The rubric asks the reviewer to spot-check each plan's remaining implementable section against the tree (is it already in the code?) and to cluster plans by subject, and emits one DISPOSITION <slug>: keep | close | merge-into <slug> | retire | re-sprint <id> — <evidence> line per plan in scope. The figures come from the existing readers (reckon/roadmap.py, reckon/_plan_html.py); the composer computes none of them itself.

§9 — A plan build reviews its neighbourhood once, in its first wave

Deliverable. The payload of a plan's implementation dispatch carries a health_review block: the newest code-mode review whose neighbourhood covers the node's write paths, its age, the open findings count from §3 for those paths, and the one compose command when none is younger than seven days. §10 — The yield is on the velocity view, with a rule for turning the reflex off

Deliverable. crew(view="velocity") gains a health_reviews field, served when named in fields, for the window: code-mode reviews composed; findings read as known against reported as new; treatments dispatched, promoted and the product-line delta of the promoted ones; findings disposed by kind; and the change in clone pairs and unreached modules inside the reviewed neighbourhoods between each review and the next. It measures disposition from the records, not from commits touching a cited file, because that proxy matched baseline churn (71.0% against 75.2%) in the 2026-10-10 measurement. The stop rule is stated in the skill and the field's docstring: after ten code-mode reviews, if fewer than half of the treatments promoted or the promoted treatments added product lines in total, §9's step becomes opt-in, and the lead decides whether to keep it.

Done when tests/test_velocity_counts_health_reviews.py builds a temporary ledger and review store with three code-mode reviews, two treatments (one promoted with a net deletion of 40 lines, one discarded) and five dispositions, and asserts the field reports 3 reviews, 1 of 2 treatments promoted, −40 product lines and the dispositions by kind. The negative control is executed and logged: with treatments counted from dispatch instead of promotion, the field reports 2 of 2 and the test fails. Write paths: reckon/velocity.py, tests/test_velocity_counts_health_reviews.py.

§ Decisions

Should codebase health review be a node every coordinator dispatches, written into reckon-build, or a separate /reckon-review skill?

Plan and sprint health need an entry point that is not a plan build, and reckon-build is being shrunk by the-crew-contract-fits-one-read. One skill serves the lead and the coordinator; the coordinator's obligation is one step that calls it (§9). The lead may reopen this.

How many treatment nodes may one code-mode review dispatch?

An unbounded treatment list is how a health review becomes busy work and contends with the plan it runs beside. Every other finding is disposed, so it is not lost.
