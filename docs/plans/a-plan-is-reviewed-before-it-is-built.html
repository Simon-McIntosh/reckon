§1 — Why every plan needs a second reader

The 2026-09-24 re-plan measured what nobody had re-read. imas-codex's sn-catalog-audit-instrument had 13 reviewed and merged nodes and read as nearly done. Measured against real call sites it stood at 0.56: 11 of 25 features were shallow, and one computed its findings on every review for no template to read. imas-ambix closed a plan as shipped whose criterion had never been met. Reckon's own consumers turned out to hardcode 1,537 lines of ~/.config/reckon paths. In every case the author was competent and the plan read well, but nothing checked the plan against the code or against a rubric before work was built on it. Code gets an independent review before promotion; plans get none.

§2 — A rubber-duck review of every plan create and edit

Every plan create, and every edit that changes prose, done-whens, relationships or sections, queues one review of the settled version. Edits are debounced, so a burst of edits gets one review, and a pure metadata change such as an impl bump is skipped. Hand edits are caught at commit as well as through the MCP write path. The review is read-only, runs on the local lane, and checks a fixed rubric:

  • the plan is wired: its depends-on, informs and gates are present and correct;
  • each done-when is measurable, with a declared negative control;
  • each node has a single goal;
  • evidence and gate logs sit on durable paths, never in a session scratchpad;
  • claims are cited, and every file, section or commit an anchor names resolves;
  • naming carries no plan labels or ticket numbers into code.

It is advisory, a rubber duck, not a gate. The authoring agent acts on each finding or declines it with a one-line reason, and both are recorded. The loop is visible in the reckon web surface next to the plan, and reaches the author as one follower line. Nothing blocks.

Done when a plan create and a prose edit each produce one review record within the debounce window. A burst of five edits produces one review, and an impl-only edit produces none. The web surface shows the review's state (pending, ready, acted on, declined) next to the plan version it reviewed. The author's action or declining reason is stored with each finding.

§3 — A prior-art and depth review before a plan is built

Before a plan's first implementation node is released, a second review searches the codebases for existing machinery the plan could reuse. That extends the build skill's reuse-map rule, which a coordinator currently remembers to apply, into a review that runs without being remembered. The review then judges the design for depth. The preference, stated as the rubric, is deep modules behind small interfaces over a spread of shallow wrappers. A new module must hide substantial behaviour behind an interface smaller than what it hides. A plan that adds a thin layer over existing machinery must say why that machinery cannot be extended. A duplicate of shared infrastructure, such as placement, path resolution, scheduler queries or state readers, is a finding naming the owner to extend. Today's evidence for why this matters: imas-ambix carried three duplicated placement paths, and the thin-interface audit found consumers parsing reckon's CLI prose in 151 places.

Done when a plan whose design duplicates an existing mechanism receives a finding naming that mechanism and its file. A plan that extends a deep module passes clean. The finding reaches the author through the same loop as §2.

§ Decisions

When an author declines a finding, is that final, or does a finding declined across several plans surface to the lead?

A finding type declined in three or more plans surfaces to the lead. A repeated decline means either the rubric or a practice is wrong, and both are the lead's to rule on.

Where do plan reviews live?

Plan reviews go in the crew review store, keyed by plan and version, with a one-line pointer on the plan. That makes them queryable across plans and projects and reuses the code-review machinery. The 2026-09-25 review-utility census found its measures blocked by unjoinable records, so plan reviews must be joinable from the start.

§ Followups

Settle the two decisions, then build the review loop

The storage decision gates §2's record shape; settle it with the lead first. §2 is the loop (trigger, debounce, rubric, record, surface). §3 reuses the loop with its own rubric. The vision review of figures is deliberately out of scope for now, at the lead's word.

The first implementation dispatch against a plan version is refused until a plan review of that version exists and the author has acted on or declined, with a reason, each of its findings. The findings themselves never block. The aim is to catch reasoning errors before work is submitted, without making the rubber duck a veto.
