Every coordinator prompt runs reckon/hooks/coordinator_obligations.py, and every run re-derives the whole fleet's state in a fresh process: every plan, every live pointer, every worker stream and the whole run ledger. On 2026-10-01 that took 31.4 s cold for the S21 session, against a 30 s hook limit, after a fix that had already removed 30 s from it. A hook on every turn has to answer in milliseconds, which no amount of tuning the derivation reaches while the hook still performs it. This plan moves the derivation into the process that already runs continuously and already watches every pointer, publishes the result, and makes the hook a reader of what was published.

§2 — The producer publishes each session's obligations

The per-project watch producer (runs.watch in reckon/crew/runs.py, started by reckon crew watch --ensure) runs continuously and already classifies every live pointer each sweep to emit transitions. Whenever one of the three triggers listed below fires, it recomputes the full obligations payload of every session whose follower registration in the project's watch directory is live (the same registration the hook resolves its session through, read through runs.list_followers and its live field), and writes <config-home>/crew/obligations/<project>/<session>.json by writing a temporary file and renaming it over the old one, so a reader never sees a partial file. A session with no follower registration gets no snapshot; the hook already treats such a session as not coordinating and stays quiet for it.

The snapshot carries the obligations payload exactly as obligations() returns it, plus:

  • computed_at, and the byte offset in the project's watch event stream (there is one per project) that the snapshot reflects;
  • the producer's pid, its process start time, and the code stamp of the source it runs, the same stamp the watcher already reports as code_stamp;
  • for every age, the UTC timestamp it is measured from rather than a number of seconds, so a reader computes the age as now minus that timestamp and a snapshot never shows a frozen age.

The three triggers, each per project, are:

  • a pointer transition, which the producer already detects;
  • a change in the stat identity (size and modification time) of any file under docs/state/<project>/ or docs/plans/, judged per file, so an in-place edit that leaves the directory's own stat unchanged still fires it;
  • a floor tick every 60 s, so obligations that become due by the passage of time, such as a stale promotable run, appear without any other event.

Done when tests show:

  • a pointer transition is in the session's snapshot by the end of the first producer sweep after it, with the test driving sweeps explicitly rather than waiting on a clock;
  • on the shared synthesised fleet described in §5, with no fixture file modified during the comparison, the snapshot the producer writes equals obligations() called over the same files (the parity case);
  • a producer killed after writing the temporary file but before the rename leaves the previous snapshot intact and readable.

§3 — The hook reads the snapshot and never derives

coordinator_obligations.py resolves its session as it does today, then reads the session's snapshot: one stat and one small JSON read. The snapshot is fresh when a process with the recorded pid is alive and has the recorded start time (so a reused pid does not pass), its code stamp equals the stamp computed for the main checkout's source (the code a restarted producer would run), and computed_at is within 120 s. A fresh snapshot goes through the hook's existing formatting and injection functions unchanged, including the digest that suppresses an unchanged list. For a snapshot that is not fresh, the hook emits one line in place of the obligations, naming the reason (no producer, producer running older code, or the age of the snapshot) and the remedy, reckon crew watch --ensure --project <project>; the hook never writes the snapshot file. Both hooks exit 0 in every case. The prompt path imports none of the derivation modules (reckon._plan_html, reckon._backends, reckon.ledger), directly or through any module it imports, so a slow plan or a large stream can no longer slow a turn.

The stop hook (--hook stop) reads the same snapshot. On a fresh snapshot it refuses the stop when the snapshot lists outstanding obligations, as today. When the snapshot is not fresh, for any of the three reasons, it imports the derivation lazily and derives inline under a time budget, then refuses the stop only if that result lists outstanding obligations. The budget is a production constant of 5 s, which §4 makes feasible, and tests override it to exercise the over-budget branch. If the budget runs out it allows the stop with a line naming the not-fresh reason, so no producer state can trap a coordinator. The decision stale-snapshot-at-stop records this. The stop path lands after §4 item 1; the prompt path does not wait on it.

Done when tests show:

  • the prompt path's transitive import surface excludes the three derivation modules, and a deliberate mutation that adds an import of one of them to the prompt path fails that test (the negative control);
  • each not-fresh reason produces its line, and the snapshot file is unchanged afterwards;
  • a pid reused by another process is not fresh;
  • the stop path has one case per branch: fresh snapshot, inline derivation inside the budget, and inline derivation over an overridden short budget.

Recorded as measurement in the evidence, not asserted in the suite: 20 consecutive invocations of the prompt hook, each in its own fresh process against the same real fleet, have a p95 under 250 ms (with 20 samples this is the second-slowest run).

§4 — The derivation itself becomes incremental

The producer, reckon crew obligations, the MCP obligations view and runs.drain all still derive. Each of the three items below (plans, pointers, the ledger) gets a cache keyed by the stat identity of the files it reads, so a recompute still stats every input but parses only the files whose stat identity moved.

  1. Plans. runs._project_executable_remainder answers from the persisted metadata index (reckon/metadata_index.py) instead of calling read_state on every plan, and the meta fields parse_meta extracts come from the same rows. Each row is revalidated by one stat of its plan file on every call, and only a plan whose stat identity moved is parsed again. The index rows gain each plan's open-followup and implementable-section counts. Target, recorded as evidence: under 0.5 s in a fresh process for 160 plans, covering both terms this item replaces, 19.7 s of plan reads and 3.0 s of meta parsing.
  2. Pointers. classify_pointer results are memoised in a file beside each pointer, keyed by the stat identity of every file the classification reads. The pointer, manifest, stream and review record are the files known today, and the key must cover any other the classification reads. Stream observation resumes from a byte offset persisted in the same file instead of re-parsing the whole stream, so a fresh process benefits as well as the producer.
  3. Ledger. _held_worktrees no longer loads crew.json whole. It reads the per-run ledger file from the-ledger-is-one-file-per-run for each run that has one, falls back to crew.json only for runs that do not, and builds no index of its own.

Done when a parity case on the shared synthesised fleet (§5) shows the cached derivation returns the same obligations as the uncached one, including after the content of one plan and of one pointer's stream changes between calls. Recorded as measurement in the evidence: on the real fleet, obligations() for the largest live session takes under 2 s on the first call in a fresh process and under 0.3 s on a second call in the same process.

§5 — Guards that keep it fast

Timing alone is a poor guard on a shared node, so each section ships call-count guards that fail deterministically. They all run on one shared synthesised fleet, a test fixture of 40 pointers and 200 plans under a temporary configuration home. A prompt-hook invocation reaches none of read_state, parse_events or ledger.load, directly or through any callee; each is patched to raise. Between two producer sweeps with the content of one plan changed, read_state is called at most once, for that plan, and for no other plan. A pointer is not re-classified unless a file its classification reads changed. Every wall-clock budget in this plan is recorded as a measurement in the evidence and never asserted in the suite.

§6 — Order of work

§4 item 1 comes first. It is the largest single term, it is independent of the snapshot, and it speeds every reader, including the MCP view and the CLI. §2 and the prompt path of §3 land in the same merge, because a hook that reads a snapshot nothing writes would leave every coordinator without its obligations. The stop path of §3 lands after §4 item 1, because its bounded derivation needs that speed. §4 items 2 and 3 follow. Each section carries its own §5 guards.

§ Decisions

Which process derives and publishes obligations?

The per-project watch producer runs continuously and already classifies every pointer. A session's follower runs only while its harness monitor is armed.

The producer is always on, holds warm caches across sweeps, and already does the classification. A follower dies with its monitor every 25 minutes, so its snapshot would go stale exactly between re-arms.

When the stop hook finds no fresh snapshot, what does it do?

The stop hook enforces obligations by blocking a stop. A snapshot can go stale when the producer is down or runs older code.

Enforcement keeps working when the producer is down. Once §4 brings a cold derivation under 2 s, the stop hook derives inline under a 5 s production budget, which tests can override, and refuses the stop only when that result lists outstanding obligations. If the budget runs out it allows the stop with a line naming the not-fresh reason, so no producer state can ever trap a coordinator.
