§1 — The claim the cutover has to earn

Agents run on the login node today and share one user slice capped at four cores. The cutover moves them into a held allocation so they stop contending with editors, git and every interactive session on the machine. That is the claim, and it is measurable — but only by an instrument aimed at the fleet's own work. The quantity is the throttled fraction of the CPU time the agents themselves consume, read from whichever cgroup is running them at the time. Before the move that is the login node's user slice; after it, the allocation's own cgroup. Reading the login slice on both sides would measure the relief felt by what stayed behind — editors, git, interactive sessions — and would report a success no matter how badly the fleet fared inside the allocation. The two instruments can return opposite verdicts on the same cutover, so the report names the counter file it read on each side.

Throughout, throttled fraction means that measured quantity and nothing else. Where this plan discusses cores per worker it says so explicitly; that is a different number, and a regression in it would not show up in the throttled fraction at all.

The baseline is already recorded, and it is not in this repository: it is 0.3366, carried by imas-ambix's slurm-hosted-agent-fleet plan under followup f-shaf-003. A reader searching this tree for it will find nothing, which is why the figure and its home are written here. The report prints the baseline beside the new measurement rather than referring to it, so the direction of the change can be checked against something on the page. It is not a figure to be re-derived at the end, and it is not the number to compare against a quiet afternoon: the measurement is taken over a working day, because the contention it reports is caused by the fleet's own bursts and an idle sample cannot see them.

§2 — What is untested and must be measured, not assumed

Two properties of the allocation have never run under load. The allocation carries twenty-eight cores and the workstation carries roughly thirty concurrent sessions, so the per-worker share after the move is a projection, not an observation — and a worse share than the login node would make the cutover a regression that every cheap signal would miss, exactly as a throughput tail does.

The second is a failure mode rather than a number. A step created with srun --overlap --jobid dies with its allocation. An ssh session does not, because pam_slurm_adopt places it in the user slice rather than the job's cgroup — so the login node's behaviour teaches the wrong lesson here. If the allocation is lost or its walltime expires, every placed worker on the machine dies at once, mid-turn, in every project. That is a fleet-wide blast radius and it needs a stated recovery before the rollout, not after the first occurrence.

§3 — Done when

Workers across at least two projects are running as steps inside the one reservation. The proof is that a live worker's job id is the job id of the published reservation, not merely that the worker is on the allocation's node: a per-worker allocation landing on the same node satisfies the weaker check while being exactly the minting this sprint exists to remove, so resolving the host alone would accept the wrong end state as evidence. Configuration saying so is not evidence either. The throttled share is measured over a working day and reported beside the stated baseline, with the direction of the change named plainly whichever way it went. The allocation-death path has been exercised deliberately once, at a moment chosen so that the workers lost are ones nobody needs — the death is fleet-wide by nature, as §2 describes, so this is a timed sacrifice and not a single-worker injection. The exercise must show that the next dispatch re-holds the shared allocation and that later workers join it rather than each taking one; a written note that they should is not the deliverable. A rollback is stated: which declaration to remove, and what the fleet does while no reservation is held. Removing the host-layer declaration is sufficient to stop the re-holding, because the ensure is reached through placement resolution and an undeclared backend never resolves a placement — so the rollback does not have to defeat the automatic re-hold, only to remove what triggers it.

The cutover also moves every background crew process, not only the agent sessions. That means per-project producers, followers, and dispatch and complete loops, placed in the order §4 sets. The proof is a census of the login node listing no crew producer, follower or dispatch loop, beside the job ids of those processes on the allocation. A configuration saying they are placed is not the proof.

§4 — What moves, and in what order

The load is mostly not the sessions. Measured 2026-09-23 by imas-ambix-b6: five per-project reckon crew watch producers used about 60% of the login node's four-core quota (48, 48, 42, 26 and 15% of a core), while all agent sessions together used 12%. The storage event that night added followers, dispatch loops and unbounded searches that had outlived their sessions (imas-ambix's research note login-node-storage-contention). Moving only the sessions would move the small half.

What the move buys, stated so it is not overclaimed. A process blocked on GPFS adds to the load average of the node it runs on, and it queues behind that node's single GPFS daemon. Moving processes to the allocation takes them off the login node's load average and its daemon queue, so editors, git and interactive sessions stop waiting behind them. It does not reduce metadata pressure on the filesystem itself: the same stat and walk load reaches the same metadata service from 98dci4-clu-2002. Reducing that load is a-crew-process-ends-with-its-owner's job. The report for this plan claims login-node relief and nothing more.

Where. rigel carries infinite walltime. The fleet allocation ambix-fleet (job 1276262) has been held there on 98dci4-clu-2002 with an UNLIMITED limit (23 h 42 min at 2026-09-24 04:59Z). Every *_debug partition caps at one hour and can never host a persistent fleet.

Order: producers first, sessions last. Producers are the measured load. They carry no TTY or messaging risk, and they can be moved one at a time with the rest of the fleet untouched. The existing producers are children of no current session, so each is stopped and re-armed from inside the allocation deliberately; nothing moves them otherwise. Followers and dispatch loops move with their parent session, because a placed parent places its children. Sessions move last, in one operation.

Why this topology, from probes of the allocation on 2026-09-24 (imas-ambix research note login-node-storage-contention §8):

  • A step dies with its client. Killing the login-side client of an srun --overlap --jobid step ended the step within seconds. A session started as srun --pty claude from a login terminal therefore lives only as long as that terminal and that login node. So no session's step may have its client on a login node.
  • Only the batch step outlives every login node. The zellij server is started by the allocation's batch script, and it owns the sessions' terminals. Login nodes attach viewers with srun --overlap --pty --jobid=<fleet> zellij attach fleet, from any node, detaching and reattaching freely.
  • A step reaps everything under it, detached or not. A setsid nohup process was gone once its step ended. Each pane therefore launches its session as srun --overlap --pty --jobid=<fleet> claude …, whose client lives in the pane on the compute node. When a session ends, every follower, shell and search it started is removed with it, which is cleanup by construction.
  • The node has no /run/user/<uid>, and a step cannot create one, while XDG_RUNTIME_DIR is inherited pointing at it. The launcher creates a private runtime directory on the node's local /tmp (mode 700), points XDG_RUNTIME_DIR and zellij's socket directory at it, and every placed session shares it. Cross-session sockets are node-local, so the sessions move in one operation: a half-migrated fleet splits into two groups that cannot message each other, and a send to an unreachable peer looks like any other send.
  • ssh to the node lands in user.slice, outside the job, and so escapes both the allocation's limits and its cleanup. It is never the route in.
  • The launcher unsets the compute node's uv function, which injects its own --no-sync so an explicit one makes uv exit 2 (measured 2026-09-07), by running unset -f uv and calling command uv.
  • The allocation is re-created, not reused. The present allocation's batch script only sleeps, and a batch step cannot be given new processes. The re-hold path that the-fleet-shares-one-allocation uses must create the batch script that starts the zellij server, so an allocation lost and re-held comes back with its server. A lost allocation stops every session. Transcripts are on GPFS, so each session resumes with claude --resume, and the tab layout is a versioned layout file.

Done when, in this order:

  1. In a test allocation, the batch script starts a zellij server. A viewer attaches from a login node through a pty step and detaches, its login-side client is killed, and on reattach the pane's process is still running.
  2. A session launched in a pane as its own step keeps its socket under the launcher's runtime directory, and two such sessions exchange a cross-session message.
  3. Ending a session's step removes a detached child the session had started.
  4. The producer of every active project runs as a step under its lease in the reservation, proven by its job id, and none remains on the login node.
  5. The sessions move in one operation, and the login node's census shows no fleet claude session, follower, producer or dispatch loop.
  6. A placed session runs uv run --no-sync successfully through the launcher.

§ Decisions

What happens to placed workers when the allocation has ended — confirmed gone, not merely unreadable from the asking host?

Follows from the ensure policy rather than being a separate call: an allocation that has ended is a state with no readable reservation, and the rule for that state is to hold the shared one and place into it. The next dispatch therefore re-holds and publishes, and later workers join it. The hazard is unchanged and is carried by the same guard: an allocation that is merely unreachable must not read as gone, or the re-hold takes a second allocation beside a live one. The monitor still reports the loss, because a fleet-wide worker death is worth a line whether or not the recovery is automatic.

§ Followups

Place the fleet, measure the throttled fraction, and show the re-hold

Place workers from at least two projects and prove it by showing a live worker's job id is the job id of the published reservation — resolving its host is not enough, since a per-worker allocation lands on the same node. Report the throttled fraction of the CPU time the agents themselves consume, read from whichever cgroup is running them, naming the counter file on each side, and print the baseline 0.3366 (imas-ambix slurm-hosted-agent-fleet, f-shaf-003) beside it. Exercise the allocation-death path once at a moment chosen so the workers lost are ones nobody needs, and show that the next dispatch re-holds and later workers join it. Move every background crew process in the order §4 sets: first prove that a zellij server started by the allocation's batch script survives the loss of its login-side viewer, that a session run as its own step from a pane gets a working runtime directory and cross-session messaging, and that ending that step reaps a detached child; then move producers under their lease, proven by job id, with none left on the login node; then move all sessions in one operation, with the login node's census showing none of the fleet left; and a placed session runs uv run --no-sync through the launcher. Claim login-node relief only, not reduced GPFS pressure.
