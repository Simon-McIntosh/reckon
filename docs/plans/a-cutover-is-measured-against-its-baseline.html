§1 — The claim the cutover has to earn

Agents run on the login node today and share one user slice capped at four cores. The cutover moves them into a held allocation so they stop contending with editors, git and every interactive session on the machine. That is the claim, and it is measurable: the throttled share of the user slice, read from the cgroup's own counters, against the baseline recorded before the move.

The baseline is already recorded. It is not a figure to be re-derived at the end, and it is not the number to compare against a quiet afternoon: the measurement is taken over a working day, because the contention it reports is caused by the fleet's own bursts and an idle sample cannot see them.

§2 — What is untested and must be measured, not assumed

Two properties of the allocation have never run under load. The allocation carries twenty-eight cores and the workstation carries roughly thirty concurrent sessions, so the per-worker share after the move is a projection, not an observation — and a worse share than the login node would make the cutover a regression that every cheap signal would miss, exactly as a throughput tail does.

The second is a failure mode rather than a number. A step created with srun --overlap --jobid dies with its allocation. An ssh session does not, because pam_slurm_adopt places it in the user slice rather than the job's cgroup — so the login node's behaviour teaches the wrong lesson here. If the allocation is lost or its walltime expires, every placed worker on the machine dies at once, mid-turn, in every project. That is a fleet-wide blast radius and it needs a stated recovery before the rollout, not after the first occurrence.

§3 — Done when

Workers across at least two projects are running as steps inside the one reservation, proved by resolving a live worker's host rather than by the configuration saying so. The throttled share is measured over a working day and reported beside the stated baseline, with the direction of the change named plainly whichever way it went. The allocation-death path has been exercised deliberately once, on a worker nobody needs, and what a coordinator should do about it is written down. A rollback is stated: which declaration to remove, and what the fleet does while no reservation is held.

§ Decisions

What happens to placed workers when the allocation ends?

Follows from the ensure policy rather than being a separate call: an allocation that has ended is a state with no readable reservation, and the rule for that state is to hold the shared one and place into it. The next dispatch therefore re-holds and publishes, and later workers join it. The hazard is unchanged and is carried by the same guard: an allocation that is merely unreachable must not read as gone, or the re-hold takes a second allocation beside a live one. The monitor still reports the loss, because a fleet-wide worker death is worth a line whether or not the recovery is automatic.
