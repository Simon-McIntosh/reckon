§1 — The gap: review verdicts evaporate, so every consumer re-derives them

A sprint-review worker reads the roadmap, validates blockers and followups against the code and git state, and produces two artifacts: a set of findings (each with evidence and a recommended action) and a priority order over the actionable plans. Today both live only in the reviewing session's chat. Nothing persists them, so a ship coordinator dispatching an hour later re-derives the same staleness verdicts or — worse — never sees them. A live example measured 2026-08-26 during a fleet review of a mounted project: the retained index pointer named one sprint while a different sprint resource carried status="active" (the audit's active-sprint-mismatch), the review validated the mismatch with git evidence and a recommended repair, and the only record of that validation was a chat transcript. This repository shows the same class of dirt right now: the derived active-sprint pointer names a planned sprint while two other sprint resources are simultaneously active.

The persisted half must stay small because the live half already exists: item lifecycle status and implementation fractions are never stored in sprint resources — they are composed at read time from plan HTML. This plan keeps that contract. What a review persists is exactly the judgment a machine cannot recompute — validated findings with their evidence, and a ranked order with the reason each rank was assigned. Everything else (current status, impl, effective blocking, sprint metrics) is joined live at read time, which is what makes the surface update automatically as work lands, with no writer in the loop.

§2 — The review resource: fixed schema, versioned, one write path

A new singleton distributed resource of type review, stored at docs/state/<project>/review.html beside the timeline, with the same semantic-HTML shape as other distributed resources (meta identity, a semantic list of findings, the JSON state script) and its own optimistic-concurrency version. It is created, read, and written exclusively through read_plan / edit_plan with doc_type="review" — lenient read, strict write, exactly like plans.

Scalars: reviewed_at (date), reviewed_by (session or person), basis (what the review read — e.g. the roadmap at a named commit). Two collections:

findings[] — each row is the persisted form of one validated review finding:

  • id — deterministic, unique within the resource
  • code — non-empty kebab-case finding name (open vocabulary, aligned with audit codes where one exists, e.g. active-sprint-mismatch)
  • category ∈ sprint · dag · lifecycle · provenance · references · calibration
  • severity ∈ error · warn · info
  • subject — {kind ∈ plan · sprint · milestone · blocker · followup · decision · project, id}; plan subjects accept the standard project-qualified ref grammar
  • evidence — one or more free-text lines carrying dates, commits, paths
  • recommended_action — {verb ∈ close · resequence · rescope · recalibrate · resolve · repair-pointer · reopen, owner_skill, detail}
  • validated ∈ confirmed · stale · conflicting, with checked_at (date)
  • resolution: resolved_at, resolved_by, outcome — resolved status is derived from a non-empty resolved_at, the same rule followups use

priority[] — the persisted ranking judgment, per plan (sprint order is derived, never stored):

  • rank — 1-based, contiguous, no duplicate refs
  • ref — plan ref (project-qualifiable)
  • reasons — non-empty subset of the fixed vocabulary critical-path · unlock · deadline · roi · decision-first
  • detail — one line saying what earned the rank (e.g. the deadline date, or which plans this unlocks)

Write verbs: set for scalars and for priority as a whole list (a ranking is one judgment — partial edits would let two reviews interleave into an order nobody produced), append for findings, resolve for findings. Strict write validation rejects any enum violation, an empty evidence list, a non-contiguous or duplicate-ref priority, and a malformed subject ref, each with the offending field named.

Done when: a round-trip test writes a review through edit_plan(create=True, doc_type="review") — including a finding carrying the real measured active-sprint-mismatch shape — reads it back losslessly with an incremented version; each invalid-write case above is refused naming its field; and resolving a finding derives its status without a stored flag.

§3 — Composed reads: the dynamic half, derived at read time

Sprint cards in the composed views (read_plan discovery/summary and the index compatibility view) gain a per-sprint metrics block joined live from plan HTML: item count, counts by effective_status, mean stored implementation fraction over items, and current_work — the items whose plans are actively moving (non-terminal status with implementation between zero and one). No field of this block is ever persisted; it must change when a member plan's HTML changes, and a test proves exactly that by editing a member plan and re-reading the sprint card.

The review resource composes the same way. Each finding row gains subject_found, subject_status, and a derived current flag — false when the subject changed after checked_at (its plan-modified or resource version moved) or reached a state that satisfies the recommended action, so an acted-on finding decays visibly instead of lingering as advice. Each priority row gains live status, effective_status, impl, and sprint, plus a landed flag for terminal plans. From the joined priority the reader also gets sprint_order: sprints in first appearance order of their ranked members, remaining open sprints after them in id order. That derived order IS the fixed-schema sprint priority — stored per plan where the judgment lives, projected per sprint where execution consumes it.

Done when: tests prove the join is live (edit a member plan → sprint metrics and priority rows change on the next read with no review write), prove current flips when a subject moves after checked_at, and prove sprint_order against a hand-computed case.

§4 — Roadmap and audit wiring: the DAG carries the review

roadmap(project) gains a review block: reviewed_at / reviewed_by, the composed open findings, the joined priority rows, the derived sprint_order, and two computed health signals — priority-order-inversion (a persisted rank places a plan ahead of its unshipped prerequisite, per the dependency graph) and review-stale (subjects moved since reviewed_at, so ranks may no longer bind). Both are wiring findings in the existing findings stream, severity warn: a review is advice about the DAG and must never gate execution the way a dependency does. A ship coordinator reading the roadmap before dispatch now sees the persisted priority and any unresolved findings against the sprints and plans it is about to execute, in one read. The audit tool validates review conformance over the corpus: dangling subject refs (dangling-review-subject), enum violations, and priority contiguity, all report-only.

Done when: roadmap payload tests cover the block's presence with and without a stored review, the inversion signal against a constructed prerequisite-behind-successor ranking, and staleness; audit tests cover a dangling subject and a broken enum; a project with no review resource reports an absent block, not an error.

§5 — SPA sprint view: execution order, live metrics, open findings

The sprint view renders what §3 and §4 compose, from the served composed endpoints — the SPA parses no plan HTML itself and persists nothing:

  • sprints listed in derived sprint_order (fallback: id order), the derived active sprint visibly distinct, and any active/pointer disagreement surfaced as the finding badge rather than hidden by picking one
  • a per-sprint metric strip — implementation mean, item counts by effective status, and the current-work items by name
  • open review-finding badges on the sprints and plans they subject, with severity and code visible, linking to the finding's evidence
  • a priority panel: ranked plans with reason chips from the fixed vocabulary, each row carrying its live status/impl so the panel visibly decays as work lands (landed rows drop to a muted tail rather than vanishing)

Done when: a served project carrying a review resource renders order, metric strip, badges, and priority panel from live endpoints; a project with no review renders the same view minus the review affordances; and re-reading after a plan status change shows moved metrics with no review write. Rendered evidence captured against the local server.

§ Decisions

Where does a persisted review live?

Findings are resolvable rows in one live stream, like followups — a singleton with its own version keeps resolve semantics and avoids a growing file-per-review corpus nobody reads twice; project.json is identity/presentation-only by contract. Superseded judgments are resolved rows, not new files.

What grain does the persisted priority order use?

Coordinated with the reviewing worker producing the real artifact: its ordering is a partial order over plans driven by critical-path membership, unlocks, deadlines, stored roi, and decision gates — sprint ordering falls out of plan order. Storing the derived form would persist what read-time composition already computes.

How does a finding or rank expire when the world moves?

Same mechanism as effective_status: derive, never persist, what live state already implies. A writer-maintained flag is stale the moment after it is written and needs an actor nothing guarantees; a derived flag is correct at every read.
