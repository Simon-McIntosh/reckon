§1 — Why this exists, and why it is not one subject

A figure of roughly two dozen failing surface tests was carried between three coordinator sessions as a single item of work, and it was never measured. Measured on 2026-09-09 across the 41 surface and SPA test files: 26 failures, 241 passes, no skips and no errors in 726 seconds. The count was right. Treating it as one subject was not.

The census that produced this plan classified every failure by cause with the evidence for each, and the three causes have three different owners. That is the finding, and it is why authoring a plan before measuring would have produced the wrong plan:

CauseCountOwner
A rendered gate whose navigation never completes on this host 15 Already owned by rendered-evidence-on-this-host, whose remaining debt needs the host's browser runtime repaired
A stale contract asserting behaviour the code no longer produces10 This plan, §2
A genuine defect in surface code1This plan, §3

The environmental explanations are excluded by measurement rather than by argument. A rendered gate on this host times out for two known reasons, and one of them is a leak: browser processes held open by earlier runs exhaust the inotify instance limit. Counted before the census and after it: zero leaked browser processes both times, and inotify at 31 then 34 of 128. So the browser gates clean up after themselves and the ceiling was never approached. The fifteen are the diagnosed navigation fault, which stops inside the browser's network service above stream-socket creation, and no amount of test repair reaches them.

The remaining eleven are worth separating precisely because the fifteen are not fixable here. A suite carrying 26 reds where 15 are permanently blocked teaches every reader to ignore the colour, and the eleven that are actionable disappear into that habit. One of them is a real defect in a surface a user reads.

§2 — Ten contracts that assert what the code used to do

Each of these fails on a deterministic assertion against current code whose behaviour has moved. They are not regressions and they are not flaky; the expectation predates a refactor or an intentional change, and the code produces the new value correctly. This is the fifth instance of this family recorded in this repository within a day, after eleven dispatch fixtures, one lane-change fixture, three recovery expectations, six promotion contracts and five remedy expectations.

They fall into three shapes, which matters because the repair differs:

ShapeCasesWhat moved
A compiled-source substring the test searches for4 Modules were refactored, so an extracted anchor or a derivation string no longer appears in the source the test greps
A hard-coded expected stylesheet rule set2 Two surfaces now set a zero minimum height, which the expected dictionaries do not list
A rendered-text or exported-surface expectation4 A public surface gained three exports; a topbar gained a project picker; a pager and a lane emission changed what they render

Two of the ten are marked as leaning stale rather than proven stale, and they must not be migrated on the lean alone. One reads a pager position of two of three where the test asserts three of three; one probes a lane count of one where the test asserts two. Each is consistent with the code having moved deliberately and with the code being wrong, and nothing in the census separates those. Establish which before touching either assertion: if the current behaviour is correct, migrate; if it is not, the case belongs in §3 and the assertion was right all along.

§3 — The graph does not mount on a page that loads

One failure is a defect in surface code, and it is separable from the fifteen by a property the census established rather than assumed: it is a file-scheme render, not a served one. Inlined documents load on this host in about four tenths of a second, which is why the host fault does not explain it. The page loads, and then the graph never populates — the readiness selectors for a node card and a handle token never appear.

So the document arrives and the component does not mount. That is a different failure from every other red in the suite, and it is the only one of the 26 where a reader looking at the surface would see something wrong.

Done when the file-scheme graph probe renders a populated graph repeatably, with the readiness selectors present and the probe's own repeat assertion passing; when the cause is stated as a mechanism rather than as a symptom, naming why the component did not mount on a document that loaded; and when the fix is verified on the file-scheme path without depending on a served navigation, since that path does not work on this host. Asserted by the probe passing twice in isolation and by the stated mechanism being checkable against the code.

§4 — What this plan does not do

It does not touch the fifteen rendered gates. They belong to rendered-evidence-on-this-host, whose own record diagnosed the boundary to the socket level and whose remaining debt is explicitly authority-required: only the owner of this host's browser runtime can repair or replace it, and the acceptance gate there requires both controls rather than one. Those tests will report themselves the moment the runtime works.

It also does not rewrite the surface tests into a different style, add coverage, or migrate the harness. The work is to make eleven assertions true again or to show that the code they describe is wrong, and to leave the suite's colour meaningful.

§ Decisions

How are the two leaning-stale cases resolved before their assertions are touched?

Chosen on evidence rather than on preference, and the evidence arrived from two independent reviews that did not know about each other. Leaning case 10, the derived-flow lane count, is now mechanically explained: the test renders DerivedFlow with no injected clock, so it reads the live wall clock against fixture stamps fixed at 2026-09-02 to 09-04, and the surface's own 60-hour retention filter drops every fixture bar, packing one lane where two are expected. Its explicitly-clocked sibling test passes, which is what establishes that the schedule logic is correct and the test is the defect. That is a stated finding, which is what this option requires, and it means case 10 is safe to migrate by injecting a clock rather than by moving the expected number. Case 8, the pager reading two of three, is the opposite and is why migrate-with-note would have been wrong: this plan's sibling artifact-feeds-and-reader carries a section titled The readout counts one behind its own position, so the current behaviour may be a real defect that the assertion is correctly catching. Migrating it would convert a defect into a passing test. Split-node is rejected because the investigation is one read-only step over two cases, not two nodes.
