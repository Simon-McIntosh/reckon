The audit agrees with the skill

On 2026-09-24 and 25, the imas-ambix coordinator landing the fleet-view sections hit three places where reckon's own validators and reckon's own skill text disagree. Each disagreement cost a hand workaround, and one left a plan un-editable by slug.

§1 — A landed section's header is not a spliced document

reckon-build SKILL.md §6b prescribes <section class="section-landed"><header>…</header> for every landed section. Meanwhile, reckon audit-doc warns header-duplicate ("document carries 2 <header> elements … content from another document spliced into this one") on any plan with two landed sections. It was seen on imas-ambix agent-sessions-live-on-the-fleet-node.html (b46d1521) and description-reader-migration.html.

The template is the canonical shape and is already used across mounted projects, so the rule changes and the template stays. A <header> that is the direct child of a section.section-landed no longer counts toward header-duplicate. A second document-level header still does.

Done when:

  • Tests assert that a plan with three landed sections, each written in the §6b template, produces no header-duplicate finding.
  • Tests assert that a plan with a second top-level <header> still produces it.
  • The declared mutation, removing the exemption, is applied, and the three-landed-sections case is observed to fail. The log is recorded.

Landed 2026-09-25 at 6e168152, base 663cc0d2. reckon/doccheck.py's _StructureScanner keeps a stack of open elements and counts a <header> only when its direct parent is not a <section class="section-landed">; every other header still counts, so a real second shell header is still reported. tests/test_doccheck_landed_header.py asserts three landed sections produce no header-duplicate finding, a second top-level header still does, and a header nested one element deeper inside a landed section still counts. tests/test_doccheck.py passes unchanged (25 passed); the doccheck-focused set is 69 passed; ruff check on the module reports 12 findings, equal to base. Full record: §1 landed.

§2 — A slug two resource types share is refused at audit

A research note at docs/research/fleet-view-rendering.html carried the plan-slug of a live plan, agent-sessions-live-on-the-fleet-node. From then on, every slug-only edit_plan on the plan failed with "resource slug … is ambiguous across types: plan, research". The worker's gate was reckon audit-doc, and it passed.

A project-aware audit should report, as an ERROR, a plan-slug that another resource of a different type in the same mounted project already carries. The error names both paths.

Done when:

  • A test builds a synthetic project in which a research document and a plan share a slug. It asserts that auditing either document with the project reports the collision as an error naming both files, and that the command exits non-zero.
  • A project whose slugs are all unique produces no such finding.
  • The declared mutation, removing the cross-type check, is applied, and the collision test is observed to fail. The log is recorded.
