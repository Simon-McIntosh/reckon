reckon · crew hooks

Every reckon hook runs under reckon's interpreter

A reckon hook is only as safe as the interpreter that starts it. Today three paths produce reckon hook commands and they disagree, so on a compute node a worker's stop hook crashes and its git guard lets a banned command through. This plan makes the interpreter part of every hook command reckon writes or seeds, makes each hook script correct itself when started by the wrong interpreter, and heals the installs that already exist.

§1 — Context

The fleet move's §15 bound the worker stop hook and the git guard to the checkout's .venv/bin/python in the commands that reckon hooks install composes. It did not reach the commands every Claude-harness worker actually runs, which come from three places:

SourceWhat it writes today
reckon hooks installThe obligations hook and the worker stop hook bound to the checkout's interpreter.
reckon sync (project setup)The native-agent guard and the worker-message guard as bare script paths; the git guard bound to the interpreter.
A run's harness homeA copy of the hooks key of the operator's ~/.claude/settings.json, whatever it holds (harness_home_files in flight-defaults.yaml, seeded by _seed_harness_entry in reckon/_backends.py).

Measured on 8 October: the operator's settings held worker_stop.py, worker_git_guard.py and native_agent_guard.py as bare script paths. Each script starts #!/usr/bin/env python3, and a plain shell on the fleet node resolves that to /usr/bin/python3, Python 3.9.16, where from datetime import UTC fails. The stop hook then crashes. A guard that cannot import its rules decides nothing, so the git guard fails open. Workers dispatched with the reckon venv first on PATH were masked; any other launch is exposed. Codex workers are unaffected, because they do not read these hooks.

A durable fix cannot depend on an operator remembering to rerun an installer, so the interpreter is put in three places: the one composer every writer uses, the seeding of each run's harness home, and the hook scripts themselves.

§2 — One composer writes every reckon hook command

Every reckon hook command, whichever script it starts, is composed by one function in reckon/hooks/install.py as the checkout's .venv/bin/python followed by the script and its arguments. reckon hooks install and reckon sync both use it, so the native-agent guard and the worker-message guard stop being written as bare paths. One recogniser identifies a reckon hook command, bare or bound, so both writers upgrade an existing bare command in place rather than adding a second entry.

Done when:

  • A test finds every script under reckon/hooks/ that either writer registers by a search over the code, not a hand list, and finds each one composed with the checkout's interpreter, so a hook added later without it fails the test.
  • reckon sync run against a temporary project and a temporary settings file writes only interpreter-bound reckon hook commands.
  • A settings file holding the bare reckon commands is upgraded in place by both reckon sync and reckon hooks install, with no duplicate entry, and every hook that is not reckon's is left byte-for-byte unchanged.
  • No test reads or writes the real ~/.claude/settings.json.

§3 — A run's harness home carries interpreter-bound hooks

When reckon seeds a run's harness home from the operator's settings.json, it passes the copied hooks through §2's recogniser and composer, so every reckon hook command in the run home is interpreter-bound whatever the operator's file holds. Hooks that are not reckon's are copied unchanged, and the operator's own file is never written.

Done when:

  • A test seeds a run home from an operator settings file holding bare reckon hook commands beside a hook that is not reckon's, and finds the run home's reckon commands interpreter-bound, the other hook unchanged, and the operator file's bytes unchanged.
  • A test seeds from a file that already holds the bound commands and finds the run home identical to it.

§4 — A reckon hook started by the wrong interpreter corrects itself

A bare command can still reach a hook script from somewhere reckon does not write: an old settings file, a hand-edited one, another harness. Each reckon hook script therefore checks, before importing anything from reckon, that the running interpreter can serve it. When it cannot, it re-executes itself under its checkout's .venv/bin/python with the same arguments and standard input. The worker git guard fails closed: when it cannot decide, it denies the command and says why, because a guard that allows what it could not check reports a protection it does not give.

Done when:

  • A test starts each reckon hook script through a python3 on PATH that cannot import reckon, and finds it re-executed under the checkout's interpreter and deciding exactly as it does when started correctly.
  • A test makes the git guard unable to load its rules and finds a banned git command denied with a reason, not allowed.
  • A script whose checkout interpreter is missing reports that and exits non-zero rather than looping.

§5 — Existing installs are healed

Once §2 is on main, the operator's ~/.claude/settings.json on this workstation is upgraded through reckon hooks install --write, and every mounted project is re-synced so its setup writes the bound commands. This is an operational step run by the coordinator, after a dry run shows the change.

Done when: the operator's settings file holds no bare reckon hook command, read back after the write; a worker dispatched through a shell whose first python3 is the system 3.9 finishes with its stop hook decided and its git guard active, shown by the guard refusing a banned command in that worker.

§ Decisions

When the worker git guard cannot decide, does it allow or deny?

The lead asked for a durable fix to a guard that failed open; a guard that allows what it could not check reports safety it does not give.
