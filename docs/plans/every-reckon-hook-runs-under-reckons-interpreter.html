reckon · crew hooks

Every reckon hook runs under reckon's interpreter

A reckon hook is only as safe as the interpreter that starts it. Today three paths produce reckon hook commands and they disagree, so on a compute node a worker's stop hook crashes and its git guard lets a banned command through. This plan makes the interpreter part of every hook command reckon writes or seeds, makes each hook script correct itself when started by the wrong interpreter, and heals the installs that already exist.

§1 — Context

The fleet move's §15 bound the worker stop hook and the git guard to the checkout's .venv/bin/python in the commands that reckon hooks install composes. It did not reach the commands every Claude-harness worker actually runs, which come from three places:

SourceWhat it writes today
reckon hooks installThe obligations hook and the worker stop hook bound to the checkout's interpreter.
reckon sync (project setup)The native-agent guard and the worker-message guard as bare script paths; the git guard bound to the interpreter.
A run's harness homeA copy of the hooks key of the operator's ~/.claude/settings.json, whatever it holds (harness_home_files in flight-defaults.yaml, seeded by _seed_harness_entry in reckon/_backends.py).

Measured on 8 October: the operator's settings held worker_stop.py, worker_git_guard.py and native_agent_guard.py as bare script paths. Each script starts #!/usr/bin/env python3, and a plain shell on the fleet node resolves that to /usr/bin/python3, Python 3.9.16. The worker stop hook and the obligations hook import reckon modules that need datetime.UTC from Python 3.11, so under 3.9 the stop hook crashes and the worker ends its turn without its stop checks. The three guards import no module that needs 3.11 and decide correctly under 3.9: the content review measured the git guard there denying a banned git reset --hard. Their exposure is different. A guard whose script cannot reach its rules, such as a script copied away from its checkout or one gaining a newer import, decides nothing, and today that allows the command. Workers dispatched with the reckon venv first on PATH were masked; any other launch is exposed. Codex workers are unaffected, because they do not read these hooks.

A durable fix cannot depend on an operator remembering to rerun an installer, so the interpreter is put in three places: the one composer every writer uses, the seeding of each run's harness home, and the hook scripts themselves.

§2 — Sync writes its hooks through the installer's composer

reckon/hooks/install.py already owns the composer, the recogniser and the in-place upgrade. build_hook_snippet composes each command as interpreter_path(), the checkout's .venv/bin/python, followed by the script. _command_identity treats a bare and a bound command as one entry. _merge_settings and _write_settings upgrade a bare command in place. reckon hooks install already uses them; reckon sync does not. Its writer, _configure_crew_guards in reckon/cli.py, composes its own commands, carries two recognisers that duplicate the installer's (_is_native_agent_guard_group and _is_worker_message_guard_group), and writes the settings file atomically on its own. The installer's in-place upgrade covers only the worker stop hook and the git guard today (WORKER_SCRIPT_NAMES), so a bare obligations hook is skipped rather than upgraded; its upgrade set is extended to every reckon-importing hook script. Sync's writer is then retired onto the installer: reckon sync composes, recognises and writes through install.py, and the duplicate recognisers and the private write are removed, with the tests that assert their bare output moving with them.

Which interpreter a command names follows from what the script needs. Scripts that import a reckon module, the obligations hook, the worker stop hook and the worker git guard, are composed with the checkout's interpreter. The native-agent guard and the worker-message guard are stdlib-only on purpose and decide correctly under any python3, so the composer writes them so they keep running where no reckon environment exists.

Done when:

  • A test finds, by a search over the code rather than a hand list, every script under reckon/hooks/ that either writer registers and that imports a reckon module, and finds each composed with the checkout's interpreter, so a reckon-importing hook added later without it fails the test.
  • reckon sync composes, recognises and writes through install.py, and _is_native_agent_guard_group, _is_worker_message_guard_group and sync's private atomic write no longer exist in reckon/cli.py.
  • reckon sync run against a temporary project and a temporary settings file writes every reckon-importing hook bound to the checkout's interpreter and the two stdlib-only guards runnable by any python3.
  • A settings file holding the bare reckon commands is upgraded in place by both reckon sync and reckon hooks install, with no duplicate entry, and every hook that is not reckon's is left byte-for-byte unchanged.
  • No test reads or writes the real ~/.claude/settings.json.

§3 — A run's harness home carries interpreter-bound hooks

When reckon seeds a run's harness home from the operator's settings.json, it passes the copied hooks through §2's recogniser and composer, so every reckon hook command in the run home is interpreter-bound whatever the operator's file holds. Hooks that are not reckon's are copied unchanged, and the operator's own file is never written.

Done when:

  • A test seeds a run home from an operator settings file holding bare reckon hook commands beside a hook that is not reckon's, and finds the run home's reckon commands interpreter-bound, the other hook unchanged, and the operator file's bytes unchanged.
  • A test seeds from a file that already holds the bound commands and finds the run home identical to it.

§4 — A reckon hook started by the wrong interpreter corrects itself

Landed reckon/hooks/interpreter_bootstrap.py: the obligations, stop and git-guard hooks load one stdlib-only bootstrap before any reckon import and re-execute under the checkout's .venv interpreter when an older python starts them; the git guard denies with a permissionDecision when that interpreter is missing. §5 — Existing installs are healed

Once §2 is on main, the operator's ~/.claude/settings.json on this workstation is upgraded through reckon hooks install --write, and every mounted project is re-synced so its setup writes the bound commands. This is an operational step run by the coordinator, after a dry run shows the change.

Done when: the operator's settings file holds no bare reckon hook command, read back after the write; a worker dispatched through a shell whose first python3 is the system 3.9 finishes with its stop hook decided and its git guard active, shown by the guard refusing a banned command in that worker.
