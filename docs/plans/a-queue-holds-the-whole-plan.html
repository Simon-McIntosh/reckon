§1 — What stalls the work today, measured on 23 October 2026

Five power_convertor coordinator sessions had been running for two days. At 06:30 CEST they held two live runs between them, and one of those had a live process. Lane capacity was not the limit. The lane document published 30 worker slots, 17 live runs across the workstation and nothing waiting (admission.verdict: open). The work was held on the coordinator side, in four ways.

  • A node can be dispatched only once its upstream has landed. Each session therefore stays awake to dispatch the next section the moment a peer lands. Each session's last turns were messages to peers about who frees which file and who lands what first. Three sessions waited on one integrated run, and two more on one solver node.
  • One unreadable status held the chain for two hours. A code review exited at 02:44:46Z with exit 0, having filed a parsed review (82/120, nothing blocking). It left its manifest at status: in-progress. The run read working, its coordinator reported it "still running", and three sessions waited. One crew repair --status complete released it, and the coordinator promoted it within minutes.
  • Review outnumbers implementation. From 19 to 23 October the project ran 247 code reviews and 98 plan reviews against 143 implementation runs. On 22 October the count was 72 reviews against 17 implementations. Every review is a queue slot and a coordinator turn.
  • Coordinator context is the scarce resource, not lane slots. Two of the five sessions sat at about 95 % of a million-token context, and one had compacted twenty times. A plan whose width is fed one section at a time costs a coordinator turn per section, plus turns spent waiting.

The queue built in a-held-dispatch-waits-its-fair-turn cannot absorb a plan's width. Its depth per session is the router's fair share clamped between QUEUED_DISPATCH_CAP_FLOOR = 2 and QUEUED_DISPATCH_CAP_CEILING = 8 (reckon/crew/runs.py). It admits only nodes that were dispatchable when queued. It orders each session by join time, reviews first (reckon/crew/queue_order.py), and has no priority. A brief dispatch stores a copy of the brief at dispatch (_store_brief in reckon/crew/dispatch_admission.py), so editing the coordinator's source file afterwards changes nothing the worker reads. A plan-section dispatch, by contrast, already reads its section at the launch base. Separately, a lift on a metered lane removes its pace hold but does not make the picker prefer that lane. Every power_convertor session held an uncapped codex lift from 22 October 19:11Z, and from 21 October the project ran one run on codex against 282 on the local lane, because the local lane always had room.

The aim: a coordinator loads a plan's whole remaining width, or a sprint's, in one pass. Each request waits on its own dependencies, is ranked by the work's priority and the projects' fair use, and launches when it is both ready and admitted. The coordinator can edit or re-rank any request until it launches. Queues of hundreds of requests that run for a week are the expected case, not an overload.

§2 — A queued request may wait on its dependencies

Dispatch accepts a node whose section waits are unmet. A wait is a plan-section-depends-on ref, a gate, or another queued request named by id. The request is stored in a new awaiting-upstream state carrying the refs it waits on (not waiting, which reckon/crew/dispatch_admission.py already uses for a count of requests queued behind a holder), and every contract check that does not depend on the upstream's output runs at queue time, so a malformed node is still refused at once. Each admission pass re-reads readiness through the same derivation roadmap uses. An awaiting-upstream request becomes queued when its last ref lands, and blocked-upstream, surfaced on the owning session's obligations, when a ref is closed as abandoned or failed. Write scopes are checked at launch, not at queue time: two requests may queue on one file, and the earlier-ranked one launches first, as the existing overlap hold already does for queued requests.

Done when a test queues a three-section chain in one call and the sections launch in dependency order as each upstream promotes, with no coordinator call in between. A negative arm marks the middle section's upstream abandoned: the tail must go blocked-upstream and never launch. A malformed node in the same batch must be refused at queue time.

Owners. The admission pass is admit_once in reckon/crew/queue_admission.py: the readiness re-read and the moves from awaiting-upstream to queued and to blocked-upstream are made there. The two new states join the request-phase vocabulary beside QUEUED_PHASE and LAUNCH_FAILED_PHASE in the same module, and every reader that filters on a request's phase, queued_placements, the obligations view and the watch stream among them, reads them from that vocabulary rather than from string literals. Write paths: reckon/crew/queue_admission.py, the module that stores a queued request (reckon/crew/dispatch_admission.py) and a new test file. Every log is under the run directory.

§3 — Queue depth is bounded by the project, not by a per-session count

Retire the 2–8 per-session clamp. A request's place comes from §4's ranking, so depth no longer needs to stand in for fairness. Depth is bounded per project by queue.max_requests in flight configuration, default 500. Requests are deduplicated on (project, plan, section, node id): queuing the same section twice returns the existing request. The review exemption from a-coordinator-can-clear-its-own-duties §2, which today exempts reviews from the per-session cap, moves to the project bound: a review of a delivered run is never refused by queue.max_requests. §3 waits on §4: retiring the clamp is safe only once ranking does the work the clamp stood in for. §3 declares its own bound: 500 requests per project, and each view's existing read deadline, the 30 s deadline_seconds that crew reads carry in their storage-slow refusal today.

Done when one session queues 200 requests without a refusal, a duplicate returns the existing id, the 501st request in a project is refused with the bound named, and crew view live and the obligations view each answer within that 30 s deadline, cold and warm, on a fixture holding 500 queued pointers.

§4 — Admission ranks by priority within a project and by weighted fair use across projects

Every request carries a priority. A request's priority is its section's roadmap key, _priority_key in reckon/roadmap_ranking.py with its signal vocabulary (critical path, sprint position, ROI, reach, stuck), plus an optional explicit override that crew queue reprioritise sets and that sorts ahead of the key. There is one ordering, the roadmap's, not a second one for the queue. Every project, and optionally every session, carries a fair-use weight in flight configuration. When a slot frees, admission chooses the project by weighted deficit round robin, so a project's share of launched work over a window tracks its weight, whatever its queue depth. Within the project it chooses the highest-priority ready request, with ageing so a low-priority request still launches within STARVATION_AGE_SECONDS, 30 minutes, in reckon/crew/queue_order.py. Reviews of delivered runs keep their precedence. The queue view reports each request's effective rank and the reason for it.

This moves the split of slots between sessions out of the router. The lane router in imas-ambix then publishes one figure, the lane's worker slots, and stops dividing it by session (admission.sessions, fair_share). Fairness becomes a reckon setting the lead can change, instead of a property of how many sessions happen to be open. In the same change §4 replaces the per-session hold in _dispatch_lane_allowance (reckon/crew/dispatch_plan.py): admission reads the lane-wide admission.worker_slots and applies the configured weights. The router's per-session figures go unused but stay published until imas-ambix drops them.

Done when a simulation with two projects weighted 3:1, each with 100 ready requests, launches within ±10 % of 3:1 over 80 admissions. A raised priority launches before an older default request in its own project. A lowest-priority request launches within the ageing bound. The negative arm sets equal weights, and the split must move to 1:1. With weights configured, a request is not held on admission.sessions[<session>].worker_slots.

§5 — A queued request's brief binds at launch, and is editable until then

A request names its authority by reference: a plan section, a steering file, or both. The plan section is already read at the launch base. A steering file is a markdown file the coordinator writes under the project's crew state. It is no longer copied at dispatch: admission reads it at launch, contract-checks it, stores the copy in the run directory and records its digest on the run, so the run still records exactly what the worker read. Reading the queue stays crew view live --phase queued, plus the awaiting-upstream phase §2 adds, because queued requests already carry position and rank there; no list or show verb is added. The new verbs are crew queue edit, crew queue reprioritise and crew queue drop, each with an MCP crew action. drop takes over from crew discard on queued and awaiting-upstream requests, and discard keeps its role for other non-running pointers. The steering copy is stored by _store_brief in reckon/crew/dispatch_admission.py. edit replaces an awaiting-upstream or queued request's steering text, done-when, write paths or time budget, re-runs the contract checks, and is refused once the request has launched. A steering file that fails its checks at launch leaves the request queued with the failure on it, as a launch failure does today, and never launches a worker on an unchecked brief.

Done when a test queues a request with a steering file, edits the file, and the launched worker's recorded digest matches the edited text. crew queue edit on a launched request is refused. A steering file made invalid while queued keeps the request queued with the failure named.

§6 — A passing run lands without a coordinator turn

A week-long queue stalls on the first run that needs a coordinator who has run out of context. A delivered implementation run gets one review, sized to its risk as a-review-is-sized-to-its-risk set out. When _review_accepts_promotion in reckon/crew/recovery_review_acceptance.py accepts that review against REVIEW_ACCEPTANCE_FLOOR, which defines the floor, the run lands mechanically and its follow-on findings are filed against the plan. The landing is what moves §2's awaiting-upstream requests to queued. The coordinator is woken only for a blocked or failed run, a review below the floor, a scope violation, or a request gone blocked-upstream. A review run that exits 0 after filing a parsed review reads complete through the-crew-does-its-own-bookkeeping §22, which owns that classification; this section consumes it. A second review of the same head is refused unless the coordinator changed the deliverable.

Driver. The admission service, crew admit, run by the fleet supervisor, gets a landing pass beside its admission pass, on the same loop. It finds each delivered implementation run whose stored review read the delivered head, is accepted by _review_accepts_promotion, the landing pass defining no floor of its own,, and for each runs the same crew land path a coordinator calls, serialised per repository under the landing lock. A refused or failed landing leaves the run unlanded and raises the owning session's obligation with the guard named; it never retries silently. The merged-head gate in that path does not run on the login node: it goes onto the fleet allocation through the same srun shim that launches workers, and the service only waits on it. The session follower's reflex is not the driver because it dies with an idle or closed session, which is the failure this section removes, and the watch producer is not because it is a reader; admission already outlives every session and already moves work when its conditions hold.

Done when the landing pass lands a passing fixture run, and its downstream request launches, with no session, coordinator or follower alive, and the run's gate executes through the srun shim rather than in the service's process. A run whose review read an older head is not landed. A below-floor review raises an obligation and does not land. A second review of an unchanged head is refused.

§7 — A lifted lane with room is preferred, so a lift is spent

The picker reads lift state as an input. A lane with an active lift, in scope for the request's session or project and with window room left, is preferred for requests at or above a stated priority and capability. Ordinary work still stays local while the local lane has room, and a named lane is still authoritative. The picker records the lift that moved a choice. Pace still ends a lift at its stated reset, and §4's ranking decides which requests the lifted lane takes first.

Done when a picker test with a lifted codex lane and an open local lane routes an elevated-risk request to codex and a low-risk one locally, and records the lift on the choice. With the lift cleared, both route locally.
