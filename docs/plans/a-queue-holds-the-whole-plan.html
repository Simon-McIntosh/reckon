§1 — What stalls the work today, measured on 23 October 2026

Five power_convertor coordinator sessions had been running for two days. At 06:30 CEST they held two live runs between them, and one of those had a live process. Lane capacity was not the limit. The lane document published 30 worker slots, 17 live runs across the workstation and nothing waiting (admission.verdict: open). The work was held on the coordinator side, in four ways.

  • A node can be dispatched only once its upstream has landed. Each session therefore stays awake to dispatch the next section the moment a peer lands. Each session's last turns were messages to peers about who frees which file and who lands what first. Three sessions waited on one integrated run, and two more on one solver node.
  • One unreadable status held the chain for two hours. A code review exited at 02:44:46Z with exit 0, having filed a parsed review (82/120, nothing blocking). It left its manifest at status: in-progress. The run read working, its coordinator reported it "still running", and three sessions waited. One crew repair --status complete released it, and the coordinator promoted it within minutes.
  • Review outnumbers implementation. From 19 to 23 October the project ran 247 code reviews and 98 plan reviews against 143 implementation runs. On 22 October the count was 72 reviews against 17 implementations. Every review is a queue slot and a coordinator turn.
  • Coordinator context is the scarce resource, not lane slots. Two of the five sessions sat at about 95 % of a million-token context, and one had compacted twenty times. A plan whose width is fed one section at a time costs a coordinator turn per section, plus turns spent waiting.

The queue built in a-held-dispatch-waits-its-fair-turn cannot absorb a plan's width. Its depth per session is the router's fair share clamped between QUEUED_DISPATCH_CAP_FLOOR = 2 and QUEUED_DISPATCH_CAP_CEILING = 8 (reckon/crew/runs.py). It admits only nodes that were dispatchable when queued. It orders each session by join time, reviews first (reckon/crew/queue_order.py), and has no priority. A brief dispatch stores a copy of the brief at dispatch (_store_brief in reckon/crew/dispatch_admission.py), so editing the coordinator's source file afterwards changes nothing the worker reads. A plan-section dispatch, by contrast, already reads its section at the launch base. Separately, a lift on a metered lane removes its pace hold but does not make the picker prefer that lane. Every power_convertor session held an uncapped codex lift from 22 October 19:11Z, and from 21 October the project ran one run on codex against 282 on the local lane, because the local lane always had room.

The aim: a coordinator loads a plan's whole remaining width, or a sprint's, in one pass. Each request waits on its own dependencies, is ranked by the work's priority and the projects' fair use, and launches when it is both ready and admitted. The coordinator can edit or re-rank any request until it launches. Queues of hundreds of requests that run for a week are the expected case, not an overload.

§2 — A queued request may wait on its dependencies

Dispatch accepts a node whose section waits are unmet. A wait is a plan-section-depends-on ref, a gate, or another queued request named by id. The request is stored in a new awaiting-upstream state carrying the refs it waits on (not waiting, which reckon/crew/dispatch_admission.py already uses for a count of requests queued behind a holder), and every contract check that does not depend on the upstream's output runs at queue time, so a malformed node is still refused at once. Each admission pass re-reads readiness through the same derivation roadmap uses. An awaiting-upstream request becomes queued when its last ref lands, and blocked-upstream, surfaced on the owning session's obligations, when a ref is closed as abandoned or failed. Write scopes are checked at launch, not at queue time: two requests may queue on one file, and the earlier-ranked one launches first, as the existing overlap hold already does for queued requests.

Done when a test queues a three-section chain in one call and the sections launch in dependency order as each upstream promotes, with no coordinator call in between. A negative arm marks the middle section's upstream abandoned: the tail must go blocked-upstream and never launch. A malformed node in the same batch must be refused at queue time.

Owners. The admission pass is admit_once in reckon/crew/queue_admission.py: the readiness re-read and the moves from awaiting-upstream to queued and to blocked-upstream are made there. The two new states join the request-phase vocabulary beside QUEUED_PHASE and LAUNCH_FAILED_PHASE in the same module, and every reader that filters on a request's phase, queued_placements, the obligations view and the watch stream among them, reads them from that vocabulary rather than from string literals. Write paths: reckon/crew/queue_admission.py, the module that stores a queued request (reckon/crew/dispatch_admission.py) and a new test file. Every log is under the run directory.

§3 — Queue depth is bounded by the project, not by a per-session count

Retire the 2–8 per-session clamp. A request's place comes from §4's ranking, so depth no longer needs to stand in for fairness. Depth is bounded per project by queue.max_requests in flight configuration, default 500. Requests are deduplicated on (project, plan, section, node id): queuing the same section twice returns the existing request. The review exemption from a-coordinator-can-clear-its-own-duties §2, which today exempts reviews from the per-session cap, moves to the project bound: a review of a delivered run is never refused by queue.max_requests. §3 waits on §4: retiring the clamp is safe only once ranking does the work the clamp stood in for. §3 declares its own bound: 500 requests per project, and each view's existing read deadline, the 30 s deadline_seconds that crew reads carry in their storage-slow refusal today. That deadline is applied by the MCP read wrapper in reckon/mcp_deadlines.py, so the measure is the MCP read, not a timed shell command.

Done when one session queues 200 requests without a refusal, a duplicate returns the existing id, the 501st request in a project is refused with the bound named, and the MCP crew reads of the live view and the obligations view each answer within that 30 s deadline, cold and warm, on a fixture holding 500 queued pointers.

§4 — Admission ranks by priority within a project and by weighted fair use across projects

Every request carries a priority. A request's priority is its section's roadmap key, _priority_key in reckon/roadmap_ranking.py with its signal vocabulary (critical path, sprint position, ROI, reach, stuck), plus an optional explicit override that crew queue reprioritise sets and that sorts ahead of the key. There is one ordering, the roadmap's, not a second one for the queue. Every project, and optionally every session, carries a fair-use weight in flight configuration. When a slot frees, admission chooses the project by weighted deficit round robin, so a project's share of launched work over a window tracks its weight, whatever its queue depth. Within the project it chooses the highest-priority ready request, with ageing so a low-priority request still launches within STARVATION_AGE_SECONDS, 30 minutes, in reckon/crew/queue_order.py. Reviews of delivered runs keep their precedence. The queue view reports each request's effective rank and the reason for it.

This moves the split of slots between sessions out of reckon's reliance on the router. Reckon stops reading the router's per-session figures (admission.sessions, fair_share); the router dropping them is imas-ambix's change, imas-ambix:local-lane-admission-control §27, which waits on this section. Fairness becomes a reckon setting the lead can change, instead of a property of how many sessions happen to be open. In the same change §4 replaces the per-session hold in _dispatch_lane_allowance (reckon/crew/dispatch_plan.py): admission reads the lane-wide admission.worker_slots and applies the configured weights. The router's per-session figures go unused but stay published until imas-ambix drops them.

Done when a simulation with two projects weighted 3:1, each with 100 ready requests, launches within ±10 % of 3:1 over 80 admissions. A raised priority launches before an older default request in its own project. A lowest-priority request launches within the ageing bound. The negative arm sets equal weights, and the split must move to 1:1. With weights configured, a request is not held on admission.sessions[<session>].worker_slots.

§5 — A queued request's brief binds at launch, and is editable until then

A request names its authority by reference: a plan section, a steering file, or both. The plan section is already read at the launch base. A steering file is a markdown file the coordinator writes under the project's crew state. It is no longer copied at dispatch: admission reads it at launch, contract-checks it, stores the copy in the run directory and records its digest on the run, so the run still records exactly what the worker read. Reading the queue stays crew view live --phase queued, plus the awaiting-upstream phase §2 adds, because queued requests already carry position and rank there; no list or show verb is added. The new verbs are crew queue edit, crew queue reprioritise and crew queue drop, each with an MCP crew action. drop takes over from crew discard on queued and awaiting-upstream requests, and discard keeps its role for other non-running pointers. The steering copy is stored by _store_brief in reckon/crew/dispatch_admission.py. edit replaces an awaiting-upstream or queued request's steering text, done-when, write paths, time budget or route (lane, backend or model), re-runs the contract checks, and is refused once the request has launched. A route set by edit is a named route: it passes the same override checks --backend and --model pass at dispatch, and §15's fallback never moves it. A steering file that fails its checks at launch leaves the request queued with the failure on it, as a launch failure does today, and never launches a worker on an unchecked brief.

Done when a test queues a request with a steering file, edits the file, and the launched worker's recorded digest matches the edited text. A queued request whose route is edited to another lane launches on that lane, and an edit naming a model its lane does not declare is refused. crew queue edit on a launched request is refused. A steering file made invalid while queued keeps the request queued with the failure named.

§6 — A passing run lands without a coordinator turn

A week-long queue stalls on the first run that needs a coordinator who has run out of context. A delivered implementation run gets one review, sized to its risk as a-review-is-sized-to-its-risk set out. When _review_accepts_promotion in reckon/crew/recovery_review_acceptance.py accepts that review against REVIEW_ACCEPTANCE_FLOOR, which defines the floor, the run lands mechanically and its follow-on findings are filed against the plan. The landing is what moves §2's awaiting-upstream requests to queued. The coordinator is woken only for a blocked or failed run, a review below the floor, a scope violation, or a request gone blocked-upstream. A review run that exits 0 after filing a parsed review reads complete through the-crew-does-its-own-bookkeeping §22, which owns that classification; this section consumes it. A second review of the same head is refused unless the coordinator changed the deliverable.

Driver. The admission service, crew admit, run by the fleet supervisor, gets a landing pass beside its admission pass, on the same loop. It finds each delivered implementation run whose stored review read the delivered head, is accepted by _review_accepts_promotion, the landing pass defining no floor of its own,, and for each runs the same crew land path a coordinator calls, serialised per repository by the mechanisms crew land already uses: the index.lock retry in reckon/crew/merge.py and the per-run promotion lease in reckon/crew/promotion.py. No new lock is introduced. A refused or failed landing leaves the run unlanded and raises the owning session's obligation with the guard named; it never retries silently. The merged-head gate in that path does not run on the login node: it goes onto the fleet allocation through the same srun shim that launches workers, and the service only waits on it. The session follower's reflex is not the driver because it dies with an idle or closed session, which is the failure this section removes, and the watch producer is not because it is a reader; admission already outlives every session and already moves work when its conditions hold.

Done when the landing pass lands a passing fixture run, and its downstream request launches, with no session, coordinator or follower alive, and the run's gate executes through the srun shim rather than in the service's process. A run whose review read an older head is not landed. A below-floor review raises an obligation and does not land. A second review of an unchanged head is refused.

§7 — A lifted lane with room is preferred, so a lift is spent

The picker reads lift state as an input. A lane with an active lift, in scope for the request's session or project and with window room left, is preferred for requests at or above a stated priority and capability. Ordinary work still stays local while the local lane has room, and a named lane is still authoritative. The picker records the lift that moved a choice. Pace still ends a lift at its stated reset, and §4's ranking decides which requests the lifted lane takes first.

Done when a picker test with a lifted codex lane and an open local lane routes an elevated-risk request to codex and a low-risk one locally, and records the lift on the choice. With the lift cleared, both route locally.

§8 — The queue respects the work's DAG across plans and projects

§2 lets one request wait on refs it names. A queue that holds a week of work needs more: the whole dependency graph the roadmap already derives, across plans and across projects. A request's waits are the union of its section's plan-section-depends-on refs, its plan's depends_on, the gates on its section, and, for a brief dispatch that has no section, the requests it names with --after <request-id>. A ref of the form project:slug#sN resolves through that mounted project's own readiness derivation, so a reckon request can wait on an imas-ambix section, and the other way round.

The graph is checked when the work is queued. A batch whose waits form a cycle, among the new requests or through requests already queued, is refused whole, and the refusal names every request in the cycle. A wait that names a section, plan or request that does not exist is refused at queue time, never discovered at launch. A request whose wait is met when it is queued goes straight to queued.

Each admission pass re-reads readiness through the same derivation the roadmap uses, once per project per pass, not once per request. A request is never launched before every one of its upstream sections is declared done or its upstream request has landed; landing, not promotion of an unreviewed head, is what satisfies a wait.

Owners. The wait derivation is one function beside the readiness re-read §2 adds in reckon/crew/queue_admission.py, and it reuses parse_plan_ref in reckon/_schema.py rather than restating it. Write paths: reckon/crew/queue_admission.py, reckon/crew/dispatch_admission.py and a new test file.

Done when a test with two fixture projects queues a request in project A whose section waits on B:plan#s2, and it launches only after B's §2 is declared done. A test queues three requests whose --after refs form a cycle, and the batch is refused naming all three, with nothing stored. A request waiting on a section that does not exist is refused at queue time. The negative arm declares B's §2 done before queuing, and the request goes straight to queued.

§9 — An orchestrator loads a plan's whole width in one beat, one sized node per dispatch

Sizing is the orchestrator's judgement and stays so. It reads each section, decides how many nodes the section needs, and writes each node's goal, done-when, write paths and time budget. Nothing in reckon composes requests from a plan's sections by itself. What changes is when the orchestrator dispatches. With §2 and §8, dispatch accepts a node whose upstream has not landed. So once a plan's review round is answered, the orchestrator dispatches every node of the plan in one beat, chain heads and tails alike, instead of one section at a time as each upstream lands. Each dispatch is an ordinary reckon crew dispatch, routed by §15, and the queue holds whatever is not ready.

A node the orchestrator forgot should be visible, not silent. The drain view lists, per plan, each implementable section that has no request in any phase and no landed run, as unloaded. The view is a read: it never composes or stores a request. Dispatching the same node again returns the existing request, through §3's deduplication, so reloading a plan after an interruption is safe.

Done when a test dispatches, one call per node, the five nodes of a fixture plan with two chains, before any upstream lands. All five are stored, the chain heads queued or launched and the tails awaiting-upstream, and they launch in dependency order as their upstreams land, with no further dispatch. The drain view lists a sixth implementable section that has no request as unloaded, and stops listing it once a node for it is dispatched. Re-dispatching a stored node returns its existing id and stores nothing. The test asserts that reading the drain view stores no pointer.

§10 — A queued request can be held and released

§5 lets a coordinator edit, re-rank or drop a request. It cannot stop one launching while it thinks, short of dropping it and losing its place. Add reckon crew queue hold and reckon crew queue release, each taking one request id, or --plan <slug> or --session <id> for every request of that plan or session, with an optional --reason. Each has an MCP crew action.

A held request keeps its place, its waits and its stored brief. Admission skips it, and it does not count as work waiting for capacity. Its starvation age does not accrue while it is held, so a release returns it to the rank it had and does not jump the queue. A hold on a launched request is refused, naming crew stop. A request held for more than 24 hours appears once on its session's obligations with its reason, so a forgotten hold is visible and is not an alarm on every beat. held joins the request-phase vocabulary §2 defines, and every reader takes it from there.

Done when a held request is skipped while a lower-ranked one in the same project launches, and on release launches next. A plan-wide hold holds every queued and awaiting-upstream request of that plan, and a release restores each one to its prior state and rank. A hold on a launched run is refused. A 25-hour-old hold appears once on the obligations view.

§11 — A plan edit never strands a queued request

A hot edit of the plan is how a coordinator steers queued work, so editing must be safe. Today it is not. The plan-review gate runs again when admission launches a queued request, and a plan that gained an unreviewed unit after the dispatch refuses every launch with PlanReviewMissingError (raised in reckon/crew/routing.py). Meanwhile the obligations view reads "waiting for a lane slot". Measured on 21 October 2026: one run held this way for four hours.

At admission the gate is evaluated only over the units the request reads: its own section and the document unit carrying decisions, gates and dependencies. An uncovered change to another section does not hold it. When one of its own units is uncovered, the request moves to held (§10) with the reason plan-review-owed and the review invocation that would cover it. The obligations view shows one row per plan, not one per request, naming the held count and that invocation. When a stored review covers the units again, the next admission pass releases those requests by itself. A request a coordinator held by hand is never released by this path.

Done when a test with §2 and §3 of a fixture plan queued edits §3's done-when: §2 launches and §3 goes held with plan-review-owed. The obligations view shows one row for the plan. Storing a review that covers §3 releases it on the next pass, with no coordinator call. A request held by hand stays held through that pass.

§12 — A week of queued work reads in one view

A coordinator who returns to a queue after a day needs one answer: what moved, what is stuck and why, and when the rest will finish. Extend the existing crew view drain rather than adding a verb. Per project and per plan it reports the count in each request phase: awaiting-upstream, queued, held (split by reason), blocked-upstream, launched, landed and failed. It also reports launches and landings over the last 24 hours, and a finish estimate, the remaining count divided by the 24-hour landing rate, which is null while that rate is zero. Every request stuck for longer than an hour in a phase that admission should have moved names the verdict that last held it, read from admission-verdicts.jsonl. The derivation is Python, so the SPA, the CLI and an MCP read all receive the same figures.

Done when a fixture of 120 requests in mixed phases yields per-plan counts that match a hand count, a 24-hour rate and an estimate (null at zero rate), and names the last verdict for a request queued for two hours. Run on 500 pointers, the MCP read answers inside its 30 s deadline, cold and warm.

§13 — The skills load the width, then steer it

The mechanism is unused until the skills teach it. skills/reckon-build/SKILL.md and skills/reckon-build/references/sprint-orchestration.md today tell a coordinator to dispatch every ready-idle section on each beat. They change to a load-then-steer pattern. After the plan's review round is answered, the coordinator sizes every remaining section into nodes, as it does today, and dispatches all of them in one beat (§9). It names no lane, so the picker routes each node (§15) and the queue holds whatever is not ready. It then confirms that the drain view lists no unloaded section. From then on it steers rather than feeds. It edits a queued section through reckon-edit and answers the review that §11 holds it for. It edits a steering file or done-when with crew queue edit, pauses with hold, resumes with release, bumps with reprioritise and withdraws with drop. It reads progress from crew view drain, and it is woken only for the obligations §6 names. skills/reckon-edit/SKILL.md gains the matching rule: an edit to a section that has a queued request holds only that request, and the edit's review releases it.

The user-global agent guidelines carry a dispatch paragraph that the coordinator updates in the same change, because a worker's fence cannot write the home directory.

The repository's own AGENTS.md carries the same rule in its orchestration pointers ("an idle lane with ready work is a defect — dispatch every ready-idle section each beat"), and a coordinator reads it every session, so it changes in the same node.

Done when the three skill files describe the queue-first pattern with each verb named once, a grep of skills/ and AGENTS.md finds no remaining instruction to dispatch section by section on every beat, and the skill-contract tests pass.

§14 — Dogfood: a week of work drains from one queue

The plan is done when the pattern has carried real work, not when its tests pass. Once every other section has landed and the admit service runs the merged code, the coordinator queues the remaining implementable width of at least two live plans, at least one in reckon and one in imas-ambix. It sizes and dispatches every node of those plans in one beat (§9), naming no lane so that the picker routes each one (§15). The load must include at least 30 requests, at least one cross-project wait and at least one request routed to codex, and it sets project weights to 3:1. Then it lets the queue drain on the local lane for up to seven days. Its only deliberate interventions are one hot edit of a queued section, with its review answered; one hold and release; one priority bump; one drop; and whatever the obligations view raises. The plans chosen and the manifest are recorded in the evidence.

Measured from the ledger, the admission verdicts and the drain view, and recorded in docs/evidence/archive/a-queue-holds-the-whole-plan-landed.html with a figure of launched and landed work per project over time and queue depth by phase:

  • No request launched before its upstream landed. Count the DAG-order violations; the measure requires zero.
  • While both projects had ready work, their share of launches stayed within ±15 % of 3:1.
  • The bumped request launched before older requests of default priority in its project, and the held request did not launch while held.
  • The edited request launched on the edited text, matching the recorded digest.
  • No request sat queued for more than an hour without a recorded verdict.
  • The count of coordinator turns the drain needed, set beside the count of landed runs.
  • The share of runs landed by §6 without a coordinator turn.
  • The drain view listed no unloaded section after the loading beat.
  • Every codex-routed request launched as soon as it was ready, without waiting on a local slot, and every fallback to local is recorded with its reason.

Done when the evidence records each measure above with its figure, and every defect the drain exposed has its own section in this plan or in a named successor. A failed measure is a result to record, not a reason to stop the drain early.

§15 — Jev routes each request before it enters the one queue, and a ready metered request launches at once

Local and codex work share one queue. Between the orchestrator's dispatch and the queue, every request passes through the picker (Jev). It chooses the request's lane and model exactly as it does for a dispatch today, including §7's lift preference. Routing is invisible to the dispatcher: a coordinator names no lane, and only --local, --backend or --model override the pick, which stay authoritative. The chosen route and the picker's reasons are recorded on the request when it enters the queue.

After that, readiness decides what happens, not the lane. A request whose waits are met launches at once if its lane can serve it. A request routed to a metered lane is never held behind the local lane's worker slots, because it does not occupy one: the slot hold in _dispatch_lane_allowance reads only a backend that declares a lane_document. A ready local request is admitted by §4's ranking as slots free. A request whose waits are unmet sits awaiting-upstream with its route, on whichever lane, and is admitted the same way once it becomes ready.

A metered lane can stop serving between routing and launch: its pace hold engages, its window is spent, or the provider refuses. When admission finds that a request's routed metered lane cannot serve it at launch, the request falls back to the local lane, keeps its rank, and records the fallback and the lane's reason on the request and the run. A request whose lane, backend or model the dispatcher named never falls back. It stays queued with the reason named, and it appears on its session's obligations if it waits more than an hour. Re-routing a queued request is explicit, through crew queue edit (§5), never a background re-pick.

Owners. The route comes from the existing pick in reckon/crew/dispatch_plan.py and is stored on the queued pointer by reckon/crew/dispatch_admission.py. Per-lane admission and the fallback live in admit_once in reckon/crew/queue_admission.py. Admission reads lane availability through the budget and lane-gate readers dispatch already uses, not a new reader.

Done when a test with an open codex lane and a full local lane dispatches three ready requests, two that the picker routes to codex and one it routes to local. Both codex requests launch at once and the local one queues. A codex-routed request with an unmet wait sits awaiting-upstream and launches on codex when its upstream lands. A codex-routed request that becomes ready while codex is pace-held launches on local with the fallback recorded. A request dispatched with --backend codex in that state stays queued with the hold named. The negative arm routes no request to codex, and every request queues on local as it does today.
