Graph, sprints and flow · the surfaces that derive from dependencies

Schedule From the Graph, Not From Dates

Three surfaces in the landed SPA draw a dependency graph and each does it differently or not at all: the Graph tab blanks when the selected endpoint has no handle, the sprint surface re-renders the same overview when a sprint is clicked, and the horizon strip places work by run timestamp inside a fixed 48-hour window, so a sprint with no dispatched runs is empty. The canvas replaces all three with one layout helper and one schedule: positions derive from dependency depth and wall-clock hours, anchored at now, and a sprint's graph includes the prerequisites it hangs off.

§1 — Why this exists

The handoff triage (design/reckon-spa-handoff.md, items A1, A7, B1, B2 and B3c) names the defects and the model that replaces them; the canvas (design/reckon-spa-handoff.dc.html) carries two algorithms this plan transcribes rather than redesigns, schedule() and layout() in its logic script. The facts checked against main on 2026-09-03:

  • docs/ui/graph.jsx's _graphHandleView() returns null unless the selected endpoint carries a handle, and _allDependencyChains() lists unnamed live endpoints after the named ones, so selecting one renders the empty state as the whole tab. Three live handles exist across the mounted projects; the empty state is wrong for every other endpoint.
  • docs/ui/sprint.jsx declares HORIZON_HOURS = 48 and horizonStrip() places only runs with a parseable timestamp inside that window; sprint rows navigate to a route that renders the same overview.
  • Plan inventory rows already carry effort_hours, wall_clock_hours, depends_on and blocks, and live run rows carry elapsed_seconds and dispatched_at; the derived schedule needs nothing the server does not serve.

This plan carries no plan-level prerequisite. Its one file-level ordering constraint is that §5 writes docs/ui/crew.jsx, which spa-shell-scope-and-visibility also writes for the scroll and scope fix; dispatch refuses the overlap, so §5 waits for that node to merge. §3 and §4 both consume the helper from §2 and wait for it.

§2 — One DAG layout helper

A single function, exported from docs/ui/graph.jsx as window.ReckonGraph.layout(plans, prefix) and consumed by the sprint detail and the Graph tab, takes plans with slug, title, status, impl, effort_hours, depends_on and an optional ghost flag, and returns nodes, edges, column labels, width and height. Its rules are the canvas's, transcribed: depth is 1 + max(depth of known prerequisites) and zero for a plan with none, with cycles terminated by a seen set; cards are 216 by 82 with 92 horizontal and 22 vertical gaps; an edge spanning one depth is a cubic; an edge spanning more than one depth is an explicit routed path, a quarter-turn down, a straight run at a clearance depth 24px below the bottom of every column it crosses, and a quarter-turn up, because a cubic with both control points at the clearance depth reaches only three quarters of it and passes beneath the intervening cards; co-terminating edges fan on arrival, each endpoint offset 8px around the card's vertical centre so two arrows into one plan stay distinguishable; stroke is red where a blocked plan hangs off an unshipped prerequisite, dashed where the prerequisite has not shipped, solid where it has; a ghost node is dashed, transparent and dimmed, and its status text names the sprint it belongs to; the stage height is the larger of the row extent and the deepest detour actually emitted plus 30.

§3 — A Graph tab that renders every endpoint

Index. One row per endpoint in the selected project, named handles first in the order the roadmap gives them, then unnamed live endpoints (a plan with prerequisites that nothing depends on). A row shows the handle chip (unnamed on a grey chip when absent), title, endpoint slug, closure shipped percentage with a bar, N members · D deep, the repositories the closure spans, and a flag reading N open, N held or ready. Header figures are inline mono, named, unnamed and largest, and the whole panel is absent when no plan depends on another, with the empty state saying so. The index ship control appears only when the project has a named handle and copies /reckon-ship graph:<handle>; it is disabled with the open-decision count while the lead handle's closure has open decisions. Detail. Prev and next through the endpoint list with a position readout, the handle chip, title, endpoint /<slug> · closure N derived, a derived-authority row of repository chips with member counts, a state chip (ready or held · N open), a 280px closure list, and the DAG from §2. An unnamed endpoint renders exactly as a named one except for its ship control: there is no invented command, only a dashed amber chip reading needs plan-graph-handle whose tooltip names the authoring act. Closure membership is the transitive prerequisite closure and reads depends_on only, so the Graph tab and the reader's dependency cone cannot disagree. Hide-done filters endpoints whose closure is fully shipped.

§4 — A sprint table, and a sprint detail whose body is the graph

Table. One row per sprint of the selected project: id, theme, a state chip, completion percentage with a bar, Nh · Mh left, and a flag. Sprint state is derived from members, never read from the file: shipped when every member is at 100%, active when any has started, planned otherwise, empty with no members; where the file's status disagrees the flag reads was <status>, because resolving the disagreement silently would hide a real inconsistency. Otherwise the flag reads N held or nothing. The header carries three inline figures for the project (left in worker-hours, chain as the derived schedule's far end in hours, held), the ship control for the active sprint (absent when there is none, because a project name is not a ship target), and the hide-done toggle. The 48-hour strip, its hour ticks and the recorded-work list are retired: the schedule of §5 replaces the first and the sprint detail replaces the second. Detail. Opened by clicking a row. Header: back, id, theme, the ship control (disabled with N open decisions while any member has one). A stat row: plans, worker-hours, depth, held, prerequisites, open decisions. A legend decoding solid and dashed cards. The body is the §2 layout over the sprint's members plus every prerequisite outside the sprint, pulled transitively and drawn as ghost nodes, so a sprint whose four members each hang off an earlier plan reads as a chain rather than four unconnected cards.

§5 — The derived flow, on the Crew surface

The canvas hosts the flow above the crew cards, because a lane is one crew session and the flow can only be computed inside one repository's dependency graph. Schedule. For every plan of the selected project, in hours relative to now: a shipped plan ends when it landed (its edited stamp) and starts wall_clock_hours before that; an active plan starts at the earliest live run's dispatch for it (else now) and runs for its wall-clock hours; a pending or draft plan starts at max(end of its prerequisites, 0) and runs for its wall-clock hours. Nothing else determines position; move a dependency or re-estimate an hour figure and the tail re-hangs. Bars older than 60 hours are dropped. Lanes are best-fit packed, each new bar going to the lane whose last end is latest among those that fit, so the lane count reports realisable width rather than arrival order; a lane is labelled session N with live · <role> when one of its plans has a live run, else N items · Mh. The axis runs from max(-48, min(-24, earliest start)) to max(24, latest end) with ticks every 12 hours (24 when the span exceeds 96), the zero tick reading now and a now-line through every lane. Bars carry the plan title, wall-clock hours and a sprint chip; a sprint chip row above dims bars of other sprints to 28% opacity; recorded, in-flight, predicted and held are decoded by a colour key. The crew header reads <project> · N runs · M sessions · polling every 3s. The sprint surface's header figure chain reads the same schedule's far end.

§7 — Out of scope

The two open design questions on graph closures, whether a plan in two closures unions the authority and whether scope escalation is silent, are recorded in the handoff as separate work and are not decided here: the closure rule stays the existing transitive prerequisite walk. The fleet prompt module and the sprint route's prompt strip are left in place; the fleet home plan retires them with the cockpit. Authoring graph handles on plans is a plan-design act for the lead, which is why the surface names the missing precondition instead of inventing a target.

§ Decisions

What is the time axis of the sprint and crew flow?

The canvas derives every position from dependency depth and wall-clock hours; a fixed window is empty for a sprint with no dispatched runs, which is the measured defect, and authored dates are a plan of record the graph then contradicts.

Does a sprint's graph include plans outside the sprint?

A sprint DAG drawn from membership alone is four unconnected cards; with its prerequisites it reads as a chain. The handoff calls this the single most important detail.

What does an unnamed endpoint offer as a ship control?

The ship skill defines exactly three targets and a closure ships by handle. An unresolvable string in a copy control is worse than none, because its whole value is being paste-ready.

Which surface hosts the derived-flow lanes?

The canvas template places the lanes on the Crew surface and states why: a lane is one crew session, and the flow is computed inside one repository's graph, which is the scope Crew now has.

Where does a sprint row's state come from?

The canvas derives it and shows the disagreement rather than resolving it, because resolving it silently hides a real inconsistency the sprint skill should repair.
