§1 — A row that cannot tell an unrun probe from a pending one

An imas-ambix incident idled four workers for 24–47 minutes each. The reporting session spent the incident investigating a serving lane whose request queue had been 0.0 all night, because the monitor row read as a node waiting on a slow dependency. The information that would have collapsed the diagnosis in seconds is computed, and never reaches the reader.

recovery.py:1890-1897 computes wait_condition_state and wait_observed, which separate a probe that was never executed from one that ran and has not gone terminal. Those are different situations with different remedies, and the pane renders them identically.

This plan is scoped to that defect and the two sites it lives at. It does not inherit the incident's own diagnosis of why those runs stalled — see §6.

§2 — Two sites, and only one of them is the renderer

§3 — Carry the five facts into the transition event

Thread wait_condition_state, wait_observed, wait_overdue, expected_horizon_seconds and resume_brief from the snapshot into the event built at recovery.py:2630, beside the next_action and lifting_condition already carried there.

Every figure travels numerically and None stays the explicit unmeasured state, matching the contract _spend_facts already states in its own docstring: a zero would assert a measurement nobody took. This section adds no rendering and changes no row; it makes the facts available to one.

§4 — Render the facts the row is now given

With the fields carried, the renderer can answer the question the incident asked. Three changes, all in ticker.py:

  • An unrun probe reads differently from a pending one. wait_condition_state distinguishes them; today both render as wait-aged.
  • The age carries its horizon. The row renders waiting 1870s raw while expected_horizon_seconds and a computed wait_overdue sit unused; 2.1× over horizon costs nothing once the fields arrive.
  • The imperative strings survive the tail. next_action and resume_brief are the two fields telling a reader what to do, and the row truncates them.

§5 — One letter, two quantities

ticker.py:230 maps "waiting": "q", so the compact counter 5q means five runs waiting. It is read as engine queue depth, on a screen that sits beside a model serve with a genuine request queue. Two quantities, one letter, adjacent on the display. This is the cheapest of the three repairs and independent of the other two.

§6 — A dry run that returns before the thing it predicts

The same shape at a third site, in resumption.py's sweep():

if dry_run:
    resumed.append({**entry, "would_resume": True, ...})
    continue
try:
    launched = _resume(...)

The dry-run branch returns before the launcher is ever called, so every guard the launcher applies is unreachable in a dry run. would_resume: True means the sweep would call the launcher, not the launcher would resume. Two different claims sharing one name, and the weaker one is reported.

Measured consequence from the same incident: a hand crew resume-ready --dry-run reported checked 4, would_resume 4, skipped 0 for four runs a real sweep refuses. Acting on that output would have attempted to resume four actively-working sessions. A dry run whose purpose is to predict the real action over-reports systematically, in the direction that causes harm.

Two repairs are available and either suffices: consult the launcher's guards before the dry-run return, or have the dry run report what the launcher would say rather than what it would be asked. The second is the smaller change and the more honest name.

Verification limit, carried deliberately. The branch structure is confirmed in source. The launcher's live-session guard is reported, not verified — it comes from another coordinator's CLI output reading resume-refused because the process is live, which is their reading of their own run. The finding does not rest on it: a dry run that returns before the thing it predicts cannot predict anything that thing does, whatever its guards turn out to be.

§6 — Landed

The first repair, guard consultation, was implemented. The rename was the smaller change and the plan names it as the more honest one, but it fixes the wording and not the harm: the damage was an operator acting on a list of runs a real sweep refuses, and only consulting the guards empties that list. A dry run that cannot answer the question the operator is asking, under a more honest name, is still unable to answer it.

_launcher_refusal() in resumption.py mirrors the guards resume_plan() applies — the run must be a CLI-spawned run, its process must have stopped, and its lane's budget verdict must not hold it — and is consulted before the dry-run return. A refusal is reported through the same formatter the real sweep uses, so a prediction and the action it predicts name a refusal identically. The consult writes nothing: the launcher's ledger hold-check and its context_fit pointer stamp are the traces of an attempt, and a prediction must not leave them.

Parity is held by a test that asks the launcher and the prediction about the same record and requires the same exception and message, rather than by asserting each side separately — two surfaces compared, not two copies asserted about.

One failure is newly visible in an adjacent test, and it is not re-swallowed. test_a_met_dead_wait_is_walked_by_the_resume_sweep builds a pointer with no launch field, which resume_plan() refuses as not a spawned run — so a real sweep never resumes it either, and the test's would_resume is True was true only of the sweep's intention. That fixture rests on the same fail-open this section closes; it needs launch: "cli" added, and that file lies outside this node's write scope, so it is reported rather than edited. Weakening the guard to keep it green would restore the defect.

Evidence: the execution record for this plan.

§7 — What this plan deliberately does not own

The incident's stall diagnosis. The reporting session also concluded that no sweeper was running. That is false: the follower is the sweeper, at cli.py:1791, inside _sweep_on_cadence() in the while not _stopped(): loop, cadence-gated and exception-wrapped. Two live registered followers were confirmed on that project. Why those four runs idled is unestablished, and this plan does not inherit a mechanism for it.

That separation is the reason this finding survived verification when six earlier hypotheses about the same surface did not. It arrived as an observation with its mechanism explicitly withheld; every one of the six that died arrived bundled with an explanation.

§8 — Order, and the falsifier that enforces it

§3 lands before §4. A renderer-only repair delivers next_action and lifting_condition, leaves an unrun probe and a pending one rendering identically, and would be reported as addressing the incident's cause. That is worse than not shipping: it closes the visible half and reports the diagnostic half closed with it.

The measure that enforces the order is a paired assertion:

  • Falsifier: a run whose wait_condition_state is never-executed renders a different row from one that is pending. This fails if only §4 lands, because the field never arrives.
  • Positive control: the same test asserts next_action reaches the row. Without it the falsifier can pass vacuously on a build where nothing renders at all.

Neither half is sufficient alone, which is the property this plan's measures are built around.
