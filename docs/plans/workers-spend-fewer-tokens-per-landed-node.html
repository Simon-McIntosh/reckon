§1 — Why: where a worker's tokens go, measured

A comparison of the crew harness with the oh-my-pi agent program (omp, a fork of Mario Zechner's pi) asked whether its reported token efficiency is worth adopting. The headline figures it publishes — 61% fewer output tokens on Grok 4 Fast, about half on Opus in a third-party measurement — come from its line-anchored edit format, which removes the retry loop a model enters when its retyped old_string does not match the file. Those are cuts in output tokens. The run store says our spend is almost all input.

Measured on 10 November 2026 from a copy of ~/.config/reckon/crew/run_store.db, every run completed since 10 October, reading budget.tokens.input_tokens_cumulative and output_tokens_cumulative from run_details:

So halving output tokens moves total spend by about a quarter of one percent. What a better edit tool can still buy is fewer turns: every failed edit costs a re-read and a retry at a context of 130 to 190 thousand tokens, and on the local lane re-prefilling evicted prefixes is what limits throughput (the cache-residency measurement recorded 18,863 of 22,557 prefill tokens per second spent recomputing prefixes the engine had already built).

An edit census over 58 randomly sampled local-lane implement runs since 25 October (Claude Code driving DeepSeek V4.1 Flash) found 168 failed edits in 1,495 edit calls, 11.2%, about three per run, against about 120 tool calls per run. The commonest refusals were String to replace not found in file (50), InputValidationError on Edit (32), File does not exist (34) and a no-op old_string equal to new_string (25). The same census over 60 codex implement runs counted 594 file_change items and zero failures, which is not believable as a measurement: codex reports a failed patch somewhere that census did not read, so the codex edit failure rate is unmeasured, not zero.

The expected size of the edit-tool effect on the local lane is therefore a few percent of input tokens per run, not half. That is still worth having on the highest-volume lane, but it has to be measured, and the measurement is what decides adoption.

§3 — A line-anchored edit tool ships with reckon

Deliverable. A new module reckon/anchored_edit.py, an MCP stdio server built on the mcp package reckon already depends on, plus a console script reckon-anchored-edit declared in pyproject.toml so a worker's harness can start it by name. Tests in tests/test_anchored_edit.py. The prototype at §2 is the starting shape; the module is product code and owes what the prototype skipped:

  • Anchors. N:HHH, or a bare HHH when exactly one line in the file carries that hash. An ambiguous bare hash, a malformed anchor, or a line number out of range is a refusal naming the accepted format, never an exception.
  • Atomicity. Every anchor in a call is verified before any byte is written; overlapping edits are refused; the file is replaced atomically (written beside the target and renamed), preserving its mode, its line-ending convention and whether it ends in a newline.
  • Confinement. An MCP server runs outside codex's command sandbox, so the server must enforce its own write roots: it refuses any path that resolves (after symlinks) outside the roots it was started with, given as repeated --root arguments. With no root it refuses every write. This is the property that makes it safe to offer a fenced worker. The containment test reuses the fence's own helper, _within_any (reckon/_worker_fence.py near line 983), applied to fully resolved paths, rather than adding a third write-root check beside it and sandbox_can_write.
  • A second stdio entrypoint, deliberately. reckon/mcp.py is the package's existing MCP server, but it is a user-scope server enabled for every worker; the edit tool must be offered per run, with that run's roots, and withheld from baseline runs, so it is its own small process rather than two more tools on the shared server.
  • Refusals that save a turn. A stale anchor returns the current anchored lines around each stale line, so the model can retry without re-reading the file; a successful edit returns the changed region with fresh anchors.
  • Reads. read_anchored(path, offset, limit) with a default limit that keeps a call under about 400 lines; files larger than the limit say how many lines remain.

Done when tests/test_anchored_edit.py passes and covers: a replace, both inserts and a delete by anchor; a unique bare hash accepted and an ambiguous one refused; a stale anchor refusing the whole call with the file byte-identical afterwards; overlapping edits refused; CRLF and missing-final-newline files round-tripping unchanged outside the edited lines; a path outside every --root, including through a symlink, refused with the file untouched; and one test that starts the console script over stdio and completes a read and an edit through the MCP protocol. Negative control: with the confinement check removed, the symlink-escape test must fail; with hash verification removed, the stale-anchor test must fail. uv run ruff check and uv run ruff format --check on the staged paths add no findings.

§4 — Claude-dialect workers can be given the anchored tool

Deliverable. A per-backend flight key, anchored_edit (default false), read where a run home is seeded (reckon/_worker_fence.py, beside _seed_worker_mcp_settings) and where the Claude argv is composed (_ClaudeDialect in reckon/_backends.py; _CliveDialect inherits it). When true for a run's backend: the run home registers the reckon-anchored-edit server with --root set to the run's write roots (the same roots fenced_write_roots computes), its two tools are allowed, and the built-in Edit and MultiEdit tools are disallowed so the run is a clean treatment arm. Write stays, because creating a file has no anchor to address.

The settings seeder runs only for a fenced Claude-dialect run whose run home had no settings.json of its own, and is passed no server list when no flight config resolves (reckon/_worker_fence.py near line 267, called from reckon/_backends.py near line 2383). An unfenced run, a resumed run and a run with an operator-supplied settings file therefore never reach it. So the run record does not copy the flight key: it records anchored_edit as what the launch actually did — true only when the server was registered and Edit and MultiEdit were disallowed in this launch, otherwise false with the reason (unfenced, resumed, operator-settings, no-flight-config). §8 splits the population on that recorded fact, never on the flight key. The field is written where the launch records what it did, beside fenced on the launched-worker record (reckon/crew/dispatch_launch.py near line 2938), so it reaches the run store with every other launch fact.

Done when tests show: with the key false, the seeded settings and argv are byte-identical to the base revision's; with it true, the seeded home registers the server with the run's write roots, the argv disallows Edit and MultiEdit, and the run record carries anchored_edit: true; with it true on an unfenced run and on a resumed run, the record carries false with the matching reason and the argv keeps the built-in tools. Negative control: a test asserting the false-key argv is unchanged must fail if the disallow list is added unconditionally. The flight schema and its generated JSON change together.

§8 — Measure each arm against the run store and decide

Deliverable. Run the arms on comparable work and report. The arms are: local lane baseline (Claude Code built-in edits), local lane with the anchored tool, local lane under omp, codex baseline, codex with the anchored tool offered. Comparable means the same roles and node classes over the same window; the arms run concurrently so the lane's load is shared. A Claude-dialect run belongs to an anchored arm only when its session-start record shows the anchored server's status as connected and it was launched after §10 landed (a deferred tool list can omit a connected server's tools, so the server status is the fact read, not the list). A codex stream carries no session-start server status, so a codex run belongs to the anchored arm when its launch record's anchored_edit is true, the condition §5 states for codex: the anchored_edit launch fact alone cannot separate a treated run from one whose tools never reached the worker, as the first local anchored run showed. That fact, like anchored_edit itself, is recorded in the run directory (worker.json and the stream's session-start record), not in the run store, so the measurement query reads each run's directory beside its run-store row. At least 30 implement runs per local arm and 15 per codex arm before any verdict. The coordinator produces that population, not this section's node: it routes ordinary ready work from the project's plans to each arm (--backend omp-local, or a backend with anchored_edit on, or the baselines) over the window, and this section's node is dispatched only once every arm has its count; the node reads the run store and writes the record.

The metrics, each read from the run store or the run's own directory, never from prose: edit failure rate (and, for the codex anchored arm, the share of edits routed through the tool); tool calls per run; cumulative input tokens per run; peak context; output tokens per run; landing rate and corrective redispatch rate. The verdict for each treatment is adopt only when cumulative input per landed node falls by at least 5% against its baseline with no fall in landing rate; otherwise do not adopt, stated as a measured result.

Controls on the query. Positive: run over the baseline local arm by the method of §1, it reproduces an edit failure rate of the same order as §1's 11.2%; and for codex, the edit-failure parser first finds the failure in a recorded stream known to contain a refused patch, so a zero for codex means zero and not an unread field. No such stream exists yet; before the node is dispatched the coordinator records one from a deliberate headless codex run whose apply_patch is given a stale context, and commits it at docs/research/fixtures/codex-refused-patch-stream.jsonl. Negative: the baseline local arm split by run-id parity into two pseudo-arms shows a difference in cumulative input per landed node below the 5% adoption threshold; if it does not, the population is too noisy for a verdict and the record says so instead of giving one.

Done when an evidence record at docs/evidence/archive/workers-spend-fewer-tokens-per-landed-node-landed.html carries the per-arm table, both controls' results, the population sizes, the query that produced it, and the verdict per treatment; and the flight default for anchored_edit per backend is set to what the verdict says. Each treatment the verdict does not adopt is removed in this section: a rejected anchored tool takes reckon/anchored_edit.py, its console script, the anchored_edit key, its dialect branches, its settings-seeder step in reckon/_worker_fence.py, its launched-worker record field in reckon/crew/dispatch_launch.py and its prompt instruction with it, and a grep for anchored_edit over reckon/ then finds nothing; a rejected omp pilot takes the omp dialect, its _HARNESS_HOME entry and the omp-local backend. On a Claude-dialect backend, where the built-in tools can be disallowed, an adopted anchored tool retires Edit and MultiEdit by default rather than leaving both edit paths in place; on codex, whose apply_patch cannot be withdrawn, adoption means the tool stays offered and the record says both paths remain. Two-population check: the record says which direction is the defect for each metric (fewer edit failures and less input are better; a lower landing rate is worse), so a treatment that cuts tokens by failing more nodes reads as a failure.

§9 — The armed suite command names only files pytest can collect

Why. The omp dialect node found it while landing: the armed suite command for a node is built from its fenced write paths by _node_test_files (reckon/crew/promotion_records.py near line 526), which reuses the dispatcher's is_test_path (reckon/crew/node.py near line 1018). That rule counts every path under a tests directory as a test, so a data fixture such as tests/fixtures/omp-stream.jsonl is passed to pytest as an argument. pytest cannot collect it and exits 4, which the arm reader takes as collected_no_test; a command naming only the collectible files is refused instead as command_matches_suite_command. So any node that writes a fixture under tests/ cannot be promoted, whichever way its arms are run. The omp node worked around it by moving its fixture under docs/research/fixtures/, which leaves the defect for the next node.

Deliverable. _node_test_files keeps is_test_path as the dispatcher's trigger (a node writing a fixture is still writing part of a check) but passes to the suite command only the paths pytest collects as tests. This repository declares no python_files in its pytest configuration, so pytest's defaults apply: test_*.py and *_test.py. The dispatcher's broader pattern (_TEST_FILE_RE) is not the rule here, because it also admits *.test.py and *.spec.py, which pytest does not collect; a bare .py rule would pass tests/conftest.py or a helper module. pytest exits 5 on either, and the arm reader counts exits 4 and 5 alike as collected_no_test. The rule lives in one predicate beside is_test_path and is used by every consumer that turns write or changed paths into pytest arguments: _node_test_files, and _landing_test_files (reckon/crew/queue_landing.py near line 996), whose fallback over the delivery's changed paths would otherwise re-admit the fixture when the narrowed list is empty. The worker-facing sentence that defines the placeholder, _suite_gate_prompt_body (reckon/crew/dispatch.py near line 1510), states the same narrowed rule, because a worker resolves {node_test_files} from that sentence and promotion compares its recorded command with the resolver's. Honouring a project's own python_files declaration is not part of this section. The armed command a run records, the command each arm is compared against, and _scoped_suite_command for both revisions all read the same narrowed list, so base and head cannot disagree.

Done when tests in the file that covers promotion_records show: a scope holding tests/test_x.py, tests/fixtures/data.jsonl, tests/conftest.py, tests/helpers.py and tests/x.test.py yields a suite command naming only tests/test_x.py; a scope holding only a fixture under tests/ yields a command naming no node test file (the project's declared census tests still appear, as they do for any node writing product paths) and never hands the fixture to pytest, and _landing_test_files given that scope and a delivery that changed only the fixture names nothing either; is_test_path still returns true for the fixture, so the negative-control requirement at dispatch is unchanged; and the run record's armed command and the compared command agree for a run whose scope holds both. Negative control: with the narrowing removed, the mixed-scope test must fail by naming the fixture. Ruff check and ruff format --check add no findings on the staged paths.

§10 — A Claude-dialect anchored worker is offered and told to use the tool

Why. The first A/B run that genuinely carried the anchored treatment on the local lane (r-20261111T130138944743-ab2-clive-anchored-a-gate-halts-s4, DeepSeek V4.1 Flash, run record anchored_edit: true) never called the anchored tools: 93 Bash calls, 4 Write, one Edit refused because the arm disallows it, and zero read_anchored or edit_anchored. Its session-start record lists reckon-anchored-edit with status pending and none of its tools among the 42 offered; the server takes 5.5 to 6.3 s to answer initialize (measured from a cold process on this node). And unlike the codex arm (§5), the Claude-dialect prompt never names the tool. So the worker edited through the shell, and the arm measured 'no edit tool' rather than 'anchored edits'. Startup time may not be the only cause: every MCP server but one was pending in that record, and the run's one ToolSearch reported total_deferred_tools: 39, a count without membership, so deferral of MCP tools behind a search is not excluded either; which mechanism applies is for the node to establish.

Deliverable. Two changes, both made in the launch step that seeds the anchored server for a Claude-dialect run (§4), so they follow what the launch actually did rather than the flight key: a run whose launch seeds no server (unfenced, operator settings, or a resume) gets neither. Where the prompt is composed before that launch step exists, the instruction moves to the launch step rather than being keyed on the flight key, which would tell such a run to use a tool it does not have. (1) the anchored tools are offered at session start, by giving the launch enough MCP startup time for the server to connect before the first turn (Claude Code reads MCP_TIMEOUT in milliseconds from the environment), or by making the server start faster, whichever the node measures to work; (2) that same launch step adds to the worker's prompt an instruction naming the anchored tools, as §5's prompt does for codex, including how to reach them if the harness defers MCP tools.

Done when the node first establishes which mechanism hides the tools, by running a headless Claude Code session (through clive, against a scratch worktree) with the anchored server registered and recording its session-start mcp_servers status and tool list, then the same with its fix applied; both records are kept as gate logs. The fixed session counts as offering the tools when the anchored server's session-start status is connected and either its tools are in the session-start tool list or a ToolSearch for them in that session returns them; the session's transcript is kept beside the record. The unfixed session must fail that criterion; if it passes, the tools were already offered, so the node ships no startup change and reports what else kept the cited run's tools from being offered, while the prompt instruction ships either way, because the missing instruction is an independent cause. A test shows that a Claude-dialect launch which seeds the anchored server carries the instruction and the node's fix, asserted at the layer the fix lives in (the launch environment for a startup allowance, the server's measured initialize time for a faster start, the prompt for a search route), and that a launch seeding no server carries neither; and, dispatched by the coordinator after the node lands, one clive-anchored implement run's session-start record lists the anchored tools as connected and its stream shows edit_anchored calls and no file that existed at the run's base is changed through Bash or Write (a Write may only create a new file); the section closes only on that run. Negative control: with the instruction removed from the launch step that seeds the server, that test's instruction assertion must fail; and when a startup change ships, with that change removed, its fix assertion must fail.

§ Decisions

How far does oh-my-pi go: replace the crew harness, run as one more worker program, or not at all?

The two systems mostly sit at different layers: oh-my-pi is an agent program, the crew harness is the control plane above whichever programs run. Replacing the harness would discard durability across process death, subscription-window pacing, SLURM placement, write fences and landing checks, none of which oh-my-pi provides. Its token claims are cuts in output tokens, which are about 0.5% of our spend, so the pilot is measured on input per landed node. The lead asked for the pilot on 2026-11-10.
