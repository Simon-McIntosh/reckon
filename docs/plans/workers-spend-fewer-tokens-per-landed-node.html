§1 — Why: where a worker's tokens go, measured

A comparison of the crew harness with the oh-my-pi agent program (omp, a fork of Mario Zechner's pi) asked whether its reported token efficiency is worth adopting. The headline figures it publishes — 61% fewer output tokens on Grok 4 Fast, about half on Opus in a third-party measurement — come from its line-anchored edit format, which removes the retry loop a model enters when its retyped old_string does not match the file. Those are cuts in output tokens. The run store says our spend is almost all input.

Measured on 10 November 2026 from a copy of ~/.config/reckon/crew/run_store.db, every run completed since 10 October, reading budget.tokens.input_tokens_cumulative and output_tokens_cumulative from run_details:

So halving output tokens moves total spend by about a quarter of one percent. What a better edit tool can still buy is fewer turns: every failed edit costs a re-read and a retry at a context of 130 to 190 thousand tokens, and on the local lane re-prefilling evicted prefixes is what limits throughput (the cache-residency measurement recorded 18,863 of 22,557 prefill tokens per second spent recomputing prefixes the engine had already built).

An edit census over 58 randomly sampled local-lane implement runs since 25 October (Claude Code driving DeepSeek V4.1 Flash) found 168 failed edits in 1,495 edit calls, 11.2%, about three per run, against about 120 tool calls per run. The commonest refusals were String to replace not found in file (50), InputValidationError on Edit (32), File does not exist (34) and a no-op old_string equal to new_string (25). The same census over 60 codex implement runs counted 594 file_change items and zero failures, which is not believable as a measurement: codex reports a failed patch somewhere that census did not read, so the codex edit failure rate is unmeasured, not zero.

The expected size of the edit-tool effect on the local lane is therefore a few percent of input tokens per run, not half. That is still worth having on the highest-volume lane, but it has to be measured, and the measurement is what decides adoption.

§3 — A line-anchored edit tool ships with reckon

Deliverable. A new module reckon/anchored_edit.py, an MCP stdio server built on the mcp package reckon already depends on, plus a console script reckon-anchored-edit declared in pyproject.toml so a worker's harness can start it by name. Tests in tests/test_anchored_edit.py. The prototype at §2 is the starting shape; the module is product code and owes what the prototype skipped:

  • Anchors. N:HHH, or a bare HHH when exactly one line in the file carries that hash. An ambiguous bare hash, a malformed anchor, or a line number out of range is a refusal naming the accepted format, never an exception.
  • Atomicity. Every anchor in a call is verified before any byte is written; overlapping edits are refused; the file is replaced atomically (written beside the target and renamed), preserving its mode, its line-ending convention and whether it ends in a newline.
  • Confinement. An MCP server runs outside codex's command sandbox, so the server must enforce its own write roots: it refuses any path that resolves (after symlinks) outside the roots it was started with, given as repeated --root arguments. With no root it refuses every write. This is the property that makes it safe to offer a fenced worker.
  • Refusals that save a turn. A stale anchor returns the current anchored lines around each stale line, so the model can retry without re-reading the file; a successful edit returns the changed region with fresh anchors.
  • Reads. read_anchored(path, offset, limit) with a default limit that keeps a call under about 400 lines; files larger than the limit say how many lines remain.

Done when tests/test_anchored_edit.py passes and covers: a replace, both inserts and a delete by anchor; a unique bare hash accepted and an ambiguous one refused; a stale anchor refusing the whole call with the file byte-identical afterwards; overlapping edits refused; CRLF and missing-final-newline files round-tripping unchanged outside the edited lines; a path outside every --root, including through a symlink, refused with the file untouched; and one test that starts the console script over stdio and completes a read and an edit through the MCP protocol. Negative control: with the confinement check removed, the symlink-escape test must fail; with hash verification removed, the stale-anchor test must fail. uv run ruff check and uv run ruff format --check on the staged paths add no findings.

§4 — Claude-dialect workers can be given the anchored tool

Deliverable. A per-backend flight key, anchored_edit (default false), read where a run home is seeded (reckon/_worker_fence.py, beside _seed_worker_mcp_settings) and where the Claude argv is composed (_ClaudeDialect in reckon/_backends.py; _CliveDialect inherits it). When true for a run's backend: the run home registers the reckon-anchored-edit server with --root set to the run's write roots (the same roots fenced_write_roots computes), its two tools are allowed, and the built-in Edit and MultiEdit tools are disallowed so the run is a clean treatment arm. Write stays, because creating a file has no anchor to address. The run record carries anchored_edit: true so §8 can split the population by arm without inference.

Done when tests show: with the key false, the seeded settings and argv are byte-identical to the base revision's; with it true, the seeded home registers the server with the run's write roots, the argv disallows Edit and MultiEdit, and the run record carries the flag. Negative control: a test asserting the false-key argv is unchanged must fail if the disallow list is added unconditionally. The flight schema and its generated JSON change together.

§5 — Codex workers can be given the anchored tool

Deliverable. The same anchored_edit key honoured by _CodexDialect: the run's own codex home (CODEX_HOME, seeded per run by the fence) gets an mcp_servers.anchored entry starting reckon-anchored-edit with the run's write roots and default_tools_approval_mode = "approve", which §2 found is the only setting under which a headless codex will call the tool at all. Codex cannot be told to stop using its own apply_patch, so this arm offers the tool rather than forcing it; the brief composed for a run with the key on says to prefer it. The run record carries the flag, and the codex stream parser counts edits made through the tool separately from file_change items, so §8 can report what share of edits each arm actually routed through it.

Done when tests show the seeded codex config with and without the key (unchanged without it), the stream parser separating anchored-tool calls from file_change items on a recorded stream fixture, and the flag on the run record. Negative control: the parser test must fail if anchored-tool calls are counted as file_change. Never write the user's own ~/.codex/config.toml; the per-run home is the only target.

§6 — Find the headless contract oh-my-pi offers a worker

Deliverable. An investigation, not an integration. The coordinator installs a pinned oh-my-pi into an isolated prefix before dispatch (version 18.13.2, published 27 October, the newest release at least two weeks old on the day this was written, with the bun it requires); the node reads that install and answers, each with a command and its output recorded:

  • Which non-interactive mode emits a machine-readable event stream (omp -p with a JSON output mode, or omp --mode rpc), and what one tool call, one tool result, one final message and a token-usage record look like in it.
  • How a run is resumed by id, and whether a resumed run keeps its transcript.
  • How to point it at the local lane's OpenAI-compatible endpoint through models.yml, and one trivial completed prompt against that endpoint.
  • How to turn off, per run, its own subagent fan-out (task), browser, desktop-control and web tools, and its loading of project MCP configuration — a worker that fans out inside itself bypasses the run ledger, so these are requirements rather than preferences.
  • Which home directory it writes (~/.omp by default) and whether an environment variable relocates it, so the fence can give each run its own.

Done when a note at ~/.config/reckon/crew/reports/reckon/omp-headless-contract.md answers every item above with the command and output that settles it, marks any item it could not settle as unsettled with the reason, and includes a recorded event-stream sample of at least one tool call as a test fixture candidate. The node writes no product code.

§7 — oh-my-pi runs as a crew worker backend on the local lane

Deliverable. An omp dialect registered in _DIALECTS (reckon/_backends.py), built on what §6 settled: argv composition for the headless mode, a stream parser that produces the same run-detail fields the Claude and codex parsers produce (token usage, tool calls, failures, final message), resume, a per-run home under the fence, the fan-out and browser tools disabled, project MCP off, and the anchored edit tool not offered — omp's own anchored edit is the thing being piloted. A host-layer flight backend named omp-local pointing at the same endpoint the clive backend uses, with placement copied from clive.

Done when parser tests pass on §6's recorded fixture; argv tests show each disabled tool; and one real read-only investigate node dispatched with --set backend=omp-local completes, writes its manifest, and its run record carries non-null input and output token totals. Positive control for the parser: the same token-summing code reports non-zero totals for a known-healthy recorded stream before it is trusted on a new one. A stream format this parser does not recognise is a refusal, never a run read as empty.

§8 — Measure each arm against the run store and decide

Deliverable. Run the arms on comparable work and report. The arms are: local lane baseline (Claude Code built-in edits), local lane with the anchored tool, local lane under omp, codex baseline, codex with the anchored tool offered. Comparable means the same roles and node classes over the same window; the arms run concurrently so the lane's load is shared. At least 30 implement runs per local arm and 15 per codex arm before any verdict.

The metrics, each read from the run store, never from prose: edit failure rate (and, for the codex anchored arm, the share of edits routed through the tool); tool calls per run; cumulative input tokens per run; peak context; output tokens per run; landing rate and corrective redispatch rate. The verdict for each treatment is adopt only when cumulative input per landed node falls by at least 5% against its baseline with no fall in landing rate; otherwise do not adopt, stated as a measured result.

Done when an evidence record at docs/evidence/archive/workers-spend-fewer-tokens-per-landed-node-landed.html carries the per-arm table, the population sizes, the query that produced it, and the verdict per treatment; and the flight default for anchored_edit per backend is set to what the verdict says. Two-population check: the record says which direction is the defect for each metric (fewer edit failures and less input are better; a lower landing rate is worse), so a treatment that cuts tokens by failing more nodes reads as a failure.

§ Decisions

How far does oh-my-pi go: replace the crew harness, run as one more worker program, or not at all?

The two systems mostly sit at different layers: oh-my-pi is an agent program, the crew harness is the control plane above whichever programs run. Replacing the harness would discard durability across process death, subscription-window pacing, SLURM placement, write fences and landing checks, none of which oh-my-pi provides. Its token claims are cuts in output tokens, which are about 0.5% of our spend, so the pilot is measured on input per landed node. The lead asked for the pilot on 2026-11-10.
