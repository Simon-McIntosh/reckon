§1 — Two clocks are published and nothing reads them

The metered provider publishes its own pace on the stream of every served run that carries a rate-limit event: unifiedWindows.five_hour and unifiedWindows.seven_day, each with a utilization and a resetsAt. Reckon reads neither. Its budget fence consults a single ceiling, so a wave may legitimately spend most of a five-hour window in one hour and the fence stays silent until the window is nearly gone.

What the pace is for. The five-hour window is not self-pacing and is not meant to be the policy. The policy is: keep the weekly burn a little above linear, end the week with the subscription drained, and never drain it on Monday. The free lane absorbs whatever the window will not admit. Stated that way, the window is not a fence at all — it is the threshold that decides which lane a node goes to.

§2 — The pace function, on two clocks

The five-hour allowance is derived from the week, not configured. A fixed five-hour cap cannot react to load: it is either too tight on a quiet Tuesday or too loose on a busy Monday, and it never learns. The derivation is self-correcting, so it needs no gain term: its two tunables are the drain deadline and a single pace multiple, and neither is a gain on the error.

Let D be the drain deadline — the point the subscription should be spent, a configured lead time before the weekly reset (12 h, so the week ends drained rather than exhausted mid-Sunday-night with work still queued). Then for a declared budget group:

remaining_budget  = 1 - utilisation
remaining_windows = (D - elapsed) / 5h

allowance_5h      = remaining_budget / remaining_windows

That single line is the whole governor. Spend heavily now and remaining_budget falls while remaining_windows falls more slowly, so the next window's allowance shrinks. Spend nothing and it grows. It converges on exhausting the budget exactly at D from any starting position, and it needs no memory of how the week has gone — the two figures already carry it.

The best five-hour estimate to start the week with is the fixed point of that formula, which is simply the nominal share: 5 / D. At D = 156 h that is 3.205% of the weekly budget per five-hour window, over 31.2 windows — 3.526% once the multiple is applied, which is the figure the on-pace case asserts against.

The pace multiple sits on top of that, and it is why the week ends drained rather than merely spent. Locked at a single value of 1.1 applied to both clocks, it is the deliberate bias above linear that §1 states as the policy, kept separate from the deadline because the two answer different questions: the deadline says when the budget should be gone, the multiple says how hard to lean into it on the way. So a group exactly on pace returns the multiple times nominal, and that equality — not the bare nominal share — is the consistency check the implementation asserts rather than a number to hardcode.

§3 — A rising bar, not a switch

Lane choice is not metered-or-local by category. Each node gets an open-endedness score from what dispatch already knows, and the metered lane admits it only when the score clears a bar that rises as the windows fill.

The third input is the one with evidence behind it: prescription completeness is what the local pilots showed makes a node viable on the free lane, and reckon/crew/prescription.py already computes it. The bar is a continuous function of window state — from zero when the account is behind pace and the window is empty, to admitting only verification bookends and resumes when the five-hour ceiling is reached.

The bar recommends; it never routes. That is the same advise-never-force contract this project already holds for lanes, and it is what makes the continuous shape workable: a score a hair under the bar is not a verdict, it is a close call an orchestrator should see. So the bar reports a position and a recommendation drawn from three outcomes, not two:

  • Send it metered. The node clears the bar, and the window has the room.
  • Send it local. The node sits below the bar because it is prescribed enough that the free lane will execute it as specified. A prescribed node is never held at any window fill — that is the whole point of having a free lane, and it is the assertion that keeps this outcome from collapsing into the one below it.
  • Split it. The node is near the bar because it is carrying more than one deliverable. Two smaller nodes both clear it, and both dispatch now — the cheapest of the four outcomes and the one a binary switch cannot express.
  • Hold it. The node is open-ended enough that it is better left undispatched than sent to the free lane to be done badly. An unmetered lane makes a bad node cheap, not good, and a wrong answer that cost nothing still has to be found and undone. Hold is a property of the node, never of the window.

The recommendation also moves as the subscription burns: the same node is a send early in a drained week and a hold late in a spent one, which is the coupling to §2 and the reason the bar is a function of window state rather than of the node alone.

§4 — Reserve the bookends, or the repairs starve

A local repair is verified by a short metered review. Those verifications are small, and they are exactly what an audit wave starves: today a pilot's bookend had to wait for a window reset because the wave ahead of it had eaten the window.

So a fraction of each five-hour window is reserved for review and verify roles and is not available to implementation work at any bar. A reserve that only applies when the window is nearly full is not a reserve; it holds from the start of the window.

§5 — Reading the windows without inventing them

Most runs do not carry the windows, and this is the correction that shapes the reader. Measured over the 400 newest streams on this workstation: 54 carry unifiedWindows and 346 do not. The local lane carries them on none of its 28, which is correct — it is unmetered. So "read the newest event" must mean the newest event that carries a window, and a reading is normally minutes to hours old rather than current.

Three rules follow, and each exists because its opposite has already been observed:

  • Read from a served run's stream, not from an account surface. The account read fails on one side with the binary absent from the server's PATH and on the other with a 403.
  • Carry the age with the figure. A window utilisation with no observation time cannot be distinguished from a current one, and the five-hour clock rolls over.
  • Never read unknown as either full or empty. Absence of a signal is not exhaustion — that rule already holds in the budget fence and must not be weakened here — and it is equally not headroom.

§5b.i — A stale reading is re-queried, and a failed re-query says so

The mechanism landed as reckon/crew/staleness.py (commit 0fc81fc). A reading observed inside its configured shelf life is returned as a position without touching the probe, so the re-query is not unconditional and a live figure is never disturbed. A reading past its shelf life — or one carrying no observation time to age it — asks the lane's probe for a fresh figure, and the probe's figure is what the caller reports. The shelf life is the flight key budget.evidence_shelf_life_minutes, the same key the budget fence already reads, so the two agree about when evidence stops speaking for now.

A re-query that cannot answer does not erase the reading and does not invent one. A probe that raises, or that answers with no figure, has not answered: the old figure is returned with the age that disqualifies it and a serving state of unknown, so a caller can neither mistake it for a current figure nor read a failed probe as full or as nothing. That is the plan's asymmetry stated operationally — absence of a signal is not exhaustion, and it is equally not headroom.

§8 — The pattern that is not blocked

The dispatch pattern that never meets a hold falls out of the two sections above, and it is the shape this workstation drifted into by accident today:

A pattern whose metered demand never exceeds its reserve cannot be blocked by construction.
  • Implementation runs local as prescribed nodes. One artifact, file and line named, a numeric gate with its before value, a literal control mutation, a thirty-minute fence. The lane ceiling is 64 and the binding constraint has been bookkeeping, not capacity.
  • Metered implementation opens only when the week is behind. That is §3's bar driven by §2's allowance: behind and late, the bar drops and open-ended work flows metered; ahead and early, it rises and everything prescribable goes local.
  • Width comes from more nodes, never larger ones. Node width is a capacity property — an over-large node cannot run beside its siblings and consumes the pool that would have carried them.

The steady state is local wide, metered narrow and reserved. It is unblocked because it never asks the metered lane for more than the reserve guarantees, and the governor only ever widens that ask when the evidence says the week is underspent.

§9 — The log that lets someone else tune this

§ Decisions

What is the default pace multiple, and is it one value or one per window?

One multiple, default 1.1, applied to both clocks. This adds a second tunable beside the drain deadline rather than folding the above-linear bias into D alone, and it is the lead's call: the lead time and the bias answer different questions, so collapsing them would mean moving the deadline whenever the bias should move. Two consequences must be carried into the implementation rather than discovered. The on-pace case no longer returns exactly the nominal share, so the self-consistency assertion becomes on-pace returns the multiple times nominal, and the equality is still what proves the formula rather than a number to hardcode. And the multiple is a flight key like the lead time, asserted by changing it and requiring the allowance to move, so 1.1 is data rather than a constant in the code. The lead also asks that burn be logged so the multiple can be tuned over a longer period than one week: that is section 9, whose rows must therefore carry the multiple in force at the time of each dispatch, since a log that cannot say what setting produced a curve cannot tune that setting.

How does the bar rise between an empty window and the ceiling?

Continuous in the window figure, so there is no cliff at which one node routes metered and the next local. The lead's requirement that comes with it changes what the bar is for, and it is not a detail of shape: the bar must leave room for orchestrator judgement rather than resolve a lane by itself. Three outcomes, not two. A node may be hard enough that it is better left undispatched than sent to the free lane; a node may be close enough to the bar that the right move is to split it into two smaller nodes and dispatch both now; and the orchestrator must be able to decide against the bar in either direction. So the bar reports a position and a recommendation and never a routing, which is the same advisory-never-force contract this project already holds for lanes. Continuity also has a cost that must be paid rather than ignored: there is no tier name for a pre-flight line to print and no natural transition to assert, so section 6's pre-flight prints the figure and the recommendation, and section 3's tests assert monotonicity over the window domain and the three outcomes at their boundaries, rather than asserting transitions that a continuous bar does not have.
