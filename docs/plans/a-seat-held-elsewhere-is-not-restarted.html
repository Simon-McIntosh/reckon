§2 — A producer finding a foreign seat waits instead of exiting

Deliverable. When reckon crew watch finds the project's seat held by a live producer on another host, it stays up and re-reads the seat at a bounded interval, taking the seat when that producer's stream goes stale, instead of exiting into the unit's restart. The foreign-seat judgement is seat_names_a_live_foreign_producer in reckon/crew/watch_unit.py, the composite of _seat_names_a_foreign_host and _seat_stream_fresh that the obligation snapshot producer already reads (reckon/crew/obligation_snapshot.py, _foreign_seat_is_live). The watch calls it rather than composing the two primitives again, so the watch and the snapshot producer share one judgement. The unit's restart policy stays as it is, because a crash should still restart it. Reporting a cycling unit is §5's deliverable.

Done when a test gives the watch a seat naming another host with a fresh stream and finds the process still running after three re-read intervals, having written no restart; with the stream made stale it takes the seat. The watch test files show no added failure against base. Negative control: with the wait removed, the first test must see the process exit 0.

§4 — Every attached session's snapshot is published, whichever host it attaches from

Deliverable. The seated producer publishes an obligations snapshot for every coordinator session with a registered follower in the project, whichever host the follower runs on, and the hook on any host reads it through the same foreign-seat judgement as §2. If §3 finds a different cause, this section is rewritten to that cause before it is dispatched.

Done when a test registers followers for two sessions on two hosts against one producer and finds a fresh snapshot for each, and the hook on the second host prints the checklist rather than "no producer". Negative control: with publication restricted to the producer's host, the second session's hook must print "no producer".

Where the fix goes, from §3. §3 confirmed this section's premise and located it: the producer selects the sessions it publishes from follower rows that read live, and live asks the producer host's own process table about the follower's recorded pids, so a registration made on another host reads registered and gone (evidence). The same reading, through runs.follower_state, decides whether the watch's review reflex dispatches a review for a session's run (reckon/crew/recovery_watch.py), so the review reflex is lost to the same sessions. On 2026-10-13 a delivered investigation of session f653840f, whose follower runs on a different node from the producer, had no reflex review after eight minutes and was reviewed only by hand. The change is therefore made once, where liveness is read: a registration made on another host is not judged gone from this host's process table. That needs a fact the record does not carry yet. reckon/crew/follower_registration.py writes the project, session, pids, delivery, scope and start time, but no host. So the registration gains the host it was written on, spelled as the producer seat spells its own (runs._seat_host), and a registration naming another host is never put to this host's process table. How such a registration's liveness is judged instead, for example from a stamp the follower refreshes, is this section's to settle. The precedent is watch_observer_alive in reckon/crew/runs.py, which already returns unknown rather than dead for a watcher registration naming another host. The follower rule follows the same shape and does not settle the question a second way. Both consumers read the result, and neither gains a second liveness rule of its own. Six readers share this value, not two. _follower_liveness in reckon/crew/follower_registration.py is the single reader, and its live value is read by: the obligation producer (runs.py, the snapshot selection); project_watch_visibility (runs.py); watch_state (watch_unit.py), whose attached reading feeds dispatch admission; _foreign_live_follower (session_host.py), which decides whether a follower this host did not start holds the session's pair; the peer-delivery listing (dispatch_watch.py); and the review reflex (recovery_watch.py). Two of these are guards. The manifest names each reader and what it reads for a foreign registration before and after the change. A guard whose new answer would be wrong is reported as a blocker, not changed, because this section's write scope does not include those modules. Done when, in addition to the above: the same two-host fixture finds the review reflex dispatching a review for a scoring run whose session's follower is on the second host. Negative control: with liveness read from the local process table again, the reflex reports that run as awaiting its coordinator.

§5 — A cycling unit is reported as cycling

Deliverable. reckon crew watch --ensure reads the unit's restart count twice, ten seconds apart. That interval is longer than the 6.7 s restart period measured in §1, so a unit cycling at that rate restarts at least once between the readings and cannot read the same count on both. The interval is one named constant, and the test injects the sleeper rather than waiting it out. The count is read by SystemdUserUnitManager in reckon/service.py, the per-unit query surface. Other modules still call service.systemctl directly, but unit state belongs on the manager. It reads the count through a unit-property reader added beside its active(). ensure_watcher_service reaches it through the manager seam it already takes, so the watch module does not become a second systemd client and the existing watch tests can supply a fake manager. When the count rises between the readings, it reports the unit as cycling, not healthy, with both readings. On 2026-10-13 it reported "already active on an unchanged unit; started nothing" for a unit that had restarted 2,376 times. This is independent of §2: it makes visible any cycle faster than the sampling interval, whatever its cause, and that covers the 6.7 s cycle measured once in §1. A unit restarting more slowly than every ten seconds can read the same count on both readings and is not caught. This section does not claim that case.

Done when a test gives --ensure a unit whose restart count rises between its two readings and finds it reported as cycling with both counts, while a unit whose count holds is reported as before. The unit test files show no added failure against base. Negative control: with only one reading taken, the rising unit must read as healthy, reproducing 2026-10-13.

The seat was held on another host, and unwatch refuses a seat it does not hold. Sessions were told to run a command their own tool refuses, and reported that reckon was blocking them.

A seat on this host keeps the cycle command. §7 — A worker writing its first status on another host is not drawn halted

Why. On 2026-10-14 the project's producer ran on clu-2018 while this session and its workers ran on clu-2002. The run r-20261014T190832327112-a-lift-is-drawn-once-per-pane was dispatched at 19:09Z. Its stream rows read working at 19:09:37Z, running with recovery classification unwritten and advice resume at 19:10:59Z, and working again at 19:11:04Z, when the worker replaced its orientation write with a status. The pane drew the middle row as working → halted. The worker had been alive throughout: its pid was running on clu-2002 and its stream was growing. The project stream holds 11 working → running rows between 10:25Z on 13 October and 19:11Z on 14 October, and every one carries recovery classification unwritten.

Where the fault is. A run whose manifest holds only its orientation write is spared unwritten by _orientation_write_of_a_run_in_motion in reckon/crew/recovery_liveness.py. That function returns early unless the pointer's liveness is True. A producer on another host cannot query the worker's pid, so it answers unknown (None), and the exemption is never reached. Until the worker writes its first status, the run reads unwritten and its reader is told to resume work that is in flight. The registry keeps such a run in running, so nothing is resumed automatically; the harm is a false halted row and wrong advice.

Deliverable. When the pointer's liveness is unknown because the run was launched on another host, the exemption is decided by the run's stream instead. A newest stream that carries an assistant record (_newest_stream_shows_work) and was written within the stall window the stall clock already applies is a run in motion, and keeps its classification. A pointer whose liveness is False still reads unwritten, because a dead process left its stub behind. A pointer whose liveness is True is decided as before. No second stall window is introduced.

Done when a test, with the crew home pointed at a temporary directory, gives the classifier a run launched on another host, whose pointer liveness reads unknown, whose manifest holds only its orientation write, and whose newest stream holds an assistant record written inside the stall window. The run's recovery classification is its classification and not unwritten. With that stream's last write moved past the stall window, it reads unwritten. A run on this host whose pid is gone reads unwritten as before. The real crew home is untouched. The test files that import reckon/crew/recovery_liveness.py show no added failure against base. For the negative control, restore the early return for any liveness other than True: the first case must then read unwritten. The control is logged under the run directory. Write paths: reckon/crew/recovery_liveness.py and tests/test_a_worker_on_another_host_is_not_unwritten.py.
