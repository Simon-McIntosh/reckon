§8 — A follower on another node is judged by a lease it renews

Why. At 14:01Z on 2026-10-15 the obligations hook in a session on clu-2002 printed "no producer; run reckon crew watch --ensure --project reckon" on every turn. The reckon producer was healthy. It was pid 960706, a reckon-watch-reckon.service unit on clu-2018, seated since 2026-10-13T19:37Z. Its seat lock carried the current source's code stamp, its log showed reloads completing, its lease was renewed at 13:59:56Z, and its event stream was written within the minute. Even so, no obligations snapshot had been written for any reckon session since 2026-10-08T00:06Z. Over the same period, every project whose producer runs on the same node as its sessions (imas-ambix, imas-codex, imas-efit, power_convertor) had snapshots from the last minute. All four live reckon followers are registered from clu-2002.

Where the fault is. §4 records the host on each follower registration and judges a registration from another host by its advisory lock. Its premise is that the lock is the one fact that crosses the shared home. On this home it does not. The filesystem is GPFS (HPC_T2), and flock there is node-local. At 14:05Z a non-blocking shared flock probe from clu-2002 was granted against the seat lock that pid 960706 holds on clu-2018. A lock held on one node therefore reads free on every other node. The producer on clu-2018 reads every clu-2002 follower as gone, so it publishes no snapshot for those sessions and dispatches no reflex review for their runs. For example, run r-20261015T125110840273-the-review-reflex-asks-before-it-requeues delivered at 13:56:36Z. Its review was launched from clu-2002 at 14:01:28Z, a minute after this session ran --ensure there, and not by the seated producer. §4's tests passed because they model both hosts inside one kernel, where flock is shared.

Deliverable. A follower registration that names another host is judged by a lease the follower renews in a lease file beside its registration, not by its lock. The follower already renews the producer's lease on each wait pass (runs.renew_producer_lease, called from reckon/crew_follow_commands.py). On that same pass it writes a renewal time into a lease file beside its registration. The renewal cannot go in the registration itself. The registration is rewritten in place (_write_watch_record truncates, then writes) precisely so that it keeps the inode the follower holds its flock on. A rename would replace that inode, and a reader on the follower's own node would then find the lock free and read a live follower as gone. In-place writes, on the other hand, can be read half-written by another node, which cannot take the lock to serialise against them. So the registration and its lock are left untouched, and the lease is a separate file, replaced atomically with a temporary file and a rename in the same directory. A reader on another node then sees the old lease or the new one, never an empty one. A reader that still finds the lease empty or unparseable reads it once more before judging it. A registration from another host reads live when its renewal falls within the lease window. It reads gone when the renewal is older than the window or is missing. The window is the producer's own (producer_lease_seconds), not a second number. A registration from this host keeps its lock and pid probes. For a registration from another host the lease decides the whole verdict, not only live. The lock is node-local, so it says nothing there: registered and released come from the lease too. A fresh lease reads registered, live and not released; a stale or missing one reads gone. Otherwise a live follower on another node would still read released: True through watch_unit.watch_state into session_follower_released, which the dispatch admission in reckon/crew/dispatch_watch.py reads. _follower_liveness in reckon/crew/follower_registration.py stays the single reader, so the snapshot sweep, the review reflex, the dispatch admission and its other readers take the corrected verdict without a rule of their own.

§13 — A stop during a reload says the producer is reloading

Why. At about 14:45Z on 2026-10-15 the stop hook in nova session s21-nova printed "reckon obligations … are not current: the producer is running older code than the checkout; run reckon crew watch --ensure --project nova". Nova's producer was healthy. It runs on srv-1006, and its log shows it reloading after each merge into reckon/; four such merges landed between 14:02Z and 14:31Z. Earlier, at about 13:40Z, the same producer logged "deferred its reload: tracked files are modified against HEAD (M reckon/crew_dispatch_commands.py); keeping the current image, retrying when the tree is clean". So it kept the old image on purpose while a session had an uncommitted source edit in the main checkout. In neither case can --ensure help. A reload completes by itself, and a deferral ends only when the tree is clean.

Where the fault is. The prompt path in reckon/hooks/coordinator_obligations.py sends a stale reading through obligation_snapshot.reload_in_progress, which treats a stale code stamp as a reload still catching up. The stop path does not. When the snapshot is not fresh and the inline derivation runs out of its budget, it prints not_fresh_line directly, so every session that stops inside a reload window is given the --ensure remedy. A deferred reload is written only to the producer's log (reckon/crew_follow_commands.py), so neither path can say that the producer is waiting on a clean tree, or which file it is waiting on.

Deliverable. The stop path asks reload_in_progress exactly as the prompt path does. A reload in progress prints the prompt path's reload wording and offers no command. The producer records a deferral on its seat record, with the reason and the paths it named, and clears it when the reload starts. While a deferral is recorded, both paths say the producer is waiting for those files to be committed, and name them, rather than offering --ensure.
