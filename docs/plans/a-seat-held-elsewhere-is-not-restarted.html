§2 — A producer finding a foreign seat waits instead of exiting

Deliverable. When reckon crew watch finds the project's seat held by a live producer on another host, it stays up and re-reads the seat at a bounded interval, taking the seat when that producer's stream goes stale, instead of exiting into the unit's restart. The foreign-seat judgement reuses _seat_names_a_foreign_host and _seat_stream_fresh in reckon/crew/watch_unit.py. The unit's restart policy stays as it is, because a crash should still restart it. Reporting a cycling unit is §5's deliverable.

Done when a test gives the watch a seat naming another host with a fresh stream and finds the process still running after three re-read intervals, having written no restart; with the stream made stale it takes the seat. The watch test files show no added failure against base. Negative control: with the wait removed, the first test must see the process exit 0.

§4 — Every attached session's snapshot is published, whichever host it attaches from

Deliverable. The seated producer publishes an obligations snapshot for every coordinator session with a registered follower in the project, whichever host the follower runs on, and the hook on any host reads it through the same foreign-seat judgement as §2. If §3 finds a different cause, this section is rewritten to that cause before it is dispatched.

Done when a test registers followers for two sessions on two hosts against one producer and finds a fresh snapshot for each, and the hook on the second host prints the checklist rather than "no producer". Negative control: with publication restricted to the producer's host, the second session's hook must print "no producer".

Where the fix goes, from §3. §3 confirmed this section's premise and located it: the producer selects the sessions it publishes from follower rows that read live, and live asks the producer host's own process table about the follower's recorded pids, so a registration made on another host reads registered and gone (evidence). The same reading, through runs.follower_state, decides whether the watch's review reflex dispatches a review for a session's run (reckon/crew/recovery_watch.py), so the review reflex is lost to the same sessions. On 2026-10-13 a delivered investigation of session f653840f, whose follower runs on a different node from the producer, had no reflex review after eight minutes and was reviewed only by hand. The change is therefore made once, where liveness is read: a registration made on another host is not judged gone from this host's process table. That needs a fact the record does not carry yet. reckon/crew/follower_registration.py writes the project, session, pids, delivery, scope and start time, but no host. So the registration gains the host it was written on, spelled as the producer seat spells its own (runs._seat_host), and a registration naming another host is never put to this host's process table. How such a registration's liveness is judged instead, for example from a stamp the follower refreshes, is this section's to settle. Both consumers read the result, and neither gains a second liveness rule of its own. Done when, in addition to the above: the same two-host fixture finds the review reflex dispatching a review for a scoring run whose session's follower is on the second host. Negative control: with liveness read from the local process table again, the reflex reports that run as awaiting its coordinator.

§5 — A cycling unit is reported as cycling

Deliverable. reckon crew watch --ensure reads the unit's restart count twice, a few seconds apart. When the count rises between the readings, it reports the unit as cycling, not healthy, with both readings. On 2026-10-13 it reported "already active on an unchanged unit; started nothing" for a unit that had restarted 2,376 times. This is independent of §2: it is how a cycle of any cause becomes visible.

Done when a test gives --ensure a unit whose restart count rises between its two readings and finds it reported as cycling with both counts, while a unit whose count holds is reported as before. The unit test files show no added failure against base. Negative control: with only one reading taken, the rising unit must read as healthy, reproducing 2026-10-13.

§6 — A stale producer's remedy names what its reader can run

Why. On 2026-10-13 followers on clu-2002 told every session that its producer ran older code, with the remedy reckon crew unwatch --project <p> && reckon crew watch --ensure --project <p>. The seat was held on another host, and unwatch refuses a seat it does not hold. Sessions were told to run a command their own tool refuses, and reported that reckon was blocking them.

What landed. In reckon/crew_follow_commands.py, _follow_watch_lines reads the seat's host through runs.watch_lock_path, runs._read_watch_record, runs._seat_host and runs._seat_names_a_foreign_host. For a seat on another host, _producer_stale_event names that host and says the producer reloads itself when the code changes. The event then carries a host field and no remedy. A seat on this host keeps the cycle command. The work ran as r-20261013T222214371236-stale-producer-remedy-runs-from-here: commit 7ebf0de29, with four tests in tests/test_stale_producer_remedy_runs_from_here.py and a negative control logged under its run directory. Its review was r-20261014T015605522579. The review's blocking finding was a truncated gate log, answered by a serial rerun to a complete log. The change merged as ed650e36b. The §4 defect is unchanged: sessions on the seat-less host still read no producer.
