§1 — One machine, one allocation

Reckon's placement design is already the right one: a reservation held once, published where every session reads it, and every worker run as a step inside it. reckon crew placement --ensure holds it. What has never been done is declaring the placement anywhere that more than one project reads.

The flight configuration has three layers — the shipped defaults, a host layer at ~/.config/reckon/flight.yaml which is not committed and applies to every project on the workstation, and a per-project layer committed in the repository. The placement declared so far has lived in the project layer, which scopes it to one repository. That is the safe choice for a first trial and the wrong shape for the goal: the aim is to move the fleet off the login node, and a per-project declaration solves it for one project at a time out of thirteen.

The arithmetic decides it, and the count is measured rather than assumed: ~/.config/reckon/mounts.json lists thirteen mounted projects on this workstation. Per-project placement means each one that wants off the login node holds an allocation of its own to escape a shared four-core ceiling. At the twenty-eight cores the current allocation carries, a fleet that fits inside one would reserve several hundred. One shared allocation is both cheaper and what the design already describes.

§2 — What the roster must count

On 2026-09-23 a host-global reservation was published while only one project had declared a placement, and forty five runs across four repositories were counted against a ceiling of twenty five while exactly one step ran inside the allocation. Dispatch was refused workstation-wide for four minutes. The cap was right; its population was not.

The repair that landed keyed the reservation record per project — each project reads only its own reservation.json and deliberately does not fall back to the host-global one — and scoped the roster count to the reading project. It removes the asymmetry by shrinking the counted side. It is correct and it is not the end state: under host-layer placement every run reaching the backend is genuinely placed, so the placed-run count and the whole-backend count coincide. They coincide only while that holds, which is why the rule is written on the placed runs rather than on the coincidence. The durable rule is narrower than either: the roster counts the runs that were actually placed, which is true under both arrangements and needs no reasoning about which layer declared what. A pointer already records its placement, so the count can be taken from the fact rather than inferred from the configuration.

So the per-project reservation keying is retired, and this plan owns retiring it. read_reservation currently states that a named project reads only its own record and deliberately does not fall back to the host-global one, because inheriting another project's reservation would place workers into an allocation the project does not own. Under one shared allocation that is no longer a defect — it is the arrangement. A shared reservation has to be readable by a project that did not publish it, so the reservation returns to a single unkeyed record and the guarantee the keying was protecting moves to where it belongs: the roster counts placed runs, so a project is bounded by what it actually placed rather than by who happened to publish the record.

The lane concurrency bound is a separate quantity and deliberately stays cross-project. A served lane is consumed by every caller that sends it a request, placed or not, so its bound has to count them all. An allocation is consumed only by the workers actually running as steps inside it, so its bound counts those and nothing else. That difference is the whole argument for scoping the roster to placed runs.

§3 — Done when

Placement is declared once, in the host layer, and a dispatch from a project that has never heard of it becomes a step in the one reservation. Two dispatches under two different projects reach the same published job id and exactly one allocation is created across the pair — the assertion counts allocations, not placement requests, since both dispatches legitimately request placement — the property a single-project case cannot demonstrate, since it passes just as well against a design holding one reservation per dispatcher. The roster refusal counts placed runs only, asserted over a population on a single backend holding both placed and unplaced runs, so the rule is exercised rather than merely satisfied by a homogeneous population. A project whose runs are not placed is unbounded by the roster.

§ Decisions

Does the workstation hold one shared reservation, or one per project?

The goal is to move the fleet, not one repository at a time. Per-project placement means five repositories hold five allocations, well over a hundred cores, to escape a shared four-core ceiling. One reservation held once with every session placing into it is what the design already describes.

Which command holds the fleet's allocation once it is shared?

Once the reservation is shared it stops being any one project's, so the command that holds it belongs where every project reads it. The project-side holder retires; partition and size become arguments to the ensure command rather than a second implementation of it.
