§1 — One machine, one allocation

Reckon's placement design is already the right one: a reservation held once, published where every session reads it, and every worker run as a step inside it. reckon crew placement --ensure holds it. What has never been done is declaring the placement anywhere that more than one project reads.

The flight configuration has three layers — the shipped defaults, a host layer at ~/.config/reckon/flight.yaml which is not committed and applies to every project on the workstation, and a per-project layer committed in the repository. The placement declared so far has lived in the project layer, which scopes it to one repository. That is the safe choice for a first trial and the wrong shape for the goal: the aim is to move the fleet off the login node, and a per-project declaration solves it one twelfth at a time.

The arithmetic decides it. Per-project placement means every project holds its own allocation to escape a shared four-core ceiling — five repositories, five allocations, well over a hundred cores reserved for a fleet that fits in one. One shared allocation is both cheaper and what the design already describes.

§2 — What the roster must count

On 2026-09-23 a host-global reservation was published while only one project had declared a placement, and forty five runs across four repositories were counted against a ceiling of twenty five while exactly one step ran inside the allocation. Dispatch was refused workstation-wide for four minutes. The cap was right; its population was not.

The repair that landed keyed reservations per project, which removes the asymmetry by shrinking the counted side. It is correct and it is not the end state: under host-layer placement every run on the lane is genuinely placed, so counting them all is right again. The durable rule is narrower than either: the roster counts the runs that were actually placed, which is true under both arrangements and needs no reasoning about which layer declared what. A pointer already records its placement, so the count can be taken from the fact rather than inferred from the configuration.

The lane concurrency bound is a separate quantity and deliberately stays cross-project: a served lane is shared by everything that calls it, whereas an allocation is not.

§3 — Done when

Placement is declared once, in the host layer, and a dispatch from a project that has never heard of it becomes a step in the one reservation. Two dispatches under two different projects reach the same published job id and request one allocation between them — the property a single-project case cannot demonstrate, since it passes just as well against a design holding one reservation per dispatcher. The roster refusal counts placed runs only, asserted with a population mixing placed and unplaced runs on one backend. A project whose runs are not placed is unbounded by the roster.
