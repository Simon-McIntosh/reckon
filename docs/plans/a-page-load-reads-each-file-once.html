§1 — Every page load rediscovered the fleet

Reported on 2026-09-23 as the SPA being unusable: slow to load on nova, reckon, imas-codex and imas-efit, and after switching to imas-efit the project picker listed no other project, so there was no path back. py-spy dump of the server put every request thread in discover_plans. A cProfile of one cold discovery of reckon took 119.6 s and made 7,776 calls to parse_meta for 410 inventory rows. Opening a file on the loaded shared filesystem cost 2.3 ms on average. Six causes compound:

  • The wiring scan is quadratic. build_roadmap calls _unwired_plan_findings, which calls _standalone_reason for each unwired plan, and each call goes through resolve_resource to iter_resources. That walks the whole docs tree and parses every file's meta, so the tree is walked and parsed once per plan. read_plan_record and _authorisation_age resolve slugs the same way.
  • A cache hit still walked the tree. The discovery cache is validated by a signature that ran four recursive globs over the docs tree, plus the same for every project the plans depend on. That took 8 to 11 s for nova, and a warm rediscovery of reckon took 19.8 s.
  • The rollup ran a full-history git log per project. fleet_index._activity30 took 6 to 10 s per repository, serially over 13 mounts, under a 10 s timeout. Its TimeoutExpired was not caught, so one slow repository aborted the whole /_projects/index.json response. That is the empty reply above and the empty project picker: the shell set its project list only after that response and all thirteen /_discover calls had finished.
  • Every page load fetched every project's inventory. The shell fetched /_discover/<p> for all thirteen mounts, although only the fleet home and the command palette read other projects' inventories.
  • The served loader still reads the superseded aggregate. state-loader.js requests state/<project>/index.json with required: true before /_discover. The server intercepts that URL and runs a full discovery to overlay the inventory on the frozen envelope, so each project page transfers its inventory twice. It also puts the persisted projects[] block of a file that the fleet migration superseded into window.STATE. All five projects measured carry the distributed marker.
  • Every response was sent no-store. Figures, stylesheets and compiled scripts were downloaded again on every refresh.

§2 — Discovery reads each file once, and a refresh reads none

The server-side repair is on main at 56e13e11 and has had only a compile check. reckon/file_memo.py memoises parse_meta, the head-meta reader, the readiness-state reader and the standalone declaration against each file's stat identity: device, inode, size, mtime and ctime. resource_scan_scope in reckon/resources.py shares one tree scan for every lookup inside a read-only pass; discover_plans and build_roadmap open it. The cache signature is one os.scandir walk. The served process reuses a walk for RECKON_DISCOVERY_REUSE_S seconds (default 5), dropped on every POST and every change event. The library default is 0, so a direct caller always walks. One discovery per project runs at a time. A change stream settles a burst of events for 0.25 s into one rediscovery, and drops only a cache entry computed before the event. The fleet rollup computes projects concurrently. The activity history is memoised against HEAD, and a git timeout yields an empty series instead of aborting the rollup. Static files revalidate by ETag with Cache-Control: no-cache, and JSON over 64 KiB is gzipped when the client accepts it.

§3 — The served loader reads discovery, not the superseded aggregate

docs/ui/state-loader.js assembles window.STATE from /_discover/<project> alone whenever that endpoint answers. Discovery already carries the inventory, sprints, milestones, blockers, timeline, active sprint, north stars, source format and resource versions for both the distributed and the legacy formats. state/<project>/projection.json is read only when discovery is unreachable, which is the static-build case, and state/<project>/index.json only when both are unavailable. The single project row in window.STATE.projects is synthesised from live counts. It is never taken from a persisted projects[] block while discovery answered.

Done when tests/test_served_loader_reads_discovery_only.py runs the real loader under node with a recording fetch, in the style of tests/test_spa_state_boundary.py. It asserts three cases.

  1. With discovery answering, no URL ending in index.json or projection.json is requested. window.STATE.sprints, active_sprint_id and timeline equal discovery's, and window.STATE.projects[0] carries no field present only in a persisted projects[] block the mock would have served.
  2. With discovery refused at the network level, projection.json is requested and its sprints are used.
  3. With discovery refused and no projection, index.json is requested.

The negative control is executed and logged: restoring the aggregate-first order at the base 56e13e11 makes the first assertion fail. tests/test_spa_state_boundary.py, tests/test_spa_live_arrival.py and tests/test_served_schedule_payload.py pass with zero added failures against the same base. The write paths are docs/ui/state-loader.js and that test.

Outcome — the served loader reads discovery alone. Commit f6529a51 perf(ui): the served loader assembles state from discovery alone asks /_discover/<project> first and, when it answers, reaches no aggregate fetch at all: its inventory, sprints, milestones and north stars are adopted for both layouts, and the single projects[0] row is synthesised from the live counts, so no field of a persisted projects[] block reaches window.STATE. projection.json is read only on a network-level refusal or an explicit 404, and index.json only when projection is also missing. §7 — The fleet rollup answers without walking every tree

The §5 re-measure at 16:23Z on 2026-09-23, at load average 8 to 12, put every /_discover and /crew request under 1.5 s warm. The exception was /_projects/index.json, at 13.6 s warm and 25.2 s cold. A py-spy dump taken during it shows the request thread waiting on the rollup's futures in collect_projects, and every busy executor worker inside _walk_discovery_signature, reached from compute_project_row through discover_plans and _fresh_discovery. Once the 5 s walk-reuse window lapses, the rollup walks all thirteen mounted docs trees to validate caches that nothing has invalidated.

The served process already knows when a tree changes: _ProjectChangeWatch receives kernel notifications for every mounted docs tree that a browser is watching. Every mounted tree is watched for the life of the served process, and a notification drops that tree's memoised walk at once. The reuse window then only backstops writes that the kernel does not report, such as writes from another login node on the shared filesystem, and it lengthens to 60 s. A POST still drops every memoised walk.

It asserts that twenty consecutive collect_projects calls with nothing changed run no tree walk after the first, counted through a counter the test installs on _walk_discovery_signature. The negative control is executed and logged: with the watch not started, a rewrite is not seen until the reuse window lapses, and the within-1-s assertion fails. The write paths are reckon/serve.py and that test. The served figure is not this section's: once §7 is merged and the operator restarts the service, §5 is measured again, and its gate is the one that closes the plan.

Outcome — the rollup reuses walks, and a watched tree's change drops its walk. Commit c06b0764 perf(serve): drop a watched docs tree's memoised walk on change. In reckon/serve.py the per-connection _ProjectChangeWatch yields its event read to a consume() method, over which a new _FleetChangeWatch selects across every mounted tree's descriptor for the life of the served process. On a notification it drops that tree's memoised discovery and its walk signature, and nothing else's. The served reuse window rises to 60 s, read from RECKON_DISCOVERY_REUSE_S with the module-level default left at 0, so the kernel is the invalidation and the window is only the backstop for writes no local kernel reports.
