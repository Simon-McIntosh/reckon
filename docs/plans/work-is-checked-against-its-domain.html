§1 — Why: work that passed every check reckon runs, and was wrong

On 2026-10-21 the four power_convertor coordinators were asked which of their recent work was low value in hindsight, and what signal would have warned them. Three answers account for most of the waste, and the lead asked for them to be treated at their root in reckon.

What happenedWhy reckon let it happen
The session host dispatched two reviews at heads whose previous review still had unanswered blocking findings. Both were certain to repeat those findings, and the coordinator stopped them by hand.The review reflex in crew/recovery_watch.py dispatches a review for every run classified scoring whose coordinator's follower is live. Neither it nor dispatch_review_for_run reads the node's previous review record.
The first CS co-wound tape model was built at 40 sections when the repository's converged count is 168, which overstated the result 15-fold.The convergence rule lives in the repository's code. No brief carries a repository's numerical invariants, and no gate checks a node against them.
A landed record claims that CS1's insertion step trips quench detection at 1.87 V. The claim rests on a static capacitive divider, which is wrong at low frequency. It passed two reviews and was found by the coordinator in a negative-control log.The review dimensions are goal_fidelity, evidence, scope_discipline, durability, fit and reuse. All six grade the work against its brief, and none asks whether the result is right in the domain.

The same coordinators named four more instances of the second and third causes:

  • A solver convergence test measured how far a 1e-5 perturbation spread and accepted it. The lead rejected that as normalising an instability, since in a lossy system a small perturbation must not grow.
  • The fast-discharge resistor's inductance was modelled three ways before anyone read the measured prototype report.
  • A converter model was fitted before anyone checked that its identification constants were available. They are withheld.
  • An acceptance compared a physical zero with a filtered measurement, so the node failed for a reason its method created rather than its physics.

Every one of these is knowledge the repository's people already hold. Reckon offers no place to declare it once, so each brief and each review has to rediscover it, and most do not. This plan gives that knowledge a declared home and makes dispatch, promotion and review read it. reckon stays repository-agnostic: the rules are the repository's, and reckon only carries them.

§2 — No review round while a blocking finding is unanswered

The derivation the refusal needs already exists. _run_open in reckon/crew/review_lifecycle.py (near line 124) answers whether a run review carries a blocking finding with no answer, and lifecycle() exposes that as the hot state open. blocking_finding_dispositions in reckon/crew/repair.py (near line 242) enumerates every blocking finding with its disposition. Obligations, review_dispositions and recovery_repair_dispatch already read them, but dispatch_review_for_run (reckon/crew/recovery_review_dispatch.py, near line 2056), which the reflex calls, reads none of it.

The change is to make it read lifecycle(). A node whose newest review is in state open is refused, with a refusal naming each undisposed finding and its crew dispose --project P --run <id> --finding <index> command (--kind folded --node <n> or --kind exempted --reason <r>). A later change to _run_open therefore reaches the refusal too. The duty the repair machinery already raises for an undisposed blocking finding is the obligation the coordinator sees.

The refusal must not stall the automatic repair loop. When the repair reflex (reckon/crew/recovery_repair_dispatch.py) composes a repair round for a review's blocking findings, it records each of them as folded into that round, through the same disposition writer crew dispose uses. The repaired head's re-review is therefore not refused, while a review at a head no repair round has addressed still is. This was found at the first node's landing on 2026-10-21. The repair path recorded no dispositions, so the guard as first built refused every re-review after an automatic repair until a coordinator disposed the findings by hand.

Surface: one refusal reason on an existing refusal path. No new duty kind and no second derivation are added.

Done when: a fixture run whose previous review has one undisposed blocking finding is refused by the reflex, naming the finding and its dispose command, and no review run is created. The same fixture with the finding disposed dispatches. On the base commit the first fixture dispatches a review, and the test fails there. A second test stubs _run_open to report the run closed and shows the refusal lifts, proving the refusal reads the one derivation.

§3 — A repository declares its domain rules once

Per-project policy already has a validated carrier: docs/state/<project>/flight.yaml. It is modelled in reckon/_flight_schema.py and published as docs/_shared/flight.schema.json. It is resolved per layer and shown by crew(view="flight"), and it already holds the per-dimension review floors (gates.dimension_floors, near line 620). The repository's domain rules join it as a typed domain block in that model, so the existing generator and the existing drift test cover its schema. No new resource is added, project.json is unchanged, and no CLI verb is added, because crew(view="flight") already shows the resolved config.

The block has three lists. invariants are rules a result must satisfy, each with an id, the rule in one sentence, applies_to path globs and an optional check command whose zero exit means the rule holds. review_checks are questions a reviewer must answer about any node they apply to, each with an id, the question and applies_to. Examples from the coordinators above are the limit behaviour at DC and at high frequency, whether both sides of a comparison pass through the same measurement operator, whether a perturbation grows, and whether a measurement of the modelled quantity already exists. model_paths is a list of globs naming where the repository's models live.

One module answers which rules apply to a node: rules_for(project, node) in a new reckon/crew/domain_rules.py. It matches applies_to and model_paths against the node's write paths, and §4, §5 and §6 call only it, so the match cannot disagree with itself. An absent block changes nothing; every repository keeps today's behaviour until it opts in.

Surface: one config block and one module with one public function.

Done when: a fixture flight config with two invariants and two checks validates, and a malformed entry (a missing rule, or applies_to that is not a list) is refused naming the field. rules_for returns exactly the matching rules for a fixture node and nothing for a project without the block. The regenerated flight.schema.json carries the block and its existing drift test passes.

§4 — A brief carries the rules its node touches, and promotion runs their checks

Brief composition already has an owner. reckon/crew/prompts.py holds the composed prompt text, and _brief_text and _brief_record in reckon/crew/dispatch_admission.py (near lines 2015 and 2026) build the brief that is stored and digested so a review can name it. The rules rules_for returns are added there, under a fixed heading. The heading is part of the composed brief and therefore of its digest, so a rule change re-keys the briefs composed after it. That is intended: a brief records the rules it was given.

Each matching invariant that carries a check is run at promotion through the replay path promotion already has, not a new executor. The integration re-run in reckon/crew/promotion_gate.py (near line 787) already runs a flight-declared command, the gates.suite_command armed in reckon/crew/promotion_records.py (near line 347), with sh -c in the repository under a bounded timeout. It already rewrites worktree roots and keeps a replay log. The invariant checks join it as further declared commands under the same bound and log convention. A failing check is a promotion guard reported by crew complete --dry-run beside the others, waivable only with a stated reason. A project that declares no check runs nothing.

Surface: one heading in an existing brief, and one guard that reuses the existing replay.

Done when: a fixture node writing a path an invariant applies to has that rule in its composed brief, and a node writing elsewhere does not. A fixture whose invariant check exits non-zero is refused at crew complete with the invariant's id, and passes once the check exits zero. A check that overruns the bound is refused, not hung, and its replay log is written where the suite replay's is. Without the declaration the same fixture promotes; that is the negative control.

§5 — A review answers the domain checks, and a failed one blocks

Declared checks are not a seventh scored dimension. REVIEW_DIMENSIONS in reckon/crew/review.py stays the global six. The acceptance floor (reckon/crew/recovery_review_acceptance.py, near line 25), the parser's completeness check and the prompt falsifier are all derived from that one constant, and a per-project dimension would change them for every project. Instead the declared checks join the checklist mechanism REVIEW_ITEMS already uses. A review of a node they apply to carries one verdict line per matching check from rules_for, and a record that omits one parses as incomplete rather than as a pass.

A failed check is recorded as a finding with a blocking severity. Nothing in review_lifecycle changes: _run_open (near line 124) already decides blocking from a finding's severity against NON_BLOCKING_SEVERITIES, so §2's refusal, the duty row and the promotion guard see a failed check through the one derivation they already share.

Surface: one checklist entry kind. The dimension vocabulary, the acceptance floor and _run_open are unchanged.

Done when: the composed review prompt for a fixture node lists exactly the checks that match it. A fixture record with every verdict parses complete, and one missing a verdict parses incomplete and names the check. A failed check is stored with a blocking severity, and lifecycle() reports the run open with no change to review_lifecycle.py. A project without declarations scores six dimensions with no checklist lines, and the acceptance floor is unchanged; that is the control.

§6 — A node names its measurement and its inputs before it starts

Both checks run in dispatch admission, reckon/crew/dispatch_admission.py. That is where the dispatched repository's root and its resolved flight config are in hand, and where admission already reports its refusals and the dry run's findings. reckon/crew/prescription.py is not the place. Its judgement is documented as pure, computable before any worktree, plan file or flight configuration exists, and a filesystem check or a model_paths match would break that, so it stays unchanged. TaskNode (reckon/crew/node.py) gains two optional fields, inputs and compares_with.

  • inputs: a node whose inputs, resolved against the dispatched repository's root, do not exist is refused, naming them, so a fit is not started on constants nobody holds.
  • compares_with: a model-building node, one whose write paths match model_paths through rules_for, states the measurement or reference its result will be checked against, or none-exists with the search that established it. A node that states neither gets a lint warning. This is the "is there a measurement of this?" question the coordinators said would have saved two node rounds.

Surface: two optional node fields, and two admission checks reported with the existing ones.

Done when: a fixture node naming a missing input path, relative to the fixture repository's root, is refused at dispatch with the path, and the same node with the file present dispatches. A node whose write paths match a declared model_paths glob and which states neither compares_with nor none-exists receives the lint, and one that states either does not. A project that declares no model_paths is never linted; that is the negative control. The dry run reports both checks with the other admission findings, and judge_prescribed still judges a synthesised node with no repository.

§8 — A finding with a line but no file names its fallback

Why. The review of §2's final head found that repair._finding_location (reckon/crew/repair.py near line 445) guards on the line alone, so a finding carrying a line but no file renders as :12. That string is truthy, so a caller's fallback to the review's findings never applies, and a refusal reads :12 — dispose it with ….

Change. The owner returns nothing for a finding with no file, so every caller's fallback applies; no caller is edited.

Done when: _finding_location of a finding with a line and no file returns the empty result, a finding with both still renders file:line, and the §2 refusal for a line-only finding names the review's findings. On the base commit the line-only case renders :12, so the test fails there.

§9 — One composer for the domain block, and no empty heading
