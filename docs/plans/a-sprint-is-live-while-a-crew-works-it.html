reckon · sprint state

A sprint is live while a crew works it

On 2026-09-25, read_plan(project="reckon") reported active_sprint_id: "S12". That value was written by hand weeks ago. Meanwhile S21, S22 and S23 each had a coordinator and live workers. The lead's directive that day: a live sprint is a sprint with a live crew implementing it, and the hard cap of one active sprint is removed. A stored marker says what someone once decided; a live crew says what is happening now, and that is the signal an agent needs.

§1 — What the surfaces say today

The cap comes from four places:

  • The push op makes one sprint active and demotes the rest to open.
  • The audit reports multiple-active-sprints as an error.
  • active_sprint_id is derived from the one sprint whose stored status is active.
  • The work-scheduling-surface plan (S22) records the invariant.

None of this consults the crew. Discovery returns a state block with counts by_sprint, but no sprint list. roadmap(view="summary") lists open_sprints ids and nothing about sprints closed recently.

The live crew is already readable. Every live pointer names its project and plan, and every plan names its sprint.

§2 — Liveness is derived from live crews

A sprint is live when at least one live pointer in its project serves a plan whose plan-sprint is that sprint, and that pointer is classified as working, starting or dispatched. A blocked or unpromoted pointer counts as held, not live. Liveness is computed at read time from the same classification crew(view="live") uses, and is never written to any resource.

Each sprint row carries four fields:

  • live
  • live_runs
  • live_sessions: the coordinator session ids
  • last_activity_at: the newest stream write among its runs

Done when:

  • A test with a synthetic config home, holding live pointers for plans in two sprints and a terminal pointer for a third, asserts that exactly those two sprints read live: true with the right run and session counts.
  • The third sprint reads live: false.
  • No resource file changes as a result of the read.
  • The declared mutation, reading the stored active status instead of pointers, is applied, and the test is observed to fail. The log is recorded.

Outcome — the read uses the fleet's recorded classification. Commit 17983be1 changes reckon/sprint_liveness.py to read runs.watch_stream_path(project) once, parse it with runs.parse_stream_line, and use the latest to_state per run. A recorded working, starting or dispatched state is live; blocked or an unpromoted completion is held. A run absent from the stream uses only a bounded manifest status-prefix read and stream mtime against the stall window. The sprint row shape and read-only behaviour remain unchanged.

Measured. tests/test_sprint_liveness.py: 5 passed, exit 0; scoped ruff check and format check: clean. The recorded-state test writes a working event while the pointer itself says failed and patches both classifier entry points to fail, proving the stream path is used. The fallback test does the same for an unrecorded, recent, non-terminal pointer. The required negative control is retained at ~/.config/reckon/crew/runs/r-20260925T124727387419-sprint-liveness-reads-the-recorded-fleet/negative-control.log: its first line is call classify_pointer per pointer again, followed by the two expected test failures against the per-pointer implementation.

On the real reckon project with 39 live pointers, three read-only calls took 0.164233s, 0.136719s and 0.138047s (all under 0.5s; 4 sprint rows, 4 live). An older record falls through to the unchanged bounded manifest-status and stream-mtime fallback, so a run that died after its last recorded working event no longer reads live. §3 — Every summary lists open and recently closed sprints

Discovery's read_plan(project) and roadmap(view="summary") both gain a compact sprints list:

  • every sprint not done or shipped
  • every sprint closed within sprint_recent_days, which defaults to 14 and is configurable in flight config

Each row gives the sprint id, theme, stored status, the §2 liveness fields, member and pending counts, completion percentage, and closed_at for a closed sprint. Rows are ordered live first, then open, then recently closed.

Done when:

  • A test on a synthetic project with one live, one open idle, one closed 3 days ago and one closed 40 days ago asserts that the first three appear, in that order, and the fourth does not.
  • The recorded length of the reckon project's discovery summary at the worktree head stays under the response budget.

§4 — The one-active cap is removed

The changes:

  • push no longer demotes other sprints. It sets active on its target as a scheduling hint and leaves every other sprint's status alone.
  • The multiple-active-sprints audit finding is retired.
  • active_sprint_id stays as a compatibility field. It now names the live sprint with the most recent activity, or the stored active sprint when no sprint is live. It sits beside a new live_sprint_ids list.

The reckon-sprint skill text and the roadmap's active_sprint_id description are updated to match. The S22 coordinator is told, because work-scheduling-surface records the old invariant.

Done when:

  • A test pushes two sprints and asserts both keep active.
  • The audit on that project reports no multiple-active-sprints finding.
  • active_sprint_id follows the live sprint when crews exist, and falls back to the stored status when none do.
  • Every existing sprint test that asserted demotion is updated to the new contract in the same commit. Each such change is named in the landing record.

Landed — the focus follows the live crew, and its cost is closed

Closed. The latency blocker described below was removed when reckon.sprint_liveness began reading each run's latest state from the watcher's recorded stream in one pass, re-measured at 0.14–0.16 s for 39 live pointers against the 11.6 s recorded below. Recorded states now carry an age bound, so a run that stopped writing no longer reads live. The paragraphs that follow record the blocker as it was measured. See the execution record.

active_sprint_id now names the live sprint with the most recent stream activity, and falls back to the stored active sprint when no crew is live. It sits beside a new live_sprint_ids list, live sprints most recent first. Both surfaces carry it: the composed project state and the roadmap report. The liveness read happens once per composition, not once per sprint.

When several sprints are stored active and none is live, the choice is deterministic: the first stored-active sprint that still carries an unfinished item, else the first stored-active sprint, else the earliest sprint with unfinished work. The rule is stated in focus_sprint_id's docstring, and the _sprint_status_buckets docstring no longer states the retired one-active rule.

Blocked on cost, not on behaviour. The wiring is correct and the tests pass, but the read it depends on is far too expensive to sit in a hot path. The done-when allowed the roadmap summary to gain at most one second; measured against a base built from be8f1330 and run in the same minutes, it gains about twenty-four. reckon.sprint_liveness.sprint_liveness costs 11.6 s for the reckon project — 34 live pointers, four live sprints, 340 ms each — because classify_pointer parses each run's whole stream (2.33 M JSON lines across the set). The roadmap summary path invokes it twice, so it pays 24.3 s of a 68.6 s read, and the summary projection emits neither active_sprint_id nor live_sprint_ids.

The behaviour itself is what §4 asks for; the cost is the liveness reader's, and that module is another node's. What unblocks this: classify a pointer from a bounded part of its stream rather than all of it, or derive the focus from a liveness snapshot the fleet records once. Evidence, with the interleaved numbers and the profile: execution record.

The reference now reads :func:`reckon.project_state.focus_sprint_id`, and the docstring it names does state the rule the sentence describes.
