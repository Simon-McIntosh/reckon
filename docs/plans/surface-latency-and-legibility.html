§1 — Why now

The lead reported being unable to reach the reckon server on 2026-08-21. The service was in fact healthy — reckon.service active, lingering enabled, listening on 127.0.0.1:8765, and serving browser requests minutes earlier. The connection failure itself was a client-side tunnel, not the server. But probing the server to prove that turned up a real defect underneath: the discovery endpoint takes seconds to tens of seconds per call, which on a laggy forwarded port is indistinguishable from a dead server.

This plan carries two halves of one complaint about the served surface. The first is mechanical and fully diagnosed: discovery is slow, and for three projects it is slow on every single request because the cache that exists never fires. The second is editorial: the server knows considerably more than the SPA puts on screen, and some of what it does put on screen is stale or unexplained. A surface that answers in 16 seconds and then under-explains what it shows is failing at both ends of the same job.

§3 — What the SPA communicates

The second half of the complaint is editorial rather than mechanical, and it is deliberately scoped as an audit first. The SPA is mature — a four-tab shell, cockpit, inline dependency graph, command palette, status menus, north-star rollups, a live crew watcher — spread over roughly 4,500 lines of JSX across eleven components. Guessing at improvements across a surface that size would produce churn, not clarity. So this section dispatches a legibility audit whose output is a ranked, evidence-backed finding list, and only then acts on it.

Three defects are already confirmed by direct inspection and are in scope regardless of what the audit adds:

  • The SPA tells users to edit a path that is no longer canonical. docs/ui/home.jsx instructs, twice and in user-visible copy, to edit ~/docs-server/mounts.json. The canonical location has been ~/.config/reckon/mounts.json since the XDG move; ~/docs-server/ is a legacy fallback only. A user following the on-screen instruction edits a file the server may not read.
  • Latency is invisible, so a slow surface reads as a broken one. This is the thread connecting both halves of this plan. The SPA gives no indication that a discovery scan is in progress or how stale the data on screen is — which is exactly why a 16-second response was reported as a failure to connect.
  • Project state that disagrees with itself is displayed without comment. docs/state/reckon/index.json still lists sprints S3–S6 with active_sprint_id: "S5", while the live distributed sprint resources under docs/sprints/ run to S11 with S9 active. Discovery composes the correct answer, but the stale legacy block remains readable and nothing flags the divergence.

Deliverables

  1. Legibility audit. A ranked finding list over every SPA surface, each finding naming the file, the specific information defect, the reader it fails, and a concrete remedy. The audit must distinguish three classes: information the server already holds but the SPA does not show; information shown but unexplained or ambiguous; and information shown that is stale or wrong. Findings must be evidence-backed against the real served payloads, not speculative redesign.
  2. Correct the three confirmed defects above, plus whatever the audit ranks as high-value and low-risk.
  3. No redesign. This section improves what is communicated, not the visual language. A proposal to restructure navigation or restyle the shell is a separate plan and belongs in a followup, not here.

Done when

The audit exists as a research resource with ranked findings; the three confirmed defects are fixed; every remaining accepted finding is either landed or carried as an explicit followup with its rank and rationale; and the SPA renders correctly against a live server with no console errors.

§ Decisions

How should a document's creation date be sourced once the full-history walk is removed from the request path?

The current call recovers true first-commit time but costs 89% of a cold scan. The alternatives trade accuracy for latency differently, and the choice determines whether the "created" column stays trustworthy.

Reopened 2026-08-25 on the lead's explicit authorisation, superseding the head-keyed-cache choice locked 2026-08-21. The superseded choice and its reasoning are preserved here rather than discarded: it kept creation dates accurate by keying on repository HEAD, correctly rejected inode ctime because a fresh clone or rsync gives every file the same ctime, and declined disk persistence on the stated ground that it optimises only the server-restart path while restarts are rare next to the per-request cost being removed. What changed is that premise. Restarts are not rare on this workstation: the server was restarted twice within twelve hours during this session alone, and each restart re-pays the full history walk — imas-efit 14.8 s and nova 7.1 s on the first call after one. That is the unmet criterion in §2, which was authored in the same session as the decision it contradicts, and the plan is explicit that the criterion must not be quietly amended to match the outcome. Persisting the map under the config home resolves the contradiction in the direction that keeps the criterion true rather than the direction that redefines it. The accuracy argument that killed drop-git-use-ctime is untouched: a persisted map stores the same first-commit timestamps, keyed on the same HEAD, and a file's first-commit time is immutable, so persistence changes only where the map lives between processes.

Should a cold discovery scan be allowed to block the request, or should the endpoint serve a stale-but-immediate result and refresh behind it?

Even with both root causes fixed, the first scan of a 898-document repository costs real time. Serving stale-then-refreshing removes the worst-case wait entirely but introduces a window where the SPA shows data it knows is out of date — which interacts directly with the §3 finding that staleness is currently invisible.

Once the cache actually holds, a cold scan is rare rather than routine, so stale-while-revalidate would add a permanent correctness caveat to every read in exchange for removing a rare wait. Serving data the server knows is out of date is a poor trade for a planning surface whose whole purpose is telling the truth about project state, and it would interact badly with the finding that staleness is currently invisible. The reader-facing remedy belongs in the SPA showing that a scan is running, not in the endpoint answering with data it distrusts.

The cold-scan target now needs a project-state composition decision, not a git one

This supersedes the cold-scan half of f-slal-002, whose premise is spent: it asked the lead to choose between persisting the creation map and restating the criterion. Persistence was chosen and landed in 00f1a92. It worked — _git_first_committed fell from 7.72 s to 0.098 s and left the hot path. The under-three-second target is still missed, for a different reason.

The new dominant cost is full-document parsing during project-state composition. A cold scan of imas-efit now spends 26.4 s in read_state across 251 calls — BeautifulSoup work reached through compose_project_state → _hydrate_items → _plan_state_by_slug, 920,845 selector matches in one scan — plus 8.7 s in parse_meta over 2,563 calls. Figures are inflated by concurrent fleet load; the proportions and the git-call collapse are the load-robust facts, and no regression is claimed because this repository was never profiled before.

The design intent is already written down and is being contradicted. discover_plans documents itself as a lightweight inventory of head meta plus a regex decision count, with no full-body parse, so that a project with thousands of documents stays cheap. Composition full-parses every referenced plan, which is what defeats it. So the question is not how to make parsing faster but whether composition needs full state per plan at inventory time at all, or whether the fields it actually consumes can come from the same cheap head read.

Ownership needs deciding before dispatch. The bottleneck is in reckon/project_state.py, which is distributed-sprint-state territory rather than this plan's. This plan owns the criterion; it does not obviously own the mechanism. Route it by lifecycle rather than by who found it.
