§1 — Why: the tool is the path until it is stale or too narrow

In the four days before 2026-10-19, coordinators made 3,308 edit_plan calls and 99 hand edits of plan HTML, plus scripted Python writes the census cannot fully count. Fifteen of sixteen live coordinators answered a request for their experience (the reports and the census). They leave the tool for three reasons.

  • The server is stale. 52 calls were refused with stale_server_code, and twelve of the fifteen coordinators hit it. Each merge to main moves the code stamp, so on a busy day an image goes stale within minutes. A coordinator cannot reconnect the server itself. The workaround is importing reckon.mcp_edit_plan._edit_plan_tool from Python, or deferring the write; one plan's closure waited about ten hours.
  • An op is missing. 28 refusals named an unsupported set path. No op edits an existing section's title, links, effort, status or body; a followup's title or body; a section's dependency edges; or a gate's measure. Another 37 text-mode refusals were edits of prose inside a structured region.
  • The guidance is wrong or a guard has no way through. 25 refusals were attempts to set impl, which the store computes, while four skill and reference files still show the write. 44 were the landing-continuation and hides-work guards, which coordinators now satisfy with an already-resolved placeholder followup.

On 2026-10-19 the lead decided the surface is centralised in MCP: the server serves current code rather than refusing, and no CLI twin of edit_plan is added. This plan makes the tool available (§3), wide enough to cover every field coordinators write (§4, §5), and honest about how to get through its guards (§6, §7). The skills are corrected first (§2), because their wrong guidance is the cheapest refusal to remove.

§3 — The MCP server answers on current code without a reconnect

Why. The guard _refuse_when_stale in reckon/mcp.py was built by an-mcp-failure-names-its-cause §14 and §15. When a call fails on a moved, trusted checkout, it replaces the answer with stale_server_code. That was the right first step: it named the cause instead of a misleading schema error. But the remedy is a reconnect only the user can perform. Every failure on a moved checkout becomes "reconnect", including a refusal the current code would also give, which the caller then meets one turn later.

Deliverable. The HTTP server already owns this machinery. _CodeReload in reckon/serve.py detects a moved checkout through _served_code_report and re-executes on a stamp change, and reckon/served_code.py owns the snapshot (take_snapshot, served_report, drift). Factor the moved-checkout decision and its trust check out of serve.py into that one owner, and have both servers call it, rather than write a second reload path.

A stdio server cannot simply re-execute as the HTTP server does: the client holds the session it initialised, and a fresh process has not received its initialize. So the MCP server answers on current code by a means the node chooses and records with its reason: re-executing and restoring the session's initialised state, a child process restarted on a stamp change behind a stable stdio front, or a module reload. When a call fails and the checkout has moved and is trusted, the call is re-run on current code and that answer returned, and later calls run on current code. A failed write wrote nothing, so the re-run cannot double it. A deadline failure is re-run with its original expected_version, so a late landing reads as a version conflict. A changed tool signature still owes a reconnect, and its refusal names the tool. An untrusted tree keeps serving the started image.

Done when tests/test_mcp_server_serves_current_code.py drives a server over its own copy of the package through three cases. (a) After a commit that changes what edit_plan returns, a call in the same session returns the new answer and no stale_server_code. (b) A tree whose tracked file differs from HEAD keeps serving the started image. (c) A change to a registered tool's parameters returns the reconnect refusal naming that tool. The negative control disables the reload, and case (a) then returns stale_server_code. Every test that imports reckon.serve's reload or reckon.served_code passes unchanged, as do tests/test_one_check_trusts_a_moved_checkout.py and tests/test_every_module_fits_a_worker_window.py. Write paths: reckon/mcp.py, reckon/serve.py, reckon/served_code.py, tests/test_mcp_server_serves_current_code.py.

§4 — An existing section is editable through one op

Why. Seven of the fifteen reports hand-edited an existing section. The edits changed its links, effort, status or title, or replaced its prose after a review, because insert_section refuses an id that exists and no set path reaches a section. Text mode refuses any replacement that overlaps the section's record, and an apostrophe stored as &#x27; makes an exact old_html miss.

Deliverable. {op:'set', path:'sections.<id>.<field>', value} accepts five fields. title rewrites the section's h2 text and keeps its id. links, effort_hours and capability are validated as insert_section validates them. body replaces the authored HTML between the section's record element and the next h2 or data-reckon section, through the replacement machinery text mode already uses. The write therefore reports review_owed for that section exactly as a text edit does, and the plan-review fingerprint keeps its one form. A body containing an h2 or a data-reckon element is refused, because it would forge structure. A section's status stays with set section_declarations.<id>, and sections.<id>.status is refused naming that path, so no second spelling is added. An unknown field is refused, naming the accepted five. The op table in skills/reckon-edit/SKILL.md names the path, which §2's widened contract test enforces.

Done when tests/test_edit_plan_sets_a_section_field.py sets each field on a temporary plan through edit_plan and asserts that the parsed state carries the change, that every other section's bytes are unchanged, and that reckon audit-doc reports no error. The body case replaces prose holding an apostrophe stored as &#x27;, and returns review_owed naming that section, as the equivalent text edit does. tests/test_the_fingerprint_has_one_form.py passes. Two negative controls: a body containing <h2 is refused, and set sections.s9.title on a plan with no s9 is refused naming it. tests/test_every_module_fits_a_worker_window.py passes; reckon/_store.py is about 40,500 of the 50,000-token bound, so the new handlers live in reckon/_store_section_ops.py. Write paths: reckon/_store.py, reckon/_store_section_ops.py, reckon/_plan_html.py, reckon/mcp.py, reckon/mcp_edit_plan.py, skills/reckon-edit/SKILL.md, tests/test_edit_plan_sets_a_section_field.py.

§5 — Followup text, section dependencies and gate measures are settable, and unset removes a key

Why. plan-section-depends-on is a head meta that no op writes and that text mode refuses as structured state; six coordinators wrote it with Python, one about twelve times in a day. Only a followup's prompt is settable, so a widened scope is written into the one-line prompt or the followup is resolved and re-appended. A gate's stale measure was answered with a correction comment because it could not be changed. A stale declaration key could not be removed.

Deliverable. Three new set paths, and a null value that removes a key, with no new verb:

  • set followups.<id>.title and .body on an open followup. A resolved followup is a record and is refused.
  • set section_depends_on.<sid> with a list of refs checked against the roadmap's [project:]slug#section grammar. It writes the head meta, and a later read gives back what was written.
  • set gates.<id>.measure and .required_evidence on an open gate.
  • A set whose value is null removes the key, for four kinds of key: section_depends_on.<sid>; section_declarations.<id> once its heading is gone; a decision field other than choice; and an optional top-level scalar. Removing a required field is refused, naming it. The op vocabulary keeps its size.

The reckon-edit op table names each one.

Done when tests/test_edit_plan_sets_followup_dependency_and_gate_fields.py gives each of the four surfaces its own case and its own negative control, through edit_plan on a temporary project:

  • Followup text: an open followup's title and body change, and the same write on a resolved followup is refused.
  • Section dependencies: after the write, the roadmap's own section_depends_on reading returns the edge, which proves the consumer and not only the meta; a ref outside the grammar is refused.
  • Gate fields: an open gate's measure changes, and the same write on a passed or failed gate is refused.
  • Null removal: each of the four key kinds is removed, and a null section_declarations.<id> while its heading exists is refused, because it would leave an undeclared heading.

The evidence gives each surface its own verdict, so the section closes on all four or records which did not land. Write paths: reckon/_store.py, reckon/_store_section_ops.py, reckon/_plan_html.py, reckon/mcp.py, skills/reckon-edit/SKILL.md, tests/test_edit_plan_sets_followup_dependency_and_gate_fields.py.

§6 — A plan closes in one write, without a placeholder followup

Why. 17 refusals said a landing left no continuation, and 27 that a followup hid work. Coordinators get past both by appending a followup already resolved "done — no followup", which one called gaming the guard. Closing a plan therefore takes several writes whose order is learned from refusals. A plan whose only remaining work waits on the lead is §8's case, which the decision deferred-continuation holds; this section needs no decision.

Deliverable. {op:'close', status, outcome, by[, superseded_by]} is one write. It sets any status in TERMINAL_STATUSES (reckon/lifecycle.py) and resolves every open followup with the outcome. It runs every guard a terminal transition fires and reports each one that fails, together:

  • a section still implementable, named;
  • the evidence record that a terminal status needs, named by path;
  • a pending transition gate (_require_transition_verdict);
  • an appended followup that hides work (_refuse_appended_hiding_followups);
  • a landing status with no continuation (continuation_present, raising CONTINUATION_REQUIRED).

The outcome a close carries is the chain-closing outcome that resolves every open followup, so a plan whose work is done satisfies the continuation guard through the close itself, with no placeholder followup.

No guard is removed. The vocabulary gains one verb and set loses its terminal path: a set of status to any value in TERMINAL_STATUSES is refused, naming close, and every reckon caller that sets one moves to close in the same node. The resolved-placeholder recipe is dropped where it lives: skills/reckon-build/references/coordinator-reference.md, skills/reckon-build/references/sprint-orchestration.md and AGENTS.md. skills/reckon-edit/SKILL.md documents close in its op table.

Done when tests/test_a_plan_closes_in_one_op.py passes three cases. A plan whose sections are done and whose evidence record exists closes in one version step, with every followup resolved and no placeholder followup appended. A plan with an implementable section, no evidence record and a pending transition gate is refused, naming all three in the same answer. A set of status to each value of TERMINAL_STATUSES, imported from reckon/lifecycle.py rather than listed, is refused naming close. The negative control reports only the first failing guard, and the second case then fails for the guards it omits.

The refusal changes a write existing tests use as their subject. The base already shows tests/test_terminal_status_needs_every_section_ticked.py, tests/test_every_section_has_a_declaration.py, tests/test_closure_gates.py and tests/test_continuation.py and tests/test_edit_plan.py. The gate log also carries a grep of the three recipe files and skills/reckon-create/SKILL.md for an instruction to append a resolved placeholder followup or to set a terminal status, which finds none. §7 — A refused or late write names the next step

Why. Four refusals made the caller do more reads than the answer needed:

  • A version conflict arrived with a null detail and no current version.
  • A write that timed out landed later, and its retry read as a conflict.
  • A batch reported only its first refused op.
  • A field's legal values (section risk, the capability shape, followup status, quarter-hour effort) were learned one refusal at a time.

Deliverable. Four changes. Before repairing each, confirm it still reproduces at the node's base: several reports came from older server images.

  • A version conflict carries the current version and the targets changed since the expected one.
  • A state-mode batch reports every op the store would refuse, each with its index and reason.
  • An optional request_id makes a retry of a write that landed late return its landed version with ok.
  • A refusal on an enumerated field names its legal values, and a capability refusal carries a valid example.

Done when tests/test_a_refused_write_names_the_next_step.py covers each change that reproduced at the base, through edit_plan, with its own negative control. Without the current version, the conflict case fails. Reporting only the first refused op fails the batch case. Reusing one request_id for a write with different ops is refused as a reused id, not answered with the earlier write's version. Dropping the legal values from an enumerated-field refusal fails that case. A change that already holds at the base (the conflict payload may: _conflict_response in reckon/mcp_deadlines.py returns current_version) is recorded in the evidence with the passing base test, and gets no code. Write paths: reckon/mcp_edit_plan.py, reckon/_store.py, reckon/_store_section_ops.py, tests/test_a_refused_write_names_the_next_step.py.

§8 — A deferred section held by a decision or a gate is a plan's continuation

Why. When the only remaining work is a deferred section waiting on an open decision, the continuation guard accepts no followup at all: a followup naming the section is refused as hiding work, and none at all is refused as leaving no continuation. Five reports met this with no legal way through, and the placeholder they used instead is the one §6 retires.

Deliverable. Once the lead locks deferred-continuation as accept, the continuation guard accepts a deferred section as a plan's continuation when an open decision names it among its sections, or an open gate holds it. A plan waiting on the lead then needs no followup. If the decision is locked as require-followup, the hides-work guard instead accepts a followup whose prompt names that deferred section.

Done when tests/test_a_waiting_plan_needs_no_placeholder.py lands a plan whose only remaining section is deferred under an open decision, and the landing succeeds with no new followup. The negative control locks that decision, and the same landing is then refused for want of a continuation. Write paths: reckon/_store.py, reckon/_store_section_ops.py, skills/reckon-edit/SKILL.md, tests/test_a_waiting_plan_needs_no_placeholder.py.

§ Decisions

When the MCP image is older than the checkout, what keeps a coordinator's plan write from blocking?

The lead centralised the surface in MCP on 2026-10-19. A server that serves current code removes the reconnect for every tool at once, and a CLI twin would add verbs while the crew CLI is being narrowed.

May a deferred section held by an open decision or an open gate stand as a plan's continuation, so that no followup is needed?

Recommended: accept. The decision or gate already records what the section waits on and who must act, and a followup naming it adds a second copy that drifts. Five reports met this guard with no legal way through.
