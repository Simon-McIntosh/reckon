§1 — Why: the tool is the path until it is stale or too narrow

In the four days before 2026-10-19, coordinators made 3,308 edit_plan calls and 99 hand edits of plan HTML, plus scripted Python writes the census cannot fully count. Fifteen of sixteen live coordinators answered a request for their experience (the reports and the census). They leave the tool for three reasons.

  • The server is stale. 52 calls were refused with stale_server_code, and twelve of the fifteen coordinators hit it. Each merge to main moves the code stamp, so on a busy day an image goes stale within minutes. A coordinator cannot reconnect the server itself. The workaround is importing reckon.mcp_edit_plan._edit_plan_tool from Python, or deferring the write; one plan's closure waited about ten hours.
  • An op is missing. 28 refusals named an unsupported set path. No op edits an existing section's title, links, effort, status or body; a followup's title or body; a section's dependency edges; or a gate's measure. Another 37 text-mode refusals were edits of prose inside a structured region.
  • The guidance is wrong or a guard has no way through. 25 refusals were attempts to set impl, which the store computes, while four skill and reference files still show the write. 44 were the landing-continuation and hides-work guards, which coordinators now satisfy with an already-resolved placeholder followup.

On 2026-10-19 the lead decided the surface is centralised in MCP: the server serves current code rather than refusing, and no CLI twin of edit_plan is added. This plan makes the tool available (§3), wide enough to cover every field coordinators write (§4, §5), and honest about how to get through its guards (§6, §7). The skills are corrected first (§2), because their wrong guidance is the cheapest refusal to remove.

§3 — The MCP server answers on current code without a reconnect

Why. The guard _refuse_when_stale in reckon/mcp.py was built by an-mcp-failure-names-its-cause §14 and §15. When a call fails on a moved, trusted checkout, it replaces the answer with stale_server_code. That was the right first step: it named the cause instead of a misleading schema error. But the remedy is a reconnect only the user can perform. Every failure on a moved checkout becomes "reconnect", including a refusal the current code would also give, which the caller then meets one turn later.

Deliverable. The HTTP server already owns this machinery. _CodeReload in reckon/serve.py detects a moved checkout through _served_code_report and re-executes on a stamp change, and reckon/served_code.py owns the snapshot (take_snapshot, served_report, drift). Factor the moved-checkout decision and its trust check out of serve.py into that one owner, and have both servers call it, rather than write a second reload path.

A stdio server cannot simply re-execute as the HTTP server does: the client holds the session it initialised, and a fresh process has not received its initialize. So the MCP server answers on current code by a means the node chooses and records with its reason: re-executing and restoring the session's initialised state, a child process restarted on a stamp change behind a stable stdio front, or a module reload. When a call fails and the checkout has moved and is trusted, the call is re-run on current code and that answer returned, and later calls run on current code. A failed write wrote nothing, so the re-run cannot double it. A deadline failure is re-run with its original expected_version, so a late landing reads as a version conflict. A changed tool signature still owes a reconnect, and its refusal names the tool. An untrusted tree keeps serving the started image.

Done when tests/test_mcp_server_serves_current_code.py drives a server over its own copy of the package through three cases. (a) After a commit that changes what edit_plan returns, a call in the same session returns the new answer and no stale_server_code. (b) A tree whose tracked file differs from HEAD keeps serving the started image. (c) A change to a registered tool's parameters returns the reconnect refusal naming that tool. The negative control disables the reload, and case (a) then returns stale_server_code. Every test that imports reckon.serve's reload or reckon.served_code passes unchanged, as do tests/test_one_check_trusts_a_moved_checkout.py and tests/test_every_module_fits_a_worker_window.py. Write paths: reckon/mcp.py, reckon/serve.py, reckon/served_code.py, tests/test_mcp_server_serves_current_code.py.

The edits changed its links, effort, status or title, or replaced its prose after a review, because insert_section refuses an id that exists and no set path reaches a section. §6 — A plan closes in one write, without a placeholder followup

Why. 17 refusals said a landing left no continuation, and 27 that a followup hid work. Coordinators get past both by appending a followup already resolved "done — no followup", which one called gaming the guard. Closing a plan therefore takes several writes whose order is learned from refusals. A plan whose only remaining work waits on the lead is §8's case, which the decision deferred-continuation holds; this section needs no decision.

Deliverable. {op:'close', status, outcome, by[, superseded_by]} is one write. It sets any status in TERMINAL_STATUSES (reckon/lifecycle.py) and resolves every open followup with the outcome. It runs every guard the transition to that status fires, as validate_landing_patch gates them today, and reports each one that fails, together. The section-ticked guard and the continuation guard fire only for a landed status (shipped, done); the others fire for every terminal status, so a superseded or archived close is not newly refused:

  • a section still implementable, named;
  • the evidence record that a terminal status needs, named by path;
  • a pending transition gate (_require_transition_verdict);
  • an appended followup that hides work (_refuse_appended_hiding_followups);
  • a landing status with no continuation (continuation_present, raising CONTINUATION_REQUIRED).

The outcome a close carries is the chain-closing outcome that resolves every open followup, so a plan whose work is done satisfies the continuation guard through the close itself, with no placeholder followup.

No guard is removed. The vocabulary gains one verb and set loses its terminal path: a set of status to any value in TERMINAL_STATUSES on a plan is refused, naming close. The refusal is plan-scoped: a sprint, milestone or blocker keeps its own set status (_apply_sprint_status), because close closes a plan and nothing else, and every reckon caller that sets one through code moves to close in the same node. The documents that describe the change (the op table, the resolved-placeholder recipe and the instructions to set a terminal status) are §10's: with them in its fence this node exceeded the local lane's context window.

§11 — A slow current-code child never forces a reconnect

Why. On 2026-10-19 two coordinators reported that §3's guard still forces reconnects under load, and the lead was asked to reconnect again that evening. power_convertor's sessions saw read_plan, edit_plan, roadmap and crew all answer stale_server_code from mid-afternoon, on a node at load 59–75. The code in reckon/mcp.py shows three causes:

  • An unanswered child becomes a reconnect. _refuse_when_stale re-runs a failed call in a child. When the child makes no answer, _answer_on_current_code returns None and _stale_code_response replaces the call's own failure with the refusal. Under load the child's import runs out its bound. A version_conflict or storage-slow, whose remedy is to re-read and retry, then comes back as "reconnect", and its detail says "This call failed on the current code too", though the current code never ran.
  • One fresh interpreter per call. Once a tool has answered on current code, _SERVE_ON_CURRENT_CODE sends every later call of that tool to a new child first. Each child pays a full import, bounded at _CURRENT_CODE_TIMEOUT_S = 120 s, so on a loaded node every call waits and many fail.
  • Every commit moves the stamp. This repository commits every few minutes, so the moved-checkout path is the normal state of a long session, not an exception.

Deliverable. The guard stops turning slowness into a reconnect:

  • When the child makes no answer, the call's own result stands, error code unchanged, with code_stamp_at_start, code_stamp_now and a note that the current code did not answer within its bound. A version_conflict stays a version_conflict.
  • Current code is loaded once per code stamp, in one persistent child behind the stdio front. When the guard first sees the stamp move, it starts the child and sends a readiness probe. The child imports the checkout, reports each tool's parameter names, and runs no tool. It is warm once it has answered the probe. It takes calls as request-tagged JSON lines and is reused until the stamp moves again, when it is stopped and one new child is started. The probe's parameter names are also what detect a changed tool signature. The child ends when the server ends: it exits when its input pipe closes.
  • While the child is cold, the running image serves every call, and a failed call keeps its own result as above, so a cold child never makes a call wait. Once the child is warm, a call of a tool that has fallen back goes to the child instead of the image, so it runs once. If the child does not answer a routed read within its bound, the read falls back to the image. A routed write (edit_plan, or crew with an action) is never re-run on the image. It returns a timeout saying the call may have landed, which names the re-read to make before retrying.
  • The stale_server_code refusal remains for one case only, a tool whose parameters changed. There the client holds the schema it connected with, and a reconnect is the real remedy.

§3 weighed re-exec and found it cannot carry an initialised stdio session. An in-process module reload would leave live references into the old modules. A persistent child keeps §3's self-reload, which the stale-image-remedy decision locked, and pays the import once.

A server started before this lands still runs the old guard, so each session needs one more reconnect to pick up this one. The coordinators who reported the defect are told so when it lands.

Done when tests/test_a_slow_child_never_forces_a_reconnect.py drives the guard on a temporary checkout whose stamp has moved, with a child it can slow or stop:

  • A call that fails with version_conflict, while the child makes no answer within its bound, returns version_conflict with both stamps attached and no reconnect field.
  • Twenty calls after the stamp moves start one child, counted by a spawn hook. A further stamp move stops it and starts exactly one more.
  • A call made while the child is still cold is served by the running image without waiting on the child. The child turns warm on its probe answer, and its call log shows no tool call sent to warm it.
  • Once the child is warm, a call of a tool that has fallen back runs once, in the child. The image's call count for that tool stays at zero.
  • A routed write that the child does not answer within its bound returns the may-have-landed timeout, and the image's write count stays at zero.
  • A tool whose parameters changed, as the probe reports them, still returns stale_server_code with its reconnect remedy.
  • Closing the server's end of the pipe ends the child.

Each case has a negative control, and each control's log is kept:

  • Restoring the refusal on an unanswered child fails the first case.
  • Starting a child per call fails the second.
  • Making a cold call wait for the child, or warming it with the caller's own call, fails the third.
  • Running a routed call on the image as well as the child fails the fourth.
  • Re-running a timed-out write on the image fails the fifth.
  • Ignoring the probe's parameter names fails the sixth.
  • Leaving the child running after the pipe closes fails the seventh.

tests/test_mcp_server_serves_current_code.py and tests/test_mcp_tools.py add no failure, and tests/test_every_module_fits_a_worker_window.py adds none either. Write paths: reckon/mcp.py, reckon/served_code.py, tests/test_mcp_server_serves_current_code.py, tests/test_a_slow_child_never_forces_a_reconnect.py. reckon/mcp.py is also the write path of the-crew-surface-is-one-tool-and-a-few-verbs §5, which waits for this section to land.

§12 — A current-code child that keeps dying is backed off

Why. The review of §11 at 110f69ed1 found that the liveness branch replaces a dead current-code child with no attempt budget, backoff or record of the failures. A child that dies right after each spawn therefore starts one fresh interpreter per guarded call. That is the per-call import cost §11 removed, and it happens silently, because the spawn sends the child's stderr to DEVNULL. A checkout that does not import is already refused by may_load, so the case left is a child that imports and then dies.

Deliverable. After a bounded number of consecutive child deaths within one code stamp, CurrentCodeServer stops respawning until the stamp moves, and the running image serves every call meanwhile. The child's stderr goes to a bounded file, so the last death's cause can be read. The answer a caller sees is unchanged. It is composed in reckon/mcp.py, which this section does not write, and a backed-off child leaves the caller's answer to the running image, as §11 does for a cold child.

Done when tests/test_a_dying_child_is_backed_off.py uses a child that exits right after every spawn. A run of twenty calls starts no more children than the bound, every call is answered by the image, and the last death's stderr is readable at the named path. A stamp move resets the count, and the next call starts a fresh child. The negative control removes the bound, and the spawn-count case then fails. tests/test_a_slow_child_never_forces_a_reconnect.py adds no failure, and nor does tests/test_every_module_fits_a_worker_window.py. Write paths: reckon/served_code.py, tests/test_a_dying_child_is_backed_off.py.

§13 — An added parameter needs no reconnect

Why. After §11, the only reconnect the guard still asks for is a changed tool signature, and it asks for any difference in a tool's parameter list, additions included. So every landing that adds a parameter makes every session reconnect. The 2026-10-19 and 2026-10-20 reconnects after §11 landed were both "tool edit_plan changed its parameters": §7's added request_id, seen by an imas-codex session at 05:05Z and a reckon session at 23:47Z. crew-surface §5 adds eight actions to crew and would do the same. An added optional parameter leaves every call the client can make valid on the new code, so a reconnect only buys the client the new parameter.

A second cause keeps this fix from reaching anyone. _probe_signature_changed in reckon/mcp.py compares the lists inside the server's own image, so a better rule never reaches a server that is already running. Each improvement to the guard costs one more reconnect per session.

Deliverable.

  • The readiness probe reports each tool's parameters with whether each one is required.
  • The current code makes the compatibility decision. The parent sends its registered parameters, each with whether it was required, along with the probe. The child answers compatible or not. The rule is a function in a module the child imports from the checkout. The probe handler in SERVED_CHILD_PROGRAM only calls it, because that program string is a constant of the parent's own image, handed to the child at spawn: a rule written there would be the parent's frozen copy. So a later change to the rule reaches running servers without a reconnect.
  • A change is compatible when every registered parameter is still accepted, no registered optional parameter has become required, and no new parameter is required. The routing stays §11's. A call the image answers successfully is returned untouched, and needs nothing. A call that reaches the current code — a failed call re-run there, or a call of a tool already routed there — is served when the verdict is compatible, with no refusal, and its answer carries a schema_note naming the parameters the client cannot send until it reconnects.
  • stale_server_code remains for an incompatible change: a registered parameter removed or renamed, a registered optional parameter made required, or a new required one.

The probe stays readable by a server started before this lands, because that server is the parent the new child answers. The probe answer keeps params as each tool's list of parameter names, exactly as now. Requiredness goes under a new key beside it, and the child's verdict goes under another, given only when the request carried registered parameters. A probe request carrying no registered parameters, which is what a pre-§13 parent sends, gets that unchanged answer. Its parent then compares as it does today and still refuses any changed signature. So a server started before this lands asks for one reconnect, and the reconnect picks this up. After that, an added optional parameter and any later change to the rule need none.

Done when tests/test_an_added_parameter_needs_no_reconnect.py drives the guard with a child whose tool signature it controls:
