§1 — One session, one monitor, and during a wave it is five

The lead's requirement is that a coordinator session shows exactly one monitor, the follower, so the lead can track progress from one place. Measured on 2026-09-22 in the reckon session that wrote this plan: four investigation nodes dispatched to the locally served lane at 21:50:30 left four background shells running beside the follower. Each shell was a reckon crew dispatch process that had not returned. The process tree for each was the dispatch process, a second reckon process beneath it, and the claude worker beneath that. All four dispatch processes exited at 21:56:20 and 21:56:38, close to six minutes after launch, and all four workers were still alive and streaming afterwards. The skill tells coordinators to background every CLI dispatch, which is why the hold shows up as extra monitors rather than as a blocked turn.

The worker is launched with start_new_session=True in _spawn in reckon/crew/dispatch.py, and it survives its dispatch process exiting normally. What holds the dispatch process for six minutes is not established. An earlier session recorded that wrapping dispatch in timeout reaped its worker, so a dispatch ended by a signal during the hold may still take the worker with it. That is the case a host which expires background shells would hit.

§2 — Measure what holds the dispatch open and what its death does

Establish two facts with a trivial backend, never a real worker. First, which code path holds reckon crew dispatch open for about six minutes after the worker is launched and its pointer written: the launched-worker reaper in reckon/crew/dispatch.py, an explicit wait, or the second reckon process in the tree. Second, what happens to the worker when the dispatch process receives SIGTERM, SIGKILL and SIGHUP, each in turn.

Use a stub backend whose command is a shell script that sleeps for sixty seconds and then writes a marker file, dispatched in a temporary repository with a temporary crew config home, so nothing reaches the real pointer directory.

Done when docs/research/data/dispatch-lifetime.json names the file and line that keeps the dispatch process alive with the quoted source, lists the process tree observed after launch with each process's role, and states for each of the three signals whether the stub's marker file appeared. The test harness that produced it is committed as tests/test_dispatch_lifetime_probe.py and asserts on the real pointer directory being untouched afterwards.

§3 — Dispatch returns once the worker is launched

Make a CLI dispatch print its JSON result and exit as soon as the worker process is running and its live pointer is written. The worker must survive the dispatch process ending by any of the three signals in §2, including a signal that arrives during what is today the hold. Collection of the worker's exit moves off the dispatching process: liveness is already read from the pointer's recorded pid by record_process_alive, and a worker whose parent has exited is reparented and collected by the system. Keep the launched-worker reaper for the follower's own sweep-launched workers only if §2 shows it is still needed there.

Done when a test dispatches the stub backend of §2 and observes the dispatch process exit within five seconds with the run id in its JSON output, then kills nothing and observes the stub's marker file appear. A second test sends SIGKILL to the dispatch process before it returns and still observes the marker. The negative control is recorded: reinstating the wait that §2 identified makes the first test fail on the five-second bound, and the log of that failing run is kept with the manifest. The write paths are reckon/crew/dispatch.py and tests/test_dispatch_returns_without_worker.py.

§4 — The skill stops telling coordinators to background a dispatch

Once §3 lands, a dispatch is an ordinary short command. Change every instruction that says to background a CLI dispatch or to yield after it, so a coordinator runs it in the foreground and reads its JSON. The follower remains the only long-lived process a session owns.

Done when grep -rn "background the call\|run_in_background" skills/ returns no instruction to background a dispatch, the launch-kind table in skills/reckon-ship/SKILL.md says a CLI dispatch returns once its worker runs, and skills/reckon-ship/references/orchestrator-harness/claude-code.md names the follower as the session's only monitor. The write paths are those two files.

§5 — A refused dispatch leaves nothing that reads as a death

imas-ambix-b6 received a row at 20:41:11 reading abandoned with the reason the process is gone without a complete manifest, four seconds after a dispatch. The dispatch had been refused because its member could not be resolved, and it had left a live pointer behind. The coordinator removed a worktree on the strength of the misreading. Find where a refusal can occur after the pointer is written, and remove the pointer on refusal, or order the checks so every refusal precedes the write.

Done when a test forces a member-resolution refusal in a temporary crew config home and asserts the live pointer directory holds no pointer for that node afterwards, and the watch stream carries no transition for it. The negative control is executed and logged at the base revision, where a pointer remains. The write paths are reckon/crew/dispatch.py and tests/test_refused_dispatch_leaves_no_pointer.py.
