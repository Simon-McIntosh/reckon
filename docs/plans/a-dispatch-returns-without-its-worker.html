§1 — One session, one monitor, and during a wave it is five

The lead's requirement is that a coordinator session shows exactly one monitor, the follower, so the lead can track progress from one place. Measured on 2026-09-22 in the reckon session that wrote this plan: four investigation nodes dispatched to the locally served lane at 21:50:30 left four background shells running beside the follower. Each shell was a reckon crew dispatch process that had not returned. The process tree for each was the dispatch process, a second reckon process beneath it, and the claude worker beneath that. All four dispatch processes exited at 21:56:20 and 21:56:38, close to six minutes after launch, and all four workers were still alive and streaming afterwards. A fifth dispatch at 22:14:34 returned at 22:18:45, a hold of about four minutes. The skill tells coordinators to background every CLI dispatch, which is why the hold shows up as extra monitors rather than as a blocked turn.

The worker is launched with start_new_session=True in _spawn in reckon/crew/dispatch.py, and it survives its dispatch process exiting normally. What holds the dispatch process for six minutes is not established. An earlier session recorded that wrapping dispatch in timeout reaped its worker, so a dispatch ended by a signal during the hold may still take the worker with it. That is the case a host which expires background shells would hit.

§3 — Dispatch returns once the worker is launched

Make a CLI dispatch print its JSON result and exit as soon as the worker process is running and its live pointer is written. The worker must survive the dispatch process ending by any of the three signals in §2, including a signal that arrives during what is today the hold.

Collection of the worker's exit moves to a detached per-run supervisor, never to init. A worker reparented to init has its exit status collected by init, and reckon never sees it. Measured on 2026-09-23 on worker-death-is-recorded §5: 0 exit records across every live pointer after a night of at least eight worker deaths. So dispatch starts a small supervisor process in its own session. The supervisor spawns the worker, writes the worker's pid, and reports the launch back to dispatch, which then prints its result and exits. The supervisor waits on the worker and records its exit status and, when a signal ended it, the signal name. It writes that record to the run directory and to the live pointer, then exits. The supervisor writes the pointer only when the pointer still exists. It must never recreate a pointer that has gone, because a discarded pointer was rewritten back into existence by a late writer on 2026-09-23. The run-directory record is what survives a discard. Liveness stays read from the pointer's recorded worker pid by record_process_alive.

One exit record serves a death and a launch failure. The supervisor writes exit.json in the run directory, and copies the same object under the pointer's exit key while the pointer exists. Its fields:

FieldTypeMeaning
worker_pidintegerthe process the supervisor waited on
launched_atUTC ISO-8601when the worker process started
exited_atUTC ISO-8601when the supervisor collected the exit
exit_codeinteger or nullthe status for a normal exit; null when a signal ended it
signalinteger or nullthe signal number when a signal ended it; null otherwise
signal_namestring or nullfor example SIGKILL; null otherwise
stream_records_seenintegerrecords across the run's stream files at exit; 0 means the worker exited before its first record, which is a launch failure
last_record_typestring or nullthe type of the newest stream record, for example result, assistant or system; null when none was written
recorded_bystringsupervisor, so a reader can tell a collected exit from an inferred one

A reader composes nothing at read time that this record carries. A launch failure is stream_records_seen == 0, not a second format. crew-runtime-positive-controls' launch-failure record and a-stalled-row-says-whether-the-worker-lives' death row read these fields rather than deriving their own.

Done when tests/test_dispatch_returns_without_worker.py covers four cases with the stub backend of §2, in a temporary repository and a temporary RECKON_HOME. First, the dispatch process exits within five seconds with the run id in its JSON output, nothing is killed, and the stub's marker file appears. Second, SIGKILL sent to the dispatch process before it returns still leaves the marker file appearing. Third, the measure from worker-death-is-recorded §5, verbatim: a real dispatch, the dispatching process gone, SIGKILL, and the exit status still recorded. Here the dispatch has returned, the worker receives SIGKILL, and within ten seconds both the run directory's exit record and the pointer carry the exit status with signal name SIGKILL. Fourth, the pointer is discarded before the worker exits, and after the exit no pointer exists for the run while the run directory's exit record does. The negative control is executed and logged: reinstating the wait that §2 identified makes the first case fail on the five-second bound, and removing the supervisor's wait makes the third case fail. Both failing logs are kept with the manifest. The real pointer directory under the user's config home is asserted untouched. The write paths are reckon/crew/dispatch.py and tests/test_dispatch_returns_without_worker.py.

§6 — A refusal is never returned for a dispatch that launched

imas-efit-e3 measured this at about 02:58 UTC on 2026-09-23, in session ship-s13-20260922. Two consecutive dispatches of node review-of-rank-floor-cost-verdict-carrying-rails returned refusals. The first read not-dispatchable. The second read dispatch-refused because the worktree path already existed. Yet run r-20260923T025720725298-review-of-rank-floor-cost-verdict-carrying-rails had a live pointer, an attempt started at 02:58:27, and a stream written eleven seconds before it was checked, so its worker was running. Its member was an auto-derived session member, although both calls passed --member clive-rev-6.

Such a refusal invites two harmful moves: a duplicate dispatch of a node already working, and removing a worktree that looks orphaned out from under a live process. Find the path on which a refusal is returned after the pointer is written or the worker is spawned, and make the result agree with what happened. Either the dispatch reports success naming the run it launched, or it launches nothing. Separately, find why an explicit --member was replaced by an auto-derived member, and refuse rather than substitute when the named member cannot be bound.

The exit status is not a defect. imas-efit-e3 first reported that refusals exited 0, then measured the bare command and corrected it: a dispatch-refused exits 1 and a contract-validation refusal exits 2, and every 0 it had seen ended in a pipe, which reports the last stage's status. A refused dry run measured here also exits 1. One part of that correction is a defect. The contract-validation refusal returns ok: false with error: null, carrying its reason only under validation.findings. The skill documents that every refusal carries error and detail, so a caller keying on error reads that refusal as success. imas-efit-e3 did exactly that.

Done when tests/test_dispatch_result_matches_launch.py drives a dispatch through the failing path with a stub backend in a temporary crew config home, and asserts that the result either names the launched run with ok: true or leaves no pointer and no process. A second test passes an unresolvable --member and asserts a refusal with no auto-derived member bound. A third asserts that every result with ok: false, including a contract-validation refusal on a done-when holding a literal placeholder, carries a non-null error and a detail. The negative control is executed and logged at the base revision, where a refusal is returned beside a live pointer. The write paths are reckon/crew/dispatch.py and that test.

§3 as written would lose every worker's exit record. It is held until it is revised. The S19 session measured this on 2026-09-23 (worker-death-is-recorded §5, commit 2e5e8f53). launch_failures holds 0 exit records across every live pointer, and the ledger carries no signal_name, after a night of at least eight worker deaths. The reason: crew dispatch exits after launching, its reaper thread dies with it, and the worker is reparented to init (a live review worker read PPID 1), so init collects the status and reckon never sees it. §3 currently makes that path the design: a worker whose parent has exited is reparented and collected by the system. The serve logged 20,507 HTTP 200 responses and no non-200 over the same period, so the mid-thinking deaths are client-side, and this missing record is what would name them.

The revision proposed to S19 keeps one mechanism with one owner. Dispatch returns, and a detached per-run supervisor stays. The supervisor runs in its own session, spawns the worker, waits on it, records the exit status and signal into the pointer, and then exits. Dispatch returns once the supervisor reports the launch. The done-when would gain S19's measure: a real dispatch, the dispatching process gone, the worker SIGKILLed, and the exit status still recorded. Which session builds the supervisor is being agreed with S19. §3 is not dispatched until that is settled and the section text is revised.
