§1 — One session, one monitor, and during a wave it is five

The lead's requirement is that a coordinator session shows exactly one monitor, the follower, so the lead can track progress from one place. Measured on 2026-09-22 in the reckon session that wrote this plan: four investigation nodes dispatched to the locally served lane at 21:50:30 left four background shells running beside the follower. Each shell was a reckon crew dispatch process that had not returned. The process tree for each was the dispatch process, a second reckon process beneath it, and the claude worker beneath that. All four dispatch processes exited at 21:56:20 and 21:56:38, close to six minutes after launch, and all four workers were still alive and streaming afterwards. A fifth dispatch at 22:14:34 returned at 22:18:45, a hold of about four minutes. The skill tells coordinators to background every CLI dispatch, which is why the hold shows up as extra monitors rather than as a blocked turn.

The worker is launched with start_new_session=True in _spawn in reckon/crew/dispatch.py, and it survives its dispatch process exiting normally. What holds the dispatch process for six minutes is not established. An earlier session recorded that wrapping dispatch in timeout reaped its worker, so a dispatch ended by a signal during the hold may still take the worker with it. That is the case a host which expires background shells would hit.

§3 — Dispatch returns once the worker is launched

Make a CLI dispatch print its JSON result and exit as soon as the worker process is running and its live pointer is written. The worker must survive the dispatch process ending by any of the three signals in §2, including a signal that arrives during what is today the hold.

The hold is the post-launch tree snapshot, measured on 2026-09-23. After the worker launches, dispatch calls _repository_tree_snapshot(repo_root) (in dispatch in reckon/crew/dispatch.py, the line assigning record["repository_tree_snapshot"]). That runs git status --untracked-files=all once in every registered worktree, one after another, so the hold is the repository's worktree count multiplied by one tree's status time: 244 × 3.3 s on reckon. The snapshot is a boundary baseline, so its placement is constrained both ways. It must follow dispatch's own writes, as its comment says, and it must predate any write the worker makes in another tree. The supervisor takes it. The supervisor takes the snapshot after dispatch's writes and before it spawns the worker, then reports the launch. Dispatch never runs a scan that grows with the worktree count before it returns. If the snapshot raises, the supervisor records the failure in the run directory's snapshot-error.txt, still spawns the worker, and the pointer's repository_tree_snapshot carries {"available": false, "detail": ...}. A snapshot failure never kills a worker and never turns a launch into a refusal.

Readings pinned after the read-back

  • What dispatch's result means. Dispatch prints ok: true with the run id once the supervisor reports the worker's pid. It does not wait to see whether the worker lives. A worker that exits before dispatch returns is still ok: true, and its exit record reads ended_during: launch. ok: false means no worker was spawned.
  • The SIGKILL case. The signal goes to the dispatch process's pid alone, never its process group, which is how a host expiring a background shell ends it. The supervisor and the worker run in their own sessions.
  • The pointer write. The supervisor updates the pointer only by atomic rename over an existing file. It never creates one, so a discarded pointer stays discarded.
  • The stream count. stream_records_seen counts records across every path stream_paths_newest_first in reckon/crew/recovery.py returns for the run directory. ended_during is one of the record's fields.
  • §1 and §2 are superseded where they conflict. §1's "not established" and §2's three candidate holders predate the measurement. The holder is the tree snapshot above. §2's probe, tests/test_dispatch_lifetime_probe.py, is merged and opt-in (RECKON_RUN_DISPATCH_PROBE=1). It measured that the worker survives SIGTERM, SIGKILL and SIGHUP to the dispatch process's pid. That fits §1's timeout anecdote, because timeout signals the process group.

Collection of the worker's exit moves to a detached per-run supervisor, never to init. A worker reparented to init has its exit status collected by init, and reckon never sees it. Measured on 2026-09-23 on worker-death-is-recorded §5: 0 exit records across every live pointer after a night of at least eight worker deaths. So dispatch starts a small supervisor process in its own session. The supervisor spawns the worker, writes the worker's pid, and reports the launch back to dispatch, which then prints its result and exits. The supervisor waits on the worker and records its exit status and, when a signal ended it, the signal name. It writes that record to the run directory and to the live pointer, then exits. The supervisor writes the pointer only when the pointer still exists. It must never recreate a pointer that has gone, because a discarded pointer was rewritten back into existence by a late writer on 2026-09-23. The run-directory record is what survives a discard. Liveness stays read from the pointer's recorded worker pid by record_process_alive.

One exit record serves a death and a launch failure. The supervisor writes exit.json in the run directory, and copies the same object under the pointer's exit key while the pointer exists. Its fields:

FieldTypeMeaning
worker_pidintegerthe process the supervisor waited on
launched_atUTC ISO-8601when the worker process started
exited_atUTC ISO-8601when the supervisor collected the exit
exit_codeinteger or nullthe status for a normal exit; null when a signal ended it
signalinteger or nullthe signal number when a signal ended it; null otherwise
signal_namestring or nullfor example SIGKILL; null otherwise
stream_records_seenintegerrecords across the run's stream files at exit; 0 means the worker exited before its first record, which is a launch failure
last_record_typestring or nullthe type of the newest stream record, for example result, assistant or system; null when none was written
recorded_bystringsupervisor, so a reader can tell a collected exit from an inferred one

A reader composes nothing at read time that this record carries. The record also carries ended_during, one of launch or working. It reads launch exactly when stream_records_seen is 0, and is stated explicitly because a worker that never started and one that died while working need different recovery. A launch failure is this record with ended_during: launch, not a second format. crew-runtime-positive-controls' launch-failure record and a-stalled-row-says-whether-the-worker-lives' death row read these fields rather than deriving their own.

The record is named worker_exit wherever it outlives the run directory. exit_status is already taken: in all 2,721 ledger rows that carry it, it holds the gate command's status supplied at promotion (reckon-84's census, 2026-09-23). A worker's exit under the same key would be two quantities in one field. The pointer is deleted at promotion, so a record kept only on the pointer is destroyed by the act of recording the run. That is why no launch failure can be counted today in any project: 0 of 4,579 ledger rows. Carrying exit.json into the ledger row is §7.

Done when tests/test_dispatch_returns_without_worker.py covers four cases with the stub backend of §2, in a temporary repository and a temporary RECKON_HOME. First, the dispatch process exits within five seconds with the run id in its JSON output, nothing is killed, and the stub's marker file appears. Second, SIGKILL sent to the dispatch process before it returns still leaves the marker file appearing. Third, the measure from worker-death-is-recorded §5, verbatim: a real dispatch, the dispatching process gone, SIGKILL, and the exit status still recorded. Here the dispatch has returned, the worker receives SIGKILL, and within ten seconds both the run directory's exit record and the pointer carry the exit status with signal name SIGKILL. Fourth, the pointer is discarded before the worker exits, and after the exit no pointer exists for the run while the run directory's exit record does. The first case runs against a temporary repository holding at least 30 registered worktrees, so a scan that grows with the worktree count is visible in the time. The negative control is executed and logged: putting the tree snapshot back between the launch and dispatch's return makes the first case fail on the five-second bound, and removing the supervisor's wait makes the third case fail. Both failing logs are kept with the manifest. The real pointer directory under the user's config home is asserted untouched. The write paths are reckon/crew/dispatch.py and tests/test_dispatch_returns_without_worker.py.

§8 — A backend carries no worker cap

Measured by imas-ambix-61 at 13:17 UTC on 2026-09-23. reckon crew dispatch --local was refused with backend 'clive' is at its concurrency ceiling (65 live runs of 64 max). At that moment 69 clive pointers existed, 23 of them with a live process, and the lane's router gate reported 13 to 18 in flight against a width of 30. It counts every non-terminal live pointer, so it measured the promotion backlog across every project, not load on the engine. The reckon-ship contract states that no slot pool and no numeric worker cap exist anywhere in Reckon. The lead's position, relayed the same day, is that the cap is artificial: a session may hold its runs as long as it needs them. Dispatch stops enforcing max_concurrent_runs. The key stays readable in flight config, so existing host files remain valid, but it is ignored, exactly as backend concurrency keys already are.
