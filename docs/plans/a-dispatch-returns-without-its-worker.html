§1 — One session, one monitor, and during a wave it is five

The lead's requirement is that a coordinator session shows exactly one monitor, the follower, so the lead can track progress from one place. Measured on 2026-09-22 in the reckon session that wrote this plan: four investigation nodes dispatched to the locally served lane at 21:50:30 left four background shells running beside the follower. Each shell was a reckon crew dispatch process that had not returned. The process tree for each was the dispatch process, a second reckon process beneath it, and the claude worker beneath that. All four dispatch processes exited at 21:56:20 and 21:56:38, close to six minutes after launch, and all four workers were still alive and streaming afterwards. A fifth dispatch at 22:14:34 returned at 22:18:45, a hold of about four minutes. The skill tells coordinators to background every CLI dispatch, which is why the hold shows up as extra monitors rather than as a blocked turn.

The worker is launched with start_new_session=True in _spawn in reckon/crew/dispatch.py, and it survives its dispatch process exiting normally. What holds the dispatch process for six minutes is not established. An earlier session recorded that wrapping dispatch in timeout reaped its worker, so a dispatch ended by a signal during the hold may still take the worker with it. That is the case a host which expires background shells would hit.

§3 — Dispatch returns once the worker is launched

Make a CLI dispatch print its JSON result and exit as soon as the worker process is running and its live pointer is written. The worker must survive the dispatch process ending by any of the three signals in §2, including a signal that arrives during what is today the hold.

The hold is the post-launch tree snapshot, measured on 2026-09-23. After the worker launches, dispatch calls _repository_tree_snapshot(repo_root) (in dispatch in reckon/crew/dispatch.py, the line assigning record["repository_tree_snapshot"]). That runs git status --untracked-files=all once in every registered worktree, one after another, so the hold is the repository's worktree count multiplied by one tree's status time: 244 × 3.3 s on reckon. The snapshot is a boundary baseline, so its placement is constrained both ways. It must follow dispatch's own writes, as its comment says, and it must predate any write the worker makes in another tree. The supervisor takes it. The supervisor takes the snapshot after dispatch's writes and before it spawns the worker. The ordering needs no handshake, because starting the supervisor is dispatch's last repository-facing step. Every write dispatch makes inside a repository, including the worktree's creation and the session-member registration commit, completes before dispatch starts the supervisor. After that dispatch writes only the pointer, which lives under the configuration home outside every repository. Dispatch waits for neither the snapshot nor the spawn. It returns as soon as the supervisor process is running and the pointer naming it is written, so the scan delays the worker's start and never dispatch's return. Dispatch never runs, and never waits on, a scan that grows with the worktree count. The supervisor writes the snapshot to the run directory's tree-snapshot.json, and promotion's out-of-fence check (the reader of record.get("repository_tree_snapshot") in reckon/crew/promotion.py) reads it from there, falling back to the pointer field for runs dispatched before this change. If the snapshot raises, tree-snapshot.json carries {"available": false, "detail": ...} and the supervisor still spawns the worker. A snapshot failure never kills a worker and never turns a launch into a refusal.

Readings pinned after the read-back

  • What dispatch's result means. Dispatch prints ok: true with the run id once the supervisor process is running and the pointer records the supervisor's pid and start time. It waits for neither the snapshot nor the worker's spawn. A worker that is never spawned, or exits before its first stream record, is still ok: true, and its exit record reads ended_during: launch. ok: false means no supervisor was started.
  • The pointer's pid is the supervisor's. The supervisor lives from dispatch until it has recorded the worker's exit, so it is alive exactly while the run is, and record_process_alive keeps reading the pointer's pid unchanged. The worker's pid is written to the run directory's worker.json when the worker is spawned.
  • The SIGKILL case and crew stop. A signal to the dispatch process goes to its pid alone, never its process group, which is how a host expiring a background shell ends it. The supervisor starts its own session and process group, and spawns the worker inside that group rather than in a further session. terminate in reckon/crew/dispatch.py already signals the process group of the pointer's pid, so crew stop reaches the worker unchanged. The supervisor ignores SIGTERM and SIGHUP, so it survives to collect the exit the stop caused.
  • The supervisor never writes the pointer. Dispatch creates the pointer, and only dispatch, discard and promotion write it. Everything the supervisor produces (tree-snapshot.json, worker.json, exit.json) goes into the run directory. The supervisor never creates that directory: it opens each file inside it and, when the directory is gone, drops the write. So neither a late write nor a rename can bring a discarded run back.
  • The stream count. stream_records_seen counts records across every path stream_paths_newest_first in reckon/crew/recovery.py returns for the run directory. ended_during is one of the record's fields.
  • §1 and §2 are superseded where they conflict. §1's "not established" and §2's three candidate holders predate the measurement. The holder is the tree snapshot above. §2's probe, tests/test_dispatch_lifetime_probe.py, is merged and opt-in (RECKON_RUN_DISPATCH_PROBE=1). It measured that the worker survives SIGTERM, SIGKILL and SIGHUP to the dispatch process's pid. That fits §1's timeout anecdote, because timeout signals the process group.

Collection of the worker's exit moves to a detached per-run supervisor, never to init. A worker reparented to init has its exit status collected by init, and reckon never sees it. Measured on 2026-09-23 on worker-death-is-recorded §5: 0 exit records across every live pointer after a night of at least eight worker deaths. So dispatch starts a small supervisor process in its own session, writes the pointer naming the supervisor, and prints its result and exits. The supervisor takes the snapshot, spawns the worker, writes worker.json, waits on the worker, and records its exit status and, when a signal ended it, the signal name. It writes that record to the run directory, then exits. It never writes the pointer, because a discarded pointer was rewritten back into existence by a late writer on 2026-09-23. The run-directory record survives a discard that removes only the pointer, and a reader finds it through the run directory the pointer or ledger row names. When a discard also removes the run directory, the record's write is dropped and nothing is recreated.

One exit record serves a death and a launch failure. The supervisor writes exit.json in the run directory. It is the only copy. Its fields:

FieldTypeMeaning
worker_pidintegerthe process the supervisor waited on
launched_atUTC ISO-8601when the worker process started

A reader composes nothing at read time that this record carries. The record also carries ended_during, one of launch or working. It reads launch exactly when stream_records_seen is 0, and is stated explicitly because a worker that never started and one that died while working need different recovery. A launch failure is this record with ended_during: launch, not a second format. crew-runtime-positive-controls' launch-failure record and a-stalled-row-says-whether-the-worker-lives' death row read these fields rather than deriving their own. Where this record and an inferred death disagree, this record wins. worker-death-is-recorded names a death it infers interrupted. That label applies only to a run with no exit.json. When exit.json exists, its ended_during and exit fields are the collected fact, and a reader reports them.

The record is named worker_exit wherever it outlives the run directory. exit_status is already taken: in all 2,721 ledger rows that carry it, it holds the gate command's status supplied at promotion (reckon-84's census, 2026-09-23). A worker's exit under the same key would be two quantities in one field. The pointer is deleted at promotion, so a record kept only on the pointer is destroyed by the act of recording the run. That is why no launch failure can be counted today in any project: 0 of 4,579 ledger rows. Carrying exit.json into the ledger row is §7.

§8 — A backend carries no worker cap

Measured by imas-ambix-61 at 13:17 UTC on 2026-09-23. reckon crew dispatch --local was refused with backend 'clive' is at its concurrency ceiling (65 live runs of 64 max). At that moment 69 clive pointers existed, 23 of them with a live process, and the lane's router gate reported 13 to 18 in flight against a width of 30. The ceiling is max_concurrent_runs, declared for clive in the host flight config and enforced in dispatch in reckon/crew/dispatch.py, where a comment begins A backend at its declared concurrency ceiling refuses a new dispatch. It counts every non-terminal live pointer, so it measured the promotion backlog across every project, not load on the engine. The reckon-ship contract states that no slot pool and no numeric worker cap exist anywhere in Reckon. The lead's position, relayed the same day, is that the cap is artificial: a session may hold its runs as long as it needs them. Engine load is bounded by the router's admission gate, which answers 529 with Retry-After past its wait bound.

Only the roster bound retires. _refuse_over_concurrency_ceiling in reckon/crew/dispatch.py refuses on whichever of three bounds binds: the roster (max_concurrent_runs), the placement's admitted partition cores, and the login memory slice. This section removes the first. The partition-core and login-memory bounds protect real resources, and they stay enforced unchanged. Dispatch stops enforcing max_concurrent_runs. The key stays readable in flight config, so existing host files remain valid, but it is ignored, exactly as backend concurrency keys already are.
