§2 — A read-only run that commits nothing says so and promotes

Deliverable. A run whose recorded role is investigate or review has no commit to name. Its manifest may state commits: none, with or without a reason in parentheses after it, and the run promotes with the no-commit form of crew complete, its run record carrying the base revision and no commit as it does for any commitless run. Four such runs were refused on 2026-11-14 and 15 with the manifest line commits: none (read-only sandbox; nothing committed): two investigations and two plan reviews. The node names the condition that refused them and removes it. The prompt composed for those roles states this form of the line. A run of any role that states none while its worktree head is ahead of its base is still refused, naming the commits.

Done when a new test file shows, using the repository's shared test isolation: an investigate run carrying a brief and no plan, and a plan-review run, each with the manifest line above, pass the manifest check and promote with the no-commit form, and each run record names the base revision and no commit; the same with bare none; a run stating none with a commit beyond its base is refused, naming that commit; and the composed prompt for each role states the line. Negative control: the manifest names which case fails at the base revision and quotes its refusal. If every case passes at the base revision, the node reports the commit that changed the behaviour since 2026-11-14 and changes no product source. The test files that import the manifest check or the promotion evidence check add no failure against the base revision, and ruff check and ruff format --check add no finding on the staged paths.

§3 — A claims review record passes the review check

Deliverable. crew check --review judges a review record by the rubric the record names. A record under the claims rubric is complete when every claim it was asked to check carries a verdict; it is not asked for the six text scores. A record under a scored rubric that omits its scores is still refused.

Done when a new test file shows: a claims-rubric record with a verdict for every claim and no scores passes crew check --review; a claims-rubric record missing one claim's verdict is refused, naming the claim; a scored-rubric record without scores is refused as it is at the base revision; and the two claims-rubric records stored for this session's census and prototype reviews, copied into the test as fixtures, pass. Negative control: at the base revision the first case fails with a missing-scores refusal. The test files that import the review record check add no failure against the base revision, and ruff check and ruff format --check add no finding on the staged paths.

§4 — A delivered run that carries a brief gets its review

Deliverable. A delivered investigation run whose authority is a brief, with no plan and no section, owes a review like any other delivered run. The review duty pass composes and dispatches that review without the coordinator, and the obligations view names the duty until the review is stored.

Done when a new test file shows, with isolated crew state: a delivered investigate run carrying a brief and no plan produces one review dispatch from the duty pass, whose brief names the run's brief; a second pass dispatches nothing more; the obligations view lists the duty before the dispatch and not after the review is stored; and a delivered run that carries a plan section is handled as at the base revision. Negative control: at the base revision the first case dispatches nothing, and the node's manifest quotes that result. If the first case already passes at the base revision, the node instead reports which condition kept this session's two runs from being reviewed, with the pointer fields that show it, and changes no product source. The test files that import the review duty pass add no failure against the base revision, and ruff check and ruff format --check add no finding on the staged paths.

§5 — One plan's run records read in seconds

Deliverable. Reading the run records of one plan through the ledger's own read, in a fresh process against the committed store of this repository, answers in under five seconds, and its cost does not grow with the number of runs that belong to other plans.

Done when one gate log, written to the node's run directory on shared storage by one job on the rigel partition, shows five fresh-process reads of one plan's run records against the committed store at the base revision and at the head, each timed, with the head's slowest read under five seconds and the base's times beside it; and a new test file shows that a one-plan read over a synthetic store of 2,000 runs across 50 plans decodes no run document of another plan and returns the same rows as the unfiltered read filtered afterwards. Negative control: at the base revision the decode-count case fails. If the base revision already reads under five seconds on rigel, the node reports the five timings and changes no product source. The test files that import the ledger read add no failure against the base revision, and ruff check and ruff format --check add no finding on the staged paths.
