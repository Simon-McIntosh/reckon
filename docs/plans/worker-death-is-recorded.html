§1 — A killed worker is indistinguishable from a working one

A dispatched worker that is ended by a signal it did not choose writes nothing on the way out. Its live pointer keeps the phase it had when it died, which is almost always working, and the ledger has no field that could say otherwise. So the seat stays held, the roadmap keeps counting the run as in flight, and a reader looking at crew state cannot tell a worker that is mid-turn from one whose process left hours ago.

Nothing reconciles this later. There is no sweep that notices a recorded pid has no process behind it, so the pointer survives until a human opens it. The oldest such pointer measured on this workstation had been reporting working for three days.

The cost is not bookkeeping. It is that the correct recovery becomes unreachable. A worker killed mid-run is exactly the case resume exists for — its session holds every turn it had taken — but resume is chosen by a human who can see that the run needs resuming, and the state never says so. The alternative a hurried operator reaches for is promotion, which asserts the work finished and destroys the resume path in the process.

§2 — What the ledger looked like after one broadcast

A signal reaching every process of the account ended eight workers across three projects. Their pointers, inventoried afterwards:

Nine live pointers, none with a living process, and thirty commits of real work sitting in worktrees that the ledger described as still being written. One run held its only copy of a 63 KB evidence record as an untracked file, with no commit behind it — the case where a worktree reclaim takes the work outright and nothing reports the loss.

Four of the nine carry no session id at all, so resume was structurally unavailable for them however they were labelled. That is a second gap and §4 treats it as one.

§3 — Three separate things are missing

The symptom is one stale phase, but it has three independent causes and fixing any one alone leaves the failure intact.

The exit is not observed. The wrapper that launches a worker has the wait status in hand — it knows whether the process exited 0, exited non-zero, or was terminated by a signal, and which signal. None of it is kept. A worker that finished, one killed by a broadcast, and one killed by the out-of-memory killer are three different situations with three different recoveries, and the record flattens them into the same stale phase.

Liveness is never re-derived. A pointer is written once and believed indefinitely. The check is cheap and already exists elsewhere in the codebase: a recorded pid plus its start time answers both "is it alive" and "is this still the same process", the second being what stops a reused pid from reading as a survivor.

A session id is captured inconsistently. Resume depends on it, and four of nine runs did not have one. Until that is reliable, recording the death correctly still leaves half the runs with no route out of it.

§4 — The shape of the fix

Add the state the system is missing, then let the existing verbs reach it.

PhaseMeansRecovery
workingA process is running and was verified so wait
interrupted (new) Ended by a signal it did not choose; worktree intact resume where a session survives, otherwise redispatch the remainder
orphanedIts supervisor went, the worker may not have unchanged
stoppedTerminated deliberately through the tool unchanged
completeExited of its own accord having finished promote

interrupted is the concept the vocabulary lacks. orphaned is close but names the supervisor's fate rather than the worker's, and a run can be both. The distinction that matters to an operator is whether the work stopped because it was finished or because something ended it, and only the second is a candidate for resume.

The phase is worth little without the reason, so a terminated run records the signal that ended it. A run interrupted by a broadcast, by the out-of-memory killer, or by a deliberate cancellation look identical today and want different responses: the first is safe to resume immediately, the second says the node needs smaller bounds before it runs again, and the third should not be resumed at all.

§5 — Implementation

  1. Keep the wait status. The launcher records the exit code and, where the process was signalled, the signal number and name, against the run. Done when a worker killed with a known signal records that signal, and one that exits cleanly records its code, both readable from the run record without inspecting a log.
  2. Re-derive liveness on read. A pointer whose recorded pid has no process, or whose process start time no longer matches, is reported as not running rather than taken at face value. Done when a pointer whose process is gone stops reporting working, and a reused pid is not mistaken for a survivor.
  3. Introduce interrupted and set it from the two above. A run whose process ended by signal, or whose pid is dead with no recorded exit, becomes interrupted rather than staying in its last live phase. Done when the nine pointers in §2 classify correctly against their real state, and a completed run is never relabelled.
  4. Make the session id reliable. Establish why four of nine runs carried none and close that gap, because resume cannot be the answer for a run that cannot be resumed. Done when a dispatched run either carries a session id or records why it could not, and the count of runs without one is zero for new dispatches.
  5. Let the roadmap act on it. An interrupted run is surfaced as needing a decision rather than counted as in flight, and its seat is released so the lane is not held by a process that no longer exists. Done when a sprint containing interrupted runs reports them distinctly from running ones.
  6. Prove it end to end. A worker is dispatched, killed by signal, and the run reports interrupted with the signal named; it is then resumed and completes. Done when that sequence passes as a test rather than as a manual demonstration.

Steps one and two are independent and can land in either order. Step three depends on both. Step four is independent of all of them and is the one that decides whether the remedy is reachable in practice.

§6 — What this does not cover

This records a death; it does not prevent one. The broadcast that produced the evidence in §2 was a separate defect in a test fixture, repaired independently, and a worker can still be ended by the out-of-memory killer, a cancelled allocation or a host-level teardown. The point of the phase is that every one of those becomes legible rather than silent.

It also leaves worktree reclamation alone. The untracked evidence file in §2 survived because someone looked; making a worker commit its work before it can be interrupted is a different plan and a harder one.

§ Decisions

What is the phase called for a run ended by a signal it did not choose?

Locked to <code>interrupted</code>. It names what happened to the work rather than to the process, which is the distinction an operator acts on, and it sits cleanly beside <code>orphaned</code> (the supervisor went) and <code>stopped</code> (deliberate). <code>killed</code> was rejected because it reads as intentional, so a reader would reach for promote or discard rather than resume — the exact wrong turn this plan exists to prevent. <code>terminated</code> was rejected for colliding semantically with <code>stopped</code>.

When is liveness re-derived — on every read, or by a periodic sweep?

Locked to re-deriving liveness on every read. The failure being repaired was a stale record believed for three days, and a periodic sweep reintroduces a smaller version of exactly that by leaving a window in which crew state is knowably wrong. The accepted cost is one process check per pointer per read, which is negligible at the measured scale of nine pointers, and the start-time comparison that guards against pid reuse is already written elsewhere in this codebase.

Should an interrupted run with a live session resume automatically, or wait for a human?

Locked to waiting for an operator. The cause of an interruption may recur — a broadcast, an out-of-memory kill, a host teardown — and resuming straight back into it burns the surviving session for nothing. Automatic resume was rejected because repeated deaths from one underlying fault present as flakiness rather than as a single cause, which is what made the originating defect take two days to find. The accepted cost is one human action per interrupted run.
