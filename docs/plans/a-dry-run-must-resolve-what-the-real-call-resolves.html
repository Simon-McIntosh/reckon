§1 — A check that answers a narrower question, affirmatively

reckon crew dispatch --dry-run is documented as "validate and resolve only: no worktree, no process, no record". It validates the eight node-contract properties and it does not resolve the plan and section against the worktree base ref, nor the roster member against the repository. So it returns ok for a dispatch that cannot run, and the affirmative answer is what makes it dangerous: a refusal teaches, a false green gets written down.

Two measured instances, 2026-09-21, and they are same-shape-different-input.

Each row: a dry run that passed, and the real call that could not have.
What was dry-runDry runReal callWhat the dry run skipped
--plan S13 --section Summary --role review on imas-efit ok plan-unavailable A sprint resource carries data-reckon="sprint-items" and no <h2 id>, so no --section can resolve against it
--member codex-b on reckon, no --repo refused, naming --repo — Nothing — but --member codex-a, identically registered in the same roster, dispatched with no --repo at all

The first instance cost a false rule. The session that ran it recorded in its handoff that "the sprint slug is an acceptable --plan for review nodes", on the strength of the green. A later session read the handoff, dispatched, and got plan-unavailable. The dry run did not merely fail to help; it manufactured a durable false belief and handed it to the next reader.

The second row is the better instance precisely because it is the same command shape with one input changed, which rules out the caller. Two identically registered members of one roster resolve differently, and the refusal names a flag the working call never needed. One of those two behaviours is wrong and the surface does not say which.

A third case shares the shape and needs no separate row: a freshly created plan. edit_plan(create=True) writes the file, the dry run passes, and the real dispatch refuses — the worktree base is a commit and the file is not in it.

§2 — The dry run performs every resolution, and stops before the side effects

The fix is not more validation. It is moving the line the dry run stops at: it should do everything the real call does up to the first thing that changes the world, and nothing after. The real call resolves the repository, the roster member, the base ref, the plan file at that ref and the named section within it, the peer scope claims, the backend and the budget — and only then creates a worktree and spawns a process. The worktree is the boundary.

Every resolution named above is read-only and every one of them is skipped today. That is what makes this cheap: nothing new has to be computed, the calls already exist on the real path and are simply not reached when dry_run is set.

Write paths. reckon/crew/dispatch.py, tests/test_dry_run_resolves_the_real_call.py (new).

Done when a dry run naming a sprint id as --plan is refused with the same error code the real call returns, asserted against a synthesised sprint resource carrying sprint-items and no section heading; a dry run naming an uncommitted plan file is refused the same way, asserted; a dry run of a valid node still returns ok and still creates no worktree, no process and no run record, asserted by listing the worktree root and the pointer directory before and after and requiring both unchanged; and for one node, the dry run's refusal payload and the real call's refusal payload are asserted equal on error and on the set of resolution keys, because a dry run that refuses for a different reason than the real call is the same defect wearing the opposite sign.

§3 — Member resolution gives one answer, not two

Whatever the correct behaviour is, --member codex-a and --member codex-b must share it. Decide which is right — a member is resolvable from the project alone, or it requires a repository — and make both obey it. The evidence for the decision is in the roster: if members can be registered against several repositories then the repository is genuinely needed and the working call is the bug; if they cannot, the refusal is.

Write paths. reckon/crew/dispatch.py, tests/test_member_resolution_is_single_valued.py (new).

Done when two members registered identically in one project resolve identically, asserted by a test that registers two and dispatches both with the same flags and requires the same outcome; whichever behaviour is chosen, a member that genuinely cannot be resolved is refused with a message naming what would make it resolvable, asserted; and the single-valued property is expressed as a test over the roster rather than over two hardcoded ids, so a third member cannot acquire a third behaviour.

§4 — The general shape, and why it is worth a plan

This plan is one instance of a family reckon keeps producing, and the family is worth naming because the members do not look alike until they are stated together: a check answers a narrower question than the caller is asking, and answers it affirmatively. The caller reads the affirmative as an answer to their question, which it is not.

The discriminator that finds them is one question, and it costs nothing to ask: what would make this field wrong while it still printed the same value?

  • A dry-run ok survives a dispatch that cannot run — this plan.
  • A review status of parsed survives a reviewer that skipped four of the five things it was told to read.
  • A fresh stream mtime survives a worker writing nothing useful.
  • A plan-slug meta survives on a document that is not a plan.
  • A commit reachable from HEAD survives a merge that reverted its content.

Each one is a true statement standing in for the one that was needed. The remedy is always the same and is never more validation: make the check resolve the thing the caller is actually asking about, or make it say plainly that it did not.

Done when the discriminator question above is recorded in the dispatch surface's own documentation next to --dry-run, in one sentence, so the next person adding a check to this file meets it there rather than in a plan they would have to know to look for.
