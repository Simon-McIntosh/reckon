An orchestrator cannot forget its obligations

On 2026-09-25 the lead watched a follower show 3u for twenty minutes, and asked why the unpromoted jobs were not being treated. One of the three had no review in flight. Its worker had been resumed and had committed a new head, the reflex had reviewed only the old head, and the coordinator did not notice for about ten minutes. The lead asked for a root-cause fix: a heartbeat of pending tasks, or a checklist the orchestrator must review and maintain, linked to the task list the agent harness already has.

Fleet-release gate. The lead directed on 2026-09-25 that this plan belongs to the fleet-release gate wave, beside the S21 and S22 gates. Large-scale dispatch waits on §2 and §5: coordinators must not lose track of returning work before the fleet widens. §3 and §6 ship with them but do not gate. A repeating heartbeat line was considered and rejected, because a signal that repeats gets ignored. Every node here is sequenced as gate work, ahead of non-gate S24 nodes that contend for the same files.

§1 — Root cause

A coordinator's obligations live only in its own context. Every link in the chain is a place to forget:

  • The follower pushes each transition once. A run that became unpromoted produces one row and is silent afterwards, and its count persists without identity. an-orchestrator-is-bound-by-its-inbox §4 measures this.
  • The harness's own task list is maintained by the model and does not survive compaction reliably.
  • Nothing stops a turn from ending while work is outstanding. The reckon-build closure fence (§4d) is a rule the agent must remember to apply.

The remedy is to make obligations state that reckon derives, re-raises and enforces, rather than something the coordinator must remember.

§2 — Obligations are a derived view

crew(view="obligations", session=<id>) and reckon crew obligations --project P --session S list every item that needs this coordinator. Each item carries a kind, the run or plan, its age, and the exact next command. The kinds are:

  • review-missing: complete, and no review is stored or in flight for its current head
  • review-ready: a review is stored for its current head, and the run is not promoted
  • blocked or needs-help
  • turn-ended-early: a resumed or first turn ended without a terminal manifest while the process is gone
  • promotable-stale: complete and unpromoted beyond the grace period
  • worktree-held: a promoted run whose worktree is still registered

The list is computed from live pointers, the review store and the ledger, so it cannot drift from the fleet. Nothing is stored. It adds no classifier of its own. The kinds are read from reckon.crew.recovery.recover's per-run classification: scoring gives review-missing, promotable gives review-ready, and blocked and needs-help map to themselves. The closure figure is the drain view's unreconciled_runs. Each item carries identity and age, never a bare total, which satisfies the rule in an-orchestrator-is-bound-by-its-inbox §4: the oldest item's age, plus a count of items unchanged since the last read. The turn-ended-early and blocked kinds inherit the classifier's false-liveness defect until S21's liveness fix lands; §5 is gated on that fix for exactly that reason.

Done when:

  • A test with a synthetic config home covers one run of each kind, plus one healthy working run and one promoted run. It asserts exactly the six obligations appear, each with its kind, age and next command.
  • The working and promoted runs are absent.
  • A run whose head moved past its latest stored review reads review-missing, not review-ready.
  • The declared mutation, judging review freshness by run id rather than by head, is observed to fail. The log is recorded.

§3 — A deferral is recorded and expires

reckon crew ack --run X --reason "…" --until <iso-time> records a deliberate deferral, for example "waiting for S21 to release dispatch.py". It removes that obligation from the list until the deferral expires. The acknowledgement is stored beside the drain dispositions, and the obligations view shows acknowledged items in a separate block.

Done when: tests assert that an acknowledged obligation leaves the list, returns when its --until passes, and reads --reason back.

§5 — The harness is bound to the list

A Claude Code hook script, reckon/hooks/coordinator_obligations.py, reads the hook's JSON input and maps the Claude session to the crew session registered by that session's follower. It has two modes:

  • --hook prompt is used as the UserPromptSubmit and SessionStart hook. It returns the unacknowledged obligations as a checklist in additionalContext, with the line "mirror these into your task list; reckon's list is the authority". The current duties therefore open every turn and survive compaction.
  • --hook stop is used as the Stop hook. It returns {"decision": "block", "reason": <checklist>} while unacknowledged obligations remain, so the agent cannot end its turn into forgotten work. The block does not fire again once the agent has continued once for the same list (stop_hook_active), which avoids a loop.

The hooks are installed in ~/.claude/settings.json, the lead's decision on 2026-09-25, so every project's coordinator gets them. The hook resolves the reckon project from the session's working directory through the mounts, and it exits silently with no output when that directory is not a mounted project or no follower is registered. A session that is not coordinating reckon work therefore sees nothing.

reckon hooks install --scope user prints the settings snippet and merges it into ~/.claude/settings.json only with --write. It preserves existing hooks, and refuses when an entry with the same command already exists.

Gate: the Stop-hook half waits on S21's false-liveness fix (the first-commit "process gone" rows), so the hook never blocks a turn on a phantom obligation.

Done when:

  • Tests drive the script with recorded hook JSON: a session with obligations, one with none, one acknowledged, and a stop hook with stop_hook_active true.
  • They assert the exact output for each. The stop hook blocks only in the first case.
  • The installer's dry run prints the snippet and writes nothing.

The per-harness reference orchestrator-harness/claude-code.md documents the hook setup.

§7 — A worker's Stop is bound to its manifest

The same hooks reach background workers that run Claude Code. The local lane's clive launches claude with an additive --settings, so ~/.claude/settings.json hooks load in every such worker, as the native-agent guard already does. Codex workers read no Claude hooks. For them the supervisor's exit record and resume-ready remain the backstop.

On 2026-09-24 and 25, at least eight local-lane turns ended on a narration line without a terminal manifest. Each cost a manual resume, and followup f-tllitd-worker-turn-endings planned to answer it with prose in the worker contract. A hook enforces it instead, and adds a task-list reflex at the start.

  • Session start. Dispatch exports RECKON_RUN_ID and RECKON_MANIFEST into the worker environment. In worker mode, the prompt hook injects the node's done-when clauses as a checklist, with the instruction to load them into the task list and tick each as its evidence is recorded.
  • Stop. In worker mode, the Stop hook blocks while the manifest is absent or its status is not complete, blocked or failed. The reason names what is missing. It blocks at most three times per run, so a worker that genuinely cannot finish is never trapped. The stop it then allows is never silent. On that final allowed stop, the hook writes the terminal record itself: it sets the manifest's status to blocked, with the blocker "turn ended without a terminal manifest after 3 refusals", and keeps every line the worker already wrote. A manifest that does not exist yet is created holding that record. So the run always reaches the coordinator as a blocked run to resume, never as work left outstanding with no durable record. A plan review on 2026-09-25 found that without this the cap recreated the defect §1 describes.

Trigger: the environment export lives in reckon/crew/dispatch.py, so this section follows S21's stop-before-spawn node there. The hook-script half can land with §5.

Done when:

  • Hook tests with recorded worker JSON assert three cases: Stop is blocked when the manifest is missing or in-progress, allowed when it is complete, and allowed after the third block.
  • A dispatch test asserts that both variables reach the worker environment, and neither is persisted to disk beyond the existing overlay rule.
  • The declared mutation, making the Stop hook ignore manifest status, is observed to fail. The log is recorded.
