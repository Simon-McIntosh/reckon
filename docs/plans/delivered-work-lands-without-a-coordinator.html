§1 — Why: finished work waits on a queue and on a coordinator

A delivered run is finished work that has not been promoted and landed. While it sits, its section stays open, every section waiting on it stays awaiting-upstream, and the local lane runs below its width. On 16 November the lead saw most coordinator sessions carrying delivered work in the monitor and not acting on it. The readings below were taken that evening from the live crew home.

Four causes are established from the records and the code, and each has a section.

  • The queue is served in run-name order. A run id begins with the run's creation time, so a request is served by how old its run is, not by when it was asked for, what priority it carries or whose it is. At 21:22 UTC one session filed 67 requests for runs created that morning. Every request from a newer run went behind them: a review that gated a tick repair waited 25 minutes and counting, and a replay request sat an hour with no error. Coordinators read this as a stalled queue (§2).
  • A waiting request is never read again. Two power_convertor review requests were parked at 21:20:35 UTC because their manifests did not read complete. The manifests were repaired at 21:36 and crew check --manifest passed. At 22:08 crew complete returned the same waiting request, unchanged. The control: two reviews given the same repair at 20:43 promoted by 20:47 (§3).
  • The drain serves about 18 requests an hour, one at a time. A burst of 76 takes four hours (§4).
  • A finished run reads blocked on a transcription. A manifest repeats fields the tool issued: the write paths, the worktree and the base revision. 49 runs read blocked because that echo differs from the issued value, in two cases by one mistyped character of a revision (§5).

The coordinator's own share is real too. Promoting two read-only reviews from this plan's authoring session took three crew complete attempts over ten minutes: the first was refused for citing the base as a commit, the second for a gate field holding prose. The obligations view named crew observe as the next command for both, which does not promote (§6, §9). A count of complete pointers also overstates the backlog: at least one was the leftover of a run landed two days earlier (§9).

The measured distribution of delivered-to-landed time over seven days, the waits by stage, and the prototype of the largest remedy are in why delivered work sits unlanded, which a measurement node writes. Sections 6 to 10 take their baselines from it.

Out of scope, because other plans own it: the station's tick and the landing check (the-monitor-reads-each-fact-once), the run-store lock a promotion retries against (history-persists-as-detail-washes-out), and the index a landing commits through (a-landing-never-waits-on-a-shared-index). No section here removes a review or a gate from the path. The question throughout is who makes the next move and how many moves there are.

§2 — The promotion queue serves by priority, then fairly, then by age

Why. §1, first cause. One session's burst of 67 requests held every other session's promotions for hours, including the review that gated a repair the lead had marked top priority.

Deliverable. The order in which waiting promotion requests are served follows the same rules the admission queue already applies to launches: a review of a delivered run goes ahead of the run it reviews; a request that has waited past the starvation bound goes next; then requests carrying a priority, highest first, where a request inherits the priority of its run; then one request per session in turn, the session with the fewest promotions served in the current window first; and within a session, oldest request first. The order is computed in one place and the queue report shows each request's position and the rule that placed it.

Done when. A test builds a queue of 67 requests from session A for runs created early and, filed afterwards, one request each from sessions B and C for newer runs and one from A carrying priority 100. It asserts the served order begins with the priority request, then alternates A, B, C, so B's and C's requests are both served within the first four. A second case asserts a request waiting past the starvation bound is served before a younger prioritised one, and a third that a queued review precedes the run it reviews. Negative control: with the order reverted to run name, the first case fails because B's and C's requests are served 68th and 69th. The importers of the touched module add no failure against the base, run on all_debug with at most -n 4. Write paths: reckon/crew/promotion_requests.py and tests/test_the_promotion_queue_serves_fairly.py.

§3 — A waiting promotion request is read again when its condition clears

Why. §1, second cause. A request parked as waiting holds no promotion slot, which is right, and is then never looked at, which leaves a repaired run waiting for ever with no verb that restarts it.

Deliverable. A request in the waiting state is promoted without anyone re-requesting it once the condition it waits on holds. A repeated crew complete for a run with a waiting request re-evaluates that request and reports the fresh verdict, not the stored one. A request that has waited longer than a stated bound becomes an obligation for its session that names the reason and the time it was last checked.

Done when. A test parks a review request on a manifest that does not read complete, repairs the manifest, runs one drain pass and finds the request promoted, with its checked_at later than the repair. A second case asserts a repeated complete on the still-unrepaired request returns a fresh checked_at and the same reason, and on the repaired one promotes. A third asserts the obligation appears once the bound has passed and names the reason. Negative control: copies of the two request records named in §1, replayed against today's drain with repaired manifests, remain waiting with checked_at unchanged. Importers add no failure against the base, on all_debug, at most -n 4. Write paths: reckon/crew/promotion_requests.py, reckon/crew/recovery_review_acceptance.py and tests/test_a_waiting_promotion_is_read_again.py.

§4 — The drain keeps up with a burst

Why. §1, third cause. Fair order decides who waits; it does not shorten the wait. At 18 requests an hour, a wave of landings from four sessions outruns the drain every evening.

Deliverable. The drain settles waiting requests at no less than 60 an hour on this workstation's store, so the burst of 16 November clears in under 80 minutes. Requests that cannot interfere are served together: a read-only review's promotion, which writes no commit, does not wait behind a promotion that lands one, and promotions for different repositories do not wait on each other. Two promotions that land commits on one branch are still taken one at a time. The queue report gives the service rate over the last hour and the stage that bounded it.

Done when. A replay harness loads copies of the 76 request records of 16 November 22:15 UTC and their run records into a temporary crew home and drains them. The measured rate is at least 60 an hour against a base measurement on the same harness, the real crew home's listing is identical before and after, and every request settles with the verdict the base gives it. A test asserts a commit-less review promotion completes while a landing promotion for the same repository is still running, and that two landing promotions for one branch never overlap. Negative control: the same harness at the base revision drains at the base rate and the overlap test fails. The harness runs on rigel; importers add no failure against the base, on all_debug. Write paths: reckon/crew/promotion_requests.py, reckon/crew/queue_landing.py, tests/test_the_drain_keeps_up_with_a_burst.py and the replay harness under scripts/.

§5 — A finished run is not blocked by a mistyped echo of what the tool issued

Why. §1, fourth cause. The worktree, the base revision and the declared write paths are facts the tool holds on the run's own pointer. Asking a worker to copy them into its manifest and then blocking on the copy turns a typing slip into a stopped run: 49 of them on one evening.

Deliverable. A run whose manifest echo of a tool-issued field differs from the pointer is classified from the pointer and from what the run actually did: the worktree it committed in and the paths its commits changed. The difference is recorded on the run as a repaired echo, and the run is delivered when its work is otherwise complete. A run stays blocked only for a difference in substance: commits in a different worktree, a base that is not an ancestor of its head, or changed paths outside its declared scope.

Done when. A test gives the classifier three manifests on otherwise complete runs: one with a single wrong character in the base revision, one with the write paths listed in another order with one omitted, and one whose commits touch a path outside the declared scope. The first two classify as complete with the repaired field recorded; the third stays blocked and names the path. Negative control: at the base revision the first two classify blocked. A replay over copies of the 49 pointers of 16 November reports how many become deliverable and how many stay blocked for substance, with the real crew home untouched. Importers of the classifier add no failure against the base, on all_debug. Write paths: the manifest classifier module the design review names, and tests/test_a_mistyped_echo_does_not_block_a_run.py.

§6 — A delivered run with a clean review is promoted with no coordinator turn

Why. A coordinator is the slowest stage a finished run meets: it may be mid-turn, stopped at a usage limit, or closed. Where nothing remains to decide, waiting for it adds only delay. And when a coordinator does act, it should not have to know that a read-only run has no commit or that a review has no gate.

Deliverable. A run is promoted by the crew itself, with no command from its coordinator, when all of these hold: its manifest reads complete; its review is stored with no blocking finding and every finding answered or disposed; its gate record carries the command, the exit status and the log; and its changed paths lie inside its declared scope. The promotion records that it was made without a coordinator and by which rule. A run that fails any condition is left for its coordinator with the failed condition named. Whether a run has a commit and whether it has a gate are read from the run's own record, so a read-only or review run needs neither flag from anyone. A project can turn the behaviour off in its flight configuration.

Done when. In a temporary crew home, a delivered run meeting the four conditions is promoted within one pass of the service that owns the move, and its ledger row names the rule; four sibling runs, each failing one condition, are left delivered with that condition named in the obligations view. A read-only review run with no commit and a prose gate field is promoted as commit-less and gate-less from its record. With the project switch off, none is promoted. Negative control: at the base revision the first run is still delivered after ten passes. The delivered-to-promoted median for qualifying runs on the replay of the seven-day record in the research document falls below five minutes. Importers add no failure against the base, on all_debug. Write paths: the modules the design review names for the owning service and the promotion preconditions, the flight schema and its generated JSON, and tests/test_a_clean_delivered_run_is_promoted_unattended.py.

§7 — Concurrent edits to one file land with no coordinator move when they merge clean

Why. File holds are gone: on 16 November no request in the live queue waited on a file, and every wait was a declared section wait. Two or more sessions now edit one source file in separate worktrees and meet at the merge. Each landing moves the primary branch under every other reviewed head, so the cost of that freedom is paid at landing, and today a coordinator pays it by hand.

Deliverable. A reviewed head whose merge with the current primary branch is textually clean lands with no coordinator move, however many peers have landed in the same files since its review. The merged tree is proved by the run's own gate, re-run at the merged head on the project's measurement partition, and the landing is refused only if that gate adds a failure. A head whose merge conflicts is returned to the worktree that produced it, as a repair round that names the conflicting files and the commits that introduced the other side, and re-enters the queue when repaired, with its review covering only the repair. When several heads are waiting, they are merged in one candidate where they merge clean together, so one gate run proves the set.

Done when. In a temporary repository, three worktrees each change a different function of one file and are delivered with passing gates. All three land with no command beyond their promotion, the branch holds all three changes, and the merged-head gate ran once for the set. A fourth worktree changing the same lines as the first is returned as a repair round naming the file and the first's commit, and lands after its repair with no second full review. A fifth merges clean but breaks the gate at the merged head and is refused naming the added failure. Negative control: at the base revision the second and third landings each need a coordinator command after the first moves the branch. The research document's count of landings delayed by a moved branch is the baseline; the same replay shows none delayed. Runs on all_debug. Write paths: reckon/crew/merge.py, reckon/crew/queue_landing.py and tests/test_concurrent_edits_land_unattended.py.

§8 — A wave of landings is one list and one decision

Why. Ten runs delivering in an hour are ten separate landings today, each with its own commands and output for the coordinator,. A session that keeps its lane full is the one that is swamped. The restarts each landing causes are §11.

Deliverable. What is left to a coordinator after §6 and §7 arrives as one list: the runs that need a decision, each with the one condition that failed and the one command that answers it, in at most 400 characters a run. A coordinator can accept every listed run whose only open condition is its own confirmation in one command.

Done when. With twelve delivered runs in a temporary crew home, of which nine qualify under §6, the coordinator's list holds three rows inside the size bound and one command lands the two that need only confirmation. Negative control: at the base revision the list holds twelve rows. Importers add no failure against the base, on all_debug. Write paths: reckon/crew/station_obligations.py and tests/test_a_wave_of_landings_is_one_decision.py.

§9 — The pane and the obligations view say what is owed and how to pay it

Why. The d counter told every coordinator it held delivered work and nothing more. The obligations row for a delivered review named a command that does not promote it. A pointer left behind by a run landed two days earlier counted as delivered. A coordinator that cannot tell what is owed, or is told the wrong move, stops reading the counter.

Deliverable. The delivered count holds only runs that are finished and unpromoted. Runs whose promotion is requested and waiting in the queue are counted apart, with the queue position of the oldest, so a coordinator can see that the next move is the drain's and not its own. A pointer whose run is already in the ledger as landed is not counted and is reported for removal. Each obligations row for a delivered run carries the command that promotes that run as it stands.

Done when. A test builds a session holding one delivered run with no request, two with requests waiting, and one leftover pointer of a landed run. The pane row reads one delivered and two in the promotion queue; the leftover appears in neither and is listed for removal. The obligations row's command, run verbatim, promotes the delivered run, for an implementation run, a read-only run and a review run. Negative control: at the base revision the pane reads four delivered and the review row's command leaves the run delivered. The ticker's colour tests run in the environment its own test file names. Importers add no failure against the base, on all_debug. Write paths: reckon/crew/station_obligations.py, the ticker module the design review names, and tests/test_delivered_rows_say_what_is_owed.py.

§10 — Shown on the fleet: a day of landings

Why. Every section above is proved in a temporary crew home. The lane widens only if the live fleet lands faster.

Deliverable. A measurement over 24 hours of the live fleet after §2 to §9 have landed, by the same census the research document used for its seven-day baseline.

Done when. The evidence record holds, for those 24 hours and beside the baseline: the delivered-to-landed median and 90th percentile; the largest number of delivered runs any session held at one instant and for how long; the promotion queue's longest wait; the count of runs blocked on a repaired echo; and the count of landings a coordinator made by hand. §11 — A window of landings is one reload

Why. Every landing that changes reckon's own code makes each standing service reload onto the new code. On 16 November the primary branch took about 25 landings an hour, and reload images were built at 22:01, 22:10, 22:17 and 22:22 UTC, one every five to nine minutes. The station's log for the day holds 64 lines announcing a held reload and 58 re-executions. A due reload pauses new work, waits for work in flight, and starts a fresh process whose first tick runs cold; a tick takes four to seven minutes. So the station spends most of its time pausing or restarting, and its exported state is written only when a whole tick fits between two landings: one session watched the export go 29 minutes without a rewrite while the process stayed alive at 86 % of a core. Stale obligations and false "producer lost" rows follow, and so does a coordinator that stops trusting its pane. The admission service, which runs the promotion drain, restarts the same way.

Deliverable. A standing service takes the code changes of a window in one reload. Between two reloads of one service at least one stated window passes, and at least one tick started after the earlier reload has finished and exported its state. A change that must be live at once has one command a coordinator can run, which reloads the named service without waiting for the window and records who asked and why. The service reports the code it runs, the newest code it has seen, and when it will next reload, so "running older code" reads as a schedule, not as a fault. The window is a flight setting with a stated default of 30 minutes.

Done when. A test drives a stand-in service through twelve code changes arriving five minutes apart on a controlled clock and counts two reloads in the hour, each preceded by a completed, exported tick; with the immediate-reload command issued after the third change it counts one more, recorded with its reason. A second case asserts the status report names the running code, the newest seen and the next reload time. Negative control: at the base revision the same drive reloads twelve times and no tick completes between them. On the live fleet, over the two hours after this lands, the station's log shows no more than five re-executions and the exported snapshot's age never exceeds twice the tick time, read from the station's own tick record; the same two hours of 16 November 21:00 to 23:00 UTC are the baseline. The test runs on all_debug with at most -n 4, and the importers of the touched modules add no failure against the base. Write paths: reckon/crew/station.py, the reload module and the flight schema with its generated JSON as the design review names them, and tests/test_a_window_of_landings_is_one_reload.py.
