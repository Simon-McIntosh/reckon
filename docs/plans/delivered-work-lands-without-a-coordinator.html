§1 — Why: finished work waits on a queue and on a coordinator

A delivered run is finished work that has not been promoted and landed. While it sits, its section stays open, every section waiting on it stays awaiting-upstream, and the local lane runs below its width. On 16 November the lead saw most coordinator sessions carrying delivered work in the monitor and not acting on it. The readings below were taken that evening from the live crew home.

Four causes are established from the records and the code, and each has a section.

  • The queue is served in run-name order. A run id begins with the run's creation time, so a request is served by how old its run is, not by when it was asked for, what priority it carries or whose it is. At 21:22 UTC one session filed 67 requests for runs created that morning. Every request from a newer run went behind them: a review that gated a tick repair waited 25 minutes and counting, and a replay request sat an hour with no error. Coordinators read this as a stalled queue (§2).
  • A waiting request is never read again. Two power_convertor review requests were parked at 21:20:35 UTC because their manifests did not read complete. The manifests were repaired at 21:36 and crew check --manifest passed. At 22:08 crew complete returned the same waiting request, unchanged. The control: two reviews given the same repair at 20:43 promoted by 20:47. A replay later showed why the two differ: a pass over the queue does re-read a parked request, but it stops at the first request that cannot get a slot, so under a full queue the parked ones are never reached (§3 for the repeated call, §12 for the pass).
  • The drain serves about 18 requests an hour, one at a time. A burst of 76 takes four hours (§4).
  • A finished run reads blocked on a transcription. A manifest repeats fields the tool issued: the write paths, the worktree and the base revision. 49 runs read blocked because that echo differs from the issued value, in two cases by one mistyped character of a revision (§5).

The coordinator's own share is real too. Promoting two read-only reviews from this plan's authoring session took three crew complete attempts over ten minutes: the first was refused for citing the base as a commit, the second for a gate field holding prose. The obligations view named crew observe as the next command for both, which does not promote (§6, §9). A count of complete pointers also overstates the backlog: at least one was the leftover of a run landed two days earlier (§9).

The seven-day census gives the scale: 3,403 completions across 18 projects, and for the 845 runs carrying commits a median of 1.86 hours and a 90th percentile of 8.61 hours from delivery to the primary branch. Its largest block of waiting, 4,542 run-hours, cannot be split between a session that never learned of a delivery and one that learned and did not act, because nothing records either (§13); the record does not support blaming coordinator attention. The distribution, the waits by stage, and the replay of the parked-request defect are in why delivered work sits unlanded, written by a measurement node and landed with that run. §4 to §13 take their baselines from it.

Out of scope, because other plans own it: the station's tick and the landing check (the-monitor-reads-each-fact-once), the run-store lock a promotion retries against (history-persists-as-detail-washes-out), and the index a landing commits through (a-landing-never-waits-on-a-shared-index). No section here removes a review or a gate from the path. The question throughout is who makes the next move and how many moves there are.

§2 — The promotion queue serves by priority, then fairly, then by age

Why. §1, first cause. One session's burst of 67 requests held every other session's promotions for hours, including the review that gated a repair the lead had marked top priority.

Deliverable. The order in which waiting promotion requests are served follows the same rules the admission queue already applies to launches: a review of a delivered run goes ahead of the run it reviews; a request that has waited past the starvation bound goes next; then requests carrying a priority, highest first, where a request inherits the priority of its run; then one request per session in turn, the session with the fewest promotions served in the current window first; and within a session, oldest request first. The order is computed in one place and the queue report shows each request's position and the rule that placed it.

Done when. A test builds a queue of 67 requests from session A for runs created early and, filed afterwards, one request each from sessions B and C for newer runs and one from A carrying priority 100. It asserts the served order begins with the priority request, then alternates A, B, C, so B's and C's requests are both served within the first four. A second case asserts a request waiting past the starvation bound is served before a younger prioritised one, and a third that a queued review precedes the run it reviews. Negative control: with the order reverted to run name, the first case fails because B's and C's requests are served 68th and 69th. The importers of the touched module add no failure against the base, run on all_debug with at most -n 4. Write paths: reckon/crew/promotion_requests.py and tests/test_the_promotion_queue_serves_fairly.py.

§3 — A waiting promotion request is read again when its condition clears

Why. §1, second cause. A request parked as waiting holds no promotion slot, which is right, and is then never looked at, which leaves a repaired run waiting for ever with no verb that restarts it.

Deliverable. A request in the waiting state is promoted without anyone re-requesting it once the condition it waits on holds. A repeated crew complete for a run with a waiting request re-evaluates that request and reports the fresh verdict, not the stored one. A request that has waited longer than a stated bound becomes an obligation for its session that names the reason and the time it was last checked.

Done when. A test parks a review request on a manifest that does not read complete, repairs the manifest, runs one drain pass and finds the request promoted, with its checked_at later than the repair. A second case asserts a repeated complete on the still-unrepaired request returns a fresh checked_at and the same reason, and on the repaired one promotes. A third asserts the obligation appears once the bound has passed and names the reason. Negative control: copies of the two request records named in §1, replayed against today's drain with repaired manifests, remain waiting with checked_at unchanged. Importers add no failure against the base, on all_debug, at most -n 4. Write paths: reckon/crew/promotion_requests.py, reckon/crew/recovery_review_acceptance.py and tests/test_a_waiting_promotion_is_read_again.py.

§4 — The drain keeps up with a burst

Why. Fair order decides who waits; it does not shorten the wait. Over 27.6 hours to 22:16 UTC on 16 November the drain recorded 1,055 outcomes of which 244 were promotions: 8.8 successful promotions an hour against 38 outcomes an hour, the rest refusals and deferrals. At 22:15 UTC 87 requests waited and 15 settled in the following hour. The drain already serves two requests at a time under a lease, and the landing measurement runs two wide; a slot stays held through locks, gate work and bookkeeping.

Deliverable. The drain settles at least 30 promotions an hour on this workstation's store while a burst is waiting, and a request that cannot succeed yet does not spend a slot. Requests that cannot interfere are served together: a promotion that writes no commit does not wait behind one that lands a commit, and promotions for different repositories do not wait on each other. Two promotions that land commits on one branch are still taken one at a time. The queue report gives successful promotions over the last hour apart from refusals and deferrals, and the stage that bounded the rate. The existing lease and width are extended, not replaced.

Done when. A replay harness loads copies of the request records of 16 November 22:15 UTC and their run records into a temporary crew home and drains them. Successful promotions an hour are at least 30 and at least three times the base measured on the same harness, the real crew home's listing is identical before and after, and every request settles with the verdict the base gives it. A test asserts a commit-less promotion completes while a landing promotion for the same repository is still running, and that two landing promotions for one branch never overlap. Negative control: the harness at the base revision drains at the base rate and the overlap test fails; a harness given an empty request directory reports no rate and fails. The harness runs on rigel; importers add no failure against the base, on all_debug. Write paths: reckon/crew/promotion_requests.py, reckon/crew/queue_landing.py, reckon/crew/landing_measure.py, scripts/replay_promotion_drain.py and tests/test_the_drain_keeps_up_with_a_burst.py.

§5 — A finished run is not blocked by a mistyped echo of what the tool issued

Why. §1, fourth cause. The worktree, the base revision and the declared write paths are facts the tool holds on the run's own pointer. The orientation check that compares a manifest's copy of them already sorts the path list, so a reordered list passes today; an omitted path or one wrong character of a revision blocks a finished run. 49 runs read blocked this way on one evening.

Deliverable. The existing orientation check, and the one other reader of its result, classify a run from the pointer and from what the run did: the worktree it committed in and the paths its commits changed. A difference in the manifest's copy alone is recorded on the run as a repaired echo and does not block. A run stays blocked only for a difference in substance: commits in another worktree, a base that is not an ancestor of its head, or changed paths outside its declared scope. No second classifier is added.

Done when. A test gives the check three manifests on otherwise complete runs: one wrong character in the base revision, the write paths with one omitted, and commits touching a path outside the declared scope. The first two classify complete with the repaired field recorded; the third stays blocked and names the path. Negative control: at the base revision the first two classify blocked. A replay over copies of the blocked pointers of 16 November reports how many become deliverable and how many stay blocked for substance, with the real crew home untouched, and fails if it read no pointer. Importers of the two modules add no failure against the base, on all_debug. Write paths: reckon/crew/dispatch_sessions.py, reckon/crew/recovery_classification.py and tests/test_a_mistyped_echo_does_not_block_a_run.py.

§6 — A review or report run is promoted from its own record

Why. A clean implementation run is already promoted and landed by the crew with no coordinator turn. A review is not, although it merges nothing. Of one session's 163 delivered runs, 61 were reviews, and 51 of those were refused until their manifests were edited by hand because the worker had written a sentence after "none" in the commits field. A review whose gate field held prose was refused as a failed gate. A portfolio review was refused for having no record path keyed to a head, which its composer never grants, and was shown as ready all the while. Refusals account for 649 run-hours of the week's waiting.

Deliverable. The existing unattended promoter's eligibility is extended to every run whose deliverable is a report: a composed run review, a plan review, a code review, and a portfolio or sprint review that is keyed to no head. Whether a run has a commit, and whether it has a gate, are read from its role and its record, so a commits field reading "none" followed by an explanation, and a review with no gate command, are promoted as commit-less and gate-less with no flag from anyone. A run that is not eligible is left for its coordinator with the one failed condition named. The plan-level landing reservation that already turns unattended landing off is the only switch; no new setting is added.

Done when. In a temporary crew home, four delivered runs are promoted within one pass with no command: a composed run review, a code review whose manifest gate field holds prose, a review whose commits field reads "none" and a sentence, and a portfolio review with no head-keyed record. Each ledger row names the rule that promoted it. An implementation run with a failing merged-head gate is still refused and names its test ids, and a plan reserving manual landing leaves all of them delivered. Negative control: at the base revision the four stay delivered after ten passes. Copies of the 61 review manifests named in the research record replay with at least 51 promoted that were refused at the base. Importers add no failure against the base, on all_debug. Write paths: reckon/crew/recovery_review_acceptance.py, reckon/crew/promotion_checks.py, reckon/crew/recovery_review_delivery.py and tests/test_a_report_run_is_promoted_from_its_record.py.

§7 — Concurrent edits to one file land with no coordinator move when they merge clean

Why. File holds are gone: on 16 November no request in the live queue waited on a file, and every wait was a declared section wait. Two or more sessions now edit one source file in separate worktrees and meet at the merge. Each landing moves the primary branch under every other reviewed head, so the cost of that freedom is paid at landing, and today a coordinator pays it by hand.

Deliverable. Clean runs are already promoted and landed by the crew; this section is about what happens when the branch has moved. A reviewed head whose merge with the current primary branch is textually clean lands with no coordinator move, however many peers have landed in the same files since its review. The merged tree is proved by the run's own gate, re-run at the merged head on the project's measurement partition, and the landing is refused only if that gate adds a failure. A head whose merge conflicts is returned to the worktree that produced it, as a repair round that names the conflicting files and the commits that introduced the other side, and re-enters the queue when repaired, with its review covering only the repair. When several heads are waiting, they are merged in one candidate where they merge clean together, so one gate run proves the set.

Done when. In a temporary repository, three worktrees each change a different function of one file and are delivered with passing gates. All three land with no command beyond their promotion, the branch holds all three changes, and the merged-head gate ran once for the set. A fourth worktree changing the same lines as the first is returned as a repair round naming the file and the first's commit, and lands after its repair with no second full review. A fifth merges clean but breaks the gate at the merged head and is refused naming the added failure. Negative control: at the base revision the second and third landings each need a coordinator command after the first moves the branch. The research document's count of landings delayed by a moved branch is the baseline; the same replay shows none delayed. Runs on all_debug. Write paths: reckon/crew/merge.py, reckon/crew/queue_landing.py and tests/test_concurrent_edits_land_unattended.py.

§8 — A wave of landings is one list and one decision

Why. Ten runs delivering in an hour are ten separate landings for a coordinator today. One manual landing returned 60 kB of output; two returned 121 kB. A session that keeps its lane full is the one that is swamped: the largest backlog held by one session in the week was 195 delivered runs, and a second took 46 hours to reach zero.

Deliverable. What is left to a coordinator after §6 and §7 arrives as one list: the runs that need a decision, each with the one condition that failed and the one command that answers it, in at most 400 characters a run, with the full evidence one read away. The existing completion verb accepts several runs in one call, so a coordinator confirms every listed run whose only open condition is its own confirmation at once; no new verb is added. A landing's reply is under 2 kB and links its full record.

Done when. With twelve delivered runs in a temporary crew home, of which nine are eligible under §6 and §7, the list holds three rows inside the size bound, one call of the completion verb naming two runs lands both, and each reply is under 2 kB and names a readable record. Negative control: at the base revision the list holds twelve rows and a second run named on one call is refused. The help-contract tests pass with the widened option. Importers add no failure against the base, on all_debug. Write paths: reckon/crew/obligations.py, reckon/crew_run_commands.py, tests/test_crew_help_names_its_state.py and tests/test_a_wave_of_landings_is_one_decision.py.

§9 — The pane and the obligations view say what is owed and how to pay it

Why. The d counter told every coordinator it held delivered work and nothing more. Of 75 entries on one session's obligations list, about 60 told it to run the completion verb for runs whose promotion was already waiting in the queue. The row for a delivered review named a command that does not promote it. A pointer left behind by a run landed two days earlier counted as delivered. A coordinator told to repeat what it has done stops reading the list.

Deliverable. The delivered count holds only runs that are finished and for which no promotion has been asked. Runs whose promotion is requested and waiting are counted apart, with the queue position of the oldest, and are not listed as owed. A pointer whose run is in the ledger as landed is not counted and is reported for removal. Each row for a delivered run carries the command that promotes that run as it stands. The count is corrected where it is classified, so the pane and every other reader agree.

Done when. A test builds a session holding one delivered run with no request, two with requests waiting, and one leftover pointer of a landed run. The pane row reads one delivered and two in the promotion queue; the obligations view lists one run as owed; the leftover appears in neither and is listed for removal; and the MCP view returns the same three numbers. The owed row's command, run verbatim, promotes an implementation run, a read-only run and a review run. Negative control: at the base revision the pane reads four delivered, the view lists three as owed, and the review row's command leaves the run delivered. The ticker's colour tests run in the environment their own file names. Importers add no failure against the base, on all_debug. Write paths: reckon/crew/ticker.py, reckon/crew/obligations.py and tests/test_delivered_rows_say_what_is_owed.py.

Why. Every section above is proved in a temporary crew home. The lane widens only if the live fleet lands faster.

Deliverable. A measurement over 24 hours of the live fleet after the other sections have landed, by the same census the research record used for its seven-day baseline.

§11 — A window of landings is one reload

Why. Every landing that changes reckon's own code makes each standing service reload onto the new code. On 16 November the primary branch took about 25 landings an hour, and reload images were built at 22:01, 22:10, 22:17 and 22:22 UTC, one every five to nine minutes. The station's log for the day holds 64 lines announcing a held reload and 58 re-executions. A due reload pauses new work, waits for work in flight, and starts a fresh process whose first tick runs cold; a tick takes four to seven minutes. So the station spends most of its time pausing or restarting, and its exported state is written only when a whole tick fits between two landings: one session watched the export go 29 minutes without a rewrite while the process stayed alive at 86 % of a core. Stale obligations and false "producer lost" rows follow, and so does a coordinator that stops trusting its pane. The admission service, which runs the promotion drain, restarts the same way.

Deliverable. A standing service takes the code changes of a window in one reload. Between two reloads of one service at least one stated window passes, and at least one tick started after the earlier reload has finished and exported its state. A change that must be live at once has one command a coordinator can run, which reloads the named service without waiting for the window and records who asked and why. The service reports the code it runs, the newest code it has seen, and when it will next reload, so "running older code" reads as a schedule, not as a fault. The window is a flight setting with a stated default of 30 minutes.

Done when. A test drives a stand-in service through twelve code changes arriving five minutes apart on a controlled clock and counts two reloads in the hour, each preceded by a completed, exported tick; with the immediate-reload command issued after the third change it counts one more, recorded with its reason. A second case asserts the status report names the running code, the newest seen and the next reload time. Negative control: at the base revision the same drive reloads twelve times and no tick completes between them. On the live fleet, over the two hours after this lands, the station's log shows no more than five re-executions and the exported snapshot's age never exceeds twice the tick time, read from the station's own tick record; the same two hours of 16 November 21:00 to 23:00 UTC are the baseline. The test runs on all_debug with at most -n 4, and the importers of the touched modules add no failure against the base. Write paths: reckon/crew/station.py, the reload module and the flight schema with its generated JSON as the design review names them, and tests/test_a_window_of_landings_is_one_reload.py.

§12 — A parked request is reconsidered while every slot is taken

Why. When no promotion slot is free, a pass over the queue stops at the first request that cannot get one and never reaches the parked requests behind it. In a replay of 16 November with both slots held and one earlier ready request, none of two parked reviews was reconsidered although both had become ready. This is the congested case that held two power_convertor reviews for over an hour. §3 made a repeated completion call re-evaluate a parked request; it did not change the pass.

Deliverable. Readiness of every parked request is re-read on each wake of the drain whether or not a slot is free, at no slot's cost, and a parked request found ready takes its place in the order of §2.

Done when. A test holds both slots, puts an earlier ready request ahead of two parked reviews whose manifests now read complete, and finds both reconsidered within one wake and both promoted in order once a slot frees. A parked request whose manifest is still in progress stays parked with its reason. Negative control: at the base revision none of the two is reconsidered while the slots are held. The readiness pass over 100 parked requests takes under one second. Importers add no failure against the base, on all_debug. Write paths: reckon/crew/promotion_requests.py and tests/test_waiting_promotion_readiness_precedes_slot_admission.py.

§13 — Every stage of a delivered run leaves a receipt

Why. The largest block of waiting in the week, 4,542 run-hours, cannot be attributed. Nothing records that a session was shown a delivery or read it, so "never learned" cannot be told from "learned and did not act". A promotion request is overwritten as it advances, so retries are lost, and the drained log is trimmed to 500 lines, so no week of service history exists. A further 958 run-hours sit between delivery and a review with no record of when the review was asked for.

Deliverable. For each delivered run a durable, append-only record holds the instant of each stage: delivery recorded, delivery shown to its session, review requested, review admitted, review started, review record written, each promotion attempt with its outcome and reason, promotion settled, and landing. The record is bounded per run and survives the request file being rewritten. The census reads it and assigns every interval once.

Done when. A test takes a fixture run through delivery, a review, a refused promotion, a retry and a landing, and reads back every instant in order with both attempts and the refusal's reason. A census over ten fixture runs assigns every interval to one stage and leaves none unattributed. Negative control: with one receipt suppressed, its interval is reported as unknown, not zero. The record for a run stays under 16 kB after 50 attempts. Importers add no failure against the base, on all_debug. Write paths: reckon/crew/promotion_requests.py, reckon/crew/recovery_review_dispatch.py, reckon/crew/session_host.py, reckon/crew/stage_receipts.py and tests/test_review_handoff_has_durable_stage_receipts.py.

§14 — The promotion queue and the admission queue share one order

Why. §2 landed its order inside the promotion module to unblock the queue on 16 November. The admission queue already ranks by the same rules and already reports the rule that placed each row. Two definitions of one rule drift, and the next change to fairness would reach one queue and not the other.

Deliverable. One definition of the order, used by both queues, with the promotion queue's one addition, the fewest promotions served in the window, expressed as part of it. The served order of §2's cases is unchanged.

Done when. git grep at head finds one definition of the precedence rule and both queues calling it; the promotion module is shorter than at the base; §2's six cases pass unchanged and the admission order's own tests pass. A test changes the starvation bound in the one definition and finds both queues' orders change. Negative control: at the base revision the same change moves one queue only. Importers of both modules add no failure against the base, on all_debug. Write paths: reckon/crew/queue_order.py, reckon/crew/promotion_requests.py and tests/test_both_queues_share_one_order.py.

§15 — A promotion that fails leaves its plan file as it found it

Why. A promotion writes its landing comment into the plan before its last checks. When it then fails, the plan file is left modified in the main checkout, and dispatch refuses every launch for that plan until someone notices and reverts it. A failure in one run stops the whole plan's queue.

Deliverable. A promotion that does not complete leaves the plan document, its version and the checkout's index for that path exactly as they were before it started, and says in its refusal that it restored them.

Done when. A test starts a promotion in a temporary repository, forces a failure after the plan comment is written, and finds the plan file's digest and git status for its path equal to their values before the promotion; a dispatch for the same plan then validates. Negative control: at the base revision the plan file is modified after the failure and the dispatch is refused. A successful promotion still writes its comment. Importers add no failure against the base, on all_debug. Write paths: reckon/crew/promotion.py and tests/test_a_failed_promotion_restores_its_plan.py.
