§1 — Why: a sprint move landed in both sprints

On 2026-11-13 the nova session reported a sprint move through edit_plan (S26 to S23) that failed with [Errno 2] No such file or directory: docs/.reckon/transactions/sprint-move-<id>.json and still changed state:

  • The first time, both sprints were updated and both versions bumped, although the reply said ok=false.
  • The second time, the destination gained the item (S23 v26 to v27) and the source kept it (S26 stayed at v7). labeller-throughput-and-shape-inverse sat in both sprints, and a retry was refused with "already exists in sprint S23". nova repaired it by hand.

The missing directory was not the cause. move_sprint_item in reckon/project_state.py creates the journal's directory before writing it, and has done since 2026-07-29. The ENOENT comes after both sprint writes, when the move marks its journal committed: by then the journal has been deleted by someone else.

Every read_resource that finds a pending journal runs recover_project_state_transactions. That pass restores the journal's "before" bytes of both sprints and deletes the journal. The move and the recovery are meant to exclude each other through the per-resource locks, and those locks are fcntl.flock. Measured on 2026-11-13:

Both probe files were under ~/.cache on the shared GPFS home. Plan state is read and written on the login node, where the reckon server runs, and on the fleet node, where sessions' MCP servers run. So a read on one node can run recovery in the middle of a move on the other. Both of nova's symptoms follow from that ordering:

  1. Recovery between the journal write and the first sprint write is a no-op restore. Both writes then land, and the commit mark fails: the state is right and the reply is wrong.
  2. Recovery between the two sprint writes restores the source with the item still in it. The target write then adds the item: it is in both sprints.

The same primitive appears 74 times in 23 modules under reckon/. a-seat-held-elsewhere-is-not-restarted §8 found the node-local flock for follower registrations and judged them by a renewed lease instead. Plan state was not covered.

§2 — A plan-state write and its recovery exclude each other on every node

Deliverable: while a process on one node holds a plan-state resource lock, another process on any node that asks for the same lock waits or is refused. This covers sprint moves, pushes, closes and every other project_state write, and the transaction recovery that reads beside them. Exclusion between two holders inside one process (two threads, or two opens of the lock file) is no weaker than today's.

Done when:

  • A probe script under scripts/ holds a plan-state resource lock through the production lock code, on a temporary docs tree and never a live project's, on the node it runs on. The tree is on storage both nodes open (the shared home, never a node-local /tmp). A second invocation on a different compute node, against the same temporary tree, finds the lock file present and reports that the lock was refused; a missing path is not a refusal.
  • The negative control is the same pair run against the base revision: there the second node reports that it took the lock.
  • Both runs are logged under the run directory with each hostname printed. The two hostnames must differ, or the run is not evidence.
  • A test, using a temporary docs tree, shows two threads of one process exclude each other on one resource lock. It also shows that a recovery started while a move holds its locks either waits for the move to finish or finds no journal; it never restores either sprint's "before" bytes.
  • The test files that import reckon/project_state.py give the same pass and fail ids at head as at base, except for the new test file.

Write paths: reckon/project_state.py, one new module under reckon/ if the lock is factored out, the probe script under scripts/, and tests/test_a_plan_state_lock_holds_on_every_node.py.

§3 — A sprint move replies with what landed

Deliverable: a sprint move, push or close that touches two sprint resources ends in one of two states, both applied or neither applied. Its reply through edit_plan names which one, with both versions as they now stand on disk. A failure after both writes have landed does not report ok=false as if nothing changed. A failure of the move itself never leaves an item in both sprints or in neither. A reader on another node recovering mid-move is §2's case, not this section's.

Done when a test with a temporary docs tree injects a fault at each step of a move:

  • after the journal is written;
  • after the first sprint write;
  • after the second sprint write;
  • while the journal is marked committed, including the journal already being gone.

For each step, the test asserts that the item is in exactly one sprint and that the reply's applied-or-not verdict and versions match a fresh read of both resources. The negative control runs the commit-mark fault against the base revision and shows the reply says not applied while both writes landed. It is recorded in the run directory. The test files that import reckon/project_state.py or the edit_plan sprint path give the same pass and fail ids at head as at base, except for the new file. Write paths: reckon/project_state.py, the sprint branch of the edit-plan write path, and tests/test_a_sprint_move_replies_with_what_landed.py.

§4 — Every flock on shared state is accounted for

Deliverable: a census of every fcntl.flock call under reckon/ that takes a lock (exclusive or shared; a call that only releases one is not a row), as an evidence fragment at docs/evidence/fragments/a-plan-state-lock-holds-on-every-node/every-flock-is-accounted-for.html, with one row per call site giving:

  • the file and line at the commit the census read;
  • what the lock guards;
  • whether a holder on another node can touch it.

Each row ends in exactly one verdict:

  • node-local by design, with the reason, such as a FIFO or socket that exists only on one host;
  • already judged cross-node by another mechanism, citing it, such as §8's follower lease;
  • needs the §2 lock, which the coordinator files as a followup or a new section on this plan, naming the module.

Done when:

  • the fragment's rows, keyed by file and line, are exactly the lock-taking fcntl.flock calls under reckon/ at the commit it names: none missing and none listed twice, with the count stated in the fragment;
  • a row claimed node-local by design names the host-local object it guards.

The negative controls are two copies of the fragment, one with a row removed and one with a row removed and another duplicated in its place; the check must fail both. Write paths: the fragment only; this section changes no source.
