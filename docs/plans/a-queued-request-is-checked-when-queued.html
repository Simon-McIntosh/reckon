§2 — A batch entry is refused at queue time for the node contract a launch would refuse

Deliverable. The node-contract verdict a single dispatch reaches is composed inline in plan_dispatch from four checks: validate_node and negative_control_finding and gate_population_finding (reckon/crew/node.py near lines 1182, 1054 and 1145) and capability.assess_execution_fit (reckon/crew/dispatch_plan.py near line 834). That composition is extracted into one function, beside the admission findings in reckon/crew/dispatch_admission.py, taking the node, repository, execution capability, locked decisions and budget ceiling and returning the failing properties. plan_dispatch calls it in place of the inline composition. queue_requests (reckon/crew/dispatch.py near line 293) takes one node list and raises on the first refusal, and the per-entry rows and refused count of a batch come from _queue_batch (reckon/crew/dispatch_batch.py near lines 518–552), which calls queue_requests once per entry; so queue_requests calls the function and raises naming the failing properties, and _queue_batch turns that into the entry's refusal row with no pointer written. A check added to the function later reaches both paths.

§4 — Find why an answer is pinned to an older stored review, and write the repair

Deliverable. read_plan_review (reckon/crew/plan_review.py near line 1229) chooses among the reviews review_coverage reports covering a plan by the largest plan_version integer (near line 1262), and both the view (reckon/mcp_views.py near line 4504) and --answer (reckon/crew_dispatch_commands.py near line 2724) reach it there; which is not commit order: reviews at successive plan commits can carry equal or non-monotonic versions, so an older review wins. The selector and the covering-review predicate it uses choose the newest covering review by the order of the plan commits the reviews read (ancestry of each record's plan_commit, falling back to the review timestamp when a commit is unreachable), so crew view plan-review serves it and --answer writes to it. --review-run naming any stored review of the plan whose findings include the id writes the answer to that review, and the refusal in reckon/crew_dispatch_commands.py (near line 2784) fires only when the named review does not raise the finding. This extends the existing selector; it adds no second one.

Done when a new tests/test_an_answer_lands_on_its_review.py shows three things with a temporary plan carrying three stored content reviews at successive plan commits whose plan_version values are not increasing: the view serves the review at the newest commit; --answer of an id that review raises writes to it and to no other review; and --review-run naming the middle review answers a finding only that review raises. Negative control: selecting by plan_version again makes the view serve an older review. The test files importing reckon.crew.plan_review add no failure against the base revision, run one arm at a time with at most -n 4.
