§5 — A second launch of a run never releases the tree its first launch holds

Why. §3's investigation (run r-20261107T100310177452, note at ~/.config/reckon/crew/reports/reckon/what-trashed-the-live-worktree.md) found the cause. The predecessor drop was not involved: a second launch of the same request r-20261106T224214853358-edge-window-settle, made by a different reckon process from a reload image, reached _create_worktree, found the first launch's tree at the shared launch path, judged it a disposable leftover and released it through _remove_worktree into _release_worktree_whole (the trash directory carried the tree name, not a run id, and a new tree appeared at the path within seconds; the gc callers also pass no run id but create no tree, so only _create_worktree fits both). The live-claim view both the refusal and the removal read, _live_pointer_worktrees (reckon/crew/routing.py near line 1078), drops the launching run's own pointer (near line 1092), the one pointer holding the tree. The new inode at the path came seconds later from the same call; the reported 23:50 was local time for 22:50:26Z. Any duplicate launch of one request therefore destroys the launch before it. Preventing the duplicate admission itself is a-reexec-never-orphans-a-dispatch's concern; this section makes the duplicate fail loudly instead of destroying work.

Deliverable. A launch-side claim view keeps a same-run pointer as a claim unless its phase is still a waiting phase in WAITING_REQUEST_PHASES (reckon/crew/node.py near line 1569). A launch pointer is written with its worktree and phase starting (reckon/crew/dispatch.py near lines 2946 and 2991) before its worker runs, so starting and the other unlaunched claim phases count as a claim unless its worker is provably gone by local_liveness (reckon/crew/recovery_liveness.py near line 1204); unprovable liveness on another host counts as a claim. It is used at the two places that decide a launch's fate, the claims fed to _launch_tree_verdict (near line 2173) and the guard in _remove_worktree (near line 2278). Every other reader keeps the current view: gc, _save_and_release_worktree and promotion release are unchanged, and no path naming changes, so _run_worktree_path and gc.py's confinement are untouched.

§6 — A batch-made request can be edited in the queue

Why. power_convertor session c71ae21b reported on 7 November that crew queue edit --time-budget 90m, and earlier --done-when, on requests created by --batch (r-20261106T224355745135-vs1-rate-placement, r-20261106T231853484901-thyristor-line-arm) were refused with “the edited request fails its contract checks and was not stored — independently-verifiable: no manifest path is named”. The batch path never stores a manifest path on the request, so no batch-made request can be edited at all, and the only remedy, drop and requeue, loses its queue position. The same report found --batch accepting a time_budget of 1h30m that admission later refused, which §2's queue-time contract check covers.

Deliverable. _queue_batch (reckon/crew/dispatch_batch.py) gives each queued entry the manifest path a single queued dispatch stores, so crew queue edit judges a batch-made request on the same contract as any other.
