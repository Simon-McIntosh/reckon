§5 — A second launch of a run never releases the tree its first launch holds

Why. §3's investigation (run r-20261107T100310177452, note at ~/.config/reckon/crew/reports/reckon/what-trashed-the-live-worktree.md) found the cause. The predecessor drop was not involved: a second launch of the same request r-20261106T224214853358-edge-window-settle, made by a different reckon process from a reload image, reached _create_worktree, found the first launch's tree at the shared launch path, judged it a disposable leftover and released it through _remove_worktree into _release_worktree_whole (the trash directory carried the tree name, not a run id, and a new tree appeared at the path within seconds; the gc callers also pass no run id but create no tree, so only _create_worktree fits both). The new inode at the path came seconds later from the same call; the reported 23:50 was local time for 22:50:26Z. Any duplicate launch of one request therefore destroys the launch before it. Preventing the duplicate admission itself is a-reexec-never-orphans-a-dispatch's concern; this section makes the duplicate fail loudly instead of destroying work.

It is used at the two places that decide a launch's fate, the claims fed to _launch_tree_verdict (near line 2173) and the guard in _remove_worktree (near line 2278). Every other reader keeps the current view: gc, _save_and_release_worktree and promotion release are unchanged, and no path naming changes, so _run_worktree_path and gc.py's confinement are untouched.
