§1 — Problem

read_plan currently returns an envelope containing project, slug, version, and a nested data object that repeats several of those fields. A default plan read also returns resolved history, option-label maps, empty strings, and machine-oriented keys before presenting the human meaning. Index reads amplify the problem by returning every sprint and project rollup in one response.

Stable identifiers are still required for links, optimistic concurrency, and unambiguous edits. The defect is not that identifiers exist; it is that raw storage shape dominates every read and the same slug is repeated where one resource reference would suffice.

§2 — Proposed response model

A default read should return one structured resource reference, a human title and summary, a compact state block, active blockers or open decisions, and the next actionable followup. Resolved history, full prompts, option maps, raw semantic fields, schema, and operation vocabulary should be requested through explicit detail levels or facets.

For example, a plan response can lead with resource: {project, type, id}, then title, state: {status, progress, sprint}, blocked_by, open_decisions, and next. The concurrency token appears once. Sprint discovery returns a list of concise sprint cards; reading one sprint returns only that sprint and resolves item titles and live state.

§3 — Tool surface

The collapsed read/edit/audit surface can remain, but read_plan should evolve toward a typed read_resource contract or accept an explicit resource reference and view. Compatibility aliases can preserve existing callers. Write operations continue to use stable IDs and expected versions; user-facing output should translate successful operations into clear sentences plus the affected resource.

Errors should report the resource title, requested operation, expected and actual versions, and the smallest corrective action. Audit should distinguish schema violations from hygiene warnings and must never return stale rollups or imply mutation when it only recomputes a view.

§4 — Done-when

  1. Default plan and sprint reads are materially smaller and contain no duplicated identity fields.
  2. Summary, detail, raw, schema, and history views have documented stable shapes.
  3. Resolved history and full prompts are opt-in while open decisions and next action remain visible.
  4. Compatibility tests cover old clients, resource aliases, concurrency conflicts, and typed directories.
  5. Token-size fixtures and human review demonstrate clearer output for representative plan, sprint, discovery, and audit calls.

§ Decisions

How should the read tool expose typed resources?

Evolving the existing read entrypoint preserves the three-tool contract while adding typed resource references and explicit summary, detail, raw, schema, and history views.

What should a default read include?

The default read should answer the common human question with identity, state, blockers or decisions, and next action; lossless storage and history remain opt-in.
