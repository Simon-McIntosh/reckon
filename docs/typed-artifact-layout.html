§1 — Current state

Reckon now has first-class plan, research, and evidence types, but live documents still share the docs/ root and landed evidence shares docs/archive/. Type metadata lets software distinguish them, while the filesystem gives humans little help and makes discovery exclusions increasingly fragile.

The target is a visible, typed hierarchy: docs/plans/, docs/research/, docs/evidence/, and docs/sprints/. Infrastructure remains in docs/_shared/, docs/ui/, docs/figures/, and project configuration locations selected by the distributed-state plan.

§2 — Identity and routing

Directory layout must not make identity depend on an arbitrary relative path. Each artifact keeps a stable project-qualified identifier and type. The server should offer canonical typed routes such as /reckon/plans/model-capability-schema while maintaining redirects or aliases for existing flat URLs during migration.

Relationships must become type-aware references, so a plan can depend on another plan, research can inform a plan, and evidence can verify a plan or stage without ambiguous collisions between identical leaf names. Discovery should scan only declared artifact roots rather than treating every HTML file as an actionable plan.

§3 — Migration

A migration command should classify existing HTML by reckon-type, move it to the corresponding directory, rewrite internal links and figure references, and emit a deterministic manifest. It must be idempotent and safe in repositories that contain legacy flat documents. Per-stage history needs an explicit home: either type-local archive directories or evidence records linked to the evergreen plan.

Static build, server discovery, MCP reads and writes, plan creation, audits, SPA navigation, mounts, and every reckon skill must use the same resolver. Tests must cover duplicate leaf identifiers, legacy routes, cross-project references, archive exclusion, and mixed-layout repositories.

§4 — Done-when

  1. The canonical layout and stable resource-identity rules are documented and schema-backed.
  2. Server, MCP, SPA, build, audit, and skills discover all four typed roots consistently.
  3. An idempotent migration moves the existing fleet without broken links or lost semantic state.
  4. Mixed old/new layouts remain readable for a bounded compatibility window.
  5. Repository and cross-repository fixtures prove routing, collision handling, and static parity.

§ Decisions

Where should completed stage history live after typed directories land?

Completed stage records remain immutable HTML audit trails beside their owning artifact type, preserving the current archive contract without returning to one mixed directory.

Should canonical URLs include the artifact type?

Typed canonical routes make resource kind unambiguous while compatibility aliases preserve existing flat links during migration.
