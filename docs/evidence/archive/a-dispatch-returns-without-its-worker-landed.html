That question belongs to §3, which owns the change; nothing here repairs it.

The defect is the order of dispatch's own unwind, not a missing guard. On any failure after the worktree is cut, the unwind removes the worktree and only then unlinks the pointer. But the worktree remover refuses a worktree that a live pointer still claims, and until this run's own pointer is unlinked it is that claim. So a failure reached after the pointer write — the tree snapshot, the peer wiring, the watcher read, the member registration, the final pointer write — met the remover with its own pointer on disk, the remover raised, and the unlink and the run-directory removal that follow it never ran. The live pointer that survived is the measured artefact, recorded in the negative-control run below, whose failing assertion reads assert ['r-20260923T…-node-refused'] == [] — a run still live after a refused dispatch, which a reader takes for a process gone without a manifest and reports abandoned.

The repair is ordering: unlink the pointer first, so the claim is gone before the remover runs, then remove the run directory and the worktree. reckon/crew/dispatch.py, in dispatch's except Exception unwind.

§7 — A promoted row carries the worker's exit record

Promotion releases the run's live pointer and its worktree, but not the run directory: that survives, exit.json with it, until crew gc prunes it on a retention window. complete in reckon/crew/promotion.py reads the file once and copies the parsed object verbatim onto the committed ledger row under worker_exit, so the row is the durable copy of the worker's exit record once gc has run.

Three boundary decisions, and what each rules out. The key is written only when a record was actually read, so a run with no exit.json carries no worker_exit key rather than an empty object — an empty object would read as a supervisor that ran and recorded nothing, which is a different fact from a supervisor that wrote no record. The row's gate_check.exit_status is left untouched: it is the gate command's status, and the worker's exit signal must not overwrite it. And a file that exists but cannot be read, or does not parse as a JSON object, is treated as absent, so a corrupt record produces no key rather than a promotion failure about the record.

What the lane does not cover. The batch step's spawn verb lives in dotfiles and is not landed, so the lane is opted into with RECKON_FLEET_SPAWN rather than triggered by the fleet record alone. With the flag unset a dispatch forks exactly as before, which is its own case in the gate. The worker-survives-scancel proof on the node itself, and the dotfiles change, are the other half's to run.
