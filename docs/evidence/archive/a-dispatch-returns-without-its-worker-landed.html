§7 — A promoted row carries the worker's exit record

Promotion releases the run's live pointer and its worktree, but not the run directory: that survives, exit.json with it, until crew gc prunes it on a retention window. complete in reckon/crew/promotion.py reads the file once and copies the parsed object verbatim onto the committed ledger row under worker_exit, so the row is the durable copy of the worker's exit record once gc has run.

Three boundary decisions, and what each rules out. The key is written only when a record was actually read, so a run with no exit.json carries no worker_exit key rather than an empty object — an empty object would read as a supervisor that ran and recorded nothing, which is a different fact from a supervisor that wrote no record. The row's gate_check.exit_status is left untouched: it is the gate command's status, and the worker's exit signal must not overwrite it. And a file that exists but cannot be read, or does not parse as a JSON object, is treated as absent, so a corrupt record produces no key rather than a promotion failure about the record.

§10 — The fleet's batch step, carried in reckon

Node the-fleet-supervisor-lives-in-reckon. Landed reckon/crew/fleet_supervisor.py and tests/test_fleet_supervisor.py. The module runs as python -m reckon.crew.fleet_supervisor and implements dotfiles' bin/fleet-supervisor protocol — the session and reload verbs, the private node-local runtime directory, the stripping of the inherited ZELLIJ, CX_ and CLAUDE variable families, and the spawn verb §10 of the plan specifies: a three-field request line names a run id and an absolute spec path, and the spec's argv is run verbatim as the batch step's own detached child, acknowledged in <run-dir>/spawned.json with the child's pid and start time.

Why the batch step lives in reckon at all. The verb carries no reckon knowledge, because the spec carries the argv — that is the plan's own constraint and it holds here. The reader is a different matter: it is long-lived, it owns the runtime directory every fleet process resolves through, and it is the process a fix must reach without a new allocation. In the repository it can be driven by pytest over a real FIFO in a temporary runtime tree, so what is asserted is what a request line does to the machine rather than what a function returns. Two environment overrides exist for that (FLEET_RUNTIME_DIR, FLEET_STATE_DIR), and the suite's distance from the machine's own fleet state is asserted, not intended: the spawn case reads the directory the module resolves when no override is set (~/.local/state/fleet) on both sides of the case and requires the two readings identical — listing, mtimes and the record.json digest alike, so a rewrite we missed cannot hide behind an unchanged file name — and it reads that directory without ever writing it. The collector is shown, in the same case, to report a digest for the temporary state directory the reader did write, so an unchanged real directory cannot pass by reading nothing at all. On this machine the real directory exists and holds a live record: its record.json mtime after every run of the suite and both controls is still 2026-09-24 14:35, from before the suite ever ran.

§10 — A headless session keeps every tab its layout names

Node headless-tabs-survive-attach. Landed reckon/crew/fleet_supervisor.py and tests/test_fleet_supervisor.py: the session verb creates the session exactly as before, then attaches one short-lived client on a pty sized to a fixed 200 × 50 with TIOCSWINSZ, waits for zellij action query-tab-names to report the layout's tabs, and detaches it. The line of a session start returns only once the tabs exist. The workaround is commented as removable when a zellij release carries the upstream per-client tab sizing fix (zellij-org/zellij#5612); 0.45.1 is the newest release and still needs it.
