Finding one: no code path holds the dispatch process after the worker launches. In every trial the process ended within a fifth of a second of its worker appearing, so there is no file and line to name for a post-launch hold. A faulthandler dump taken every two seconds while each dispatch process lived shows no frame of the reckon package on the main thread's stack, which is the same reading from the other side: the process was never parked in reckon code.

Finding two: the time a dispatch spends is pre-launch, and it is cited instead. The blocking call is reckon/crew/routing.py:880 in _create_worktree, whose source reads result = subprocess.run( — the dispatch blocks there on worktree_fleet.py create before any worker exists. The other candidates are ruled out by inspection: the launched-worker reaper is constructed daemon=True at reckon/crew/dispatch.py:4311, so the interpreter does not wait for it; the watcher arming is bounded at WATCHER_LOAD_BOUND_SECONDS = 30.0 (dispatch.py:119) and happens before the worktree is created; and the worker is detached with start_new_session=True (dispatch.py:4639) into redirected files, so nothing reads or waits on it.

Finding three: the worker survives its dispatcher dying. In the SIGTERM, SIGKILL and SIGHUP trials the dispatch process died (exit codes −15, −9 and −1) and the stub still wrote its marker about sixty seconds after launch, in all five trials including the untouched graceful one. The marker is the positive control: an absent marker after a killed dispatch would be a finding only because the same stub writes one when nothing was killed.

Read against the plan's own observation. §1 records four dispatch processes that exited close to six minutes after they were dispatched. This probe does not reproduce a six-minute hold, and it cannot: at this revision a dispatch ends well before one could exist. What it cannot separate is whether §1's six minutes were spent before the worker appeared rather than after — the observation there is of wall-clock dispatch-to-exit, which this probe's table shows is dominated by the pre-launch path on a contended host. That question belongs to §3, which owns the change; nothing here repairs it.

Tests and the guard. One test, five trials, 320 s: tests/test_dispatch_lifetime_probe.py. Log: ~/.config/reckon/crew/runs/r-20260923T044807192716-dispatch-lifetime-probe/probe-full.log. The declared negative control is none: the test records observed behaviour rather than asserting a repair, and its one guard — the real live-pointer directory under ~/.config/reckon/crew/live holding no pointer naming any run the probe created — can only be falsified by writing into the real fleet. It passed, with the directory's mtime recorded before and after, and the probe's own pointers read back from the throwaway homes as the positive control that they were in fact being written.

Follow-ons. The trial after a killed one first failed for a reason that is not this node's: a dispatch killed mid-flight leaves the crew ledger — docs/state/sample/crew.json, a committed file inside the dispatched repository — staged and uncommitted, and the next dispatch in that repository then cannot commit its own session-member registration over it, retries twelve times and rolls back before launching a worker, on a worktree it cannot remove because the run it just registered still claims it. The probe was repaired by isolating one repository per trial, which removes the coupling for the measurement; the underlying refusal is unmeasured here and is a candidate node for §5, which owns a refusal that leaves a run behind.

The defect is the order of dispatch's own unwind, not a missing guard. On any failure after the worktree is cut, the unwind removes the worktree and only then unlinks the pointer. But the worktree remover refuses a worktree that a live pointer still claims, and until this run's own pointer is unlinked it is that claim. So a failure reached after the pointer write — the tree snapshot, the peer wiring, the watcher read, the member registration, the final pointer write — met the remover with its own pointer on disk, the remover raised, and the unlink and the run-directory removal that follow it never ran. The live pointer that survived is the measured artefact, recorded in the negative-control run below, whose failing assertion reads assert ['r-20260923T…-node-refused'] == [] — a run still live after a refused dispatch, which a reader takes for a process gone without a manifest and reports abandoned.

The repair is ordering: unlink the pointer first, so the claim is gone before the remover runs, then remove the run directory and the worktree. reckon/crew/dispatch.py, in dispatch's except Exception unwind.

The gate. tests/test_refused_dispatch_leaves_no_pointer.py forces each path above in a temporary crew home and repository and asserts, for each, no live pointer, no run directory, no worktree and no watcher transition row naming the node. §10 — The fleet's batch step, carried in reckon

Node the-fleet-supervisor-lives-in-reckon. Landed reckon/crew/fleet_supervisor.py and tests/test_fleet_supervisor.py. The module runs as python -m reckon.crew.fleet_supervisor and implements dotfiles' bin/fleet-supervisor protocol — the session and reload verbs, the private node-local runtime directory, the stripping of the inherited ZELLIJ, CX_ and CLAUDE variable families, and the spawn verb §10 of the plan specifies: a three-field request line names a run id and an absolute spec path, and the spec's argv is run verbatim as the batch step's own detached child, acknowledged in <run-dir>/spawned.json with the child's pid and start time.

Why the batch step lives in reckon at all. The verb carries no reckon knowledge, because the spec carries the argv — that is the plan's own constraint and it holds here. The reader is a different matter: it is long-lived, it owns the runtime directory every fleet process resolves through, and it is the process a fix must reach without a new allocation. In the repository it can be driven by pytest over a real FIFO in a temporary runtime tree, so what is asserted is what a request line does to the machine rather than what a function returns. Two environment overrides exist for that (FLEET_RUNTIME_DIR, FLEET_STATE_DIR), and the suite's distance from the machine's own fleet state is asserted, not intended: the spawn case reads the directory the module resolves when no override is set (~/.local/state/fleet) on both sides of the case and requires the two readings identical — listing, mtimes and the record.json digest alike, so a rewrite we missed cannot hide behind an unchanged file name — and it reads that directory without ever writing it. The collector is shown, in the same case, to report a digest for the temporary state directory the reader did write, so an unchanged real directory cannot pass by reading nothing at all. On this machine the real directory exists and holds a live record: its record.json mtime after every run of the suite and both controls is still 2026-09-24 14:35, from before the suite ever ran.

The two controls added with the assertions behind the untouched-state and runtime-mode claims. Driver …/logs/negative-controls-assertions.sh, log …/logs/negative-controls-assertions.log. Dropping the state override makes the reader publish into the directory the module resolves by default, and the byte-identity assertion fails on precisely that: {'exists': True, …'record_sha256': '466451e3…'} == {'exists': False}. One detail of that control is load-bearing and is stated in the driver: the fixture's state directory is pointed at the default one as part of the same act, because otherwise the case fails earlier, on the pre-existing assertion that reads the record the reader left, and the comparison under control is never reached — a control that looks red while measuring something else. The control also redirects HOME into its overlay, so the directory it makes the reader write is its own and the machine's real fleet state is untouched by the control as much as by the suite. Dropping the runtime directory's 0o700 chmod and running the mode case under umask 000, so the outcome does not depend on the umask of whoever runs the control, leaves the directory created 0o777 and the assertion fails on the mode it reports (assert 511 == 448). Both controls copy the package and the test tree, exclude the byte-compiled caches, and print the resolved paths of the modules they measured — the cache exclusion is what the next paragraph is about.

An artifact this control exposed, recorded because it nearly read as a defect. The first run's traceback named the test file at the worktree path while the control was supposedly measuring its overlay. The cause was the copy: __pycache__ travelled with it, and a byte-compiled file carries the source filename it was compiled from, so the module was loaded from the overlay while displaying the worktree's path. The measured tree was never in doubt and was confirmed by a collection hook printing the resolved test and package paths; the fix is to exclude the caches from the copy, which the driver now does and the log now shows. A reader who trusted the traceback would have concluded the control was inert.

What this node does not take. dotfiles' bin/fleet-supervisor is unmodified and so is every caller. Writing the spawn line — _start_supervisor choosing the FIFO over a fork when a live fleet record names this node, waiting bounded for the acknowledgement, and recording the pid, with the crew watch producer and the resumption paths taking the same route — is the sibling node's work. This node delivers the batch step that work dispatches into.
