Finding one: no code path holds the dispatch process after the worker launches. In every trial the process ended within a fifth of a second of its worker appearing, so there is no file and line to name for a post-launch hold. A faulthandler dump taken every two seconds while each dispatch process lived shows no frame of the reckon package on the main thread's stack, which is the same reading from the other side: the process was never parked in reckon code.

Finding two: the time a dispatch spends is pre-launch, and it is cited instead. The blocking call is reckon/crew/routing.py:880 in _create_worktree, whose source reads result = subprocess.run( — the dispatch blocks there on worktree_fleet.py create before any worker exists. The other candidates are ruled out by inspection: the launched-worker reaper is constructed daemon=True at reckon/crew/dispatch.py:4311, so the interpreter does not wait for it; the watcher arming is bounded at WATCHER_LOAD_BOUND_SECONDS = 30.0 (dispatch.py:119) and happens before the worktree is created; and the worker is detached with start_new_session=True (dispatch.py:4639) into redirected files, so nothing reads or waits on it.

Finding three: the worker survives its dispatcher dying. In the SIGTERM, SIGKILL and SIGHUP trials the dispatch process died (exit codes −15, −9 and −1) and the stub still wrote its marker about sixty seconds after launch, in all five trials including the untouched graceful one. The marker is the positive control: an absent marker after a killed dispatch would be a finding only because the same stub writes one when nothing was killed.

Read against the plan's own observation. §1 records four dispatch processes that exited close to six minutes after they were dispatched. This probe does not reproduce a six-minute hold, and it cannot: at this revision a dispatch ends well before one could exist. What it cannot separate is whether §1's six minutes were spent before the worker appeared rather than after — the observation there is of wall-clock dispatch-to-exit, which this probe's table shows is dominated by the pre-launch path on a contended host. That question belongs to §3, which owns the change; nothing here repairs it.

It passed, with the directory's mtime recorded before and after, and the probe's own pointers read back from the throwaway homes as the positive control that they were in fact being written.

Follow-ons. The trial after a killed one first failed for a reason that is not this node's: a dispatch killed mid-flight leaves the crew ledger — docs/state/sample/crew.json, a committed file inside the dispatched repository — staged and uncommitted, and the next dispatch in that repository then cannot commit its own session-member registration over it, retries twelve times and rolls back before launching a worker, on a worktree it cannot remove because the run it just registered still claims it. The probe was repaired by isolating one repository per trial, which removes the coupling for the measurement; the underlying refusal is unmeasured here and is a candidate node for §5, which owns a refusal that leaves a run behind.

§5 — A refused dispatch leaves no pointer, no worktree and no watch row

Node refusal-leaves-no-trace, at revision 12155ff8. The defect is the order of dispatch's own unwind, not a missing guard. On any failure after the worktree is cut, the unwind removes the worktree and only then unlinks the pointer. But the worktree remover refuses a worktree that a live pointer still claims, and until this run's own pointer is unlinked it is that claim. So a failure reached after the pointer write — the tree snapshot, the peer wiring, the watcher read, the member registration, the final pointer write — met the remover with its own pointer on disk, the remover raised, and the unlink and the run-directory removal that follow it never ran. The live pointer that survived is the measured artefact, recorded in the negative-control run below, whose failing assertion reads assert ['r-20260923T…-node-refused'] == [] — a run still live after a refused dispatch, which a reader takes for a process gone without a manifest and reports abandoned.

The repair is ordering: unlink the pointer first, so the claim is gone before the remover runs, then remove the run directory and the worktree. reckon/crew/dispatch.py, in dispatch's except Exception unwind.

The gate. tests/test_refused_dispatch_leaves_no_pointer.py forces each path above in a temporary crew home and repository and asserts, for each, no live pointer, no run directory, no worktree and no watcher transition row naming the node. A positive control drives the ordinary successful path and shows every read does see a present run, so the clean result is a measurement rather than a blind read; the occupied-worktree case additionally asserts the earlier run's worktree is left untouched, because the refusal must not over-reach. list_live's own publishing read is driven with a registered producer, which is the path the durable watcher uses.

Follow-ons. The occupied-worktree refusal is correct, but the worktree it refuses over is a leftover: after crew discard of a launch-failed run the worktree stays on disk and a re-dispatch of the same node is refused with worktree path already exists. Removing it is the discarding command's job, not dispatch's, so it is recorded here rather than repaired in this node. §6 owns the sibling case, a refusal returned beside a live pointer, whose candidate cause — the tree-snapshot exception handler signalling a launched worker's process group — is removed by §3 moving that snapshot into the supervisor.
