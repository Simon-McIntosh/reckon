The topic directory is an exclusive claim that refuses a second node

Landed 2026-09-15, commit 4437fbf3, run r-20260915T100103055425-the-topic-directory-is-the-claim. 202 insertions over 2 files (one source, one test).

Measure: tests/test_crew_dispatch_guard.py passes 14 of 14 — the eight pre-existing cases unchanged plus six new figure-topic cases, each added without modifying a pre-existing assertion (the diff is additions-only).

The six new cases demonstrate the three refusals the section's done-when names, each as an actual dispatch refusal rather than an assertion about the rule:

  • A second node on a claimed topic is refused naming the owner. First dispatch declares docs/figures/capture; the second declares the same topic. The ScopeConflict carries the owner's run id and node id in the exception fields and in the message, the refused node never reaches worktree creation, and the topic directory has not been created on disk at any point.
  • A path inside a claimed topic is refused the same way. The owner claims docs/figures/capture; the second declares docs/figures/capture/after/plot.png and is refused naming the owner. The reverse direction is asserted separately: an owner that claims the leaf docs/figures/geo/plot.png refuses a second node declaring the topic directory docs/figures/geo, so the claim covers the tree both ways.
  • Both hold for a topic directory that does not exist on disk. The fixture repository never creates docs/figures at all; the assertion checks the root is absent before dispatch and that declaring the claim creates nothing. This is the ordinary capture-node case, where an empty path is easy to mistake for no claim at all — the walk is path-based, so a topic with no contents binds exactly like one that does.

The never-combined corollary is pinned too: two nodes declaring the same figure filename (docs/figures/deploy/plot.png) is refused as a scope defect — a figure is replaced wholesale, and the same filename cannot be written twice. The disjoint-topics control proves the rule refuses overlap rather than figure writes: docs/figures/alpha and docs/figures/beta dispatch concurrently.

The count of claims the check walks, as a digit: at the moment the refusing dispatch is judged, the exclusive-claim walk reads 3 live claims for a single owner — the plan file, the owner's cumulative evidence record, and the claimed figure topic directory. Asserted by instrumenting the walk itself (_raise_repository_scope_conflict wrapped to count its claims), so a regression that stops walking a claim changes the count and fails the test.

Proving the refusals are the guard, not an incidental failure. A mutation control run replaces the containment predicate so that no two paths overlap and re-runs the file: exactly the six refusal tests fail with DID NOT RAISE ScopeConflict, while the eight non-refusal tests — including the disjoint-topics positive control — pass. A containment rule that admitted everything would leave those six green; the guard fires, and the tests measure it.

What changed in the source. The enforcement already existed as the generic live-claim containment walk in reckon/crew/dispatch.py; the node verified it rather than reimplementing a working guard, and added a five-line mechanism comment at the refusal site stating the allocation unit the plan names — a topic directory is claimed as a tree, a figure is replaced wholesale and never merged, and the walk is path-based so an empty topic binds like a full one. No runtime behaviour changed. The two touched files add no new lint findings (the file's pre-existing findings are unchanged), and the added test region is format-clean.

Open decision left to the plan, not decided here: two nodes writing different filenames under one topic are admitted today, because each claims a leaf rather than the topic; whether that is allowed is the plan's own sibling-writers-in-one-topic decision, which this node does not foreclose.

The rule is written where an author and a coordinator read

Landed 2026-09-15, run r-20260915T144835970476-the-rule-is-written-where-it-is-read. Documentation-only: no runtime code changed.

Both surfaces state the allocation unit. The figure guidance in skills/reckon-create/SKILL.md (rule 8) and section 5 of skills/reckon-ship/references/worker-protocol.md now state that each per-topic directory beneath docs/figures/ is claimed by exactly one node, the claim covers the whole tree under it, and a second node declaring that same directory or any path inside it is a scope conflict caught at dispatch — naming the owning run, never a conflict a coordinator resolves at integration. Both surfaces also state the never-merged corollary verbatim: a figure is added or replaced WHOLESALE, never combined; two nodes producing one filename is a scope defect caught at dispatch, not a conflict resolved at integration, because there is no correct resolution at integration — the halves cannot be combined and neither is obviously right.

Either surface alone is sufficient for a capture node. Neither references dispatch source; both instead instruct a node that will write figures to declare the topic directory itself as its write path, docs/figures/<topic>, not a file inside it. The clause-4 self-test passes from either text alone: a capture node producing docs/figures/burn-visibility derives the exact dispatch argument --write-path docs/figures/burn-visibility.

The refusal count, as a digit. Number of figure-writing plans in this repository that would have been refused under the rule when they ran: 0. Method: every figure topic directory in the repo was enumerated two independent ways — the 995 promoted runs in docs/state/reckon/crew.json (each run's declared write_paths under docs/figures/) and the git add-history of docs/figures/ — and every one of the 20 topic directories was written by exactly one distinct plan, with no same-topic live-window overlap between any two runs. A rule refuses only a second concurrent declarer of a claimed topic or a containing or contained path, and none ever existed; the rule written to the two surfaces changes no dispatch outcome that occurred, confirming the plan's own expectation.

Left open, not decided here: the sibling-writers-in-one-topic question. Both surfaces state the tree-claim rule as enforced today; neither presupposes whether two nodes may write different files inside one topic. That decision belongs to the plan.
