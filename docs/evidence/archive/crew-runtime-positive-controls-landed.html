Crew Runtime Positive Controls

A launch either resolves its backend to an absolute path before anything is written, or it refuses naming the PATH it searched; a launch that runs and dies before its first turn is one recorded failure, and the run leaves the lift loop until a person acts.

§1 — The launch resolves its executable, or it refuses before writing

The launch plan carried a bare backend name and inherited the PATH of whoever built it, so a watcher armed without the backend directory exec'd a missing binary and left a 0-byte stream per tick while the run read as working. Resolution now happens where the plan is built, at the three sites that construct a plan for a run: a dispatch, a resume, and a member move. A fourth site constructs a plan without resolving it — the lane-availability probe at reckon/crew/resumption.py:234 — and is deliberately left unwrapped because it probes a capability rather than launching a run: its failure is loud (it reports unavailable and the availability report says so) and it writes no pointer, stream or stderr, so the property this section claims still holds there.

The refusal is literal and names what was searched, so the repair is a command rather than an investigation:

backend command 'python3' cannot be resolved on the PATH this launch would
search: /nonexistent — install it or add its directory to PATH, then retry;
nothing has been launched

reckon crew watch resolves every backend its project can route to before the seat is taken, in the single-event arm as well as the streaming one, so no arming mode takes a seat it cannot lift from and a watcher that cannot lift is never a watcher that reads as armed.

A later review of this section found that claim true of the streaming arm and false of the single-event one: crew watch --once claimed the seat with no resolution check anywhere on its path, so a host whose backend directory was off the project's PATH could arm a seat-holder that read as live and could lift nothing from it — a posture defect rather than a silent launch failure, because dispatch resolves at launch on the same host and refuses before writing anything. The single-event arm now refuses through the same check, before the seat is claimed. A case enters the --once path with the backend directory absent from the PATH handed to the call and asserts both the refusal and that no lock file appears under crew/watch, with a positive control showing that the same call does take the seat once the backend resolves; with the refusal disabled that case is the only one in its file that fails. The count stated above was also wrong in one direction and is corrected here: the lane-availability probe at reckon/crew/resumption.py:234 is a fourth launch_plan construction site, deliberately left unwrapped because it probes a capability rather than launching a run — it reports unavailable loudly and writes no pointer, stream or stderr, which is why the property this section claims still holds there.

The refusal precedes every write. That ordering was not true of the resume path as found: the pointer was mutated with the context fit before the launch plan was built, so a refusal there would have landed after the pointer write. The reorder is what the resume case pins, by comparing the pointer's bytes before and after the refusal rather than asserting only on the message.

The path is made absolute without being canonicalised, and that distinction was found by the population rather than by reading: resolving a launcher installed as bin/codex symlinked to codex.js followed the link, so the run recorded codex.js, the dialect is selected by the command's name, and the run's own stream could no longer be read back — a run made unreadable rather than unrunnable. Three cases outside the new files caught it; the linked launcher now has its own case.

§2 — A worker that exits before its first turn is one launch failure

The reaper knew the child had exited and read that exit against nothing. A run whose stream file is empty when its process is gone is a launch failure, not a worker turn: it is recorded once on the run with the exit status, the argv and the stderr tail, the pointer moves to launch-failed, and the automatic lift refuses that phase until a person resumes or completes the run. The hand-typed resume is deliberately left ungated, so the phase is clearable by the person who repaired the environment.

The control case is the one that makes the first meaningful: it runs the same spawn and the same reaper on a backend whose stream is not empty, and asserts no record appears. It also waits for the reaper to have actually consumed the child, so it cannot pass on a process that was never reaped. With the emptiness guard removed, that control fails — which is how the guard was shown to be the thing the first case rests on. The reaper's exit status is converted from the raw wait status before it is recorded, so a process that exited 127 records 127 rather than 32512.

A later review found the once-only guard load-bearing and unpinned by these cases. The end-to-end cases show one record per launch, but the once-ness they measure comes from the pid being consumed by os.waitpid before a second tick can reach the recorder — not from the guard inside the recorder. Removing the guard's phase check leaves all four pre-existing cases green while a direct probe that records twice for one launch turns red, which is how the guard was shown to be what the node's cases were not resting on. A case now reaches the recorder twice for one launch without waiting on a reap and asserts one record and one phase, so a second reaper or a handover edge that re-records is caught rather than silently double-counted.

launch-failed is added to the states the follower needs action on, which places it under the blocked bucket rather than the working bucket, and classify_pointer renders it as its own classification carrying the failure count and the last cause. Its classification is also in the actionable set the drain reading counts, which it was not: the state had a classification and a recovery verb and was then left out of the set that count reads, so a run that occupied a lane appeared in no count at all — the same defect as the working bucket, one layer over. The measured reading with one such run is actionable_runs: 1 with actionable_classifications: ["launch-failed"].

What remains open is a width question and not a correctness one: the fleet counter's fixed block has four buckets — working, blocked, unpromoted, queued — and no bucket of its own for an infrastructure fault, so the number a reader sees sits under blocked. Adding a fifth bucket changes a deliberately fixed-width column and is left for the plan owner rather than decided here.

§4 — A terminal list naming a live state, and a lift that re-parks unchanged

Measured 2026-09-19 on r-20260919T111944475334-cco-review-repairs. The run's manifest declared a squeue probe whose first branch prints RUNNING while the job is still queued, and listed RUNNING among its wait_terminal values. The condition therefore reported terminal on every sweep of a job that had not started, and the recovery watcher lifted the run thirty times in one afternoon — resume-1 through resume-30 in the run directory, most of them producing a 0-byte stream. The second half is what made the first repeat: each re-park rewrote the manifest, and the lift was keyed to the file's modification time, so every rewrite read as a brand-new condition.

Three control facts make the refusals mean something. The repaired stanza still reads, so the refusal is the token and not the probe. The probe with no live branch is left alone, so the reader is not refusing every conditional probe. And a first lift still happens, so the re-park marker is a second-cycle verdict rather than a blanket stop.

Each new test fails against a declared mutation of the change, and both red logs sit beside the green one. With the live-state refusal removed, the gate reads 6 failed, 4 passed: the four refusals above fail while the repaired-stanza, no-live-branch, first-lift and cleared-declaration controls pass — the controls are what show the four failures are the guard and not an accident of the fixtures. With the declaration key reverted to the manifest mtime, the gate reads 2 failed, 8 passed: exactly the two re-park cases fail and the eight controls pass, which is how the key was shown to be the thing the re-park detection rests on.

What this change does not reach. The lift itself runs in reckon/crew/resumption.py, outside this node's write scope. Keying the signature to the declaration makes that module's existing duplicate guard stop a re-parked unchanged declaration, which is the observable the plan asks for; but recording the probe output that lifted a wait, and comparing a re-park against it literally, are not implemented here. Two consequences belong to whoever next touches that module: the guard's detail string still reads that a rewritten waiting manifest creates a new condition, which is no longer true of a declaration-keyed signature; and a probe whose output changes while its declaration does not is, under this key, still a single condition. Both are carried as follow-ons rather than quietly claimed.
