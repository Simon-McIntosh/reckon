Execution evidence

Crew Runtime Positive Controls

A launch either resolves its backend to an absolute path before anything is written, or it refuses naming the PATH it searched; a launch that runs and dies before its first turn is one recorded failure, and the run leaves the lift loop until a person acts.

§1 — The launch resolves its executable, or it refuses before writing

The launch plan carried a bare backend name and inherited the PATH of whoever built it, so a watcher armed without the backend directory exec'd a missing binary and left a 0-byte stream per tick while the run read as working. Resolution now happens where the plan is built, at the three sites that construct a plan for a run: a dispatch, a resume, and a member move. A fourth site constructs a plan without resolving it — the lane-availability probe at reckon/crew/resumption.py:234 — and is deliberately left unwrapped because it probes a capability rather than launching a run: its failure is loud (it reports unavailable and the availability report says so) and it writes no pointer, stream or stderr, so the property this section claims still holds there.

The refusal is literal and names what was searched, so the repair is a command rather than an investigation:

backend command 'python3' cannot be resolved on the PATH this launch would
search: /nonexistent — install it or add its directory to PATH, then retry;
nothing has been launched

reckon crew watch resolves every backend its project can route to before the seat is taken, in the single-event arm as well as the streaming one, so no arming mode takes a seat it cannot lift from and a watcher that cannot lift is never a watcher that reads as armed.

A later review of this section found that claim true of the streaming arm and false of the single-event one: crew watch --once claimed the seat with no resolution check anywhere on its path, so a host whose backend directory was off the project's PATH could arm a seat-holder that read as live and could lift nothing from it — a posture defect rather than a silent launch failure, because dispatch resolves at launch on the same host and refuses before writing anything. The single-event arm now refuses through the same check, before the seat is claimed. A case enters the --once path with the backend directory absent from the PATH handed to the call and asserts both the refusal and that no lock file appears under crew/watch, with a positive control showing that the same call does take the seat once the backend resolves; with the refusal disabled that case is the only one in its file that fails. The count stated above was also wrong in one direction and is corrected here: the lane-availability probe at reckon/crew/resumption.py:234 is a fourth launch_plan construction site, deliberately left unwrapped because it probes a capability rather than launching a run — it reports unavailable loudly and writes no pointer, stream or stderr, which is why the property this section claims still holds there.

§2 — A worker that exits before its first turn is one launch failure

The reaper knew the child had exited and read that exit against nothing. A run whose stream file is empty when its process is gone is a launch failure, not a worker turn: it is recorded once on the run with the exit status, the argv and the stderr tail, the pointer moves to launch-failed, and the automatic lift refuses that phase until a person resumes or completes the run. The hand-typed resume is deliberately left ungated, so the phase is clearable by the person who repaired the environment.

The control case is the one that makes the first meaningful: it runs the same spawn and the same reaper on a backend whose stream is not empty, and asserts no record appears. It also waits for the reaper to have actually consumed the child, so it cannot pass on a process that was never reaped. With the emptiness guard removed, that control fails — which is how the guard was shown to be the thing the first case rests on. The reaper's exit status is converted from the raw wait status before it is recorded, so a process that exited 127 records 127 rather than 32512.

A later review found the once-only guard load-bearing and unpinned by these cases. The end-to-end cases show one record per launch, but the once-ness they measure comes from the pid being consumed by os.waitpid before a second tick can reach the recorder — not from the guard inside the recorder. Removing the guard's phase check leaves all four pre-existing cases green while a direct probe that records twice for one launch turns red, which is how the guard was shown to be what the node's cases were not resting on. launch-failed is added to the states the follower needs action on, which places it under the blocked bucket rather than the working bucket, and classify_pointer renders it as its own classification carrying the failure count and the last cause. Its classification is also in the actionable set the drain reading counts, which it was not: the state had a classification and a recovery verb and was then left out of the set that count reads, so a run that occupied a lane appeared in no count at all — the same defect as the working bucket, one layer over. The measured reading with one such run is actionable_runs: 1 with actionable_classifications: ["launch-failed"].

What remains open is a width question and not a correctness one: the fleet counter's fixed block has four buckets — working, blocked, unpromoted, queued — and no bucket of its own for an infrastructure fault, so the number a reader sees sits under blocked. Adding a fifth bucket changes a deliberately fixed-width column and is left for the plan owner rather than decided here.

§3 — The watcher is a process, and the command that starts one carries its environment

Two incidents on 2026-09-19 set the shape. A project ran for an hour with no watcher process while dispatches kept being admitted, because a session follower was armed and the admission path read the follower. Separately, a watcher unit ran for seven hours whose PATH did not contain the backend's directory, so every lift it attempted died at exec — the unit was alive and none of its work could start.

The figure places the two decisions beside each other: what an --ensure call does with the unit it finds on disk, and which of the two registration facts carries which meaning.

reckon crew watch --ensure is the command the refusal will teach. It renders a systemd user unit for the project and reconciles it against what is already on disk: with no unit it writes one and starts it; with an unchanged unit that is already active it starts nothing and reports started nothing; with a rewritten unit it restarts onto the new definition. The count of service starts is the measure of idempotency, and it is one across the first two cases together.

The unit carries the environment rather than inheriting it. ExecStart is the resolved absolute executable, obtained as a sibling of the running interpreter and falling back to the one reckon on PATH, and the Environment="PATH=…" line is built from the directories this project's routable backends resolve in, unioned with the ambient PATH and ordered so the backend dirs come first. That is exactly the fact the seven-hour unit was missing, and it is why the test asserts the backend directory appears in the unit's PATH line while the same directory is absent from the ambient PATH — the ambient value cannot pass the assertion in its place.

§6 — The repository comes from the project's mount, not from the caller's shell

The incident this section records: two nodes were dispatched for one project from a shell whose working directory was a different project's checkout, so the dispatch cut its worktrees from the repository enclosing the caller. One worker oriented and found none of its declared write paths; the other was stopped before it acted. The project's mount is the authority, so a caller naming no repository is given the mount and a named repository resolving elsewhere is refused before any worktree, pointer or ledger row exists.

reckon/crew/dispatch.py gains two functions. project_mount_repository(project) answers a project's repository root from the single mounted-project map every other scope resolution already consults, rather than a second spelling of the same map. resolve_project_repository(project, repo, flag="--repo") returns the mount when no repository is named, admits a named repository whose repository_identity equals the mount's — a linked worktree shares the mount's git common directory, so it is one repository under two paths, which is what lets a coordinator dispatch from inside a worktree — and otherwise refuses naming both resolved roots and the flag. dispatch() resolves through it, plan_dispatch() runs the same resolution for a dry run so the dry verdict matches the real one, and resume_plan() resolves the run's recorded repository from the project's mount before the ledger and budget lookups. reckon/crew/resumption.py does the same at the point a resume rebuilds its launch, and reckon/crew/promotion.py resolves before writing, ahead of the per-run commit check so a repository defect is reported as itself rather than as a missing commit further down.

§7 — A node that writes a check declares the mutation it fails against

The failure this section answers: a guard, assertion or test whose author never named the mutation it must fail against is a check that passed by not exercising anything. Three of those landed in one week, each green under its own gate, and each found by an independent reviewer rather than by the gate it was supposed to serve. The trigger is therefore the node's declared write paths containing a test file, not prose mined from the done-when, so the refusal rests on a structured field a dispatcher can read.

reckon/crew/node.py carries the evaluation and the composed text: is_test_path recognises a test-naming basename (test_*.py, *_test.py, *.test.*, *.spec.*) or an enclosing test/tests directory, and negative_control_finding returns a finding naming the negative_control field and the test path that triggered it. reckon/crew/dispatch.py appends that finding inside plan_dispatch, immediately after validate_node, so a triggering node without a declaration is refused before any worktree, live pointer or ledger row exists — the same way a missing specification level is refused. The declaration travels as the new structured field TaskNode.negative_control, emitted by as_dict into the live pointer and read back through both rebuild paths, so promotion tests a field rather than re-deriving intent from the brief.

reckon/crew/promotion.py's _require_declared_negative_control is the second surface. It resolves the manifest's negative_control_log against the manifest's own directory, refuses when the field is absent, when the named log cannot be read, and when the log's text does not name the declared mutation — a failing log for an unrelated reason is not the negative control, so the declaration is matched against the log's content rather than against its existence. The recorded row carries negative_control beside impl_move, with a verdict of matched, none-recorded or exempt and the reason, so an audit reads the outcome without reopening the run. A declaration of none: <reason> is the explicit escape for a check no mutation can redden, and it is recorded rather than refused; a bare none with no reason is refused naming that requirement.

§13 — A resolved launcher reports its origin before a bounded HTTP probe

Meaning and cost. §10 — Arming a watcher survives a service manager that cannot be reached

Implemented: commits 851249ed and 5a068617 at base a42b3f8626539fb0c771cd7c876a89266dbb023b, changing reckon/crew/runs.py and adding tests/test_watcher_arming_fallback.py.

The change. ensure_watcher_service now separates the calls that touch no bus from the ones that do: the unit is still rendered and written first, and the manager calls (active, start, the lingering check) sit under a handler that arms by the process path when the failure means the bus is unreachable, and re-raises otherwise. §15 — A wait the reader does not understand is refused by name, and a file condition has a shape

Implemented, awaiting coordinator review: commit 800bef46 changes reckon/crew/recovery.py and adds tests/test_wait_shapes.py at base ca943455.

What the reader now accepts. A wait declaration has one of two shapes. An wait_file condition names a file condition as one path or a JSON array of paths, and its probe and terminal are derived from those paths rather than declared: the probe is test -e a -a -e b -a -e c, run without a shell through the same single argument vector every other wait uses, and the terminal it is matched against is exit:0. So the reader that answers the condition and the sweep that lifts the parked run need no second machinery, and a condition about files needs no scheduler query written by hand. A scalar is one path and is never comma-split, because a comma inside a path is part of the path. wait_probe keeps its meaning unchanged: a shell-free argument vector whose first element is a bare program name.

What the reader now refuses, and how. A probe or file condition that is present and unreadable is refused at the declaration, not at the probe, so the reason reaches the field the follower already renders. Each refusal names both accepted shapes, so the repair is stated in the row rather than inferred from it. A declaration carrying both wait_probe and wait_file is refused as two shapes for one wait, and so is a wait_terminal naming an exit-code sentinel, because the observation a terminal is matched against is the probe's own output and an exit status is not a state any probe prints. Absence stays a separate outcome: a manifest written without wait_probe at all still reports the missing field, so a value the reader could not read no longer reports the same reason as a value that was never written.
