Crew Runtime Positive Controls

A launch either resolves its backend to an absolute path before anything is written, or it refuses naming the PATH it searched; a launch that runs and dies before its first turn is one recorded failure, and the run leaves the lift loop until a person acts.

§1 — The launch resolves its executable, or it refuses before writing

The launch plan carried a bare backend name and inherited the PATH of whoever built it, so a watcher armed without the backend directory exec'd a missing binary and left a 0-byte stream per tick while the run read as working. Resolution now happens where the plan is built, at all three sites that construct one: a dispatch, a resume, and a member move.

The refusal is literal and names what was searched, so the repair is a command rather than an investigation:

backend command 'python3' cannot be resolved on the PATH this launch would
search: /nonexistent — install it or add its directory to PATH, then retry;
nothing has been launched

reckon crew watch resolves every backend its project can route to before the seat is taken, so a watcher that cannot lift is never a watcher that reads as armed.

SurfaceCaseResult

watcha routable backend missing from the project's PATHrefused at arm time; the watch seat directory is never created
launch planbackend presentargv[0] is absolute and keeps the launcher's own name

The refusal precedes every write. That ordering was not true of the resume path as found: the pointer was mutated with the context fit before the launch plan was built, so a refusal there would have landed after the pointer write. The reorder is what the resume case pins, by comparing the pointer's bytes before and after the refusal rather than asserting only on the message.

The path is made absolute without being canonicalised, and that distinction was found by the population rather than by reading: resolving a launcher installed as bin/codex symlinked to codex.js followed the link, so the run recorded codex.js, the dialect is selected by the command's name, and the run's own stream could no longer be read back — a run made unreadable rather than unrunnable. Three cases outside the new files caught it; the linked launcher now has its own case.

§2 — A worker that exits before its first turn is one launch failure

The reaper knew the child had exited and read that exit against nothing. A run whose stream file is empty when its process is gone is a launch failure, not a worker turn: it is recorded once on the run with the exit status, the argv and the stderr tail, the pointer moves to launch-failed, and the automatic lift refuses that phase until a person resumes or completes the run. The hand-typed resume is deliberately left ungated, so the phase is clearable by the person who repaired the environment.

The figure places the two outcomes of a launch beside the path each one takes.

MeasureResult
Backend exits 127 immediately, stream emptylaunch-failure records on the run: 1, exit status 127, argv equal to the launched argv
Second reaper tickphase unchanged, record count still 1 — no relaunch
Backend writes a turn, then exits 127 (control)0 records; the phase stays working
Automatic lift of a launch-failed runrefused with the phase and the exit status named; the launcher is never called and no resume-* file appears

The control case is the one that makes the first meaningful: it runs the same spawn and the same reaper on a backend whose stream is not empty, and asserts no record appears. It also waits for the reaper to have actually consumed the child, so it cannot pass on a process that was never reaped. With the emptiness guard removed, that control fails — which is how the guard was shown to be the thing the first case rests on. The reaper's exit status is converted from the raw wait status before it is recorded, so a process that exited 127 records 127 rather than 32512.

launch-failed is added to the states the follower needs action on, which places it under the blocked bucket rather than the working bucket, and classify_pointer renders it as its own classification carrying the failure count and the last cause. A dedicated infrastructure bucket in the flight and drain views was not added; the state, the count and the cause reach the follower through the classification instead, and that gap is recorded as a follow-on rather than claimed as covered.

Verification

The gate is the crew dispatch, watch, recovery and resume populations plus the two new files, run once to reports/reckon/s18-takeover/crpc-launch-resolution-and-failure-record-2/gate.log: 9 failed, 169 passed, exit 1. The same population at base e0a8a967 gives 9 failed, 161 passed — the eight added passes are the new cases, and the failure sets are identical, so the node adds no failures. The nine pre-existing failures are unrelated to the launch path (strictly, the resolution and reaper cases are the only ones touching the changed lines and all of them pass).

An earlier run of the same gate added three failures, all from the canonicalisation defect above; they are the measurement that found it, and they pass now.
