§2 — Honour the anchor, or refuse it

A dependency ref carries an optional section anchor ([project:]slug[#stage]) and the roadmap honours it: the anchor scopes the blocking to the section it names. A plan declaring depends_on="other#s3" stays dispatchable — its unanchored sections report ready and only the anchored section reports blocked — so a partial dependence no longer hides ready work as a whole-plan blocked. The mechanism landed in 9e666e3 (merged 1790e61) and was re-verified clause by clause at the merged head by a verification node.

The measure — one staged ref, two kinds of section report

The defect this section removes is that a staged ref was parsed and then discarded, so any unmet prerequisite blocked the whole plan. The gate reproduces the portfolio shapes and asserts each clause:

§3 — An obligation that neither project can see

Commit fd0b1d4. reckon audit now scans every open followup in every mounted project for a skill reference that names a plan in a different mounted project — an obligation the owning project's audit could never surface and the target's audit would never look for. Three outcomes, each a distinct flag:

  • the foreign target exists and is in a terminal state — FOLLOWUP_FOREIGN_TERMINAL, the finding naming both the holding plan and the foreign target plus the target's status;
  • the foreign project is not mounted — FOLLOWUP_FOREIGN_UNMOUNTED, reported distinctly rather than as terminal;
  • the foreign project is mounted but the named plan does not resolve — FOLLOWUP_FOREIGN_MISSING.

A followup pointing at a live (non-terminal) foreign plan carries no finding at all, and a resolved followup or a local / same-project-qualified reference is never foreign.

The measure — the missing row is reported, counted, and named

The core of this defect is that the row did not exist anywhere: the obligation was excluded from the owning project's pending work because its target is terminal, and from the consuming project's because the target is foreign. The gate therefore reproduces the three-state classification directly and counts the findings over the registered mounts:

What the finding is and is not

The finding is a lifecycle-shaped record carrying both holder identity (project, slug) and target identity (target_project, target_slug, target_status), so the audit CLI and the MCP audit tool consume it unchanged. One boundary is out of scope for this landing and noted as a gap: the CLI's fixed six-column audit table renders the finding row but has no column to display the foreign target, so a terminal reading at the CLI shows the holder and flag only. The finding object and the MCP surface carry the target; making the CLI present it belongs to the surface that owns cli.py.
