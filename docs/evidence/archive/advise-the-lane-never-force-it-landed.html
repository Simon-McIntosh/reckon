Advise The Lane, Never Force It

A dispatch onto a lane that will exhaust inside the node's own horizon carries the trajectory it never asked for, names the lane measured rework says serves the role more cheaply, and changes nothing about where the work goes.

§2 — The advisory arrives where the choice is made

Commit abfee217 adds a lane_advisory carry to the dispatch payload. The carry rides the lane reading the dispatch already takes — it opens no second probe — and reports the utilisation, the burn multiple, the projected exhaustion and the reset, with the node's own horizon placed beside them.

It is emitted without a caller asking, and without a second probe

The observing read is counted. A dispatch that emits the advisory reads the lane trajectory exactly once — the same call the dispatch made before the advisory existed — so no caller asks for the advisory and no extra request is spent on it.

Nothing about it moves the work

Three dispatches onto one lane are taken: one whose projection lands inside the horizon, one whose projection lands beyond it, and one whose lane publishes no projection at all. The payloads differ only in the carry. The resolved backend and the agent's backend are the same string in all three, so the advisory is data and never a routing decision.

§3 — The choice is recorded, so advice becomes evidence

Commit 7059a778 carries the advisory a dispatch computed onto the run's live pointer record, and makes the insufficient-evidence clause render the count that fired it. The record assembly in reckon/crew/dispatch.py had copied lane_declaration and lane_reading beside requested_backend and dropped lane_advisory, so the cheaper-lane clause was computed on every emitting real dispatch and then discarded, with no reader anywhere in reckon/ outside the payload object's as_dict.

The pointer carries the advisory, read back from the written record

A real dispatch onto a metered lane whose projection precedes the node's horizon writes lane_advisory onto its pointer record with the same four figures and the same cheaper-lane clause the payload object builds. The assertion reads the record the run actually wrote (crew.read_pointer) rather than the payload the CLI echoed, because the payload is assembled from a different object and cannot show a record assembly that omitted the key.

An absent advisory leaves no key, rather than a null

A dispatch whose resolution carries no advisory writes no lane_advisory key at all. A null would read as a lane that was assessed and found quiet — the opposite of a lane that was never assessed — and a reader cannot tell the two apart once the key exists with a null value. The case is driven by supplying a resolution whose advisory is absent; the pointer's neighbouring lane fields are asserted present, so the absence belongs to the advisory and not to a record that never landed.

The refusal renders the count that fired it

The insufficient-evidence clause reported the resolved lane's total usable runs while the cost it refuses over is drawn only from the runs carrying a paired worker-and- coordinator reading. A lane with twelve usable runs and three paired readings therefore rendered 12 usable run(s), 10 needed beside a refusal citing ten — a count that already met the floor. The clause now fires on the chargeable count and renders the same number, so the figure a reader sees is the figure that refused.
