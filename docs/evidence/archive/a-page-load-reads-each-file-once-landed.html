A Page Load Reads Each File Once

One section per landed node of the page-load repair. The served loader reads /_discover alone whenever it answers (§3), and the project picker is filled from the static mount list so it never waits on the computed rollup (§4).

§3 — The served loader reads discovery, not the superseded aggregate

Node: served-loader-reads-discovery-only.

What landed. Commit f6529a51 perf(ui): the served loader assembles state from discovery alone inverts the source order in docs/ui/state-loader.js. The loader now fetches /_discover/<project> first; when that response is ok it assigns disc and reads nothing else — the aggregate fetch is unreachable on that branch, not merely deprioritised. Discovery's inventory, sprints, milestones and north_stars are adopted whenever present, for both the distributed and the legacy layout, and active_sprint_id, timeline, blockers, source_format and resource_versions already preferred disc. The single row in window.STATE.projects is synthesised from the live counts, so no field of a persisted projects[] block reaches the surface while discovery answered.

The fallback is now lazy and ordered. Only an unreachable discovery — a network-level refusal or an explicit 404 — reaches the static views: state/<project>/projection.json first, and state/<project>/index.json only when projection is also unavailable. Any other HTTP discovery failure is raised even when a projection exists, so a live server refusing its own inventory is never disguised by a stale aggregate. That last rule is not new: it is what tests/test_project_state.py already pinned, and it is now reachable without the aggregate being read on the answering path.

Method

tests/test_served_loader_reads_discovery_only.py runs the real state-loader.js under node with a recording fetch, in the style of tests/test_spa_state_boundary.py. A branch per URL records each request and answers it, so the assertions read the requests the loader made and the state it assembled, not the source text. Case 1 makes discovery answer while serving a marker field (persisted_projects_count) only a persisted projects[] block would carry; cases 2 and 3 refuse discovery at the network level and supply projection, then index.

§4 — The project picker never waits on the rollup

The three assertions and what they observed

tests/test_shell_project_list_is_immediate.py loads the shell through tests/spa_browser_harness.py with the fetch layer replaced by a mock. The mock answers /_projects/mounts.json with five mounted names, /crew with an empty run list, and /_discover/<p> with an empty inventory; /_projects/index.json returns a promise that is never settled, which is the reported failure reproduced deterministically rather than waited on.

§4 assertionObserved
With /_projects/index.json never resolving, the picker menu lists every name in the mocked mounts file ["imas-codex","imas-efit","imas-ink","nova","reckon"], and the rollup request was observed as made (indexRequested true)
On a project's plan view, no /_discover/<other project> request is made zero discovery requests before the palette opened
Opening the command palette makes one such request per mounted project the set of discovery requests equals the five mounted names

The rollup's rows are still merged into the picker when they arrive; the merge is additive and is not a gate. The first assertion is the one that carries the reported defect, and it is the one the negative control falsifies.
