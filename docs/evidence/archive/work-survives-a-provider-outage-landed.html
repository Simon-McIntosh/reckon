Work survives a provider outage — landed evidence

One incident cost five resumable sessions. All four executable sections now close the routes it took: a promotion that would destroy a resume path is refused, the worktree outlives the promotion while its session lives, a missing session id is no longer evidence of an unresumable run, and the recovery order is carried in the record rather than recalled from guidance.

Record scope

The incident is worth restating because every measure here points at one of its steps. Five runs were killed by per-request provider refusals, read as unresumable because their live pointers said session_id: null, promoted as infrastructure failures, and had their worktrees released. The session ids were in the runs' own streams the whole time and were written into the permanent record by the very operation that destroyed the resume path. Only the working directories were actually lost.

§2 and §3 stop the loss recurring; §4 removes the reasoning error that started it; §5 stops the recovery order depending on anyone remembering it. §6, recovering the five runs themselves, is owned by the coordinator holding the S16 write scope and is recorded on the plan rather than here — it is a recovery task against specific runs, not a change to this repository.

§2 — A promotion that would destroy a resume path is refused

Found already landed by a currency audit rather than dispatched. _require_resume_waiver in reckon/crew/promotion.py refuses a promotion that would delete a resume path, naming both reckon crew resume --run <id> --advice <answer> and the explicit --waive-resume-path REASON override. The discarded path survives on the ledger row as resume_waiver beside the session it discarded, so a deliberate discard is distinguishable afterwards from an accidental one — precisely the distinction the incident could not make. A waiver carrying no stated reason is itself refused. Covered by the accepted and unreasoned cases in tests/test_crew_promotion.py.

The evidence that matters here arrived unsolicited, from the operator it inconvenienced. At about 13:20 on 2026-09-04 this guard stopped the peer coordinator shipping S16 from promoting exactly this state on its own run, and required it to state in writing why the session was safe to discard. That session had destroyed five resumable sessions the same morning by promoting this state and reading session_id: null as a verdict; it reported the interruption as the behaviour it had asked for. A guard measured by the person it obstructs is the only measurement of a refusal that means anything.

§3 — The worktree outlives the promotion while the session lives

Commit a1bf7da, 340 insertions. Gate uv run --no-sync pytest tests/test_crew_promotion.py -q — 19 passed in 1.50 s, ruff findings delta zero against a baseline of 10.

Releasing the worktree is what converted a recoverable outage into a loss: the transcripts survived and the directory they had been oriented against did not, and a resume has no working directory. So the release is now conditioned on the session being unrecoverable rather than on the run reaching a terminal state. A retained tree records its retention on the ledger row, and reads as its own third category in the worktree audit — never as clean-and-reachable, never as holding unintegrated work — so a deliberately held tree is not mistaken for residue. A waived promotion still retains the tree unless the waiver explicitly discards it.

Asserted through the crew complete entry point and through the audit that enumerates worktrees, not through the release helper. The plan's insistence that this not be folded into §2 as one node was right: refusing a promotion and conditioning a release are different behaviours with different negatives, and one node would have let either pass on the other's evidence.

The node was also killed once mid-flight by an infrastructure fault — codex reported apply_patch verification failed: invalid patch: multiple operations target …/manifest.md — and was resumed rather than redispatched, after its worktree was confirmed clean and carrying nothing beyond base. It kept its context and cost one turn.

§4 — A missing session id is not evidence of an unresumable run

Commit e4dacc2. Gate uv run --no-sync pytest tests/test_crew_recover.py -q — 18 passed in 1.99 s, zero failures.

observe now answers recoverability as a derived fact rather than handing back a field whose meaning the caller must know the internals to read. A dead run whose pointer carries no session id but whose stream does reports resumable and names the recovered id. A run with neither reports not resumable and states which evidence was absent. Neither answer requires reading session_id directly, and the negative is asserted so the not-resumable answer stays reachable rather than becoming an unreached branch.

The sharpest part of this section is that the capability already existed. resume_plan had recovered exactly this case for some time — where the record lacks a session id it calls observe and re-reads. So the coordinator's reasoning was sound given what it was shown, and what it was shown omitted the one fact that would have changed the decision. That is the same defect family as a display discarding a value the record holds: not a wrong answer, but an unanswerable question, which is more expensive because a wrong answer can be contradicted by a measurement and an absent one sends its reader elsewhere.

§5 — The recovery order is carried by the tool, not by memory

Commit a88e833. Gate uv run --no-sync pytest tests/test_crew_recovery.py -q — 64 passed against a base of 62, with tests/test_crew_promotion.py at 23 passed and tests/test_ledger.py at 77 passed as supplementary gates, and zero added ruff findings.

The correct order after a per-request refusal — inspect the worktree, resume the session, reconcile only once resume is impossible — had been written in this workstation's guidance since the first instance and was not applied at the second, four hours later, by a different session. Guidance recalled at the moment of an incident is a compensation, and compensations fail. So the ordering is now carried by the record: the classifier returns resume_remedy with the resume command, the recovered session id and the source that answered, and crew complete passes that mapping once into ledger.build_record so it survives into the promoted row. A post-hoc reader of a discarded run can see what was available at the time.

Two design properties were held deliberately rather than by accident. The remedy is a distinct field from resume_waiver: the waiver records a deliberate discard and the remedy records an available recovery, and collapsing them would make a discarded run and a recoverable one indistinguishable — the exact defect this plan exists to remove. And classify_pointer stayed pure and read-only, with the persistence decided in one place rather than promotion reaching back into the classifier for a second opinion.

The negative half is asserted, which for this section is the half that matters: a folded real refusal with no pointer session, no readable stream and no ledger row omits the remedy, names all three absent evidence sources in its detail, and emits no resume action. A remedy that always appears would be a suggestion, not a finding.

Two notes on how it ran. The evidence came from tests/fixtures/backends/codex-usage-limit.jsonl — a recorded refusal rather than a synthesised one, as the section required. And the worker proved the combined state rather than its own half: it built a virtual merge tree against the test-role promotion refusals that had landed hours earlier and confirmed both those refusals and the remedy pass-through survive together. The node also blocked once, correctly, because the fence I gave it excluded the two files that persist a promoted row; the scope was granted on the live pointer and the session resumed, and the run is recorded --scope-changed.
