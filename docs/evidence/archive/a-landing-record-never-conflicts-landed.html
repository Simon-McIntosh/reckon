A Landing Record Never Conflicts — landed record

Composition of a plan's cumulative evidence record at read time: the record file's own bytes followed by its fragments in ledger promotion order.

§3 — The record is composed at read time, and the plan comment goes through the versioned write

compose_landed_record in reckon/evidence.py reads a record's own bytes and appends each fragment under docs/evidence/fragments/<plan>/<node>.html in the order the ledger records the fragments' promotions, resolving both the archived and live record spellings. A fragment is named for the ledger row's node, so a redispatch carries that node's latest fragment once, at its earliest promotion. Only rows for this plan are read, so another plan's same-named node cannot reorder this record. A fragment whose node has no promotion yet — merged by a coordinator before its run is promoted — has no recorded order, so it is composed after the ledgered ones in filename order rather than hidden. The function writes no file and does not call synthesize_landed_record, so a record with no fragments composes to its own bytes byte-for-byte.

Readers through the composer — the served record and the audited record read through compose_landed_record. The reckon serve file route for docs/evidence/archive/<plan>-landed.html returns the composed bytes with an ETag that is the digest of those bytes rather than the record's stat, so a fragment landing after the record was written is seen on the next load instead of a 304 on stale bytes. reckon/doccheck.py audit_file audits the file route's composed text, so a fragment-only audit error such as a relative <img src> is reported. Both readers fall back to the record's own bytes when the ledger or the record cannot be read, and a record with no fragments is served and audited byte-identically.
