Correction — two repairs were measuring the runner

A coordinator verification at 601d0239 reported three failures in tests/test_crew.py where this node's own run had reported one. Two were this node's fault: both repairs below encoded the machine rather than the behaviour.

  • The in-harness directive's scope. test_an_in_harness_dispatch_returns_a_directive_to_bind asserted the plan's shared landing paths join the declared scope. They do, but only when the worker can write the worktree it is handed, and that judgement is resolved from the sandbox write roots, which include the process temp directory. A throwaway repository under /tmp therefore reads as writable and one outside it does not, so the assertion's outcome followed where pytest's tmp root lived — and this node's own base and head runs named a --basetemp under it. Measured directly: with the --basetemp under /tmp the directive carried four scope entries; with the same --basetemp under ~/.cache it carried one and the test failed, exactly as the coordinator's run found. The judgement is now pinned and both branches are asserted, so the test measures the directive contract rather than the filesystem layout.
  • The redispatch delivery clock. test_redispatch_does_not_inherit_a_terminal_delivery holds that the previous attempt's terminal delivery is not credited to the next attempt. Manifest freshness compares the file's mtime against a second-resolution attempt start, so a delivery whose mtime lands inside the following attempt's own second is judged to have been written after that attempt began. Demonstrated against the classifier with a delivery stamped one nanosecond into the following attempt's second: freshness returns True, where a delivery in an earlier second returns False. Each delivery in the test is now back-dated to the attempt that wrote it, which keeps the two attempts ordered however quickly the run proceeds.

Cause, named with file and line. Two test-side defects in tests/test_follower_freshness.py::test_running_follower_reloads_without_stream_or_registration_gap. First, and the one both logged base runs actually meet, the test appended its first event immediately after the registration was observed and then read the stream. A follower fixes its read offset to the stream's length at the instant it attaches (watch_stream_cursor, reckon/crew/runs.py), so an append whose bytes are already written when the offset is taken sits behind the offset and is never rendered: the append raced the attach, and the read raised _queue.Empty at the base test's line 113. Repair

The seam is now a module-level override appended to the copied module rather than a replacement of a known fully-qualified line. The test writes _render_watch_transition = format_watch_transition followed by a new def format_watch_transition(event, **kwargs) that returns 'fresh:' + _render_watch_transition(event, **kwargs). Writing the file advances the stamp the follower reloads on, and the override is what its re-imported module serves, so the rewrite names no source line and survives any change to how a transition returns. Determinism comes from _await_attached, which appends throwaway probe records (named attach-probe-* so no measured run can be mistaken for one) until one is rendered, proving the follower is reading before the measured transitions are seeded — none then sits behind the attach offset. The wait ends only on a row carrying the probe node, and _drain_probe_rows then discards every probe row still queued: the follower polls at 0.1 s against a 1.0 s read, so a stall can render two probes before the first is read, and the second was once handed to the measure as a measured row — failing the node set with a message about the transitions rather than about the probe. The measured reads (_measured_rows) count only rows carrying a measured node and skip any probe row, so one left over from proving the attach can never stand in for a measured one. reckon/crew/recovery.py is not modified.
