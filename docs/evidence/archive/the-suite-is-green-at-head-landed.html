The Suite Is Green At Head — landed evidence

This cumulative record holds the evidence for the suite-repair plan. Each repair node appends its own section as it lands: the red files it owned, the cause group behind them, the ids it repaired, and the negative control that shows the repaired assertions can still fail. The question the record answers is deliberately narrow — not "does the suite pass" but "was each red file red for the cause the repair names, and does the repaired assertion still bind".

The nine crew test files: 25 recorded ids red at base, 57 tests green at the repaired head

Scope. Nine test files owned by one repair node, carrying 25 of the failing node ids recorded for the plan's repair partition. One pytest process per file, each with its own --basetemp, never the whole suite in one process.

Revisions. Base 77c20349aa33b7ddda106d6b3a35fa62f9549fa5; the repair is de851cfa, which changes the nine test files and no product source. Because the source tree is untouched, a reading at the repaired head differs from base only through the test files — which is what makes the comparison below a statement about the repairs rather than about the fleet.

Cause. Every id was red for the same cause group: an assertion that had been passing only because a guard was open. The guards whose closures the files had not absorbed are the now-required declaration of a specification level, the required negative-control declaration on a node that writes a test path, a lane-declaration refusal that is now gated on the backend being metered rather than on the caller's silence, session reuse keyed to the task rather than to the member, and the grant of the shared landing paths to every node's write scope. The repairs move the assertion in all nine files and move no behaviour; the one file that compares two dry runs field by field now masks the lane advisory's wall-clock stamps, which differ between invocations of the same dispatch.

Result at the repaired head — 57 passed, 0 failed. test_a_brief_points_rather_than_quotes 13, test_crew_cross_project_claims 10, test_crew_dryrun 4, test_crew_ephemeral_members 1, test_crew_members 3, test_crew_routes 13, test_crew_watch_visibility 5, test_dispatch_lane_disagreement 7, test_execution_fit 1. Exit status 0 for every file's process.

Negative control — 25 of 25 recorded ids failed, none passed. Each file was run as it stood at the base revision, selecting only the recorded ids, from a copy of the base content placed under a synthetic root so that the tree's own provenance never enters the reading. The first line of the control log states the control being run. All 25 ids failed with their recorded errors, so none of the repaired assertions is a test that would have passed at base anyway — each is one that can still fail. Full transcript: negative-control.log in the node's run directory, whose first line reads run each repaired file as it stood at the base revision and observe its listed ids fail with the recorded error.

Two ids renamed to the rule they assert. test_bare_session_from_member_add_resumes_and_then_records_its_configuration and test_unnamed_dispatches_are_isolated_and_reuse_their_captured_session claimed the member-keyed session reuse that task-keyed reuse replaced. The recorded id is written beside its replacement here because the rename removes it from the tree.

Not evidence for. This section does not claim the suite is green at head. Eight further repair nodes own the remaining red files, and the plan's §2 measure "Green at the integrated head" is answered by one full-suite run at the merged head after every node lands — which no node's own file-local reading can stand in for.
