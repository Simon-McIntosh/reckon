Eleven surface failures that are not the browser — landed evidence

The count is nine failures and four errors gone with none added. The result worth recording is the one assertion that is still red on purpose, and the reason a node was told not to fix it.

Record scope

Twenty-six surface tests were failing. Fifteen are the host's navigation fault and belong to another plan. This plan separated the remaining eleven into ten stale contracts — assertions describing what the code used to do — and one real defect hiding among them.

Non-landing was proven rather than assumed before any work began: the census revision is an ancestor of the head and the diff over all eight plan-relevant test files and their surface sources was empty, so every census classification still transferred five days later.

The two leaning cases, resolved before the sweep rather than during it

Two of the failures were consistent both with the code having moved deliberately and with the code being wrong. The plan's locked decision required each to be settled by a stated finding first, in a read-only step. They landed on opposite verdicts, which is the whole argument for the decision.

One case is not covered by that delta and says so. The rendered topbar ordering gate skips on both sides in the worker sandbox, so its migration rests on the census's recorded rendered text and has not been executed. It needs a rendered run on a host where that gate runs.

§3 — The one real defect, and its section title was a symptom

The section read the graph does not mount on a page that loads. It mounted. It rendered its empty branch — no plan in this project depends on another — while the inventory it had been handed held dependency edges. The pre-fix probe returning zero node cards beside that message is what separates a component that failed to mount from one that mounted with nothing to draw.

The view derived endpoint rows only from the roadmap-computed field, which a document carrying just the plan inventory does not have. The fix falls back to deriving the same rows from the inventory when that field is absent or empty, so the roadmap stays authoritative wherever it is present and the empty branch stays reachable where there genuinely are no edges. Verified on the file scheme, since served navigation does not complete on this host: populated on each of six consecutive probe runs against a stated floor of three.

Follow-up: the roadmap-endpoint assertion now follows the source

One stale contract survived outside the six files the sweep measured. tests/test_roadmap_endpoints.py asserted the source literal _roadmapEndpointRows(M?.endpoints) in docs/ui/graph.jsx, which appears once at the §3 fix's parent and zero times at the fix itself — counts 1 and 0 at revisions 1d9e90c^ and 1d9e90c — because the fix moved the call into a guard that falls back to deriving rows from the inventory when the roadmap field is absent. The object of the assertion, a call-site spelling, was never the property the test protects.

The migration drops the source-substring assertion and keeps the behavioural node-run the test is named for, which renders the real adapter over the real roadmap report and asserts the graph's endpoint rows equal the project's roadmap rows. A substring assertion over source is how this broke at all; re-pinning it to the new spelling would only relocate the fuse. No surface change was made, and all five tests in the file pass.

What the deliberate red protects

The sweep was dispatched with an explicit instruction to leave tests/test_spa_reader_geometry.py untouched and failing, and that assertion still reads 3 / 3 at the integrated head. Had the leaning-cases decision gone the other way — migrating both on the lean, which was one of the three options and the cheapest-looking — the sweep would have rewritten that expectation to 2 / 3, the board would have gone green, and the only thing currently reporting a live reader defect would have been deleted.

The cost of avoiding that was one read-only investigation node.
