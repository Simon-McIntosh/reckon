§5 — Every storage read has a deadline

Commit d026717e wraps every registered MCP tool as an async adapter that runs its unchanged synchronous body on a worker thread under a deadline, and answers an expired deadline with a typed storage-slow result. The premise was confirmed from the installed SDK rather than assumed: mcp 1.28.1's server/fastmcp/utilities/func_metadata.py calls a synchronous tool body inside the coroutine (else: return fn(...)), so the event loop is the serialization point, and a second call waits behind the first.

The bound is proved by a filesystem stand-in that blocks on one path and answers on another, with the deadline set through RECKON_MCP_DEADLINE_SECONDS so the gate runs in seconds. The mutation removes the worker thread and the deadline together: the blocked read then returns past the test's bound and the concurrent read waits behind it.

§2 — A follower that never held the registration checks its owner

Outcome — the owner check runs on every wait pass, holding the lock or not. _check_consumer in reckon/cli.py no longer returns before it compares the owner, so a read-only follower ends on the tick after its own owner dies. The owner is resolved once, at the follower's first start, by runs.follower_owner(): from RECKON_FOLLOWER_OWNER when an armer stamped one, from os.getppid() exactly once otherwise, and held from that read onward so a later re-parent cannot move it. _FollowerRegistration.acquire() in reckon/crew/runs.py writes that owner into the record instead of os.getppid(), and a recorded owner of pid 1 or below is treated as gone rather than as a reason to skip — which closes the takeover hole where a read-only follower inherits a released registration while orphaned and becomes an immortal holder naming init. A reloaded image is handed the same owner through the environment its execve receives.

How the bound is derived

The exit bound is not a round number chosen to be comfortable. The wait pass polls every 0.1 s, so a five-second bound admits fifty passes, and a regression that asked about the owner once every fifty passes would satisfy it while leaving a follower alive for nearly five seconds after its owner died. Two seconds is 2.2× the slowest of the read-only samples above — enough for interpreter teardown and the jitter of a loaded node, and about twenty passes rather than fifty. The live-owner control is what makes the window meaningful: it requires a follower whose owner is alive to still be running and still the holder at the end of the same two seconds, so the bound separates a follower that checked its owner from one that did not. The re-parented case is bounded separately, from the replacement image becoming live, because that window carries the replacement's own import cost: three seconds against samples of 1.193, 1.220 and 1.240 s, at 2.4× the slowest.

How the read-only case is set up, and why

The done-when's first case asks for a holder and a read-only follower armed by one stub parent, both leaving on the tick after that parent is killed. Written that way the case cannot show the defect: when the one owner dies, the holder leaves and frees the registration, and the read-only follower then leaves by taking that registration over in the same tick it acquires it — with the early return restored it still leaves, so the mutation passes. The mask is exactly the scheduling slack the done-when says the assertion may not allow.

The orphan's real condition is a read-only follower whose own owner is gone while an older follower still holds the registration — one re-armed Monitor behind another, which is how the ten nova orphans accumulated. The case therefore arms two stubs, one per follower, and kills the read-only follower's owner first while the holder's owner stays alive. The read-only follower cannot leave by takeover, so the only thing that can end it is the check the early return skipped. The holder's own half is then measured by killing its owner. Both halves of the path are asserted, and the deviation from the single-stub form is what makes the declared mutation fail.

Why the owner carry needs its own case

The reload is easy to mistake for coverage of the carry. It is not: execve does not change a process's parent, so when the reload happens while the owner is alive, a replacement that read os.getppid() would read the owner and the case would pass with the carry deleted. That was measured here — removing the two carry lines leaves the reload case green (log negative-control-mutation3.log, which runs it alongside the failing case).

The carry is therefore read where the parent is not the owner. A subreaper process is started above the arming stub (prctl(PR_SET_CHILD_SUBREAPER) via ctypes), the follower is held still with SIGSTOP, and the stub is killed. The follower is now adopted by a live process rather than init — asserted from the process table, not assumed — and it has not yet looked at anything. Its source stamp is then advanced, the follower is resumed, and on its first pass it replaces its image. The replacement resolves the process it reports to: from os.getppid() that is the live subreaper and it runs on forever; from the carried RECKON_FOLLOWER_OWNER it is the dead stub and it leaves. The replacement is observed on its own command line, so a run in which no reload happened cannot pass by measuring the first image, and the clock for its exit starts only once it is live.

Human-readable estimation

Regression risk of the change itself is low: it removes a branch and changes where an identity is read from. The risk it carries is the identity, and that is what the second and third declared mutations probe. A reviewer should read follower_owner()'s resolve-once semantics and acquire()'s write of it together, because a change to either that made the value follow the current parent would be caught only by the takeover case; and the reloader's carry separately, because the reload case alone cannot see it. The two failure shapes are different and both are covered: a follower that keeps running under a dead owner (mutations 1 and 3) and a record that names the wrong process (mutation 2). Confidence in the landed behaviour is high: six latency samples across three cases, all three mutations fatal to the gate, and §7's landed test green in the same invocation.

§4 — Promotion releases only its integrated, unclaimed worktree

The promotion cleanup now removes a run's worktree only after the ledger row and landing comment are committed, and only when the tree is clean, its HEAD is reachable from the integration branch, and no other live pointer claims it. The promoted pointer is explicitly excluded from the claim set, so the decision does not depend on a timing assumption about pointer deletion. Cleanup is withheld for dirty, unintegrated, live-referenced, blocked, and failed runs, and the release result is amended onto the same landing commit and persisted on the ledger row.
