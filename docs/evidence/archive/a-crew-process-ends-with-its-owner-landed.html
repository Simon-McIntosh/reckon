§5 — Every storage read has a deadline

Commit d026717e wraps every registered MCP tool as an async adapter that runs its unchanged synchronous body on a worker thread under a deadline, and answers an expired deadline with a typed storage-slow result. The premise was confirmed from the installed SDK rather than assumed: mcp 1.28.1's server/fastmcp/utilities/func_metadata.py calls a synchronous tool body inside the coroutine (else: return fn(...)), so the event loop is the serialization point, and a second call waits behind the first.

The bound is proved by a filesystem stand-in that blocks on one path and answers on another, with the deadline set through RECKON_MCP_DEADLINE_SECONDS so the gate runs in seconds. The mutation removes the worker thread and the deadline together: the blocked read then returns past the test's bound and the concurrent read waits behind it.
