§2 — A follower that never held the registration checks its owner

Outcome — the owner check runs on every wait pass, holding the lock or not. _check_consumer in reckon/cli.py no longer returns before it compares the owner, so a read-only follower ends on the tick after its own owner dies. The owner is resolved once, at the follower's first start, by runs.follower_owner(): from RECKON_FOLLOWER_OWNER when an armer stamped one, from os.getppid() exactly once otherwise, and held from that read onward so a later re-parent cannot move it. _FollowerRegistration.acquire() in reckon/crew/runs.py writes that owner into the record instead of os.getppid(), and a recorded owner of pid 1 or below is treated as gone rather than as a reason to skip — which closes the takeover hole where a read-only follower inherits a released registration while orphaned and becomes an immortal holder naming init. A reloaded image is handed the same owner through the environment its execve receives.

The read-only follower leaves well inside the gate's five-second bound, and the registration it never held still names the holder when it goes: it left by checking its owner, not by taking a registration nothing had released.

How the read-only case is set up, and why

The done-when's first case asks for a holder and a read-only follower armed by one stub parent, both leaving on the tick after that parent is killed. Written that way the case cannot show the defect: when the one owner dies, the holder leaves and frees the registration, and the read-only follower then leaves by taking that registration over in the same tick it acquires it — with the early return restored it still leaves, so the mutation passes. The mask is exactly the scheduling slack the done-when says the assertion may not allow.

The orphan's real condition is a read-only follower whose own owner is gone while an older follower still holds the registration — one re-armed Monitor behind another, which is how the ten nova orphans accumulated. The case therefore arms two stubs, one per follower, and kills the read-only follower's owner first while the holder's owner stays alive. The read-only follower cannot leave by takeover, so the only thing that can end it is the check the early return skipped. The holder's own half is then measured by killing its owner. Both halves of the path are asserted, and the deviation from the single-stub form is what makes the declared mutation fail.

Negative control

Declared as: restore the early return in _check_consumer for a non-holder; and make acquire() record os.getppid() again. Executed in three runs against this node's final source, each reverted afterwards with the file verified byte-identical to its pre-mutation copy:

  • Mutation 1 alone: 1 failed, 3 passed. test_a_read_only_follower_leaves_when_its_own_owner_dies fails on exactly the mechanism: the follower was still running 5.0 s after its owner was killed, so it did not check its owner.
  • Mutation 2 alone: 1 failed, 3 passed. test_a_takeover_records_the_armed_owner_not_the_claimants_parent fails on the record naming the claimant's parent instead of the armed owner.
  • Both together: 2 failed, 2 passed, the same two tests. The red log's first line repeats the declared string verbatim.

Two controls guard the window rather than the mutation. test_a_follower_whose_owner_still_arms_it_keeps_reading leaves the owner alive and requires the follower to still be running and still the holder past the same five seconds, so the bound separates a follower that checked from one that did not. test_a_reloaded_follower_still_leaves_when_the_original_owner_dies confirms the image replacement from the replacement's own command line — the launcher it inserts its import root with is absent from the armed argv — so a run in which no reload happened cannot pass by measuring the first image alone. Every test also asserts the real follower directory for the probe project is absent before and after, so a temporary home did not leak into live state.

Human-readable estimation

Regression risk of the change itself is low: it removes a branch and changes where an identity is read from. The risk it carries is the identity, and that is the second declared mutation. A reviewer should read the two together — follower_owner()'s resolve-once semantics and acquire()'s write of it — because a change to either that made the value follow the current parent would be caught only by the takeover case. Confidence in the landed behaviour is high: three independent latency samples, both mutations fatal to the gate, and §7's landed test green in the same invocation.
