§2 — The commit guard asks about repository paths

Defect reproduced before repair. A run whose manifest was status: complete, whose commits field was correctly empty, and whose changed_paths named only absolute paths outside its repository was refused by _require_commit_for_changed_manifest in reckon/crew/promotion.py with “has a complete manifest with changed_paths, but the manifest field 'commits' is missing”. That is the shape of a review or investigate run: its deliverable lands under the crew reviews directory, so there is nothing inside any repository to commit and the run could never be reconciled. At base the outside-only case raised that error and failed.

The guard now asks whether any named path resolves under the run's own repository root: a relative path is repository-relative, an absolute path resolves as written, and a path anywhere else — a store directory, a scratch path under the crew home — requires no commit here. A write claim can be narrowed or released without a promotion

A run's declared write paths are created at dispatch and were, until this change, destroyed only at promotion. --write-path appears in the help of one of the 31 crew subcommands, dispatch, and the scan finds it there as its own positive control; no crew claim subcommand exists. A coordinator whose worker blocked at its fence therefore had two moves, both wrong: hand-edit the live pointer under the shared crew config home, or redispatch and discard every turn of context the worker held.

reckon/crew/claims.py (commit c754cfe2a37fd5e4e25ab3523078804de99f0020) adds release_claim and narrow_claim, which rewrite the pointer's node.write_paths and report the amendment as a ClaimAmendment — previous and current declarations, the paths removed, and any unintegrated work the stopped run still holds. Nothing is wired to a command: reckon/cli.py is owned by a second node, so the module is the deliverable and the intended entry point is crew claim narrow|release, rendering ClaimAmendment.as_dict().

Refusal is the mechanism

An amendment is admitted only for a worker shown to have stopped, and "shown" is narrow by design: a live process refuses; a pointer whose launcher_host is not this host refuses, because a pid answers only on the machine that issued it and the crew config home is shared across login nodes; and a pointer that records no process yet refuses, because the pointer is written before its worker is spawned. Ones that cannot be answered refuse rather than being read as dead.

A dispatch commits the session member it registers for itself

Defect reproduced before repair. A dispatch handed no member provisions one under its own session, and that registration path wrote the roster without requesting a commit. At base 7dfae503, after a session registration succeeded, git rev-list --count base..HEAD was 0 and git status --porcelain -- docs/state/proj/crew.json reported the file untracked: the row existed only in the checkout that wrote it and rode whichever commit came next. A declared member's registration never sits in that state, because the registration code commits what it writes.

Commit 6a0bb500 requests the commit at the call site that performs the write. _register_session_member passes commit=True to ledger.register_member, so the row reaches the repository as chore(roster): register <id> under a subject naming the member and a commit carrying only docs/state/<project>/crew.json. A commit that fails is surfaced as a CrewError naming the uncommitted registration instead of being retried into a registration the caller believes landed.

The committing registration exposed an ordering defect in the same path. A dispatch reaps idle session rows before it registers its own, so both roster writes land in one checkout in sequence. A reap left in the tree is content that is not the registration's to record, so the registration's commit must refuse it — and then the dispatch provisions no member at all. The reaper now commits the removal it writes, and skips that commit when the roster already carries content that is not its own, which leaves the write in the tree exactly as an unrequested write would and leaves the next named commit to refuse it. The skip is what keeps a roster whose checkout cannot answer, and a concurrent peer's uncommitted registration, from being absorbed.
