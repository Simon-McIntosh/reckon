§5 — Per-node wall time and width-at-start

reckon/crew/summary.py:run_rows returns the project's committed run rows, each carrying two derived figures: wall_seconds from that row's own dispatched_at and completed_at, and width_at_start from the measured spans of the same row set at the row's dispatch instant. The stored wall_seconds field is never consulted. The derivation reuses reckon/ledger.py:_worker_seconds rather than restating the subtraction, so the read and the ledger agree on what a span is by construction. Landed in 20496d11.

What reaches a reader, and what does not

A figure the row's stamps cannot support is None, never 0 — an absent measurement and a zero-second span are different facts and the second is a plausible-looking lie. A ratio of 0.99 between the widths at two dispatch stamps that are close together is possible, so no rounding or floor was applied; the counts are integers over the measured spans. No surface reaches this read. crew ledger --view summary resolves to ledger.summary (reckon/cli.py:3122), the aggregate, which carries no per-run rows; crew ledger --view records reaches ledger.runs (reckon/cli.py:3117), the rows before either figure is derived. The seam is therefore one call in an existing view rather than a new view, and wiring it touches reckon/cli.py, reckon/ledger.py and reckon/mcp_views.py, none of which was in this node's write scope.

§9 — The check-command test witnesses the isolation it depends on

The gap was named by the independent review, not by the suite. The review of the node that gave audit_manifest its first production caller scored the work 95/100 and spent its one finding on the new test file: the fixture redirected RECKON_HOME to a test-config home but never asserted the crew home was left untouched, so a broken home resolution would write the fixture's pointer into the real directory and every case would still pass. The repository rule names exactly that assertion for every write-shaped test, and it names why the write direction is the one that matters — a reader can only be wrong, while a writer can make others wrong. Four cases in that file each write a live pointer.

The obvious watch is the wrong one, and the reason is measured. A byte-for-byte comparison of the production crew home is not merely slow: on a live wave it is a moving target. Measured before writing the assertion, that directory held 598,286 entries and 138 of them were rewritten inside six seconds — stream logs growing, pointers appearing and being cleared by concurrent runs, reports rewritten mid-wave. A whole-tree comparison there would be slow, would be flaky, and a pass over it would be a statement about the fleet rather than about the case under test. So the watched root is the crew home this process resolved before a case substitutes one, which is the directory a broken resolution would actually write into — the suite's own temporary home, not the production one.

The order is guaranteed by a dependency, not by luck. The witness fixture requests the suite's temporary-home fixture by name, so the substitution is in place before it captures anything and the root it captures cannot be the production directory; the manifest fixture in turn depends on the witness, so capture precedes the case's write. Ordering by autouse alone would have left the root dependent on fixture instantiation order. The witness also refuses to be vacuous: if the root it resolved lies under Path.home() it raises, because a pass in that state would be measuring the fleet — the aim assertion, without which a witness pointed at the wrong directory reads as silent success, which is the failure shape this plan keeps finding.

The assertion is shown to fire, on a root the production home never sees. A guard that never fires is indistinguishable from no guard, so the file carries a permanent fifth case that constructs the witness over a substitute root under tmp_path, calls it once with nothing written (it stays quiet), writes the same pointer the manifest fixture writes, and requires the assertion to name the path it caught. The seam, and why it is a default rather than a new view

reckon/cli.py reaches ledger.runs for crew ledger --view records; reckon/mcp.py's records read calls ledger.read_records. runs keeping the stored row is not conservatism. runs is the raw promotion-order read and tests/test_ledger.py asserts its rows against the stored shape, so derived keys appearing there would have changed a shared shape in service of a read that did not need it. The two reads differ in exactly one respect and the difference is declared rather than incidental: read_records answers the reader's two questions, runs hands back what was committed.

The stored wall_seconds is not consulted on the derived path. The stored-vs-derived measurement for this repository's ledger is in the derivation record above and is not restated here.
