§2 — A follower never runs code older than the fleet it watches

Commit e5f4ef4 at 07:02 on 2026-09-04 — fix(crew): reload followers from imported code. The first of the section's three candidate shapes: the follower compares follower_code_stamp(), a SHA-256 over cli.py and crew/*.py mtimes and sizes, against the stamp it started with at a one-second cadence, and re-execs itself through the sys.path root that supplied the imported package, carrying a reader checkpoint across the replacement so no transition is lost. The third shape is the failure path rather than an alternative: when os.execv itself fails, the follower prints that it is stale and the exact command to cycle it, then stops trying.

Measured on a running follower, which is what the done-when required

The section is explicit that this must be asserted "by landing a change to the swept behaviour under a running follower and requiring the new behaviour, not by asserting that a re-exec function exists". This session supplied that incidentally:

  • The follower was started from the console script (.venv/bin/reckon crew follow --project reckon --session …) at 14:15:24.
  • Five crew modules then landed beneath it — promotion.py, prompts.py, query.py, recovery.py and ledger.py.
  • Its argv is now the launcher form, python3 -c "import sys; sys.path.insert(0, …); from reckon.cli import main; main()" crew follow …, which only the re-exec produces.
  • Its pid (4176213), its start time, its session registration and its stdout are all unchanged, and the watching pane received transitions continuously across the whole period.

So the reload costs no gap in the pane and no lost registration, which were the second and third clauses of the done-when. The fourth — that no skill text instructs a reader to restart a follower after a merge — holds: the ship skill states that a long-lived follower reloads the installed code when it advances and reports explicitly when a reload fails.

A reading trap, recorded because it caught the author

os.execv replaces the process image in place, so both pid and start time survive a reload. An unchanged pid is therefore consistent with reloading rather than evidence against it, and the argv is the only tell. The first reading taken here was that the follower had not reloaded, on exactly that mistaken inference.

The limitation is a property of the shape, not a bug in it

The mechanism cannot retrofit itself into a process that predates it, because the code that would re-exec was never in that image. Measured the same afternoon on the peer coordinator's follower for the same project: started 05:48:52, seventy-four minutes before e5f4ef4, still carrying the plain console-script argv nine hours later.

That follower was therefore missing every crew behaviour landed that day — including 6af7656, refresh live run classifications, which is the fix for the exact failure that session had independently reported: terminal rows sitting unnoticed while it believed it was waiting for a completion event. So the section's own motivating failure was still live in a second session, with the fix merged, for the one reason the fix cannot address.

The operational consequence is small and worth stating rather than rediscovering: a fleet adopting this needs one cycling pass at adoption, once, and never again. Neither the stamp-driven nor the announce-only shape would have avoided this — both also require the running process to hold code that knows to check.

The collaboration default, carried over from §7's own text

A finding about another repository is worth more to the session working in it than to the one that found it, and the night §7 was written the evidence was one-sided: every correction that mattered came from a peer measuring something the author could not see. A stale-base warning caught a merge misreading inherited ancestry as delivered work. A count of five-of-six dead-process claims holding unintegrated work stopped a data-loss predicate shipping. A measurement of zero file-writing tool calls corrected a loss claim in the other direction. Each arrived unbidden, and each was cheaper to send than to rediscover. So a coordinator that finds a defect touching a repository it does not own reports it to the session working there when one is live — as a finding, never as an instruction, and never as authority, since a peer cannot authorise work in a repository that is not theirs.

That default was exercised twice on 2026-09-08, in both directions and with a correction landing each way: a peer's dirtiness scan had concluded the largest unlanded delta was gone, and the reply that it was sitting in an unmerged commit was itself corrected on the instrument rather than the conclusion. Neither correction would have been sent under a silence default.

The repair derives the expected set from the server's own registry rather than retyping it, so the exact-five guard survives the next rename instead of becoming its first casualty: 1 failed becomes 7 passed.

The companion path is the finding. That repair could not pass without one line outside its fence, and the worker said so rather than making it quietly. skills/reckon-ship/SKILL.md still listed the pre-rename wire names in its allowed-tools — five tools the server no longer publishes, so the line authorised nothing at all. A stale authorisation list is invisible in exactly the way this plan keeps finding: it fails open, silently, and only a derived assertion notices.
