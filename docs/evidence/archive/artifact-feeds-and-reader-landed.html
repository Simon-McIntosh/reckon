Arrival is non-destructive — landed evidence

The section's own done-when and the boundary gate both pass, and the part of this record worth reading is the assertion that carries the whole point: the order of the rendered list before a change event arrives is kept equal after it, and differs only once the reader asks for the new rows. That assertion is demonstrated failing against the pre-change behaviour, because a hold that has never been shown to break a re-sort could not be told apart from an arrival that never happened.

Record scope

The loader diff, held against a rendered snapshot

The loader keeps a module-level rendered snapshot of the keys and version stamps (edited || last || version) that were on the page. Each change event refetches discovery and diffs the fresh inventory against that snapshot. Keys new to the snapshot become pending rows, never inserted; keys whose stamp moved become updates; keys that leave the inventory are pruned. The snapshot advances only when the reader reveals a held row, so an unrelated later change cannot silently absorb the pending set into the snapshot and drop the banner early.

window.STATE.arrival publishes pending, updates, byKind, total and a receipt that reads 2 new instead of live. The load keeps the inventory in state complete — nothing is removed at load time, so the hold is a view concern and the boundary gate, which requires new rows to remain in the inventory after a change event, is undisturbed.

The render-level hold

Artifact indexes freeze their rendered order while arrival metadata is present. The memo that previously re-derived the rows from the fresh inventory now runs against a frozen order that excludes the pending keys, keyed by the view state (kind, sort key and direction, status filter, hide-done) so a sort change rebuilds it. An in-place update keeps its position because the frozen order is keyed by resource id and the row's contents refresh in place.

The banner reads N new <kind> since you opened this list · show. The show control calls the loader's reveal, which adopts the held keys into the rendered snapshot, rebuilds the order to insert them in sort position, applies a one-shot three-second arrive tint, and clears the receipt back to live. A kind whose rows arrive does not disturb an index open on another kind.

The order-equality guard, and the demonstration that it fires

The assertion that carries the whole point is that the rendered row order before the click equals the order after the arrival payload: arrival_result["before"] == order0. A list that re-sorts under a reader loses the reader's place, and a test that only counts the pending rows cannot see that. The demonstration ran the suite against the base shell-plans.jsx and recorded the guard failing: the arriving rows re-sorted the list under the reader, baseline ['evidence:gamma', 'evidence:beta', 'evidence:alpha'] != post-payload ['evidence:gamma', 'evidence:delta', 'evidence:beta', 'evidence:epsilon', 'evidence:alpha'], the exact defect the section exists to stop. On the landed code the same assertion holds, and the order differs only once the show control is used.
