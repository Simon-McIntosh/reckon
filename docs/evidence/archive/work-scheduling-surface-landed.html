One pushed sprint — landed evidence

A project schedules exactly one sprint at a time. That invariant was implicit: any sprint could be written active, so two could be, and the derived active sprint became ambiguous. This section makes the invariant explicit in the type, gives it one atomic write to change, derives it for the reader, and reports its violation.

Record scope

Four code changes and one skill change. SPRINT_STATUS_ENUM in reckon/_schema.py gains open between planned and active, and reckon/project_state.py validates it as a stored status, so a project may hold several live sprints that are not the pushed one. A new push_sprint writes the promote-and-demote pair atomically: the selected sprint becomes active and every other sprint that was active becomes open, under one resource-lock set behind a move journal with compensating recovery, so an interrupted push restores both files rather than leaving two active sprints or none. The push op routes to it through apply_resource_ops. reckon/roadmap.py derives active_sprint_id from the unique active row, reports the remaining live sprints in a top-level open_sprints bucket, and labels member progress in-progress rather than active so an open sprint whose members have started carries no state_drift. reckon/mcp.py raises multiple-active-sprints to error severity and adds pushed-sprint-has-no-ready-work at warn. The sprint skill documents the status meanings and the op.

The two audit codes and their severities

CodeSeverityFires when
multiple-active-sprintserrorMore than one sprint carries active, so the derived pushed sprint is ambiguous. Raised from warn.
pushed-sprint-has-no-ready-workwarnExactly one sprint is active and none of its member plans is live with work remaining, so the push schedules nothing.

The warn is deliberately not an error: an exhausted or freshly pushed sprint is a legitimate transient, and gating on it would make the audit unusable at the moment the state changes. multiple-active-sprints is an error because no single sprint answers active_sprint_id in that state, which every consumer of the field depends on.

Recorded rather than smoothed over

  • An out-of-fence sibling test carries the superseded label. tests/test_roadmap_sprint_derivation.py:66 asserts the derived sprint label the spec changes to in-progress, and reds by exactly that one literal (1 failed, 1 passed). The adjacent assertion at line 67 that an agreeing sprint carries no state_drift still passes. That file sits outside this node's write scope and was not edited; the repair is the two string literals in that one test. It is the measured cost of the label change, not a defect in it.
  • The push op is placed on the sprint resource being pushed, not literally on the project resource. The plan text names the op on the project resource, but project.json is forbidden by PROJECT_DERIVED_FIELDS from carrying active_sprint_id, and sprints are separate resources, so a project-resource op cannot read or write the sprints it must change. The op therefore selects the sprint to push (doc_type="sprint", with the sprint id as the requested op's resource), and the atomicity is what the plan requires regardless of which resource carries the verb. Re-routing the surface to doc_type="project" is a small change in apply_resource_ops and no change to push_sprint.
  • Plan state is untouched by design. The pushed sprint and the plan's own metadata are the coordinator's write; a worker records the outcome and returns it. The stating of the new tests is evidence of the behaviour at the recorded commit, not proof that a later merge keeps it.
