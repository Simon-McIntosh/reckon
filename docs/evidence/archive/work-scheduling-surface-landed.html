One pushed sprint — landed evidence

A project schedules exactly one sprint at a time. That invariant was implicit: any sprint could be written active, so two could be, and the derived active sprint became ambiguous. This section makes the invariant explicit in the type, gives it one atomic write to change, derives it for the reader, and reports its violation.

Record scope

Four code changes and one skill change. SPRINT_STATUS_ENUM in reckon/_schema.py gains open between planned and active, and reckon/project_state.py validates it as a stored status, so a project may hold several live sprints that are not the pushed one. A new push_sprint writes the promote-and-demote pair atomically: the selected sprint becomes active and every other sprint that was active becomes open, under one resource-lock set behind a move journal with compensating recovery, so an interrupted push restores both files rather than leaving two active sprints or none. The push op routes to it through apply_resource_ops. reckon/roadmap.py derives active_sprint_id from the unique active row, reports the remaining live sprints in a top-level open_sprint_ids bucket, and labels member progress in-progress rather than active so a sprint stored open or active whose members have started carries no state_drift. reckon/mcp.py raises multiple-active-sprints to error severity and adds pushed-sprint-has-no-ready-work at warn. The sprint skill documents the status meanings and the op.

The two audit codes and their severities

CodeSeverityFires when

The warn is deliberately not an error: an exhausted or freshly pushed sprint is a legitimate transient, and gating on it would make the audit unusable at the moment the state changes. multiple-active-sprints is an error because no single sprint answers active_sprint_id in that state, which every consumer of the field depends on.

The failure a two-file gate could not see

The first gate named two files, which was itself the defect: a gate that selects only the files the author thought of cannot reach a file the change broke. The coordinator measured tests/test_surface_parity.py green 11 of 11 at the base revision and red at this head, so the failure was added rather than pre-existing. It is test_a_single_patched_value_on_one_side_makes_the_comparison_fail[sprint-drift-returned], and it is not the same class as the label literals. The mutation patches the returned side's state_drift for a sprint stored planned whose members have started, and at this head that row carried no state_drift at all, so the mutation raised KeyError: 'state_drift' before any comparison ran. The parity harness was right, and the drift-suppression rule was wrong.

The rule treated a member-derived in-progress as compatible with any non-terminal stored status, including planned. That collapses a real contradiction: planned says the work has not begun and a started member says it has. The rule is narrowed to open and active — the two statuses a started member genuinely does not contradict — and the contract is pinned by test_planned_sprint_with_started_members_reports_drift. Measured across the three stored statuses with one started member: planned → drift {stored: planned, derived: in-progress}; open and active → no drift.

One name, two sets

The top-level open-sprint bucket was first named open_sprints, the name the payload already uses for a different set: schedule.open_sprints is the schedule-horizon list of sprints holding open work, ordered and bounded by the configured window, while the top-level bucket is the sprints whose stored status is open. The two are not the same set, and one name made them indistinguishable to a reader. The top-level key is renamed open_sprint_ids, beside active_sprint_id; the horizon key and its consumers are untouched. Measured: no consumer outside this change reads the top-level key, and the three tests that assert open_sprints read the nested schedule object.

Recorded rather than smoothed over

  • The sibling test that carried the superseded label is updated. tests/test_roadmap_sprint_derivation.py asserted the member-derived sprint label as active; the two literals now read in-progress, which is what the member-derived label became. The adjacent assertion that a sprint stored active with a started member carries no state_drift is unchanged. The file was outside this node's write scope when the failure was measured and was added to the scope by the coordinator before the edit.
  • The push op is placed on the sprint resource being pushed, not literally on the project resource. The plan text names the op on the project resource, but project.json is forbidden by PROJECT_DERIVED_FIELDS from carrying active_sprint_id, and sprints are separate resources, so a project-resource op cannot read or write the sprints it must change. The op therefore selects the sprint to push (doc_type="sprint", with the sprint id as the requested op's resource), and the atomicity is what the plan requires regardless of which resource carries the verb. Re-routing the surface to doc_type="project" is a small change in apply_resource_ops and no change to push_sprint.
  • Plan state is untouched by design. The pushed sprint and the plan's own metadata are the coordinator's write; a worker records the outcome and returns it. The stating of the new tests is evidence of the behaviour at the recorded commit, not proof that a later merge keeps it.
