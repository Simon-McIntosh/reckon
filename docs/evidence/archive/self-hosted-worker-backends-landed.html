§2 — The transport gap, and a fence with the wrong blast radius

A backend declared ten keys and none of them carried an endpoint; the single worker Popen passed no environment. So a self-hosted server was reachable only by mutating the orchestrator's own environment — global, unrecorded, and identical for every node in a wave. Naming a wrapper directly did not help either: dialect selection matches the command's basename, so an unknown command was refused before launch.

Landed as an optional environment map on the backend class, resolved through the layered config with per-leaf provenance and merged over the inherited environment at the spawn boundary. Commit 072112a, 7 files, 328 insertions, 5 tests. Both generated schema artifacts regenerated byte-identically (_flight_schema.py sha256 b7e8781a…, flight.schema.json sha256 61edc890…); full suite 2,460 passed.

One assertion in that node's own contract was carried deliberately and is the reason no credential can leak: the persisted agent configuration must remain exactly backend, launch, model, effort and sandbox. The run ledger is committed to git, so an environment value reaching the run record would put a secret in history.

The correction, and why the specification caused it

The section's done-when asked for an unset reference to raise a typed error naming the variable. That is correct for a backend a call routes to and wrong for every other caller. Implemented as eager whole-config expansion, one unresolved reference in one defined-and-defaulted-by-nothing backend became a hard failure for every dispatch in the project. A concurrent session's work stopped on it within a minute of the config landing, and reported it.

The precedent to follow already existed: a backend whose command is absent reports command_found: false as an availability finding and breaks nothing. Expansion now happens at selection; an unresolved reference stays visible through resolution in that same availability shape, and the typed error naming both the variable and the backends.<name>.environment.<key> path survives at launch-plan construction for the backend that actually carries it. Commit 5dbf304, 3 files, 3 tests added; full suite 2,465 passed.

The class of defect is worth naming: a fence with the wrong blast radius. The check was not wrong and it did not fail to fire — it fired correctly, on callers who had nothing to do with what it was checking. It passed its own author's testing because that testing ran in a shell which happened to have the variable exported, which is why a single-session test cannot see this class at all.

§3 — The local endpoint routes, by a better mechanism than specified

The section specified an environment map naming the endpoint. What landed instead names the local wrapper as the backend's command, registered as an alias of the agent CLI's dialect because the wrapper execs that CLI with its arguments unchanged. The wrapper resolves the endpoint and its token itself, so no secret passes through Reckon at all — strictly better against a constraint that the work must run without provider API keys. Commits 479d286, 6ddb052.

Routing is inert as the ladder requires, verified rather than asserted: a dry-run dispatch resolves the incumbent backend by default and the local backend only under an explicit override.

The end-to-end measure, delivered by an unrelated dispatch

A worker ran on the served model through this backend, took a worktree, executed commands and returned a well-formed manifest with structured evidence. The qualitatively important part is not that it succeeded: it contradicted its own dispatch's premise. The node assumed one accelerator; the model reported a different one and that inference routed to a remote host, and filed the discrepancy as a follow-on rather than agreeing with the prompt. A worker that reports its dispatch is wrong is doing the thing a fence depends on.

That run's landing comment went to a plan at implementation 1.0, because that is where it was dispatched. This is itself the recorded finding: evidence dispatched against a completed plan lands in a container the roadmap excludes from every open path, which is the mechanism by which work becomes invisible while leaving a paper trail that looks like tracking.

Machine-specific routing does not belong in a committed layer

The backend was first written into the project layer, which is committed. The executable it names exists only on one cluster, so a site-specific path was travelling to every checkout of a repository whose first principle is that it hardcodes nothing site-specific. Moved to the host layer, which is also what “global config” means. Effort was pinned in the same move: unpinned, a backend inherits whichever reasoning preference the interactive CLI holds, and the first run's agent record accordingly reads none — a value the ledger cannot attribute to anything.

§7 — The gate was an assertion, not a measurement

An independent audit of what a shadow pair can establish returned the harder result. Tracing the promotion path, completion accepts the caller's gate string and passes it to the ledger, which validates that it is one of three words and stores it: no manifest is read, no named check is re-run. Across 1,534 records over 12 mounts and 4 populated ledgers, 0 carry a gate command, exit code, log path or evidence digest. A reader cannot distinguish an audited pass from a rubber-stamped one.

The audit ranked eleven weaknesses by direction of bias: nine inflate a candidate's apparent pass rate and two deflate it. Inflation is the dangerous direction, because the errors argue for adopting a model that has not earned it. Three are structural rather than statistical — the named check is not identifiable, so nothing prevents a pair being scored on a different check from its primary's; control is recorded but not enforced, because capability derivation branches on lineage kind and never reads lineage configuration, so the corpus's one confounded shadow pools with its one controlled one; and node choice is discretionary, with no sampling frame recorded, which is how both pre-existing shadows came to target a single primary.

It also falsified this plan's own evidence floor. Ten pairs is a feasibility threshold, not an inferential one: at the measured 93.305% live base rate, detecting a ten-percentage-point difference at 80% power requires 161 pairs, so ten is 6.21% of the powered depth. Ten controlled pairs can show a candidate is not catastrophically broken. They cannot show it is as good as the incumbent, and no recommendation built on them may claim otherwise.

§4 — Shadow qualification

The sampling frame was computed rather than chosen, in direct answer to the audit's discretionary-selection finding: across four populated ledgers, 137 eligible primaries over 25 distinct plans — passed implement runs with a complete stored node definition, a recorded base revision, no required decisions, and no shadow lineage. Restricted to those whose done-when names a runnable check, the local ledger holds 19 candidates over 5 distinct plans spanning 4.2 to 42 recorded worker minutes.

Control quality was verified on a dry run before any pair was launched: only backend and model are substituted, while effort, launch, sandbox and time budget are all inherited from the primary. That is the property the corpus's one discarded pair lacked, and it is what makes a difference in outcome attributable to the model rather than to its budget.

The shape of the two failures matters more than the count, because neither is an engineering failure. One left its worktree and wrote into the shared checkout; the other did its work correctly, in scope, with a green suite, and never wrote the manifest that constitutes delivery. Both are fence failures. Nothing in the six pairs suggests the model cannot do the work — the evidence says it can, and twice did it better than the model it replaced. What it does not yet do reliably is respect the two contracts that make an unattended worker safe: stay inside your scope, and deliver to the named path.

A note on the closed failure-class set introduced earlier in this plan: it has no row for did the work, did not deliver it. The undelivered pair is recorded as work-rejected because that is the least wrong of six, with the distinction carried in its outcome text. A seventh class for a delivery failure is a real gap, found by using the vocabulary rather than by designing it.

The one failure is a write-fence violation, and the harness does not prevent it

The failed pair never worked in its assigned worktree at all. Its stream carries 61 tool inputs referencing the shared main checkout and zero referencing its worktree; its single edit targeted the main checkout's copy of a file two other sessions were holding; its worktree ended empty. Reading the current tree rather than its own base revision it concluded the node's work was already done — true of the current tree, irrelevant to its node — and replaced an accurate sentence with a false one. The claim was checkable and wrong: the CLI projection carries 17 fields against the live view's 24.

A second pair did the same thing and corrected itself: it wrote a stray file into the shared checkout, noticed, and removed it with rm before finishing. It passed its gate. Across five pairs the candidate left its worktree twice and recovered once.

Nothing in the harness prevented either. Both dialects disable their own confinement: the launch line carries a permission bypass, the directory flag adds to the allowed set rather than restricting to it, and the observed permission mode reads as a full bypass. So sandbox: worktree-full reads like enforcement and is advisory — the only thing keeping any worker inside its worktree, on any backend, is the worker choosing to obey its prompt. The incumbent has chosen to across more than 1,300 committed runs, which is why the gap was never visible. It is a property of the harness that a less obedient worker exposed, not a property of one model.

Three of these results were destroyed while promotion reported success

Six pairs were promoted with crew complete, every call returning ok: true. Three of the six do not exist in the run ledger — absent from the working tree, from every commit, and from every worktree copy, confirmed by run id against data.runs, which is the only run key the file has. The three that persisted include both a pass and a fail, so the loss does not track the verdict; the three that vanished were the three promoted earliest and in quickest succession. The surviving evidence is the run directories, manifests, streams and the diffs audited above, which is why this record rather than the ledger carries the result.

Two supports offered for this earlier do not hold, and are withdrawn here. Consumed version numbers prove nothing: the counter increments on any write to the file — holds, observes and pre-flights included — so versions advancing faster than records is expected. And the claim that two promotions reported the same version was not established: only one of the two figures was ever actually read, the other having been truncated in the output. What survives is the run-id lookup, which is sufficient on its own and is the whole of the evidence.

A concurrent-promotion lost update remains the most plausible mechanism, several sessions having written this ledger throughout, but that is a hypothesis and not a finding. Confirming it needs a reproduction this plan does not own.

A verification trap worth knowing before anyone re-checks this: a presence check by node name returns a false PRESENT for every lost row. Shadowing re-runs a committed node, so the primary bearing that same node name is still in the ledger by construction. Grepping the name finds the primary and reports the pair as recorded. Two independent attempts to disconfirm the loss failed this way before a lookup by run id settled it. The trap is worst exactly where it is most likely to be used, because re-running committed nodes is what shadow qualification is. Check by run id, and treat lineage.kind rather than a name prefix as the shadow predicate.

The consequence for this plan is a prerequisite, not a caveat. The six-pair result above rests on diffs audited directly in the run directories, so it survives; but a qualification ladder that needs ten controlled pairs to open a pilot, and 161 for a powered claim, cannot be accumulated on a store that silently drops rows while reporting success. Nothing downstream can detect the loss, so every calibration read afterwards inherits it. Fixing the ledger write is therefore upstream of collecting any further pairs.

§5 — Verdict and adoption recommendation

Adopt for read-only roles now. Do not give it repository write access until the sandbox tier is enforced. The blocking issue is not capability.

On capability the candidate is credible: it closes an agent loop, holds a tool conversation, and on four of five controlled pairs produced work an audit accepts — twice producing a better diff than the model it was compared against, once by keeping a test case the incumbent dropped and once by writing half the lines for the same outcome. It also showed the judgement a fence depends on, declining to edit historical documents that merely mentioned the module it was retiring. It is roughly 2.3× slower in worker minutes on the one pair where both were measured.

On safety it is not yet trustworthy with a shared checkout. It left its worktree on two of five pairs. Once it recovered on its own; once it did not, and what it left behind was a false statement in a file two other sessions were editing, which blocked a merge and cost a peer session a diagnosis. In a wider fleet that is peer work corrupted rather than one wrong sentence.

The remedy is not to distrust the model, it is to make the fence real. Reckon declares a sandbox tier per backend and then launches every worker with its harness confinement disabled, so the tier documents an intention rather than enforcing a boundary. Fixing that helps every backend and is the prerequisite for unattended execution generally — it is also, on the evidence here, the mechanism behind more than one incident where a session found work it did not author in its own checkout.

  1. Enforce the tier before any local-model write role: stop passing a blanket bypass, restrict the writable set to the worktree plus the run directory, and assert the restriction in a test that a worker attempting an out-of-scope write is refused rather than trusted.
  2. Route the local backend to read-only roles in the meantime — investigation, review, reporting — where its capability is already demonstrated and a stray write cannot reach a shared file. It has one clean end-to-end investigate run on record already.
  3. Fix the ledger write before collecting another pair. Half the promotions in this benchmark reported success and left no row. Any further accumulation toward the ten-pair pilot threshold or the 161-pair powered depth is measured on a store that loses rows undetectably, so this is a prerequisite for the ladder rather than a parallel concern. Until it is fixed, pair evidence lives in the run directories and in records like this one.
  4. Run verification on a scheduler compute node, not on the shared interactive login host. This is a correction of a claim made earlier in this session and it reverses the remedy. Concurrent local workers were blamed for a 48-core host at load 136 and that attribution was wrong: measured by process, one unrelated user's eight MATLAB instances plus a control binary account for roughly 147% CPU, while all 63 of this session's agent processes together account for 30.1%, mostly idle-waiting. Fleet size was a rounding error beside foreign load, and throttling it buys nothing. The real defect is that every suite run here ran on a shared login server, against standing guidance that heavy suites belong on compute nodes — and a gate measured against contention no participant controls is not a measurement, which is exactly how two independent nodes produced unfalsifiable browser-tail failures.

The honest summary of the opportunity: an unmetered local endpoint whose model does competitive work is a real capability change, and the two things standing between this one and unattended use are both in Reckon rather than in the model — an unenforced fence and an unreliable ledger write. Both are fixable, and neither was visible before a worker that does not automatically obey was pointed at them.
