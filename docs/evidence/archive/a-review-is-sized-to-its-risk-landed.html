§2 — A review tier derived from what the node changed

A finished run now resolves to one of three review tiers from what it actually changed. The rule lives in a new module, reckon/review_tiers.py, and reads the SPA-aware classifier reckon.path_classes.path_class — imported, not copied — so a .jsx file under docs/ui/ counts as runtime source while a plan, figure, test or data file does not. Tiers: full when the run changes runtime source or its plan or section declares capability risk elevated/critical; light when it changes runtime source by fewer than the configured changed-line ceiling at spec level exact or guided with no elevated risk; none when it changes no runtime source.

The light tier's ceiling and budget ride a new review.tiers flight key. It is declared as a LinkML slot and class in reckon/schema/flight.yaml, and the generated artefacts reckon/_flight_schema.py and docs/_shared/flight.schema.json were regenerated from it, so tests/test_flight.py's two parity cases hold. The shipped defaults layer carries the values — 50 changed lines, a ten-minute light budget — so a host or project layer retunes the tiers without a code change, and flight.review_tier_thresholds() reads them from the resolved config.

  • tests/test_flight.py 87 passing, its schema-parity cases executed against the LinkML generators rather than skipped.
  • Negative control executed and logged: classifying paths with reckon.path_classes.file_class instead of path_class makes the docs/ui .jsx fixture resolve none instead of full (runs/…-review-tier-resolver/negative_control.log).

Promotion reads the tier in place of the role check

Promotion now resolves each run's tier before it reads the review gate, so the refusal and the ledger row agree about which review the run owes. The four inputs are read from the run itself at the promoted head — its changed paths and their added-plus-deleted line count, the specification level its node declares, and the capability risk its plan or section declares — and the light ceiling comes from the resolved review.tiers flight key rather than a literal in the module. The gate reads that tier in place of the role check: a none-tier run promotes with no stored review and records the tier on its row as the reason none exists, a light- or full-tier run is refused until a review of the promoted head is stored, and a review run stays exempt. A run whose own declarations measure no scope at all is granted the fuller run — silence about what changed is not evidence that what changed was safe — so the resolver never reads an empty path list as a run that touched no runtime source.

  • Base and head arms, each header naming its revision, tree and imported module: at the base revision fb747528 (committed tree, extracted to a scratch tree) the thirteen pre-existing review and promotion files are 157 passed, exit 0; at the changed revision the same set plus the new file is 153 passed, 10 failed, exit 1 (runs/…-promotion-reads-the-review-tier/gate-base.log, gate-head.log).

accept_clean_review in reckon/crew/recovery.py promotes a run when all of these hold:

  • its stored review totals at least 90 of 100 and carries no finding;

§5 — the reflex reviews a settled head, and re-reviews only what changed

Two nodes landed §5.

  • review-carries-forward (r-20261002T183953299469; commits cc17465ef, 8b9b68003 and 31798fcde; merged at 2f7df7952; reviews 87 and 85). A stored review is carried forward over a head move that changes no runtime source. The carried record is re-stored at the new head with a carried_forward mark, so the requirement is recorded as satisfied, not left absent. A runtime-source move earns a light re-review scoped to the new commits, and a queued review whose head a resume moved is withdrawn. Its fragment is docs/evidence/fragments/a-review-is-sized-to-its-risk/review-carries-forward.html.
  • a-running-review-finishes-across-a-resume (r-20261002T214407238376; commits cda91f6a0 and 135f7b3f6; merged at ceecfaae2; review 95). withdraw_superseded_review withdraws only an attempt whose worker never launched, as read from the review run's own launch record. A launched review runs to its verdict, which reaches the new head through the carry-forward rule, or earns a light re-review over runtime source.
