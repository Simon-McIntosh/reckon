Follower re-arm continuation

Run r-20260925T101452768368-follower-rearm-continues-the-stream made a follower's place in its project's watch stream durable, so a re-arm continues the stream it left rather than replaying a baseline and skipping the margin written while nothing was attached. The work ships in b7b16d5c (the durable checkpoint), 8183a9fd (the place written before the first read) and ec7b35d9 (the rendered rows replayed across a re-arm); the plan section is §4.

reckon/crew/follow_checkpoint.py writes one record per project and session into the follower directory: the stream path, the stream's device and inode, the byte offset after the last delivered line, and the state last reported per run. The write is atomic (a sibling temporary file, fsync, os.replace), so a reader sees the previous record whole or the new one whole. _follow_resume_plan in reckon/cli.py chooses the start mode: baseline for a first arming, continue to seek to the recorded offset and deliver only lines written since (the stream's own observed_at and to_state are carried, not re-derived), and restart when the stream was replaced or truncated — re-read from its start, filtered to runs whose state differs from the checkpoint's.

The place is written before the first read rather than after the first line, because a first arming derives its baseline rows from the live fleet and not from the stream: with a producer that has claimed but not yet written, the arming reads no line at all, so a place written only on the line pass would leave nothing behind and the next arming would replay the baseline. The observed case was a follower for session s23-coord whose checkpoint file was absent a minute after its baseline.

The pane keeps its history across a re-arm. The follower also keeps, per session, the rows an arming rendered — each row's text with its original timestamp — capped at the most recent 100 rows or 4 hours, whichever is smaller, both read from flight config. A re-arming follower re-emits that log before the gap lines as one dim burst: a header line naming the span, the rows exactly as they were first rendered with their original timestamps, then one separator line naming the re-arm. The burst is one write, so a line-batching consumer receives it as one notification. The replayed rows are the log's own, never a re-derived baseline, so no run is re-announced in a state it did not hold at that time; a reload onto new code instead prints one ── ticker format updated ── line and re-emits nothing. The Ticker's remembered states are seeded from the checkpoint and the replayed history, so a re-armed pane's next row for a run chains from the state the previous arming showed.
