Follower re-arm continuation

Run r-20260925T101452768368-follower-rearm-continues-the-stream made a follower's place in its project's watch stream durable, so a re-arm continues the stream it left rather than replaying a baseline and skipping the margin written while nothing was attached. The change and this anchor ship in one commit; the plan section is §4.

reckon/crew/follow_checkpoint.py writes one record per project and session into the follower directory: the stream path, the stream's device and inode, the byte offset after the last delivered line, and the state last reported per run. The write is atomic (a sibling temporary file, fsync, os.replace), so a reader sees the previous record whole or the new one whole. _follow_resume_plan in reckon/cli.py chooses the start mode: baseline for a first arming, continue to seek to the recorded offset and deliver only lines written since (the stream's own observed_at and to_state are carried, not re-derived), and restart when the stream was replaced or truncated — re-read from its start, filtered to runs whose state differs from the checkpoint's.

The place is written before the first read rather than after the first line, because a first arming derives its baseline rows from the live fleet and not from the stream: with a producer that has claimed but not yet written, the arming reads no line at all, so a place written only on the line pass would leave nothing behind and the next arming would replay the baseline. The observed case was a follower for session s23-coord whose checkpoint file was absent a minute after its baseline.

The seat record now carries host (socket.gethostname()), and the three judgements split on it: a record naming another host is never erased here and is live while its events stream moved within its stall window; a record naming this host is judged by the local process table as before; a record naming no host is never erased by pid alone and lives off its stream. Delivery (producer_live) judges a seat it cannot attribute by stream freshness; admission (watcher_live, project_watch_visibility) stays conservative, so a dispatch is still refused off an erased seat. ensure_watcher_service now settles lingering before starting a unit and routes service.LingerUnavailableError to the session-owned process producer rather than raising on a compute node with no user session bus.
