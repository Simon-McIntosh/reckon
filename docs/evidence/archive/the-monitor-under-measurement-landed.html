The Monitor Under Measurement

The four measurements the sweep-ownership recommendation rests on, taken together over one seven-day window in a single file: docs/research/data/monitor-sweep-ownership.json.

Window 2026-09-15T20:53Z to 2026-09-22T21:09Z; census host 98dci4-srv-1006.iter.org. The counts below are read from that file; every figure states the population it is a count over.

Note on shelf life. The live-pointer population is read from ~/.config/reckon/crew/live, which the fleet rewrites continuously. An earlier reading an hour before the one recorded here saw 5 unattended sessions over 8 pointers; this one sees 3 over 3. The file carries its own generation timestamp and the orphan figures move.

§7a — The re-arm gap

A crew follow Monitor is a Monitor tool_use whose input.command runs crew follow. The host writes its expiry as [Monitor expired after Nm with K events delivered] inside a Monitor event: "DESC" summary, delivered once with a <task-id>; duplicate records sharing a task id are one notice. A notice counts only where DESC names a crew follow monitor. The gap is the notice's delivery time to the next crew follow Monitor call in the same transcript.

Two things the distribution says. The median re-arm is twelve seconds, so the gap is not usually an operator problem. The ninety-ninth percentile is five hours, and the maximum is nearly thirteen; the tail is where a follower is left off across a working day, which is the case the grace period exists to classify.

All seven non-.json entries are backups of the form <run-id>.json.bak-before-scope-grant and similar, written beside a live pointer rather than replacing it; a reader that lists the directory by extension is correct, and one that globs it is not.

The owning coordinator's transcript is resolved by the crew follow arm that names the session, falling back to the newest transcript naming the session at all. The fallback is an upper bound: another session quoting the name counts, so the cross-check against pointer age is the stronger signal. All three unattended sessions resolve only by the fallback, and each resolves to a transcript being written during the census, which is the fallback reporting on the census's own session rather than on the unattended one. Every one of the three has an oldest live pointer between 23.7 and 119.8 hours old, and every pointer process is gone, so the unattended reading rests on the pointer age and on the pointer's process being gone.

Neither source records the sweeping session. The log carries checked, dry_run, project, resumed, reviews, skipped and swept_at; the status file adds swept_by_pid and writers. That is a key inventory, not an inference: 925 of 9812 log lines carry the reviews key and 8887 do not, and the two shapes carry no session field in either case.

A resume entry does carry a session, and it is the resumed run's own engine session, resolved from that run's stream (34 of 37) or its live pointer (3 of 37). It is not the sweeper.

For a review dispatch, the file follows the plan's direction and reads the review run's own record. That record holds the reviewing worker's own engine session, and the reviewed run's committed row holds the reviewed worker's own engine session; both are engine sessions of dispatched workers, so they differ by construction and comparing them attributes nothing. The count of cross-session actions is therefore reported as unavailable rather than inferred, and all 224 review action rows are marked unattributable. The launching session is recorded in exactly one place: a run's live pointer, under the session key, removed when the run is promoted.

A follower registration records no host field at all: its keys are delivery, parent_pid, parent_start_time, pid, pid_start_time, project, scope, session and started_at. So the second row is a property of the record's shape rather than a finding about the fleet. The host a follower is on is reachable only through the pointer it serves, which carries launcher_host; on that evidence every pointer read at this census named the census host, and none was unknown.

This matters for the recommendation it informs: a rule that treats a session whose pointers name another login node as unknown rather than orphaned cannot be exercised against anything in this population, because the population holds no host-mismatched record. That the rule is untested here is the point of reporting the denominator beside it.

§7e — The grace period, and the positive controls

The 99th percentile re-arm gap is 18586.37 s, which is 309.77 minutes. Rounded up to the next five minutes, that gives a grace period of 310 minutes. At the census moment, that grace period classifies 3 of the 11 sessions holding live pointers as orphaned: all three unattended sessions, whose single live pointer is 26.17, 24.09 and 120.13 hours old. None of the three would be classified unknown instead, because every pointer process belonging to them is gone.

The two positive controls hold.

  • The nova-a9 transcript yields 16 expiry-to-re-arm gaps, against the required minimum of 14.
  • The review run r-20260922T161442206389 is not among the cross-session sweep actions, and the file names the record that would have shown it: the run's live pointer, the only carrier of a dispatch's launching session. That pointer is removed when the run is promoted and this run is not live. What remains in its run directory is stream.jsonl, holding the reviewing worker's own engine session d00bdddf-64ed-4391-9bd0-bf2d956accde, plus stderr.log and prompt.txt, and the prompt names no session. What the sweep log records instead is 52 refusals in recovery/nova.jsonl between 2026-09-22T16:16:51Z and 17:11:47Z, every one dispatched false with the reason a review is already in flight as a live run, paired with the run it would have reviewed. The run is absent from run_store.db and from all 9 project ledgers

What these figures do not support

  • No cross-session count. The section asks for the number of sweeps acting on another session's run. The logs do not carry the sweeping session and the run store does not carry a dispatch's launching session, so the count is unavailable from the recorded data. Reporting the 224 review rows as cross-session would be an artefact of comparing two worker engine sessions that differ by construction.
  • The orphan count is a live reading. It is a count over a directory the fleet rewrites. An earlier pass in the same hour read 5 unattended sessions over 8 pointers against 3 over 3 here.
  • The host rule is untested. No pointer at any read named a host other than the census host, so the recommendation's cross-node clause is re-read from a single-host population.

One instrument defect was found and repaired while taking the measurement, and it is recorded because it is the kind that reports "nothing" rather than failing: the fallback that resolves a session's transcript globbed <root>*.jsonl against roots that already end in a separator, a pattern that matches no file at all. It ran without error and returned no result for every unattended session until the pattern was corrected.

Verification

The four measurements are computed by three scripts against the live crew config home and the Claude Code project directories, and the data file records every source path it read. The build asserts the nova-a9 control and exits non-zero when it fails. The control-run paragraph rests on counts read directly from recovery/nova.jsonl, the run directory listing, run_store.db and the nine project ledgers.
