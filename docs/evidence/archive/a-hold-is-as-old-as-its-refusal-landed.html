A hold is as old as its refusal — landed evidence

Three sections, three measures, all passing. The load-bearing one is §2: a refusal's age is now derived from the event that was the refusal, so the act of investigating a held lane cannot renew the hold on it. The other two make the fence operable — a declared lever an operator can reach at the moment of an incident, and a refusal that says what would clear it.

Record scope

The plan carried one defect and two absences. The defect was a renewal loop: the ageing rule measured from the live pointer's observed_at, and observe rewrites that stamp whenever it re-reads a run's stream — so re-reading a refused run re-stamped an old refusal as a fresh one, and a coordinator investigating why its lane was held extended the hold by looking. The absences were a configuration key that existed in code and not in the schema, and a refusal message that stated the position without stating the cure.

All three are closed. One of them, §3, turned out to be closed already; that is recorded below as its own finding rather than folded silently into a landing.

§2 — The age is taken from the refusal, not from the last read

Commits 8d6e4fc and c684a42. Gate uv run pytest tests/test_budget.py -q — 62 passed in 5.20 s against a 61-passed pre-feature gate on the same file, 218 insertions across the module and its tests.

The implementation reads the newest rejected rate_limit_event in the run's stream together with its closest immutable surrounding timestamp, and publishes which source answered as age_source in the budget state. The mutable pointer stamp is not discarded — it survives for the one job it is still correct for, choosing the freshest of several readings — but no age is derived from it. Where no rejected event can be timed, the state says created_at-lower-bound in words, so an unparseable stream reads as a bound rather than as a fresh refusal. That fallback is what the locked decision required to be stated explicitly rather than left implicit.

The measure that had to be one case, not two. The defect is invisible to a test that decides once, which is precisely why the ageing rule shipped carrying it. So the receipt is an observe-then-decide sequence: one hundred repeated observations leave both the derived timestamp and the hold verdict unchanged; a hold whose refusal is older than the shelf life reads expired immediately after such an observe rather than being renewed by it; a genuinely fresh refusal still holds even when its run was created three hours earlier, which is the case that would have failed under a created_at-only rule; and no hold decision depends on age_source itself beyond the existing shelf-life comparison.

Every assertion goes through budget.preflight, which builds its state from live pointers and invokes the same decide path crew dispatch uses. That was a stated requirement of the section and not an implementation detail: a measure taken against a helper cannot tell whether the entry point a coordinator actually calls has the behaviour.

A second finding, delivered as a separate commit. The node's baseline gate came back 11 failed, 50 passed before it changed anything — fallout from the specification-level requirement that landed earlier the same session, whose dispatch fixtures in this file predated it. The worker repaired the fixtures under c684a42, a three-line change touching no production behaviour, and kept it separate from the feature so the feature's own delta stays readable. The post-repair pre-feature gate was 61 passed, which is the number the 62 above is measured against.

§3 — The shelf life was already declared, and nothing said so

Landed under commit 30a4460, found by a currency audit against the tree rather than by a dispatched node. The section's premise — that BudgetConfig does not declare the field, so --set budget.evidence_shelf_life_minutes=1 fails as an extra input — was already false when the section was read.

The key is declared in reckon/schema/flight.yaml with its meaning and not merely its type, which is what the section asked for: the description states that the field bounds how long a refusal naming no reset keeps describing the present, that a value at or below zero disables ageing and restores the indefinite hold, and that it has no effect on a refusal that named a reset, since a stated reset is stronger evidence than an age.

Verified at the entry point an operator holding an incident would actually use, rather than by reading the schema:

reckon crew preflight --project reckon --role implement \
  --set budget.evidence_shelf_life_minutes=1
  → "policy": { "evidence_shelf_life_minutes": 1.0, ... }

This was the fourth section in this sprint found implemented under a commit that wrote no comment against it. The pattern is recorded in the observability plan's evidence, where it belongs; noted here because it is the reason this section closed without a node.

§4 — The refusal names the instrument that would inform it

Commit 9fc4d5d. Gate uv run --no-sync pytest tests/test_crew_refusal_visibility.py -q — 8 passed in 0.68 s, 149 insertions across two paths.

Three facts were already known at the moment a hold was emitted and none reached the reader. All three now do. The refusal names the backend it governs, so it implies nothing about a sibling backend on a different account — a distinction that has misled a reader here before, when one account's reset was taken as evidence about another's. Where ageing is what holds the wave, it states the evidence age against the bound in force and the wall-clock time at which the bound will pass, measured in the test as 20.0 minutes against a 60-minute bound, so an operator can wait deliberately instead of retrying blindly. And it names a served turn on that same backend as the observation that would refresh the record, because the cure is per-lane exactly as the hold is.

The negative matters as much: no refusal message suggests re-reading the refused run. That was the natural theory a coordinator supplied for itself, and before §2 it was actively harmful — observing the refused run looked like gathering evidence and was in fact renewing the hold. §2 removed the harm; this section removes the mistake. A hold carrying a stated reset names that time instead of an age, since a reset is the stronger evidence.

Both new assertions consume the JSON detail emitted by a CliRunner invocation of crew dispatch. Neither calls the message helper. This was stated in the measure for the same reason as in §2, and it is the discipline that has failed most often in this repository: a capability landing in the module that holds the mechanism while the call site a reader reaches stays unchanged.

What this record does not claim

The plan's own framing is worth preserving: none of this makes a hold correct, only honest about its age and its cure. A refusal that named no reset time is still a weaker piece of evidence than one that did, and the shelf life is still a policy number rather than a measurement. What changed is that the number is now reachable, the age is now immutable under reading, and the refusal now says which of the two is holding the wave.

The burn-rate fence that would catch a lane spending its window too fast is not part of this plan — it landed the same day under dispatch-cost-per-durable-node §6, deliberately report-only, and the two fences answer different questions: this one is about whether a stored refusal still describes the present, that one about whether a clear lane is on course to stop being one.
