A plan is reviewed before it is built — landed evidence

The plan-review record: one durable file per reviewed version, joined to the plan content it read by a fingerprint that drops the metadata scalars the store rewrites on every edit.

§2 — The plan-review record and its store

Node: plan-review-record-and-store.

What landed. One module, reckon/crew/plan_review.py, owning the plan-review record: plan_review_path, store_plan_review, read_plan_review, list_plan_reviews, plan_fingerprint, record_response and declined_recurrence. The record lives at reviews/<project>/plan-<slug>.v<N>.json beside the code reviews, with a .at-<blob8> sibling the second review of one version lands on, so a re-review accumulates beside its predecessor instead of over it.

The fingerprint join. The plan store and the MCP write path bump version on every write, including the impl-only edit that must not produce a review, so a record keyed to the integer would be orphaned at the first impl bump and no review could clear the later gate. The record is therefore joined to plan content by plan_fingerprint, which digests two components: the parsed state with the exclusion set removed, and the document's authored prose. An authored edit moves the fingerprint and a metadata-only edit does not, so the review-due rule and the dispatch gate agree by construction.

The exclusion set is two sets. Dropping the ten server-managed metadata scalars (version, modified, impl, status, roi, effort_hours, owner, sprint, tags, archived) proved insufficient, and the review of this node found it: the parser derives further state from those scalars, so writing the named effort field to a plan that carried only the legacy effort letter moved the derived calibration flag and the diagnostics list, changing the fingerprint on a metadata-only write and orphaning a review on exactly the plans that predate the named field. A sweep of every document under docs/ named the two keys and no others; both are now excluded as PLAN_DERIVED_SCALARS, named beside the scalar set with the reason for each.

The prose is digested separately, because the state has none. The parsed state carries no section prose at all — read_state reads the metas, the typed section records and the reckon-owned blocks, and the paragraphs a reader sees under each heading are never part of it. A fingerprint over state alone therefore did not move when a plan's prose was rewritten, leaving the one edit a review exists to catch invisible. The digest now also covers the body text outside every data-reckon block (whitespace-normalised), with the head skipped so a metadata write cannot reach it through the title.

Method and the six named cases

tests/test_plan_review_store.py runs six cases, each named for the property it holds:

  • test_two_versions_of_one_plan_are_two_records — reviews of versions 1 and 2 land at plan-demo.v1.json and plan-demo.v2.json, and a fingerprint filter selects the right one.
  • test_metadata_only_edit_keeps_the_fingerprint — every excluded scalar moves while no content key does, and the two fingerprints are equal; a content edit moves the fingerprint.
  • test_re_reviewing_one_version_keeps_both_files — a second review of one version lands at plan-demo.v1.at-bbbbbbbb.json and the first file survives; re-storing identical content is idempotent on the plain path.
  • test_a_response_without_a_reason_is_refused — a reasonless decline raises before any write, the stored record is untouched, and an act or a decline-with-reason closes the finding.
  • test_recurrence_counts_distinct_plans — one type declined in three distinct plans surfaces (plan_count 3, surfaced true) and in two does not; a plan carrying two declines of one type still counts once.
  • test_real_plan_metadata_edits_keep_the_fingerprint_while_prose_moves_it — the boundary against the real corpus, not a fixture: each excluded scalar is written in turn to a legacy plan (reckon-mcp-plan.html, which carries the legacy effort letter and the derived uncalibrated flag) and to a current plan (a-plan-is-reviewed-before-it-is-built.html), the edit is asserted to have landed in the parsed state, and the fingerprint is asserted unchanged; an authored paragraph inside a section then moves it on both plans.

§2 — The rubric prompts and their loaders

Node: plan-review-rubric-prompts.

What landed. Two rubric prompts held as diffable files rather than strings in a module, each read from disk at call time. reckon/crew/prompts/plan_review.md reads a plan's authored content for wiring, done_when (measurable, with a declared negative control), single_goal, evidence_paths, anchors_resolve and naming, and adds a reasoning check in three parts: the stated root cause matches the cited evidence, each section's mechanism produces its done-when, and the mechanism runs on the real code path with its caller named. The anchors_resolve item resolves an href that names no file extension as <path>.html, as the surface does (docs/ui/plan.jsx fetches /<project>/<href>.html), before it reports a finding — the house convention, per the pilot's own declined finding. reckon/crew/prompts/plan_design_review.md carries four items: reuse_search, deep_module, thin_wrapper and duplicate_owner, the last requiring that a duplicate finding name the owning file. Every finding in either prompt carries a WOULD_CHANGE_THE_PLAN verdict and a one-line REASON, so a review is scored on whether it would have changed the plan rather than on finding count.

Loaders and mirror. load_plan_review_prompt and load_plan_design_review_prompt live beside load_review_prompt in reckon/crew/review.py, with the item constants PLAN_REVIEW_ITEMS and PLAN_DESIGN_REVIEW_ITEMS. Each prompt carries its own RUBRIC_ITEMS: line, and tests/test_plan_review_prompt.py holds the two together in both directions for both prompts: every item the constant enumerates is named in the prompt, and the prompt's own list equals the constant.
