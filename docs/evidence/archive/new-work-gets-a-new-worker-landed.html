New Work Gets A New Worker — landed evidence

The dispatch-time session decision is keyed to the task (project, plan, node id), or to the reviewed run id for a review. A new node sent to a member that last ran a different node composes no resume.

§2 — The dispatch-time decision compares task identity

Node: session-resumes-only-its-own-task. The decision that composes resume <session> into a launched argv read the resolving member's session map, so a member that had last run one node offered that node's conversation to the next node dispatched to it.

The five cases asserted on the composed argv

Every case drives the real reckon.crew.dispatch.dispatch path with session_reuse: true on the backend and reads the argv back, never a helper's return value.

CaseWhat it asserts
1 A new node sent to a member whose recorded session belongs to a different node composes no resume.
2 A second dispatch of the same project, plan and node id composes the prior run's recorded session.
3 A re-review — a review node whose id names the same reviewed run — composes the prior review run's session; a review of a different run starts fresh.
4 A prior run whose stream ended in Prompt is too long, blocking_limit, or a compaction with no compact_boundary is not composed; a completed boundary still is.
5 crew resume of a run still composes that run's own session.

Where the prior session is read from

Committed ledger rows under docs/state/<project>/crew.json — which store node as an id string and carry no stream path — and the live pointers under <RECKON_HOME>/crew/live/<run_id>.json, which store the node block and the stream path. The roster's sessions map is used by neither: it is where a captured session is written back, not an authority for which task may continue.

§5 — The guidance teaches the same rule, keyed by task identity

The defect. Both continuity passages routed a dispatch by member, not by task. skills/reckon-ship/SKILL.md §Continuity sent same-plan follow-up work to "the roster member whose long-lived session remembers the node"; skills/reckon-ship/references/sprint-orchestration.md §13 routed a followup on landed work to "the same worker, via its roster member's long-lived session" and told the coordinator to dispatch every node as a roster member by default so the session would survive on the member's committed crew.json entry. A member's session was keyed by agent configuration, so a new node sent to that member inherited another task's transcript and paid for it on every turn — the same defect §2 repairs in the dispatch path, restated as guidance a coordinator would follow around the fix.

What landed. Both passages now state the same-task rule: a session continues the task it began and nothing else, keyed by (project, plan, node id) for implement, test and investigate runs and by the reviewed run id for a review. Both name the three reuses kept deliberately. Both carry the measured cost as the reason — a rule without its reason is routed around the first time the alternative looks slower. The routing table in §13's reference is rewritten to route by task: the same run's session for a NEEDS-HELP: brief, the same run on a new lane for a redispatch, a new run on the same node for a repair, a new review run for a re-review, and a fresh dispatch for anything else. Codex input spent carrying an earlier task's session — the before figure

Codex's stream publishes one turn.completed usage summed over the whole turn, so it cannot show what a run's opening request re-sent. Its client rollout file can: one token_count per model request, and one task_started/task_complete pair per exec run. A run that resumes an earlier session appends a task to an existing rollout; a fresh run opens one. That boundary is the instrument.

Before figure. Over every codex run under ~/.config/reckon/crew/runs: 3,274 runs across 1,916 sessions; 1,916 fresh (median opening-request input 40,997 tokens) and 1,358 resumed (41%; median 166,421). The input attributable to the inherited transcript, priced above the fresh median, totals 172,082,502 tokens. same_run is zero — every resume is a cross-task resume.

Positive control. r-20260909T124530581873-n-swcr-observe-the-missing-validation resumed the session opened by r-20260909T072310390297-n-pidp-restore-pedestal-density-family; opening request 378,921 tokens (9.2× the fresh median), inherited 337,924. It reads non-zero through the same parser that reports 0 for a fresh run, so the total is measured rather than assumed.

Corroborator. For that control the run's own stream reports turn.completed.usage.input_tokens = 13,970,122 and the rollout's per-request sum over the same task is 13,970,122 — ratio exactly 1.0, two instruments that share no parser.

A false-positive control, kept. The dialect appends resume <session id> to a codex exec argv, but no codex run's recorded argv carries the syntax durably — argv lives only on the ephemeral live pointers — and a pointer's session_resumed flag is not a substitute: r-20260923T034949217912-pcrf-production-route-ladder carries session_resumed: true, no resume token in argv, and a rollout that opened fresh.
