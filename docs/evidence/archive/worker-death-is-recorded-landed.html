Worker Death Is Recorded

A launched worker's wait status is kept on its run: the exit code where the process chose one, and the signal number and name where a signal ended it, so a worker ended by a signal stops reading like a live one.

§5.1 — The launcher keeps the wait status it already holds

Plan §5.1. The reaper was the only place that ever observed a worker's end: it held os.waitstatus_to_exitcode(status) at the moment the child was reaped and threw it away whenever the stream was non-empty, so a worker ended by a signal kept its working phase and carried nothing about its process having gone. That is the whole of this node: the status is now kept.

How the wait endedRecorded on the runWhy
process exited, code Nexit_code: N it chose to end
process signalled, signal S signal: S, signal_name: SIGTERM it ended by nothing it chose, and the two cases want different responses

A signalled process chose nothing, so it records no exit code; a signal number outside the named set is still recorded by number, so an unfamiliar kill is legible rather than dropped. The record lives in the pointer's wait_status and in the same three fields on a run's launch-failure entry.

What was measured

Two cases in tests/test_crew_launch_failure.py, each spawning a stub backend through the real spawn and reaped on a real tick, each reading the run record rather than a log:

  • a stub that writes one turn and then kill -TERM $$ records signal: 15 and signal_name: SIGTERM, with exit_code absent, its phase left working and no launch-failure entry;
  • a stub that writes one turn and then exit 3 records exit_code: 3 with no signal.

Both streams are non-empty, which is the case the launcher was discarding, so the record can only have come from the wait. The existing empty-stream cases are unchanged, and the focused gate runs 7 passed at b0c8ff90.

The declared negative control restores the branch that discards the wait status when the stream is non-empty; the signal case is then observed to fail, and that log is negative-control-discard-wait-status.log in the node's run directory. Gate log: gate-wait-status-focused.log, same directory.

Corrected inside the node

The first cut recorded the wait status for a placed launch too. A scheduler client's wait status is the client's rather than the worker's, and a placed run whose payload log shows a turn ran must gain no record at all — tests/test_crew_placed_liveness.py::test_the_payload_log_decides_that_the_work_ran caught it, failing on a record it was never meant to see. The placement case now returns before any pointer write, and that file and this node's gate are green together (25 passed).

Boundary

A run already in a terminal phase is left untouched: the existing guard that never relabels a finished run is unchanged, so a straggler reap arriving after a promotion adds nothing. Classifying an interrupted run, and the phase that names it, are §5.3 — a different node.
