§3 — A deliverable that exists is not an abandoned run

The invariant held at base; the ordering that guarantees it was unstated and untested. Before any change, classify_pointer returned promotable for a dead pointer carrying a complete manifest and a parsed stored review, and a sweep over manifest case × phase × role × review presence flagged no abandoned row that had delivered. So the plan's defect is a silence, not a live misfire: nothing named the ordering, so nothing stopped the next edit from reordering the arms and losing a third of the deaths to abandonment again. The change locks the property and records the falsifier that would catch a reversion.

The falsifier, applied. The negative control reorders classify_pointer so the process liveness verdict is consulted before the manifest and its review record are read. Under that mutation the delivered-run lock fails on all three phases a death can freeze on — assert 'abandoned' == 'promotable' — which is the condition the plan names. The control's own log leads with the declared string and records 3 failed, 3 passed, 14 deselected; the verbatim transcript is in docs/figures/a-review-dies-where-nobody-is-looking/negative-control.txt.

What the tests assert

  • A dead process behind a complete manifest and a parsed review classifies promotable — never abandoned — across the exit phases a death can freeze on, because the stored phase is the last writer's label and not evidence of what the run left behind.
  • A review-role run's delivery is its own complete manifest, so it is promotable with no stored review of itself.
  • A dead run with a complete manifest and no stored review waits in scoring: the row names the missing review, not the death.
  • A stored review that does not parse is still evidence the run delivered, so the run is scoring rather than abandoned.
  • The dead control: a dead process with no manifest and no review is still abandoned, so the reading the ordering reserves is not disabled.

Read before repair

Per the dispatch contract, the already-correct behaviour was verified and the missing lock added rather than a working guard reimplemented. The one comment added in reckon/crew/recovery.py states the ordering at the abandon arm — why an arm that only ever sees a run with nothing to show can safely carry the abandoned verdict — and changes no byte of behaviour.
