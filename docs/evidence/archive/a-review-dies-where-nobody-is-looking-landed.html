§3 — A deliverable that exists is not an abandoned run

What the tests assert

  • A dead process behind a complete manifest and a parsed review classifies promotable — never abandoned — across the exit phases a death can freeze on, because the stored phase is the last writer's label and not evidence of what the run left behind.
  • A review-role run's delivery is its own complete manifest, so it is promotable with no stored review of itself.
  • A dead run with a complete manifest and no stored review waits in scoring: the row names the missing review, not the death.
  • A stored review that does not parse is still evidence the run delivered, so the run is scoring rather than abandoned.
  • The dead control: a dead process with no manifest and no review is still abandoned, so the reading the ordering reserves is not disabled.

§7 — The context fit gated on the boundary the lane actually refused at

The defect, reproduced from the recordings. The plan records a run that passed the pre-dispatch context fit at an estimate of roughly 285k against a declared usable_input_window of 480000 and was then refused by the endpoint after three records, with no deliverable. Reading every recorded run stream under ~/.config/reckon/crew/runs whose last result is an error carrying the refusal text finds 18 such runs, of which five were served on the flash model this lane carries. Every one of those five announces a context window of 200000 tokens in its own modelUsage block, against the 480000 the configuration declares — the declared figure overstates what the endpoint accepts by more than a factor of two.

What landed. reckon.crew.context_budget.refusal_census reads every run stream and keeps those whose last result is an error carrying the refusal text, taking each run's estimate as the context window its own result announced for the model it was served on, and returning the lowest of them as the effective boundary. A boundary belongs to one lane, so the census is narrowed to the lane's own model — pooling every model returns the minimum across lanes, which is the narrowest neighbour's figure rather than this lane's — and the runs that narrowing excludes are reported alongside rather than dropped. The estimate is deliberately the lowest figure the recording supports rather than a usage count: the rejected request produced no usage record of its own, so the announced window is what bounds it from below, and a run carrying no modelUsage block is reported unmeasured rather than zero, so it cannot move the boundary. reckon.crew.routing._context_fit_verdict then gates on the smaller of the declared window and a declared effective_input_window, and a refusal inside the band between the two names both figures. Either figure may be absent: a lane declaring no window is unbounded and its recorded boundary alone gates it, and a lane with no recorded boundary keeps its declared window.

The routing-surface fixture now initialises a repository, closing the file's failures

The failures the gate above left standing are repaired here. §2 — The experiment neither session could run

Node: review-deaths-by-effort-and-role counted every recorded run on the locally served lane and separated its death rate by role and by effort, which is the separation the two earlier sessions could not make from the runs they happened to hold.

Method. The population is every run directory under the crew run store whose ledger row names the locally served backend (clive). A run's stream is its terminal attempt — the highest-numbered resume-N.jsonl when the run was resumed, otherwise stream.jsonl — because an earlier attempt's stop is not where the run ended. A run is dead when its terminal stream carries no result record and no live pointer reports its process alive; a run whose stream carries a result record is completed, and a stream without one whose pointer reads alive is running and is never counted a death. Liveness is derived from the pointer's own pid and its recorded kernel start tick, not read from a stored process_alive field: most live pointers carry no such field, so a reader that trusted it would call a live run gone and add it to the death count. The record's own success flag is not consulted: a failed turn still wrote a result record, so it still says the turn ended.

What the separation shows

At a constant effort of xhigh, role separates the death rate by more than a factor of four: review at 12.1% (45/373) against investigate at 2.6% (2/76) and test at 5.9% (3/51), all on the same effort. So role discriminates while effort is held fixed, which the earlier session's pooled observation could not separate because every review it held ran at xhigh and every implement at high.

Effort does not separate within review: xhigh at 12.1% (45/373) against high at 8.3% (1/12), and the high cell is twelve runs, so the interval it supports contains the xhigh rate outright. The plan's requirement that no fix be justified by effort is therefore unrefuted and better supported than before: the observed confound is partly broken by the role side, and the effort side has no cell large enough to carry a claim.

Controls

Positive. A run whose own manifest records status: complete is read by the parser as carrying a result record of subtype success, and is reported not dead (reports_dead: false). This is the check that the parser was aimed at something known present, which an absence count alone cannot show.

Negative. The declared mutation — make the census parser ignore result records so every run reads as dead — is applied and the completed fixture is observed to read dead: the unmutated parser reads it completed, the mutated parser reads it dead with totals {'dead': 1}. The red log is negative-control.log in the node's run directory, its first line the declared string verbatim.

What this does not claim. The census classifies by the terminal shape of a stream, which has to bracket what produced it before it can separate effort from role with confidence in the review/high cell: eleven runs is a population that neither confirms nor refutes a difference, so the honest reading is role discriminates, effort undetermined at this sample. The unit is the run's terminal attempt, so a run resumed after a first-attempt death is scored by its last attempt; the census artifact's runs list carries each run's stream name so that choice is auditable. The measure ranges over this node's own change only; verifying the merged result is a separately dispatched node's job.

§4 — The sweep's composition is deterministic, attributable and printed

Node: the-review-lane-follows-the-owning-run made the review lane a property of the run being reviewed rather than of the session sweeping, and made the flight configuration able to withhold a backend from review routing outright.

Mechanism. _review_lane_candidates now orders the owning run's recorded backend first, then the locally served lane, then the configured rest in stable alphabetical order — and removes every name in the new flight key review_excluded_backends before any ordering, so a fallback cannot step around the exclusion. dispatch_awaiting_reviews bookends only runs whose pointer session matches the follower registration the sweeping process holds; a process holding no registration keeps the unfiltered behaviour. The printed next-action and the composed argv carry --backend <owning> where the run recorded a lane, and keep --local only for a pointer written before runs carried one.

What the gate shows

  • a review of a run recorded on clive composes onto clive, not the locally served lane — the fixture's local lane is deliberately a different backend;
  • a failed attempt on the owning lane falls back only to a lane not excluded, never to the excluded one;
  • when every remaining candidate is excluded the review is refused, and the refusal names review_excluded_backends rather than dispatching;
  • a sweep composes only its own session's runs; another session's run is left untouched;
  • the copyable next-action carries --backend clive and no --local.

Controls

Negative. The declared mutation — restore the alphabetical fallback in _review_lane_candidates that ignores the exclusion key — is applied and the exclusion tests are observed to fail: the fallback lands on the excluded local lane (alpha instead of beta) and the all-excluded case dispatches instead of refusing. The red log is negative-control.log in the node's run directory, its first line the declared string verbatim.

Base delta. tests/test_review_reflex_sweep.py and tests/test_review_reflex_selects_a_backend.py pass 13 tests at base 75b39d4d and the same 13 at this node's head: no added failures.

What this does not claim. The change composes the lane; it does not verify that a dispatch onto a non-local backend succeeds where the local one would have, which is the merged result's job. The session filter keys on the follower registration this process holds, so a hand-run sweep outside any follower stays unfiltered by design.
