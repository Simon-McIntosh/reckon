The per-read times do not account for the release stage

Every receipt also reports more memory resident than the threshold it declares for itself: resident_bytes 2.33 GiB to 7.99 GiB against memory_bound_bytes of 2 GiB, read after the pass had already shed its caches in answer to that threshold. Those named reads do not account for the release stage. The readiness read, and the store it reads

The post-write readiness helper — the call the baseline's 406.6 s measured — took 28.9 s, 39.6 s and 99.4 s on three runs against the live checkout: median 39.6 s, against a bound of 30 s. The first read ran against a snapshot of the store pair in a temporary config home; the other two ran against the live store itself, named through RECKON_RUN_STORE, which is the store the coordinator's own server answers from. The bound is missed, and the reason is visible in the profile rather than inferred.

The landing audit is not the cost. In the live-store run the audit's population was eleven plans holding runs, of which one declared a done section holding runs, and zero of those rows was in the promoted state the audit compares ancestry for, so it made zero git probes: git merge-base contributed nothing. What the read spends its time on is discovery over the live pointers. A profiled call of 108.9 s — its plain sibling in the same run took 99.4 s — breaks down as classify_pointer (recovery_classification.py:1577) at 92.0 s over 176 calls, reached through _discover_project → discover_plans → _discover_plans_uncached → _attach_ready_set (85.6, 84.2, 83.1 and 78.7 s) → build_roadmap (78.7 s). Each classification reads the run store, and those reads are not free: stored_run_rows is 80.8 s over 207 calls, of which _refuse_owed_migration is 77.5 s over 177 calls — about 0.44 s per call, on a 1.6 GB store that the fleet is writing to while the read runs.

That accounts for the spread between the three reads: the same code against a quieter snapshot is 28.9 s and against the contended live store is 39.6 to 99.4 s. So the miss is not a fixed cost of the readiness helper. It is 176 pointer classifications each paying a store read whose migration check dominates, and the number moves with the store's write load. The bound as written — one readiness read under 30 s against the live fleet — is missed on two of the three reads and met on the one that read a snapshot.

Two further reads sit beside these and are not the same operation. A declaration write plus readiness on a clone of the documentation root, with the fleet's git caches cold, cost 42.9 s and repeated at 14.7 s; the same write on a copied docs root with no git repository cost 53.3 s and then 32.0 s. Both are dominated by the first git object read, not by the store, and neither is comparable to the three above.

How each number was taken

  • Previews. Three crew dispatch --dry-run calls against three sections of this plan's project, each timed at the process boundary. The worker fence makes the live crew home read-only, so they ran with RECKON_HOME at a temporary config home whose crew subdirectories are symlinks to the live ones and whose writable dirs are real; --local was passed so the picker's routing latency was not inside a preview-cost measure. No worktree and no live pointer was created: two worktrees and two pointers before, the same after. The first attempt failed three times in a row at about 8.8 s with OSError: Read-only file system on a watch lock, which is the reading, not a measurement.
  • Receipts. Sampled from the verdict log every 15 s until ten distinct passes were held. The log trims at 1,048,576 bytes, roughly six passes, so a single read cannot supply ten.
  • Store read. stored_run_rows('reckon', plan=...) against a node-local SQLite backup of the hot store and archive, three times; each returned 1,055 rows, equal to the exhaustive filter over the same rows. The full read of the same store is 33.3 s for 12,925 rows.
  • Census. Candidates enumerated from the run store, never by walking the crew home; a run counts as delivered when its stage receipts hold a delivery_recorded stage; the split comes from review_request_census.
  • Readiness. Three reads, each in its own rigel job: the first with the store pair snapshotted into a temporary config home, the second and third with RECKON_RUN_STORE naming the live store and every other file the read writes — roadmap snapshot, state and runtime directories — in a temporary home, so the live config home was only read. All three used the live mounts and the fleet's git caches. The profile wraps the same helper call; the landing audit's population and its ancestor probes are counted by wrapping _unlanded_run_findings and merge._is_ancestor, and the 176 classifications are the profile's own call count for classify_pointer.

What could have failed. The population this pass works from is small: the receipts name two to six live pointers, not the 240 the sections reason about. An empty or unknown census population reports null lags rather than zeros (checked), a nine-receipt set is below the section's read floor (the sampler's target enforces ten), and the three previews that failed under the fence were counted as failures before the writable home was built. One observation is recorded without an explanation: asked through RECKON_RUN_STORE, stored_run_rows('reckon') answered 14 rows for both the config-home path and the explicitly named path, while the same store pair copied into a node-local SQLite backup minutes earlier answered 12,925. Something between the two reads — a retirement pass moving rows into the archive is the untested candidate — changed the figure, and this pass did not chase it. The plan-selected store read above stands on the backup that answered 12,925 and equals its exhaustive filter; the readiness reads stand on the live store and their cost is measured at the call boundary; if anything, that row count makes the miss larger, since 39.6 to 99.4 s was spent on a read that saw fewer rows than the snapshot that took 28.9 s.

What this leaves open

Three of the four bounds are missed; the preview meets its bound at 13.9 s against 30 s. The admission miss is in the launch stage and, underneath it, in the dispatch call each launch makes: the pass waits on that call (101 to 261 s per launched run), which no dry-run preview predicts (13.9 s). The review miss is in the request, not the launch. The readiness miss is discovery: 176 pointer classifications, each reading the run store, with the migration check 78 s of it. None of the three is repaired by this measurement, and §9 stays open until each is met.

The readiness result also tells the next section where to look. The landing audit the sections spent their effort on is cheap here because it is asked nothing — zero promoted rows in zero done sections that hold runs — so it is neither exonerated nor implicated. What is expensive is the pointer classification and the store read under it, which no section in this plan was aimed at.
