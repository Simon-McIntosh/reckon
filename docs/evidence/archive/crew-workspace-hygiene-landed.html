Reclaimable inventory matches the apply path

Commit f3e3fad (2026-09-01) repaired a misleading dry-run headline. The collector already removed both integrated and disposable worktrees under --apply, but its report exposed only the latter as the apparent action count. A measured imas-codex inventory therefore read as 0 disposable even though 40 of its 46 worktrees were reclaimable.

Classification Measured count Reclaimable Reported meaning
integrated 40 yes HEAD is already reachable from the integration revision.
disposable 0 yes A shadow run retains the patch that protects its work.
dirty 2 no Uncommitted work exists nowhere else.
live-referenced 3 no A live run pointer still claims the worktree.
unintegrated 1 no HEAD is not reachable from the integration revision.
Total 46 40 The report now states the same removal set that --apply uses.

Every worktree row now carries a boolean reclaimable field, the aggregate counts.reclaimable is the actionable headline, and each withheld row names the condition that must clear: uncommitted work, an unreachable HEAD, or a live claim. Tests in tests/test_crew_gc.py cover the per-row explanations and pin the reported reclaimable classes exactly to the branch that removes worktrees.

General lesson. A field that visually answers “is there anything to do?” must count the action the command will take. A narrower implementation category in that position is not merely incomplete detail: it can turn a 40-of-46 cleanup opportunity into an apparent zero, the same failure shape as a follower list that counts dead rows instead of sessions that can receive events.
