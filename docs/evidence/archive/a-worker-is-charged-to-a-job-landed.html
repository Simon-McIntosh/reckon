A worker is charged to a job — landed evidence

The mechanism is landed and its guard is shown to fire. The proving run the section is finished by is a dispatch a coordinator owns rather than this node, and its four measurements are written out as a command in this node's manifest.

Record scope

Three things are landed and each is proved by a case rather than by a design: a backend may declare a placement and the launch it produces is wrapped rather than rebuilt; the field is a first-class slot of the flight schema, declared in the source and regenerated into the served JSON Schema; and the run record names the job beside the pid, carried onto the committed ledger row. What is not here is the run itself — no placed worker has run on a compute node from this work — and that measurement is the coordinator's, named as a follow_on because a worker that dispatches a worker does not fit a fence.

§1 — The wrap, the schema field, and the record

A backend's placement declares a scheduler executable, its options, and optionally a job_id_probe. Dispatch resolves the scheduler head against the same PATH the launch searches and prefixes the already-resolved argv, so the absolute executable, the environment and the stream file descriptors are the ones the launch was built with — the wrap carries the launch through rather than replacing it. A backend that declares no placement is returned untouched, which is the sense in which the field is optional and the reason no undeclared backend changes behaviour. An unresolvable scheduler is refused before anything is launched, rather than at exec, where it would leave an empty stream that reads as a worker turn.

The field is declared where the schema is declared. The placement lives in reckon/schema/flight.yaml as a PlacementConfig, and reckon/_flight_schema.py and docs/_shared/flight.schema.json are regenerated from it with the repository's own generator rather than edited. The field therefore validates under the same forbids-unknown-keys rule as every other backend key, and reaches the served JSON Schema and its editor completion. A placement naming a scheduler but no options wraps the launch with an empty prefix rather than failing on a required key.

The guard was shown to fire. Declared mutation: make apply_backend_placement return the resolved plan unprefixed, so a declared placement is silently dropped. The red log at /tmp/awcj/negative_control.log fails test_a_declared_placement_prefixes_the_resolved_launch and test_an_unresolvable_scheduler_is_refused_before_launch — the two claims the mutation removes. A passing suite would not have shown that.

The job is read, not guessed. A placed launch records job_id beside pid, read through the placement's declared probe so reckon learns no scheduler's own vocabulary; a probe that answers nothing records its reason rather than a fabricated id, and an unplaced run records the key absent rather than zero, so the two remain distinguishable. Promotion carries the field onto the committed ledger row, which is the durable record a later attribution reads — the live pointer it was first written on is removed by that same promotion.

The defect, reproduced before it was repaired. Held against the base revision, the two new claims fail with reckon._backends.BackendError: no launch translation for command 'srun'; reckon can translate: claude, clive, codex, raised through crew.complete on a placed run whose stream is on disk. The wrap the section landed was correct for launching; what it changed is the identity a downstream reader infers, because it puts the scheduler at argv[0] while the lane the run launched from is named beside it.

What carries the identity now. Dispatch records the harness command it resolved, captured before the placement wraps the plan, together with the translation it resolved to. The reader consults those, falling back to argv[0] only for a record written before the fields existed, and the translation takes the recorded identity when the command's stem names no dialect — which is what makes a placed run already in flight promotable, since its argv names the scheduler and nothing else. A mapping built from configuration carries no recorded identity, so dispatch-time strictness is unchanged and an untranslatable command with nothing beside it is refused exactly as before; that half is asserted, not assumed.
