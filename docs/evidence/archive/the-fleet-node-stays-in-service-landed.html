§7 — a watch producer sweeps the whole fleet every second

Each producer cycle lists every project's live pointers, walks run directories, parses streams and calls git on a 1 s beat whether or not anything moved. That costs about 1,880 opens, 1,575 stats and 1.25 git-shim calls per cycle, which is 114 to 115 git executions in 32 s, independent of the live pointer count. Five producers make roughly 9,000 GPFS opens a second and about 35 of the node's 80 process creations a second. The change-driven fix is to gate the sweep on inotify, or on one mtime stat of the crew home, and keep only the liveness probe on the beat. The live 56% versus 8% CPU gap stays unattributed, because ptrace from the worker sandbox was refused. The git figure is the review's recount; the review scored the node 85/120. fragment

§3 — a stopped worker ends inside its step

A step-placed worker is stopped by signalling the processes below its sandbox's PID-namespace init. The step task (the outer bwrap) and the srun client's local subtree are never signalled, and the escalation is SIGKILL to the same inner processes. The supervisor reads the task identity from a record its wrapper writes before it execs the sandbox (job, step, pid and start tick). It checks membership from the task's cgroup and start time. The wrapper execs only after its record is written. Live probes on the fleet allocation, where the worker and its child both ignore SIGTERM against a 55 s grace: steps 1281970.6964, .6972 and .7012 ended FAILED|9:0 in about 60 s, the sender receipts name only the inner pids, and the node state was unchanged. The controls were step .6508 (client signal, CANCELLED) and step .6958 (signal to the outer task, CANCELLED|0:15 in 3.02 s). A run whose step has not started is ended by one client SIGTERM, by pid, sent only when squeue lists no step of the fleet job named after the run (each placed step is named with --job-name). After ten minutes of waiting, the supervisor records the step's processes and wait channels. Commits a68080406, 2d3edd6c2, 04f6ace9a and 4596a01ba, merged into main as a80d85d25. §6 — a worker step carries a memory bound

Every fleet worker step now carries an explicit --mem from placement.step_prefix. It is 24 GB by default (DEFAULT_STEP_MEMORY_GB, overridable with RECKON_STEP_MEMORY). fleet_node.placement_argv composes through it, so the bound is stated once. A node that needs more declares it through the existing dispatch override, which replaces the whole options list: --set 'backends.<backend>.placement.options=["--ntasks=1","--mem=48G"]'. One parser reads the declaration for both placement and the admission summary, in both --mem=N and --mem N forms. A declaration above the 48 GB ceiling leaves the shared 96 GB allocation and runs as srun in a fresh allocation on the partition's _debug sibling, with its SLURM_* job identity removed and --time at most an hour. §10 — the code identity is read only when HEAD moves

§11 — a moved checkout is proved importable once

reckon_imports now proves a published reload image once per interpreter. It does so under an exclusive lock in the image's directory (.import-probe.lock) and records the verdict beside the image by rename (.import-verdict-<interpreter digest>), so concurrent askers on one image start one probe and read its answer. A pass and an import failure are both recorded; a timeout is not. The wait for the lock is bounded by the probe's own 30 s timeout. A wait that reaches the bound with no verdict is answered as a timeout, so a follower never stalls its stream behind a queue of proofs. The follower's timeout retry draws up to a quarter of its gap as downward jitter, so retries no longer fire in step. One shared recogniser, published_reload_image, serves the proof, the running-code identity, the tree pin and the follower's reload path. A source checkout keeps its per-process probe.

On the fleet allocation, sixteen concurrent askers on a freshly published image started 16 probes at the base (7.09 s) and 1 at the change (7.52 s), with every answer inside 30 s. The night's lighter load meant the base herd did not time out this time, as it had at 20:48 on 19 October. The declared negative control, an image carrying a module that fails to import, gave 16 refusals from 1 probe and no re-execution. The reload and follower suite passed 87 at the base and 99 after: the 87 plus 12 new tests. Code review gave 93/120 and raised four follow-ons. Those, plus the coordinator's finding that the lock wait was unbounded, were repaired, and the re-review gave 106/120. §12 — a process table is read once per beat

The environment-mark liveness read (_processes_owning_run in reckon/crew/process_signal.py, reached from _env_scan_run_pid) now takes each process's environment from one shared index (_ENVIRON_INDEX). It rereads a process only when its pid, start tick, executable path or stack base changes. The stack base moves on every exec while address randomisation is in force, which it is on the fleet node (kernel.randomize_va_space is 2), so a same-binary re-exec is read afresh. A process owned by another user is skipped by the owner of its /proc entry without opening its environment. The index drops pids that have left the table. The stop path's signal-time checks, the start-tick floor and the crew home, are unchanged.

§13 — one walk of the process table answers every run in a beat

The liveness read's environment reach now takes one walk of the process table per beat (_walk_marked_processes, held for BEAT_SECONDS by _beat_marked_processes in reckon/crew/process_signal.py). The walk maps each pair of run mark and crew home to its pids, and every run asked in that beat is answered from the map. _env_scan_run_pid asks with from_beat_map=True. Keying on the pair keeps the crew-home qualifier, so a process carrying another home's run id is never named as this run's worker. The stop path keeps a fresh walk at signal time, with its start-tick floor and crew-home checks.

On the fleet allocation, a 5 s strace of a producer harness over 5 beats with 8 runs needing the scan listed /proc 40 times at the base and 5 times at the change, and every scan still found its worker. The 34-file paired suite failed 2 and passed 557 at the base, and failed 1 and passed 558 at the change, with no added failure.
