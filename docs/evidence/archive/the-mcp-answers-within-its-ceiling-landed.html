§4 — A crew read returns the fields it was asked for

Commits 39dee90a (the projection and the widened runs vocabulary) and d5773b49 (live field validation against the live set) in the crew-live-honours-fields worktree, base revision a130260c.

A narrowed live read returns the requested fields plus run_id, so the key count falls from the whole classification to the request. The runs read is additive: it always carries its base row, and the three coordinator fields widen the request. The counts, measured:

The defect, reproduced

crew(view="live", fields=[…]) accepted the list and ignored it: the live arm called classify_pointer per pointer and returned every field of the classification, so the compact projection the runs view applies was never reached on this path. crew(view="runs") honoured fields but refused the three fields a coordinator checks first, because they were absent from the accepted set.

A second defect sat in the projection itself. It validated a requested field against the compact runs vocabulary, so fields=["phase"] was refused although every live row carries phase, and a field with no compact counterpart such as next_action could not be asked for at all. When session was supplied, the projection also dropped mine, so a session-scoped read that narrowed its columns lost the one column the session argument exists to add.

The change

  • reckon/crew/query.py — commits_beyond_base, log_age_seconds and manifest_reported_status joined OPTIONAL_RUN_FIELDS, so the existing refusal widened to accept them and the compact row carries them from the same classification the live path computes. A new session-aware project_live_rows classifies and, when fields is given, projects each row to the requested fields plus run_id. A requested field is now validated against the keys the live classification actually produces — plus mine when a session was supplied — rather than against the compact runs vocabulary, and mine is kept on every projected row when session is given.
  • reckon/mcp.py — the live arm routes through project_live_rows, so the requested fields are honoured; the mine marker is computed from the full classification and survives projection.

The gate measures, as executed

tests/test_crew_live_honours_fields.py on a synthetic config home with two live runs, head d5773b49 against base a130260c. Four tests, all passing:

  • Live projection. crew(view="live", fields=["classification", "node"]) returns two rows whose key set is exactly {run_id, classification, node}.
  • Live-only fields are requestable. fields=["phase","process_alive"] returns rows whose key set is exactly {run_id, phase, process_alive} — names the compact runs vocabulary does not carry.
  • A session-scoped read keeps mine. fields=["node"] with session="session-run-1" returns rows whose key set is exactly {run_id, node, mine}, with mine true for the run whose session matches and false for the other.
  • Refusal names the live set. fields=["not_a_field"] returns ok: False with a detail beginning unknown live fields and naming phase, process_alive, next_action and classification among the accepted fields.
  • The three fields are populated from the classification. A runs read with source="live" returns the three values equal to classify_pointer(row) for the same pointer, with manifest_reported_status == "in-progress", commits_beyond_base == 1 (a real git worktree one commit past its base), and log_age_seconds an int from the run's own log file.

Negative control, as declared and executed

Declared: remove the fields projection from the live arm. Applied to reckon/mcp.py (the fields= argument dropped from the project_live_rows call) and run over the whole gate: three of the four tests fail — the projection test, the mine test and the refusal test — because every live row comes back as the whole 48-key classification, so the key set, the mine column and the unknown live fields refusal all disappear. The log is recorded beside the run. The control was then reverted and the tree returned to the committed revision.

§2 — the summary names its pending plans

The summary projection stays exactly what it was without a sprint scope, and gains a pending_plans list only when the report carries a sprint. Each element is one compact row: slug, status, impl (the plan’s implementation fraction), ready, blocking (the sorted ids that hold the plan) and implementable_sections (the section ids still declared implementable). Nothing else is added, and no prose is carried.

The row is projected from the pending_work row the report already builds, so the summary does not re-derive readiness or blockers. Two details are worth naming. First, blocking unions the ids of explicit, held, gate and decision blockers with the slugs of unsatisfied depends_on edges, de-duplicated. Second, the MCP path inventories slim rows — the inventory whitelist drops the plan’s section_declarations — so the section ids are read from the plan file itself when the row carries none, which is the rule the wiring scan already follows.

Negative control

The declared mutation — removing the pending-rows projection from the sprint summary — was applied at the worktree head and the gate re-run. Five of the six cases failed with KeyError: 'pending_plans' and the no-sprint case passed, which is the shape a real control has: the projection’s presence is what the failing cases measure, and the case that asserts the sprint-less path is untouched keeps passing either way.
