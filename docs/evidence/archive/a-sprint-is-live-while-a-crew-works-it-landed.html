A Sprint Is Live While A Crew Works It — landed record

Execution record for a-sprint-is-live-while-a-crew-works-it §2 and §4. Liveness is derived at read time from a project's live crew pointers: a pointer working or dispatched makes its sprint live, a blocked or unpromoted pointer is held. Nothing is written back to a sprint resource.

§2 — Liveness is derived from live crews

Added reckon/sprint_liveness.py, exposing sprint_liveness(project, docs_dir, live_records). The read composes machinery that already existed rather than rebuilding it: classify_pointer and the watch state mapping from reckon/crew/recovery.py decide each pointer's state, and list_live from reckon/crew/runs.py supplies the record set when the caller omits one.

Each sprint a pointer serves yields one row carrying live, live_runs, live_sessions, last_activity_at and held_runs. A sprint is live when at least one of its pointers reads working or dispatched; a pointer that is blocked, or a completion nobody has promoted, counts as held, not live. A terminal pointer on a sprint makes that sprint read live: false. The sprint's stored status is never consulted, so a sprint's stored status cannot disagree with what is running.

No file is written: the read is computed from the pointers and the plan meta the pointers name. The plan → sprint join reads the pointer's own node.plan and that plan's plan-sprint meta.

§4 — The one-active cap, push no longer demotes

push_sprint in reckon/project_state.py no longer treats active as an exclusive slot. It writes active on its target alone — under the same single resource lock and recovery journal the op used before — leaves every other sprint's stored status untouched, and returns only new_version. The push branch of the apply op no longer emits demotion warnings. The change landed in 0ad5a171.

The measure — push S2 while S1 is active, both stay active

The defect is that a push wrote a second sprint file to demote the previous holder of the slot. Reproduced at the base revision before the repair: pushing S2 while S1 was active returned demoted=['S1'] and left S1 at open; the same script against the repaired module returns no demoted key and leaves both at active.
