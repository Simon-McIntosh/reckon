A Sprint Is Live While A Crew Works It — landed record

Execution record for a-sprint-is-live-while-a-crew-works-it §2 and §4. Liveness is derived at read time from a project's live crew pointers: a pointer working or dispatched makes its sprint live, a blocked or unpromoted pointer is held. Nothing is written back to a sprint resource.

§2 — Liveness is derived from live crews

Added reckon/sprint_liveness.py, exposing sprint_liveness(project, docs_dir, live_records). The read composes machinery that already existed rather than rebuilding it: classify_pointer and the watch state mapping from reckon/crew/recovery.py decide each pointer's state, and list_live from reckon/crew/runs.py supplies the record set when the caller omits one.

Each sprint a pointer serves yields one row carrying live, live_runs, live_sessions, last_activity_at and held_runs. A sprint is live when at least one of its pointers reads working or dispatched; a pointer that is blocked, or a completion nobody has promoted, counts as held, not live. A terminal pointer on a sprint makes that sprint read live: false. The sprint's stored status is never consulted, so a sprint's stored status cannot disagree with what is running.

No file is written: the read is computed from the pointers and the plan meta the pointers name. The plan → sprint join reads the pointer's own node.plan and that plan's plan-sprint meta.

An age bound on the recorded state

The recorded state was trusted with no bound on its age. A run that died after its last recorded working event kept reading live: the record still said working, the watcher had stopped writing, and nothing compared the record against the clock. Commit 81279f94 carries each record's own observed_at beside its to_state and uses the recorded state only while that observation is inside the stall window the fleet classifier uses (DEFAULT_WATCH_STALL_WINDOW, 15m) or the run's own stream was written inside it. An older record falls through to the unchanged bounded fallback: the manifest status prefix and the stream mtime against the same window.

The second clause is load-bearing. A long turn whose last recorded transition is older than the window stays live while its engine is still producing output, because the run's own stream is being written inside the window. When the process dies, both clocks go stale together, so neither clause holds and a stale working cannot outlive the run.

§4 — The one-active cap, push no longer demotes

push_sprint in reckon/project_state.py no longer treats active as an exclusive slot. It writes active on its target alone — under the same single resource lock and recovery journal the op used before — leaves every other sprint's stored status untouched, and returns only new_version. The push branch of the apply op no longer emits demotion warnings. The change landed in 0ad5a171.

The measure — push S2 while S1 is active, both stay active

Reproduced at the base revision before the repair: pushing S2 while S1 was active returned demoted=['S1'] and left S1 at open; the same script against the repaired module returns no demoted key and leaves both at active.

§4 — The focus follows the live crew, and what it costs

Verdict: complete. The behaviour landed at bec9f24a. The one check it failed when it was written — the added cost, measured while sprint_liveness still parsed every live run's whole stream — now passes: with the reader taking the watcher's recorded stream (merged at a4fa01f6), the same read costs no more with the focus than without it. Both measurements are below: first the one that blocked the node, then the re-measurement that closes it.

active_sprint_id names the live sprint with the liveness reader's newest last_activity_at, and falls back to the stored active sprint when no pointer is live. A new live_sprint_ids list carries the live sprints, newest activity first. Both the composed project state (reckon/project_state.py) and the roadmap report (reckon/roadmap.py) expose both, and each composition reads liveness once rather than once per sprint.

Three helpers in reckon/project_state.py carry it: live_sprint_ids(liveness) orders the live rows itself; focus_sprint_id(sprint_rows, liveness) resolves the focus; and _has_unfinished_items supplies the deterministic tie-break. They live in project_state and not in sprint_liveness so that the module deriving liveness stays the only place that derives it — roadmap imports the two resolvers from project_state, and neither new dependency closes a cycle.

The deterministic choice when several sprints are stored active

The live sprint wins whenever one is live. With none live and more than one sprint stored active, the focus is the first stored-active sprint that still carries an unfinished item; failing that, the first stored-active sprint; failing that, the earliest sprint with unfinished work. The rule is written into focus_sprint_id's docstring and is what keeps the pre-existing test_default_sprint_focus_is_earliest_incomplete_and_never_persisted true — the earlier contract preferred the earliest incomplete sprint and would otherwise have been contradicted.
