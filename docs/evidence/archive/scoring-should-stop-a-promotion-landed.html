The refusal, the reasoned waiver, and the fixtures it exposed

What landed. reckon crew complete now refuses to promote a passing implement run whose pointer classifies as scoring — a completed manifest with no complete independent review attached. The refusal names the run and the review dispatch that produces the review, reusing the dispatch classify_pointer already composed for the run. An explicit --waive-unreviewed-promotion REASON permits the promotion and records the reason verbatim on the promoted ledger row, so an unreviewed landing stays possible and stays visible.

One reader, not two. The refusal consults the review the promotion path already resolves rather than adding a second reader: read_review occurs exactly once in reckon/crew/promotion.py, inside the existing _review_row_block, whose result the guard receives. A second reader is the defect this change must not introduce, so the check is a count rather than a promise.

Exposure, and what it cost. The measured cohort — the 15 test files that invoke promotion.complete, 184 tests — ran at 18 failures before the change and 18 after, with 0 newly failing. Fifteen of the fixtures left exposed by the earlier probe needed repair, not a waiver: 14 of them build a complete-manifest run with no review, so each now carries a stored parsed review, keeping the test measuring its own subject (landing comments, stream figures, worktree retention, suite-delta policy) rather than the review gate; the commit-shortfall fixture waives the requirement explicitly, because that file writes no review home of its own.

Evidence that could have failed. The declared negative control — forcing the guard's unreviewed flag false so no scoring promotion is refused — makes tests/test_crew_promotion_requires_review.py fail (2 failed, 4 passed), naming the mutation on the log's first line; the control was reverted before the commit and the guard's source is byte-identical to the committed revision afterwards. A suite that passes never shows a guard fires, so the guarded thing was made to happen and the refusal shown.

A completed review-role run is exempt from the scoring classification

What landed. classify_pointer in reckon/crew/recovery.py reads the role the run carried and returns promotable for a completed review run, with a next_action that composes no dispatch naming it. Every other completed run is unchanged: promotable when a parsed review is attached, scoring when one is missing or incomplete, and scoring is the classification the review reflex acts on. Without the exemption the reflex dispatches a review of a review run, that review completes, classifies as scoring in turn, and dispatches another of the same shape — a chain in which every link is a real dispatch against a real member.

The defect reproduced at the base revision before the repair. With aa3c5ac6's reckon/crew/recovery.py restored in place, the module run against the base tree reports 6 failed, 1 passed, and the composed action for a completed review-role run reads, verbatim:

reckon crew dispatch ... --role review --spec-level exact \
  --node review-of-r-prior-review \
  --goal 'attach an independent review to run r-prior-review' \
  --done-when 'the review for r-prior-review stores a parsed record ...' \
  --write-path .../crew/reviews/sample/r-prior-review.json ... --local

That is a review of a review, composed by the same function that composes the review a genuine scoring run needs. After the repair the same fleet mints exactly one review node, review-of-r-work, and none for the review run.
