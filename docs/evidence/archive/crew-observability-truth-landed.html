Refuted peer finding — a ledger commit "not reachable from origin/main"

Claimed (a peer session's characterisation, relayed in §4's c-20260903-ledger-claims-unmerged, 08:50): run r-20260903T083356777926-spec-level-names-a-backend-with-provenance is promoted with gate passed and commit 957c042, and that commit is not an ancestor of origin/main — so the ledger asserts a landed commit that main does not have, with the worktree already removed and the object surviving only as a dangling one (tagged rescue/spec-level-names-a-backend-957c042 as a precaution).

Measured, first pass (c-20260903T1052, 08:52): git merge-base --is-ancestor 957c042 origin/main succeeds; the merge commit is 862d8cf with parents 56d13fc and 957c042; the 69 insertions are in the tree, not only in a dangling object. The commit is, and was, reachable. This first measurement attributed the false original finding to a stale local remote-tracking ref that had not been fetched.

Measured, second pass, correcting the mechanism (c-20260903T1103, 09:03, and independently confirmed by the peer's own c-20260903T085741678595): the stale-ref mechanism was itself wrong. This checkout shares one .git ref store across 20 worktrees, so a peer's push updates origin/main directly and there is nothing to fetch — git reflog show refs/remotes/origin/main records every entry as "update by push," never "fetch." The real mechanism is shelf life: the merge was created at 10:46:24, the ref moved to it at 10:49:05, and the original finding was authored at 10:50:27 — so the reachability check ran before 10:49:05, when "not reachable" was the momentarily correct answer, and was published at least 82 seconds after it stopped being true, into a wave that put four pushes on the branch in 21 minutes.

Superseded: "the ledger asserts a commit main does not have" (false) → "the reading was correct at the instant it was taken and stale by the time it was published; fetch-before-judging is hygiene for a separate clone or CI, not the remedy here." The agreed-and-surviving half of the original proposal stands: promotion should verify a recorded commit is reachable from the integration branch, or record explicitly that it is not, and must stamp that verdict with the instant it was taken and the ref it was taken against — because an unstamped reachability claim gives a reader no way to tell whether it has expired, and "reachable" is itself ambiguous between merged-locally and pushed.
