A Worker Cannot Write Your Home — landed evidence

The worker's launch argv is composed inside a bubblewrap fence that overlays every protected path read-only and re-binds the run's own write roots, proved by executing the argv rather than inspecting its shape.

§1 — Every CLI worker launches inside a filesystem fence

Node: launch-plan-wraps-a-filesystem-fence.

What landed. reckon._backends.launch_plan gained fence (default False) and an injectable fence_home. When asked, it wraps the dialect's argv through fence_argv: bwrap --dev-bind / /, then one --ro-bind per existing protected path, then a --bind for each write root that falls inside a protected path, then -- and the harness argv. The protected set is derived by protected_paths(home) from the home in force, so a test stands a temp home in and the operator's real dot directories are never touched. Because every dialect and every entry path — fresh dispatch, resume and redispatch — builds its argv at this one point, the wrap cannot be left off for one of the three.

Why it defaults off. A read-only ~/.claude without a per-run harness home stops the claude harness writing its own transcript (§2), so no field run changes until that section lands. The default is pinned by an exact-argv assertion, not a shape.

Method. tests/test_launch_plan_fences_the_home.py builds a synthetic home with a stand-in for every protected class, places a sentinel in each, and runs the composed argv with a stub in place of the harness. The stub attempts an rm -rf of each sentinel and a write into each granted root and records the outcome in the run directory; a non-empty record is itself the proof that the run directory stayed writable.

The reproduction, quoted

Run with the fence dropped entirely — the stub executed unfenced — the same stub deletes every sentinel, so the fenced survival is not vacuous:

unfenced rc 0 deleted count 15
claude sentinel exists unfenced: False

Fenced. Every protected sentinel survives an rm -rf and the removal is refused (Read-only file system); every granted root and the worktree are writable. The worktree in the fixture lies inside a protected checkout, so its writability rests on the re-bind rather than on it merely lying outside the set. A second assertion covers the checkout class by expansion: a .git directory under Code is recognised as a main checkout without being named literally.

Negative control

Applied, the ~/.claude sentinel is deleted and every other overlay still refuses — so the deleted sentinel is attributable to the removed overlay and not to an unfenced run. Log: docs/figures/a-worker-cannot-write-your-home/negative-control.txt, whose first line is the declared mutation verbatim.

§2 — A worker's own harness state lives in its run

Node: each-run-owns-its-harness-home.

What landed. launch_plan now points the harness at a home inside the run: CLAUDE_CONFIG_DIR at <run>/harness for the claude and clive dialects, and CODEX_HOME at <run>/codex-home for codex. Each home is seeded with the directory alone, and only when the manifest's parent directory already exists — a preview composes a plan before anything has been created, and a run with nowhere to keep a transcript is not given a variable pointing at one. The operator's ~/.codex/auth.json is bound read-only into the codex home rather than copied, so a worker cannot shadow a login the operator refreshes. With both homes in place the fence is now composed by default (fence=True), which is what §1 was waiting for.

The lock directory, an addition to the granted roots. Every plan write serialises through <config>/locks/<namespace>/<hash>.lock, and opening that file is a write. A worker editing the copy of a plan in its own worktree takes the same lock as one editing the main checkout, so a sealed lock directory refuses a fenced worker every plan write it could make. The directory is therefore seeded and granted writable, beside the run directory the fence already re-opened inside a sealed config home. Measured under the fence before the grant: mkdir of an existing directory succeeds, while opening a lock file and creating a new directory both fail Read-only file system.

Method. tests/test_each_run_owns_its_harness_home.py stands a home, a main checkout, a worktree and a live run directory in a temp tree, composes the plan through launch_plan, asserts the environment and the composed argv, and then executes the argv with a stub in place of the harness. The stub writes its own state where its own variable points, attempts to remove the codex login, and optionally starts reckon's MCP server as a child of the fenced process and calls edit_plan twice — once without checkout_path and once naming the worktree.

The reproduction, quoted

harness-state-write ok /tmp/…/crew/runs/r1/harness/session-probe.txt
edit no-checkout-path refused=True isError=True path=None detail=Error executing tool edit_plan: [Errno 30] Read-only file system: '/tmp/…/Code/proj/docs/plan-a.html.tmp'
edit checkout-path refused=False isError=False path=/tmp/…/.worktrees/wt/docs/plan-a.html detail={ "ok": true, "message": "Updated plan plan-a to version 1." … }

The refusal names the target path and not the lock, because the lock is taken: the write into the sealed main checkout then fails on its own temp file. The main checkout's plan file is byte-identical afterwards (sha256 compared before and after), and the worktree's copy carries the replacement text. So the fence holds the route that goes live for every session through the editable install, while the worker keeps the route it exists to take.

The plan-write half of the measure is unmoved by the mutation, which is the check that the two are independent. §2 follow-up — a fenced resume reaches its harness

The defect reproduced at base 18a89e6f. A dispatch built through launch_plan(fence=True) and recorded the way dispatch records it — command from the composed argv[0] — then asked for its resume: the dispatch argv's inner command is clive, the resume argv's is /usr/bin/bwrap, and the resume record's command field is /usr/bin/bwrap. Reproduced with the composition alone at base (docs/figures/a-worker-cannot-write-your-home/repro-fenced-resume-base.txt), which is the same argv shape the smoke saw in a real run. At head 49ecff80 the same procedure at the same lane yields clive behind a single fence element (repro-fenced-resume-after.txt).

The repair. _backend_settings refuses a recorded command that names the fence binary and recovers the harness from the run's own composed argv, searching after the fence element so a placed launch's scheduler options cannot be mistaken for the fence's own separator. A resume therefore composes the fence around the harness exactly as a dispatch does, and the run's own harness home — including its per-run CODEX_HOME, where a codex session rollout lives — is the home it reuses.

§2 follow-up — a worker cannot run mutating git against another checkout

The defect, measured 2026-09-25 at 20:52:06Z. Unfenced imas-ambix worker r-20260925T203357366663-s18-pause-cut-flag ran git -C /home/ITER/mcintos/Code/imas-ambix checkout -- docs/plans/local-lane-admission-control.html against the coordinator's main checkout to undo its own stray plan write. That verb is banned for files an agent did not author, and had the coordinator held uncommitted plan edits it would have destroyed them with no trace. With the fence off, nothing stopped it.

The repair: a PreToolUse Bash guard that is in scope only inside a crew run. reckon/hooks/worker_git_guard.py reads RECKON_RUN_ID, exports nothing when it is absent, so a coordinator session is untouched. It tokenises the Bash command, splits it at the shell separators (;, &&, ||, |, &), and tracks a cd so a later segment's working directory is the one the cd left behind. For each segment running git it resolves the target from -C, --git-dir or --work-tree (both separated and attached forms), and from that working directory otherwise. The run's own worktree is read from its live pointer (<RECKON_HOME>/crew/live/<run>.json, the worktree field). A mutating verb — checkout, restore, reset, clean, stash, commit, merge, rebase, pull, push, add, rm, mv, switch, cherry-pick, revert, am, apply — whose target resolves outside that worktree is denied, and the refusal names the run, the worktree and the target. A read-only verb, and any verb outside that set, stays allowed everywhere. The guard is stdlib-only and ships as a bare script command.
