A per-node fence charges a worker for the fleet's load

This node blocked once, correctly, and the specification behind the block was the coordinator's. Its contract required a full-suite delta inside a 25-minute fence. The untouched baseline took 814.58s unloaded; a second full suite could not finish while four peer full suites contended for the same machine. The worker did the work, committed it, measured what it could, and reported a blocker rather than claiming a receipt it did not have — which is the escape hatch behaving exactly as designed.

The amended acceptance is stricter where it matters rather than merely cheaper: grep -rnE 'state/reckon/flight.yaml|effort-routing.md' over tests/ and reckon/ returns empty, so no Python behaviour can depend on either changed path and a full-suite delta could never have measured this change. That argument bounds the blast radius by construction, where a green suite would only have bounded it by coincidence. The gate became 99/99 tests across three files plus four resolved-config assertions, with the full-suite receipt moved to one integration verification at the merged head.

The generalisable finding is a measurement one. A node's recorded duration, and whether it hits its fence at all, currently depend on how many peers are running a suite at the same time. For a plan whose purpose is comparing configurations from ledger time, that is a confound of the same family as the inherited-budget confound the effort-routing plan had to fix: the run record says 1,530 worker-seconds and cannot say how much of it was contention. Nothing in the record distinguishes a slow model from a busy machine.

§3 — The local lane is reachable by name

Run r-20260902T133012246969, member local-alias at gpt-5.6-sol/medium, 1,970 worker-seconds, first attempt, commit 42a339f: 287 insertions and 14 deletions across exactly the twelve authorised paths, 8 tests added. Gate: full suite 2,660 passed / 0 failed in 855s, focused 352 passed, ruff findings on the touched paths down from 68 to 60 with none added.

The baseline was not clean, and the manifest says so. At 302022e the suite carried one failure — test_the_attention_filter_is_inside_the_follower — which passed in the after suite. The worker recorded it as negative baseline evidence rather than claiming it as a fix. That is the correct handling of a timing flake: the delta is what the node is judged on, and an absolute green would have been a claim it could not support.

What the change actually removes is a rule with no bound check. The ship skill has always said a request to use local workers routes through “the configured locally served backend alias”, and no such configuration existed — the phrase was honoured by a coordinator remembering to pass an override on every call.

  • local_backend is an optional peer of default_backend in the LinkML source, validated against the merged backend map with its own key path and carrying leaf provenance; both derived schema artifacts regenerate byte-identically.
  • --local resolves it as that dispatch's default through the existing plan_dispatch authority rather than a second resolver, which is what the reuse map asked for; dry run and real dispatch therefore report the same backend.
  • An unset or undeclared key is a request error at exit 1 naming local_backend, so a host with no local lane fails loudly instead of silently running the incumbent — the whole point of the decision.
  • Role and specification overlays still apply after the selection, so a local review node keeps its read-only sandbox.
  • local: true is retained on the live pointer and in the promoted ledger record, so the calibration slices can separate local runs later.

Verified end to end after the merge, not from the diff. The host layer declares local_backend: clive, reckon flight attributes it to the host layer, and a --local --dry-run resolves clive / deepseek-v4-flash with local: true on the agent.

Two host-layer comments were corrected in the same beat because this change and §4 made them false: the clive entry still said nothing but an explicit --set could route to it, and the codex-spark entry still described the project mapping §4 removed. A comment that describes routing which no longer exists is the same defect as a stale pointer — it reads as current.

§2 — Availability learns to ask what the wrapper actually serves

Run r-20260902T140912669453, member local-avail at gpt-5.6-sol/medium, first attempt, commit ca6288d: 407 insertions across seven paths, 6 tests added. Gate: full suite 2,673 passed / 0 failed, focused 58 passed, scoped ruff findings 10 before and 10 after, both derived schema artifacts regenerated byte-identically.

A backend may now declare a catalog: list_command, the argument vector that asks its command what it serves, and model_pattern, how a served model is matched in that output. Both are leaf-provenanced through the layered schema. The probe runs the vector, substitutes the escaped configured model into the pattern, and reports model_served with either the matched line or a census of every non-empty offered line — and never acts on it, which keeps availability a report rather than a router.

Two properties decide whether this actually closes the hole:

  • The probe runs against the effective backend, after role and specification overlays — not the bare default. An overlay cannot route past the check.
  • The refusal happens before a run pointer exists, on the dry-run and real paths alike, through the existing exit-5 competence envelope carrying refusal=model-unavailable and the catalog detail. Nothing is created and then unwound.

A backend that declares no catalog is byte-for-byte unaffected, which is why no existing backend needed an edit. Test isolation held to the constraint recorded before dispatch: every assertion uses an executable synthetic wrapper created under a pytest temp directory and placed on PATH. Nothing reads the cluster, a sibling checkout, or user state.

The live catalog, measured once here rather than in a suite: clive --list serves deepseek-v4-flash · 2×H200 · fp4+fp8 · 492,288-token usable input budget · 32,000-token output reservation, and nothing else. GLM 5.3 has no release id. What remains of §2 is therefore not code — the clive-glm entry waits on the catalog, and with this landed it becomes one safe config block instead of a backend that would have claimed to be available.

§6 — The worktree boundary stops being the worker's good manners

Run r-20260902T140832755711, member boundary-check at gpt-5.6-sol/medium, first attempt, commit 0226835: 313 insertions and no deletions across exactly the four authorised paths, 5 tests added. Gate: full suite 2,672 passed / 0 failed, focused 202 passed, scoped ruff findings unchanged at 29.

The tier called worktree-full resolves to the harness's no-sandbox mode, and for a good reason — a sandbox is inherited by child processes and would break the test runners a gate depends on. The consequence was that the boundary was the worker's obedience to its prompt, which a local-model worker had already disproved by editing the shared checkout with sixty-one tool inputs naming it and none naming its worktree.

Dispatch now takes one registry enumeration after its own writes settle — one, not one call per path, because the fleet changes between calls — sorts the roots deterministically, and stores each absolute path, HEAD, a SHA-256 digest of porcelain status, and the parsed entries on the live pointer. Promotion re-inspects exactly those recorded roots under the lock it already holds and refuses before ledger append when any main-checkout or peer-worktree path changed, naming both the repository-relative path and the tree that owns it.

Three properties keep it usable rather than merely strict:

CaseBehaviourWhy it matters
A worktree registered after dispatchnot enumerated, not charged Otherwise every long run would be refused by the next dispatch in the wave.
The live plan resourcecoordinator-owned, excluded from attribution The coordinator writes the plan during every landing beat; charging that to a concurrent worker would refuse healthy runs.
A refusalpointer present, ledger empty The run stays recoverable, exactly as the existing out-of-scope-commit refusal leaves it.

Five cases, each strict half paired with its negative: main-checkout stray refused, main-checkout clean promotion, peer-worktree stray refused, peer clean promotion, and the after-dispatch worktree. The worker recorded completed: false for the baseline suite it did not arm rather than fabricating one, which is the right answer when the after-suite has zero failures and the delta is therefore zero either way.

This is the gate the locked local-write-access-order decision names, and it closes the second of the two harness failures the six-pair local qualification recorded. With a stray write refused at promotion by test, what stands between the local lane and implementation work is the six controlled requalification pairs — a measurement, no longer a missing mechanism. And the fix benefits every backend, which is why it was worth putting in front of the lane rather than around it.
