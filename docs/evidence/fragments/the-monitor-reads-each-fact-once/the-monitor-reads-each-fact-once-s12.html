The cutover window on the fleet node: the bound is not met

The decision. The retirement is withheld and the per-project producers stay. The station carries the rows, but its cost is not inside the bound this plan sets, and the condition for retiring the producers — that the station cost the node less than they do — is not met either: measured on the fleet node the station alone reads 11,645–13,622 MB/min against a bound of 20, and the twelve producers together read a further 10,702–6,469 MB/min.

Re-measured after the store-signature change. The station alone reads 16,779–18,953 MB/min, so the verdict is unchanged; the re-measurement is below.

The instrument seen counting before any absence is claimed

Each window's log opens with a positive control in the measuring process itself: a known 197-byte file is read and the rchar delta is printed. The first window reports rchar_delta=300 and the second rchar_delta=294 for that 197-byte file, so a small or zero total could not have been a counter that stopped working. Neither total is zero, and six producer seats read nothing at all in each window: an idle seat inside the measured set is a quiet process, not a dead instrument.

Where the station's bytes go

strace -f -ff -yy -e trace=read,pread64 over 10 s, aggregated by path over one file per thread, puts 90 % of the station's reads in two files: run_store.db (37.8 MB, 47.6 %, 1.16 GB on disk) and run_store.archive.db (33.6 MB, 42.3 %, 504 MB). The rest of the sample is the per-project review index (7.0 MB, 8.8 %) and run documents. The trace's own total is lower than the process's rchar delta for the same period because ptrace slows the tick, so what it is used for is the share and not the rate.

A direct probe of the read path, run at this revision against the live store and timed with /proc/self/io, gives the per-call cost the tick pays. One run_store.stored_run_signature("reckon") — 12,929 rows — reads 1,165,905,463 bytes, the whole 1.166 GB store, in 2.2 s; a second call reads 1,165,626,178 bytes again. ledger.picker_runs("reckon") reads 2,319,775,486 bytes, two whole scans of it. A smaller project (imas-efit, 1,538 rows) costs 61 MB and 168 MB respectively.

The mechanism is in reckon/ledger.py and reckon/run_store.py: stored_history calls stored_run_signature whenever the store's change stamp moves, the stamp moves on every write to the store, and the signature query selects LENGTH for every row of the project across the live table and the attached archive. About ten such calls a minute account for the station's measured read volume, which is why the tick is not steady state even though every stream reader now resumes from its cursor.

D-state. Window 2 has a monitor process in state D in four of its six samples — the station itself is one of them, at cxiWaitEventWait — so "no crew monitor process appears in six D-state samples" fails. Window 1 had one of six.

The rows. The pane replay against a recorded hour of today's event log was not run. The cutover it would qualify is withheld on the cost clause, and the RCA's section 11 already recorded that the station carries every row at that earlier attempt. Recording the replay as unmeasured is the honest reading; it is not evidence that the rows fail.

The negative control

The plan asks for the same window with the old followers running, to show the old figures. Both windows above are that arm: all twelve producers and twelve followers are live and inside the measured set. The old figures are visible in it — a follower reads 299–799 MB/min and the producer set 6,469–10,702 MB/min, against the RCA's §2 figures of 100–130 MB/min per follower and up to 612 MB/min per producer. There is no after arm to compare, because the station alone is already 580 times the bound.

What would move it

Retiring the producers does not reach the bound: after that retirement the station alone is still 11.6–13.6 GB/min and 90–105 % of a core. The measurable next step is the store path the census names — the signature read re-scanning 1.166 GB per call on every change, and picker_runs scanning the store twice. Until that reads only what changed, the plan's condition is not met and the producers are what keeps the fleet watched.

Why: the mirror answers for eleven projects, not thirteen

The store-signature change keeps a payload-free mirror in the store, and stored_run_signature answers from it only when the mirror's row count agrees with the project's stored run count; otherwise it falls back to _legacy_run_signature, which measures every payload. A probe of the live store at this revision asks that question through the module's own functions and then times one call per project (signature-probe.txt). The mirror is present and answers for eleven of the thirteen projects, each for between 0.045 MB and 2.09 MB: nova 2,027,933 B, imas-codex 2,093,468 B, power_convertor 1,450,397 B, imas-ambix 1,044,892 B, and the rest under 0.2 MB.

Two projects disagree, and each one's call still scans its whole stored payload. reckon has 21 stored runs against 34 mirror rows marked present, and one call reads 12,681,155 bytes; imas-efit has 1,549 stored runs against 1,548 mirror rows, and one call reads 62,280,070 bytes. The station's tick reads the run signature of every mounted project, so those two calls are the whole-store scans the earlier census measured, and the eleven cheap answers do not reduce the total.

The disagreement is not a stale-cache artefact, and its cause is in the rebuild path: that path deletes runs rows with raw SQL and never writes the mirror's tombstone, while _retire_signature is called only from retire and delete_run. So every rebuild that removes a run leaves a present=1 mirror row behind. reckon's thirteen surplus rows include this plan's own sessions from today, which is why its disagreement grows exactly as fast as the plan is worked. The repair belongs to run_store's rebuild path, outside this node's declared paths, and is reported as out of scope rather than made here.
