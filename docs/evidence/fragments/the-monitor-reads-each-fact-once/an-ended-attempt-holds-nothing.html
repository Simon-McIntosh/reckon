An attempt that has ended holds nothing

What landed. Three facts now govern a hold. _reserved_attempt_ended reads attempt-N-exit.json from the run directory it is handed, rather than resolving the run id out of the reading process's own crew home, and applies the exit-receipt owner's strict rule: a receipt that cannot be decoded, or that names another run, frees nothing. reservation_in_flight asks the same question, so a launch asking about the reservation standing where it is about to write its own is freed by the receipt the hold scan already honoured. promotion.discard refuses a run whose attempt is still in flight, which the pointer's own pid does not show once a resume has taken an attempt, and a promotion's cleanup that keeps a newer attempt says which attempt it kept.

The recorded defect, reproduced at the base revision. A run directory reached by path was built from the recorded shape: reservations for attempts 1, 3 and 4, a worker receipt and an exit receipt for each, attempt 1's reservation naming only its admitting door (a live process that outlives every run it launches), and attempts 3 and 4 naming supervisors that are not running. At 6acc2ef37f the reader resolved a different run directory for the same run id and answered False for attempts 1, 3 and 4 although each receipt was present beside it: _reserved_attempt_ended(1) = False, receipt present: True. The refusal came from reserve_launch_attempt to held_launch_reservation to _reservation_refusal, and its text is the recorded message naming attempt 1: already has attempt 1 in flight. At this head the same run directory frees all three attempts, the resume door takes attempt 5 and the discard proceeds.

A live attempt still holds. The second case keeps attempt 4 without an exit receipt and with a live supervisor the test owns, and keeps exit receipts for attempts 1 and 3, whose supervisors are gone. Both doors refuse, and both name attempt 4 rather than attempt 1, whose attempt recorded its end. The pointer is untouched, which is what a refusal owes a live run.

A promotion keeps what it did not check. The third case records attempt 5 on the pointer after the promotion read it and then runs the cleanup every promotion reaches, _remove_promoted_pointer_or_defer, not the pointer-removal step beneath it: a refusal built inside that step and re-raised by the caller without its subject is a message no coordinator can act on. The pointer stays, and the refusal names attempt 5: changed while promotion ran; attempt 5 was recorded after this promotion read the pointer; its pointer and workspace are preserved; retry promotion. The cleanup's own two refusals carry the naming too, so whichever branch a promotion takes the launch that kept the pointer is named.

Gate. tests/test_an_ended_attempt_holds_nothing.py runs on a temporary crew home, holds the three cases above, and asserts afterwards that the operator's real crew home is untouched.

Negative control, applied verbatim. Declared mutation: restore the reservation check that ignores exit receipts, and the first case is refused naming attempt 1 again. With the receipt checks removed the file reports 2 failed, 1 passed, and the first case reports already has attempt 1 in flight.

The repair round. Two refusals of the same receipt were the defect the review named. The promotion-level cleanup now appends the attempt the newer pointer recorded to both of its own refusals, so the naming survives the wrapper every promotion goes through; and _retired_attempt_ended now reads the newest attempt's exit receipt through _reserved_attempt_ended, the module's one strict reader over an explicit run directory, so the reader that answers "has this attempt ended?" and the guard that refuses a launch cannot answer the same receipt differently. Reverting only the cleanup's naming makes the third case fail with the attempt-free message; the reader deduplication is behaviour-preserving, so the arms stay green across it.
