A steady station tick stops re-reading what did not change

The station classifies every live run on every tick, and each tick re-read the same unchanged facts for the runs that had not moved. A census of one tick against the live crew home at 143 pointers found the attributed reads concentrated in three repeated reads: the committed range a promotion cites, the shared answer file for git's answers about immutable object ids, and the review rubric. Each is an answer about state that changes only when something moves, and each was being fetched as though it changed every tick.

The three defects, reproduced at base

Commit 785fbc2eaf holds a run's committed range against the head identity of its tree, and holds the parsed answer store against the stat identity of the file it came from. Commit 522174404f holds the six rubric prompts the same way. The base revision shows each defect as a count rather than an opinion, in negative-control-base.log:

  • "the second tick ran 6 git subprocesses with nothing moved" — one git log --reverse per live run per tick.
  • "a steady promotion read ran 1 git processes with no head move" — the same read isolated to a single run.
  • "five steady reads opened the same answer file 5 times with nothing written between them" — 848 opens of an 80 MB file in one measured tick.
  • "five steady reads opened the unchanged rubric 5 times" — 740 opens of the same few kilobytes of text in one measured tick.

At the head the same file reports 14 passed; at base it reports 4 failed, 10 passed. The held answers change what is read and not what is reported: one test asserts every tick payload equals the payload the same state produces with the memos cleared, and another asserts every verdict classify_tick returns equals a fresh recovery_watch._watch_snapshot classification for the same pointer and moment.

What one tick still reads

The census instrument wraps io.open, builtins.open, os.open and os.read, counting every byte handed back and attributing it to the first caller frame outside the interpreter and site-packages. Over one tick at 143 pointers it attributed 640 MB across 1,880 paths, with 90% of the bytes falling in 145 of them. The stream reader already reads only appended bytes when it holds an entry, but its parsed cache is bounded at 32 MB while the live population's streams are far larger, so an entry is evicted before the next run asks for it and the file is read whole again. That is a cache budget decision rather than an unchanged read, and it is left to a node that can measure the memory cost. The two other large reads are whole-file JSON decodes, which the plan's earlier work already reduced for the ledger and which remain for the project and metadata stores.

The live window the plan asks for

The plan's bound of under 20 MB/min and under 5% of one core at the default interval is not met and not claimed by this node. On this workstation the station's own kernel accounting puts one tick at 1.96 GB of reads and 63.9 s of CPU over 91 s — the tick itself lasts 91 s, so a station over this home cannot tick once a second, and a per-minute figure computed from a single tick describes the population more than the interval. The figures are recorded rather than smoothed: window-head.log carries the uninstrumented measurement and census-after.log and census-after-table.log the attribution.

Gate

Focused gate: tests/test_the_station_reads_only_what_changed.py, 14 passed at the head against 10 passed and 4 failed at base. Matched suite arms over the whole test tree are running on a compute partition at both revisions, with their logs named in the run manifest; their outcome is recorded when they land.
