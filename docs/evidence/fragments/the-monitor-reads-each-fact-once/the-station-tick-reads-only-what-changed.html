A steady station tick stops re-reading what did not change

The station classifies every live run on every tick, and each tick re-read the same unchanged facts for the runs that had not moved. A census of one tick against the live crew home found the attributed reads concentrated in repeated reads of answers that change only when something moves: the committed range a promotion cites, the shared file of git's answers about immutable object ids, and the review rubric. Each was fetched as though it changed every tick.

The three defects, reproduced at base

Commit 785fbc2eaf holds a run's committed range against the head identity of its tree, and holds the parsed answer store against the stat identity of the file it came from. Commit 522174404f holds the six rubric prompts the same way, and 05e58f1c3ca5135718ab7857e67e05db32f55e5d moves all three onto the repository's one file memo, reckon/file_memo.py, so each shares one bounded cache and hands a caller a copy rather than the stored value. The base revision shows each defect as a count rather than an opinion, in negative-control-base.log:

  • "the second tick ran 6 git subprocesses with nothing moved" — one git log --reverse per live run per tick.
  • "a steady promotion read ran 1 git processes with no head move" — the same read isolated to a single run.
  • "five steady reads opened the unchanged answer store 5 times with nothing written between them" — the answer file re-read against an unchanged identity.
  • "five steady reads opened the unchanged rubric 5 times (expected one, for the first)" — the same few kilobytes of rubric text re-read per classification.

At the head the same file reports 14 passed; at base it reports 4 failed, 10 passed. The held answers change what is read and not what is reported: one test asserts every tick payload equals the payload the same state produces with the memos cleared, and another asserts every verdict classify_tick returns equals a fresh recovery_watch._watch_snapshot classification for the same pointer and moment.

What one tick still reads

The census instrument wraps io.open, builtins.open, os.open and os.read, counting every byte handed back and attributing it to the first caller frame outside the interpreter and site-packages. Run as a compute-partition job (all_debug 1316002) over one tick against 145 live pointers, it attributed 1.24 GB across 17,040 paths, with 90% of the bytes falling in 7,515 of them. The stream reader already reads only appended bytes when it holds an entry, but its parsed cache is bounded at 32 MB while the live population's streams are far larger, so an entry is evicted before the next run asks for it and the file is read whole again: 26 opens of a 69.3 MB stream in one tick. That is a cache budget decision rather than an unchanged read, and it is left to a node that can measure the memory cost.

The answer-store hold is correct where the file is quiet and ineffective where it is not. Over ten seconds of this home the store carried 29 distinct stat identities at an unchanged size, because peers rewrite it whole through os.replace each time one of them adds an answer, and a new inode defeats an identity key even when no byte changed. The station therefore re-parsed it 292 times in one tick, 37.4 MB. Making that hold effective fleet-wide needs an append-only or per-process store rather than a stronger key.

Two repeated whole-file reads sit beside those: _read_dispatch_detail_file opened each of 108 dispatch-detail files 14 times within one tick, and _entries_from_listing opened 15,305 review records 61,668 times, about four opens per record in one tick. Neither is memoised.

The live window the plan asks for

The plan's bound of under 20 MB/min and under 5% of one core at the plan's default interval is not met and not claimed by this node. Measured without any instrumentation, as a compute-partition job (all_debug 1316025) over a 60 s window at 148 live pointers, the station's own kernel accounting reports one tick in 98.003 s at 7.18 GB of rchar, which is 4394.61 MB/min and 106.41 s of CPU, or 108.58% of one core. The instrumented census on the same partition (job 1316002, 145 pointers, one tick in 161.001 s) reads 1.24 GB at the Python level and 82.61% of one core, and the gap between the two is the reads the interpreter makes outside a Python frame.

The tick outlasts the window, so the default one-second interval is not reached at all over this home: a station cannot start its next tick before the previous one ends, and the figure a per-minute rate implies is one long tick divided by its own duration rather than a steady rate. The figures are recorded rather than smoothed, in window-after.log, census-final.log and census-python.json.
