The station re-derives a verdict only when what a verdict depends on moved

What changed. StationStore.classify_tick classifies the crew home's live runs through recovery._watch_snapshot with the station's stored verdicts as its reuse cache, so a run is classified afresh only when recovery_watch._snapshot_reuse_key moved — the pointer, the manifest, the stream, the run directory's own records, the review-store candidates, the tree head, the newest stream a resume writes beside the original, and the promotion ledger row — or when the liveness triple read from the process table moved. Every other run on a tick takes only the quiet-beat reading: its silence recomputed from the stream instant already recorded on the verdict and the clock, through _stall_reading. The verdicts live in a new classifications table keyed by run id, so a restarted station serves them exactly as the producer's in-memory cache does. A run whose pointer names another node is never probed: the liveness gate in recovery_liveness.local_liveness keeps that host's process table out of the reading and carries the stored answer unproven.

The nine counts

  • A tick where nothing moved classifies no run (0 full classifier calls after the first tick).
  • A pointer rewrite classifies exactly that run, once.
  • An appended stream classifies exactly that run, once.
  • A manifest that appears with pointer and stream still classifies exactly that run — the case a key on those two alone misses.
  • A resume writing resume-1.jsonl beside the original stream classifies that run.
  • The process-table probe is called only for the two runs whose launcher_host is this node; the foreign run is never probed.
  • A live worker that exits with every file still reads its new verdict on the next tick, and is classified once.
  • A working run whose silence grows past its window between two ticks reads stalled with no file moving and no classifier call.
  • The same silence explained by a bounded wait in the stream reads waiting with no file moving.
