One pass pays one recognition per live pointer, and every duty reads that answer

The defect. The station evaluates every finished run's duty on every tick, and each duty asks the reflex's own recognition rule — recovery_review_dispatch._review_in_flight, reached through obligations._in_flight_review — which live reviewer stands for the run's head. That rule scans the launched pointers. The station already publishes the pass's pointer snapshot through _VIEW_LIVE_POINTERS and builds the session's in-flight set once, but the duties then asked the recognition rule again for themselves, so one pass over 40 live pointers made 60 recognition calls: two for each of the same 30 deliverables, one from the current-review predicate and one from the refused-delivery reader, and nothing shared between them.

What landed. reckon/crew/obligations.py memoises the in-flight answer beside the pointer snapshot a view or a tick publishes. _sweep_reviews_in_flight makes one walk of the launched pointers and returns the standing review for each run; _reviews_in_flight stores that map in _VIEW_REVIEWS_IN_FLIGHT, keyed on the identity of the snapshot object itself, so every later duty in the same derivation reuses it and a later pass never reads it. A reader outside a pass holds no snapshot, so it clears whatever map it finds and sweeps for itself: the answer never outlives the pointers it described. _standing_review is the single entry point. The two duty sites that asked the question — _current_review_in_flight and _refused_delivered_review — now read it. Both already excluded a queued reviewer from the candidates, and the sweep keeps that exclusion, so a review the lane accepted but has not launched still cannot answer for a head a working review is reading. The refused-delivery reader previously passed the whole live set and now passes the launched-only candidates the sweep builds; for a delivered or refused review the two are the same, because a queued review has no record a working review could stand in for, and it is the candidate set the in-flight predicate already used.

The harness. tests/test_a_duty_pass_reads_reviews_in_flight_once.py builds a temporary crew home and repository holding 30 delivered runs, 10 of them with a live reviewer working on the delivered head and 20 carrying a complete stored review, so the live directory holds 40 pointers. Recording stand-ins wrap the module attributes: _in_flight_review counts recognition calls, _live_pointers counts the walks taken inside the in-flight build, and _review_duty_item records each row's run id, kind and next command. The pass then runs a second time through the base read path, and the test requires the populations object and the recorded rows to be identical and the control's count to be strictly larger, so a comparison with nothing in it cannot pass. A second case removes the reviewer's pointer before the first pass and restores it before the second, and requires the later pass to see the review that started between them.

Gate. Base revision b18903b553, head b32f91adc3. The gate at the head, run with -s so the counts are readable: 4 passed, EXIT=0. It prints head: searches=40 walks=1 live_pointers=40 duties=30, base read path: searches=60 duties=30 and no snapshot: searches=1: one recognition per live pointer inside the pass, exactly one walk for the in-flight set, the same 30 duty rows as the base read path, and one search for a question asked outside any pass. The walk count reads 0 in the base arm because it counts walks taken inside _reviews_in_flight, which does not exist at base; the figure that matters there is the search count.

Negative control. The head's test file against the base obligations.py: 2 failed, 2 passed, EXIT=1. The sharing case fails with a pass made 60 in-flight searches for 40 live pointers: it asks more than once per live pointer, printing the count before the assertion; the outside-a-pass case fails on the base having no _VIEW_REVIEWS_IN_FLIGHT to leave behind. The pass-scoping case passes at base, which is right: it tests that the answer belongs to its pass, and the base has no answer to carry.

Deviation from the plan's declared base count. The section predicts the base makes P walks and P×P comparisons and calls its base search count "of the order of 40×40". The measured count of calls to the recognition rule is 60, not 1,600: two per delivered run, one from each duty site, and each call scans the launched list. What the sharing removes is the repetition of the question, and the comparisons fall with it from 60×40 = 2,400 to 40×40 = 1,600. The quadratic term is not removed: the sweep still calls the recognition rule once per live pointer, and each call is linear in the launched set. That is what this section's own done-when asks for, "at most 40 searches (one per live pointer)", so the section is met, but the 22.9% of the main thread the profile attributed to this path should fall by roughly a third rather than disappear. Returning the map from one pass over the reviewers, instead of one scan per pointer, is a different design and is not claimed here.

Suite. The node's case plus the two files that exercise the same module family. Base arm, which drops the node's cases because they do not exist at base: 55 passed, EXIT=0. After arm: 59 passed, EXIT=0. Added failure ids: none. Both arms run on all_debug through env -u SLURM_JOB_ID -u SLURM_JOBID sbatch, never on the fleet node. The base arm's tree is a real detached worktree at the base revision carrying the node's test file, because tests/test_staged_write_inventory.py reads git metadata in its own root and an archive extraction has none.

Repair: the answer is shared inside a pass, and only there. Review found the first version answered a reader with no pass published by sweeping the whole set. The fleet-state derivation asks the current-review predicate once per live pointer outside any published pass, so that path paid one sweep per question, P sweeps of P pointers where the base revision paid P searches — worse than the code the sharing replaced. Outside a pass the shared answer now returns nothing and the caller answers its own pointer, one walk and one search, which is what the question cost before; the sweep is built only where a snapshot is published. A new case calls the predicate with no snapshot published and requires one search for one pointer: 1 at this head, 40 at the previous head 072c413f9a. The case run against that head's code fails on exactly that assertion — 1 failed, 3 passed, EXIT=1, one question outside a pass made 40 in-flight searches for one pointer.

Repair: the memo ends with the pass. The shared answer was published without a token, so a finished pass's pointer snapshot stayed referenced by the context after the derivation ended. It is now published with a token and reset in a finally, the idiom the pointer snapshot and the classification-input family use, at both publishers: the obligations view, and the station's duty pass. One pass's map lives exactly as long as the snapshot it was keyed on.

Repair: a queued reviewer still answers for no head. A run whose review the lane accepted and has not started is a live pointer and must not read as in flight. A case builds a one-run crew home with exactly that pointer and requires the refused-delivery answer to read as it does through the base read path — both None — and shows the answer has teeth by letting every pointer stand as a candidate, where the same reader names the queued reviewer. The queued pointer also stays a live pointer in the pass: it is asked about, and it answers nothing.

Why the queued case has its own home. Carrying the queued reviewer in the declared fleet made the pass ask the recognition rule 41 times for 40 live pointers. The extra question is not the one this node shares: the queued-wait fields narrow the candidates to the pointers still waiting in the queue, the opposite narrowing the in-flight sweep makes, so its answer cannot come from the shared map and the two must not be merged. The declared fleet therefore keeps its shape — 30 delivered runs, 10 live reviews on their delivered heads, 40 live pointers — and the queued case measures the queued reading on its own.
