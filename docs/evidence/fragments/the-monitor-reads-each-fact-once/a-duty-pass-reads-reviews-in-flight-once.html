One pass pays one recognition per live pointer, and every duty reads that answer

The defect. The station evaluates every finished run's duty on every tick, and each duty asks the reflex's own recognition rule — recovery_review_dispatch._review_in_flight, reached through obligations._in_flight_review — which live reviewer stands for the run's head. That rule scans the launched pointers. The station already publishes the pass's pointer snapshot through _VIEW_LIVE_POINTERS and builds the session's in-flight set once, but the duties then asked the recognition rule again for themselves, so one pass over 40 live pointers made 60 recognition calls: two for each of the same 30 deliverables, one from the current-review predicate and one from the refused-delivery reader, and nothing shared between them.

What landed. reckon/crew/obligations.py memoises the in-flight answer beside the pointer snapshot a view or a tick publishes. _sweep_reviews_in_flight makes one walk of the launched pointers and returns the standing review for each run; _reviews_in_flight stores that map in _VIEW_REVIEWS_IN_FLIGHT, keyed on the identity of the snapshot object itself, so every later duty in the same derivation reuses it and a later pass never reads it. A reader outside a pass holds no snapshot, so it clears whatever map it finds and sweeps for itself: the answer never outlives the pointers it described. _standing_review is the single entry point. The two duty sites that asked the question — _current_review_in_flight and _refused_delivered_review — now read it. Both already excluded a queued reviewer from the candidates, and the sweep keeps that exclusion, so a review the lane accepted but has not launched still cannot answer for a head a working review is reading. The refused-delivery reader previously passed the whole live set and now passes the launched-only candidates the sweep builds; for a delivered or refused review the two are the same, because a queued review has no record a working review could stand in for, and it is the candidate set the in-flight predicate already used.

The harness. tests/test_a_duty_pass_reads_reviews_in_flight_once.py builds a temporary crew home and repository holding 30 delivered runs, 10 of them with a live reviewer working on the delivered head and 20 carrying a complete stored review, so the live directory holds 40 pointers. Recording stand-ins wrap the module attributes: _in_flight_review counts recognition calls, _live_pointers counts the walks taken inside the in-flight build, and _review_duty_item records each row's run id, kind and next command. The pass then runs a second time through the base read path, and the test requires the populations object and the recorded rows to be identical and the control's count to be strictly larger, so a comparison with nothing in it cannot pass. A second case removes the reviewer's pointer before the first pass and restores it before the second, and requires the later pass to see the review that started between them.

Negative control. The head's test file against the base obligations.py: 1 failed, 1 passed, EXIT=1, id test_a_duty_pass_reads_reviews_in_flight_once, with a pass made 60 in-flight searches for 40 live pointers: it asks more than once per live pointer and the count printed before the assertion. The second case passes at base, which is right: it tests that the answer is scoped to its pass, and the base has no answer to carry.

Deviation from the plan's declared base count. The section predicts the base makes P walks and P×P comparisons and calls its base search count "of the order of 40×40". The measured count of calls to the recognition rule is 60, not 1,600: two per delivered run, one from each duty site, and each call scans the launched list. What the sharing removes is the repetition of the question, and the comparisons fall with it from 60×40 = 2,400 to 40×40 = 1,600. The quadratic term is not removed: the sweep still calls the recognition rule once per live pointer, and each call is linear in the launched set. That is what this section's own done-when asks for, "at most 40 searches (one per live pointer)", so the section is met, but the 22.9% of the main thread the profile attributed to this path should fall by roughly a third rather than disappear. Returning the map from one pass over the reviewers, instead of one scan per pointer, is a different design and is not claimed here.
