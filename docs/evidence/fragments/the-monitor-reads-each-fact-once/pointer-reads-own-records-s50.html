Classification reads one run's names, not the store's

What landed. The staging store's index document now carries a per-run name map, run_names, beside its entries: for each reviewed run, the sorted record names that run holds, including its revision copies. The three paths that already rewrite the document maintain it -- the writer's _index_stored_record, which moves a name from one run's list to another when a record is rewritten under a different run, and reconcile_foreign_write, which also drops a removed record's name from the run that held it. The per-run map is rebuilt from the entries whenever the document is rebuilt, so a store that predates it gains it at the first rebuild that the code stamp already invalidates. A new accessor, review_run_record_names(directory, run_id), answers a classification from that map. A store that keeps no index -- the committed reviews tree, or any directory the writer does not own -- answers None, which keeps the previous listing path. recovery_memo._review_input_identities asks the accessor first: when it answers, the run's own record's existence and its revision copies come from the answer, and no listing of the store happens at all; when it answers None, the previous listing path runs unchanged. The directory key that classifies a single staging store's pricing no longer varies with the document: on the indexed path it is a constant, so another run's write to the same store does not force this run's classification to re-read. That matters more than it sounds: the stored document version changes on every write, and keying the directory on it allocated a fresh classification for every live run, which the sibling case tests/test_a_tick_reads_the_review_store_once.py observes and rejects.

What a pass cost. The producer ran at about 98% CPU in fnmatchcase under _store_paths, called from _own_review_record_exists for each pointer, and separately read the store's whole stat view through _tick_store to price the tick. Both were costs of the store's size, paid once per pointer. After the change a pointer's classification examines the record names that pointer's run holds: ten, for a run with a primary record and nine revision copies, whatever the store holds.

The two counts. The same 200 pointers were classified against two indexed stores, one of 2,000 records and one of 20,000. At the head revision each store's pass examined 2,000 names -- 2,000 from the per-run map, 0 from a whole-store stat view, 0 from a listing -- so the larger store costs exactly what the smaller one does, and 2,000 is exactly the number of records belonging to the 200 classified runs. The negative control is the declared string matching the whole store's names per pointer fails the equal-cost case: at the base revision the same case's larger store examined 12,000,000 names against the smaller store's 1,200,000, whole-store names every one of them, which is the declared factor of ten and satisfies the "at least ten times" the section requires.

Gate. tests/test_a_pointer_reads_only_its_runs_records.py fails the equal-cost case if the two counts differ or if either exceeds the 2,000 names the classified runs hold. Before believing that absence, the case proves its instrument can see a whole-store read: a control pass over the smaller store's own stat view must report exactly the store's 2,000 names, so a counting stand-in that silently stops counting fails here rather than passing the equal-cost assertion by measuring nothing. Both arms run against stores the fixture indexed first, which is the state a running store is in.
