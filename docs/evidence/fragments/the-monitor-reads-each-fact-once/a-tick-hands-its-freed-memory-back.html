A tick hands its freed memory back

What landed. Station.tick now runs the pass and then calls release_freed_memory(), which asks the C library for malloc_trim(0) where that symbol exists. The release is in a finally around the pass, so a tick that raises hands its freed arenas back as a tick that returns does, and it runs after the pass's own work rather than inside it. The entry point is resolved once and cached, because the tick asks for the release every pass and the absence of the symbol never changes. A platform whose C library does not offer it skips the call and the tick runs unchanged.

Why. The census of §62 found the station does not leak: across six traced ticks its RSS rose 856 MB to 4,623 MB while the memory tracemalloc still held after each tick rose only 112 MB to 240 MB. The pass frees 0.2 to 3.3 GB and the allocator keeps the emptied arenas, so between ticks RSS tracked the largest decode any tick had made — 6.7 to 10.5 GB on the fleet node, against a 96 GB cgroup shared by every session, which the kernel OOM-killed ten times in an hour.

Gate. tests/test_a_tick_hands_its_freed_memory_back.py builds a station over a temporary crew home and a temporary store, replaces its tick body with a stand-in, and runs three ticks. The release is a recorder, and the case asserts the event order is tick then release for each of the three, so the release is observed after the stand-in's own work rather than instead of it. A second case raises from the stand-in and asserts the release still follows and the exception still reaches the caller. A third case resolves no entry point, as a C library without the symbol does, and asserts the tick returns its own result and no release is recorded.

Census arms. Both arms ran six ticks each as separate all_debug jobs, over the live crew home read through an overlay and a temporary store, with tracemalloc's ten-frame peak and RSS read after every tick. The base arm (2780ddad20) logs RSS after ticks 1 to 6 as 580, 636, 705, 739, 747, 752 MB against tracemalloc peaks of 267, 298, 332, 345, 340, 323 MB, so it retained 313 to 429 MB beyond each tick's peak and its RSS rose with every tick. The head arm (3598481d8d) logs RSS as 440, 502, 475, 480, 491, 497 MB against peaks of 255, 293, 302, 292, 257, 258 MB: its RSS stays between 173 and 240 MB above that tick's own peak — inside the 1.5 GB bound at every tick — and, unlike base's, it stops rising.

The halving bound is not met on this population. The done-when asks that head's RSS after the sixth tick be at most half of base's RSS after its sixth tick. Head reads 497 MB against base's 752 MB, a ratio of 0.66, so the bound fails as written. The release does bound the ratchet — head's sixth-tick RSS is 252 MB below base's and head's own ticks plateau where base's climb — but it does not halve a tick whose alive set is 170 MB of traced memory in a 440 MB process, and this fleet's six ticks peaked at 255 to 302 MB rather than the 1.6 to 3.3 GB peaks the section was written against. Both figures are the logs' own rss_bytes and tracemalloc_peak_bytes lines.

The bound is unmeetable on this population, not merely missed. Head's lowest RSS after any tick is 440,213,504 bytes, read after tick 1 — a tick that already released — and half of base's sixth-tick RSS is 375,844,864 bytes. A release returns only pages a pass has already freed; it cannot free the roughly 440 MB the process is still holding, so no implementation of this section's deliverable could read 376 MB on this fleet. The bound was written against the census peaks of 1.6 to 3.3 GB that motivated the section; today's six ticks peaked at 255 to 302 MB, below every one of them, which puts the whole bound below head's floor. What the change does deliver is visible in the shape: base's RSS climbs at every tick, 580 to 752 MB, while head's stops rising after tick 2 and stays 173 to 240 MB above its own peaks.
