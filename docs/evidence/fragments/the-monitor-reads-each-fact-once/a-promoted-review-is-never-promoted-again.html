A recorded promotion is retired by the sweep, never requested again

What landed. Promotion now records its own success on the live pointer it could not retire. reckon/crew/promotion.py's _remove_promoted_pointer_or_defer reads the record as a review, and when the recorded worker is still alive it writes promoted: true onto the pointer and returns without removing it. It does the same when the pointer has moved under the promotion and its pending_landing attempt no longer matches, which is the shape the incident actually had: a review worker writes its own pointer, so a live worker's next phase lands between the promotion's read and its removal. The acceptance sweep then retires that marked pointer on the first pass whose recorded process is gone, and files nothing. Non-review runs keep the existing pending_landing_repair behaviour untouched.

What it prevents. A review run's deliverable is the record it writes, so its manifest reads complete before its worker exits. crew complete --no-commit could then promote it — writing the ledger row and committing the review — while the worker was still running, and return ok with pointer_removed: false. Nothing on disk said the run was promoted, so the sweep read an unpromoted review with a stored record and filed a review-self promotion request for a run the ledger already held. That request failed on every pass, wrote a station-sweep-run-failure line each time, and raised a sweep-failed obligation that only a hand discard of the pointer lifted.

Why a mark rather than a refusal. Refusing promotion of a live review worker would block the coordinator's own crew complete, which is a legitimate operation: the review is finished in every sense that matters, and the worker has nothing left but its exit. The mark is the smallest record that says so, and it is set by the only code that knows a promotion happened. The sweep's retirement reads that mark, not the phase, so an attempt in flight — a resume, a redispatch — keeps its pointer: the pointer is removed only when no recorded process is alive.

Gate. tests/test_a_promoted_review_is_never_promoted_again.py builds a temporary repository and crew home. A live child process holds the review run's worker pid and rewrites its own pointer at the moment promotion commits its stores, so the move is a live process's, as in the incident. The case completes the run with --no-commit, asserts the ledger row and promoted: true on the surviving pointer, then kills the child and runs dispatch_awaiting_reviews three times, asserting the pointer is gone, no promotion request was filed, and the run appears in neither the report's failed nor its review_self_refused list. A second case delivers an unmarked review with no worker and asserts it still promotes itself, so the mark gates retirement only.

The two arms. Both ran on the all_debug partition, each log opening with its revision, its cwd and the literal command and ending in its own EXIT=. The base arm (5617397173) reports 1 failed, 56 passed — the one failure is this node's case, at assert pointer.get("promoted") is True reading None, which is the declared negative control: at the base revision the pointer survives the promotion unmarked and the sweep then files for a run the ledger already holds. The after arm (96c8881f19) reports 57 passed, EXIT=0. No other test fails in either arm, and the two files that import the changed modules — tests/test_staged_write_inventory.py and tests/test_every_shared_home_lock_holds_across_nodes.py — pass in both.

One owner for the pointer. The retirement this node added first carried its own lock, unlink and absent-pointer decisions, beside the landing owner those decisions belong to, and it wrote its mark itself. Both are the landing owner's now: pending_landing.retire_pointer_if is the one compare-under-lock-and-retire, and pending_landing.mark_promoted_pointer writes the mark and writes it through the same _write_mark as the landing mark. The sweep hands its predicate — marked, and no recorded process alive — to the owner rather than looping the lock itself, so a pointer has one writer and one remover.
