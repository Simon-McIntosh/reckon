A classification reads only new stream lines

The defect. Every classification of a live run decoded that run's newest stream from its first byte, although a stream only grows by appending. The decode census at s65's head put 71.6 MB of a 93.5 MB tick in _stream_holds_assistant_record and 21.9 MB in _tool_call_in_line, and two smaller passes decoded every live pointer's fields once a tick, 5.2 MB each, in Station._tick and StationStore.classify_tick.

What landed. A scan record per stream holds what a scan learned — whether an assistant record appeared, the last tool call, the last record type — beside the byte offset each answer stands at, keyed by the stream's inode. A later pass decodes only the bytes appended past that offset; a stream whose inode moved or that is now shorter than the bytes a scan read through is scanned again from its start. A scan stops at the last newline, so a record still being written is decoded once the bytes that complete it land.

The store now keeps each stored document decoded beside the text it was decoded from — a pointer's fields, a run's stored verdict, a project's fleet image — and compares the text before decoding, so a tick decodes only what it or another writer moved. A document the tick itself wrote is recorded already decoded, so a pass never decodes its own output back.

Thirty runs, classified twice

tests/test_a_classification_reads_only_new_stream_lines.py builds 30 runs with 2,000 lines each on a temporary crew home and classifies every one twice, counting json.loads calls made from recovery_wait. The first pass makes 60,000 decodes; the second makes 0 and returns the same verdicts. The first pass's count is asserted before the second pass's zero is reported, so the instrument is shown seeing something known present before an absence is claimed.

Appending one assistant line to one stream makes the next pass decode exactly that record — the decoded-text set equals the appended record line — and flips that run's reading from resume to observe, with the other 29 runs' verdicts unchanged. Truncating a stream to 25 lines makes the next pass decode the whole of the new content, first line included, which is the rescan from the start. A stream whose last line is unterminated keeps the scan's offset at its last newline; completing that record makes the next pass decode exactly it and flips the run.

The store's own columns and a quiet tick

The same file ingests a codex pointer through the store's ingest path and asserts the stored backend and dialect columns — a row the backfill path covered and no test did.

Two station ticks at one moment over an unchanged store: the second makes 0 json.loads calls from reckon.crew.station and reckon.crew.station_store. Before the store kept a document decoded, Station._tick decoded every pointer's fields (reckon.crew.station: 1) and classify_tick's pointer pass, the stored verdict and the fleet image decoded theirs (reckon.crew.station_store: 2 on the first tick, 4 on the second, as the row and the image the first tick wrote were read back and decoded).

The negative control

With _stream_scan made never to reuse a record — whole-stream scans restored — the same file fails 3 of 5 cases and the first reports 60,000 decodes on the second pass. The log is logs/negative-control-restore-whole-stream-scans.log under the run directory, ending EXIT=1.
