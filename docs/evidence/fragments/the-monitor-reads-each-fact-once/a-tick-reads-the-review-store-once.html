A run's review is re-read only when something the review is read from has moved

The defect. A working run appends to its own stream every tick, and the stream is one of the inputs of the run's classification. The stored review was served only through that wider key, so the stream moving was enough to make the classification stale, and the tick then read every live run's review again: on the base revision, a second tick over 40 live pointers whose only change was one line appended to each worker's stream called read_review 40 times — once per run, for records that had not moved. The review's own inputs are the store's files for the run, the reviewed run's manifest.md and the gate logs that manifest names, and the head the record describes; none of them is the stream.

What landed. reckon/crew/recovery_memo.py gains _review_read_inputs, the identity of exactly those inputs, memoised per run and per tick, and _read_review_once, which keeps one answer per run per selection (the record describing a named head, or the newest record) beside the digest of the inputs it was read against and asks again only when that digest moves. The digest covers the store's per-file identities taken from the tick's single enumeration, so an in-place rewrite, an atomic replacement, a new copy filed under another run's id, a reviewed manifest rewritten and a named gate log rewritten each move it. Answers are copied into and out of the cache, because a caller normalises or annotates the record it was handed and a cache that served those edits onward would report a review nobody stored; the cache is bounded at 1024 entries for a producer that sees every run the fleet ever had. reckon/crew/recovery_review_subject.py routes select_review_for_head and newest_review_for_headless_run through it, so the classifier, promotion and the review reflex all take the same answer.

One computation of the inputs per tick. The classification key already carried the review's inputs; it now takes them from _review_read_inputs, so the tick's change token, the publish's reuse key and the review answer share one computation per run rather than three. That set is read from the tick's own snapshot of the store, one enumeration per store directory per tick, so no run re-stats the store's files.

The harness. tests/test_a_tick_reads_the_review_store_once.py now builds its own producer tick rather than importing another test module's fixture, and its six existing cases were erroring at base for that reason alone: the shared fixture patched an attribute recovery_watch no longer defines. The file patches every name that binds read_review, os.scandir, os.stat and Path.stat across the loaded modules, proves the counters see a stat it makes itself before measuring, and then drives two ticks over 40 live pointers with review records in the store. A seventh case is the sharp one: between the two ticks it appends a line to every worker's stream, and the second tick must still call read_review zero times while making one enumeration of the store.
