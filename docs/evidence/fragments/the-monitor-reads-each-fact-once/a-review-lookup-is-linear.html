A review lookup is linear

The defect. The station classifies every live pointer once a tick, and each delivered run that owes a review asks the reflex's own recognition which live reviewer stands for the run's head. That recognition walked the live pointers and read each candidate's reviewed run directory inside the walk — _review_pointer_rubric through runs.run_dir and Path.exists, and _review_subject through the same read again: two GPFS stats and a config-home check per candidate, for a reviewed run that is the same on every iteration of one row. A tick over P pointers therefore cost on the order of P² filesystem checks, which is what the station's first tick after the 06:00Z restart on 16 November never finished.

What landed. A snapshot index (_ReviewInFlightIndex) holds, for one read of the live pointers, the answers that depend on a pointer or on a reviewed run alone: the run's directory, the directory it keeps its review records in, the record names each pointer declares, the record name each rubric composes for a reviewed head, and the subject a review pointer stands for. _review_pointer_rubric and _review_in_flight read the walk through it, so every classified run pays each of those reads at most once for the whole snapshot rather than once per candidate. The index is keyed on the identity of the sequence the caller passed and holds that sequence, so a later read's list cannot answer from an earlier reading; a caller that passes no snapshot — every reader outside a tick — gets an index for that one call, and outside a tick every answer is derived from the pointers the call held.

Two hundred pointers, classified once

tests/test_a_review_lookup_is_linear.py builds a temporary crew home of 160 delivered implement runs, each with a manifest reporting completion and no review attached, so each reaches the scoring branch of classify_pointer, and 40 live reviews declaring the head-keyed record path of one of those runs: 200 live pointers. A recording stand-in counts every Path.exists and Path.is_dir call made under the crew home while the lookup looks a review in flight, and every pointer is classified once.

At head bc54586305 the pass makes 400 checks for 200 live pointers — 2.00 each, against a budget of five per pointer. Counting every existence check the whole classification pass made at the base revision, the same fixture cost 73,601 checks — 368 per pointer — so the stand-in is shown seeing a population whose cost is known to be large before a small number is claimed for it, and the negative control below applies this case's own instrument to the base lookup. The review the lookup matches to each of the 160 delivered runs is compared, run by run, with a candidate-at-a-time walk of the base algorithm: the pairing is identical, so answering those reads once changes how often the question is asked, never the answer.

A doubled fleet at doubled cost

The second case builds the same fixture at twice the size — 320 delivered runs and 80 reviews, 400 live pointers — in a home of its own, and asserts the sweep's count at most doubles: it makes 800 checks for 400 pointers — 2.00 each again, exactly double the 400 the 200-pointer fleet took. A count quadratic in the pointers would have quadrupled.

The negative control

With the base lookup restored — each candidate's reviewed run directory read again inside the sweep, and each candidate's subject read again per row — the same file fails both cases: the first makes 60,960 checks for 200 live pointers (304.80 each) and the second 243,520 for 400 (608.80 each), four times the smaller fleet's count rather than twice it. The log is logs/negative-control.log under the run directory, ending EXIT=1.
