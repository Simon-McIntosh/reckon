An admit pass attributes its reads to the store they came from

What changed. A pass reading carried a total and a per-reader count and duration, so a pass that re-read the review store and one that read a handful of pointers reported the same volume. Each pass now runs inside one accounting scope and publishes reads_by_source on the same reading: the bytes it read under each store it reads — the live and queued pointers, the run store, the ledger, the review store and the plan documents — plus attributed_bytes, process_bytes and unattributed_bytes. A source the accounting misses therefore shows up as a gap rather than vanishing from the total.

Files are charged the bytes they were decoded from. A text read is charged its encoded length, not its character count, through the encoding the opened file carries, so a document of multibyte characters is not reported at a fraction of what the process read. The scope patches builtins.open, io.open and io.open_code, because pathlib reaches the interpreter's opener by module attribute and a patch of builtins alone leaves every read_text unaccounted.

The review store is charged by its sharded layout. Records sit one directory below the store root, one shard per project, so a rule that matched the store root alone charged nothing on the fleet: the first sample reported the store as zero bytes while it holds 178 MB. The rule now matches the sharded prefix, and a fixture store in that layout is a test case.

The process figure comes from the kernel, not the accounting, and the remainder is named. process_bytes is rchar read from /proc/self/io; unattributed_bytes is the difference between it and the attributed sum. The run store is a SQLite database read through C pages, which no Python-level accounting sees, so its bytes land in the remainder instead of being charged to a source the bytes did not come from.

Two stores are the whole optimisation surface: the run store's pages, which the accounting cannot see, are the only large term neither source accounts for.

Gate. The baseline arm ran at revision 08338737e698 — the three-file command's two pre-existing files only, since the node's own test did not exist there — and reported 58 passed in 36.28s. The after arm ran at revision e1b0a89cc6 over the node's test plus those two and reported 63 passed in 37.64s; the scoped gate at the same revision reported 63 passed in 37.52s. Both arms and the gate exited zero, so the node's five cases add no failure to the base.

The check that the sum holds. A pass over a fixture crew home writes a reading whose attributed sum is within five percent of what the process read, taken from its own record. Removing one source from the product's source rules — the declared negative control — makes the sum shortfall exceed the band: 16.7 % at the fixture, against a five-percent band. The control mutates service.admit_read_sources and the account's own record path, so it removes the wiring, not a test hook.
