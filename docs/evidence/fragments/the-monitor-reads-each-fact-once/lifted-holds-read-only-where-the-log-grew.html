Lifted holds are read only where the log grew

The defect. resumption._lifted_holds rebuilt the sweep's lift set from the project's whole append-only recovery log on every tick, decoding every line to reach an answer the previous sweep already held. On reckon's 41.6 MB, 6,747-line record that put 30% of one sweep thread in the function and 19% in json.loads inside it.

What landed. The read is incremental: each log's byte offset through the last whole line and the lift set those lines produced are kept, and a later read decodes only the bytes appended past that offset. A log replaced (its inode moved) or shortened below what a read reached is read from the start. The reading itself is not new code: recovery_wait.appended_lines is the function the stream readers already use, and _stream_scan already owns both the inode and the not-shorter test. The scan record gained the appended-record offset it covers, the store is guarded by one lock because a sweep and a classification can advance the same record at once, and the read reports the offset it began at — a start below the offset a caller recorded is how the caller learns the file on disk is no longer the file it read.

Five thousand lines, then none, then three

tests/test_lifted_holds_read_only_what_was_appended.py writes 5,000 recovery-report lines on a temporary crew home, 715 of them marked dry_run, and counts decodes through a recording stand-in for json.loads in resumption. The first call decodes 5,000 lines and returns a set equal to a whole-file decode of the same log; the second call on the unchanged log decodes 0; appending three lines makes the next call decode exactly 3 and return the enlarged whole-file set; replacing the log with a shorter file makes the next call decode 4 of 4 lines, from the start. The whole-file count is asserted before the zero is reported, so the instrument is shown seeing something present before an absence is claimed. A 12-line log staged at a new inode is decoded in full, so a replacement is not mistaken for an append.

A record landing mid-append

The same file writes half of a report line with no newline after 20 complete lines. The call decodes the 20 complete lines and the scan's offset is asserted to stand at the last newline rather than at the file's end, so the fragment waits; appending the completing bytes and the newline makes the next call decode exactly 1 line, which is that record, and the set gains its pair.

Each mutation of the check was applied and its run kept. With the base revision's whole-file read restored, the second call decodes 5,000 again and the incremental case fails (assert 5000 == 0). With the whole-line clamp removed from _appended_lines — its last segment kept as a line — the fragment case fails (assert 21 == 20), because the half-written record is handed to the decoder and consumed.
