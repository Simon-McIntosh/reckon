One document beside the records, advanced by whoever writes one

What landed. reckon/crew/review_records.py owns a writer-maintained index document at <store>/.review-index/index.json, with its lock beside it (lock, an fcntl.flock on the shared home). Per record the document holds the SHA-256 of the bytes that landed; per run a digest over that run's (name, hash) pairs; per store a monotonic version, a bounded change log of (version, run id) and the store directory's mtime as of the last indexed write. record_written is the store's one writer path: it writes the record atomically, hashes what landed and advances the entry, the run digest, the version and the log in one locked write. review._write_record — the writer every run review and disposition already shared — and plan_review.store_plan_review both route through it.

One index, not two. Section 35's sqlite review-lookup projection is gone: open_run_index.review_written, review_rebuilt and the sqlite reader behind review_paths are removed, so nothing on the station's main thread opens a per-store sqlite file there any more. review_paths survives as a pointer-only selection for a directory that keeps no document — the committed reviews tree — and derives nothing from a store listing.

Why the old index was not enough. The prior index was keyed on the store directory's stat identity, so a record written for any run moved it. The next reader then listed the store and stat'ed every record it named — 7,563 records and 5.6 s of GPFS on the fleet node, paid once per duty item, per run and per session.

What a reader does now. A run's records (_store_indexes), the non-tick store view (_store_paths), a changed-run query since a version, the station's misfiled-review candidate search and stored_record all answer from the document: no listing of the store, and no stat of any record the reader does not open. Per-record revalidation is not run for an indexed entry — a known writer advances the version, and any other write moves the store directory the document is probed against, which is one stat per store per refresh. A record written outside the writer path is found by reconcile_foreign_write, which compares that directory mtime with the one the index recorded and then lists names only: a name the index lacks is hashed and entered, a name the listing no longer holds is dropped, and every record already indexed is left alone. A missing, unreadable or foreign-stamped document is rebuilt from one listing and one hash of each record.

Why the document is in a subdirectory. The document is rewritten on every indexed write. A document beside the records would therefore move the store directory's own mtime after the writer had recorded it, so every read would find the store moved and no read could settle. In .review-index/ its writes move only that subdirectory, and the record listings skip it by name.

Gate. tests/test_the_review_store_is_indexed_by_its_writers.py builds a temporary crew home holding 500 records across 50 runs and shows seven things: a record stored through store_review is returned by a run-id lookup with no listing; reading every run's records after that store, inside review_store_tick, lists nothing and stats no record; the change log since the prior version names exactly the run written, and that run's digest moves while no other run's does; a record written directly to the directory is found by one listing of names and no stat of an existing record; a deleted document is rebuilt from one listing; a record stored by a second process is returned to the first process's next lookup; and the station's own two reads — recovery_memo._misfiled_review_candidates and review_records.stored_record — list nothing and stat no record outside the one run they select.

Negative control. Running that test against the pre-change head turns the read-pass case red, naming the store scan the case exists to catch.

What the change supersedes. Three cases in tests/test_a_persisted_review_index_never_claims_more_than_it_read.py measure the accounting of the per-file cache that a staging store no longer reads: they hook _persist_store_entries, which the document path does not call, and count _store_directory_identity calls the document path does not make. The behaviour their substance asserts — a cold reader finds a record filed before the index was written — still holds, because that write goes through record_written. The cases need retiring with the cache they measure; that file is outside this node's write paths.
