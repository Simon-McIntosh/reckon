A foreign run is freed by its allocation ending

The defect. The foreign-host guard freed a run only when the scheduler showed its node holding no job for this user, in any state. Every debug job lands on these nodes, so one peer job kept the run unresumable for as long as it ran. On 16 November at 19:56Z the repair resume of r-20261115T224050940768-a-stream-is-decoded-once-per-byte was refused on an answer listing 1319675|CANCELLED, 1320441|COMPLETED and 1320449|RUNNING: neither terminal job could hold a worker, and the running job began about sixteen hours after that worker launched.

What landed. The reading. recovery_liveness.launcher_host_is_gone now reads the node's job answer for the job that can hold the worker. A job is live only while its state is one process_liveness._JOB_LIVE_STATES owns as in flight, so any other readable state means it left the queue whatever the scheduler calls it — there is no enumerated terminal list. Where the record names its launcher job, that job's own answer decides and the node's other jobs are beside the point. Where it names none, every live job is dismissed only by a start time after the attempt's launched_at, which is why the node's job query (squeue --format %i|%T|%S, built inline) now selects the start time as well. A failed query, an unparsed line, an unreadable start time, a launcher job the answer does not name, or a live job that started at or before the launch all keep liveness unknown. The observation file now carries relied_on — the launcher job and the state it answered, or the launch instant and the live jobs that started after it — so the answer that licensed recovery can be checked after the fact.

What landed. The record. A CLI launch writes the allocation it runs inside on its live pointer as launcher_job_id, beside launcher_host, read from FLEET_JOB_ID (published by fleet_supervisor) or else SLURM_JOB_ID. The write hangs off dispatch_launch._prepare_attempt_records, which every launch of an attempt already runs before its supervisor starts. An in-harness launch records none: an in-harness run executes inside whatever holds its orchestrator, so that allocation is not the run's own. A placed run records none either — it already answers through the job_id its placement writes, and a second id would name a job it does not run in.

The five cases

tests/test_a_foreign_run_is_freed_by_its_allocation_ending.py replaces the scheduler query with a recording stand-in on a temporary crew home, over a pointer whose launcher_host is a foreign machine, and asserts each stated case against a scripted answer: (a) 1319675|CANCELLED and, in the same case, 1320449|RUNNING after the launch reads gone; (a) the launcher job answered BOOT_FAIL reads gone; (b) a launcher job answered RUNNING reads unknown; (c) no launcher job with one terminal job and one running job started after launched_at reads gone; (d) the same with the running job started before launched_at reads unknown; (e) a failed query reads unknown, as does an unknown node, which is asserted not to have asked for the node's jobs at all. The test also asserts that a CLI launch made with SLURM_JOB_ID set records it as launcher_job_id, that FLEET_JOB_ID outranks an inherited SLURM_JOB_ID, and that an in-harness launch, a placed run and a launch made outside any allocation record none.

Two conditions the adjacent tests added. A node answer that lists no job in flight frees the run without needing a launch instant to dismiss any of them — the empty queue the guard always accepted still proves the allocation cannot hold the worker, and a pointer that predates launched_at is no longer refused. And the field is written only on a pointer whose launcher_host is this host: the job id describes the allocation this attempt runs inside, so stamping this host's allocation on a pointer naming another machine would name an allocation the run never ran in. A record naming a job its node's answer does not carry stays unknown, which is the direction a live worker is safe in.

Arms. The gate and both suite arms ran as all_debug partition jobs submitted with env -u SLURM_JOB_ID -u SLURM_JOBID sbatch, never on the fleet node. The gate at head 9c1a9dafa8 (job 1320576) reads 12 passed in 1.58s, EXIT=0; the matched suite arms read 58 passed at the base content (job 1320577) and 58 passed at head over the two test files the base tree carries, and the head arm over all three reads 70 passed (job 1320579) — the added test accounts for the twelve-case difference.

Negative control. The same test file against the base content of d72a7d9b251b (job 1320575) fails six cases, EXIT=1, including test_a_foreign_run_is_freed_by_its_allocation_ending case (a) — test_a_launcher_job_that_left_the_queue_frees_the_run and ..._failed_to_boot_frees_the_run — and case (c), test_a_record_with_no_launcher_job_is_freed_by_a_later_start: each reads assert False is True, because the base guard reports any job on the node as a reason to keep liveness unknown. The two CLI-record cases fail on the absent field with KeyError: 'launcher_job_id'.
