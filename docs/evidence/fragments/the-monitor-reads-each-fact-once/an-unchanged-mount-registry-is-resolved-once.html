The registry is parsed and its paths resolved once per stat identity

What landed. reckon.flight.mounted_project_docs now reads the registry through file_memo.memoized("mounts_registry", mounts_file, read), so the JSON parse and the Path.resolve on every mount entry happen once for as long as the file's stat identity holds. An unchanged mounts.json costs one os.stat per ask; a rewritten one moves that identity and is parsed again on the next call. The fallbacks are unchanged: an absent registry returns no mounts, and invalid data still fails closed naming the offending entry. Every caller of the function inherits the reuse, which matters because each project's docs root and its flight layer path are reached through it.

What it cost. The station tick resolves one project per reviewed plan, and flight.resolve reached the registry through project_config_path → _project_docs_root → mounted_project_docs on every call. The live profile that motivated the section put 17.7 per cent of the station tick's main thread under flight.resolve, of which 12.8 per cent is that chain — a parse of the whole registry and a realpath, isdir and exists per mount on GPFS, for a registry that does not change between asks.

Gate. tests/test_an_unchanged_mount_registry_is_resolved_once.py writes a three-project registry into a temporary configuration home and calls flight.resolve 50 times for each project. Recording stand-ins count reads of the registry file itself and Path.resolve calls whose path is one of the registry's own entries, so a stand-in that never fired reads zero rather than passing as reuse. Every resolution is also compared with the same project resolved directly by the docs root the registry names, so a memo that served a stale path would fail on the value and not only on the count.

A rewritten registry is read again. The second case rewrites the file to drop one project and asserts the next call parses it afresh — two reads, five resolves — then resolves the dropped project through the same state-root fallback it had at base, and compares that result with the same layer resolved directly by the fallback path.

The two counts. At the head revision 150 resolutions read the registry 1 time and resolve 3 entries. At the base revision (7997d712f6) the same case reads it 150 times, which is the declared negative control: one read per call, three resolves per read.

Matched arms. Two arms ran as all_debug partition jobs, each in a scratch extraction of its own revision, and each log opens with its revision and literal command and ends in its own EXIT=. The base arm (7997d712f6) runs the two suite files the brief names: 55 passed, EXIT=0. The after arm (da4afea0ff) runs those two plus this node's case: 57 passed, EXIT=0. The extra two passes are this node's case; no arm reports a FAILED id. The scratch tree carries its own one-commit repository over the extracted files, because test_staged_write_inventory reads the tree through git ls-tree HEAD and an extraction has no metadata to answer with.
