A no-record refusal costs one record search and one log line, not one per sweep

The defect. A review run that ended without storing its record is refused by review_self_state with "the review run stored no readable record … for the run it read". The refusal is not durable: the sweep re-derived it on every pass, paying the record search again for a run nothing about which had changed, and a run left in that state wrote a station-sweep-run-failure line per sweep — 141 lines for one nova plan review out of 19,920 on 14 November. On the base revision, three sweeps over one unmoved ended review called _delivered_review_record six times, and three station sweeps wrote two lines naming the run.

What landed. reckon/crew/recovery_review_acceptance.py derives an identity for a review run from its pointer's stat signature and its run directory's stat signature, and memoises the delivered-record read — and the plan-report read beside it, for a plan review's record — through reckon.file_memo.memoized_key under that identity. The first pass pays for the search; every later pass at the same identity reads what it found. Moving either the pointer or the run directory changes the identity, so the next sweep looks again. The gate described in the record is therefore the one the plan names: the pair that can move, not the run's inputs.

The station's line. A refusal also reaches the station through the durable review-self receipt the drain leaves, which every later sweep reads again. A refusal whose receipt is refused and whose error names the same reason this pass reads is put in the sweep report only the first time that identity is reported, so the station writes one line per refusal rather than one per pass. A moved run reads a new identity and is reported again. The refusal text itself is unchanged: the test compares it with the base revision's literal rather than with a value the new code builds.

The harness. tests/test_a_refused_review_is_retried_only_when_it_moves.py builds a temporary crew home and repository holding one ended review run with no stored record, counts _delivered_review_record through a recording stand-in over three dispatch_awaiting_reviews passes, then touches the run directory and counts again. It prints the failure lines the station writes over three SweepBeat sweeps with the promotion queue drained between them, and asserts the first sweep's review_self_refused entry is non-empty and carries the base revision's reason. The fixture asserts the workstation's real crew pointer directory is untouched afterwards.

Gate. Base revision 1e767410b3 and head 09079a5ef6, both run on all_debug through env -u SLURM_JOB_ID -u SLURM_JOBID sbatch, never on the fleet node. The suite is the node's case plus the two files that exercise the same module family: base arm (the node's case does not exist at base and is dropped) 55 passed, EXIT=0; head 56 passed, EXIT=0; added failure ids: none. The base arm runs against a snapshot of the base revision committed as its own repository, because tests/test_staged_write_inventory.py reads git ls-tree HEAD in its own root and an archive extraction has no HEAD — the first attempt at that arm reported two setup errors for exactly that reason, which is the arm's construction and not the code under test.

Negative control. The head's test file against the base acceptance module: 1 failed, EXIT=1, id test_an_unmoved_refusal_is_read_once_and_reported_once. Both base counts are in the log and were printed before the assertion: record searches over three sweeps 6, after the run directory moved 8, station failure lines 2; the head reads 1, 2 and 1. One deviation from the plan's declared base count. The plan predicts three searches over three sweeps and the measurement is six, because one sweep reaches review_self_state twice for a single review run: once in the review branch, and once in the synchronous job _hand_off runs when no durable queue is passed, which is the path that fills review_self_refused. The property the plan states holds either way — the base searches on every pass and the head does not — but the declared figure of three was wrong about the base, and it is reported here rather than made to read three.

Repair: the identity of what the search reads, not of the run that makes it. Review found that the first version keyed the remembered answer on the review run's own pointer and run directory. Those are not what the search reads: the record it looks for is filed under the run that was reviewed — a head-keyed path in that run's review-records directory, or a path in the crew review store — so filing it moved neither key and the cached “no record” stood forever. tests/test_a_review_promotes_only_its_own_verdict.py::test_a_predecessor_round_is_no_delivery_and_its_own_round_promotes failed 3 of 3 at eec6e60d56 for exactly that. The identity now carries every candidate path the search would read, absent ones included, and a plan review's report directory with its entries, so storing the record changes the identity. A new case in the node's own file files the record after a pass has cached its absence and asserts the next sweep promotes: at eec6e60d56 the search count stayed at one and self_promoted was empty; at 4d3ae94dd6 the count rises to two and the run is promoted.

Repair: the receipt's refusal is claimed where the collection reports it. The review pass was not the only place a refused review-self receipt reached the sweep report: the collection that reports the promotions a sweep handed off appended it without claiming its identity, so one unchanged refusal was stated again on every later pass. Both paths now claim the same identity. A case seeds a refused receipt and counts the entries naming the run over three durable sweeps: [1, 1, 1] at eec6e60d56 — one refusal logged three times — and [1, 0, 0] at 4d3ae94dd6.
