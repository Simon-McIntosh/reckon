Older code never migrates a newer store

The defect, reproduced. A store records the hash of the schema declarations it was last migrated to. An open whose declaration hash differed from that record ran the runs backfill: every row decoded and rewritten inside one exclusive transaction, and then the store stamped with the opening process's declaration. A store holding 500 rows, given a record this code does not know and one column it does not declare — the shape newer code leaves behind — reproduced it at the base revision d5694fa44d63c6b52d9b80e8315d1afa897bc11e:

FAILED tests/test_older_code_never_migrates_a_newer_store.py::test_a_store_written_by_newer_code_is_opened_without_a_backfill - assert 500 == 0
FAILED ...::test_reads_and_appends_on_a_store_written_by_newer_code_still_work - AssertionError: assert '71ab98ba3c3b...5c90fceae480b' == 'a-declaratio...by-newer-code'

500 row decodes on a store that was missing nothing, and the newer code's record replaced by the older code's hash. That is the whole-store write lock the plan's Why records, held by a process that had nothing to add, and the claim on the store that let it keep doing so.

What landed. Members and holds remain as they were; the open changed.

  • RunStore._lacks_declaration asks what the store is missing — a declared column, a declared index, or the table itself — instead of whether its columns equal the declaration. A superset is complete for this code, and the open returns without migrating and without rewriting the recorded version (_create).
  • _migrate_runs gates the row backfill on a declared column being absent. A store carrying every declared column re-asserts its indexes and decodes nothing, however its record reads.
  • The declared index names are stated once (_RUNS_INDEX_DEFS) and both the creating script and the coverage check read them, so the check cannot ask for an index the code no longer creates. The generated schema text is byte-identical to base, so _STORE_SCHEMA_VERSION did not move.

The measure, and the guard that could have failed silently. The test counts the rows the migration decodes through a stand-in on _legacy_payload, the one per-row decode the backfill performs. The same recorder reads 500 on a store that really lacks activity_seconds and 0 on the newer store, in the same run: the zero is the store reporting it did no work, not an instrument that never fired. That missing-column case still adds the column, backfills every row, builds the index on it, and passes at both revisions — the guard fires where it should and only there.

The contradiction, and its repair. tests/test_a_promotion_does_not_migrate_the_run_store_every_call.py carried test_a_changed_declaration_version_is_not_taken_as_current, which moved a complete-shaped store's record to an unknown version, opened it, and asserted the record was rewritten to this code's hash — the behaviour this node removes, so the landed change left it red. It is replaced by two cases that ask the question the open asks: a complete store with an unknown record is opened with no migration pass and keeps the record it carried, and a store that really lacks a declared column is migrated whatever its record says and records the declaration the pass reached.

Two assertions that had to be shown to bite. Review found one assertion comparing the fixture store against the constant that built it, which holds whatever the code does; it is replaced by a count of migration passes. Removing the coverage check from _create now fails the newer-store case with assert 500 == 0 on the row count and assert 1 == 0 on the pass count. The second gap was the backfill gate in _migrate_runs, which no case reached because a complete store returns before the migration: a store missing one declared index now takes the pass, gets the index back, keeps this code's record, and still decodes no row, so reverting that gate to column equality fails it with assert 500 == 0. Both mutations were applied and their logs kept beside the arms.
