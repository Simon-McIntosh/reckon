§116 — A small read of a large file costs its bytes, not a filesystem block

A default binary reader fills one st_blksize block before it returns the first byte, and on GPFS that block is 4 MiB (stat -f -c 'blksize=%S' on the trace file below reports 4194304). Every monitor, admission and dispatch path that wanted a tail of a worker's stream, a lock's small JSON record, or a bounded probe therefore paid 4 MiB of transfer per open however few bytes it consumed.

Every binary read in reckon/crew/, reckon/run_store.py and reckon/ledger.py that takes a bounded slice or reads after a seek now opens unbuffered (buffering=0), so a read costs exactly the bytes it asks for. The shared lock-record reader (_read_watch_record) reads positionally with os.pread, which fixes every lock holder at once: those handles are opened a+b/r+b by many callers and all of them read the same few hundred bytes.

A tail-to-EOF read of exactly the tail costs its bytes even buffered, so the honest measure is a bounded read with data beyond the slice. The trace below is a single producer pass over logs/trace-data/stream.jsonl (16,940,000 bytes on GPFS): _is_binary_receipt (8 KiB probe), _read_range(0, 64), and _tail_record_type (64 KiB trailing chunk).

The two 4 MiB requests are the block fill in front of the 8 KiB probe and the 64-byte range read; the 64 KiB tail chunk is the same in both arms because it reads the whole tail it asks for. The pass reads 8,454,146 → 73,794 bytes, a factor of about 114.

  • base suite arm at 9ed4c9ee2e: 58 passed in 43.03s — the importing files without the new test, which does not exist at the base.
  • after suite arm at f90e3db88f: 63 passed in 53.43s — the same importing files plus the five new cases, so the change adds no failure.
