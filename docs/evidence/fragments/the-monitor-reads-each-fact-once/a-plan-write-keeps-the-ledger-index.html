The ledger keys its own writes, not the plan's

The cause. ledger.ledger_generation read _store.read_write_generation, the project's plan-write counter, and _store.write_plan advanced that same counter. The open-run index compares the generation it recorded against ledger.ledger_generation and reloads the whole ledger when they differ, so a promotion's plan record, a comment or a section edit sent every ledger reader back through ledger.load — a rebuild for a write that had the wrong shipping address and had touched no run document.

What landed. The store keeps two counters, one file per project per family under the crew home: crew/write-generation/ for plan writes and crew/ledger-write-generation/ for ledger writes. _store.ledger_write_generation_path, read_ledger_write_generation and advance_ledger_write_generation are the ledger's own; write_generation_path, read_write_generation and advance_write_generation keep the plan meaning every other reader already had. ledger.ledger_generation reads the ledger counter, ledger.ledger_generation_path names its file, and _bump_generation advances and verifies that one. open_run_index needed no change: it already keyed on ledger.ledger_generation, so it now keys on the counter its own writes move.

Absence keeps its meaning. A counter that does not exist still reads as "no key" rather than as a value, so a ledger whose documents were written by something that never bumped keeps walking to the documents. A project picks its ledger counter up with its first ledger write after this lands; until then its index reads as no-key and walks, which is the pre-existing behaviour for an untouched project rather than a new one.
