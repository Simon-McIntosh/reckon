A stored git answer is left alone

What landed. _remember_commit_answer and _remember_count_answer in reckon/crew/recovery_watch.py now return early when the crew home's git answer store already carries the value they were asked to record. Both writers previously took the store's exclusive lock and rewrote the whole file through a rename to store an answer the file already held: _resolve_commit is called uncached while a tick composes each run's review subject, so every tick asked git again for every citation and rewrote the store with the same answers, once per citation. Each rewrite also gave the file a new stat identity, which is why a reader's held copy of the store stopped matching a moment after it was taken.

Why the skip is safe. The store holds only answers that are functions of immutable object ids — a full revision resolves to the same commit forever, and the commit count between two object ids never changes — so an answer already present is the answer the caller is about to write. A different answer still writes, which is the only case that changes the file.

Gate. tests/test_a_steady_tick_writes_no_known_answer.py builds a temporary crew home and a temporary repository of 20 commits, then resolves each commit's ten-character citation through _resolve_commit twice. A recording stand-in wraps _update_git_answer_store and counts the writes. The first pass writes 20; the second writes 0, every returned sha equals the same commit's first-pass answer, and the store's st_ino and st_mtime_ns are identical across the second pass. A twenty-first commit resolved afterwards is written once, and _stored_commit_answer reads its full sha back out of the two.

Negative control. The same case run against the base revision (5617397173), with the node's test file copied into a scratch extraction, reproduces the defect: the second pass makes 20 store writes and the case fails on assert 20 == 0. That is the declared control — the fixture is driving the path the change shortens, not a path the change removed.

Matched arms. Two arms ran on the all_debug partition, each in a scratch extraction of its own revision; each log opens with its revision, tree and literal command, prints the resolved measurement module and working directory, and ends in its own EXIT=. The base arm (5617397173) runs 53 passed, 2 errors; the after arm (f5e5e8e52d) runs those two files plus this node's case for 55 passed, 2 errors. The extra two passes are this node's cases. The two errors are the same pair in both arms and carry no FAILED id: test_staged_write_inventory's module fixture reads its trees with git ls-tree HEAD, which a scratch extraction has no metadata for. The change adds no failure.
