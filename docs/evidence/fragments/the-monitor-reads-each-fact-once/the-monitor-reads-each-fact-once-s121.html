An unanswerable lookup must not read as "no rows name this tree"

The incremental held-tree pass asks the store which rows name a tree it has just seen (_rows_naming_trees). That reader answered an empty list on any failure, which the pass could not tell apart from a successful answer of no rows, so it recorded the new tree as inspected. Its held duty was then dropped and never offered again, because the next refresh computes its "new trees" as the present trees minus the inspected ones and the failed tree was already in neither set. Only an unrelated rewrite of the aggregate, which rebuilds the index, brought the duty back.

The lookup now returns None for a failure and [] for a confirmed empty answer. The pass leaves a tree whose lookup failed out of the inspected set so the next refresh asks again, and advances the index's generation. The generation matters because the published pass is memoised on its source signature: a transient store failure does not move that signature, so without it the memoised, incomplete answer would keep answering every retry. A successful lookup is unchanged and its tree joins the held set as before, so the retry repeats no work once it succeeds.

Implementation commit 2a0618b403 changes reckon/crew/obligations.py and adds tests/test_a_failed_held_tree_lookup_is_retried.py. The fixture writes a landed row for a fourth tree and parks its directory, so the row is reachable only through the store projection and not through a re-read per-run document. Three cases run against the real refresh: a failed lookup leaves the tree uninspected and the next readable refresh shows its duty; a successful lookup is made once and not repeated on the next refresh; and the recovered duty view equals a from-scratch build's after the cached inputs are cleared.
