A held run is not resumed

The defect. A coordinator's hold lived only in the run's live pointer, and the station's repair pass read a held delivery as free work. On 15 November the coordinator held r-20261115T184907801020-an-answer-the-tick-reads-is-never-evicted at 21:03Z; at 21:52:23Z attempt 4 was reserved as a resume, the resumed worker committed 5cdbc394e9, and the station reviewed that new head. The hold's own record did not survive: the promotion that ends a run's life deletes the pointer.

Which pass reserved the resume. dispatch_repair_for_run, the repair pass, through resumption._resume. The run directory's resume-2-advice.txt opens Repair round: r-20261115T184907801020-an-answer-the-tick-reads-is-never-evicted@6c0f8e7edb9458e141dde4d477fe8b3d5cc7f310 and names the round's blocking finding f0a36b7a321, and attempt-4.reservation records kind: resume taken by the station's pid 1522386. The pass is inside reckon/crew/recovery_repair_dispatch.py, so no module outside the node's scope was changed.

What landed. The repair pass asks the lander's own question before it composes a round and asks it again at the launch, so a hold taken during the pass's own lane resolution is met as it is read. A coordinator's hold names no head and covers every delivery; a resume's hold names the head it was issued against and stops covering the run once a new head is delivered — the same covers_delivery reading the lander and the acceptance sweep already make, so the two doors cannot disagree. Taking and releasing a hold now also writes hold.json into the run directory, carrying the release's reason beside the reason the deferral began, so the delay outlives the pointer.

The held run over three station passes

tests/test_a_held_run_is_not_resumed.py builds a temporary repository, worktree and crew home, holds a delivered run whose newest review carries a blocking finding disposed as folded into the node and a round with an open blocking finding, and runs dispatch_awaiting_reviews — the station's repair and review passes — three times: 0 launches, so no attempt reservation is taken, and 0 reviews dispatched for the run. The run directory carries hold.json with the hold's reason and no release stamp.

After crew release the same record carries released_at and the release reason, and the next pass reserves attempt-2.reservation and resumes the run — the base pass's own action, reached only after the release.

Negative control. With the two guards removed the same first case fails and the launcher reports attempt-2.reservation: the base pass reserves a resume for the held run. The log ends EXIT=1 and the failing id is test_a_held_run_is_not_resumed_reviewed_or_redispatched.

A resume's hold and a new head

The second case holds the run with a resume's head-scoped hold, delivers a new head in the run's worktree, and runs the same passes: the pass reserves attempt-2.reservation and resumes, exactly as it does at base. The hold still names the superseded head in the run directory, and the delivery it named is no longer the one in hand.
