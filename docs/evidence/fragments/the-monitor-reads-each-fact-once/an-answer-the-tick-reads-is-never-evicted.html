One answer file per tree, so a steady tick neither evicts nor rewrites an answer it reads again

What landed. The git answer store is now one file per tree under ~/.config/reckon/crew/git-object-answers/, each named from a digest of the tree's path and each holding that tree's commits, counts and unreachable answers. recovery_watch._update_git_answer_store(tree, mutate) writes that one file under that file's own lock, through a pid-suffixed temporary and an atomic replace; _read_git_answer_tree(tree) holds that file's parse under its own stat identity through file_memo. The per-candidate cap is gone: an answer keyed by an abbreviation in a tree is immutable while the tree stands, so a tree's file has no per-answer bound. The bound now removes whole files, in the order that costs least — a file whose tree is gone, then the files of trees no live pointer cites, then the oldest — and it runs only past the 256-file ceiling. A legacy single-file store is read once as a migration source, split into the per-tree files, and removed.

What the old shape cost. One file held every tree's answers with a 512-answer cap per tree, and its write was one lock plus a whole-file rewrite of 22.5 MB. Four main checkouts and one worktree sat exactly at the cap, so a tick whose working set in one tree passed 512 made each new answer evict an answer the same tick, or the next, needed again: the eviction cost a git call and a lock, the rewrite handed the file a new stat identity, and every reader in every process parsed the whole store again. Three py-spy dumps of the station's main thread all sat in that path.

Gate. tests/test_an_answer_the_tick_reads_is_never_evicted.py builds a temporary crew home and a temporary repository of 600 imported commits, and records every answer file as (inode, modification time, size) before and after each pass.

The counts. The first pass resolves the 600 abbreviated revisions: 600 git calls and 600 answer writes. The second pass, with the in-process resolution cache cleared, returns the same 600 shas with 0 writes (0 bytes) and 0 git calls. The two-tree case resolves one new candidate in the first tree and writes exactly 1 file, the first tree's, while the second tree's file keeps its identity and its bytes. The legacy case serves its answer with 0 git calls and leaves no legacy file behind.

Matched arms. Both arms ran as one all_debug partition job, each over a tree of its own revision, each log under the node's run directory opening with its revision, tree, literal command, imported recovery_watch.__file__ and resolved working directory, and ending in its own EXIT=. The base arm (e83210b, a scratch extraction) ran the four files the template resolves there — 3 failed, 70 passed, EXIT=1; the three failures are the three fresh-process cases this node repairs, so the arm still reproduces the defect the store layout removes. The after arm (da84a8a125) ran those four plus this node's case — 76 passed, EXIT=0.

Negative control. The declared mutation — restore the base single-file store — replaces the head module with the base revision's and exits EXIT=1 with three failing ids, each the symptom the section names: the first case's second pass writes the one shared file (29,916 bytes), the two-tree case reports the other tree's file changed identity when this tree's answer was written, and the legacy case reports the legacy single-file store was not removed. The head module was restored byte-for-byte from a copy taken before the run, and the restored file was compared against that copy.

Two guards whose instrument had rotted. Three cases in tests/test_a_fresh_process_asks_git_only_what_moved.py were already failing at the base revision, and neither the store nor the node caused it: the file's recording stand-in recognised a commit count by the argv prefix git rev-list --count, while the command it counts carries --first-parent first, so the stand-in reported that the count never ran. The stand-in now matches the verb and the option, and the moved-head case asserts that the stored count is what the next read is served rather than the shape of the store's key. That file is in this node's scope, so the rot is repaired here rather than reported: the base arm fails those three ids and the after arm does not.
