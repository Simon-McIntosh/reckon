A publish reads each promotion request once

The defect. An obligations publish called promotion_requests.failure_obligations once per subscribed session, and each call listed and decoded every file under crew/promotion-requests/ before filtering on project and session. Six sessions therefore decoded the station's 1,578 requests six times, 28 MB each, and the function held 11.9% of every sample in the tick's profile.

What landed. A request is decoded at most once per version of its file. The record is cached under the file's full stat identity, taken on both sides of the decode so a write landing in between stores nothing rather than pairing one file's bytes with another file's identity. A publish builds one RequestIndex from that decode, groups it by the owner each request is owed to, and carries it on the fleet state, so a slice decodes nothing its publish has not changed. A request a publish settles is left out of its own later slices, and the settle guard reads through the same identity check, so settling a request already read costs no second decode.

The measure. 400 requests across 3 projects and 6 sessions, one publish:

The 401 in the third row is the request the same publish settled: it is the only file whose version changed mid-publish, so the session that re-lists the directory after the rewrite decodes it again. One index for the publish leaves it at one decode, because the settled request is left out of the later slices.

Parity. The duties each session is owed, and the set of requests a publish settles, are compared against a transcription of the base revision's loop over the same files — tests/test_a_publish_reads_each_promotion_request_once.py. Every failed or waiting request in that fixture carries a live pointer, so it is raised as a duty; the one failed request with no pointer is settled and its file rewritten, and the earlier settled requests are left as their readers wrote them.
