A run whose review has delivered waits on a promotion

The defect. A scoring run whose review_dispatch names a review run that has delivered, whose record no promotion has landed, carried no review duty at all. _current_review_in_flight read the recorded dispatch through _reflex_review_in_flight, which asks only whether the named pointer is readable, so a review holding its pointer in phase complete still counted as working on the revision and the duty was dropped by the view's suppression branch. The same run asked through _review_duty_item alone read review-missing. Either reading tells the coordinator to inspect a follower or dispatch a review when the actual wait is a promotion of a review that already exists.

What landed. reckon/crew/obligations.py gains _recorded_review_run_id (the review run the run's own pointer records a dispatch of, both rubric fields read, a withdrawn attempt ignored), _delivered_review_run (the same run when its pointer's phase is one of DELIVERED_REVIEW_PHASES), and the duty kind review-awaiting-promotion. The duty carries the review run's id in review_run_id, names it in its reason, and offers _delivered_review_promotion_command, composed through the classifier's own _promotion_command so the offered promotion cannot drift from the one a promotable run is offered. _current_review_in_flight now answers False for a delivered review, so the duty is built instead of suppressed; _review_duty_item reads it only when no stored record covers the head and none describes an older one, because a landed record of an earlier revision is a promotion that already happened.

Gate. tests/test_a_delivered_review_reads_as_awaiting_promotion.py with tests/test_staged_write_inventory.py, on the worktree's environment: base revision 51 passed, EXIT=0; head 54 passed, EXIT=0. The node's three cases show a review in phase working still reading review-in-flight, the same review once delivered reading review-awaiting-promotion and naming its review run and promotion command, a landed record reading review-ready, and a completed review of another run leaving this run review-missing. Negative control: the head tree with _delivered_review_run forced to return nothing, 1 failed, 2 passed, EXIT=1, the failing id being test_a_delivered_review_reads_as_awaiting_promotion's main case, whose duty list is empty there. At the base revision the same file fails the same case for the same reason, so base reads worse than the plan's review-missing: no duty at all. The cases that were already correct at base (a landed record reads ready, another run's review leaves this one missing) pass on both arms. ruff check and ruff format --check report nothing on the staged paths.

Logs. base-arm.log, after-arm.log and negative-control.log in the node's run directory, each headed with the tree, revision, command, imported module path and working directory it ran against, and ending in a bare EXIT= line.
