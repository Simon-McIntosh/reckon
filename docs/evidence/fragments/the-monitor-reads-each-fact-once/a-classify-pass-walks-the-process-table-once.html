One listing of the process table per classify pass

What landed. StationStore.classify_tick now opens process_signal.process_table_walk_once around its whole pass, beside the review-store region it already opened. Inside that region the first read of the process table walks /proc once and every later read is answered from the same map, so a pass that classifies a fleet costs one listing however long it runs. Nothing else changed: the region's table is the table the first read of the pass would have walked, and the stop path never reads a region because a map up to one beat old must never select a process to signal.

What a pass cost. A pointer whose recorded pids have both gone falls through the liveness read to the environment scan, which finds a reparented worker by the run mark its launcher wrote into it — and that scan is answered from a walk of the whole process table. The walk is shared for one second, which bounds a poller's pass and not a sweep's: a classify pass over a loaded node runs for minutes, so nearly every pointer's liveness read fell in a beat of its own and listed the table again. The live profile that motivated the section put 398 of 775 samples under that walk's frame.

Gate. tests/test_a_classify_pass_walks_the_process_table_once.py builds a temporary crew home of 40 live pointers whose pointer pid and worker-record pid are both dead, so every one of them reaches the environment scan. The process table is a recording stand-in for process_signal._walk_marked_processes, and a beat clock steps past BEAT_SECONDS between reads, as a pass of minutes does. One further pointer's run mark is carried by a live child the test starts and stops itself, so the same table is observed to answer alive for the marked run and dead for an unmarked one before either count is believed. The case asserts one walk, that every verdict equals the base revision's verdict for the same pointer, and that the live carrier reads alive in both arms.

The two counts. At the head revision the pass walks the table 1 time over 40 pointers. At the base revision (b8abf8233c) the same case walks it 40 times, which is the declared negative control: the recording stand-in counts one walk per pointer, so the fixture still reproduces the defect the region removes.

Matched arms. Two arms ran on the all_debug partition, each in a scratch extraction of its own revision, and each log opens with its revision and literal command and ends in its own EXIT=. The base arm (b8abf8233c) runs tests/test_staged_write_inventory.py and tests/test_every_shared_home_lock_holds_across_nodes.py: 53 passed, 2 errors. The after arm (287b37eb72) runs those two plus this node's case: 54 passed, 2 errors. The extra pass is this node's case and the two errors are the same pair in both arms — the staged_write_inventory fixtures read the repository's own HEAD with git ls-tree, which a scratch extraction carries no metadata for — so the change adds no failure. No arm reports a FAILED id.
