Plan resolution reads its directory once per change

The defect. A named plan read takes the plan's canonical path and then asks whether another file in that root claims the same identity. That question is one lookup into a held index of the root, and the index is revalidated against the root's listing: a glob of the directory and one stamp of every sibling. The listing itself was rebuilt per resolve, so the whole plan population's metadata was paid once per named read. At the base revision 200 named reads cost 400 directory globs and 80,000 sibling stamps across two passes over an unchanged directory.

What landed. reckon/resources.py holds each directory's entry names against metadata_index._dir_identity — the directory identity that moves when an entry is added, removed or renamed — read before the names are taken. A directory whose entry set has not moved is therefore not globbed again. Every entry is still stamped on each call, because a sibling rewritten in place changes no directory entry: holding its stamp would hand the index the identity the file carried before the write. The index itself is still reused, so the identification of every sibling is paid once per change of the listing rather than once per resolve.

The held listing is what the index is revalidated against, so the fresh stamps are what keep an in-place rewrite visible. Measured cost per resolve over 200 plans at the head: no glob, 200 stamps. Base: one glob and the same 200 stamps, plus an identification stamp per sibling whenever the held index cannot be reused. The glob is what this section removes; a stamp cannot be removed without answering from a stamp the file no longer carries.

The section's own bound, restated. The section's done-when asked for at most 200 sibling stats across the first two passes. That figure is only reachable by answering the index from held stamps, which is exactly the divergence the review reproduced: a rewrite into a second claimant goes unseen and the resolve that base refuses succeeds. One stamp per sibling per resolve is the floor for returning what the base revision returns, so that bound is not met here; the test asserts the invariant it can hold instead — every listing stamps the whole directory, never a held stamp — and the in-place case below holds that down.

Two passes, then one change

tests/test_plan_resolution_reads_the_directory_once_per_change.py writes 200 plans at their canonical paths, resolves all 200 twice, then adds one plan and renames one and resolves all 200 plus the added plan. It stands in for the listing function, for the plans directory's glob, and for file_memo.file_signature, so the globs are the directory's own and the sibling stamps are the ones one listing takes.

The head arm reads one glob across the two passes — 400 at the base revision — and stamps each entry once per resolve; every listing it builds stamps the whole 200-entry directory, which is the check that a held stamp is never reused in place of a fresh one. One further glob follows the plan that is added and the one renamed. Each resolve is compared for equality with the classifier's answer for the file it names, including the added and the renamed plan.

A sibling rewritten in place

The test warms the held names and the held index, confirms that the directory's identity is unchanged by the write, rewrites plans/beta.html so it declares the slug an already resolved plan owns, and requires the resolve of that slug to raise ResourceCollision naming both files. The base revision gives that refusal; a listing that held its stamps answers the resolve instead. The assertion that the directory identity did not move is what keeps the case about a file's own stamp rather than about an added entry.

The negative controls

The same test file, run against the base revision's reckon/resources.py in a scratch tree, fails on the glob assertion with two passes over 200 plans globbed the directory 400 times and EXIT=1, the section's declared string.

Reverting only this repair's reckon/resources.py at the head revision fails the in-place case with DID NOT RAISE ResourceCollision and the listing invariant with listings stamped different numbers of siblings: [0, 200], at EXIT=1 — the defect the review reproduced. The same file passes both cases at the repaired head, EXIT=0.
