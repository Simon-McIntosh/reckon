A repeat read of the store's index costs a stat, not a decode

The defect. store_index_document answered every call outside a producer tick by reading and decoding .review-index/index.json afresh — 4.8 MB on the shared store. On the base revision, 100 calls in a row over an untouched store decoded the document 100 times: the file had not moved between any two of them, and the reader had already parsed exactly those bytes.

What landed. reckon/crew/review_records.py keeps the parsed mapping it last read from each store, keyed on the document file's inode, size and modification time. A repeat read stats the file and, when the key matches, returns the mapping it already holds; a changed file is parsed again. Every writer replaces the cache entry as it persists a document, so a write is always followed by a read that takes the file. The reconciling path takes a private parse of its own: it mutates what it reads, while the cached mapping is what other readers in this process are already holding. The settle path that read the document inside the index lock also parses afresh, because another process may have written while it waited for the lock. A held mapping is still re-checked against the code stamp the document is filed under, which is process state rather than file content: an unchanged file filed under a stamp this process does not accept answers nothing and the caller rebuilds, so a held copy never stands in for an index the process must not trust. The population arm found that omission; the base revision re-checked it by construction because it had no held copy to skip the check on.

The harness. tests/test_an_unchanged_index_is_parsed_once.py builds a store on the test's temporary crew home through record_written, then counts decodes of the index document's own bytes through a recording stand-in for json.loads. It calls store_index_document 100 times outside any tick and asserts one parse. It then writes another record through record_written and asserts that the next call parses once more and returns the entry the write added.

Repair: the owner's mechanism, and a read a reader cannot change. Review scored reuse at five, below its floor, on two findings about the hand-rolled cache, and both are answered here. The mapping was a second parse mechanism beside reckon.file_memo, which the ledger, the resources index and the flight layer already use for exactly this job; the read now asks file_memo.memoized for the document, with the index code stamp as the memo variant because the stamp, not the file's bytes, decides whether a document is usable. And a cache hit used to hand every caller the one mutable dict, so safety rested on each caller remembering to take a private parse before it wrote; inside a read-only region file_memo hands out a read-only view instead, so a reader cannot change what the next reader is given, while the writer paths keep taking their own parse because they mutate what they read. Two cases name those mechanisms: one records the memo's calls and asserts the read goes through it with kind index_document, the other asserts a held document refuses a nested assignment and that the entry it tried to inject is absent from the next read.
