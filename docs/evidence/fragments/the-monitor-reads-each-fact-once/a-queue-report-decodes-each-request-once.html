A queue report decodes each promotion request once

The defect. promotion_queue_report is reached from the fleet's delivery summary on every station tick that has a promotion-queued tick, and on a busy fleet that is most ticks. Its _pending_requests listed crew/promotion-requests/ and decoded every file there with _read on each call, so a directory of about 1,600 requests — 28 MB — was JSON-decoded in full for every report. The tick after the obligations path was fixed still spent 16% of its samples in this call, 21.7% of that self time in the decoder.

What landed. _pending_requests now reads each file through _request_record, the same identity-keyed memo the obligations path already uses. The memo stores a decode under the file's full stat signature, re-verifies that signature after the read, and hands back a fresh copy outside a read-only region, so the report owns what it may write a priority override onto. The directory is still listed per call, so a request added or removed between ticks is seen; only the decode of a request whose bytes did not move is skipped.

What the measure shows

The gate builds 400 requests over the three projects and six sessions of the obligations fixture — 100 requested, 100 running, 150 settled and 50 failed — and counts every decode through a stand-in for _read. Each report is compared with a transcription of the base revision's loop over the same files, so a faster report is held to the same answer.

At the base revision every one of those calls decoded all 400 requests. The first call's count is the instrument's positive control: it saw the whole population, so the second call's zero is an absence of decodes rather than an absent reader.
