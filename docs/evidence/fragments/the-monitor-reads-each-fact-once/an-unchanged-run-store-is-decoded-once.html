An unchanged run store is decoded once

The defect. run_store.stored_run_rows opened the store and decoded every selected row on every call. Many readers reach it within one pass — the budget verdict through budget._ledger_readings, ledger.load, the readiness waits, section attempt counts and plan-owned identities — so one dispatch's worth of work decoded the same rows several times over even when nothing had written to the store between the reads. A 150 s py-spy record at 05:21Z put 35.8% of samples in stored_run_rows, with JSON decoding 25.3% of self time.

What landed. Each answer is held beside the store's change token, which stamps the store file and its archive (store_stamp/change_token, the same token the file memo already uses). A call whose question and token both match the held answer returns it without opening the store at all. The token is read before and after the rows are read, and an answer is kept only when the two agree, so a write that lands during the read cannot be cached under a token it moved past. The question — project, run ids, plan, node, fields, activity cut-off and the store's path — is part of the key, so one call is never answered from another call's rows. Every answer is copied out, so a caller that mutates a record it was given cannot change the next caller's answer. Both bounds on what is held are counted: 32 answers and 50,000 rows between them, and an answer larger than the row bound is not held at all.

Four identical calls, 2,000 rows

tests/test_an_unchanged_run_store_is_decoded_once.py builds a temporary store holding 2,000 run rows across three projects, 800 of them for alpha, and counts decoded rows through a stand-in on json.loads that counts a dict carrying a run_id. Four calls of stored_run_rows("alpha", path=store) at head make 800 decodes in total: the first call decodes the rows and the next three decode nothing, and all four answers are equal.

Against the same unchanged store the file then asks with a different project, with run_ids naming one run, with fields=("run_id",), with a node filter and with a plan filter. Each answer is compared with the same read taken from a byte-identical copy of the store that has no held answer to reuse, which is the read the base revision makes, so each argument is shown answered with its own rows and not ones another call left behind.

Updating one row through RunStore.sync_run moves the token; the next read of alpha decodes the 800 rows again and returns the amended record. Mutating a record in a returned answer leaves the next answer's copy of that record unchanged, and leaves it decoding nothing.

The negative control

At base 43f48118fa (main after 0958895bcc) the same file fails its decode-count assertion with assert 3200 == 800 — the four identical calls decode project alpha's 800 rows four times — and the mutation case reports assert 1600 == 800 after two reads. The log is logs/negative-control-base.log under the run directory, ending EXIT=1.
