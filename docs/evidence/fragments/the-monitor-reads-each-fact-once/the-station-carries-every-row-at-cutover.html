Every row of a recorded hour reaches a pane, and the cost of carrying it is still far above the bound

What this node was asked, and what it did. The producers, the producer user units and the follower snapshot path were to be retired once the station was shown to carry every row they carry, at a cost under 20 MB/min of read volume and 5 % of one core across all crew monitor processes. The first half is now shown: a recorded hour of one fleet node's event log replays through the station and every row of it is delivered to the pane it is addressed to. The second half is not met — the station on its own reads 1,067 MB/min and spends 92 % of one core at 71 live runs — so nothing was retired. The producers, the units and the snapshot path stay where they are, and the evidence behind that decision is recorded in the RCA's §11.

The hour, and what carries it. tests/test_the_station_carries_every_row.py replays 17:00–18:00 on 2026-10-23 for one node: 100 transitions over eight sessions. Eighty-six name a run and are addressed to the session that owns it; fourteen name no run at all — a budget lift granted or ended is workstation-wide — and reach every session watching the node. Each row is built by recovery_watch._watch_transition, the function the live fold calls, then written through station_store.record_tick and read back through the store's own query, so the test measures the station's storage and addressing rather than a re-derivation of them. The four cases assert that the carried set equals the recorded set key for key, that the hour is one ordered sequence with unique ids and non-decreasing times, that each carried row holds the facts a pane draws (state, the state it came from, the duty class, the run, the audience), and that a pane reading its own audience and the broadcast audience sees its own rows and nothing from another session.

The bound, measured with the RCA's own instrument. A 60 s window on clu-2068 with per-process /proc/<pid>/io and /proc/<pid>/stat deltas and six process-state samples, the station running alone as crew station --interval 1 over a crew home carrying 71 live pointers, read 1,067 MB/min of rchar against a bound of 20, spent 92 % of one core against a bound of 5, and recorded one D-state sample at xlog_wait_on_iclog, where the bound asks for none. read_bytes was zero, so the volume is page-cache traffic rather than GPFS. The same window over five live pointers read 126 MB/min and 42 % of one core, so the cost scales with the population of live runs rather than sitting in a fixed startup. Both arms ran while eight test processes shared the node, which suppresses the station's CPU share: the CPU figures are a lower bound on the true cost, not an inflated one.

Where the bytes go, and why the retirement waits. The store is not the source. On a cold runtime root one store tick over five live runs reads 8.2 MB, one whole station tick reads 91 MB on a cold store and 83 MB on a warm one, and every later tick reads 0.07 MB — the per-stream ingest already resumes from a stored offset and an unchanged stream is not read at all. The cost is the classification pass, which replays a run's whole stream whenever that run's pointer file signature moves; a live run's signature moves continuously, so the whole-stream read is paid every tick. The repair is in that pass — classify from the folded state the store already keeps — and it sits in reckon/crew/station.py and reckon/crew/station_store.py, neither of which this node held. Retiring the producers on top of a station that reads fifty times the bound would move the node's load from three producers and fourteen followers into one process without reducing it, which is the outcome the measure exists to prevent. The D-state sample is a wait on the runtime root's own journal, so it is a consequence of the read volume rather than an independent fault.

Gate. The armed suite command on this node's file, unedited: 6 passed, EXIT=0. The importer population for the four modules this node held — the 78 test files named for the station, the watch, the follower and the producer — ran in matched arms on the fleet node with the shared environment linked into both trees: the worktree arm 2 failed, 432 passed, 2 skipped, EXIT=1 and the base-tree arm 9 failed, 419 passed, 2 skipped, EXIT=1. Both failures the worktree shows also fail at base; nothing is added. The seven failures only the base arm shows are unrelated to this node's work — they cluster in the crashed-producer and changed-bytes families, and the base tree is a git archive extract carrying no .git. ruff check and ruff format --check on the staged paths are clean. The negative control mutated the delivered test so that a row naming no run is never carried: 2 failed, 4 passed, EXIT=1, with test_every_recorded_row_is_carried_once and test_a_lift_row_reaches_the_session_it_lifts red — the two cases the head arm passes and the mutation must break.

The control (the limits of it). The control this node was asked for was the same 60 s window taken with the old followers and producers running. It was not run, and the reason is recorded rather than hidden: no producer or follower was running on the node when the window was taken, and starting the retired-style producers and fourteen follower panes to measure against them is a live fleet action on a shared node, not a measurement this node may take on its own. What stands in its place is the sensitivity check the instrument needs: the same window over two populations of live runs moves the reading from 126 to 1,067 MB/min, so the instrument responds to the load it is asked to measure; and an empty process set is refused as a void reading rather than reported as a zero. The before figures the RCA already holds were counted in file syscalls per second, not bytes, so they cannot be plotted beside these — that difference is stated in the RCA rather than papered over.
