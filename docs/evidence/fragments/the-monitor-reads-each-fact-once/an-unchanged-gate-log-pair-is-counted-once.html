One read per arm log, one count per pair of log identities

The defect. Every read of a stored review annotates it with the failures the reviewed run added, and the annotation re-read both arm logs and rescanned them in full. The station reads the same review many times per tick through read_review → annotate_review_of_run, and a delivered run's logs never change, so 6.7% of the station's samples sat in recounting a number that had not moved. Five reads of one unchanged review read each arm log five times.

What landed. reckon/crew/review.py derives the pair once and holds only its result. _added_failures_for_arm_logs keys file_memo.memoized_key(..., "review_gate_log_added_failures", ...) on both logs' stat identities and on the two arm working directories, and the held value is an _ArmLogPair: the count, the added ids, whether the base log was present, and the two revisions each header names. annotate_review_of_run builds the record from that result, so a repeated read neither reads nor scans either log. _read_gate_log_at is the one place an arm log is read and is reached only on a miss.

Repair round: the result is held, never the bytes. The first cut also memoised each arm log's text. The station is a long-lived process with a history of out-of-memory kills, and a reviewed pair runs to megabytes; a 50,000-entry bound constrains how many entries there are, not how many bytes each one holds. The text memo is gone. A rewritten log now misses the pair's key and both arms are read again — the difference needs both, and with no bytes retained there is nothing to save the second read with. The entry bound that remains is the memo's own, and an entry's size now follows the number of failing tests rather than the size of the logs.

The harness. tests/test_an_unchanged_gate_log_pair_is_counted_once.py stores one review over a synthesised run whose directory carries a green base log and a failing head log, names them from the manifest as arms do, and stands in for Path.read_text, counting only reads of the two log names. Five reads of the stored review must read each log once and report the added failure. Rewriting the head log with one more FAILED line must read both arms again and report one more added failure, and the read after that must come from the memo. A head log in neither recognised format must read as unmeasured, not as a measured zero.

Negative control. The head's test file against the base tree at e6d692b1: 3 failed, EXIT=1, each arm log read 5 times over five review reads, which is the defect the section names. Removing the pair memo from the head tree instead — deriving the result per call — leaves the same three failures and the same 5 reads per log, so the file-read assertions guard the pair memo itself and not some other saving.

Gate and suite. The node's case plus the two files that share its module family, run on all_debug: base arm 58 passed, EXIT=0 at e6d692b1 (the node's test file does not exist there, so its command drops it); after arm 61 passed, EXIT=0 at the head; added failure ids none. The scoped check at the head passes 61 tests with EXIT=0. ruff check and ruff format --check report no finding on the two staged paths.
