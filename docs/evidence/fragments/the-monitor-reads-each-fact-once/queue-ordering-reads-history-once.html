Queue ordering reads section history once

The defect. The queue ordering rebuilds the roadmap whenever a plan input moves — a plan edited, a tick written to the sprint index — and every rebuild asked section_holds.held_section_blockers for the project's promoted rows. Those rows come from the run store, which gains a few an hour, so each rebuild decoded the project's whole history out of a 797 MB SQLite file on GPFS to reproduce the answer it had read a minute earlier. The same store refused promotions with database is locked through the night, so the read cost the writers as well as the tick.

What changed. run_store.store_stamp names the store's current contents: the file's stat identity (device, inode, size, mtime, ctime) plus the database header's change counter, so a commit that writes into a freed page is seen even when the file's size and timestamp do not move. The section history read keeps its rows beside that token and answers from them while the token is unchanged. The token is taken before the read and again after it, and the rows are kept only when the two agree: a promotion landing mid-read would otherwise be cached as already seen, and the section it delivered would read free until some later promotion. An absent store reads uncached, so the file-backed index path is untouched.

The measure. Over a temporary crew home whose run store holds 2,000 promoted rows over three plans, beside 20 queued requests, the queue ordering is computed three times. A recording stand-in wraps run_store.stored_run_rows and counts the rows every read decodes. Each ordering is preceded by a move of the sprint index, an input the ordering's own roadmap memo watches, so each one rebuilds the roadmap rather than answering from its priority build:

first, store unchanged2,00020 placed
second, roadmap rebuilt0equal to the first
third, roadmap rebuilt0equal to the first

The store moving. Recording one promotion through run_store.append and ordering again decodes the store again, and the section history the ordering was given carries the promoted row: the delivered section reads held by that row rather than by the contents read before it. The places themselves do not move, because the fixture's live set places this queue and a promoted row adds a hold rather than a readiness term — the same answer the base revision gives for the same store, which the matched arms show by running this file against both.

The write that lands mid-read. A third case writes the promotion from inside the population's own read, after the rows have returned and before the token beside them is taken. The next ordering decodes the store again rather than answering from rows that never saw the promotion.

Negative control. The declared mutation restores the base read — section_holds._history_rows calling ledger.picker_runs directly — and the second ordering then decodes the 2,000 rows again, which is the failure tests/test_queue_ordering_reads_history_once.py reports. The base revision's own tree, carrying the same test file, fails the same assertion, so the defect was reproduced before it was repaired rather than assumed.

Files. reckon/run_store.py (the change token), reckon/crew/section_holds.py (the read keyed on it), tests/test_queue_ordering_reads_history_once.py (the three cases).
