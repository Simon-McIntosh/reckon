A landing write waits out a held index lock

The defect

The landing commit staged its writes with a single git add and refused on any failure. A .git/index.lock that another session's git command holds for a fraction of a second is enough for that one git add to fail, so a promotion that had already committed its landing was reported as a refused verb. Two runs on 2026-10-20 lost that way — r-...074209872047 whose promote commit landed at 07:55:31Z and whose next staging failed at 07:56:00Z, and r-...082557577198, already promoted at 08:38:53Z, whose record rewrite at 08:47:10Z failed to stage on the lock and rolled back to the committed copy. Both landed a landing.json refusal at step stage.

The change

In reckon/crew/promotion_scope.py, staging is now performed by _stage_landing_writes. It calls git add as before, and on a failure whose message names a held index.lock (_staging_names_a_held_index_lock) it retries for a bounded window (_INDEX_LOCK_RETRY_WINDOW_SECONDS = 5.0, spacing _INDEX_LOCK_RETRY_INTERVAL_SECONDS = 0.5), appending a step: "stage_retry" entry with its attempt number and git's message to the run's landing.json before each wait. A staging failure whose message names no lock is returned at once, so a real error — an unreadable file, a bad path — is never hidden behind the window. A lock that outlasts the window returns the failing result to the caller, which refuses exactly as before.

The evidence

tests/test_a_landing_write_waits_out_a_held_index_lock.py drives _commit_landing_writes against a temporary repository holding a real .git/index.lock. Its three cases: a lock released once the first retry is recorded commits, with the retries present in landing.json; a lock held past a shrunk window refuses with a message naming the lock and records its retries; and a staging failure naming no lock — an unreadable file — refuses with no retry recorded. The focused gate is 3 passed (log head-gate.log).

The negative control reverts the retry around the staging git add to a single direct call; under it the briefly-held-lock case fails (log negative-control.log, EXIT=1).
