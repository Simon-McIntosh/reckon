A tracked landing write is restored under a held lock

The defect

The rollback that follows a refused landing restores each path the promotion wrote with git restore --source=HEAD --staged --worktree, a single index-writing call. The lock that refused the landing is still held, so that restore is refused too, and the fallback _restore_one_landing_write could only settle a path HEAD never carried — it dropped an untracked file from the index, and for a tracked path it returned unrestored and left the working-tree write in place. The plan file the landing had written is tracked, so its landing comment survived the rollback.

Reproduced at base a346c2e1 with a temporary repository (repro_tracked_restore.py, log reproduced at base): a tracked plan file carrying a landing narrative was asked to settle with a real .git/index.lock held. The report was {plan.html: False} and the working tree still carried "landing narrative the refusal left behind\n" against HEAD's "committed plan\n".

The change

In reckon/crew/promotion_scope.py, when the index-dependent restore is refused and HEAD carries the path, the fallback now calls _restore_tracked_landing_write. It reads HEAD's blob with git cat-file blob — plumbing that takes no index lock, so it answers while another process holds .git/index.lock — and writes it over the working-tree file. The path carries its committed content again with no staged entry this run never committed.

A path the index already carries a change for is reported unrestored rather than half-restored: clearing that entry needs the lock the fallback is running without, and rewriting only the working tree would leave the index staging content no reader can see. A blob git cannot read, or a file it cannot write, reports the path unrestored too — and _unrestored_landing_writes appends those paths to the refusal, so a coordinator reading the receipt sees which file to restore before re-promoting.
