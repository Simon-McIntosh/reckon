A finding states whether it blocks

The defect

A finding's emitted form carried a file, a line and free text, and nothing else. A reviewer's judgement that a defect has to be repaired before the node lands — the judgement that decides whether a node carrying one open finding should land at all — therefore lived as prose inside text, legible to a human and invisible to any gate reading the record.

The change

reckon/crew/review.py declares the vocabulary once, as the module constant FINDING_SEVERITIES = ("blocking", "follow-on"), with BLOCKING_FINDING_SEVERITY naming the blocking value on its own so a gate acting on blocking findings compares against a name rather than a literal. The parser records a finding's severity only when the finding opens with one of the declared words and a colon; an undeclared word is left where the reviewer wrote it — in the text — and a finding that states no word carries no severity key at all, because a defaulted severity is a judgement nobody made.

A finding's file, line and text are never rewritten by the new slot, so the parse an existing reader got is the parse it still gets, and a finding's identity — derived from those three fields — does not move when a reviewer adds a severity word.

reckon/crew/prompts/review.md teaches the same two values in the emission form the reviewer is asked for (FINDING <file>:<line> <severity>: <what is wrong and why it matters>), states which one holds a node and which does not, and says that a finding opening with neither carries none rather than defaulting to either.

The head arm adds no failure id; its ten extra tests are the new falsifiers, which assert that each declared value parses to itself, that the blocking value is a declared one, that an undeclared word stays in the text with no severity, that a finding with no severity word has no severity key, that a severity word leaves file, line and text unchanged, that the prompt names every declared value and carries the slot in its emission form, and that a stored review round-trips the field through both production readers.

The negative control

The declared control makes the parser ignore severity and requires the blocking case to go red. Its log's first line, verbatim:

make the finding parser in reckon/crew/review.py ignore severity; the blocking case in tests/test_a_finding_says_whether_it_blocks.py fails

Run against a scratch export of the head revision whose only change is the helper's return replaced by None: 5 failed, 5 passed, exit 1, the failures including the blocking case and the stored round-trip. The five that pass are the ones asserting an absence, which a parser that records nothing satisfies trivially — which is why the blocking case is the declared control rather than any of them.

What this node does not do

Nothing downstream reads the new field yet: the promotion refusal is unchanged, and a gate that acts on blocking findings alone is a separate node. Findings already in the store that carry a severity key were written by hand rather than parsed from an emitted line, and this change does not touch them — the parser reads the emitted form, and a record written by hand still stores whatever it carries.
