One actor dispatches a run's review

The defect

A run entering scoring is owed a review, and two surfaces answered that duty with the same dispatch. The review reflex composes it from the follower's own sweep (dispatch_awaiting_reviews), and the review-missing obligation printed the identical reckon crew dispatch --role review line as the duty's next action. The race fix keeps the first registered review, so nothing was lost — but a coordinator following the printed line lost the race and saw its review dispatched then withdrawn, and the reflex's claim on the review JSON path was spent on work the coordinator had already done.

The change

reckon/crew/obligations's review duty now asks the reflex's own question before printing a command: whether the session that dispatched the run has a live follower registration, read through runs.follower_state — the same reader the sweep uses to decide whose runs it may act for. While that follower is live and the row is scoring, the duty's next action becomes a statement that the reflex owns the dispatch, naming the session and the window the follower's sweep cadence gives, read from resumption.DEFAULT_SWEEP_SECONDS rather than restated. The row also carries review_owner: reflex so a reader sees the ownership as a field rather than parsing the sentence. With no live follower the row is unchanged and the dispatch command prints, because nothing else would launch that review.

Because the registration is now an input to the derivation, the snapshot parity case in tests/test_obligations_snapshot_is_published.py takes its expected payload inside the registration it already held while the snapshot was written. That case passed at both arms after the move (13 passed each), which is the evidence the fixture edit is neutral and not a second behaviour change.

Evidence

  • Focused gate, 3 tests, EXIT=0: an armed follower reads review-missing with no reckon crew dispatch in its next action, names the review reflex, the session and the 120 s window, and carries review_owner: reflex; a stored record at an earlier head reads the same way; with no armed follower the row still prints the dispatch command.
  • Declared mutation — the unconditional command restored in a scratch extraction of the node commit — reddens both armed-follower cases (2 failed, 1 passed, EXIT=1) while the no-armed-follower case still passes, so the guard is what the two cases measure.
  • Importer population, 57 test files that import reckon.crew.obligations, both arms from git archive extractions on node-local disk with the main checkout's .env linked: base f7d3f476d gives 325 passed, 10 errors; after c9ce8c287 gives 325 passed, 10 errors — no added failure. The 10 errors are identical in both arms and are pytest-timeout at 300 s in the two ledger fixtures (test_held_worktree_records_match_each_record_once.py, test_the_held_worktree_read_is_bounded.py) under -n 8 on eight CPUs; each fixture's own timeout, not a code failure, and present at base.
  • ruff check and ruff format --check are clean on both staged paths and on the fixture.

Scope note

The fixture repair in tests/test_obligations_snapshot_is_published.py is outside this node's declared write paths. It is the direct consequence of the in-scope change — the parity case compared two derivations across a released follower registration, and the registration is now an input — and leaving it would have turned the importer population red at the merged head. Recorded here and in the manifest's outside_scope for the coordinator.
