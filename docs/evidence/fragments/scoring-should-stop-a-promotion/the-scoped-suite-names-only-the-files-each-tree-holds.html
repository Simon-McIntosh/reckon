The scoped suite names only the files each tree holds

The defect

The armed suite command carries a {node_test_files} placeholder that stands for the node's fenced write paths. A write path is not a file that exists: a node that replaces a test deletes one file and creates another, so one write scope names a different file list in the base tree and in the head tree. Resolved once over the write paths alone, the head command named a file the head no longer held, pytest stopped with exit 4 having run nothing, and the empty failure list read as a clean observation in a delta computed from failure ids alone.

The change

_scoped_suite_command in reckon/crew/promotion_records.py takes the revision the command will run against and keeps only the write paths that revision's tree holds, read through the object store so a linked worktree reads the revision it names rather than the head's content. _paths_present_in_tree answers which paths a revision holds and answers unknown rather than none when it cannot see the tree, so an unreadable object store falls back to the declared scope instead of silently deleting every file.

The arm comparison accepts each arm's per-tree resolution of the same template alongside the whole-scope spelling a run dispatched before the rule recorded. An after arm left naming no test file, and either arm that exited 4 or 5 having collected nothing, are refused as unmeasured; an empty baseline is recorded honestly when the change creates every test in the scope.

This node found the behaviour already present at its base revision and did not reimplement it. The prior review of this section recorded the base-fail limb as unmeasured — the suite arm at the base revision passed five cases because that base already carried the rule. This node measured that limb against the two shapes it can be measured in: the pre-rule module, and the declared mutation.

Evidence

The head arm at this worktree's revision passes both files in the node's test scope: 56 passed and EXIT=0. The same template over the base revision's own tree passes the same 56, so the node adds no failure.

Against the pre-rule module — the resolver before the per-tree rule landed, in a scratch extraction with the current test file — the same test file fails all five cases: 5 failed, EXIT=1, the first naming the absent per-tree resolution; this is the base-fail limb the prior review found recorded as a pass.

The declared negative control bypasses the presence check in a scratch extraction of this head and runs the same test: 3 failed, 2 passed, EXIT=1, with the failures on the behavioural assertions — the head command retains the deleted test and the per-tree pair no longer differs. In the same tree the resolver is then driven over a fixture repository whose head deletes one test and adds another: the head command hands pytest tests/test_deleted.py, which that tree does not hold, and pytest reports no tests ran in 0.00s with exit 4 — the measured defect reproduced at the point the guard is meant to stop it.

The test file and the module are unchanged by this node: the guard was already correct, so the node verified it and recorded the failing limbs rather than reimplementing a working rule. Log paths are recorded in the run manifest.
