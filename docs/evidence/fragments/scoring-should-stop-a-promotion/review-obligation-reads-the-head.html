A review obligation names the review of the run's own head

The review-ready and review-missing duties were projected from the classifier's reading alone. A run whose stored review described a revision its worktree had moved past could therefore read review-ready, offering crew complete against the new head — landing unreviewed repair commits.

Both kinds are now read against the selection the promotion gate uses, select_review_for_head, for the revision the run's tree carries now (reckon/crew/obligations.py, _review_duty_item). A complete review stored at the current head reads review-ready; a stored record describing another revision reads review-missing and carries both heads on the duty (head and reviewed_head), so the reader sees which two revisions disagree. With no stored record at all the classifier's own reading stands.

Cases, run on a synthesised repository and a temporary configuration home

Two cases pass in the node's focused run (2 passed, commit 8de4ca55b): a stored review at an earlier head with the worktree advanced past it reads review-missing naming both heads; a review stored at the current head reads review-ready. The moved-head case fails at the base revision, quoting the missing naming; the current-head case already passed at base — the base classifier's own head-aware reading reported the moved head correctly but named neither revision on the duty.

Negative control

Making the obligation read any stored review regardless of its head (the head argument forced to the empty string in reckon/crew/obligations.py) reddens the moved-head case, which then reads review-ready (1 failed, 1 passed, EXIT=1). Red log: gate-negative-control.log in the node's run directory.
