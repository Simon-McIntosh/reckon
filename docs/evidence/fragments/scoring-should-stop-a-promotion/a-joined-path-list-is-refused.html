A path list joined by an unsplit separator is refused, not read as one path

A manifest's list fields are split on commas and newlines only. A worker that wrote several entries on one bare line joined by ; had that value read as a single entry: the first path satisfied the write-scope audit and every path after the separator was never scope-checked at all, so the guard looked applied while covering one path. The measured shape — a report path under the reports root, then scripts and logs under the run directory — parsed to ['docs/evidence/reports/x.html; scripts/foo.py; logs/bar.log'], and the audit answered ok: true against a scope declaring only the reports root, with the out-of-scope scripts/foo.py and logs/bar.log never reported.

What changed. reckon/crew/reports.py now refuses a list-field value whose entries a semicolon joins before a path-like token, at the parse, naming the field and the separator. Commas and a JSON array stay accepted forms and still split into separate entries; an entry that keeps a semicolon after its own split is refused the same way. A semicolon whose tail is a word rather than a path — a blocker written as one sentence — stays prose, so a list field's ordinary writing is not caught by the rule.

The measure. A manifest whose changed_paths is docs/evidence/reports/x.html; scripts/foo.py; logs/bar.log with scope docs/evidence/reports is refused, the refusal naming changed_paths and ';'; at base the same manifest parsed to one entry and answered ok: true. The same three paths comma-separated and as a JSON array parse into three entries, and scripts/foo.py and logs/bar.log are reported outside the write scope. The declared negative control — restore the comma-only list reading; the semicolon-joined case then answers ok — removes the refusal call and the two refusal tests fail (2 failed, 3 passed, EXIT=1).
