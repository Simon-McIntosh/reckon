An unmarked finding is refused at the write

The defect

A finding in a stored review record that opens with neither declared severity is recorded without a severity key — the parser never defaults one, which is right, because a defaulted severity is a judgement nobody made. What was missing is the write-time refusal: audit_manifest judged the review worker's own manifest and never read the record that run stored, so the one missing judgement — does this finding block the landing or is it a follow-on — stayed invisible until promotion, hours after the reviewer's turn had ended.

Reproduced at the base revision 84fd7ff4f in a scratch export of that tree (gate/base-gate.log): a record written through the production store (review.store_review) carrying two findings that declare no severity yields no audit finding about either, so the new falsifier fails on assert len(findings) == 2. The same arm's other three cases pass, so the empty result is a check that is absent, not a run that read nothing.

The change

reckon/crew/reports.py adds a write-time check to audit_manifest. When the node's role is the review role, the declarations the dispatch granted it are scanned for review-store record paths; the project is the directory beneath the store root and the reviewed run is the id the record's own name keys (legacy <run>.json and head-keyed <run>.at-<head>.json spellings both resolve, and one record is judged once). The record is read through the review store's own reader (reckon/crew/review.py, unchanged), and every finding whose severity is absent or outside FINDING_SEVERITIES (blocking, follow-on) is reported, naming the finding's file and line so the reviewer can restate it and store the record again in the same turn.

The check reports and never rewrites: the fix belongs in the record's next write by the party that authored it. A node that is not a review is not judged even when the same store paths are declared on it, because its deliverable is repository work and the record belongs to another run. The parser's rule that a finding emitted without a severity is recorded absent rather than defaulted is untouched.

The new falsifiers cover four cases: two unmarked findings are each named by file and line; a record whose findings all state a declared severity yields none; a record with no findings yields none; an implement-role node declaring the same store paths is untouched. ruff check and ruff format --check over the changed Python paths report no finding at head that the base did not (two pre-existing findings in reports.py at both revisions, zero in the new test file).

The negative control

The declared mutation removes the unmarked-finding check from audit_manifest in reckon/crew/reports.py; the unmarked case then passes clean. Run against a scratch export of the head revision whose only change is that call removed (gate/negative-control.log): 1 failed, 3 passed, exit 1, the failure being test_a_record_with_an_unmarked_finding_is_refused_at_the_write.

What this node does not do

The check reads and reports; it changes no stored record and no promotion decision. A gate that refuses a promotion on blocking findings alone is a separate piece of work, as is the prompt/parser pairing that gives new reviews their severities. One pre-existing failure in tests/test_crew.py (test_promotion_refuses_a_commit_that_names_no_object, a refusal message that no longer matches its expected regex) is red at both arms and is outside this node's write scope; it is reported, not triaged here.
