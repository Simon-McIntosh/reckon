The node that finishes a plan offers its close

A section moves to done through the edit_plan landing beat (set section_declarations.<id>), so that write is where a finish is seen. The write's response now carries the plan's readiness after the write beside its closure_blockers, so a coordinator ticking the last section reads closable and the close op in the same answer rather than re-reading the roadmap to discover the plan finished.

The helper _plan_readiness_fields sits beside _review_owed_fields in reckon/mcp_deadlines.py, following its shape. It reads the assembled roadmap the roadmap surface serves and selects this plan's row from pending_work, so readiness is the roadmap's own verdict rather than a second computation of the same fact and cannot drift from the surface a coordinator reads. On any failure to compute, readiness is null and readiness_error names why, and the write itself still succeeds — a failed read never reports a completed write as a tool error its author could retry into a version conflict. No obligation row is added and reckon/crew/obligations.py is unchanged, as the section requires.

reckon/mcp_edit_plan.py attaches the fields where it already attaches review_owed, gated on the write being a state-mode batch that addresses a section declaration: a set whose path is section_declarations or section_declarations.<id>. That is the landing beat the section names. A write to a section's typed fields, a decision or a status cannot leave a plan newly finished, so it carries no readiness field — the third case below pins that.
