A gate over finished work stops holding the plan

split_unpassed_gates in reckon/roadmap.py now reads a gate against the plan's declarations: a gate holds a section only while the plan still declares that section implementable, so a gate whose named sections are all done, descoped or deferred holds nothing. The gate over a resolved section is no longer a wait, and the plan it was pinning reads unblocked — closable where the declared-remainder reader gives it that value, ready where other live work remains.

A settled gate holds nothing at all, whatever its verdict. The pass and fail ops write a gate's status together with its verdict, so a gate whose status records that verdict is an outcome the plan already carries: a failed verdict says the measure will not be met and the work proceeds without it. A gate naming an implementable section therefore holds the plan only while it is still open — the same gate once closed holds neither the plan nor its section, live or finished.

The four plan shapes the census measured are covered: an open gate over a done section, an open gate over a deferred section, a concluded gate whose verdict is failed over a deferred section, and a concluded gate over a section that is still work. A gate naming no sections still holds the plan, so the split's existing contract is unchanged for open gates.

One boundary is worth naming. A plan that persisted no section classification tells this function nothing about which sections a gate still holds, so it keeps the reading an undeclared plan had before declarations were consulted at all: every unpassed gate holds it. That is the population the readiness ladder itself sets aside, and it is why the settled-gate reading sits inside the declaration-aware branch. Applying the settled-gate rule to undeclared plans as well needs a one-line fixture change outside this node's write scope, at tests/test_roadmap.py:1391, where the gate's "status": "closed" would become "open"; it is filed as the node's scope request rather than made here.
