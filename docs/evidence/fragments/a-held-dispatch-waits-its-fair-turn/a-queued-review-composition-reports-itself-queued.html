A queued review composition reports itself queued

A held dispatch answers as an acceptance: a local lane hold stores the request as a queued crew run the admission service will launch, and crew dispatch names that run's id, its position and its lane gate, then exits 0. A held crew review composed its report separately and answered every hold with error: lane-paused at exit 1, so a caller following the contract either respected a hold that had queued nothing or composed the same review again. One builder now owns that contract for both commands — _emit_held_result in reckon/crew_dispatch_commands.py — and each caller supplies only what is its own: the noun a hold sentence names (node for a dispatch, subject for a review) and, where the command composed a report, the report directory's id under report_run_id. An ordinary dispatch therefore carries no such key, and the dispatch command's output is unchanged. A queued record naming another phase reports that the run is already in that phase, also at exit 0; a paused gate with no queued record still reports lane-paused, now at exit 75 where it exited 1. Both branches of crew review read a hold this way, and the code-review branch catches the gate hold LanePaused as well as the router hold LaneHeld that subclasses it: catching only the subclass let a shut gate reach the generic handler and be reported as crew_error at exit 1, a failure of the command where the work was merely waiting. The composition's own report keeps error: lane-paused, so the sweep in dispatch_awaiting_reviews that sorts on that field is untouched and still counts a queued review as lane-paused.
