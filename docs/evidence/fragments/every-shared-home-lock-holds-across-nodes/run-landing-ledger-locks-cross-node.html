Run, queue, landing and ledger locks exclude across nodes

Seven shared-home locks guarded state that more than one node reads and writes, and each took only flock, which the local kernel grants: a holder on the login node never excluded a taker on the fleet node. They are the run pointer and the queued-dispatch and watch-registration locks in reckon/crew/runs.py, the ledger write lock in reckon/ledger.py, the landing pass lock in reckon/crew/queue_landing.py, the admission pass lock in reckon/crew/admission/service.py, and the reservation hold lock in reckon/crew/placement.py. Every one now takes reckon.node_exclusive_lock.exclusive_lock, whose POSIX record lock the file server holds for a holder on another node; flock is still taken first inside that helper, so a holder running the previous primitive on this node is excluded exactly as before.

Each site keeps the answer its callers already got. A non-blocking pointer take still raises PointerLockHeldError for a held lock and nothing else, so a resume beside a promotion still refuses rather than waits. The landing pass still returns {"landed": [], "obligations": [], "deferred": [], "busy": true} rather than waiting. The pointer lock and the landing pass wrap the take in contextlib.ExitStack and call enter_context inside the try, so a LockHeld raised by the take is translated into the site's own refusal while a PointerLockHeldError raised from inside the body is not caught and relabelled as a lock refusal. The admission lock keeps its one-call-site helper name, because the call site and the two tests that hold it sit outside this node's write scope; the helper body is now the single exclusive_lock take.

Every one of the seven lock files is opened under reckon/ only through exclusive_lock. The other references to each path neither open nor write the file. The run pointer's locks/<run-id>.lock is globbed by routing._stale_run_locks and named by routing._clear_run_lock, both of which only stat and unlink; gc.py imports and calls those two and takes the pointer lock itself through _pointer_lock, so it opens the file only through the helper. queued-dispatch.lock is constructed at runs.py:884 alone and is skipped by name in the prune. The ledger-write-<project>-<digest>.lock path is constructed at ledger.py:2608 and taken at ledger.py:2629; the prune's generic sweep only matches a stem that is a ledgered run id, so a ledger-write lock is never offered. landing-pass.lock, placement/reservation.lock and the project's watch/<project>.registration.lock each appear once, at their own take, and ADMIT_LOCK_NAME is a constant re-exported by name only. That exhausts the references, and it matters because a POSIX record lock is dropped when the process closes any descriptor for the file.

A second process stands in for the other node in tests/test_run_and_landing_locks_hold_across_nodes.py: it takes only the POSIX record lock on the lock file, never flock, and the two tests then read what each site does. The non-blocking pointer take raises PointerLockHeldError, and the landing pass returns its busy result with an empty landed list. Each test then repeats the call with the stand-in gone: the pointer take succeeds and the pass is not busy, so the earlier refusal is the holder and not a lock this process could never take.

Against the base revision 63b51b8337, where both sites take only flock, the same file fails both tests: the pointer take saw a free lock and did not raise, and the landing pass ran with busy absent from its result. That log is the node's negative control (negative-control.log, EXIT=1, two failing ids).
