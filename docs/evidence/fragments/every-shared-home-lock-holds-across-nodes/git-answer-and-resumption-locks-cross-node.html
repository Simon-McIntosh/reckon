Store, review and recovery locks exclude across nodes

Three shared-home locks in this node's scope moved onto reckon.node_exclusive_lock.exclusive_lock, whose POSIX record lock the file server holds and flock is not: the git-answer store (reckon/crew/recovery_watch.py _update_git_answer_store), and the lane-probe cache and sweep-status record (reckon/crew/resumption.py probe_lane_availability and _write_sweep_status). Both resumption sites were a context manager each owning exactly one caller, so the wrappers are deleted and the call sites take the lock directly; their path derivations stay with the callers that already hold them.

Each site keeps the answer its callers already got. The git-answer update still returns quietly rather than failing a read when the crew home cannot be written, with the lock's own OSError now raised from inside that existing guard. The lane probe still refreshes under one request at a time and the sweep status still merges per writer rather than overwriting, so the cross-node lock changes who excludes whom without changing any caller's result.

The measurement is tests/test_recovery_store_locks_hold_across_nodes.py. For each site it starts a holder in a second process that takes only fcntl.lockf on the lock file, starts the site beside it, and asserts the site's write has not landed after 1.5 s; the holder is then released and the write is required to land. On the head all three tests pass. Against the base revision ffcba6679c the same file fails all three, each naming that its site "wrote while another process held only the record lock" (3 failed, log negative-control-base-revision.log). That failure is what says the test can tell the two primitives apart, rather than merely passing.

Each lock file is opened in reckon/ only through the helper. The three derivations are reckon/crew/recovery_watch.py:241 (git-object-answers.json.lock), reckon/crew/resumption.py:702 (the lane-probe .lock) and reckon/crew/resumption.py:2438 (the sweep-status .lock), and each is the argument of one exclusive_lock take. Nothing else opens those paths: the store file name is referenced only by its own path helper and the two cache/status paths only by the code that reads and writes their data files.

The guard tests/test_every_shared_home_lock_holds_across_nodes.py passes with this node's three pending rows removed — reckon/crew/recovery_watch.py::_update_git_answer_store, reckon/crew/resumption.py::_lane_probe_lock and reckon/crew/resumption.py::_sweep_status_lock. The other pending rows belong to the peer nodes migrating their own modules and are untouched here.
