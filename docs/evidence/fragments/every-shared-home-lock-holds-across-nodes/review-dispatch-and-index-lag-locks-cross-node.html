Review dispatch and index-lag locks hold across nodes

Two shared-home sites took a bare flock and now take reckon.node_exclusive_lock.exclusive_lock: the per-plan review dispatch lock in reckon/crew/recovery_review_dispatch.py (_dispatch_text_review_for_run, <review report root>/dispatch.lock) and the index-lag seen-set lock in reckon/crew/obligations.py (_record_index_lag, <crew home>/index-lag-seen.json.lock). Both rows left the guard's pending table; the guard passes with them removed (57 passed in the after arm against 55 at the base revision).

Each site keeps the answer its callers already got. The dispatch takes the lock non-blocking through an ExitStack, so a LockHeld from the take maps to the existing moved-on report ("another sweep is composing this plan's review now") and nothing in the body can be caught as a moved-on result. The index-lag record waits for the lock as before, and an unwritable crew home still returns best effort through the same OSError guard.

A second process holds only the POSIX record lock on the dispatch lock file (fcntl.lockf, no flock), the parent proves the flock half is free by taking and releasing it, and _dispatch_text_review_for_run returns the moved-on result without composing or launching. At the base revision the same test fails: the dispatch takes only flock, sees the record-lock holder as free, and launches (assert True is False on report["dispatched"] is False). That failing run is negative-control-base-dispatch-lock.log in the run directory, ending EXIT=1.

Neither lock file is opened anywhere in reckon/ outside the helper, so no other descriptor can drop the record lock mid-body. The only other references are the two paths themselves: the test tests/test_a_held_plan_review_lock_does_not_hold_a_sweep.py opens dispatch.lock to hold a same-node flock for its own case, and tests/test_a_landing_leaves_the_index_at_head.py reads INDEX_LAG_SEEN_NAME, which is the seen-set data file rather than the lock file. The index-lag body writes index-lag-seen.json and its .tmp sibling, never the .lock path it holds.

Both suite arms ran on all_debug: the baseline arm at db9288122b reads 55 passed EXIT=0 over the guard and tests/test_staged_write_inventory.py (a new test file this node adds is not in that tree, so the two arms' commands differ); the after arm reads 57 passed EXIT=0 over the guard, the new test and the inventory. A focused arm over the tests that import both changed modules reads 19 passed EXIT=0 at each revision, so the change adds no failure.
