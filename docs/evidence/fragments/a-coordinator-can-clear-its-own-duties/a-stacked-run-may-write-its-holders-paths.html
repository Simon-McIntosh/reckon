A run built on a stopped holder's chain tip is admitted onto its paths

What changed. A stopped run that committed past its own dispatch base still fences its declared paths, and that refusal is right for a dispatch cut from the integration branch: a second writer there would bury commits that survive only while the holder's worktree does. It is wrong for a dispatch deliberately cut from the holder's own chain tip, whose worktree already carries every one of those commits — refusing that one strands the repair the holder cannot make for itself.

The exception is relational: it depends on the base of the dispatch under admission, which the claim walk cannot see because it judges one pointer at a time. So _raise_repository_scope_conflict in reckon/crew/dispatch_claims.py is given the two facts it lacked. It now takes base_revision, and passes over a stopped holder whose claim overlaps the dispatch when the holder's chain tip is that revision or an ancestor of it — reading the holder's head from its worktree with _head_revision, because the pointer records only the base the holder was dispatched from. A holder with no commits past its base still refuses, so the claim keeps its own rule for everything that is not a stacked dispatch.

Both claim build sites carry the same facts, so the exception applies whichever route reaches the check: the dispatch sweep in dispatch_claims.py, and the registry facade in reckon/crew/runs.py that rebuilds claims from _LiveScopeClaim. The admitted stacking is written on both pointers by record_stacked_dispatch — the holder gains the descendant in its stacked_runs, the descendant records the run it was stacked on — and the registry row the holder's claim already produced lists the stacked runs while still reading binding. Promoting or discarding the holder while a descendant is live is not refused: the promotion and discard results read the stacking and name each descendant still live. No refusal family is added.

Handing the check what it needs. The base exists only inside dispatch(), so reckon/crew/dispatch.py resolves the revision the dispatch builds on once, before the first claim check, and passes it to both _raise_repository_scope_conflict call sites together with the sink the admitted holders land in. Once both checks have passed the stacking is written on both pointers, before the pointer the descendant is published under. That is the whole of the dispatch-side change: one value threaded, plus the write that records an admission the check has granted.
