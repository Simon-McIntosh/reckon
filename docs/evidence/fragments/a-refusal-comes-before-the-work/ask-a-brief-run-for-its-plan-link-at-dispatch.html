A brief implementing run names its plan owner when it is dispatched

A brief implement or test run has no plan section to move, so nothing joined its product change to a plan unless the landing said so. Landing already refused to promote such a run without --plan-link or --unplanned-reason, and the coordinator met that refusal only after the work was done, when answering it cost the whole node. Reproduced at the dispatch base: a --dry-run brief dispatch with --role implement, no --plan and neither flag exited 0 and reported "admission": {"state": "admitted"}.

The refusal is now a finding composed in reckon/crew/node.py beside the contract findings and called by the dispatch command, above the pair split, so the live call, the --dry-run preview and both arms of a paired dispatch reach it before any of them resolves a request. Only that entry refuses: the production callers of plan_dispatch re-dispatch, re-resolve or re-lane a run that already exists and have no owner left to choose. The value given is recorded in the request's dispatch_options and copied onto the launched pointer, so the run lands with no flag; a landing flag still wins over the recorded value, and a pointer carrying neither still refuses as before.
