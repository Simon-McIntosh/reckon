A reconciled refusal reads as waiting

A queued request whose stored refusal is UnreconciledRuns is now read against the live pointers it names. The remedy publishes the first named run that still has a live pointer, because promotion removes the pointer. When none of the named runs is live the refusal has already been answered: _queued_failure_remedy returns no remedy, the request classifies as queued with no session_refusal, and the obligations derivation lists it as run-queued rather than queued-awaiting-session. That branch returns instead of falling through to the text search, so the refusal's quoted --allow-unreconciled-runs dispatch is never published as the next command. The detail drops its closing advice to discard the queued run and dispatch it again.

Measure: tests/test_a_queued_run_is_never_told_to_redispatch.py passes 4 of 4 at this change, against 3 failures at the base revision. Negative control — the live-pointer check dropped — fails test_a_named_run_whose_pointer_is_gone_reads_as_waiting and test_two_named_runs_are_read_for_the_one_still_live, with EXIT=1.

  • The same refusal with that run's pointer removed carries no session_refusal and is listed as run-queued.
  • With two runs named and only the second live, the remedy names the second.
