The cached index absorbs each change

The index keeps its cached build across every change a source can attribute, and drops it only when a change names nothing. The gate passes: 7 passed, EXIT=0. One case in a neighbouring suite that this landing was required not to regress still fails, and the mechanism behind it is identified but not repaired here, so this record is partial rather than done.

The change is carried as a value, not as a count. metadata_index.TreeChange holds a set of docs-relative files and a set of docs-relative directories, and mark_tree_paths folds one into a mark map keyed by the docs root. The cached read takes the mark, re-observes each marked directory's stat identity, re-parses each marked file, and reuses every other row from the persisted shape without a stat. A mark the cached build cannot absorb — its persisted shape is unusable — falls through to the rebuild that was the old answer, so a mark never costs correctness. Every other derived view is invalidated and every subscriber is notified exactly as before, because the marking happens inside _invalidate_tree_views, which still drops the discovery reuse window and the cached discoveries on every reported change.

Five sources name their paths. The kernel watch's consume() and drain() now return the (path, is_directory) events they read rather than a bare count, and observed_change turns them into marks: a directory event marks its parent directory, a covered file name marks the file, and anything else marks nothing. The detector's fast pass marks every directory whose identity moved and, when the git identity moves and HEAD moved with it, marks the covered paths the commits between the two heads touch by name; staging alone moves the index file and marks nothing, because a staged file has no new commit date to give a row. The slow pass marks the covered files whose stat moved, and a state-directory rewrite marks nothing because state files are not covered. _send_project_changes marks the names from its own burst, and a fleet-pipe wake that carries no names marks nothing. An inotify queue overflow, an unresolvable HEAD and a commit range git refuses to diff are all unattributable, and an unattributable change drops the build.

The gate is tests/test_the_cached_index_absorbs_each_change.py: 7 passed, EXIT=0. Case 1 writes a JSON file in a deep state directory and confirms neither build_index nor _dir_identity is called, on a tree whose documents sit under a typed root. Case 2 edits one HTML document under a kernel burst and asserts the exact set of stat-ed directories is the one holding the change, with its inner directory included and the figures directory absent. Case 3 moves a directory and shows the fast pass marks that directory, then picks up an HTML added inside it. Case 4 stages, commits a JSON-only change and commits an HTML change, showing that staging and the JSON commit leave the build alone and the HTML commit refreshes the row with the commit's own date. Case 5 overflows the event queue and shows the build is dropped, not kept. Case 6 edits a document in place for the slow pass and shows the row refreshed within the build, while a state rewrite marks nothing. Case 7 holds an open change stream across a JSON write and shows the build object is the identical one afterwards.

Eight controls are armed one per environment variable, each applied, run, logged and unset, and each fails the case it belongs to with EXIT=1 against the head arm's 7 passed and EXIT=0: dropping the build on every kernel burst fails cases 1 and 2; ignoring HTML names fails cases 2 and 4; dropping on every moved directory fails case 3; skipping covered entries in the re-scan fails four cases; dropping on every git identity change fails cases 3 and 4; keeping the build on an unattributed change fails case 5; dropping whenever the slow signature moves fails case 6; dropping on every stream wake fails case 7. Nothing was mutated in the source tree to apply them, so no reversal was needed, and git status --porcelain is empty after the run.

The population is every test file importing the two changed modules except the browser suite and the compliance suite, run with -n 4 at head with a per-run basetemp: 151 passed, 1 failed, EXIT=1. The failure is tests/test_cross_node_writes_refresh_the_index.py::test_an_open_stream_receives_the_added_row_and_stays_open. It passed in the first population run of this same head and fails in the second and on every standalone run since, and it fails 4 times out of 4 when run alone.

The failing case adds a second document while the first document's change event is being composed, and no event carries the second document at all. The mechanism is in the detector's stamp bookkeeping and not in the marking: when the handler absorbs a mark it writes the patched shape to the persisted index, the detector sees that file's identity move and reloads its directory stamps from the shape the read just wrote, and a directory identity measured after the second write is then adopted as the baseline — so the second change is compared against a stamp that already includes it and the fast pass never fires. The remedy is to adopt a reloaded stamp only where it matches the directory's current identity and to keep the detector's own observation otherwise, so a change that lands inside a read's write window still fires; it belongs in the detector and it is not attempted here, because it changes the firing rule for every tree and needs its own gate.

Three assertions elsewhere were superseded and rewritten rather than reported. Two test doubles in tests/test_cross_node_writes_refresh_the_index.py and one in tests/test_metadata_index_survives_restart.py shadow the invalidation entry point with a fixed keyword list, which the index-change keyword they did not know landed in; all three forward what they are given. A fourth adaptation gives the never-firing kernel watch in the first file the empty name lists the watch's own methods now return. The arming step was also moved off git: it reads the loose ref's own characters as files instead of resolving HEAD, because a process started there delays the baseline the detector compares against and a commit landing in that window is recorded as the tree's starting state — measured as a stand-alone case failing 9 runs in 10 before the change and 3 in 3 passing after it.

Ruff adds no finding on the staged paths and ruff format --check is clean over them.
