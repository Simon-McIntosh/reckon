A change pushes its rows, and the page patches them in place

Commit 79d925018 changes /_changes/<project> from a bare content digest to the index rows that moved. The stream keeps the row list it served when it opened, re-stats the tree on a reported change, and diffs the rebuild against that list: a rewritten file arrives in rows.changed, a new file in rows.added, a departed file in rows.removed, each carrying the full row the /_index endpoint serves. The rows go out before the derived payload's digest is recomputed, so a reader waits on a stat-and-diff pass rather than on a full rediscovery; a change the index does not see — project state without a row move — still reports its digest alone, which is the event shape the loader answered before. _served_index_rows is now the one call shape behind both the endpoint and the stream, so the pushed row and the served row cannot disagree on stamps.

docs/ui/state-loader.js patches a pushed event into window.STATE in place: a changed row keeps its object and its position, a row the page never carried is held as an arrival rather than inserted, and a removed row leaves the inventory. The derived fields a discovery merge delivered are left in place — the index carries no effective status, so the patch never overwrites one with a locally defaulted value — and the derived refetch follows at most once per settle window, in the background. An event carrying only a digest keeps the refetch the loader always made, so an older server still drives the page.

  • Event latency, ten flows in one process: 0.45–0.48 s from rewrite to pushed row, against the 2 s bound. Emitting rows ahead of the derived digest is what bought that margin: the same flow measured 1.13–1.48 s while the digest was resolved first, and one run under a busy node reached 3.23 s. A change resolves six git forks either way, but only the row rebuild's two then sit between the rewrite and the event; resolving the digest first put all six there.
