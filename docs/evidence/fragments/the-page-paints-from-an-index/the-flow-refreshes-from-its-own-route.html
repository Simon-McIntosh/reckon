The flow refreshes from its own route

The derived flow's bars are placed relative to the instant the flow's own comment describes — the in-flight bar's done share sits at now — so a flow built once at page load drifts away from the fleet it draws as the minutes pass, and one refreshed only when a project document changes stays frozen for as long as nobody writes. The refresh had no route of its own: it rode on /_discover/<project>, which rebuilds the whole derived payload for a caller that already holds the inventory and the live run rows. This node gives the flow a route that answers the schedule alone, and moves the refetch from the event that says nothing about this project's documents to the poll that does.

GET /_schedule/<project> answers {project, schedule, schedule_error?}. It is built the way discovery builds it — the same stored inventory, the same live crew rows, the same derivation — and differs only in that every request anchors its own walk at that request's instant. A crew-row read that fails costs the schedule and nothing else: the stored inventory is already in hand, so the route keeps its 200 and serves a null schedule beside the error, as discovery does. A missing or malformed project name answers 400 and an unmounted project 404, both before any tree read.

Three route cases serve a temporary project in-process with the clock frozen at a supplied instant, so the anchor is checkable rather than asserted: an in-flight bar's done share, read back as reference + split hours, equals the first request's instant and then the second's, seven minutes later. The control builds both answers at the first instant, and its second answer provably lacks the second instant — so the arm's pass is about the per-request anchor and not about a route that happens to place bars somewhere.

A run that appears between two requests is the case the route exists for. Its plan's bar is predicted before the run lands and in-flight after, which is the same bar read twice with only the crew rows moving; a schedule built before the run went live keeps the bar predicted, and that schedule is the control. A failure arm patches the crew-row read to raise, and the route answers schedule: null with schedule_error: "RuntimeError: crew rows unavailable"; the control lets the same failure through and answers 500, so the failure arm's 200 is a decision the route makes and not a route that never reaches the code.

The crew view owns the fetch. docs/ui/state-loader.js holds scheduleRunSignature, scheduleFetchDue and refreshSchedule: the signature is each of this project's own runs' identity and phase, sorted; the due test is a moved signature or a minute elapsed since the last fetch, whichever comes first; and the fetch replaces window.STATE.schedule, or — when the route answers a null schedule beside an error and one is already on screen — keeps that schedule and marks it stale with the error, which is §10's rule applied to this route. Discovery's null schedule keeps its own anchor for the merge that cannot build one.

The signature selects one project's runs because the poll does not. /crew answers every mount's rows, so it carries the runs of every mounted project and their live crews; a signature written over all of them moves when a run anywhere moves, and spends a request on a schedule that has not changed — the waste this route exists to remove, multiplied by every live crew on the workstation. The shell names the project it is fetching for, and the loader keeps only that project's runs. A loader case reads both directions: another project's run moving phase leaves the schedule not due and spends no request, this project's own run moving is due and spends exactly one, and the unscoped signature is shown to have moved on the very input the scoped one did not — so the case does not pass because the two run lists happen to agree.

A node loader case drives the real clock and the real state-loader.js against a recording fetch: the first poll for a view with nothing built fetches once, a poll showing the same runs inside the minute fetches nothing, a poll showing a run whose phase moved fetches once, and a further unchanged poll after the minute fetches once more. The fetched schedule is installed on window.STATE.schedule, and the control — the same poll with the fetch removed — leaves the schedule the view already held, at the reference discovery served. A render case then draws the replaced schedule and reads the newly working run's plan's bar as in-flight, with the earlier schedule as the control, so the replacement is shown to reach the picture.

The failure branch has its own case. When the route answers 200 with a null schedule and a schedule_error, the schedule on screen is the last that was actually served, so it is kept and marked stale with that error rather than emptied. The case holds a schedule, drives that answer, and reads the kept object back: same object, same bars, same reference, with stale set and the error carried — the reference matters because a schedule that moved for a read that failed would be a different picture rather than the same one aged.

docs/ui/shell.jsx calls the fetch inside the poll it already makes, and only while the crew view is the visible one; the project is read from window.STATE and the view through a ref, so the poll effect keeps no dependency on either. A served-page case in a browser counts the requests a real page makes: on the crew view, a run whose phase moves between two polls produces exactly one further /_schedule request and a later unchanged poll produces none; and the same page, the same poll, on a route that draws no flow makes no schedule request at all while the poll itself still runs several times. Removing the shell's call reddens the first case with zero requests and fifteen polls.

A fleet event no longer refetches the project's derived state. Those events carry no owning project, so the server publishes them on every open stream, and with many mounts and live crews they arrive constantly while speaking about nothing this project holds. The event still reaches a view computing that key through reckon-fleet, and a change event still revalidates — once per settle window. The node loader case that reads the stream asserts one fleet dispatch and zero refetches within the settle window, then asserts a change event still refreshes exactly once, so the first assertion is about the fleet event and not about a listener that stopped answering.

The served-page revalidation case that already proved the derived blocks survive an index revalidation used to assert the checks and crew routes were attempted. That is satisfied by a preload that holds a request open, so an edit that answered one of them would have left the case green. Its preload now counts answered responses separately from attempted ones, and the case requires at least one attempt and zero answers on each route: answering /_checks reddens it, and the declared control does exactly that.

Nothing outside the schedule path changed. reckon/serve.py gains one handler beside the discovery route and reuses _served_result and _attach_schedule_for_read, so the schedule a browser draws and the schedule an agent reads from discovery remain one computation; the module stays within the window bound the module-size test checks. The loader loses one call and gains three functions; the shell keeps one poll.

The declared control is applied as one edit set and kept as a log, one mutation for each case the node's done-when names by its control: restore the derived refetch on fleet events; neuter the poll-driven fetch's due test so no poll asks; remove the shell's call; answer /_checks in the served case; serve the schedule built for the first request to every later one, which anchors both answers at one instant and keeps a run that went live since the first out of the second; let the crew-row failure raise, so the route answers 500 where the arm requires 200; keep every mount's runs in the signature; and drop the stale marking of a kept schedule. Nine cases redden, each one its own mutation's, and the log ends EXIT=1 against the head arm's passing run. The reverse runs from a trap, so it runs whether the cases pass or fail, and the log's git status line is empty: the tree is identical to the head revision afterwards.
