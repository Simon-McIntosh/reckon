The pass that wrote the record late

The staging record is written by the plan-review store's delivered-report pass, store_delivered_reviews in reckon/crew/plan_review.py (through _store_deliveries and _store_delivered_report). Both call sites named in the section reach that one pass: a later dispatch on the same plan runs it from routing.require_plan_reviewed (reckon/crew/routing.py:2949), and promotion's own delivery read runs it from promotion_checks._plan_review_promotion_outcome and promotion_checks._plan_review_record_for_promoting_run. Neither caller changes; the guard is fixed in the one writer they share.

What changed

_store_delivered_report now calls _commit_record_when_run_promoted after it has written a plan review's staging record. The helper resolves the crew run that produced the record through review._plan_review_crew_run_id — the one owner of the composed-id-to-run join — and asks open_run_index.has_row whether that run already holds a ledger row. Only then does it write the committed record through review_records.store_committed_review, the same committed writer the promotion uses, and commit it with review_records.commit_record_write. A run with no ledger row leaves the record in the staging store for its own promotion to commit, so the before-promotion path is unchanged and nothing is committed twice.

Only the case with nowhere to commit is decided up front: a project whose committed reviews tree does not resolve is skipped before the write. A commit that is refused for any other reason is not caught — the ledger refuses by raising, and that refusal leaves the pass, so the caller learns the record did not land rather than the store returning as if it had. Swallowing it would leave the record staged with no promotion left to commit it, which is the state this section exists to remove.

reckon/crew/promotion.py needed no change: its guard is correct for the write it makes, which happens before the ledger row exists. The gap was that nothing committed a record written after that row landed.

Durable receipts

  • base-arm.log, head-arm.log, negative-control.log — each starts with its revision, tree, imported module path and literal command, and ends in a bare EXIT= line, under the run directory.
  • Each arm is that revision's tracked tree exported with git archive into a freshly made temporary directory on the compute node that ran it, committed there so the inventory test reads a real repository, and removed on exit.
