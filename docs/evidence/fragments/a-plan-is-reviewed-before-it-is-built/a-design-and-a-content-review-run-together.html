Two holds refused a second plan review of one plan, and both are now settled. The first was the compose's own in-flight check, _standing_plan_review, keyed on the plan alone; it now keys on the plan and the rubric, read from the composed node's goal line (review the <rubric> of plan <slug>), and a pointer whose rubric cannot be read keeps standing for every rubric, so an unclassifiable record never admits a duplicate.

The second was dispatch()'s existing-run answer, _answer_existing_node_run (reckon/crew/dispatch.py:430), which reads runs.existing_node_run (reckon/crew/runs.py:670) keyed on (plan, section, node id) (reckon/crew/runs.py:544). Both rubrics composed under the one node id plan-review-of-<slug>, so the design review passed the compose check and was refused by dispatch with run r-…-plan-review-of-fixture is already starting for this node. The composed node id now carries the rubric for the design review — plan-review-of-<slug>-design — while a content review keeps the bare id every stored pointer and store reader already carries, so the two rubrics are two node ids and dispatch's check needs no change. round_node_source strips the rubric suffix from a plan-review id — only under that prefix, since it is the one grammar that writes it — and every reader of a plan-review id recovers the plan slug through it: the compose's in-flight check, the admitted-review join, the obligations view, the review-record key, and the four promotion readers that resolve a delivered review's report from the plan its run names. A reviewer, an obligations row, a queued request and a promotion all resolve either spelling to the same plan, and a review of a layout whose own name ends in the same word keeps it.
