The station's memory is a JSON working set, not a retained cache

Six traced ticks over 133 live pointers, at revision 2bf8e6947d, in a temporary station store and an overlay whose live/ and runs/ entries are symlinks into the live crew home. Process RSS after each tick was 856, 2563, 2561, 4262, 4498 and 4623 MB; the memory tracemalloc still held after each tick was 112, 128, 214, 263, 252 and 240 MB. So RSS grew 3.68 GiB across the six ticks while retained memory grew 128 MB, and 5.2 % of RSS at the last tick (240 of 4,623 MB) was traced at all.

The gap is the working set, not a growing structure. Tracemalloc's peak inside each tick was 207, 1664, 298, 3264, 3254 and 2255 MB: between one and three gigabytes are allocated and released inside every tick, and the allocator does not return those arenas to the kernel. A station that leaks nothing still walks its RSS upward by the size of its largest per-tick decode.

One allocation site holds the retained share in every tick: json/decoder.py:361, raw_decode, at 113, 130, 169, 207, 197 and 181 MB with 1.24–1.77 million live objects. It is the scanner inside json.loads, reached from the stream decode in station_store.ingest_stream and from the review-index read in file_memo.memoized("index_document", ...). No other site reaches 100 MB in any tick.

The review-index views in reckon/crew/review_records.py are present but small beside it. _DOCUMENT_STAT_VIEWS holds one stat view per store directory, _STORE_INDEXES the per-store entry lists, and _DOCUMENT_MAPS the run maps for one document version; each is a decoded copy of the store's index, whose on-disk sizes on this node are 5.8 MB for reckon and 12.1 MB across nine stores. In this census their allocation sites are _entries_from_listing (1.2 MB) and _indexed_record_stat (1.2 MB), and the decoded document they are built from shows as file_memo.py:351 with 17.6 MB retained in 95 objects plus 13.4 MB of read-only dict wrappers at file_memo.py:69.

None of the three grows per tick in this arm, so no keying defect is reported. Twenty-six sites did rise in every tick, leaving out the census harness's own three allocation sites that the log also lists, and the largest of them are interpreter-level: <frozen codecs>:325 to 3.7 MB, pathlib/_format_parsed_parts to 2.2 MB, copy/_deepcopy_dict to 1.4 MB, and file_memo.file_signature to 0.1 MB. The growth is per-path and per-signature bookkeeping at tens of kilobytes per tick, four orders of magnitude below the working set.

Instrument control. The same harness, run with a module-level list that grows by 50 MB per tick, attributes 52.4 MB per tick to that list's allocation site (minimum 52 428 857 bytes over five intervals, against a 45 MB floor), while its own census shows the same shape: RSS 4.23 GB, retained 585 MB, peak 2.68 GB. A census that could not see the injected list would prove nothing; this one does.

Limits. Derivation was disabled in this arm: station_obligations.publish hands each project's refresh to a worker and a drained tick costs more than three minutes per project even with no pointers present, so the arm that includes it did not finish inside the partition limit. The review-index derivation path is therefore attributed from code and from the sites above, not from a completed per-tick series. Tracemalloc ran at one frame per block, so callers are not in the tracebacks; attribution is by allocation site plus the code that reaches it. The store was warmed untraced (55.6 s, 712 MB RSS) before tracing began, so the first tick is an incremental tick and not the cold fold.

What the job wrote. The station store was a temporary root (/tmp/mcintos-censuswarm-*/store, 10.96 MB). The production store is node-local to the fleet node, so a census on a compute node cannot see it: the path /tmp/39486-fleet there is that node's own directory, and the job's before-and-after comparison of it describes nothing about the fleet's store. Captured on the fleet node itself, that store moved throughout the run (station.sqlite3-wal at 12:56Z against a 11:16Z preflight), written by the live station's own ticks. The live pointer directory moved too: 133 pointers at the start, 129 at the end, with the newest file named for another session's run id. Both movements are the fleet's own, on its own node; the census wrote only its temporary store and its overlay, and read the live home through symlinks.
