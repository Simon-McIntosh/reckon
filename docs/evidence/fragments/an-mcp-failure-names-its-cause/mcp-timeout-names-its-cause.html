A reckon MCP timeout names its cause

_run_under_deadline reads the worker thread's CPU time and run-queue wait at the deadline, through /proc/self/task/<tid>/stat and /proc/self/task/<tid>/schedstat, subtracts the baseline it took before the body ran, and reports a cause of computing when the sum of the two reaches half the wall time it held (with a small floor for counter granularity), otherwise waiting. Counting the run-queue wait is what stops an oversubscribed node's starvation from reading as a slow filesystem: a body runnable but not running burns little CPU but sits on the runqueue, while a body blocked on storage is not runnable and its run-queue time does not grow. The result carries waited_seconds (wall), cpu_seconds and run_seconds, and the error value stays storage-slow so no existing caller's branch changes. The message names the cause, and a computing body whose tool has a CLI counterpart is given the command that answers without a deadline — reckon roadmap, reckon audit or reckon crew list; read_plan and edit_plan have none, so they name no command rather than pointing at a read that answers something else.
