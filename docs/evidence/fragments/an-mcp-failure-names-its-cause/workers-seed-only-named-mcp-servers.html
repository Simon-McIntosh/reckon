§7 — A worker starts only the MCP servers its work uses

The run's harness home is seeded by seed_harness_home in reckon/_backends.py, the one writer of that home. The seeder now writes two Claude Code settings keys into the settings.json it creates from the operator copy: enableAllProjectMcpServers false, which disables the project's .mcp.json servers as a group, and enabledMcpjsonServers naming the servers the project lists under its flight configuration's worker_mcp_servers key. reckon is a user-scope server carried in the run home's .claude.json and stays enabled. A run's own settings file, written by a run that already owned its home, is never overwritten.

Measure. tests/test_worker_mcp_servers.py passes at EXIT=0 (7 passed): a project with no worker_mcp_servers seeds a settings file with the project's servers off and reckon carried in .claude.json; a project listing imas-cx seeds enabledMcpjsonServers == ["imas-cx"]. The declared negative control — removing the seeded settings write — fails at EXIT=1 with 4 failing test ids the head arm does not fail, and the project server then reads enabled (repro log gate_negative_repro.log). Existing tests over reckon._backends' launch/seed surface pass at EXIT=0 (167 passed, 1 assertion in test_fence_is_on_again.py updated in this round).

Scope note. The record is written only when the launch carries a resolved flight configuration: a bare composition with no project layer governs no project, so the existing operator-harness-home test that asserted the seeded settings.json held only the hooks key passes unchanged. The dispatch path does carry a configuration, so test_fence_is_on_again.py — granted to this round's write scope — was updated to expect the record.

Follow-on. The flight-config key worker_mcp_servers is read from the resolved configuration, but flight's schema (reckon/flight.py) forbids unknown top-level keys, so a project cannot yet declare it without a one-line exclusion there — outside this node's write scope.
