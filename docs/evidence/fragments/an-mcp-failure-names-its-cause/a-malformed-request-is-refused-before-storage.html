§17 — A malformed request is refused before it touches storage

A request whose only defect is an argument — a crew view outside the served set, a crew field no row carries, a read_plan or roadmap view outside the declared shapes, an edit op verb outside the edit vocabulary — was answered only after storage had been consulted. Against a stub whose every open raises, the base revision reached the stub: _crew read the live pointers through reckon.crew.list_live and classified an empty pointer before it read the requested field names, and the store read the plan before it dispatched _apply_one_op.

Change. reckon/mcp.py gained _crew_argument_refusal, called at the head of _crew for a read request (no action). It refuses a view the crew read does not serve, a live field outside the vocabulary the live view itself declares — the field checks delegate to the views' own validators, query._refuse_unknown_live_fields and query._refuse_unknown_fields, so the accepted set and the wording of its refusal have one owner — and a runs scope or source outside the set the view serves, each naming the accepted values (that check took its set from the pre-flight's own copy of the view's constants and was later moved onto the view's own validators, below). reckon/mcp_edit_plan.py gained _refuse_unknown_op_verbs, called before the edit tool resolves the run-scoped checkout, which refuses an op whose verb is outside the grammar reckon.mcp._OP_VOCAB publishes — the one declaration, minus create, which is a parameter rather than an op key — naming the op's position and the accepted verbs.

Judged by the read that serves it. Each view pre-flight first declared a set of its own beside the read it was guarding: the crew tool carried an alias of the dispatcher's registry, and the roadmap view tuple was written out in reckon/mcp.py. A copy is a second place a name can be added or renamed, and nothing fails when the two disagree — the pre-flight then refuses a view the read serves, or admits one it does not. The declarations are gone, and each pre-flight calls the owner: mcp_views.crew_view_name for the crew view, mcp_views.normalize_view for the plan read, and a new mcp_views.normalize_roadmap_view, declared beside the roadmap view set, for the roadmap. Both new validators do no I/O, which is what lets them be reached before the scan that builds the report, and each is the same function its own read calls once it does read — so the accepted set is one fact, and a view added to the owner is admitted by the pre-flight with no second edit.

Base arm. The head test file, run against the base revision 3a985827b extracted with git archive into a scratch tree, reports 10 failed, 5 passed (EXIT=1). The five that pass are the cases the base already answered: an unknown runs scope, an unknown runs field, a plan and a roadmap naming an unknown view, and a case-spelled view reaching the plan read. The base carried no argument pre-flight at all, so it reached storage for every one of them — which is the defect this node repairs, and what the ten failures measure against.

One owner for the vocabulary. The pre-flight first restated the live vocabulary as a literal of its own, and a literal drifts: it named every field a classification carries but none that the view adds, so a live read naming section — the field a run is dispatched for, added by project_run_rows from the run's pointer — was refused from the argument while the view would have answered it. The set is now declared once in reckon/crew/query.py as LIVE_FIELD_VOCABULARY, composed from the same named parts the derivation uses, and the derivation, the view's projection and the MCP pre-flight all read it. The projection also carried no vocabulary on a narrowed request, so it judged the fleet's current rows as though they were the whole accepted set; it now carries the declaration on both paths. Two checks hold the declaration: one compares it against what a classified pointer produces, and one asserts it contains each named part, because a classification alone cannot see a name dropped from COMMON_RUN_FIELDS. A third asserts the served direction — a live read of section and the other common fields returns rows rather than a refusal — so a check that refused everything cannot read as a pass.

The served direction is asserted under the same storage stub the refusal cases use. The plan and roadmap reads match a view after stripping and lowercasing it, so view='RAW' and view='SuMMaRy' are served; the test requires the read to reach storage rather than merely to answer with something other than invalid_view, and the stub now covers the project docs resolution as well as open, since that is the first storage access a read makes here and it stats the mounts file rather than opening one. The earlier version of this case read the host's own project registry, so its verdict depended on the machine.

The op pre-flight reads its verbs from the store's own dispatch rather than from the grammar an answer publishes. read_plan returns op_vocab — every op a caller may write, which is the right thing for a caller to read and the wrong thing to judge a batch against, because it lists push. push marks a sprint active and is dispatched for a sprint alone, in apply_resource_ops; it is not in the shared handler table _OP_DISPATCH that answers every other op. Judging the batch from the grammar accepted ops=[{"op": "push"}] against a plan and let the request through to the store, which answered from the resource lookup instead of refusing the verb. The accepted set is now composed from the dispatcher itself and is per document type: accepted_op_verbs in reckon/project_state.py returns the handler table plus the ops that type is dispatched for, and the type comes from the request's own arguments without a read — the index is a project resource reached by its slug, a plan is the untyped default, every other type is named by doc_type. A test asserts one verb both ways: push is accepted for a sprint and refused for a plan, and the refusal names the verbs a plan does dispatch.

A view refusal answers one contract whichever path refused it. The plan and roadmap reads answer a ViewRequestError raised inside them through error_response, which carries error, message, operation and hint; the pre-flight answered a detail shape of its own. The pre-flight now refuses through that same function, so a caller reads one answer shape either way, and the validator's verdict keeps its own fields — the message names the view that was refused and the hint the values it accepts. The tests assert the shape and the split, not merely the error code, which is what tells the two contracts apart. The crew read carried the same divergence in the other direction: the crew tool's pre-flight and the crew view CLI both answer through serve_crew_view, and the server's own refusal answered a detail shape while the pre-flight answered the contract, so one malformed view read two different things depending on which surface asked. Both go through error_response now, and a test calls both entry points under the storage stub and asserts the two answers carry the same keys — so a refusal added to one surface alone fails it.

A pre-flight that compares the raw argument refuses what its owner serves. The runs view strips and lowercases both its source and its scope before comparing them, so source='ALL' and scope=' Project ' are served; the pre-flight tested the arguments as written against RUN_SOURCES and RUN_SCOPES and refused both. That refusal is the one a caller cannot act on — the answer names a set the caller's own value belongs to, and the read that would have answered the request never ran. The view's acceptance now lives in two no-I/O validators beside it, normalize_runs_source and normalize_runs_scope in reckon/crew/query.py, which the view calls for its own arguments and the pre-flight calls for the request's, so the accepted set and the normalisation that decides it are one fact.

Every check the two pre-flights make, with the owner it routes through: the crew view name through mcp_views.crew_view_name; the live fields through query._refuse_unknown_live_fields and the runs fields through query._refuse_unknown_fields; the runs source and scope through the two validators above; the plan view through mcp_views.normalize_view and the roadmap view through mcp_views.normalize_roadmap_view; the op verbs through project_state.accepted_op_verbs, which composes the dispatcher's own tables. Two more name their owner without restating it: the document type a batch is judged against comes from canonical_type and, for the index slug, from a rule now held in one helper — _is_project_slug — that the pre-flight and the write path both call, and the edit mode is the tool's own write path, which compares the value the pre-flight compared. Those last two are the checks whose owner normalises nothing, so their requirement is agreement rather than a served spelling, and the test asserts it that way: a table names each check and a spelling its owner normalises, and the two non-normalising checks are asserted as agreeing with their owner on a value it refuses.
