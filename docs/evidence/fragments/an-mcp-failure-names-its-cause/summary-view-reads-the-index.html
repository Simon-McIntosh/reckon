A summary read takes its inventory from the index

A one-plan summary read embeds the derived blocking from the project's plan inventory, and the plan's provenance, and both were taken by walking the docs tree and recursively globbing every HTML file, so the filesystem work of a read about one plan grew with the number of plans. The inventory rows now come from the persisted metadata index — the same source a sprint read already uses — and the selected document resolves at its canonical path instead of through the project's whole resource map. The index persists each visited directory's stat identity beside its rows: a reader with no change watch still rehashes every covered file to revalidate, and it needs the file set to do that, so recorded directory identities that all still match let it take the set from the persisted rows instead of walking the tree to rediscover it. Any difference, or an absent index, falls back to the walk and a rebuild.
