A replayed gate runs at the checkout it is replayed in, and keeps what it printed

What changed. A verify-gate replay now rewrites each worker worktree root the run records to the checkout it is replaying at, and keeps the replay's own output in a log under the run directory whose path the report cites. Both halves exist because the replay is the second measurement of a gate whose first measurement happened somewhere else: the command was authored in a worker worktree, and by the time it is replayed at the merged tree that worktree has been released.

The defect, reproduced before the repair

A stored command of the shape env -C <worker-worktree> … pytest -q <worker-worktree>/tests/… names its tree twice — as the directory it runs in and as the path of every test it names. At the base revision, with that worktree removed and a checkout whose copy of the probe passes, the replay reported:

'exit_status': 125, 'integrated_verdict': 'failed', 'base_verdict': 'passed' — env refusing to enter the directory it was told to, recorded as the merged tree failing a gate that passed where it was written. env: '<worktree>/tests/…': No such file or directory was printed into the void: the replay kept result.returncode and let the runner's stdout and stderr go, so the one artifact that said why was unrecoverable and the ids behind a genuinely red replay had to be re-measured by a second node at the same revision.

The repair

  • Where the roots come from. The run's own release audit — release.worktree_audit.worktrees[].path, present on real rows — plus a top-level worktree when the row carries one. A row that records no root replays exactly as before; there is nothing to rewrite.
  • The rewrite is at path-segment boundaries and skips a root that already resolves to the checkout, so a root is replaced where it is named as a path and never as a substring of a longer word. The text that ran is reported as worktree_roots_rewritten; the recorded gate_command stays the text the worker stored, because that is the record of what was measured at the base.
  • The log. stdout and stderr are captured as one stream and written to verify-gate.log under the run directory, in the fleet's gate-log convention — header lines naming the replayed revision, the replay's cwd and the command as executed, then the output, then a terminal EXIT=<n>. The report cites it as log_path, and the finding carries failure_ids extracted from that text by the same helper the gate-log readers use. A replay killed by its timeout writes what it produced with no EXIT= line, the absence being the fact.

Measured

The gate is the two new cases plus the four existing test files that drive verify-gate, run as one arm per revision — each arm an env -C-pinned interpreter, its own tree on PYTHONPATH, and the arm's own reckon.__file__ printed into its log:

armrevisionresult
baselineb5c8ce92 + the new cases2 failed, 72 passed — the two failures are the new cases, both on the removed worktree
aftera9ce802d74 passed, exit 0

The failing ids are two removed and none added. The first case asserts the replay ran at the checkout and reported exit 0, not 125 — and that the probe's marker file exists in the checkout, which is the executed-command receipt: the tree the command names no longer exists, so nothing else could have written it. The second replays a gate that genuinely fails and asserts the log sits under the run directory, holds the failing id and the replay's stderr, ends in EXIT=1, and that the committed row's integrated_gate_check cites the same path.

The negative control

In a scratch copy of the committed tree, the declared mutation — restore the discard of the replay's stdout and stderr in a scratch copy; the failing-gate case must fail — was applied as a return at the top of the log write, so the replay's output is discarded again while everything else stands. The failing-gate case turns red in 2.8 s with the report cites no replay log … 'log_path': None, exit 1: the case fails on the missing log and not on anything else, which is the discrimination. The red log's first line repeats the mutation verbatim, the mutated helper's text is printed under it, and the log ends in EXIT=1; it is named in the node's manifest under negative_control_log.

What is not here

No suite-wide run: this change is measured by the verify-gate gate set (74 ids), which is the set that reaches the code. The rewrite covers whichever command actually executes — stored or supplied by --command in the shape the existing cases exercise — but the new cases pin the stored path. The logs live under the run directory on this workstation, so a later reader opens them by path rather than by URL. No worker worktree is recreated and no real fleet run is replayed: the cases build a promoted row in a temporary config home and the real one is asserted untouched by this run's own id. The row's release key is read, not written, so a ledger row assembled without it is replayed unchanged.
