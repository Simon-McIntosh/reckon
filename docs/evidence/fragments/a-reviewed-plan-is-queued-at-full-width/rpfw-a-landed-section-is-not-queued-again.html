A landed section is not queued again

A plan-level dispatch asks, section by section, whether a section's work already exists. It asked the ledger documents beside a checkout, and those documents are no longer written: the run store is where a promotion puts its row. At dde7b001 a run retired its live pointer when it landed, so the live set could not answer either, and a section still declared implementable in the minute before its landing's closing write read as never delivered. A second request was queued for it. At that revision the new test reports 1 failed, 1 passed in 1.73s.

The delivery read now comes from the run store through the ledger's own picker projection, and a row is matched on the plan and section it names rather than on the node id. A section dispatched on its own carries the node id that dispatch chose, which is not the plan-level id queue_plan derives from the section, so a node-id match could not see the landed run of a section that was built as its own node. reckon/crew/dispatch_batch.py: queue_plan reads ledger.picker_runs and resolves each candidate's plan through ledger.row_plan.
