A landed run keeps its store row"> #

A request waiting on a run: ref is released when the run's promoted revision is an ancestor of the base branch. That revision was read from the run's own ledger document (reckon/crew/admission/readiness.py, _request_state), and a retention pass that removes that document leaves nothing to read: the store's archive is itself rebuilt from the committed ledger, so a run whose document has left the tree loses its hot row and its archived copy in the same rebuild. A landed run then answered as never promoted, and its waiters never released. The four §18 runs measured at the plan review are the instance: their commits are on the primary branch and no row of theirs survives anywhere in the four-pass chain.

What changed

  • The landing is kept apart from the row. reckon/run_store.py declares a landed_runs index (run_id, project, promoted_revision) in the auxiliary schema, written whenever a promoted row is appended, synced, retired to the archive, or about to be dropped by a membership rebuild. Every pass that can remove a row copies the landing out first; only an explicit delete_run or a refused landing removes it (reckon/crew/promotion_scope.py).
  • One read answers it. run_store.promoted_revision reads the index first, then the row hot before archive, through a read-only connection; the admission wait reader falls back to the run document for a project with no store, and the batch wait validator counts a retired-but-landed request as known so a released wait can still launch.

Measured

  • The declared negative control, executed and logged (negative-control.log). The pinned base 0e50b0b188 in a scratch tree built from that revision, with this node's test copied in, fails its first case with the row missing after the pruning pass: assert 'pending' == 'satisfied', 1 failed in 0.74s, closing EXIT=1. The row and the document are both gone at that point in the passing arm too, which is what proves the failure is the landing read and not the passes failing to run.
  • The head arm. At 044f4dd7 the node's three cases pass: a promoted run taken through every retention pass — archive retirement, the document leaving the tree, and the membership rebuild — is still reported landed at its commit and still releases a wait; a run discarded without landing is reported as not landed after the same passes; and a queued request held on the landed run is released and launched.
  • The gate and its arms. The scoped gate at 044f4dd7 ran 61 passed in 52.66s, EXIT=0. The baseline arm at 0e50b0b188 reported 58 passed in 54.34s and the after arm at 044f4dd7 reported 61 passed in 52.26s, both EXIT=0: the three added passes are this node's cases and the head adds no failure id.

The four §18 runs

The four runs landed as ce451ced11, ec359cbdb2, 9b8baaa6dc and dde7b00176. Each one's row is absent from the hot store, the archive, and the retirement index, and none of their documents is in the committed ledger. The pass that removed each is the store's membership rebuild (RunStore._refresh) and not the archive retirement: a retirement inserts a retired_runs row, and none of the four is there, so retire --apply never took them. The rebuild deletes rows whose document is gone from the committed ledger, and these four documents were never committed, so the first rebuild after their per-run state files disappeared removed them. No time is recorded: a membership removal writes no timestamp, and the earliest rebuild that could have run against a tree where the documents were never committed before 2026-11-21T20:19Z — the earliest run start of the four — bounds it from below and 2026-11-22T15:24Z, the store's newest archive write, from above. The attribution is by exclusion, and no surviving record dates the moment.
