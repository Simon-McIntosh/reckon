A session takes on an unowned plan only inside a shared sprint

A plan's coordinator is derived from the session that dispatched its most recent run, so taking an unowned plan on is not a separate act: it is what a whole-plan dispatch already does. Nothing constrained which plan, so any session could become the coordinator of any unowned plan in the project, including one in a sprint it does not work in. At the pinned base 11d1229dde the new test's second case fails with the plan's sections queued, reporting assert 3 == 0 over a result reading 'queued': 3.

The queue read now asks, before it answers that an unowned plan's sections may be queued, whether the dispatching session already coordinates a plan carrying the same plan-sprint the plan declares. Where it does not, every section answers with one reason and queues nothing. A plan that declares no sprint is unaffected, so the read's existing answer for such a plan is unchanged.

When a session does take a plan on, one row is appended to the project's watch stream naming the plan and the session. The row carries no session field, so it is a broadcast rather than one coordinator's run: the follower's project-wide partition puts it in every live session's own rows, the taking session's included. The append is outside the dispatch's success: a row that cannot be written never fails a dispatch whose requests were queued.

The admission service is exempt. Its purpose is to queue work that no session owns, across every sprint the project holds, so the sprint rule that constrains which unowned plans a session may take on does not apply to a dispatch filed under the service identity. The rule lives in the shared read (reckon/crew/dispatch_batch.py, _QueueReads), so the whole-plan dispatch, a single-section dispatch and the service's own pass all answer in one vocabulary.
