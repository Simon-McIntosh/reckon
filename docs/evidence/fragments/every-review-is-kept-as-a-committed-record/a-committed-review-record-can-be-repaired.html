Landing: a committed review record can be repaired

What landed

  • reckon/crew/review.py — repair_run_review takes the project the verb resolved and accepts a record at either location a run review is stored in: the host review-records directory a live reviewer delivers into, or the run's directory in the project's committed reviews tree, located through the new committed_run_review_directory (which resolves through committed_review_root). The committed location accepts a file named for its review run, because the committed store keys the file on the review run rather than the reviewed run; the staging location keeps its reviewed-run-name rule. A path under neither is still refused with the same sentence. A committed record is a tracked file, so the rewrite is committed through commit_record_write; the preserved as-delivered copy is written under <name>.asdelivered, outside the *.json glob the committed reader selects from, so the original can never be selected in place of the repair. A committed record's path names its own project, so when the caller resolves none — a promoted run whose live pointer has been cleared and whose ledger row no longer resolves — committed_record_project reads the project from docs/state/<project>/reviews/run/<run>/ and the repair commits without --project. The staging location is excluded from that inference, so a host-side record never borrows a project from its path.
  • reckon/crew/review_records.py — commit_record_write accepts one path, as a disposition writes, or a set of paths that share the one commit. A repair rewrites the record and preserves the original beside it, and the two belong to the same write; committing them apart would leave an untracked file in the committed tree.
  • reckon/crew_run_commands.py — crew repair keeps the project _accept_a_matching_project resolves and passes it through crew_repair_review into the repair, so the committed location is reachable from the command an operator runs.
  • tests/test_a_committed_review_record_can_be_repaired.py (new) — three cases over a temporary repository, crew home and mounts registry, each asserting the record the promotion gate sees rather than the file a repair rewrote. The first repairs a record held alone in the committed run directory to unparsed and asserts, before reading anything else, that select_review_for_head returns unparsed — so a repair that wrote nothing fails on the status it left behind; it then asserts the repair is committed (the committed blob reads unparsed and git status is clean for docs) and that the preserved copy is not a *.json file. The second passes no --project and asserts the same selection, the clean checkout and the committed blob, so the commit itself proves the project resolved from the path. The third writes a valid record under neither location and asserts the same refusal, with the file unchanged.

The defect reproduced before the repair

Run under the declared mutation — the pre-change directory check, which accepts only the host review-records directory — the first case fails exactly as the plan records it:

>       assert result.exit_code == 0, result.output
E       AssertionError: Error: record is outside the reviewed run's review-records directory
E       assert 1 == 0

The record sat exactly where the promotion had landed it, and the verb could not reach it. With the check extended to the committed location, the same case passes and the record reads unparsed through the gate's own selection.
