Landing: a stored review carries the total its scores make

What landed

  • reckon/crew/review.py — three helpers derive a landed record's total from its six measured dimensions. _score_total sums only when no dimension is absent; _derive_landed_total replaces the record's total with that sum and keeps a disagreeing reviewer figure under reviewer_total; _has_integer_total lets the reader tell a record that already states a total from one that omitted it. The text parser (parse_review) now routes through _score_total. store_review derives on every landed write. read_review derives only for a record that carries no integer total of its own, so an older unsummed record reads complete while a record that already states one reads as stored. The claims rubric is unchanged, and the existing added-failure cap is applied after the derivation, as it is to the text path.
  • tests/test_a_stored_review_carries_its_total.py (new) — six cases: sum-without-a-reviewer-total reads back complete; a missing dimension withholds the total and reads incomplete; a disagreeing reviewer total is kept beside the derived sum; a record written straight to the store without a total reads complete; an unretired added failure caps the derived total; a claims record keeps its own shape.
  • tests/test_review_counts_added_failures.py — the no-lowering case now makes its six dimensions sum to the cap before asserting that capping leaves the total unchanged, so it measures the same intent under a derived total.
  • tests/test_one_automatic_repair_round_per_run.py — the repair-round fixture stored six dimension scores of 15 (sum 90) beside a recorded total of 75, numbers that contradict each other, so the hand-back reason named the derived 90 while the test asserted the recorded 75. The six scores now sum to the recorded total, so the stored and the derived total are one number and the assertion reads the round cap on every run.

Why the repair-round test flipped between runs

The test asserts "75" in reason. At this head the derived total is 90, so the reason reads this review scores 90; the only other literal text in it is the round id r-reviewed@<first-head-sha>, the attempt count and the prose. The assertion is therefore satisfied only when the fixture repository's random first-head sha happens to contain the substring 75 — a property of the commit timestamp, not of the revision or of any stored state.

  • state-probe-findings.md in the run directory carries the full evidence, including five isolated runs that fail with scores 90, thirty more that fail twenty-nine times, and a strace run that imported this worktree's review.py and made no open under the operator's real review store.
  • The decisive pair fixes only the commit timestamp at the same head: with the sha 182fabd498ff26aa6362d23a846754aa513fcde3 (contains 75) the test passes; with a timestamp whose sha has no 75 it fails naming 90.
  • The derived total is uniform across read paths: the store's index caches paths and heads only and re-reads the selected file, so no cached read can serve an underived total.
