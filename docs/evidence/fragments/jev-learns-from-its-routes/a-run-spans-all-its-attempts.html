A promoted run's timing spans every attempt it made

Defect. A run that moved lane or resumed many times keeps one timestamped stream — its first, claude attempt — beside streams that carry no event timestamps at all. The end and the span were read from the first stream, so a morning of work was recorded as its opening two minutes. The primary run r-20261015T160647356198-fast-map-production ran from 2026-10-15T16:07Z to 2026-10-16T03:11Z, mostly on a codex client with twenty resumes sharing one thread; its committed row records completed_at 2026-10-15T16:08:25.469Z, wall_seconds 76 and worker_seconds 18, all three measured on the two minutes before its first lane change.

Change. promotion_checks._terminal_stream_data now folds every attempt the run made. A timestamped stream contributes its own event span and its last event's instant; a stream with no timestamps contributes its file mtime as an attempt end and, where its codex session has a rollout receipt, that receipt's generation_seconds plus machine_seconds as that session's span. The run's end is the latest attempt end, named by completed_at_source (terminal_event or stream_mtime), and worker_seconds is the sum, with worker_seconds_source naming the composition (stream_events+rollout_receipts). Sessions are counted once, so two streams resuming one codex session do not double its span. rollout._locate_rollout and rollout.read_rollout_receipt take the run id through to the run-home lookup, so a receipt is found under the run's own codex-home and not only in the client's shared session home. A run with a single attempt takes the path it always took: a claude stream keeps terminal_event with stream_events, a codex stream keeps stream_mtime with rollout_receipt.

Measure. tests/test_a_run_spans_all_its_attempts.py passes 4/4 with a temporary crew home: a timestamped first-attempt stream ending at T1 beside two codex streams whose receipt-bearing sessions end at T2 and T3 promotes with completed_at at T3, the wall span from dispatch to T3, and worker_seconds the first stream's 19 s span plus both receipts (120 s and 230 s) = 369 s under stream_events+rollout_receipts; one session reached through two streams is counted once; and a single-attempt claude run and a single-attempt codex run each record what they record on the base revision. The negative control reads timing from the first timestamped stream only, and the multi-attempt tests then fail on the first attempt's end (assert '2026-10-15T16:08:25Z' == '2026-10-15T18:00:00Z').
