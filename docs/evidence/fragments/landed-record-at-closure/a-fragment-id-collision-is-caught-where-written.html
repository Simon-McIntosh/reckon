Landing: a fragment id collision is caught where it is written

The brief now tells a fragment-writing node that every element id carries its node id, check-manifest audits a plan's composition whenever a run declares a change to one of that plan's fragments — through the plan's landing record when one exists, and over the fragments together when it does not, because the record is synthesised once, at closure — and the three fragments of the-obligations-hook-reads-a-snapshot that had already claimed each other's anchors are renamed under their node ids.

What landed

  • reckon/crew/prompts.py — the landing brief states that every element id in the fragment begins with the node id, so sibling fragments composed into one record cannot claim the same anchor. The sentence sits after the small-node rule, whose adjacency an existing test pins, and before the figure sentence.
  • reckon/doccheck.py — audit_composed_record_ids(record_path, plan_slug, project=None) returns the duplicate-element-id findings for a record composed with its plan's fragments, through the same composition and the same finding text audit-doc uses, so the two surfaces describe a collision in one wording. The caller names the plan from the fragment's own directory rather than reading it back from the record's plan-evidence-for meta: a record whose meta is missing or names another plan would otherwise be composed without the fragments that put it at risk and the check would pass silently. A second entry point, audit_fragment_ids(fragment_dir), composes a plan's fragments alone — each read as its body, the way composition appends it — for a plan whose record does not exist yet, and reports a duplicate in the same wording.
  • reckon/crew/reports.py — check-manifest collects the plans named by the run's declared changed paths under docs/evidence/fragments/<plan>/<node>.html, audits each such plan's composition in the run's worktree, and reports every duplicate as [duplicate-element-id] naming the id and the fragments that carry it. A run that changes no fragment is not audited. A plan whose landing record does not exist yet is audited over its fragments together: the record is synthesised once, at closure, so until then the fragments are the composition a reader will meet, and two of them that reuse an id collide with each other. A path that is not a fragment file is not read as one.
  • tests/test_fragment_ids_are_checked.py (new) — five cases driving check-manifest against a temporary repository: a new fragment repeating a committed fragment's id is refused by name, the run passes once that id is prefixed, a run changing no fragment is not audited, a lone fragment of a recordless plan has nothing to collide with, and a recordless plan whose second fragment repeats the first's id is refused naming the id and both fragments.
  • Three fragments of the-obligations-hook-reads-a-snapshot repaired — landing-what-landed, landing-measure and landing-commits in worktree-held-names-an-existing-tree.html, held-worktrees-fast-path-names-differ.html and a-worktree-held-row-is-rechecked-at-read.html are renamed with the writing node's id, nine renames in all. No same-fragment href pointed at them, and landing-reproduction in the middle fragment was never colliding, so it is unchanged.
  • Two tests pinning the brief text updated with it: tests/test_crew_prompts.py asserts the rule reaches a fragment-writing node's prompt, and tests/test_brief_prompt.py's snapshot carries the sentence.
