A dispatch can name a model inside a lane

crew dispatch --model KEY resolves the name through the catalogue's one resolver (reckon/ledger.py::resolve_name) and narrows it to the backend whose expanded entry serves that (lane, model_key) pair. A model key, a model id and an alias all reach the same backend the legacy <lane>-<key> spelling names, so --model opus beside --backend claude is the same route as --backend claude-opus. A bare --model two lanes declare is refused naming both lanes; a name no lane declares is refused, never guessed. Because the narrowing happens on the request, a named lane or model stays authoritative and no shadow selection is recorded.

The two sibling surfaces that already take --backend take --model as well. crew preflight resolves each named model to the backend that serves it and checks that backend's budget; crew shadow narrows a named model to the backend serving it before it builds the routing override, so a shadow re-run reaches the same configuration a caller would get from the legacy backend name.

A promoted run row and its bytes now carry lane and model_key beside backend, resolved through the same catalogue resolver at record time, so a reader carries the pair without re-resolving a backend name that may since have retired.
