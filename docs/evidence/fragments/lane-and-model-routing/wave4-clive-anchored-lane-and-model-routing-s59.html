A dispatch waits for the router's answer, and a default route is never silent

A dispatch asked the picker inside a five-second bound, and on expiry it placed the request on the configured default lane and returned a selection that read as an ordinary fallback: a route the router never weighed, indistinguishable from one it gave. Three things changed. The bound is 120 s by default and a flight's routing.picker_timeout_seconds sets it (reckon/crew/dispatch_picker.py, picker_dispatch_timeout). The section's capability and declared effort are resolved by the dispatcher before the ask (dispatcher_declared_difficulty) and travel on PickRequest as capability and estimated_hours, so the pick's own difficulty step resolves nothing inside the bound (reckon/crew/picker/__init__.py, _declared_difficulty returns on the "request" source). A pick still running at the bound now sets awaiting_pick on the selection, and plan_dispatch stores the request as a queued pointer with reason: awaiting-pick and raises the lane hold that reports where it waits, rather than routing it. A stored request whose pick never answered is picked again at launch through the existing launch_route_* decision, which reads its awaiting_pick marker as a re-pick. A pick that fails rather than expires still falls back, and the fallback carries route_defaulted naming the step that ran out, so a default route is reported with the work that produced it.

Measure: tests/test_a_dispatch_waits_for_the_router.py ran 4 passed in 10.36 s at this revision. Its four cases are, in order, that the dispatcher resolves the section's deep capability and its 6 declared hours and the pick is handed both with no plan read on its difficulty step (the plan resolver is replaced by a raiser and none fires); that a pick answering after 8 s is routed where it answered, which the old 5 s bound could not do; that a pick that never answers leaves backend: null with awaiting_pick at the bound and the stored pointer reads phase: queued, reason: awaiting-pick, and the launch decision calls repick rather than replaying a default; and that a failing pick carries route_defaulted naming its step and the failure's own text. The negative control restores the 5 s bound with default routing, and the second and third cases fail (3 failed, 1 passed, EXIT=1, the third failure being the fallback marker the same mutation removes).

Suite arm: the base revision ed0ca92be6 and this head both ran 7 failed, 61 passed, EXIT=1 over the six picker- and dispatch-importing test files, with no failure id added at the head, so the change adds no failure against its base. The node's own test file fails all four cases at the base revision (4 failed, EXIT=1), which is what makes it a measure of this change rather than of the tree. ruff check reports All checks passed! and ruff format --check reports the five declared paths already formatted.

One deliverable is met short of its full surface. The fallback's route_defaulted marker is recorded on the selection and reaches the dispatch payload, but the obligations view does not yet list it as a duty: that listing lives in reckon/crew/obligations.py and reckon/crew/picker/recovery_classification.py, which this node does not hold. The flight key is read defensively from config["routing"]; declaring it in reckon/flight.py and the flight schema is likewise outside this node's paths, so an undeclared key falls back to the 120 s default instead of being refused.
