A lane model launches at the effort and time budget it declares

Launch settings now resolve in one order, highest first: a value the dispatch sets explicitly, then a key the selected lane model declares in lanes.<lane>.models.<key>, then the role, spec-level and capability-class overlays, then everything else in the backend's block. _effective_backend applies the selected lane model's keys last, read from that mapping through the backend's own lane and model_key; a backend carrying neither, such as a catalogue backend that is no lane model, keeps the overlay's value. snapshot.candidates builds each lane model's row through flight.select_lane_model and then routing.resolve_role_override — the two steps dispatch takes — and no longer updates the model's settings itself, so each row carries its own model_key instead of the lane default's. The picker's rows and the dispatch therefore share one calculation.

The new gate file resolves a flight with a codex lane (sol high, astra xhigh with time_budget: 55m, luna xhigh), a claude lane (sonnet medium), a non-lane backend at xhigh, roles.implement.time_budget: 8m and roles.implement.by_spec_level.exact.effort: high, and asserts astra launches xhigh/55m, luna xhigh/8m, sol high/8m, sonnet medium/8m, the non-lane backend high, an explicit --time-budget 33m and an explicit --set lanes.codex.models.astra.effort=high-style effort override winning on astra, and that every candidate row the picker offers carries the effort, time budget and model_key the dispatch path resolves.
