catalogue-declares-lanes — the model catalogue declares lanes with a default model each, plus an alias table old names resolve through

docs/state/reckon/model-catalogue.yaml gains a lanes: block regrouping its eight backend entries under three lanes, each with a default_model and its models keyed: claude (default sonnet) offering sonnet, opus, haiku; codex (default sol) offering sol, astra, luna; and clive (default flash) offering flash. Each model carries the same model/effort/alias/budget_group values its backends: entry already had, and the eight backends: blocks are kept unchanged so the new grouping can be compared with the old one directly.

Alias table. A top-level aliases: table maps each legacy backend name to the (lane, model_key) pair it names: claude-opus, claude-haiku, codex-astra, codex-luna (live), and codex-terra, codex-spark, clive-glm (retired). The table is history, not routing — a stored ledger row or run record is never rewritten, so a name whose backend block has retired still resolves to a pair. codex-terra and codex-spark name codex models the lane no longer offers, and clive-glm a clive model that retired; the test asserts these are exactly the names with no declared model behind them, so a live alias whose model is deleted reddens. The field is model_key in the catalogue entries, matching the plan's own wording and §7's resolve_tuple -> (lane, model_key) signature (the design report used model as shorthand — recorded for the §7 node).

Schema source. The catalogue schema had no slot for either block, so reckon/schema/flight.yaml gains a top-level aliases slot (range ModelAlias, inlined) and a ModelAlias class with lane and model_key slots, added to FlightConfig.slots. reckon/_flight_schema.py and docs/_shared/flight.schema.json are regenerated from it with scripts/regen_flight_schema.py; neither generated file is hand-edited, and the round-trip tests below assert both match the source. reckon/flight.py lists aliases among _KEYED_MAPS.

LANE_MODEL_KEYS in reckon/flight.py hand-clear-copied LaneModelConfig's field list; it is now derived from the generated model (_lane_model_keys() reads LaneModelConfig.model_fields less the map-key name), and tests/test_flight_lanes.py::test_lane_model_keys_are_the_generated_model_fields pins the derivation, so a hand-copied list that drifts from the schema fails.
