A batch dispatch holds a bounded amount of memory

A crew dispatch --batch asks, once per entry, whether the node it is about to queue has already been delivered. That answer was read from the project's whole promoted history: every row decoded with the wide detail a promotion records, then filtered in Python. Queuing eight entries therefore decoded everything the store held, and the batch's peak resident memory grew with the store rather than with the work it was asked to place.

The read now asks the store's own plan and node index for the rows of the node it is about to queue, projected to the six fields a hold decision reads (run_id, node, plan, section, role, completed_at). What the module caches is the hold index the decision builds — one small record per delivered node — and not the decoded rows behind it. Queuing one node decodes its own rows: 3 in the test's 603-row store, unchanged when the store is doubled to 1,203, against 603 and 1,203 for the read it replaced. The new tests/test_dispatch_batch_memory_profile.py measures the rows actually decoded through the store's one decode point, so a projection that decoded the population and then dropped it would fail the measure rather than pass on its answer.

The head peaks at 0.83 and 0.96 of the base at eight and forty entries — below the 0.5 the section asked for, so the criterion is not met — and the head's peak no longer grows with the batch's width (12.32 GiB at eight and 12.62 GiB at forty before the index cache, 11.71 and 11.75 after it). The decoded population fell from 51,769 rows and 2.34 GB to 34,972 rows and 0.69 GB at eight entries, and from 120,692 rows and 6.57 GB to the same 34,972 rows and 0.69 GB at forty: the read is now bounded by the node, not by the batch's width.

What did not move is the peak, and a resident attribution pass says why. At the base, 11.81 of an 11.82 GiB resident high-water mark is anonymous heap against a traced Python heap peak of 3.34 GiB, so about 8.5 GiB is allocator-retained churn from decode traffic rather than memory the hold read keeps live. Doubling the prepared store's delivered-run rows from 12,266 to 24,532 takes the head's forty-entry peak from 11.75 GiB to 22.19 GiB, an 89 % rise against the 10 % the section allows, and the base's from 12.25 GiB to 24.62 GiB, a 101 % rise that satisfies the section's negative control. Both arms grow by about the same amount, so the population the batch decodes is not the hold read: roughly 19,500 main-store and 15,500 archive rows per pass are decoded on the roadmap's section-history read, which covers the section's whole plan set and stays population-wide. That read is outside this node's write paths, and the section's 0.5 ratio and 10 % doubling bound move to a section that owns it.

A review of the first landing found that the read had its own answer for a store that holds no promotions. A store exists for a project's mutable state before anything is promoted into it, and the store reports that as an empty list rather than as absence, so a ledger-only project's delivered nodes read as free and the queue could queue a node it had already built. The repair adopts the ledger's own rule — any empty answer falls through to the committed ledger — and the fallback read is ledger.picker_runs, as the whole-population read always did.

The same review found the index kept a node's last row in iteration order, and the store answers hot rows before retired ones, so a node re-promoted after its first row was retired kept the retired record. Rows are now ordered by ledger.promotion_order_key, the ledger's own answer for the position a row takes in the union of the two sources, before the last row per node is kept. One case in the node's test file covers each repair, and both fail against the revision before it: the store-with-no-promotions case answers from the ledger and the retired-row case answers with the later delivery; that run ends EXIT=1 with both cases named against EXIT=0 at the repair head.

The gate is the node's own file plus the two files that cover the section-hold read and its plan fallback: tests/test_dispatch_batch_memory_profile.py, tests/test_staged_write_inventory.py and tests/test_every_shared_home_lock_holds_across_nodes.py at head, and the last two at the base revision, because the node's file does not exist there. Both arms exit 0 on rigel. The two covering files alone run at head as 15 passed, EXIT=0.
