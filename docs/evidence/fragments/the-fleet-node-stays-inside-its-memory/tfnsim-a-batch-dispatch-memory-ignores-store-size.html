A batch dispatch's store read follows the batch, not the run store

Three reads on a batch's queueing path followed a population rather than the batch. The plan-history read asked the ledger for the project's whole projected history to decide whether one of a plan's own sections had been delivered, and every plan the batch queued paid that projection again. The roadmap was derived once per project through project discovery over the whole inventory, so every plan document the project carries cost the batch a derivation of it. And the section-hold index kept its own dict, its own eviction rule and its own reset path beside the shared memo that already does that job for every other cache in the process. Two further reads kept the batch's footprint tied to the store's row count after those three were narrowed: the landing verdict behind each entry's wait check asked the ledger for one plan's whole history and decoded every field of every row, and the lane advisory's rate window decoded the project's activity-windowed history, neither of them a population the batch names.

Each read now follows what the batch names. The plan-history read selects that plan's rows in the store's own plan index, resolving the plan through the same three fields row_plan reads, and falls through to the committed ledger only when the store holds nothing for the project at all. The batch's roadmap is derived over the plans it names, so a project with 240 plan documents is not derived once for each of them. The section-hold index asks file_memo.bounded_map for its store, so the bound, the lock and the LRU order are the shared ones and file_memo.clear() empties it with the rest of the memo. Nothing the batch decides changes: the store answers with the same rows the projection gave after filtering, and the roadmap rows the wait check reads are the ones the plan set carries. The prior round's empty history scope stays in place. The landing verdict and the lane advisory now ask the store for the fields each decides from — the identity fields row_plan resolves a plan through plus the promoted revision the verdict checks, and the run, lane, model, completion time and throughput the rate consumes, with its activity window applied in SQL — so neither read carries a row's brief or budget into the process. Both were changed under a scope extension granted for them, and the cases added here hold each projection to its field set.

The home is a copy of the crew home whose store carries the project's promoted history: 10,192 promoted rows over 240 plan documents, each recording its plan on the impl move as a brief-carried dispatch does, so a reader that asks for the narrow projection must read the fallback fields as well. Each seeded row carries one of this store's 93 recorded promotion payloads, cycled, with its identity fields rewritten and its width capped at 200,000 bytes so that one promotion's multi-megabyte list is not cycled onto every row. The widths are therefore the ones this project's promotions record, with a median payload of about 48 kB, and the detail is the recorded document. The live store copy holds only a few dozen promoted rows for this project's plans, so a criteria test on it alone cannot show the term the section is about. Every tree's discovery index is written once before its arms, unprofiled, so an arm measures the batch rather than a first-ever parse of its own corpus; without that, the plan-doubled tree pays for 498 never-seen documents while the arm it is compared against pays for none, and the difference is the instrument rather than the batch. The seeding is the same for both revisions, so only the code differs between the bars.

The store read is what the change was for, and it moves in both dimensions. At eight entries the batch reads 57,073 store rows and decodes 30,981 of them at the base revision, against 276 rows and 144 decodes here. At forty entries the base reads 74,931 rows and 30,981 decodes against 1,104 rows and 144 decodes. The base reads essentially the same population at either width, because the projection it decodes is the project's whole promotion history; the rows here are the plans the batch names and the answers to its entries, so the read grows with the batch (4.0 times from eight entries to forty) while what it decodes does not (144 rows at either width).

All three criteria hold on this home. The base revision here is 4a98aef29769, the revision the section's memory measure names; it is not the fence's suite base 0d4e508516652090a9d97e8198f92cd21e2105e0, whose arms are recorded separately under the gate below. The eight-entry peak moves from 2.91 GiB at that base revision to 0.41 GiB here, a ratio of 0.14 against the 0.5 the section asked for. Doubling the store's delivered-run rows, from 16,128 to 32,256 hot rows, takes this change's forty-entry peak from 0.41 to 0.38 GiB, a rise of -8.6 % against the 10 % allowed. Holding the batch and the store fixed and doubling the project's plan documents, 249 to 498, takes it from 0.41 to 0.44 GiB, a rise of +6.2 %. The negative control holds: at the base revision the same store doubling takes the forty-entry peak from 2.49 to 4.34 GiB, a rise of +73.8 %. Every arm quoted here was measured in one job on copies of one prepared snapshot, the store-doubled snapshot being cut from that same seeding before any arm ran; the head's single-store arm was repeated 4 times and its doubled-store arm 4 times. Those repetitions span 0.39 to 0.44 GiB on the single-store arm, 0.34 to 0.43 GiB on the doubled-store arm and 0.44 to 0.44 GiB on the plan-doubled arm, and the base's forty-entry arm spans 2.49 to 2.50 GiB. The first two spans overlap, so the peak cannot separate the store doubling from the run-to-run spread at this size; each criterion is read from the arm's median, and the store's own share is measured where it is deterministic: doubling the store doubles the rows decoded, 144 to 288, and the payload decoded with them, 1.26 MB to 2.52 MB, a difference of 0.3 % of the 0.41 GiB peak.

Every forty-entry arm ends EXIT=1, and the reason is the same on the base revision and here: one entry names a node whose declared write paths exceed the model's context window, so that entry is refused before its pointer is written and the pass stores thirty-nine of forty. The pass still walks all forty entries, and the profiler reports the refusal after the walk, so the peak covers the whole batch; the refusal is scaffold-level and identical across the arms, which is what makes the comparison like for like.

§14's peaks at this base revision were measured on a home prepared by §8's node, which its run directory no longer holds, and that home is not reproduced here: §8 recorded 11.71 GiB at this base revision for eight entries, against 2.91 GiB on the home built here. What the criteria test is the ratio between the two revisions and the growth of each with its input, and those are read from arms taken on one home in one job. The magnitudes are this home's.

The criterion that did not hold in the prior round was the store doubling, and the two reads that owned it were outside this node's files and were changed on the scope extension granted for them. A read trace over the prepared home had attributed every decode to two call sites: the landing verdict at crew/admission/readiness.py and the lane advisory at crew/recovery_stream.py. The verdict now projects onto the identity fields row_plan resolves a plan through and the revision it checks, and the advisory onto the run, the lane, the model, the completion time and the throughput, with its activity window applied in SQL. The batch decodes 1.3 MB as prepared and 2.5 MB with the store's delivered-run rows doubled, moving 144 rows to 288 against 30,981 at the base revision, and the peak no longer follows either dimension.

tests/test_a_batch_dispatch_memory_ignores_store_size.py holds six cases. Four count what the batch reads through the store's one decode point: a batch queueing one node decodes the same count over a store and over that store with its delivered-run rows doubled, a control names the delivered node and requires exactly one row decoded so a zero is a measurement rather than a dead counter, a node with no delivered row costs no decode, and the section-hold index is the shared bounded map that file_memo.clear() empties. A fifth requires one store read per named plan, the holds of those plans' sections only, and the committed ledger as the fallback for a store holding nothing. The last two hold the projections to their fields: each asks the store for its own field set and requires that the rows it receives carry nothing beyond it. The first two fail at revision 0d4e508516652090a9d97e8198f92cd21e2105e0, which recorded 2 failed in 1.03s; the two projection cases fail against the sources this round replaced, which recorded 2 failed, 4 passed in 74.50s (0:01:14), while the same file at this head records 6 passed in 33.93s.

The gate is the node's own file plus the two that cover the batch's home handling, run on rigel. The base arm runs the two home-handling files at revision 0d4e508516652090a9d97e8198f92cd21e2105e0 and records 58 passed in 46.09s, EXIT=0. The head arm runs all three files at revision b89ea93f3b11e345c6f658dd56a7f10a0e18c9b7 and records 64 passed in 207.67s (0:03:27), EXIT=0. Each log carries its own revision, host, tree and literal command above those result lines.
