A batch dispatch's store read follows the batch, not the run store

§8 bounded the section-hold read and left the roadmap's section-history read covering the project's whole plan set on every batch pass. §8's own text put the remaining driver at about 19,500 main-store and 15,500 archive rows per pass. A batch builds each project's roadmap once and serves every reader inside it from that derivation, but queueing writes a run row, which bumps the store's stamp, which invalidates the hold index the roadmap was built from — so a batch of forty entries rebuilt the project's history several times over, and the read grew with the batch's own width as well as with the store.

A batch now builds its roadmap inside roadmap_history_scope(()). The scope empties the set of plans whose promoted history a roadmap build consults, so the section-history read is skipped and the attempts aggregate is not computed, while the duplicate check the batch needs is untouched: that is the per-entry held_node_rows read, which the store answers from its own node index. The scope is a context variable and is restored on exit, so no other reader of the roadmap sees it. Nothing the batch decides changes: its only roadmap reader is the wait check, which reads gate and decision blockers and never a section's run holds.

The home is a copy of the crew home whose store carries the project's promoted history: 10,192 promoted rows over 240 plan documents , each recording its plan on the impl move as a brief-carried dispatch does, so a reader that asks for the narrow projection must read the fallback fields as well. Each seeded row carries one of this store's 48 recorded promotion payloads, cycled, with its identity fields rewritten and its width capped at 200,000 bytes so that one promotion's multi-megabyte list is not cycled onto every row. The widths are therefore the ones this project's promotions record, with a median payload of about 48 kB, and the detail is the recorded document. The live store copy holds only a few dozen promoted rows for this project's plans, so a criteria test on it alone cannot show the term the section is about. Every tree's discovery index is written once before its arms, unprofiled, so an arm measures the batch rather than a first-ever parse of its own corpus; without that, the plan-doubled tree pays for 498 never-seen documents while the arm it is compared against pays for none, and the difference is the instrument rather than the batch. The seeding is the same for both revisions, so only the code differs between the bars.

The store read is what the change was for, and it moves in both dimensions. At eight entries the batch reads 67,778 store rows and decodes 30,903 of them at the base revision, against 22,726 rows and 191 decodes here. At forty entries the base reads 85,636 rows and 30,903 decodes against 26,248 rows and 191 decodes. The base's forty-entry read is 1.3 times its eight-entry read, which is the stamp-invalidated rebuild; here the ratio is 1.2 and every row read is a node the batch names or a read that answers one of its entries.

The criteria do not all hold on this home: the store doubling, the plan-document doubling falls outside its bound. The eight-entry peak moves from 3.12 GiB at the base revision to 1.55 GiB here, a ratio of 0.50 against the 0.5 the section asked for. Doubling the store's delivered-run rows, from 16,055 to 32,110 hot rows, takes this change's forty-entry peak from 1.40 to 1.64 GiB, a rise of +17.1 % against the 10 % allowed. Holding the batch and the store fixed and doubling the project's plan documents, 249 to 498, takes it from 1.40 to 1.62 GiB, a rise of +15.7 %. The negative control holds too: at the base revision the same store doubling takes the forty-entry peak from 3.06 to 4.59 GiB, a rise of +49.8 %.

Every forty-entry arm ends EXIT=1, and the reason is the same on the base revision and here: one entry names a node whose declared write paths exceed the model's context window, so that entry is refused before its pointer is written and the pass stores thirty-nine of forty. The pass still walks all forty entries, and the profiler reports the refusal after the walk, so the peak covers the whole batch; the refusal is scaffold-level and identical across the arms, which is what makes the comparison like for like.

§14's peaks at this base revision were measured on a home prepared by §8's node, which its run directory no longer holds, and that home is not reproduced here: §8 recorded 11.71 GiB at this base revision for eight entries, against 3.12 GiB on the home built here. What the criteria test is the ratio between the two revisions and the growth of each with its input, and those are read from arms taken on one home in one job. The magnitudes are this home's.

The head still returns 26,248 store rows at forty entries, and they rise to 46,968 when the store's delivered-run rows double, which is the rise the store criterion measures. The rows are projections, not payloads: the project's whole run history, read without decoding, from the per-entry planning step that asks the ledger for the history a section decision needs (ledger.picker_runs in the batch's section walk). The change here removed the section-history read and its decodes; this projection is a different read, in this node's own file, and narrowing it changes what the picker sees for an entry, so it is a separate change with its own measure.

tests/test_a_batch_dispatch_memory_ignores_store_size.py counts the rows the store decodes, through its one decode point, for a batch queueing one node over a store and over that store with its delivered-run rows doubled: the counts are equal, and a second case requires zero rows decoded for a node with no delivered row. A control arm names the node that was delivered and requires exactly one row decoded, so a zero is a measurement rather than a dead counter. Both cases fail at revision 0d4e508516652090a9d97e8198f92cd21e2105e0, which recorded 2 failed in 1.03s and ended EXIT=1.

The gate is the node's own file plus the two that cover the batch's home handling, run on rigel at the repair head; the base arm runs the two home-handling files at revision 0d4e508516652090a9d97e8198f92cd21e2105e0.
