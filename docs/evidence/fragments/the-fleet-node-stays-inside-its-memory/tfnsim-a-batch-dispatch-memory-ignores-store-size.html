A batch dispatch's store read follows the batch, not the run store

§8 bounded the section-hold read and left the roadmap's section-history read covering the project's whole plan set on every batch pass. §8's own text put the remaining driver at about 19,500 main-store and 15,500 archive rows per pass. A batch builds each project's roadmap once and serves every reader inside it from that derivation, but queueing writes a run row, which bumps the store's stamp, which invalidates the hold index the roadmap was built from — so a batch of forty entries rebuilt the project's history several times over, and the read grew with the batch's own width as well as with the store.

A batch now builds its roadmap inside roadmap_history_scope(()). The scope empties the set of plans whose promoted history a roadmap build consults, so the section-history read is skipped and the attempts aggregate is not computed, while the duplicate check the batch needs is untouched: that is the per-entry held_node_rows read, which the store answers from its own node index. The scope is a context variable and is restored on exit, so no other reader of the roadmap sees it. Nothing the batch decides changes: its only roadmap reader is the wait check, which reads gate and decision blockers and never a section's run holds.

The store read is what the change was for, and it moves in both dimensions. At eight entries the batch reads 6,247 store rows and decodes 117 of them at the base revision, against 2,086 rows and 30 decodes here. At forty entries the base reads 24,105 rows and 117 decodes against 5,608 rows and 30 decodes. The base's forty-entry read is 3.9 times its eight-entry read, which is the stamp-invalidated rebuild; here the ratio is 2.7 and every row read is a node the batch names or a read that answers one of its entries.

The section's peak criteria are not met on this prepared home. The eight-entry peak moves from 1.33 GiB at the base revision to 1.47 GiB here, a ratio of 1.10 against the 0.5 the section asked for. Doubling the store's delivered-run rows, from 5,851 to 11,702 hot rows and 8,412 to 16,824 retired rows, takes this change's forty-entry peak from 1.51 to 1.68 GiB, a rise of +11.4 % against the 10 % allowed — missing it by a little. The negative control is met: at the base revision the same doubling takes the forty-entry peak from 1.47 to 1.75 GiB, a rise of +19.4 %.

Every forty-entry arm ends EXIT=1, and the reason is the same on the base revision and here: one entry names a node whose declared write paths exceed the model's context window, so that entry is refused before its pointer is written and the pass stores thirty-nine of forty. The pass still walks all forty entries, and the profiler reports the refusal after the walk, so the peak covers the whole batch; the refusal is scaffold-level and identical across the arms, which is what makes the comparison like for like.

Holding the batch and the store fixed and doubling the project's plan documents, 249 to 498, takes this change's forty-entry peak from 1.51 to 1.80 GiB, a rise of +19.0 % — larger than the store's. That is the decomposition the criteria needed: on this home the peak is set by the batch's parse of the project's plan documents, not by the store. Each arm's own allocation sample agrees: about 460 MiB traced at the head, of which the largest sites are the plan-document parse (HTML and JSON), while the store's whole contribution is the 5,608 projected rows it returns.

§14's peaks at this base revision were measured on a home prepared by §8's node, which its run directory no longer holds, and that home is not reproduced here: §8 recorded 11.71 GiB at this base revision for eight entries against 1.33 GiB on the home built here. Two homes were prepared for this measure — one with the home's mount table emptied, one with the live mount table kept — and both give the same order, so the difference is not in what the batch resolves its plans from. Until a home reproducing that magnitude is prepared, the section's peak criteria can be neither met nor refuted: they are a statement about a home where the store read dominates the peak, and on either home built here the plan-document parse does.
