A batch dispatch's store read follows the batch, not the run store

Three reads on a batch's queueing path followed a population rather than the batch. The plan-history read asked the ledger for the project's whole projected history to decide whether one of a plan's own sections had been delivered, and every plan the batch queued paid that projection again. The roadmap was derived once per project through project discovery over the whole inventory, so every plan document the project carries cost the batch a derivation of it. And the section-hold index kept its own dict, its own eviction rule and its own reset path beside the shared memo that already does that job for every other cache in the process.

Each read now follows what the batch names. The plan-history read selects that plan's rows in the store's own plan index, resolving the plan through the same three fields row_plan reads, and falls through to the committed ledger only when the store holds nothing for the project at all. The batch's roadmap is derived over the plans it names, so a project with 240 plan documents is not derived once for each of them. The section-hold index asks file_memo.bounded_map for its store, so the bound, the lock and the LRU order are the shared ones and file_memo.clear() empties it with the rest of the memo. Nothing the batch decides changes: the store answers with the same rows the projection gave after filtering, and the roadmap rows the wait check reads are the ones the plan set carries. The prior round's empty history scope stays in place; this round moved the two reads that scope could not reach.

The home is a copy of the crew home whose store carries the project's promoted history: 10,192 promoted rows over 240 plan documents , each recording its plan on the impl move as a brief-carried dispatch does, so a reader that asks for the narrow projection must read the fallback fields as well. Each seeded row carries one of this store's 50 recorded promotion payloads, cycled, with its identity fields rewritten and its width capped at 200,000 bytes so that one promotion's multi-megabyte list is not cycled onto every row. The widths are therefore the ones this project's promotions record, with a median payload of about 48 kB, and the detail is the recorded document. The live store copy holds only a few dozen promoted rows for this project's plans, so a criteria test on it alone cannot show the term the section is about. Every tree's discovery index is written once before its arms, unprofiled, so an arm measures the batch rather than a first-ever parse of its own corpus; without that, the plan-doubled tree pays for 498 never-seen documents while the arm it is compared against pays for none, and the difference is the instrument rather than the batch. The seeding is the same for both revisions, so only the code differs between the bars.

The store read is what the change was for, and it moves in both dimensions. At eight entries the batch reads 67,800 store rows and decodes 30,913 of them at the base revision, against 23,376 rows and 203 decodes here. At forty entries the base reads 85,658 rows and 30,913 decodes against 28,257 rows and 211 decodes. The base's forty-entry read is 1.3 times its eight-entry read, which is the population read widening with the store; here the ratio is 1.2 and every row read is a node the batch names or a read that answers one of its entries.

The criteria do not all hold on this home: the store doubling falls outside its bound. The eight-entry peak moves from 2.81 GiB at the base revision to 0.96 GiB here, a ratio of 0.34 against the 0.5 the section asked for. Doubling the store's delivered-run rows, from 16,049 to 32,098 hot rows, takes this change's forty-entry peak from 1.15 to 1.33 GiB, a rise of +15.7 % against the 10 % allowed. Holding the batch and the store fixed and doubling the project's plan documents, 249 to 498, takes it from 1.15 to 1.10 GiB, a rise of -4.6 %. The negative control holds too: at the base revision the same store doubling takes the forty-entry peak from 2.74 to 4.19 GiB, a rise of +53.2 %.

Every forty-entry arm ends EXIT=1, and the reason is the same on the base revision and here: one entry names a node whose declared write paths exceed the model's context window, so that entry is refused before its pointer is written and the pass stores thirty-nine of forty. The pass still walks all forty entries, and the profiler reports the refusal after the walk, so the peak covers the whole batch; the refusal is scaffold-level and identical across the arms, which is what makes the comparison like for like.

§14's peaks at this base revision were measured on a home prepared by §8's node, which its run directory no longer holds, and that home is not reproduced here: §8 recorded 11.71 GiB at this base revision for eight entries, against 2.81 GiB on the home built here. What the criteria test is the ratio between the two revisions and the growth of each with its input, and those are read from arms taken on one home in one job. The magnitudes are this home's.

The criterion that does not hold is the store doubling, and a read trace over the prepared home names where it goes. Every store read the batch performs is attributed to the first frame outside the store and ledger modules, and two call sites own every decode: crew/admission/readiness.py:561 and crew/recovery_stream.py:206. The first is the batch's wait verdict — readiness._section_run_unlanded asks the ledger for one plan's whole history (ledger.load(project, plan=plan)) and decodes every row of it — which took 72 rows and 7.3 MB on the traced home. The second is the lane advisory's rate window, which reads the project's history bounded by activity and decoded 49 rows and 14.9 MB. The batch decoded 23.2 MB as prepared and 45.0 MB with the store's delivered-run rows doubled, moving 211 rows to 404. Both call sites read a population the batch's own entries do not name, and neither is in this repair's write scope. The wait verdict needs only a row's identity and its promoted revision, which is the field set row_plan already resolves a plan through, so a bounded projection in the admission module would close the criterion; the advisory's window is bounded in time rather than in rows, so it needs the same treatment by its own owner. Both are named here with their measurement rather than changed from a scope this node does not hold.

tests/test_a_batch_dispatch_memory_ignores_store_size.py holds four cases. It counts the rows the store decodes, through its one decode point, for a batch queueing one node over a store and over that store with its delivered-run rows doubled: the counts are equal, and a control names the delivered node and requires exactly one row decoded, so a zero is a measurement rather than a dead counter. A second case requires no decode for a node with no delivered row. A third asserts the section-hold index is the shared bounded map and that file_memo.clear() empties it. The fourth reads a named plan set and requires one store read per named plan, the holds of those plans' sections only, and the committed ledger as the fallback for a store holding nothing. The first two fail at revision 0d4e508516652090a9d97e8198f92cd21e2105e0, which recorded 2 failed in 1.03s and ended EXIT=1.

The gate is the node's own file plus the two that cover the batch's home handling, run on rigel. The base arm runs the two home-handling files at revision 0d4e508516652090a9d97e8198f92cd21e2105e0 and records 58 passed in 47.88s, EXIT=0. The head arm runs all three files at revision bcfe9b0f9bd01acca971217a4a46dc1bf7ca6dc2 and records 62 passed in 82.67s (0:01:22), EXIT=0. Each log carries its own revision, host, tree and literal command above those result lines.
