A batch dispatch's store read follows the batch, not the run store

Three reads on a batch's queueing path followed a population rather than the batch. The plan-history read asked the ledger for the project's whole projected history to decide whether one of a plan's own sections had been delivered, and every plan the batch queued paid that projection again. The roadmap was derived once per project through project discovery over the whole inventory, so every plan document the project carries cost the batch a derivation of it. And the section-hold index kept its own dict, its own eviction rule and its own reset path beside the shared memo that already does that job for every other cache in the process. Two further reads kept the batch's footprint tied to the store's row count after those three were narrowed: the landing verdict behind each entry's wait check asked the ledger for one plan's whole history and decoded every field of every row, and the lane advisory's rate window decoded the project's activity-windowed history, neither of them a population the batch names.

Each read now follows what the batch names. The plan-history read selects that plan's rows in the store's own plan index, resolving the plan through the same three fields row_plan reads, and falls through to the committed ledger only when the store holds nothing for the project at all. The batch's roadmap is derived over the plans it names, so a project with 240 plan documents is not derived once for each of them. The section-hold index asks file_memo.bounded_map for its store, so the bound, the lock and the LRU order are the shared ones and file_memo.clear() empties it with the rest of the memo. Nothing the batch decides changes: the store answers with the same rows the projection gave after filtering, and the roadmap rows the wait check reads are the ones the plan set carries. The prior round's empty history scope stays in place. The landing verdict and the lane advisory now ask the store for the fields each decides from — the identity fields row_plan resolves a plan through plus the promoted revision the verdict checks, and the run, lane, model, completion time and throughput the rate consumes, with its activity window applied in SQL — so neither read carries a row's brief or budget into the process. Both were changed under a scope extension granted for them, and the cases added here hold each projection to its field set.

The home is a copy of the crew home whose store carries the project's promoted history: 10,192 promoted rows over 240 plan documents, each recording its plan on the impl move as a brief-carried dispatch does, so a reader that asks for the narrow projection must read the fallback fields as well. Each seeded row carries one of this store's 53 recorded promotion payloads, cycled, with its identity fields rewritten and its width capped at 200,000 bytes so that one promotion's multi-megabyte list is not cycled onto every row. The widths are therefore the ones this project's promotions record, with a median payload of about 48 kB, and the detail is the recorded document. The live store copy holds only a few dozen promoted rows for this project's plans, so a criteria test on it alone cannot show the term the section is about. Every tree's discovery index is written once before its arms, unprofiled, so an arm measures the batch rather than a first-ever parse of its own corpus; without that, the plan-doubled tree pays for 498 never-seen documents while the arm it is compared against pays for none, and the difference is the instrument rather than the batch. The seeding is the same for both revisions, so only the code differs between the bars.

The store read is what the change was for, and it moves in both dimensions. At eight entries the batch reads 67,910 store rows and decodes 30,931 of them at the base revision, against 1,456 rows and 198 decodes here. At forty entries the base reads 85,658 rows and 30,913 decodes against 3,500 rows and 196 decodes. The base's forty-entry read is 1.3 times its eight-entry read, which is the population read widening with the store; here the ratio is 2.4 and every row read is a node the batch names or a read that answers one of its entries.

All three criteria hold on this home. The eight-entry peak moves from 3.07 GiB at the base revision to 1.07 GiB here, a ratio of 0.35 against the 0.5 the section asked for. Doubling the store's delivered-run rows, from 16,055 to 32,110 hot rows, takes this change's forty-entry peak from 1.10 to 1.04 GiB, a rise of -5.7 % against the 10 % allowed. Holding the batch and the store fixed and doubling the project's plan documents, 249 to 498, takes it from 1.10 to 1.08 GiB, a rise of -1.7 %. The negative control holds too: at the base revision the same store doubling takes the forty-entry peak from 2.74 to 4.19 GiB, a rise of +53.2 %. The eight-entry ratio and the base-revision control are read from arms rerun together after this change, and the two forty-entry comparisons from the job that ran this change's three forty-entry arms, so every difference quoted here is between arms taken in one job on one home.

Every forty-entry arm ends EXIT=1, and the reason is the same on the base revision and here: one entry names a node whose declared write paths exceed the model's context window, so that entry is refused before its pointer is written and the pass stores thirty-nine of forty. The pass still walks all forty entries, and the profiler reports the refusal after the walk, so the peak covers the whole batch; the refusal is scaffold-level and identical across the arms, which is what makes the comparison like for like.

§14's peaks at this base revision were measured on a home prepared by §8's node, which its run directory no longer holds, and that home is not reproduced here: §8 recorded 11.71 GiB at this base revision for eight entries, against 3.07 GiB on the home built here. What the criteria test is the ratio between the two revisions and the growth of each with its input, and those are read from arms taken on one home in one job. The magnitudes are this home's.

The criterion that did not hold in the prior round was the store doubling, and the two reads that owned it were outside this node's files and were changed on the scope extension granted for them. A read trace over the prepared home had attributed every decode to two call sites: the landing verdict at crew/admission/readiness.py and the lane advisory at crew/recovery_stream.py. The verdict now projects onto the identity fields row_plan resolves a plan through and the revision it checks, and the advisory onto the run, the lane, the model, the completion time and the throughput, with its activity window applied in SQL. The batch decodes 1.4 MB as prepared and 2.8 MB with the store's delivered-run rows doubled, moving 196 rows to 392 against 30,913 at the base revision, and the peak no longer follows either dimension.

tests/test_a_batch_dispatch_memory_ignores_store_size.py holds six cases. Four count what the batch reads through the store's one decode point: a batch queueing one node decodes the same count over a store and over that store with its delivered-run rows doubled, a control names the delivered node and requires exactly one row decoded so a zero is a measurement rather than a dead counter, a node with no delivered row costs no decode, and the section-hold index is the shared bounded map that file_memo.clear() empties. A fifth requires one store read per named plan, the holds of those plans' sections only, and the committed ledger as the fallback for a store holding nothing. The last two hold the projections to their fields: each asks the store for its own field set and requires that the rows it receives carry nothing beyond it. The first two fail at revision 0d4e508516652090a9d97e8198f92cd21e2105e0, which recorded 2 failed in 1.03s; the two projection cases fail against the sources this round replaced, which recorded 2 failed, 4 passed in 1.97s.

The gate is the node's own file plus the two that cover the batch's home handling, run on rigel. The base arm runs the two home-handling files at revision 0d4e508516652090a9d97e8198f92cd21e2105e0 and records 58 passed in 48.60s, EXIT=0. The head arm runs all three files at revision 1a7841958aa489c80b80d5ed1584a8d732cd40ac and records 64 passed in 196.65s (0:03:16), EXIT=0. Each log carries its own revision, host, tree and literal command above those result lines.
