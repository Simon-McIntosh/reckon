An ordinary resume finds the session a lane change started

A run moved onto a lane whose harness differs from its own starts a fresh conversation, because a session id belongs to the harness that minted it. The section's defect was that the destination harness's id was never written anywhere a resume reads, so the next plain crew resume --advice found no id in the live pointer, the run's stream or the ledger and refused; the only continuation left was another lane change, and there are finitely many backend names.

The read path was repaired before this node ran: the harness-aware resolution in _current_harness_session withholds a session that belongs to another harness and reads the destination harness's own stream instead. This node supplies the regression the section asked for — assert it by performing a lane change and then a plain resume — and verifies it end to end rather than stubbing the capture.

What the cases do

A run on a claude-family lane is moved to a codex lane by change_lane; the launcher writes the stream that lane really emits, whose id arrives on thread.started. The first case then asks for an ordinary resume and requires the composed argv to name the destination lane's command and to carry the destination thread id, and never the source session. The second requires the first observed turn to record that id beside its harness on the live pointer.

CaseAssertsHead 65c75b9e01

first observed turn the pointer records the codex id and its harness, replacing the source harness passes
declared mutation restoring the old first-harness lookup makes the ordinary resume refuse 1 failed, EXIT=1

Under the declared mutation the resume composes the source harness's session onto the destination lane — the stranding the section records — so the case fails on the id it requires, not on wording. The node changes no product source: the behaviour is already correct, and the contract for such a node is to verify it and add the missing test rather than reimplement a working guard.
