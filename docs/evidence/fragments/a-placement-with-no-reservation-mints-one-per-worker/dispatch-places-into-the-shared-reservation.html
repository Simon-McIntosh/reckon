Dispatch places into the shared reservation

A new resolution step in reckon/crew/dispatch.py, resolve_backend_placement, calls ensure_reservation for a backend that declares a placement before delegating to the existing apply_backend_placement wrapper. The ensure holds the shared allocation if none is readable, publishes its job id to the unkeyed record, and starts nothing when a live one is already held, so the first dispatch to arrive creates the one allocation and every later dispatch joins it. The dispatch site at dispatch.py:4911 now calls the resolution instead of the bare wrapper.

The declared wrapping is left in place inside apply_backend_placement, because other callers reach it directly; the dispatch path no longer takes it, because it always reaches the ensure first. A resolution guarded on flight.placement_for(backend) is None leaves a backend declaring no placement untouched: nothing is held and the scheduler is not asked after.

Cases

  • A dispatch declaring placement with no readable reservation reaches the ensure from resolution: one salloc is run, the job id is published to the unkeyed record, and the worker is placed as a step with --overlap and that id.
  • A second dispatch under a different project reads the published record, starts no allocation, and steps into the same allocation; across both dispatches exactly one allocation-obtaining request is logged.
  • A backend declaring no placement is untouched: no ensure, no request, wrapping identical.
  • A legacy per-project record (placement/<project>/reservation.json) is honoured: its job id is placed into and no allocation is obtained.
