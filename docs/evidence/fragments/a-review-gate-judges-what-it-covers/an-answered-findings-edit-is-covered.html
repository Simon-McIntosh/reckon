An answered finding's edit is covered

A review that raises a finding and is answered acted has already said what the plan must change, so the edit that follows is the review's own subject. plan_review.review_coverage now lets that review cover the section the finding anchors while the edit stays under review.plan_change_threshold (0.30), even when the review-need judge answers that a review is required — the answer the gate gave to a 1 % correction a finding had asked for. An edit of the same size to a section no finding named is still owed, an edit past the threshold still is, and the document unit is unchanged, still covered only by an exact digest match.

The rule is one branch in the existing per-review loop: the units whose findings carry an acted response, read through _acted_finding_units and finding_unit, are remembered when the measured share falls under the threshold, and the pending-unit verdict honours that memory ahead of a judge that asks for a review. record_response records the edit's commit on an acted answer, named by the caller or resolved as the newest commit touching the plan through promotion_scope._newest_commit_touching_path, so the covering record carries the evidence for its verdict; the answer also records what that commit is evidence of, so an answer given before its edit landed cites the plan commit at answer time rather than presenting it as the edit's. Two normalisation helpers became one: the earlier digest definition, which dropped only the per-section lifecycle status, is now a field set (_PREVIOUS_SECTION_FIELDS) on the present _without_section_bookkeeping, and the _fingerprint_forms docstring states only the two forms that function returns. The two acted-finding readers folded into one _acted_findings, whose callers read types or units from the same walk.

The predicate runs on every dispatch, plan edit and admission pass, and those passes were already 15–19 minutes apart, so its own cost is measured rather than argued. A first version resolved an anchor against the text its review read, and that text came from walking the plan history for the commit carrying the reviewed bytes — one walk per line-anchored finding, which took a 10.3 s call to 20.4 s. The review already holds that text as its own snapshot, so coverage now reads the snapshot and walks history only for a review with none; the text is memoised per reviewed revision for the whole call, resolved once per review, and a unit a digest already covers is dropped before any text is read, since the rule only fires for a pending unit.
