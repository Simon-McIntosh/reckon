One timestamp parser — evidence

A new primitive module reckon/_timestamps.py with one function parse_utc(value) -> datetime | None, its behaviour fixed by tests/test_timestamps_parse_utc.py before any caller migrates, and the 44 callers the code-depth census found today grouped into migration batches disjoint from each other and from every live run's claims. No caller is migrated in this node.

The behaviour the tests fix

  • A Z suffix and an explicit numeric offset both return an aware UTC datetime; the offset case is asserted with a positive and a negative offset, both normalising to the same instant.
  • A naive value is read as UTC. This is the one policy choice the parser makes rather than inherits, so it is asserted against a fixed moment (and again against .timestamp()) so the result cannot depend on the host's zone.
  • A numeric epoch in seconds and one in milliseconds are both read, told apart by magnitude split at 1e11, the threshold stated in the module docstring.
  • Malformed input returns None rather than raising: a non-string, a non-numeric, a bool, an empty string, an unparseable string and an out-of-range epoch each assert None.
