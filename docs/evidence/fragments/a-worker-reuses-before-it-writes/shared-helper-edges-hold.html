Two edge defects in the shared helpers' callers — evidence

Two behaviours that review of the first migration wave found broken are repaired: the atomic JSON writer leaked its sibling temporary when the chmod applying a requested mode raised, and the watch-stream and rollout callers decided whether a stamp names a zone from the text's shape, so an offset carrying seconds was read as naming no zone. Both fixes are asserted against the pre-migration base outputs by tests/test_shared_helper_edges.py.

The defects and their repairs

The leaked temporary. _open_sibling_temporary creates a unique sibling with os.open, then applies the caller's exact mode with os.chmod. When the chmod raises, the descriptor is closed and the exception propagates, but the file the open just created stays on disk. The caller's own finally cannot reach it: it unlinks only a returned temporary, and the assignment never completed. Reproduced at the base revision before the repair by patching os.chmod to raise, leaving .dest.json.<pid>.<hex>.tmp beside an untouched destination. The chmod-failure branch now unlinks the candidate before re-raising, so a failure after the temporary is created removes it.

The seconds offset read as zoneless. Both callers tested the text with _ZONE_DESIGNATOR = re.compile(r"(?:[Zz]|[+-]\d{2}:?\d{2})$"), which matches an offset ending in minutes but not one carrying seconds. For 2026-09-29T01:02:03+00:00:30 the base c786e44a returned ("2026-09-29T01:01:33+00:00", "utc") from query._normalize_stamp and an aware 2026-09-29T01:01:33+00:00 from rollout._parse_timestamp; the migrated callers returned (None, "unknown") and a naive 2026-09-29 01:01:33. The zone is now read from the parsed result's tzinfo through reckon/_timestamps.py:parse_iso, a shared helper beside parse_utc that keeps a zoneless string naive rather than pinning it to UTC. Both outputs again match the base: the watch-stream caller reports the UTC instant and "utc", the rollout caller returns the aware instant.

Scope note

The fix requires a naive-preserving parse reachable by both callers. It cannot live in reckon/crew/query.py or reckon/crew/rollout.py: tests/test_timestamp_callers_batch_a.py:test_no_caller_parses_iso_strings_itself asserts that no migrated crew module calls datetime.fromisoformat, and parse_utc normalises a zoneless string to UTC, discarding the very distinction the zone test needs. The helper therefore lands in reckon/_timestamps.py — the home the batch-a review names ("one shared helper belongs beside parse_utc") — which is outside this node's declared write paths — since authorised by the coordinator and now inside the fence. parse_iso is the zone-preserving view of the one parser: it names whatever zone the text states and leaves a zoneless string naive, while parse_utc is the normalising view of the same parser, pinning a zoneless string to UTC for callers that need one instant.

Why this is the fix, not a re-guard

The recorded behaviour is the base's, not a new one: the seconds-offset outputs above are the values c786e44a produced, transcribed from the caller doors already exposed. The repaired writer's failure branch is exercised by making the chmod actually raise, so the refusal is shown rather than inferred from a green suite.
