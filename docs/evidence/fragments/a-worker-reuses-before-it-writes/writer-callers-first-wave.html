First wave of writers and decoders onto the shared helpers

Node writer-callers-first-wave extended the shared atomic JSON writer with the parameters its callers needed and moved the first disjoint wave of writers and two numeric decoders onto it. Commits fbc29bca (the migration) and d6a72a6e (an explicit write mode made exact past the umask) on a detached worktree, base a7895e72.

The shared writer's new parameters

reckon._store.write_json_atomically gained keyword parameters, each defaulting to its previous behaviour: indent, sort_keys, a mode applied to the temporary before the rename, fsync_directory to fsync the parent directory after the rename, and create_parents so a caller that must not resurrect a removed directory can refuse. No second writer was added. The temporary sibling is now opened directly (O_CREAT|O_EXCL with a random name and a retry loop) rather than through NamedTemporaryFile. An explicit mode is then set with os.chmod on the temporary before the rename, so it lands exactly under any umask — the open's own mode is filtered by the umask, and a caller asking for 0o600 would otherwise land 0o400 under a umask such as 0o277. A plain Path.write_text caller (mode None) still takes the umask-applied process default, so it is reproduced rather than silently narrowed to 0o600.

Each caller keeps its serialisation, its file mode, its fsync behaviour and its locking. _write_private_json keeps its owner-only ceiling: the mode is set on the temporary before the rename (and made exact with a chmod), so the destination is never the wider inode. The two private numeric decoders _backends._number and crew.carryover_census._measured were deleted; their call sites now call reckon._observations.optional_number, with each caller's own rounding (_seconds) or summing (_sum_tokens) kept in the line around the call.

Retained exception in resources.migrate_typed_layout

Only the plain no-active-items manifest write moved onto the shared writer. The grouped staging install (transformed[MANIFEST_PATH] written with write_bytes and installed with os.replace, with a byte-restore rollback) is a multi-file group transaction that a single-file atomic writer cannot express, so it is left in place deliberately. The detector that named this caller looks for write/write_text, not write_bytes.

Declared negative control

The control drops the mode argument from the _backends._write_private_json call so the file is written with the default mode. The owner-only case then fails: the destination is 0o600 (384) where 0o400 (256) is required.
