The velocity view counts promotion's clone matches per week

Promotion already records a clone_matches report on every ledger row, but nothing surfaced it. velocity.report now carries a clones block: for each ISO week in the window it counts the promoted runs whose function copied an existing one, the total matches, the runs measured with no match, and the runs no revision pair could be measured for.

What changed

  • reckon/velocity.py carries clone_matches on each captured run row (the compact field list gains it), so the ledger's own clone report reaches the measurement rather than being dropped at capture.
  • _clone_week_cells buckets the promoted runs by UTC Monday-start ISO week, clipped to the window the same way measure buckets its own weekly cells, and charges each run to the week it was promoted. Three states stay apart: a run whose function copied an existing one (runs_with_match, its matches summed into matches), a run the detector measured and found nothing in (runs_no_match), and a run carrying the unmeasured marker (runs_unmeasured). The last is a missing reading and is never folded into the no-match count — an empty list is a measurement, the {"status": "unmeasured"} mapping is not.
  • The block is emitted by report as {"weeks": [...], "definition": ...}, and clones is accepted as a view field.

The two-week fixture

tests/test_velocity_clone_matches.py builds a repository whose ledger spans two ISO weeks: a run with two matches and a measured-empty run in the first week, one unmeasured run in the second, each dated by its own promote commit. The figures are hand-computable from the fixture, so folding the unmeasured state into the no-match count moves a figure and fails an assertion.
