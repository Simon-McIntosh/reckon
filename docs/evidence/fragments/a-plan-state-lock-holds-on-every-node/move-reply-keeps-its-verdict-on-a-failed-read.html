A move reply keeps its verdict when a version read fails

An independent review of the sprint-move reply found three defects. A settled move read both sprint versions back from disk, but a failed read was skipped, so when every read failed the reply omitted applied entirely and a caller could not tell a successful move from a silent failure. The reply now sets applied whenever the edit carries a move and names each failed read in warnings, so the caller always learns what landed. The same pass removes an unreachable parser branch and a lint finding the earlier change introduced.

What changed

PathChange
reckon/mcp_edit_plan.py _move_sprint_versions returns the versions it could read beside the sprint ids whose read failed, and no longer continues out of an exception handler. The success path sets applied whenever a move op is present, attaches sprint_versions when any read succeeded, and warns sprint_version_read_failed=<id> for each failed id. The refusal path unpacks the same pair and still names whatever could be read.
