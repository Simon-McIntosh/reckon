A resume of a run whose worker lives is refused, naming its pid

Landed. recovery.live_worker_pid reports which process a run's liveness reading rests on, composing the same two host-gated reads in the same order as local_liveness — the pointer's pid, then the run directory's worker record, which is where a supervisor that exits ahead of its worker leaves the process still running the attempt. The shared observed-end gate in resumption.py refuses with that pid named, so a coordinator reading the refusal can check the process table rather than take it on faith; both the hand-typed crew resume and the automatic sweep reach that gate, and neither launches anything on the refusal. Where liveness came from a fixed snapshot carrying no process, no pid is named and the refusal stands as before.

Reproduction. Probed before the change, against a temporary RECKON_HOME and a real sleeping child: pointer pid gone, worker record naming the live child, an exit.json present — the manual door refused and named no pid, and the sweep's skip detail likewise carried none, so the operator could not tell which process to inspect. After the change the same record refuses with (pid <n>) in the message, the sweep launches nothing, and the refusal changes nothing about the run: a non-parked one still classifies running, a parked one reads exactly as it did before the sweep touched it.

What the two existing resume tests cover, and what they miss. tests/test_direct_resume_needs_an_observed_death.py pins the manual door's lift gate over stored answers: an exit record licenses a resume, a proven-dead local pid licenses one, an unknown reading refuses, and a proven-live pointer pid refuses with the launcher's own message — but every case drives the pointer's pid, so the run-directory worker record, which is the only process a supervisor's early exit leaves behind, is never the thing that answers, and no case pins a pid in the message. tests/test_resume_sweep_needs_an_observed_death.py pins the sweep's lift over three parked runs in a dry run: a live pointer pid is refused and the refusal carries the launcher's message — but it drives the sweep's read-only door, never the launching path, and names no pid either. The new file tests/test_resume_refuses_a_live_worker.py closes both gaps with a real short-lived child process as the live worker, bounded by its own 300-second sleep and ended by its pid: the manual door refuses a run whose worker record pid answers alive, naming that pid, and the run keeps classifying running through the refusal; the sweep refuses a live pointer pid on its real launching path (a recorded launcher stands in for the spawn, and the assertion is that it is never called), skipping with reason resume-refused; and an early signal exit record sitting beside a worker that still answers alive does not license a lift on either door.

Fold-in from the exit-half review. Its follow-on — "when the launcher is killed by signal but the worker it adopted lives on, no exit record is written early" — has a writer half and a reader half. The reader half is here and now pinned: an exit record written beside a run whose worker still answers alive does not license a lift on either door (third case above). The writer half is out of this node's write scope: the signal short-circuit in reckon/crew/dispatch.py _reap_the_launched_worker still returns the worker's signal status and lets the supervisor write an exit record while an adopted worker lives on, and that file is claimed by concurrent nodes. Recorded in the manifest as a follow-on with that exact location.

One nearer gap the same fence held shut. When the refusal comes from the pointer's own pid still answering — before the observed-end gate is reached — the message is the launcher's own, "still has a live process", composed in dispatch.py and held word for word by the prediction-parity test. It names no pid, and parity forbids rewriting it from resumption.py; the pid naming therefore lives on the observed-end gate, which is the gate that meets the run directory's worker record — the shape a supervisor's early exit leaves behind. Extending the launcher's own message to name the process belongs with the node that owns dispatch.py; the manifest records it beside the writer half.
