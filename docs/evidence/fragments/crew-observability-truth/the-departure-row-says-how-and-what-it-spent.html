The commitless completion correction

The first repair treated every row with no commits as if its pointer had vanished without a row. A wider stacked measurement found seven failures: a live row was no longer held, a real report-only promotion read as unfinished, and later departures read withdrawn. A focused reproduction at 2583015ce confirmed all seven failures against twelve passes. The correction keeps ledger presence as the settlement guard and uses the row's commit list only to choose promoted or recorded. A row carrying an explicit no-commit reason reads recorded both while its pointer lives and after it leaves; the live row is announced once.

Fixtures were given commits only where they describe a code landing: test_a_promoted_live_run_does_not_reannounce.py and test_crew_watch_lifetime.py already put HEAD in their manifests; test_a_rewritten_terminal_manifest_transitions.py rewrites its manifest with abc1234; and the synthetic landed control in test_a_promotion_never_reads_unpromoted.py asserts a promotion. The real report-only promotion in that last file instead declares no commit and asserts recorded at the pointer-removal boundary.

A later review found two more inconsistent reads. A live committed row with no commits had fleet_verdict.state=recorded but classification=promoted; both now take the same settled word. A malformed run identifier made the ledger path raise rather than answer that no promotion row could be found; the guard now returns false. Both failures were reproduced before the correction. The departure reader also resolves only the runs leaving the fleet, reading their per-run rows after a cheap membership check instead of decoding every row in the ledger on each watch transition. A full watcher case proves a commitless completion announces recorded and then stops, just as a committed promotion does.
