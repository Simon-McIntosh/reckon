ack-after-promotion — a promoted run's remainder can be acknowledged

A run promoted with its worktree retained leaves a duty the obligations reader raises from its ledger record, and that duty outlives the live pointer. crew ack wrote only beside the live pointer, so once the run was promoted the deferred remainder could not be recorded and the stop hook blocked every turn on a remainder the coordinator held on purpose. At base the refusal reproduces: acknowledging the promoted run raises reckon.crew.CrewError: no live run 'r-20261003T060000000000-promoted-remainder' (looked in …/config/crew/live/r-20261003T060000000000-promoted-remainder.json), and the two cases that record an acknowledgement fail on that line. The deferral is now written to the run's own ledger record — the store that survives promotion, with the ledger's writer keeping the aggregate copy identical to the per-run file — and the obligations reader honours it through _acknowledgements_in_force and _partition_acknowledged, exactly as it honours a live run's. An acknowledgement with no reason is refused, and one past its until is not in force, so the duty returns on the next read with no second write. Implemented in reckon/crew/runs.py and reckon/crew/obligations.py at 6f9bb1056, with the reader's promoted lookup moved off the held-tree scan at bb0347100 (the scan cost about five seconds per obligations read on a fleet-sized ledger and pushed the snapshot publisher's transition write past its latency bound); tests/test_ack_after_promotion.py, 3 passed.
