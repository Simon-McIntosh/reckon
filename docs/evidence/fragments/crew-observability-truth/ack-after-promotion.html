ack-after-promotion — a promoted run's remainder can be acknowledged

A run promoted with its worktree retained leaves a duty the obligations reader raises from its ledger record, and that duty outlives the live pointer. crew ack wrote only beside the live pointer, so once the run was promoted the deferred remainder could not be recorded and the stop hook blocked every turn on a remainder the coordinator held on purpose. At base the refusal reproduces: acknowledging the promoted run raises reckon.crew.CrewError: no live run 'r-20261003T060000000000-promoted-remainder' (looked in …/config/crew/live/r-20261003T060000000000-promoted-remainder.json), and all four cases fail on that line. The deferral is written to one small file of its own per run under the crew home, atomically, carrying the run id, project, reason, until and recorded time; the run is still required to exist, found by reading the run's own file beside its project's ledger rather than loading the ledger. Nothing under the project's committed state is written: the earlier design stored the deferral by rewriting the promoted run's ledger record through the ledger's writer, and the case added here shows that defect — at the reviewed head it read M docs/state/<project>/crew.json, the tracked aggregate rewritten and left uncommitted, which is the single-file ledger the split closed and which an acknowledgement must never reinstate. The obligations reader, _acknowledgements_in_force, honours these files beside the live pointers' deferrals and ignores an expired one, so the duty returns on the next read with no second write.
