A sub-floor disposition is written by a command

A coordinator retires a sub-floor review dimension through reckon crew dispose instead of editing the review store by hand. The command writes one entry through record_dimension_disposition, into the very file the obligations list reads the review from, and every refusal is the store's own — so an unknown dimension, a kind outside the closed set, a fold naming no node, an exemption carrying no reason, a fold carrying a reason and an exemption naming a node all exit non-zero with nothing written and the obligation row standing.

What landed

  • reckon/cli.py — a crew dispose subcommand taking --project, --run, --dimension, --kind, and whichever of --node / --reason the kind requires. It resolves the reviewed head from the run's own live pointer, or — a run with no live pointer being the ordinary case once it is promoted — from the run's own records rather than from the directory the operator stands in, and selects the stored record through the reader's own call (recovery.select_review_for_head), writes through review.record_dimension_disposition and re-reads the stored record for the receipt, so the reply repeats what the store now holds rather than what the call intended (reckon/cli.py:3793 the pointer-less head resolution, reckon/cli.py:3892 the subcommand).
  • reckon/crew/review.py — the writer's gate for the closed set is now the reader's own predicate dimension_disposition_valid. A second copy of the vocabulary in the writer could accept a kind the read-back then ignores, which stores a row that reads as answered and stands.
  • reckon/crew/review.py:1042 — stored_record returns the file it read beside the record it holds, and record_dimension_disposition writes back into that file. Deriving a target from the record's own fields instead put the entry in a copy the obligations list never reads: a store holding a legacy copy beside the revision-keyed record for one head reported the disposition as recorded while the row stood.

The refusal is asserted through the same entry point the acceptance is, because a refusal that still wrote would be indistinguishable from an accepted call at every later read. The read-back case is asserted on its own as well: the store is reachable by hand, so an entry naming a kind the closed set does not define is not a disposition however complete its other fields look.

Those last two rows refuse a half-answered call: the field belongs to the other kind, so storing the entry would drop it in silence while the reply reported success. Refusing by name leaves the caller to say which kind they meant.

Which stored record the entry belongs in

A store can hold two records for one head: the review at the revision-keyed path, and a legacy copy beside it carrying the same head — the shape this plan's own review store holds. The obligations list reads the row through recovery.select_review_for_head, which takes the first candidate carrying the head, and the identity path is a candidate before any keyed one. The command selected the newest record instead, and the writer re-derived its target from the record's own fields, so on such a store the entry could land in the file the reader never reads: the reply named a path and reported success while the sub-floor row stayed.

The new case asserts the premise first — both files for one head, the reader resolving the legacy copy, the row standing — and after the call requires the row gone and the disposition in exactly the file stored_record reports reading. Against the pre-repair source it fails with the command exiting 0 while the row stands, which is what makes it load-bearing rather than a case that would pass either way.

A promoted run's revision comes from its own records

A run with no live pointer is the ordinary case once it is promoted, and the command read its reviewed head from the tree the pointer named. With the pointer absent the mapping was empty, an empty mapping is the empty path, and Path("") is . — so the head was resolved by git rev-parse HEAD in whatever repository the operator's shell stood in. Nothing downstream could catch it: the head was a revision, the record selected against it was a stored review, and the entry written into it named a head belonging to something else entirely. The same hazard was already answered in the reader — obligations reads an empty tree as no tree, so the selection falls back rather than comparing revisions a caller cannot honestly make — but the command resolved the head one step earlier, where the empty path was still a legal one.

The revision is now resolved from the run's own records: the tip the run's ledger row records as the revision its promotion landed (promoted_revision), or the head its stored review carries. Both are the run's own account of itself, and they agree in the promoted case, because a review record is accepted by the promotion gate carrying that head. A run whose records name no revision is refused by name, as is a ledger that cannot be read — a revision nobody recorded cannot be answered, and writing a disposition against a guessed one reports the finding retired on a diff that was never read.

The case for this stands the command in a temporary git repository whose head is deliberately not the run's, removes the run's live pointer and records its promotion in the ledger. The floor comment

A floor of zero reports nothing, because every stored score is at or above zero — so reading an undeclared floor as zero would claim a standard the configuration never declared while changing no verdict. The sentence said the opposite of what the code does:

before: “A floor of zero would report every dimension of every review, so the absence of a declared floor is read as the absence of a standard rather than as a standard of nothing.”

after: “A floor of zero would report nothing, since every stored score is at or above zero — so reading an undeclared floor as zero would claim a standard the configuration never declared while changing no verdict.”

No behaviour changed with the sentence: sub_floor_dimensions already skipped a dimension the map does not name.

The test stands its world up in a temporary config home

The fixture writes mounts, a live pointer, the reviewed run's tree and the stored review under a temporary RECKON_HOME, and patches the derivation's clock. The last case resolves every root the command uses — the review store, the run pointers, and the ledger the pointer-less path reads — and requires the path it reports inside the temporary home; an absence check against the real home would itself be a read of it. The pointer-less cases stand their unrelated repository under pytest's own temporary directory and assert afterwards that the command wrote nothing into it. Nothing in this node reads or writes the operator's ~/.config/reckon.
