Execution record · 2026-09-29

A stored review score is queryable from committed state

Every review a promotion attaches is written onto the run's committed ledger row as five per-dimension scores and a total. The reader that turns those rows into an answer existed and had no caller, so the record was written by every promotion and consulted by nothing: reading a plan's scores meant opening the ledger file by hand. The crew view surface now carries a scores reader over the committed rows, filtered by plan, node or run id, and it keeps the three row shapes apart — a stored review answers with its own dimensions, a row whose review was never stored is left out rather than returned as zeros, and a stored review that never parsed answers with its status and no scores.

§1 — What no reader could answer

At the base revision reckon.ledger.review_scores is defined and called from nowhere in production: git grep review_scores 89890b94 -- reckon/ returns the definition and nothing else, and the only callers anywhere are cases in tests/test_ledger.py. The committed rows are the only place the scores live — the real ledger at the time of this record holds 2,379 rows, 550 of which carry a stored review block, every one of them written by a promotion. A coordinator asking which dimension a plan's work scored low on had to open docs/state/reckon/crew.json and read it by hand.

§2 — What the view returns

reckon/mcp.py at 2523db17 adds a scores branch to the crew view dispatch, beside records and summary. It reads the ledger of the checkout named by checkout_path through ledger.read_records and hands those rows to ledger.review_scores, whose per-row shape is unchanged: the reader already omitted an absent review and already returned an unparsed one with its status, so the change gives it the caller it never had rather than teaching it the distinction a second time. Filters bind the row's own attributes, so a score is read against the job that earned it.

Row shape in the committed ledgerWhat the view returns
a review was stored and parsed one entry naming the run, plan and node, the five dimensions (goal_fidelity, evidence, scope_discipline, durability, fit), the sum as total, and the dimensions the reviewer recorded as unmeasured in absent
no review was ever stored no entry at all — a review that was never recorded is not a score of zero, and a caller cannot read it as one
a review was stored but did not parse one entry with its own status, scores empty, total null, and the dimensions it could not read listed in absent — the refusal is visible rather than rendered as a measurement

A parsed review that genuinely scores zero keeps its entry with total 0: a measurement of zero and an absent measurement are different readings, and collapsing either into the other is the failure this shape exists to prevent.

The new cases are six: the reviewed row's five dimensions come back filtered by plan, by node, and by run id (each dimension carries a different value, so a dimension returned against the wrong name is visible rather than hidden by the total); an unreviewed row matching a filter exactly contributes no entry; a parsed review that scored zero keeps its entry with total 0; and a review that never parsed answers with its status, empty scores, a null total and its absent dimensions. The fixture builds its ledger in a temporary repository and points the config home at an empty temporary directory, so the tests neither read nor write the real ledger or ~/.config/reckon.

§4 — Boundaries and open items

  • Joining a score to work its run later generated is out of scope. The view answers from the row's own attributes; attributing a score to work that landed after the run it measured is an open decision on the parent plan and is not attempted here.
  • The CLI's ledger view is untouched. The score reader lands on the crew MCP surface only; reckon/cli.py is held by a concurrent node, and the sibling surface there is not this node's change to make.
  • A pre-existing failure, not this change's. tests/test_crew_scoring_state.py::test_scoring_action_dispatches_the_named_review_worker fails identically at base and at head: it asserts a --local flag that the dispatch string does not carry (the string ends --backend native). Identical id in both arms, so it is recorded as a follow-on rather than triaged here; the dispatch surface belongs to a concurrent node.
  • Files. reckon/mcp.py (the view branch and its docstring), tests/test_review_scores_are_queryable.py (the gate), this fragment and its figure. reckon/ledger.py was in scope and needed no change — the reader already held all three distinctions.

§5 — Outcome

Commit 2523db17 carries the change, with the figure at 3064f77d. review_scores now has a production caller: the crew view answers view="scores" from the committed rows of the named checkout, filtered by plan, node or run id. Read against the real ledger, the view returned 550 reviewed rows across 60 plans, every one of them parsed, three carrying a dimension the reviewer recorded as unmeasured — a record that until this change no surface could read.
