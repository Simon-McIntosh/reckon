the-scopes-view-says-what-it-evaluated — the payload names the question it asked, and each claim carries the enforcer's binding verdict

The dispatch-refusal-surface census found the scopes view answering two questions with one shape. A scopes call carrying no candidate wave returned empty conflicts, empty live_conflicts and empty lanes — the same payload an evaluated, clean wave produces — so a caller that forgot the manifest read a clean verdict out of an unasked question. And a listed live claim carried its owner (run id, node, declared path) but not whether that claim binds: the registry read dropped the verdict the enforcer had already computed, so a worker reading the registry for itself chose a stricter rule than dispatch applies and blocked on a stopped claim that holds no unintegrated work while dispatch walks past it.

What the payload says now. plan_scope_lanes in reckon/crew/runs.py returns a candidate_wave block: state: "unevaluated" with a detail naming what was not evaluated when no candidates were supplied, state: "evaluated" once a wave is. Each claim from _LiveScopeClaim.as_dict() now carries binding and disposition_reason, computed by claim_disposition (reckon/crew/node.py) — the same function the dispatch scope check runs, not a parallel rule. A pointer naming no pid, or a live pid, is binding; a stopped run with unintegrated work at its declared paths is binding with the reason clause …promote or recover…; a stopped run with nothing left is non-binding with the reason clause …so its claim is disregarded. The mcp.py scopes view gives every claim_map owner both fields unconditionally, defaulting an unverdicted claim to binding — the answer the read model's own default and the disposition rule's no-recorded-process branch both give, so a reader never has to guess what an absent key meant. tests/test_mcp_response_budget.py, which stubs the planner with claims that never carry a verdict, exercises that default, and the node's test file pins it directly with a stubbed planner of its own.
