crew dispatch writes one JSON document to stdout and every notice to stderr

The defect. A caller reads crew dispatch's stdout as one JSON document (json.loads(payload)), and the documented failure is a caller seeing Extra data from a notice that landed on the same stream. The command's own outcomes are sound — every _emit in reckon/cli.py is followed by an exit — but nothing structural kept a print from anywhere beneath it off stdout, so the contract held by convention rather than by construction.

What was checked at the base revision. Each outcome path of crew_dispatch was driven (dry run, launch, watcher-required refusal, request error, unknown backend, not-dispatchable, contract refusal) and each wrote exactly one JSON document; every _emit call in the command body is followed by raise click.exceptions.Exit. Grepping the modules beneath it found the stdout writers in reckon/crew/dispatch.py to be the peer-channel entry (dispatch.py:2933, a separate command) and remove_worker_scratch (dispatch.py:7708, 7712, 7719, whose only callers are in promotion.py), plus the supervisor launcher's pid print (dispatch.py:8970, over a private pipe) and the watcher producer's reload notice (runs.py:2320, whose stdout the watcher redirects to its own log). None is on a path crew_dispatch walks, so at base no outcome wrote a second document — the case the specification requires to fail at base has to be a notice placed on a seam the command really calls.

The change. In reckon/cli.py, crew_dispatch is wrapped by _holds_stdout_for_one_document, which runs the whole command with sys.stdout bound to _OneDocumentStdout. Any write made anywhere beneath the command — including a bare print in code this node may not edit — is forwarded to stderr, and the helper exposes the real payload stream so _emit still writes the one document to the caller's stdout. The channel also answers fileno() with stderr's descriptor, so a writer that reaches for the fd rather than the object lands on the notice channel too, and a reader that asks the channel to be read from is told it is not readable instead of silently getting nothing.

The gate. Both arms ran with pytest -n 8 --timeout=300 over the sixteen tests/test_dispatch*.py files plus test_brief_dispatch.py, test_crew_orphan.py, test_gate_population_resolves.py, test_crew_routing_visibility.py and test_skill_contracts.py, each arm with its own --basetemp and its own log. Head (74bb83d47eda): 1 failed, 231 passed, 1 skipped at EXIT=1 (logs/head-arm-2.log), the one failure being the skill-contract id the base already fails, so the head arm adds no failure id and the declared control is green at head.

A first head run named two ids a re-run did not reproduce, and they are recorded rather than buried. The first head arm (logs/head-arm.log) failed test_dispatch_returns_without_worker.py::test_dispatch_returns_once_its_supervisor_runs (the dispatch process alive 20.5 s against an 8 s bound) and ::test_dispatch_returns_when_its_supervisor_finished_the_launch (a pointer naming no supervisor), while base failed a third case in the same file. The file is timing-sensitive and takes its bounds from wall clock on a shared, loaded node: run alone at head it passes 7 passed twice (logs/stability-head-isolated-1.log, logs/stability-head-isolated-2.log), and the full head set re-run gives 1 failed, 231 passed with only the pre-existing skill-contract id (logs/stability-head-full.log). Both first-run ids are therefore classified as load-dependent flakiness in that file, not as this change's regression; the evidence for that classification is the three logs above, and the file is named under follow-ons.

The control, executed. The declared mutation removes the redirect, so the notice the presence case prints beneath the command returns to the caller's stdout. Run against the base tree with -k presence-check: 1 failed, 7 deselected at EXIT=1 (logs/negative-control.log), JSONDecodeError out of json.loads(stdout). The head arm passes the same case, and the red log is the one the manifest names.

What this does not cover. The launch path's config-error outcome emits no document at all (empty stdout), a zero-document shape outside this node's stated measure of more than one document or non-JSON text; remove_worker_scratch prints to stdout from the promotion path, which no test on this node's gate drives; and dispatch.py:2933's peer-channel document is a second entry point that this node may not edit. All three are recorded under follow-ons rather than fixed here.
