A killed worker is classified, resumed and landed

The measure

The steps that make a worker's death legible — the supervisor's exit record, the interrupted classification, the resume route, promotion — were each covered on their own. What was missing was the sequence: a worker dispatched, ended by a signal it did not choose, read as interrupted with that signal named, offered for resume, resumed, and its second attempt landed. A phase an operator never reaches would have passed every test the pieces had.

tests/test_a_killed_worker_resumes_to_completion.py drives that sequence against a stub worker in a temporary repository and crew home. The first attempt is started through the run's own supervisor, which spawns the stub, waits on it and writes exit.json; the stub writes one stream record and then lets SIGTERM end it, so the run reached a model and is not a launch failure. The pointer carries no wait status, which is the shape a supervisor-launched worker leaves: the record is the only thing that can name the signal.

What is asserted, in order

  1. The classification reads interrupted, and the recorded signal is named — interruption["signal"] is 15 and signal_name is SIGTERM, with SIGTERM in the row's own detail.
  2. The run is offered for resume: the classifier routes it to resume, its next action names crew resume, and the launcher that verb calls builds its plan rather than refusing.
  3. The resumed attempt runs as a supervised process of its own: its supervisor ends only when its worker does, the run's pointer then names the second attempt with a resume attempt kind, the attempt's own exit record reads exit_code 0, and the manifest is one the worker wrote.
  4. Promotion completes from that manifest, and the evidence is the committed ledger: the row is read back from the store, and the exit it carries is the resumed attempt's (exit_code 0). A promotion that had landed the killed attempt's record would carry SIGTERM there instead.

The mutation replaces the exit-record signal arm of _interruption_evidence in reckon/crew/recovery.py with elif False:, so a record exists but its signal is never read.

The run then reads abandoned rather than interrupted, and the case fails at the first half of the interrupted-with-signal assertion (assert 'abandoned' == 'interrupted'). That is the honest reading of the dependency: the signal arm is not a decoration on an interrupted verdict, it is what produces one once a record is present, because the record's presence short-circuits the dead-pid inferences.
