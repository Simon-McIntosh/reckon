A scratch-removal docstring states the moved-root refusal it actually makes

What changed. The _removable_scratch_target docstring in reckon/crew/dispatch.py claimed that accepting a recorded scratch path gave the removal resilience to a root that moved. The guard does the opposite: it requires the recorded path's parent to equal the scratch root that resolves now, so a record made under a root that has since moved is refused. The docstring now states that case for both the guard and remove_worker_scratch, and a new test drives the case — it redirects RECKON_WORKER_SCRATCH_ROOT between the create and the remove and asserts the record is withheld with the original directory still present.

The defect, reproduced before the repair

At the base revision 13f950ff the docstring read:

A recorded path is therefore only ever allowed to equal <scratch root>/<run id> — its value is resilience to a root that moved, never a licence to name a directory the run does not own.

But the behaviour is the reverse. With the root moved between create and remove, the guard resolves the current root B, finds the recorded path's parent is A, and returns None with "scratch path is not the directory this run owns" — so the recorded path supplies no resilience; it is withheld. A docstring that names a policy the code does not follow is a claim a later reader acts on, so the wording is the defect and the reproduction is the behaviour that contradicts it. The probe at 13f950ff reported removed: False, withheld: scratch path is not the directory this run owns, original dir present: True.

The repair

Both docstrings now state the moved-root case and drop the resilience claim. The behaviour is unchanged — a working guard is documented, not reimplemented:

  • Narrowing, not widening. The new wording says a recorded path is allowed only as <scratch root>/<run id> beneath the root that resolves now, so it narrows what may be removed rather than widening it.
  • The moved case, stated. A record made under a scratch root that has since moved names a directory no longer a child of the resolved root; it is withheld and left in place, never removed. remove_worker_scratch carries the same sentence for its recorded-path argument.

The negative control

The declared mutation is accept a recorded path whose parent is not the current scratch root. Applied as RECKON_WORKER_SCRATCH_MOVED_NEGATIVE=1, it drops only the parent-of-the-current-root refusal at the guard, keeping every other check. Under it the new case and the pre-existing outside-the-root case both turn red — 2 failed, 12 passed, exit 1 — which is the discrimination: the recorded directory is removed because the guard no longer withholds it. The red log's first line repeats the mutation verbatim, the two failing ids are listed beneath it, and the log ends in EXIT=1; it is named in the node's manifest under negative_control_log.

What is not here

Verifying the merged result belongs to a separately dispatched test node. The behaviour was confirmed unchanged rather than reimplemented: the probe above and the new case both exercise the guard as it already was.
