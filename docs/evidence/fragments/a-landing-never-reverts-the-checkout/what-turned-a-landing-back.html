what-turned-a-landing-back

Read-only investigation of the promotion that committed its landing 2321fba57 and left nova's shared checkout holding a staged reversal of it. Delivered docs/research/what-turned-a-landing-back.html (timeline of every HEAD, index and working-tree change at the four paths from 19:23:40 to 19:37:06, each with its record) and scripts/reproduce_landing_reversion.py.

Finding. The reverted state is exactly what _restore_landing_writes (reckon/crew/promotion_scope.py:1672) leaves when it resolves a pre-landing HEAD. Two scratch-repository experiments fix the shape: git commit --only -- <paths> records the working-tree content and holds the shared index.lock, and run at the landed HEAD the rollback changes nothing. So the committing process must have used another index file. The leading candidate is a rollback from a second promotion of the same review run through promote_review_run_itself (reckon/crew/recovery_review_acceptance.py:416), reachable when the sweep is not confined to one session (_sweeping_session, reckon/crew/recovery_repair_dispatch.py:1000). The peer-pull candidate is ruled out: no reflog entry exists for the pull or its merge.

Measure. python3 scripts/reproduce_landing_reversion.py exits 0: with the interleaving the plan path ends staged back to pre-landing content and the three created paths staged as deletions and absent from disk; without it all four paths are equal in HEAD, index and worktree (negative control).

Separating record. None survives; the per-path rollback report rides only on the LANDING_ROLLBACK_ATTRIBUTE exception (promotion_scope.py:1762). §2 is what adds it.
