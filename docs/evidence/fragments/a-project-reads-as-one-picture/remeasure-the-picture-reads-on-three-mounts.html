The four coordinator questions through the served reads

Method

Twelve calls: the four questions on power_convertor, nova and reckon. Every call went through the tool function reckon.mcp builds for registration — reckon.mcp.roadmap_tool, read_plan_tool and crew_tool, each produced by _deadline_tool(..., request_scope=True) — so each call enters the covered-tree and identity-index scopes a served read enters. No inner _read_plan, _roadmap or _crew body was called directly. The measuring process imported reckon.mcp from the head worktree (…/remeasure-the-picture-reads-on-three-mounts/reckon/mcp.py), and each record carries that path. RECKON_HOME was a writable copy under the run's scratch directory holding mounts.json and a copy of the live run pointers, so the write fence did not force a cold cache on every call. Each mount was warmed by one discarded roadmap call before its measured calls. Each call ran in its own process under timeout -k 5 55 with faulthandler.dump_traceback_later(45, exit=True), so a call that hung printed every thread's stack and exited rather than blocking the measure. All of it ran in the foreground on the fleet allocation, job 1291586, node 98dci4-clu-2068.

The three reckon calls that did not answer

All three printed a thread dump at the 45 s bound. critical and next are the same roadmap read, and both were interrupted in one chain, identical in both dumps:

  1. mcp.py _roadmap → _roadmap_scoped → mcp_discovery._discover_project
  2. serve.py discover_plans → _discover_plans_uncached → _attach_ready_set
  3. roadmap.py build_roadmap → _build_roadmap → _critical_path_links → critical_path_coordinators → _critical_path_coordinators
  4. crew/plan_coordinator.py resolve_plan_coordinators → _plan_of_run → _plan_from_node → _reviewed_run
  5. crew/dispatch_sessions.py _reviewed_run_id, inside its record scan

The why call was interrupted in the same chain, one frame lower: read_plan reaches the same critical_path_coordinators path through the roadmap composition it reads. So on reckon the cost is not the why view's own enumeration that §16 removed; it is resolve_plan_coordinators, which walks every run record per plan node, and it is on the path of both the roadmap and the why read. The same chain answered in 3 to 10 s on power_convertor and nova, so the driver scales with the mount's run-record count, which is largest on reckon's own ledger.
