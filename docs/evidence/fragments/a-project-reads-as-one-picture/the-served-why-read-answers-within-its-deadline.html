A git date lookup that ran out of time is not paid again

landing: the served why read answers in 15.9 s on the reckon mount and 9.5 s on the nova mount through the head's code, against a 30 s deadline. The cost removed is in reckon/git_dates.py: _git_first_committed and _git_last_committed each ran a bounded git log and, when the ten-second bound expired, returned their fallback and recorded nothing, so every cold discovery at the same commit paid both bounds again. Each now records the fallback it used in the same persisted map the successful answer uses, keyed on the repository's HEAD, so the next discovery at that HEAD reuses it without spawning git while a commit moves the map on. On the reckon mount, whose two lookups both time out, a warm-home read falls from 38.4 s to 15.9 s; the first read of a fresh home falls from 141.9 s to 103.6 s and records the outcome the next read reuses.

How the figures were taken

Every figure is one call to reckon.mcp._read_plan(project, slug, section, view="why", checkout_path=<mount root>), made inside metadata_index.discovery_file_scope() and resources.resource_scan_scope() — the two scopes mcp_deadlines._deadline_tool(request_scope=True) enters — under timeout -s INT 240, on the fleet allocation (node 98dci4-clu-2068, job 1291586). RECKON_HOME was a writable directory on node-local scratch holding a copy of the user's mounts.json; the ledger rows the read consumes live in the mount's own docs/state/<project>/runs, so the figures measure the real mount's content. The base arm ran the base revision c849288268 from this worktree; the head arm ran the same call from a git archive extraction of head edebdc6b. The two mounts' refs are reckon:a-project-reads-as-one-picture#s8 and nova:iron-core-magnetisation#s9.

The stage that took the time

A cProfile run of the base call on the reckon mount attributed 47.9 s of its 51.0 s to reckon/mcp_discovery.py:149 _discover_project, and 20.1 s of that to four subprocess calls — two reckon/git_dates.py:_run_git spawns, each printing Git history lookup timed out after 10 seconds or Git last-modified lookup timed out after 10 seconds. The same profile puts reckon/serve.py:1852 _attach_ready_set at 15.3 s, of which roadmap.py:3473 _critical_path_coordinators is 9.8 s: the coordinator resolution that once dominated this read is now a minority of it. At the head, the only two timeout warnings of a fresh-home read are still those same two lookups, and the next read of that home prints none because it reuses what they recorded.

The test, and what it fails against

tests/test_the_served_why_read_answers_within_its_deadline.py builds a temporary repository and drives the reader the discovery calls, with a stand-in for the subprocess module that lets git rev-parse answer normally and makes git log run past its bound, counting the git log spawns through it. Two discoveries at one HEAD spawn two git log queries in total and any number after that spawn none; a commit moves HEAD and the next discovery spawns two more. A second test clears the process memo and keeps the persisted maps, so a fresh process reuses the recorded outcome. Both assert on counts the code produces rather than on literals about time. Against the base tree both tests fail on the spawn count (assert 4 == 2: the second discovery paid the timed-out lookup again); against the head tree they pass.

The negative control removes the recording itself, keeping everything else, and both tests fail on their spawn counts (EXIT=1, log logs/negative-control.log).

What is left, and why it is not this node's

The first read of a brand-new RECKON_HOME is still over 30 s on both mounts, and the stage is not reckon/git_dates.py: a head profile of that read on the reckon mount puts 95.9 s of 189.7 s in reckon/serve.py:1852 _attach_ready_set → roadmap.py:3499 build_roadmap, of which 82.6 s is mcp_views.py:1765 section_attempts_by_plan → ledger.py:1242 picker_runs building the ledger for the first time. That is a one-time index build at the read's first contact with a home, present at the base too, and it is outside this node's write scope; it is recorded under outside_scope in the run's manifest rather than changed here.
