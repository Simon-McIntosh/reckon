A git date lookup that ran out of time is not paid again

landing: at a warm writable RECKON_HOME, the served why read through head ae1bf9d7 answers in 15.7 s on the reckon mount and 11.7 s on the nova mount, both within the 30 s deadline. The first read against a brand-new RECKON_HOME is 103.6 s on reckon, still over 30 s; that stage is the one-time ledger index build in mcp_views.py:1765 section_attempts_by_plan → ledger.py:1242 picker_runs, which the base pays identically and which is outside this node. The cost removed here is in reckon/git_dates.py: _git_first_committed and _git_last_committed each run a bounded git log, and when the ten-second bound expired they returned their fallback and recorded nothing, so every cold discovery at the same commit paid both bounds again. Each now records the commit it ran out of time at — kept apart from the commit its incremental range starts from — so a discovery at an unchanged HEAD reuses the record, while a commit moves the range start past the unanswered gap instead of over it.

How the figures were taken

Every figure is one call to reckon.mcp._read_plan(project, slug, section, view="why", checkout_path=<mount root>), made inside metadata_index.discovery_file_scope() and resources.resource_scan_scope(), the two scopes mcp_deadlines._deadline_tool(request_scope=True) enters, under timeout -s INT 240, on the fleet allocation (node 98dci4-clu-2068, job 1291586). RECKON_HOME was a writable directory on node-local scratch holding a copy of the user's mounts.json; the ledger rows the read consumes live in the mount's own docs/state/<project>/runs, so the figures measure the real mount's content. The base arm ran base revision c849288268 from this worktree. The head arm ran head ae1bf9d7 from a git archive extraction, which is the revision the head logs name: logs/head3-reckon.log and logs/head3-nova.log. The stage that took the time

A cProfile run of the base call on the reckon mount attributed 47.9 s of its 51.0 s to reckon/mcp_discovery.py:149 _discover_project, and 20.1 s of that to four subprocess calls — two reckon/git_dates.py:_run_git spawns, each printing Git history lookup timed out after 10 seconds or Git last-modified lookup timed out after 10 seconds. The same profile puts reckon/serve.py:1852 _attach_ready_set at 15.3 s, of which roadmap.py:3473 _critical_path_coordinators is 9.8 s: the coordinator resolution that once dominated this read is now a minority of it. At the head, the only two timeout warnings of a fresh-home read are still those same two lookups, and the next read of that home prints none because it reuses what they recorded.

A timeout must not move the range start

Both lookups query incrementally from the commit their map was last answered at (cached.head..head). Recording the timed-out commit as that entry's head would have made the next query start past everything added between the last answer and the timeout: with no prior map, an empty map recorded at H1 would have meant only pages touched after H1 ever got a date, and the full-history query is exactly the one that runs out of time on the reckon mount. The entry therefore keeps the last answered commit as its range start — empty, meaning the whole history, when nothing has ever answered — and carries the timed-out commit in a separate field that suppresses a re-query only while HEAD is unchanged.

Two tests cover it in tests/test_the_served_why_read_answers_within_its_deadline.py. With a successful map at H0, a timeout at H1 and a successful query at H2, the H2 map holds the page added at H1. With no prior map, a timeout at H1 and a successful query at H2 give the full-history map. Both fail against head 3831c35a, where the timeout moved the range start; the negative control records the timed-out head as the range start and case (a) fails again, with EXIT=1 in logs/negative-control.log.

The test, and what it fails against

tests/test_the_served_why_read_answers_within_its_deadline.py builds a temporary repository and drives the reader the discovery calls, with a stand-in for the subprocess module that lets git rev-parse answer normally and makes git log run past its bound, counting the git log spawns through it. Two discoveries at one HEAD spawn two git log queries in total and any number after that spawn none; a commit moves HEAD and the next discovery spawns two more. A further test clears the process memo and keeps the persisted maps, so a fresh process reuses the recorded outcome. All four assert on counts and map contents the code produces rather than on literals about time. The gate at head ae1bf9d7 is 4 passed, EXIT=0 (logs/gate.log); the same file against base c849288268 fails both spawn-count tests with assert 4 == 2.
