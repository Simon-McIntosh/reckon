A section can be descoped

descoped joins the section declarations in reckon/_schema.py (SECTION_DECLARATION_ENUM and the SectionRecord model). It is deliberately outside OPEN_SECTION_DECLARATIONS in reckon/_plan_html.py, so the terminal guard and the critical path read it as closed, while both impl derivations count it as neither built nor outstanding — the same denominator position deferred holds. The reason rides on the section record as descope_reason, rendered to data-descope-reason and parsed back from it, so a plan read shows the declaration and why the work was dropped rather than a done tick that says the work exists. A reasoned declaration is one op: {"op":"set","path":"section_declarations.s4","value":{"status":"descoped","reason":"…"}}. A bare "descoped" value and a descoped entry in a whole-map set are both refused, because neither form carries a reason; _require_descope_reasons re-checks the same invariant over the whole working state, so no op order or path reaches the store with no reason attached.

The gate is tests/test_a_section_can_be_descoped.py. On the base commit 04ffdaf88, extracted with git archive onto node-local disk, the same file reads 5 failed, EXIT=1: the declaration is refused as unknown (status must be one of ['implementable', 'deferred', 'done']) and the record refuses descope_reason as an extra input. At the head de780f08 the same command reads 5 passed, EXIT=0. The five cases: a plan whose only open section is descoped closes through the close op; the derived impl figure reads 1.0 from a done section beside a larger descoped one, with source computed; the declaration and its reason survive a read; a reasoned descoped set is accepted; a bare descoped set is refused naming the reason and stores nothing.
