The create path (reckon/mcp_edit_plan.py) reads it with _pending_plan_limit, counts pending plans by the velocity census's own closed definition, and at or beyond the limit attaches the warning built by _pending_limit_warning to the successful create response. The lead locked warn in wip-limit-mode: creation always succeeds, and the reply carries the limit, the pending count and the three pending plans nearest to closing by implementation.

Creating a plan beyond the limit, on the real project

A full-state copy of reckon's docs tree (plans, distributed project state and its marker) holding 72 pending plans was asked to create zz-probe-limit-check through the same create path. The create ok and created were true, the plan file was written, and the response carried this warning:

plan created: project 'reckon' already holds 72 pending plans, at its limit of 25.
Nearest to closing, by impl (highest first):
a-dispatch-returns-without-its-worker (impl 1.0);
a-plan-is-reviewed-before-it-is-built (impl 1.0);
a-read-answers-inside-its-deadline (impl 1.0).

The first run of this probe read the copied project's limit as None and emitted no warning. That reading was an instrument fault, not the guard switching off: the copy lacked the distributed project-state marker, so the project manifest composed from the legacy index row, which carries no limit key. With the marker and its seven resources copied, the same instrument reads the limit as 25 beside the schedule horizon of 3 — a positive control that it sees a key known to be present — and the warning above follows.
