A long window's ledger search stays inside its git bound

recover_ledger_clocks no longer runs its ledger search as one patch-generating call over the whole window. A window reaching back months asks git for the patch of every commit that touched the ledger, and the unbounded call over the 2026-08-01 window measured 225.94 s producing a 429 MB patch, longer than the runner's 180-second bound, so the read timed out. Two changes keep it inside the bound. A run whose own record file (docs/state/<project>/runs/<run_id>.json) is added in the range is now placed at the adding commit by a path-limited git log --diff-filter=A --name-only that generates no patch, recorded under its own source, first_primary_record_file_addition_upper_bound, so promotion_clock_sources reports the two mechanisms apart. Only the ids left after that reach the search, which now lists the window's ledger-touching commits with a plain path-limited log and runs the existing -G expression over consecutive slices of _LEDGER_SEARCH_SLICE_COMMITS commits, oldest first, dropping the ids already placed from each slice's expression. The cache is stored after every slice with its head at the slice's last commit, so a long window is walked across slices and an interrupted read resumes at the slice it reached; a repeated read of a completed window issues no git call at all. The whole recovery is skipped once the cache reaches the window head. Neither source is promote_commit, so dispatch_to_explicit_promotion_seconds still excludes both.

Measure: tests/test_velocity_places_a_run_by_its_record_file.py builds a temporary repository with several ledger commits and a per-run record file, records every argv the module's git runner receives, and points both caches into the temporary directory so the real cache root is asserted untouched. Three cases hold: a run whose record file is added in the window is placed at the adding commit under first_primary_record_file_addition_upper_bound with no -p log over crew.json issued for it; with _LEDGER_SEARCH_SLICE_COMMITS set to one, a run with no record file is still placed by the sliced crew.json search, which takes several slices; and an interrupted read, with the runner raising subprocess.TimeoutExpired on the second slice, resumes with its first searched range beginning at the first slice's last commit and none beginning at the window base, while a third read of the completed window issues no search. Gate: 27 passed at head, 24 at base, EXIT=0 both arms. Each of the two declared mutations fails its case alone — disabling the record-file scan makes the first case fail on its argv assertion, removing the per-slice cache store makes the interrupted-read case fail — both at EXIT=1. _LEDGER_SEARCH_SLICE_COMMITS is 128; the measured worst slice over the full 2026-08-01 window (10,432 ledger-touching commits, sliced into 82) is 1.68 s, well inside the runner's 180-second bound. ruff check is clean on both staged paths; ruff format --check adds no finding to the pre-existing ones.
