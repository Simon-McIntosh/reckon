Presence checks read the project configuration, not the ledger

What this is. Four presence checks decided a repository was crew-managed by finding docs/state/<project>/crew.json. The two pre-tool-use guards fail open, so the untracking would have turned both silently off in every checkout. Each now recognises a crew project by the project configuration its state directory carries, which stays tracked after the run ledger leaves git.

The rule. A project is crew-managed when docs/state/<project>/ contains index.json, flight.yaml or crew.json. The ledger and the flight configuration are still honoured while a tree has not migrated; neither is required, because a migrated checkout carries only the project's own configuration. All four call sites use the same three markers: native_agent_guard.crew_managed_projects, worker_message_guard.crew_managed_projects, cli_entry._crew_state_exists and the shadow-dispatch fallback in crew/dispatching/comparisons.py.

Why project.json is not a marker. It is written into docs/state/<project>/ by every reckon sync, crew-managed or not, so keying on it would install the guards into repositories that have no crew project. Measured by running the sync CLI on a project state directory holding nothing else: it leaves project.json and timeline.html behind, and the existing sync case that requires the refusal be skipped still passes with project.json excluded from the marker set.

Evidence. tests/test_guards_hold_without_a_tracked_ledger.py builds a project whose state directory holds index.json, creates both ledger files and removes them, then requires the refusal from both guards and recognition from the CLI and the shadow fallback. A control case asserts a repository with no project state is still allowed by both guards, so the check is shown to see something rather than merely to be quiet.
