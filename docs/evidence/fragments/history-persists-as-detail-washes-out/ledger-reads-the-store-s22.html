Every ledger reader answers from the run store, and the documents it holds cover it run id by run id

What this is. The per-run directory docs/state/<project>/runs/*.json is the ledger's last file-shaped copy of history, and the locked decision committed-export-scope takes it out of git so the crew-home run store is the only store. A reader that still walked that directory would answer an empty ledger — reporting a project with no history rather than one whose history moved. This landing makes the store answer every reckon/ledger.py read path and the operational projection in reckon/crew/open_run_index.py.

The precedence rule. The documents cover the store rather than replacing it, so the merge is by run id and never by project. A project with its documents intact answers from its files; one whose directory is gone answers from the store; and a half-migrated project — one surviving document beside many stored runs — answers both. Choosing one source for the whole project would have shortened that project's history to whichever file survived, silently. Where both hold the same run id the document wins, because a stored row carries the durable half (a rotation may have washed its wide detail out) while a document still carries the promotion record.

The store read is the store's own, and it costs one project. A record is split across two tables and its retired rows live in an attached database whose name the store chooses, so the read that joins them back lives in reckon/run_store.py, beside the membership reader: one query scoped by the project column, its wide detail joined from the record's own table, retired rows read from the archive. The ledger asks for it and no longer names the store's private record index.

Two properties of that read matter as much as what it returns. It is scoped to one project, because one config home serves every project on the machine and a load for one must not decode every other project's history on a path a station tick takes. And it cannot write: the connection is opened read-only, so a store that is absent answers empty and leaves nothing behind, and a store that still owes a schema migration is left for whoever opens it to write rather than migrated by a reader.

How the population is measured. One fixture — three promoted runs, each still owing its retained worktree — is written as run documents and into the store over an isolated config home (RECKON_HOME set, RECKON_STATE_ROOT and RECKON_MOUNTS_PATH cleared). The first answer is taken with the documents present. The directory is then removed, the test asserts the removal reached the absent-runs-directory case and that the chosen run's own run_path no longer exists, the operational cache is dropped, and the same reader must return the same answer. Each answer is checked against the whole population, so an empty read cannot agree with an empty directory and be counted as a pass.

What the equality fixture cannot show, and the tests that can. An answer taken from documents and one taken from a lossless store are equal by construction, so equality alone cannot tell a store that keeps everything from one that keeps the durable record — exactly the difference a rotation makes. Seven tests measure the distinctions directly. A reader answered by the store decodes no payload (the store's JSON parser raises, and run_ids must still name every held run). A load decodes no other project's payload, on the same instrument aimed at a second project's payload. A load against an absent store leaves no file and no directory behind. A load answers a store it cannot write, with the store's schema record removed so the read would have to migrate it to fail. One surviving document beside stored rows answers both, with the document winning its own run id. A retired row still answers through the store's archive with its wide detail intact (a retirement moves a row, it does not rotate it), and a rotated row answers its durable half with the detail absent — the asymmetry the equality fixture cannot express.

The negative controls, and what they prove. Reverting the store read fails the two checks that measure what it changed: a load decodes another project's payload, because the reverted read decoded the whole store before filtering; and a load needs to write the store it reads, because the reverted read went through the store's constructor, whose schema setup migrates a store that still owes a migration — the test removes the schema record and makes the file read-only, so that write fails. The nineteen that pass in both arms are the population the earlier landing answered, plus the absent-store case: a store that is absent is not opened, so the old read happened to create nothing there, which is why the migration case is the instrument that can see the write. Reverting the figure fails its own check with 21 SVG text elements and two renders that differ.

What this node did not do. Two things belong elsewhere. load_aggregate keeps its writer semantics by design (see the table). The store read answers one project whole, so a caller that wants a single run still pays for its project's rows; no ledger reader names a single run id today, and a run-id filter belongs in the store's own reader; this round did not need it. detail-horizon, the decision that sets the store's location, is the plan's, not this node's.
