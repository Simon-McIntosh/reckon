Every ledger reader answers from the run store, and the documents it holds cover it run id by run id

What this is. The per-run directory docs/state/<project>/runs/*.json is the ledger's last file-shaped copy of history, and the locked decision committed-export-scope takes it out of git so the crew-home run store is the only store. A reader that still walked that directory would answer an empty ledger — reporting a project with no history rather than one whose history moved. This landing makes the store answer every reckon/ledger.py read path and the operational projection in reckon/crew/open_run_index.py.

The precedence rule. The documents cover the store rather than replacing it, so the merge is by run id and never by project. A project with its documents intact answers from its files; one whose directory is gone answers from the store; and a half-migrated project — one surviving document beside many stored runs — answers both. Choosing one source for the whole project would have shortened that project's history to whichever file survived, silently. Where both hold the same run id the document wins, because a stored row carries the durable half (a rotation may have washed its wide detail out) while a document still carries the promotion record.

The store read is the store's own. A record is split across two tables and its retired rows live in an attached database whose name the store chooses. _stored_run_rows therefore reads through RunStore._indexed_records(include_archive=True) and names the archive through RunStore.archive_path, rather than reproducing that layout against the tables itself: a second copy is one the store's own change would break silently. That read is not project-scoped — one config home serves every project — so the filter is this caller's, which is a cost recorded below.

How the population is measured. One fixture — three promoted runs, each still owing its retained worktree — is written as run documents and into the store over an isolated config home (RECKON_HOME set, RECKON_STATE_ROOT and RECKON_MOUNTS_PATH cleared). The first answer is taken with the documents present. The directory is then removed, the test asserts the removal reached the absent-runs-directory case and that the chosen run's own run_path no longer exists, the operational cache is dropped, and the same reader must return the same answer. Each answer is checked against the whole population, so an empty read cannot agree with an empty directory and be counted as a pass.

What the equality fixture cannot show, and the four tests that can. An answer taken from documents and one taken from a lossless store are equal by construction, so equality alone cannot tell a store that keeps everything from one that keeps the durable record — which is exactly the difference a rotation makes. Four further tests measure the distinctions directly: a reader answered by the store decodes no payload (the store's JSON parser raises and the run_ids answer must still name every held run); one surviving document beside stored rows answers both, with the document winning its own run id; a retired row still answers, reached through the store's archive, with its wide detail intact (a retirement moves a row, it does not rotate it); and a rotated row answers its durable half with the detail absent, which is the asymmetry the equality fixture cannot express.

The negative controls, and what they prove. Reverting the store read fails exactly the two checks that distinguish it: test_run_ids_decodes_no_stored_payload, because the reverted run_ids reaches its answer through a full read and so decodes the payload the instrument forbids, and test_one_document_beside_many_store_rows_answers_both, because the reverted rule chose one source for the whole project and the surviving document hid the store's rows. The remaining sixteen pass in both arms: they are the population the earlier landing already answered, and a control that failed them would be measuring something other than this repair. Reverting the figure fails its own check with 21 SVG text elements and two renders that differ, which is the blank-label failure the repair removed.

What this node did not do. Three things belong elsewhere. load_aggregate keeps its writer semantics by design (see the table). The store's record read is answered for every project and filtered here, so this caller pays a decode of other projects' rows — a project-scoped read on RunStore is the cleaner shape and lives in reckon/run_store.py, which this repair did not open. detail-horizon and the store's location are untouched.
