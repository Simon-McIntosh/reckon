An unreadable store is an error, not an empty project

What this is. The run store is the ledger's only store, so a read that cannot reach it must not be confusable with a project that holds no runs. Three shapes were measured doing exactly that through stored_run_rows, the read-only reader the ledger calls on every load: a file that is not a database, an archive that will not attach, and a runs table predating the payload column. Each answered an empty population while the id columns still listed every id, so nothing failed and a whole history read as absent. A fourth sits behind the same swallow with the guards passed: a store whose hot half is complete and whose run_details is gone fails inside the record query, and the swallowed query error answered an empty population there too.

The three base-revision shapes, what they answered there, and what a read now does — with a fourth, measured by the mutation that restores the swallow rather than by a base probe.

The rule. A store that is present but cannot be read raises run_store.UnreadableRunStoreError, and the message carries the store's path and the cause. The two read-only readers cannot migrate: the backfill is a write, and RunStore is what performs it. So a store whose runs table lacks a column a read selects is refused, naming the missing column and the migration that supplies it. The schema record is not the test: a store carrying every column answers whatever store_meta says, because that is the state a migration leaves when it commits its backfill and is interrupted before writing the record. Absence stays distinct from failure: an absent store still answers None.

The guard was first too wide. Keying the refusal on the recorded declaration refused a readable store — measured against the base, a test that deletes store_meta and requires the load to answer a store the caller cannot write passed at base and failed at head. The criterion moved to the table's shape, and that test passes again. Its lesson is the one the measure asks for: a guard is shown firing, and it also has to be shown not firing where reading is sound.

One record join. The record is split across runs and run_details, with retired rows in an attached archive carrying both tables. The join was written twice — once in RunStore._indexed_records and once in the read-only reader — so the module held two descriptions of what a record is. run_store._record_rows owns it, and both readers call it. The main branch carried that consolidation by the time this node merged; the refusal is applied on it rather than beside it, so the read-only reader and the indexed reader meet the same query and the same failure. A test holds the two readers equal over a store carrying a retired row, so a drift between them fails rather than passing quietly.

Evidence. tests/test_an_unreadable_store_is_an_error.py holds eight tests. The four error arms are asserted through ledger.load, which is where a reader meets the store, and each also asserts the reader itself raises rather than answering empty: a damaged file, an archive that will not attach, a runs table without the payload column, and a store whose hot half is complete while run_details is gone — the failure that lands inside the record query rather than at a guard. One test asserts the refusal is bounded — the same store, migrated through RunStore, then answers its row to both readers. One asserts a store with every column but no schema record still answers, which is the interrupted-migration shape and the over-fire this node measured and fixed. One asserts the absent store still answers empty, so the guard is shown to see a failure rather than to be loud. The last holds the ledger reader and the indexed reader equal over a store with a retired row, over a population of two runs, one of them archived.

Arms. Base 8e542a224c: the declared suite without the new test file, 58 passed. Head 2abf394180 with it: 66 passed. Both arms exited zero and ran to their summary line on one all_debug allocation; each log's first line names the revision, tree, module file, working directory and literal command, its last a bare EXIT=. Three of the seven tests the file then held fail at base (AttributeError: module 'reckon.run_store' has no attribute 'UnreadableRunStoreError') and the other four pass, so the file is not uniformly red against a tree that merely lacks the name. The base column of the table above is a probe run against the base tree rather than something a passing suite would show, because at base these shapes raise nothing.

Each guard is load-bearing. Three mutations were applied one at a time at the head, and each turned exactly its own arm red, with reckon/run_store.py restored byte-identical after each pass (logs/negative-control-a.log, -b, -c):

  • swallowing the query error inside stored_run_rows reddens test_a_store_whose_detail_half_is_unreadable_raises_rather_than_losing_the_record (Failed: DID NOT RAISE UnreadableRunStoreError, exit 1);
  • letting _refuse_owed_migration return instead of refusing reddens test_a_runs_table_without_a_payload_column_is_refused_naming_the_migration, and shows what the guard adds beyond the raw driver error: without it the base-style store still raises, but the message the reader sees is no such column: r.payload with no statement that the store owes its migration;
  • passing a failed attach over — continuing against the main database alone — reddens test_an_archive_that_will_not_attach_raises_rather_than_losing_retired_rows, which is the retired row that used to disappear.

Cost. The live store's runs table carries the current declaration, so the migration refusal does not fire on it: a whole-project read returns its rows in one call, and the two readers agree on the population — 11,382 rows read in one call against 11,382 ids listed at this pass. The figure moves with every run; the equality between the two readers is the property, not the number.
