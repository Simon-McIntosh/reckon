An unreadable store is an error, not an empty project

What this is. The run store is the ledger's only store, so a read that cannot reach it must not be confusable with a project that holds no runs. Three shapes were measured doing exactly that through stored_run_rows, the read-only reader the ledger calls on every load: a file that is not a database, an archive that will not attach, and a runs table predating the payload column. Each answered an empty population while the id columns still listed every id, so nothing failed and a whole history read as absent.

The three shapes, what the base revision answered, and what a read now does.
shapebase answernow
the store file is not a database stored_run_rows returned [] raises naming the store and DatabaseError: file is not a database
the archive cannot be attached returned the main database's rows only: the retired run r-1 vanished, while indexed_run_ids listed r-1 and r-2 raises naming the store and the archive, and why the attach failed
the runs table has no payload column returned [] while indexed_run_ids listed r-old raises naming the store and the migration it owes, including the missing column
no store at all None, and an empty roster unchanged

The rule. A store that is present but cannot be read raises run_store.UnreadableRunStoreError, and the message carries the store's path and the cause. The two read-only readers cannot migrate: the backfill is a write, and RunStore is what performs it. So a store that owes its migration is refused, naming the migration and the declaration it should carry, and opening the store through RunStore migrates it before answering. Absence stays distinct from failure: an absent store still answers None.

One record join. The record is split across runs and run_details, with retired rows in an attached archive carrying both tables. The join was written twice — once in RunStore._indexed_records and once in the read-only reader — so the module held two descriptions of what a record is. run_store._record_rows now owns it, and both readers call it. A test holds the two readers equal over a store carrying a retired row, so a drift between them fails rather than passing quietly.

Evidence. tests/test_an_unreadable_store_is_an_error.py holds six tests. The three error arms are asserted through ledger.load, which is where a reader meets the store, and each also asserts the reader itself raises rather than answering empty. One test asserts the refusal is bounded — the same store, migrated through RunStore, then answers its row to both readers. One asserts the absent store still answers empty, so the guard is shown to see a failure rather than to be loud. The last holds the ledger reader and the indexed reader equal over a store with a retired row, over a population of two runs, one of them archived.

Arms. Base 8e542a224c: the declared suite without the new test file, 58 passed. Head 24f983870b with it: 64 passed. Both arms exited zero and ran to their summary line. The three error arms fail at base. The base column of the table above is a probe run against the base tree rather than something a passing suite would show, because at base these shapes raise nothing. The declared mutation — restoring the swallow that returns an empty population — leaves the damaged-store test red (Failed: DID NOT RAISE UnreadableRunStoreError, exit 1), which is the log the run keeps.

Cost. The live store's recorded declaration version matches the current one, so the migration refusal does not fire on it and a whole-project read still returns its rows (10,979 rows for reckon, read in one call).
