Record consumption releases the store for writers

The shared record join fetches each selected query and closes its cursor before yielding rows. Python decoding and row consumption therefore do not extend that query's rollback-journal read lock. SQL projection and selection remain in place; encoded results are buffered per query rather than streamed from a live cursor.

At base 2f5dffd47271265c2a67ae2df52e4a84d3d30245, all three contention cases fail with sqlite3.OperationalError: database is locked: stored, projected and indexed reads hold off a separate process's record append. With the cursor change, all three pass. Commit receipts arrive in 0.313–0.434 s while consumption remains paused for at least 3 s. Each reader returns the same 10 hot and retired rows as its uncontended read.

The tests assert rollback-journal mode and the unchanged 120 s default record writer timeout. Their separate writer uses an explicit 1 s timeout to expose the blocked commit within the consumer's 3 s pause. The base-reader negative control records 3 failed in 9.37 s, exit 1; the focused repaired run records 3 passed in 12.31 s, exit 0. Both ran on all_debug.
