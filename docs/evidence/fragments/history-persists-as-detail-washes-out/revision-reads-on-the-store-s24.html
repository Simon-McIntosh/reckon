Velocity and the review-cycle figure read their revision-scoped history from the run store

What this is. Two readers answered a question about history out of a checkout's working tree. Velocity read docs/state/<project>/crew.json and each runs/<run_id>.json at the window head; the review-cycle figure (docs/figures/plan-review-cycles/measure_review_cycles.py) read the same aggregate for its build-dispatch times. Once the ledger leaves git — the cutover this plan makes — the first reports a project with no runs and the second drops every dispatch time out of the cadence, and neither fails.

The defect, quoted at the base revision. A repository whose four runs enter the tree one commit at a time and then leave it in a fifth, with the same four rows in an isolated run store:

held tree runs: 4
absent tree runs: 1 [["r-20260903T000000000000-node-0", "sqlite_fallback_for_reachable_promotion"]]
dispatch times with no crew.json: {}

The single surviving run is the one whose landing commit carries a promote(r-…) subject, so the pre-existing fallback could still find it; the three that landed under a plain record subject are gone, and a project whose promotions are all worded the other way reports zero. The figure's answer is empty with no error. Log: logs/base-defect-probe.log.

What the store now carries. The runs table gains a revision column: the commit the run's own record file entered the tree at. No record can supply that value. A promotion's promoted_revision is the tip of the run's own work, and the promotion commits the run's record file in its own commit, so the two are different commits by design; a column stamped from the record would name a revision whose tree does not hold the file, and the reader would get the row back as its own fallback with nothing failing. So every row starts empty and one pass writes the column: run_store.backfill_revisions reads run_store.record_file_additions, a single path-limited log over docs/state/<project>/runs that generates no patch, so the backfill costs one git call per project rather than one per run. The scan has one owner: velocity's own placement of a run at its record file's adding commit reads it too, narrowed to the window it is asking about. Rows whose file never entered the tree the checkout can see stay unresolved rather than being stamped with a guess, and a row that already names a revision is left alone.

Velocity. While the tree at the window head still carries the ledger or any run document, nothing changes: those documents answer. When both are absent, velocity._read_store_records reads the project's rows from the store and reads each record from the revision its row names, in one batched object read — the row carries the durable half, the historical file still carries the promotion record a rotation may wash out. A row the store cannot place answers from the row itself. A tree with no ledger, a store holding none of the project's rows, and a history that never carried the path are three states: the first two together raise with the store's own path named, and only a project whose ledger never entered the tree answers empty.

The figure. load_dispatch_times reads the store instead of a checkout, so its repos argument is gone and its one call site passes only the project set. A project the store cannot answer for — absent store, unreadable store, no row of that project — raises naming the store, because an empty mapping there is exactly the silent drop the read replaces.

The existing store keeps its rows. A store written under the pre-change schema gains the column on open, keeps every row, and keeps its payload verbatim: the probe builds a runs table without revision, opens the store, and reads back the same record it wrote while the column reads back empty — which is what the backfill is for. An archive written under the older schema gains the column too when the store attaches it, and a retirement through that archive keeps the rows it already held. Log: logs/store-migration-probe.log.
