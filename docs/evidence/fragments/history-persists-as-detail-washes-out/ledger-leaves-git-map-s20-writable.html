Outside reckon/

The revision-scoped readers are the ones an untrack loses silently. Two committed scripts read the ledger as git objects, not as files: reckon/velocity.py:731 lists blobs under docs/state/<project>/runs at a head, and :754 reads crew.json's blob at that head — docs/figures/plan-review-cycles/measure_review_cycles.py:333 constructs the same path. Those follow the history argument in §1 and §4: they keep working only while the ledger travels with a clone. velocity.py:1289 reads the same path from a patch. Neither fails loudly when the path vanishes: _read_ledger maps an absent blob to an empty ledger, so velocity would report zero runs and no error.

The one-time migration

Ordered so that no promotion is ever left unable to record a run. The two populations are one aggregate of 81,079,470 bytes and 8,795 per-run files under docs/state/reckon/ at the base revision.

  1. Make the store write load-bearing first. Today _index_append (ledger.py:3319) returns a failure on the payload and never raises, deliberately. That is correct while the file is the authority and fatal the moment it is not. Invert it before anything is untracked.
  2. Convert the aggregate into store tables. run_store.db already holds runs with the five query keys; members and holds do not yet have tables. register_member and the reap write them through ledger.write with a version pair, which a row-per-member table does not need.
  3. Import every row once, and prove it. run_store.import_ledger is that verb and is idempotent on live data. The check is run_store.compare: rows in file absent from store, rows in store absent from file, rows present in both and disagreeing — all three zero, per project.
  4. Untrack: git rm --cached, one .gitignore entry each. git rm --cached takes no glob, so one command per population: git rm --cached 'docs/state/*/crew.json' and git rm --cached 'docs/state/*/runs/*.json'. Two .gitignore entries follow, docs/state/*/crew.json and docs/state/*/runs/. History stays in git: a removed path is still in every earlier commit, which is the property the lead accepted with the export scope. Nothing is rewritten.
  5. The export lives outside the repository. The committed file becomes a periodic narrow export under the crew config home, so a reader with no shared home is served by it rather than by a clone.

What untracking silently breaks, and why each needs a section. The presence checks at native_agent_guard.py:92, worker_message_guard.py:94 and cli_entry.py:376 decide a repository is crew-managed by crew.json existing. The first two are the guards that stop a native agent writing into a managed tree — they fail open, so untracking them silently turns both off in every tree. Velocity's reads fail as zero, not as an error. The four commit paths above start failing on git add of an ignored path. Each is stated as its own section below rather than discovered by a promotion.

The proposed split

Write scopes are disjoint. The order is forced by the invariant, not by preference: each section is safe alone and no earlier one leaves a promotion unable to record a run.

Sections 1–3 are prerequisites, not ordering preferences. Untracking before 1 makes a store failure the silent loss of the only record. Untracking before 2 leaves every file reader with nothing to read. Untracking before 3 leaves the roster and holds — the small mutable halves §2 separates — with no home on the first dispatch that writes one. Section 4 must land before 6 because velocity reads at a revision and would report zero rather than refuse; section 5 likewise, because both guards fail open.

What this map does not decide. detail-horizon stays open and blocks nothing here — rotation is §5's gate and touches no path this untracking moves. The location of the store is settled by the earlier measurement rather than re-opened: GPFS under hosts reached from both login nodes, integrity ok in every configuration, and the default staying shared so one host's promotion is visible to another's reader. Nothing in this map writes a figure; the done-when names only this fragment, and the two relationships it describes — which writers commit, and which readers still open a file — are tables.
