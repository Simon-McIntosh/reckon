Critical work takes a freed slot ahead of waiting reviews

What changed. The admission order ranked a delivered run's review above every priority override, so no override could reach a freed slot while a review waited. A request whose override reaches its project's critical level now leads the lane: the critical level is the flight setting queue.critical_priority (default 100), read per project through the same resolved config the pass uses. Below that level every request keeps the order it had, with delivered reviews first. The setting is declared in reckon/schema/flight.yaml, shipped at 100 in reckon/schema/flight-defaults.yaml, and read by flight.queue_critical_priority; the ordering applies it in queue_order._precedence, and the admission pass's own hoist (ordering.priorities_first) no longer rebuilds the review's lead over a request the ordering raised above it.

Measured

With one queued review of a delivered run and one implement request, the order's head is the implement request at override 100 and the review at override 99, with no override, and at override 50 under a project layer setting the level to 50. At the base revision the same first case offers the review the slot ahead of the override-100 request.

The production paths, not only the raw ordering, are covered: the admission pass's fair_share_admission_order now returns the critical request, then the review, then a lower override, and the promotion queue's promotion_requests._pending_requests honours a project level of 50 for an override of 50.
