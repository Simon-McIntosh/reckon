Dispatch spends its time launching the worker

The launch-to-claim time, measured

The claim grace covered the window in which a dispatch that lost a registration race waits for the winning claim to launch its worker. That window was fixed at 15 s. Measured on the fleet node 2026-10-08 over 397 recent run directories, the launch-to-claim time — a claim's registration to the instant its worker record carries launched_at, the interval the loser actually waits on — is: minimum 1 s, median 10 s, 90th percentile 22 s, maximum 41 s.

The grace is now derived from that figure

The grace is the observed tail scaled by a margin, floored: max(5 s, 1.5 × p90). On the measured distribution that is max(5, 1.5 × 22) = 33 s. A slow fleet waits longer, a fast one does not hold a losing dispatch's turn, and a deliberate outlier beyond the tail does not stretch the bound because the figure is a percentile rather than the maximum. A fleet with nothing recent to learn from falls back to the 5 s floor rather than refusing on sight.

Committed run records under docs/state/reckon/ are 270 MB of the 359 MB tree — three quarters of it, across 5,042 tracked files. Leaving that share out of provisioning was considered and not implemented. The share is read: 20 test files reference docs/state or state/reckon, and the ledger, review-store and state-write paths resolve through it. An exclusion would break readers that depend on it, so the size cannot be cut without a scoped change to those readers, which this node does not own. No before-and-after provisioning measurement is therefore offered; the size is measured and stated, not cut.

Provisioning cost

A real git worktree add could not run on this host — the main checkout's .git is sealed read-only by the worker fence — so the write volume was measured directly by materialising the same revision with git archive <sha> | tar -x: 3.1 s to write 359 MB across the tree. This is the floor of the provisioning cost, since a worktree add performs the same write volume.
