pick candidates in one pass

A production pick now scans the ledger rows once instead of once per backend, and reuses its instruction census while the files it read still carry the stamp the census was built from.

What changed

  • snapshot.candidates calls one helper, _candidates_scan, which walks the rows once and yields both the per-(backend, model) outcome counts and the per-backend peak-utilisation values. The per-backend readers recent_outcomes and _peak_input_utilisation stay as the reference and produce identical figures.
  • Each lane document is parsed through routing.pick_lane_document with a pick-scoped cache, so a pick reads a document once however many backends name it. Every candidate field is unchanged: same counts, same peaks, same lane facts.
  • routing.context_census caches the node's input estimate on the stamps of the files it read (standing instruction chain plus the node's declared files). A second census of unchanged files reads none of them; a file whose stamp moved makes the census run again. The reused figure equals an uncached census of the same files.
