The suite keeps only failed tests' temp dirs and blocks live Jev whatever the credential

Temporary directories are cleaned

pytest 9.1 defaults tmp_path_retention_policy to all, so every test's tmp_path survived the run; the [tool.pytest.ini_options] block set only timeout. Four coordinator population runs with explicit per-arm --basetemp left 5.2 GB on the fleet node's /tmp, which reached 90%. pyproject.toml now sets tmp_path_retention_policy = "failed", so only a failed test keeps its directory for debugging and a green gate leaves nothing behind.

Measured on a fixed 20-file sample run with -n 8 and an explicit --basetemp, once at the unmodified revision and once with the retention change, same file list, both green (base 395 passed / 2 skipped; head 396 passed / 2 skipped, the extra case being the new JeV guard case):

The residual 2.1 MiB is directory state the retention policy does not own — session and module-scoped factories, and the fixture homes this suite's own conftest places — not retained per-test trees.

The reap runs before the prune

Retaining only failed tests' temporary trees collided with the suite's watch-producer reaper, which finds detached producers through the seat records written under each test's configuration home. A passing test's home is pruned at that test's own teardown, so by the session-end reap the record was gone and the producer could no longer be attributed — the liveness scan then failed the session on a producer it could not reap (test_a_watcher_armed_by_a_child_session_is_not_left_running failed twice alone at head). A function-scoped autouse fixture now reaps, at each test's own teardown, the producers recorded under the run's base temp directory — signalling before tmp_path is pruned — and mirrors the seat records into a stable subtree so a later reader (the parent test that measures the child session) still finds them after the tree is removed. The session-end /proc scan is unchanged and still fails the session on any live producer that never wrote a record (test_watch_arming_isolation.py::test_the_session_check_reads_a_producers_own_home, 8 passed).

No test reaches live Jev, whatever the credential

The previous isolation rested only on the credential being absent: the autouse no_live_jev fixture removed OPENROUTER_API_KEY_RECKON and pointed credential resolution at a path holding none. A test that set the key itself would build the request and send it. The same fixture now also wraps the client's HTTP call (urllib.request.urlopen, which reckon/crew/picker/client.py uses), so a request aimed at the picker endpoint (client.DECISIONS_ORIGIN) raises the existing LiveJevDisabledError before a connection is opened, while any other host a test fetches — its own loopback server — still reaches the network through the original call. A test that patches urllib.request.urlopen itself replaces this guard, so a test answering the call with a fixture keeps working.

A new case, test_a_present_credential_is_refused_before_the_network, sets a fake OPENROUTER_API_KEY_RECKON, dispatches a dry run with no lane named, patches socket.getaddrinfo to catch any host lookup, and asserts no lookup was attempted and that the selection is a recorded fallback (jev-error: LiveJevDisabledError) to the default backend. Loopback fetch tests (test_service_unit.py, test_server_listens_before_it_watches.py, test_rollup_isolates_a_project.py) still pass, confirming the guard delegates for non-picker hosts.

Gate and negative control

Gate over tests/test_suite_never_calls_live_jev.py, all tests/test_picker*.py, and the 20-file sample: base 395 passed / 2 skipped (EXIT=0), head 396 passed / 2 skipped (EXIT=0), zero added failures. Declared negative control — delete the guard's urlopen setattr — makes the present-credential case fail: the dispatch resolves openrouter.ai:443 and the socket spy records it (1 failed, EXIT=1), so the guard, not the credential, is what keeps the suite off the live service.
