Reckon owns the model catalogue

The model-selection facts for every backend — family, model, alias, effort, budget group and per-million rates — are a reckon decision, not a property of a machine, so they live in a reckon-owned layer at a precedence below the host layer. The host layer keeps only facts about the machine. This record classifies every key the host layer carried, places the catalogue, reports a host value over a catalogue value as a shadow, and proves that emptying the host layer of catalogue keys moves provenance and no value.

2. The catalogue, held as versioned repository data

The catalogue is the file docs/state/reckon/model-catalogue.yaml in this repository. It is versioned data read by every project's flight resolution, and it is not shipped in the wheel: naming models and providers inside the package would put routing identifiers into what agents read, which the routing-data rule forbids — tests/test_skill_contracts.py::test_no_routing_identifier_leaks_into_skills_or_source scans skills/ and reckon/ only, and docs/state is data outside that scan. It carries the catalogue keys for every backend the host layer defined, resolved as values at 2026-10-03: codex(gpt-6-sol, high, sol6, codex-sub), codex-luna(gpt-6-luna, xhigh, luna6, codex-sub), codex-terra(gpt-5.6-terra, xhigh, terra5.6, codex-sub, 2.0/12.0, as_of 2026-09-09), codex-astra(gpt-6-astra, xhigh, astra6, codex-sub), clive(deepseek-v4.1-flash, xhigh, dsv4.1-flash), claude(claude-sonnet-5-5, medium, sonnet 5.5), claude-opus(claude-opus-5-5, high, opus 5.5), claude-haiku(claude-haiku-4-5-20251001, high, haiku 4.5), native(alias harness). The catalogue carries no rates for the codex subscription lanes or the unmetered local lane, so they classify explicitly unpriced rather than pricing at a stale number.

The file is located from the running package's own checkout root — the repository root above the reckon package directory — so no other project's name enters the path and no foreign mount is consulted. RECKON_MODEL_CATALOGUE overrides the location for tests and unusual installs. A missing file means no catalogue layer, so the resolved values are exactly what the host layer supplies; a wheel install, which carries no docs/, resolves as it did before the catalogue existed. Every project's resolution applies the catalogue rather than only project reckon's: a test resolves a second, synthetic project — a temp project layer under a temp host layer, for a name that is not reckon — and shows the catalogue filling its backends.

Two rules hold the layering honest, both enforced in reckon/flight.py:

  • A catalogue entry alone creates no backend. The catalogue fills a key only for a backend another layer already defines, so a host that does not declare codex resolves no codex backend and no other workstation or project sees a phantom candidate.
  • A host, project or override value still wins. The catalogue is a default below the host layer, not an override above it.

3. The shadow report

reckon flight and the crew flight view report each host-layer value for a catalogue key as a shadow, naming the key, the backend and the file. The shadows ride the layer inventory rather than a new top-level key, so the report's existing shape is unchanged: the host layer's own row carries a shadows list. With the host layer as it stood at 2026-10-03, 32 host values shadowed the catalogue, every one naming /home/ITER/mcintos/.config/reckon/flight.yaml.

4. Proof that no resolved value changes

The resolved flight for --project reckon was captured as JSON under the run directory (r-20261003T032115043790-model-catalogue-in-reckon/before.json, after.json, emptied.json), re-generated against the relocated catalogue. before.json resolves with no catalogue layer (the pre-catalogue behaviour), after.json with the catalogue and the host layer as it stands, and emptied.json with the catalogue and the same host layer with its 32 catalogue keys removed — the later dotfiles commit this node makes safe. The relocated file's parsed data is identical to the packaged copy from the prior commit, so the move alone changes no value.

  • Resolved config: identical. Zero differing leaves across all three captures (before = after = emptied).
  • Provenance: 32 entries moved from host to catalogue, every one under backends.<name>.<catalogue-key>; no other key's provenance changed. With the host layer as it stands, 0 leaves resolve from the catalogue (the host supplies all 32); with the host emptied, all 32 resolve from the catalogue.
  • Shadows: 32 → 0. Once the host stops declaring a catalogue key, nothing shadows the catalogue.

So the host layer can be emptied of catalogue keys in a later commit, and the resolved values do not move.
