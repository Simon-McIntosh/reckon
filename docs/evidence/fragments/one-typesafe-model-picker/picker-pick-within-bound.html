picker-pick-within-bound — a pick measures each phase once and counts every live local worker

What changed. The dominant in-pick cost was re-done work. snapshot._fit measured every candidate's context window twice: routing._competence_verdict already measures the window and returns it under context, and _fit then called routing._context_fit_verdict a second time. The measurement reads the backend's instruction chain, whose repository lookup shells out to git rev-parse (~1.9 s each on this GPFS), so each candidate paid that subprocess twice on the pick's critical path. _fit now consumes the measurement the competence verdict already returned and only measures again when that verdict skipped its context check. lane_context._expected_wait reuses the pick's own records rather than re-reading its project's ledger through run_time_profile, which is what carries the pick's own ledger size off the critical path.

A narrowing that wasnot kept. An earlier revision also made _expected_wait skip a live local worker whose project differed from the pick's, on the grounds that reading a foreign ledger is slow. That is a latency trade, not a correctness one: the figure expected_wait_s is the median wall time for the local runs now live, so dropping a foreign project's worker makes it read null (or low) while the lane is genuinely busy. Every live local worker's shape is counted again; the only ledger read left on the pick's path is one per distinct foreign project that has a live local worker.

Result against the bound. With no live foreign local worker the median total fell from about 3.34 s to about 1.37 s, inside the 1.5 s target and well inside the 5 s dispatch bound; the duplicate context measurement is removed and the pick's own profile is read from the records it already holds rather than from its whole ledger. One ledger-scaling phase remains and is kept deliberately: profiling a foreign project that has a live local worker. On this workstation the pick's own project profile costs 3377 ms but is avoided; the one live foreign project cost 635 ms to read, so a pick that must wait on it lands near 2.0 s — inside the 5 s bound, above the 1.5 s target. Counting that worker is a correctness requirement, not a latency one: the estimate answers how loaded the lane is, so a narrowed answer is wrong rather than fast. A bounded recent-window ledger reader would remove the cost without narrowing the figure; that edit belongs to ledger.py and is recorded as a follow-on.

Cut phase outside this node's fence — reported, not fixed. The dispatch path pre-builds three inputs before pick() runs and outside its 5 s bound: ledger.runs (one ledger.load over 1567 per-run files, ~3.4–5.4 s), routing.shared_verdict_inputs together with capabilities.project_cache_status (~3.1–6.0 s), and budget.preflight (~2.7–6.5 s). These sit in ledger.py, capabilities.py and budget.py, outside this node's write scope, and they scale with ledger size. They do not touch the pick's bound, but they make a cold dispatch slow overall; the measured per-phase figures are recorded here and the follow-on node carries the repair. They are not a reason to raise the 5 s pick bound — they are a separate dispatch-latency defect.

Slow-Jev fallback. A pick whose Jev client runs longer than the bound must yield a recorded fallback, never a refusal. The bound is enforced in dispatch.dispatch_picker_selection, which runs pick() in a thread with PICKER_DISPATCH_TIMEOUT_SECONDS = 5.0. The new test test_slow_client_still_times_out_as_a_recorded_fallback lowers the bound to 0.05 s against a client that sleeps 0.4 s and asserts the result is {"action": "fallback", "fallback_reason": "timeout"} — the recorded fallback, returned before the client finished.

Negative controls. Reverting the _fit change — restoring the second _context_fit_verdict call — makes test_fit_reuses_the_competence_context_measurement fail: the test monkeypatches the second measurement to raise AssertionError("context fit measured twice in one _fit"). The control ran 1 failed / 3 passed with exit 1, the failing id being exactly that test (negative-control.log). Reinstating the wait-estimate narrowing — restoring if records is not None and owner != project: continue — makes test_expected_wait_counts_a_foreign_projects_live_worker fail, because the foreign worker is dropped and the estimate returns None where the test requires its median. That control ran 1 failed / 3 passed, the failing id being exactly that test (negative-control-repair.log).
