A fresh-process dispatch pick finishes inside its 5 s bound

Every reckon crew dispatch is a fresh CLI process, so the picker step that reaches dispatch_picker_selection is always a cold pick. Two of its inputs — the instruction-chain context estimate (routing._standing_context_input, whose repository lookup shells out to git) and the shared verdict inputs (routing.shared_verdict_inputs: capabilities.load_capabilities plus capabilities.project_cache_status, which walks the ledger) — are pure functions of files that change rarely. A new per-input cache file under ~/.cache/reckon/, resolved through RECKON_PICK_CACHE so a test points it at a temp dir, makes the second process skip them: the entry is keyed on a cheap [mtime_ns, size] stamp of every file the input reads, written atomically, and read as a miss when absent, unreadable, corrupt or version-mismatched. Nothing live is cached: availability, lane load and budget pace are untouched, and a pick's answer is unchanged.

A small driver runs dispatch_picker_selection in a new python process exactly as reckon crew dispatch reaches it (the three dispatch-scope inputs built as dispatch builds them, then the bounded call), on project reckon at 98dci4-clu-2018, one cold run then three back-to-back warm runs each arm. The bounded pick — the step the 5 s bound wraps — has a warm median of 916 ms, below the 2.5 s target, and its cold first pick is 1497 ms, inside the 5 s bound. The cut is the candidate snapshot (≤105 ms warm versus ~0.86 s) and the verdict-inputs ledger walk (14 ms versus ~4.1 s), both served from the cache on the second process. The full fresh-process path still reads about 7.5–9 s warm, dominated by the dispatch-scope ledger rows (ledger.runs) and the live budget snapshot (budget.preflight → latest_recorded); both are pure ledger reads the picker cannot cache in scope, and both belong to the files a concurrent node owns — see the follow-on.

Equivalence is proven, not assumed: tests/test_picker_fresh_process_pick.py builds the shared verdict inputs once uncached and once through the cached reader on the same fixture and asserts the two agree, that a moved stamp recomputes, that a corrupt file is a miss, and that a real second process skips the build — counted through a spy file the build appends to.

Follow-on. _picker_ledger_rows (ledger.runs, ~3.8 s) and _picker_budget_snapshot (budget.preflight's recorded-readings walk, ~3.9 s) are the remaining dominant fresh-process costs and are pure ledger reads over files a concurrent node owns (reckon/crew/dispatch.py and reckon/budget.py). The same capabilities.cached_pick_input facility keyed on the ledger stamp would serve both; wiring them is a one-cache-call change at their call sites outside this node's scope.
