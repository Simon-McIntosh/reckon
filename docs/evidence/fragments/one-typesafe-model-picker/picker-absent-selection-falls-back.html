An absent picker selection falls back deterministically

plan_dispatch resolves the picker route and then received no picker selection from any caller that does not run dispatch's own picker step — a validating dry run, or an internal re-dispatch. It previously raised picker route has no selection, so once routing defaults to route those callers would be refused before they could resolve. The route now falls back to the routing that would have run without the picker and records why the picker's answer is absent.

What the change does

  • A missing selection is turned into the same fallback shape every other absent picker answer uses, carrying fallback_reason: picker-selection-absent.
  • The caller's own backend request, when it made one, is kept; otherwise the configured default stands in — the deterministic backend a dispatch reaches with no picker at all.
  • The fallback is recorded on the resolved plan's picker_selection, so a dry-run preview shows what was decided and why.

Evidence

  • tests/test_routing_picker_key.py::test_absent_picker_selection_resolves_deterministically: at the base revision, applied against the base source, it fails with CrewError: picker route has no selection; at the head it passes and the resolved backend is the configured default alpha.
  • Negative control — the missing-selection raise restored on the head source: the new test fails (EXIT=1).
  • Gate tests/test_routing_picker_key.py tests/test_flight.py tests/test_picker_in_dispatch.py tests/test_a_brief_points_rather_than_quotes.py: base 128 passed, 2 skipped; head 129 passed, 2 skipped, zero added failure ids.

  • test_shipped_routing_default_is_shadow is renamed to test_shipped_routing_default_is_route and asserts route, applied against a shipped-layer configuration fixture that declares it so the check holds on either side of the routing-default change.
