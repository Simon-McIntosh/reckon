The member-friction guard fails when its store path is wrong

The member-friction guard test compared _guard_store() against real_store_home(), the same helper the guard calls, so on the standard XDG layout a guard reverted to a path literal stayed green. The test now sets HOME to a temporary directory and RECKON_HOME to a second, unrelated directory with RECKON_GUARD_HOME unset, and asserts the guard's target against a path written out in the test. Two cases cover the resolver's branches: with .config/reckon under HOME the guard must return <HOME>/.config/reckon, and without it the resolver's legacy branch must return <HOME>/docs-server. Only the legacy case separates the resolver from the XDG literal, which matches the XDG case too.

Before the change, replacing _guard_store()'s body with the literal Path.home() / ".config" / "reckon" left all six tests in tests/test_member_friction.py green (6 passed) — the guard guarded nothing.

The XDG-literal mutation now fails test_isolation_guard_watches_the_legacy_store_home and passes the XDG case (1 failed, 6 passed). The keep-RECKON_HOME mutation, which returns the second directory, fails both test_isolation_guard_watches_the_xdg_store_home and test_isolation_guard_watches_the_legacy_store_home (2 failed, 5 passed).

The gate — tests/test_member_friction.py, tests/test_no_test_spawns_a_provider.py, and every file using the isolated_project fixture (26 files) — runs 200 passed at the base revision and 201 passed at head, zero added failures.
