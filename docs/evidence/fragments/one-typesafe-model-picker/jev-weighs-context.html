Jev weighs each lane's context window against the node's estimate

A node whose input approaches a lane's window risks dying mid-way with no deliverable, so the picker now hands Jev the facts to send it elsewhere. Every offered candidate carries a context block: the window that gates the lane, this node's deterministic estimate against it, the share of the window that leaves free, and the peak input utilisation recent passed runs recorded on the lane. No numeric threshold is coded — headroom is one more figure Jev weighs, and a null figure reads as unknown, never as zero.

What the change does

  • PickRequest.estimated_context is filled on the dispatch path from snapshot.estimated_context_tokens, the same standing-instruction-plus-file census the context-fit verdict charges a node against.
  • The request-level estimate and every candidate's block are one estimate: the dispatch authority is threaded into both, so a dispatcher-granted landing fragment is exempt in each and the two figures describing one node agree. Measured for a node with a granted fragment: both read 51535 tokens; measured without the authority the request-level figure is larger, which is the split the threading removes.
  • Each block renders window_tokens, estimated_tokens, headroom_pct and peak_utilisation_p50_pct / peak_utilisation_p90_pct and peak_utilisation_runs; the peak figures come from recent passed runs on that lane whose throughput block recorded a percent.
  • A lane the node cannot fit is not offered at all — it stays excluded with its context-fit: context-window-exceeded reason rather than left for Jev to weigh.

One real node's rendered context block

An implement node whose brief names a 4 kB repository file estimates 51 535 input tokens. Against a local lane declaring a 60 000-token window the estimate leaves 14.1 % headroom; against a metered lane declaring 200 000 it leaves 74.2 %. Both blocks are rendered from the same once-per-pick estimate, so the node is described identically wherever it is weighed.

A node whose estimate exceeds the local lane's window (60 000 here) is excluded from that lane with context-fit: context-window-exceeded and offered on the lane whose window holds it with positive headroom — the behaviour fixed by tests/test_jev_weighs_context.py.

Rendered state size

The state Jev reads for a representative 9-candidate implement node was measured at both arms with the picker's own rendered_token_estimate (tests/test_picker_pressure.py::test_representative_live_state_fits_the_token_bound):

armrendered tokensbound
main (no context block)14961500
head (context block)18812200

The context block adds 385 tokens across nine candidates, about 43 tokens per candidate. The render bound rose from 1500 to 2200 in test_picker_pressure.py and from 1500×4 to 1500×5 in the sibling picker tests to admit it; the head figure of 1881 sits well inside both. Each field carried is one Jev acts on — the window, the estimate, the headroom and the three peak-utilisation figures — so none is dropped; a shared window is not yet hoisted, and the block is the only cost of the change.
