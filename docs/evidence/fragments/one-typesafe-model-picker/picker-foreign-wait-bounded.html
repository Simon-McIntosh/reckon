picker-foreign-wait-bounded — a pick reads each foreign project's ledger once

What changed. The expected-wait figure counts every live local worker, so it profiles each distinct foreign project that has one. Profiling a project decodes its whole ledger: the pick's own records are reused, but each foreign owner called run_time_profile on every pick, so a pick's cost grew with the number of projects live on the local lane. The profile is a function of the ledger's contents and the trailing window alone, so a reading whose ledger has not moved is the same answer. lane_context._cached_run_time_profile now memoizes each project's profile, keyed on a freshness stamp of its ledger, and re-reads only when that stamp moves. A real dispatch is a fresh process, so the memo alone would be cold on every pick; each profile is also persisted to a small per-project file (~/.cache/reckon/run-time-profile/<project>.json, path overridable through RECKON_RUN_TIME_PROFILE_CACHE) holding the stamp, the window end date and the profile summary — never raw rows — written atomically through a temporary file and os.replace. A missing, unreadable, foreign or stamp-mismatched file is a cache miss, never an error. The figure itself is unchanged: every live local worker, foreign or not, still contributes its shape's median.

The key, chosen by measurement. Decoding one project's whole ledger on this GPFS costs 123 ms (imas-ambix, 223 run files), 242 ms (nova, 223 files) and 2948 ms (reckon, 1589 files). The alternatives the plan names measure as follows: a stat of the ledger directory's modification time is 0.02 ms; a glob-and-stat of the newest run file is 3.8 ms for the small ledgers and 28 ms for reckon's 1589 files. The chosen key is two stat calls — the aggregate ledger file's modification time and size beside the runs directory's modification time — which is about 0.04 ms, four orders of magnitude below the read it guards. It still covers every way the ledger moves from outside: a promoted run adds a file (directory mtime) and any edit to an existing row rewrites the aggregate (file mtime). The window's end date is folded into the key too, so a project whose ledger stays still is re-read at least daily and a reused window cannot grow arbitrarily stale. Deriving the foreign contribution from the lane document was rejected: that document carries counts and throughput, not the per-shape wall-time medians this figure is built from.

A real dispatch-path pick, in fresh processes. A real crew dispatch is a fresh process, so an in-process memo alone cannot bound a pick. Two separate interpreter invocations of a real pick(…, cached_only=True) for project reckon (its foreign set is {nova}), pointed at one shared cache directory (log: measure-pick-fresh.log): the first process read nova's ledger once (434.0 ms) and routed to clive; the second read no foreign ledger at all and routed identically. Both pick totals were about 9.7–10.6 s, dominated by non-foreign phases (candidate context measurement and Jev, itself 354–499 ms) that this node does not touch. The phase measurement above is where the bound shows, because it holds the two large foreign ledgers in the set. That the whole pick still runs near ten seconds in this worktree is recorded under follow-ons rather than repaired here.

The test. tests/test_picker_foreign_wait_is_bounded.py puts four foreign projects' live local workers on the lane, monkeypatches run_time_profile to record every project it is asked for, and calls the expected-wait figure twice with no ledger moved. It asserts each project was read exactly once, so a reverted reuse doubles every count and fails. A second case moves the ledger stamp between picks and asserts both projects are read again, so the reuse cannot pass by ignoring a changed ledger. A third case runs the pick in two separate subprocesses against one shared cache directory and asserts the second process reads no foreign ledger, which is the property an in-process memo cannot provide.

Negative control. Removing the persisted-profile read makes the cross-process test fail: 1 failed / 2 passed, exit 1, the failing id being exactly test_reuse_survives_between_processes, whose second process then reads all four foreign ledgers (negative-control.log).
