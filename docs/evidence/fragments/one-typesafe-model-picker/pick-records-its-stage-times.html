Every production pick records where its time went

A pick that hit the five-second dispatch bound recorded only fallback_reason: timeout, so the stage that spent the budget could not be attributed. picker.pick() now times each stage it runs and appends one JSON line per pick under the crew home, so a timed-out pick and a late pick are both attributable to the stage that spent the time.

What landed

  • Per-stage timing in pick() (reckon/crew/picker/__init__.py). Five stages are timed: snapshot_ms (the candidates snapshot, including the one docs-tree scan), estimate_ms (the estimated-context figure), state_render_ms and questions_render_ms (prompt rendering, split so a slow render is not charged to Jev), and jev_ms (the request: connect plus response). A stage that did not run reads null, never a measured zero.
  • One line per pick, appended best-effort. _record_pick_timings writes to pick-timings.jsonl under crew_home() — the same resolver every other crew-home path uses, so a test's RECKON_HOME isolation covers it. The append is a single os.write on an O_APPEND descriptor (one small line cannot interleave with a concurrent pick's), and the whole write is wrapped so a pick never fails or stalls on its own record.
  • The bound comes from the dispatcher, not a copy. within_bound is computed against dispatch.PICKER_DISPATCH_TIMEOUT_SECONDS, read at write time, so the flag cannot drift from the timeout dispatch actually applies.
  • Late picks still record. The pick runs on the dispatcher's daemon thread, so when the wait returns at the bound the pick keeps running; its line is written when the slow stage completes, carrying within_bound: false and the whole-pick latency_ms.

The line

Fields: started_at, project, node, session, latency_ms, outcome, decision_source, fallback_reason, the five stage milliseconds, and within_bound. A representative line produced by a stubbed pick (stages present, all in bound) reads:

{"started_at":"2026-10-07T18:23:59.079226+00:00","project":"example","node":"parser","session":"s-demo","latency_ms":1.469,"outcome":"route","decision_source":"jev","fallback_reason":null,"snapshot_ms":0.02,"estimate_ms":0.005,"state_render_ms":0.028,"questions_render_ms":0.026,"jev_ms":1.346,"within_bound":true}

Checks that could have failed

tests/test_pick_records_its_stage_times.py holds four tests:

  • A routed pick writes exactly one line with every stage present and numeric (test_a_pick_records_every_stage).
  • A pick slower than the bound still writes its line, marked past-bound (test_a_pick_past_the_bound_records_when_it_completes). The pick runs on its own thread as dispatch starts it; the waiter gives up at the bound while the pick is still inside its slow stage, the log is asserted empty at that moment, and the line is asserted only after the stage returns.
  • An unwritable log path leaves the pick's result unchanged (test_an_unwritable_log_leaves_the_pick_unchanged) — a file stands where the crew directory must be, so every append fails.
  • The log resolves through RECKON_HOME, never a candidate real home (test_the_real_crew_home_is_untouched): with Path.home() pointed at a temp tree holding an existing ~/.config/reckon, the line lands under the isolated home and the candidate real home is left absent.
