The control is judged against the head arm — evidence

_require_declared_negative_control in reckon/crew/promotion.py now admits a control on a failure its head arm passes rather than one its baseline does not fail. The head arm is the run's own after_suite: the suite as it stands after the repair. The baseline — the suite taken over the unfixed tree — is still read, but only when the manifest records no readable head arm, which is the one case where it is the best evidence available. A node that writes its cases before the repair is the reason: every new case is red at the base by design, so the old comparison refused exactly the controls that reddened them and four promotions on 2026-09-28 could proceed only on --waive-negative-control.

The defect, reproduced before it was repaired

A test-first node runs its suite twice: the baseline arm over the unfixed tree, the head arm after the repair. Its control reddens one of its own new cases, so the failing id is present in both arms' failure sets at the moment the baseline is taken — the case does not exist before the node writes it, so it fails there by construction. The old gate subtracted the baseline's failure_ids from the control's failing ids and admitted the control only if something remained. Nothing remained. The refusal, quoted from base-arm.log (revision 27f6266a, the commit before this node's change):

E  reckon.crew.CrewError: run 'r-20260929T070000000000-control' declares the mutation
   'applied: the early return was removed in a scratch copy' but the log at
   '.../control.log' shows no failed control run: it adds no failure to the baseline's:
   every test it names (tests/test_guard.py::test_a_red_before_the_repair) is one the
   baseline already fails.

The node's measurement was correct and the control was sound; the arm it was compared against was the wrong one. Four promotions hit this on 2026-09-28 and each was recorded on a waiver rather than admitted on its facts: r-20260928T142644163914, r-20260928T193532461213, r-20260928T204215455574 and r-20260929T001417713998.

The arm is also the one place the comparison could be defeated by the honest answer: three of those four runs share a suite with concurrent nodes, so their head arms do carry failures — other nodes', not theirs. Containment against the head arm's own failure set is what tells the two apart, and it is why the rule is a set difference rather than “the head arm is clean”.

The admitting fact

  • Two facts, unchanged and still not inferred. The control's log must carry a terminal EXIT=<n> record other than zero, and must name at least one failing test id. A log with no record, a log reading zero, and a log naming nothing each refuse the control, as before.
  • The third fact changes arm. The control's failing ids are differenced against the head arm's failure_ids. At least one id the head arm passes admits the control; every id already in the head arm's set refuses it, with the refusal naming the head arm.
  • A readable head arm is after_suite carrying a failure_ids list of non-empty strings, and not marked completed: false. Anything else — the key absent, the observation incomplete, a failure_ids value that is not a list of ids — reads as no readable head arm and falls back to the baseline comparison. The fallback is deliberate: reading a malformed arm as failing nothing would admit every control, which is the fail-open shape this gate exists to avoid.
  • The verdict row carries all four. control_failure_ids, baseline_failure_ids, head_failure_ids when a head arm was read, and comparison_arm naming which of the two decided — so a reader sees the disagreement between the arms without reopening either log.

The remedy text a refused worker receives now reads “at least one failing test id the head arm does not fail, falling back to the baseline's failing ids only when the manifest records no readable head arm”, and the two refusal branches are worded apart, so the message says which arm refused and what to re-run.

The gate and its two arms

The population is this node's new test file plus every tests/ file whose name contains negative_control or control_gate — seven files, 51 cases. The baseline arm ran them against the base revision tree (git archive of 27f6266a) with this node's new test file added, since the file is the measurement: 4 failed, 47 passed, exit 1 (logs/base-arm.log), the four failures being exactly the cases that assert the new arm — case (a), case (b), and both parametrisations of case (c), each red because the behaviour does not exist at the base. The head arm ran the same population in this worktree at the committed head: 51 passed, exit 0 (logs/head-arm.log and logs/focused-gate.log), adding no failing id to the baseline's four. Both logs carry their revision on line one and end in an EXIT= line; the two scratch-tree runs name reckon/crew/promotion.py as imported and the directory they resolved from, so the tree a figure measures is checkable rather than asserted.

The five cases the gate is written around: (a) an id red in baseline_suite and green in after_suite admits the control, with comparison_arm reading after_suite; (b) an id that also fails in after_suite is refused by the head-arm branch; (c) with no readable after_suite — absent, and present-but-completed: false — the baseline decides, refusing an id it fails and admitting one it does not; (d) a log whose capture exited zero is refused whatever it names; (e) a log with no exit record is refused. The tests build their manifests and logs under pytest's tmp_path and read nothing outside it: no real run directory is touched.

The negative control

The declared mutation is “restore the baseline-only comparison in a scratch copy; the test-first case (a) must be refused and fail”, applied in /tmp/nc-head-arm-mutation-tree by forcing reference_ids back to baseline_ids. The restored comparison refuses the control in case (a) with the old baseline wording, so the case fails on the attribute the change introduced; case (b) fails with it, because a gate that never reads the head arm admits a control whose id the head arm also fails. 2 failed, 49 passed, exit 1 at a non-zero EXIT record (logs/negative-control.log), the mutation verbatim on line one and the EXIT=1 record after pytest's own output. The 49 that stayed green are the rest of the population, so the mutation's blast radius is the two cases it should move and nothing else.

The four waived promotions, replayed

A rule that admits a control the old one refused has to be shown against the runs it was written for, and read-only: docs/figures/crew-runtime-positive-controls/control-is-compared-with-the-head-arm/replay_head_arm_admission.py reads each run's own manifest, its control log and its committed row from disk, rebuilds the node record the gate judges, and calls the gate. No run directory is written to. All four are now matched, each with comparison_arm: after_suite and the control's failing id named as the one id added to the deciding arm:

  • r-20260928T142644163914 (lane reading) — admitted via after_suite; its head arm's three failure ids all name cases in tests/test_lane_advisory_on_dispatch.py, another node's file, so this is the containment case rather than an empty-arm case.
  • r-20260928T193532461213 (receipt rollback) — admitted via after_suite; its head arm records no failing id.
  • r-20260928T204215455574 (directory row) — admitted via after_suite; its head arm records no failing id.
  • r-20260929T001417713998 (orientation stub) — its head arm's four failure ids name cases in other test files; the control's id is in none of them.

A replay that could only print the answer it wanted would be evidence of nothing, so a fifth entry replays the first run with its head arm removed: with no readable arm the baseline decides again and the control is REFUSED, in the fallback's own wording. The instrument can still say no, and the fallback is exercised rather than assumed. Both halves are in logs/replay.log.

Lint and format

ruff check and ruff format --check over the changed paths add no finding against the base: reckon/crew/promotion.py carries ten findings before the change and ten after, and the new test file carries none — counted per finding with --output-format=concise rather than by line count, because a clean file prints its own summary line.

What this measure is not

This gate measures the change on its own tree. Whether the merged result holds alongside the other nodes of this section is a separate measurement belonging to a node dispatched for it, and none is claimed here. No finding outside the declared scope was triaged: the failures visible in two replayed runs' head arms name other nodes' test files and are recorded on those runs, not repaired here.
