An arm that declares no completion decides no control, on both arms — evidence

The control gate compares a red log against a readable suite arm. The head-arm reader _head_suite_failure_ids was already strict: it asks observation.get("completed") is not True, so a key-less or null after_suite is unreadable and the baseline comparison decides. The baseline reader _baseline_suite_failure_ids was not: it returned the failure_ids of any baseline_suite mapping regardless of completion, so a baseline that omitted the key or carried null decided the control while its own run said nothing about having finished. The followup asks that a missing or null completed be unreadable on both arms.

The baseline reader now asks completion the same way, a literal True, and returns None for an arm that omits the key or carries null. A manifest that recorded no baseline_suite at all still reads as the empty arm, because it observed nothing and every failure its control names is one the baseline does not.

A naive strict read is fail-open in one direction, and that direction is closed here. If the unreadable arm were folded into the empty set, a control would be admitted with no comparison at all, and a manifest omitting completed from both arms would admit every control. Instead, when the head arm is also unreadable, there is no arm left to compare against: reference_ids stays None, comparison_arm is recorded as none, and the control is refused rather than admitted on a comparison that was never made.

The measure

  • Two cases, one per form. tests/test_control_is_compared_with_the_head_arm.py gains a baseline_suite with no completed key and one with completed: null, each over a log whose failing id that baseline would have exempted had it been read as complete, and with no readable head arm. Under the old reader both were admitted; under the new one both are refused with no readable comparison arm is recorded, and a third case shows the same manifest with completed: true admitting the control via comparison_arm: baseline_suite.
  • Head arm (7e452839): 21 passed in 0.66s, EXIT=0, over the two control-gate files. logs/head_arm.log.
  • Negative control (whole answering commit reverted to 7e452839's parent, tests unchanged): 2 failed, 12 passed in 0.59s, EXIT=1, the two failures being exactly the missing-key and null baseline cases, each reporting DID NOT RAISE CrewError — the lenient baseline reader admitting the control it should refuse. logs/negative_control.log.
  • Gate-adjacent population (nine files touching negative_control_log or the gate): 101 passed in 234.11s, EXIT=0. logs/gate_population.log.
  • Lint. Zero added findings on the changed paths: ruff check reports 5 against a 7-finding baseline over the same two paths, and ruff format --check leaves the same nine pre-existing hunks in promotion.py and none in the test file.

A pinned fixture keeps its refusal, but by a different path

Under the new rule that baseline is unreadable, so the case now refuses through the no-readable-arm branch rather than through the baseline comparison. It still refuses and its assertions still hold, but it no longer exercises the comparison its name describes.
