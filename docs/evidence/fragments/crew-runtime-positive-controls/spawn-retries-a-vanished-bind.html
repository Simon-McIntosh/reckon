A worker spawn retries when a protected bind source vanished — evidence

The fence composes a read-only bind for every protected path present at composition, from the declared set, and a writer that replaces a file by rename leaves the name missing for an instant — the harness replaces ~/.claude.json that way. A spawn landing in that instant died inside bubblewrap before the worker started: bwrap refuses a --ro-bind whose source is absent at mount time, so the run was recorded as a launch failure for a source that was back a moment later, and the node was failed for a race the retry now absorbs.

The mechanism, and what is deliberately not retried

  • Recognition is keyed to this launch's own binds. _read_only_bind_sources(argv) lists the --ro-bind sources the argv would mount, and _refusal_names_a_bind_source matches one of the two phrases bwrap answers with when a source is gone (Can't bind mount, Can't find source path) and a source this launch mounted. A refusal over anything else, and any spawn failure at all, is returned at once for its caller to record as the launch failure it is.
  • The retry is inside one attempt. A worker that starts on a later try is the attempt that launched: nothing is appended to launch_failures and the run's phase is untouched. Each dead try is reaped by process.wait() so it cannot later be mistaken for the worker's own exit. Tries are bounded by _backends.PROTECTED_BIND_WAIT_ATTEMPTS with _backends.PROTECTED_BIND_WAIT_INTERVAL_SECONDS between tries; a refusal that outlives the bound ends as the launch failure it is.
  • The startup window is its own constant. Whether the sandbox started is judged over SANDBOX_STARTUP_WINDOW_SECONDS (0.5 s), sized for a loaded host: bwrap's startup competes with every other process on the machine, and a too-tight window is wrong in both directions — a refusal missed becomes a launch failure recorded for a worker that would have started. The composition's own wait constant is not reused for this, and the test runs under the shipped values with a floor assertion on the window.
  • Both spawn seams share the retry — _spawn_detached_worker and _supervisor_spawn_worker each build a per-try attempt() closure.
  • A poll consumes the status it observes. The retry's startup check polls the fresh child, so a worker that died inside that window is no longer waitable; registering its pid handed the reaper a child it could not wait (ChildProcessError ECHILD), and the reap discarded the pid without recording the failure while the _LAUNCHED_WORKER_RUNS entry leaked. The detached seam now records the exit the check collected, exactly as a reap would record it, instead of registering a pid the reaper cannot wait.
  • The launch seam accepts a stand-in. The supervisor seam is exercised both by real spawns and by tests that replace Popen with an object carrying only a pid; the startup check treats a launch that cannot be polled as started rather than failing on it, since the refusal is proved by the child's own exit.

The pool control driver mutates what the fence reads

The fence composes from declared_protected_paths (the intent), not from the narrowed protected_paths (what is on disk now) — a protected path absent for an instant must still be sealed, which is the same race this node retries. tests/test_fence_protects_the_worktree_pool.py's _negative_control_report therefore patches declared_protected_paths through _without_pool, so stripping Code/.reckon-worktrees removes the pool's read-only overlay from the composed argv and case 1's write into the sibling lands, which is the control's red result. The new test file's last case pins both directions: the composed launch really does overlay the pool, and under the mutation it no longer does.

The review's three changes

  • The reformat sweep was reverted. The retry commit had formatted the whole of reckon/crew/dispatch.py, joining and wrapping eleven regions with nothing to do with the retry. 897205ea4 restores them to their base text, so the file's diff against base carries only the retry hunks (three hunks at lines 7885, 8003 and 8760 as committed).
  • The startup window is its own constant. It previously reused PROTECTED_BIND_WAIT_INTERVAL_SECONDS (the composition's own wait, 50 ms) and the test widened that shared constant to 250 ms, so the shipped value was never exercised. f4cffd20e adds SANDBOX_STARTUP_WINDOW_SECONDS = 0.5, keeps the retry pacing on the composition's constant, removes the test's widening, and asserts the window's floor.
  • The baseline arm is recorded as JSON (gate-base-bind-2.json: arm, revision, the literal command, log_path, completed: true, exit_status, failed_ids), run over the gate files from a fresh git archive of the base.
