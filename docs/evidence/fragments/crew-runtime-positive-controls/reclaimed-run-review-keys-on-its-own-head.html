A reclaimed run's review keys on its own head

The review reflex keyed on the shared checkout's HEAD whenever a run's worktree had been reclaimed: the manifest cited its commits by nine-character id, the pointer carried no head, _record_carried_head accepted only full object ids, and _reviewed_run_head then fell through to the run's repository — the main checkout. Each review's own promotion commit moved that HEAD, so the next sweep found the stored review stale and dispatched another, five reviews in half an hour. Two readings now close that loop. _record_carried_head resolves an abbreviated commits: entry of seven or more hex characters to its full commit id through the run's repository, which shares the object store its worktree wrote into, by running git rev-parse --verify on the entry with ^{commit} appended, and still skips an entry git cannot resolve unambiguously. And _review_head_and_tree returns an empty head, not the repository HEAD, for a run whose worktree path no longer exists and whose record names no resolvable head; the reflex then composes no review for that run and records the missing head as the reason.

The pre-existing pin this done-when collides with

test_a_reclaimed_worktree_with_no_recorded_head_does_not_accept_the_newest (from 08a8a7d2f, 2026-09-30, two days before this section's observation) asserts both halves of the superseded reading at the evidence-selection surface: with a reclaimed worktree and an unresolvable manifest commit, recovery._stored_review must return None when only an earlier-head review is stored, and must return the review when it is at the repository HEAD. Its docstring states it plainly: the repository fallback resolves the head, and a review of it stands. This section's done-when requires the opposite — the archived run must never resolve to the shared checkout's HEAD — and its fence states the empty head is returned by _review_head_and_tree itself, the one source _stored_review reads. No implementation of that function can satisfy both texts, and the pin is outside this node's write scope (reckon/crew/recovery.py and the new test file). The implementation therefore stands as specified, its own two cases pass, and this run reports blocked naming the failure rather than editing a peer's file or bending the reading. Resolving it is a scope decision for the coordinator: either the pin is updated to the new reading in its own node — dropping the repository-HEAD half; and with an empty head the newest-head selection for an empty head's record needs settling, which is where the first assertion lands — or the done-when is amended.
