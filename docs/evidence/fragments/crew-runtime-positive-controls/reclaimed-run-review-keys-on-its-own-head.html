A reclaimed run's review keys on its own head

The review reflex keyed on the shared checkout's HEAD whenever a run's worktree had been reclaimed: the manifest cited its commits by nine-character id, the pointer carried no head, _record_carried_head accepted only full object ids, and _reviewed_run_head then fell through to the run's repository — the main checkout. Each review's own promotion commit moved that HEAD, so the next sweep found the stored review stale and dispatched another, five reviews in half an hour. The readings that close that loop: _record_carried_head resolves an abbreviated commits: entry of seven or more hex characters to its full commit id through the run's repository, which shares the object store its worktree wrote into, by running git rev-parse --verify on the entry with ^{commit} appended, and still skips an entry git cannot resolve unambiguously; _review_head_and_tree returns an empty head, not the repository HEAD, for a run whose worktree path no longer exists and whose record names no resolvable head, and the reflex composes no review for that run and records the missing head as the reason; and the head-move carry-forward reads the same resolution, so no branch borrows the checkout.
