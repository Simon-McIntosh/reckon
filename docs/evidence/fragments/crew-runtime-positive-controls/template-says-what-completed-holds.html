The manifest template states what a suite arm's completed holds — evidence

The manifest block in reckon/crew/prompts.py asked for a completed key on both suite arms and stopped there: the field was listed in the JSON shape with the clause completed=false is absent evidence, which names one value's meaning and not the rule. The reader that decides a negative control asks completion as a literal True, so an arm carrying null or omitting the key is unreadable and the decision falls to the other arm — a refusal the worker could not have anticipated from the contract it was handed. Both lines now state the rule the reader applies:

completed is true only when the suite ran to its summary line, false otherwise, and null or absent is unreadable

The clause is on each arm's own line, so a worker filling in baseline_suite or after_suite reads it at the key it is about to write.

The measure

  • The composed contract carries the rule twice, once per arm. tests/test_brief_prompt.py gains test_the_manifest_template_states_what_completed_holds, which counts the wording in the composed prompt and then asserts it on the line each arm actually occupies, so a rule stated elsewhere in the contract cannot satisfy the check. A second assertion, test_the_literal_copy_of_the_suite_lines_carries_the_completed_rule, holds the same rule on the snapshot the byte-identity check pins, so the literal copy and the template cannot drift apart.
  • Base arm (9202f42c, the worktree before the change): 6 failed, 229 passed in 57.22s, EXIT=1; the six are the pre-existing landing-contract and skill-parity failures. logs/baseline_suite.log.
  • Head arm (4ee76537): 6 failed, 231 passed in 75.31s, EXIT=1 — the same six ids, none added, and the two extra passes are this node's own two cases. logs/after_suite.log.
  • Negative control (the two former template lines restored in reckon/crew/prompts.py): 1 failed, 15 deselected in 0.60s, EXIT=1, assert 0 == 2 — with the former lines back the composed contract carries the rule zero times and the new assertion reddens. logs/negative_control.log.

Both arms ran in the worktree itself, not a scratch tree: the base arm was taken at 9202f42c before the first edit, the head arm at 4ee76537 after the commit, over the same 22-file population — tests/test_brief_prompt.py plus every test module that imports reckon.crew.prompts. Each log's header names its revision, tree, the imported module.__file__ and the command, and the head arm's module.__file__ resolves under this worktree, so the run measured the tree under test rather than the main checkout.

The six red ids are not this change's

Both arms carry the same six failures — two in tests/test_crew_prompts.py and four in tests/test_skill_contract_parity.py — and the set difference between the arms is empty. They read the landing contract against the skill prose outside the repository (_slice_between looks for Append your landing record to your own section, which the in-tree contract text no longer carries), so they track a wording change in flight on that surface rather than anything this node touched. They are reported under follow_ons, not repaired here: the skill files lie outside this node's fence.
