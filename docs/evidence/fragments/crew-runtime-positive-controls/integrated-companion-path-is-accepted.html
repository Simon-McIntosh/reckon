An already-merged companion path is accepted despite a peer's claim — evidence

The claim loop in reckon/crew/promotion.py::_accepted_scope_exceptions raises cannot accept <path>: live run <peer> claims <claim> for any accepted path a live peer claims. That refusal protects two runs from editing one file concurrently, but r-20261002T203452309560-resume-refuses-a-session-over-the-window had already been merged at 34eb46322 while a relay of live runs claimed its two companion paths, so the refusal blocked only the ledger record of a landing that had happened. The check now admits a path whose change by this run is already behind the integration head (_path_change_reaches_integration_head): each cited commit that changed the path, read from its own diff against its first parent (the instrument _committed_scope charges the run by), must be an ancestor of the repository's HEAD and strictly behind it — a cited commit that is the head itself was integrated by no later commit, so it stays refused. The admission records already_integrated: true and the peer claims present (peer_claims, run id and claim path) on the acceptance entry, and never writes the peer's pointer.

The measure

  • The cases. tests/test_integrated_companion_path_is_accepted.py, in a temporary repository and RECKON_HOME, drives crew.complete on a run whose commit changed a declared path plus an undeclared companion while live peer runs claim the companion. With the run's commit merged strictly behind the head, the promotion succeeds and the stored row's scope_acceptances carries already_integrated: true with both peer claims named; both peer pointers are asserted byte-for-byte unchanged. Without the merge, the same promotion is refused with the claim named, the ledger stays empty and the run's pointer is retained.
