What this node measures

A landing writes three things before it commits them: the plan file carrying the run's comment, the run's own ledger file, and the run's row in the rebuildable store. When the commit is refused — a peer's .git/index.lock is the measured case — every one of the three must be taken back, or the next reader inherits a half-landing: a plan file no commit owns, a staged path a peer's next commit can sweep in, or a store row the retry's insert collides with. The guard is tests/test_failed_landing_leaves_nothing_behind.py: it holds a real .git/index.lock across a whole promotion, then asserts the plan file is byte-identical to its pre-promotion content, nothing is staged, no store row remains, and that a second promotion after the lock clears succeeds and leaves a clean worktree.

The two measured incidents, read from the source

Both incidents have one cause. The rollback's restore is a single index-writing call, git restore --source=HEAD --staged --worktree, so the very lock that refused the landing's git add refuses the restore too. The old fallback then read the failure as “nothing to do” for a tracked path and reported it preserved while the plan file stayed modified in the shared working tree (the first incident: the run's comment and its incremented plan-version left uncommitted, where any peer's next commit could take it). For a path the promotion created it unlinked the file after a failed git rm --cached, leaving the index holding a staged path no longer on disk. And the store row inserted by ledger.append_run was never removed at all, so the retry's insert failed with UNIQUE constraint failed: runs.run_id instead of re-recording the run.

The repair

The rollback splits the two halves. The working tree comes back from HEAD's blob, read through the object store and written directly, so a held index lock cannot block it; only the index entry needs the lock, and a path whose entry is still staged is reported as not restored rather than as clean. A landing refused after its own append also removes the store row that append inserted. The index is read before it is written, so an attempt whose staging call was the one refused takes no unstage call at all.

Gate arms

Both arms ran with pytest -n 8 --timeout=300, one at a time in the foreground, each from its own basetemp outside any repository, each to its own log naming its revision on the first line and ending with a bare EXIT= line. Thirteen test files: the new guard plus every existing test carrying _commit_landing_writes or rolled back.

  • Base arm (git archive extraction of 4efd4fdeae367f7f5c5931a24d41e674136c0c54 under /tmp): 1 failed, 64 passed, EXIT=1. The single failure is the new guard at its plan-file assertion (“the landing's plan write survives”) — the defect reproduces.
  • Head arm (worktree at 00abd9ad88f3d37d42598c342a14970f9e230d29, carrying the repair and the guard): 4 failed, 61 passed, EXIT=1. The guard now passes; no base failure id remains.
  • The head arm adds four failure ids, so this node is blocked rather than complete. Each is a test that asserts the pre-repair behaviour and lives outside this node's write scope; each is recorded as a follow-on:
  • tests/test_rollback_asks_head.py::test_head_path_survives_unrelated_restore_failure — asserts a tracked path's landed content survives a refused restore and that exactly one restore call is made; both statements are the defect the plan removes.
  • tests/test_receipt_names_the_rolled_back_row.py::test_survived_row_receipt_keeps_the_do_not_re_promote_wording — seeds a run file at HEAD whose content the ledger refuses to load, and requires the row to survive a refused restore.
  • tests/test_landing_commit_carries_only_its_own_comment.py::test_a_re_promotion_commits_a_plan_differing_only_by_its_own_comment and tests/test_repromotion_commits_its_recorded_comment.py::test_a_failed_landing_then_a_repromotion_commits_the_recorded_comment — both assert the plan file is dirty after a refused landing, which is the first measured incident verbatim.

Negative control

The declared control was applied, verbatim as declared: the working-tree restore was removed from the rollback (the Path(path).write_bytes(content) block of _restore_one_landing_write), and tests/test_failed_landing_leaves_nothing_behind.py was run against the mutated source. It fails at the plan-file assertion — “the landing's plan write survives” — with exit code 1 and a failing id the head arm does not fail. The mutation was applied to a git archive extraction of the head revision under /tmp, so the promoted file was never mutated; the log is gate/negative-control.log.

Follow-ons

  • Update the four tests above to assert the repaired contract, or replace them with the guard's assertions. They sit outside this node's exclusive write paths.
  • The uncommitted plan write in the shared checkout at the time of the first incident was left by the pre-repair code; the repair takes the write back, but a plan file left dirty by an attempt that ran the old code still needs a manual look before the next peer commit in that checkout.
