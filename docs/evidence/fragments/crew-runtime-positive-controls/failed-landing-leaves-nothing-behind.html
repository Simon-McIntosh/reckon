What this node measures

When a landing's commit is refused — a peer's .git/index.lock is the measured case — the plan comment stays on the plan file's working tree on purpose, because the retry commits that write. The residue a refusal must not leave is the part a peer could act on without the run: an entry left staged in the shared index, and the run's row left in the rebuildable store. The guard is tests/test_failed_landing_leaves_nothing_behind.py. It holds a real .git/index.lock across a whole promotion, asserts nothing is staged and no store row remains, and then requires a second promotion after the lock clears to succeed and leave the worktree clean; a second test holds the lock across a rollback of a created path whose entry is already staged.

The two defects, read from the source

The rollback's restore is one index-writing call, git restore --source=HEAD --staged --worktree, and a lock another process holds refuses it. The per-path fallback that follows then branches on whether HEAD carried the path. A tracked path keeps its working-tree write and is reported as surviving — deliberate, because the retry commits it, and pinned by existing tests. A path HEAD never carried — the run's own ledger file is one — is dropped from the index and then unlinked. When the lock refuses the drop, the unlink runs anyway, so the index is left staging a path no longer on disk: a peer's next commit would sweep in content no reader can see in the working tree. That is the first defect, and the guard's second test fails against it at the base revision.

The second defect is the store. A landing appends the run to the ledger file and to the rebuildable store; a refused landing rolls the file back but left the store row in place. The store's insert then hits UNIQUE constraint failed: runs.run_id on the retry, and _index_append swallows an index failure by design (it returns {"status": "failed"} rather than failing the append), so the collision is silent: the store keeps the refused attempt's row and never records the landed one. The guard's first test fails against this at the base revision.

The repair

A path HEAD never carried is now dropped from the index first, and its file is removed only once the entry is confirmed gone — the index is read with git diff --cached, which answers while a lock is held, so a rollback that cannot drop the entry leaves the file in place and reports the entry as surviving rather than manufacturing a staged path with no file. A refused landing that inserted its own store row also removes that row, so the retry's insert records the landed attempt instead of colliding with a record of the attempt nobody accepted. The tracked path's working-tree write is left exactly as the base revision left it.

Gate arms

Both arms ran with pytest -n 8 --timeout=300, one at a time in the foreground, each from its own basetemp outside any repository, each to its own log naming its revision on the first line and ending with a bare EXIT= line. Thirteen test files: the two guards plus every existing test carrying _commit_landing_writes, rolled back or the landing commit's plan comment.

  • Base arm (git archive extraction of 4efd4fdeae367f7f5c5931a24d41e674136c0c54 under /tmp, carrying the guard): 2 failed, 64 passed, EXIT=1. Both guard tests fail — nothing staged is violated by the unlink, and the store row survives the refusal — so both defects reproduce.
  • Head arm (worktree at 1b68a6b79d92966566589eb901e8379c09b9edc3, carrying the repair and the guards): 66 passed, EXIT=0. The head arm adds no failure id and no base failure id remains.

Negative controls

Two mutations, each applied to its own git archive extraction of the head revision under /tmp, so the promoted file was never mutated. Both logs are in gate/.

  • Index residue. The created-path branch restored to the base behaviour — Path(path).unlink(missing_ok=True) unconditionally after the index drop. test_a_staged_created_path_is_never_left_without_its_file fails at the file's existence assertion; exit code 1; log gate/negative-control-index.log.
  • Stale store row. The removal of the row the refused landing inserted neutered to a no-op. test_a_refused_landing_commit_leaves_nothing_behind fails at the "no store row remains" assertion; exit code 1; log gate/negative-control-store.log.

Each control fails an id the head arm does not fail.

Scope note: the plan-file clause

Section 39's clause that the rollback must restore the plan file itself was written from a misreading of the 02:49Z incident: the retry does commit the attempt's recorded comment, and four existing tests pin that design (test_repromotion_commits_its_recorded_comment.py states it in its docstring). The repair therefore leaves the plan and tracked-file working-tree writes as the base revision had them, and those four tests pass unchanged.

Limit

While a lock is held, nothing can drop a staged entry — the index cannot be written by anyone. The repaired rollback's guarantee is therefore: no residue beyond what the lock itself makes unavoidable, and a refused drop is reported as such rather than papered over with an unlink. In the measured cases the staging call is what the lock refuses, so nothing is staged at all.
