A head arm that does not declare completion decides no control — evidence

_head_suite_failure_ids in reckon/crew/promotion.py reads the arm a negative control is compared against, falling back to the baseline comparison when no head arm is readable. Its completion test was observation.get("completed") is False, so only the literal False made an arm unreadable: an after_suite that omitted the key, or carried null, was read as a completed arm and decided the control while its own run said nothing about having finished. The strict arm validator (ledger.suite_observation_missing_fields) and the manifest report both refuse that same mapping, and the strict validator runs only for a run whose record carries a suite_command — the class of run this gate serves carries none, so nothing else caught it.

The reader now asks completion as a literal True, the idiom those two validators use. At the head tree a key-less arm reads as None (logs/head_arm.log, line 6: key-less arm reads as: None), so the decision falls to the baseline comparison, which refuses a control whose failing id the baseline also fails. A declared-complete arm is unchanged and still decides.

The measure

  • Three cases, one manifest apart. tests/test_control_is_compared_with_the_head_arm.py gains an after_suite with no completed key, one with completed: null, and one with completed: true. All three carry the same baseline, whose failure set holds the id the control reddens; only the key in the head arm differs. The first two are refused with adds no failure to the baseline's; the third is admitted with comparison_arm: after_suite, which is the arm that decides when completion is declared.
  • Base arm (64d8c18e, the three cases copied into the unfixed tree): 2 failed, 52 passed in 19.26s, EXIT=1, the two failures being exactly the missing-key and null cases, each reporting DID NOT RAISE CrewError — the head arm decided, which is the defect reproduced. logs/base_arm.log.
  • Head arm (b4d154e1): 54 passed in 18.53s, EXIT=0, no failing id, over the same seven-file gate population. logs/head_arm.log.
  • Negative control (is False restored in a scratch copy of the head tree): 2 failed, 9 passed in 1.91s, EXIT=1, both completion cases reddening again — the check is load-bearing and the mutation reddens only what it should. logs/negative_control.log.

Both arms are scratch-tree runs whose own headers name the revision, the tree, the command and the imported module.__file__; the base arm's failure set is itself the provenance check, since a run that had imported the fixed reader would have failed nothing.

One clause of the followup is not implemented, and cannot be inside this fence

The followup asks that a missing or null completed read as unreadable on both arms. Only the head arm can carry that rule here. The baseline reader's handling of a mapping without the key is pinned outside this node's write scope: tests/test_control_gate_checks_facts.py::test_a_control_that_adds_no_failure_to_the_baseline_is_refused passes a baseline of {"failure_ids": [...], "failure_count": 1} and requires the refusal to come from those ids, and tests/test_control_is_compared_with_the_head_arm.py's own _gate cases treat a key-less baseline as the deciding arm. Reading that mapping as unreadable would return the empty set, which is the fail-open direction — a control would then be admitted with no comparison at all, and a manifest omitting the key from both arms would admit every control — and it would redden that pinned case. The head arm is where the rule changes the decision; the baseline arm needs the key to be made mandatory before the same rule can be applied to it, which is a change to the pinned fixture and belongs to a node holding that file.
