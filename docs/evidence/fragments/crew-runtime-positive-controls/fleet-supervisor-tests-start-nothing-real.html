The fleet supervisor's tests start nothing real — evidence

tests/test_fleet_supervisor.py started every service named by <config home>/fleet/services.json, and each case's reader resolved that path in the operator's real config home, so the file's own suite launched the operator's declared services — as own-session children — and nothing stopped them. A reader had no stop path at all: the file exercised session, reload and spawn requests, none of which ends the services a reader started. Two changes close both halves: an autouse fixture pins XDG_CONFIG_HOME into each case's temporary directory, and a stop request stops every declared service the reader started. There is no figure here because the measurement is a list of pids and a set of test ids, which a table carries better than a plot; the node's done-when names no artifact.

The defect, reproduced before it was repaired

The base arm ran tests/test_fleet_supervisor.py with its three companion files over a git archive of the base revision 53b5172bc: 59 passed in 12.62s, EXIT=0 — green, and leaving 24 processes behind. Twelve cases of the file start a reader, and every reader started both services the operator's config declares, so each is one row of the enumeration that follows. A row quoted from logs/base-arm-survivors.txt, read from that process's own /proc/<pid>/environ:

pid=3398244 RECKON_HOME=.../basetemp-base/popen-gw1/reckon-home0 \
  PYTEST=tests/test_fleet_supervisor.py::test_a_session_line_sizes_the_tabs_with_a_brief_client (call) \
  cmd=/home/ITER/mcintos/Code/imas-ambix/.venv/bin/imas-ambix agent ingest --cadence 60

The other eleven named cases and their pids are in the same file, 24 rows in all, every command line one of the operator's two declared services. They were signalled by that explicit pid list — SIGTERM, no pkill pattern anywhere in the procedure — and all 24 exited on SIGTERM. A second half of the same defect: with no stop request available, the fixture could only leave a reader running or kill it, and a killed reader leaves its own-session services running, which is what the rows show.

The instrument, shown seeing something before it reports absence

Survivors are found by reading each of this user's /proc/<pid>/environ files and matching the RECKON_HOME the case handed the reader — never by a command-line pattern, which would match the search itself and would miss a service whose argv is whatever the config declared. The base-arm scan was first shown seeing a known-present process (a probe carrying a scratch RECKON_HOME, count=1), then run against the arm's own basetemp, where it found the 24. The head-arm scan repeats that control on its own prefix: the probe appears as pid=3424756 ... cmdline=sleep 25, count=1, then count=0 before and after it is reaped.

  • Head (logs/head-arm.log, revision 91ff84f541813f69a30f038319725a50ac217577, this worktree): 61 passed, 0 failed, EXIT=0; survivors 0. The two new cases are the difference from the base population, and the head arm adds no failing id to the base arm's empty set.

Both arms ran the same four files under -n 8 --timeout=300, never serially, each with its own basetemp outside every repository, each log carrying its revision on line one and a bare EXIT= record last. The stop half is visible in the head arm's own evidence: the new case waits until the reader has started the stub, then stops the reader, then requires that nothing carrying the case's RECKON_HOME remains — and the same scan over the whole head basetemp afterwards reads zero.

The negative control

The declared mutation is “With the services-file isolation removed from the fixture, the stub-service case in tests/test_fleet_supervisor.py finds a surviving process carrying the test's RECKON_HOME and fails.” It was applied in two variants, both under HOME pinned to a scratch directory so the operator's real config could not be reached, and both logs are kept at logs/negative-control.log.

  • The declared construction (neg-a: the fixture no longer sets XDG_CONFIG_HOME): 2 failed, 16 passed, EXIT=1. The stub-service case fails at Path(os.environ["XDG_CONFIG_HOME"]) with KeyError: 'XDG_CONFIG_HOME' — with no config home to resolve, it refuses to guess one and never reaches the survivor assertion. The operator-file case fails with the isolation removed: the un-isolated resolution lands on the operator-shaped path and it is read.
  • The same cases over a reader whose end does not reap (neg-b: serve()'s end no longer calls stop_all(), every test and the fixture otherwise as committed): 1 failed, 17 passed, EXIT=1, and the failure is the declared one verbatim — AssertionError: processes carrying RECKON_HOME=... outlived the reader's stop: [3430469]. The survivor was the stub itself (python -c with the case's marker path, ppid 1 after the reader's end) and was signalled by that single pid.

So the survivor assertion is shown both saying nothing when the reader reaps (head arm) and naming the process when it does not, and the isolation half is shown by the case that reads the real path when the pin is removed. The operator's config is unchanged across both runs: sha256 9f40a926… before and after. A scan of the whole run scratch for any process carrying a RECKON_HOME under it reads count=0 after the controls, so neither variant left a service behind.

Lint and format

ruff check and ruff format --check over the two changed Python paths report all checks passed and both files formatted, at the base revision and at the head, so the change adds no finding the base did not carry.

What this measure is not

This is the change on its own tree. Nothing here says the merged result holds beside the other nodes of the section, and no case outside this node's files was run for it. The operator's real services file was read by the base arm (that is the defect) and never written by any run recorded here.
