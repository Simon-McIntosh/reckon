What this node measures

A promotion refused on an accept-path claim conflict — a live peer run claiming a path the promoted run accepted — must be refused before anything touches the run's worktree, its live pointer or the project ledger. The observable checked here is that after such a refusal all three are byte-for-byte as they were: the worktree directory still exists, the pointer file is unchanged, and no row was appended.

This is a regression guard on an ordering that holds at the base revision, and the negative control below shows it can fail: moving the workspace release above the refusal makes the guard red because the worktree is gone when the refusal is read.

The order established in complete() (committed blob, base revision)

Line numbers are from the committed blob at base; the promoted file is unchanged by this node.

  1. complete() (promotion.py:4989) takes the pointer lock (5034) and reads the record (5035).
  2. The refusal sweep _require_independently([...]) (5226-5280) runs every check and raises a combined refusal. The accept-path claim conflict is inside its last entry, _landing_gate (5278) → _landing_preconditions (5193, 6953) → _landing_scope_products (7039) → _accepted_scope_exceptions (2575), refused at 2663 with “cannot accept”. This refusal is reached before any side effect.
  3. _evaluate_suite_delta (5281, body 5336) can write a suite_delta_refusal record onto the live pointer and then raise _write_json(pointer_path(run_id), updated) before the raise at 5416-5423, with the same pattern at 5452-5460 and 5472-5478. This is the one refusal reached after a pointer side effect at the base revision.
  4. _complete_locked (5286 call; definition 7138) then runs the accepting path: _require_committable_checkout (7208) and _refuse_unrelated_plan_edit (7216) refuse before anything is written; ledger.append_run (7699) writes the row; _commit_landing_writes (7741) commits the stores and rolls the row back if it fails; only then does the live pointer get unlinked (7760) and the worktree released (_release_after_promotion, 7761, which reclaims only trees classified “integrated”, “disposable” or “d…” — _release_run_workspace, 5738) and the release recorded (_record_release_on_ledger, 7768).

So in the accepting path the workspace release and the pointer removal happen only after the ledger row has been written and committed, and every refusal of the claim conflict family is reached before all three.

Deviation from the instruction to reorder

The instruction expected a reorder. The order established above shows the accept-path claim conflict is already raised before every workspace, pointer and ledger side effect, so no reorder of the accepting path is required and none was made. The single refusal reached after a pointer write is the suite-delta family above, which writes the refusal's own record onto the pointer before raising; that behaviour is pinned by existing tests (tests/test_crew_test_role.py:453, tests/test_gate_evidence.py), so moving it would break the pass contract "existing tests that call complete() keep passing". Recorded as a follow-on rather than repaired here.

Negative control

The declared control was applied: the workspace release was called before the accept-path refusal in complete(). Under that mutation tests/test_refused_promotion_leaves_the_worktree.py fails because the worktree is gone after the refused promotion (the fixture's worktree path no longer exists when the test asserts it does). Exit code 1, the failing id named in test-logs/negative-control.log. The mutation was reverted and git status --porcelain over the promoted file reports no modification.
