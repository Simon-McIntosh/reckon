Every reader of a reclaimed run's review head uses one resolver

Result: blocked on one added failure id. The two readers this section names now select a run's stored review through the classifier's reading, and the node's own two-run test holds: for a reclaimed run whose record cites its head by a nine-character id both readers select the record keyed to the run's own full id, and for a reclaimed run whose record names no head both select nothing, exactly as the classifier does. What blocks the node is the other direction: the keep-passing case test_a_live_run_with_no_readable_tree_still_owes_its_sub_floor_duty asserts that a reclaimed headless run still produces a sub-floor duty row — the reading the classifier refuses — so the two requirements cannot both hold. The implementation follows the dispatch's explicit selection requirement; the manifest names the added id.

What changed

A run outlives the worktree it worked in, and once that worktree is gone the only tree a reader can reach is the shared checkout, whose HEAD is whatever that repository reached since. The classifier reads a reclaimed run's head from the run's own record through _review_head_and_tree and refuses a reclaimed run whose record names no resolvable head; two other readers still resolved the head themselves. _sub_floor_items_by_session in reckon/crew/obligations.py called the classifier's headless helper with reclaimed=False, so it read the store's newest record exactly where the classifier refuses — a duty derived from evidence the rest of the runtime does not accept as this run's. The crew dispose branch of reckon/cli.py composed its head from _review_tree and _reviewed_run_head, so for a reclaimed run it too could select against the checkout.

Both now go through the classifier's own reading. The duty reader takes the head and tree from _review_head_and_tree; when that head is empty it takes newest_review_for_headless_run(project, run_id, reclaimed=_worktree_reclaimed(pointer)), the classifier's own flag and its own helper, so a reclaimed run reads no record and builds no duty row while every other headless shape reads the store's newest as before. The disposition command reads head, tree = _review_head_and_tree(pointer) in place of the two direct calls. Only the disposition command was touched in reckon/cli.py, which a concurrent node shares.

The conflict the head arm measures

test_a_live_run_with_no_readable_tree_still_owes_its_sub_floor_duty stands up two runs: r-vanished-tree, whose pointer names a worktree path that is not on disk, and r-no-tree, whose pointer names no worktree at all. It stores a review with a sub-floor dimension for each and asserts a duty row for both. For r-vanished-tree the classifier reads no record: the run's worktree is reclaimed and its record names no head, and _stored_review refuses that shape, measured directly before the change was written. The case's docstring claims the duty reader "takes it through the same headless reading the classifier uses", and the assertion is what kept that claim true only for r-no-tree. Against this node's implementation the duty set is {'r-no-tree'} where the case requires {'r-no-tree', 'r-vanished-tree'} — the measured red assertion.

The dispatch's fence and the keep-passing list pull in opposite directions: the fence requires the duty reader to select what the classifier selects — no record for a reclaimed headless run — and the case asserts the disagreement for exactly that shape. Two resolution paths exist, and both are a scope decision rather than a local fix: the case is updated to the classifier's reading for the reclaimed shape, kept for r-no-tree, in the way the predecessor record updated a superseded pin under a coordinator scope decision; or the classifier's reclaimed refusal is itself revisited, which this node's fence and its rejection of the store's newest record as evidence about a revision the run cannot name both contradict. The implementation takes the fence's reading; the case stands unchanged and red, named in the manifest.
