A duty raised from a stored review is one the disposition command retires

Result: pass. The duty reader and the disposition command now select a run's stored review through one shared reading, so a coordinator shown a sub-floor duty row always has a command that retires it at the same record. The head arm is green over the 22-file gate population plus the new test file (160 passed, EXIT=0), the negative control is red on ids the arm does not fail (3 failed, EXIT=1), and the earlier attempt's conflict is resolved: a duty follows from a stored review that exists, whether or not the run's worktree survives, and agreement with the classifier was never the requirement.

What changed

Two readers of a run's stored review resolved the record independently. _sub_floor_items_by_session in reckon/crew/obligations.py derived a duty from a run's review whether or not its worktree survived; the crew dispose command in reckon/cli.py resolved the same run's record separately, so a row the duty reader raised for a reclaimed run could be unreachable from the command that retires it — a row the coordinator is shown and no command can dispose is worse than no row.

Both now take one reading, stored_review_for_run in reckon/crew/obligations.py, with the same arguments. It resolves the head through the recovery resolver every other reader uses (_review_head_and_tree), so a reclaimed run is keyed to the head its own record carries rather than to the shared checkout's HEAD; a record naming no resolvable head is read through the store's newest record for the run, because a low dimension is a finding about a review that exists and a reclaimed worktree neither supplies nor retires one. _sub_floor_items_by_session keeps its base reading and takes it through the shared function; the crew dispose branch for a live pointer takes the same function and arguments. A promoted run has no live pointer and therefore no duty row, and its command path keeps the record-based head and head-first selection it had.

The second commit repairs a defect the first commit's gate population caught: replacing the disposition's own resolution left the disagreement message — which names the revision the run's work is at beside the revision the record describes — without its head, so the refusal path raised UnboundLocalError instead of the refusal. The head is now taken from the same resolver the shared reading uses, so the two revisions the message names are the two the reading itself compared.

How the requirement was settled

The first attempt implemented the dispatch fence literally — the duty reader selecting exactly what the classifier selects, which is no record for a reclaimed run whose record names no head. That reddens tests/test_reclaimed_run_review_head.py::test_a_live_run_with_no_readable_tree_still_owes_its_sub_floor_duty, the keep-passing case pinning the opposite: a stored review outlives the worktree, and the duty it owes stays raised. The run closed blocked naming that id, with both resolution paths recorded in the previous revision of this fragment (logs/head-arm.log).

The coordinator's ruling settled it: a sub-floor dimension duty follows from a stored review that exists, whether or not the run's worktree survives; the requirement is that the writer that disposes a duty selects the same record as the duty reader, so every duty raised can be disposed; agreement with the classifier is not the requirement. This record implements that reading, and the kept file is a load-bearing pin rather than a conflict.

One intermediate arm is on disk as the record of that path: logs/head-arm-2.log (f3db9769aaee727129bc9123c26db8acf25de660) is red on the refusal-message defect the second commit repairs, since the gate population includes tests/test_sub_floor_disposition_has_a_writer.py, the file covering the changed command.
