Completed history moves to a separate archive

RunStore.retire moves runs whose completion instant is more than thirty days before the sweep into run_store.archive.db, beside the configured hot store. One attached-database transaction copies the durable payload and detail, records narrow membership, and removes both hot rows. Each scheduled pass moves at most 2,000 runs and uses PRAGMA incremental_vacuum to reclaim at most 256 pages; both budgets are configurable. Every archived run is printed and recorded through the retention sweep's existing rotating log.

gc._retire_run_store extends the scheduled sweep after cache pruning. It reuses the review resolver, committed-review check and queue wait parser. Live pointers, live review subjects, outstanding review obligations and explicit queued run dependencies keep their subject hot. Recent runs, unknown completion times and projects without a resolved checkout also stay.

The narrow retired_runs membership table keeps imports and membership refreshes from recreating archived rows. Historical keyed reads, durable comparisons and node lookups recognize archived records. Warm current-state reads query the hot tables without attaching the archive. Ledger and velocity readers preserve their recorded measurements. Import destination selection and retirement candidate selection acquire the SQLite writer reservation before reading, preventing a racing import from recreating a retired hot row.

Bounded archival and incremental compaction

The default row cap is 2,000, configurable through retention_sweep(store_limit=...) or the scheduled module command's --store-limit. The default incremental compaction budget is 256 pages, configurable through store_vacuum_pages or --store-vacuum-pages. Both budgets must be positive; zero is refused because SQLite treats an incremental vacuum of zero pages as unbounded. Compaction continues on later passes after all eligible runs have been archived, so leftover free pages do not need another retirement.

Fresh stores select incremental auto-vacuum before creating their tables. An existing store without incremental support is left in its current mode by the hourly sweep, which reports maintenance_required: true. Its one-time conversion is an explicit maintenance command: python -m reckon.run_store --enable-incremental-vacuum --store /home/ITER/mcintos/.config/reckon/crew/run_store.db. The coordinator runs it after integration in a separate sbatch --partition=all_debug job. The hourly sweep never calls the conversion. The command reports the previous and resulting auto-vacuum modes and whether it rewrote the store; rerunning it after conversion reports rewritten: false.
