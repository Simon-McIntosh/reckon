A gate replay runs on the measure partition

What changed. rerun_gate_at_integrated_revision in reckon/crew/promotion_gate.py executed every replay with subprocess.run(["sh", "-c", replayed], cwd=repository, ...) in the coordinator's own process, so promoting a computing project ran that project's suite on the cores and GPFS bandwidth every session shares. The replay now reads the flight resolved for the replayed repository, and when landing.measure_partition is declared it submits the replayed command as its own sbatch --wait job instead: the command runs as an srun step inside that batch job, the job's --time is the replay bound rendered as HH:MM:SS (450 s reads 00:07:30), the caller's SLURM_* and SBATCH_* variables are removed from the submission's environment, and a bound past 3600 seconds takes measure_long_partition. A bare srun is deliberately not used, because a step started from the fleet node stays inside the fleet allocation whatever partition it names. A repository whose flight declares no partition keeps the in-place call, and the replay log's header now names the partition it ran on.

The argv and environment form is one function. partition_job_argv and partition_job_environment carry the submission form, and replay_domain_invariant_checks reaches them through the same replay it already used, so a declared domain check is submitted the same way and no second executor exists. The replay's captured output, exit status and timeout reporting are unchanged: the job writes its own log, the replay reads the text back from it, and its terminal EXIT= record is the status reported. A replay cut short cancels only the job id sbatch --wait printed.

Repair

A stale job log could pass a job that never ran. The replay derived its job log from the caller's replay log (run_dir(run_id) / "verify-gate.log"), so every verify-gate of a run wrote the same file and nothing cleared it. When a submission was refused by the scheduler, or the job was stopped before its step's redirect ran, the previous attempt's log was still on disk, its EXIT=0 was read back, and the replay reported a gate that had passed without ever running. The log is now truncated before every submission (_replay_job_log writes an empty file), a log with no EXIT= receipt is unreadable and reports status 3 rather than the client's return code, and only the last receipt line in the log decides the status.

One submission form. The argv and environment construction moved to landing_measure.partition_submission, which also returns the partition the bound selected; _partition_runner calls it and the copies in promotion_gate.py (partition_job_*, partition_bound_text, measure_partition_for) are gone. The replay reads the flight's declaration and passes it to the shared helper.

Measured. Four new cases at 8c9f0483bc: the job's own log decides the verdict against a client that returns 1 with a FAILED id, a log with no receipt reports status 3 and a failed verdict, only the last receipt line counts, and a stale EXIT=0 log from an earlier attempt beside a submission that writes nothing reports status 3 rather than that earlier verdict. The file's eleven cases pass. The negative control removes the truncation line: test_a_stale_job_log_is_not_read_as_this_attempt_s_verdict fails and the other ten pass (1 failed, 10 passed, exit 1). The landing measure's own partition tests (16 cases) pass unchanged against the shared helper.

Matched arms. Each arm was run as an all_debug batch job submitted with env -u SLURM_JOB_ID -u SLURM_JOBID sbatch and resolved over its own tree. The base arm at 0dee9730af reports 51 passed, exit 0. The after arm at 4d847e1a3f reports 62 passed, exit 0.
