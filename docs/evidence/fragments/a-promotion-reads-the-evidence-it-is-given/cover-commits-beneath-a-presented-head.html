A presented head covers the commits beneath it

What changed. A promotion's shortfall report compared the presented commits with the manifest's declared commits as exact sets, so a coordinator who cited the head of a complete delivery was told the commits beneath it were missing. The out-of-scope boundary check runs against what is presented, and a run's work is the span its head sits on, not only the head itself. In reckon/crew/promotion_evidence.py, _commits_a_presentation_covers is the one function that reads the arms: a presented commit covers itself and every commit in base..it, read with git rev-list in the run's own tree, and a manifest commit is short only when nothing presented covers it. With --commit a b c each of the three contributes its own ancestors above the base, so no single presented head has to be chosen. A base that does not resolve, or a range git cannot enumerate, leaves that commit covering only itself rather than claiming coverage the repository did not confirm. A presented commit the manifest does not declare still reports nothing, because that is the coordinator declining the worker's revision and the presented list is the one that resolves. promotion.py only carries the record this returns, and _require_commits_beyond_base is unchanged: it already refuses a presented commit that is not above the base.

The defect was reproduced before it was repaired. Against the dispatch base, with the new test file copied into a scratch export, the first case fails: a manifest declaring five commits, promoted by naming only the fifth, reports the four ancestors as missing (presented_commits_subset_of_manifest, presented: 1, declared: 5). Two further cases fail there for the mirror reason — the old exact-set rule also names commits the presentation does cover.
