A merge releases the worktree it landed

What changed. A run promoted with crew complete has its live pointer deleted and its worktree left held, because the head is not on the primary branch yet. crew merge --head then landed and pushed that head, but reckon/crew/merge.py had no release step, so the tree stayed a worktree-held obligation until a hand crew gc --run … --apply. The merge now calls release_landed_worktrees once the push is confirmed. It reads the held set from obligations._held_worktree_records — the one join of Git's worktree registry to the ledger rows, through record_names_worktree, rather than a second derivation kept in the merge — and releases each tree with the promotion's own release path, judged against the merge commit the landing wrote. A tree is offered only when its HEAD is the reviewed head or a commit beneath it, so a tree carrying work no reader has is reported withheld and left in place. The merge result carries release.released and release.withheld, naming each tree. A refusal before the push — a conflict, a failed check — reaches the call with nothing released, because the call sits after the confirmed push. merge.land passes release=False: crew complete --land makes its own release after the merge and reports it, and releasing twice would report the path as the tree is removed rather than the outcome.

Measured

Gate: tests/test_a_merge_releases_its_worktree.py, run as PYTHONPATH=. .venv/bin/python -m pytest -p no:cacheprovider -q tests/test_a_merge_releases_its_worktree.py at each arm's own revision. Every case goes through the real CLIs — crew complete and then a separate crew merge --head — over a temporary repository, a bare origin, a registered checkout and a linked worker worktree named for its session and node id. Each log names its revision, tree and command on the header lines and ends in EXIT=<code>.
