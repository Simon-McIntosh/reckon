A merge's default gate is never the negative control

What changed. _default_gate_evidence_from_manifest (reckon/crew/promotion_records.py) took test_logs[0] as the head gate whenever the caller named no gate log. Workers commonly list their deliberately failing negative control first in test_logs, so the default read the one log whose failures exist to prove the check can fail: on 10 November a merge given no gate flags refused imas-efit run r-20261110T144158998914-sizing-solver-fixes for unit/pressure_bounds, an id that fails only in negative-final.log and passes in both the candidate and base unit logs. The selection is now a helper, _default_gate_log_from_manifest: the after_suite arm's own log_path when the arm names one, otherwise the first test_logs entry that is not the manifest's negative_control_log. A manifest whose only test log is its negative control has no default, and the refusal names --gate-log-path rather than promoting on a gate nobody measured.

The guard. A new tests/test_a_default_gate_is_never_the_negative_control.py builds a temporary manifest and asserts three facts. With the negative control first in test_logs and an after_suite arm naming its own log, the default gate log is that arm's log and its exit status (EXIT=0) is the one read. With no after_suite log the default skips the negative control and takes the next entry. A manifest whose only test log is the negative control raises a refusal carrying --gate-log-path.

Measured

The three cases pass locally: 3 passed, exit 0. The gate was run as two arms on the all_debug partition, one arm at a time with -n 4, the base arm over an extraction of d1d74874e6 and the after arm over the worktree at its head. Over the twelve test files importing reckon.crew.promotion_records: base 6 failed, 137 passed and head 6 failed, 137 passed — the same six ids on both sides, so zero added. Over the promotion template's own suite (tests/test_a_default_gate_is_never_the_negative_control.py plus tests/test_staged_write_inventory.py): base 52 passed, 2 errors, head 54 passed, exit 0 — the two base errors are the staged-write fixture failing to resolve a repository in a bare extraction, not a failure of the code under test.

Negative control. Restoring test_logs[0] as the default makes all three cases fail: 3 failed, the first case reporting /…/unit.log where it expects /…/after/unit.log — it picks the negative-control log. Ruff check and format --check report no findings on the two staged paths.
