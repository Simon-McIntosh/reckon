One identity for one section

Four callers derived a section's identity themselves and two of them disagreed. A section authored as <h2 id="s5-1"> carries s5-1 in its typed record, but the routing lookup spelled it s5.1, so the record was not found; promotion spelled the hyphenated anchor correctly and its section-risk lookup used it as a record id. reckon/crew/routing.py now carries one derivation, section_record_id (with section_anchor applying the comment-anchor default), and all four callers resolve through it: the routing record lookup, the two HTML section scanners in routing.py and dispatch.py, and promotion's comment anchor. Promotion's section-risk lookup reads the record id the state carries rather than an anchor for it. The parity case in the new test file shows one key for s5.1, s5-1 and the printed §5.1 across the dispatch, routing and promotion callers.

Both authored-HTML scanners admit either spelling an id was authored under: a plan authored with the dotted anchor s5.1 is found when a node names the hyphenated s5-1, and the reverse, through one candidate set (section_id_candidates) built once in routing.py and drawn by both lookup sites, so the two cannot drift apart. A guard case pins it with a heading whose text omits the reference, so the id lookup has to answer rather than the heading-text fallback: restoring the guard's old candidate set (the raw spelling and the hyphenated identity only) fails that case at assert False is True for s5-1 against the dotted anchor (logs/negative-control-guard.log, EXIT=1).
