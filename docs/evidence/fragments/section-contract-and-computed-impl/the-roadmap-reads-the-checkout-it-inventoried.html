The roadmap reads the checkout it inventoried

Every production caller of build_roadmap now names the checkout its inventory came from, so the wiring scan reads plan-standalone from the same tree as the rows it judges instead of the registered mount.

The defect and the change

build_roadmap took a docs_dir naming the inventoried checkout and passed it to the wiring scan, which falls back to the registered mount when none is supplied. All five production callers omitted it, so a worktree-scoped roadmap inventoried one tree's plans and read another tree's standalone declarations: a plan that declares it stands alone in the checkout was still reported unwired, because the mount's copy of that plan was silent. The finding is the only roadmap output the declaration reaches, which is why the fix is a call-site change and not a scan change.

Gate

tests/test_roadmap_wiring_reads_its_own_checkout.py::test_a_worktree_roadmap_reads_that_worktrees_declaration synthesises a registered mount and a second checkout under temporary directories. Both trees hold the same plan; only the second declares plan-standalone. It then drives each caller at the second checkout and requires the wiring finding to follow the tree the rows were inventoried from. An opening positive control builds a roadmap scoped to the mount and asserts the finding is reported there, so the arms cannot pass on an instrument that sees no plan at all. The test redirects RECKON_HOME, RECKON_STATE_ROOT and RECKON_MOUNTS_PATH into its temporary tree and reads or writes no real mount.

Two callers do not hand the roadmap back — the HTTP discovery projection consumes it, and the graph resolver schedules from it — so the test records the call itself: a wrapper is patched over build_roadmap in both modules it is imported into, delegating to the real builder and asserting exactly one roadmap per caller.
