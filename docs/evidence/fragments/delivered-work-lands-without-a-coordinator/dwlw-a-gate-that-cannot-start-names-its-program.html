A merged-head gate that cannot start says so, instead of blaming the merge

At the pinned base dde7b001769544957d5ca63f50cbb48c26574553, replaying a gate command that names .venv/bin/python against a tree carrying no .venv ends with the shell's exit status 127 and the finding text the gate passed at the worker's base but reports failed on the integrated revision …: the merge changes what this node's gate proves. Nothing was measured at the merged head, and the refusal sent a r-20261122T032524701158 coordinator into the merge for a missing program.

What changed. One resolver — gate_program, resolve_gate_program and rewrite_gate_program in reckon/crew/promotion_gate.py — now serves both the promotion guard that admits a recorded command and the replay that executes it, so one tokenisation, PATH lookup, relative-candidate resolution and executable test answer for both. The replay resolves the command's program before the shell receives it. A relative spelling — .venv/bin/python — is looked for under the tree being measured, then under each recorded worker root, then through any resolved .venv, then through the interpreter running the measurement, and the first executable found is substituted into the command as an absolute path, leaving every other word alone. The guard looks in fewer seats than the replay: it resolves over the run's own checkout and repository and applies no interpreter fallback, so a run whose checkout lacks the .venv/bin/python it recorded is still refused naming that tree. The extra fallback exists for the opposite case — a merged head whose tree holds no .venv although the run's own checkout did. The report names gate_program, the seats it was looked in, and gate_program_rewritten. A program that resolves nowhere is reported as a gate that did not start — integrated_verdict: not-run, gate_started: false, missing_program — with the program and the tree in the reason and in the finding, whose message now says outright that the failure came from a program that could not start rather than from anything the merge changed. An exit status of 127 from the shell is read the same way, with the program taken from the shell's own not found line where it prints one. A not-started replay still writes its log, under the same header, with a # not started: line and no EXIT= record.

What does not change. A gate that starts and fails keeps its verdict and the failure ids its own output named. A command whose program already resolves replays byte-identically to before. The shell-builtin set is recognised as startable, so a stored command such as exit 3 is still executed rather than refused.
