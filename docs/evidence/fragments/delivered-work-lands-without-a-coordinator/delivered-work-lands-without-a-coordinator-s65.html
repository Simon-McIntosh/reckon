A partitioned arm judges a test file's presence against its own revision

A partitioned landing arm runs in a scheduler job built from its own revision, so no local base tree exists for the measurement to inspect. The base arm's file selection nevertheless asked the local trees, and a partitioned base tree is never created: every file the measurement named read as present at the base revision. The base arm's command therefore named test files the base revision does not hold, and a file added at head was charged to the base arm as a failure it could not have had.

What changed. Presence is now read from the revision itself whenever a measurement is partitioned. The measurement resolves each revision with git rev-parse --verify --quiet <rev>^{commit} and asks git cat-file -e <rev>:<path> whether that revision's own tree holds the file. A revision that cannot be resolved is not read as absence: the file is kept, so the arm reports its own failure rather than silently narrowing to nothing. A partitioned base arm left with no file to run is recorded as an empty baseline — its command, a zero exit status and an empty id list — which adds no base ids, so a case whose only node test file is new at head lands on its head arm's own result. An unpartitioned measurement still reads presence from the local base and head trees, which is what tests/test_a_landing_arm_measures_only_files_its_tree_holds.py already states.

The head arm over the same list plus the new file ran at 6be79c28ce6a8a60ea9dc3306be1e10efb68d46f: 10 failed, 413 passed in 260.15s (0:04:20), EXIT=1. The two failure sets are identical apart from one id, tests/test_the_drain_keeps_up_with_a_burst.py::test_a_commitless_promotion_finishes_beside_a_landing[False]. The base revision already had the same nine ids red, so no test that imports the changed modules adds a failure.

The one differing id does not reproduce. That file references none of arm_test_files, revision_holds or partitioned, so no path through the change reaches it, and its assertion is a half-second event wait. Run alone at the head revision, built at the head, the file gave 26 passed in 4.65s; at a tree built from the base revision, 26 passed in 4.04s; and five further runs at head gave 26 passed each time, in 3.79–4.34s. It failed once inside a 423-test arm on a busy node, which is a repetition failure rather than a defect.

Control. The negative control copies tests/test_a_partitioned_arm_judges_files_against_its_revision.py into a tree built from the base revision and runs it against that revision's code: 2 failed, 1 passed in 1.00s, EXIT=1. Both partitioned cases fail — the first because the base arm's command names tests/test_added.py, a file the base revision does not hold, and the second because that file is charged to the baseline as an id instead of being left out. The unpartitioned case passes, which is the half of the earlier behaviour this change must not move. At the head revision the same file gives 3 passed in 1.07s, EXIT=0.
