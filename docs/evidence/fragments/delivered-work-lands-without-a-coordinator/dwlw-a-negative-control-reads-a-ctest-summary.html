A cut-down ctest control log reads red from its progress line

A negative-control log is sometimes an extract of a longer ctest run. The capture opens below the run summary, so the log carries ctest's progress lines, the test's own colourised output and the entry line ctest repeats, but no The following tests FAILED: block and no percentage line. The shared gate-log reader recognised a ctest run only from the failure block or from the run summary, so such an extract fell through to the pytest reader — its 1 failed, 0 passed line matches the pytest summary — and a pytest log with no FAILED node id names no failure at all. The control was then refused as one never shown to fail, and the run was landed with the control waived.

The reader in reckon/crew/review.py now recognises ctest from two further markers. A progress line ending in a *** status, 1/1 Test #1155: unit/imas/iron_limb_outline ......***Failed, names a failed test whatever its status; a bare Passed-style progress line marks the runner without naming a failure, so it is read only after a pytest FAILED node id has had its chance. An entry line outside a block, 1155 - unit/imas/iron_limb_outline (Failed), names a failure only when its reason is one of ctest's failure statuses, so a test's own output printing that shape with a harmless reason is not read as one.

Where a failure block is present it stays authoritative: a full-summary log reads exactly as it did, and a log carrying both the block and the progress lines of the same tests does not count one failure twice under two spellings. The block's entries, the progress line's name and the entry line's name are all taken verbatim, so a ctest name needs no reduction against the reader's working directory.
