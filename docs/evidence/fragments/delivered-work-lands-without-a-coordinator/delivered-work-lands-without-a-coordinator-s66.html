A ledger row that cites the wrong commit is corrected from its merge

A landing pass can record a delivery the primary branch already carried against the branch tip at the time of the pass rather than against the run's own head, so the run's row ends up citing an unrelated promotion. The row is written once and has no append path: crew record-merge refused any run the ledger already held, with run '…' is already recorded in the 'proj' ledger; a run the ledger holds is not recorded again — read its row instead. Every reader of that run's reviewed head therefore read a revision the review never covered, and nothing could repair it. At the base revision d7f54a14d1dcf7ae8054acd61fbf1a2e20d0425e the node's four cases fail, the first on exactly that refusal, as negative-control.log records (4 failed in 1.94s, EXIT=1).

What changed. crew record-merge, given a run whose row the ledger already holds, now resolves the run from its stored row alone and corrects the row instead of refusing. The reviewed head is read from the merge that carried it — the second parent of a --no-ff merge — and the row's commits and promoted_revision are replaced with that head and the merge is recorded in recorded_merge. Because the run is resolved from the row, the correction works with no live pointer and no run directory, which is the state a misattributed row outlives.

What is kept. The citation that was replaced is kept beside the corrected fields in a citation_superseded block naming the old commits and promoted_revision, the corrected head, the merge, the time and the caller's reason. What a promotion believed when it landed is evidence in its own right, and a later reader has to see what was wrong rather than a row that silently changed. The corrected row is committed through the landing helper every store write already uses, under a record-merge(<run>): correct a row's commit citation subject, with the row file and the aggregate ledger staged by name.

What refuses. A row that already cites the head its merge carried is left byte-identical and writes no superseded block and no commit, so running the verb twice cannot append a second correction. A commit with no second parent names no head at all, so it is refused with merge … carries no second parent, so it names no reviewed head this row's citation can be corrected to and the row untouched; the verb never guesses a head. A correction with an empty --reason is refused, because the superseded block exists to say why.
