A project declares the scheduler profile its gate arms run under

What this measures. A gate that can only be measured on one scheduler states that scheduler once, as a named profile under landing.gate_profiles in the project's flight layer. The profile names the partition, a reservation, a gres request, a memory, a CPU count and a default time. Every submission a gate makes resolves the name it was given against those profiles and carries the whole declaration: the job a crew declare-gate --partition <profile> submits, the arms a crew suite run --partition <profile> submits, both arms of a landing measure for such a run, and the replayed gate at the integrated revision. A name no profile carries is a bare partition and submits exactly as it always did.

The refusal is at load. A profile that declares no memory, or a memory of zero, is refused while the flight layer is validated, naming the profile: an absent or zero memory requests a whole node and pends on Resources. A profile that names no CPU count keeps the shipped population's, so omitting it does not silently run an arm one CPU at a time.

The job's own environment (see table). A profile's submission keeps TMPDIR node-local and runs the project's interpreter directly; nothing in the submitted step calls uv.

The profile name reaches the scheduler as though it were a partition, which is exactly the reading the change exists to replace.

Measure. The importer population of the changed modules — 139 files plus the node's own test — was run on all_debug at both revisions, each arm with TMPDIR on node-local memory so the two readings share one scratch policy. At the base bee04f7fb92b66ebdd1f107eeb8cbc466a98b5ae the population reports 31 failed, 1438 passed, 9 skipped in 685.36s (0:11:25). At the head 0087fa7291f217c762719d36318986eb0aad1701 it reports 27 failed, 1447 passed, 9 skipped in 747.06s (0:12:27).

No failure is added. Every id the head arm reports is one the base arm reports too. Four ids the base arm reports pass at the head (tests/test_fleet_health_records_node_tmp.py's disk and sampler rows, and test_health_sampler_calls_scratch_sampling_and_keeps_the_reading), which are host-sampler readings rather than code this node touched. The node's own test exists only at the head, is named in that arm's command, and passes there.

The scratch filesystem decides some of these ids, and the arms were matched for it. Node-local /tmp on all_debug exhausted twice while this node was measured (418 fixture errors creating pytest's own temporary directories, with the measurement passes unaffected), and an arm with TMPDIR on shared storage added 22 environment failures in the disk and store suites. Those logs are kept beside the arm logs so a reader can see what produced them; they are not the comparison above.

The replay waits for the bound its job runs under. The replayed gate at the integrated revision is submitted through the same builder, so a profile raises that job's --time above the bound the replay resolved. The client wait follows the job's bound rather than the resolved one, and the cut-short message names the bound the job actually had: waiting for the shorter figure killed a job the scheduler was still running and reported the kill as the gate's own timeout, which is the one gate a long GPU profile exists to run. At the revision before this, the same case reports a 720 s client wait for a job permitted 14400 s.

What does not change. A bare partition name keeps the shipped defaults — the population's CPU count, 32 GB and the bound the measure computed — and carries no reservation or gres. A profile's default time raises the arm's bound but never shortens a caller's longer one, and the client wait is raised with it so the wait and the scheduler limit the arm runs under agree.
