A project declares the scheduler profile its gate arms run under

What this measures. A gate that can only be measured on one scheduler states that scheduler once, as a named profile under landing.gate_profiles in the project's flight layer. The profile names the partition, a reservation, a gres request, a memory, a CPU count and a default time. Every submission a gate makes resolves the name it was given against those profiles and carries the whole declaration: the job a crew declare-gate --partition <profile> submits, the arms a crew suite run --partition <profile> submits, both arms of a landing measure for such a run, and the replayed gate at the integrated revision. A name no profile carries is a bare partition and submits exactly as it always did.

The refusal is at load. A profile that declares no memory, or a memory of zero, is refused while the flight layer is validated, naming the profile: an absent or zero memory requests a whole node and pends on Resources. A profile that names no CPU count keeps the shipped population's, so omitting it does not silently run an arm one CPU at a time.

The job's own environment (see table). A profile's submission keeps TMPDIR node-local and runs the project's interpreter directly; nothing in the submitted step calls uv.

Negative control. At the base bee04f7fb92b66ebdd1f107eeb8cbc466a98b5ae, the node's first case fails with the submission carrying the partition alone: AssertionError: assert 'h200' == 'betelgeuse'. The profile name reaches the scheduler as though it were a partition, which is exactly the reading the change exists to replace.

Measure. The importer population of the changed modules — 139 files plus the node's own test — was run on all_debug at both revisions. At the base bee04f7fb92b66ebdd1f107eeb8cbc466a98b5ae the population reports 26 failed, 1443 passed, 9 skipped in 679 s. At the head 0087fa7291f217c762719d36318986eb0aad1701 it reports 27 failed, 1447 passed, 9 skipped in 747 s.

The one difference is the scratch filesystem. The head arm ran with TMPDIR on node-local memory, where the base arm ran with it on /tmp, and the six ids the head arm adds are all tests of the /tmp scratch policy itself (tests/test_session_scratch_uses_bounded_node_tmp.py and test_a_control_pass_profiles_without_live_writes.py::test_the_filesystem_fence_refuses_an_external_write). Re-run over the same head with TMPDIR on /tmp, those files report 96 passed and one failure, test_excess_reaches_only_its_conversation_in_both_obligation_views — which the base arm already carries. No failure is added by the change.

The scratch runs are recorded too. Node-local /tmp on all_debug exhausted twice while this node was being measured (418 fixture errors creating pytest's own temporary directories, with measurement passes unaffected), and a run with the scratch on shared storage added 22 environment failures in the disk and store suites. Both logs are kept beside the arm logs so the readings above can be checked against what produced them.

What does not change. A bare partition name keeps the shipped defaults — the population's CPU count, 32 GB and the bound the measure computed — and carries no reservation or gres. A profile's default time raises the arm's bound but never shortens a caller's longer one, and the client wait is raised with it so the wait and the scheduler limit the arm runs under agree.
