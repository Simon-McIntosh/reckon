The run view separates failure from delivery

The coordinator's run view reported every receipt under one delivered key, so a message the hook claimed and then could not read was presented as delivered. It now reads the receipts through a split the hook itself owns — worker_inbox.delivered_receipts and worker_inbox.failed_receipts — and answers them under delivered and failed. The same split backs the manifest audit, so the record a worker owes and the view a coordinator reads cannot disagree about whether a message arrived.

A queued message that cannot be read stays visible

_unclaimed_message swallowed every OSError, which dropped a queued message from the answer on any failure, not only on the claim race. Only FileNotFoundError — the hook's rename landing between the listing and the read — now returns nothing; every other failure is reported as present and unreadable, carrying its message name, its size and the error, and counted under unreadable_count. A message that vanishes from the view is otherwise indistinguishable from one that was never written.

The race test drives the hook's own delivery

The race case previously claimed the message in the test and asserted only the unclaimed half, so nothing measured the hook's receipt. It now runs the real hook process — claim and receipt together — and hands the view the stale listing it read before that claim, then asserts the delivered receipt carries the tool call the hook saw (tool_use_id: toolu_race) and equals the run's own receipt list.
