A run's priority carries to its review and its promotion

Mechanism

  • The review class in reckon.crew.queue_order._precedence now reads the points the review's own queued record carries, so two reviews are ordered by their runs' points and fall back to the shared fair-share pass when the points are equal. The review already inherited its run's points through recovery_review_dispatch._composed_review_options; what was missing was a reader that ranked by them.
  • reckon.crew.queue_edit.reprioritise accepts a run in one of runs.DELIVERED_POINTER_PHASES (complete, promotion-requested, promotion-waiting). The raise is charged to the session's budget and marked on the pointer with runs.PRIORITY_DELIVERED_MARK, which is what runs._holds_priority reads: a delivered run's points returned at launch, so only a mark saying they were spent again charges them. Landing retires the live pointer, and the budget is read from the pointers, so the points come back with no second ledger. The mark charges the run only where nothing else holds the same raise. Where the run's review is still queued, the review is the record admission ranks, so the raise is judged against the session once — the review's points are excluded from that judgement and the run's mark is cleared — and the session reads the raise once rather than twice.
  • A raise is also written onto the queued review and the queued promotion request for that run, because both queues rank their own records rather than the run's pointer. Without that write the raise would move nothing a queue reads.

Negative result: one done-when bullet was already true

"Of two promotion requests, the priority-4 one is drained first" passes against base revision 8d870f62598f unchanged. request_promotion snapshots its run's at-launch points into priority_override, and _pending_requests already passed each request through the shared precedence, where a non-review request's points outrank fair share. That bullet is therefore a guard this node adds, not a defect it repairs; the review ordering and the delivered-run raise are the two behaviours the base revision lacks. Both fail against the base revision with the node's tests, and the red log is recorded in the section's gate log (s3.html).
