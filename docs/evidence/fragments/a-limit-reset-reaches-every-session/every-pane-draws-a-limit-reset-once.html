Every pane draws a limit reset, once, because a producer writes it

A reset was durable and readable but invisible: the store held the event, and nothing on the watch stream a follower reads said so, so a session stopped at its usage limit still learned of the reset only if a human told it. lift_watch.sweep_resets is the module's second entry point and folds the recent events into each project's stream. It runs on the producer's clock-driven block — recovery_watch._sweep_reset_rows, called inside the WATCHER_SWEEP_INTERVAL_SECONDS branch under the registered-producer guard — rather than on the change gate the lift fold reads, because a reset becomes due when the clock passes an announced instant and every file stays still; a store the gate's fingerprint does not cover is the second such case. It remembers the event ids it has announced, so an event reaches the stream once, and an event whose instant is still ahead reaches it on the first pass after that instant with no file changing in between. The one-hour RESET_HORIZON is what stops a restarted producer — which has announced nothing — from replaying every reset the store still holds, while still admitting a session resumed twenty minutes later.

On the pane, a reset is not a lift, so it joins ticker.LIFT_STATES with its own case in _feed_lift. That case takes the shared claim on (session, event id, limit-reset) and returns without touching _lift_groups, which is what lets a group holding a lift still draw its own baseline and end rows as before. The row maps to the pane word working — a reset is the fleet resuming, not a new one — and its stage cell reads limit, so the grid draws it as its own family rather than as a lift. Both projects' producers write the same workstation-wide event into their own streams, and the pane's claim is what makes that one row rather than two.
