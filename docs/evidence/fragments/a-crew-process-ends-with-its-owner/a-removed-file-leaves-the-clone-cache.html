A removed file stops holding a clone cache entry

The clone scan's corpus fingerprint cache is bounded to one entry per corpus file. A path present in the cache counted toward that cap unconditionally, so a file removed or renamed out of the corpus kept its own entry in the count and pinned the cap open: neither the removed path nor a superseded revision of a live path could ever be evicted, and corpus.json grew with every path ever scanned rather than with the current corpus. A cached path now counts toward the cap only while a recent scan read it.

What changed

  • reckon/clones.py: each cache entry records seen, the scan ordinal at which its path was last part of a scan's corpus. The cap counts a cached path (_fresh_cached_paths) only while scan - seen < _STALE_PATH_SCANS; a path no scan has read for that span stops counting and the least-recently-used prune evicts it.
  • The ordinal is derived from the entries themselves (_current_scan is one greater than the highest seen), so it survives the in-memory cache being cleared and the store re-read — no separate versioned field in the document. Successive scans advance it even when every file is a cache hit.
  • _STALE_PATH_SCANS = 5, in scans rather than seconds so it is exercised without sleeping: large enough that a partial scan between two full scans never ages a still-present path out, small enough that a departed path is reclaimed within a few scans.
  • The reading is unchanged: the freshness filter bounds only the prune cap, never the fingerprint index, so the matches a warm scan reports equal a cold scan's.

The gate

tests/test_a_removed_file_leaves_the_clone_cache.py scans a five-file corpus, removes one file, runs _STALE_PATH_SCANS + 1 scans of the remaining four, and asserts the removed path's entry is gone while the entry count equals the current corpus. A second case keeps the partial-scan guarantee: a full scan, a one-file scan, and a full scan again re-parse nothing.
