A dispatch holds while the lane is paused

A backend may declare gate_document, an absolute path to the JSON gate the router resolves, and every dispatch whose resolved backend declares it reads that file before creating a pointer or a worktree — whether --local or an explicit --backend chose the backend. The read returns one row of the five-state rule and carries it as lane_gate on every result: not-declared (proceed), open (proceed), declared-but-missing (proceed, naming the mistyped path), paused (wait), and unreadable (wait). The two waiting rows raise a dispatch hold — ok: false, error: lane-paused, exit status 75 — with no pointer and no worktree left behind. A declared path that differs from the lane document's published router_generation_gate.config_path waits and names both paths; a comparison that cannot be made records lane_gate.path_check: skipped with its reason and never holds on its own. Each of the two reads — the gate file and the lane document — carries its own 5 s deadline. The follower's review reflex (dispatch_review_for_run) launches nothing while the gate waits and reports the row it read, and the dry run reaches the same hold as the launch.

Nineteen cases pass in a temporary RECKON_HOME against a stub local backend, a temporary gate file and a stub lane document; no real gate file, lane document or scheduler is read or written. They drive every row of the rule and assert lane_gate.state in each result, including the --local and explicit --backend CLI dispatches (exit 75, no pointer, no worktree) and the in-process sweep review.

The declared mutation — the gate wait raise disabled (if False and lane_gate.get("state") in _LANE_GATE_WAITING_STATES) — leaves the paused dispatch creating a pointer and a worktree, and the head-paused cases fail (EXIT=1, 10 failed ids the head arm does not fail).
