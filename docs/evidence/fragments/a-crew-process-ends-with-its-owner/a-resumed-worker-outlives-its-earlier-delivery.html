A resumed worker outlives its earlier delivery

What changed

A resumed run keeps its manifest path, so the previous attempt's delivered manifest is still on disk when the new worker starts. The supervisor decides which manifest is this attempt's delivery from the generation it may claim — the baseline. It read the pointer's manifest_baseline_mtime_ns and treated that alone as the baseline. A pointer that still carried its dispatch-time baseline predates the previous attempt's manifest, so the stale complete manifest read as this attempt's delivery and the resumed worker was signalled after the grace on the supervisor's first poll.

The baseline is now never earlier than the current attempt's own start. The attempt start is read from the spec, else the pointer, else the supervisor's own launch instant, and a recorded generation counts only when it is at or after that floor. A manifest written before this attempt began cannot count as its delivery.

  • reckon/crew/dispatch.py — _supervisor_manifest_baseline_ns takes the maximum of the pointer's recorded generation and the attempt start; _attempt_started_ns resolves that start; the caller passes the supervisor's launch instant as the last-resort floor.
  • tests/test_a_terminal_worker_exits_within_its_grace.py — a case resumes through the same launch the resume path uses, so the spec carries this attempt's real start and the pointer still carries the stale baseline.
