Complete refuses while the checkout has a merge open

Promotion commits the two stores it writes — the ledger row and the plan landing comment — into the checkout's index. Measured 2026-09-26, a crew complete of a review run committed into the shared checkout while a peer session's merge was open there, changing that merge's first parent under it. complete now refuses, before either store is written, while the checkout has an open MERGE_HEAD, a rebase state directory (rebase-merge or rebase-apply) or CHERRY_PICK_HEAD, and the refusal names the state it found.

Each marker path is resolved with git rev-parse --git-path rather than a literal .git/ join, so a linked worktree — whose .git is a file pointing at its private directory — is read where git actually keeps the marker. The guard lives in promotion._require_committable_checkout (helper _open_operation_state), the checkpoint that already refuses a checkout which cannot host the landing commit, so both the ordinary and the reconcile promotion paths refuse at the same place.

tests/test_complete_refuses_an_open_merge.py builds a scratch repository under tmp_path: the MERGE_HEAD case is a genuine conflict-free merge left open, the rebase cases create the state directory, and the cherry-pick case writes CHERRY_PICK_HEAD. For each, promotion refuses naming the state, no ledger row is written, the live pointer survives and the plan carries no landing comment. A clean checkout still promotes, and a case in a linked worktree (mount repointed so promotion commits into the worktree) shows the marker resolved at the linked worktree's own git directory. 6 passed.

The declared mutation — the open-state check removed — lets the MERGE_HEAD case promote (DID NOT RAISE) and turns the rebase and cherry-pick cases red: EXIT=1, 5 failed ids the head arm does not fail, recorded in negative-control.log. Head and base arms of tests/test_crew_promotion.py show zero added failures: 50 passed, EXIT=0 at the base revision (fresh scratch tree) and 56 passed, EXIT=0 at the head revision, the six extra passing ids being this node's new file. This gate measures only this node's own change; verifying the merged result belongs to a separately dispatched test node.
