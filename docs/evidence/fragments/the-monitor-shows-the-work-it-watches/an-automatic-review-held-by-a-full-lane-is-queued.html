A review the router holds now waits as a queued run

The condition that separated the unqueued 06:44Z dispatch from the queued 07:25Z run is which code path raised the lane hold, not the lane's state. The recorded reason on both sides is the router granting the session 0 extra workers while the gate document read paused: False. At 06:44Z the reflex composed the review through dispatch(), which raised LaneHeld (a LanePaused subclass meaning the router granted no worker) carrying the allowance gate and no queued record; recovery_review_dispatch's except LanePaused branch reads getattr(exc, "queued", None) and reports error: lane-paused when it is absent, so the reflex had no queueing of its own and the review existed only as a hold. The queued review at 07:25Z (r-20261024T072532586923) was not dispatched by reckon crew dispatch: its run record carries route_mode: explicit and was dispatched by the coordinator's session, consistent with the reflex's reroute retry asking the picker for a lane. The first hold on the deterministic route is therefore the one that did not queue, and the conclusion stands. A shut gate is the other half of the split: LanePaused without LaneHeld withholds without queueing.

The reflex now queues a router-held review itself, deciding on the exception the dispatch already publishes rather than re-reading the gate: isinstance(exc, LaneHeld) is the router-hold test and LanePaused alone is the shut gate, so the state set the admission module owns is not duplicated here. _queue_router_held_review stores the request with runs.queue_dispatch using the same _queued_request_record builder the dispatch path uses, so the queued position rule is one rule rather than two. The write is guarded: the reflex is a sweep whose automatic caller walks the delivered records without a handler, so a CrewError from the queue or an OSError from the write is recorded as lane-paused with the error in its reason and reported, instead of ending the whole project's review pass.

Evidence: tests/test_an_automatic_review_held_by_a_full_lane_is_queued.py holds the section's three cases plus one for the guarded write, each on temp paths for the crew home, the mounts, both gate documents and the worktree root. Case 1 raises the recorded production shape (a real LaneHeld from _dispatch_lane_allowance with no queued attribute) and finds exactly one queued pointer whose run id the report names. Case 2 captures the exception the dispatch raises and asserts it is LanePaused and not LaneHeld, then finds error: lane-paused with no queued key and no pointer at all. Case 3 runs the CLI against the same config and gets queued: true, position: 1. Case 4 makes the queue write raise CrewError and finds a lane-paused report naming the error, no queued pointer, and no exception out of the reflex. Negative control, with the queue condition widened to any LanePaused, case 2 fails on a queued key in the paused-gate report — a shut gate would have queued.
