A reloaded process launches its shims through its own interpreter

The first automatic review dispatch after the reload process learned to find its fleet script launched through the image's reckon/host_shims/srun and failed at once with ModuleNotFoundError: No module named 'pydantic'. The shim resolves its repository root two directories above itself — the reload image's root — which carries no .venv, so it fell through to a bare python3.12 or python3 on PATH that cannot import the package's dependencies. Every launch a reloaded follower or producer makes through a shim failed the same way; none had reached this step before, because each earlier attempt failed on the missing fleet script.

The reloader now names the interpreter it runs under — RECKON_SHIM_PYTHON = its own sys.executable — in the environment it hands the replacement image, so every shim the reloaded process launches resolves that interpreter first and never reaches a system one. A caller that has already named an interpreter keeps it, and a process outside a reload image is unchanged. The change is in reckon/crew_follow_commands.py.

Two focused tests pass. Re-executing a follower into a materialised image carries RECKON_SHIM_PYTHON set to the reloading process's interpreter, and keeps a value already set. The image's srun shim, run with a PATH whose python3.12 is a stub that exits non-zero with a marker, resolves the exported interpreter and reaches the fake real tool (TOOL=srun, exit 0), never the stub. The declared negative control dropped the export and the shim reached the stub (STUB-PYTHON3.12-RAN, EXIT=1), logged under the run directory. The 43-file importer population ran 361 passed at base and 363 passed at the changed revision — the two additions being these tests — with no failing id on either arm. ruff check and ruff format --check added no findings on the changed Python files.
