A settled child is re-checked every tick and re-armed when its session owns work

A follower that finds its session drained prints one idle line and exits with the settle status, and SessionHost.tick left it settled for its next request. A run can appear with no request to the host at all — an admitted queued request, a resume, a delivery whose review is still owed — so the pane that shows it was gone: a delivery at 20:43Z went unseen for eighty minutes, and each resume on 7 November left its session unwatched until a dispatch happened to re-request the pair.

Change. reckon/crew/session_host.py. Each tick now asks a live view for the settled pair; a run the view names re-arms the child in that tick, and a pair owning nothing stays settled. The default view is live_work_run, which asks the fleet's own judgement — station_subscriber.population_has_live_work, the one statement of which runs owe a pane (anything not yet terminal, and a delivered run whose review is not stored) — of the same live-pointer directory a follower settles by, scoped to the child's own session. Naming the run is local to the module, and the census carries it as rearmed_for on the child, so a reader can tell a re-arm from a restart of a failed child. The view is a constructor argument, so a harness states the fleet rather than writing pointer files. A view that fails to read is read as no work, leaving the child settled for the next tick rather than ending the host.

Gate. tests/test_a_settled_follower_rearms_while_its_session_owns_work.py drives tick with a stubbed spawn and a stated live view: a child settling over a working run is spawned again (2 spawns) and the census names r-owns-a-working-run; one settling over a queued request is spawned again; one settling with nothing owed is not, and stays settled across two further ticks.
