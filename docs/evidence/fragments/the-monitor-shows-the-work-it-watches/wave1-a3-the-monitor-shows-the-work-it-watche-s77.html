§77 — A follower armed after a settle continues the pane's words

Path found. The checkpoint was not the defect: the copied pane records under ~/.cache/reckon-monitor-noise/2026-10-21/ carry the run in reported (r-20261021T165659379209-cbl-replay-hardening: "promoted"), and the history shows the pane drawing working → delivered for it at 21:12:46 and new → landed at 21:16:09. The restore was computed and then thrown away: the fresh-arming branch of _follow_watch_lines receives the checkpoint's states from _follow_resume_plan and yields the resume event with an empty reported map, while only the in-place-reload branch calls path.reseed(recorded, lift_groups=carried_lifts).

Reproduction at base. A run is drawn as delivered by one arming, that arming settles, the promotion leaves the live fleet, and a second arming reads the landing. At the base revision the second arming draws no row at all: a landing is observer context unless the pane carried the delivery it follows, and the new process's row path starts with no such memory.

Fix. _restore_carried_words restores the word the pane carried from the checkpoint, and the resume event carries the checkpoint's states for the runs the fleet replay will not re-announce, so the grid continues from the word the reader saw. Live runs are left out of that map: seeding them would collapse the replay's inventory rows into self-transitions and take the fleet off the pane.

Measure. tests/test_a_second_follower_keeps_a_landing_from_state.py drives follower A to draw delivered and settle, then arms follower B for the same project and session as the host does; B's row for the landing reads delivered → landed. The negative control removes the restore, and B draws no row for the run.
