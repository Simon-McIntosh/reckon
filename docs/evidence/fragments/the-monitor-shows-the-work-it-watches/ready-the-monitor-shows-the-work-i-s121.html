A session whose follower is gone is told to re-arm it

A session's obligations snapshot is republished only while that session has a delivering follower, so a session whose follower stopped keeps the snapshot its producer last wrote: it stays on the older code stamp and it ages. That combination had no reading of its own, so it fell through to producer-stale-code, and the line it earned named the producer's watch service. The producer is healthy in that state and publishes for every session that still has a follower, so the remedy sent the coordinator to a command that could not help. freshness_reading now answers follower-released for exactly that population: an aged snapshot, a code stamp other than the checkout's, and a registration that no longer delivers. Both conditions are required, so a released session whose snapshot is still inside the freshness window keeps the stale-code reading it had.

“Released” is asked of the publisher's own reader, follower_registration._follower_liveness, rather than re-derived from a lease or from the registration file's age, so the producer and the hook cannot disagree about one session. That import sits inside the call, as the seat read's own does, so the prompt hook's module-level surface still loads the snapshot reader alone; it is paid only by a read whose snapshot is already past the window. In the hook, not_fresh_line says the follower has stopped and how old the last publication is, then ends with the follower-arming command the hook already carries for a session with no follower. It reuses neither NO_FOLLOWER, whose reason names a foreign seat and claims no snapshot exists, nor the producer's crew watch --ensure remedy.
