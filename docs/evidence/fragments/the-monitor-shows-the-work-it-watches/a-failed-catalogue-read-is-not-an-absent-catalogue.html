A failed catalogue read is not an absent catalogue

The code identity folds the model catalogue, with the package and its dispatch scripts, into one content tree naming what a reloading process will run. The catalogue reader returned None both when HEAD carried no catalogue and when its git read failed — a timeout under load included. One failed read therefore yielded the catalogue-less tree, a valid-looking identity every follower and producer reloads onto, launching with no model named until the next good read moved the identity back and forced a second reload. A read that did not answer now leaves the identity unknown, and the reloader keeps the image it is running.

The gap: one failed read changed the code identity

_committed_catalogue_blob in reckon/checkout_trust.py asked git rev-parse --verify HEAD:docs/state/reckon/model-catalogue.yaml and returned None on any non-zero exit or on OSError/SubprocessError. _committed_reload_tree read that None as “a checkout with no catalogue” and returned the package-and-scripts tree. So a read that never answered was indistinguishable from git answering that the path is absent, and the identity computation produced a different tree either way. committed_reckon_tree folded its own failed read the same way.

The reproduction is the first case of the gate: a temporary repository whose HEAD carries the catalogue, with the catalogue read made to raise subprocess.TimeoutExpired. At the base code the identity comes back as the catalogue-less tree; at the delivered code it comes back as IDENTITY_UNKNOWN. The declared negative control below re-applies that folding and the first case fails again.

What changed

  • reckon/checkout_trust.py gains IDENTITY_UNKNOWN (the value "unknown", which collides with neither a 40-digit tree id nor a 64-digit content digest) and IdentityReadError.
  • The catalogue is now read with git ls-tree HEAD -- <path>, which answers whether or not the path exists: exit zero naming the blob when present, exit zero naming nothing when absent, non-zero only when it could not answer. So empty output is git's own statement of absence, and a read that could not be completed is raised rather than read as absence.
  • Unknown is earned by that read alone. It runs only after a listing has answered for both reckon and skills, so it can only fail on a checkout git answered for. Every other way the computation can fail to identify a checkout — a git that cannot be run, a directory that is no repository, or a tree this process cannot compose — returns None, which source_code_identity has always read as a checkout outside Git and identified by its package content stamp. Those keep the identity they had before.
  • reckon/crew_follow_commands.py: _FollowerReloader.poll treats an unknown reading as no new identity — it returns before comparing, keeping its current image and its recorded stamp rather than materialising a tree from a partial read. The producer's reloader is the same class, so it gets the same treatment.

The first attempt raised too widely, and the follower-pane gate caught it

The first delivery raised the failure from the listing, the catalogue lookup and the tree composition together. On this workstation a worker process may not write to the repository's object store, and git mktree — which writes one — therefore returns nothing for it. The composition that follows a perfectly good catalogue read failed, every identity read in that environment returned IDENTITY_UNKNOWN, and the follower's reloader returned early on every tick.

tests/test_a_pane_settles_when_no_work_is_live.py::test_the_real_follower_settles_when_the_host_advertises_it spawns a real follower and waits for it to settle and leave. It failed 5 of 5 runs alone at the first delivery, and passes 5 of 5 runs alone at the delivered revision and at base. The attribution is the gate's, not the loader's: the failure was reproducible in isolation, in the foreground, with TMPDIR unset.

The gate

tests/test_a_failed_catalogue_read_is_not_an_absent_catalogue.py builds a temporary checkout carrying the package, its dispatch script and the catalogue. The first case makes the catalogue read raise TimeoutExpired and requires the identity to be IDENTITY_UNKNOWN, distinct from the catalogue-less tree. The second removes the catalogue from HEAD and requires the package-and-scripts tree. The third makes tree composition unavailable and points at a directory that is no repository, and requires both to keep the package content stamp rather than report unknown. The fourth requires a fully successful read to fold the catalogue in, confirmed by materialising the identity and finding the catalogue file inside the image. The fifth arms a reloader on a good stamp, then feeds it IDENTITY_UNKNOWN and requires it to keep its recorded stamp, to run its check without re-executing, and never to materialise a tree.

Declared negative control

Declared mutation: restore folding a failed catalogue read into an absent catalogue; the first case then returns the catalogue-less tree and the reloader reloads. Applied to a scratch extraction of the delivered revision: in _committed_catalogue_blob the two raise IdentityReadError(…) statements are replaced with return None, and the reloader's unknown-reading guard is removed. Both modules are recompiled to prove the mutation is loadable. test_a_timed_out_catalogue_read_reports_unknown_not_an_absent_catalogue then fails (reading is the catalogue-less tree, not unknown) and test_a_reloader_given_an_unknown_identity_keeps_its_recorded_stamp fails (assert execs == [] — the reloader re-executes). The scratch tree is discarded; the delivered worktree is not touched.
