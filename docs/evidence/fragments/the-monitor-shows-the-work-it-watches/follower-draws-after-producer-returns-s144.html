A follower keeps drawing after its producer returns, and records what it drew

Session 874a3927's pane drew nothing for half an hour while seven of its runs changed state, and its follower was alive and looping the whole time in StationSubscriber.wake. Nothing recorded what that follower emitted, so a lost row could be blamed on the follower or on the reader and neither could be shown. Driving one subscriber through a producer restart reproduced the stop at two gates, in this order.

The generation gate came first. The follower holds one connection to the node-local station store for its whole life. When the runtime directory is re-created and a fresh station process opens a new database at the same path, that handle still names the file that was unlinked, and PRAGMA data_version -- which moves only when another connection commits to the database this connection has open -- never moves again. generation_moved answered "nothing moved" for as long as the follower lived. The place came second. A fresh store begins its own id space, so the rows it writes carry ids below the cursor the follower reached in the store that is gone; even with the right file open, a read after that cursor returns nothing.

StationStore now records the device and inode of the database its handle opened (database_identity) and reopens when the file at that path is a different one (reconnect_if_replaced) -- one stat beside the pragma the gate already pays for, and no reopen while the path holds no file. A subscriber that reconnects onto a store opened fresh takes that store's own place for its audience and forces one read; a store carrying the same birth stamp forward, as a restored copy does, leaves the in-memory place alone so nothing is drawn twice. A store with no counter yet also opens its sequence after the highest id its surviving day files hold (_opening_sequence), so a lost database over living day files can neither write below ids already held nor leave a cursor naming a row already read.

Every row a follower yields is now written to its own stderr -- which the session host opens onto <cache>/session-host/<owner>.log -- as a follower-emission line carrying the follower's sequence number, the row's time, its run, its transition and the station event id. A later report of a missing row can be placed on the follower that emitted it or on the row's reader without a live capture. A terminal arming skips the line, where it would read as a second copy of the pane's output, and a log that cannot be written never ends the pane.

tests/test_a_follower_keeps_drawing_after_its_producer_returns.py drives one subscriber over a fixture store through two transitions, a producer lost past obligation_snapshot.STATION_STALE_SECONDS, and a fresh station process writing five more transitions. The same cases run as a fence: the base revision's tree at 3bc474f is 58 passed with exit 0, and the head at ddebbfa is 61 passed with exit 0 — the three extra cases are this measure's own. The wider population that imports the subscriber, the watch unit or the follow commands is 101 files at the base and 102 at the head: 24 failed and 669 passed against 23 failed and 673 passed, with no failing id added and one base failure gone, so the change's own three cases account for the difference. The declared negative control — StationStore.reconnect_if_replaced answering False, which is the base gate — leaves 1 failed and 2 passed and names test_a_follower_keeps_drawing_after_its_producer_returns, so the measure is the one the gate turns.
