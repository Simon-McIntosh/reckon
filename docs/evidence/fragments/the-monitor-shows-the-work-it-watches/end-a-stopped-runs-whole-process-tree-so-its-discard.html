What changed

terminate in reckon/crew/dispatch_sessions.py resolves the run's whole process tree to pids before it signals anything, records that list in the stop record (target_pids) and names it in the printed detail, then — after the existing bounded settle — escalates to SIGKILL for whatever is still alive and waits again. The escalation re-walks the run's own tree instead of signalling the survivor list by pid, so the reach stays bounded to the run and a pid the kernel has since reused can never be signalled; the survivors it could not end are reported in alive_after. _signal_process_group and signal_worker in reckon/crew/process_signal.py take the signal to deliver, so the escalation passes the same identity and self-group guards as the graceful signal.

The defect, reproduced before repair, and gone after

A probe built a run tree of a parent and a child that both ignore SIGTERM, wrote it into a live pointer and ran the stop against the base revision:

detail: SIGTERM sent to 2 process(es) of run r-probe-stop-tree; 2 still alive afterwards: [379, 380]
DISCARD_REFUSED CrewError cannot discard live run 'r-probe-stop-tree': recorded pid 379 is alive

The same shapes now end both processes and leave the discard to succeed — that is what the gate below asserts behaviourally, before it reads the record.

Measure

tests/test_stop_reaps_run_tree.py passes at head (2 passed). Its first case asserts the parent and the child are dead, that both pids are printed in the record, that promotion.discard then succeeds, and that a bystander in its own session is still running.

The escalation is unconditional in product code: no environment switch can turn it off in a deployment. The test's own control replaces _escalate_run_stop with a no-op, which is the stop as it stood before the fix, and asserts the wrapper survives and the discard is refused. The declared mutation — removing the escalation call from terminate — makes the first case fail with 1 failed, 1 passed, EXIT=1 (negative-control-escalation-dropped.log); the file was restored afterwards and its digest re-checked.

Both arms ran one at a time at -n 4 over the 49 test files that import the changed modules, plus the new test in the head arm: base 1 failed, 742 passed, 2 skipped, head 1 failed, 744 passed, 2 skipped — the same single failure tests/test_crew_obligations.py::test_obligations_reads_scoring_without_observing_or_dispatching in both, so the change adds none. ruff check reports no findings on the staged paths; ruff format --check reports the same one pre-existing unformatted file at base and at head.
