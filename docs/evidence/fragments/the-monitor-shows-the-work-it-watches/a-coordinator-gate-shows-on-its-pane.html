A coordinator's own gate run draws a start row and an end row on its own pane

reckon crew verify-gate and reckon crew suite run now write a durable gate record under the shared config home when a gate starts and complete it with the exit status when it ends. The record holds the calling coordinator's session, the project, the run id when one is named, the checkout, the command's first words, the start instant, and the pid and kernel start tick of the process running the gate.

The new reckon/crew/gate_watch.py reads that document and folds it into watch-stream rows the way lift_watch.py folds budget lifts and resets: one row when a gate starts, one when it ends, and — for a producer that has just re-armed — a baseline row for every gate already running rather than announcing it as new. Each row names the gate's own session, so it reaches that session's pane and no other. reckon/crew/recovery_watch.py calls the sweep in its clock-driven block beside lift_watch.sweep, because a gate becomes due when its process ends, which moves no file.

An end needs no writer. A gate whose process is gone with no completed record reads as ended, with no exit status, so a killed CLI or a dropped ssh leaves a row saying the gate stopped rather than a pane claiming it still runs. The record's pid and the kernel's start tick for it are compared, so a pid since handed to another process is not mistaken for the gate. The fold is read-only: every project's producer folds one workstation-wide document, and a producer that stamped an end would race its peers over it.

skills/reckon-build/SKILL.md now names verify-gate --command as the way to run a long coordinator gate, so the verb that puts the gate on the pane is the one the skill recommends.

Evidence: tests/test_a_coordinator_gate_shows_on_its_pane.py passes five cases — a verify-gate --command run writes a start record the gate's own command can see and completes it with exit status 0; a sweep over a running gate emits one start row for the owning session and none for another; a second sweep repeats nothing and a sweep after the end emits one end row naming the exit status; a record whose pid is gone with no end reads as ended with no status; and the skill carries the sentence naming the verb. The declared negative control — skipping the record write in verify-gate — fails the start-row case (1 failed, 4 passed). The 87 related files of the crew suite pass (644 passed) with no added failure.

The record is never the gate's work. A gate record that cannot be written is reported on stderr and the gate runs anyway, on both verbs. Opening the record for suite run reads the declared command from an object or a mapping, because the declaration is external configuration and a shape the gate did not expect refused the suite before it started — that regression was caught by the related-file gate and repaired.

stream_carries in reckon/crew/ticker.py admits a row by its destination state, and the gate states were not among the words the renderer knew, so every gate row classified as observer context and the row policy dropped it. The renderer now spells the two gate words itself, for the reason it spells the lift words — the fold imports the recovery watch, which imports the renderer, so reading them back would close an import cycle — carries both, and maps both to the working pane word, because a coordinator running its own gate is present and working rather than idle. A test feeds the fold's start and end rows through the policy a follower uses and requires both to be released; with only that clause removed, it fails on the drop. Writing a row and drawing it are different claims, and only the second one puts the gate on the pane.
