A station subscriber re-executes onto its source checkout's code

A follower subscribed to a station renders every row with its own code: the station commits rows and station_subscriber composes the sentences the pane prints. The subscriber's delivery in crew_follow_commands.crew_follow therefore builds the same _FollowerReloader the stream delivery builds, polled through the per-wait hook at a row boundary and never through _StampPoll, whose signal handler would re-execute mid-render. Driving that path also showed the station registration could not hand the session's claim across an image replacement; it now delegates prepare_reexec/cancel_reexec to the claim it wraps.

tests/test_a_follower_runs_current_code.py enters crew_follow's subscriber branch itself, with a stubbed subscriber and a stubbed per-wait loop, so the reloader under test is the one that delivery builds and polls. It shows the four required cases, and two more: a moved-and-trusted checkout re-executes (one recorded os.execve); a matching stamp and an untrusted checkout do not; a follower running from a reload tree reads the checkout its carried environment names rather than the tree it imports from, and materialises the replacement from that checkout; and over 100 sweeps spanning three checked_at intervals with a matching stamp the sweeps read the checkout's identity exactly 3 times (the delivery reads it once more as it arms its image). The claim hand-over is observed, not merely not-raised: against a stub claim the moved-checkout case records one prepare_reexec before the exec and one cancel_reexec when the replacement is refused, and a session-less pane takes no claim and so calls neither while still reloading.
