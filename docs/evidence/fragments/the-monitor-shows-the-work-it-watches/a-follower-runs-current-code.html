A station subscriber re-executes onto its source checkout's code

A follower subscribed to a station renders every row with its own code: the station commits rows and station_subscriber composes the sentences the pane prints. The subscriber's delivery in crew_follow_commands.crew_follow therefore now builds the same _FollowerReloader the stream delivery builds, reached through the per-wait hook at a row boundary and never through _StampPoll, whose signal handler would re-execute mid-render. A long-lived subscriber no longer keeps the wording of the image it was armed with.

`tests/test_a_follower_runs_current_code.py` shows the four required cases against a temporary home and a stubbed checkout: a moved-and-trusted checkout re-executes (one recorded os.execve); a matching stamp and an untrusted checkout do not; a follower running from a reload tree reads the checkout its carried environment names rather than the tree it imports from, and materialises the replacement from that checkout; and over 100 sweeps spanning three checked_at intervals with a matching stamp the checkout's identity is read exactly 3 times, so the cadence keeps the subscriber off the shared filesystem per row.
