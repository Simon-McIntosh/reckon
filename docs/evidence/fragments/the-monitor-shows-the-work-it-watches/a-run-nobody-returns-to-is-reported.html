A run nobody will come back to is reported

A live pointer is forgotten when both hold: its classification is terminal and unpromoted — the classifier's promotable, scoring, blocked or failed, or the fleet verdict's complete or abandoned — and its owning session has had no live follower registration and no dispatch for a threshold defaulting to six hours. The derivation lives in reckon/crew/forgotten_runs.py and joins classify_pointer with _follower_liveness and _unattended_seconds, the two readings that until now drove only the watcher's sweep. It deliberately does not reuse overdue_unreconciled_runs: that list feeds the dispatch fence and refuses, while this one only reports. The threshold is a parameter of the derivation, and a pointer naming no session is judged by its own terminal age, because absence is not ownership.

The list is served as a crew read view rather than a new verb — crew(view="forgotten") and reckon crew view forgotten --project P call the one function both surfaces share — and each row names the run, its node, its session, its classification, its unattended and terminal ages and the recovery the classifier already offers it.

Five pointers are built in a temporary RECKON_HOME: a complete run whose session holds a live follower registration, a complete run whose session has had neither follower nor dispatch for seven hours, a running run under that same second session, and two complete runs under it whose outcome has already landed — one by a ledger row carrying commits, one by a report-only row declaring none. pytest tests/test_forgotten_runs_are_reported.py — 5 cases — lists exactly the second, with its age and its recover action; the two settled runs are held out by the landing while the session age that lists the third sits on them unchanged; and the derivation called at an eight-hour threshold lists nothing. The no-dispatch guard reads every reckon/crew/dispatch*.py module and finds neither the new module nor its function, and its positive control finds the name in reckon/crew/forgotten_runs.py by the same instrument, so the absence is a reading rather than a failed search. The settled pair is what holds the unpromoted half of the predicate: a pointer exists for them only for the window between the ledger write and the pointer's removal, and without that case a derivation that stopped filtering settled rows would leave every other case green.
