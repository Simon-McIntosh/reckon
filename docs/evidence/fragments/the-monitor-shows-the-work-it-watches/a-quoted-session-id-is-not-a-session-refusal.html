A queued refusal is read by its stamped class, not by a substring of its text

_queued_failure_remedy (reckon/crew/recovery_classification.py) decided whose refusal a queued pointer's failure was by asking whether the dispatching session's id appeared anywhere in its text. An UnreconciledRuns refusal names each finished run beside the action that settles it, and a review action carries --session <id>, so the id appeared in a refusal whose subject was a set of finished runs. The queued run was published under queued-awaiting-session with reckon crew follow as its remedy, and no follower clears an unreconciled-runs refusal.

What changed. The admission pass stamps the exception's class name at the head of the stored failure (<ClassName>: <text>), and that name is now what the reader keys on. UnreconciledRuns publishes the first named run's own action, read from its - <run_id>: <action> line; the classified row's session_refusal detail states that a queued run cannot take --allow-unreconciled-runs after it is queued and that the alternative is to discard it and dispatch again with that waiver. The follower condition keeps the follower remedy, matched on the private subclass _FollowerAdmissionUnmet beside its public base WatcherRequired. A failure recorded with no class stamp keeps the text search it had. The row still reads under queued-awaiting-session for both kinds, because in both the session owes the fix.
