A request the lane holds, or a launch that keeps failing, is left where it is

admit_once now asks two more questions before it releases a queued pointer, so a request whose state has not moved is neither withdrawn nor re-queued and appends no transition. First, it asks the lane's gate document (_dispatch_lane_gate) alongside the session allowance, so a request the lane would still hold keeps the same run id and queued phase. Second, it holds a request whose last attempt failed for a reason other than a lane hold (_retry_backoff_*): the failure records the attempt count, the next retry time and a fingerprint of the request's brief, its plan and the flight configuration layers that resolve its backend (reckon.flight host and project layers) — deliberately not the router's lane document, which is republished every few seconds. The pass leaves the pointer untouched until one of those changes or a bounded doubling back-off elapses. The first such failure is reported once to the session: the pointer records failure_reported_at and the drainer appends one row to the project's watch stream, the channel the pane reads; later passes report nothing. The launch-failed re-queue path stamps the same back-off.

tests/test_a_held_request_stays_queued.py covers a gate-held request, an allowance-held request, a request that still launches once the lane opens, a missing-brief request run three times (first pass records the failure and reports it once; the next two leave the pointer unchanged and append nothing), a lane-document rewrite that must not retry, and a launch-failed requeue run twice. Six cases pass; with the pre-release questions removed the held arms fail.
