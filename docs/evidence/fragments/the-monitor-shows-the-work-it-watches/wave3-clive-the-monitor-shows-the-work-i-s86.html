§86 — The obligations snapshot is fresh, or says why it is not

Cause, read from the committed blob at the base revision. A session's snapshot carries an age, so publishing a fresh one becomes due with the passage of time. Every producer-side trigger for the sweep nevertheless read a document: a pointer transition, a file under the project's state or plan trees, and the crew home's fingerprint the ticker gates its fleet listing on — a fingerprint that deliberately excludes the watch directory.

The obligations sweep is reachable only through that gate. reckon/crew/recovery_watch.py:3425 calls list_live(project=project) inside if sweep:, and list_live is the only producer-side caller of runs._publish_watch_stream — the only caller of _publish_obligation_snapshots. obligation_snapshot.FLOOR_TICK_SECONDS (60 s) is documented as publishing duties that become due with time alone, but on a quiet fleet no beat ever reached it.

That is the reported reading exactly: the seat held, watcher_live: true, the pane still drawing rows, and the session's obligations snapshot ageing without bound — 8308 s, then 8461 s, then 9382 s — while the hook could name only the age of the reading, never who held the seat.

Repair

  • runs.publish_obligations_on_beat(project) starts one sweep from the producer's own clock. It lists nothing and folds no transition; the sweep's own floor interval decides whether that beat publishes, so a fleet that is moving costs nothing extra. A sweep already in flight is skipped rather than queued, as a change-gate trigger already is.
  • The ticker's existing 30 s clock block calls it beside the reset, gate and orphan sweeps, best-effort: a beat that raises is printed and never ends the seat.
  • The stale notice now names the holder. not_fresh_line reads the seat's registration and says the snapshot is 8308s old; the seat holder (pid 4242 on host H) last wrote it 8308s ago. With no registration to read it names no holder rather than guessing one.

Evidence

The four cases in tests/test_the_obligations_snapshot_is_fresh_or_says_why_it_is_not.py pin both halves. The positive case drives a real ticker, a real producer and a real follower registration against a synthesised project, with the fleet listing pinned to one answer so the change gate opens once and never again; the snapshot it had aged past the freshness window is refreshed within one producer interval, and the listing is never called again, which shows the refresh came from the clock. The negative control removes the beat's publication and drives the identical beats: the same snapshot stays stale past the window. The two notice cases pin the pid, host and last write, and the no-registration shape.
