A discarded request is never reported queued

The admission pass reports a request's first failure once through the session's pane stream, so a watching session sees the run it is waiting on. A request the operator discards while the pass holds it was still reported: the discard removed the pointer and recorded the departure, the restore correctly declined to write the request back, and the report then appended a row naming a run the fleet no longer holds — a failure reported for a request nobody is waiting on. _report_queued_failure now reads the discard record before it builds the row and returns early when one exists, so the same record that stops the restore also silences the report. A request nobody discarded is unchanged: the row is still appended once, at state queued, and the pointer carries failure_reported_at so the next pass appends nothing further.

Measure: tests/test_a_discarded_request_stays_discarded.py — 5 passed; the two new cases bind the report to the discard record, one asserting no stream row names a request discarded mid-pass while its failing launch runs, the other asserting a kept request gains exactly one row at state queued with the report marker on the restored pointer. Declared negative control EXIT=1: with the discard check removed from _report_queued_failure the discarded case fails on the appended row (a discarded request is reported nowhere), and the kept case still passes.
