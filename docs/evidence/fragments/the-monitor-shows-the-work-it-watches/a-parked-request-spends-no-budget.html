A request that never launched spends no budget

A live pointer waiting on upstream work carries no launch stamp, but _budget_timing (reckon/crew/recovery_stream.py) fell back to the pointer's creation time and charged the whole wait against the time budget. A pointer parked for a week therefore read as a week of work, and every awaiting-upstream request raised an overrun alarm — 539,530 s against a 10,800 s budget on csrr-report-assembly.

Elapsed now counts from the run's first launch, the attempt start or the launch stamp. A pointer still in a waiting phase (queued, awaiting-upstream, blocked-upstream, held) has no launch stamp and reports no elapsed time and no overrun; the time it has spent parked is reported under waiting_seconds, measured from its creation, so the figure stays readable without being charged as budget. A pointer in a waiting phase that does carry a launch stamp — a reprogrammed request — is still charged, from that launch.

The wait reaches a parked row, and the name is declared with the live fields, so crew view live --fields waiting_seconds is accepted whether or not a parked row is in flight: waiting_seconds joins LIVE_CLASSIFICATION_FIELDS in reckon/crew/query.py, and LIVE_FIELD_VOCABULARY is built from that tuple, so the live view, the runs view and the MCP pre-flight all answer it. Removing the name from the tuple refuses the request again (unknown live fields 'waiting_seconds'), which is the guard the new case holds.

Measure: tests/test_a_parked_request_spends_no_budget.py — 7 passed. Against the base source the same test fails 6: the week-old awaiting-upstream pointer reports budget_overrun true, and a run created ten hours before its launch reports 39,600 s of elapsed instead of 3,600 s. Declared negative control EXIT=1: with the waiting-phase fallback restored to created_at, the four parked cases fail on assert True is False at the overrun assertion, the live-view case fails with the wait absent from its row, and the two launched cases still pass. A second control removes waiting_seconds from the declared tuple and fails only the live-view case, EXIT=1. The baseline and after arms over the nineteen test files importing reckon.crew.query, reckon.crew.recovery_stream, reckon.crew.recovery_classification and reckon.crew.recovery carry the same failure set either side — 4 failed and 10 errors at origin/main against 4 failed and 10 errors after, with passes rising 264 to 271 — so the change adds none.

The captured answer that tests/test_read_verbs_retire_behind_crew_view.py compares the live view against carried the same defect for its queued pointer: the retired listing charged a request that had never launched, so it answered 300 s of elapsed time and an overrun against a 200 s budget. That capture's queued row now records the corrected answer — no elapsed time, no overrun — while every other field and every assertion over it stand unchanged. The two parity cases ([project], [session]) pass, and pass again on a detached export of the merge candidate, so the correction is the capture's rather than an exemption in the comparison.
