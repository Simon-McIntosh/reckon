A resume sends the host request a dispatch sends, and the host re-arms the pair

A session's pane is fed by one follower its host runs, and SessionHost.tick does not restart a child that exited settled — the pair waits for its next request. A dispatch sends that request; a resume sent none, so a session whose last action was a resume stopped following once that child settled while the resumed worker ran on and delivered into nothing.

resumption._resume now asks the calling session's host for a follower after the launch is recorded, through the same request line a dispatch writes (_request_host_follower), and reports the answer as follower_rearmed on the resume result and on the crew resume payload. Both doors reach it: the CLI verb and the repair reflex both launch through _resume, so neither needed a second statement of the rule. The launch is not failed over a host that did not answer — the worker is already running, and the re-arm only decides whether its rows reach a pane.

The answer is the calling session's own host, not attachment. _session_host_child_pid reads that host's census record and returns the pid of a non-settled child for the pair; _rearm_session_follower answers success only on that pid, and _session_host_runs_follower now shares the same reader so dispatch and the re-arm cannot disagree about what a child of this host is. A live follower another host registered, or one a coordinator armed by hand, keeps session_attached true and is still not a re-arm this host made, so it no longer reads as one.

Evidence: tests/test_a_resume_rearms_its_follower.py drives _resume against a temporary crew home and a stub host on the session host's FIFO. Case one: no follow request reaches the host at base, and at head exactly one line {"project": …, "session": …} arrives, the stub's re-armed child appears in the census, and the result carries follower_rearmed: True. Case two: a live follower registration for the session, with the census naming no child for the pair, answers follower_rearmed: False — the discriminator the old criterion could not make. At 97c71c15d6 both cases fail (2 failed); at head both pass (2 passed).

Both declared negative controls were applied in scratch copies of the head tree and run: dropping the host request from the resume leaves case one with no child (2 failed, EXIT=1), and answering on any live registration instead of the host's own child makes case two report success (2 failed, EXIT=1).

The 25 test files importing reckon.crew.session_host or reckon.crew.resumption run serially on both arms: 218 passed at head (EXIT=0); at base 217 passed and test_dispatch_session_host.py::test_dispatch_asks_the_session_host_and_is_admitted_by_it failed with _FollowerAdmissionUnmet. That id passes at head serially and fails at base, so the delta is zero added failures and the base failure is pre-existing and load-sensitive — under -n 4 a different settle case timed out at head and passed serially, the same signature.

No rule was added for the two live followers per session seen on 6 November, and the exit record is §112's. Nothing in reckon/crew/session_host.py changed: handle already re-arms a settled pair on request, which is what the resume now supplies.
