A run that has already landed no longer asks to be promoted

A station computes each session's duties once per tick and keeps that answer until the next tick, so the list the obligations view and the stop hook serve can be minutes old. Promotion unlinks a run's live pointer as it writes the run's ledger row, and the review-ready or promotable-stale duty derived from that pointer survived in the held answer: the view and the stop hook went on naming "promote the completed review run" for a run already promoted, and the hook blocked the coordinator's turn on it.

Deliverable. review-ready and promotable-stale join LIVE_POINTER_DUTY_KINDS in reckon/crew/obligation_snapshot.py. Both are promotion duties, and a promotion is taken only through crew complete against the run's own live pointer, so once the pointer is gone — through promotion or through discard — the duty names an action nobody can perform. The settlement is still one stat per such duty at the run's own pointer path: no ledger is opened, which is what the module's banner requires of the prompt path. The comment above the set, the helper's docstring and the derivation's docstring in reckon/crew/obligations.py state the rule and who settles it. Every other kind is unchanged: a review-missing row is evidence a promotion did not settle, so it is still listed for a departed run.

Gate. tests/test_a_promoted_run_owes_no_promotion.py, four cases, each writing the station's answer while the run's pointer existed and reading it after removing it: (a) a run promoted in the project ledger set produces neither a review-ready nor a promotable-stale duty, read through serve_crew_view("obligations") and through the stop hook, which no longer returns decision: block; (b) the same run with its pointer present and no ledger row still reads review-ready on both surfaces; (c) a run discarded with no ledger row at all also produces no promotion duty; (d) a review-missing duty for a departed run is still listed on both surfaces.

Negative control. Leaving the promotion kinds out of LIVE_POINTER_DUTY_KINDS fails the first and third cases and keeps the two positive controls green: 2 failed, 2 passed. Log: negative-control.log under the run directory. The two green cases are the instrument's own positive control — the same assertions do see a duty when one is owed, so the absence in (a) and (c) is not an absence of work.
