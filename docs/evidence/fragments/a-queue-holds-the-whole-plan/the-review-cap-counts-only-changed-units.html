The third-review cap counts only the reviews that read a unit's change

What changed. The carried-findings landing was reverted because its third-review cap counted every stored review of a unit's current digest. A unit whose prose had not moved across a long-lived plan's revisions accumulated one counted review per revision, so composing a review of any plan reviewed more than twice was refused, and answering the named findings did not help. Three repairs restore the landing: the cap is bounded to one plan revision, an answer is read from whichever stored record holds it, and a carried answer no longer displaces an earlier one.

Reproduction before the repair. On the live store at the reverted code, compose_burst_refusal('reckon', 'a-queue-holds-the-whole-plan') refused with unit s1 … has had 47 reviews for this edit, and compose_burst_refusal('nova', 'kernel-compile-barrier') with unit s0 … has had 6 reviews. The forty-seven were real stored reviews: section s1 carried the same prose digest from plan version 5 through version 200, and each review of the plan after that carried it unchanged.

The bound. reviews_for_unit_burst in reckon/crew/plan_review.py still selects the reviews that carried the unit's present digest, and now keeps only those at the newest plan revision among them (_plan_revision, the whole-plan fingerprint with the reviewed blob and version as fallbacks). Two reviews of one revision still reach the cap and refuse a third, which is the loop the cap exists to stop; a unit that a later revision did not touch stops counting at the review that read it.

The answers. review_burst_refusal resolves a finding's answer across every stored review of the plan, not only the counted records. An answer is written to the record the answering command resolved, which need not be the record the cap counted, so a finding answered there was named open again and no answer command could clear it.

The carry. record_response leaves an earlier acted or declined answer in place when a --carried answer follows it. Carrying hands the finding to a node; it is not a later judgement about the prose, and replacing the answer erased a decision the gate had already read.

Which revision is "newest". The bound finds the newest revision by ordering the counted reviews. It ordered them by dispatched_at, a field store_plan_review never writes — only timestamp, which it stamps on every record — so every sort key was empty and the newest review was whichever one the listing returned last. The order is now timestamp with plan_version as a tiebreak, and an arm hands the listing back newest-first, the reverse of the store's own order, and still counts at the revision the plan carries now.

Evidence. tests/test_a_carried_finding_reaches_the_node.py reports 9 passed, EXIT=0 at the head revision (logs/after-suite.log). The four added arms fail against the base revision's code with the head test file in place — 4 failed, 5 passed (logs/baseline-suite.log) — so each repair is falsifiable. The declared negative control restores the reverted cap, counting every stored review of a unit's current digest: the two arms that assert the bound fail and the other seven pass — 2 failed, 7 passed (logs/negative-control-count-every-stored-review.log). The ordering arm is falsifiable on its own: restoring the dispatched_at sort fails that arm and leaves the other eight passing. The live-store arm is called read-only at the head revision and both compose_burst_refusal calls return None (logs/live-store-arm.log). ruff check and ruff format --check pass on the changed Python paths.
