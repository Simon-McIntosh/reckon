A batch entry carries the test its done-when names

Eight runs of one crew dispatch --batch stopped blocked, each on a section whose write-paths sentence ends "and the new test". _PlanRead.write_paths keeps only tokens that look like paths, so a described test yielded nothing and the run's fence omitted the very file the worker was told to write; the manifest audit refused it as outside scope, the pointer is read-only inside the fence, and each run cost a coordinator crew widen and a resume.

Where the sentence describes a test and no literal path in that sentence names one, dispatch_batch now takes the path from the section's done-when, which is where the test the node writes is actually named. Exactly one file under tests/ in the done-when resolves the entry; two or none is refused by name, quoting the description and the sentence, in the same shape as a section with no write-paths sentence, and the rest of the batch is still stored. The evidence for the described file is what the done-when says before its own write-paths sentence, so the description is never read back to itself. An entry that supplies its own write paths is not asked for the derivation at all, so a description the sentence cannot resolve cannot refuse an entry that never needed it.

The gate, tests/test_a_batch_entry_carries_its_done_when_test.py, queues seven entries over one fixture plan. The section ending "and the new test" with one tests/ file in its done-when is stored with ["one.py", "tests/test_one.py"]. Three sections are refused, each naming 'the new test' and its sentence: the done-when naming two tests/ files (two.py and the new test), the one naming none (three.py and the new test), and the one naming a single file under tests/ that is not a .py test (seven.py and the new test). The section ending "and its regression test" resolves the same way (["four.py", "tests/test_four.py"]), so the rule is not one phrase. The section that names its test path outright derives exactly the base revision's list (["five.py", "tests/test_five.py"]). The seventh entry supplies its own write paths over a section whose description resolves to no path at all, and is stored with ["custom/own_six.py"] — the sentence is never read for it.

A path counts as a test path here by the repository's own definition, not by a second one written in dispatch_batch. The description resolves through _TEST_PATH_PATTERN, the pattern the repair round already grants a test from, so a batch entry accepts the set a repair grants — a tests/ path ending .py — and the two cannot drift apart. The seventh entry's section is what makes that visible: its done-when names tests/seven.json, which a looser suffix-accepting extractor would have taken as the described test, and the shared pattern refuses it.

The release path takes the same rule one step further: rederived_section_fields asks for the write-paths derivation only when the request carries a mark on that field, so a request that supplied its own write paths is never made to read a sentence it did not use. Without that guard the new resolution reached the release, and a section describing a test whose done-when names zero or two tests/ files held the request at release instead of launching it. The gate holds both directions: a request marked on done_when alone re-derives that field and nothing else, while a request marked on write_paths still gets the sentence read and is still refused when the description cannot be resolved.
