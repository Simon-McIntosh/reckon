A launch refused on a claim returns its request to the queue

A claim can be taken in the window between the pre-launch claim check and the launch itself. The launch then raises ScopeConflict after the request's pointer has been published in phase starting. Recording that refusal as a failed attempt stamped the failure onto the starting pointer and left it there: the run carried no admit_request and no attempt start, so _requeue_admitted_failures never touched it, and it had no launch clock for the stranded-launch reaper. On 8 November such a request sat for 55 minutes until a coordinator discarded it.

The refusal is now a hold. _restore_refused_launch_to_queue writes the request back as one queued pointer, carrying the hold _refusal_hold builds from the refusal — the holder's run, node, session, phase and path — and the pass records the verdict held-on-claim instead of failed. No failure and no retry back-off are stamped, so the next pass launches the request as soon as that claim is released. The pre-launch check already judges a stopped run's claim through claim_disposition, the rule the dispatcher uses; the tests here now guard that reading as well.
