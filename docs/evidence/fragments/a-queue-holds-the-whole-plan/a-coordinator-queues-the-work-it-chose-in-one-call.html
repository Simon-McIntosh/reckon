A coordinator queues the work it chose in one call

reckon crew dispatch --batch <file> queues a coordinator's chosen sections as one call. A new reckon/crew/dispatch_batch.py reads the file's entries, reads each plan the batch names once through _plan_html.section_prose (memoised for the whole batch, including the queue-time review-contract read), and takes every field an entry omits from its own section: the done-when through _done_when_paragraph, the write paths through the section's own Write paths: sentence (every path it names, not only .py ones), the capability and effort from the section record. An entry's own value always wins, and an entry may wait on another entry of the same batch by that entry's node id, resolved to the sibling's stored run id. Each entry is validated and stored on its own, so a refused entry never stops the rest, and the call prints one row per entry: queued, awaiting-upstream, already queued, or refused with its reason.

Queuing runs through reckon.crew.dispatch.queue_requests rather than the project-wide wrapper in queue_admission: that wrapper sets the bounded-readiness context off for every request, so each entry would rebuild the project's whole roadmap. The batch stamps the same review contract per stored request that the single-dispatch queue path stamps, so the queued semantics are unchanged. Entries are stored in an order that puts a batch-sibling before the entry waiting on it, and a cycle among node-id waits is refused whole, naming every member.

The gate is tests/test_a_batch_queues_the_chosen_sections.py, a batch of six entries over two fixture plans with a third plan never named. It shows the six required facts: the sibling wait is stored awaiting-upstream on the sibling's run id; the entry omitting done-when and write paths stores the section's own (the three check passes. and ["three.py"]); the entry giving custom/own_module.py keeps it; the entry on a section with no write-paths sentence and none of its own is refused by name while the other five are stored; a repeat of the batch reports already-queued for the stored section and leaves one pointer; and the two named plans cost exactly 2 section_prose calls for six entries, with no project-wide readiness read (project_section_readiness is never called) and exactly one build_roadmap call for the whole batch, counted through a patch on it — the one derivation discovery already makes for the project's ready set, which the batch reuses for queue ordering and for each section's own verdict.

Two negative controls, both applied to the final code and logged. Dropping the derived write paths from _PlanRead.write_paths fails the queuing report the first arm measures; removing the batch's roadmap memo, so every stored request rebuilds the project roadmap, fails the one-build arm with the count it actually reached. Each arm records a non-zero EXIT=1 the head run does not.

The build skill and its sprint-orchestration reference now name the batch call as the way to queue the chosen work, replacing the wording that told a coordinator to dispatch each section in one beat.
