A queued request whose section waits are unmet is held until they land

What changed. A dispatcher may now queue a batch whose later nodes depend on sections an earlier one builds, and the queue holds them. queue_requests in reckon/crew/queue_admission.py reads each node's section waits off its plan (plan-section-depends-on, via section_wait_refs) and stores the request in a new awaiting-upstream phase beside QUEUED_PHASE when it declares any. A request in that phase is not eligible for launch, so a batch of three chained sections launches its head alone.

Each admission pass calls advance_waiting_requests before it builds its launch list, and that pass re-reads readiness and moves each waiting request to the phase its refs now justify: queued once its last wait is satisfied, blocked-upstream once a wait can no longer be satisfied. No coordinator call sits between the two, which is the point of the state: the queue releases itself as upstream promotes.

Readiness is imported, not re-derived. The pass builds the roadmap's own report (reckon.roadmap.build_roadmap, through the same discovery the plan-review path uses) and reads each ref's outcome from the blocker rows of that plan's section_readiness. A second derivation is how a request comes to be held for a reason the roadmap would not report, and the roadmap's row is also what tells a wait that is still pending from one that was closed unfinished — the latter reading abandoned wherever a terminal non-completed status reaches it. Blocking is transitive: a request blocked by a ref the same pass has just blocked becomes blocked too, which the fixpoint in advance_waiting_requests guarantees whatever order the pointers are held in.

Refusals move to queue time; scope does not. A node the batch carries that cannot be dispatched at all — a declared input the repository does not hold, a malformed goal, a missing time budget — is refused when the batch is queued, so it never takes a place in the queue or hides behind a chain that has not moved. A node's write scope is still checked at launch and not at queue time: what a node may write is a property of the tree it lands in, which has not been resolved when the request is only stored.

The two states. AWAITING_UPSTREAM_PHASE ("awaiting-upstream") and BLOCKED_UPSTREAM_PHASE ("blocked-upstream") are defined in reckon/crew/queue_admission.py, beside QUEUED_PHASE and LAUNCH_FAILED_PHASE, with WAITING_UPSTREAM_PHASES naming the pair. The name is not waiting: dispatch_admission.py already uses that word for a lane's queue count, and a phase reusing it would make one word mean two things in the same document.

The three arms the new module measures

  • Ordering. One call queues a three-section chain. The head is stored queued; the middle and the tail are stored awaiting-upstream, each carrying its own ref (plan-a#s1, plan-a#s2). An admission pass launches exactly one of the three. Declaring s1 done and passing again launches the middle and leaves the tail waiting; only after s2 lands does the tail launch, and no call other than the admission pass sits between them.
  • The blocked arm. A second chain queues identically, then the head's request is closed as failed — nothing will ever deliver s1. The pass then launches nothing, and both the middle and the tail read blocked-upstream: the middle because its ref is dead, the tail because the fixpoint carries the middle's blockage through.
  • The refusal arm. A batch of two whose second node declares an input file the repository does not hold is refused by the queueing call itself, and the section that node names is absent from the live requests afterwards — the refusal wrote nothing.

The negative control

The declared mutation is the one line that matters: advance_waiting_requests computed a target from resolve_waits, and the control replaces that target with QUEUED_PHASE outright. Readiness is then never re-read, every waiting request is released the moment the pass looks at it, and the chain launches out of order. Both the ordering test and the blocked-arm test go red on that mutation — the ordering test on the assertion that only the head has no unmet wait, the blocked arm on assert launched == [] where two prompts were launched — against a head arm in which the same module fails nothing. That is the defect this node exists to close, and the control confirms the test detects it rather than merely passing.

Repair round: the hold is reached from the command that queues

The first attempt built the hold and the pass that releases it, and left the hold unreachable: nothing in production called it, so a dispatched node could never enter awaiting-upstream and only a test could. A dispatch that records a queued request now writes the hold itself. That is both places a dispatch stores one — the local lane's allowance check, and the yield to a session's older queued request — so the entry point is the command a coordinator runs rather than a helper behind it. The refs are read from the plan the node names, the same declaration the pass re-reads, so a wait is never stated twice.

Two further changes came with it. A request held on its refs is listed on its session's duties view: the view reads the phase from the pointer and the refs from the pointer, rather than the classification word, because that word is built from a phase vocabulary the view does not own and has not yet learned these two phases — a held request was therefore real, released on time, and drawn nowhere. And the section ref is now parsed by the repository's own reader (reckon._schema.parse_plan_ref, which the roadmap and the ledger already share) instead of a local split, so two spellings of one ref compare equal here as they do elsewhere, including in the match against a blocker row the roadmap reports.

Re-review round: the hold depends on the waits, and on three kinds of them

The hold was written only inside the local lane's held branches, so a node whose section's waits had not landed launched at once whenever its lane had room — the case the hold exists for. A dispatch now asks what the node's waits resolve to before it launches anything (queue_admission.unmet_waits, sited ahead of the launch path in reckon/crew/dispatch.py) and stores the request awaiting-upstream itself, so the waits decide the hold and the lane state does not.

A wait is now any of the three kinds a section may declare. The kinds are spelled apart rather than guessed from a ref's shape (wait_ref_kind): a bare ref is a section, gate: names a gate, and run: names another queued request by its run id. A gate wait is resolved through the roadmap's own gate edges — the blocker rows that derivation reports on the gated section — rather than by re-parsing the plan's gate records. A request wait is read from that request's own pointer and manifest: one still in flight cannot release the wait behind it, a delivered one can, and a discarded or failed one blocks it.

The admission pass no longer takes a moment argument its body never read. One arm per wait kind now stands in the node's module: a section ref holds until that section lands, a gate ref holds until the section the gate names lands.

Third round: the waits are read before the lane is consulted, and both phases are drawable

The hold was sited after the lane-allowance branch, so it answered a dispatch whose lane was already known to be full and never one whose lane had room. It now sits where the lane has just been resolved and before any branch that is taken for a lane's sake, so there is no path to a launch that reaches the lane without having read the node's waits. The two calls the move replaces are gone: the lane-allowance branch and the yield-to-an-older-request branch store a request that waits on the slot it lost and on nothing else, because a node with an unmet wait never reaches either.

The store, not the answer. The earlier site reported a hold without writing one. The request it had just stored kept phase: queued, so the pointer read as a request that could launch, and only the answer the command returned named awaiting-upstream. The site now moves the pointer through queue_admission.hold_request_for_upstream, the same writer the admission pass reads back, so the phase and the refs the answer names are the phase and refs the pointer carries; a store the writer cannot move is reported as the phase it really holds. That defect is what made the free-lane arm fail, and it is why the arm is a check on the file rather than on the reply.

The free-lane arm, and its discriminator. Two arms now stand where one did. The first configures the session with slots to spare (session_slots: 4) and declares a wait: the node is stored awaiting-upstream carrying its ref, and no process is started. The second runs the same fixture, the same lane and the same route with no wait declared, and the node is not stored in a waiting phase — so the arm measures the wait and not the fixture. Neither assertion can pass by accident: the first reads the pointer's phase and the second reads the same pointer for its absence.

The watch line learns both names. A request stored and not launched was previously classified by falling past the queued arm into whatever the rest of the classifier made of a phase it did not know. The classification is now read from the pointer's own phase, the phase-to-verb map carries both names (wait for a wait that time releases, decide for one that nothing will), and the unreleasable phase counts as a duty while the releasable one does not. Two arms in the node's module read the classification of each phase and the map beside it.

Fourth round: the hold reads only what has not launched, and the phase words live in one leaf

What was wrong. Moving the wait read ahead of the existing-run guard made a worse defect than the one it fixed. A re-dispatch of a node whose waits read unmet wrote the waiting phase over whichever pointer carried that node, and the writer did not look at what it was writing over. A run already starting or working is not a stored request at all: it is the record of a launch that happened. Overwriting it took a live run off its lane and re-stored it as a request that nothing was running, and no pass would launch it again.

What the hold reads now. The existing run is resolved first, and the waits are read only for a node that has no run at all or whose run is still a stored request. A node whose run is queued, being admitted or working is answered with that run exactly as before, and its pointer is never touched. The writer refuses any pointer whose phase is not the queued one or one of the waiting ones, and it reads that phase inside the mutation that writes, under the pointer's own lock, so a run admitted between the caller's read and the write is refused too. The refusal is not silent: the hold reports that it did not land, and the answer reports the phase the pointer really carries rather than a wait it does not have.

One leaf for the phase words. The admission pass writes the waiting phases and the recovery readers draw them, and neither could import the other: naming them through reckon/crew/queue_admission.py from the recovery vocabulary cycles through dispatch_plan and recovery and fails at import, which is why an earlier round restated them as literals. The queued phase and the two waiting phase names now live in reckon/crew/node.py, the leaf both modules already import — the admission module re-exports them, so every existing caller is unchanged, and no reader spells a phase out.
