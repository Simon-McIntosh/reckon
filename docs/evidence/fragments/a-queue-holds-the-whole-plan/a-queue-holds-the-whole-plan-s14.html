A drain week read from the records, and the guarantees those records cannot answer

What changed. The operational drain had no instrument, so none of the section's nine measures could be read at all. This node adds one: reckon/crew/drain_measure.py measures each guarantee from the records a finished run leaves behind, and scripts/measure_queue_drain.py gathers those records — the ledger, the admission verdict log and the drain view — across every project, prints one JSON report and draws the figure beside it. The module is deliberately plain data: a guarantee whose records do not exist reports unmeasured with the name of the record it needs, never a zero.

The reading. A real seven-day window, 2026-11-15T07:54Z to 2026-11-22T07:54Z, over the durable ledgers of reckon and imas-ambix: 2,194 runs launched or landed in it. This is not yet the drain the section describes — no coordinator has queued the two plans' remaining width in one beat, and the project weights are 1:1 rather than 3:1 — so the numbers below describe a normal week of the queue as it actually ran, with the gap named in each measure. The loading beat is recorded as not performed, which is itself a result: at measurement the drain view listed 119 unloaded sections across 2 plans (reckon 124 executable sections remaining, imas-ambix 49), and the live queue held 37 requests (reckon 33, imas-ambix 4).

The seeded control. A plan comment requires the drain instrument to report exactly the one seeded DAG-order violation and nothing else. test_a_launch_before_its_upstream_landed_is_the_one_seeded_violation seeds exactly one, and the measure returns violations: 1 naming that run while a correctly ordered pair beside it is not counted. The fourteen violations in the real week are therefore not a trigger-happy measure; they are what the week recorded. Two of them wait on a section that never landed at all (the-escape-lane-and-reviews-keep-pace#s2, workers-spend-fewer-tokens-per-landed-node#s17), and ten are two review runs that covered the-monitor-reads-each-fact-once §104–§108 while those sections had not landed.

Two instrument defects, found and fixed before this reading. The first measure returned 132 violations. The cause was in the measure, not of the queue: landing moments were computed from the seven-day window only, so an upstream that landed before the window read as "never landed" in 44 of 50 sampled rows. It now resolves upstreams against the whole ledger, and a regression test covers that case (test_an_upstream_that_landed_before_the_window_is_not_a_violation). The second: the figure's text check refused to write a figure because a top tick label sat outside the canvas — but the label belonged to a tick beyond the view limits, which is never drawn. The check now considers only ticks inside the view limits. An implausible result was treated as a claim about the instrument, which is what it was.

Every cross-project wait in the pair. The two projects' plans declare 822 section waits, 11 of them cross-project, including imas-ambix:local-lane-admission-control §27 waiting on reckon:a-queue-holds-the-whole-plan §4. The measure resolves a project:plan#section reference against the other project's runs, so a drain that carries a cross-project wait is measured rather than skipped.

Defects the reading exposed

Each needs its own section in this plan or a named successor. This node cannot write docs/plans/, so they are recorded here for the coordinator to file.

  1. A launched request loses the steering state the drain acted on. Priority override, queue hold and steering digest are dropped when the run launches, so three of the section's measures cannot be answered after the fact. Either the run record carries the pointer's steering fields at launch, or the verdict log keeps per-request history rather than a pointer snapshot.
  2. The admission verdict log is not kept for the window it is read over. It spans about 37 minutes here, so a silence measure can only be answered for the covered span. The log needs retention at least as long as a drain's measure window, or the measure must name the span it actually covers rather than the drain's.
  3. Project weights are undeclared. All six projects resolve to 1.0, so a 3:1 drain would silently run 1:1. The loading beat has to write the weights before it dispatches.
  4. Fourteen launches beat their upstream, two of them waiting on a section that never landed. A stale declaration and a genuine release are different defects and both appear here; the two "never landed" pairs read as stale section waits.

The evidence. The gate is tests/test_the_drain_measures_its_own_week.py: 17 tests, all passing, covering the seeded violation, the pre-window upstream, the cross-project wait, the healthy verdict control, the log that opens inside its window, and the unmeasured arm of every measure. The report and the run log live beside the run's other records, and the figure is drawn by the same script so it cannot drift from the numbers it illustrates.
