A landing refused under one rule is judged again when that rule changes

What changed. land_once in reckon/crew/queue_landing.py skipped any run whose current head already carried an admission_landing attempt, so a run refused under one acceptance rule was never judged under the next one. When the score floor left the acceptance rule on 28 October, the five runs it had already refused kept that refusal and the pass reported nothing for two hours. A second silent exit sat beside it: the delivered head was compared against the whole last manifest_commits entry, so an entry carrying its subject or three space-joined revisions matched no head and the run was dropped with no record at all.

The refusal keeps what made it. _record_attempt now writes two stamps beside the head, guard and status. code_stamp is the content identity of the code the pass runs from (_landing_code_stamp, through the same follower_code_stamp the admission service uses for its own reload decision), and review_stamp is a digest of the review record the judgement read (_review_stamp). Both are written on every refusal, the interrupted-attempt record and the pre-landing attempting record alike.

The skip is conditional. A refused attempt at this head is skipped only while _refusal_holds finds both stamps unchanged. A stamp that cannot be read, and a refusal recorded before stamps existed, matches neither, so such a run reaches the acceptance judgement once more — which is how the six runs held by the retired rule are released without an operator touching the store.

The delivered head is parsed. _delivered_revision reads the last entry as the last token that spells a hex revision (_REVISION_TOKEN, seven to forty characters, not part of a longer word), so 82f3a3bdc docs(evidence): record the section-wait repair and fe3d85589 be1c86dd5 229f3fcde each reach the worktree head rather than being compared whole.

Measure. The gate command PYTHONPATH=. .venv/bin/python -m pytest -p no:cacheprovider -q tests/test_a_refusal_is_judged_again_when_it_changes.py reports 5 passed, EXIT=0. Against the base module the same five tests report 4 failed, 1 passed, EXIT=1, the one pass being the unchanged-refusal arm, which is behaviour the old pass already held. The declared negative control — restore the skip on any attempt at the same head — reports 2 failed, 3 passed, EXIT=1, and the first arm (test_a_refusal_under_an_old_rule_is_judged_again_when_the_code_moves) is among the failures. The three test files that already import reckon.crew.queue_landing report 37 passed at the base module and 37 passed plus the new file's five at head, so the change adds no failure outside its own gate.

Scope. One behaviour in one module: the skip, the stamps it compares, and the manifest entry it parses. A conflict refusal keeps its own guard and is unaffected; whether a cleared conflict should also release a refused head is a separate question this change does not answer.
