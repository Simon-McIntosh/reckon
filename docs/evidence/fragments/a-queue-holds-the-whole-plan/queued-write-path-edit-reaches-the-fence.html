A queued write-path edit reaches the landing fence

What was wrong. A request held for plan review carries section_derived marks naming the fields its section supplied. The admission pass releasing it re-derived those fields from its own in-memory snapshot of the live pointers — taken at the start of the pass — and wrote the result onto the pointer it was releasing regardless of what the pointer itself said. A coordinator who had run crew queue edit --write-path between the snapshot and the release lost the path: the section's list replaced it and the field was re-marked as the section's, so every later release repeated the loss. The landing scope check then refused a path the coordinator had declared before the run ever started, which is the refusal the reported run met.

The repair. The release re-derives inside the pointer's own lock from the record it is about to write, so the pass reads the request fresh rather than through its snapshot, and it adopts the written node onto its in-memory record so the launch carries the released contract. Re-deriving a field now also requires the pointer being written to still mark it: a mark the queue writer cleared is what makes the field the coordinator's, so it is never re-derived, while a field the section still supplies is re-derived and stays marked. A section that cannot be read raises the release's own refusal, which keeps the request held and records the reason in its hold exactly as before.

The measure. tests/test_a_queued_write_path_edit_reaches_the_landing_fence.py holds three cases. The first queues a request, widens it with queue_edit.edit, launches it through queue_admission.admit_once with a stub worker that commits the added path, and asserts the added path is in the launched record's declared scope, that promotion_scope._outside_declared_scope names nothing outside the fence, and that declared_write_grants holds it as a claim. The second snapshots a held request as the pass does, edits its write paths, releases it from that stale snapshot, and asserts the added path survives, the field stays unmarked, and the pass's in-memory record carries the written node. The third releases an unedited held request and asserts the section's field is still re-derived and still marked, so the fix does not disable the re-derivation it repairs.

Evidence at two revisions. The reproduction. Before any repair, reproduction-stale-release.log drove the real _release_plan_review_holds over a held request and showed the edit surviving the queue edit — three write paths, write_paths unmarked — and gone again after the release, with the mark restored. That is the mechanism this node's brief only suspected, and it is what the second case now fences.
