Admission chooses the project for each freed slot by weighted fair use

What changed. The admission pass no longer launches whichever project's request happens to come first. It ranks the queue by the roadmap order it already had (queue_order.admission_order, which keeps priority, ageing and reviews inside a project), then interleaves that ranking across projects by weighted deficit round robin: weighted_project_order in reckon/crew/queue_admission.py. Every project still holding a request accrues its weight each round, the largest deficit is served next and pays the round's total, and it contributes its own highest-ranked request. A project whose queue runs dry accrues nothing, so it cannot sit on a share it can no longer use.

Where the weights live. queue.project_weights in flight configuration, read by flight.project_weights in reckon/flight.py. A project the configuration does not name — and every project when the key is absent — carries the equal default 1.0, and flight.fair_use_weights_configured tells the pass whether any weight is declared at all. With none declared, the pass keeps exactly the order it had, so an install that never sets weights is unaffected.

The allowance becomes lane-wide. _dispatch_lane_allowance and _lane_worker_allowance in reckon/crew/dispatch_plan.py take weights_configured. When it is set they skip the router's admission.sessions map — both this session's entry and the new-session figure — and read the lane-wide admission.worker_slots, because the split between sessions is now reckon's setting rather than the router's. The dispatch path passes the flag from the resolved config it already holds; the admission path passes it from the per-project config it resolves for the request.

Reading a weight from any project's config. Each project resolves its own configuration, so the pass merges only the weights those configurations actually declare — first declaration wins — and applies the equal default once at the end. Merging completed maps instead would let whichever project came first in the queue fix every other project at the default, which is what a declared 3:1 split did whenever the declaring project was not first: the split silently ran 1:1. flight.declared_project_weights returns the declared map without filling defaults, which is what makes the two distinguishable.

The measure. Two projects, 100 ready requests each, with the ordering the pass uses: weights 3:1 launch 60 / 20 in the first 80 admissions (exactly 3:1), and equal weights launch 40 / 40. A project with one ready request against another's nine takes its single slot and then leaves every remaining slot to the other, and priority order inside a project is unchanged by the interleave. Seventeen tests carry the behaviour, three of them the cross-config declaration: the same 60 / 20 split holds when only the project queued second declares the weights.

The delta. Both arms run the same 144 test files — every one importing queue_admission, dispatch_plan or reckon.flight — each from its own tree with that tree's module imported (module.__file__ recorded in the log header). Not yet declared by the schema. reckon/schema/flight.yaml (and its generated _flight_schema.py and docs/_shared/flight.schema.json) is another node's write scope, so the queue namespace and its project_weights slot are not declared there yet. Strict layer validation refuses an undeclared key, so a configuration that sets weights reads them here but is refused by reckon flight until that slot lands. It is recorded as an out-of-scope finding for the coordinator.
