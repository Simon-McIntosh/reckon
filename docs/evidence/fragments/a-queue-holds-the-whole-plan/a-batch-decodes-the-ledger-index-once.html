A batch decodes the ledger index once

Every entry of a batch read the same project's ledger to decide what was already promoted, what each section still waited on and what its lane had cost, and each read rebuilt and decoded the whole stored index. The costs therefore multiplied: an eight-entry review batch at a live history spent about 21 percent of its profile inside ledger.load, split across _index_payload (17 percent) and _last_good_index_data (10 percent) with _indexed_data.update at 11 percent, one decode per entry.

A batch now opens one ledger.index_reuse() region around the batch call and holds it for the whole batch. Queueing writes no ledger row, so nothing inside the batch can invalidate what the region holds, and the region is dropped when the batch returns. Inside that one region a second ContextVar holds the decoded payload itself, keyed by the index file, the projection options and any activity bound, so two read shapes of one index — the roadmap's picker projection and the readiness read's full record — share a single decode; the picker projection is derived from the shared payload rather than decoded again. The trade is paid at the column: inside a region a picker-only read decodes the full payload column instead of the leaner picker column, because the held record has to answer the full read shape as well, so a read that only ever asks for the picker projection is slightly more expensive in a region than on its own. The last-good index reader returns a shallow copy, so a caller's age stamp cannot leak into the shared payload.

The gate, tests/test_a_batch_decodes_the_ledger_index_once.py, builds a crew home whose ledger holds 200 rows and dispatches ten entries over three plans, every section waiting on a section another plan declares done. It counts calls to _index_payload and _last_good_index_data and requires each at most once for the ten entries. Two parity arms show the change alters cost and not results: one dispatches the same batch with the region removed, and the other extracts the base revision's own tree from this checkout's history and runs the same entries through it in its own interpreter, so the comparison is against the code the change replaces rather than against this revision with a switch turned off. The two arms queue the same entries with the same per-entry status, plan, section and declared waits.

The negative control is the declared mutation: with the region taken out of the batch, each entry decodes the index for itself. The ten-entry batch reports AssertionError: the whole batch decodes the stored index at most once: 11 decodes over 10 entries and 1 failed, EXIT=1. The head arm ran the fence command over tests/test_a_batch_decodes_the_ledger_index_once.py and tests/test_staged_write_inventory.py: 55 passed in 23.04 s, EXIT=0, run on the all_debug partition; the base arm at the base revision content ran the file set that exists there, tests/test_staged_write_inventory.py: 51 passed in 10.55 s, EXIT=0. No failure is added.

The measured batch shape was eight review entries over two plans, run on the all_debug partition against a home seeded at the 10,300 ledger rows the live ledger held when the node was dispatched. With the region the batch took 0.477 s in total, 0.060 s per entry at load average 4.31; with the region removed it took 0.760 s, 0.095 s per entry at load average 4.53. The measured ratio is 1.59 in favour of the shared decode for this batch shape, and it is reported rather than gated.
