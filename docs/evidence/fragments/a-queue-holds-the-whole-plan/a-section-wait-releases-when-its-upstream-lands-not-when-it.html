A section wait releases when its upstream lands, not when it is declared done

The defect

A declaration of done is not a landing. A coordinator marks a section done in the plan and commits that immediately before crew complete --land, so between the two the plan reads done while the section's revision is still off the registered checkout's HEAD. Every route that released waiters read the declaration alone, so a request waiting on that section could launch onto a base without its upstream code.

Reproduction at the base revision. The new test file run against bc6d7fd9f1306f21d21daa58f44f235265e6cca3 reports 2 failed, 1 passed, EXIT=1. Both failures are the same assertion: a waiter on a section that is declared done, whose run has delivered and whose head is not in HEAD, reads queued where it must read awaiting-upstream (assert 'queued' == 'awaiting-upstream').

The change

One derivation, every route. _section_run_unlanded in reckon/crew/queue_admission.py answers whether a run of one section has delivered or been promoted and is not landed. A section declaration of done releases only when it answers no. It is consulted from the three places a section ref is resolved — _ref_state, _section_readiness_state and the dispatch fast path _dispatch_nonrun_wait_state — and that one derivation already serves the admission pass, a promotion's own release and a dispatch's queue-time check, so all three reach the guard.

What is read. Promotion removes the live pointer and then records the revision, so in production the project ledger is the only record of a promoted run and the pointer branch never decides. The guard asks the queue's own derivation — runs._unloaded_sections, which names declared work with no live request and no reachable promotion — whether the section is still unloaded, and keys sections by section_record_id, the one identity every spelling of a section resolves through. The live pointers are read too, for the window between delivery and promotion, where a run whose pointer phase is dead or whose discard is recorded holds nothing and a delivered run holds.

What still releases. A section declared done with no run at all, such as one completed by hand, releases its waiters at once, and a discarded run stops holding the moment its discard is recorded.

A landing that cannot be read is unknown, not absent. Two records can be missing, and each holds the wait rather than releasing it. A ledger that cannot be read says nothing about what was promoted. A project no mount names offers no HEAD to compare against. In both cases releasing would put a waiter onto a base the queue cannot show carries its upstream, which is the answer the request-ref path already gives a run whose record or project it cannot find. The unregistered-checkout hold applies only once a run of the section exists, so the release of the no-run case above is unchanged.

The index was checked, not assumed. A warm index is keyed on the project's write generation, which every ledger write path bumps, so a read made after a promotion is answered by an index that already carries it. A case warms the index while the section is still unlanded, promotes, then asserts that the index now carries the promoted revision and that the guard still holds — so an index built before the promotion cannot be what releases the wait. Flipping the read to use_index=False leaves every case green, which is what established that the index was not the cause of the failure reported against a clean tree; the read therefore stays indexed, which is also the cheaper of the two.

Cost. The ledger rows are read once per project per pass and kept in the readiness cache beside the plan rows, and the drain's own derivation — which reads the ledger itself — has its answer kept for the pass too, so a release tick pays one read and one derivation rather than one of each per waiting request.

The measure

Gate. PYTHONPATH=. .venv/bin/python -m pytest -p no:cacheprovider -q tests/test_a_wait_releases_when_its_upstream_lands.py tests/test_staged_write_inventory.py reports 58 passed, EXIT=0 at the head, run on the all_debug partition in a fresh tree with the suite's TMPDIR inside that tree, which is the layout the fixture now answers. The base arm of the same template, resolved over the base tree where the new file does not exist, reports 51 passed, EXIT=0: the six added tests are the only difference and no base failure is added.

Cases. The first test drives the whole sequence: a delivered run off HEAD holds its waiter through an admission pass, and keeps holding through the promotion's own release once the pointer is removed and the ledger is the only record, and the waiter is released once the delivered head is merged into HEAD. The second discards the delivered run and shows the waiter released. The third makes the ledger unreadable once its run has delivered and shows the waiter held. The fourth removes the project's registration and shows the waiter held. The fifth declares a section done with no run at all and shows the waiter released at once. The sixth warms the ledger's index before the promotion and shows the waiter held after it, because the write moved the generation the index is keyed on and the index therefore carries the promotion rather than a view of the moment it was built. The seventh is the layout case: it moves TMPDIR inside the fixture's checkout, confirms that path lies inside a work tree, and asserts that the ledger still resolves its own checkout, still reads the promotion it wrote, and still holds the wait. That is the case that fails when the read escapes, and it is what the earlier head failed on a host whose temp path sat inside the tree.

The test owns everything it reads. Four inputs can resolve outside the fixture, and each one is pinned and then asserted rather than assumed. The mounts registry outranks the config home wherever both are consulted, so a host that exports RECKON_MOUNTS_PATH would leave the fixture's repository unnamed and the guard would read another tree's HEAD; it is pinned at the fixture's own mounts.json. The configuration home, the state root and the pick cache are pinned inside the fixture. The state root is the fixture checkout's own docs/state, which is the path the ledger's work-tree resolution re-roots to, and the ledger's path is asserted to be inside the checkout and its resolved work tree to be that checkout. HOME and the XDG directories are pinned to the fixture's temp path as well, so nothing falls back to the invoking user's live configuration. The fixture then asserts that project_mount_repository resolves the checkout it built. After the promotion each test names the ledger row the guard must read and calls _section_run_unlanded directly, so a tree where any of these resolves elsewhere fails at the component that decides rather than as a phase assertion further down.

A temp path inside a work tree. The failure reported against a head that passed in this worker's own runs had one cause, and it was neither the index nor the write generation nor the guard. The ledger resolves the git work tree above its own path and reads a project's runs through that tree's checkout, so a suite whose temp tree sits inside the tree under test — a basetemp beneath the checkout, which a run from a freshly extracted tree produces — had every ledger read answered from that tree while the fixture's promotion wrote under its own state root. The read came back with no runs at all, which is what both reported failures asserted.

The cure, and a cure that is not one. Bounding git's own discovery does not reach this: the ledger finds the tree by reading a .git marker in each ancestor directory, never by asking git, so GIT_CEILING_DIRECTORIES leaves the walk unchanged. That was measured rather than reasoned: with the variable set at a temp root inside a checkout, the resolved work tree is still the enclosing checkout (shared → …/Code/reckon). The variable is set in the fixture all the same, because it does bound the git subprocesses the fixture and the ancestry check start, but the boundary that fixes the read is nearer. The walk's answer is the nearest ancestor carrying a marker, and the path it then reads is <tree>/docs/state/<project>/<ledger>; so the fixture makes its own checkout a repository, which is the nearest marker, and points the ledger's state root at that checkout's own docs/state, which is the path the resolution reads. Written and read are then one file wherever the temp path sits, with no relocation and no dependence on a writable directory outside the tree. The round trip in the fixture asserts it on a project name of its own, so an escaping read fails at the fixture instead of surfacing as a phase assertion further down.

Fresh trees. Runs of the gate command in a tree of their own report 58 passed, EXIT=0 at the head with TMPDIR inside that tree, 57 passed, EXIT=0 at the same head in the ordinary layout, and 56 passed, EXIT=0 at the revision whose failure was reported, the latter with the host's real mounts registry exported and the fixture's config home unset, which is the hostile case the pinning exists for. A literal git worktree add cannot be created from this worker: the main checkout's .git is read-only here (git worktree add fails with could not create directory of …/reckon/.git/worktrees/…: Read-only file system), so each fresh tree is the revision extracted into a new directory, made a repository of its own, with the shared .venv symlinked in — log fresh-tree-head.log, and repro-224-hostile.log beside it. The one read whose answer could depend on which tree is asking was the ledger index, and it is gone: the guard reads the run rows through an index keyed on the write generation.

Negative control. With _section_run_unlanded made to answer False — the declaration alone releasing — the same six tests report 5 failed, 1 passed, EXIT=1, failing every case that holds. The guard is load-bearing: without it the first case releases before the merge, which is the defect the section reports.

The ledger branch is the one that decides. A second control removes only the _unloaded_sections branch and runs the same six tests: 2 failed, 4 passed, EXIT=1. Both failures are the cases that hold through the promotion — the one that drives the sequence and the one that warms the index before it — and both fail at the point where the pointer has been removed and the promotion has recorded its revision. The branch production takes is therefore exercised by the test rather than merely present beside it.

Regression. Six queue tests carrying dependency waits, discards, holds and the drain (test_a_queued_request_waits_on_its_dependencies, test_queue_dag_waits, test_a_released_request_takes_the_sections_current_contract, test_a_discarded_request_stays_discarded, test_a_held_request_stays_queued, test_drain_lists_unloaded) report the same result at the base revision and at the head: 30 failed, 38 passed, with the failing id sets identical. Those 30 failures predate this change and are not reached by it; the delta is zero.
