A section wait releases when its upstream lands, not when it is declared done

The defect

A declaration of done is not a landing. A coordinator marks a section done in the plan and commits that immediately before crew complete --land, so between the two the plan reads done while the section's revision is still off the registered checkout's HEAD. Every route that released waiters read the declaration alone, so a request waiting on that section could launch onto a base without its upstream code.

Reproduction at the base revision. The new test file run against bc6d7fd9f1306f21d21daa58f44f235265e6cca3 reports 2 failed, 1 passed, EXIT=1. Both failures are the same assertion: a waiter on a section that is declared done, whose run has delivered and whose head is not in HEAD, reads queued where it must read awaiting-upstream (assert 'queued' == 'awaiting-upstream').

The change

One derivation, every route. _section_run_unlanded in reckon/crew/queue_admission.py answers whether a run of one section has delivered or been promoted and is not landed. A section declaration of done releases only when it answers no. It is consulted from the three places a section ref is resolved — _ref_state, _section_readiness_state and the dispatch fast path _dispatch_nonrun_wait_state — and that one derivation already serves the admission pass, a promotion's own release and a dispatch's queue-time check, so all three reach the guard.

What is read. A delivered run keeps its live pointer until promotion removes it, so the pointers are read first: a run whose pointer phase is dead or whose discard is recorded holds nothing, a run carrying a promoted revision holds nothing when that revision is an ancestor of HEAD, and a delivered run with no promoted revision holds. A promoted run whose pointer is gone is read from the project's ledger, which is where promotion records its revision. The landed test is the queue's own — _revision_is_ancestor(checkout, revision, "HEAD") — so a section ref and a run ref now answer the same question the same way.

What still releases. A section declared done with no run at all, such as one completed by hand, releases its waiters at once, and a discarded run stops holding the moment its discard is recorded.

A landing that cannot be read is unknown, not absent. The landed test reads the project's registered checkout, so a project no mount names offers no HEAD to compare against. The guard holds the wait in that case rather than releasing it, which is the answer the request-ref path already gives a run whose project no mount names; the hold applies only once a run of the section exists, so the release of the no-run case above is unchanged.

Cost. The ledger is read once per project per pass and kept in the readiness cache beside the plan rows, so a release tick pays one ledger read rather than one per waiting request.

The measure

Gate. PYTHONPATH=. .venv/bin/python -m pytest -p no:cacheprovider -q tests/test_a_wait_releases_when_its_upstream_lands.py tests/test_staged_write_inventory.py reports 55 passed, EXIT=0 at the head, run on the all_debug partition. The base arm of the same template, resolved over the base tree where the new file does not exist, reports 51 passed, EXIT=0: the four added tests are the only difference and no base failure is added.

Cases. The first test drives the whole sequence: a delivered run off HEAD holds its waiter through an admission pass and through the promotion's own release, and the waiter is released once the delivered head is merged into HEAD. The second discards the delivered run and shows the waiter released. The third removes the project's registration once its run has delivered and shows the waiter held. The fourth declares a section done with no run at all and shows the waiter released at once.

The test owns the checkout it reads. The mounts registry outranks the config home wherever both are consulted, so a host that exports RECKON_MOUNTS_PATH would leave the fixture's repository unnamed and the guard would read the host's HEAD. The fixture pins the registry at its own mounts.json and asserts that the guard resolves the checkout it built. The file therefore passes in any tree: a fresh tree of the head revision, with the host registry exported, reports 4 passed.

Negative control. With _section_run_unlanded made to answer False — the declaration alone releasing — the same four tests report 3 failed, 1 passed, EXIT=1, failing the first, second and third cases. The guard is load-bearing: without it the first case releases before the merge, which is the defect the section reports.

Regression. Six queue tests carrying dependency waits, discards, holds and the drain (test_a_queued_request_waits_on_its_dependencies, test_queue_dag_waits, test_a_released_request_takes_the_sections_current_contract, test_a_discarded_request_stays_discarded, test_a_held_request_stays_queued, test_drain_lists_unloaded) report the same result at the base revision and at the head: 30 failed, 38 passed, with the failing id sets identical. Those 30 failures predate this change and are not reached by it; the delta is zero.
