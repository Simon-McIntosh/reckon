A waiting request can be edited, re-ranked and dropped before it launches

What changed. Three verbs now act on a request that has not launched: reckon crew queue edit, reckon crew queue reprioritise and reckon crew queue drop. The operations live in a new module, reckon/crew/queue_edit.py, so the CLI verb and the MCP action call one implementation rather than two that could drift.

Edit. An edit replaces the request's steering.md in its own run directory and any of its done_when, write paths, time budget or route. The edited node is judged by the dispatch's own validate_node — with the decisions the original dispatch recorded as locked — before anything is written, so a refused edit leaves the request byte-identical. A route is a named route: it passes the same --backend and --model checks a dispatch applies, and a model the named lane does not declare is refused by the catalogue's own resolver. The chosen backend, lane and model key are recorded on the pointer under named_route, with route: deterministic in the request's dispatch options.

Reprioritise. The verb stores priority_override (with its reason and the instant it was set) on the request, so every later ranking pass reads the coordinator's intent from the request rather than from a session's memory. The roadmap key the request otherwise ranks by is untouched beside it.

Drop. A drop is the discard's own removal path, reached only for a queued or awaiting-upstream request, so the departure is recorded where a later reader looks for it and any worktree a launch left behind is released by the audit a discard uses.

The launched boundary. All three verbs refuse a pointer whose phase is no longer waiting, naming the phase it holds. The check runs again under the pointer's own lock immediately before the write, because a request can launch between the first read and the lock, and an edit that slipped in there would change a brief a worker is already reading.

Measured

tests/test_queue_verbs.py (15 cases) drives every claim above: the steering file and node fields are replaced; an edit that fails its contract is refused and stores nothing; a named route lands as named_route beside backend, lane and model_key; a model outside the named lane is refused; edit, reprioritise and drop each refuse a working pointer; an awaiting-upstream request is still editable and droppable; the priority override and its reason are stored; and each of the three MCP actions returns the document its CLI verb returns for the same call.

Each was run per file in that base tree and in this branch, with the same interpreter and the same caps. Eleven pre-existing failures stand in the base arm — two in test_a_lane_change_keeps_its_waivers.py, four in test_crew_lane_change.py, four in test_read_verbs_retire_behind_crew_view.py and one in test_crew_tool_carries_the_write_verbs.py — and the identical set stands in the branch arm: no failure is added. The new tests/test_queue_verbs.py passes its 15 cases in the same interpreter.

What the 121-file sweep did not settle. Every test file importing reckon.mcp is 121 files, and sweeping all of them was attempted twice and did not complete inside the attempt's time fence: the parallel form was abandoned because tests here terminate child processes and killed their own workers, and the serial form reached roughly a fifth of the population before the harness stopped it, so neither left a usable arm. The five files above are the subset that exercises the tool surface this branch changes; the rest were not measured, and the zero delta is claimed only over what was run.

Negative control. With the launched-request guard made to return early for edit alone, exactly one arm fails (test_a_launched_request_is_refused_by_every_verb[edit], which then reports the edit landing on a working pointer) and the other fourteen pass, so the edit guard is what holds that arm. Removing the early guard for all three verbs fails the edit and reprioritise arms while drop still refuses, because its check runs inside the removal's lock; and removing that in-lock check in turn fails exactly the launch-race arm, whose own output shows the pointer removed at phase working. Logs: logs/negative-control-edit-only.log, logs/negative-control.log and logs/negative-control-drop-lock.log under the run directory.

Reachable through the crew MCP tool. The crew tool declares the three actions and the parameters they take, and forwards them to the same implementation the CLI verb calls. A test calls each one through the tool and compares the answer with the CLI's answer for the same call, so the two surfaces are held together by comparison rather than by an assertion about either.

Drop's launch race. The check a drop makes before it reads the queue is not the one that protects the removal: the removal itself takes the phases it will accept and tests the record it re-reads under the pointer's own lock, so a request that launches in between is refused instead of removed. An arm launches the request exactly in that window, and the refusal names the phase it found.
