A waiting request can be edited, re-ranked and dropped before it launches

What changed. Three verbs now act on a request that has not launched: reckon crew queue edit, reckon crew queue reprioritise and reckon crew queue drop. The operations live in a new module, reckon/crew/queue_edit.py, so the CLI verb and the MCP action call one implementation rather than two that could drift.

Edit. An edit replaces the request's steering.md in its own run directory and any of its done_when, write paths, time budget or route. The edited node is judged by the dispatch's own validate_node — with the decisions the original dispatch recorded as locked — before anything is written, so a refused edit leaves the request byte-identical. A route is a named route: it passes the same --backend and --model checks a dispatch applies, and a model the named lane does not declare is refused by the catalogue's own resolver. The chosen backend, lane and model key are recorded on the pointer under named_route, with route: deterministic in the request's dispatch options.

Reprioritise. The verb stores priority_override (with its reason and the instant it was set) on the request, so every later ranking pass reads the coordinator's intent from the request rather than from a session's memory. The roadmap key the request otherwise ranks by is untouched beside it.

Drop. A drop is the discard's own removal path, reached only for a queued or awaiting-upstream request, so the departure is recorded where a later reader looks for it and any worktree a launch left behind is released by the audit a discard uses.

The launched boundary. All three verbs refuse a pointer whose phase is no longer waiting, naming the phase it holds. The check runs again under the pointer's own lock immediately before the write, because a request can launch between the first read and the lock, and an edit that slipped in there would change a brief a worker is already reading.

Measured

tests/test_queue_verbs.py (13 cases) drives every claim above: the steering file and node fields are replaced; an edit that fails its contract is refused and stores nothing; a named route lands as named_route beside backend, lane and model_key; a model outside the named lane is refused; edit, reprioritise and drop each refuse a working pointer; an awaiting-upstream request is still editable and droppable; the priority override and its reason are stored; and each of the three MCP actions returns the document its CLI verb returns for the same call.

Negative control. With the launched-request guard replaced by a no-op, exactly the three refusal arms fail (test_a_launched_request_is_refused_by_every_verb[edit], [drop], [reprioritise]) and the other ten pass, so the guard is what holds those assertions. Log: logs/negative-control.log under the run directory.

Not reachable through the crew MCP tool yet. The three actions are registered in reckon/mcp_crew_actions.py and answer correctly through crew_action(), but reckon/mcp.py — outside this node's write scope — still declares the tool's action vocabulary and parameter list, so the tool surface cannot forward them until that file gains the three action names and their parameters.
