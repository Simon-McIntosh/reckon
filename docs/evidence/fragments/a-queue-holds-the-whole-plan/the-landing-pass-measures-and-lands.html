The landing pass measures the suite before it lands a run

A delivered implementation run is no longer landed on the run's accepted review alone. reckon/crew/landing_measure.py runs three readings before the landing: the run's armed command at the base revision and at the delivered head, the importer population (the test files importing each module the change touched) at both revisions in parallel with -n 8, and every test id that fails at the head and not at the base, re-run alone three times at each revision. An id is a regression only when it fails at the head more often than at the base, so a flake that fails as often at base as at head does not hold the landing.

reckon/crew/queue_landing.py refuses to land a run whose measurement names a regression, raises one obligation naming each real id with its isolated base and head results, and otherwise lands the run and records the suite pair as the run's evidence. On a landing it also records the landing beat through the same edit_plan ops a coordinator uses: the node's evidence anchor in the cumulative landing record, the section's declaration set to done, and the c-close-<section> comment linking to the anchor.

A single id is re-run through the same command: the node's own test files — the ones the armed command was resolved from — are removed and the id appended, so the interpreter, any env or timeout wrapper, every option and its path value survive unchanged. An arm that cannot be started, or that exits non-zero without reporting the id, is unreadable and refuses the landing rather than reading as a failure at both revisions.

The step runs inside the admission loop, so it is bounded. Every measurement subprocess — the suite arms, the population arms, each isolated re-run and the base checkout's git worktree calls — carries a wall-clock timeout from flight config (landing.measure_timeout_seconds, default 600 s). A timed-out arm is unmeasurable: no failure id is taken from a partial log, the landing is refused and the run's obligation is raised. A pass measures at most one delivered run (the rest are deferred in delivery order), a measurement is stored per run and head and reused while the head is unchanged, and the base checkout is built under the fleet's own node-local scratch root (dispatch_launch.worker_scratch_root, which rejects a shared-storage TMPDIR) and removed on every exit path, including a checkout that times out. A removal that fails or exceeds its bound leaves the repository's worktree registration behind, so it is pruned with git worktree prune --expire now under the same bound; a stale entry would otherwise make a later checkout of the same path fail. A measurement that raises is reported as itself, not as a base checkout that could not be built.

Measured on the node's gate: fifteen tests pass against a test suite with stubbed repositories and commands, covering a clean population landing with its armed suite pair recorded, a flaky added id landing, a real added id refused with one obligation naming it, the landing beat ticking the section, a run whose review is not accepted left untouched, narrowing across --cov-config, env, timeout and a multi-file command, an unreadable arm refusing the landing, a measurement that exceeds its bound refusing the landing with no scratch tree left behind, a pass with three delivered runs measuring exactly one, and a second pass reusing the stored measurement of an unchanged head, a failed worktree removal leaving no entry in git worktree list, and a measurement error that keeps its own message. The importer population — every test file importing landing_measure, queue_landing or queue_admission — shows no added failure at the delivered head.
