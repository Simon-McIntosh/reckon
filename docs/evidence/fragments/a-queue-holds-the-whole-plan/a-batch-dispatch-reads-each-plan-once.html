A batch dispatch reads each plan once

A batch dispatch resolved its wait graph one entry at a time, and every entry and every wait edge re-read the plans it named. Each state lookup reached metadata_index.discovery_state, which stats the whole metadata index, and each section-naming wait edge re-parsed the target plan's authored headings through authored_section_headings. On 13 November a 109-entry batch ran at about 3.5 minutes per entry, 9 entries queued in 31 minutes, with the process in D state on GPFS; three py-spy dumps found it in _validated_batch_waits > section_edges each time.

The batch now holds one plan-read scope for its whole duration. dispatch_batch.queue_batch enters readiness.plan_read_scopes(), which already held one covered-tree observation and one metadata-index read per project for an admission pass; the batch therefore pays one discovery_state call per project rather than one per state lookup. Inside the same scope each plan document's text is read once (readiness.plan_document_text), and the batch's parse-once boundary memoises authored_section_headings on the document text, so the roadmap's heading walk and every wait edge naming a section of the same plan share one parse. The scope is entered once per batch and dropped at its exit, so a later reader still sees a changed plan.

The gate, tests/test_a_batch_dispatch_reads_each_plan_once.py, queues twenty entries over four plans whose sections wait on one another (a→b→d and a→c→d, so every entry resolves a foreign section and each walk steps through a further plan). It counts discovery_state calls and authored_section_headings calls and requires each at most the number of distinct plans: 2 state reads and 4 heading parses for four plans at the changed revision. It also asserts the twenty stored requests carry the same phases and the same declared waits — plan-a-s1 awaits plan-b#s1 and plan-c#s1 — so the shared read changed what the batch paid, not what it wrote.

The negative control is the base revision with the head test file: the same twenty entries report 1026 state reads for four plans, assert 1026 <= 4, 1 failed, EXIT=1. The head arm ran the fence command over tests/test_a_batch_dispatch_reads_each_plan_once.py and tests/test_staged_write_inventory.py: 52 passed in 13.70 s, EXIT=0. The base arm at the extracted base tree ran the same file set with the new test absent from that tree: 51 passed in 13.24 s, EXIT=0. The fourteen test files importing the changed modules ran 85 passed, 16 failed with EXIT=1 at both revisions over an identical failure-id set, so this node adds no failure. Receipts: arms/head.log, arms/base.log, arms/negative.log, arms/imports_head.log and arms/imports_base.log in the run directory.
