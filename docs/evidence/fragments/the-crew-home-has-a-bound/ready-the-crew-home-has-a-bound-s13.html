crew gc bounds the persisted memo store

The sweep and its measure

The persisted-memo store writes one file per memo identity under <config home>/cache/<kind>/<digest>-v<version>.json through metadata_index.persisted_memo, and nothing removed them, so every plan edit whose review persists a snapshot digest added a file holding whole prose. reckon/crew/gc.py now declares PERSISTED_MEMO_MAX_AGE_DAYS = 7 beside LEDGER_INDEX_UNRECORDED_MAX_AGE_* and sweeps metadata-index, plan-review-coverage and plan-review-snapshot-evidence in both the retention pass and the retention sweep. An entry is judged on its mtime, the last write _write_persisted_memo makes; a read never refreshes it, and a file a process holds or whose stat moved is left alone. Each removal is printed as removing persisted memo <path> (<n> bytes) and recorded in the pass report under persisted_memos.

The new test drives the real pass with a temporary config home. It writes one entry older than the threshold and one inside it: an applied pass leaves the recent entry, removes the aged one, and prints its path; a dry pass leaves both. The gc-importing test files show no added failure against base 3ddc28c71f — the base arm reports 4 failed, 356 passed, 2 errors and the head arm the same 4 failed ids, 360 passed, so the delta is zero. The two base-arm errors are the staged-write-inventory tests refusing an extracted tree with no git repository, and they do not occur in the head arm.
