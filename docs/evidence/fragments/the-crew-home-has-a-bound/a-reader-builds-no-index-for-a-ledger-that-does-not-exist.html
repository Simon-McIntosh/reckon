What changed

load() in reckon/ledger.py now takes the index route only when the ledger it would index holds something. The new private predicate _ledger_holds_content answers true when the aggregate docs/state/<project>/crew.json exists, or when at least one run record sits in the runs directory beside it. A ledger holding neither is read down the uncached path that _load_aggregate already answers with the empty roster at version 0.

Before the change a read of such a project resolved _run_index_path and opened SQLite, creating ~/.cache/reckon/ledger-<sha256>-v4.sqlite for a ledger that is not there. Those files are keyed to a path whose checkout does not exist, so gc classifies each as recorded-checkout-gone and nothing removes it until someone runs a sweeping --apply. Ten such indexes of 28 KB each appeared within an hour of the backlog reclaim for projects that never ran a worker.

The narrowing matters and is the one design decision this node made. A project may hold per-run documents under runs/ and no aggregate file at all; that ledger has content, and its index is kept. Skipping on the aggregate's absence alone broke four derivation tests, which is how the shape was found. A runs directory that exists and holds no record is the other side of the same rule: it is a shape, not content, and indexing it publishes the same artefact an absent ledger leaves. The first form of the predicate tested the directory's existence and so still indexed that emptiness; review caught it, and it is now a record count.

The gate

The gate is tests/test_a_reader_builds_no_index_for_a_missing_ledger.py, committed so the suite holds the rule rather than this record. Its four cases read:

  • a temporary project with no crew.json and no runs directory reads as the empty roster and writes no ledger-*.sqlite under a temporary cache root;
  • a temporary project whose runs directory exists and holds no record reads the same and writes no index;
  • a temporary project holding run records and no aggregate still builds exactly one index and returns the record;
  • a temporary project with a crew.json still builds its index.

Head arm: 4 passed, EXIT=0, the module resolved inside this worktree and its predicate recorded as glob (logs/head-gate.log).

Two negative controls, each a full archive of the head revision with one change applied and the committed test copied in. The old predicate — the runs directory's existence rather than a record count — turns the empty-directory case red: 1 failed, 3 passed, EXIT=1, failing test_a_project_with_an_empty_runs_directory_builds_no_index (logs/negative-control-old-predicate.log). The unconditional index build turns both no-content cases red: 2 failed, 2 passed, EXIT=1, failing test_a_project_with_no_ledger_and_no_runs_directory_builds_no_index and the empty-directory case (logs/negative-control-unconditional.log). Each log's header names the tree, the working directory, the imported module path, and whether load() is gated at all.

The imported-module suite

The 81 test files importing reckon.ledger ran on both arms with -n 8 and a session cache root of their own. Head: 714 passed, 3 skipped, 1 failed (logs/head-suite.log, EXIT=1). Base at ab87725e6 with the guard test copied in: 712 passed, 3 skipped, 3 failed (logs/base-suite.log).

Two of the base failures are the guard test's own no-content cases, which is the control working. The third, tests/test_roster_write_commits.py::test_commit_refuses_roster_with_uncommitted_registration, does not reproduce at head.

One added failure. tests/test_a_sweep_resolves_review_heads_once.py::test_one_derivation_builds_the_index_once builds a crew home whose ledger is an empty runs directory with no aggregate, and asserts its derivation built the index once. Under this change that ledger holds nothing, so no index is built and the count is zero. The premise the test rests on — that an empty ledger is worth indexing — is the behaviour §8 removes, so the repair is a line in that fixture giving it a ledger rather than a change to this node's product code. The file is outside this node's write paths. The one-line repair was verified in a scratch copy of the head revision and turns the file green (4 passed), so the fix is known rather than assumed.
