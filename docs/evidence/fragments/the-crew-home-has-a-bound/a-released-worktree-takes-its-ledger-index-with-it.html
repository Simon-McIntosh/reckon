What changed

_release_run_workspace in reckon/crew/promotion_release.py now unlinks the ledger index of the worktree it releases. Every worktree resolves its own ledger path, so its reader publishes a full-size index under ~/.cache/reckon/ keyed to that checkout; the release removed the tree and left the index behind, where nothing resolved it again until a sweep nobody ran.

Three properties hold the change to the narrow part of the leak. The index path is resolved before the tree moves, so it is the key the tree's own reader published under. The unlink runs only after _release_worktree_whole reports the tree itself released. And an index a live process holds open — SQLite's write lock refused, the same test the run-less sweep already applies — is kept and named in the release record.

One guard is not in the plan's text and was added because the hash alone does not prove provenance: a checkout whose docs/state reaches the main checkout through a link publishes the shared index, so the release names no index at all when the resolved ledger path is not inside the released tree. Deleting by hashed filename would have taken a live index there.

The removal is printed and returned on the release result as ledger_index_removed, so the record names the path it took rather than only that it took one. The run-less crew gc --apply sweep is unchanged: it keeps reaping what earlier releases left behind.

The gate

tests/test_a_released_worktree_takes_its_index.py is the committed gate. It builds a synthesised checkout, two linked worktrees and a temporary cache root under a temporary configuration home; no real fleet directory is read or written. Its four cases are:

  • releasing one worktree removes that worktree's index, leaves the peer worktree's index in place, and prints the path it removed;
  • an index a live process holds open is kept, and the release says so;
  • the run-less sweep removes an index whose recorded checkout is gone, and reports it recorded-checkout-gone;
  • the sweep leaves an index whose checkout exists.

Each case publishes its index by reading a ledger through ledger.load, so the file under test is the one a worker's reader builds rather than one the fixture names by hand; the first case asserts both indexes exist before the release, so the absence it later reports cannot be an instrument seeing nothing.
