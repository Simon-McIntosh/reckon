The apply pass removed 4,636 stale run locks (zero-byte ownership markers 30 to 60 days old), 3 report trees whose plan is done (260,984 bytes), and 5 worktrees. Outside the four stores the fence names it also removed 3 persisted memos totalling 5,002 bytes, all from a fifth store, ~/.config/reckon/cache/metadata-index, and the report records that count as persisted_memos_removed. It removed no run directory and no ledger index: the report named nothing reclaimable in either family. The report-only listing, printed in full at the head of the apply log before its first removal line, names 4,633 locks, 3 report trees and 5 reclaimable worktrees beside totals of 4,633, 3 and 70, and names 0 reclaimable run directories beside a total of 216 withheld and 956 kept.

The project scope held, and it is the reason the run store was not touched. Of the 956 unledgered run directories past retention (29.6 GB), every one is attributed unknown: their live pointer is gone and their manifest carries no project key, so no sweep can name their project, and each is reported keep with that reason and left on disk. The 216 ledgered run directories past retention are withheld for a missing review result (179) or a review still owed (37). No removal line names a run belonging to another project: the apply report's removed run directories number zero, and the overlap check reads removed_run_directories_naming_another_project=0 and removed_ledger_indexes_naming_another_project=0.

Two store figures rise rather than fall, and neither rise is a removal that failed. The pass removed 3 report trees totalling 260,984 bytes (255 KiB) while 18 files totalling 2,211,080 bytes (2,159 KiB) were written into the same store inside the window — two review snapshots of one plan alone account for 1.8 MB — which is 1,904 KiB of net writing against the 2,019 KiB the store measures. The 115 KiB between them is block accounting: du charges a 4 KiB granule per file and per directory across a store of 813 entries, so bytes written and bytes measured do not reconcile exactly, and no mtime separates a rewrite from a fresh write. The measurement behind the 18-file figure, its command and its window are recorded in logs/backlog-reclaim/reports-window.log.

The cache store's +515 KiB is 0.005% of its 10.3 GiB and is not explained by anything the pass removed: the three memos it removed, 5,002 bytes in total, sit under ~/.config/reckon/cache/metadata-index, which is a different store from the measured ~/.cache/reckon. So that figure carries no information about the pass in either direction, and the removal counts are read from the report's own rows rather than inferred from a store-size difference.

The keep-guard is shown rather than assumed. Before the pass a script wrote two lists into the run's log directory: before.live, holding all 124 live run pointers with their run id, project and worktree, and before.worktrees, holding all 67 registered worktrees with their dirt and their commit count ahead of main, of which 44 carried uncommitted changes or commits not reachable from main. The apply log prints the counts it compared — live_run_pointers_at_start=124 and risky_worktrees_at_start=44 — and then checks every removal line against those lists, printing CHECK VERDICT: NO OVERLAP with zero removed run ids holding a live pointer at the start and zero unexplained worktree overlaps.

One removed worktree was on that list and is declared rather than counted as clean: …/a337e0e6-c34c-4497-878a-bc42ce1b7cf6/release-a-landed-heads-worktree carried one untracked file, tests/test_a_landed_head_releases_its_worktree.py, while its head was an ancestor of main with 0 commits beyond it, so gc classified it dirty-integrated release residue and reclaimed it. The file is a superseded draft of a test that exists on main; the draft is preserved outside the tree at logs/backlog-reclaim/preserved/ with its sha256 and a diff against the committed copy, recorded before the pass in declared-untracked-residue.txt. The 4 other removed trees were clean with 0 commits ahead of main.

The drop reconciles with what the report named, inside the churn the log lists. Worktrees fell by 4, which is the 5 the report named less the 1 tree created during the pass (…/8e41a6d3-…/review-of-qwnw-an-edit-op-accepts-the-input-forms-its-examples-2e06b36414be, listed as NEW). Within the apply pass's own before and after snapshots the run store went 2,666 to 2,667: one run started, none was removed, matching the report's zero. Lock files numbered 4,636 rather than the 4,633 named, three having aged past the threshold in the interval, which is the pass reaching the same figure plus drift rather than a disagreement.

The 2,410 run directories and 21,747,834 KiB (20.74 GiB) that the run store lost across the window were not this pass's. Its own snapshots, taken either side of the --apply call, show no run directory removed, and its report named none reclaimable for reckon. The loss falls between the two jobs and coincides with the run-lifecycle sweep under crew-state-stays-bounded. Two files record how far that sweep has got, and both were rewritten inside the interval: ~/.config/reckon/crew/retention-cursor.json at 04:30:16Z, holding {"after": "r-20260907T191107338286-n-sli-the-reasonless-failures-are-triaged"}, and ~/.config/reckon/crew/cleanup-cursor.json at 04:41:42Z. The first of those falls 11 minutes before the apply job's pre-apply snapshot and inside the interval in which the 2,410 directories left, and it is the only evidence of a moving sweep in that interval. That is an association, not a proven cause: a cursor advancing during the interval does not prove that sweep removed exactly those directories. The figures are recorded here because the node's fence asks for counts before and after, not as a reclamation this pass can claim.

The before-measure recorded a remover already at work. Its du -sk of the run store reported rc=1, and its two stderr lines name run directories that ceased to exist part-way through the walk: r-20261115T024952708941-review-of-archive-pulse-schema-179e16f1bee2 and r-20261115T034245513789-review-of-a-local-worker-compacts-and-continues-measured-bbfc8256932e-figure, the second written at 03:42Z, eleven minutes before the measure. Nothing this node ran had removed a run directory at that point: its report-only pass was still running and removes nothing by design. So a second process was deleting from the same store while the before-state was taken. That is why the two readings are not two samples of one undisturbed population, and why the drop is attributed to that process rather than to this pass.
