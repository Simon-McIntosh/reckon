A project-scoped gc removes only that project's unledgered state

With --project P, the unledgered run-directory sweep attributes each directory to the project its live pointer, manifest or run record names, and the orphan ledger-index sweep attributes each index to the project whose own ledger path it records. Only P's entries are removed; an entry belonging to another project, or to none the sweep can name, is reported as kept with its project or unknown and left on disk. Every row carries the project it was attributed to.

The new test tests/test_gc_reclaims_only_its_project.py builds a crew home with run directories for reckon and nova plus an unattributable one, and an orphan ledger index recorded against each project's ledger. gc --apply --project reckon removes reckon's directory and index, keeps nova's and the unattributable directory, and names each project. It is red at base 042d4a27f — the same call offers the peer's directory for pruning — and green at the node's head; the declared arm reads 56 passed, the baseline arm 53 passed with two scaffolding errors from a base tree extracted without git metadata.

Two pre-existing tests encode the previous unscoped expectation and now fail under the scoped rule: test_gc_reaches_every_crew_store.py::test_gc_reports_and_removes_each_unbounded_store, ::test_gc_keeps_a_peer_projects_run_directory, and test_gc_sweeps_ledger_indexes.py::test_gc_reports_and_removes_orphan_ledger_indexes. They assert that an unattributable entry is removed; the rule now keeps it. Updating them lies outside this node's declared write paths and is reported for a scope extension.
