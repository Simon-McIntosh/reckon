arcwc-find-where-a-plan-read-spends-ten-times-its-parse — a version read pays the project's index, not its own parse

What was measured. The served entry points were profiled on revision 319b74cb95: read_plan(view="version") and a no-op-shaped edit_plan (setting status to the value it already held) of the-monitor-shows-the-work-it-watches (904,485 bytes) and of a 29 KB control, a-dry-run-must-resolve-what-the-real-call-resolves (29,282 bytes), both through reckon.mcp.read_plan_tool / edit_plan_tool with checkout_path naming the working tree. Because the deadline wrapper runs the body on a pool worker, each cProfile was taken on the synchronous body inside exactly the request scopes the read wrapper enters on that worker (metadata_index.discovery_file_scope(), resources.resource_scan_scope()); full served calls were timed separately without a profiler.

Result. Warm version read: 1.474–2.112 s (wall) / 0.828–1.003 s CPU for the monitor plan and 1.373–2.112 s / 0.661–1.199 s for the 29 KB plan — flat in plan size. Cold index: 27.732 s / 19.457 s CPU for the monitor plan against 0.769 s / 0.337 s for the 29 KB plan. No-op edit: 8.167 s / 6.308 s CPU for the monitor plan and 4.573 s / 2.537 s for the 29 KB plan with the index current. The requested plan's own parse is 0.332 s (monitor) and 0.013 s (29 KB) in a fresh process. Load average was logged with every figure.

Dominant cost. A version read does not spend its time parsing the plan it names: on a cold cache 66.5 of the 69.5 profiled seconds (96%) is one whole-project metadata discovery index build reached from _section_dependency_rows (reckon/mcp.py:1920) -> _indexed_plan_states (:1952) -> metadata_index.discovery_state -> build_index, which calls _plan_html.read_state 548 times and parse_meta 548 times (25,315 soup.select calls, 2.24 million CSS-match calls). The plan declares 40 sections with waits and 50 section-scoped refs; the 29 KB control declares none, never enters the path, and builds no index. With the index warm, 3.14 of 3.29 profiled seconds sit in _read_state: resources._directory_identity_index re-lists the plans directory on every resolution (5,297 posix.stat calls, 1.5 s) and a 21,642,761-byte persisted index is decoded per read (0.76 s) and re-encoded (2.999 s) whenever any covered signature has moved. The no-op write parses the same 904 KB document five times inside write_plan plus twice more in the section-coverage guard, then the next read rewrites the 21 MB index.

Proposed repair (a plan section, for the coordinator to write). (1) Resolve deps and section-scoped refs only for the views that serve them, so version, raw and section resolve none. (2) Resolve refs from metadata_index.persisted_discovery_entries / current_discovery, validating only the target plans named, rather than a tree-wide validation pass. (3) Serve resources._directory_identity_index from file_memo.memoized keyed on the directory's stat identity. (4) Thread one parsed state through write_plan, _require_heading_for_section_records and new_section_coverage_gaps so a write parses once. Write paths: reckon/mcp.py, reckon/metadata_index.py, reckon/resources.py, reckon/_store.py and a new test. Test: a synthetic store whose target plan declares section refs and whose index is cold, asserting view="version" builds no index and parses at most once while view="detail" still builds it; two resolutions list the directory once; a no-op edit parses once. Negative control: restore the unconditional section-ref resolution for the version view and the first case fails.
