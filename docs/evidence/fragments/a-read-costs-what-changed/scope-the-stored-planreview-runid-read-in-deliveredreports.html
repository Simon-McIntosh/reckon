A promotion reads one plan's stored reviews

Promoting one delivered plan review asked the store which review-run ids it already held, and asked for the whole project's. _stored_review_run_ids called list_plan_reviews(project=project) with no plan, so a promotion of one plan read every stored plan review of every plan, while the run names the plan it reviewed. On the live store that day — 2,035 stored plan reviews across the project's plan directories — one delivered_reports call for a single plan took 20.2 to 25.6 s.

The stored-id read now takes the plan it is asked about and passes it to the same listing: _stored_review_run_ids(project, plan_slug) calls list_plan_reviews(project=project, plan_slug=plan_slug), and delivered_reports passes the plan it was given. The listing already scoped itself to one plan's committed plan/<slug> directory and to the staging glob plan-<slug>.v*.json; only the caller failed to ask. A whole-project read is kept for a caller that names no plan, which is what the parameter being optional does.

A new tests/test_a_plan_review_promotion_reads_one_plan.py fills a temporary store with a review of each of two plans and a delivered report for one of them, then records every path plan_review._load opens while delivered_reports answers for that one plan. The other plan's record is never opened, every stored record opened belongs to the plan asked about, and the report already stored for that plan still reports stored=True while the unstored one reports stored=False. Head arm: 2 passed, EXIT=0.

The declared mutation passes no plan to the stored-id read, and the negative control applies exactly that: with stored=_stored_review_run_ids(project) the one-plan case opens plan-plan-scope-other.v1.json and fails on the assertion that no other plan's record was opened — 1 failed, 1 passed, EXIT=1. The same mutation run through the node's own test as the base arm fails the same case, EXIT=1, so the case distinguishes the scoped read from the unscoped one and not merely from a missing file.

The same timer on the live store, five runs each: delivered_reports for the-monitor-shows-the-work-it-watches measured 20.176, 25.590, 23.947, 23.166 and 20.176 s at the base code, and 1.995 to 3.485 s at head on the same loaded store; for a-plan-is-reviewed-before-it-is-built it measured 1.652 to 2.495 s at head. The scoped stored-id read itself, which is what this node changed, measured 1.135 to 1.524 s on the first plan and 1.537 to 2.127 s on the second. The remainder of delivered_reports is the report-root enumeration of 101 delivery sidecars, which this node does not touch; the shared store was heavily loaded while these ran and the figures move by a second or more between passes.

One arm is recorded as measured and not as complete: the 101 test files importing reckon.crew.plan_review were run at head with -n 4 and reached 93 % with 4 failures before the background runner's own limit stopped it, so no summary line and no failure ids exist for it. That arm is not evidence of a clean population and is reported as stopped rather than as passed; the failures were not attributed. The node's own gate, the scoped-arm and base-arm logs beside it, and the ruff checks on the staged paths are complete.
