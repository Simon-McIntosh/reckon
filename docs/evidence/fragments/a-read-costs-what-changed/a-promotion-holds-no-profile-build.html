A promotion folds its row without reading the ledger

The promotion hands the run-time profile refresh the row it has just written beside the ledger state it observed before appending. The refresh extends the stored fold samples with that row and reads nothing else, so no index decode and no run-document read happens while the promotion lock is held. When a stored profile exists but that anchor does not account for it — a moved source, a different date, a rewritten history — the fold declines and leaves the served profile alone instead of rebuilding it under the lock. A project with no published profile has nothing to fold into and still takes one build, which is the cost of a cold home paid once per project.

The new case drives crew complete --gate not-run for three review runs against a 200-row ledger, once with a fresh index and once with an index held stale, and counts calls to _index_payload, _last_good_index_data and _merge_run_documents made from the profile path while the promotion lock is held. Both cases record none, and the promotion's own ledger reads are still observed, so the instrument is proven to see something. A pick made afterwards serves a profile of 203 rows with a group per promoted backend.

The negative control restores the current refresh: the stale-index case then makes three _merge_run_documents calls and two index decodes per promotion from the profile path, and the case fails. Its log is logs/negative-control-stale-index.log in the run directory.
