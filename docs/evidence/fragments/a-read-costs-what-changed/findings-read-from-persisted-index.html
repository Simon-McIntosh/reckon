A dispatch reads findings from an index kept at write time

What changed. reckon/crew/findings.py no longer derives the finding rows of a project inside the process that reads them. It persists them to the node-local cache directory review_records.node_local_cache_dir already uses for its own store index — never the tracked tree — under a document stamped with the digest of the four modules that fix how a row is derived (findings.py, review.py, review_records.py and runs.py). A fresh process starts from that document.

Two levels of stat identity decide what is reused. A review directory whose own identity is unchanged is trusted whole: no listing, no record read, one stat. A directory that moved is rescanned record by record against each record's identity, which is what carries the rows of every other record forward and reads only the one that changed. The two parents — reviews/run/ and reviews/plan/ — are cached the same way, so a store of thousands of review directories is not re-listed by each dispatch. Two subtrees are covered: the committed reviews tree, and the crew-home store the code reviews live in, which list_code_reviews previously read whole on every call.

The three writers that change a record refresh the entry they wrote: review_records.store_committed_review, plan_review.record_response (on the committed copy it rewrites) and plan_review.store_code_review. The entry's directory is left with no trusted signature — a concurrent write could land between the writer's read and its directory stat, and a signature recorded then would make a later reader trust an entry missing that write — so the next reader rescans that one directory, finds every record's identity unchanged and opens nothing. A writer never creates the document a reader builds: an index covering part of a store would look trustworthy everywhere it was silent.

Each row now also carries response, the answer recorded against its finding, which the reader did not surface before; the disposition it already carried is a different question and is unchanged.

The check

tests/test_findings_are_read_from_a_write_time_index.py holds the six facts the section names against a temporary crew home, checkout and code-review store, with the node-local cache redirected and the operator's own cache asserted untouched: a fresh process opens no record; an answer recorded through record_response comes back on its row without opening another record; a record committed by promotion is returned by the next read; a record written into a directory behind the index's back is returned; a code review stored through store_code_review is returned without opening another; and a moved source digest rebuilds every entry. A further three cases hold each writer to leaving the next read nothing to open, and their control withholds the hook and shows the same read opening exactly one record.

Negative control: deleting the persisted index before the fresh read makes that first case open both records and fail.
