A plan read answers its section waits from the index, not with a full read per ref

What changed. Resolving a section wait used to cost a full plan read of the target. _section_dependency_rows walked each section's plan-section-depends-on refs and called _resolve_plan_ref once per ref, and _resolve_plan_ref reached _store.read_plan for every one of them. A plan waiting on six refs across two plans therefore read each target three times, and the profile put 86.1% of a plan read's samples under that path.

reckon/mcp.py now resolves a ref from the metadata index. _indexed_plan_states(project, checkout_path) returns each live plan's parsed state keyed by slug from metadata_index.discovery_state, keeping the live document where a live and an archived document share a slug, which is the live-first resolution a full read takes. _indexed_plan_state answers one slug from it and memoises the project's lookup in a cache that one _read_plan creates before it resolves anything, so the whole-plan refs (depends_on) and the section-scoped refs share one lookup per referenced project. A plan the stored index cannot answer for is parsed once from its own document through _resolve_html_file and _plan_html.read_state_file rather than read in full, so no ref reaches the full-read path and the answer still comes from one pass. The cross-project refs in _audit_read pass a cache of their own.

The row a ref contributes is unchanged in shape and content: status, impl, title, followups and section declarations are what the ref row is built from, and those are what the index holds. External refs keep resolving without a checkout path, exactly as before.

Measured

Two counts are taken on one read of a waiting plan whose six sections wait on three refs each into two other plans. A wrapper on reckon.mcp.read_plan — the full plan read path — records every target read wherever it is made; a wrapper on _indexed_plan_states records each index lookup by project. The same fixture also rehearses the base revision's per-ref full read, so the rows are compared rather than assumed equal.

The index lookup is counted by project, so a lookup count that falls as refs are added is the property the deliverable asks for: one project's index answers every ref that names it. The head count is asserted 0 < lookups ≤ 2 — the lower bound proves the index is consulted rather than skipped, and the upper bound proves the count does not grow with the six refs.

The rows do not move

The same read is run twice in the head tree: once as implemented, and once with _indexed_plan_state replaced by a per-ref full read, which is the base revision's behaviour. The six rows must be identical, and the plan's own data payload must be identical, so the change is a cost change and not a state change.

Found and not taken

The metadata index is not always populated with parsed state. A store whose persisted entries carry only a path makes discovery_state return nothing and never rebuild, so the indexed lookup answers empty for that project. That is why the per-plan parse fallback exists rather than the index being assumed complete. Making the persisted store rebuild in that case is the index's own repair, in reckon/metadata_index.py, which is outside this node's write scope; the fallback keeps the ref path a single parse meanwhile.
