A stalled request reaches its coordinator as a stalled duty

What changed. A queued request whose last recorded admission verdict is the stall verdict now builds a run-stalled duty in its coordinator's obligations instead of the plain run-queued row it built before — the two used to read identically, so a request admission had already failed to take looked exactly like one that was simply waiting its turn. The new kind carries the pass's own record rather than a second derivation: the age the request has been admissible (age_seconds from the verdict, not the request's own age, because a request queued before its section was ready has waited long without ever being launchable), the stage the pass was in (stage), that stage's duration on the last pass (stage_seconds), and an action naming the two things a coordinator can do with a request the lane owns — reprioritise it or drop it.

The kind is non-blocking in both places that decide a stop: it is added to obligations.NON_BLOCKING_DUTY_KINDS and to the hook's mirror set _NON_BLOCKING_KINDS in reckon/hooks/coordinator_obligations.py, because the request stays the lane's to launch and a coordinator cannot shorten the wait by acting.

The admission verdict log is read once per obligations build and that one reading is handed to every _queued_item call — the derivation reads it in _obligations_view, the published slice reads it in obligation_snapshot.payload_for — so two rows in one build cannot disagree about what the pass last decided, and a later launched verdict replaces the stall for every reader. A request that is merely waiting keeps its existing row, and a verdict left behind by a request that has since moved to another phase is ignored: the row is built as stalled only while the request still reads as queued. needs_you.py and the drain view's reader are untouched.
