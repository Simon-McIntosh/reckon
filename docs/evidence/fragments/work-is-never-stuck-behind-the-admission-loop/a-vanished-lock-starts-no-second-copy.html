A vanished service lock never starts a second copy

Two adopted services lost their <name>.lock and <name>.pid files while they ran. DeclaredServices._alive fell back to lock_held, whose probe opens the lock path without O_CREAT, so a missing file read as an ended service. The supervisor logged both as exited and started second copies, which ran beside the originals for two days while both serialized on the same admit lock.

Liveness no longer rests on the lock file alone. A copy whose recorded pid names a process whose command line is that service's is alive whatever the lock path says; the supervisor keeps it, and records one alert naming the service in the fleet state's alerts.log when a lock file it has seen has gone. A lock that has not been created yet is not a vanished one, so a copy just started raises nothing. Each supervision pass also lists the copies of every declared service that the current pass can see and stops all but the recorded one, by pid, with the list logged first. The pid record now carries the lock file's inode beside the pid, so a reader can tell a replaced lock file from the held one.

The new test file's three cases run against a temporary runtime and state tree, and assert that the machine's own runtime and state directories carry none of the case's files afterwards. Head arm: 3 passed, exit 0. Declared negative control — restoring the lock-only liveness read in _alive — fails the vanished-lock case: 1 failed, exit 1, with the log showing the restart starting a second copy. The files importing reckon.crew.fleet_supervisor were run at the base revision in an extracted tree: 2 failed, 2 errors, 261 passed; the same three files at head give 1 failed, 60 passed, the remaining failure being a leftover reload-trees directory under the real fleet runtime that the base extraction itself created. Ruff check and format are clean on the two staged paths.
