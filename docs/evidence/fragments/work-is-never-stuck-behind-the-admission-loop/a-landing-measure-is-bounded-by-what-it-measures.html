A landing measure is bounded by what it measures

An arm's wall-clock bound is now the larger of the configured floor (600 s by default) and twice its file count times the project's median seconds per file across stored measurements. Every arm records its elapsed seconds and file count in its Arm record and in landing-measure/measurement.json, and that record now carries the project it belongs to. A measurement that could not be taken is no longer reused: the stored record for a timed-out head yields no measurement, so the retry actually re-runs the suite.

The bound follows the population

A stored population arm that took 900 s over 100 files is a rate of 9 s per file; an arm of the same size is then bounded at 1800 s rather than at the fixed 600 s that refused it. The median is taken across the project's own stored measurements only, so another repository's suite cannot size this one's bound, and a project with no history is bounded by the floor. The median rather than the mean keeps one arm that ran on a saturated host from setting every later bound.

The history is read once per pass

The history is the measurement record of each of the project's own live runs, read once for the whole landing pass and handed to every run it measures — not a walk of the runs directory, which holds thousands of other projects' and promoted runs' entries on shared storage. Measured: a pass over three runs with 60 unrelated run directories present reads three records and adds none per measured run, against 192 for a per-run walk of the same directory.

A timeout is retried; a regression is not

A refusal whose guard is a measurement bound that was exceeded, or a base checkout that could not be built, is environmental: it says nothing about the delivered code, so the run is judged again once its back-off has elapsed even though the code stamp and the review record are unchanged. The back-off starts at 900 s, doubles per repeated timeout on the same head, and is capped at 6 hours. A refusal for an added regression, a blocking finding or a merge conflict keeps the behaviour it had: it holds while the code stamp and the review record are both unchanged.

Evidence

Eleven cases in tests/test_a_landing_measure_is_bounded_by_what_it_measures.py: a 100-file population that last took 900 s is bounded above 900 s and above the 600 s floor, an arm with no history gets the floor, a stored measurement from another project is not used, every arm's elapsed seconds and file count reach measurement.json, a timeout and a base-checkout refusal are each judged again after their back-off with code and review unchanged, an added regression is not judged again until one of them moves, the back-off doubles and caps, repeated timeouts count attempts while another guard restarts them, a stored timed-out measurement is not reused, and the history is read once per pass rather than per measured run. Two negative controls: restoring the fixed bound fails the first arm (1 failed, 10 passed), and walking the runs directory per run fails the read count at 192 against 3 (1 failed, 10 passed). The seven test files importing landing_measure and queue_landing pass at the base revision (61 passed) and at the change.
