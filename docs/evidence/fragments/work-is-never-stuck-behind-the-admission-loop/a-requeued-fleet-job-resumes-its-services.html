A requeued fleet job resumes its services

What changed

reckon/crew/fleet_supervisor.py: a new restarted_own_job answers whether this start is a restart of the fleet the published record already names — SLURM_JOB_ID equals the record's job_id and SLURM_RESTART_COUNT is above zero. serve asks it once, before it decides whether to stand by, and a standby that answers yes is not a standby at all: it publishes its own record, reserves its projects and starts the station and the declared services on the spot, logging that it promoted instead of standing by.

A standby whose record names a different job is a migration still in progress and is unchanged: it publishes nothing, starts nothing, and waits for the promote request as before. A first start of a job the record already names, with no restart count, also holds.

Measure

Gate: tests/test_a_requeued_fleet_job_resumes_service.py, three cases driving a real serve loop in its own process over a temporary state and runtime directory with the station and the declared services replaced by recorders of their own calls — 3 passed, EXIT=0.

Negative control: the first case at the base revision, whose serve has no restart check, stays in standby and leaves the record naming the dead node — assert 'some-old-node' == '98dci4-clu-2023', 1 failed, EXIT=1.

Importer population (20 test files importing reckon.crew.fleet_supervisor, at most -n 4), base 3118c296 against head: the same five failure ids in both arms, 0 added at head (base 5 failed / 164 passed, head 5 failed / 167 passed). The five are the machine-state surfaces of a shared host — producer seat, staging inventory, admission log trim, station reload image — not this change.

Caveat

This gate measures this node's change only. Whether a live requeued allocation actually resumes its services on the fleet node is a property of a running job, and belongs to the separately dispatched test node.
