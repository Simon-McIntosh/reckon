A request that never launched holds no claim another landing must clear

Landing a run with --accept-path reckon/crew/runs.py was refused because a peer claimed the path, and the claimant was r-20261103T002057887892-a-coordinator-launches-one-request — a request still awaiting-upstream, never launched, with no worker and no worktree. The refusal came from the accept-path walk in promotion_scope._accepted_scope_exceptions, which judged every peer claim by two questions: has the holder's process ended with a terminal manifest, and has the claiming run's change already reached the integration head. A request that has never launched answers neither, so its claim blocked the landing until the coordinator discarded the request and dispatched it again — losing the request's place in the queue to clear a conflict that protected nothing.

One rule, one walk that did not consult it

The rule already existed and four other claim walks already applied it. node.claim_disposition returns binding=False for a pointer whose phase is in WAITING_REQUEST_PHASES — queued, awaiting-upstream, blocked-upstream, held — because such a request has no worker and no worktree, so its paths are checked when it reaches launch rather than while it sits in the queue. queue_admission, dispatch_claims, queue_edit and runs all read it. The accept-path walk was the one that re-derived the question from liveness alone.

The walk now asks claim_disposition about a peer whose phase is in that set, and admits the acceptance when the disposition is non-binding. The admission is written on the acceptance under waiting_request_claims, naming the run, the claim and the phase, so a reader of the landing record can see which request was walked past and why. The peer's pointer is untouched: the request keeps its claim, and the scope conflict that protects its later launch is unchanged. Nothing else in the walk moves — the shared-file exemption, the stopped-peer branch and the already-integrated branch are the same code, and a peer that is actually running keeps refusing exactly as before, because its phase is not in the waiting set.

Evidence

Three cases in tests/test_a_parked_request_does_not_block_a_landing.py, the first parametrised over all four waiting phases. A run landing a path outside its declared scope, beside a request in a waiting phase that declares that path and has no pid and no worktree, is admitted, and the acceptance carries waiting_request_claims with that request's run id, claim and phase. The same fixture with a peer whose phase is not a waiting phase and whose process is alive is still refused: no ledger row is written, the claimant's pointer is unchanged and the landing run keeps its own pointer. The third asserts the parked request's pointer is byte-identical after the acceptance and that list_live still lists it, which is the claim surviving for its later launch.
