A claim hold is judged against its holder's pointer, not the pass's reading

What changed. An admission pass reads the live set once (reckon/crew/queue_admission.py, _launch_queued) and judges every queued request against that one reading, and its launch stage can run for an hour. A run that landed while the stage ran kept fencing its peers until the next pass began: on 5 November one landed run held eight requests more than an hour after it landed, and two further holders had no live pointer left at all.

_live_claim_hold now re-reads the one pointer whose claim would fence the request (_refreshed_claim) before the held-on-claim verdict is written. The claim is judged again on that fresh record through the same path comparison the stale entry went through (_claim_collision), so a pointer that is gone, no longer claims the path, or no longer binds does not hold the request. The re-read is one runs.read_pointer per hold, not a fresh read of the live set; an unchanged pointer reuses the pass's cached disposition, so the common case costs one file read and no extra worktree inspection.

Measured

Two cases over a temporary crew home. In the first, a stopped holder with an unintegrated commit claims claimed.txt; the pass's live reading returns, the holder's pointer is unlinked, and the request is then judged. It launches instead of being held. In the second the pointer stays and the request is held held-on-claim naming the holder, exactly as before.
