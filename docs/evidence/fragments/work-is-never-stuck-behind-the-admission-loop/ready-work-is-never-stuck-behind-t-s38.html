A refused launch records one verdict

A pass that refused a request before launch wrote two rows in one pass record, refused-before-launch and then stalled, because the pass's held set knew only the hold verdicts. The next pass read the refusal as a request still waiting — _last_verdict_of returns the first matching row — and appended another stall, so a request nothing was wrong with accumulated one stall verdict per pass for as long as it sat. Both defects reproduce at the base revision: one pass records ['refused-before-launch', 'stalled'], and the stall rows in the verdict log grow 1 then 2 across two passes.

A refusal settles the request for the sessions that follow

refused-before-launch joins a TERMINAL_VERDICTS set in admission/shared.py. The pass's own held set unions that set, so a request it refused gets no stall row beside the refusal in the same pass, and admission/verdicts.py's _record_stalls skips a request whose last verdict is terminal, so a later pass reads the refusal as answered rather than as a wait it repeats. The behaviour lives in the admission package because the facade split left reckon/crew/queue_admission.py holding re-exports only.

Evidence

An exit record written at the launch decision stops the launch, which tells a guard that reads attempts where it decides from one that read them at pass start. A refused request's pass record holds exactly one row, and two passes record no stall row at all for it. Each case asserts that its own change landed in the window, so neither can pass by never applying it.
