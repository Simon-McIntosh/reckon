A request too large for the local lane is never placed there

The router already refuses to *offer* a lane whose context window cannot hold the node, so on the answered path an oversized request reaches a lane that fits it. The fallback path had no such check: a pick that timed out resolved the configured default — local — and a full local lane then queued the request there, with the context refusal surfacing only when admission launched it. That is the shape of the 28 October records in the admit verdict log, where a request of 236,783 tokens sat against local's 230,144 window across 24 passes.

A dispatch that resolves a backend without a router answer — a pick that fell back, or the deterministic route — now applies the router's own check before anything is queued or launched. dispatch._gating_input_window asks routing._context_fit_verdict for the resolved lane's gating window (the smaller of the declared usable_input_window and effective_input_window; declaring neither leaves the lane unbounded and skips the check), so a window that is malformed raises on this path exactly as it does on the router's. When the node's estimate exceeds it, dispatch._widest_context_candidate takes the fitting candidates from picker.snapshot.candidates — the same scan the router weighs, under the lifts in force — and chooses the one with the largest usable window, with an undeclared window ranking above any declared one and ties broken by backend name. No loop over config["backends"] is made. The chosen lane is re-planned through plan_dispatch so it gets its own execution fit, sandbox and write-path checks, and the move is recorded on the run as a route fallback with reason context-fit. With no fitting candidate the dispatch refuses through the competence verdict routing._competence_verdict already builds for the resolved lane — the same payload a --dry-run preview carries, so the preview and the dispatch describe the shortfall identically — rather than queueing.

The candidate scan the fallback needs is the one the timed-out pick had already built. dispatch_picker.dispatch_picker_selection now wraps the snapshotter it hands the picker and keeps a copy of the scan on its result (snapshot_candidates), so a fallback reuses that measurement instead of reading every window a second time. The field is taken out of the selection before the selection is recorded, on either branch — a selection the caller supplied and one this dispatch asked for alike — and _reportable_picker_selection keeps it out of the resolved plan as well. A fallback with no captured scan builds one with cached_only=True, which takes no network probe.

A lane the caller named — --local, --backend, a briefing default or a roster member — stays authoritative: dispatch._router_free_resolution excludes every such dispatch, so an oversized named request refuses at launch as it did before rather than being moved.

Measured by tests/test_a_request_too_large_for_local_is_never_placed_there.py, four cases, all four passing at head and three failing at the base revision with the base code and the new test: an oversized fallback resolves the unbounded codex lane and records route_fallback.reason == "context-fit"; the same dispatch with the local lane full is placed on codex and leaves nothing queued on local; a request that fits local still resolves local with no route fallback; and a request no permitted lane holds refuses naming its shortfall (9,856 tokens against the widest declared window of 230,144) instead of queueing, with a --dry-run of the same node carrying an identical competence payload. The declared negative control makes the fallback path skip the check, and the oversized case fails.
