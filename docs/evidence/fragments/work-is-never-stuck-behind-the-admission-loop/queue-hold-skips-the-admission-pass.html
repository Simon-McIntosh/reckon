A hold applies while a pass is running

queue_edit.hold and queue_edit.release no longer take queue_admission._admit_lock. Each writes the one pointer it changes inside runs._pointer_lock(run_id), the lock every pointer writer takes, which is the path reprioritise already used. A pass holds the admission lock for its whole length, so a steering verb that queued behind it was unusable exactly when a coordinator needed to shrink the queue the pass was working through.

queue_admission._launch_reread_refusal parsed nothing before; it now reads the pointer and refuses the launch when the request's phase is held, naming the recorded hold reason. It already ran immediately before every launch from the pass's launch set, under the same per-run lock, so a hold that lands between the pass's opening read and the launch is honoured instead of being overwritten by a launch from a stale reading.
