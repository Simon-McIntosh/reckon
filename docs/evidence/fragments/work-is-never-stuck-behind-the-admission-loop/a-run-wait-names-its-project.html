A run wait always names the project it lands in

A request stored awaiting-upstream on a run: ref is released when that run's promoted revision reaches the base branch, and the release is read from the ref's project. Only some writers of a request's waits recorded that project, and _wait_state read a missing entry as wait_projects.get(run_id) or "", so a pointer written by a writer that did not record it read as a wait naming no project. Such a wait never resolves: _request_state returns PENDING on every pass, and the only trace was an obligation string on the pointer. That is the three hours and eighteen minutes a request spent awaiting-upstream after its upstream landed, released only by a hand edit.

One derivation, read and written

queue_admission.wait_project_for_run answers which project a run: ref lands in, in the order a dispatch resolves one: the live pointer's own project, then the owner project the dispatch falls back to, then any other mounted project whose ledger holds the run. A ref none of those holds returns nothing, which is the fact the obligation reports. wait_projects_for applies it to a whole list of refs, and the writers and the reader both call it: _rederive_waits writes the result beside the rewrites waits in the same pointer mutation, _hold_pointer does the same for a refs-and-phase write, and _wait_state resolves a missing entry through it rather than reading it as no project. Pointers written before this record carried projects carry missing keys, and nothing rewrites them, so the reader is the half that releases them.

A wait that cannot resolve says so

A wait whose run no project holds is not waiting upstream — no pass will ever release it. The reader records it as a wait-unresolvable obligation naming the ref, and obligations.obligations lists it under its own kind (wait-unresolvable) rather than as a waiting row, so the coordinator hook blocks on it instead of showing a wait that never ends.

One registry, one reader

The wait derivation and a promotion both resolve a run through the mounted ledgers, and both read the same registry. Resolving it twice was resolving it two ways: queue_admission reported a registry it could not read as a failure to retry, while the promotion owner caught the same error and returned no roots, which a caller reads as no project holding the run. So one reader saw a lookup that had failed and the other saw a verdict about the run, from one read of one file. runs._mounted_project_roots is now the only place that maps a project to its checkout root, and it has a form that returns the mapping with the reason it could not be read; the wait derivation calls that form and reports the failure, and every caller that only needs the roots keeps resolving an unreadable registry to no root exactly as before.

Evidence

Nine cases in tests/test_a_run_wait_names_its_project.py. The reader case stores a request whose waits already equal what the plan derives, so the writer has nothing to rewrite, strips its wait_projects, and releases it on the first pass after its upstream's promoted revision reaches the base branch. The writer case adds a run: ref by a plan edit and reads wait_projects beside it. A third case asserts every run: ref in the stored waits has an entry after the writers run. A fourth deletes the run's ledger row, so no project holds it, and reads wait-unresolvable from both the pointer and the coordinator obligations view. The seventh raises the mount-registry read itself as unreadable, and reads the wait as unresolved with that failure recorded rather than as a wait no project holds, so the issue names a re-read instead of advising a discard. The eighth counts reads of the mount registry at the seam every reader goes through, flight.mounted_project_docs: one derivation over three run refs reads it once, one admission pass over three reads it once, one unreadable read is reported once for the whole pass rather than re-failed per ref, and a gate-only dispatch reads it zero times. The fifth keeps a genuinely open upstream reading as waiting with no obligation. The sixth counts mount-registry reads through a patch: one wait_projects_for over three run: refs reads it once, and one resolve_waits pass over a pointer with three such refs reads it once, so a pass costs one registry parse rather than one per unresolved ref per pointer. The ninth makes the registry unreadable and reads it through both paths: the wait derivation returns no project and the reason, the promoted-record scan returns no project and the same reason, and the registry is parsed once per derivation — two derivations, two reads.

Five negative controls, each run against the committed change and restored clean, each log ending in a bare EXIT= line. Re-reading the registry per ref inside wait_projects_for fails the counting case: 1 failed, 8 passed, EXIT=1. Reporting an unreadable registry as wait-unresolvable fails the unreadable-registry and both-readers cases: 2 failed, 7 passed, EXIT=1. Swallowing the reason in runs so an unreadable registry resolves to no roots fails the same two: 2 failed, 7 passed, EXIT=1.
