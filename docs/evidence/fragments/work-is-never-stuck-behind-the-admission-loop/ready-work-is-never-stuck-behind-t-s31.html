A promoted run never re-enters the queue

Both write-backs an admission pass can use to republish a request — _restore_queued and the failed-launch requeue — write through _writeback_pointer, which holds runs._pointer_lock and calls _require_live_writeback (reckon/crew/admission/launching.py, re-exported by reckon/crew/queue_admission.py). That guard reads the run's promotion record through runs._promoted_record_project before it looks at pointer presence, and raises _PointerWritebackError naming the promotion when a record exists, or naming the removed pointer when the file has gone. The refusal is recorded once in the pass's verdicts, and the request is neither requeued nor reported as stalled. The failure annotation path (_record_queued_failure) that runs before restoration carries the same check inside its annotate closure.

Which write-back recreated the recorded pointer is read from the failure fields. A reaper's mark writes launch_failures and phase launch-failed; neither is on the recorded pointer. It carries failure, failure_at, failure_attempts and the failure_guard shape that _holds._stamp_failure writes, and a queue phase in place of any argv — what _restore_queued produces. So the recreating write is a restoration, and the failed-launch requeue is the second route the guard closes. The guard does not depend on which of the two wrote: both pass through it.

The guard and the regression file both exist at the base revision, so this node verified the behaviour rather than reimplementing it. The regression file drives real admission passes over a temporary crew home, and writes the promotion during the launch attempt — after the pass has read its queue, which is the window the incident came through.
