A promoted run never re-enters the queue

What changed. The guard the section asks for is already in reckon/crew/queue_admission.py at the base revision, and its regression file is already beside it. _require_live_writeback reads the run's promotion record through runs._promoted_record_project before it looks at pointer presence, and raises _PointerWritebackError when either fact says the request has departed. Both write-backs the section names pass through it under the pointer lock — _restore_queued, and the failed-launch requeue, which now writes through _writeback_pointer.

This node verified that behaviour rather than reimplementing it. The field record's failure fields name the route: a refused launch stamps failure, failure_at, failure_attempts and failure_guard on the pointer in place, which is _record_queued_failure's annotate path, with _restore_queued behind it if that write fails. Both call _require_live_writeback, so a promotion recorded between the pass's read and its write-back refuses the write and the verdict names it.

Measured

The regression file runs five cases over a temporary crew home: a launch failure after promotion with the pointer left in place and with it removed (both refuse, and the verdict names the promotion); the requeue of a failed launch whose pointer was removed and whose pointer was replaced by a promotion (both write nothing); and a launch failure for a queued run, restored with phase queued and failure_attempts 1.
