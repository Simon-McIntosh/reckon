A landed section releases its waiters

The resolve-and-move idiom had one owner only inside an admission pass: the queue-time check in dispatch.py resolved a request's waits once, when it was queued, and the release step of admit_once was the only thing that moved a waiting request once its upstream landed. Nothing ran that step when a section landed, so release latency was the duration of whatever pass was in progress — measured on 28 October at 41 minutes on nova, where assembled-step and tracked-read waited behind a pass running six crew complete --land subprocesses in series.

queue_admission._resolve_and_move now owns the idiom, beside resolve_waits: it resolves one request's waits against the roadmap and moves the pointer to the phase they justify, reporting the phase the request holds where the write cannot land. Five routes reach a waiting request through it. The queue-time check in _queue_validated_waits (dispatch.py) calls it in place of the lines that duplicated it. The pass's release step, advance_waiting_requests, routes its fixpoint through it. A promotion calls _release_waiters_of_the_landed_section inline once its landing is recorded, naming the promoted run's plan#section, so the requests queued behind the section move without any pass. A discard calls _release_waiters_of_a_discard with the discarded run's run: ref, so its dependants are blocked rather than left waiting to be reported stuck. And _release_tick runs the release step alone, on its own RELEASE_TICK_SECONDS (30 s) clock, called by admit_until_stopped as a stage before the landing and the launch pass rather than inside either.

_release_waiters treats a landed ref as a trigger, not a verdict: each candidate's waits are re-derived through the roadmap, so a request whose other refs are still pending stays awaiting-upstream. A release that raises for one request is recorded on that request as release_failure and does not end the release for the others, and the landing that triggered it stands. The readiness cache keeps its §18 key: _readiness_rows still composes project|docs_dir|plan|refs|_plan_tree_fingerprint, so a plan edited in place during a pass misses the cache and a plan landing merged during a pass is read again.

Measure: tests/test_a_landed_section_releases_its_waiters.py, six arms. Promoting a run that delivers plan-a#s1 moves r-n2, waiting on that section, to queued with no admission pass run, and leaves r-n3, waiting on s2, awaiting-upstream. The release tick moves a request whose upstream landed by a hand merge of the plan within one tick, and a second tick inside the 30 s window runs nothing. A release that raises leaves the promotion landed, records readiness read failed on r-n2, and leaves that request in the phase it held. The queue-time check and the pass are counted reaching the one function through a patch. _release_waiters selects its candidates by the refs they wait on, and a discard blocks the request waiting on the run it removed.
