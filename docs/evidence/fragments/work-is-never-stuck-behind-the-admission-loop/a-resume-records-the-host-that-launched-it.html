An attempt records the host that issued its worker's pid

What changed. A pid answers only on the machine that issued it, and the crew configuration home is shared across login nodes, so a live pointer's launcher_host is what lets a reader decide whether its own process table can speak for the worker. Two writes issue a worker pid and recorded no host.

  • A resume. record_resumption in reckon/crew/dispatch_sessions.py published the attempt's pid and phase without a host, so the pointer kept the dispatching machine's. Once that machine was gone no host could prove the worker dead: recovery_liveness._launched_on_this_host answers false, the reading becomes liveness unknown, and every later resume is refused. The record now names the launching host, so the attempt is judged on the machine that started it.
  • An admitted launch. _queued_request_record stores a held request with launcher_host: None, because no process exists while it waits, and the launch record that attach_launch_identity merges over it carried no host either. The launch record now names the launching host, so an admission pass running on a different machine than the dispatch is recorded as the attempt's launcher.

Every other pointer write is unchanged and still carries the recorded host forward: runs._stamp_pointer_launch_host leaves a payload that states no host alone unless the pointer is new, so a station sweep rewriting the pointer from a third machine cannot claim an attempt it did not start.

Reproduced before repair

At the base revision, a pointer naming host-a and holding a dead pid, with the socket naming host-b, gives both halves of the measured incident in one call:

refusal on the base pointer (launcher_host host-a): run 'r-probe-host' is not
resumed: the process reading is 'liveness unknown' — no pid was checked dead on
this host and no supervisor exit was recorded — so nothing observed the end the
lift would rest on
launcher_host after a resume on host-b: host-a
attempt: 2

After the repair the same probe reads launcher_host: host-b, and the reading above is reached only for a pointer whose host really is another machine.

What the cases pin. A resume on the launching machine puts that machine on the pointer; a second resume after a stop there is not refused as liveness unknown; a write from a third machine that is not a launch keeps the launch host; and a queued request launched here carries this host on its pointer once the launch record is merged over the queued one.
