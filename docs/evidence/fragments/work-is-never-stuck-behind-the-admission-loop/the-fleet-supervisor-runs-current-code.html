The fleet supervisor reloads itself when its checkout moves

What changed. The supervisor's request loop in reckon/crew/fleet_supervisor.py now compares the code stamp it recorded when it started with the stamp the checkout carries on every pass. When the two differ and the checkout is trusted, it replaces its own image through _reexec — the same path a manual reload request takes — so the declared services it adopted keep running and a later reader sees one supervisor. Both inputs are the ones the admission service already uses: follower_code_stamp() for the identity and checkout_trust.moved_checkout_is_trustworthy() for the trusted-checkout test, resolved against the same import root (reckon.crew_follow_commands._import_root). A tree with a tracked file modified against HEAD is not trusted, so the supervisor keeps the image it has rather than running code a half-finished edit produced. An identity read that did not answer is never treated as a moved stamp: the loop adopts the first readable stamp instead of re-executing on every tick, which would loop forever while the read keeps failing. Once the stamp has been acted on it is recorded, so a stand-in replacement that returns cannot make the loop act twice. No request verb and no CLI option is added, and the manual reload request stays for an operator. serve() takes code_stamp and checkout_trusted by argument, defaulting to the admit service's implementations, so a test can drive the comparison against a temporary checkout.

Why it was needed. The station was down for 73 minutes on 28 October while the supervisor ran eight days on code that predates its station request. It answered unknown request: station until an operator sent reload by hand. Every fix to how it keeps services now reaches the node without a request.
