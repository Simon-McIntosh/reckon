One rule chooses the lane for an oversized request

Two paths place a request too large for its own lane, and each chose for itself. The admission pass took the first candidate carrying no exclusion; a dispatch whose router answer never arrived took the widest. Neither read the same rule, so the same candidate set could resolve two different lanes. Dispatch's copy also read a malformed window as an absent one, ranking a broken declaration above every real window, and returned the oversized resolution unchanged when no candidate was usable — so a request no permitted lane holds went back onto the lane the fit check had just measured too small.

The rule is picker.snapshot.widest_fitting_candidate, and both paths call it. It reads a candidate either as the scan's dataclass or as the mapping dispatch exports, excludes any candidate carrying a reason, takes the largest usable input window, ranks an absent window as unbounded above every declared figure, and breaks ties by backend name so two equally wide lanes resolve the same way on every call. A window that is present but malformed or non-positive raises the refusal the router's own fit check raises for the same declaration, rather than reading as unbounded. dispatch.py's private _candidate_window and _widest_context_candidate are gone. Where nothing fits, _reroute_oversized_request builds the refusal from the two figures it weighed — _context_shortfall_refusal, naming the estimate, the lane's window and the distance between them — and raises CompetenceLimit for every case instead of returning the resolution. The resolved lane's own verdict is still preferred where it refuses, so the live refusal and the dry run that previewed it carry one payload.

Measured by tests/test_one_rule_chooses_the_lane_for_an_oversized_request.py, seven cases, driving routing's own _context_fit_verdict and _competence_verdict from a config that declares the windows and stubbing neither. The same candidates resolve the same lane on both paths, and it is the widest usable one: with alpha at 300,000 and beta at 400,000 tokens, dispatch moves the request to beta with route_fallback {"from_backend": "clive", "to_backend": "beta", "reason": "context-fit"} and the admission pass moves it to beta too. The figure the rule weighs is routing's, not the test's: the node's brief declares a 700,000-byte input, and the candidate block reads 200,000 estimated tokens against clive's 230,144 window, while deleting that input from the same node leaves the request on its own lane. A window declared as 0 or "not-a-number" raises on both paths — dispatch exits non-zero with dispatch-refused naming the input window, admission raises CrewError — and the rule itself refuses such a candidate rather than ranking it. With no usable lane, dispatch exits 5 with competence-refusal, naming context-window-exceeded, the estimate above the window and the shortfall in its detail, creates no worktree and queues nothing; the case is built so the resolved lane's own verdict is satisfied while the request's estimate is not, which is exactly the disagreement that used to place the request.
