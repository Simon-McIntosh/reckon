One rule chooses the lane for an oversized request

Two paths place a request too large for its own lane, and each chose for itself. The admission pass took the first candidate carrying no exclusion; a dispatch whose router answer never arrived took the widest. Neither read the same rule, so the same candidate set could resolve two different lanes. Dispatch's copy also read a malformed window as an absent one, ranking a broken declaration above every real window, and returned the oversized resolution unchanged when no candidate was usable — so a request no permitted lane holds went back onto the lane the fit check had just measured too small.

The rule is picker.snapshot.widest_fitting_candidate, and both paths call it. It reads a candidate either as the scan's dataclass or as the mapping dispatch exports, excludes any candidate carrying a reason, takes the largest usable input window, ranks an absent window as unbounded above every declared figure, and breaks ties by backend name so two equally wide lanes resolve the same way on every call. A window that is present but malformed or non-positive raises the refusal the router's own fit check raises for the same declaration, rather than reading as unbounded. dispatch.py's private _candidate_window and _widest_context_candidate are gone. The rule also takes the backend that refused the request and excludes it itself, so neither caller keeps a skip of its own and the rule cannot answer with the lane the request came from. Where nothing fits, _reroute_oversized_request has no branch that returns the resolution unchanged: it refuses with the resolution's competence verdict, the same object a dry run answers with, computed the way the preview computes it when the resolution carries none. Its context block is the fit verdict routing._context_fit_verdict measured for the resolved lane — the estimate that check weighed against that lane's gating window, and the distance between the two — so the figures a reader acts on are that check's, and the refusal also carries the lane's agent key and cache status. The payload is built by routing._context_refusal, the one builder both this refusal and the verdict's own context refusal answer through, so the detail is routing's own: the figures followed by the inputs that carried the estimate and how the largest of them arrived. Because the verdict states the figures from the fit check it holds, the shortfall stays the fit check's own estimate minus the resolved lane's window rather than a second measure computed beside it. The real refusal and its dry run are therefore one payload, field for field, so a caller that previewed the dispatch has already seen every field the dispatch answers with. Dispatch's private _context_shortfall_refusal is gone.

Measured by tests/test_one_rule_chooses_the_lane_for_an_oversized_request.py, twelve cases, driving routing's own _context_fit_verdict and _competence_verdict from a config that declares the windows and neither stubbed for the placement cases. The same candidates resolve the same lane on both paths, and it is the widest usable one: with alpha at 300,000 and beta at 400,000 tokens, dispatch moves the request to beta with route_fallback {"from_backend": "clive", "to_backend": "beta", "reason": "context-fit"} and the admission pass moves it to beta too. The figure the rule weighs is routing's, not the test's: the node's brief declares a 700,000-byte input, and the candidate block reads 200,000 estimated tokens against clive's 230,144 window, while deleting that input from the same node leaves the request on its own lane. A window declared as 0 or "not-a-number" raises on both paths — dispatch exits non-zero with dispatch-refused naming the input window, admission raises CrewError — and the rule itself refuses such a candidate rather than ranking it. A lane that is the widest usable candidate and also the one that refused the request is not chosen: given such a lane and a narrow one beside it, the rule returns the narrow one, and the admission pass is given the case where the refused lane is the widest and the only usable candidate, which it answers by refusing rather than moving the request onto that lane. A spy on the rule records that the name it receives from the admission pass is the pointer's own backend. With no usable lane, dispatch exits 5 with competence-refusal, naming context-window-exceeded, the fit check's estimate above that lane's window and their difference, creates no worktree and queues nothing. The payload is the one the preview produces: the same node dispatched and previewed answers equal competence objects, carrying the lane's agent key, its cache status and the nested fit verdict, whose own shortfall equals the top-level one. The detail it carries is routing's own: the same detail string both times, naming corpus.txt and the form it arrived in, so the fallback renders the refusal rather than a shorter sentence beside it.
