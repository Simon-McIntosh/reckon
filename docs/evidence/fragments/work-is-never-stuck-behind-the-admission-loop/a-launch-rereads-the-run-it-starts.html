A launch re-reads the run it starts

An admission pass reads the queued pointers once, ranks them, and then works through the queue, so what it launches from is its opening read. A request can move in that window: on 5 November one pass launched r-20261105T091632392412-review-of-one-derivation-per-fact-82f3a3bdc63b at 11:16Z although its run had been promoted at 10:06Z and its pointer removed, and another launched r-20261105T112218135978-review-of-a-deferred-only-plan-reads-not-closable-736e61d3ade5 under the same run id as an attempt that had exited at 12:00:46Z with a filed review, overwriting the delivered manifest. The pass now re-reads the request immediately before it launches.

The pointer and the attempts, read under the pointer's own write

queue_admission._launch_reread_refusal runs immediately before the handover and the launch, and takes runs._pointer_lock — the lock every pointer writer takes — while it reads the live pointer and then the run directory's attempt-*-exit.json records. A pointer that is gone refuses the launch and the verdict row names the removal. An attempt exit record refuses it when the attempt recorded a result, which is the reading recovery_liveness._exit_record_is_launch_failure already owns: a launch that never reached a model writes an exit record too, and that attempt carries no result, so the queue's own back-off retry still follows it. The refusal is recorded as a refused-before-launch verdict and writes nothing to the pointer, so a request that has moved is left exactly as it now stands.

Evidence

Three cases in tests/test_a_launch_rereads_the_run_it_starts.py, each writing its change after the pass has read the request as queued: a pointer removed in that window is not launched and its verdict names the removal; a run directory holding attempt-1-exit.json with a recorded result is not launched and the delivered manifest is byte-identical afterwards; an unchanged queued request still launches through the real dispatch path. The test asserts the change landed in the window (fired), so a case cannot pass by never applying its change. Because dispatch itself refuses a run whose pointer is gone, the first case stubs the launch seam to observe the pass's own decision; the other two run the real dispatch path.

Negative controls, each applied to the committed change and restored byte-identical afterwards, each log ending in a bare EXIT= line.
