A held request parks nothing behind it

What changed. The admission pass held a later request behind an earlier overlapping one whatever state the earlier one was in (reckon/crew/queue_admission.py, _earlier_overlapping_request). On 3 November the pass that ended at 11:25Z held the repair for two tests red on main behind a request naming the same path, and that earlier request was itself held-on-claim behind another run's worktree. Neither launched, and the repair's priority override of 100 changed nothing.

The pre-check now skips every request the same pass has already held on a claim, a gate, a retry back-off or a plan review (_non_binding_holds over the pass's own verdict rows): each of those is a reason to wait that lies outside the queue, so the earlier request cannot launch in this pass and fences nothing. A request the pass holds for its session's allowance, or one that has already launched, still holds the later one, which is what the existing overlap case pins.

A priority override is also applied over the lane's whole order (priorities_first, used by fair_share_admission_order and queued_placements), so a request raised through crew queue reprioritise ranks ahead of every request without one across sessions and projects, not only within its own session. A delivered review keeps its place at the head, because it is what lets a finished run land.
