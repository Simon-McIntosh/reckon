The station holds its lease while it beats

On 29 October the fleet supervisor re-executed itself onto new code and started a station while the previous station, pid 827990, was still alive; two stations wrote the same store for several minutes. run_station renewed its lease only between ticks, while HostLease treats a lease untouched for LEASE_STALE_SECONDS (30 s) as stale, so a tick that took 14.5 minutes left the live station's lease reading stale for most of its own run and anything that asked was free to claim it.

The renewal now runs on a thread of its own, beside the heartbeat beat and on the same cadence, and touches only the lease file: no SQLite, so a heartbeat write waiting out its 30 s busy timeout cannot delay it. A failed renewal marks a StoreWriteGuard shared by every handle the station holds; each store write checks it before touching the database, so the tick record, live-work and obligations publish, retention sweep, the finish stamp and the beat thread's own heartbeat all refuse from that moment, and the station's loop stops with StationHeldError instead of writing beside the successor. A station hosted off the main thread keeps the signal handlers it already had, since the stop handler installs only in the interpreter's main thread.

Measured through tests/test_the_station_holds_its_lease_while_it_beats.py under a fast lease clock, so the stale window passes in two real seconds. A held-open tick: the lease read fresh in every one of the arm's samples taken across 1.6 stale windows, a second run_station raised StationHeldError naming the holder, and StationProcess.ensure started no process. With the heartbeat write blocked on every handle past the window, the lease stayed fresh throughout, which is what says the renewal is not the beat. With the lease handed to a successor mid-refresh, no store write completed after the replacement, the guard refused the tick's later writes, and the loop ended with StationHeldError.
