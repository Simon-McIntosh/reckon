A resume that never started reads as not started

The claim. A run reads as working only once its worker has begun a turn. A resume records its launcher's pid and the working phase the moment the spawn returns, so a launcher that blocks before starting any worker — an srun client waiting for an allocation its step never receives — left the run reading as working for as long as it waited. Nothing released it.

The reading. The one fact that answers for a resumed attempt is a turn in the attempt's own stream. Past the bound, the stranded-launch clock, with no assistant record written at or after the attempt started, the run is classified launch-failed, the launcher's own waiting reason is carried on detail and launch_error, and the offered remedy is crew resume: no end was recorded, so nothing is offered as discardable and the session survives. An attempt whose stream does hold an assistant record still reads as working.

The stop. A placed run's client tree was held to be the scheduler's to end. That holds only once the step has started, and a step writes step-task.txt on the node that runs it. Absent that record the client and the processes under it are the launch's own local tree, so the stop signals them individually, never by process group, and reports every pid it signalled.

Measure — the declared negative control, observed. At the base revision the same test module reports 2 failed, 2 passed: the blocked run reads running where the case requires launch-failed, and the stop leaves the stand-in launcher alive. At this head the module reports 4 passed. The log is negative-control.log beside this run's manifest.
