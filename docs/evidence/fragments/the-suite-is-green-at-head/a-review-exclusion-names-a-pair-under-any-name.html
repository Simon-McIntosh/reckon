A review exclusion names a pair under any of its historical names.

Cause. recovery._ordered_review_lanes builds the set of review-excluded backends through _review_backend_excluded, which resolves an exclusion to a lane-and-model pair, but then tests the two preferred candidates — the owning backend and the local backend — as literal strings against that expanded set (preferred not in excluded). The set holds the configured backends the resolver accepted, keyed by their configured name. The preferred names are not in it: the owning lane is often stated as a run-record spelling the configuration does not carry as a key, so an exclusion that names the same pair through an older spelling removes the configured backends of that lane but leaves the preferred alias admitted. The regression landed with a04480487 (2026-10-15, "route with the session's own worker slots and any lift in view"), which replaced the pair call not _review_backend_excluded(preferred, config) with the literal membership test while adding the lift subtraction. The test predates it, added 2026-10-07 in fa9f9dc36, and all three parameters passed at a04480487^ and fail from a04480487 onward: the two historical spellings claude-opus-5-5 and opus 5.5 are admitted while the current spelling claude-opus is removed.

Fix. _ordered_review_lanes now judges every candidate, the preferred pair included, through _review_backend_excluded, which resolves the pair. A preferred lane named by an older spelling of an excluded pair is removed exactly as its current spelling is. A lift in force is honoured rather than overridden: a lane under a lift is admitted first, because the fleet has opened it, and only a lane without a lift is judged through the pair resolver. The test is not loosened; two cases are added beside it. An independent review of an earlier attempt at this repair found that the guard as first written rejected a lifted lane outright — including one no exclusion named — which dropped the owning lane's lead and could remove a preferred lane that is not a configured backend from the ordering entirely; that is the behaviour this repair now holds against, and the case below covers it.

New case. tests/test_old_names_resolve.py::test_local_backend_exclusion_matches_pair_across_names sets local_backend to claude-opus, leaves the owning backend empty, excludes opus 5.5, declares one other backend and expects ['other-model']. It exercises the local preference path the owning lane cannot, so both preferred candidates are covered. test_a_lifted_preferred_lane_keeps_that_lead grants a real lift on a declared group and asserts the whole ordering ['claude', 'alpha-model'], with the lifted owning lane leading. The ordering is asserted whole because a lane dropped from the head still appears in the alphabetical tail, so a first-element check would miss it; and the case first asserts the lift is in force, so it cannot pass by quietly exercising no lift at all.
