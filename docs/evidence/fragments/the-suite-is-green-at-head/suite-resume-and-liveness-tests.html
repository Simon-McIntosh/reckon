The carried defect

reckon/crew/recovery.py:4638, in _worker_record_liveness:

pid = data.get("pid")
...
alive = runs.process_alive(pid)          # bare primitive on a record's pid
if alive is True:
    expected = data.get("pid_start_time")
    ...

It duplicates runs.record_process_alive, whose docstring states the rule -- \"Every liveness decision about a run is taken from the run's own record, so the pid lookup lives here in one place and the call site never handles a bare pid.\" -- and it is also reached without the host gate: classify_pointer (recovery.py:5539) computes worker_alive = _worker_record_liveness(record) unconditionally, and a worker_alive is True there feeds superseded_manifest (recovery.py:5716–5723) and deferred_outcome. A run launched on another host whose worker-record pid happens to be live here can therefore have its terminal manifest deferred as superseded. The repair is return runs.record_process_alive(data, process_alive) at that site. Evidence: test_no_module_decides_record_liveness_with_a_bare_pid fails at head naming recovery.py:4638.

The scan false positive

The guard's _process_alive_calls collected record-read names across the whole module and flagged any process_alive call using one. dispatch.py:7628 is if process_alive(pid) is False: inside _confirm_supervisor_survived(pid, ...), where pid is the supervisor this dispatch has just spawned -- the case the list_live docstring explicitly permits (\"dispatch probing the process it has just spawned\"). It was flagged only because a different function in the module binds a local pid from a record (dispatch.py:9822). The scan is now scope-aware: a record read and the probe that consumes it are compared within the scope that owns both, so the guard still fails on _worker_record_liveness (same scope) and no longer on the permitted probe.
