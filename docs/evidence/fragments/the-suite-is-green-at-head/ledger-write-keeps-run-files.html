ledger-write-keeps-run-files — the writer keeps each per-run file identical to its aggregate row

What changed. A write to the ledger now re-encodes every written run row that already owns a per-run file through serialize_run, so the aggregate row and its file stay byte-identical. Before this, a write that edited an aggregate row left the file holding the previous revision, and the next ledger.load refused the project with the differs-between refusal — the writer produced state its own reader cannot read. A row with no file is left alone; creating one remains the explicit, committed run split. The reader is unchanged.

Across the test files importing reckon.ledger, the head arm measured 21 failed / 1640 passed (log logs/05-head-arm.log) and a base arm over those same 21 ids failed exactly them at base (log logs/07-base-arm-targeted.log): 0 added failures. The full 101-file base arm (log logs/06-base-arm.log) was discarded as ENOSPC-contaminated (490 errors), which is why the base arm of that pass was targeted; the full arm was obtained later, under Repair measure below. The declared negative control — drop the per-run write from ledger.write; case 1’s read-back fails with the differs-between refusal — fires: 1 failed, EXIT=1, log logs/04-negative-control.log.

Repair. The first form of the fix rewrote the per-run files after the aggregate envelope had already advanced, with no way back. A store that refused a single file write — a read-only tree, a full disk — therefore left the aggregate on the new revision while the file kept the old one, and the next read refused the whole project: the writer causing the very disagreement it exists to prevent, from a call that reported no success at all. The files are now brought into line with the rows they copy before the envelope advances, each through a sibling temporary and os.replace so a failed write cannot leave a file holding a prefix of its own content, and each replaced file yields the revision it held. A file that refuses its write abandons the write while the aggregate still holds the revision it read, putting back what it had already changed; an envelope refused on a stale version, or that fails its own write, puts them all back in turn.

Repair (a second writer). The re-review scored 86 and found the window between the per-run writes and the envelope write open to a second writer. Two writers prepared from one revision: the loser rewrites its per-run file, the winner rewrites and commits, and the loser, refused on its stale version, puts back the copy it captured before the winner wrote — leaving a per-run file holding a row the aggregate does not, and the next ledger.load refusing the whole project. The write now takes an exclusive fcntl.flock on a lock file of its own, outside the repository’s tracked tree, and holds it across the whole read-modify-write: the version check, the per-run file writes and the envelope write, plus the roster commit that can follow. A writer prepared from a revision another has committed is refused under that lock having written nothing, so the files a failing write puts back are only ever the ones it wrote itself. For project reckon the lock is ~/.config/reckon/crew/locks/ledger-write-reckon-18dc8a86709b6aa8.lock (a readable project slug plus a digest of the exact name, so two projects never share one file). The lock file lives outside the checkout on purpose: one inside the tree would dirty the repository it protects and would be written by the same store whose failures the write already has to survive.

Repair measure (the interleaved write). A new case forces the schedule rather than hoping for it, and runs it in processes, not threads: the exclusion that must hold is the one between separate commands, and a thread would share it invisibly. One writer is held by a seam between its per-run write and its envelope write; the other is held until that seam is reached, then writes and announces its commit, which is what resumes the first. Red at f1b9e06f before the repair — 1 failed, EXIT=1, log logs/13-race-case-red-at-f1b9e06f.log; green at the repair, 1 passed, log logs/17-race-case-green-at-repair.log, with each writer’s own line printed as the evidence for every claim.

What the red shows at the un-serialised revision is worth stating exactly. Under the real writer the second arrival re-reads the project while the first is between its two writes, so its own read refuses first and it is answered with differs between … refusing to read conflicting history — a corruption the ledger does not have, named before any version check, and the wrong remedy for a write that should simply re-read. No version conflict is raised at all. The reviewer’s own schedule, which interposes a commit behind the first writer’s envelope call, reaches the stale restore instead (their logs 08-race-head.log and 09-race-base.log). Both are removed by the same serialisation; the two-writer shape is the one a second command actually produces.
