ledger-write-keeps-run-files — the writer keeps each per-run file identical to its aggregate row

What changed. A write to the ledger now re-encodes every written run row that already owns a per-run file through serialize_run, so the aggregate row and its file stay byte-identical. Before this, a write that edited an aggregate row left the file holding the previous revision, and the next ledger.load refused the project with the differs-between refusal — the writer produced state its own reader cannot read. A row with no file is left alone; creating one remains the explicit, committed run split. The reader is unchanged.

Measure. Five test_shadow_* ids failed at base 57e4ea2e inside ledger.load (log logs/01-base-shadow-ids.log) and pass at head bc444b40 (log logs/03-head-shadow-ids.log): 5 failed → 5 passed. Across the test files importing reckon.ledger, the head arm measured 21 failed / 1640 passed (log logs/05-head-arm.log) and a base arm over those same 21 ids failed exactly them at base (log logs/07-base-arm-targeted.log): 0 added failures. The full 101-file base arm (log logs/06-base-arm.log) was discarded as ENOSPC-contaminated (490 errors), which is why the base arm of that pass was targeted; the full arm was obtained later, under Repair measure below. The declared negative control — drop the per-run write from ledger.write; case 1’s read-back fails with the differs-between refusal — fires: 1 failed, EXIT=1, log logs/04-negative-control.log.

Repair. The first form of the fix rewrote the per-run files after the aggregate envelope had already advanced, with no way back. A store that refused a single file write — a read-only tree, a full disk — therefore left the aggregate on the new revision while the file kept the old one, and the next read refused the whole project: the writer causing the very disagreement it exists to prevent, from a call that reported no success at all. The files are now brought into line with the rows they copy before the envelope advances, each through a sibling temporary and os.replace so a failed write cannot leave a file holding a prefix of its own content, and each replaced file yields the revision it held. A file that refuses its write abandons the write while the aggregate still holds the revision it read, putting back what it had already changed; an envelope refused on a stale version, or that fails its own write, puts them all back in turn.

Repair measure. Two cases were added. The first injects OSError(ENOSPC) on any write under the project’s runs/ directory: at a55213dd, before the repair, ledger.write reported no error and the read that followed died with the differs between … refusing to read conflicting history refusal — 1 failed, EXIT=1 (log logs/08-unwritable-case-before-repair.log). After the repair the same case shows ledger.write raising and the read returning the run the reader already had, alongside a second case where the envelope itself refuses and the file is put back: 4 passed, EXIT=0 (log logs/09-unwritable-case-after-repair.log). The declared negative control was re-run against the reordered writer and still fires: 1 failed, EXIT=1 (log logs/11-negative-control-reordered.log).
