A revision label is read in any case.

Cause. The manifest audit holds each suite arm's gate log against the revision that arm records, reading the revision from the log's first line with the pattern _GATE_LOG_REVISION in reckon/crew/reports.py. That pattern was compiled without re.IGNORECASE, so a first line labelled REV=<sha> or Revision: <sha> named no revision and the audit refused a log whose revision was in fact the one the manifest recorded. On 2026-10-17 the whole-suite worker r-20261017T141450191818 met this refusal and rewrote its own gate logs' first lines after the run, lowercasing REV= to rev= with a script so the audit would pass: the revision value was unchanged, but a log edited after the fact is no longer the capture it claims to be.

Fix. _GATE_LOG_REVISION is now compiled with re.IGNORECASE. Nothing else about the match changed: the label is still required, so a first line carrying only a bare hexadecimal run — a tree path with digits, a timestamp — still names no revision. The label is read as written, so no writer is driven to edit its own capture.

Sibling reader. The annotated review reads the same first-line revision through recorded_log_revision in reckon/crew/review.py, behind its own pattern _LOGGED_REVISION_RE. That pattern was case-sensitive and required the full word revision, so it also returned None for REV=, Revision: and rev= — meaning a log the audit now accepted annotated with a null head_log_revision, and the two readers disagreed about the same line. _LOGGED_REVISION_RE is removed and recorded_log_revision now reads reports._GATE_LOG_REVISION, imported lazily inside the function so the module-level reports → review import is not closed into a cycle. One pattern now answers for both the write-time check and the annotation.

New case. tests/test_a_revision_label_is_read_in_any_case.py holds both halves through the audit's public entry point, audit_manifest. Four first-line labels — REV=<sha>, Revision: <sha>, rev=<sha> and # arm=head REVISION=<sha> — are each followed by the forty-hex sha the manifest records for the arm, and each must produce no finding naming the head log. The negative half feeds a first line naming only a tree path carrying the same forty hex digits and requires the audit to report that the log names no revision. Three further cases call recorded_log_revision directly: REV=, Revision: and rev= each yield the sha, and a bare hex tree path yields None, so the annotation and the audit are pinned to one reading of the same line.
