race-winner-reads-its-own-write — a stale index fallback no longer hides a committed run from its reader

Cause

test_a_loser_of_the_write_race_cannot_overwrite_the_winner runs two writers of one ledger as separate processes. Both call ledger.load before either writes. Each read refreshes an SQLite index keyed by the aggregate path; while one process holds the index's write lock the other's refresh is refused with sqlite3.OperationalError: database is locked, and load falls back to _last_good_index_data. That fallback served the last published snapshot without checking it still described the aggregate on disk. The fixture's own seed had published an index while the aggregate was still absent — _seed writes through the writer, whose internal read refreshes the index before the aggregate envelope is written — so the fallback handed the refused reader the empty pre-write revision. The child then ran data["runs"][0] against no runs and exited 1 with IndexError: list index out of range; the other writer, waiting on the first's seam, timed out behind it.

Fix

_last_good_index_data now compares the aggregate stamp the snapshot recorded against the aggregate's current file identity and returns nothing when they disagree, so a refresh refused under a peer's lock falls through to the aggregate instead of a revision a committed write has replaced. The check is a stat, not a parse, so an unchanged aggregate still avoids the scan. A deterministic case, test_a_refused_refresh_opens_the_aggregate_rather_than_a_stale_index, publishes an index, moves the aggregate past it, forces every refresh to be refused, and asserts the read sees the later revision with no index_age_seconds.
