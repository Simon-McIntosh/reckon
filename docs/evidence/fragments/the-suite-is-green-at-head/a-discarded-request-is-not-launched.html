a-discarded-request-is-not-launched — a request discarded before its worker is spawned is refused, and its record survives

Defect, reproduced first. The admission pass releases a selected request into the shared dispatch path (_launch_queued, reckon/crew/queue_admission.py), which publishes the run's claim (_publish_launch_claim, reckon/crew/dispatch_claims.py) and then composes the launch for several seconds before starting the worker. An operator's crew discard landing inside that span removed the pointer and recorded the departure (discard, reckon/crew/promotion.py), and no step on the launch path read promotion.discard_recorded. The launch wrote the pointer back and spawned a worker, so the discard record sat beside a live run and every reader that takes a recorded discard for an abandoned run (the queue readers in reckon/crew/queue_admission.py, the departure row in reckon/crew/recovery_watch.py) read the new worker as one.

A new case drove the window through the pass's own seam (the discard issued as _launch_queued is entered) with a launcher that succeeds. At the base revision 0ab156b37 it failed with the live pointer present and launcher calls: 1 (1 failed, EXIT=1, logs/base-reproduction.log).

Fix, one commit (5f9f2ae3a). dispatch_claims.py gains _refuse_a_discarded_launch, and the two spawn sites in reckon/crew/dispatch.py call it immediately before _start_supervisor and before the caller-supplied launcher. A recorded discard raises a CrewError inside the _claim_released_on_refusal guard the path already holds, so the claim is given back and the ordinary rollback removes the pointer and the run directory. The record is copied to the shared spool (preserve_discard_record) before the refusal is raised, so the rollback cannot remove the only copy of a departure recorded in the run directory.

Window left open, and its second half. _require_fleet_gate_open() runs before the check and a discard it trims away is the largest removal; the check then sits immediately before the fork. What a first cut left was the spawn itself: the worker's pid reaches the pointer through _mutate_pointer only after the process exists, and promotion.discard refuses only a pointer naming a live process (record_process_alive answers None for one naming none), so a discard landing between the fork and that merge removed the pointer and wrote its record into the run directory. The refusal rollback destroyed the directory, the admission restore read no record and wrote the request back queued, and a running worker was left named by neither a pointer nor a departure.

Second repair (e513e59cd). _release_launch_claim copies any discard marker into the shared spool before removing the run directory, so no rollback can destroy the only record of a departure, and the launch reads the record once more after the pid is merged onto the pointer. From that merge onward a discard is refused by discard's own liveness test, so the second read closes the span rather than narrowing it: a discard it finds refuses the launch and the rollback stops the worker it already holds a pid for. Nothing between the fork and the merge is covered by a check that runs before it, and that is the reason the second read sits after the merge rather than before.
