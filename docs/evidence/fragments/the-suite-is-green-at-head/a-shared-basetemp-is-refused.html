a-shared-basetemp-is-refused — a basetemp a live session holds is refused before the second session removes anything

Defect. At startup pytest removes and recreates an explicit --basetemp (TempPathFactory.getbasetemp, _pytest/tmpdir.py: if basetemp.exists(): rm_rf(basetemp)). This suite's session reaper, reaped_watch_producers in tests/conftest.py, then signals every crew watch producer whose RECKON_HOME lies under the same root. Two sessions given one basetemp therefore destroy each other: the second removes the first's in-flight configuration homes and watch seats, and a dispatch then refuses with WatcherRequired. Measured by s22-coord at ~/.config/reckon/crew/reports/reckon/s22-coord/reflex-tests-environment/report.md.

Fix, one commit. tests/conftest.py's pytest_configure now takes a lock when config.option.basetemp is set. The lock is a file beside the basetemp directory (basetemp_lock_path = basetemp.parent / (basetemp.name + ".lock")), never inside it, because the directory it guards is exactly what a session removes at startup. acquire_basetemp_lock writes this process's pid with O_CREAT | O_EXCL; a lock whose recorded pid is alive is refused (BasetempInUseError → pytest.UsageError, exit 4) before pytest removes anything; a lock whose pid is dead is removed and the acquisition retried. The lock is released at unconfigure through config.add_cleanup, so a clean exit frees the basetemp for sequential reuse, and a crash leaves a stale lock that the next session takes over. Only the explicit-basetemp path is touched; a default numbered basetemp is unaffected.

Evidence — three cases, each driving two real child pytest sessions connected to the repository's conftest with -p tests.conftest, in a temporary directory outside any repository (tests/test_a_shared_basetemp_is_refused.py):

  • Refused, first session intact. The first session holds the basetemp and writes a pid-named fixture under its tmp_path; the second session exits non-zero with a message naming the first's pid and the basetemp, the first is still running, and its fixture file is unchanged.
  • Sequential reuse starts normally. A session run after the first exits acquires the same basetemp and passes (the lock is released on clean exit).
  • A dead pid is taken over. A session killed with an unreleased lock (its pid then dead) is followed by a session that acquires the same basetemp and passes.

Measured (base vs head), both arms -n 8, each with its own --basetemp under $TMPDIR. Head (531027092, lock present): 3 passed, EXIT=0. Base (531027092, lock absent; new test file against the unmodified conftest): 2 failed, 1 passed, EXIT=1 — the head arm adds no failing id. Logs in the run record: logs/head-arm-xdist.log, logs/base-arm-xdist.log.

Declared negative control, executed and logged. Remove the basetemp lock in a scratch tree; the second concurrent session then deletes the first's fixture directory and the case fails. Log logs/negative-control.log: 1 failed, EXIT=1, failing id test_a_second_session_is_refused_and_the_first_keeps_its_fixtures, failing on “the second session removed the first session's fixture directory” — the two sessions rebuilt the same numbered tmp_path directory, so the fixture file is named for the pid that wrote it; without the lock the first session's file is gone.

Existing guards unchanged. tests/test_watch_arming_isolation.py (the scheduler guard and producer reaper) run at base and head under -n 8: 2 failed, 6 passed at base and 2 failed, 9 passed at head, the same two ids failing in both arms — the head arm adds the three new passing ids and no failing id. The two failures are pre-existing and outside this node's scope (see follow_ons).

Scope. Only tests/conftest.py and the new test file change; no product source is touched, no test is skipped, xfailed, deleted or weakened.
