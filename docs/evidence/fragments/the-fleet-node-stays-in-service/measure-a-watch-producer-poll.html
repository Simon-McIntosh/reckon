A watch producer sweeps the whole fleet every second

The poll is watch_ticker in reckon/crew/recovery_watch.py. Each cycle does five things whether or not anything has moved:

  • It lists live/ for every project before filtering (runs.py:705, runs.py:720).
  • It reads the handover and lift documents.
  • It re-takes liveness for every live pointer, with a signal-0 probe and a /proc descendant walk (recovery_watch.py:1050).
  • It parses run stream files for metering and head fingerprints.
  • It calls git through the worker shim for its sweeps.

The cycle period starts at 1.0 s and doubles to a 30 s cap only while the project lists no live pointer. The ledger reader is lazy, firing only when a run departs, so a project's recorded-run count is not a per-cycle cost.

The figures come from two 32 s windows on 98dci4-clu-2002 at revision 517c1d323. A producer instance was run with strace -f -e trace=%file,getdents64 and profiled with py-spy record --rate 100 -d 20. The worker's namespace could not ptrace the live producers (EPERM), so it profiled instances of the same code against an isolated crew home that held a copy of the fleet's 48 live pointers. One populated cycle costs about 1,880 openat, 1,575 stat, 1,396 newfstatat, 618 lstat and 146 getdents64 calls. It also makes 1.25 calls to the git shim. Each shim call spawns the shim, dirname and a Python process, and the window shows about 2.9 real git executions per shim call. That is 114 to 115 git executions in 32 s. JSON decoding takes 31 to 35% of profile samples. The cost does not scale with the live pointer count: the 4-pointer and 11-pointer projects carry the same totals to within a few per cent.

The corrected git figure comes from the independent review. The report delivered 2.5 shim calls per cycle, which counted dirname's execve lines as shim spawns. A recount of the delivered strace files gives 40 shim executions for power_convertor and 41 for imas-codex, and 114 and 115 executions of /usr/bin/git.

On the live node five producers run this cycle. That is roughly 9,000 file opens a second against GPFS. Git alone accounts for about 35 of the node's measured 80 process creations a second.

What the evidence does not show is why the live imas-codex producer averages 56% CPU against power_convertor's 8%. Neither scratch arm reproduced its live figure: power_convertor's scratch instance sampled 37% against 7.9% live. The two frames that best fit the live gap are _terminal_lane_signal (recovery_memo.py:466) and _cached_stream_entry (_backends.py:2565). Attributing it needs a profile of the live process taken from outside a worker sandbox.

The change that makes the poll change-driven is this: watch the crew home's live/, runs/ and watch directories with inotify, or gate the cycle on one mtime stat of them. Run the listing, the run-directory walk and the git sweeps only when that fires, and keep only the per-run liveness probe on the fixed beat.

Raw artefacts are under ~/.config/reckon/crew/reports/reckon/the-fleet-node-stays-in-service/measure-a-watch-producer-poll/: report.md, the two strace files, the py-spy raw profiles and the gate logs. The review scored the node 85 out of 120.
