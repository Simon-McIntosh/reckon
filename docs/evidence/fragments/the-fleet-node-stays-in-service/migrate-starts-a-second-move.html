The migrate command starts a second move

Finding. reckon fleet-node migrate read the newest move-*/ledger.json and, once its next_step was done, returned migration complete on every later invocation. Because the census step was reachable only when no ledger existed, the command could carry exactly one move, so a fleet that had since been replaced left the command reporting a stale completion.

Change. In fleet_migrate.migrate, a ledger whose next_step is done always makes the next invocation begin a new move at census, writing a fresh move-<stamp>/ledger.json and leaving the earlier ledger untouched; --dry-run reports the census step. The rule is unconditional — it does not consult the fleet record — because census and layout only read state, so a new move starts nothing costly, and the measured case has the fleet record still naming the same drained job the last move promoted, which any fleet-record comparison would read as "no move due".

Status wording. fleet_node.describe_allocation no longer says "the allocation ends when the drain completes" (the reverse holds — the drain completes when the allocation ends). The warning now states that the scheduler places no new job on the node, that the allocation continues until it ends, and that the node returns only when an administrator resumes it.

Evidence. Focused tests pass in tests/test_migrate_starts_a_second_move.py (4 selected): a completed ledger whose fleet record still names the job the move promoted announces the census in --dry-run and writes a new move ledger while leaving the old bytes untouched; a completed ledger whose fleet record names a different job does the same; a ledger at cutover still resumes its move rather than starting a census; and the drain warning carries the three replacement statements and not the old one.

One assertion in tests/test_fleet_migrate_cutover.py was updated in the same commit from == "migration complete" to a census --dry-run: it encoded the retired behaviour and is a direct consequence of the corrected rule. That file is outside this node's declared write scope; the change is one line and is called out in the commit body and manifest.

The related suites (test_fleet_migrate*, test_fleet_node) pass 91 tests.

Negative control. Declared string: "a ledger at cutover must resume its move, not start a new census". Applying the mutation — starting a new census for every ledger, not only a done one — makes the cutover ledger start a census, and the cutover test fails with assert 'census: read…' == 'cutover: sessions still to move: one-fleet' (1 failed, 3 passed). See negative-control.log in the run record.

Commits and paths. reckon/crew/fleet_migrate.py (done ledger advances to census), reckon/crew/fleet_node.py (drain-warning wording and the comments that described the old behaviour), tests/test_migrate_starts_a_second_move.py (new), tests/test_fleet_migrate_cutover.py (one retired assertion updated).
