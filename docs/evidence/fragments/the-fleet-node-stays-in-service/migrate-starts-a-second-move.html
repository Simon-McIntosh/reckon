The migrate command starts a second move

Finding. reckon fleet-node migrate read the newest move-*/ledger.json and, once its next_step was done, returned migration complete on every later invocation. Because the census step was reachable only when no ledger existed, the command could carry exactly one move, so a fleet that had since been replaced left the command reporting a stale completion.

Change. In fleet_migrate.migrate, a ledger whose next_step is done is compared against the fleet record: a record naming a job other than the one the move's stand_up promoted means the allocation has moved on, and the invocation begins a new move at census, writing a fresh move-<stamp>/ledger.json. The earlier ledger is left untouched, --dry-run reports the census step, and a record still naming the move's own job keeps the previous migration complete behaviour.

Status wording. fleet_node.describe_allocation no longer says "the allocation ends when the drain completes" (the reverse holds — the drain completes when the allocation ends). The warning now states that the scheduler places no new job on the node, that the allocation continues until it ends, and that the node returns only when an administrator resumes it.

Evidence. Focused tests pass in tests/test_migrate_starts_a_second_move.py (4 selected): a completed ledger with a matching fleet record reports migration complete in both dry and non-dry runs and writes nothing; a completed ledger with a moved fleet announces the census in --dry-run and writes a new move ledger while leaving the old bytes untouched; a ledger at cutover still resumes its move rather than starting a census; and the drain warning carries the three replacement statements and not the old one. The related suites (test_fleet_migrate*, test_fleet_node) pass 91 tests.

Negative control. Declared string: "a ledger at cutover must resume its move, not start a new census". Applying the mutation — reading the fleet record for every ledger rather than only a completed one — makes the cutover ledger start a census, and the cutover test fails with assert 'census: read…' == 'cutover: sessions still to move: one-fleet' (1 failed, 3 passed). See negative-control.log in the run record.

Commits and paths. reckon/crew/fleet_migrate.py (census-on-done move), reckon/crew/fleet_node.py (drain-warning wording and the comments that described the old behaviour), tests/test_migrate_starts_a_second_move.py (new).
