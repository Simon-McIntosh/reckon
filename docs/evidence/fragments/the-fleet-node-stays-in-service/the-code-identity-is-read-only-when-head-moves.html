The code identity is read only when HEAD moves

Result. source_code_identity now holds its reading against a fingerprint of the files HEAD resolves through — HEAD, the ref it names and packed-refs — located by reading .git and commondir rather than by spawning git, so a worktree whose .git is a file is fingerprinted through its gitdir. The git reads in _committed_reload_tree run only when that fingerprint moves. A read that did not complete is never held, so IDENTITY_UNKNOWN keeps the meaning it was given.

Every git invocation is counted as the module spawns it, and the spawn assertion is taken immediately around the identity read so the assertion measures the read and not the commit that precedes it. The suite clears RECKON_FOLLOWER_SOURCE_ROOT for every check, because the production call shape resolves its root from that variable and an ambient value would answer every read from a checkout the fixture never made; the gate is run twice, once with the variable unset and once set to this worktree, and passes 8 passed in both.

Why no new reader, and why packed-refs needs no watch of its own

reckon/git_dates.py already reads HEAD and the ref it names as files without spawning git, and reckon/change_streams.py already holds its stream against that reading. The hold uses it directly (source_code_identity reads git_dates._head_identity), so the four helpers written for this change — a git-directory resolver, a commondir follower, a file fingerprint and a head fingerprint — are deleted rather than kept beside the ones that already did the same work.

_head_identity does not watch packed-refs, and a commit that moves a branch moves the identity anyway: a commit writes the loose ref, changing its mtime, inode and size, and the ref's presence is part of the identity, so git pack-refs — which deletes that loose ref into the packed file — moves the identity as well. A packed-ref that later moves without a new commit changes no commit id, so there is nothing to re-read. The git pack-refs check covers this and passes.

Scope of the hold

The hold covers the checkout this process runs from: the root resolved when no other is named, which is the shape the followers, producers, MCP server and queue admission all use. A caller that names a source root is answered from that tree on every read. A blanket hold was written first and measured against the existing cohort: it served its reading over test_a_timed_out_catalogue_read_reports_unknown_not_an_absent_catalogue, whose second read interposes a failing catalogue read at an unmoved fingerprint, so the failure could not surface and the check was red. The hold being scoped to the process's own root is what keeps that failure path reachable.

Negative control

Declared mutation applied to a scratch extraction of the head revision: a commit touching nothing under reckon/ or skills/ moves the stamp, so the git reads run, and the identity is unchanged. The mutation drops the ref HEAD names out of git_dates._head_identity in the scratch copy, where the hold now reads it, so such a commit moves no stamp.
