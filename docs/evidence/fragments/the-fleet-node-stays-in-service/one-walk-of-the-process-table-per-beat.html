One walk of the process table answers every run in a beat

The liveness read's environment reach walks the process table once per beat, not once per run. _walk_marked_processes visits /proc once and files every process of this user that carries a run mark under the pair (run mark, crew home) its own environment resolves to; _processes_owning_run answers a run by looking that pair up, and its new from_beat_map keyword takes the answer from this beat's walk (_beat_marked_processes) instead of walking again. recovery_liveness._env_scan_run_pid — the only caller reached once per live run in a producer's sweep — asks with from_beat_map=True, so the first run scanned in a beat walks the table and every other run scanned in the same beat is a lookup on its own pair. The key stays the pair and never the mark alone, so a process carrying another crew home's run id is still never named as this run's worker. A beat is the interval the fleet's producers poll on, armed at one second (BEAT_SECONDS); a run asked in a later beat walks afresh, so a worker that started after the walk is found on the next beat. The stop path does not read the map at all: _run_process_pids keeps from_beat_map=False and walks the table afresh at signal time, with its start-tick floor and crew-home checks unchanged, because a map up to one beat old must never select a process to signal.
