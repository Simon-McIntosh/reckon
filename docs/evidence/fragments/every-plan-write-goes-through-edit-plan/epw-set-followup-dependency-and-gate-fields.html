Followup text, section dependencies, gate text and null removal

edit_plan accepts three further set paths over the same handlers the section fields already use, and a null value that removes a key instead of writing one. No new verb is added. An open followup's title and body are authorable through followups.<id>.title and .body. A section's dependencies are written through section_depends_on.<sid>, as the list of [project:]slug#section refs the roadmap's own grammar accepts. An open gate's measure and required_evidence are authorable through gates.<id>.measure and .required_evidence. Each field lands where the plan's own writer reads it: a followup and a gate are typed records the state writer renders from the working state, so those two write the record; the dependency mapping is a plan-section-depends-on head meta the state writer leaves untouched, so that one queues an authored-HTML edit which reads the current mapping, sets or drops the one section's entry, and rewrites the meta — the same read-modify-write shape the section title uses.

A null value removes the key for four kinds. section_depends_on.<sid> drops that section's entry, and the meta comes off the page entirely once the mapping is empty. section_declarations.<id> drops a declaration and its record. A decision field other than choice is dropped. An optional top-level scalar is dropped, which needs an explicit meta removal because the state writer emits a plan-* meta only for keys present in state and never removes one for a key that has gone. A field whose absence the plan cannot express refuses its own removal and names itself, so decisions.<key>.choice and a required scalar each keep their value.

Four refusals bound the surfaces. A resolved followup is refused for a text write, and a gate whose verdict is passed or failed is refused, because text settled against an outcome is a record of what was done rather than a plan. A dependency ref outside the grammar — one naming no target section — is refused naming the ref. A null section_declarations.<id> while its heading is still authored is refused: a declaration and its heading are one statement, and removing the declaration alone leaves an undeclared heading. That check is judged against the document the write is about, in the write pipeline, rather than trusted from the caller, because the same state is refused by the coverage guard on the way back in — the handler refuses first and names the path, so the caller learns which of the two it met.

The control this node declares — make the heading-presence refusal in apply_declaration_removals unreachable, so a null declaration is accepted while its heading still exists — was applied at the node head in a scratch export. The case then failed, test_null_declaration_while_its_heading_exists_is_refused, logged at negative-control.log with EXIT=1, and the mutation was reverted without being committed. It takes that shape only because of what the first run showed: with the removal accepted, the write is still refused by the pipeline's coverage guard, whose message reads authored section heading 's1' carries no section_declarations entry. The test as originally written asserted only that the write was refused, which both guards satisfy, so it could not tell which had spoken and the declared control passed through unaided. The assertion now requires the refusal to name section_declarations.s1, the handler's own message, and the control bites. The behaviour was correct in both runs — what changed is that the test can now distinguish the guard it means to exercise from the backstop behind it.
