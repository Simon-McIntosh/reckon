The reload's untested branches have cases, and one of them was a defect

The MCP server's current-code guard decides a failed call on three facts about the child interpreter it runs behind the stdio front: whether the child's parameter list disagrees with the registered one, whether the child reached the tool at all, and what the child answered. All three now have a case in tests/test_mcp_server_serves_current_code.py, driven through the same temp-checkout harness the file already used, over the crew tool rather than edit_plan: a current-code answer that is itself a failure (crew_answers), a child that never reaches the tool because the moved checkout no longer serves it (crew_never), and a child that makes no answer at all because the interpreter dies inside the call (crew_silent).

The second case exposed a defect, and it is the one this section's fix repairs. The child protocol reported a tool's parameter names and its answer, but said nothing about whether it ever found the tool. A child that found none therefore reported empty parameters — which the guard already reads as no signature change — and its own crash was then served as the checkout's answer, marked with the checkout's stamp. Reproduced at the node's base revision (2cbe964a), the second call returned, with no code ever running the call; the child's failure was a StopIteration from an empty tool lookup: 

{'ok': False, 'error': 'crew_error', 'detail': 'StopIteration: ',
 'served_by_code_stamp': 'a9f1646d7ec0dc1c8405395989deb27223ce7c047b30d3c143c8a283592d9593'}

The child now reports reached, set once the tool has been found and before it is called, so a failure raised after that point is the tool's own answer and a failure raised before it is the child's. _current_code_answer returns None for a child that did not reach the tool, so the caller keeps the reconnect refusal rather than an answer credited to code that never ran the call. The repair is additive: a child that reached the tool is unaffected, which is why the crew-failure case passed before it and after it.

Each case has a negative control that removes the branch it covers, and each fails on its control. Removing the branch that serves a failing current-code answer as the answer (_current_code_answer restored to refusing a failure) returns the refusal instead of crew_view_refused, so the first case fails. Removing the never-reached guard restores exactly the served StopIteration above, so the second fails. Removing the child-is-no-answer branch in _answer_on_current_code raises inside the guard and the call answers as a tool error rather than the refusal, so the third fails.
