The crew page renders the open decisions the payload carries

The open decisions reach the browser on the same /crew payload as the run list: _waiting_decision_rows in reckon/serve.py walks each mounted project's plans and answers open_decisions beside runs. The crew view was handed only the runs, so the decisions that derivation produces reached no reader. The payload already carries every field a row shows — the plan slug, the key, the title, the sections the decision holds, the recommendation and its source, and the plan's own plan_modified stamp — so docs/ui/crew.jsx reads that list and formats it, and derives nothing: no status, no count, no age is computed beyond rendering the stamp it was given.

One poll answers for the page. docs/ui/shell.jsx owns the single /crew poll, and its own comment states that it hands what it receives to every surface that needs it; tests/test_a_poll_waits_for_its_previous_answer.py pins that as exactly one poller of the route, in the shell. The shell already receives the whole payload, so it now keeps the decision list beside the run list and hands both to the crew view, which renders them and polls nothing. Reading the route a second time from the view would have doubled the derivation per cycle — _waiting_decision_rows reads every mounted plan on each request.

The list starts unread rather than empty. An empty list is a claim that nothing waits, and a page that has not yet been answered cannot make it. CrewOpenDecisions therefore draws nothing until decisions is an array, and the empty line is drawn only in answer to a payload that carried no row. Measured while building this: with the state seeded as [] the empty line rendered on the first paint, before the poll resolved, and the case below read the empty line where the row should have been (polls: [], rowCount: 0 at the moment of the assertion). Seeding it as null removed the race and the same probe then answered polls: [1, 1], rowCount: 1.

Each row carries the project it belongs to, and the list narrows to the projects the page is showing, so the crew page's project filter reaches the decisions exactly as it reaches the runs. One filter does that for both lists: crewRunsForVisibleProjects takes the rows and the visible projects, and it is applied to the run list and the decision list alike, because a run and a decision each name the project they belong to. The decision list carried its own copy of that predicate, and the copy is gone.

A row links to the decision rather than to the top of the plan: the href is /<project>/plans/<slug>#decisions. The anchor was chosen by reading what the plan page actually renders for a decision. The plan reader draws the section around its decisions with id="decisions", the authored document carries the same id on <section data-reckon="decisions">, and neither the decision component nor the plan writer emits an id per decision — the decisions section is the only anchor a decision has. The reader route cannot carry that anchor anyway: parseHash in docs/ui/shell-route.jsx takes the whole fragment as the route, so #plan/<slug>#decisions would be read as the slug <slug>#decisions and name no plan at all. The row therefore addresses the plan document's own canonical route, the form canonical_href in reckon/resources.py publishes, with the decisions anchor on it. The case asserts the href the page renders and then requests the page that href names, requiring that page to carry the anchor.

tests/test_the_crew_page_shows_open_decisions.py serves a temporary project holding one plan with one open decision, drives a real browser over the served crew page, and asserts the decision key, its title, the plan link and the sections it holds as they appear in the rendered page. The second case locks the decision, waits for the next poll, and asserts the row is gone and the single empty line stands in its place. The case reads the page, not the source: no assertion opens crew.jsx as text.

Both arms ran the new case, the crew page's existing browser cases — tests/test_spa_crew_cards.py, tests/test_spa_crew_geometry.py, tests/test_spa_crew_stylesheet.py, tests/test_spa_crew_burn.py and tests/test_crew_view_serves_every_view.py — and the poll contract, tests/test_a_poll_waits_for_its_previous_answer.py. At base (3d80d654) 35 passed in 73 s and at head (2b31734f) 37 passed in 191 s, both EXIT=0, so the change adds the two new cases and no failure. No case reported SKIPPED in either arm. Each arm's log opens with the revision it ran at and the literal command it was handed, and closes with its own EXIT= line. The base arm ran over a tree exported with git archive from the base revision, because the shared .git is read-only for this run and git worktree add is refused. The filter's own case lives outside this gate — tests/test_spa_project_visibility.py evaluates crewRunsForVisibleProjects by name — so it was run at both revisions as well: 10 passed and 4 failed in each, the same four browser-mode cases (test_topbar_keeps_one_ordered_row_with_tools_flush_right at three viewports and test_first_visit_renders_live_runs_from_every_mounted_project) failing at base as at head, and test_hidden_projects_leave_crew_and_home_aggregates, the case that covers the shared filter, passing at both. The change adds no failure there either.

Two controls. The declared one — render the crew page from a /crew payload with waiting_decisions removed, and the new test fails on the missing decision key — was run by making _waiting_decision_rows answer no rows in an exported copy of the head tree: the case failed on assert '' == 'transport', the missing key, at EXIT=1. The repair's own control answers the poll finding: restoring the crew view's /crew poll in an exported tree fails the contract's crew count on assert (1 + 1) == 1 at EXIT=1, against the same check passing at head.

The repair for the poll finding needed docs/ui/shell.jsx, which the repair round's write scope did not list. The shell is the only surface allowed to poll the route and the only one holding the payload, so no change confined to the crew view could both keep one poll and render the decision list; the excursion is three additive lines — one state, one assignment from the payload already received, one prop — and it is recorded as a changed path in the manifest rather than left off it.
