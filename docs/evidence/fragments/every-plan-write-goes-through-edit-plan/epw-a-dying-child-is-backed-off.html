A current-code child that keeps dying is backed off within one code stamp

The MCP server serves the checkout's current code from one persistent child behind the stdio front, started when the guard first sees the stamp move and replaced when it dies. A child that died right after every spawn was therefore replaced on every guarded call, so the session paid one interpreter import per call, and silently, because the spawn sent the child's stderr to DEVNULL. spawn_served_child was changed to write the child's stderr to a bounded file named beside the served tree, child_stderr_path(root) = <root>/.reckon-served-child.stderr.log. The file is rewritten on every spawn, so it holds the most recent child's output rather than the accumulation of every death, and the last death's cause stays readable after the child is gone.

CurrentCodeServer now counts consecutive child deaths within one code stamp (death_bound, default 3). A child found dead is dropped and counted; a replacement is started while the count is under the bound, and at the bound the server backs off and starts none until the stamp moves. While backed off, _child_for returns None, so warm and run answer nothing and the running image serves every call — the same path §11 uses for a cold child, and no answer the caller sees changes. A stamp move clears the count and the next call starts exactly one fresh child.

tests/test_a_dying_child_is_backed_off.py drives the guard over a temporary tree with a child that prints a marker to stderr and exits right after every spawn, launched through the server's own spawn_served_child so the file under test is the one the product writes. Three cases: a run of twenty calls starts no more children than the bound, every call is answered by the running image, and the server is backed off; the last death's stderr is readable at the named path and holds that death's output alone; a moved stamp clears the backoff and starts one fresh child.
