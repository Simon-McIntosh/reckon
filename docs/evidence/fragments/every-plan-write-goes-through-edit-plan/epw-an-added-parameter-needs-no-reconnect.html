§13 — An added parameter needs no reconnect

After §11 the only reconnect the guard still asked for was a changed tool signature, and it asked for any difference in the parameter list, additions included. So every landing that added a parameter made every session reconnect: §7's added request_id alone drove the 2026-10-19 and 2026-10-20 reconnects seen by imas-codex and reckon sessions. An added optional parameter leaves every call the client can make valid on the new code — a reconnect only buys the client the new parameter — so the refusal was owed for a much narrower change than it was asked for.

The rule, held by the current code. A change is compatible when every registered parameter is still accepted, no registered optional parameter has become required, and no parameter the client does not hold is required. signature_compatible in reckon/served_code.py states that rule once; the readiness probe reports each tool's parameter names beside required, the subset carrying no default. The parent sends its own registered parameters, each with whether it was required, with the probe, and the child answers compatible per tool. The child holds the rule, not the parent, so a later change to it reaches every running server without a reconnect — the probe is the one channel that crosses the image boundary.

The routing stays §11's. A call the image answers successfully is returned untouched. A call that reaches the current code — a failed call re-run there, or a call of a tool already routed there — is served when the verdict is compatible, and its answer carries a schema_note naming the parameters the client cannot send until it reconnects. A change the client's calls cannot survive — a registered parameter removed or renamed, a registered optional made required, or a new required parameter — still returns stale_server_code with its reconnect remedy, because there a reconnect is the real fix.

A parent that predates the verdict still reads the probe. A server started before this lands is the parent the new child answers. The probe keeps params as each tool's list of parameter names, exactly as before; requiredness and the verdict sit under new sibling keys, and the verdict is given only when the request carried registered parameters. A probe carrying none — what a pre-§13 parent sends — gets the answer it already understands, and that parent keeps comparing parameter names itself, refusing any difference. So a server started before this lands asks for one reconnect, and the reconnect picks this up; after that an added optional parameter needs none.

The six cases in tests/test_an_added_parameter_needs_no_reconnect.py drive the guard against a temporary tree whose fake child's probed signature and verdict the test controls: an added optional parameter on a failed call re-run on the current code is served there with a schema_note naming it and no reconnect field; a removed parameter, a new required parameter, and a registered optional made required each return stale_server_code; a probe with no registered parameters gets the parameter names and no verdict, and the pre-verdict comparison still reports an added parameter as changed; and a child whose rule answers compatible makes the parent serve even when the parent's own parameter names differ.

The two existing changed-signature cases become removals. tests/test_a_slow_child_never_forces_a_reconnect.py case 6 and tests/test_mcp_server_serves_current_code.py's signature case now drop a parameter the client registered rather than adding an optional one, so each still asks for the refusal §13 keeps. The server test's _SIGNATURE move redefines the edit_plan tool without request_id, which the parent registered and the child no longer accepts.

Each declared mutation is kept, one log per control: restoring the equality comparison (the parent ignoring the verdict) fails the added-optional case; deciding in the parent — computing compatibility from the probe's parameters instead of reading the child's verdict — fails the child's-verdict case; and nesting requiredness inside params instead of a sibling key fails the old-parent case, because a parent comparing parameter names then reads a mapping and sees no change. Every control's log ends in a non-zero EXIT= line.

The gate. At the node head the four targets run 1 failed, 23 passed and at the base revision the three that exist there run 1 failed, 17 passed, both exiting 1. The one failure is the same test in both arms, test_every_module_fits_a_worker_window, naming reckon/crew/review.py and reckon/ledger.py — two modules this node neither touches nor changes. It is present at the base revision before any of this work, so the node's own delta is zero added failures.
