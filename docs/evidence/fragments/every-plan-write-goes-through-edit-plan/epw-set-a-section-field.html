An existing section is editable through one op

edit_plan now accepts {op:'set', path:'sections.<id>.<field>', value} over five fields. Three of them — links, effort_hours and capability — are typed metadata the state writer already regenerates from the record, so the handler validates the record whole through the same SectionRecord an insert_section builds one from and changes only the working state. The other two — the h2 title and the authored body — are HTML the state writer preserves untouched, so each queues an authored-HTML edit the same write consumes, applied through the one replacement path the text editor uses. That path has two entry points over one body: the text form a caller supplies still locates its fragment by an exact-once match, and the section-field form addresses the span it located from the section's own heading and record element. The distinction is load-bearing rather than cosmetic. A section that has no prose yet authors a bare newline between its record element and the next heading, and a bare newline occurs throughout the document, so the match could not place the write a freshly created section most needs — it refused with sections.s4.body must match exactly once; found 23 occurrences. Locating by span also means an apostrophe stored as &#x27; cannot make an edit miss, the failure that made a hand text edit refuse.

Two guards keep the two write kinds from colliding with the store's own model. A section's status stays a declaration: sections.<id>.status is refused naming section_declarations.<id>, so no second spelling is added. A body carrying a heading or a data-reckon section element is refused, because it would forge structure. An unknown field is refused listing the accepted five, and a section id the plan does not carry is refused naming it.
