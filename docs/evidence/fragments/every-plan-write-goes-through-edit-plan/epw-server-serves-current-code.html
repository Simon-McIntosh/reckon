The MCP server answers a failed call on the checkout's current code

The stdio mechanism, and why re-exec cannot carry an initialised session

The HTTP server owns its process: _CodeReload drains its handlers and calls os.execv, and a re-executed image is simply a new server, because every caller reconnects to a listener. A stdio MCP server has no listener to reconnect to. Its client holds the session it opened with initialize, and a replacement process has received no initialize — the front the client is talking to would have to be discarded for the connection to survive, which is the reconnect the section exists to remove.

So the front stays and the current code runs behind it. When a call fails, the guard asks the moved-checkout owner (reckon.served_code.moved_checkout) whether the code has moved and whether the moved tree is trusted, and if both hold it runs the same call against the checkout in a child interpreter (_CURRENT_CODE_RUNNER) whose answer stands in for the stale image's. That child is disposable and holds no session, which is exactly why the mechanism can be restarted per call where the server cannot.

Three verdicts follow, and each is a case of the gate:

  • The current code answers — that answer is returned, and the session serves its later calls on the current code (_SERVE_ON_CURRENT_CODE) rather than falling back to the image.
  • The current code also fails the call — its own failure is returned, carrying the stamp of the current code and the error text under it. A reconnect cannot help when the current code gives the same failure, and returning "reconnect" there keeps the stale image's failure masked, which is half of what this section exists to fix. — delivered, unverified at the fence: see the state below.
  • The tool's parameter list changed on disk — always refused, naming that tool, because the client holds the schema it connected with and no in-process answer can stand for it.

One owner for the moved-checkout decision

reckon/served_code.py now owns MovedCheckout, code_fingerprints, served_code_moved (the HTTP server's half, comparing the executed-code report's fingerprints) and moved_checkout (the MCP server's half, comparing the checkout's code identity and running the shared trust check). reckon/serve.py calls served_code_moved and no longer carries its own fingerprinting; reckon/mcp.py calls moved_checkout. Neither server carries a check of its own.

State at hand-off

All six subprocess cases of the gate pass, and the case that was red for two attempts is the one that exposed the deepest defect. Its call is crew rather than edit_plan, and its child — a fresh import of the checkout, guard included — composed a refusal of its own and handed that back as the answer the current code gave. The guard read a refusal where an answer should have been and returned it, so the caller was told to reconnect for a call the current code had answered. The child now runs the tool rather than a second copy of the decision, and an answer that is the refusal itself is read as no answer at all, so this decision is made once, in the server the client is talking to.

Three defects were found on the way, and the first two were in fixtures rather than the mechanism: the simulated checkout-ahead wrapped the registered tool, which made the tool manager classify an async tool as sync and never await the call; a tool that raises left the child with no answer to print, so its exception is now the answer it returns; and the child's own guard was the third.

The declared negative control was run at the node head: with the current-code re-run disabled so the guard falls back, test_a_call_on_a_moved_checkout_answers_on_the_current_code fails on stale_server_code — the log records it (negative-control.log), and the mutation was reverted without being committed. The acceptance is therefore a check that can fail, not a case that passes for want of anything to test. Two failures remain in the wider gate file set, test_every_module_fits_a_worker_window and test_structural_invariants::test_only_the_shared_parser_calls_fromisoformat; both fail at the dispatch base as well, so neither is this node's, and neither is triaged here.
