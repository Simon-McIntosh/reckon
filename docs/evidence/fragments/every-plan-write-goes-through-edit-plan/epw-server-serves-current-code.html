The MCP server answers a failed call on the checkout's current code

The stdio mechanism, and why re-exec cannot carry an initialised session

The HTTP server owns its process: _CodeReload drains its handlers and calls os.execv, and a re-executed image is simply a new server, because every caller reconnects to a listener. A stdio MCP server has no listener to reconnect to. Its client holds the session it opened with initialize, and a replacement process has received no initialize — the front the client is talking to would have to be discarded for the connection to survive, which is the reconnect the section exists to remove.

So the front stays and the current code runs behind it. When a call fails, the guard asks the moved-checkout owner (reckon.served_code.moved_checkout) whether the code has moved and whether the moved tree is trusted, and if both hold it runs the same call against the checkout in a child interpreter (_CURRENT_CODE_RUNNER) whose answer stands in for the stale image's. That child is disposable and holds no session, which is exactly why the mechanism can be restarted per call where the server cannot.

Three verdicts follow, and each is a case of the gate:

  • The current code answers — that answer is returned, and the session serves its later calls on the current code (_SERVE_ON_CURRENT_CODE) rather than falling back to the image.
  • The current code also fails the call — the failure is not the stale image's, so the reconnect refusal is the answer, carrying the original error text. This is what keeps the shared trust check's reader (tests/test_one_check_trusts_a_moved_checkout.py) passing: a read the moved checkout also refuses is still refused.
  • The tool's parameter list changed on disk — always refused, naming that tool, because the client holds the schema it connected with and no in-process answer can stand for it.

One owner for the moved-checkout decision

reckon/served_code.py now owns MovedCheckout, code_fingerprints, served_code_moved (the HTTP server's half, comparing the executed-code report's fingerprints) and moved_checkout (the MCP server's half, comparing the checkout's code identity and running the shared trust check). reckon/serve.py calls served_code_moved and no longer carries its own fingerprinting; reckon/mcp.py calls moved_checkout. Neither server carries a check of its own.

State at hand-off

Cases (b) and (c) of the gate pass; case (a) failed on a defect in the test's own fixture — the simulated "checkout ahead" wrapped edit_plan with (*args, **kwargs), which changed the tool's inferred parameter list and so tripped the intended signature refusal. The fixture now preserves the signature with functools.wraps, which was not re-run before the time budget expired. No uncommitted work is left in the tree.
