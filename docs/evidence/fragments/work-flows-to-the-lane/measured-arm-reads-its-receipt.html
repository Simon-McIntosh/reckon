§26 — A measured arm is read by its receipt, not the log's last line

A partitioned arm's job script prints EXIT=<status> from its own trap, and the scheduler then writes lines of its own after that receipt. Both real base logs the section names end that way: EXIT=1 on one line and srun: error: … Exited with exit code 1 after it. The reader matched the receipt only as the log's last line, so both arms were judged unreadable with status 3 and the measured pair was discarded.

That falls hardest on exactly the nodes the measurement exists for. A node that adds a test has a red base arm by construction, because its new test fails where the change is absent, so its base log is the one carrying both the receipt and the scheduler's line after it.

The receipt is now read on its own line, last match wins, because the trap prints after everything the arm itself ran. The reason an arm cannot be read is carried from the runner to the arm, so the landing-measured refusal names the arm and says which of the two it was: no receipt at all, or a receipt disagreeing with the status the job returned.

Neither refusal says the arm did not run: an arm that produced test output did run, and the record now says what was actually missing.

Negative control: reading the receipt only as the log's last line again makes the red-base case unreadable and the run case refuse. With _EXIT_RECEIPT reverted to ^EXIT=(\d+)\n?\Z the new file reads 3 failed, 2 passed, EXIT=1, the red-base, run and disagreeing-receipt cases among the three.
