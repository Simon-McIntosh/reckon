Every launch route runs the resolved command

The call that ran the bare command

reckon/crew/resumption.py::_request_lane_availability composes a launch plan with fence=False and hands plan.argv straight to subprocess.run. A composed argv carries the backend's bare command name, so this call execs the name rather than the absolute path the launch routes resolve. It is the first call a dispatch makes that runs a backend's own command, so a host whose PATH omits a directory the flight layer declares for that backend kills the probe and the lane reads unavailable although the flight view reports the command found.

What the composed launch route already did

An end-to-end crew dispatch --backend <backend> --no-watch through the CLI, with a stub codex that exists only in a directory on the backend's declared search path and a PATH that omits that directory, launches on the unchanged code: the record's argv carries the absolute stub path behind the fence's --. The composition routes therefore already rewrite the harness element, and the surviving call is the probe above rather than the launch composition.

The reproduction, on unchanged code

The probe is driven with a marking stub on the declared search path, a PATH without that directory, and a backend entry declaring only launch: cli, command: codex and search_path. The stub never runs and the call raises: 

AssertionError: {'status': 'unavailable', 'detail': "lane probe could not run:
[Errno 2] No such file or directory: 'codex'"}

The exception text is the incident's own: a bare name the resolution had already located, raised by subprocess.run inside _request_lane_availability.

The repair

That call now resolves its command before it resolves whether the lane is up: the plan the probe composes is passed through resolve_launch_executable, the same rewrite every launch route applies, and an unresolvable backend refuses with the resolution's own message naming the PATH and the declared directories it searched.

The negative control

Restoring the bare command name on that call — the composed plan handed to subprocess.run without the resolution — fails the test again with the same text: 

1 failed, 1 passed in 4.53s
E  AssertionError: {'status': 'unavailable', 'detail': "lane probe could not run:
[Errno 2] No such file or directory: 'codex'"}

What this evidence does not show

The gate ran on the fleet node rather than on all_debug, because the time fence was reached before the submission. The baseline arm at the declared base revision was not run as a separate full-file arm at that revision: the before state is the failing run of the same test against unchanged source, and the after state the passing run at the head, which is the same comparison at a finer grain. The end-to-end dispatch test in the same file passes on both sides; it is the guard that the composition route keeps resolving, not the reproduction.
