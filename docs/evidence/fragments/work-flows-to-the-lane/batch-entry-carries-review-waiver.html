A batch entry carries the plan-review waiver

Queueing several sections in one batch call was impossible for any section whose plan carried no review. A single dispatch accepts --allow-unreviewed-plan, but a batch entry had no field for it, so each such section went out as its own call — about two and a half minutes apiece for the sections this plan was built from.

reckon/crew/dispatch_batch.py now accepts allow_unreviewed_plan on an entry, and reckon/crew/dispatch.py's queue_requests stamps it onto the stored request's dispatch_options, which is the field admission reads before it holds a request on the review gate. The waiver therefore travels the same path as the single-dispatch flag rather than a parallel one: an admission pass sees the request's own options and admits it. The value is required to be a boolean, so a batch file spelling it "false" cannot waive the review by being a non-empty string. A field the entry does not carry leaves the queue path exactly as it was, and the unknown-field refusal still fires first, naming the misspelt key.

The cases the node pins

  • A batch entry naming a plan no review covers, with allow_unreviewed_plan true, queues; its pointer's dispatch_options.allow_unreviewed_plan reads true, and the admission gate owes it nothing.
  • The same entry shape without the field queues as before, and with the project's review gate set to its enforced mode the admission gate holds it, naming the plan's missing review.
  • An entry carrying allow_unreviewd_plan is refused, the row's reason naming the unknown field, and nothing is stored for it.
  • The control the two holds rest on: with no waiver and no stored review, the gate reports the plan's review missing rather than admitting the request, so the admitted case measures the waiver and not an empty gate.
