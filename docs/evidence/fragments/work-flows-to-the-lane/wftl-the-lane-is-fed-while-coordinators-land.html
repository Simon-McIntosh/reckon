The instrument, and what it read

A working worker is a live worker process. Each run contributes one span, from its worker's own launch stamp to its exit stamp (worker_exit.launched_at and worker_exit.exited_at in the ledger). The mean is the total worker-seconds inside the ledger divided by the window's seconds; the peak is the highest count reached at any instant. Where a worker exit was never recorded the run falls back to its dispatch and completion stamps, which bound a wider interval. This definition is what makes the negative control read below twelve: the same script counting dispatch to completion read 17.2 against 6.83 on that afternoon, because a run's completion stamp lands well after its worker stopped.

The ledger is read through the store that owns it, hot rows and retired ones. RunStore.records() answers the rows still in the hot table and RunStore.durable_rows() answers a project's rows in both databases, so the read is 11,670 hot rows plus 12,227 retired ones — 23,897 runs — rather than the hot table alone. Retirement moves old rows into a separate file, and a window older than the hot table would otherwise report itself empty. For this window and its baseline the archived rows contribute no span: every one of the 148 spans overlapping the window is also a hot row, so no published figure rests on the archive for either window.

A landing record's first step time is the promotion time. Each run directory holds a landing.json whose first step is the landing commit, stamped when it was made. The cohort is the implement runs whose completion stamp falls inside the window, so the two windows compare the same population. A landing record survives only while its run directory survives, so the baseline reports 15 of its 506 implement runs with a record: that median is computed over the records that survived, not over all 506.

Admission holds are read from the verdict log, and it rotates. At the 09:42Z read admission-verdicts.jsonl held passes only from 2026-11-15 05:55 to 09:41, hours after the window closed, so the window, the baseline and the control all report null with a note rather than a zero: nothing there was measured. The window's admission figures are therefore the 02:54Z read's, in the earlier committed output, where the log still held the window: eight passes, five of them holding a request on a claim under the shared crew home, over six pointers. A hold counts for this gate only where the path its detail names lies under that home. The six pointers each named a review record under ~/.config/reckon/crew/runs/…/review-records/ — the file name is read after the wording that introduces it, so a path holding an apostrophe is still read whole rather than shifting the parse.

Identity files are counted at the window's end, not at read time. An identity file is written once, when its process first publishes it, so counting by modification time reports the claims directory as it stood at 01:00Z. The sweep that retires them exists as reckon crew gc --sweep-exec-identities; the hourly retention timer does not pass the flag, so nothing retires these files and the count only grows.

The ledger takes late writes for a window that has closed. A run that completed inside the window can be written to the ledger hours after, so a repeat read moves the digits: the 02:54Z read reported a mean of 20.72, a median of 90.9 minutes over a cohort of 36 and 10,959 hot rows, while the 09:42Z read reported 23.55, 92.5 minutes over 39 and 11,670. Both reads agree on every verdict. The baseline moves with it — 3.71 became 4.34 — and its median promotion wait is computed over the records that survived, 15 of 506. Three adjacent windows (20:00–00:00, 22:00–02:00 and 17:00–21:00) read means of 18.44, 27.18 and 8.81 and medians of 97.2, 92.0 and 112.4 minutes, so no window in reach meets the twenty-minute bound, and the start-hour choice raises the mean rather than producing it.
