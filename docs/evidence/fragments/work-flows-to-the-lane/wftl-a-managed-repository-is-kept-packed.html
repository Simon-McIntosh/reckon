Every managed repository is packed daily, from a compute partition

reckon/crew/repository_maintenance.py packs one repository with git repack -a --cruft -d: reachable and unreachable objects alike go into packs, and the unreachable ones wait in a cruft pack beside its .mtimes index until git's own expiry removes them. A successful pass clears a stale .git/gc.log — the file git writes when its automatic collection fails, which switches collection off for a day — and records the object and pack counts before and after beside the repository, at <crew home>/repositories/<name>-<digest>/maintenance.json.

The schedule is the station, which is the fleet's long-running service. MaintenanceSweep is called on the station's tick and submits one pass as a scheduler job for every managed repository whose recorded pass is older than a day, and none for a repository whose pass is younger. A user systemd timer cannot carry this: the cluster refuses lingering, so a timer stops at logout while the station runs as long as the fleet does. The submitted job runs the same crew gc --maintain --repo verb a hand run uses, so the two paths cannot drift.

The crew view that reports repositories (fleet_index.compute_project_row, read through the fleet view) now carries the repository's loose-object count and the time of its last pass, read from the record. The view does not walk each object store: the count is already written by the pass.

One pass over a repository above git's own threshold

tests/test_a_scheduled_maintenance_pass_keeps_a_repository_packed.py builds a temporary repository whose gc.auto is 100 and writes 150 unreachable loose blobs, which is what a discarded run and a landing pass's conflict check leave behind, plus a stale gc.log. The test reads the loose count before the pass as 153, above the threshold; after the pass it is 0. The unreachable object is still readable with git cat-file -e and the repository holds a cruft pack, so the objects moved rather than being dropped. The gc.log is gone and the record says it removed it. The recorded counts match the counts read independently from the repository before and after, and the fleet row reports the recorded loose count and pass time. Two further cases cover a second pass leaving a packed store exactly as it found it, and a pass that cannot run (a zero timeout) recording its failure and leaving the gc.log in place, since clearing the file without packing would switch collection back on to fail on the same population.

The schedule needs no hand command

tests/test_the_schedule_needs_no_hand_command.py drives one station tick with two managed repositories: one whose recorded pass is two days old and one whose pass is an hour old. Exactly one script is submitted, naming the stale repository and not the fresh one. The script's #SBATCH --partition= is read back as all_debug, a compute partition, and the submitting argv names the same partition — the station submits from inside the fleet's own allocation, where a launch naming no partition is refused as an implicit nested job. The script's working directory is read back and required to sit outside every managed repository: python -c puts the working directory first on the import path, so a job started in the checkout would run that checkout's reckon rather than the installed one. A third case shows a refused submission reported on the station's stream without stopping the other repository's pass.
