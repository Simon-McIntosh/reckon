§16 — A launched run owes no queued duty

A session's obligations are derived once per station tick and served from the published snapshot while that tick is current: the station answer is replaced only when the derived payload's identity moves, and both readers serve it while its heartbeat is under the 120 s STATION_STALE_SECONDS window. A tick held in the per-project refresh stage for minutes therefore serves an answer computed before a launch, and a request the admission pass launched in that interval kept its queued-awaiting-session row whose published next command is reckon crew dispatch — the action that would put a second worker on a run already working. The read-time settlement (without_departed_run_duties, used by the obligations view, the prompt and stop hook, and the station answer the follower relays) dropped such a row only when the run's pointer file had been removed, which a launched run never does: launching moves the pointer's phase from queued to starting and then working.

The settlement now also compares a queued duty against the phase its run's pointer carries at serve time. QUEUED_POINTER_DUTY_KINDS (run-queued, queued-awaiting-session, queued-contract-refused) are owed only while the pointer reads queued; an absent pointer still settles the row, and a pointer present but unreadable keeps it, because an unreadable file is not evidence that the run moved. One read per run per served answer, cached within the call, so a snapshot served minutes late answers from the fleet as it reads now. A request still queued keeps its duty through the same snapshot, and every kind outside the queued family is untouched.
