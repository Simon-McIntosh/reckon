A fenced worker's /tmp is its own scratch directory

The fence sealed the node's /tmp read-only and granted the run its own scratch directory as TMPDIR, but every worker, and the standing guidance each job follows is written with TMPDIR=/tmp, kept writing the literal path. Those writes met the seal and failed with Read-only file system: at least eight runs did so between 09:00 and 10:40Z on 14 November, one of them recording its own negative control failing as tempfile.mkdtemp failed on fenced read-only /tmp.

The composition now mounts the run's own scratch directory over the node tmp, after the read-only seal, so every /tmp path a worker or its tools write lands inside that scratch whatever TMPDIR says. The seal stays beneath the mount: a sibling run's scratch and every other session's file under the node tmp read as absent rather than merely read-only, and only the runtime paths a launch must write — the fleet's sockets and codex's sandbox marker directory — are re-bound inside the fence's view of the node tmp. A scratch root that is not beneath the node tmp mounts nothing, so a purely synthetic scratch never invents a /tmp it does not own.

Measurements run on all_debug, one arm at a time, each arm's log carrying its revision, tree, working directory and command as its first line and its own exit status as its last. The three negative-control arms name gate-negative.log (the dropped mount), gate-negative-without-seal.log and gate-negative-runtime-creation.log in the run directory.
