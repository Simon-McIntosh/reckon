A refusal outlives the run it asked about

A refused or failed promotion request stays in the requests directory, and every obligations read projected it into a promotion-failed duty with a next command that can no longer apply. The row survived its run being promoted by hand, landed, or discarded, and crew ack could not defer it either: a discarded run has no live pointer and no ledger record, so the deferral was refused with "no live run … and no ledger record for it".

The reproduction below was taken against the assigned base before the repair, with the settlement phase present and its behaviour absent: the duty list still names the promoted run after an in-process promotion, and the acknowledgement exits 1.

promotion_requests now settles a refusal when its run has arrived where the refusal asked it to go: a discard marker settles the request as discarded, a ledger row for the run settles it as landed, and a run with no live pointer settles it as gone. The request file is rewritten in place with the refusal kept, so the record stays readable and a reader skips any phase outside ERRORS without a second store to reconcile. A promotion that succeeds in the caller's own process calls settle_requests_for, which is the case a coordinator's crew complete --wait creates: the queued request for that run is settled rather than drained again.

crew ack files a deferral for a run with no live pointer, resolving the project from the run's ledger record first, then the caller's own --project, then the promotion request the run left behind — and refuses only when none of the three names one.

The sibling test that asserted the retired behaviour now asserts the settled one. With the pointer gone and no promoted row naming its own run, a refusal used to raise a duty; it now reads promotion-settled as gone and keeps the refusal's recorded error, in all four parametrisations. That file was reported as an outside-scope finding in the first delivery and was brought into this node's write paths for the repair round.

The settlement reads the ledger row before the pointer, so a run that landed and whose pointer has since gone is recorded landed rather than gone. Two tests hold it: one for the landed row with no pointer, one for a run with neither a record nor a pointer settling as gone.
