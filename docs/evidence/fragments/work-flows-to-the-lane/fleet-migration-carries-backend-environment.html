A fleet hold carries the backends' environment

At base 6ff4f572a2f9c924c8ead49acb0483323fe2f8d2 the generated hold script exported no PATH, so the batch step handed every session and service whatever environment the submitting shell carried. Composing a hold from a submitting environment whose PATH is only /usr/bin:/bin left codex unresolvable: the run printed hold PATH export: ABSENT — services inherit the submitting PATH and command -v codex: MISSING (exit 1) (logs/live-hold-path-base.log). That is the fault reported for the move to job 1313886 on clu-2001, where every codex dispatch failed until a link was placed in ~/.local/bin by hand on 14 November.

In reckon/crew/fleet_node.py, declared_backend_directories reads every search directory the resolved flight declares for a backend, and hold_path composes the submitting environment with those directories appended. generate_hold_script takes the submitting environment and writes one export PATH line above the supervisor it execs, so the sessions and services the hold starts inherit the composed PATH. A directory the submitter already holds is never displaced, because the declared entries go after the inherited entries. The same script is composed for a named fleet and a standby hold, since both run the same body.

In reckon/crew/fleet_migrate.py, unresolved_backend_commands asks which commands the flight places in a declared search directory are still absent from the composed hold PATH, and verify_backend_commands refuses with a message naming both the command and the allocation. It runs in the promote step before the reservation is replaced and before the supervisor is asked to publish the new fleet record, so a refusal leaves the fleet record naming the node that still serves every backend. A backend that declares no search directory is not judged there: its location is a fact about the submitting environment, which a hold cannot add to either.
