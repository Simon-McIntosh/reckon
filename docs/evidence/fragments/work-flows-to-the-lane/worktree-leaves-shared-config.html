§18 — A worktree leaves the shared configuration alone

The defect. Worktree creation wrote extensions.worktreeConfig into the shared checkout's configuration on every dispatch, though the setting is a property of that checkout and reads true after the first one. Two concurrent dispatches therefore contended for the shared configuration lock, and one was refused outright. The base arm reproduces it verbatim: worktree creation failed: git config extensions.worktreeConfig true at …/repo: error: could not lock config file .git/config: File exists, raised from _give_worktree_minimal_stat.

The change. reckon/crew/routing.py reads the setting with git config --bool --get first and writes it only when absent (_enable_shared_worktree_config, returning whether it wrote). When the write is needed and git reports that it could not lock the configuration file, the write is retried every 50 ms for up to 5 s; a lock still held at the bound is named in the refusal, with the lock path resolved from git rev-parse --git-common-dir, because a dispatch that fails here otherwise reports only that the worktree could not be created. The worktree's own core.checkStat=minimal is set as before, in the worktree's configuration rather than the shared one, so an already-enabled setting still yields a minimal-stat tree.

Each arm is one log whose first line names its revision, tree and command and whose last line reads EXIT=<code>. Both ran on all_debug, one at a time.

Negative control. Making the shared write unconditional again turns the held-lock case red: with the setting already true and .git/config.lock held, creation refuses, and the second test observes the setting rewritten. Log: runs/…-worktree-leaves-shared-config/negative-control.log (2 failed, 2 passed, EXIT=1).

What the new test pins: with the setting already true, creation succeeds while the shared configuration's lock is held and leaves that file's content, mtime and inode unchanged; a repository without the setting gets it once, and a second call writes nothing; with the setting absent and the lock held, creation waits out a lock released inside the bound and succeeds; a lock held past the bound refuses, naming the lock; the new worktree reads core.checkStat=minimal.

Review repair: the git calls reuse the module's own runner. The configuration reads and writes first each built their own git subprocess beside _git, the git runner this module already carries, so the new path repeated that runner's argument shape, output capture and decoding. All four calls now go through _git, and the worktree-config region holds no hand-rolled subprocess call. The repair changes no behaviour, which the suite arms show: reverting the repairing commit restores four hand-rolled calls where the head has none, and the suite is green at the head either way. Control: runs/…-worktree-leaves-shared-config/negative-control-reuse.log.
