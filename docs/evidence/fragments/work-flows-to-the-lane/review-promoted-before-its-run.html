A run's queued review is promoted before the run, and the run waits rather than being refused

On 13 November the reviews of two runs were requested at 15:02 and 15:04Z and the implementations of the same runs at 15:04Z. The promotion service took up the implementations first and refused both as terminal for having no complete independent review stored, while the reviews that would have licensed them sat in the same queue. A refused request stays refused, so a coordinator had to notice and re-request work that was about to become promotable.

The drain now reads a review run's subject from its own node id (review-of-<run>) and starts that review ahead of the run it reviews whenever both are waiting. Every other request keeps the plain name order the queue has always drained in.

A run refused only because the review it needs is still queued has its request written back as waiting instead of terminal, so the pass after the review promotes it with no second request. A run refused for anything else, or whose review is neither queued nor stored, is refused exactly as before. The refusal text is owned by constants the predicate reads, so the waiting case is recognised from the message the refusal actually writes, and a refusal carrying several reasons of which the absent review is only the first is not mistaken for a request that should stay queued.
