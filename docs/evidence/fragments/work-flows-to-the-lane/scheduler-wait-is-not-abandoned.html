A wait on a batch of scheduler jobs is read as a row that names what it asked

A probe that hands a script a comma-separated batch of job ids — python …/wait_jobs.py 1312389,1312390,1312391 — now names those jobs to the classifier. Before, a job id was read only from a job flag or from a scheduler command's operand. The interpreter separator set splits a comma-separated operand into its digits, where a run of bare numbers is indistinguishable from pids, so the batch arrived as none and the scheduler was never asked. The row then asserted that no scheduler job was alive on a question nobody had put.

The classifier asks one squeue query about the whole batch and the run stays waiting while any of them is listed: one completed job beside five still running is a healthy wait, and asking per job would call the wait dead on the one that finished. Three readings are now distinct on the row. A live job in the batch keeps the run waiting. A batch the scheduler listed none of reads as nothing can lift it, and the row names the jobs that were asked about. A wait naming no job reads as it did before, and its row says the scheduler was not consulted rather than that no job is alive. Every one of them names the run's own process, so the reading can no longer be acted on as a stopped project watch producer.

Measurements run on all_debug, one arm at a time. Both arms carry their revision, command, imported module and working directory, and end with the process exit status.
