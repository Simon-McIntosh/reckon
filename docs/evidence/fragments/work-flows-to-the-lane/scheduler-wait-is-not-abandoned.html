A wait on a batch of scheduler jobs is read as a row that names what it asked

A probe that hands a script a comma-separated list of two or more job ids — python …/wait_jobs.py 1312389,1312390,1312391 — now names those jobs to the classifier. Before, a job id was read only from a job flag or from a scheduler command's operand. The interpreter separator set splits a comma-separated operand into its digits, where a run of bare numbers is indistinguishable from pids, so the batch arrived as none and the scheduler was never asked. The row then asserted that no scheduler job was alive on a question nobody had put.

A single bare number handed to a script stays unread, because a pid and a port are handed over the same way and only a job flag, a scheduler command or a list of two or more settles which one it is. The classifier asks one squeue query about the whole batch and the run stays waiting while any of them is listed: one completed job beside five still running is a healthy wait, and asking per job would call the scheduler's answer negative on the one that finished.

An operand carries no label, so the command decides what its number list is. A list of two or more under a command that takes ports by position — nc -z a-host 80,443 — is read as ports and names no job, and the scheduler is not asked about it. The same list handed to an interpreter beside a script is read as jobs. A number above the port ceiling cannot be a port, so a list carrying one is a job list whatever the command. Counting digits cannot answer this: the module's own port range runs to 65535, so nc -z host 50000,50001 would read as two jobs while a script handed 1234,5678 named none, and a wait on those jobs could reach producer-gone with one still alive.

A job flag's comma list is read from the raw argument vector, before the interpreter separator set splits the words, because that split breaks at the comma and kept only the first id: --jobs=1312389,1312390 and the glued -j1312389,1312390 each named the first job alone, so a wait resting on the second read as abandoned while it ran.

Four readings are distinct on the row. A live job in the batch keeps the run waiting. A batch the scheduler listed none of reads as nothing can lift it, and the row names the jobs that were asked about. A batch whose query could not be put — the scheduler command absent, or run and refusing the query — keeps the wait and its row says the scheduler could not be asked, so nothing there claims the jobs have ended. A wait naming no job, including one given a single bare number or a port list, reads as it did before, and its row says the scheduler was not consulted rather than that no job is alive. Every detail names the run's own process, so the reading can no longer be acted on as a stopped project watch producer; the classification and obligation kind keep their names, which another plan reads.
