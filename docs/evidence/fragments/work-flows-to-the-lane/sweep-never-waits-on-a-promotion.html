A session's sweep runs its promotions beside itself

What changed. The review pass in reckon/crew/recovery_review_acceptance.py promoted each finished review and accepted each clean one in the sweep's own thread, so a session holding several reviews dispatched no new review until the last promotion returned. The pass now runs in two phases: every review it owes is dispatched in the walk over the runs, and only then is each promotion and acceptance handed to a worker of its own.

The workers. PromotionWorkers in reckon/crew/resumption.py runs them at most config["promotion"]["width"] at a time — two when no layer configures it — and the sweep waits config["promotion"]["wait_seconds"] (180 s by default) for the ones it started. A promotion still running at the end keeps running, so the sweep's own time is bounded by that wait rather than by the sum of the promotions. Each worker holds the run's cross-host promotion lease for the whole job and an in-process claim, and a second sweep reaching a run already being promoted reports it in flight instead of promoting it beside the first. A promotion that raises is reported against its run in the sweep's failed list, and the next sweep reads the run as still awaiting acceptance and tries again.

The measure. tests/test_a_sweep_never_waits_on_a_promotion.py runs a temporary crew home with a stubbed promotion that takes a configured time and a stubbed review dispatch. Six assertions hold: the newly delivered run's review is dispatched before the first promotion completes; under a width of two the peak concurrent promotions is exactly two and all four complete; a failed promotion is named on its run and retried by the next sweep; two sweeps never promote the same run at once; the status record and recovery log carry what the report named.

What the delta says. The first arm pair left two failure ids added at the head, both since repaired. One was test_one_run_cannot_stop_a_sweep.py::test_ledger_failure_and_vanished_pointer_leave_the_third_promoted[True], whose fixture unlinks a later run's pointer from inside an earlier run's promotion and expects that run to read as vanished — an ordering only serial promotions give. Two things were wrong and both are fixed: a worker now re-reads the run's pointer at the moment it would promote, so a run that has stopped being live is reported vanished instead of being promoted from the mapping the sweep handed over; and the fixture asks for a width of one, which is the ordering it means to assert. Reverted, the id fails four runs in five; at this head it passes five of five.

The other, test_the_pane_carries_counts_not_names.py::test_a_settle_with_outstanding_runs_prints_no_line_and_still_emits, passes six of six in isolation at this head and failed only inside the 60-file parallel arm.
