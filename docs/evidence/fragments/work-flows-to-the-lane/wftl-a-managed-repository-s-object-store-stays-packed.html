A merge conflict check leaves no object in the repository it checks

The defect reproduces before the change and is quoted here rather than described. A temporary repository, a bare origin, and one conflicting candidate: running git merge-tree --write-tree --name-only HEAD <candidate> there writes the merged tree even though the merge conflicts and nothing lands, and git cat-file --batch-all-objects --batch-check=%(objectname) grows by two objects — the conflicted tree and one subtree — on every pass. The measured population on this workstation was 7,692 unreachable loose objects in the reckon checkout, about 95% of them trees, accumulated because the check runs on every pass of every candidate and gc's two-week unreachability window never expires them.

Commit b06fca782b1d423fe74cf6e14ea059fa312efee5 builds the merge in a throwaway object store: GIT_OBJECT_DIRECTORY points at a directory under the attempt's own temporary root and GIT_ALTERNATE_OBJECT_DIRECTORIES at the repository's objects, so merge-tree and commit-tree read everything they merge and write nothing the repository keeps. A merge that lands copies its delta back — every object reachable from the merge commit and not from either parent — and then reads it back with git cat-file -e <commit>^{commit}, because a pack git accepted is not a promise that the object resolves in the store it was unpacked into. A merge whose parents already hold every blob introduces only trees and its own commit, so the copy is small.

Two things were rejected. Deleting the objects afterwards is unsafe: an unreachable object can become reachable, and a peer may reference the same tree concurrently. Re-running the check in the repository after a successful build is unsafe in the other direction: the fast-forward may fail after the build, and the retry loop would then leak once per attempt.

The measure reads the store, not the report

The leak is invisible to every return value — a pass that refused the candidate reads exactly like a pass that left the repository untouched — so tests/test_a_merge_check_leaves_no_object.py reads the repository's object set directly. The first test runs three landing passes over one conflicting candidate while the fixture advances the primary revision between passes on an unrelated file, keeping the conflict intact. It wraps merge._merge_tree to count reaches, and asserts that the count equals the number of passes — every pass reached the conflict check — and that the object set afterwards equals the set before the passes unioned with exactly the objects the fixture itself wrote while advancing the primary. The second test lands a clean candidate and requires the merge commit, its tree and a blob named by that tree to resolve in the repository, so the change is not proved by an absence alone.

A seam that reads the merge with another process

The first delivered head passed a fifth argument through the verification seam so a reader could consult the scratch store, and two callers kept their four-argument signatures: one bound the object environment to a keyword default meant for the run pointer, and both then replayed the gate against a candidate that existed only in the attempt's object directory. The gate caught it — test_a_gate_failure_after_promotion_is_not_bypassed_by_recovery and test_a_clean_review_lands_and_records_the_measured_head failed at that head and pass at the base revision — and the repair is commit b275b82b99f82abbb22e110c1d7f32f4743de536: both seams copy the built merge into the repository through one named operation before they measure it, and the landing step's own copy is then a no-op.
