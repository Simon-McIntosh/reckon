A plan commit releases the requests backing off on it

A queued launch is refused with PlanVisibilityError while the plan file's working tree differs from base, and the refusal is recorded with a bounded back-off. The dependency guard already fingerprints the plan file, but it fingerprints the file: committing an edit leaves every byte of it where it was, so the one thing that cured the refusal was the one thing no fingerprint could see. Measured on 11 November: queued requests failed launch on an uncommitted plan eight times between 16:04 and 16:07Z, the plan landed at about 16:07, and those requests sat held-on-retry-backoff to retry_at 16:16:10 and launched from 16:16:44 — about nine minutes each, with the lane open.

reckon/crew/queue_admission.py now records failure_plan_commit when the recorded failure is a plan refusal: the blob HEAD holds for the plan file, read with git -C <repo> rev-parse HEAD:docs/plans/<plan>.html. A blob identity is the committed content, so it moves when the commit moves and not when the file does; a plan no commit holds yet reads absent, which the first commit that lands it also changes. _retry_backoff_hold compares that stamp for a request whose failure is a PlanVisibilityError and attempts it on the pass that differs, before retry_at. The stamp is recorded only for that refusal and dropped when a later failure is anything else, so a stamp left from an earlier plan refusal cannot release a request the plan never held. The field joins QUEUED_LIFE_KEYS, so a launched pointer keeps it under admission_history rather than carrying it as live-run state.

The gate is the new tests/test_a_plan_commit_releases_its_backed_off_requests.py: 3 passed, EXIT=0. It builds its own temporary repository and crew home, edits the plan without committing, and makes each attempt against the production check, routing.require_plan_section_visible, so both the refusal the pass records and the launch that later succeeds are the real ones. Case 1: the request is attempted once, fails with the plan's own refusal, stays held-on-retry-backoff at a pass before retry_at, stays held through a commit that touches only the project index, and on the pass after the plan's commit is attempted again and launched — probe.attempted reads ['r-plan', 'r-plan'] and the verdict is launched. Case 2: a request refused by a ValueError records no failure_plan_commit and is not attempted on the pass after the plan commit, its verdict still held-on-retry-backoff. Case 3: with the plan still uncommitted, the recorded stamp equals git rev-parse HEAD:docs/plans/plan-a.html — the committed blob the working edit has not replaced — and the request stays queued and held.

One mutation is applied and logged: ignore the plan's committed content; the first request must wait for its retry_at, deleting the comparison from _retry_backoff_hold. The run fails test_a_plan_commit_releases_the_request_it_refused — 1 failed, 2 passed, EXIT=1 — against 3 passed, EXIT=0 at head, so the release is the line the case measures and not an accident of the passes around it.
