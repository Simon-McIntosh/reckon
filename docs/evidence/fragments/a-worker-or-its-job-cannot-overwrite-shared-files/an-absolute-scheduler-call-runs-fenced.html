An absolute scheduler path runs fenced

A fenced worker's fence now puts the sbatch/srun/salloc shim in front of every copy of those tools its search path resolves, so a call by absolute path and a call by name reach the same guard — and the task the scheduler is handed re-enters the submitting worker's fence either way.

Why the guard had a door

The shims guard a launch only while the tool resolves through PATH. A worker that ran type -a sbatch and then submitted every later job as /usr/bin/sbatch never consulted the shim, so the wrapper that re-enters the fence was never built: jobs 1332134, 1332191 and 1332272 completed unfenced on a node. Only interpreter file permissions stood between a scheduler and an unfenced task, and they are the fence's last resort rather than its rule.

What changed

  • reckon/_worker_fence.py: scheduler_shields() resolves every copy of each scheduler tool on the composing node's search path and in every directory the flight layer declares for finding a backend's command — the directories launch_search_path appends to the worker's own path — skipping shims by their marker, and fence_argv overlays each with that tool's shim read-only. The copy the shim itself would forward to is bound read-only at <run>/.scheduler-bin/<tool>, a mount point resolved and made at composition because bubblewrap cannot create one below a symlink; on a job node that holds no such binary the relay is a --ro-bind-try and the shim searches its own path instead. The masks and the relay travel in the recipe's argv, so a submitted job masks its own copies too. The recipe's recorded limit now states what remains unguarded rather than claiming the route is open.
  • reckon/nested_launch.py: relocated_binary() reads the relay from RECKON_SHIM_REAL_DIRECTORY before searching, because every copy a masked search path holds is now the shim; real_binary() takes the caller's environment, and main() hands it the unmodified one. RECKON_SHIM_HOME names the shim's own directory for a shim bound at a masked path.
  • reckon/host_shims/{sbatch,srun,salloc}: self_dir reads RECKON_SHIM_HOME when the fence names one. Only the file differs at a masked path, never $0's basename, so the tool name still comes from the path the caller used.
  • reckon/crew/reports.py: the launch notice no longer says absolute paths bypass the guard, and log recognition keeps the retired wording, so a log written before this change still reads its own first line.
  • tests/test_an_absolute_scheduler_call_runs_fenced.py: three cases enter a composed fence and read the argv a stand-in scheduler records — the absolute path, the bare name, and a copy that exists only in a directory the flight layer declares.

Measured

  • The guarded thing happens. A stand-in sbatch sits one directory after the shim on PATH and records a NUL-separated argv. Head arm: calling it by its absolute path from inside the fence hands it --partition=all_debug and a --wrap= whose decoded spec carries the worker's own recipe — the same bytes the by-name arm hands it. 2 passed.
  • The declared directory is shielded too. A composition run where the composing process's path holds no scheduler at all, and the only copy sits in a directory the flight layer declares, still hands the caller a wrapped task; a mutation that reads only the process's own path fails that case with the declared directory's scheduler was reached with a bare task: ['--partition=all_debug', '--wrap=echo fenced-task'].
  • Negative control. At base revision e6d692b1 in a scratch tree the same file reports AssertionError: the absolute path reached the real scheduler with a bare task with the recorded argv ['--partition=all_debug', '--wrap=echo fenced-task'], while the by-name arm is wrapped: the exact sequence the nova run used. 2 failed, EXIT=1.
  • Gate and arms. Scoped gate at 135bb40a on all_debug: 60 passed, EXIT=0. Suite arms: base e6d692b1 58 passed, EXIT=0; after 135bb40a 60 passed, EXIT=0. ruff check and ruff format --check clean on the staged paths.

What this does not cover

Every copy of a scheduler tool this node resolves — on its own path or in a directory the flight layer declares — is masked at the shim. Two cases are not: a binary only the node a job lands on holds, and one a worker's path gains after the fence is composed. Neither is forwarded unfenced from a masked path: a masked call whose shim finds no tool refuses with status 127 and never starts the task.
