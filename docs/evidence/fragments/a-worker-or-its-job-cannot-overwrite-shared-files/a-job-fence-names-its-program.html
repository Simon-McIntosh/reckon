A job's fence names its program

A submitted job's task started the fence by the bare name in its carried argv's first element, so a node whose search path holds no fence program could not start it and the task never ran. The recipe now carries the program's absolute location, resolved on the dispatching node, and the task runs that location or refuses by name before its command starts.

What changed

  • reckon/_worker_fence.py: fence_program() resolves the fence program once, on the node composing the fence, and fence_argv writes the result into the recipe's new program field. An unresolvable program composes an empty field rather than an absent one.
  • reckon/nested_launch.py: the task bootstrap reads program, refuses with FENCE_PROGRAM_STATUS when it is empty, not absolute, absent or not executable — naming the node, the program and where it looked — and substitutes it for the recipe's argv head, so the prepare step and the task's own fence both exec the carried location and never search the job node's path. os.execvp became os.execv; a recipe that names no program is never treated as an unfenced launch.
  • tests/test_a_job_fence_starts_on_any_node.py: six cases added — the prepare step runs the carried program with an empty search path; an absent carried program refuses and names the node and the location; a recipe with no carried program refuses rather than searching even where the program is findable; a program present only at the carried location starts the task; a program present but not executable refuses; and a recipe whose head is an option still starts the task from the field.

Measured

  • Head: tests/test_a_job_fence_starts_on_any_node.py passes 10 cases and the two opt-in scheduler cases ran on all_debug from this branch — sbatch job 1327763 and srun job 1327767 on node 98dci4-clu-3141 — each a task native to another node, whose granted directory was empty on arrival, whose marker was written there, and whose redirect onto the shared interpreter was refused with Read-only file system. The refusal is not the absence of an error: the message names the node, the program and the location, and no task output follows it.
  • Negative control: the same test file against the base revision's product modules in a scratch tree - 6 failed, 4 passed, 2 skipped, EXIT=1; base runs the recipe head as the program (FileNotFoundError on the empty search path) and starts the task where the carried field is absent.
