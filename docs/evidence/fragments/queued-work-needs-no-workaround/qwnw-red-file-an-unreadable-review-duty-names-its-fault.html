What changed. A review record the reader cannot use becomes a duty row, and the row's remedy comes from the fault that read reported. That fault was produced by the first read, and the review reads this derivation memoises answered every later derivation without touching the file, so the fault was dropped: the second derivation published fewer duties than the snapshot written beside it, and the record disappeared from the view on the sweep after the one that reported it.

The skips a read reported now travel with the memoised answer (review_records.memoised_read) and are replayed into the region the current derivation opened. One holder serves every call site: the four obligation memos whose keys name the store's current entries — presence, selection, rounds and the headless read — in reckon/crew/obligations.py, and the stored-review answer in recovery_memo._read_review_once, whose key is the run's classification inputs rather than the store's entries. That last key outlives a record's deletion, so the replay itself decides: a finding is noted only while the file it names is still there. A store index that has not revalidated can answer for a removed record, and a duty naming a path nobody can open is worse than no duty. The unreadable row also states the id list the view's own projection gives it (obligation_snapshot._unreadable_record_items), which is what makes the row a snapshot reader rebuilds equal to the row the writer derived.

Merged with primary main. Main reached the same intent by another route (3573a365: a stored-review answer carries the findings its read collected, replayed through note_read_failure) and renamed the shared appender to _append_read_failure. The merge keeps one mechanism: memoised_read is the carry-and-replay holder, note_read_failure is where the file-must-still-exist rule lives, and _read_review_once calls the holder instead of repeating the carry.
