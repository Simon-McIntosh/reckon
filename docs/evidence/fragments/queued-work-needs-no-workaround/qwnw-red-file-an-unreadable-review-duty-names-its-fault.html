An unreadable review duty keeps its fault on the second reading

What changed. One obligation row exists per review record the sweep cannot use, and its remedy is read from the fault the reader reported: a record met mid-write is read again once its writer finishes, and a record that parses but holds a finding stating no claim is rewritten or its reviewing run resumed. That finding was produced by the read that first met the record, and the review reads this derivation memoises answered a second derivation without touching the file — so the finding was dropped, and a derivation published fewer duties than the snapshot written beside it. The same record then disappeared from the view on the sweep after the one that reported it.

The skips a read reported now travel with the memoised answer and are replayed into the region the current derivation opened (review_records.memoised_read, used by the presence, selection, rounds and headless review memos in reckon/crew/obligations.py and by the stored-review memo in reckon/crew/recovery_memo.py), so a cached answer says what the read that filled it said about the same bytes. The unreadable row also states the id list the view's own projection gives it (obligation_snapshot._unreadable_record_items), which is what makes the row a snapshot reader rebuilds from the stored finding equal to the row the writer derived.

Reproduced before repair

Clearing only the obligation_* memos restored the row while the stored-review memo stayed warm, which names the cache as the cause rather than the record or the reader. The verdict is product wrong: no assertion was weakened or deleted.

Disabling the replay alone (review_records.report_read_failures replaced with a no-op) makes the node's file read 3 failed / 2 passed, so the guard is what carries the cases rather than the surrounding change.
