One fleet-state derivation decodes each live pointer once

What was wrong. A derivation lists the project's live directory once, and the review-dispatch fields and the delivery reading then asked for one run by id through runs.read_pointer, which decoded that run's document again. One sweep over 300 pointers decoded every document three times: 900 decodes, measured at 23b901694b4bfec73d95be3a082d4c336d9a4101.

What changed, at the merged head. The listing and the by-id read now meet at the same memo. runs._pointer_record fetches a pointer's text only when its stat identity has moved and decodes it through file_memo.memoized, the repository's one owner of parse-per-identity; runs.read_pointer reads through that same function, so a document an earlier listing decoded is answered without reading the file. A derivation therefore reaches each pointer file once, whether it walked the directory or looked a derivation's run up by id, and the count is the population's own: 300 decodes for 300 pointers.

One rule for the copy. runs._pointer_as_read is the one place a by-id read becomes the caller's record: it deep-copies and removes the station's pid where the record names it. Deep is load-bearing, not tidier. The memo hands out one shallow copy of a document whose nested values are frozen for the region it was decoded in, so a shallow copy gives the caller nested dispatch options and section records it cannot write — and, where the freeze does not apply, nested values that are the memo's own, so a stamp would reach every later listing. The station-pid removal lives there too, so the single read is the place that answers both.

The population this node first added is gone. The merge of primary a61f278b06 brought the memo and the held listing, so published_pointers had become a second owner of the same answer — and a worse one: it stat'ed each pointer afresh at publish time, pairing a rewritten file with the older listed content. It is deleted, and obligations.live_pointer_snapshot no longer opens it; the derivation keeps its own listing under _VIEW_LIVE_POINTERS, which is what the guards measure.

The merge with primary 03d91dda. Primary had widened the by-id read with a third rule: the node's body now lives in the run's own file once it has been moved there, so a record whose node is a mapping has its definition hydrated on read, while a listing still returns the slim record it decoded. The one conflict was read_pointer, where this node had gathered the rules into _pointer_as_read and primary had written them in place. Both survive: the helper now deep-copies, hydrates the definition, then drops the station's pid — hydration where primary put it, before the pid strip — and read_pointer is again that one call. Neither side's rule was dropped and no conflict marker was committed.

What the merge costs a pre-move pointer. A pointer written before the body moved names no body file, so hydrating its definition re-reads that pointer's text: once as the reduced record every listing decodes, once for the body fields the reduction dropped. That second read is the pre-move pointer's own one-off and is charged only when a reader asks for the body, which the by-id read does; a pointer written now names node.node_body, so its definition is hydrated from the run's own file and its pointer text is read and decoded once. The arms below measure the current shape: the fixture's pointers name their body file, as the writer produces them, and one derivation still decodes 300 documents for 300 pointers.
