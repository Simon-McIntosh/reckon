The discovery cost is gone, and the ten-second bound is not met

What changed. A dispatch preview, a batch and a lane change's re-plan all answer document stamps from the working tree instead of calling _git_first_committed and _git_last_committed, each bounded at ten seconds, and the answer is cached under its own key so a reader that needs commit times never receives the approximation. The flag behind that scope is a contextvars.ContextVar, so it is not shared with a reader on another path. The lane change reaches plan_dispatch by importing it straight from the plan module and so never passed the preview wrapper; it enters the scope itself now. reckon/crew/dispatch_batch.py keys its one-derivation cache on the project and derives from the registered mount, because a dispatch from a worktree named two docs trees and derived the project twice.

The two measure files, both arms. tests/test_a_batch_derives_the_project_once.py counts the project derivations a batch of three entries costs from a worktree, and counts the git history and last-modified invocations a batch dispatch makes, with the same counter proven alive on a discovery outside the scope first. tests/test_a_lane_change_reads_no_git_dates.py records the suppression flag at the moment a lane change calls the re-plan, and reads the flag from a thread that did not enter the scope while it is open — which is what separates a per-context flag from a module global.

What the dry-run table cannot show, measured rather than asserted. A dry run resolves a placement without deriving the project, at the head revision and at the base revision alike: the instrument wraps nine discovery entry points — reckon.mcp_discovery._discover_project and discover_plans, reckon.serve.discover_plans and that scope's two git queries, and the roadmap reads in route_results, fleet_index and project_maintenance_commands — and every one of them reads zero on all fifteen runs. So this table measures contention, not this change, and §21's negative control (base wall times over ten seconds with a discovery share above 80 percent) cannot be produced by it. What the change is proven by is the two measure files above, four failures at base and four passes at head.

Where the twelve to twenty-one seconds go. A profile of one preview of the same command at load 45: 2.2 s of interpreter and imports; plan_dispatch 15.6 s of a 26.6 s command, dominated by 45 thread joins totalling 16.1 s inside the claim sweep (_repository_scope_claims 3.9 s, _grant_landing_write_paths 1.8 s, _live_conflict_rows 1.1 s, 66,546 lstat and 16,433 stat calls in one process); build_picker_inputs 4.2 s. None of it is project discovery.

Still open. The deliverable's ten-second bound is not met: a dry run of one section answers in twelve to twenty-one seconds on the fleet node at load 34 to 47. The next node should read the live-pointer claims once and for the project only, because that sweep — not discovery — is what holds a dispatch there.
