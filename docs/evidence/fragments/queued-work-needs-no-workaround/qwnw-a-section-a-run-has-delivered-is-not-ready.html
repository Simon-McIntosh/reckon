A section a run has delivered is no longer offered again

The roadmap's ready set, batch dispatch and admission now treat a section's node as not ready while that node has a live, delivered, promoted or landed implementation run, and each of them names the run that holds it. The change is fb9067dda2aa6c447ea3bb7f559283093603cf29 in this worktree. The three readers agree because the hold is computed once, in reckon/crew/section_holds.py, and feeds the roadmap's own section verdict, which is the answer admission and dispatch already derive their waits from.

The defect was structural. The roadmap's only run input was crew.list_live(); section readiness was derived from that live set and from declared holds alone, by section_readiness_verdict at reckon/roadmap.py:964, whose ready is plan_ready and not blockers. Promotion unlinks the live pointer (reckon/crew/promotion.py:251), so the moment a node was delivered the run left the only set the roadmap read, and the section came back ready. Nothing in that path could see a promoted run, which is the record promotion leaves.

The hold is read from both records a run leaves: the live pointers, where a phase of complete or a running phase holds and a stored request (queued, held, awaiting-upstream, blocked-upstream, launch-failed) or a dead run (failed, stopped, interrupted) does not; and the ledger rows, which are the only record left once the pointer is gone. Only the roles that implement a section (implement, test) are counted, so a review never holds its own section. A row's gate says what the run's check found, not whether it delivered. Every row the ledger's picker projection returns is a completed promotion: passed, not-run (the check's evidence could not be produced) and failed (the check lost and the promotion was taken anyway) all promoted a node, so none of the three is filtered out. The hold is per node: a section is held only when every node the records know of is held, so a section split into several dispatch nodes keeps the work of a node that has not been delivered dispatchable. Nodes are the dispatch node ids the records carry; a record with no node id is its section's own node. A row is the later record of the two, so it also takes its node out of the free set: a pointer released after the delivery — an attempt dropped, or one that stopped without delivering — no longer puts the section back in play.

What changed, by site:

  • reckon/crew/section_holds.py — the hold itself: held_section_blockers (:179) for a readiness answer and held_node_rows (:205) for one node about to be queued. The promoted history is the ledger's own indexed read (ledger.picker_runs), so the probe keeps no cache of its own;
  • reckon/roadmap.py:3781 — the hold is computed once per build and folded into named_holds (:4591), which is what makes it a section blocker of kind run; :4617 adds it to the condition that populates ready_sections, so a plan held only by a run reports the key rather than omitting it;
  • reckon/roadmap.py:4821 — a section held only by a run that has left the page's live set gets a section row anyway, with the holding run in its blockers;
  • reckon/roadmap.py:1948 — the wiring finding run-not-landed: a section declared done whose promoting run's head is not an ancestor of the local integration branch (main, or the checked-out branch), naming the run and the head;
  • reckon/crew/dispatch_batch.py:838 — a batch entry for a held node is answered status: held with held_by naming the run, and is not stored; the summary counts it separately at :924 rather than as queued;
  • reckon/crew/admission/readiness.py needed no change: it derives a request's wait from roadmap.section_readiness_rows, so the same verdict keeps a request that carries a readiness ref pending while the run holds the section.

The done-when is held by tests/test_a_section_a_run_has_delivered_is_not_ready.py over a temporary repository and crew home: a promoted row on alpha#s1 leaves s1 out of ready_sections with a run-kind blocker naming run-n-one, while s2, whose second node exists as an awaiting-upstream request, stays listed; a batch entry for n-one answers held while n-other queues; and a done section whose run's head is on a side branch yields the finding, with the landed-head twin of that fixture emitting nothing. Two further cases hold the edges: a delivery promoted under each of passed, not-run and failed holds its node identically, and a stopped pointer naming an already-delivered node is not taken as freeing it, while a stopped pointer with no row behind it stays ready — the fix must not read every stopped run as delivered.

Evidence, all resolved over its own revision. Against the base revision 34e8cf65b53bd57225fc6acbf74230a493a3527e the same test module fails four of five: KeyError: 'ready_sections' where the promoted section is ready with no hold at all, assert 'queued' == 'held' where the duplicate was queued, and no finding at all for the unlanded head; the landed-head control passes on both arms, which is the direction that must not move. The two gate files the node was dispatched with (tests/test_staged_write_inventory.py, tests/test_every_shared_home_lock_holds_across_nodes.py) run 55 passed at the head. Command and full output for each arm are the logs named in the manifest.

One boundary is left explicit rather than hidden: a section's nodes are known from its run records, so a node that has never been dispatched has no record and cannot be counted. The plan's own wording — a section "split on purpose into several nodes" — is satisfied once any node of the section has a stored request or a run; a section split for the first time has nothing to split from until its first node exists. Declaring a node list in the plan would close it, and that is a plan-format decision this node did not take on. The run-not-landed finding reads the local integration branch only: a checkout whose branch cannot be resolved reports nothing, because an unanswerable ancestry question is not a defect in the plan.
