A delivered section still reads ready, and the deliverable sits outside this node's write grant

This node was dispatched to implement the section's deliverable: the roadmap's ready set, batch dispatch and admission must treat a section's node as not ready while that node has a live, delivered, promoted or landed implementation run, and say which run holds it. The node's declared write paths are its landing fragment and its figure directory only (docs/evidence/fragments/queued-work-needs-no-workaround/qwnw-a-section-a-run-has-delivered-is-not-ready.html, docs/figures/queued-work-needs-no-workaround/qwnw-a-section-a-run-has-delivered-is-not-ready), and the promotion gate records its suite as unarmed because no test lies in that scope. The change the section asks for is a code change in four modules plus its tests. It is therefore delivered as a measured diagnosis and a ready-to-run brief rather than as a code change, and the node reports blocked on the missing grant.

The defect reproduces on the base revision 34e8cf65b53bd57225fc6acbf74230a493a3527e, with a hermetic fixture: a temporary docs tree holding one plan declaring s1 and s2 implementable, a temporary state root, a temporary crew home, and one ledger row for a promoted run on demo#s1 (gate: passed, promoted_at set). With one ledger row and zero live pointers, build_roadmap reports s1 verdict: {'ready': True, 'blockers': []}, no ready_sections key at all, and no section row for s1. The run is in the ledger and nowhere in the readiness answer. The command and its full output are in negative-control-base-promoted-section-reads-ready.log in the run directory.

The mechanism is structural, not a missed edge case. The roadmap's only run input is crew.list_live(), joined into per-section rows at reckon/roadmap.py:3642; section readiness is then computed from declared holds alone — named_holds at reckon/roadmap.py:4444 into section_readiness_verdict at reckon/roadmap.py:952, whose ready is plan_ready and not blockers. Promotion unlinks the live pointer (reckon/crew/promotion.py:251, _remove_promoted_pointer), so the moment a node is delivered the run leaves the only set the roadmap reads. Per-section run blockers reach the page only through the section rows at reckon/roadmap.py:4695, which are built from the same live set.

A fix has these sites, and one constraint that shapes it:

  • the hold itself — read delivered, promoted and landed runs from the ledger (reckon/ledger.py's runs/picker_runs, whose rows carry plan, section, gate and completed_at), join them by node with the live pointers, and add the row as a section blocker beside the existing kinds;
  • the constraint: the dispatch and admission path reaches readiness through reckon/crew/plan_review.py:6321 into roadmap.section_readiness_rows (reckon/roadmap.py:3297), which builds with include_attempts=False, readiness_only=True. Ledger reads are skipped on exactly the path that decides a dispatch, so the fix cannot ride on section_attempts_by_plan;
  • batch dispatch: reckon/crew/dispatch_batch.py:845 stores each entry through queue_one and derives the status at :869; a held entry needs its own status and the run id, beside already-queued and awaiting-upstream;
  • the wiring finding: a sibling of _undeclared_wait_findings and _overlapping_scope_findings at reckon/roadmap.py:4554, using the ancestry probe already in the tree (reckon/crew/merge.py:845 _is_ancestor) so a done section whose run's head is not on the integration branch names that run;
  • the promoted-but-unmerged case already has an instrument: _keep_pointer_for_pending_landing (reckon/crew/promotion.py:255) marks the pointer it cannot remove, and reckon/crew/pending_landing.py:141 already computes on_branch.

Three questions the section leaves to the implementation and that the re-dispatch brief should settle rather than rediscover: which run states hold (the section names live, delivered, promoted and landed, and a landed run's hold must not outlive its section's own declaration); how a node is identified when a section carries several (the hold is per node, so the second node of the section must stay ready); and how far the ledger read may cost on the dispatch path, which today avoids it deliberately.

The grant this node needs to finish the section is: reckon/roadmap.py, reckon/crew/dispatch_batch.py, reckon/crew/plan_review.py (if the readiness pass needs the join), reckon/crew/admission/readiness.py, and a test module at tests/test_a_section_a_run_has_delivered_is_not_ready.py. With those, the reproduction above becomes the test's positive case and the base-revision run recorded here is its negative control.
