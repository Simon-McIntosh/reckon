A worktree release is whole

What changed. The named file failed on one case at the base revision: test_no_removal_site_still_deletes_with_git_worktree_remove found landing_measure.py::base_checkout. The product was wrong, not the test. Every other removal site vacates a registered path in one rename onto a trash directory before git is told to forget the tree, because git worktree remove deletes the files while deregistering the tree under a single deadline, and a deadline that expires partway leaves a registered tree holding a fraction of its files. The base checkout was written in October, after that rule was established, and deleted its scratch tree with git worktree remove --force under the measurement's own deadline, then pruned the registration if the call failed — the same defect the rule exists to prevent.

base_checkout now releases through reckon.crew.routing._release_worktree_whole, with run_id="landing-base". Its tree sits on node-local scratch, so the helper takes the scratch directory as its trash root: the rename stays on the tree's own filesystem instead of crossing onto shared storage, and the scratch directory is deleted whole afterwards. The helper gained the optional reckon-side trash_root argument for exactly that case; the existing fallback to the primary root's trash is unchanged. A release that fails still prunes the registration, as before.

The file's list of removal sites that must route through the helper now names reckon/crew/landing_measure.py: base_checkout, so a site that stops routing through it is named rather than counted, and a case exercises the release itself: it observes the copy offered to deletion, that the copy sits in the scratch directory the tree was built in, and that the tree is gone from the repository's registration afterwards. No assertion was deleted or weakened; the only test change is that case and the one entry in the callers' map.
