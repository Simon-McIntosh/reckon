A repeated complete reports the promotion it drove

What changed. A crew complete whose own promotion request is still queued does not answer duplicate and stop: it carries that queued request out in the call that found it, settling the request and writing the ledger row. The completion record it writes on disk says so, with "driven": true. The public reply does not, because _complete_many in reckon/crew_run_commands.py assembles that reply from a fixed key list, and the list omitted driven. A coordinator repeating its own complete therefore could not tell the promotion it drove from one it waited on: the reply named ledger_path and pointer_removed, the same words a synchronous promotion answers with.

The record is the evidence, and it disagrees with the reply: 

completion-<first>.json   no driven key        (the queueing call)
completion-<second>.json  "driven": true        (the repeat that drove it)
second reply             {"ledger_path": ..., "ok": true, "pointer_removed": true,
                          "record_path": ..., "run_id": ...}   no driven key

One key joins the list, so the bounded reply carries the marker its own record already held. No assertion was deleted or weakened; the test file is unchanged.

Measured

Each arm is a log whose header lines name the revision, the tree, the command and — for the two runs of the node's file — that SLURM_JOB_ID was unset for the run, and whose last line reads EXIT=<code>. The head arm and both suite arms ran as all_debug jobs.

The suite the dispatcher armed for this run — the two project-wide inventory and lock tests — reads 58 passed at both revisions, so the change adds no failure there.

The thirty test files that import reckon.crew_run_commands run as one arm on each revision, and the two arms name the same twenty failing ids: the population carries twenty reds at its base none of which this change touches, and the head adds none. Both read 20 failed, 518 passed with EXIT=1, so the added-failure count is zero.
