The working-tree-read instrument reads a revision range as two commits

What was red. At the base revision 3d6255122828c0e4a4ef5a2dfb093668da7eb02b the module tests/test_promotion_checks_read_only_what_moved.py was red with one id: test_a_full_promotion_reads_no_unbounded_working_tree. The promotion's own range read — git diff --numstat --no-renames <base>..<head> from reckon/crew/recovery_review_subject.py — was charged as an unbounded working-tree read.

Cause and verdict: the test was wrong. The instrument counted revision tokens rather than the commits they name, so A..B read as a single revision and fell to the len(revisions) < 2 branch that means "diffs the working tree against a commit". A two-endpoint range compares two tree objects and touches no working tree at all — the distinction the helper's own docstring states. The product rule was right and is untouched; the test now asserts the rule the code keeps. No assertion was deleted or weakened: a single-revision diff, a bare status, an unbounded ls-tree/ls-files and a diff with no revision still count as unbounded reads.

The change. Each revision token is split on .. and its non-empty endpoints summed, so A..B and A...B contribute two; revision collection stops at a -- bound, so a path named after it cannot be mistaken for a revision. One file changed, tests/test_promotion_checks_read_only_what_moved.py, no product source.
