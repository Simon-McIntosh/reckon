A ledger write cannot shrink the committed roster or the run count

What changed. ledger.write guards a write that reports fewer runs than the committed aggregate holds, and a write that leaves out a member id the roster holds. The run axis worked. The roster axis could not fire: a payload read through ledger.load carries the store's imported roster, and _write_state replaced the payload's member list with the aggregate's own copy before comparing. Every member a truncated write dropped was therefore dropped from the comparison as well as from the payload, and the write was accepted. That is the measured incident shape, taken from a project's ledger by one crew complete write: 110 runs and 87 members to a single row.

The guard now measures the members the caller declared against the roster the same read returns — the store's roster, read through run_store.read_auxiliary so a guard never imports into the store, and the aggregate's own members when no store holds an imported roster. The payload still keeps the aggregate's copies, which is what an aggregate run update requires, so the guard's reference roster and the rows the write commits are computed separately. The roster check keeps its place before the run check, so the incident write is refused for its roster first and for its run count only once the roster removal is declared intended.
