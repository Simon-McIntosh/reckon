A manifest is refused while its worker is live for anything promotion would refuse

The rules a delivered manifest can fail are stated once, in reckon/crew/manifest_faults.py, and both readers ask that module: the pre-delivery check appends each reason to its findings, and promotion raises the same reason in front of the run id. The reasons are therefore one string rather than two descriptions that drift. They cover the two faults the check previously passed and promotion refused: a suite arm whose revision is prose or an abbreviation of an object id, and a gate command naming an absolute path under the temporary directory. An unrecognised status is refused by both through the manifest reader.

A manifest whose only test file is absent at the base now reads as a complete base arm with zero failures when the base tree holds none of the node's test files and the suite is the scoped form: an empty suite is a measurement of nothing failing, not missing evidence. The same absent arm beside a base tree that does not hold them is still refused.

A suite arm can be re-pointed by a coordinator through crew repair --run <id> --arm baseline_suite|after_suite --revision <sha> --reason <text>. The verb writes manifest.md.asdelivered once, rewrites the arm line in place, records the previous arm and the reason in arm-repair.json, and refuses a revision that is still not an object id, an arm the manifest does not carry, and a missing reason.

A commit citation written as the revision and the subject it was committed under is not refused by either reader: the delivery check already resolved the ids an entry carries, so promotion now resolves an entry the same way rather than refusing it whole. That row of the fault list converges in the accepting direction, where a worker pasting its own git log output is honest and no run is refused.
