Appending a run writes one run file

What was red. The file failed on the primary branch for two causes, both a test encoding a rule the ledger stopped keeping rather than a regression in the product. Each cause was reproduced at the base revision before anything was edited, in the log cited under arms.

Cause 1 — a byte-scan miss decodes nothing. Verdict: the test was wrong about which append it was measuring. test_byte_scan_miss_never_parses_aggregate_or_opens_other_run runs the fixture's empty store, so the append in question is the project's first stored row. Since _complete_store_from_ledger (commit 57edff12f41ec24500093f48fc7fbf570983d4f4, 18 November) seeding the store from committed history is that first row's job, and the import necessarily decodes the aggregate it seeds from — a different read from the duplicate check. The test now stores one row for the project first, so the append under test is an ordinary one and the assertion it makes is exactly the one it was written for: a byte-scan miss on the duplicate check decodes nothing and opens no other run's file. Mutating the product's byte scan away makes it fail with the test's own message, so the guard still fires.

Cause 2 — a failed store write is a refusal. Verdict: the test was wrong about the store's authority. test_index_lag_observes_failed_insert_without_rebuilding expected a failed run_store.append to return {"status": "failed"} with the run file left behind, so lag could observe it. Commit 7a8fdac445a60e9913e5bda85d38cf08b1240560 (15 November) made the store the authority: an append whose store write fails refuses and takes back the run file, so no refused insert leaves a run file the store lacks and the lag it asserted can no longer arise from an append. The test now asserts the rule the code keeps — the refusal names the store path, the injected cause and the repair verb, and neither store keeps the row — and keeps every unrebuilding assertion by writing the lagging run file by hand, which is the only way that state now arises. Mutating the refusal back into a failure payload makes it fail as DID NOT RAISE LedgerError.

No assertion was deleted or weakened: the byte-scan assertion, the no-other-run-opened assertion, the two repeated lag readings, and the no-rebuild and byte-stable store checks all remain, and the refusal assertions are stronger than the failure payload they replace.
