A lock past the retry bound is a refusal, and the test says so

What changed. tests/test_a_locked_ledger_store_is_retried.py was red on the primary branch: its third case called ledger._index_append against a store lock held longer than the retry bound and asserted the call returned {"status": "failed"}. It raised LedgerError instead, and the run read 1 failed, 2 passed.

The cause, with its verdict — the test was wrong. The file was written on 2026-11-05 (02f6f1b963) against the contract as it then stood: a store write that declined was reported as a merely unhealthy index and the run file was left for a later import. On 2026-11-15 7a8fdac445 reversed that rule deliberately — the store is the durable authority for every promoted run, so a declined write refuses the promotion, and append_run takes back the run file it had already written rather than leaving a run whose row no store holds. The product keeps that rule and its docstring, its caller and tests/test_a_failed_store_write_leaves_no_row.py all state it. Only this file still encoded the superseded rule, so the product is untouched here and the file is updated to the rule the code now keeps.

The assertions were replaced, not weakened. The case (test_a_lock_past_the_bound_is_refused_then_imported) now requires the refusal — pytest.raises(ledger.LedgerError) — asserts the message names the wait bound it exceeded, and asserts no row survived the refusal. The second half is unchanged and still writes the run file and shows run_store.import_ledger supplying the missing row. The module docstring and the case name carry the same rule, so no prose tells a reader the write is reported rather than raised.
