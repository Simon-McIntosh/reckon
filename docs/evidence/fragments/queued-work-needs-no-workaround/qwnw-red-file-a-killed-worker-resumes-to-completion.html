A killed worker is classified, resumed and completed

What changed. The per-run supervisor spawned its worker, kept only the pid, and let the Popen handle be collected the moment the spawn returned. subprocess reaps its own child from that handle's finaliser, so when the handle won the race the supervisor's os.waitpid raised ChildProcessError and the attempt was recorded as ended by neither a code nor a signal: a worker killed by SIGTERM left an exit record whose signal and signal_name were both null, and the classification that reads that record could not name the signal that ended the run. In reckon/crew/dispatch_launch.py the pid carrier (_WorkerPid) now holds the Popen it was made from, so the handle lives for the whole wait and the reap stays where the exit record is composed; a wait that still finds nothing asks the handle for the code it collected, so the reading survives if some other owner got there first.

What was already right. The resume fixture in tests/test_a_killed_worker_resumes_to_completion.py placed its stub worker on the node's own /tmp. A resumed attempt is fenced, and the fence seals the node /tmp and overlays the run's scratch on it, so the resumed worker could not execute a command from there and the attempt ended with exit_code 1. That is the fence doing what it is sealed to do, so the fixture now places its stub inside the run's own directory, which the fence binds through at its own path. No assertion was deleted or weakened: the same sequence runs, and the last assertion still reads the exit the resumed attempt left on the committed ledger row.

Negative control

The base package is red for two distinct causes, and both are recorded here.

The stub is unreachable from inside the resumed attempt. A job on all_debug at the base revision runs the node's own test file against a base extraction and reads 1 failed in 4.15s, EXIT=1, failing at assert second["exit_code"] == 0 — assert 1 == 0, which is the resumed worker refusing the stub's path before any of the work that follows.

The exit record names no signal. The product defect is a race, so it was run repeatedly: the base product with the head test file left signal_name and signal both null on six consecutive local runs, each reporting AssertionError: assert None == 'SIGTERM' at the first assertion after the record is read, EXIT=1 every time. One run of the same arm on an all_debug node passed, which is what a race looks like when the node's timing goes the other way; the local six-for-six is the reading that names the defect, and an instrumented run of the supervisor printed waitpid(6635) raised ChildProcessError at the moment the supervisor tried to collect the worker it had spawned.

The two logged runs are base-arm.log (base revision, base test, an all_debug job) and base-race-reproduction.log (base product, head test, six local repetitions).
