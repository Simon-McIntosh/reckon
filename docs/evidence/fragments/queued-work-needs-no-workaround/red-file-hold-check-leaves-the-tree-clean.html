A hold check that writes only the store is read by its own file again

Verdict: the test was wrong. The file asserted that ledger.record_hold_checks rewrote the committed aggregate and the run record that write folded, and that it committed them under a chore(holds): open|close <id> subject — the behaviour of 8 November, when the hold path wrote the whole aggregate. That path was superseded on 15 November by the store-backed mutable state (feat(store): persist roster members and budget holds, whose own evidence reads "a roster or hold mutation rewrote a committed path" as its declared negative control). Holds now replace project-scoped rows in the run store and touch no committed path at all, so the file's four hold cases had been red on the primary branch since that change landed.

What changed. Only tests/test_hold_check_leaves_the_tree_clean.py. Each case now asserts the rule the code keeps, and none is weaker: the tree is clean when the call returns; HEAD is where it was, read before and after; the committed aggregate is byte-identical, so a regression that wrote it again fails on content rather than on a commit subject; the run record that still carries the retired follow_on_paths key is byte-identical on disk, while the reader still maps it to outside_scope_paths, so leaving the file alone changes no answer; and the transition itself is read from the store, including the closed hold's held_seconds of 600 for its ten-minute window. The merge case asserts the checkout's status is byte-identical to what the merge itself left, which subsumes the old stderr notice: the notice was the commit path reporting a commit it could not make, and there is no commit path left to skip. The two cases that were already green — a committing roster write commits the run record it rewrote, and a hold check that changes no hold commits nothing — keep their assertions unchanged. The fixture now names RECKON_RUN_STORE inside its temp tree beside RECKON_HOME, so a case cannot reach this workstation's own store.
