tests/test_dispatch_returns_without_worker.py passes in full

Verdict per cause: one product regression and one placement mistake in the case itself. The product cause is the boundary check below; the placement cause is the case's base sitting beneath the node's own /tmp, which is where the promotion gate puts it and where a fenced worker cannot see it. Neither was a test encoding a retired rule.

  • The repository-tree boundary check exempted every source path. _repository_tree_boundary_violations asked _claim_paths_share(shared_files, changed, changed) — whether two claims on the path would share — and every source and test path shares, so the scan reported no source edit at all. The delegated-launch case sees it as an empty violation list for a stray edit at its declared path in the main checkout. The filter now asks the project's own declaration (changed not in shared_files), which is what the comment above it and the two cases in tests/test_boundary_check_reads_two_trees.py and tests/test_boundary_check_reads_only_declared_roots.py have always described.
  • The fixture repository published no sharing declaration. A project that declares nothing shares its source paths by default, so no boundary violation is possible there. The fixture now writes docs/state/sample/shared-write-paths.json with {"shared_roots": []}, the same declaration the boundary modules' fixtures carry.

Not a cause: the scratch headroom refusal. Run in place on this node, five cases fail with tmp-headroom-refusal: … bytes free, floor 5368709120 — the node's /tmp held 0.7–1.1 GB free at the time, and the check reads the filesystem the run's scratch sits on. The rule is right and is exercised by tests/test_dispatch_refuses_without_tmp_headroom.py; the gate therefore runs where the scratch disk has room, as its done-when says (a job on all_debug, 24 GB free there).

A base beneath the node's own /tmp

The second cause was the case's own placement, not the product. The promotion gate runs the file with its base under /tmp with the crew harness's own TMPDIR, and a fenced worker's /tmp is its own scratch directory mounted over the node tmp (reckon._worker_fence.worker_tmp_mount_source). Inside the worker's view the host's /tmp is therefore absent rather than read-only. The case's stub backend is written into bin-<case> beside the base, so it was absent too and the launch died before the stub ran. The run's own stderr.log carries the proof, with nothing after it:

bwrap: execvp /tmp/qwnw-repro-1320746/basetemp/dispatch-returns0/bin-returns/claude: No such file or directory

The supervisor was running and the worker never was, which is what the four spawn-lane cases reported: "the supervisor neither spawned nor kept a worker," "the worker named on the record is not running," "the worker had already exited." Nothing about dispatch, the boundary scan or the supervisor's own spawn was wrong; the case had put the program it launches behind the one tree the fence guarantees a worker cannot see.

The repair is where the base lives. /var/tmp is the node's other temp root and the fence does not overlay it, so the base — repository, stub backends, worktrees and the marker directory the stub writes — is now created there by GATE_BASE_ROOT rather than inherited from the caller. The file therefore passes whether the harness puts its basetemp under /tmp or anywhere else. The marker directory moved under that base for the same reason: a directory beneath the node tmp is not reachable from inside the worker, so the stub could neither wait for its release file nor leave a marker, and handing the directory to the launch as the fleet runtime directory only granted it when the harness happened to pin that variable itself.
