Orchestrator lane fence: the rules hold, the payload reader did not

What was wrong. Three of the seven cases in tests/test_orchestrator_lane_fence.py errored with json.decoder.JSONDecodeError: Expecting value: line 1 column 1 (char 0). The failing line is tests/test_dispatch_names_its_backend.py:161, the shared helper the fence cases read their payload through: json.loads(result.output.splitlines()[0]).

Cause and verdict: test wrong. Since 4a73e31fe3 the dispatch writes reckon: created run <id> to stderr as its first durable notice, and the product states the contract in that commit: "stdout remains a single final JSON document". Click 8.2 changed Result.output from a proxy for stdout into an interleaving of stdout and stderr in write order, so the notice is now line 0 of the mixed stream and the document is line 0 of result.stdout. The helper encoded the old Click generation's stream shape, not a rule the code keeps. No product rule broke: a probe through the real CLI shows stdout carrying exactly one JSON document and stderr carrying only the notice.

What changed. One helper in tests/test_dispatch_names_its_backend.py: _payload now parses result.stdout, and its docstring names the channel and why the mixed stream cannot serve. No assertion is deleted or weakened; every case still asserts the same declarations, states, discharges and write order it did before.
