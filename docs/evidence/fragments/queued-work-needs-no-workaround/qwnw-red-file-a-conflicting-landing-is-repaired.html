Cause 1: the promoted-run refusal blocked the repair round

A delivery that promotes and then meets a merge conflict has no live pointer, because promotion retired it. The repair round is the only owner of that conflict, so dispatch_merge_repair rebuilt the pointer through mark_pending_landing_repair. That writer refused every promoted run, so the round was recorded as "status": "refused", the pending landing reported record-obligation on every pass, and read_pointer raised no live run.

The refusal is right for the replay it was written for: a landing re-read long after it ran must not recreate a promoted run's pointer, or a landing that already happened is read as live again. What it could not tell apart is the conflict in front of the pass. Its first round now rebuilds the marked pointer.

The rebuild applies only to a first round. It needs all of these:

  • the run is promoted;
  • a pending record exists for the run;
  • that record names no merge conflict yet;
  • a project is named, so the promotion row can be read;
  • the record names no landing group, because a group's members are resumed by the group journal as one cohort.

Cause 2: a running round was re-issued on every sweep

The landing pass calls dispatch_merge_repair for the same conflict again on the next sweep. That call found the round resumed and, with the pointer live again, tried the write a second time, so the test saw the round resumed twice. dispatch_merge_repair now returns the round it already opened and resumed, so one conflict resumes one worker.
