A queued run reads where held work is shown: repaired

The named file reproduces at the base revision and passes at the head. Two causes, both product faults, both repaired without touching the test file. The raw logs are named in the manifest; the figures below are their summary and exit lines.

Cause 1: the live view resolved a row's configuration the way a dispatch does

Product wrong. The live view composes each row's lane reading through reckon.crew.query._lane_config_for, which resolved the row's project configuration with the admission path's _resolve_lane_config(record), whose local-lane selection defaults to on. Selecting the local backend raises when the host declares none, so a read view answered with a dispatch's refusal, naming local_backend and the route a local dispatch needs. Three of the four failing cases came from this one cause.

Repair. The read resolves the row's configuration with select_local=False: a row's lane document is named by the backend the row records, so the read never needed this host's local lane. A configuration that cannot be resolved is caught as a row with no reading, which is what the helper's own contract already promised.

Cause 2: the stop hook's copy of the non-blocking vocabulary was short one kind

Product wrong. The hook keeps its own copy of the derivation's non-blocking duty kinds because the paths that read a fresh snapshot cannot import the derivation. The derivation carries route-defaulted, documented there as a notice about a run that is working and as never holding a stop open; the hook's copy did not carry it, so that notice held a coordinator's stop open. The case asserts that the derivation's non-blocking set is a subset of the hook's, which is exactly that drift, and the copy now carries the kind.
