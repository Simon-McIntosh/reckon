The failing id was tests/test_a_terminal_worker_exits_within_its_grace.py::test_a_resumed_worker_is_not_ended_by_its_earlier_attempts_baseline, and it failed before its own subject was reached: the supervisor printed run 'r-terminal-grace' no longer names this supervisor's launch attempt to stderr and spawned no worker, so the case's driver timed out waiting for the worker record (the stub worker's record not met within 15s).

One cause, verdict product wrong. The spawn guard in _supervisor_spawn_worker refused whenever the pointer named the launch's own attempt number with a different start instant. A resume reaches its supervisor through supervised_launch, which writes the spec and the attempt marker and starts the supervisor, and writes the pointer's attempt and start only afterwards, in record_resumption. While that supervisor runs the pointer therefore still carries the dispatch-time instant at the same attempt number, and that is the launch the resume has taken over.

The repair compares the two stamps for order instead of difference. A pointer instant later than the spec's belongs to a launch made after this one was built and is still refused: the recovered-attempt case in tests/test_admission_survives_a_kill.py still raises SupersededSupervisorError for it. An earlier instant is the identity this launch supersedes, so the worker starts; stamps that do not parse keep the difference test, and the reservation and live-worker refusals are untouched.

The defect was reproduced before the repair against the case's own fixture: the pointer named attempt 1 with start 2026-10-02T00:00:00Z, the spec named attempt 1 with a fresh start, and the supervisor raised instead of spawning (no worker.json). After the repair the same script printed worker record: True.
