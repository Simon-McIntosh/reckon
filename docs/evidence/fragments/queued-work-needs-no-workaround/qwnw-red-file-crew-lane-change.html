A lane change's resumed command is read from the run's stored detail

What changed. Two cases in tests/test_crew_lane_change.py failed on the primary branch with KeyError: 'argv'. Both indexed the live pointer directly: after["argv"]. The live pointer no longer carries dispatch-time detail — DISPATCH_DETAIL_FIELDS in reckon/crew/runs.py names argv among the fields a pointer write moves into the run's own dispatch-detail.json, and the pointer keeps only that file's path. The single reader for the move is dispatch_field(record, field), which returns the value inline when an older pointer carries it and otherwise reads the stored detail. The assertions were reading a rule the product has retired, not a product defect: the resumed argv exists, it is simply not on the pointer.

Verdict: test wrong, product correct. The product rule kept unchanged is runs.dispatch_field: a run's argv is a dispatch-time detail read through that one accessor, with the pointer carrying no copy. The test now asserts the same fact against the same subject — a continued session's id is the word the resumed command passes to the harness after resume, and the alpha session id appears in the resumed command — but reads it through dispatch_field, which is what the launch path itself calls (at reckon/crew/dispatch_sessions.py:1030) and what a queued launch and a protected-set read already use in their own tests. No assertion was deleted or weakened; both now resolve their subject through the product's reader.
