Ledger plan selection goes through the plan owner

A plan-filtered read of the store answered from the stored plan column, a value written when the row landed, so the column was a snapshot of the owner answer rather than the answer. The plan of a row is owned by ledger.row_plan: the row field itself, then the implementation move it reported, then the node definition it ran. A plan read now narrows to candidate rows with a SQL expression over those three fields, then asks row_plan about every candidate, so the owner decides and the expression decides only what is worth decoding; reading every row of a 20,000-row project instead would fail tests/test_plan_selected_store_read_is_bounded.py. Because that expression restates the precedence, a guard compares the two statements across every combination of the three fields, so a precedence that drifts drops a row a test names. Commit 12e0bf633b.

The test was right and the product was wrong: the failing assertion named the rule the code broke (SQL selection bypassed the shared plan owner) and no assertion was weakened.
