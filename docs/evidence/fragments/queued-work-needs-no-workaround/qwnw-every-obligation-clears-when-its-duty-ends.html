Every obligation that can clear when its duty ends, and the four that cannot

The section asks that a duty clear once the run it names has left the fleet, whatever route ended it, and that the acknowledgement path accept a run that still raises a row whatever its pointer and ledger state. This record holds the census that named the gap, the change that closes it, the tests that hold it, and the figure that remains — which is not zero, and why.

The census that named the gap

Every stored obligation row in the live crew home was read at the base revision, and each row's run classified by two independent facts: whether it still holds a live pointer, and whether it still has a ledger row. The reading ran as an all_debug job at 2026-11-14T20:55:53Z (census.log, exit 0): 130 stored documents, 151 rows carrying a run id, 77 of them naming a run with no live pointer — 62 of those runs had a ledger row and 15 had neither.

The sweep-failed route was reproduced directly (repro.log, exit 0): a stored failure for a run with no live pointer and no ledger row still raised a row after one pass, because the failure list is durable per session and only that session's next completed sweep replaces it. The acknowledgement probe (ack.log, exit 0) showed the second half of the gap: a deferral for such a run was refused unless the caller passed --project, and a row's own command never carries one.

The change

Three source files and one new test module, committed as 23441432588509b0e37d7f85a3cdf499bac2c476, with the held-tree settlement added by the repair round in f34655ee:

  • reckon/crew/station_obligations.py — _ended_sweep_failures keeps a failure only while its run holds a live pointer and has no ledger record; _with_sweep_failures publishes through it, and prune_sweep_failures applies the same reading to the durable per-session record, writing back only when an entry ended. The mount registry is read once for the whole list, so no ledger is decoded per row.
  • reckon/crew/obligation_snapshot.py — sweep-failed joins LIVE_POINTER_DUTY_KINDS, so an answer computed before the run ended stops naming it at read time. The module still reaches no derivation, plan, backend or ledger module.
  • reckon/crew/obligation_snapshot.py (repair round) — the held-tree settlement the repair round adds: worktree-held is withheld once its run has no live pointer and the terminal cleanup queue holds an intent for it.
  • reckon/crew/runs.py — a deferral's project now falls back to the stored duty document that still raises the run's rows, after the caller's own --project, the ledger record and the promotion request have all failed to name one. A run nothing names is still refused.

The tests

tests/test_a_duty_clears_when_its_run_ends.py raises each case in a temporary crew home and reads it back through the station's own functions: a live run's failure is published (the positive control); both endings the station can see — no record left, and a ledger record — clear the row and the stored entry; one session's ended failure leaves another session's standing; a deferral reaches a run with neither pointer nor record and moves the row to acknowledged; and a run no record names is still refused. The repair round adds the held-tree arms, which serve the same row with no cleanup intent and withhold it once the intent exists.

The negative control runs the committed test module against the base revision's source (negative_control.log): 4 of the 6 tests fail there, with the row still raised after its run ended and the deferral still refused. The two that pass are the positive control and the still-refused case, which the base also satisfies — an honest control has to pass where the behaviour was already right.

The suite arms

All three arms ran as one all_debug job over the two files the fence names (tests/test_staged_write_inventory.py, tests/test_every_shared_home_lock_holds_across_nodes.py), each in its own exported tree that carries a HEAD of its own so the inventory test can ask git for the staged paths. baseline_suite.log at 7b45ca90, after_suite.log at c0b40266 and change_suite.log at the change's own commit each report 55 passed, exit 0, so the delta the change carries is zero.

The figure the section asks for is not zero, and the groups that make up the 25 are named here rather than averaged:

  • 22 are worktree-held and are the stratum of held trees still on disk, in sessions whose directories still exist. Their evidence is the tree, not the run's pointer, so a pointer stat cannot settle them; the next section measures which of them something else already owns.
  • 2 are blocked whose run has gone, and 1 promotion-failed whose run has landed. These settle in a derivation pass — _settled_state for the promotion request, the resume reading for a blocked row — not on the pointer stat the read path holds. The stored document is the station's last pass, and the installed station process still runs the code from before this commit, so nothing has re-derived them yet.

So the change removes the route the section names — a durable failure list that outlived its run and could be cleared only by hand — and leaves the three rows above to the next pass with the fixed code, plus the 22 held trees, which are duties rather than defects.

What owns a held tree

A retained tree outlives the run that made it, so a missing pointer settles a worktree-held row on nothing: the row is the only surface naming the bytes. Two facts settle it instead, and the second is what the repair round adds. The derivation was read whole at f34655ee (probe_held.log, exit 0): 102 held-tree duties across every project the crew home carries rows for, none of them with a live pointer, 3 whose run the terminal cleanup queue holds an intent for, and 99 with no owner at all. Every one names a tree that is still on disk.

So the duty a row names has three states rather than two. It is owed when the tree is on disk and nothing else owns the release; it is not a duty once the cleanup queue has written its intent, because that queue's release is already the scheduled work; and it is discharged when the tree is gone, which the derivation already reads. The settlement now applies the middle state: a row whose run has no live pointer and whose intent exists is withheld, and the arm that keeps it without an owner is the one that stops the other 99 trees from being hidden. Both arms are held by test_a_held_tree_settles_once_its_release_has_an_owner.

What the repair round changed, and what it did not

A review of the delivered head read sweep-failed joining the pointer kinds while worktree-held stayed out, and noted that the post-change census carried 22 held-tree rows whose run has a ledger record and no live pointer. Those rows are the held trees, and the finding is right that they do not settle on the run's ending. They do not, because the tree outlives the run: settling them there would leave 99 trees on this fleet with no surface naming them, measured in probe_held.log as duties with no live pointer and no owner.

What the round does settle is the middle state, a row whose release the terminal cleanup queue already owns, and that is a settlement the section changes rather than a papering over: the queue's release is the scheduled work, so the row names a duty somebody else is doing. The 99 with no owner stay, and so does the 22-row figure in this record, because the honest count is the one that reports a real held tree rather than the one that reads zero.

Fences and honesty notes

Every measurement above ran as an all_debug job or against a temporary crew home, and none on the fleet node. Two of this session's commands did start a whole-suite pytest in the shared checkout by mistake while an arm was being prepared; each was stopped within about two minutes of starting and no process was left behind.
