Every obligation that can clear when its duty ends, and the four that cannot

The section asks that a duty clear once the run it names has left the fleet, whatever route ended it, and that the acknowledgement path accept a run that still raises a row whatever its pointer and ledger state. This record holds the census that named the gap, the change that closes it, the tests that hold it, and the figure that remains — which is not zero, and why.

The census that named the gap

Every stored obligation row in the live crew home was read at the base revision, and each row's run classified by two independent facts: whether it still holds a live pointer, and whether it still has a ledger row. The reading ran as an all_debug job at 2026-11-14T20:55:53Z (census.log, exit 0): 130 stored documents, 151 rows carrying a run id, 77 of them naming a run with no live pointer — 62 of those runs had a ledger row and 15 had neither.

The sweep-failed route was reproduced directly (repro.log, exit 0): a stored failure for a run with no live pointer and no ledger row still raised a row after one pass, because the failure list is durable per session and only that session's next completed sweep replaces it. The acknowledgement probe (ack.log, exit 0) showed the second half of the gap: a deferral for such a run was refused unless the caller passed --project, and a row's own command never carries one.

The change

Four source files and one new test module, committed as 23441432588509b0e37d7f85a3cdf499bac2c476, with the held-tree settlement added by the repair round in f34655ee and the unmerged-work rule this round adds in c778aaa1 and 9d886bbf:

  • reckon/crew/station_obligations.py — _ended_sweep_failures keeps a failure only while its run holds a live pointer and has no ledger record; _with_sweep_failures publishes through it, and prune_sweep_failures applies the same reading to the durable per-session record, writing back only when an entry ended. The mount registry is read once for the whole list, so no ledger is decoded per row.
  • reckon/crew/obligation_snapshot.py — sweep-failed joins LIVE_POINTER_DUTY_KINDS, so an answer computed before the run ended stops naming it at read time. The module still reaches no derivation, plan, backend or ledger module.
  • reckon/crew/obligation_snapshot.py (repair round) — the held-tree settlement the repair round adds: worktree-held is withheld once its run has no live pointer and the terminal cleanup queue holds an intent for it.
  • reckon/crew/obligations.py — a retained tree is filed as held only while it carries unmerged work, decided by the tree's own git state rather than by the run's pointer.
  • reckon/crew/runs.py — a deferral's project now falls back to the stored duty document that still raises the run's rows, after the caller's own --project, the ledger record and the promotion request have all failed to name one. A run nothing names is still refused.

The tests

tests/test_a_duty_clears_when_its_run_ends.py raises each case in a temporary crew home and reads it back through the station's own functions: a live run's failure is published (the positive control); both endings the station can see — no record left, and a ledger record — clear the row and the stored entry; one session's ended failure leaves another session's standing; a deferral reaches a run with neither pointer nor record and moves the row to acknowledged; and a run no record names is still refused. The repair round adds the held-tree arms, which serve the same row with no cleanup intent and withhold it once the intent exists; this round adds four arms over one parametrisation — a landed tree and a gone tree each stop raising the row, an uncommitted change and a commit the primary branch does not reach each keep it — and a deferral stored under a second project, so the project read back can only have come from the document.

The module holds thirteen tests. The negative control runs it against the base revision's source (negative_control.log, exit 1): eight of the thirteen fail there and five pass. The failures are behavioural rather than missing names — the row still standing after its run ended on both endings, the held-tree arm whose release is owned still served, the deferral still refused, and the two rule arms that expect a landed and a gone tree to be released still keeping them. The five that pass are the positive control, the still-refused case, and the three arms whose expectation the base already meets — an honest control has to pass where the behaviour was already right.

The suite arms

All three arms ran as one all_debug job over the two files the fence names (tests/test_staged_write_inventory.py, tests/test_every_shared_home_lock_holds_across_nodes.py), each in its own exported tree that carries a HEAD of its own so the inventory test can ask git for the staged paths. baseline_suite.log at 7b45ca90, after_suite.log at 9d886bbf and change_suite.log at the change's own commit each report 55 passed, exit 0, so the delta the change carries is zero.

A first run of these arms showed two errors in the inventory test on both arms; they were the exported tree having no repository behind it, identical at both revisions, and they are gone once the export is given a HEAD.

So the change removes the route the section names — a durable failure list that outlived its run and could be cleared only by hand — and puts the held-tree stratum under a rule of its own, measured in the next section rather than asserted here.

What owns a held tree

A retained tree outlives the run that made it, so a missing pointer settles a worktree-held row on nothing: the row is the only surface naming the bytes. The derivation was read whole at both fence revisions (probe_held_base.log and probe_held.log, both exit 0): 102 held-tree duties across every project the crew home carries rows for, every one naming a tree still on disk, 3 whose run the terminal cleanup queue already owns and 99 with no other owner. The count reads the same at 7b45ca90 and at the repair head, and that flat reading is itself the finding rather than a null result: the next measurement says why.

Each of the 102 was then read at the repair head for the two facts the question turns on (probe_trees.log, exit 0): 96 carry commits their primary branch does not reach (86 clean, 10 carrying an uncommitted change as well), 16 carry an uncommitted change and none of the 102 is both clean and merged. So a rule that releases a tree whose work a landing has taken releases nothing on this fleet today: every retained tree is a duty. That includes the 28 whose run already has a landing record — their trees hold commits main does not reach, which is exactly what a row naming them is for.

That is the rule the row answers to now, and four arms in test_the_derivation_holds_a_tree_only_while_it_carries_unmerged_work hold it: a landed tree and a gone tree stop raising the row, an uncommitted change and an unmerged commit keep it. Beside it stands the settlement the earlier repair round adds — a row whose run has no live pointer and whose cleanup intent exists is withheld, because the queue's release is already the scheduled work. Both readings are applied in obligations._HeldWorktreeState.refresh_trees, at the one place a tree is filed as held.

What this round changed

The review of the earlier head read the held-tree rows as rows that should have cleared with their runs, and read a census instant and a table beside it that had moved since the paragraph citing them was written. Both halves are answered here by measurement rather than by argument: the rows now clear on the tree's own state, and every figure in this record is taken from the log named beside it, table and instant included.

The rule is a settlement at the derivation, in the place a tree is filed as held. It asks the only question the row asks — would deleting this tree lose work — with the tree's own git state: git status --porcelain for an uncommitted change, and one git rev-list --count HEAD --not over every primary ref the repository resolves — main, develop, master, and the remote's tracking head — for commits no landing took. A reading that fails keeps the duty, because a tree nobody could read is not a tree nothing needs. Reading the remote head first was the first attempt at this and released nothing at all: the tracking ref lags the local branch until someone pushes, so every merged tree read as unmerged. Both revisions are in the record as a pair of logs for that reason.

What the rule does not do is release a tree that still holds work, which is why the derived count reads the same either side. The 18 rows the census serves name 18 such trees, and the honest report of that is the count, not a zero.

Fences and honesty notes

Every measurement above ran as an all_debug job or against a temporary crew home, and none on the fleet node. The arms at the delivered head, the two controls and the four probe readings ran as three all_debug jobs (1316701, 1316726, 1316717), each log carrying its revision and command on the first line and an EXIT line last.
