A dispatch names its backend: the file is green again

What changed. One helper in tests/test_dispatch_names_its_backend.py. Its _payload decoded result.output.splitlines()[0], which is Click's mixed stream: since Click 8.2 output interleaves stdout and stderr in write order. A launched dispatch publishes its durable claim and then writes reckon: created run <id> to stderr, so on every dry_run=False path the first line of that mixed stream was the notice and the json.loads raised. Eleven cases in the file split five passing (dry-run and refusal paths, which print no notice) against six failing (every launched path).

The helper now decodes result.stdout, which the command holds for exactly one JSON document on every exit path: refusals, dry runs and launches alike. No assertion was removed or weakened — only the stream read into them.

The cause, and its verdict

The product is right; the test was reading a stream the product never promised. reckon/crew_dispatch_commands.py runs every dispatch callback under _single_document_stdout, which points everything the command calls at the notice channel and emits the payload on the stream held aside — a rule its docstring states and that tests/test_dispatch_stdout_is_one_document.py already guards with json.loads(result.stdout) over eight cases, a launch among them. reckon/crew/dispatching/preparation.py writes the created-run id to stderr for the same reason, its comment reading "stdout remains the command's final JSON document, so notices use stderr". The guard is not reimplemented here; it is run at head, eight cases passing, which is what makes "the product is right" a measurement rather than an assumption.
