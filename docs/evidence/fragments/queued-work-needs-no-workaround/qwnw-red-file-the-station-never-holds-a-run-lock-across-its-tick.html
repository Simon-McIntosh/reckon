The station's pointer-lock regression file passes

What changed. The file's three red cases were two stale expectations, in one test file and no product source. A station sweep no longer promotes a delivered review inside its own pass: since b4840067ad it hands the file's promotion to a worker, or files a durable request the fleet service drains. The two station cases hold a promotion at its checks, or during waiter release, and then assert the run's pointer lock can be taken within a second — but with no promotion running they failed on their own precondition, the sweep never reached the promotion barrier. The fixture now gives the sweep the in-process promotion workers, and the acquisition it asserts belongs to the worker the sweep started rather than to the sweep thread. What the cases measure is unchanged: the lock stays available while a promotion is held.

The third case expects a refusal — run ... changed while promotion ran — when another host rewrites a review run's pointer mid-promotion. A review run has nothing to land, so since 692bf59a1b it neither refuses nor retires a newer attempt's pointer: the promotion completes, the pointer is kept, and it is marked promoted so the sweep retires it once nothing owns it. The case now asserts that state — attempt, pid and phase kept, promoted set, no pending_landing_repair mark — instead of the refusal the code stopped raising. No pointer assertion was dropped.
