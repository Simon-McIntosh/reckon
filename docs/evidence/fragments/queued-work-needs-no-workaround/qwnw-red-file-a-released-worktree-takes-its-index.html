A released worktree takes its index

What changed. One case in tests/test_a_released_worktree_takes_its_index.py waited for a project-scoped sweep to remove a ledger index whose recorded checkout was gone. That rule no longer holds. Since e4f4dbf2c7 scoped a gc pass to the project it runs for, an index whose recorded ledger path does not resolve to that project is attributed to no project and is reported as kept: reclaiming it would reach another checkout's cache, which is what the scoped rule exists to prevent. tests/test_gc_sweeps_ledger_indexes.py already pins that half of the rule — a scoped --apply keeps every index it cannot attribute, and an unscoped pass removes it.

The case now asserts both halves against the same synthesised checkout: the scoped pass reports the row with reason recorded-checkout-gone, project unknown, action keep and removed false, and leaves the file on disk; a pass naming no project then still removes it. Every original assertion remains; the scoped-keep assertions are additions, so nothing is deleted or weakened. No product file changed.

The row is reported at all — reason == "recorded-checkout-gone" passes — so the sweep sees the orphan and declines to remove it because the named project does not own it. That is the rule the code keeps; the case encoded the rule it replaced.
