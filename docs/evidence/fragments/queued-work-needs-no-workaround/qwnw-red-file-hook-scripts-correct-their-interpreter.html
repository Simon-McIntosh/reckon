Two causes, one per failing case.

Cause 1, product wrong. reckon/hooks/worker_inbox.py imports a reckon module (reckon._store) and did not load the shared interpreter_bootstrap that the three hooks beside it load, so a bare python3 worker_inbox.py on a system interpreter reaches that lazy import under a Python that cannot import the package. The file landed after the bootstrap rule and was never brought under it. The reproduction is the base arm's own assertion: the population the source walker finds is coordinator_obligations.py, worker_git_guard.py, worker_inbox.py, worker_stop.py, and only worker_inbox.py carries no with_name("interpreter_bootstrap.py") line. The product fix loads the bootstrap in that script and calls it from main — deferred rather than at import, because the fleet and the MCP view import this module to compose a message and a module that re-executed on import would replace the caller. A checkout with no .venv reports checkout interpreter is missing on stderr and exits non-zero, the harness surfacing that without blocking the tool call the hook followed, rather than exiting silently and dropping the head instruction it exists to deliver.

Cause 2, test wrong. The file pinned the importing-hook population as three literal names and keyed its re-execution cases by that list, so a fourth importing hook could only arrive as a KeyError from the case map rather than as a measured result. The case map keyed the error KeyError: 'worker_inbox.py'; it now names the four hooks and carries a case that seeds one waiting message before each interpreter, so the two arms compare a real delivery and the delivery is asserted rather than assumed. No assertion was weakened; the population assertion was kept and its expected set extended, and the missing-interpreter case now covers the new hook too.
