The overdue-runs fence classifies only the dispatching session's runs

What changed. The check that records a session's overdue unreconciled runs at dispatch read every live pointer on the host and classified each one, whichever session owned it. Classification is the costly part: each read opens the run's manifest, its stream and its stored review. It now takes the dispatching session and skips a pointer another session owns before reading it, so the check's cost is that session's own rows rather than the fleet's queue.

Two surfaces call it and both pass the session. The dispatch fence (reckon/crew/dispatching/fences.py) hands _recorded_backlog the session it is fencing for, and the drain keeps the project-wide reading by omitting the argument. A pointer with no recorded owner stays in scope either way, because absence cannot prove that a live pointer belongs to a peer. One rule, one implementation (reckon/crew/recovery_watch.py).

The record is kept. A dispatch is not refused for its own session's backlog — that was settled before this node, by tests/test_a_dispatch_is_not_refused_on_its_backlog.py, which states that the backlog is "recorded on its runs, never enforced". This node preserves that behaviour exactly and adds the assertion that the recorded run is the session's own: the fence names the run it chose the work over, and no run belonging to another session is named.

The done-when's "every one is under ten seconds" is not met, and the cause is not the fleet's queue. Timed without a profiler, one queued dispatch is 53.64 s, of which project discovery is 50.03 s and the overdue-runs fence 0.09 s; three dispatches in one warm process read 54.43, 51.08 and 54.19 s with build_roadmap taking 21.83, 19.18 and 25.43 s of each and the fence 0.07 s. A profile of one discovery names the rest: 70.5 s total, discover_plans 65.4 s, _attach_ready_set and build_roadmap 33.0 s, and three git_dates calls 20.0 s — two of which are the ten-second ceilings firing, logged as Git history lookup timed out after 10 seconds and Git last-modified lookup timed out after 10 seconds.

Two instrument caveats, both measured, affect these numbers and neither changes the conclusion. First, the timing was taken on the allocation's node (98dci4-clu-2001, load 8 to 27), not on the fleet node the section names. Second, a dispatch run from a worktree pays discovery twice — 66.96 s against the worktree and then 24.29 s against the main checkout — because the batch keys its one-derivation cache on the resolved docs directory and the mount resolves to a different tree; the numbers above are from the main checkout, where it derives once.

What the node delivers is the part the section's deliverable names first: the check costs the same however many live pointers other sessions hold. It was 5.33 s over 67 rows on the same store and is 0.04 s over one, and the absolute dispatch time is now dominated by plan discovery and roadmap building. That residual is recorded in the run's outside_scope; it is not repairable by narrowing a further reader.
