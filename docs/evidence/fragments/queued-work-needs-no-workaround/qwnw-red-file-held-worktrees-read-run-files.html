A held-tree fixture that held nothing

What changed. tests/test_held_worktrees_read_run_files.py registered every fixture tree with git worktree add --detach <path> HEAD: a tree whose head is the primary branch's own tip and whose working tree is clean. Commit c778aaa1f6 made the derivation file a retained tree under its record only while the tree carries work a landing has not taken — an uncommitted change, or a commit the primary branch does not reach — so every tree these cases registered held nothing, the derivation returned no record, and all nine cases read back an empty held set.

Verdict: the test was wrong, the product was not. The rule is deliberate and guarded elsewhere: tests/test_a_duty_clears_when_its_run_ends.py asserts _tree_holds_unmerged_work over a landed tree (false), an uncommitted change (true), a commit past the primary branch (true) and an absent tree (false), and asserts the derivation withholds the row for a tree that holds nothing. Nothing in reckon/ was changed by this node.

What was updated, and to what rule. The _worktree helper now commits one file in the tree it registers, so each fixture tree carries a commit its primary branch does not reach — the state of a dispatched run whose work has not landed. The file's module docstring and the helper's docstring name the rule they now rely on: a retained tree is held only while it holds unmerged work, so every tree here satisfies it. No assertion was deleted or weakened: the held-set assertions, the expected runs, the age and kind assertions and the refusal that the merged ledger is never read for a tree a file names are unchanged. The fixture now models a tree that has work rather than a tree that has none, which is what each case was written to measure ordering and attribution over.
