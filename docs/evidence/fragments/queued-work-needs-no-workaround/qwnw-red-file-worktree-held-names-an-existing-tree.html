Held-tree cases are decided by the rule the reader keeps

The cause. The held-tree derivation (reckon/crew/obligations.py, _tree_holds_unmerged_work) raises worktree-held for a retained tree only while deleting it would lose something: an uncommitted change, or a commit the primary branch does not reach. The rule arrived after this file was written, which had been written around the earlier rule — a tree is held when its directory exists and no promotion record shows it released. Its second case therefore built a clean detached worktree at HEAD, registered it, and asserted the duty was raised; under the current rule that tree holds nothing, so the file failed on the primary branch with [] against the one expected run id.

Verdict: the test encoded a rule the code no longer keeps. The product is not repaired. The new rule is deliberate and is already pinned by its own cases in tests/test_a_duty_cleared_when_its_run_ends.py (landed, uncommitted, unmerged-commit and gone arms), so nothing was reimplemented here and no assertion of this file was removed or weakened.

What changed in the file. Each retained tree now carries work a reader would otherwise hold, so the case under test is the deciding fact rather than a fixture that happens to be clean. The deleted case leaves an uncommitted change before removing the directory, so presence is what removes the duty. The released case leaves one too, and additionally shows git status --porcelain reporting it, so its release record is what removes the duty. The kept case is the arm where both hold, and its assertion is unchanged.
