A merge releases the worktree of a run that promoted itself

What changed. This file's four red cases were two causes, and they had opposite verdicts.

A promoted row's tree was not in the set a landing frees — product wrong. merge.release_landed_worktrees asked the obligations view which trees a record holds, and that view holds a tree only while _tree_holds_unmerged_work answers true for it. The landing this function follows is precisely what removes the tree's commit from the side the primary branch lacks: after the merge, the tree's git status is clean and its commits are ancestors of the branch, so the duty view stopped naming the one tree the landing was meant to free. The result was {'judged': True, 'released': [], 'withheld': []} — nothing released and nothing withheld, which is the one outcome the landing report cannot describe.

reckon/crew/obligations.py now files every tree it inspects and a row names, not only the trees that fail the duty judgement, and _named_worktree_records answers that view; release_landed_worktrees reads it. Both views come out of one pass, so the wider answer costs no extra status read, and the duties other callers show are unchanged. The retention rule is untouched: a tree a recoverable session keeps stays held, which is why the release judges worktree_retention before it removes anything.

The fixture's promotion never happened — test wrong. The fixture drove crew complete through the CLI and read its zero exit as a promoted row. That command now files a promotion request for the fleet service to carry out, and a plain completion refuses a reviewed head the remote branch does not yet carry, so no row existed for a merge to judge and three cases failed at promotion or at the absent row. The fixture promotes through the same entry point the command calls, and records a recoverable session's retention in the run store — the copy every reader unions against — rather than in the per-run file that the store's row wins against. The rule the file now asserts is that a promotion is a call that returns its receipt, while a queued request is not a promotion. Every assertion is unchanged: a landed head releases the tree, a tree holding a commit the head does not carry is withheld, a merge refused before it pushes releases nothing, a retained tree is withheld and named, and a release that raises leaves the landing standing.

A test stub mirrored an old signature — test wrong. The arm over every test file that imports the changed modules found one case newly failing: the warm-read case in tests/test_a_review_duty_reads_its_run_review_once.py replaces _held_worktree_records_read with a stub that accepted the project and repository only, so the reader's new view argument raised TypeError. The stub forwards the view and counts re-reads exactly as it did; no assertion in that file changed.

Outside scope

ledger.write_run_file writes a run's document, advances the write generation and publishes the document index, but never calls run_store.sync_run. A promoted row lives in the run store, and the union readers use takes the store's copy, so an amendment written only through write_run_file is invisible to every reader that asks the store — the retention this file records was lost that way until the fixture wrote the store as well. Production amends promoted rows exactly this way: promotion_release._update_run_record writes a release receipt and crew_run_commands writes completion changes, both through that writer alone.

This node's measure is the release path, so the writer was left as it is. The defect is worth its own section: a promoted row's amendment should reach the same store the row was appended to, or the file should stop being written where no reader would see it.
