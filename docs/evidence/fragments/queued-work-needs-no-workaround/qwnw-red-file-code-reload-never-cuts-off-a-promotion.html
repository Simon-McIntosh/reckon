A reload test that never let the reload window come due

tests/test_code_reload_never_cuts_off_a_promotion.py did not fail at base: two of its three cases hung, and a run of the file never returned. The two cases that hang are the ones that drive the loop, and the case that only drives PromotionService passes.

Cause, verdict: test wrong. The test was committed as 966e47a3b6bd4bd2c6be52445af428a39210971d, when the loop compared the stamp directly:

if _admit_code_stamp() != code_stamp and _checkout_code_is_trusted():

8a45bd001e then batched standing service reloads behind an export window, and the same line became a query of that window.

if reload_window.due(newest_code) and _checkout_code_is_trusted():

The test's fixture moves the stamp and then spins the loop on a zero interval, never satisfying ReloadWindow.due, which requires the image to have exported a pass and the window's deadline to have passed. A fresh window carries its deadline 1800 s ahead, so the loop never reaches its drain and never replaces itself. The test now writes the pass schedule the product reads, with a deadline already in the past, so the move is due in the pass after the first; the window's length stays what the product computes. No assertion was deleted or weakened, and the fixture additionally places the loop's pass boundary inside tmp_path, because its default name resolved against the working directory and left lock and registration files in the checkout.

The window, read both ways

fresh schedule next_reload_at: 1799.9986851215363 seconds from now
fresh due('new'): False
past-deadline due('new'): True
past-deadline due('old'): False

The instrument sees the true reading as well as the false one: with the deadline in the past and the stamp moved, due answers True, and with the stamp unchanged it answers False.
