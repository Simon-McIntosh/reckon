A clean landing releases its worktree and leaves no held duty

What changed. A hand landing of a promoted run judged the run's tree twice after the merge. The landing's own release reads the commit the merge wrote, and it removes the tree. The release's audit then reads the run's declared write paths to describe what was left behind — and it read them off node, which a promoted ledger row carries the node id in, with the definition under node_definition. The audit therefore raised on every run whose manifest still named changed paths, after the reviewed head had already been pushed, and the release was recorded as raised. A tree the landing had just removed was reported withheld, naming a tree no command could free; the duty it raises offered reckon crew gc, whose sweep answered that no record named a worktree for the run.

Three changes in reckon/crew/promotion_release.py and reckon/crew/promotion_evidence.py. _declared_repository_roots now reads the node definition in whichever shape the record carries it, so the audit describes the release instead of raising through it. A tree whose directory is already gone is reported released rather than withheld, because it holds nothing to release. And an audit that fails after the removal is recorded beside the outcome rather than inverting it, so a release cannot be undone by its own receipt.

A tree holding a commit the primary branch lacks is unchanged: it is withheld, its obligation is named, and the sweep that obligation suggests frees it once that commit lands.

Measured

Every case synthesises its own origin, checkout, ledger and workspace under a temporary config home, and enters the project's real entry through crew complete --land. The three cases are: a clean landing whose worktree holds exactly the reviewed head; a landing whose worktree was removed before the landing; and a worktree holding one commit beyond the reviewed head.

Each arm is a log whose first lines name the revision, tree and command and whose last line reads EXIT=<code>.

The gate covers thirteen files: the node's two test files, the release, landing-plan and promotion-release suites, and the three repository-wide invariant tests over removal sites and worktree-held records. Both arms run the same file list, so the delta is the source change rather than the test set.

Negative control

At the base revision the two clean-landing cases fail and the withheld case passes: the first two report "worktree_released": false with "worktree_withheld": "tree is no longer available" on a tree the landing had already removed, while the reviewed head is pushed and the merge succeeds. The failing run is docs/evidence/fragments/queued-work-needs-no-workaround/s20.html. The second case's failure carries the whole landing report, including "merged": true beside the withheld release — the defect in one object.

Outside scope

Nine tests fail identically in both arms, so none of them is caused by this change, and they fail alone in an unmodified base extraction as well:

  • test_a_merge_releases_its_worktree.py: four cases, three of them refusing at promotion because the fixture's gate record carries no command, exit status, log path or digest, and one reading an absent run record file.
  • test_promotion_releases_its_worktree.py: one case, which expects a refusal that does not raise.
  • test_refused_promotion_leaves_the_worktree.py: one case, the same missing refusal.
  • test_a_released_worktree_takes_its_index.py and test_a_worktree_release_is_whole.py: one case each, the repository-wide removal-site invariants naming landing_measure.py::base_checkout.
  • test_every_removal_path_reads_the_wide_claim.py: one case, the removal-path set having changed without a direct driver.

This gate measures only this node's own change. Verifying the merged result belongs to a separately dispatched test node.
