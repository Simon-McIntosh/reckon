Cause. The case publishes the index from inside the landing's staging hook with a plain ledger.load(..., use_index=True) and then makes that index unwritable. That read no longer touches the index: the promotion has already written the run's row into the run store, so a project-wide read is answered from the store. Nothing is published, and index.chmod(0o400) raises FileNotFoundError on a file that was never created. Measured at the hook: the pick cache held only open-run-index, ledger.load returned ['failed-landing-row'] from the store, and the index path was absent.

Repair. Publish the index through a read the store does not answer: naming a run the store holds no row for falls through to _indexed_data, which hashes the promotion's row into the index while its per-run file is on disk. The fixture also resolves the crew home inside the test tree, so the live pointer, the open-run index and the run store belong to the test — a row a previous run left in a shared store made the promotion answer already_promoted before it staged, a second way this case read red for a reason it does not test. No assertion is deleted or weakened; the head run keeps every one, including that the refused index still serves the rolled-back row.
