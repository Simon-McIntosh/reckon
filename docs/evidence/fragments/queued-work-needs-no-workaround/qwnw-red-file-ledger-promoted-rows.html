A stored read answers the record the promotion wrote

Eight tests in tests/test_ledger.py were red on the primary branch at f4403247ef233a2efb644c2deceb8165611da16c. They were not eight defects. Six were one product defect on the store's write path; one was a completion reply that had been made compact without its reader following; one stated a per-checkout isolation that ended when the shared store became the reader.

The product defect, reproduced before the repair: a promotion writes a run record carrying no project key, while the store's row for that run carried one, because the append injected the routing key into the durable payload. A read then answered a record that matched neither the record it was given nor the file it came from:

# before, module reckon/run_store.py at the base content
column project: proj
payload has project: True
read has project: True
read == record: False
file == serialize(read): False
# after, the same probe against the same module
payload has project: False
read has project: False
read == record: True
file == serialize(read): True

The repair moves the key to where it already belonged: the runs column, which every read already filters on. The payload is now the record the writer passed. The project a write files a row under is passed to the column separately, and a read that answers an identity — get_run, durable_rows, and the equality reference — declares the project from that column onto the record it answers, so both sides of a comparison agree field for field. Rows written before the repair keep their key in the payload; a rewrite through sync_run keeps the column it had.

The three causes and their verdicts

  1. Product wrong — six tests compared a read row to the record the promotion was given and to the file that promotion wrote: test_a_foreign_projects_promoted_row_reaches_its_registered_checkout, test_an_explicit_checkout_is_used_when_the_mount_registry_is_absent, test_a_projects_own_checkout_remains_its_promotion_target, test_a_successful_index_write_follows_the_file_and_is_reported, test_a_failed_index_write_keeps_the_rows_already_written and test_the_crew_tool_reads_the_ledger_and_the_live_pointers. The injected key broke both comparisons. Repaired in reckon/run_store.py; no assertion weakened. The one assertion naming the payload's own project now states where the project is held: the runs row's column, with the payload carrying no such key.
  2. Test wrong — test_the_crew_tool_reads_the_worktrees_ledger_not_the_main_one encoded per-checkout isolation, true while the per-run documents were the ledger. One run store now answers a project's history for every checkout, so the test states the rule the code keeps: both runs answer from either checkout, and the path reports the tree that asked.
  3. Test wrong — test_complete_command_assumes_utc_for_a_naive_completion_stamp read payload["record"] from a reply that is now the compact receipt naming record_path. The test reads the retained full outcome from that path; every field assertion is unchanged.

The store's write path had three further readers declaring the injected key, none of them in the node's file: test_writes_keep_the_readers_plan_identity (five cases), test_a_repository_without_commits_accepts_its_first_run, and the seeding helpers of test_a_scanning_store_read_holds_no_lock, test_an_owed_review_pass_pays_for_what_changed and test_the_landing_check_reads_only_the_runs_it_checks (which built rows through the store's own split). Their expectations are updated to the rule the code now keeps, and the helpers pass the project to the column. No expectation lost a check.
