A composed plan review is a first attempt, not a redispatch

What changed. Only tests/test_a_new_plan_review_is_a_first_attempt.py. The product tree is untouched: both causes below are a test that encoded a rule the code no longer keeps, and each is stated here against the rule the code now asserts.

Cause 1 — a composed review's node id carries its rubric (test wrong). The file named the node plan-review-of-fixture and expected the design review — the rubric crew review --plan defaults to — to dispatch under it. _plan_review_node_id in reckon/crew/recovery_review_subject.py appends PLAN_REVIEW_RUBRIC_SUFFIX (-design) for that rubric, so the design review composed under plan-review-of-fixture-design and the file's pointer assertion failed on the id before reaching its subject. The rule is stated and guarded by tests/test_a_design_and_a_content_review_run_together.py: the design rubric names itself after the plan so two reviews of one plan can run together, while the content rubric keeps the bare id every store reader carries. The constant is now composed from PLAN_REVIEW_NODE_PREFIX and the suffix rather than written out, so the id the cases seed is the id the composer builds.

Cause 2 — a launch numbers an attempt from the run store (test wrong). The helper seeded the prior completed run through the ledger envelope and asserted it there through ledger.runs(). dispatch() numbers a node's attempt through preparation._committed_node_runs, which answers from the run store whenever a store exists and returns nothing for a node it holds no row for; it deliberately does not fall back to the ledger, and tests/test_a_launch_reads_only_its_own_rows_from_the_store.py guards that with test_a_node_with_no_stored_row_reads_nothing. A store created for mutable state holds no runs, so the ledger-seeded row was invisible and every case read attempt 1. The helper now seeds through run_store.append, the seam a promotion commits a run's row to, and its positive control reads the rows through preparation._committed_node_runs — the reader dispatch itself uses.

No assertion is deleted or weakened. The positive control still states the precondition, reads it where the launch reads it, and fails loudly when a seeding did nothing.
