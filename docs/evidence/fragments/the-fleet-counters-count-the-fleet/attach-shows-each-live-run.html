A fresh arm opens with the fleet — node record

A follower re-armed while work exists must open with the fleet, not with an empty pane. At the dispatch base it printed nothing until the first transition, because the row policy consulted the state a checkpoint had restored for a run against a row whose whole purpose was to put that state on a pane the reader had never been shown it. The two memories the policy now keeps — the state the pane shows and the state this arming has actually drawn — separate the inventory from a repeat.

§2 — The mechanism: two memories, not one

RowPolicy held one memory, _reported: the state a pane shows. A checkpoint restores into it, so a re-arm began believing it had shown the reader a state the reader had never seen. The generic rule — a row restating the state the pane already shows is silent — then dropped the inventory the arm existed to draw.

The policy now also keeps _drawn: the states this pane has actually put on screen. Both are written wherever a row is released, and the baseline rule consults the drawn one:

MemoryWritten byDrives
_reporteda released row, a checkpoint seed, a reseedtransition suppression, the left side of the next arrow
_drawna released row, an adopted pane memorythe baseline rule only
  • A baseline prints unless this arming has already drawn the same state for that run. A state carried in from a checkpoint was never put on this pane, so it cannot stand in for the row that puts it there.
  • A resume re-derives the fleet on an arm whose recorded place names no boundary: the fleet report is fed through the pane's own row path, so the row policy answers for it exactly as it answers for a stream row.
  • A reseed keeps the drawn memory and seeds only the reported one, because a continuation is the same pane continuing: it must not re-announce a run it has already shown.
  • A reload adopts the memory it is handed as drawn, because that memory is what the pane it replaces had on screen.
