A resume naming a replaced stream derives its baseline on the first pass

What the arming now does

A follower arming carries a resume state whose checkpoint records the stream it was watching and the offset it had reached. When that stream has been replaced, the recorded offset names a file that no longer describes the arming's place: the arming must re-derive the fleet baseline from the live runs rather than continue from an offset into a different file.

The generator already had a baseline branch, but a resume state routed the arming into the in-place reload branch — reloading was set from the mere presence of a resume state — which read the replaced stream from its recorded offset. The re-derived baseline row therefore arrived only on a pass that the outer loop ran after the in-place read, and that pass is gated on the arming's remaining lifetime. The checkpoint write that follows the first line can consume that lifetime outright, so the arming ended with the pane's owed row never drawn.

An arming is now treated as a fresh arm whenever a reloading pass did not resolve to a continuation of the same stream (reloading and mode != "continue"). The fleet baseline is re-derived and fed through the row path on that same first pass, before any wait, so the row the pane is owed reaches it regardless of how much of the arming's lifetime remains. The change is confined to the follow and replay path in reckon/cli.py; it touches neither the row policy nor the atomic writer.
