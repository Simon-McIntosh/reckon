An admitted launch keeps the record of its failure

An admitted launch releases the queued pointer so the shared launch path is not refused as a conflict with itself, publishes its own pointer under the same run id, and only then starts the supervisor. The supervisor's first act is to read that pointer. When the pointer is gone by then, the attempt ended at worker did not spawn: CrewError: no live run '…' (looked in …/live/<run>.json), the pane offered a remedy about the command and PATH that could not help, and the next launch wrote its own exit record at the same attempt number, overwriting the only account of the failure.

The supervisor's read now marks a missing pointer where it happens, so a launch failure can be told apart from a command that could not be run without reading the exception's wording. The failure record carries what stood on disk at that moment: the run directory listing taken before this record was written, the pointer path with its presence, phase and modification time, whether the admitted request is still held, the pass that admitted it with its process, time and checkout stamp, and whether a deliberate discard was recorded for the run. The admitting pass's identity rides the admission handover, which is the one record that spans the gap between the released queued pointer and the published launched one.

The launch-failure detail branches on that. A missing pointer names the path it was looking for and says the pointer went missing between the dispatch's write and this read; a command that cannot be executed keeps naming the command and the PATH it was searched on. Either way the record keeps the exception's own type and message, so nothing a reader relied on is replaced by the branch.

Every attempt keeps its own exit record. An immutable receipt takes the first attempt number at or above the one the launch arrived with that carries no receipt yet, so a relaunch under the same run id — which arrives with its predecessor's number — writes attempt-2-exit.json beside an intact attempt-1-exit.json. The retirement of the canonical exit.json before a launch never overwrites an elder immutable receipt, so the account of an attempt that ended is not replaced by a copy of it.
