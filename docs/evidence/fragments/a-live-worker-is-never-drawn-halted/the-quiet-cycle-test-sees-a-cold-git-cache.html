The quiet-cycle test reads a cold identity hold, not a warm one

test_quiet_cycles_list_nothing_and_spawn_no_git opens by requiring that its opening sweep spawned git at least once, so that its later claim — a quiet beat spawns none — is a measurement rather than a vacuous one. That opening spawn is not produced by the fleet fixture at all: it comes from the producer's own first pass taking the seat (watch_ticker → _watch_registration → runs._project_watch_claim → follower_registration.running_code_stamp → checkout_trust.source_code_identity), which reads this process's own checkout through git ls-tree. Those git reads are held in checkout_trust._identity_hold, a process-global cache keyed by the checkout root and held against a spawn-free reading of HEAD. Any earlier test in the same process that took that reading leaves the entry behind, HEAD has not moved, and the opening sweep is then answered from the hold and spawns no git at all. The positive control measured the cache's state rather than the instrument.

Measure. Ordered run of the 73 test files that reach recovery_classification and recovery_liveness, followed by tests/test_a_producer_sweeps_only_on_change.py in one pytest process. At the base revision the quiet case fails assert marks["spawn"][0] >= 1 — AssertionError: the opening sweep must have exercised git, assert 0 >= 1 — with 13 failed, 634 passed, 1 skipped, exit 1 (gate-base.log). With the fix, the same 73 files hold checkout_trust._identity_hold at exactly one key — the session checkout root — when the quiet case is set up, and the case passes (gate-head.log). The fix is one monkeypatch.setattr(checkout_trust, "_identity_hold", {}) in that file's fleet fixture; no product module changed.

Scope. tests/test_a_producer_sweeps_only_on_change.py. The base arm and the head arm run the same ordered cohort; the failures the cohort adds beside the quiet case (in test_a_folded_finding_widens_its_repair.py, test_a_resume_is_not_drawn_halted.py and five further files) are present at the base revision too and are outside this node's write scope, so they are recorded as follow-ons rather than repaired here.
