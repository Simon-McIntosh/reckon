Landing record — a coordinator's own status repair prints no halted row

A crew repair --status rewrites a run's manifest verdict because the coordinator read the run and decided what the record should say. The transition it causes into a halted word is therefore a duty that coordinator has just discharged by its own act — the same reading a landed or dropped row from its own merge or discard is given — so it carries nothing new and the stream must not print it. Before this node the transition printed as a halt, which is the alarm row the section exists to remove.

The producer reads the run's status-repair.json onto the snapshot (status_repair_at, status_repair_reason) and stamps the single transition the repair caused, by comparing that instant against the previous observation (recovery_watch._status_repaired). The event builder carries the stamp as status_repair (recovery_watch._watch_transition, the dict built at what was line 1878). ticker.stream_carries reads the stamp and withholds the row; it stays in crew view and the pane history. The remembered snapshot then holds the same instant, so the comparison is false afterwards and the stamp rides only the one transition the repair caused.

tests/test_a_status_repair_prints_no_halted_row.py holds both directions: a row-policy check that a stamped complete → blocked event prints nothing while the same event without the stamp prints the halted row, and a producer check that the fold stamps the event emitted after a fixture status-repair.json is written, plus that a later transition off the repaired word carries no stamp.
