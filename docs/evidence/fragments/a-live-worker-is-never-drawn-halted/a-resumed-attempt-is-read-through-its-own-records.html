A resumed attempt is read through its own records

A resume takes attempt-N.claim before it composes anything else, and publishes the attempt record, the worker record and the worker's own stream only afterwards. In that window the run directory holds the claim and nothing else naming attempt N, while the predecessor's exit record and the coordinator's repaired blocked manifest are both still in place. The guard that owns this reading — _manifest_is_the_predecessor_attempts_report in reckon/crew/recovery_classification.py — resolved the current attempt from the attempt record alone, so in that window it resolved no attempt at all, stood its deferral down, and let the repaired word govern an attempt that was only starting. The run drew halted and a reader was sent to a blocker the resume had already answered.

The claim is the run's own statement that an attempt began, and it carries the moment it began, so it is the record that dates a resumed attempt while the rest of its own evidence is still being written. _current_attempt_number in reckon/crew/recovery_liveness.py now answers with the higher of the attempt record's number and the highest claim the run directory holds, and _attempt_started_seconds reads the claim's own timestamp beside the pointer's and the attempt record's. What keeps this from swallowing a real halt is the end: the existing predicate _exit_record_names_attempt in reckon/crew/recovery_liveness.py, carried unchanged from the base revision, stands the guard down whenever an exit record names the current attempt, so an attempt that recorded its own end is read from that end and no claim after it can take the verdict away. This is the size the node declared — the existing resolver extended, not a second rule beside it.
