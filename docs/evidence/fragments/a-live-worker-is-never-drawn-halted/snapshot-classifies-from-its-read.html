Landing record — a snapshot classifies from the records its sweep already read

Reducing a live pointer to a snapshot can ask whether a review is already in flight for a finished run, and that question is answered from the project's live-pointer population. The sweep holds that population already, but the snapshot did not pass it on, so every scoring row listed the live directory again. Inside a producer's own transition write that read re-entered the publisher that builds the snapshot, which crash-looped the reckon producer on a recursion error on 2026-11-05. A same-thread re-entry guard in runs.py stops the recursion; handing the sweep's own read over stops the read.

The pointers parameter classify_pointer already accepts is extended rather than joined by a new reader: _watch_snapshot and _compute_watch_snapshot take it and pass it through, and the three sweeps inside recovery_watch.py that hold the population hand it over — the producer's own snapshot pass, the quiet beat's reuse path, and the legacy per-session count rebuild. When no population is handed over the classification call is byte-for-byte the one it was, so a caller with a single pointer classifies exactly as before.

tests/test_snapshot_classifies_from_its_read.py counts list_live calls while a one-row sweep reduces a scoring pointer with no live review, and carries two controls so the zero cannot be read as an instrument that saw nothing: the row's classification is asserted to be scoring (the branch the read lives on), and the same row classified without the population is asserted to read the set at least once in the same run.

Gate

Head: 902 passed, 6 failed, EXIT=1, 270 s. Base (revision c15f841ed1): 900 passed, 8 failed, EXIT=1, 196 s. The delta is one added failure, test_a_crashed_producer_is_restarted.py::test_repeated_crashes_reach_a_reported_limit, a 20-second timing bound on restarted producers; it passes 3/3 alone in the head tree and failed 3/3 alone with the head source reverted to base in the same worktree before passing there too, so it is a load-sensitive bound and not this change. Base-only failures are the reproduction and two further timing-bound cases.

The declared negative control drops the hand-over in _compute_watch_snapshot; the count test then reports one read and exits 1 (negative-control.log).
