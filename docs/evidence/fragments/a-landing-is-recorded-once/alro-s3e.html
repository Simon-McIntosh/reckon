§3 — A run dispatched with a brief keeps the plan it names on its record

The closure overview cannot be written for a plan whose runs were dispatched with briefs: reckon evidence synthesize --plan … refuses with has no committed landed runs. The defect reproduced on the committed store in the record ending 085741072175-rorp-s5: its top-level plan reads None while node_definition.plan reads a-read-only-run-promotes-as-delivered and impl_move.plan reads the same slug. Every brief-carried run is in that state, and the plan-selected read (ledger.runs(project, plan=…)) selected on the top-level field alone, so it returned none of them.

Decision. The stored records are read through their dispatch rather than rewritten. The plan a row belongs to has one owner, ledger._row_plan, and it now reads the row's own field first and then the impl move the run reported, then the node definition it ran. The impl move is read before the definition because the definition is wide detail a later rotation may wash out while the impl move is durable, so one row's plan reads the same before and after that rotation. No second run read is added: the index extracts the owner's answer into the column the plan-selected read already filters on, so the selection stays inside the index query and still decodes no other plan's payload.

The already-stored records. A warm index is never re-read from its sources, so a row indexed before this change would keep the empty column it was built with. The index version therefore moves to 7, which makes the next read build a fresh index and re-extract every stored row's plan from the payload it already holds — the store's own migration path, with no separate command and no record rewritten.

Measure, over a temporary store built through write_run_file: tests/test_a_brief_carried_run_keeps_its_plan.py reports 4 passed at the head, covering a promoted brief-carried run naming a plan, a stored record naming it only on its node definition, a record whose definition rotation washed out naming it through its impl move, and a brief-carried run naming no plan returned for no plan. The negative control runs the same file over the base revision, where _row_plan reads the top-level field alone: 4 failed, the first being the promoted brief-carried run that is not returned by the plan-selected read.

Live pass, read-only against the committed store from a batch job with the index published to scratch: the plan-selected read returns 0 rows for a-read-only-run-promotes-as-delivered and 0 for a-landing-is-recorded-once at the base revision, against 11,007 rows in the store and 5,415 of them carrying no top-level plan; at the head it returns 15 and 14. The instrument is checked before the zero is reported: two plans whose runs were dispatched without a brief read 59 and 69 at the base and 59 and 69 at the head, so the change adds the missing rows and takes none from another plan, and a slug no run names reads 0 in both arms.
