A sprint move writes the plan's sprint in the same call

What changed. A sprint item and the plan it names each record which sprint holds it: the sprint's member list, and the plan's own plan-sprint. A move wrote only the index, so the plan kept naming the sprint it came from while the write reported success — six plans moved between sprints on power_convertor on 2026-10-23 kept their old sprint until six separate set sprint writes were made, and the lifecycle audit then reported the disagreement the write itself had produced.

The index batch is one batch to one document, so the plan half cannot ride along with it, and it cannot live in _apply_move in reckon/_store.py, which is index-only and never touches disk. The pairing therefore lives in reckon/mcp_edit_plan.py. edit_plan reads each moved plan before it applies the batch (_sprint_move_plan_writes), then writes each moved plan's sprint through that plan's own versioned store write (_carry_plan_sprints), and reports the plan writes beside the index version (plan_writes). _move_sprint_item, the module's second implementer of the move, goes through the same read and the same writer, so neither entry point can move a plan and leave its sprint behind. A plan write that fails after the index move landed is reported as partial_write naming the plan, never as success.

What is refused, and what is not. A member list holds refs that owe no plan write: an unparsable ref, or one naming a plan this project has no file for — the sprints still move, which is the behaviour the existing move tests exercise. The refusal is reserved for a ref qualified with another project (_unwritable_move_refusal), whose plan-sprint this call cannot write; refusing names both sprints and leaves the index, the sprints and the foreign plan untouched rather than half-applying the membership change.
