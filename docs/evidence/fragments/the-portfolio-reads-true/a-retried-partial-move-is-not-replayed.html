A retried partial sprint move finishes its plan write instead of replaying

What was wrong. A sprint move writes the index and then each moved plan's own sprint. When the plan write failed after the index had moved, the call correctly reported partial_write — and still recorded a write receipt reading as plain success. A retry carrying the same request_id was therefore answered replayed with nothing written, telling the caller the move had landed while the plan kept the sprint it came from.

Reproduced against the unrepaired tree by driving _edit_plan_tool on a temporary project whose plan write is made to raise once:

first: {'ok': False, 'error': 'partial_write', ...}
plan sprint after first: S1
retry: {'ok': True, 'error': None, 'replayed': True, 'message': 'A write for request_id
        already landed at version 1; this is its recorded result.'}
plan sprint after retry: S1

What changed. The index is the authority for which sprint a plan belongs to, so a partial write now records on its receipt — beside the version and digest record_write_receipt stores — the plans still owing a sprint write and the sprint each was sent to (reckon/_store.py). A retry that finds such a receipt does not re-apply the batch, whose index move has already landed. It reads the index's current membership for each pending plan (_finish_pending_plan_writes in reckon/mcp_edit_plan.py): still listed where the move sent it and its sprint differs, the plan's sprint is written against the plan's current version; already in agreement, the entry retires as settled; listed elsewhere or nowhere, another write superseded this one and nothing is written. A plan that still cannot be written stays pending, the retry reports the partial write again, and a retry that leaves none returns success naming each plan written, settled or superseded and records the request as complete.

After the repair the same probe reads plan sprint after retry: S2 with the request's receipt carrying "pending": [].
