A review that never launched is not running

A reflex-dispatched review writes its live pointer and its claim, and the launch stops before any supervisor exists. The pointer holds launch: cli and a pre-spawn phase, the run directory holds claim.json and nothing else, and no attempt was ever composed, so neither attempt_started_at nor an attempt claim dated it. A pointer with no launch clock cannot age, so it fell through to the in-harness sentence and read as running until a manifest appeared. A cli run is not in-harness, so a review that never started stayed running indefinitely and surfaced only as overdue. It is now dated from the claim its dispatch registered, and failing that from the pointer's own creation; past the stranded-launch bound it reads as a launch failure naming the host that issued it.

What changed

  • reckon/crew/recovery_liveness.py: _claim_registered_seconds reads the run directory's claim.json and returns its claim_registered_at, refusing a claim that names another run. _claim_or_creation_seconds takes that claim and falls back to the pointer's created_at. _stranded_launch_age_seconds dates a launch from the attempt clock where one exists and from that fallback only for a launch: cli pointer, and _stranded_launch now ages through it, so an in-harness pointer under the same conditions keeps its existing reading.
  • reckon/crew/recovery_classification.py: the launch-failed stranded-launch clause names the launcher host and the span the pointer has held, where it previously stated only the bound.
  • tests/test_a_review_that_never_launched_is_not_running.py (new): three cases against a temporary crew home. A cli review pointer in starting with a claim older than the bound, no attempt record and no attempt_started_at, classifies launch-failed and names its launcher host. The same pointer with a claim younger than the bound reads running. An in-harness pointer under the first case's conditions still reads running.
