A stop inside the spawn window spawns nothing

A per-run supervisor reads its stop flag once before it forks the worker. Between that read and the fork a stop delivered to the run's process group could run its handler, set the flag, and still be followed by the fork — so the stop was recorded and a worker spawned anyway. The supervisor now blocks SIGTERM and SIGHUP across the read and the spawn, reads the stop again under the mask immediately before the fork, and clears the mask afterwards. A blocked stop is not delivered, so the second read observes it as a pending signal rather than a set flag; a stop delivered inside that window means no worker is ever spawned.

What changed

  • reckon/crew/dispatch.py, _run_supervisor: after the pre-spawn tree snapshot the stop signals are blocked with signal.pthread_sigmask, the stop is read under the mask immediately before _supervisor_spawn_worker, and the previous mask is restored in a finally. A set flag or a pending stop writes the one launch-failure exit.json (worker_pid: null, ended_during: launch) and abandons the launch. The stop read and the abandon record are factored into _stop_is_requested and _record_launch_abandoned_before_spawn.
  • reckon/crew/dispatch.py, _worker_default_signals: the fork inherits the blocked mask, so the spawn hook clears SIGTERM and SIGHUP in the child as well as restoring their default dispositions — otherwise the worker would never see the group stop that ends it.
  • tests/test_stop_before_spawn_spawns_nothing.py: two cases added. One holds the supervisor at the blocked read through a sitecustomize that pauses the moment pthread_sigmask blocks the stop signals, delivers a group stop, and requires no worker.json, no stub marker, a dead supervisor and a launch-failure record. The other delivers a group stop to a live supervisor after its stub worker has spawned and requires the exit record to name SIGTERM. The module docstring states the invariant in place of the earlier changelog sentence.
  • The test instrument carries three repairs needed to run it under a fenced worker: the git shim's scan root names <base>/.reckon-worktrees (where dispatch actually creates the run's worktree), the real git is resolved past the worker shim with reckon.shim_lookup.real_executable, and the real live-pointer guard now intersects appeared entries with the pointers the case itself wrote, so a peer session's concurrent pointer is not read as this case's leak.
