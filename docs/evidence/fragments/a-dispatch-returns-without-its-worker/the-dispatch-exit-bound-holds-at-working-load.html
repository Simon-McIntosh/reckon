The dispatch-exit bound holds at the fleet node's working load

The dispatch-return case bounded dispatch's own clock by a measured import time alone. Dispatch does more than import before it returns, and that extra work is repository-facing process and file traffic, so a loaded host slows it faster than it slows an import; at load near 11 the case failed 3 of 4 runs at a bound derived from a 0.475 s import reference. The bound now adds a measured round trip of dispatch's own preparation work, so the cost the import unit cannot see is in the bound rather than outside it.

What changed

  • tests/test_dispatch_returns_without_worker.py names the part the import reference omits: dispatch's own preparation of the run, whose repository-facing step is the worktree creation subprocess at reckon/crew/routing.py:2472 inside _create_worktree (reckon/crew/routing.py:2456), which runs python worktree_fleet.py create and so git worktree add, plus the state reads and run-record writes that go with it. A bare import reckon.crew.dispatch contains none of that work.
  • _measured_preparation_seconds measures that preparation here and now as the round trip of one delegated dispatch, which prepares a run — worktree, project fallback state, run records — and spawns nothing. That is the same preparation the measured dispatch pays, measured beside it.
  • the bound is now SUPERVISOR_SURVIVAL_SECONDS + 8.0 × import reference + 3.0 × preparation reference. Both references follow the host's load, so a loaded host widens the bound through both classes of cost.
  • the case report carries preparation_seconds beside reference_seconds, so each run's two margins are readable rather than inferred.
  • a preparation reference that recorded no dispatch_seconds, or no run id, is refused rather than read as zero: the term enters the bound added, so a zero would silently remove it and restore the bound this change exists to widen. test_a_preparation_reference_that_recorded_no_time_is_refused holds that refusal, and fails if the guard is removed.
  • the declared mutation is runnable through the environment the case's child interprets: RECKON_GATE_JOIN_SUPERVISOR=1 makes the launch seam wait for the supervisor it started to exit, so the negative control is reproducible by a reader without editing the module under test.

Which arm carries which claim. The 20-of-20 contended head row is a positive result only: it says the new bound holds on this node beside eight spinners, and it does not by itself separate head from base, because the base contended arm passed 12 of 12 as well. No arm on this node demonstrates the pre-change bound failing under load — the base whole-file arm does fail, but its supervisor-case failure is a peer's untracked_roots TypeError raised before the bound is reached, and its second failure is the delegated case that fails at head too, so neither is the defect this node repairs. The claim that the old bound under-reads at load therefore rests on the failure recorded when the defect was found, not on a reproduction here: this node was already loaded enough at every measurement that the import reference inflated with the same contention, and the old bound survived it. What this node shows is that the new bound is not tighter than the old one on this host and passes 20 of 20 where the case's own history is failing runs.

Declared negative control

With the mutation that joins the supervisor applied through RECKON_GATE_JOIN_SUPERVISOR=1, the case fails: the dispatch process never returns, the case times out waiting for it, and the run exits non-zero. The bound still judges a dispatch that returns, so the mutation remains caught whatever reference is used. The log was taken at the committed head 88cdb3b1b, the same tree the traceback names.

The guard on the preparation reference has its own control: replacing the refusal with if False: in a scratch copy of the file makes test_a_preparation_reference_that_recorded_no_time_is_refused fail with DID NOT RAISE AssertionError, 2 failed, EXIT=1 (logs/negative-control-reverted-guard.log).
