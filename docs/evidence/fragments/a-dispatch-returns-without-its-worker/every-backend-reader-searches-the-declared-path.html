Every backend reader searches the declared path

A search path declared only in a project's own flight layer, docs/state/<project>/flight.yaml, was honoured by the pre-flight and by no reader after it. The launch plan carried the backend by name, so composition read the host layer and refused a directory the pre-flight had accepted, and the persisted worker PATH never saw the declaration at all. The directories are now resolved once, when the plan is built from the project-resolved backend entry, and every later reader takes them from the plan: the executable resolution, the placement's scheduler lookup, the persisted worker environment, the supervisor spec a resume composes, and the run record a later attempt reads them back from.

What changed

  • reckon/_backends.py: LaunchPlan carries backend_search_path, the directories its backend declares, resolved at plan build by backend_search_directories() from the backend entry the composer already holds. That entry is the project-resolved one every construction site passes, so a directory a project layer declares is resolved here rather than re-derived later. as_dict() carries the list so a lane-change preview names what it resolved.
  • reckon/crew/dispatch_launch.py: declared_backend_search_path() now delegates the expansion to _backends.backend_search_directories, so a plan and a reader resolve a declaration by one rule. launch_search_path() takes the plan's resolved directories and prefers them over reading the flight layers again. resolve_launch_executable(), resolve_backend_placement() and _persisted_worker_environment() all read them from the plan, and _supervisor_spec() writes them into the worker's persisted PATH.
  • reckon/crew/dispatch.py: the cli launch branch records backend_search_path on the run, so a resume reads what this launch searched rather than what the layers declare when the later attempt runs. The in-harness branch composes no plan and is unchanged.
  • reckon/crew/dispatch_sessions.py: _backend_settings() reads the recorded directories back into the rebuilt backend. Its rebuild from the record's own command copies only the harness identity and the lane's window, so it would otherwise drop the declaration from every resumed attempt.
  • tests/test_every_backend_reader_searches_the_declared_path.py (new): a temporary host layer declaring no search path, a temporary project layer declaring one, and a stub clive in a directory absent from PATH.

The two cases

The first launch composes a plan from the project-resolved backend entry, the way dispatch.py does. The stub resolves to the declared directory, the plan carries it, and the supervisor spec's persisted PATH holds it. The second case builds the run record a launch writes, rebuilds the backend from it with _backend_settings(), and composes the resumed plan and its supervisor spec. The host layer reachable by name declares nothing in either case, so a reader that resolved the layers again would find no directory at all — the resumed PATH carries it only because the record was read back.
