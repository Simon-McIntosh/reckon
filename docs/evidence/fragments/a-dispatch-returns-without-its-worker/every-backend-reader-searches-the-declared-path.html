Every backend reader searches the declared path

A search path declared only in a project's own flight layer, docs/state/<project>/flight.yaml, was honoured by the pre-flight and by no reader after it. The launch plan carried the backend by name, so composition read the host layer and refused a directory the pre-flight had accepted, and the persisted worker PATH never saw the declaration at all. The directories are now resolved once, when the plan is built from the project-resolved backend entry, and every later reader takes them from the launch's own run record: the executable resolution, the placement's scheduler lookup, the persisted worker environment, the supervisor spec a resume composes, and the record a lane change rewrites.

What changed

  • reckon/_backends.py: LaunchPlan carries backend_search_path, the directories its backend declares, resolved at plan build by backend_search_directories() from the backend entry the composer already holds. That entry is the project-resolved one every construction site passes, so a directory a project layer declares is resolved here rather than re-derived later. as_dict() carries the list so a lane-change preview names what it resolved.
  • reckon/crew/dispatch_launch.py: declared_backend_search_path() now delegates the expansion to _backends.backend_search_directories, so a plan and a reader resolve a declaration by one rule. launch_search_path() takes the plan's resolved directories and prefers them over reading the flight layers again. resolve_launch_executable(), resolve_backend_placement() and _persisted_worker_environment() all read them from the plan, and _supervisor_spec() writes them into the worker's persisted PATH.
  • reckon/crew/dispatch.py: the cli launch branch records backend_search_path on the run, so a resume reads what this launch searched rather than what the layers declare when the later attempt runs. The in-harness branch composes no plan and is unchanged.
  • reckon/crew/dispatch_sessions.py: _backend_settings() reads the recorded directories back into the rebuilt backend. Its rebuild from the record's own command copies only the harness identity and the lane's window, so it would otherwise drop the declaration from every resumed attempt. The lane-change move records the destination plan's directories, and clears the field with None when the destination composes no plan.
  • tests/test_every_backend_reader_searches_the_declared_path.py (new): every case drives the production path that writes the record, rather than constructing one. The first launch is a real crew.dispatch with a stand-in launcher; the resume case reads that launch's own live pointer back; the lane-change case moves the same run twice through change_lane.

The three cases

The first launch runs crew.dispatch against a project layer that alone declares the stub's directory, with a launcher standing in for the harness. The returned record carries the directory, and the composed argv resolves the stub through it.

The resume case reads the live pointer that launch wrote, asserts the host layer reachable by name declares nothing, and rebuilds the backend from the record with _backend_settings(). The rebuild from the record's own command drops every key it does not copy, so the resumed plan and its supervisor PATH carry the directory only because the record was read back.

The lane-change case takes the same dispatched run, moves it to a backend whose declaration lives in the host layer, and asserts the record now names that destination's directory; it then moves the run to an in-harness backend, which composes no plan, and asserts the field is cleared to None rather than carrying the previous lane's directories.
