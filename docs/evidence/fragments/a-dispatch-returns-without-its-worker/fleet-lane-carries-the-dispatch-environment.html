The fleet spawn lane carries the dispatcher's crew environment

The defect

The allocation's batch step starts each run's supervisor through the spawn verb with its own environment. A per-run supervisor resolves the run it was asked to hold through reckon's crew home, so one started under the batch step's home rather than the dispatcher's finds no run and exits at once — after the spawn has already been acknowledged. Dispatch then reports a live pid for a worker that never started.

Measured on 2026-09-29 in the fleet rehearsal (job 1278427): a dispatch with a scratch RECKON_HOME got an acked pid and returned success, while the supervisor read the default ~/.config/reckon/crew/live, found no run, and wrote an exit.json reading worker did not spawn: CrewError: no live run. The in-repo gate could not see it because its stub batch step never ran a real supervisor.

What changed

  1. _supervisor_spec writes an environment mapping into the spec carrying the dispatcher's values of every variable that relocates crew state, named once as the module constant CREW_STATE_ENVIRONMENT — RECKON_HOME, RECKON_STATE_ROOT, RECKON_MOUNTS_PATH, RECKON_FLIGHT_CONFIG and RECKON_RUN_STORE. Only variables that are set are carried: an unset one must arrive absent, not empty, because every reader that falls back on a default resolves those two differently.
  2. fleet_supervisor.spawn_supervisor applies the spec's environment over the batch step's own environment when starting the argv. A carried environment that is not a mapping, or whose entries are not name/string pairs, raises TypeError rather than being passed on, so a malformed spec cannot smuggle a value the child would misread.
  3. Dispatch confirms the supervisor survived its first seconds before reporting success. After the acknowledgement, it waits a bounded window (SUPERVISOR_SURVIVAL_SECONDS, 2 s) and raises CrewError if the supervisor has already exited, naming the supervisor's own exit.json detail when one exists. The refusal unwinds through dispatch's launch-failure path, so it leaves no live pointer and no worktree. The check runs on both the fleet branch and the fork branch.

Evidence

tests/test_fleet_lane_carries_the_dispatch_environment.py stands in for the batch step with its FIFO reader, but calls the real spawn_supervisor under an environment whose RECKON_HOME deliberately differs from the dispatcher's. The supervisor it starts is a real per-run supervisor, and the worker beneath it is a stub codex that records its pid and stays alive.

Controls

  • Negative control (declared): spawn_supervisor was mutated to start the argv with dict(environ) — the batch step's environment alone, dropping the carry. The new dispatch case then failed with CrewError: the supervisor for … exited within 2s of starting: worker did not spawn: CrewError: no live run, and the mutation was reverted. So the carrying is what makes the supervisor reach the run, rather than the case passing whatever the environment.
  • Malformed-spec cases: a spec whose environment is a list, and one whose value is not a string, each raise TypeError before any child is started.
  • Lint delta: the three staged paths add no new ruff findings against their base revision.
