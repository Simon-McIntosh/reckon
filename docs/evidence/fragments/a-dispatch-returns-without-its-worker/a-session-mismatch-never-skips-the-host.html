A session mismatch never skips the host silently

A dispatch issued with --session naming something other than the calling Claude session reaches the host of the process that ran it, so _request_host_follower refuses the pair: that host does not own the session. With nothing beside the refusal the caller's pane showed no run while the run read as unattached everywhere else. The dispatch now hands the run to the calling session's own waiting host, names both sessions, and records the hand-off on the launch payload.

Measure

tests/test_a_session_mismatch_never_skips_the_host_silently.py exercises five cases on a temporary crew home, with a stub reader holding the caller's session-host FIFO:

  • a mismatched session with a waiting host writes the run's request to the caller's FIFO, prints one line naming both sessions, and returns host_handoff with requested_session, calling_session and handed_to_host true;
  • a mismatched session with no waiting host returns handed_to_host false and the line says no waiting host received the run;
  • a matching session leaves the ordinary ask path alone and _request_host_follower still writes its request;
  • an empty session name is not a mismatch;
  • the real entry point: crew.dispatch(...) with a mismatched session writes the request to the caller's FIFO, names both sessions, and the returned payload carries host_handoff with handed_to_host true beside watch.delivery == "host". That case arms a watch producer, because the shared fixture suppresses arming for every other test, and a suppressed dispatch waives the watch before the follower is arranged at all, so it would never reach the hand-off.

Where the hand-off reaches a real dispatch

_arrange_dispatch_follower (reckon/crew/dispatching/requests.py) calls the hand-off in the branch where neither the run's own host nor a follower of it was found, so a real dispatch with a mismatched --session goes through it. When a waiting host took the run, the delivery verdict becomes host, which is what stops launch.py from also arming a Monitor watch for a run it would then double-deliver.

The record is composed after the follower is arranged, so the hand-off travels between them in this process through take_session_hand_off(), which clears as it reads: _launch_dispatch puts the value on the payload as host_handoff, and a dispatch held or queued on an earlier step cannot leave one behind for the next dispatch's record. A matched session carries no field rather than a null, which would read as a hand-off that found no host.

A resume whose run belongs to another session hands the run over the same way and reports a refusal only when no waiting host took it.

Where the line goes

A dispatch writes its payload to stdout and callers parse it as JSON, so a line printed beside it makes the payload unparseable; the refusal path caught exactly that as a decode failure at the first character. The line is for the operator, so it is written where a terminal receives it and nowhere else; a piped dispatch carries the same fact in host_handoff, which is what a caller reads instead of the line.
