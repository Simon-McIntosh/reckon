A review's followed lane yields to a hold, and the route says it was followed

A review composed onto the lane its reviewed run used carries a named_route whose set_by is review-follows-run. The admission pass reads that field: a route the reflex wrote is a preference derived from which lane ran the work, so a budget hold on that lane rebinds the request onto the local backend and records a route_fallback naming the held lane. A route a caller named with --backend or --local keeps set_by: dispatch and stays authoritative — its answer is a queued request that waits, not a silent lane move.

The run edge of the guard was already present in the tree when this node opened: _local_fallback (reckon/crew/admission/holds.py) rebinds the reflex's spelling whatever the picker's action and whether or not a picker_selection is recorded, and dispatch_review_for_run passes the origin on the route it hands dispatch. The remaining gap was in the evidence: the composition case captured the arguments handed to dispatch rather than the route admission reads. That is an input echo — a composer that passed the origin and a dispatch that dropped it would still have satisfied it, and the queued request would carry no origin for admission to act on.

The composition case now holds the metered lane, composes the review for a run carried on that lane, and reads the review's own queued pointer: named_route is {backend: beta, set_by: review-follows-run}. The rebind case and the caller-named case are unchanged.
