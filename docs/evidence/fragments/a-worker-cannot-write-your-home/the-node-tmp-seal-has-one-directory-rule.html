One creation rule for the node-tmp runtime paths

create_node_tmp_runtime_paths re-implemented the module's own create_write_roots: the same resolved-destination existence check, mkdir(parents=True, exist_ok=True) and BackendError loop for each directory a fence is about to bind writable. The rule therefore had two copies that could drift. It now calls create_write_roots with the enumerated runtime paths and returns their resolved forms, which is all that was specific to it; fence_argv is unchanged and its binds are unchanged.

The §15 test file's "no probe in the node-tmp root" assertion guarded nothing, because its stub wrote probes only into its own scratch and the runtime paths — so the assertion held whatever the fence did. A new test function, test_a_probe_written_directly_into_the_node_tmp_root_is_refused, drives a stub that writes a probe straight into the node-tmp root, outside its own scratch and the runtime paths, and asserts the write is refused and no probe lands. The probe check is the test's first assertion, so nothing stands between the seal and it.

A second test, test_creating_the_runtime_paths_goes_through_create_write_roots, intercepts create_write_roots and asserts the runtime paths are created through it with every runtime path among the roots it receives. A third, test_the_composed_fence_argv_for_a_fixed_root_set_is_literal, pins the whole composed argv for the fixture's fixed roots against a literal list, with the host's real delivery stores pointed away so the fixture determines the expected argv.
