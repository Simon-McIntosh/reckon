The removed protected defaults reach every launch — evidence

The fence's protected set is a flight key whose shipped default is the built-in list, and a layer removes a default only by naming it under unprotected_paths. Primary dispatch already threaded the resolved config into fence composition and recorded the removed defaults on the run's pointer. Two other launch paths compose a fence through the same plan builder — an in-place resume (resume_plan) and a lane-change redispatch (change_lane) — and both called it without that config, so a run resumed or lane-changed under a layer declaring unprotected_paths re-sealed a default the layer left writable. Promotion copied fence_waiver onto the ledger row but not the removed list, so the pointer held it only until promotion deleted it. Both launch paths now pass fence_config=config, and a shared helper records fence_unprotected_paths on the pointer exactly when the composed fence leaves a default out, popping it otherwise; promotion copies the list onto the committed row beside fence_waiver. A run that removes nothing carries the key on neither surface.

Measure: tests/test_unprotected_paths_reach_every_launch.py passes its three cases — a resumed run's fence leaves the named default writable and keeps the ones not named, a lane-changed run's fence does the same, and promoting a run whose pointer carries the list writes it onto the ledger row. The declared negative control drops the fence config from the resume launch path in a scratch tree; the resumed fence then re-seals the default and case 1 fails.
