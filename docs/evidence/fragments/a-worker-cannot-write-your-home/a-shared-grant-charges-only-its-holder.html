A shared grant charges only the run whose worktree holds the file

Two live runs granted the same figures directory each refused the other's uncommitted file. The boundary walk at promotion iterated every dispatch-visible tree and charged any changed path under the completing run's declared roots, without asking which run held that tree: a file another run left in-flight in its own worktree matched the shared grant and was reported as docs/figures/fixture/sketch.svg in peer worktree …/first-tree.

The new case synthesises two unfenced runs in a temporary repository and RECKON_HOME, both granted docs/figures/fixture. The first leaves sketch.svg uncommitted in its own worktree; the second lands its own committed change there and completes. Red at the base revision (a0d770a6): 1 failed, 10 deselected … EXIT=1, the refusal above. The fix reads the worktrees the currently live runs hold and skips them in the boundary walk, so an in-flight peer's uncommitted path is charged at that peer's own completion rather than to every run whose grant covers it. At head the case is green: 11 passed … EXIT=0. The run's own path outside its fence, a declaration off the shared list, and a bare peer worktree with no live run still refuse — those cases remain in the file and pass.

The declared negative control — attributing the dirty path to every run whose grant covers it — restores the removal of the skip and reddens exactly the new case (1 failed, 10 deselected … EXIT=1) while the head arm does not fail it.
