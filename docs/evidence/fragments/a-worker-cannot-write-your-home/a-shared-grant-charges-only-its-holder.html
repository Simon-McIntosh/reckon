A shared grant charges only the run whose worktree holds the file

Two live runs granted the same figures directory each refused the other's uncommitted file. The boundary walk at promotion iterated every dispatch-visible tree and charged any changed path under the completing run's declared roots, without asking which run held that tree: a file another run left in-flight in its own worktree matched the shared grant and was reported as docs/figures/fixture/sketch.svg in peer worktree …/first-tree.

The exemption is narrowed to the paths a live peer's own declaration covers, resolved through the same _repository_scope_paths helper the completing run's declaration reads. A dirty path a peer holds under its own grant is that peer's work, charged at the peer's own completion; any other dirty path in a peer's worktree is a stray edit the check exists to catch and stays charged here.

Two cases in tests/test_promotion_scope_counts_only_the_runs_commits.py pin both directions. The shared-grant case synthesises two unfenced runs both granted docs/figures/fixture, leaves sketch.svg uncommitted in the first worktree, and asserts the second run's completion succeeds — red at the base revision (a0d770a6): 1 failed, 10 deselected … EXIT=1, the refusal above. The stray-edit case grants the figures directory to the completing run only, leaves a file there uncommitted in a live peer's worktree that the peer never declared, and asserts the completing run is refused naming that path and the peer worktree. At head the file is green: 12 passed … EXIT=0. The run's own path outside its fence, a declaration off the shared list, and a bare peer worktree with no live run also still refuse.

The declared negative control — restoring the exempt-every-peer-path skip — reddens exactly the stray-edit case (1 failed, 11 deselected … EXIT=1, the refusal no longer raised) while the head arm does not fail it.
