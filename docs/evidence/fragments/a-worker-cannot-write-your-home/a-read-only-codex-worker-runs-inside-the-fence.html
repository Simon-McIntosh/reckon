A read-only codex worker is handed only roots the fence keeps writable

reckon/_worker_fence.py: fence_writable_roots appends the node-tmp seal — node_tmp_seal_root(), the node's own /tmp — to the sealed set it filters against, so a declared root at or above that seal is dropped exactly as one at or above a shared delivery store already was. A root beneath the seal still survives, so a run's own scratch directory is not collaterally withheld. No bind and no seal changed; the fence's grant loop and the fenced dialect both read the one rule, and delivery_write_roots' ambient temp root — /tmp where TMPDIR is unset — is the root this removes from a read-only codex launch.

tests/test_a_read_only_codex_worker_runs_inside_the_fence.py is new and passes 3/3. It composes a fenced read-only codex launch against a synthetic node tmp whose scratch root is <node-tmp>/reckon-crew-scratch and whose crew home sits outside it, declares the run's own scratch as a dispatch does, and asserts no --add-dir names a path at or above the node-tmp seal, that the run scratch beneath the seal is still handed and bound writable, and that every --add-dir the argv carries is either bound writable by the fence or outside every sealed path. The declared negative control restores the base rule — the one consulting only the shared delivery stores — under RECKON_TEST_NODE_TMP_ADDDIR_NEGATIVE=1, and reddens at 2 failed, 1 passed, EXIT=1.

The composed-argv listing at the dispatched base fccdd3136 carries --add-dir /tmp with bound-writable=False and sealed=True; at head the same listing carries only the run's scratch root beneath the seal, bound writable. The fence's --ro-bind destinations are unchanged between the two arms.

The named gate adds no failure against the base. Base arm, from a clean extraction at fccdd3136: 1 failed, 118 passed in 106.58s. Head arm: 1 failed, 121 passed in 122.10s. The single failing id is the same in both — tests/test_every_module_fits_a_worker_window.py::test_every_module_fits_a_worker_window, pre-existing at the base. ruff check and ruff format --check add no finding on the staged paths against their base blobs.

The live launch measure is not satisfied, and the cause is not the --add-dir mismatch this change removes. The base launch reproduces the plan's error verbatim — every shell command answers bwrap: Can't mkdir /tmp/.git: Read-only file system, and the run writes no manifest. Stripping --add-dir /tmp by hand leaves that failure unchanged, which the plan names as the branch where the mismatch is not the trigger. Three variants isolate it: with --add-dir /tmp present and the run directory under a non-tmp home, with only the run scratch as an --add-dir, and with no path under /tmp in the writable set at all and TMPDIR pointed outside it — codex's own sandbox still materialises a read-only mount point at /tmp/.git, and the node-tmp seal refuses the mkdir. So a fenced read-only codex worker still cannot run a shell command on this node for a reason outside fence_writable_roots. The head launch itself reached the provider only to be refused (429 Too Many Requests) and produced no fence signal, so it neither confirms nor contradicts the fix's effect on a live launch. What the change does buy is proved by the argv listing and the unit tests: the launch is no longer handed a root the fence seals. The residual cause belongs to the codex CLI's own sandbox and is carried as a followup.
