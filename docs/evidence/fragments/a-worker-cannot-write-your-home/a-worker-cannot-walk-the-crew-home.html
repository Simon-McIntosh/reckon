A worker cannot walk the crew home

A new pre-tool-use hook, reckon/hooks/worker_walk_guard.py, refuses a crew run's recursive walk rooted at the crew home, at a store root inside it (runs/, reviews/, reports/), or at an ancestor of the crew home up to /. It is scoped by RECKON_RUN_ID exactly as worker_git_guard.py is, resolves the crew home through that guard's own config-home resolver so RECKON_HOME moves it in a test as it moves every other reckon path, and reads a Bash command through that guard's tokeniser, segment split and cd tracking rather than a second shell parser. The git guard's interpreter hand-off moved into its entry point, so loading its module to reach the splitter has no side effect on the loader.

Refused for Bash: grep/egrep/fgrep/ugrep with -r, -R or --recursive (bundled groups such as -rl included), rg, fd, tree, du, ls -R, and find/bfs without -maxdepth 0 or -maxdepth 1. The Grep and Glob tools are judged on their path. The refusal names the root it would have walked and where each kind of record lives.

Installing the guard is a the operator path rather than a new option: --include-git-guard binds the pair. reckon/cli_entry.py resolves the walk guard beside the git guard and passes both paths to hook_installer.configure_crew_guards, which composes the walk guard's Bash and Grep|Glob groups whenever it composes the git guard's. That flag's meaning is what pinned two assertions in tests/test_worker_git_guard.py, which required it to bind exactly one Bash entry. They now state the pair contract: two Bash groups with the git guard's first and the walk guard's second, the walk guard again on Grep|Glob, and a merge that adds the walk guard beside the already-installed git group without duplicating it.
