A relaunch is refused while another launch of the run is in flight

Every relaunch of an existing run id now takes an exclusive reservation before the worktree is touched, keyed once on the newest attempt receipt in the run's own directory plus one. Two racing doors compute the same key, so exactly one holds it, and a door that loses is refused naming the attempt in flight. The launched attempt is carried from the reservation rather than re-derived, so a resume no longer launches the pointer's attempt plus one. The spawn guard admits the attempt its own reservation covers and refuses another.

A reservation is freed by its launch's own end and never by age or by comparing the pointer with its key: the reserving process holds it until a supervisor is recorded, and the supervisor's exit frees it thereafter, which is what lets the long-lived admit service launch repeatedly while a scheduler wait outlasts the launch window. An in-harness relaunch takes no reservation and is refused while a CLI launch holds one.

Six failures at head, each against its door and step:

  1. test_a_second_resume_records_the_third_attempt — resume CLI. The reservation key is computed from the receipts alone, so on a run whose first attempt left no receipt it is 1 while the launched attempt is 2. record_resumption then writes the pointer's attempt as the reservation's (1), and the supervisor's _publish_stored_phase declines to publish the ended phase because _record_is_this_attempt sees another attempt's pointer. The rule that breaks: the launched attempt is carried from the reservation, but the pointer is not.
  2. test_a_shortlived_launcher_leaves_a_worker_that_survives_and_completes — dispatch, no run directory. _spawn reaches _spawn_detached_worker because the stream is worker.log, so no reservation is taken and no reservation rule applies. The session leader this door returns is still alive five seconds after a worker that sleeps one. Nothing in the reservation path explains it; it needs a reproduction before a fix is designed.
  3. test_a_group_stop_after_the_spawn_is_recorded_as_that_stops_exit — dispatch CLI. The worker reports itself through its scratch marker before the supervisor has written worker.json. The reservation adds work to the launching process between the spawn ack and the survival wait, and the record lands after the marker. The rule that breaks: no reservation rule does; the ordering of the worker record against the spawn's first observable effect does.
  4. The three test_worker_env_export cases — dispatch CLI and in-harness. The dispatch call passes reservation= to _start_supervisor, and the tests' stand-in takes three positional arguments, so it raises TypeError: got an unexpected keyword argument 'reservation'. The rule that breaks: the door's handover is expressed as a keyword on a seam that pre-dates it.

Smallest design that passes all six

  1. Hand the reservation over after the start, not through it. Call _start_supervisor(spec_path, directory, run_id) as before and record the returned pid with record_reservation_supervisor(reservation, pid) in the calling door. The reservation still names the supervisor (the first finding stays answered), every three-argument seam keeps working, and the handover's reservation= keyword disappears. This clears the three test_worker_env_export failures.
  2. Record the attempt that was launched. Pass the same number the spec carries to record_resumption (max(reservation.attempt, pointer + 1), exactly as supervised_launch derives it) so the pointer names the attempt the supervisor started and the phase is published. This clears test_a_second_resume_records_the_third_attempt.
  3. Give a synchronous launcher an end. When the seam branch returns, the launch it stood in for is over: release the reservation there, or record the seam's pid, so a run launched through a seam is not held by the process that called it. This is what makes rule 2 safe and is the rule the deliverable already states (“freed by its launch's own end”).
  4. Leave the two timing failures to measurement first. Write worker.json before the survival wait in the supervisor's own path (it is already written immediately after Popen; move it ahead of any work that follows the spawn), and reproduce the detached-worker case before changing it. Neither should alter a §13 case, and both must be measured against the base arm before being claimed.
