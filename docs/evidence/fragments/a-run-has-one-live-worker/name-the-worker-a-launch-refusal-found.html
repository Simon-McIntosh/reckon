A launch refusal names the worker it found

Both refusals that stop a second launch worded themselves from the run's recorded pid. When the worker had been found by its session that pid was dead, so the refusal sent a coordinator to a process the table no longer held. The refusals now read the arm-carrying liveness reading and name what was actually found: the pid, the session, or the scheduler job.

The gap: a refusal worded from a pid that had gone

live_worker_pid in reckon/crew/recovery_liveness.py asked whether the pointer read alive and then returned the pointer's recorded pid. That answer is the worker's own only in the recorded-pid arm: the session walk reaches a worker whose recorded pid is dead, and a placed run's recorded pid names the scheduler client. Both refusals in reckon/crew/dispatch_launch.py — _prepare_attempt_records and _supervisor_spawn_worker — built their text from that pid.

Reproduced first, in a temporary crew home, with the recorded pointer pid 508 dead and a stand-in process 510 carrying the run's session id. The launch was refused, and the refusal named the dead pid and no session:

REFUSAL: run 'r-repro-launch-refusal' still has a live worker (pid 508): a launch
that started now would run a second worker beside it; observe or stop it before
launching again
refusal names the recorded dead pid: True
refusal names the session: False

§5's session-walk case asserted only the prefix still has a live worker (pid , so the dead pid passed it, and its remaining control was assert pid > 0.

What changed

  • reckon/crew/recovery_liveness.py gains live_worker_reading, a companion beside live_worker_pid. It composes the same reads in the same order — the pointer's pid, the supervisor's worker record, the environment mark — and returns the LivenessReading §8 added to process_liveness.py, so the arm that answered is kept: recorded pid, session walk, or placed job.
  • live_worker_pid keeps its int | None shape and now takes its pid from that reading. It answers a pid only for the arms that read one this host probed as the worker's own, so a run found by its session, or placed on a scheduler job, names no process rather than a number that belongs to something else. Its other consumer, the lift refusal in resumption.py, is unchanged.
  • Both refusals read live_worker_reading and word themselves through one helper, _live_worker_naming: the recorded pid, the session id, or the job id, whichever the arm that found the worker carries. Every arm that reads alive still refuses; only the wording changes in the session-walk and placed arms.

The gate

tests/test_a_queued_run_launches_once.py shows five cases, each asserting the whole refusal text rather than a prefix, against a temporary crew home:

  • beside a live recorded pid, refused naming that pid;
  • beside a worker found only by the session walk with the recorded pid dead, refused naming the session and not the dead pid;
  • beside a placed run's live worker, refused naming the job and not the scheduler client's pid;
  • beside a run whose worker is proven dead, the launch proceeds;
  • a fresh dispatch refused at _prepare_attempt_records names the session and not the dead pid.

An autouse fixture asserts the operator's real crew home is untouched by every case. The armed suite ran 3 passed at the base revision and 5 passed at the head; tests/test_resume_refuses_a_live_worker.py passed 10 tests unchanged, guarding the worker-record and environment-mark pid wording.

Three declared mutations were applied and each reddened its named case: wording from the recorded pid alone failed the second case; removing the liveness read from _supervisor_spawn_worker let the second worker launch in the first case; rewording only the supervisor site failed the fifth case.
