A worker spawn refuses a run that already has a live worker

The supervisor's spawn seam, _supervisor_spawn_worker in reckon/crew/dispatch_launch.py, asks live_worker_pid — the same read the launcher's own refusal uses — before it starts a worker and before it writes this attempt's worker record. One read therefore answers for the run: the pid an earlier attempt recorded, and, when every recorded pid is dead, a walk for a live process of this user whose command line carries the run's session id. A live worker refuses the launch and the refusal names its pid (still has a live worker (pid N)); the refusal is raised before anything in the run directory is rewritten, so a refused launch leaves the incumbent's records exactly as it found them. A run with nothing live spawns as before.

The pointer names the attempt that was just started, so by the time the supervisor runs its pid may already be this process. The seam drops the pointer's own pid when it equals the caller's and answers from the run's worker record and session instead; without that exclusion every launch refuses itself, which is what the dispatch-race control below measures.

The gate is tests/test_a_queued_run_launches_once.py. At the head revision it reports 3 passed, EXIT=0 on the declared command. At the base revision with the test copied in it reports 2 failed, 1 passed, EXIT=1, both failures reading DID NOT RAISE CrewError: the second launch proceeded beside the live worker, which is the defect reproduced. Both refusal cases also assert the run's attempt records are unchanged after the refusal, so each reddens when the liveness read is removed; with the refusal made unreachable the arm reports 2 failed, 1 passed, EXIT=1, failing exactly those two ids.
