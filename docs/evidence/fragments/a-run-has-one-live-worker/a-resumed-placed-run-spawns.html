A resumed placed run spawns once its previous attempt has ended

A resume of a run placed on the fleet's srun placement was refused at the spawn guard. _prepare_attempt_records retires the canonical worker.json and exit.json into attempt-N-worker.json and attempt-N-exit.json before either guard runs. The scheduler cannot answer for that placement, so the liveness read stays placed with liveness unknown. _launch_refused_by in reckon/crew/dispatch_launch.py then found the attempt receipts, so _record_holds_a_worker answered true, while _worker_record_liveness found no canonical worker record and answered None, and is not False refused. The refused attempt left its own exit receipt and no canonical worker record, so the first guard refused every further resume the same way.

The shared predicate now reads the newest attempt receipts when no canonical worker record exists: the highest N with an attempt-N-worker.json or attempt-N-exit.json. An exit receipt for that attempt is its own record that it ended. A worker receipt with no exit beside it is probed through record_process_alive, the same start-tick comparison the retired worker's pid needs, and a dead pid lets the launch through. A retired worker receipt whose pid is alive; a receipt that cannot be read; and every reading that is alive all still refuse. While a canonical worker record exists the predicate answers exactly as before, so a pointer pid with no worker record to answer for it is still a refusal. Both callers, _prepare_attempt_records and _supervisor_spawn_worker, reach the one predicate and answer alike; live_worker_reading and record_process_liveness are unchanged.

The reproduction ran first: a temporary crew home holding a placed run with a retired attempt-1-worker.json naming a dead pid, an attempt-1-exit.json, a current attempt.json for attempt 2, no canonical worker record and a pointer pid that is not the supervisor's own was passed to _supervisor_spawn_worker, which refused with cannot read whether its worker is live (placed on job 1291586, liveness unknown): a launch that started now would run a second worker beside it. The gate is tests/test_a_resumed_placed_run_spawns.py: at the head revision it reports 5 passed, EXIT=0, and the same three-file population including tests/test_a_queued_run_launches_once.py and tests/test_a_run_not_yet_launched_is_not_refused.py reports 16 passed, EXIT=0. At the dispatch base (e8fa945150) with the new test copied in it reports 3 failed, 2 passed, EXIT=1, failing the exit-receipt case, the dead-worker-receipt case and the further-resume case — the defect reproduced — and the same population reports 3 failed, 13 passed, EXIT=1 with the two neighbouring launch tests passing at both arms.

The negative control restores the predicate that refuses a placed-unknown reading whenever attempt receipts exist without a canonical worker record, in a scratch copy of the head tree. It reports 3 failed, 2 passed, EXIT=1 on the same three ids, so the check fails against the mutation it declares.

The five cases run with the scheduler query stubbed to answer nothing. Four go through _supervisor_spawn_worker: a resumed placed run whose previous attempt has an exit receipt spawns; one whose previous worker receipt names a dead pid and has no exit receipt spawns; one whose previous worker receipt names a live pid is refused with the second-worker text and records no worker; a never-launched placed run still spawns. The fifth goes through _prepare_attempt_records: a further resume of a run whose previous attempt was itself refused at spawn, leaving only attempt-N-exit.json and no canonical worker record, passes the first guard and spawns. Every case asserts the operator's own crew home listing is unchanged.
