A relaunch never touches a live tree

A dispatch on a non-local lane, or an admitted launch, is not answered by the existing-run branch, so it reached worktree creation. This dispatch's own claim overwrote the live pointer first, the worker's tree read as a disposable leftover, and it was released and re-cut from a newer base. A dispatch of a run id whose worker this host still sees running is now refused before the claim, the run directory or the tree is touched.

The defect, reproduced

The reproduction builds a temporary crew home and repository, lays down a live stand-in worker holding a worktree, advances the repository by one commit, then dispatches the same run id on a non-local lane. A recorder wrapped around _create_worktree captured the tree's state either side of the call, so the ordering is shown on its own and not inferred from a later refusal:

tree-creator observed     {'before_head': 'b0ebdbd18fe5…', 'before_note': True,
                           'after_head': '4ce47efa0775…',  'after_note': False}
stand-in file present     False
stand-in tree exists      False

The worker's head moved from b0ebdbd18fe5 to the newer base 4ce47efa0775 and its own file was gone at the moment of creation — the tree it had been writing into was released and re-cut. The dispatch then hit a later refusal and the unwind removed the replacement tree as well, leaving the live worker with no tree at all. The reproduction is reproduce-relaunch-rebuild.py and its output is repro-live-tree-defect.log.

What changed

  • reckon/crew/dispatch.py gains _refuse_a_live_worker_before_the_worktree. It reads the run's live pointer and takes the holder through the composition a launch uses — live_worker_reading, which carries the arm that found the worker it names, narrowed by the same _launch_refused_by predicate _prepare_attempt_records refuses a second launch with — so a dispatch and a launch cannot disagree about whether a run is held. A run id with no live pointer has never launched here and is not refused; a placed record that has never launched is not refused either, because the predicate already answers that.
  • A pointer that exists and cannot be read — bad JSON, a non-object, an I/O failure — refuses and names the read failure. Only a missing pointer passes. Skipping the check on a read error would turn a corrupt record into permission: it says nothing about whether its worker is still running, so the tree could be rebuilt underneath a live one. That is the same fail-open shape the check exists to close, one level down.
  • The refusal is raised immediately after budget and before directory = run_dir(run_id), which is the first write this dispatch makes. Nothing of the refused dispatch exists afterwards: no claim, no brief copy, no run directory, no tree. The local-lane answer through _answer_existing_node_run is unchanged, because it returns before this point.
  • The refusal names the attempt and the worker the reading found, so the reader can check the same process: run 'r-held-run' still has a live worker (pid 1234): attempt 2 still holds this run, …

The gate

tests/test_a_relaunch_never_touches_a_live_tree.py runs the three cases §10 asks for, plus the unreadable-pointer case, on a temporary crew home and repository, with the stand-in's file git-ignored so the tree reads clean and _create_worktree's own disposable-tree rule can release it — which is exactly what a real worker's fence mounts look like.

  • Live worker, non-local lane. The dispatch is refused with this section's text, and afterwards the tree's head is the stand-in's own, its ignored file is intact and git status is clean, the pointer's bytes are unchanged, and the run directory listing and the operator's own crew home are untouched. It also asserts the clause unique to this refusal (cutting its worktree again), because the prefix it shares with the launch refusal would be satisfied by that other refusal alone.
  • Unreadable pointer. A pointer holding invalid JSON, with a stand-in tree laid down, is refused naming the read failure; the tree is unchanged, the pointer's bytes are unchanged and no run directory is written.
  • Worker proven dead. The dispatch proceeds as today: the returned record carries the run id, the tree is cut at the newer base and the stand-in's file is gone with it.
  • Spy on the tree creator. With a live worker and _create_worktree replaced by a recorder that raises; the dispatch is refused with this section's text and the recorder's call list is empty.

The base arm fails the live-worker case with DID NOT RAISE CrewError — the dispatch went through and rebuilt the tree — the corrupt-pointer case for the same reason, and the spy case with the worktree was created over a live worker. The dead-worker case passes at the base, as it must: it pins behaviour that already worked. Moving the check after _create_worktree reproduces all three failures from the head revision, so the ordering, not merely the presence of some guard, is what they rest on; removing the check alone would not be a control, because the launch refusal in _prepare_attempt_records still stops the second worker after the tree has been rebuilt. Swallowing the read failure again fails the corrupt-pointer case alone (DID NOT RAISE), which isolates the fold: the other three cases stay green under it.

A related dispatch suite (tests/test_dispatch_guard_consults_liveness.py, tests/test_a_run_not_yet_launched_is_not_refused.py, tests/test_concurrent_dispatch_of_one_node.py, tests/test_dispatch_launch_is_not_its_own_conflict.py, tests/test_a_redispatch_keeps_the_queued_identity.py, tests/test_a_queued_dispatch_is_accepted.py, tests/test_a_discard_releases_its_dispatch_claim.py and tests/test_crew_dispatch_guard.py) reports 50 passed and one failure, test_occupied_project_reuses_the_watcher_armed_by_the_first_dispatch, which fails identically at the base revision — a pre-existing failure, not a delta from this change.

A placed record with no readable worker at all is not this check's case: the launch refusal in _prepare_attempt_records answers it, so this guard leaves it alone.
