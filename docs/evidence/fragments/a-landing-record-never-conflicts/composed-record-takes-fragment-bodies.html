The composed record takes each fragment's body

A landing record composes its fragments by appending each fragment's body content rather than its whole document, so a fragment's own head metas can no longer duplicate the record's scalars.

The defect: a fragment's document wrapper entered the record

compose_landed_record read each fragment with read_bytes() and extended the composed bytes with it whole. A fragment is written as a full HTML document, so its <!doctype>, <head> and <html> wrapper followed the record's own bytes into the composition. When the fragment's head carried the record's scalar metas — plan-slug, plan-evidence-for — the composed document held each twice, and doccheck reported it as a duplicate-plan-scalar: the reader takes the last value, so a writer updating the record's line would report success while the surface kept the fragment's.

What changed

  • _fragment_body_bytes in reckon/evidence.py returns the children of the fragment's main element when it has one, else the children of its body, so the document wrapper never enters the record.
  • A fragment with no html and no body element — a bare anchor — is returned unchanged, so a fragment written before the wrapper existed still composes byte-identically.
  • A record with no fragments still composes to its own bytes exactly: the no-fragment early return is untouched.

The fragment anchor the composed record is expected to carry is its body content, which is kept; only the wrapper is dropped.

The gate: tests/test_composed_record_takes_fragment_bodies.py

A record for plan demo carrying plan-slug demo-landed is composed beside one full-document fragment carrying its own plan-slug demo and plan-evidence-for demo. The composed text holds exactly one plan-slug and one plan-evidence-for, both the record's, and reckon.doccheck.audit_file reports no duplicate-plan-scalar finding. A second case asserts the fragment's section id appears once in the composed text.
