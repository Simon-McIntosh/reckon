A re-synthesis carries every appended anchor and names each loss

What changed. An evidence append writes an anchored section into a plan's landed record, and a link in the plan points at that anchor. A synthesis rewrites the record from the plan's comments and the run ledger, so every anchor it did not render used to disappear: the section was gone and the link it backed pointed at nothing, with no line saying so. synthesize_landed_record in reckon/evidence.py now reads the record it is about to overwrite, classifies each top-level section, and writes the survivors into the new document.

One function decides which ids the record can render. _evidence_anchor_sets derives two sets of element ids from the plan, the ledger runs and the plan source, normalising every spelling through _section_key so s5.1 and s5-1 name one section: the rendered set, the keys this synthesis will write a section for, and the reserved set, the rendered keys plus every declared plan section, every labelled section and the plan-level outcome id. The synthesis carries by the first set; the append_evidence refusal reads the second. Both are the same function's output, so a record the synthesis would overwrite and an anchor an append may not take cannot drift apart.

Four outcomes, each named. An appended section — marked data-evidence-origin="append" when it is written — is carried verbatim into the new record unless a run now renders its id, in which case it is dropped and the rendered section replaces it. An unmarked section on a rendered id is replaced: the synthesis owns that id and says so. An unmarked section outside the reserved set is carried, because nothing else will ever write it back. An unmarked section on a reserved-but-unrendered id is retired — dropping it is the synthesis doing its job, and the tag says so rather than staying silent. EvidenceSynthesisResult.lost_anchors carries the tag and the anchor for every classification except a clean carry, and reckon evidence synthesize prints one line per entry.

The refusal closes the other half. _apply_evidence_appends in reckon/_store.py now resolves the plan and its ledger runs and refuses any anchor whose _section_key is in the reserved set, before a byte is written. Previously an append could take the id a ledger run already rendered, and the next synthesis silently discarded it. The path helper _evidence_record_path moved into evidence.py as its sole owner, so the write and the refuse read one record path.

What the cases hold. A marked append survives a re-synthesis with its text and its mark; the record writes each section once; a marked anchor a later run now renders is dropped and named; an unmarked section on a rendered id is replaced and an unmarked one outside the reserved set is carried; a declared, unrendered plan section is retired rather than kept; an append on a plan section id (s4, and s5.1 spelling the plan's s5-1) is refused; an append on an id only a ledger run renders is refused; and one test drives a key from appendable to rendered to refused, so the two sets are shown to be one.

Not done here. The carry re-series carried markup through BeautifulSoup, so attribute quoting and whitespace inside a carried section are normalised, not preserved byte for byte; the section and its text are. The project's ruff backlog is untouched: the four staged paths add no findings and no new unformatted hunk against the base.
