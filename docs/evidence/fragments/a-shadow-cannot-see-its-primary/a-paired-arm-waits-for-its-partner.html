A paired arm waits for its partner

Change. _require_partner_terminal_before_promotion (reckon/crew/promotion_checks.py) refuses a promotion whose partner arm is non-terminal. The partner is resolved from the record's own pairing: paired_shadow_run_id on a primary arm, or the shadow lineage's primary_run_id on a shadow arm. A partner pointer that is absent reads as terminal — the partner has been promoted — and one whose phase is in the terminal set lifts the hold. Anything else refuses, naming the partner run id and the phase it is in, before any store is written. The check is registered in the lambda list reckon/crew/promotion.py passes to _require_independently, beside _require_worker_stopped_before_promotion.

New tests (tests/test_a_paired_arm_waits_for_its_partner.py, each in a temporary repository with RECKON_HOME under tmp_path):

  • a paired primary arm whose partner's pointer reads working is refused, the refusal naming the partner id and the phase, and nothing lands — no ledger row for the run and its live pointer intact;
  • the shadow arm is refused the same way through its lineage, so either arm can be held;
  • the same promotion succeeds once the partner's pointer is terminal (complete), and succeeds when the partner's pointer is gone;
  • an unpaired run, and a standalone shadow whose primary was already promoted, promote unchanged;
  • a shadow whose stream reads its primary's run directory promotes with shadow_contaminated: primary_run_directory_read and shadow_controlled: false on the stored row, guarding the _shadow_control_marks call in _complete_locked.
