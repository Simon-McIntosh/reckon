The review verb composes a code neighbourhood, and the plan form survives as an alias

reckon crew review now takes a code subject beside its plan subject. --around <plan> resolves the production paths a plan's still-implementable sections name in their Write paths sentence, and --path <path> names one directly. The verb turns those paths into a module set through reckon.served_code.neighbourhood(repo, revision, paths) — the existing reachability instrument, so no second import walker was written — which yields the named modules plus every production module one import away in either direction. The composed brief is the health rubric from reckon/crew/prompts/health_review.md, followed by the reviewed revision, the named paths, the neighbourhood modules, the open findings reckon/crew/findings.py already stores against those paths, and the four figures from reckon/interface_counts.py. The report directory is keyed by the neighbourhood digest, so two reviews of one neighbourhood share a directory and a changed neighbourhood earns its own.

reckon crew review-plan is kept as a hidden alias: it prints one deprecation line to stderr and otherwise composes the same plan brief, calling the same body as reckon crew review --plan. All pre-existing options moved to the new verb unchanged.

Measure: tests/test_review_composes_a_code_subject.py passes at EXIT=0 (5 passed). It builds a temporary repository in which reckon/a.py imports reckon/b.py while reckon/c.py is unrelated, mounts it as project sample, and gives plan fixture an implementable section whose prose names reckon/a.py as a write path, with a committed plan-review record carrying an open finding anchored to reckon/a.py:3. The test asserts the composed brief's Named paths line names reckon/a.py and its Neighbourhood modules line names reckon.b and not reckon.c, that the stored finding and the four interface-figure keys are present, and that crew review --plan fixture --dry-run composes the same plan brief as crew review-plan --dry-run once the per-invocation run id and stamped instant are folded out (the two invocations mint their own identity, so literal equality would be a false measure).

The delivered report and the stored record. Composition alone left the review as prose in a directory. A composed code subject now writes its sidecar beside its brief, and a delivered report is read back by the path that delivers plan reviews: delivered_report_record takes a sidecar whose subject is code, reads the report through the health rubric's own parser (parse_health_review) and returns a record keyed by the neighbourhood, _store_delivered_report writes it through store_code_review, and store_delivered_reviews stores the code reviews composed around the plan it is storing — so a code review takes the plan-build route a plan review does rather than needing a store step of its own. The store keeps code-<neighbourhood>.json beside the plan-<slug>.v<N>.json family, so the plan-review listing never reads one as the other. The test writes a fixed health report into a composed code review's report directory, runs the delivery path, and reads the record back by neighbourhood: the finding anchor is reckon/a.py:3, the treatment is the rubric's none form with its reason, the run id is the composing run's, and a second pass stores nothing further.

One subject per command. --plan given together with --around or --path is refused with a one-line crew_error detail at exit 1, and the test asserts that for both companions. The two kinds read different subjects and are keyed differently — a plan by its content, a code review by its neighbourhood — so silently preferring one would report a review of something nobody asked for.
