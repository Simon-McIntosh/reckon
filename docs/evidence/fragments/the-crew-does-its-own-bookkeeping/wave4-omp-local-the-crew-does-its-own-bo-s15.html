A held review duty clears when the review exists, not only when it launched

Reproduction at the base revision. The stall was not the derivation: the obligations view already listed a dispatched review as review-in-flight, a queued review as review-queued, and a review admitted under a new id as no duty at all, each with a report or wait command and never a dispatch command. The stale listing lived in the held answer a station tick publishes and the stop hook reads, whose read-time settlement accepted only a recorded attempt with the status dispatched. Measured against the base revision, reading one published review-missing row through without_departed_run_duties with the reviewed run's pointer recording each status in turn: dispatched kept [], queued kept ['review-missing'], lane-paused kept ['review-missing'], refused kept ['review-missing'], withdrawn kept ['review-missing']. A review run the reflex had handed to the lane therefore left the hook naming a dispatch for a review that already existed, which is the reported defect.

Change. REVIEW_DISPATCH_STARTED_STATUSES in reckon/crew/obligation_snapshot.py names both statuses that carry a review the fleet holds — dispatched and queued — and the settlement reads it. A refused, skipped or withdrawn attempt, and a lane that composed no review run at all, still keep the row, because the review is still owed there.

Gate. tests/test_a_review_missing_duty_clears_when_its_review_is_dispatched_or_queued.py reads both surfaces for each window: the derivation, then the held answer published before the fleet moved and settled at read time. Every case first shows the row exists — review-missing with a reckon crew dispatch command — then moves the fleet and reads again: a dispatched review (review-in-flight, the row settled elsewhere and the held row dropped), a queued review (no review-missing, nothing naming a dispatch, the held row dropped), and a queued review whose live pointer was replaced by an admitted one under a new id while the recorded entry still names the queued id (no duty at all, the two ids asserted, the held row dropped).

Arms. Both arms are git checkouts under the run's scratch directory, with the four follower variables unset, run in place on the fleet node with pytest -n 8, and each log names the revision, the tree, the literal command, the module as imported and the resolved cwd. Base 36 passed, EXIT=0; head 39 passed, EXIT=0 — the head arm carrying the three new cases and no added failure. Logs: arms/base.log, arms/head.log.

Negative control. Removing the check — REVIEW_DISPATCH_STARTED_STATUSES narrowed back to frozenset({"dispatched"}) — turns the gate red: 2 failed, 1 passed, EXIT=1, on both queued cases, each failure printing the row it found: {'kind': 'review-missing', 'next_command': 'reckon crew dispatch …'}. The dispatched case still passes, which is the control's own statement: only the queued statuses were unloaded. Log: arms/negative_control.log.

Lint. ruff check and ruff format --check on the changed module and the new test add no findings.
