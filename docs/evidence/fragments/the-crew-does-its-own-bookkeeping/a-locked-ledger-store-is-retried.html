A locked ledger store is retried

run_store.append retries an index write that lost a race for the store's write lock, with a backoff bounded by wall clock (INDEX_RETRY_SECONDS) rather than by an attempt count, so a lock held for milliseconds still writes its row and one held past the bound is raised instead of holding the promotion open. The retry sits below that seam, inside one call, so ledger._index_append still makes one append per run however many attempts a lock took — the concurrent-append test measures the seam's call count and fails on a retry placed above it. Only a lock is retried: _locked accepts an OperationalError that says locked or busy, and a duplicate-row or malformed-record refusal is raised at once because the same write would fail again. The one retry helper, _retrying, opens its connection with a short busy timeout (INDEX_BUSY_TIMEOUT_SECONDS) because a five-second driver wait would spend the whole bound inside the first attempt; every other connection — a refusal stamp, a reader, a corpus import outside the retry — keeps the driver's own patience, so nothing but the retried write changed its waiting behaviour.

The repair pass is run_store.import_ledger, which the promotion gate already runs: it inserts every committed run the store lacks and corrects a row that disagrees, so a run promoted with a failed index append is covered without a second implementation beside it. import_ledger writes through the same _retrying helper, so a lock met while it walks the corpus is waited out rather than surfacing as an uncaught OperationalError; its counts are recomputed per attempt, because a retried attempt re-walks the corpus and sync_run is idempotent.

Measure: the defect reproduced at base 327ce7a6bb — a write lock held for six seconds made the append return {"status": "failed", "error": "OperationalError: database is locked"} after a single 5.01 s attempt, with the row absent. At the repaired head 9812a25966, a 0.6 s lock writes its row on a later attempt (0.97 s elapsed, row indexed); a 5.0 s lock is reported failed and then appended by import_ledger (rows_imported: 1, row indexed); and an import begun while another connection holds the lock for 1.0 s finishes it (rows_imported: 1, 1.07 s elapsed). Negative controls: the same 0.6 s lock against a package whose retry bound is removed fails the append in 0.6 s with the row absent, so the passing arm is the retry rather than the store's own patience; the same 1.0 s lock against the pre-repair tree raises OperationalError: database is locked out of import_ledger after 0.2 s, so the passing import arm is the scoped timeout and the retry together; and repair_index/unindexed_run_ids exist in the pre-repair tree and are absent at the repaired head, so the deletion is what removed the duplicate.

No repository regression test could be added: this node's granted write scope carries no tests/ path, so nothing in the tree reddens if the retry is removed. The measures above are produced by probe_index_retry.py under the run directory and recorded there; adding the test belongs to a node whose scope includes tests/.
