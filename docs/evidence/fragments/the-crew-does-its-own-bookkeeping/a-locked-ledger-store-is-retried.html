A locked ledger store is retried

_index_append in reckon/ledger.py retries an index write that lost a race for the store's write lock, with a backoff bounded by wall clock (_MAX_INDEX_RETRY_SECONDS) rather than by an attempt count, so a lock held for milliseconds still writes its row and one held past the bound is reported failed instead of holding the promotion open. Only a lock is retried: _locked_index_error accepts an OperationalError that says locked or busy, and a duplicate-row or malformed-record refusal is returned at once because the same write would fail again. RunStore's connection now takes a short busy timeout (INDEX_BUSY_TIMEOUT_SECONDS in reckon/run_store.py) because a five-second driver wait spent the whole bound inside the first attempt, leaving the backoff nothing to retry with. A failed append no longer waits for a reader to rebuild the whole index: unindexed_run_ids lists committed run filenames the index lacks without decoding a payload, and repair_index appends just those rows through the same bounded retry, reporting which were missing, appended and failed.

Measure: the defect reproduced at base 327ce7a6bb — a write lock held for six seconds made the append return {"status": "failed", "error": "OperationalError: database is locked"} after a single 5.01 s attempt, with the row absent. At the change, a 0.6 s lock writes its row on a later attempt (1.61 s elapsed, row indexed), and a 5.0 s lock is reported failed and then appended by repair_index (appended: ["r-locked-append"], row indexed). Negative control: the same 0.6 s lock against a package whose retry bound is removed (_MAX_INDEX_RETRY_SECONDS 3.0 → 0.0) fails the append in 0.6 s with the row absent, so the passing arm is the retry rather than the store's own patience. No regression test could be added, because this node's granted write scope carries no tests/ path; the measure is produced by probe_index_retry.py under the run directory and recorded there.
