§29 — A state write's commit waits out a held index lock

The defect reproduced at the base revision. With .git/index.lock created before the call, a state write raised could not stage state write docs/state/proj/crew.json: fatal: Unable to create '…/.git/index.lock': File exists and left the commit count at 1, so the write did not land.

ledger._commit_state_write now runs both its git add and its git commit through merge._run_waiting_out_a_held_index_lock, so a transient hold is waited out on that helper's cadence and bound. The lock is read from the checkout's own index.lock, not from the failing command's text. A failure that leaves no lock behind raises at once as before; a lock that outlasts the wait raises naming index.lock and the attempt bound. The call returns the retries it made, so a caller can record that its write waited.

Measure: the focused gate python -m pytest -q tests/test_a_state_write_waits_out_a_held_index_lock.py reports 3 passed at the head revision: a lock released between attempts lets the write commit with 1 retry counted; a lock held past the bound raises naming index.lock after 7 waits (the helper's 8 attempts less the first); and a failing pre-commit hook with no lock raises at once with 0 waits. The negative control replaces the add's lock wait with a single direct attempt and the first case fails (2 failed, 1 passed). Over the 52 test files of the ledger-importing population that completed, the head arm's 16 failures are the same 16 the base revision fails, so the change adds none.
