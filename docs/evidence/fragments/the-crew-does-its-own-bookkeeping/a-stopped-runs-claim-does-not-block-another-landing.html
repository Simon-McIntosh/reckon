a-stopped-runs-claim-does-not-block-another-landing — a stopped run's claim admits another run's landing

What changed. A promotion that accepts a path outside its run's declared write scope now walks past a peer claim when that peer's process has ended and its manifest records a terminal status. The judgement is made where the acceptance calls in: widen_claim(..., acceptance=True) in reckon/crew/claims.py passes the stopped peers to refuse_widen_scope_conflicts to set aside, and _accepted_scope_exceptions in reckon/crew/promotion_scope.py applies the same rule and writes the walked-past claim on the acceptance as stopped_peer_claims: [{run_id, claim}]. The shared _raise_repository_scope_conflict is unchanged, so a dispatch over the same paths still refuses. Stoppedness is read at the acceptance from local_liveness(pointer) (host-gated) and from the peer's own manifest through parse_manifest, never from a field kept on the pointer. The manifest is read through the repository's own _manifest_freshness pairing with the pointer's manifest_baseline_mtime_ns, so a predecessor's terminal manifest left at the same path by a resumed or redispatched attempt is not read as this attempt's delivery.

The refusal, reproduced before the repair. A temporary crew home held two stopped runs with terminal manifests, each holding a commit that changed the path the other declared. Promoting either with accepted_paths={…} raised reckon.crew.CrewError: run 'r-run-a' cannot accept b.txt: live run 'r-run-b' claims b.txt from promotion_scope.py:635 in _accepted_scope_exceptions, reached through promotion.complete → _landing_preconditions → _landing_scope_products. The first fixture recorded each run's repo as its own worktree, which made the peers look like different repositories and the promotion succeeded; the reproduction is only valid once both runs record the same repository root.
