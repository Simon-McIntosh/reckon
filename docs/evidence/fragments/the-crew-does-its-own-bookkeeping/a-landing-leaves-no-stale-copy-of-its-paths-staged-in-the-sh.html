A landing leaves no stale copy of its paths staged in the shared index

A landing now reads the shared index back once the branch has moved. Any path the landing moved that the index stages with content other than HEAD's is restored in the index, with the working-tree file left exactly as the peer left it, so the next plain git commit from any session cannot take the pre-landing copy back. Promotion's own landing commit does the same over the paths that commit moved.

The reproduction at the base revision (4cae3c76ca) runs a real landing with a peer staging pre-landing copies in the post-merge window: the landing returns a commit, git diff --cached --name-only lists ledger.py test_ledger.py tracked.txt, and the following plan commit reverts all three. With the reconciliation the same run prints an empty staged set and the plan commit touches plan.html only.

Four cases in tests/test_a_landing_leaves_no_stale_staged_copy.py pass at the head. Removing the reconciliation turns two of them red, naming test_a_landing_leaves_no_landed_path_staged and test_a_peer_edit_stays_uncommitted_rather_than_staged.
