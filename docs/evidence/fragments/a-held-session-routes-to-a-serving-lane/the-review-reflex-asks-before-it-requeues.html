The review reflex's retry asks the route question before it re-queues

§4's last sentence was unbuilt: the review reflex composed an automatic review onto the local lane deterministically, so a local lane whose router grants this session no worker held the review, queued it, and the next sweep composed the same review onto the same lane again — the loop the plan records as a review re-queued twice on the local lane 17 minutes after the first hold.

reckon/crew/recovery_review_dispatch.py now carries two additions. _zero_slot_held_lane reads the lane a recorded hold names (status lane-paused/awaiting-lane) and asks that lane's own published admission, through dispatch_plan._dispatch_lane_allowance, whether it grants the session no worker — the same reader §2 gave the picker, and the check that tells a zero-slot hold from a paused gate, which records the same status. _reroute_held_review then asks the route question once with that lane left out of the offering (the picker's own _config_without_lane), and the answer is the retry's: a route carries the review onto the lane the answer named; a hold or refuse is reported as awaiting-lane rather than stepped over; a fallback (a timeout, an unreadable input) is not an answer at all and keeps the existing path. Both asks are written to the run's REVIEW_DISPATCH_FIELD record, so a reader sees the lane that refused the review beside the answer the second ask produced.

The question is asked only when the reflex has another lane it may offer. That test is _review_lane_candidates, the same list the compose itself draws from, so review_excluded_backends — minus the backends a lift has opened — is what decides it. A fleet whose only other lane is review-excluded therefore asks nothing and re-queues on the local lane exactly as before, which is why the un-lifted arm of the measure is a preserved behaviour rather than a new branch.
