racing-claims-order-by-parsed-time — the racing-claim order reads parsed moments, not raw strings

_peer_claim_is_a_later_racing_arrival (reckon/crew/dispatch.py) decided which of two overlapping dispatch claims owns the paths by comparing each claim's registration timestamp as raw text. One caller writes ...T04:00:00Z and another writes ...T04:00:00.500000+00:00; those spellings name moments half a second apart but sort the wrong way round, because 'Z' is above '.'. A later arrival could therefore rank as the earlier one, so the pair could both proceed or both withdraw instead of exactly one surviving.

Each registration time is now read through reckon._timestamps.parse_utc and the claims are ordered by the parsed instant, falling back to the run id when the instants are equal. A stamp the parser cannot read leaves the comparison inconclusive, so the peer claim stays binding exactly as an absent timestamp does today.

Measure. tests/test_one_of_two_racing_reviews_survives.py gained a mixed-spelling case that both directions of the old ordering got wrong, and an unparseable-stamp case asserting the peer is still refused. The gate ran only that file: 6 passed, EXIT=0.

Negative control. Restoring the raw-string comparison makes the mixed-spelling case fail (test_mixed_spelling_registration_times_order_by_the_parsed_moment) and the unparseable-stamp case fail, while the four pre-existing cases pass: 2 failed, 4 passed, EXIT=1. The log is negative-control.log under the run directory.
