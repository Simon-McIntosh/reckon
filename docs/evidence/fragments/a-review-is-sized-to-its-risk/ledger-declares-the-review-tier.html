The promoted-row schema declares the review tier

Once promotion resolved and wrote each run's review tier, the tier rode every promoted row as an undeclared key. RECORD_FIELDS in reckon/ledger.py omitted review_tier, so the declared-field check that reads the mounted promoted rows reported the key the moment any promoted row was read, and build_record did not carry the key at all, so declaring it alone would have broken the invariant that RECORD_FIELDS ⊆ build_record(...).

Reproduction

The defect is the declared-field check's own subject matter. At the base revision ba1a26e4, git grep -l '"review_tier"' docs/state/reckon/runs/ matches 19 committed rows, and "review_tier" in ledger.RECORD_FIELDS is False — a key present on real promoted rows and absent from the schema that describes them. reckon/crew/promotion.py has set run["review_tier"] = review_tier on every promotion since 13f950ff.

The change

  • Commit 106e0c16 (fix(ledger):) adds "review_tier" to RECORD_FIELDS and adds tests/test_ledger_declares_the_review_tier.py, which mounts a synthesised promoted row and runs the mounted-row declared-field check, reusing that check's own _promoted_ledger_key_union rather than a second copy of the walk.
  • Commit 45f54d6c (fix(ledger):) makes build_record emit the key (record.setdefault("review_tier", None)), so declaring the key leaves RECORD_FIELDS a subset of every built row. The first commit alone reddened two tests/test_ledger.py cases that assert exactly that subset relation; the second restores them.

Gate

Three files, run at the committed head 45f54d6c: tests/test_ledger_declares_the_review_tier.py, tests/test_ledger.py, tests/test_record_fields_declare_every_key.py — 98 passed, 1 skipped, EXIT=0. The one skip is the mounted-row check itself, which skips when the config home mounts no ledger (as in the test environment); the new case supplies its own mounted row, so it exercises the same check's collection directly rather than resting on the skip.
