§5 — The per-run supervisor survives the process that launched it

Off the fleet, _start_supervisor (reckon/crew/dispatch.py) no longer makes the supervisor a child of the process that launched it. A single Popen did, so the launcher's own end — a coordinator turn finishing, a shell returning — reaped the supervisor and orphaned the run it carried. The spawn now runs through a short-lived intermediate: _spawn_detached_supervisor starts a fresh interpreter — subprocess.Popen([sys.executable, "-c", …], stdin=PIPE, stdout=PIPE, close_fds=True) — hands it the supervisor argv and stderr path as JSON on stdin, and reads back the one-line pid the intermediate prints before exiting at once. The intermediate starts the supervisor with start_new_session=True and close_fds=True, so the supervisor is reparented away from the launcher before it does any work and leads its own session and process group — the group crew stop signals, with the worker spawned inside it. The fresh interpreter is the point: a bare os.fork would run Python in a forked copy of a launcher that may be threaded, and the MCP server is one such launcher. _start_supervisor still returns the supervisor's own pid and still runs _confirm_supervisor_survived on it; the manual closerange and the os.execv S606 suppression are gone, because close_fds=True covers the descriptor leak. An intermediate that exits without a pid raises CrewError carrying its exit status and the tail of its stderr, so the cause of a silent launch is not lost. The fleet batch-step path is unchanged.

Two test instruments moved with the mechanism. The parking shim in tests/test_dispatch_returns_without_worker.py and the fork recorder in tests/test_dispatch_spawns_through_the_fleet.py both used to intercept the launcher's own subprocess.Popen; they now wrap reckon.crew.dispatch._spawn_detached_supervisor — the seam that starts the supervisor — so their holds and recordings survive a change to how the spawn is built. Both files are outside this node's write fence and were edited at coordinator direction.

Measure: tests/test_supervisor_outlives_its_launcher.py 5 passed exit 0, tests/test_dispatch_returns_without_worker.py 7 passed exit 0, and tests/test_dispatch_spawns_through_the_fleet.py 6 passed exit 0. The supervisor cases start a supervisor from a long-lived child launcher whose argv is a sleep stub and read the kernel's /proc/<pid>/stat: the supervisor's parent pid differs from the launcher's, its pgrp and session both equal its own pid, it survives a SIGKILL of the launcher's whole process tree, it inherits none of the launcher's descriptors (a live pipe in the launcher is absent from its /proc/<pid>/fd), and an intermediate that writes to stderr and exits without a pid has that text in the refusal. Negative control: restoring the single Popen with start_new_session=True fails the parent-pid assertion on exactly the launcher's pid (assert 1411282 != 1411282) and the tree-kill assertion, 2 failed / 3 passed, exit 1. A second control sets close_fds=False on both Popen calls and fails the descriptor case naming the inherited pipe, exit 1.

No figure is produced: this is a process-lifecycle property carried entirely by the tests above, and a drawing of forks and sessions would add no reading the assertions do not already make explicit.
