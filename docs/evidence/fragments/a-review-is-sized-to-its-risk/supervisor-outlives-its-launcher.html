§5 — The per-run supervisor survives the process that launched it

Off the fleet, _start_supervisor (reckon/crew/dispatch.py) no longer forks the supervisor with a single Popen. A Popen made the supervisor the launcher's child, so the launcher's own end — a coordinator turn finishing, a shell returning — reaped the supervisor and orphaned the run it was carrying. The forking path now double-forks: an intermediate process starts the supervisor in a session of its own (setsid) and exits at once, so the supervisor is reparented away from the launcher before it does any work. The intermediate reports the supervisor's pid back over a pipe, so _start_supervisor still returns the pid crew stop signals and still runs _confirm_supervisor_survived on it. The returned pid is the leader of its own session and process group, with the worker spawned inside that group. The fleet batch-step path is unchanged.

Measure: tests/test_supervisor_outlives_its_launcher.py starts a supervisor from a long-lived child launcher whose argv is a sleep stub and reads the kernel's /proc/<pid>/stat — 3 passed, exit 0. The checks are that the supervisor's parent pid differs from the launcher's, that its pgrp and session both equal its own pid, and that SIGTERM to the launcher's process group leaves it alive. Negative control: restoring the single Popen with start_new_session=True fails the parent-pid assertion on exactly the launcher's pid (assert 448375 != 448375), 1 failed / 2 passed, exit 1. Only the named test file was run; the coordinator runs the wider population at merge.
