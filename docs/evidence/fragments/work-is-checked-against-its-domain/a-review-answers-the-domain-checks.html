A review answers the domain checks its node touches

What changed. A repository's declared review_checks join the review checklist rather than a seventh scored dimension. The composed run-review brief in reckon/crew/recovery_review_subject.py now carries a Declared review checks this node touches block naming every check the reviewed node's write paths match, taken from the one matcher that answers which rules a node touches (rules_for in reckon/crew/domain_rules.py), with the verdict form stated beside the questions — a reviewer in another project's worktree holds no flight config of its own, so the questions and the grammar reach it only through the brief.

On the parser side, parse_review takes the declared check ids as its required set. Each answered check joins item_verdicts under its own id; a check that carried no answered verdict is named in absent_items and leaves the record incomplete; and a check answered fail is stored as a finding carrying blocking. Nothing else moved: REVIEW_DIMENSIONS, the acceptance floor in reckon/crew/recovery_review_acceptance.py and reckon/crew/review_lifecycle.py are untouched, so the existing severity derivation reports such a run open with no new lifecycle code. _VERDICT_RE accepts - and . in an item name, because a declared check is named by the project that declared it rather than by a constant in the parser; the captured item is still matched against a known set, so a line naming nothing declared parses exactly as it did before.

Where the required set is resolved

An independent review found that the required set as first written never reached production: parse_review takes review_checks, but its two callers — repair.py and reports.py — both call it with the defaults, so a reviewer that skipped a declared check still delivered a record the delivery contract filed as complete. The parser is handed a reviewer's emitted text and never the review it belongs to, so it cannot resolve the checklist itself.

The resolution therefore lives in the delivery contract, which does hold the record: review_record_refusals now calls unanswered_review_checks, which resolves the checks from the reviewed run's own live pointer — the node the pointer carries, its write paths, and the project's flight layer, matched through the same domain_review_checks the brief is composed from — and refuses the record naming each check it left unanswered. The answers are read from both spellings: the item_verdicts a parse handed the set writes, and the reviewer's own VERDICT lines in the emitted text it stored, which is where an answer survives when the parse was not handed the set. Every existing caller of the contract gains the guard without a change of its own, and a record whose reviewed run has no readable pointer — one already promoted and reclaimed — owes nothing and is left alone.

The guard does not switch itself off when its subject is promoted

A second review, of the repaired head, found the resolution above still had one way to fail quietly: it read the reviewed node from the run's live pointer alone and returned no checks when that pointer was unreadable. A run's pointer is reclaimed the moment it is promoted — which is when its review is filed — so the guard switched itself off at exactly the point it was needed, and a review of a promoted subject could skip every declared check and still file as complete.

The resolution now distinguishes three states rather than two. The node comes from the live pointer, or failing that from the committed per-run row beside the project's ledger, which carries the node definition the run was dispatched from, or failing that from the run's own delivered manifest, whose declared write paths are read before its changed ones. When none of the three can be read the contract refuses the record and says the checks cannot be established, instead of reading an unreadable subject as owing nothing. A project that declares no check under any node is not in that state: every node beneath it owes the same empty checklist, so it resolves to nothing owed without the node, and no record is refused merely because its subject cannot be read. Only a project that declares checks can be unable to say which of them the node touched, and only that case is refused.
