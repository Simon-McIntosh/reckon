A waived domain check and its reason ride the promoted ledger row

The promotion guard _require_domain_invariant_checks returns the waiver it applied — the ids of the declared invariants that failed and the reason the operator stated. That record was bound to _domain_checks in reckon/crew/promotion.py and used for nothing else, so it survived only until the live pointer was deleted: the waived check left no trace on the promoted ledger row, and a reviewer auditing a landed run could not see that a declared invariant failed or why. Every other waiver a promotion accepts already rides the row; this one was dropped.

The guard's product is now passed to _complete_locked and written as domain_waiver beside boundary_waiver. reckon/run_record.py seeds the key to null in build_record and reckon/ledger.py declares it in RECORD_FIELDS, so a waiver-carrying row and a row whose checks held are told apart by one field on every surface that reads a committed row. No new waiver option is added.

Measure: the fixture repository declares two invariants — one matching a node's models/** write path with a check that exits 3, one matching a second node's tools/** path with a check that exits 0. The first promotion is refused until a reason is stated, its check leaves a replay log whose terminal line is EXIT=3, and the landed row read back through crew(view="records") carries domain_waiver: {"waived_invariants": ["convergence"], "reason": "the record predates the convergence fix", "checks": [...]} — the guard's own returned mapping, compared against the value the guard was observed returning in the same run. The second promotion, whose declared check ran and held, carries domain_waiver: null. On the base revision the row carries no such key at all, so all three cases fail there.
