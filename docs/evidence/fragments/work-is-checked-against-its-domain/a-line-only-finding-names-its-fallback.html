A line-only finding names its fallback

What changed. repair._finding_location (reckon/crew/repair.py) guarded on the line alone, so a finding carrying a line and no file rendered as :12. That string is truthy, so the review-waits-for-its-repair refusal's fallback to the review's findings never applied and a refusal read :12 — dispose it with …, sending a coordinator to a file nobody named. The function now returns nothing when the finding names no file, so every caller's fallback applies. No caller was edited: the two call sites in repair.py and the refusal in recovery_review_dispatch.py already spell their own fallback, and the composer's join takes the empty result without change. A finding naming a file, with or without a line, renders exactly as before.

Measure. tests/test_a_line_only_finding_names_its_fallback.py holds four cases: the renderer's empty result for a line-only finding and its unchanged file:line and bare-file results; a parse of the emitted grammar FINDING :12 blocking: … proving the empty location is a fact about a shape the review grammar really produces rather than one the test constructed; and the refusal driven through the real dispatch against a real git history and a real stored review, asserting it names the review's findings, carries no :12, and still prints the finding's crew dispose command.
