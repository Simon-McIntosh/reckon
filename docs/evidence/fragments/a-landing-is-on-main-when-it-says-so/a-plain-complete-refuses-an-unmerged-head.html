A plain complete refuses an unmerged head

What changed

A plain crew complete --gate passed promoted a run as landed without asking whether the primary branch carried its reviewed head. After crew merge --run refused, the complete still promoted and removed the live pointer, so the ledger read work main did not hold and the landing verb could no longer find the run it had been asked to land.

reckon/crew/merge.py now answers the question with the ancestry the landing already uses. head_on_remote_branch reads ls-remote for the remote branch over the existing port-22 to 443 retry, fetches the remote head's commit over that same route when it is not held locally, and answers through _is_ancestor. Three causes are distinct answers and not one cannot read: an unreachable remote, a reachable remote carrying no such ref, and a checkout configured with no remote at all. The last promotes as before, because the question is not askable there.

reckon/crew_run_commands.py asks it in the plain-complete path before promoting, for a run that is not a review run, whose gate passed, and whose reviewed head resolves. A refusal names the run, the head and origin/main, and touches neither the pointer nor the ledger. The new family D25 carries the repair in reckon/crew/refusals.py. A --land complete, the crew merge --run verb, a gate that did not pass and a review run all keep their behaviour; the guard is deliberately not in the shared dry-run list both paths would run.
