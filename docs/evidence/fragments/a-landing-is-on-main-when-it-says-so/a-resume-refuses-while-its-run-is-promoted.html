A resume refuses while its run is promoted

What changed

A promotion holds a lock named for the run for the whole of the promotion and takes the run's pointer lock inside it. The live-worker check that runs before that lock can only refuse a promotion starting while a turn is alive; it says nothing about a resume that starts after it has passed. Such a resume took only the pointer lock, so it rewrote the pointer underneath a promotion that had already decided what to do with that run.

_pointer_lock in reckon/crew/runs.py takes an optional non-blocking mode, which raises PointerLockHeldError when the lock is held instead of queueing for it. reckon/crew/resumption.py composes it into hold_against_promotion, which takes the run's promotion lock without waiting and raises PromotionInProgressError when a promotion holds it. The hold is re-entrant within one context, and the lock name is imported from the module that owns it rather than spelled again, so a rename in promotion cannot leave this guard watching a lock nobody takes.

Three places take it. mark_resume_launching holds the run before it writes the launch mark. resume_plan in reckon/crew/dispatch_sessions.py holds the run around both its pointer write and that mark, because taking them separately let a promotion start in between and the guard fire after the write it exists to prevent. And _resume answers a refusal without touching the pointer: the mark is dropped only if the pointer is free, because the pointer is the promotion's to rewrite and remove, so a mark left on it is not the refusal's to undo.

The locks are taken in promotion's own order — promotion lock, then the run's pointer lock — so a promotion and a resume started together cannot hold what the other waits for.

Measure

Gate: tests/test_a_resume_waits_out_a_promotion.py over a temporary crew home and a run whose pointer and worktree are under it. At the head revision it reports 4 passed, EXIT=0. The cases are: a resume attempted while the promotion lock is held refuses naming the promotion, with the pointer byte-for-byte unchanged and the launch seam never called; a real promotion holding its lock and the run's pointer lock together, with the refusal required inside two seconds, which fails if the refusal queues behind the pointer lock; a resume with no promotion in progress proceeding and leaving no in-flight marker; and a promotion-shaped critical section and a resume started together finishing inside a five-second bound in all 25 rounds, in whichever order they arrive.

Negative control: at the base revision f6a07c1c23, over a tree extracted from that revision with the node's test copied in, 2 of the 4 cases fail and 2 pass so a guard that refuses everything could not pass either. The refusal case fails with DID NOT RAISE CrewError — the resume proceeds while the promotion lock is held — and the both-locks case fails with the refusal queued behind the promotion's pointer lock, which is the defect this repair round named.

A second control applies one mutation to the repaired head: the refusal's mark is cleared through the blocking pointer lock again, and the both-locks case fails with the refusal queued behind the promotion's pointer lock, EXIT=1.

Importer arm: the six existing test files that name _pointer_lock, mark_resume_launching or a promotion lock report 11 failed, 205 passed at the head and the same 11 failed, 205 passed at the base revision, with identical failing ids, so this change adds no failure. Ruff check and format are clean on the four staged paths.
