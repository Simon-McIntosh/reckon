The reflex acceptance reads the remote primary branch

What changed

The accepting branch of the reflex promoted a reviewed run once its recorded gate still passed at the merged head, but it answered "is the run merged?" with git merge-base --is-ancestor ... HEAD against the checkout's own tree. A checkout whose main was fast-forwarded while the push failed satisfies that test while the remote has never seen the work, so acceptance could promote a run no other reader can find.

reckon/crew/recovery_review_acceptance.py now asks merge.head_on_remote_branch — the function the plain-complete path already uses, which reads ls-remote over the port-22 to 443 retry, fetches a remote head it does not hold, and answers through the same _is_ancestor the landing lands by. No local-HEAD probe remains: a checkout configuring no remote declines, as the next paragraph records.

An unreachable remote and a reachable remote carrying no primary ref are distinct answers and each declines the promotion, recording remote_cause and a reason naming the remote, the branch and the commits. So does a checkout that configures no remote at all: there is no remote branch to show the work on, and judging the checkout's own HEAD is exactly the local-only promotion this section closes. A detached HEAD and a commit the checkout cannot resolve are told apart from those three, because each has a different repair — check the primary branch out, fetch the commit, configure the remote, retry the network — and reporting any of them as an unreachable remote sends the coordinator to the wrong fix.

Measure

Gate: tests/test_reflex_acceptance_reads_the_remote_primary.py over a temporary repository and a bare origin. At the head it reports 12 passed, EXIT=0. Each declined arm carries a control, because a guard that never fires passes the same assertions as one that refuses everything: a run whose commits are only on local main is not promoted, while the same run with the deliverable pushed promotes; an unreachable remote declines with remote_cause: unreachable and a control that answers the remote read as promotable promotes it; a remote with refs/heads/main deleted declines with remote_cause: missing-branch; a checkout configuring no remote declines with remote_cause: no-remote and a control that answers the question as promotable promotes it; and a detached checkout declines with remote_cause: detached-head, with a control that supplies the branch the refusal named promoting the same run. A commit the checkout cannot resolve is asked of the guard directly, since the review store refuses to record a reviewed head it cannot resolve, and its reason names the commit rather than the network.

Negative control: the declared mutation reverts the question to the local checkout. Over a tree extracted from base revision bf85149157 with this node's test copied in, the local-main case fails because the run is promoted, and report["accepted"] reads ['r-20261109T120000000000-reflex-acceptance'] against the expected empty list — the defect §7 records, reproduced. With it the unreachable-remote and missing-branch arms fail too, since neither cause is represented in the base code. That run reports 3 failed, 5 passed, EXIT=1.

The importer file tests/test_review_acceptance_promotes.py built its repository with no remote, so the no-remote decline returned four of its cases before reaching the behaviour each measures. Its fixture now builds the checkout through tests/helpers/landing_repository._write_origin_and_checkout, the helper every landing test already shares, and pushes each landed commit, so the shared setup is used rather than re-derived and the remote-less state no longer exists in the suite. With it the two files report 18 passed, EXIT=0; the same command over the repair's base 1219837c0f reports 4 failed, 14 passed, EXIT=1, every refusal naming remote_cause: no-remote.
