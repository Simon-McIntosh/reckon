gc releases a worktree whose commits landed elsewhere by patch equivalence

Change (commit d4951807). garbage_collect judged a worktree only by ancestry: a head that was not an ancestor of the integration head read as unintegrated and was kept whatever its commits contained. Each commit beyond the merge base is now compared against the integration head with git cherry -v (reckon/crew/routing.py, _commits_beyond_merge_base, called from _inspect_workspace and from _save_and_release_worktree). A dirty worktree every one of whose commits has a patch-equivalent there is classified dirty-integrated and releases through the same residue-preserving path as an ancestor-integrated tree, with its patch and untracked tar saved first. A tree carrying any commit with no equivalent is kept, and its row names that commit under non_equivalent_commits with its sha and subject; a tree whose release is justified this way names the equivalents under patch_equivalent_commits. The residue classification now measures a head that landed elsewhere against the merge base rather than against its own head, so superseded asks whether the integration head moved the path since the histories parted. A worktree claimed by a live run is still never touched: the claim is resolved before the classification and re-checked in the apply loop.
