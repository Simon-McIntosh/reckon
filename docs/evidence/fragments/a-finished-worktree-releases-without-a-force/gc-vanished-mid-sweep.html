A worktree that vanishes mid-sweep no longer stops gc

Change (commits 088ab8a4a and fe33d6d04). garbage_collect (reckon/crew/routing.py) reclassifies a row whose action fails because the directory is gone, instead of stopping the sweep. When an action raises and path.is_dir() is false, the row is re-read through _inspect_workspace(..., raise_on_unavailable=False), marked gone_before_action: true, given a detail naming the vanish, and the pass continues to the remaining worktrees; the row is never appended to removed_worktrees. An action that fails while the directory is still present still refuses the row and propagates, exactly as before — that distinction is the whole change, and the existing stop-mid-pass contract tests still pass unchanged.

Why the earlier vanished-worktree test did not cover this. tests/test_gc_applies_past_a_vanished_worktree.py removes the directory before invoking gc, so classification itself reads it missing: _tree_state's leading path.is_dir() guard returns the unavailable row at classification and nothing ever acts on the tree. It exercises no directory that disappears between classification and an action, and its surviving tree is merged and clean, so the pass's action for it is a plain removal — the --pin-unique-commits path, where the 2026-10-03 failure landed, is not exercised at all. The mechanism is that the pin step's first act is git rev-parse HEAD run with the worktree as its working directory, and a missing working directory makes Popen raise FileNotFoundError before git starts: subprocess.run([...], cwd='/nonexistent/dir/xyz', check=False) still raises from _execute_child, because check=False covers a non-zero exit and not cwd resolution. The failure therefore arrives as an OSError rather than as a git error, and the action loop's single except Exception treated it as a defect of the sweep and propagated.
