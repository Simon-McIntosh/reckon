The follower's lifetime bounds a poll, a reload and its children

The defect

Four findings, all in the arming path the host ends at thirty minutes.

The lifetime bounded the gap between polls, not a poll. Two crew follow --lifetime 29m processes ran 3 h 36 m and 2 h 07 m under degraded storage, both inside the full-tree git status walk the recovery sweep runs over every registered worktree. The deadline was read between polls, so the only thing that could end the arming was the poll returning — which is exactly what a walk over hundreds of worktrees does not do.

A reload re-anchored the deadline at the replacement image's start. The carried instant is absolute, but the watch loop re-anchored it at its own started_at, so each reload charged the grant for that image's setup: a six-second grant ended 7.49 s after the arm, 8.61 s when the first sweep spawned a probe, and 8.61 s is past the eight-second bound §8's own case asserts.

Two hand-off variables lived in os.environ. The reader checkpoint (RECKON_FOLLOWER_CHECKPOINT) was placed in the follower's own environment at the reload, and the arming variable (RECKON_WATCH_ARMING) was inherited from the session that armed it. Every child of the follower inherits that environment — the recovery sweep's condition probes among them — and those children then carried a variable that governs an arming none of them owns. The lifetime deadline had the same defect before it was carried to the replacement alone.

The dispatch preflight reported follower conditions one at a time. A coordinator met them in sequence: no producer, then a follower whose lines end in a file, then session_attached: False with another session named as the delivering one. Each refusal named one condition, so each fix revealed the next; measured at about twenty-five minutes for one worker.

What changed

  1. reckon.cli._follow_watch_lines._sweep_on_cadence runs the sweep on its own thread and waits for it only as long as the arming has left. A poll still walking at the deadline is abandoned and the arming ends; a sweep begun after the deadline is not started at all. Without a deadline the sweep runs synchronously, exactly as before, so an arming without a lifetime is unchanged.
  2. reckon.cli.crew_follow converts the deadline — the absolute UTC epoch, fixed at the first arming and carried to replacements — into the watch loop's own clock once, at arming, and passes it in beside the grant. _follow_watch_lines uses an absolute lifetime_deadline when one is handed in and falls back to granting lifetime from its own start only when one is not.
  3. _FollowerReloader.poll writes the reader checkpoint into the mapping the re-exec passes and never into os.environ; the replacement reads and removes it in one step, as it already did for the deadline. crew_follow drops RECKON_WATCH_ARMING from its own environment as it arms, so no child inherits either variable.
  4. reckon.crew.dispatch._watcher_delivery_admission judges the producer and the session's delivery in one pass, and _unmet_follower_conditions names every unmet condition: no live producer, a follower that is registered but not delivering (with the reason follower_state gives), no registration at all, and — whenever this session's delivery is not in place — the sessions that do deliver right now. _FollowerAdmissionUnmet raises one WatcherRequired carrying the whole list and the one follower command that clears it, so the error key, exit code and watch payload a caller already reads are unchanged. A released registration is still admitted with the re-arm warning.

Evidence

tests/test_follower_bounds_its_lifetime.py holds one case per finding. Its clock and its poll are injected, so the first case is exact rather than timed from the outside: the poll blocks far past a deadline 0.5 s away, and the case requires the follower to end within one second of it with the poll still blocked — a follower that waited for the poll would end when the poll released it.

The declared negative control is executed and logged: with the deadline check removed from the blocking poll in reckon/cli.py, the bound case fails at tests/test_follower_bounds_its_lifetime.py — 1 failed in 3.31 s, EXIT=1 — and cli.py was restored byte-for-byte afterwards. The log's first line is the declared string.

The gate — the new module plus tests/test_follow_lifetime.py, tests/test_follow_lifetime_survives_reload.py, tests/test_follower_reload_is_safe.py, tests/test_follow_rearm_continues.py and tests/test_crew_watch_lifetime.py, in one invocation — run at both revisions, each pytest process with a basetemp private to it:

  • Head, revision 9ac0530d: 42 passed in 117.17 s, EXIT=0 — no failure id.
  • Base, revision 33c5e761, source extracted with git archive into a scratch tree (no worktree, no branch): 3 failed, 39 passed in 155.90 s, EXIT=1. The three ids are exactly the new module's discriminating cases: test_a_poll_that_outlives_the_deadline_is_abandoned, test_no_child_of_an_armed_follower_carries_the_hand_off_variables and test_a_refusal_names_every_unmet_follower_condition_and_the_one_command. Added failures at head: 0.
  • The reload case, test_a_reload_does_not_restart_the_lifetime, is a regression guard rather than a discriminator in this base arm: it passed at base, because the base re-anchoring costs only the replacement image's pre-loop setup, and that setup measured under the case's one-second slack in this run. The same figure measured 1.49 s over the grant (7.49 s against a six-second grant) on 2026-09-23, and 2.61 s in the case that spawned a probe — so its base failure is load-dependent, and the case is recorded here as a bound on the head behaviour rather than as a demonstrated base failure.
  • The instrument for the child-environment case is proved to see a known-present variable before any absence is read: the probe records the environment it was handed, and every recorded line carries RECKON_HOME (which the test set) while carrying neither RECKON_FOLLOWER_CHECKPOINT nor RECKON_WATCH_ARMING. The base arm failed on RECKON_WATCH_ARMING appearing in a child's environment, which is the leak the finding named.
  • No new lint findings: ruff check over the changed Python paths is identical to the base revision's output (same 11 findings, same rules and files), ruff format --check breaks on the same six pre-existing regions of reckon/crew/dispatch.py, and the new test file is clean under both.
