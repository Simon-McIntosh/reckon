A re-arm case cannot end the runner that hosts it

A follower replaces its own process image when the content stamp over its source moves while it is attached. The three re-arm cases here run the real follower command, so a stamp moved mid-case — a peer's commit landing in the checkout, or the reload cases that append probe bytes to the follower's source — re-executed the xdist worker hosting the case, and the arming's own lifetime then ended that replacement. Measured at the base revision under an oscillating edit of the follower's source beside CPU load: nine workers crashed, and nine follower reload launchers were observed in /proc, one per crash.

Each case now runs its follower invocation in a child process the test owns, with the case's capture and patches applied inside the child, and an autouse fixture holds the code stamp still for the duration of the case. No case can reach os.execve, os._exit or a signal path that runs in the runner.

The 26 iterations that were not green

Every iteration that failed carries the follower's stale-producer line (producer … runs older code than this follower), and the three cases that assert a pane's exact rows fail on the extra line. The line is the follower's correct answer to the loop's own edit: the producer registered its stamp while the source was clean, the arming read the edited stamp, and the line persists for that arming. Neither revision draws it without the source edit, and at base the same trigger ended the process before a line could be drawn: nine of the ten base failures are worker-crash attributions, and the tenth is an in-process stamp assertion raced by the loop's own edit.

The loop edits the source every 100 ms, which no commit and no probe append does, so it is a harsher trigger than the tree sees in a real run. Crashed workers are the measure the loop exists to take, and that count is zero across 30 iterations at head against nine in the base arm's single iteration.

The case children are python -c processes whose launcher names the tree under test, so a child that re-executes still shows as one /proc hit per iteration; none was seen in 30. Producer reloads under measure still exec, inside the children those cases own.

The stacked measure, and the importer it caught

A later measure stacked the main revision 11e86b0ff against its merge with this head, over 130 follower files at -n 8. No worker crashed in either arm, so the defect this change removes stayed removed with the change merged. The same measure found one failure the change had added, and it was deterministic: a case importing the arming helper and calling it with no rows list, which the helper had begun to require, failed three times of three at the head and passed three times of three at the base revision.

The list is optional again: a case that passes one still has the child's rows appended to it, and a case that passes none has them replayed through the cli._echo_follow_line it installed, which is the capture shape the importing modules were written against. Both importer files run green with the three re-arm files — 49 tests in 94 s without xdist workers, and 49 in 18 s at -n 8 — and the two importer files alone passed four tests in each of three consecutive -n 8 runs. The same five files were then put through the loaded loop at the delivered revision: three iterations, no crashed worker and no reload launcher naming the tree, with the four failures that did appear being the exact-pane cases drawing the stale-producer line above.
