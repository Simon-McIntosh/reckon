One limit reset draws one row per pane

What changed. A pane is served by more than one follower: a session host runs one per project the session follows, a second follower streams the same session read-only beside the one holding the registration, and every one of them reads the station's rows. A limit reset is a row about the account rather than about a run, so each follower drew it, and a session read one announced reset as several rows.

The shared claim that exists to stop exactly this — one exclusive-create file per pane, lift id and transition, so whichever follower reaches the row first draws it — was wired into the producer-stream row path and not into the station subscriber's path, which is the delivery path a follower takes whenever the node runs a station. The claim was therefore absent precisely where several followers meet.

The claim belongs to the pane rather than to whichever delivery path a follower read through, so ticker.PaneRowPath now resolves the pane's shared claim from its own session when it is handed none. A path that names no session — the fleet-wide reader, and ticker.replay_row_policy measuring a recorded stream — is still handed none and draws on its own memory alone; the replay now passes a claim that always permits, so today's claim directory can never subtract a row from a recorded stream. A claim that cannot be written still leaves the row drawn rather than dropped: take_lift_claim answers that, unchanged.
