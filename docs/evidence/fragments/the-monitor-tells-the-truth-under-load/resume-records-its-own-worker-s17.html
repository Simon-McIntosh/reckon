A run records the supervisor it started, never the process that launched it

What changed. An attempt reservation taken by a launch made inside a long-lived door recorded the door's own process under the reservation's pid — the field every reader probes to decide whether an attempt is still in flight, and the pid crew stop and crew discard act on. A recovery-sweep resume started inside the station therefore left a hold naming the station. The station outlives every run it launches, so the hold never cleared: age frees only a reservation that reached no supervisor, and the reported record named one. Signalling that pid ends the process that holds every session's claims.

reserve_launch_attempt now records the door under launcher_pid and launcher_pid_start_time, and leaves pid for the supervisor the launch starts; record_reservation_supervisor writes that supervisor into pid as well as into supervisor_pid. The three fences that recognise "the reservation this process took" — adoption, withdrawal and the supersede fence — read the door from the new fields, falling back to pid for a reservation written before the split. A pid naming the reading host's station is read as naming no process of the run: as a supervisor it holds nothing, and as a door it is judged by the launch's own age like any other launch that reached no worker. runs.read_pointer applies the same rule to the pointer, which is the record crew stop, crew discard and every liveness reading take their pid from, so a pointer naming the station reads as naming none.

The station pid is read from the lease the station keeps, through the lease mechanism that writes it — station.station_lease for the name of the one writer on a node, HostLease.holder for the record — rather than through a second reader of that format. host_lease.process_runs_here then decides whether the pid the record names is still the process that wrote it, from the start tick and the process table recorded beside the pid, so a number the kernel has since recycled is not mistaken for the station and a pid from another process table is not matched by number alone.
