A stopped claim's git answer is reused until its worktree moves

Judging a stopped claim asks git two questions in its worktree: which commits neither the integration ref nor the recorded base can reach, and which declared paths hold uncommitted changes. A roadmap read judges every live pointer more than once, and a stopped run's worktree almost never moves, so the second read repeated the first's subprocesses. The commit answer now reads the worktree head and the integration ref's current commit from git's files and is served from the crew home's git-answer store against those three object ids, so a fresh process answers it without spawning git. The uncommitted-change answer reads the working tree, so it is reused only within a process and only while the index and every declared path hold the stat identity they held across the call; a pointer declaring any directory always asks git, because editing a tracked file beneath a directory moves neither the directory's stat nor the index's while git reports the edit. An unanswerable command is never reused.

On the fleet node, one fresh process per arm against the real home, warm with one reckon.mcp._roadmap(project="reckon") call and then profiling a second: at base (479cd489af) the second call took 140.67 s with 40 git subprocesses and _live_scope_claims accumulated 1.736 s; at head (3b1344fb865) the second call took 121.34 s with 40 git subprocesses and _live_scope_claims accumulated 1.416 s. One stopped pointer's worktree moved between the head's two calls (68 live pointers at base, 67 at head). In both arms the remaining git subprocesses came from git log and git rev-parse, not from the claim path: the profiled call spent no git status and no git rev-list at either revision, so this fleet reading cannot separate the two arms on that count and the separation is shown by the test's own wrapper instead: two dispositions of one unmoved stopped pointer ask git once at head, and with both memos and the store write disabled the same two dispositions ask twice, which is the failing case the negative control records (three test ids red, the first of them the first case).

  • reckon/crew/node.py — unintegrated_claim_work reads its two answers through _claim_commit_answer and _claim_status_answer; the second is keyed on the index and the declared paths' stat identity, and the first on the head identity, the integration ref's commit and the base.
  • reckon/crew/recovery_watch.py — the crew home's git-answer store gains one reachability bucket beside its commit and count buckets, with the same bound and the same corrupt-store fallback.
  • tests/test_a_stopped_claims_git_answer_is_reused_until_its_worktree_moves.py — the nine cases above, including the negative control.
