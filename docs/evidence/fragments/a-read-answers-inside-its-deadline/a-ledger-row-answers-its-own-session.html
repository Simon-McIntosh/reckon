A ledger row answers its own session

_compact_row discarded the committed row it held and asked resolve_session for the run by id, so the ledger source loaded the whole ledger to find the same row again — one load per promoted row, quadratic in the ledger's size. resolve_session now takes the row the caller already holds as ledger_row and the ledger source reads the session from it. Source order and answer shape are unchanged (pointer, then stream, then ledger, with source naming the one that answered), and a caller that holds no row still loads, so every other ledger caller is untouched.

Measured on a synthetic ledger of 52 promoted rows, 51 of them carrying a session_id, counted with a wrapper over ledger.load: one runs_view with the ledger as its source made 53 loads at base and 1 here. Every row kept its base answer — session_id and session_id_source equal what the resolver returns for the same run with no row supplied — and the row recording no session still reports the absence naming all three sources. The negative control passes record=None again for ledger rows and the count returns to 53, over a run whose log ends in a non-zero EXIT= with that test failing.

The gate arm adds one failure at head that is not this node's to repair: tests/test_crew_runs_by_run_id.py::test_one_run_read_opens_a_fixed_small_number_of_files asserts a positive control that the full non-indexed walk opens more than 100 files, and the per-row reopen it counted is exactly what this change removes. The control held at base — the assertion it now fails is that the count exceeds 100 — and reads 1 here, because the read makes one load instead of one per row. Re-founding that control is outside this node's write scope and is recorded as a follow-on.
