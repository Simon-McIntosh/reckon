A persisted review index never claims more than it read

What changed. The persisted review-store index in reckon/crew/review_records.py carries the store directory's stat identity beside the entries it was built from, and a later process adopts it without listing the store only when the identity it reads matches the one recorded. The document was written with an identity read after the listing its entries came from, so a record another process filed between the two — the window the document's own write opens — was missing from the entries while the recorded identity covered it. Every cold process on the node then adopted that index until the directory moved again, and a promotion reading it could miss the review.

Both paths that persist the index now record the identity read before their listing, and nothing later. _store_indexes passes the identity it already takes at its entry, which precedes both the build and the update; _refresh_store_entries takes one before _update_store_entries instead of persisting the identity its cache held, and stores that one in the cache beside the refreshed entries. _persisted_index_document and _persist_store_entries take the identity rather than stat'ing the directory themselves, so there is no site left where a document can record a directory newer than its entries. The adoption rule is unchanged: a record filed during the write leaves the store looking moved from what the document recorded, and the next reader lists it instead of adopting an index short of the record.

What the test drives

tests/test_a_persisted_review_index_never_claims_more_than_it_read.py wraps _persist_store_entries so that a new record is filed in the same store directory at the instant before the index document is written — exactly between the read and the write — and then starts a cold reader. Both persist paths are driven that way: the load-or-update path (test_a_record_filed_before_the_index_write_is_not_claimed) and the refresh a lookup no held entry explains takes (test_a_record_filed_before_the_refresh_write_is_not_claimed). In each the cold reader must find the record, and the load-or-update case also asserts the recorded identity differs from the directory's current one, which is the invariant stated directly rather than only its effect.

The third case, test_a_cold_reader_of_an_undisturbed_store_stats_nothing_per_record, counts stats in a cold read of an undisturbed 40-record store: 1 directory stat, 0 record stats — no more than the base revision pays, which is the same two figures.
