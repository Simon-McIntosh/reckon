The store index re-reads only what changed

What changed. The store index in reckon/crew/review_records.py — the thing that answers a misfiled lookup for a run whose record sits at another record's path, and a delivered review's lookup by the review run that produced it — no longer rebuilds itself from scratch when its directory's stat identity moves. One directory listing now names the files, and a file is parsed only when its name is new to the index or when its stat identity (inode, size, modification time) differs from the entry the index holds for it; every other file keeps the facts already read for it, and an entry whose file the listing no longer names is dropped, so a deleted record stops answering. Each entry now carries that identity beside the path, modification time and selection facts (reviewed_run_id, review_run_id, head) it already carried.

The updated index is persisted per store directory, not per project, in a node-local cache directory every process on the node shares: node_local_cache_dir(project) resolves $XDG_RUNTIME_DIR/reckon/<project>/, or /tmp/<uid>-reckon/<project>/ when no runtime directory is set — the helper this section adds, which a project's other node-local caches store through. Within it, each store's index is one file keyed by a digest of the store directory's resolved absolute path, so a worktree's or a scratch tree's store is indexed apart from the main store even when both carry the same project name. The document is stamped with a code stamp — the content identity of the two modules the index's facts and selection rules are defined in — and a document written under another stamp, or naming another store, is ignored and rebuilt rather than trusted. The process-wide code stamp was not used here: measured on this node it costs about 11 s on a cold process, which is the cost this section exists to remove; the content stamp costs about 10 ms and moves for an uncommitted edit as readily as for a commit.

The record a lookup selects is still read again from disk, exactly as before, so a rewrite in place is answered current.

What the parse counter reads

A 300-record temporary store, every environment-resolved directory — RECKON_HOME and XDG_RUNTIME_DIR alike — pointed at temporary paths. The counter wraps the index's own parse (_index_entry), so the lookup's re-read of the record it selected sits outside it.

caseparses
first build300
one record added, looking up again1
one record rewritten in place with a new modification time1
one record deleted0, and its entry is gone
a fresh process, nothing changed (module cache cleared)0, answered from the persisted index
a persisted index written under another code stamp300 — ignored and rebuilt
a record added since the index was persisted1

Each lookup above is made twice — once answered from the updated index and once after both the in-memory index and the persisted document are discarded, which rebuilds from the store — and the two results are asserted equal in full, the record's body included, not only the path they share. The cases carrying that comparison are the addition (test_adding_a_record_parses_only_the_new_file), the rewrite in place (test_rewriting_a_record_parses_only_that_file), the deletion (test_deleting_a_record_drops_its_entry), the two stores under different roots (test_two_stores_under_different_bases_are_indexed_apart), the fresh process (test_a_fresh_process_parses_nothing_when_nothing_changed), the rebuild under another stamp (test_a_persisted_index_under_another_code_stamp_is_rebuilt) and the write between processes (test_a_record_changed_between_processes_is_still_found). A right path answered from a body the index failed to refresh therefore fails its case, which the second control below measures.

The negative control

The declared mutation restores the replaced behaviour exactly — an identity change answered by a from-scratch build (entries = None in _store_indexes). The add case then reads assert 301 == 1: one new file costs a pass over all 300. Five other cases of the same file fail with it (the in-place rewrite, the deletion, the fresh process, the foreign code stamp and the write between processes), and the pre-existing seven files stay green — the mutation moves only what this node added.

A second control, for the full-result assertion above, makes the index keep the record it parsed and answer a lookup from that copy while the incremental update carries the old body forward for a file whose stat identity moved: the path and the parse count are right and only the body is stale. One case fails on it — the rewrite in place, reading total: 80 where the rebuild reads total: 81 — and the other seven pass. Its log is gate-negative-control-stale-body.log beside the first, and its mutation is mutate_stale_body.py in the run directory.
