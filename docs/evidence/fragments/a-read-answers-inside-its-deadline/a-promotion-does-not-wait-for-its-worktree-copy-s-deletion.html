A promotion hands its worktree copy's deletion to the trash sweep

A release still vacates a tree's registered path in one rename and deregisters it, but a promotion no longer deletes the moved-aside copy inside its own run lock: reckon/crew/routing.py gains deferring_worktree_copy_deletion, a context that _release_worktree_whole reads before its deletion step, and reckon/crew/promotion.py enters it around both calls to _release_after_promotion. Every other caller — discard, crew gc and the release tests — keeps the inline deletion unchanged, so no second policy was written. The copy is left in the worktree trash root, which the gc pass sweeps and prints (removed worktree trash <path>) with no age wait, so a copy older than an hour does not survive a pass.

Measure. Both tests drive real crew complete --gate not-run promotions over a temporary crew home and checkout, with the copy deletion replaced by an injected 30 s sleep. At head the slowed promotion returns within 5 s of the same promotion undelayed, and a second promotion of the same run reaches its lock inside the same 5 s budget; the file runs both in 12.0 s. At the base revision the same file fails both: the delayed promotion takes at least 30 s longer, and the second promotion waits 31.1 s for the first's deletion (the assertion's own figure). After the head promotion, a garbage_collect(apply=True) pass removes the backdated moved-aside copy and prints its path.

Negative control. The base revision, run from an extraction of d2e5fb667e: 2 failed, with the lock case reading AssertionError: the second promotion waited 31.1s for the first's deletion. Logs: negative-control-base.log, gate-head.log, baseline-suite.log, after-suite.log under the run directory.
