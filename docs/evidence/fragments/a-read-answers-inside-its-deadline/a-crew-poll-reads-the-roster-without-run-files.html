A crew poll reads the roster without a stat of every run file

The crew row a poll builds reads one thing out of a project's ledger — its members — and members live in the aggregate, never in a per-run file. The read went through the union ledger.load(..., headers_only=True), which validates its index against every file under docs/state/<project>/runs/ before answering a question those files cannot answer. _crew_rows in reckon/serve.py now reads each referenced project's roster through _project_roster, which keys the members it last answered with on the identity of the aggregate alone — st_mtime_ns, st_ctime_ns, st_size, st_ino, the same signature the ledger keys its own run index on. While that identity is unmoved the poll returns the held members after one stat and reads neither a run file nor a byte of the aggregate. A member added to or removed from the aggregate moves its identity, and the next poll re-reads it. An aggregate whose identity cannot be taken — absent, unreadable, or a project name the ledger refuses — is never cached, so the previous fallback still runs on every call and no later write is served stale; an identity taken after the read that differs from the one taken before it is not cached either, so an aggregate that moved mid-read is re-read rather than pinned.

The gate is tests/test_a_crew_poll_reads_the_roster_without_run_files.py. It builds a temporary project with 200 valid run documents under runs/, one roster member in its aggregate and one live pointer naming the project, then wraps Path.stat and Path.read_text and counts the stats whose path lies under the project's runs/ and the bytes read back from the aggregate. The warming call is the instrument's positive control: it must show the cost an absence is being claimed for, and reports stats >= 200 and aggregate_bytes > 0. The second call over the unchanged aggregate reports 0 stats and 0 aggregate bytes, where the base revision reports 200 stats — one per run file. Rewriting the aggregate's member then makes the next call return the change.

At the base revision the same test fails on the stat assertion alone: assert 200 == 0, EXIT=1 (logs/base-arm.log). At the delivered revision the gate passes, EXIT=0 (logs/head-arm.log). The declared mutation routes the roster read back through ledger.load(..., headers_only=True) on every call; the second-call count returns to 200, the test fails (assert 200 == 0, EXIT=1) and the log is logs/negative-control.log. ruff check and ruff format --check report 17 findings on reckon/serve.py at both the base and the delivered revision — the delta is zero — and none at all on the new test file. Every log ends in an EXIT= line.
