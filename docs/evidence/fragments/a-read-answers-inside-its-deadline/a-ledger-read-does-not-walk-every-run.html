A warm ledger read makes a constant number of stat calls

Reproduced at the base revision. A counting wrapper over Path.stat around a warm ledger.load, over a temporary project ledger whose documents were written through ledger.write_run_file, measured 21 stat calls at 20 run documents and 201 at 200 at acfbdab8c1bb3d0ac8027ed85658a8344f82621a — one remote stat per document, under _run_snapshot, and the +1 that is the aggregate. That is the promotion path the plan records waiting in D state on GPFS.

Change. The index's cache key is no longer the per-document walk. A project's write generation — the store's own file under the crew home, already consumed by the roadmap snapshot and the coordinator obligations — stands in for it. Keying it by the project alone matters: the index directory falls back to the user cache when the configured one cannot be written, so a token kept beside the index would give a writer and a reader in different directories two different files, and the reader would serve stale rows. Every ledger write path advances it once its own files are in place: write_run_file, append_run, _write_state (hence write, the hold and repair paths), _commit_run_split and _restore_run_files. A read whose generation and run-directory identity both still match what its index recorded reuses the stamps the index holds and walks nothing. A read whose generation differs, or whose index recorded none, walks the documents exactly as it did before, so a ledger this code has never written reads correctly and an index published before the key existed refreshes on its next read. The run directory's own identity is compared beside the generation, so a document added or removed by a writer that predates the generation is still noticed.

Measured. The same probe at the head commit 3eca4c75: 2 stat calls at 20 documents and 2 at 200 — the aggregate and the run directory, both constant. The reuse needs the counter to be writable, and a fenced worker's crew home is mounted read-only, so the probe points RECKON_HOME at scratch. Where the counter cannot be written it does not exist either, so a read walks there: the old cost, never a stale answer. tests/test_a_ledger_read_does_not_walk_every_run.py asserts that equality and, as a positive control, that each warm read still returns every row (20 and 200). It drives each write path — write_run_file, append_run, write, _restore_run_files — and asserts the generation moves and the next read returns the written row. It deletes the generation file, edits a document outside every write path, and asserts the read returns the edit, which is the rebuild condition observed rather than assumed. The declared negative control, restoring the per-document walk, was executed and logged: the warm-count case reds (3 failed, EXIT=1) because the 200-document count climbs back above the 20-document one.

Writers outside the ledger. A warm read answers from the index only when the generation matches, so a row moved by anything other than a ledger write path would be served stale. The production surface was searched and none exists: every writer of docs/state/<project>/runs/*.json reaches the file through ledger.write_run_file or ledger.write — the crew run commands, routing, the promotion record, gate and release paths, and the duration-backfill and figure scripts. The one direct write into a runs directory outside the ledger writes a synthetic row under tempfile.mkdtemp() inside a census control script, never a real ledger. The search, with its commands and output, is in writer-search.log.

Two existing tests had made their point by rewriting a run document in place, outside every write path. Both now amend their row with write_run_file and keep their assertions that the next read answers from the new record: a released worktree, and a retention recorded after the index was published, are each seen by the next bounded read. The pair passes (10 passed).

The key is one file. test_a_write_is_seen_through_another_index_directory publishes an index under two directory configurations, asserts both resolve the same generation path, writes through one and reads through the other, and requires the new row. test_a_run_split_is_seen_by_the_next_read drives _split_project_runs over a seeded aggregate and reads the rows back through load. The rollback case reads the generation immediately before the restore, so a bump from the write that preceded it cannot satisfy the assertion.

A bump that did not happen is not a write. The store's advance suppresses a failure so a plan write is never failed by its cache key, which for the ledger would leave the counter exactly where the index recorded it and an in-place edit invisible. The ledger's bump therefore reads the counter before and after the advance and removes it when it did not move — an absent counter sends the next read back to the documents. The removal is attempted, never required: requiring it failed every ledger write in this worker, whose crew home is read-only, and where the counter cannot be written it does not exist either. Two tests hold that down: a no-op advance with an mtime-preserving edit, and a generation directory held read-only, where the write lands and the read still sees it. Both mutations that remove the mechanisms red their tests (mutation.log), and the split case asserts the generation advanced, so removing that path's bump reddens it too.

An absent counter is not a key. A project no ledger write has touched has no generation, and the store reads that absence as "none". Comparing that value let an index look fresh forever, so a ledger whose documents were all written outside the write paths — a fixture, a project this code has not written since the key existed — served its first snapshot and never noticed an edit. Eight index and dispatch-speed tests failed on exactly that shape when the key first moved to the store's file. An absent counter now reads as no key: the read walks the documents, which is what it did before the key existed, and test_a_ledger_no_write_has_touched_never_reuses_a_stale_index drives it with an in-place edit that preserves the document's mtime. So correctness for a ledger this code has not written is the old behaviour, and only a project a ledger write has bumped gets the constant-cost read.
