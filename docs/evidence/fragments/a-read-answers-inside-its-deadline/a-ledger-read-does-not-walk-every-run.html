A warm ledger read makes a constant number of stat calls

Reproduced at the base revision. A counting wrapper over Path.stat around a warm ledger.load, over a temporary project ledger whose documents were written through ledger.write_run_file, measured 21 stat calls at 20 run documents and 201 at 200 at acfbdab8c1bb3d0ac8027ed85658a8344f82621a — one remote stat per document, under _run_snapshot, and the +1 that is the aggregate. That is the promotion path the plan records waiting in D state on GPFS.

Change. The index's cache key is no longer the per-document walk. A project's write generation now stands in a file beside the index it invalidates, keyed by the same ledger path hash and written atomically — in the disposable cache, not inside the checkout that owns the ledger, because a marker no write commits would otherwise leave every session's tree dirty. Every ledger write path bumps it once its own files are in place: write_run_file, append_run, _write_state (hence write, the hold and repair paths), _commit_run_split and _restore_run_files. A read whose generation and run-directory identity both still match what its index recorded reuses the stamps the index holds and walks nothing. A read whose generation differs, or whose generation file is absent, walks the documents exactly as it did before, so a ledger this code has never written reads correctly and an index published before the key existed refreshes on its next read. The run directory's own identity is compared beside the generation, so a document added or removed by a writer that predates the generation is still noticed.

Measured. The same probe at the head commit: 2 stat calls at 20 documents and 2 at 200 — the aggregate and the run directory, both constant. tests/test_a_ledger_read_does_not_walk_every_run.py asserts that equality and, as a positive control, that each warm read still returns every row (20 and 200). It drives each write path — write_run_file, append_run, write, _restore_run_files — and asserts the generation moves and the next read returns the written row. It deletes the generation file, edits a document outside every write path, and asserts the read returns the edit, which is the rebuild condition observed rather than assumed. The declared negative control, restoring the per-document walk, was executed and logged: the warm-count case reds (3 failed, EXIT=1) because the 200-document count climbs back above the 20-document one.

Writers outside the ledger. A warm read answers from the index only when the generation matches, so a row moved by anything other than a ledger write path would be served stale. The production surface was searched and none exists: every writer of docs/state/<project>/runs/*.json reaches the file through ledger.write_run_file or ledger.write — the crew run commands, routing, the promotion record, gate and release paths, and the duration-backfill and figure scripts. The one direct write into a runs directory outside the ledger writes a synthetic row under tempfile.mkdtemp() inside a census control script, never a real ledger. The search, with its commands and output, is in writer-search.log.

Two existing tests had made their point by rewriting a run document in place, outside every write path. Both now amend their row with write_run_file and keep their assertions that the next read answers from the new record: a released worktree, and a retention recorded after the index was published, are each seen by the next bounded read. The pair passes (10 passed).
