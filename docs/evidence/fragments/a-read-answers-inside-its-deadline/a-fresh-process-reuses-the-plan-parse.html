A fresh process reads discovery from the persisted parse

The metadata index now carries each covered document's discovery state — the parsed <meta> record, its readiness tuple and its section declarations — beside the row and the content digest it already persisted. A discovery read asks the index for the docs tree and receives, per file, the parse recorded for it, so the tree is parsed once and a restarted server or a fresh MCP process reuses that parse instead of building the soup again. Only a file whose bytes moved is parsed, and the parse the reading process made is written back under its new digest.

Two guards keep the answer current. An entry whose recorded digest no longer matches the file's is left out of the returned map rather than handed back, so the caller parses the file it cannot vouch for; and a store that cannot be read — absent, truncated, written by another schema — falls back to a full build rather than to the entries it could partly parse. The reused parse is also handed to the shared per-file memo, so the roadmap's authored-section read, which would otherwise parse each plan a second time, reuses it.

Measured as the number of body parses a fresh process makes while answering discovery over a temporary tree of 24 plans, counted in a child process so its in-memory memo starts empty: the first read parses 24, a second process parses 0, a one-file edit makes the next process parse exactly 1 and return that plan's new status, and the process after it parses 0 again. With the store bypassed the same fresh process parses all 24. Time and memory are read from the reckon.metadata-index store; the temporary tree is written by the test and removed with its tmp_path.
