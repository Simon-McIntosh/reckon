The served count reads the assembled blocker list, and the orphan rule speaks in lifecycle

A plan stored blocked with no recorded blocker row is held by a wait nothing has written down. roadmap.plan_blocker_state assembles that state and synthesizes a persisted placeholder so the plan does not read open, but the served view counted only the rows recorded_blockers returns. The plan therefore reported effective_status blocked beside blockers 0: a reader of the count saw no wait at all. Reproduced before the change on a temporary project — effective_status: blocked, blocking: [], blockers count: 0.

reckon/serve.py now counts the assembled list, len(state["blocking"]), at the call site, so the placeholder is in the count while plan["blocking"] still publishes the recorded rows — the list the audit reads to ask whether a blocked status has an explanation. Counting the placeholder there instead would have hidden the finding this node's other half reports.

The roadmap's orphaned-blocked-status finding now carries the lifecycle category rather than the dag default that roadmap._finding gave every finding it built. The category is a keyword argument with the old default, so every other roadmap finding keeps dag, and the orphan rule keeps its released-plan exemption: a stored-blocked plan whose cleared blocker a probe released has no live hold and is not orphaned. Before the change the same probe reported the finding with category: "dag".

tests/test_the_served_count_and_the_orphan_rule_read_the_assembly.py builds a temporary project in a temporary home — RECKON_HOME covering the configuration home, the crew home and the cache, plus RECKON_STATE_ROOT and RECKON_MOUNTS_PATH — with one plan stored blocked and nothing recorded, and one plan stored blocked whose held blocker a probe cleared. It holds that the first reports a non-zero served count while its recorded list stays empty, that the roadmap reports exactly one orphaned finding for it in category lifecycle, and that the released plan gets none and counts zero.
