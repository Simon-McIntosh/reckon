A slow roadmap read serves its last snapshot

The defect. _roadmap stored a composition only when the key was unchanged after the read — if settled is not None and settled[0] == scoped[0], before this change — so on a busy fleet, where the key moves during most compositions, the node-local cache directory held no snapshot at all and a fallback would have had nothing to serve. The second half of the defect is the read itself: a key miss recomposed for the whole 30 s deadline and then reported storage-slow, discarding a composition that was still running.

Every composition is kept, per tree and per shape. The record is filed under the project's resolved docs root and a digest of the request shape — sprint, max_paths, view, cursor, limit — under the key it was composed from, and carries held: whether that key was still the tree's when the record was composed. A record whose key held answers an exact-key read; one whose key moved does not, because the tree has since changed past it, but it is still the freshest answer the tree has for that shape.

The reserve. A read whose request shape has a stored record awaits its recompute only to the deadline less STALE_SNAPSHOT_RESERVE_SECONDS (1.0 s, overridable through RECKON_ROADMAP_STALE_RESERVE_SECONDS), then answers from the last record for that shape, marked stale: {age_seconds, key, shape, stored_at, reason} with the reason the key moved and a recompute is in flight.

The wait is the existing shielded one in _await_body, so the recompute is abandoned rather than cancelled: it runs on, stores its composition, and the next call serves it fresh. A request shape with no stored record keeps the whole deadline and reports storage-slow exactly as before, and one recompute per key stays the job of _read_joining_running over _INFLIGHT_READS.

Two follow-ups from the same review. The keep bound counted files while records are one per docs root and per shape, so a tree answering more shapes than the bound lost its oldest answers to age alone. It now counts docs roots and keeps each kept tree whole, counting the file just written, and the gone-tree rule is unchanged; the case test_one_tree_keeps_its_record_for_every_shape_it_holds stores ten shapes in one tree and requires all ten back. Separately, every read asked the fallback for a full stale answer up front, building a whole composition only to discard it on every read that did not time out. The deadline wrapper now takes a presence check, which the roadmap read answers from the record lookup alone, and builds the marked answer only at the timeout.
