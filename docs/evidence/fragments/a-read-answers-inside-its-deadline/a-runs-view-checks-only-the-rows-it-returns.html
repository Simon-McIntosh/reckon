A runs view loads the ledger once and checks only the rows it returns

Two costs came out of runs_view compacting every row of a project before it filtered, sorted and applied limit. A live row whose pointer and stream carry no session reached the ledger source with no committed row in hand, so that source loaded the whole ledger to search for the row the view had already read — once for each such row. And every compacted row probed its worktree, its manifest and its transcript, though a limited view returns a handful.

The view now holds one committed-row mapping per project, keyed on the canonical root so the live and ledger arms reach one ledger from different spellings of the same path, and hands each live row a nullary lookup into it. The ledger source calls that lookup only when the pointer and the stream leave the session unanswered, so a live row whose session is already answered costs no read at all. The path-derived fields are deferred: a row carries them absent until it survives the filters, the sort and the limit, and the one caller that judged on resumable finalizes the rows it must judge. resolve_session keeps its source order and answer shape; ledger_row now also accepts a callable.

Measured on a synthetic project of 52 promoted rows and 3 live pointers whose run ids appear in the ledger, with every environment-resolved directory pointed at temporary paths, and counted with wrappers: one runs_view with limit=5 makes 1 ledger.load call and 12 _path_exists calls over the 5 rows it returns, where the bound is 1 per project and 3 per returned row. Its rows equal the eager projection's first five field for field; a source="live" view makes 1 load over the 3 live rows and keeps each row's ledger-sourced session; and a view filtered on resumable returns the rows base returned for both values.

On the real crew home, a census of callers at this revision — before the cache key was canonicalised — recorded 2 ledger.load calls, both from ledger.runs: one per arm, because the two arms spelled the project root differently. 7,133 committed rows were answered from the row the view already held with no load, and 6 live rows were answered through the new lookup, which read the ledger for no row of its own. The canonical root collapses those two reads into one; that figure was not re-measured here, and the coordinator times the live view after landing.

The declared negative control computes the path-derived fields for every row before the limit again. Applied to a scratch head tree by restoring with_path_fields=True at both call sites, it makes 162 _path_exists calls against the 15 the bound allows for 5 returned rows, over a run ending EXIT=1 with tests/test_a_runs_view_checks_only_the_rows_it_returns.py::test_a_runs_view_checks_only_the_rows_it_returns failing — an id the head arm does not fail.

So this change adds no failure.

One ledger read per live pointer whose classification is blocked, interrupted, stopped or abandoned was found and not repaired, because it happens inside classify_pointer — which this section leaves alone — and outside this node's write scope: _blocked_session_resolution resolves those runs' sessions with no committed row, so each such live row loads the ledger once. The fixture here therefore stands live pointers that classify as running, and the finding is reported for a follow-on node rather than absorbed.
