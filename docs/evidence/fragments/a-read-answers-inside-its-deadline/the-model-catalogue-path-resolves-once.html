The catalogue's package-relative path resolves once per process

What changed. flight.model_catalogue_path resolved Path(__file__) through realpath on every call, and ledger.resolve_name calls it once per name it normalises, so a single held-worktree read paid tens of thousands of resolutions for one file that cannot move while the process runs. The package-relative default now comes from a cached helper (_default_catalogue_path, functools.cache), so it is resolved on the first call and reused for the life of the process. A code change replaces the process, from an image that carries its own catalogue beside the package.

What did not change. RECKON_MODEL_CATALOGUE is still read on every call, so an override set after the first call takes effect on the next one, and resolve_name still compares the catalogue's file identity (st_mtime_ns, st_ctime_ns, st_size, st_ino), so a catalogue edited between two reads is read again. No caller changed.

Measured

The first case warms the path once, then counts pathlib.Path.resolve calls during 1,000 ledger.resolve_name calls: 0, against 1,000 for the negative control. The second case sets RECKON_MODEL_CATALOGUE between two calls and observes the returned path change. The third rewrites a temporary catalogue between two resolve_name calls and observes the answer move from ("temp", "first") to ("temp", "second"), so the file-identity check still governs.

One correction found while measuring. The first negative control run passed when it had to fail. The documented cause was the suite's autouse catalogue-isolation fixture, which points RECKON_MODEL_CATALOGUE at an absent path for every test outside its catalogue-subject set, so no override-free measurement was possible: the case never reached the code it measures. The case now clears that variable before warming, and the mutation then reports the full 1,000 resolutions.
