The served view takes each plan's blockers from the roadmap's assembly

serve._derive_lifecycle built its own blocker list from unsatisfied dependencies, sprint-declared explicit blockers and unpassed gates. The roadmap's row built a different one, folding in held paths and the plan-level open decisions that plan_level_decisions selects. The two disagreed exactly where the served view is the surface a reader sees: a plan held by an unscoped open decision read active through the served plan list and blocked through the roadmap, with nothing comparing them. Reproduced before the change on the fixture the test now uses: served effective_status: active, served blocking: [], while the roadmap row for the same row read blocked.

reckon/roadmap.py now exports plan_blocker_state, which assembles one plan row's blockers — dependency rows the caller resolved, explicit and held rows, unpassed gates, plan-level open decisions — and returns the blocker list, the per-kind lists, the blocked flag, the closable flag and the effective status together. Unresolved dependency resolution stays with the caller, because it needs the project's other rows. The roadmap's own loop reads that function for its row instead of assembling a second list, keeping dependency cycles as the one graph-wide hold it adds itself, and _derive_lifecycle keeps no assembly of its own: the change there is at the call site, and the module's width is untouched.

A released hold was the second divergence, found in review of that change and folded into this attempt. The assembly synthesizes a persisted/unrecorded blocker for a plan stored blocked whenever it sees no blocker rows, and the roadmap suppresses that placeholder for a slug a probe has released (plans_released_by_cleared_blockers, now exported and read once by each surface). The served view passed no released argument, so a plan whose cleared blocker the probe had already ended read blocked through the served list while the roadmap read it ready — the reverse of the defect above and the same defect in substance, a fact derived twice. The served view now takes the released set from the same roadmap read and passes it into the same assembly, so both surfaces answer one call. No second released set is computed, and serve.py's change stays at call sites.

tests/test_the_served_view_reads_the_roadmaps_blockers.py builds a temporary project with four plans — one held by a plan-level open decision, one by an unpassed gate over its only implementable section, one free, and one stored blocked whose held blocker a probe has released — and compares the served view's blocker kinds and blocked state against the roadmap's for each: 5 passed. Under the declared negative control, restoring the served view's own assembly, the decision-held plan disagrees and two cases fail (EXIT=1), while the released, gate-held and free plans still agree, so the check is aimed at the decision rather than failing for any change at all. Under a second, targeted control — dropping only the released argument from the served view's call — the released plan alone fails, reading {'persisted': {'unrecorded'}} on the served view against {} on the roadmap, 2 failed and 3 passed at EXIT=1; with the argument restored the file returns to 5 passed.

A third reading of the same fact was a divergence in review: the assembly took the plan's status from the stored status, while the roadmap ranks a plan by _status(plan), which prefers workflow_status. A row carrying both spellings would then be ranked by one status and reported by the other, and the persisted-placeholder guard would synthesize a wait from a status the row had already left. The assembly now takes the status the roadmap prefers and reads it through _status, the dependency-row state and the served view both call the same helper, so the rule has one spelling and only _status's own body carries it, and the served view keeps a workflow status already on its row rather than overwriting it with the stored status. A row with neither status spelling now reports a draft through the dependency assembly, the same answer every other reader gives it; a case pins that, and under a control restoring the inline precedence in dependency_row_state the case fails at EXIT=1 (negative-control-dependency-row.log). The new case gives both surfaces one row with workflow_status: active and status: blocked and requires them to agree and to read open: with the preference it passes, and under a control reading plan.get("status") again it fails: both surfaces then synthesize the placeholder and read the plan blocked while the row says active, the served view listing it as {'persisted': {'unrecorded'}} where the roadmap's field lists it among {'explicit': {'unrecorded'}}; restored, the file returns to 6 passed. Both controls are logged beside the gate — negative-control-declared.log and negative-control-status-source.log — the released-argument control remains in negative-control.log, and the dependency-row control is in negative-control-dependency-row.log.
