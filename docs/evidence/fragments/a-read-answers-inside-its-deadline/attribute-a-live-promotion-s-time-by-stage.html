Method. Each profile was recorded by the coordinator with py-spy record --idle --format raw --subprocesses --threads --rate 100 and read in place under ~/.cache/reckon-promotion-rollout/live/; none was copied. A stage's estimated wall time is the receipt's wall seconds multiplied by that stage's share of the original main thread's samples, and a stage's execution mode is subprocess wait when the stack holds subprocess.py, lock wait when it holds _pointer_lock, lock/thread-pool waits otherwise distinguished from CPU and filesystem waits by the leaf frame. Helper threads and child processes remain in the raw profile and are excluded from wall-time addition, because their samples overlap the parent's wait. The independent coverage check is min(1, main samples / 100 / wall) times the named share, and it must reach 90%; every table above reaches at least 94.2%.

Set against §71's seeded tables, the seeded run's largest single stage was interpreter startup, at 40–62% of a 1.6–8.3 s promotion, and it named no stage over 1.6 s. Live, interpreter startup does not reach the top ten. Fourteen stage/verb pairs are more than ten times their seeded time: landing preconditions 664x (review) and 437x (implement landing), git revision/status 304x (landing), plan comment 248x (review) and 157x (landing), review-tier resolution 38x and 55x, ledger index decode 41x (landing), commit landing record 25x and 49x, ledger snapshot 22x (landing), worktree copy deletion 13x and 12x, and the merge/push 10x. Five live stages have no seeded analogue at all: rollout-stream pointer classification, the review-store index and stat, the pointer lock, the file-memo reads and the fleet-state read. What the seed did not reproduce is what dominates live: shared-filesystem contention on the real checkout and index, concurrent promotions holding the same run's pointer lock, real review records and plan sizes, live peer pointers, and the network remote.

Caveat that bounds the subprocess rows. None of the thirteen profiles contains a child-process sample, so a subprocess stage measures the parent's own wait and its argv is read from the profiled revision's source at the innermost product call site rather than observed: _uncommitted_paths issues git status --porcelain, _tree_state issues git rev-parse --verify HEAD, run_git issues git -C <repo> <args>. A short git call is not sampled before it exits. One further profile was recording while the analysis ran and is excluded: its receipt carries neither a wall time nor an exit status, and it has no raw file.
