the-held-worktree-read-is-bounded

One fleet_state derivation now decodes only the per-run crew documents whose node id names a registered, inspected tree. The screen reads each run's node id from the ledger's own picker projection; a run the projection does not carry stays a candidate, so a lagging index costs a read rather than dropping a duty. The whole read runs inside file_memo.read_only_region, which stats and decodes each document once and hands it over without copying.

The screen's key is safe because a tree's directory is named for the run's node id: _launch_worktree_path builds <root>/<session>/<node id> and every attempt to launch a node in a session reaches that same directory, so a retry, a redispatch and a shadow re-run reuse the node-named tree rather than naming a new one. Measured over the live corpus — 8,733 per-run documents in ten projects, 250 carrying a retained worktree — every retained path's directory name equals its record's node id; the two whose parent is not the record's session (shadow re-runs, reused trees) still carry the node-named directory, so the screen reaches them and only record_names_worktree's session rule then declines them. test_a_tree_reused_under_a_foreign_parent_stays_a_candidate pins that: the screen admits a foreign-parented tree and an unlisted run, and declines only a genuinely different node.

Measure over a home of 500 per-run documents, 15 of which name a tree: _run_file_record 15 (bounded by the trees, not the corpus), copy.deepcopy by the derivation 0, posix.stat 537 (at most one per document plus a small constant). At the base tree the decode count is 500 and grows with the corpus.

tests/test_the_held_worktree_read_is_bounded.py: 3 passed at head. The negative-control arm runs the same test against a scratch checkout at the base revision, where the decode count is 500 rather than 15 and the test fails on the read bound.
