A fresh read takes the run ledger from its index, once

On the live fleet node a fresh process read every committed run file instead of its index. ledger._indexed_data raised sqlite3.OperationalError: unable to open database file at sqlite3.connect, because the pick-input index resolves under the configuration home and the fleet mounts that home read-only around worker launches: no index could be created there, and _last_good_index_data had nothing to fall back to, so ledger.load scanned all 4,197 run files. Independently, mcp_views._cached_attempts published its aggregate only while the newest run file and the live-pointer set held still across the read, so one roadmap read aggregated twice and loaded the ledger twice.

reckon/ledger.py: _index_directory publishes the index to the user cache root when the configured directory exists and is not writable, resolving that root through the store's own cache kind. reckon/mcp_views.py: the attempt memo is published only under the stamp taken before the ledger read — the state its value is a reading of — with the index file's own identity left out of the comparison, because the read itself rewrites that file. A memo published under the post-read stamp answered every later reader whose stamp showed a live pointer written during the aggregate with a value computed before it, so the pointer stayed missing from the result for as long as that stamp stood.

Measure: tests/test_a_fresh_read_takes_the_ledger_from_its_index.py — 5 passed at head; at base 2 fail (the index moves to the user cache and the fresh process that decodes no run file). Restoring the post-read-stamp publication fails exactly the freshness case, a pointer written during the aggregate is seen by the next read. On the live node with the pre-fix tree, one mcp._roadmap made ledger.load=2 and ledger._read_run=0.
