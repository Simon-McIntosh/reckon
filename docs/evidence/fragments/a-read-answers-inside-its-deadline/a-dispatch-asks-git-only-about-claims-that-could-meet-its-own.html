A dispatch asks git only about claims that could meet its own

A dispatch read every live pointer's write claims and then spent a git status --porcelain and a reachability query in each pointer's worktree, whatever those paths were. Of 53 live pointers that morning, a dispatch could be refused by only the handful whose paths could contain, or be contained by, one of its own. The rest cost the read a pair of subprocesses in a worktree it never needed to touch, and the read sat in cxiWaitEventWait behind them.

The claim read now takes an optional candidate_paths. A pointer's entries are resolved first — as before, and before any disposition is read — and its disposition is read only when one of those entries overlaps a candidate by the containment rule the arbitration already uses. Every other pointer is returned with unread set and no disposition, and the arbitration and the refusal skip an unread claim rather than reading a verdict that was never reached, so no collision goes unreported and no claim that could refuse is dropped. A caller that names no candidate paths — a re-read of a run's own claim, and the scopes view that reports every claim — judges every pointer exactly as it did before. The repository identity behind each pointer's checkout is now shared across one read, so the git rev-parse costs one subprocess per distinct checkout rather than one per pointer, and the derivation-project lookup reuses the same cache and the mount table the read already holds, so it adds no probe of its own.

A narrowing that no production caller asks for narrows nothing, and the first landing of this change left the dispatch asking for nothing: _repository_scope_claims was called with no candidate paths from the dispatch's own admission check, so the read it exists to bound still disposed every live pointer — the cost the section measured at 463 s. Both of the dispatch's arbitration reads now hand over the node's own resolved scope: the check that runs before the arbitration, and the re-check that runs after the claim is published. The candidate paths come from the same expansion the arbitration matches on, and the read filters on the same repository-and-containment test over the same entries, so no claim that could refuse this dispatch is dropped.

Measured with a wrapper around subprocess in reckon.crew.node, over a fixture of twenty-one live pointers — ten in each of two repositories declaring files the dispatch does not write, and one declaring the package directory that contains the dispatch's package/target.py. The read returns twenty-one claims; the overlapping one is binding and not unread; the other twenty are unread and cost nothing. Dispositions are spent for the overlapping run alone: the wrapper counts 2 git calls, one status --porcelain and one reachability query, both in that run's worktree and neither in any other. Identity probes are at most one per distinct repository root among the claims that can meet it, and none at all in the checkout of a claim that cannot: each of the ten pointers in a repository shares that one probe, and the twenty disjoint claims name twenty checkouts of their own that the read never reaches. Before the derivation-project lookup shared the read's identity cache, the same fixture counted 23 rev-parse probes — two from claim_repository and twenty-one from repository_projects, one per pointer — which is the count this node's test caught red.

The declared negative control reads every pointer's disposition again. Applied to a scratch head tree by forcing the overlap predicate true, it turns the wrapper's disposition count from 2 to at least one per pointer, over a run ending EXIT=1 with two failing ids the head arm does not fail: tests/test_a_dispatch_asks_git_only_about_claims_that_could_meet_its_own.py::test_the_read_probes_git_only_for_a_claim_that_can_meet_its_own and tests/test_a_dispatch_asks_git_only_about_claims_that_could_meet_its_own.py::test_a_claim_that_cannot_meet_the_dispatch_is_returned_unread. The log is logs/negative-control.log in the run directory.

The bound is asserted from the dispatch's own entry in test_the_dispatch_itself_probes_git_only_for_a_claim_that_can_meet_its_own, over the same fixture, so a read wired to no candidates cannot pass it: a dispatch of that fixture spends 2 disposition calls, both in the overlapping claim's worktree. Reverting the wiring and nothing else — the read called with no candidate paths again — spends 42, two for each of the twenty-one pointers, over a run ending EXIT=1 with that test failing and the other five passing.

Gate arm at 1150dcc49 runs the cohort of eleven files to 1 failed, 91 passed in 165 s; the base arm at 7cb177e8a runs the same cohort less this node's file to 1 failed, 86 passed in 254 s. The single failure is the same pytest node id in both arms — tests/test_overlapping_queued_requests_launch_in_turn.py::test_a_new_dispatch_over_a_queued_claim_queues_then_launches, which a peer node owns and which is red at base. Five tests are green at head that are absent at base: this node's own. So the change adds no failure.

One part of the section's deliverable is deliberately not applied. Reordering _WORKTREE_REPOSITORY_FIELDS to ("repo", "worktree") makes claim_repository resolve a pointer's repository through its recorded repo first, and that admits a second writer of one file: tests/test_crew_cross_project_claims.py::test_one_repository_file_refuses_a_second_writer_across_projects fails with the dispatch admitted, because a pointer whose repo names another project's checkout has its declared path resolved against that checkout rather than against the worktree it actually writes in. The verdict is not one this section may trade away — its own deliverable holds that the arbitration's verdicts are unchanged — so the field order stays ("worktree", "repo") and the read's cost is bounded by the memoised identity cache and the overlap pre-filter instead. The bound this node holds is the measured one: no git at all for a claim that cannot meet the dispatch — not its disposition, not the rev-parse that would place its checkout — and, among the claims that can meet it, one identity probe per distinct repository root, shared by every pointer in it rather than spent per pointer.
