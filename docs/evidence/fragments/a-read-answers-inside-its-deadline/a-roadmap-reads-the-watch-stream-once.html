One read parses the project watch stream once, then only its new bytes

Both readers of a project's watch stream — the sprint liveness derivation in reckon/sprint_liveness.py and the live-run classification in reckon/mcp_views.py — need the same fact: the newest transition recorded per run. Each used to open runs.watch_stream_path(project) and parse it whole, so one roadmap read parsed the stream once per reader per call. A shared reader, runs.watch_stream_latest_events, now holds the byte offset it has parsed to and the reduction it built, keyed by project, in one process. The first reader to consult the stream parses each line once; every later reader in the same read receives the shared reduction. Only bytes appended since the last read are parsed, and a stream whose identity (device, inode) changed, or whose size fell below the parsed offset, is parsed again from the start rather than trusted to be an extension.

The reduction keeps only events that name a run and carry a classification (recovery_classification or to_state), which is exactly the set both readers already act on, so it replaces both readers' own loops without changing what either returns. The offset advance and the reduction are held under one lock, because two server threads consuming the same appended bytes would both advance the offset past them and skip those records for every later read.

Measured as the number of runs.parse_stream_line calls a single mcp._roadmap makes over a temporary project whose watch stream holds 10,000 lines, counted by wrapping the parser both the shared reader and the from-scratch reference call through.

second read after ten lines are appended—10

Each read is checked against a from-scratch parse of the same stream, so a read returns what an unshared read returns. The negative control is the case that gives the first row its meaning: the same test file run against a copy of the base tree counts 40,000 parses of the 10,000-line stream — the two readers each parsing it whole, twice and once — and fails the bound, logging EXIT=1 under the run directory. A pass on the base tree would mean the count measured something other than the sharing.
