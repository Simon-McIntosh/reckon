A tick over 230 live runs reads only the streams that moved

What landed. The tick asks two questions of every live run on every pass — whether its newest stream carries an assistant record, and which tool call it closed on — and both walk the stream to answer. _stream_holds_assistant_record and _last_tool_call in reckon/crew/recovery_wait.py now answer through the shared file memo, keyed on the stream's stat identity, so a stream that did not move is not read again and a stream that grew is. The scans themselves are unchanged, in _scan_stream_assistant_record and _read_last_tool_call.

The defect, reproduced before repair. A temporary crew home carrying 230 live runs was ticked with a counter standing on Path.open, first shown seeing reads known to happen (690 opens on the cold tick). With nothing appended, the next tick opened 874 run streams — about four per run — and a tick where one run appended opened 502. The cause is in _last_tool_call: it walks a stream backwards until it finds a tool call, which is the whole stream when the stream holds none, and nothing remembered the answer between ticks. A tick's cost was therefore the fleet's whole stream volume rather than the bytes that arrived since the last pass.

After the repair. The same home and the same counter: the quiet tick opens 0 run streams, and the tick where one run appended opens 5. The answers still follow the bytes: a stream that grows from no tool call to a sleep 5 call answers with the new call, asserted in the same case.

The measure is tests/measure_station_tick_at_230_runs.py. It builds a crew home of four mounted projects and 230 live runs with 1 MiB streams, appends 32 KiB to every stream before each of 20 consecutive ticks, and records each tick's duration and the station's resident memory after it (VmRSS from the process's own status). Every reading is checked against the section's bounds: 30 seconds a tick, 2 GiB resident.

Negative control, and this record's verdict. The section's own control — the same measure at the base revision recording ticks over 30 seconds — does not reproduce, so this record carries plan-verdict="qualified" rather than a passing verdict the control would have to support. The base revision records no tick over 30 seconds on either node: its worst tick is 18.3 seconds on the run's node and 9.0 seconds on all_debug, with a median of 3.2 and 1.5 seconds. What the base revision does show is the mechanism the repair removes, quoted above as 874 stream opens on a tick with nothing new. The red log this node declares is the repair's own mutation: with the memo removed from reckon/crew/recovery_wait.py, the quiet-tick case fails on the streams it reads, and it passes with the memo restored.

What these numbers do not say. Both populations still spike — every thirteenth tick in each arm — and the spike halves with the repair (14.4 s to 8.3 s on the run's node, 6.1 s to 3.8 s on all_debug). Neither arm crosses the section's bound, so the spike is named here rather than fixed. The measure's seconds are the host's wall clock against a synthetic population with no process load and no memory pressure; they bound the tick's own work, which is what the repair changed.
