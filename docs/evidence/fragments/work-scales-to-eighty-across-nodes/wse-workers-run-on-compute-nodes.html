A worker on a compute node leaves no scratch on the fleet node

A dispatch composes a worker's launch on the fleet node and places the worker as a scheduler step, which runs it on the compute node the allocation is held on. The one path a launch owns beneath a node's /tmp is the run's own scratch directory. The composition created it on the host that composed the argv, so every compute-node worker left a scratch directory for itself on the fleet node's local disk, and the node that actually ran it created nothing. The run's scratch is now created where the worker runs and granted by the fence whether or not the composing host has it.

What changed

  • reckon/_worker_fence.py: worker_scratch_write_roots() identifies the handed writable roots that are some run's own scratch directory — a child of the shared node-local scratch root, never the root itself. fence_argv grants those by construction, so the absent-on-this-host scratch directory still composes its --bind pair while every other absent root keeps composing no grant.
  • reckon/_backends.py: launch_plan creates every handed fence root except those, so composing a launch on the fleet node writes no run scratch on the fleet node's disk.
  • reckon/crew/dispatch_launch.py: placed_step_argv() names the placement test once (an srun --jobid= step). _worker_runtime_environment creates the run's scratch only for a worker that runs as the launcher's own child, and otherwise only names the path in TMPDIR. step_node_directories takes expected sources, so the placed step's wrapper mkdir -ps the run's scratch directory on its own node before the fence is exec'd.
  • tests/test_a_worker_on_a_compute_node_leaves_no_fleet_scratch.py (new): a composed fenced launch with a synthetic host scratch root, the placed step's node-directory list, and the launcher-child case that must still make the directory here.

The measure this node owns is the defect above, and it reads as a directory count: with the change, a composed launch places 0 run scratch directories under the composing host's scratch root, and the placed step's node-directory list names the run's scratch directory so the worker's own node makes it before the fence runs. At the base rule, applied as the negative control, the same composition creates 1 — the run's directory, under the composer's scratch root. The rehearsal this section's done-when describes (twenty workers through the scheduler, each delivering, reviewed and landing, with the fleet node's memory read before and during) is the separately dispatched test node's measure, not this one's.

What the test shows

  • A composed fenced launch leaves the run's scratch directory absent on the composing host, and still carries the --bind pair that grants it, so the grant is not lost by not creating it.
  • A placed step's node-directory list names the run's scratch directory although it is absent on this host, and names nothing when the source is read only from this host's disk — the two readings differ by the placement decision alone.
  • A worker that runs as the launcher's own child still gets its scratch directory created here, so the rule is placement and not the run: an unplaced worker would otherwise be the only one whose TMPDIR nobody makes.
