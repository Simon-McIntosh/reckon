The station tick at 230 live runs: 20 ticks, both arms

The instrument. tests/measure_station_tick_at_230_runs.py builds a temporary crew home: four mounted projects, each a real repository, and 230 live runs spread across them, each with a 1 MiB stream. Before each of 20 consecutive ticks it appends 32 KiB to every run's stream, as a live fleet's producers do; after each tick it records the tick's duration and the station's resident set size, read from the process's own VmRSS. A reading that reaches 30 seconds or 2 GiB makes the run exit non-zero.

Both arms. Two revisions were measured through the same instrument, each in its own tree on the all_debug partition: the base revision 0f519315992f429fae018708f84eba960b99fb15 in a scratch extraction, and the run's head 325e19aa9644320fae50fb747b55b9bfd82ef6ba in its worktree. The scratch extraction carries the measure module copied in, so both arms run the same instrument against their own reckon tree.

Negative control. The section's control is the same measure at the base revision recording ticks over 30 seconds. It does not reproduce at this population: the base arm's worst tick is 8.997 s and its median is 1.523 s. The base revision of this worktree already carries the earlier stream work, so the 2 to 6 minute ticks recorded on the fleet node are not reproducible from 230 live runs alone — they also depended on the node's memory pressure, which a synthetic population does not carry. What the base revision does show is the mechanism this node repaired: a tick over 230 live runs with nothing new read 874 run streams before the repair and reads none after it.
