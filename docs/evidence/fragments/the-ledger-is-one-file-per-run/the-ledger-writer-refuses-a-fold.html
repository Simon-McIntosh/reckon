the-ledger-writer-refuses-a-fold — the ledger writer refuses a write that folds per-run rows into the aggregate

What changed. ledger.write refuses an incoming write that carries a run id the aggregate's own rows do not hold while that run's per-run file exists, naming how many rows it would have folded and citing five of them. The comparison is against the aggregate's own rows, read directly, never against ledger.load's union. The existing run-count guard is re-based the same way: it now measures the aggregate's own row count, so a caller passing the aggregate's rows to a project whose runs are split is not mistaken for a shrinking write. record_hold_checks reads and writes the aggregate's own rows and its holds rather than the union, so a hold transition cannot carry per-run rows into the tracked aggregate.

Measure. tests/test_the_ledger_writer_refuses_a_fold.py drives a throwaway project whose aggregate holds 10 rows and whose runs/ holds 50 files. A write of ledger.load's 60-row union is refused naming 50 folded rows and changes neither copy; a write of the aggregate's own rows plus one new run is accepted, and its fifty files are untouched; a record_hold_checks call opens a hold, leaves the aggregate at 10 rows and the 50 files byte-identical, and the reader still returns 60 rows. Head gate: 4 passed, EXIT=0.

Declared negative control, executed and logged. Against the base tree (2e9a07c237, guard absent) the union write is accepted: the same test file run there is 4 failed, EXIT=1, with the two refusal cases failing on DID NOT RAISE for the acceptance the base writer permits, and the append and hold cases failing because the base run-count guard measures the union. Log: logs/negative-control-base-arm.log.
