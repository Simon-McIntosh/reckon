the-ledger-writer-refuses-a-fold — the ledger writer refuses a write that folds per-run rows into the aggregate

What changed. ledger.write refuses an incoming write that carries a run id the aggregate's own rows do not hold while that run's per-run file exists, naming how many rows it would have folded and citing five of them. The comparison is against the aggregate's own rows, read directly, never against ledger.load's union. The existing run-count guard is re-based the same way: it now measures the aggregate's own row count, so a caller passing the aggregate's rows to a project whose runs are split is not mistaken for a shrinking write. record_hold_checks reads and writes the aggregate's own rows and its holds rather than the union, so a hold transition cannot carry per-run rows into the tracked aggregate. ledger.register_member reads the aggregate's own rows for the same reason: a roster registration in a project whose runs own files folded them until this landed.

Measure. tests/test_the_ledger_writer_refuses_a_fold.py drives a throwaway project whose aggregate holds 10 rows and whose runs/ holds 50 files. A write of ledger.load's 60-row union is refused naming 50 folded rows and changes neither copy; a write of the aggregate's own rows plus one new run is accepted, and its fifty files are untouched; a record_hold_checks call opens a hold, leaves the aggregate at 10 rows and the 50 files byte-identical, and the reader still returns 60 rows. Five further cases drive one production writer each over that same project — the idle-member reap, the disposable-identity retirement, the gate re-run record, and the figure and duration backfills — and each finds the aggregate's ten rows and fifty files still standing after the writer ran. Head gate: 13 passed, EXIT=0.

Declared negative control, executed and logged. Against the base tree (2e9a07c23, guard absent) the whole test file is 9 failed, EXIT=1. The refusal cases fail on DID NOT RAISE and the append case on the base run-count guard measuring the union (“this write takes the committed run count from 60 to 11”); the hold case's aggregate row list comes back with 50 more items, first extra f-000. The five writer cases fail because each writer folds the fifty per-run rows into the aggregate, which is the defect reproduced through the production path rather than asserted. With the guard present and the writers unrepaired the same cases fail the other way, each writer refused, so the cases hold the guard and the repairs together and neither half is green alone. Log: logs/attempt2-negative-control-base.log.

Other callers that write the aggregate, and how they read. Five production writers read ledger.load's union and would have handed the per-run rows back to the writer, so each is repaired here rather than left to refuse: the idle session-member reap (reckon/crew/routing.py), the gate re-run record when the run's file is missing (reckon/crew/promotion_gate.py), the disposable-identity retirement (reckon/crew/promotion_records.py), and the two row backfills (scripts/derive_run_figures.py, scripts/backfill_run_durations.py), and ledger.register_member inside the ledger itself. Each reads the aggregate's own rows through ledger.load_aggregate, passes those to ledger.write, and patches a row held by its own file through that file's canonical serialiser, so the union's run rows are never copied into the aggregate and no per-run file is removed or folded. A case per writer, driven over the same ten-row, fifty-file project, asserts the aggregate's row set is unchanged and every file still stands. A sixth writer lives in the ledger itself: register_member read the union and folded it on every roster registration in a split project, which the wider neighbour arm found and which is repaired the same way.

The completion repair, and the seventh writer. An independent review found that ledger.repair_completion read ledger.load’s union and handed it back to ledger.write, so over a project holding per-run files it raised the fold refusal instead of persisting — the CLI reaches it through the crew run command, and its own cases seed an unsplit aggregate, so nothing caught it. It now measures every run from the union, because the repair is about the whole history, and persists through one helper that patches an aggregate-held row in the aggregate and writes any other repaired row through that run’s own file, writing the aggregate only when one of its own rows changed. A case drives it over the ten-row, fifty-file project with a stream per run and asserts both halves landed: the aggregate still holds its ten ids with the repaired stamp, and each of the fifty files carries it. Reverted, the repair fails that case with the fold refusal the review named. Head gate over the fold and hold-check suites plus the six completion-repair cases: 19 passed, EXIT=0. A rescan of every ledger.load-then-ledger.write function under reckon/ and scripts/ finds no other union-fed writer.

One owner of the run-file write. A review of this node found the same function copied three times: the private helper inside ledger.py, and one in each of the two backfill scripts, each re-encoding one run through serialize_run into that run's own file beside _keep_run_files_identical, which did the same thing inline. All four are now one public helper, ledger.write_run_file, and the three in this node's scope route through it: _persist_repaired_rows, which the completion repair calls; _keep_run_files_identical, which re-encodes the copy of an aggregate row; and the figure and duration backfills. The two script copies and the private one are deleted. reckon/crew/promotion_release.py's _update_run_record re-encodes a run file itself and is not routed through the helper — it sits outside this node's write scope, so it keeps its own copy and this paragraph does not claim otherwise. The helper keeps each caller's permission bits: the callers that amend or create a run file pass the 0o600 they used before, while _keep_run_files_identical passes mode=None so a rewrite that only re-encodes a file already on disk leaves its bits as they were, which is what its inline write did. No behaviour changes: the bytes written are serialize_run(row) in every path, exactly as before. A later review found the fold test file added one ruff finding of its own, a timezone.utc where the UTC alias belongs; that is fixed, and the same check applied over every Python file this node changed found one more, a typing.Mapping import the figure backfill had gained, which now comes from collections.abc. The four files those two findings touched are clean under ruff check, and across all eleven changed files the head holds 15 findings against 15 of the same rules at the base revision, so the node adds none. Head gate over the fold suite and the hold-check suite: 13 passed, EXIT=0; the three widened files in full: 60 passed, EXIT=0; the suites covering the ledger and the run-file write path, including the two backfill scripts: 134 passed, EXIT=0.
