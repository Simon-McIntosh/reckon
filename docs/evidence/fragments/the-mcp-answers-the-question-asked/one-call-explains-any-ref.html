One call explains any ref

read_plan(view="why", project, slug[, section]) answers the question a coordinator otherwise settles by reading a plan, then a pointer file, then messaging a peer. One call reports the ref's own state (its section declaration, never the containing plan's status), what it declares it waits on and — transitively, to a bounded depth — what each of those waits on in turn, each wait carrying its kind; the sections that declare they wait on it; the runs and sessions working on it now with the paths they hold; and the plan's last five events. A ref that does not resolve is refused with the nearest refs that do. No MCP tool and no CLI verb was added: it is one value of read_plan's existing view parameter.

Every fact is read from the owner that already answers it, never derived again. Waits are the roadmap's own section-scoped edge rows: the mapping roadmap._plan_section_deps reads, resolved by roadmap._section_scoped_edges, so a wait carries the roadmap's satisfaction judgement and cannot read satisfied here and unsatisfied on a roadmap row. The holds are its named-hold assembly too — roadmap.plan_blocker_state and roadmap._decision_rows for a gate or a decision, run_blocker_rows for a run reported blocked — so the same gate, decision or blocked run holds a section on both surfaces, and each hold keeps its kind. Runs come from mcp_views.partition_live_runs, so a run reads the same here as it does on a roadmap row and in crew live; the paths each run holds are the dispatch scope claims its pointer already carries. The kinds are the shared vocabulary in live_run_classification. The composition lives in the new module reckon/why_view.py; reckon/mcp.py routes the view and trims its answer to the row reckon/mcp_budget.py declares for it, so the size contract is the shared table's rather than a figure this view keeps to itself.

The gate fixture is the shape the question takes: section alpha#s1 waits on beta#s1, beta#s1 waits on gamma#s1, a live run targets beta#s1 and holds reckon/held.py, and an open followup names alpha §1. The read names the wait on beta#s1 with kind section-dependency, its runs and held_paths, the depth-2 wait on gamma#s1, the followup, at most five events, and the answer's serialised size is inside the view's contract. Two further cases hold the rest of the contract: a plan-level ref names the run working on any of its sections rather than reading unheld, and a gate scoped to one section and an open decision scoped to one section each arrive as a hold carrying its own kind. Ten tests pass at the head (45 with tests/test_mcp_tools.py); the size and event figures are asserted against the shared budget table and the literal five rather than against the constants the answer trims to. On the base revision the same read is refused invalid_view — Unknown MCP response view 'why' — and the gate log records that base probe beside a base arm that cannot run the test file at all because it does not exist there.

The declared negative control removes the frontier advance in _transitive_waits, so only direct waits are named; the wait-chain assertion then fails and nothing else does — 1 failed, 9 passed, EXIT=1 — while the same suite at the head is 10 passed, EXIT=0, and tests/test_mcp_tools.py is green in both arms. The adjacent importer arm is unchanged across revisions: 88 passed at both the base and the head.

A review of the landed head found one blocking defect in what waits on a ref: the waited_on_by rows passed no declarations, so roadmap.dependency_row_state fell back to the waiting plan's status and the row reported its container's state instead of the waiting section's own. The rows now pass the authored declarations (states.of(waiting_slug).get("section_declarations")), and the test asserts the section's declaration where it differs from the plan's status — implementable against active, so a fallback reads the wrong value. Reverting the repair reproduces it: 1 failed, 9 passed, EXIT=1; with it, 10 passed and 45 with tests/test_mcp_tools.py.

The budget row is registered: reckon/mcp_budget.py declares ("read_plan", "why") at 24,000 and the view reads it, so no fork remains.
