One call explains any ref

read_plan(view="why", project, slug[, section]) answers the question a coordinator otherwise settles by reading a plan, then a pointer file, then messaging a peer. One call reports the ref's own state (its section declaration, never the containing plan's status), what it declares it waits on and — transitively, to a bounded depth — what each of those waits on in turn, each wait carrying its kind; the sections that declare they wait on it; the runs and sessions working on it now with the paths they hold; and the plan's last five events. A ref that does not resolve is refused with the nearest refs that do. No MCP tool and no CLI verb was added: it is one value of read_plan's existing view parameter.

Every fact is read from the owner that already answers it, never derived again. Waits come from _schema.section_depends_on over the plan markup the roadmap reads (roadmap._plan_authored_html), and their state from roadmap.dependency_row_state and roadmap._section_satisfied. Runs come from mcp_views.partition_live_runs, so a run reads the same here as it does on a roadmap row and in crew live; the paths each run holds are the dispatch scope claims its pointer already carries. The kinds are the shared vocabulary in live_run_classification. The composition lives in the new module reckon/why_view.py; reckon/mcp.py routes the view and bounds it.

The gate fixture is the shape the question takes: section alpha#s1 waits on beta#s1, beta#s1 waits on gamma#s1, a live run targets beta#s1 and holds reckon/held.py, and an open followup names alpha §1. The read names the wait on beta#s1 with kind section-dependency, its runs and held_paths, the depth-2 wait on gamma#s1, the followup, at most five events, and the answer's serialised size is inside the view's contract. Eight tests pass at the base-plus-change head (43 with tests/test_mcp_tools.py); on the base revision the same read is refused invalid_view — Unknown MCP response view 'why' — and the gate log records that base probe beside a base arm that cannot run the test file at all because it does not exist there.

The declared negative control removes the frontier advance in _transitive_waits, so only direct waits are named; the wait-chain assertion then fails and nothing else does — 1 failed, 7 passed, EXIT=1 — while the same suite at the head is 8 passed, EXIT=0, and tests/test_mcp_tools.py is green in both arms. The adjacent importer arm is unchanged across revisions: 88 passed at both the base and the head.

Two declarations the plan makes live outside this node's write scope. reckon/mcp_views.py owns VIEW_NAMES and reckon/mcp_budget.py owns the §2 budget table; both are outside the granted paths, so the vocabulary-completeness test and the default-fit test do not yet enumerate why, and this view declares and enforces its own figure (WHY_VIEW_BUDGET = 24_000) until that row is registered in the one table.
