§10 — A moved checkout serves every call on current code

The routing is the fix. _refuse_when_stale in reckon/mcp.py served a call on the current code only once the call had failed: _SERVE_ON_CURRENT_CODE recorded that, and was read as the gate on every later call. A call that still worked on the running image was therefore answered by the image, and after a landing that answer was behaviour the tree no longer has, with nothing in it to say so. Once the child is warm — its readiness probe has answered — and the tree is moved and trusted, every call is now routed to it. The record survives for one purpose: a write is routed only once the child has answered a call of that tool, because a write the child does not answer is never re-run on the image and the image has not run it yet, so routing it there would answer a write that never ran with write_may_have_landed instead of its own result. Reads, which are what the section's defect is about, are routed on the first warm call.

A raised failure while the child is cold. The guard's except re-raised, so a caller saw a crash where a returned failure had carried both stamps and a remedy. A call that raises while the tree is moved and trusted is now answered with stale_server_code, code_stamp_at_start, code_stamp_now, the reconnect remedy, and original_error naming the exception that was raised.

A schema failure beside a successful answer. An edit_plan write can succeed and report why its review predicate could not answer in review_owed_error; when the running image's classes cannot validate config the tree has moved past, that failure is this guard's own case. _embedded_schema_failure reads an *_error field naming a validation or config error as a failure, and the call is re-run on the current code like a returned one. An error of any other kind in such a field is the call's own result and stands, which is the case the neighbouring test holds.

Gate. Five cases in tests/test_a_moved_checkout_serves_every_call.py run the guard in process against a temporary tree with a controllable child: a successful call served by the warm child and carrying its stamp, with the image's tool never called; an unmoved checkout serving in process and starting no child; a raised failure while the child is cold, answered with both stamps and the remedy; an embedded schema failure re-run on the current code; and an embedded error that is not a schema failure left standing. That file and the five neighbouring stale-code test files run as one gate, judged by failure delta against the assembly base.
