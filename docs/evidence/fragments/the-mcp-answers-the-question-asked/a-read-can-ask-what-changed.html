§7 — A read can ask what changed

The existing since reaches three more reads, and each answer carries the instant to pass next. The roadmap tool gained the parameter (reckon/mcp.py, _roadmap_tool), so a view-less call — the brief — and every named view accept it alike; crew(view="live") already took it and now answers with it. A read that names a window answers with observed_at and the change set; one that names none is returned exactly as its view built it, so a raw read stays lossless and no view grows a key nobody asked for. No cursor was added, no store was written, and no read refuses a window that it used to accept. Both surfaces compose it through one helper, reckon/mcp_views.py's with_change_set, so the roadmap tool, the brief and the crew view verb answer one document for the same arguments. A read that spans projects — no project, *, or a graph: selector — has no single plan history or transition stream to bound, so it is answered with change_set.error reading cross_project rather than with a set narrower than the read.

The composition is a new module, reckon/change_set.py, reading two sources that already exist. Plan changes come from the plan files' git history through velocity._plan_history. Each plan's revisions are read in one batched blob read — the last commit at or before the window's start, then every commit inside the window, then HEAD — and a section's change is credited to the commit in that walk that actually moved its declaration, so a window holding two commits names two commits. Run changes come from the producer's transition stream (~/.config/reckon/crew/watch/<project>-<key>.events), whose rows carry observed_at; the change set filters on event="transition" and a real state move, and carries each row's own instant rather than a file mtime. Wiring findings are absent by construction — they are recomputed on every read and keep no history.

A section's landing reports the dependents it released. For each section whose declaration moved to done, the module walks the plan-section-depends-on edges and compares each waiting section's readiness across the same two revisions: implementable and every declared dependency satisfied. A dependent reported as newly_ready is one that was not dispatchable entering the window and is dispatchable at its end, and the entry names the refs it finished waiting on. Satisfaction is decided by the roadmap's own _section_satisfied, so a section released here is one the roadmap releases too — including a section carrying no declaration, which a gate closing to passed satisfies. A ref naming no section waits on the plan itself, and is released when that plan completes inside the window, judged by the roadmap's whole-plan rule — a completed plan, or one with a done section, every open section deferred and every authored heading declared — read against the revision rather than the checkout. Dependency refs are split by _schema.parse_plan_ref, the grammar every other surface reads them with.

The window is half-open at the start and closed at the end, at second resolution. A change is reported when since < time <= observed_at, so a change landing in the same second a read observed state is reported by that read and not again by the next. Both ends are applied to both sources: a commit or a transition landing after the instant a read observed state is outside that answer and is reported once, by the next one, rather than appearing in a reader's window before the read that owns it. A since the transition stream cannot reach back to is widened to the oldest row the stream still holds and marked full: true; "nothing changed" and "I cannot see that far back" are different answers and only one of them is safe to act on. An instant that cannot be parsed is named in the answer's error rather than read as an empty set.

The measure, and both controls. tests/test_a_read_can_ask_what_changed.py builds a repository under tmp_path whose first commit declares a#s1 implementable with b#s1 waiting on it and whose second declares a#s1 done, plus a transition stream in which one run's classification moves inside the window and another's moved before it, alongside a plan whose section is satisfied by a gate alone. A read with the previous read's observed_at returns exactly a#s1 (implementable → done) credited to the commit that moved it, exactly b#s1 newly ready, and exactly the one run (15 passed at head, 50 passed with tests/test_mcp_tools.py, EXIT=0). Four further cases each fail against the previous revision of the module and pass at this one — a second in-window commit crediting its own section, a commit and a transition landing after the observation instant and waiting for the next answer, a gate closing to passed releasing its dependent, and a project with no stream reporting sources.runs false (4 failed, 10 passed, EXIT=1), and a fifth — a dependent on a whole plan that completes in the window — fails against the revision before this round (1 failed, 14 passed, EXIT=1). The base arm runs tests/test_mcp_tools.py over an extracted c15f841ed1 tree (35 passed) and answers red on the new file; a probe against that same tree records the defect the node repairs — _roadmap_tool() got an unexpected keyword argument 'since', and a crew live answer carrying neither observed_at nor change_set. The declared mutation, ignoring since and returning the full answer, reds the window assertions: 7 failed, 3 passed, EXIT=1.

Two contract breaks the wider suite found are repaired, and the attach is one helper. A roadmap(view="raw") read that names no window must stay exactly {project, view, data}, and crew(view="live") must answer one document on the crew tool and on reckon crew view live; attaching a change set to every answer broke both. The change set is now composed only when the caller names a since, inside serve_crew_view — the one function both surfaces call — and a later review found the attach-and-error glue still written twice, in reckon/mcp.py and reckon/mcp_views.py, with the copies disagreeing on scope. That copy is deleted: with_change_set is the only implementation, the roadmap tool calls it from its own path, and the cross-project rule above is settled in it once. The gate at 3f08e5fdbc is 38 passed, EXIT=0 across tests/test_a_read_can_ask_what_changed.py, tests/test_mcp_recovery.py and tests/test_crew_view_serves_every_view.py.
