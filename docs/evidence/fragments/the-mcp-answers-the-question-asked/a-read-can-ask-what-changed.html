§7 — A read can ask what changed

The existing since reaches three more reads, and each answer carries the instant to pass next. The roadmap tool gained the parameter (reckon/mcp.py, _roadmap_tool), so a view-less call — the brief — and every named view accept it alike; crew(view="live") already took it and now answers with it. Every answer from those reads carries observed_at. No cursor was added, no store was written, and no read refuses a window that it used to accept.

The composition is a new module, reckon/change_set.py, reading two sources that already exist. Plan changes come from the plan files' git history through velocity._plan_history; for each plan the module reads the last commit at or before the window's start and compares that revision's section declarations with HEAD's, so a change is measured between two revisions rather than inferred from the present. Run changes come from the producer's transition stream (~/.config/reckon/crew/watch/<project>-<key>.events), whose rows carry observed_at; the change set filters on event="transition" and a real state move, and carries each row's own instant rather than a file mtime. Wiring findings are absent by construction — they are recomputed on every read and keep no history.

A section's landing reports the dependents it released. For each section whose declaration moved to done, the module walks the plan-section-depends-on edges and compares each waiting section's readiness across the same two revisions: implementable and every declared dependency satisfied. A dependent reported as newly_ready is one that was not dispatchable entering the window and is dispatchable at its end, and the entry names the refs it finished waiting on.

The window is half-open at the start and closed at the end, at second resolution. A change is reported when since < time <= observed_at, so a change landing in the same second a read observed state is reported by that read and not again by the next. A since the transition stream cannot reach back to is widened to the oldest row the stream still holds and marked full: true; "nothing changed" and "I cannot see that far back" are different answers and only one of them is safe to act on. An instant that cannot be parsed is named in the answer's error rather than read as an empty set.

The measure, and both controls. tests/test_a_read_can_ask_what_changed.py builds a repository under tmp_path whose first commit declares a#s1 implementable with b#s1 waiting on it and whose second declares a#s1 done, plus a transition stream in which one run's classification moves inside the window and another's moved before it. A read with the previous read's observed_at returns exactly a#s1 (implementable → done), exactly b#s1 newly ready, and exactly the one run (10 passed at head, 45 passed with tests/test_mcp_tools.py, EXIT=0). The base arm runs tests/test_mcp_tools.py over an extracted c15f841ed1 tree (35 passed) and answers red on the new file; a probe against that same tree records the defect the node repairs — _roadmap_tool() got an unexpected keyword argument 'since', and a crew live answer carrying neither observed_at nor change_set. The declared mutation, ignoring since and returning the full answer, reds the window assertions: 7 failed, 3 passed, EXIT=1.
