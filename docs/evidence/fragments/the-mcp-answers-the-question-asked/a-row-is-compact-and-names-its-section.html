A row is compact and names its section

Every crew list view that lists runs — live, runs, obligations and directory — builds its rows and routes them through one projection, project_run_rows in reckon/crew/query.py. That one function owns the field vocabulary the views share, fills each row's section from the run's own pointer, canonicalises the spelling, refuses a requested field the view does not carry while naming the fields it does have, and leaves a field whose value is empty off the row where the view serves a narrowed row. The runs view is the exception, and it is the one its own suite has always asserted: it serves its row whole. Every field it declares — the ones it answers by default plus the optional ones a caller may ask for — is on the row whether or not it holds a value, so a row can be read against the field list the view publishes and an empty field is not confused with one the view cannot answer; an optional field the caller did not ask for is absent, and a request adds that field to the declared row rather than cutting the row down. What each view did before, view by view: the live view could not name a run's section at all and refused fields=["section"], because its row builder never carried the field; runs carried it but narrowed its own fields and never reached the projection; obligations had no such field either; and directory carried the author's own spelling, so the same run read s4 there and §4 in runs. All four now call the projection, so the four agree and one rule answers for all of them.

The dependency row follows the same shape, now with one owner rather than three copies. The state a section-scoped row reports — the section's own declaration, falling back to the containing plan's status only where the plan declares none — is computed by dependency_row_state in reckon/roadmap.py, and both row builders call it: the roadmap's own section edges, and the ref resolver behind read_plan's deps list. The section_blocking projection does not re-derive the verdict at all; it reads the one the row already reached, so a wait whose target section reads satisfied is reported as holding nothing whether the section was declared done or its gate passed.

The declared mutation — returning section to the run row's omitted set, by dropping the projection's fill-and-canonicalise step — turns the four-view measure red: EXIT=1 with eight failing ids, all four views of both the names_the_section and the accepts_the_section_field case. The runs view now fails with the other three, which is the direct evidence that it routes through the projection rather than narrowing its own row. A second control turns the section-state rule red on its own: making dependency_row_state ignore the section declaration and report the containing plan's status fails both section-state cases (EXIT=1, 2 failed of 14, 12 deselected). A third control covers the runs row's shape: returning that view's projection call to the empty-field omission leaves the runs row narrowed and turns the cases that state its shape red — this node's own runs-row case, in the suite that holds the row whole (EXIT=1, 3 failed), and the live view's marker case goes red under a control that reads mine from the narrowed row again (EXIT=1, 1 failed of 2). A fourth, fifth and sixth control cover the declared vocabulary, one per view: with each repair reverted in turn — the duties' declared field set dropped, the directory rows' dropped, and the runs row built narrowed to the request again — the case that names that defect fails alone (EXIT=1 each).

The roadmap shrinks for one reason, and the reason is the rule above rather than a compaction pass: the section-scoped rows it carries now report the section's own declaration instead of the containing plan's status, and the declaration is the shorter string. A per-key comparison of the two serialised payloads puts the whole difference there — depends_on[].status and section_depends_on[].status fall from 559 to 410 characters in pending_work and from 495 to 374 in ready_now, while the readiness blockers' own status fields rise from 169 to 195. Nothing else moves beyond live-run counts. The roadmap's own row shape is unchanged.

The accepted field set is a property of the view, not of the rows a call happened to return. Three of the four views projected two lists, or a list whose fields the request does not need, with the accepted set read from the rows in hand, so an empty list narrowed the vocabulary to the four common run fields and a field the view does have was refused: obligations refused kind whenever nothing was acknowledged, which is the ordinary case; directory refused phase for any project whose runs all belong to a session, so unowned_runs is empty; and runs built its row narrowed to the request, so the view's own classification, session_id and resumable filters read an absent key and listed nothing. Each view now declares the fields it is able to answer for, beside the builder that produces its rows, and hands that set to the projection. The declared set is what a request is measured against; an empty list, or a list carrying fewer fields than the view has, changes nothing about what a caller may ask for. Narrowing a row to the request still happens in the projection for the views that serve a narrowed row, after the filters, which is the order the third defect was about. The runs view narrows nothing: the row it builds is its declared set, a request adds optional fields to that set, and its own classification, session_id and resumable filters read the whole row because the whole row is what the build produces. That is also the contract its own suite asserts — a row for fields=[...] is the view's default field set plus the requested optional fields — so the request cannot be answered by a smaller row than the one the view documents.

References the rows and the projection travel in remain strings of the one grammar, [project:]plan[#section][@run|@f-id]: the rows carry plan and section as plain strings, never as expanded objects, and the projection adds none.

One divergence from the done-when's literal wording, recorded rather than smoothed over: the fixture dispatches for P#s4 and the four views read §4, the canonical spelling of the same identity, because the one projection normalises every row's section through normalize_section. Before the change the views disagreed — runs read §4 and directory read s4 for the same run — so a single spelling is the point of the clause.
