A newer key in a shared flight config no longer stops an older reader

The generator now produces the flight models with extra = "ignore", so a key the running schema does not declare is ignored at load instead of raising Extra inputs are not permitted. The reader is told rather than stopped: resolve() walks each contributing layer against the model's own field declarations and returns every unrecognised key path on ResolvedFlight.unknown_keys, which flight_report() publishes as flight_unknown_keys — the field crew(view="flight") already spreads through. Ignoring alone would have been a silent typo, so the warning is the half that keeps a mistake visible.

Authoring stays strict. reckon flight --check resolves with strict=True and refuses the first undeclared key by path with the same Extra inputs are not permitted constraint the loader used to raise, so a typo is caught where the config is written. A type error on a declared key is still refused on the ordinary read, which is what keeps this forward compatibility for keys rather than for shapes.

Measured over a fixture host layer carrying a_key_from_newer_code at the top level and budget.a_key_from_newer_code nested: the load succeeds and reports both paths; --check on the same file exits non-zero naming the key; the shipped defaults and this workstation's real ~/.config/reckon/flight.yaml both report an empty list, so the walk finds keys the config carries rather than finding something in every config. Against the base revision the same load test fails with Extra inputs are not permitted; the negative-control log restoring extra="forbid" is cited in the manifest.

Two pre-existing tests assert the old strictness through a path this node may not write, and are recorded as follow-ons rather than edited: tests/test_budget_lift.py asserts the generated BudgetConfig itself refuses an undeclared key, and tests/test_one_check_trusts_a_moved_checkout.py forces a crew(view="flight") failure by adding an unknown key to the copy's shipped defaults. Both need their vehicle changed — the first to the strict read, the second to a fault that still faults — and neither is a regression in the loader.
