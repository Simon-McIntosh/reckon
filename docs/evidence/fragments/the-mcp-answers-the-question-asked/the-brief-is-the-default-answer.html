§6 — The brief is the default answer

A single project's roadmap read now answers with the brief. _roadmap_selected_view in reckon/mcp.py resolves a call that names no view to brief when the target is one project, and leaves a portfolio ("*") or graph: target on its own default, because neither carries a single project to brief. view="summary", "detail" and "raw" are unchanged and remain the drill-downs. The brief view is composed by _brief_view: the summary's own fields, produced by the function the summary view calls, plus text and the typed lines behind it, so the two answers cannot disagree about a figure. An explicit view="brief" against a portfolio or graph target is refused with a detail that names the three views it can take.

Every ranked row carries the ranking's own reason. The brief's ready_sections line already emitted each ranked row's ref, plan, reason and unlocks; this node holds the default answer to it, so the test compares each entry's reason against the payload row it was read from rather than against a literal. The brief does not call §4's why(ref), which is why this section did not wait on it.

Both skills lead with the brief. skills/reckon-roadmap/SKILL.md now opens its fast path with the brief and describes summary, detail and raw as drill-downs; skills/reckon-status/SKILL.md makes "where are we / what to do next" the brief's question and moves read_plan(project, view="summary") below it. The test parses each file's ## Fast path block and requires the first mention of the brief to precede the first named roadmap or plan view, so a later edit that lists summary first fails rather than silently reordering the reader's question.

The measure, and the control. tests/test_the_brief_is_the_default_answer.py asserts a view-less single-project read returns view="brief" with a non-empty text and typed lines, that each ranked row's reason equals its payload row's, that a named view="summary" read is unchanged and carries no text/lines, that the brief's summary fields equal the summary view's, and that both skill fast paths name the brief first. On the base revision the same file answers 5 failed, 1 passed (the passing arm is the summary-unchanged assertion, which already held); at the head it answers 6 passed. The declared mutation — resolving the default view to summary again — reds test_a_default_roadmap_read_answers_with_the_brief at EXIT=1.

The brief has its own row, above the summary's. reckon/mcp_budget.py now declares ("roadmap", "brief") and names brief as the roadmap's default view, so a call that names no view is held to the answer it receives instead of to the summary's row. The row is sized for a project's brief with headroom over that summary row rather than at a figure measured once: a brief carries the summary's own fields plus the composed lines and the typed rows behind them, and grows with the project's dependency graph.

The boundary is measured on an answer, not the table. The case that guards this builds a brief-shaped payload of 25,000 characters and asks the resolver the MCP read uses two questions: does the view a call naming no view resolves to admit it, and would the summary's 20,000-character row turn it away. Both hold, so the two rows describe different answers. The earlier form of this assertion compared the table's brief row with the row the default view resolved, and passed with the brief row lowered back to 20,000 because both sides moved together. The case now fails on that mutation: 1 failed, EXIT=1 in logs/negative-control-brief-row.txt. A fixture project was tried first and rejected: a project whose brief exceeds 20,000 characters is large enough that roadmap view="detail" answers 54,389 characters over its own 30,000-character row, so the contract is tested on the composition it governs.

The slow-read snapshot keeps working, filed under its own shape. A roadmap read stores every composition as its tree's last answer for the request shape it composed, marked with whether its key held, and answers a read held past its reserve from that record. The shape carries view, and its own documentation states why: two calls that differ in any shape field compose different payloads. A brief answer carries text and lines that a summary answer does not, so a view-less read now files under view="brief" and a named summary read under view="summary". Nothing in the store changed. On the merge of current main the slow-read cases answered 6 failed, 5 passed because they pinned the default shape to summary. That constant now names the brief, no assertion was weakened, and the same file answers 11 passed.
