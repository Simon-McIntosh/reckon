A close whose report fails still closes, and says why

The store composes a plan's evidence report after the plan file is already written, on the one transition where a plan reaches a landed terminal status. The composition used to be caught only for the two errors it names, so any other exception escaped after the close was committed: the plan was closed with no report and no account of it. The catch is now total, every failure leaves a durable record naming the plan and the error, and the close's own result says no report was composed.

What landed

  • reckon/_store.py — _write_state_locked catches every Exception from evidence.compose_closed_plan_report, writes the failure record, and warns. A failure writing the record itself is folded into the same warning rather than undoing the close. write_plan, _write_state and _write_state_locked gained an optional report_warnings list so the caller's own result carries the sentence.
  • reckon/evidence.py — record_close_failure writes one JSON record per plan under the crew home (close-failures/<project>-<plan>.json), carrying the project, the plan, the error type, the error text and when it was recorded. It sits outside the repository: a close that composed no report is a fact about the close, and committing it would put an unrequested report in the docs tree the retention sweep reads.
  • reckon/mcp_edit_plan.py — the state write passes a report_warnings list and appends its sentences to result["warnings"], so a caller of edit_plan reads that no report was composed in the same answer that reports the close succeeded.
  • tests/test_a_failed_close_composition_is_recorded.py — three cases: an unexpected error leaves the plan closed and a failure record naming the plan and the error; the close result says no report was composed; a healthy composition still writes its report and leaves no failure record.
