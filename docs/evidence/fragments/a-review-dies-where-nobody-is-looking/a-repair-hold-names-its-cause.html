A repair held with no lane names each rule that removed one

The defect

When the repair reflex found no candidate lane it recorded the repair for <run> has no eligible lane and nothing else. The review's hold, one branch away, named each rule that had removed a lane: the backends the routing key excludes, the backends whose declared launch is the calling harness and so cannot be started by anything, and the lane a previous attempt already dropped. Both holds draw their lanes from the same candidate list, so a reader of the repair's pointer was told the run had no lane while the configuration was the thing to change, and was given nothing that said which lever to reach for. The review half of this was repaired earlier the same day; the repair's hold kept the bare reason.

What changed

  1. reckon/crew/recovery.py: _no_review_lane_reason becomes _no_lane_reason(run_id, config, *, kind, previous_lane="") — the same clause composition, with the run the hold is about named by parameter rather than fixed. The review call site passes kind="review" and its previously dropped lane, so the review's wording is byte-for-byte unchanged; the repair call site passes kind="repair", which yields the same sentence it already wrote followed by the clauses that explain it. The lane rules are shared between the two kinds, so the clauses are composed once rather than copied.
  2. An empty clause list still composes the bare sentence, so a configuration with nothing to name reads exactly as before.
  3. New tests/test_a_repair_hold_names_its_cause.py: a fleet whose only backend launches in-harness holds the run with the harness's own declaration named; a fleet whose every spawnable lane the routing key excludes holds it with the key and each named lane; and a control in which one spawnable lane remains, which dispatches the same composition — so a hold is read as the lane drop rather than as a fixture that never composed a repair.
