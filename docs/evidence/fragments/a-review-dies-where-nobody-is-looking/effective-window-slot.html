A backend can declare the window its endpoint actually refuses above

The half that was missing

The context-fit check already read two figures from a backend's resolved settings: the window the configuration declares (usable_input_window) and the boundary the lane's own endpoint is recorded refusing above (effective_input_window). It gates on the smaller of the two and names both in a refusal, so a node sized between them is refused by reckon before a worktree exists instead of dying at the endpoint with three records and no deliverable.

Only the first of the two had a schema slot. The flight schema closes its classes (gen-pydantic --extra-fields forbid), so a configuration declaring the effective boundary was rejected at load, and the check could receive that figure only from a hand-built mapping in a test. Nothing in the repository set a value, and this node sets none — it declares the slot and carries it.

What changed

  1. reckon/schema/flight.yaml: effective_input_window is declared as a backend slot beside usable_input_window, attached to BackendConfig, with range: integer and minimum_value: 1. Its description states what it is measured from — the smallest input recorded being refused for that backend's own model, read from the lane's run streams rather than declared — why a census must be narrowed to the lane's own model, and that absence means undeclared rather than zero.
  2. reckon/_flight_schema.py and docs/_shared/flight.schema.json are regenerated by scripts/regen_flight_schema.py from that source, never edited by hand. The delta is the one field and its description in each.
  3. reckon/crew/routing.py: _agent_configuration copies effective_input_window onto the recorded worker configuration exactly as it copies usable_input_window, so the settings a run record keeps carry both figures and the reader at the context-fit check receives the boundary from a configuration rather than only from a fixture.
  4. New tests/test_effective_window_slot.py: a lane declaring the boundary below its window is written as a host layer and resolved through the dispatch path, then read through the settings copy. It asserts the resolved settings carry both figures; that a prompt estimate between them is refused by the context-fit check with the reason naming the effective figure and the declared window; that the same estimate passes when the key is absent, the changed window still gating; and that a non-integer value is refused at load with backends.<lane>.effective_input_window as the key path.

The value is a separate decision

This node declares the slot; it sets no value for any backend. No host or repository configuration file is touched here, so every lane stays exactly as it routed before — a lane that declares no effective boundary keeps gating on its declared window alone. Choosing a figure for a real lane is a separate configuration decision, and for the local lane it changes fleet routing: a boundary near 200k against the 480k currently declared would refuse nodes that dispatch today. That decision waits for the lead and does not ride along with the slot.

Two further limits are stated rather than papered over. The boundary is read from the backend mapping, so a lane whose recordings establish a boundary still needs the declaration to reach the check through a configuration; the reading is the recruiter, and the slot is what lets it be written down. And this gate measures this node's own change only — the merged result is a separately dispatched test node's job.
