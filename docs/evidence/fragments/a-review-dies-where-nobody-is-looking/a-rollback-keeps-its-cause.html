A rollback keeps its cause, and a capture blocks no registration

The defect

A dispatch publishes a live pointer, cuts its worktree, and then runs the steps that can still refuse it — the launch above all. If one of those refuses, the dispatch unwinds: it unwires peer channels, signals the worker, unlinks its own pointer, and removes the worktree it created. The unwind ran unprotected, so a failure inside it became the exception the caller read. Reproduced at base by forcing both failures at once: the launcher raised LaunchStepError: the launch step refused after the pointer was published and the removal raised WorktreeRemovalError: refusing to remove worktree …/coordinator-a/node-launch: claimed by live runs r-other; what surfaced was the removal error, with the launch failure demoted to a context the message never showed. The reader of a dispatch failure is told about the cleanup, not about the failure — which is how the run that motivated this section was diagnosed only by running the registration by hand afterwards.

The roster half is the same shape one layer down. A commit names one change, so a registration's own commit is refused while the roster holds another author's unrecorded member write. The comparison was of whole member rows, so a member row that had gained only a captured session — the resumable id a run reported, written by whatever run last reported one and not by anyone registering a member — read as a pending registration and refused the next named commit. Reproduced at base: a roster whose only uncommitted change was worker-a's captured session refused cannot commit roster registration 'worker-b': uncommitted member registration(s): worker-a; commit or discard that roster write before retrying.

What changed

  1. reckon/crew/dispatch.py: the unwind in dispatch's guard now runs inside one try. A failure in it is printed as crew: undoing run <id> failed: … and re-raised as the cause of the original — raise exc from rollback_failure — so the surfaced exception is the one that started the rollback, its message names the launch or registration step, and the rollback's own failure is still visible, both on the exception and on stderr, where a caller that prints only the original's message would otherwise lose it. The pointer-first ordering the unwind already had is unchanged: the run's own pointer is unlinked before the removal, so the removal no longer meets a claim this call published.
  2. reckon/ledger.py: _roster_obstruction compares member rows on their registration content — everything but session_id, session_model and the per-model sessions map — through the new _registration_content and _SESSION_CAPTURE_FIELDS. A row that differs only by a capture therefore obstructs nothing, exactly as a hold history or a completed-run row already did; a row that gained, lost or moved identity, harness or role still refuses the commit and still names the member.
  3. New tests/test_a_rollback_keeps_its_cause.py: the two red cases above, plus guards for behaviour already correct at base — the rollback releases its own claim so the worktree the same call created is removed and the launch error surfaces, an uncommitted new member still refuses a registration, and an existing member row whose harness moved still refuses one.
