A finished review releases its scope claim

A review run declares the reviewed run's review-records/<run>.json, so a follow-up review of the same run names that same path. When the earlier review had delivered its record but had not been promoted, its claim fenced that path, because the review's recorded worktree is reclaimed when its worker ends and the claim then reads as work nobody can inspect. The second dispatch was refused with a scope conflict and the operators ended the finished review by hand six times. A delivered review now ends itself through the same self-promotion its own sweep reaches, before the later review's scope is judged, and a reviewer that has not delivered keeps its claim.

The defect: a delivered review's claim outlives its work

Measured against the base revision a4ef64e348 with the gate copied into a scratch tree: a review run whose record parses, whose manifest reads complete and whose worker has exited still fences review-records/<reviewed run>.json, because claim_disposition reads a recorded worktree that is gone as work it cannot inspect. The follow-up review is refused scope-conflict naming that holder.

What changed

  • reckon/crew/recovery_review_dispatch.py: _release_delivered_review_claim walks the project's live pointers, keeps those whose declared paths meet this dispatch's composed record paths and whose claim still binds, and ends each through promote_review_run_itself — the promotion the review-self sweep already reaches, which files the record and deletes the pointer. It runs in _dispatch_composed_review before the scope check, never for a dry run, and the launched report carries released_reviews.
  • tests/test_a_finished_review_releases_its_scope_claim.py is the gate.

The gate

  • test_a_finished_review_releases_its_record_path — a review of the run is delivered (record parses, manifest complete, exit recorded, dead pid, reclaimed worktree). The follow-up review of the same run at a later head is dispatched: it is admitted, the finished review's pointer is gone, released_reviews names it, and the stored record's bytes are unchanged.
  • test_a_working_review_keeps_its_claim — the same shape with the review's manifest still in progress: the second dispatch is refused, the reviewed run's dispatch record carries status: refused with the claim naming the working review, and that pointer is left in place.
