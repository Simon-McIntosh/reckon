The duplicate-scalar audit states the rule the reader follows

The defect

_scalar_duplicate_findings in reckon/doccheck.py reported a duplicated plan-* scalar and told its reader that "the reader takes the last one" — in its message and its docstring — while read_state keeps the first occurrence in document order and every later copy is ignored. The writer (_set_meta) rewrites that same first line, so the audit told its reader the reverse of what both reader and writer do.

Reproduced before repair. The new test module run against base source (revision b5f74d36b, scratch tree) fails on the first copy order as assert 0.1 == 0.9 — the audit's message names the last copy (0.1) while the reader returns the first (0.9) — and its docstring arm fails on assert 'first occurrence in document order' in ...last-wins.

What changed

  1. The message now names the copy in force by quoting it, in the reader's own terms: <meta name="plan-impl"> appears 2 times ('0.9', '0.1') — the reader takes the first occurrence in document order ('0.9'), so a writer updating a later line reports success while the reader keeps that first value. "The first occurrence in document order" is the phrase the reader's own duplicate warning uses.
  2. The docstring states the same rule: read_state keeps the first occurrence and ignores every later copy — the line _set_meta rewrites — so a duplicate is the first value read while every later copy sits unread. The module comment above _SCALAR_META_PREFIX, which stated the old last-wins rule, is corrected with it.
  3. tests/test_the_duplicate_audit_states_the_reader_rule.py builds a document carrying plan-impl twice, reads it through read_state and the audit, extracts the copy the audit's message names as in force, and asserts it equals the reader's returned value — in both copy orders, so either order alone cannot satisfy the assertion trivially. A second test asserts the docstring states the first-occurrence rule and no longer claims last-wins.
