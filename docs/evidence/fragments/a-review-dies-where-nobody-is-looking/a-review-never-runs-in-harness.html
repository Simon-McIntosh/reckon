A review is never composed onto an in-harness backend

The defect

_review_lane_candidates removed lanes from review routing only by name, from review_excluded_backends. A backend declared with an in-harness launch is started by a coordinator attaching it to a task it already runs, so a review composed onto one is written as a live pointer, holds the review's write-path claim, and never executes. The exclusion therefore held only for project layers that happened to name the in-harness backend in the exclusion key: the host layer and the committed reckon layer both do, and a layer that omits the name gets the unlaunchable review back. Field occurrences: pointers reading backend: native, launch: in-harness, pid: null.

What changed

  1. reckon/crew/recovery.py: a new _review_in_harness_backends reads the launch kind from each backend's own flight declaration, and _review_lane_candidates drops those names before ordering — from the sorted rest and from the owning-run/local lanes that lead it, so the owning run's own recorded backend and the declared local backend are dropped with the rest. The guard is a property of the declaration, so a layer that never lists the name still cannot route a review onto it. Both callers of the ordering (the review reflex and the repair composer) share the drop.
  2. With no candidate left, the existing no-lane hold records awaiting-lane with its reason on the reviewed run's own pointer and creates no review run.
  3. New tests/test_a_review_never_runs_in_harness.py: the candidate list with an in-harness backend the exclusion key does not name (including as the owning run's backend); the hold when only in-harness lanes are configured; the fall-through case where the owning run recorded the in-harness lane and a spawnable lane remains; and the control that a spawnable lane still dispatches.
