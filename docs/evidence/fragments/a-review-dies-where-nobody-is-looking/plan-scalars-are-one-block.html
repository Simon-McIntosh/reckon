The lifecycle scalars are one block, and a duplicated scalar reads by a stated rule

The defect

A union-resolved merge of two landing records leaves a document carrying two copies of a plan-* scalar line, and the three lifecycle scalars — plan-impl, plan-version and plan-modified — are the lines both merge sides rewrite. Written as three independently positionable meta elements they are three independently unionisable hunks, so the merge keeps a line from each side.

The reader then resolved the duplicate by document order: read_state walked every meta and overwrote each field in turn, so the last copy won — while the writer (_set_meta) replaces only the first occurrence in place. Reader and writer named different lines, so two successful set impl calls could coexist with a promotion refusing that impl had not moved. Reproduced before repair on a document carrying plan-impl twice: 0.9 then 0.1 reads as 0.1, and the same document with the copies swapped reads as 0.9.

The first block writer carried a second defect of its own, measured in review: it anchored the block at the earliest of the three names in document order, which in the plan corpus is plan-modified — a line that sits above plan-impl. Every write then relocated the plan-impl line up to that anchor, rewriting bytes no edit asked to rewrite. The corpus write test compares a plan outside the version/modified stamps before and after an edited write, and failed on exactly that relocation for the corpus plans whose impl sits after version or modified.

What changed

  1. reckon/_plan_html.py: _set_meta_block emits several metas as one contiguous block, and write_state routes plan-impl, plan-version and plan-modified through it. The block is anchored at the FIRST pair's own tag — where plan-impl sits when it is emitted — so that line is rewritten in place and only the later names move to it; a document already carrying the three contiguously is rewritten in place and changes no placement at all. Duplicates collapse: every later occurrence is removed, so a document carrying two copies converges to one on its next write, and a document carrying none gets the block before </head>. A three-way merge of two landing records then sees one hunk for the three scalars rather than three independently unionisable lines. The plan writer in reckon/_store.py reaches the block through write_state, which both of its plan-write paths call — no separate emission site can drift from it. A plan whose records carry its impl keeps that figure out of the block, as before.
  2. Both reader paths in reckon/_plan_html.py — read_state and parse_meta — resolve a duplicated plan scalar by one stated rule: the first occurrence in document order wins; every later copy is ignored and reported as a compatibility warning. Chosen over refusal because the writer already replaces the first occurrence, so first-wins makes reader and writer name the same line and removes the disagreement at its source; refusing would instead make every read of a document carrying a duplicate fail, the same project-wide read outage this plan measures for an absent resource island. The warning keeps the duplicate visible rather than silent, and audit-doc's duplicated-plan-scalar error already reports it.
  3. tests/test_plan_scalars_are_one_block.py: a plan written through the store's write_plan carries the three lifecycle metas as adjacent elements (asserted as next-element adjacency, so a non-meta element between them fails the test); a document carrying each of the three twice resolves to the first copy in both copy orders, with the duplicated names in the warnings, through read_state and through parse_meta; and a scattered document (impl after version and modified, the corpus shape) keeps every other meta in document position through a real write while the three converge onto the block.
