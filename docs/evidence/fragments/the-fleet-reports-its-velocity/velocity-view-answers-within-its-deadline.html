The velocity view answers within its deadline

A two-week velocity read of one project replays the whole window on every call. Caching the two stages that dominate that replay takes a warm read from 576.9 s to 5.2 s, and to 16.9 s after one new commit, against a 30 s read deadline.

The measured timings

The three arms ran one after another on one cache directory against a throwaway clone of reckon under /tmp, with the module under test imported from the working tree and the repository named as data, so nothing was checked out and no commit was made in any real repository. The scratch commit that moves the head for the third arm is created with commit-tree alone, which writes one object attached to the clone's head without moving a ref.

Both warm figures are under the crew tool's 30 s read deadline (READ_DEADLINE_SECONDS in reckon/mcp.py). The window is 2026-09-15 to 2026-09-29 and the figures are single observations on a shared compute node, so they are evidence of the order of magnitude and not of a stable second decimal.

What the profile said, and what was cached

A warm cProfile run at the working tree's head put 110.3 s of 154.9 s inside report in recover_ledger_clocks, and 32.4 s in the capture step; the measurement and summary stages together accounted for the remaining twelve seconds. The recovery stage was the larger by a wide margin and was the one worth caching.

The capture stage was already cached when this node started, keyed by the repository path and its first-parent head, extending a head that has moved with only the commits after the cached one. This node added the second layer beside it:

  • The captured history — the commit census, the ledger and every committed run record, keyed by repository path and head. The ledger and the run records are additionally keyed by the blob each was read from, so a window read re-reads only the objects that changed.
  • The ledger-clock recovery — where each run that has no promote commit first appears in the ledger, keyed by repository path and the window's base commit. A head that has moved is searched only over the range the cache had already reached, and only for the run ids it had not yet placed; a cached head this one does not descend from cannot supply them, so that search restarts from the window base.

Both entries live under the user's cache directory — ~/.cache/reckon/velocity/, or XDG_CACHE_HOME, or a directory named by RECKON_VELOCITY_CACHE — outside every repository, and both are written through reckon._store.write_json_atomically. A file that is absent, unreadable, version-mismatched or shaped like nothing this module writes is rebuilt rather than trusted.

The values are unchanged

A cold read and a warm read of one window return the same mapping, compared as whole payloads rather than field by field: eighteen top-level keys, equal: True. The cache stores the capture and the recovery, not the report, so a served read recomputes the measurement and the summary from the same captured inputs a cold read does.

Three properties are asserted by tests/test_velocity_cache.py against repositories it synthesises under tmp_path, with the cache directory pointed there, so nothing is read or written outside the repository under test: a warm read equals a cold read value for value; a head that has moved is extended rather than rebuilt, counted by the number of commit-capture calls rather than timed; and a corrupt entry is rebuilt. Two further cases cover the second layer the same way — the recovery is reproduced value for value without searching again, and a corrupt recovery entry is rebuilt.

The negative control

The declared control was to make the cache rebuild from scratch whenever the head moves, and to require the extended-not-rebuilt case to fail. It failed as declared: with the injection applied, test_a_moved_head_is_extended_not_rebuilt raises assert 2 == 1 on the count of capture calls, the run exits 1, and the other two cases still pass. The test therefore detects the property it names rather than passing for any cache at all.

What this does not cover

The cache is keyed by repository path and head, so a read of a window whose base has moved — a caller naming a different start — cannot reuse a cached entry and pays the cold cost again. That is the intended boundary rather than a defect: the entry records the base it was captured from, and extending across a different base would change which commits the window contains. A caller reading a fixed rolling window, which is what the crew tool's own view does, stays inside it.
