The velocity view is served on the command line

The delivery-rate view gains its command-line surface, and the whole composition the caller sees — the window parsing, the mount resolution, the default summary and the paging of the cells — moves into one function that both surfaces call.

One composition, two surfaces

reckon.velocity.view(project, *, since, until=None, checkout_path=None, fields=None, limit=None, cursor=None) now owns everything between a caller's request and the payload they read: it parses and refuses the window, resolves the mount set, composes the default summary, and pages the project-lane-day cells. Both surfaces call it, so no derivation exists twice. crew(view="velocity") in reckon/mcp.py is now a thin call, and reckon crew velocity in reckon/cli.py calls the same function — they cannot disagree about a window because there is one window to agree about.

project is one mounted project's name, or "*" for every mounted checkout; since names the window start and is refused by name when absent or unparseable, because there is no safe default — a view that silently measured "since forever" would report a window the caller did not ask for; until names the close and defaults to now. The per-project, per-lane and per-day tables are the default answer. Every other block is served only when named in fields, and the project-lane-day cells — the largest block — are paged by limit and cursor through the same paginate helper the other crew views use. An unrecognised field is refused with the accepted set named.

The composition returns the payload both surfaces emit, so a refusal — ok: false with a detail naming the reason — reads the same on either surface. The command line raises click.ClickException carrying that detail, so a missing ok: false is a nonzero exit whose message names the parameter.

The command line

reckon crew velocity follows the crew ledger command's pattern and options: --project (required; one project, or * for every mounted one), --since, --until, --fields (repeatable and comma-separated), --limit, --cursor, and --pretty. It reads and emits through the same composition the MCP read uses, with the same meanings and the same refusals.

The measurement's progress lines — the per-project head line, the ledger clock recoveries and the positive-control line — move from stdout to stderr. The projection's narration was previously interleaved with the answer; a caller of the command line now parses the JSON on stdout without filtering the library's narration out of it. The returned data is unchanged: only the stream the narration lands on.

Tests, arms and the negative control

tests/test_crew_velocity_cli.py synthesises two git repositories under tmp_path — each with a committed run ledger at its head and a mount entry in an isolated mounts.json — exactly as tests/test_crew_velocity_view.py synthesises them, and reads nothing outside tmp_path. Three tests:

  • the default call's command-line JSON equals the read view's payload for the same window (the aggregate tables, no cells);
  • a project-lane-day cells page reached by cursor matches the read view's page for the same cursor, and differs from the first page;
  • a missing --since is refused by name, at a nonzero exit.

The parity assertions compare the parsed payloads, so the two surfaces are held to the same data rather than to the same serialisation; the command line emits its JSON with sorted keys.
