The anchored server answers before the harness snapshots it

A cold reckon-anchored-edit process took 3.0 to 7.3 s to answer initialize because importing the module pulled in the MCP framework (about 4.4 s) and the fence and store modules. The harness reads a server's status from its initialize and tools/list answers inside a two-second snapshot at session start, so a server still importing then is recorded as pending and its tools are never offered. The fix keeps the session-start answers on the standard library: a newline-delimited JSON-RPC loop in reckon/anchored_edit.py answers initialize, tools/list and tools/call directly, and the editing machinery (reckon._store, reckon._worker_fence) and the MCP framework are imported only when a call actually needs them.

A headless clive session against the worktree, with the server registered through --mcp-config --strict-mcp-config, records it in its session-start init record as {"name": "reckon-anchored-edit", "status": "connected"}, with mcp__reckon-anchored-edit__read_anchored and mcp__reckon-anchored-edit__edit_anchored in the offered tool list. A test in tests/test_anchored_edit.py runs the console-script module in a fresh interpreter, serves initialize and tools/list, and asserts none of mcp, reckon._store or reckon._worker_fence is imported before the first request; a following read_anchored call proves the check can see reckon._worker_fence appear. Restoring the eager import fails that test, which is the declared negative control.
