The context preflight can describe the agent it is sizing

What changed. reckon/agent_context.py declares one layout per agent it can describe — the root under the user's home, the entrypoint file there, the instruction filenames that agent loads, and whether a directory contributes one of them or all of them. The omp layout joins codex and claude; an agent outside the table is still refused with unsupported agent: <name>. Tests in tests/test_agent_context.py cover the omp manifest, the omp chain's two filenames per directory, an explicitly declared agent root, the unknown-agent refusal, and the unchanged codex and claude manifests.

Where the layout's facts come from. They are read from the pinned install at /home/ITER/mcintos/.local/share/omp-pilot (omp 18.13.2), not guessed from the harness's name:

  • @oh-my-pi/pi-utils/src/dirs.ts — the config root is path.join(os.homedir(), ".omp") and the agent directory is <root>/agent (profile-dependent), so the default root the preflight resolves is ~/.omp/agent.
  • @oh-my-pi/pi-coding-agent/src/discovery/builtin.ts — the user instruction file is path.join(getAgentDir(), "AGENTS.md"), and the user skill root is path.join(getAgentDir(), "skills"), which is why the default agent root is the agent directory rather than the config root.
  • src/discovery/agents-md.ts and src/discovery/claude-md.ts — both register a standalone walker over the same ancestor chain, so a directory holding AGENTS.md and CLAUDE.md contributes both. The codex layout takes the first candidate that exists; the omp layout takes every one.

What the measure does now, and what it used to do. The probe calls the two functions dispatch calls for the context step (_context_agent, then _standing_context_input) with the mapping a resolved omp-local backend hands them — a cli launch whose command names the omp binary:

The same probe against the base revision's module stops at the refusal ValueError: unsupported agent: omp, which is the failure the node exists to remove; the head revision returns the standing-context figure. The full crew dispatch --dry-run cannot be driven from inside this write fence — it stops earlier, opening a watcher lock under ~/.config/reckon/crew/watch that the fence mounts read-only, a failure that predates and is unrelated to the context step. The probe is the narrowest command that reaches the step in question.

Why the codex and claude arms are a test and not a promise. The two layouts share every code path this change touched, so the risk is not that they break loudly but that a field is added, removed or renamed for all three and nobody notices. The test therefore spells out the whole manifest for both agents — every key, the byte and sha figures, the sorted input-path set, the budget source, the skill roots — with the paths derived from the fixture at assertion time rather than frozen. Measured before and after on one fixture, base and head produce byte-identical JSON for both agents.

Left open

The omp project skill root is not modelled. The manifest's skills.metadata_roots lists <dir>/.agents/skills for every agent, while omp's builtin provider scans <dir>/.omp/skills (discovery/builtin.ts). The standing-context figure does not read skill roots, so the estimate is right; the metadata field is inaccurate for omp and is the coordinator's call.

@-import expansion is still not counted. A repository CLAUDE.md of the loader form here is 14 bytes and imports AGENTS.md and ~/.agents/AGENTS.md, which omp expands at load. The measure charges the loader at its own size, as it already did for claude; the canonical policy is counted once, separately.

The fence still seeds no omp agent store. _HARNESS_HOME relocates HOME, so a run's agent directory is <run home>/.omp/agent, and the host flight entry omp-local must declare the models.yml it needs there. Without one the preflight's entrypoint is absent for a fenced run, which reports agent_entrypoint_missing rather than sizing it — the same shape as the codex and claude layouts on an operator home that carries no entrypoint.
