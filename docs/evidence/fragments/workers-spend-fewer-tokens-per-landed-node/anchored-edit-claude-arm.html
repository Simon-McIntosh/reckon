A worker records whether anchored editing actually ran

The per-backend anchored_edit flight key defaults off. A fresh, fenced Claude-shaped launch with resolved flight configuration and no existing run settings registers reckon-anchored-edit in its own .claude.json. The server receives one repeated --root argument per declared run write root. Its command uses the launching Python interpreter with -m reckon.anchored_edit, so server startup does not depend on the worker's search path or a separately installed console script. A smoke test executes the registered command.

The seeded settings allow mcp__reckon-anchored-edit__read_anchored and mcp__reckon-anchored-edit__edit_anchored, preserve the operator's existing hooks and servers, and leave the operator's source files untouched. Only successful registration enables the argv restriction --disallowedTools Edit MultiEdit. The built-in Write remains available.

Both claude and clive use the same launch rule.

The actual result and its reason travel through LaunchPlan, the supervisor specification beside fenced, and the spawned-worker record. The supervisor publishes them to the current attempt's run pointer, which supplies the run-store record. An older attempt cannot replace the newer attempt's result. A treated run that resumes records false with resumed, even though its prior seeded settings remain on disk.

The authoritative reckon/schema/flight.yaml declares the key. The repository's existing generator regenerated both reckon/_flight_schema.py and docs/_shared/flight.schema.json in one invocation.

Run logs retain their literal commands and terminal exit statuses.
