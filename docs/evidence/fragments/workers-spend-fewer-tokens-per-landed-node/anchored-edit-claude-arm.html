A worker records whether anchored editing actually ran

The per-backend anchored_edit flight key defaults off. A fresh, fenced Claude-shaped launch with resolved flight configuration and no existing run settings registers reckon-anchored-edit in its own .claude.json. The server receives one repeated --root argument per writable delivery root and includes the detached worktree that the fence grants separately. Its command uses the launching Python interpreter with -m reckon.anchored_edit, so server startup does not depend on the worker's search path or a separately installed console script. A smoke test executes the registered command.

The seeded settings allow mcp__reckon-anchored-edit__read_anchored and mcp__reckon-anchored-edit__edit_anchored, preserve the operator's existing hooks and servers, and leave the operator's source files untouched. Only successful registration enables the argv restriction --disallowedTools Edit MultiEdit. The built-in Write remains available.

The server can edit the worktree it was launched to change

The initial fixture supplied the worktree directly as a delivery root. Production does not: _fence_write_roots omits declarations inside the worktree because fence_argv binds that tree separately. The initial 71-test arm therefore missed a treatment worker whose built-in edits were disabled while its server refused every normal source path.

The server roots now pass the delivery roots and worktree through fence_writable_roots, which also withholds the sealed shared stores. The fixture calls production _fence_write_roots and asserts that no returned root contains the worktree. Its temporary root is a disjoint scratch directory, so an ambient temporary ancestor cannot mask an omitted worktree grant.
