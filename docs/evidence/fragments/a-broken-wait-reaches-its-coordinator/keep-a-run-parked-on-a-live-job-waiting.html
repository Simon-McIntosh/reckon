A run parked on a live scheduler job keeps waiting

A wait over a long scheduler job answers the same state on every sweep: the run re-parked with ["sacct","-n","-X","-P","-j","1307334","-o","State"] reported RUNNING, which is exactly what a healthy wait looks like. The stillness bound therefore cannot separate a working wait from a dead producer on its own, and the scheduler is the only witness that can. But the classifier asked the scheduler only when the probe's own head was squeue, through a job-id reader of its own. Reproduced at the base revision, with the scheduler reporting the job present: both the sacct vector and the incident python3 -c code string resolved no job id, the scheduler was never asked, and both runs read producer-gone with the probe stuck at RUNNING.

The classifier's own reader is deleted and both call sites take the job id from the shared probe reader, which already sees through a sacct vector and through an interpreter's code string. Every shape a wait is written in now names its job, so a named job the scheduler still lists keeps the run waiting however long its value stands still, and a wait naming no job asks the scheduler nothing. The scheduler query itself is unchanged: it is squeue -h -j <id>, and an answer that cannot be read still leaves the job's liveness unknown rather than absent.

Measure: the new gate passes 4 of 4. The base arm over the 77 test files importing reckon.crew.recovery_classification gave 663 passed, 1 failed; the head arm gave 667 passed, 1 failed. The four added passing cases are this node's, and the single failure id is the same in both arms — test_crew_obligations.py::test_obligations_reads_scoring_without_observing_or_dispatching, which reports two git-object-answers.json memo files in a directory a pure read is asserted not to touch — so no added failure id against the base revision.

Two negative controls, each applied to the committed source and reverted, the worktree verified identical to the commit afterwards. Restoring an squeue-only job-id reader at both call sites makes the first and third cases producer-gone: 2 failed, 2 passed, EXIT=1. Skipping the scheduler query, reading a named job as alive, makes the second case keep waiting: 3 failed, 1 passed, EXIT=1.
