A launch records its node's role

The launch's recorded treatment did not carry the role at all. WorkerBehaviour.dimensions, which is what a launch plan records and what a reader compares, named the lane, the inbox, the allowlist, the fence roots, the review duty and the landing route — and left the role out. Every review launch therefore read from its own record as an implement run: it owed a review of its own and declared the implement landing route, and no caller could have corrected that by passing a role because there was nowhere for it to land.

Two changes close it. The role is a recorded dimension. And the three routes that compose a worker launch pass the role the node was dispatched with: _launch_dispatch in reckon/crew/dispatching/launch.py reads node.role, which also serves the queued admission launch because _launch_queued hands its rebuilt node to the same dispatch; resume_plan and change_lane in reckon/crew/dispatch_sessions.py read it through _pointer_role — the read the recovery module already owns for a recorded run, which answers from the pointer root and the recorded node — and fall back to IMPLEMENT_ROLE. A run carries the role it was dispatched with, so a later configuration change cannot restate what an earlier attempt owed.

Each route is driven through its real door and the treatment read off the composed launch. A direct dispatch of a review node records role: review, review_duty: false and reviewed-under-its-lane. A queued request carrying a review node, launched by one admission pass, records the same. A stopped run whose record names the review role, resumed through resume_plan, records the same. An implement node on each of the three routes records role: implement, review_duty: true and promoted-under-its-lane. A third role on each route — investigate, which is neither of the two the plan names — records role: investigate, review_duty: false and promoted-under-its-lane.

The implement cases pin the contract but cannot see the wiring: an implement node records the same treatment whether or not the call site passes the role, because the default describes it. The investigate cases are the ones that discriminate, since a defaulted role records implement where they require investigate.

The declared control holds. With the role left at the launch call site's default — the behaviour_role argument removed from the dispatch and session call sites, the recorded dimension left in place — the node's file reads 6 failed and 3 passed, exit 1 (wlsr-negative-control.log). The six failures are the three review cases and the three investigate cases, each reporting a launch that recorded the implement default; the three implement cases pass, because the default describes them correctly and that is exactly why they cannot carry the control on their own.
