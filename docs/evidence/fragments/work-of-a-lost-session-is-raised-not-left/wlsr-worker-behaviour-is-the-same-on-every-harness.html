One lane, several harnesses, one treatment for the worker launched on it

What changed. A worker's treatment is now composed in one place, reckon/crew/worker_behaviour.py, and carried on the launch plan as facts a reader can compare: the lane identity taken from the lane document, the inbox directory inside the run directory, the MCP server allowlist, the fence's write roots and protections, the review duty taken from the role, and the landing route. The four differences the harness interface forces — launch argv, harness-home layout, stream format, model identifier — are the only ones excluded from that comparison.

The defect the record named, repaired. The inbox hook was seeded into a run home only for the dialect whose name is claude. A claude-shaped wrapper was therefore given no run home at all: no inbox hook, no MCP allowlist and no exclusion list, while its harness read the sealed operator home. That is the local lane’s own case, because the configured local backend moved to a wrapper on 20 November. A dialect now declares the interface it speaks — home_interface, settings_file, mcp_config_file, mcp_refusal_list — and the seeding and the behaviour facts read those attributes instead of a name, so a wrapper and the harness it wraps are seeded identically. The shipped home-file defaults resolve through the same interface, so a wrapper inherits the instruction files and settings group its harness reads rather than starting empty.

Why the second control mutates the drainer. The gate-hold predicate delegates to drainer_serves_the_local_lane, which is the one reader that compares the two backends’ lane documents; the case starts the drainer under the name the configuration has moved away from, so a name-only comparison admits nothing and both parametrisations fail. A first attempt mutated the wrapper instead and stayed green, which showed the wrapper restated a rule the drainer already owns — that duplication is removed.

Not in this node

Delivery to a harness that declares neither a settings group nor an argv override is recorded as file-only: the message is written into the run directory’s inbox and read on the next resume. Giving such a harness a live delivery trigger needs that harness’s own hook interface, which this node cannot verify and does not invent.
