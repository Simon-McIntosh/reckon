A wait that cannot resolve is removed

A request stored awaiting-upstream was one condition in the live view. A wait on an upstream that had been superseded hours earlier read the same as a wait on work that was landing, and neither the request's owner nor a reader of the fleet could tell them apart. The admission pass now classes each waiting request from the per-ref states it already resolves, in reckon/crew/stranded_wait.py, and stamps the answer on the request as wait_class beside the free-text wait_detail the live view already shows.

ClassWhat it meansWhat the pass does
progressingAn upstream section has a live run or a queued request.Nothing, however long the wait has stood.
idleEvery unlanded upstream is still declared open and none has a run or a request.After stranded_wait.report_after_hours (72 by default) the wait appears once in its owner's obligations, naming the sections nobody is building.
strandedAn upstream it names can never land: the plan is absent, is closed, superseded or abandoned with the section not done, or no longer carries the section.The request is retired on the pass that finds it, with a discard record naming the upstream and why, and its owner's obligations carry the retirement once.

The class is a value on the wait state the readiness module computes rather than a second resolution: resolve_waits reads it from the same per-ref states the request's phase comes from, so a request can never be advancing and stranded at once. The class adds one live-view field in reckon/crew/query.py and one flight setting in reckon/_flight_schema.py, with the account a reader shows derived from the class rather than parsed back out of the refs.

Three rules bound what the pass may do. A wait is never removed for its age alone; only the stranded class is retired, and an idle wait is reported rather than touched. A request a coordinator holds with crew queue hold keeps its hold whatever its class, because the hold is a decision about the work rather than a reading of the upstream. A plan that exists but does not parse is withheld rather than stranded, because retiring work on the strength of a failed read would discard a request a working read would have released.

A request naming a section its plan does not carry cannot be queued at all, since the queue refuses a wait on a missing section; the case is exercised the way it arises in practice, by dropping the declaration from a plan the request already waits on.

One defect was found and fixed while proving the retirement path. The pass marked its round changed when it retired a request, which sent a second round over a pointer that no longer existed; the retired phase is now carried on the pass's own copy so a later round skips it, and a second pass over the same repository is asserted to rebuild nothing and to record no second retirement.
