A session job names its session

The owner comment the scheduler shim adds to a submitted job was keyed on RECKON_RUN_ID alone, so a job a coordinator submits for itself, with no worker's run, reached squeue with no comment naming anyone. owner_comment in reckon/nested_launch.py now names the session when the run is absent, names both when both exist, and still returns nothing when neither is set. The dispatch side is proven rather than assumed: the test composes a launch through _backends.launch_plan and dispatch_launch._worker_runtime_plan, taking the session from a run record as the launch does, asserts RECKON_SESSION_ID reaches the worker's environment, and feeds that environment through the shim into a stand-in scheduler whose recorded argv carries the session.

A script submitted as sbatch nightly.sh that declares its own #SBATCH --comment= directive lost that text once the shim added a command-line comment, because a scheduler gives the command line precedence over the script's directives. _script_comment lifts the script's comment out of the kept directives and _with_comment_text merges it into the command line, so the caller's words and the owner are both handed to the scheduler. A script whose directive carries no comment is left as it was.

The fleet allocation readers in reckon/crew/fleet_node.py compared a scheduler comment exactly, so an allocation whose comment gained the owner suffix stopped being found and its fleet name read as the whole trailing text. _fleet_token reads the fleet identity as the first word of the comment, which the catch-all, earlier-fleet and named-fleet readers all use. An unrelated comment still reads as no fleet's.
