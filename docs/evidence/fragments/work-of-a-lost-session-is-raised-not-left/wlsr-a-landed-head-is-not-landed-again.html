A landed head is not landed again

A delivered run whose reviewed head the primary branch already carries used to be measured, gated and handed to promotion like any other. The landing pass now asks first, in _primary_carries_the_delivery beside the delivery loop in reckon/crew/queue_landing.py, and settles such a run through the integrated release path: the pointer is retired, its workspace released, and no promotion request or gate replay is spent on work the branch already contains.

The condition is narrower than ancestry. A head that is the branch's own tip is its own candidate, not a delivery merged into history; a head that sits behind the tip only because the run added nothing has no delivery to carry, and no change markers to check. Both keep the ordinary path. So does a head whose ancestry or changed paths cannot be read, which is reported as unverified rather than settled on a guess. The check itself is the merge reader's: merge.change_markers from the run's recorded base, then merge.surviving_change_refusals against the primary tip, so a path that was added, deleted, modified or replaced is judged the same way the merge path judges it.

A head that is carried while a path it changed has since left the branch is not settled. It is recorded as a refusal naming the surviving-change refusal, and it appears in the pass's obligations so a coordinator sees it, with the pointer held so the run stays visible.

The second half of the node is in reckon/crew/promotion_gate.py. A replay that exits non-zero and writes no log used to publish that exit status as the run's integrated verdict. It now writes the log first, and when there is no log to open it records integrated_verdict: not-run beside a replay_failure naming the exit status, leaving the run's base verdict untouched and the pass not ok. A replay that exits zero with no log still passes; the absence of evidence is charged to the replay only when the replay failed.
