Delivery reads host for a host-run follower

A dispatch read delivery as monitor for a session the calling host had already attached. It now reads the host's own census of running children and reports host with an empty arming line when a child for the project and session carries the live registration's pid.

The gap

session_delivery was set to "host" only on the branch that asked the session host to attach a follower at that moment (_ask_session_host_for_follower). A session attached earlier -- by a prior dispatch, or by the plugin monitor at session start -- short-circuited that branch, so its payload carried delivery: "monitor" and an arming line, offering a second Monitor watch for a follower the host already consumes.

What changed

  • reckon/crew/dispatch.py: _session_host_record_path resolves the calling Claude session's census record under the config home's crew/session-hosts directory, named for the Claude pid and its kernel start tick, with the filename suffix read from the host module that writes it. _session_host_runs_follower reports whether the host names the pair with the pid the live registration holds.
  • The dispatch admission block reports session_delivery = "host" when the session is already attached and that check is true, beside the existing ask-then-upgrade path. A session attached by a foreign follower still reads monitor, because the pid does not match the host's child.

The gate

tests/test_dispatch_session_host.py adds two cases beside the existing two.

  • test_dispatch_reads_host_for_an_already_attached_host_follower — the host census names the pair with the live registration's pid; the payload's delivery is host and its arming_line is empty.
  • test_dispatch_reads_monitor_for_a_follower_the_host_did_not_start — the census names the pair but with a different process's pid, so delivery is monitor and the arming line is kept.
