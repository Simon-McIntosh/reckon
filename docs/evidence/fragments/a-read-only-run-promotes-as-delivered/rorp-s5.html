What landed

A read of one plan's run records decoded every run document in the store and threw away the rows that belonged to other plans. Against the committed store that is 3,124 runs across 133 plans, so the answer to a question about one plan cost the whole ledger: 7.3 to 14.8 seconds per read in a fresh process, and more as the store grows.

_index_payload in reckon/ledger.py is the single owner of decoding and filtering, and it already pushed the activity bound into its own SQL query. The plan filter now goes there too: records and aggregate_rows carry a plan column with an index on each, a row's plan is stored as the empty string rather than null so one equality answers the question, and the added predicate narrows both the aggregate and the per-run document queries. _RUN_INDEX_VERSION moves to 6, so a store's index rebuilds once with the new column. The selection reaches the query through load, _indexed_data, _index_payload and _payload_slot, whose region cache is now keyed by plan as well: two plans' reads in one process no longer share a decoded region.

The cold path, which reads the run files without an index, applies _row_plan at the same moment it applies the activity bound, so both paths select, and neither decodes a document it then discards. The rows returned are the ones an unfiltered read returns filtered afterwards, in the same order — the filter moved the cost and not the answer.

The figures path (read_records(with_figures=True)) still reads the whole store: reckon/crew/summary.py counts width_at_start over every plan's runs, so that read genuinely needs them all. The affected read is ledger.runs(project, root, plan=...), which is the one an orchestrator makes to ask about one plan's history.

The untimed read that builds each revision's index took 7.130 s at base and 30.683 s at the change — that one-time rebuild is the new column being written, and it is paid once per store rather than once per read.
