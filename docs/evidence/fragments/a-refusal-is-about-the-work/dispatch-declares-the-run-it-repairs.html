§4 — A dispatch declares the promoted run it repairs

One node's evidence: the impl-move exemption a corrective run already carried now has a name a fresh dispatch can declare, so a repair of an already-promoted run lands without a hand-written operator flag.

Outcome

reckon crew dispatch gains --repairs RUN_ID. The named run must already be promoted in this project's own ledger; a dispatch that names a run which is unknown, still in flight, or owned by another project is refused before launch, and the refusal says which of the three it is. A run dispatched with the declaration records repairs: RUN_ID on its run record beside attempt_kind, and reckon/crew/promotion.py reads that field through the same corrective-attempt check it already uses for the resume and redispatch kinds: the promotion records impl_move as exempt, names the repaired run in the reason, and needs no --no-impl-change.

Change

The corrective-attempt exemption in _require_impl_moved read its marker from the record's attempt_kind alone, so only a run that continued an earlier one — a resume or a redispatch — could inherit the plan movement its predecessor produced. A node dispatched fresh to repair an already-promoted run carried no such marker, its own landing moved nothing, and the promotion was refused for an unmoved impl unless the coordinator recorded a reason by hand. This node names that gap.

reckon/crew/dispatch.py gains _require_repairs_target, which refuses a --repairs target that is not a promoted run of the project's ledger. It reads the project's ledger first; a target absent there but present as a live pointer is distinguished from one that is nowhere — the live pointer's own project separates a foreign run from one still in flight, so each refusal names which of the three the target is. It runs from plan_dispatch, so both the launching path and the dry run reach it before any run is created. The declaration lands on the record beside attempt_kind.

reckon/crew/promotion.py extends the existing corrective check rather than adding a second one: after the attempt_kind branch, a record carrying repairs takes the same exempt verdict, with the reason spelling the chain corrective-run:repairs:RUN_ID. reckon/cli.py adds the --repairs option and forwards it to both plan_dispatch and dispatch.

Evidence

  • The declaration lands, and the landing is exempt. The new file's test_a_repairs_dispatch_records_the_field_and_promotes_exempt promotes a predecessor whose landing advanced the plan's impl (verdict: moved), dispatches a fresh node with that predecessor named, and asserts both that the returned record and the written pointer carry repairs: predecessor and that the fresh node's own promotion records impl_move.verdict == "exempt" with reason corrective-run:repairs:<predecessor>. The plan genuinely did not move a second time under the repair, so removing the exemption refuses this run — which the negative control shows.
  • Unknown, in-flight and foreign targets are each refused before launch. Three cases assert the reason text: an id in no ledger and no pointer refuses with "names no run in project"; a live pointer refuses with "is not yet promoted"; a live pointer owned by another project refuses with "belongs to project" and names that project. None creates a run.
  • A dispatch with no declaration is unchanged. test_a_dispatch_with_no_repairs_is_still_refused_when_the_impl_did_not_move promotes a run whose plan impl did not move and is refused, naming --no-impl-change — the behaviour the declaration replaces for a repair, and which stays in force for everything else.
  • The reuse holds. _require_impl_moved carries one corrective branch after its attempt_kind test rather than a parallel one, and the new test's exempt case reaches it through crew.complete, the same entry the attempt_kind forms use.
