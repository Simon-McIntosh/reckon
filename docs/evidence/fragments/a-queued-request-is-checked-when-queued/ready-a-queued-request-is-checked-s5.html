A second launch of a run never releases the tree its first launch holds

A worktree path is named for its session and node, not for its run, so a duplicate launch of one run reaches the tree the launch already running is using. Re-verified at base 078f7c800cf487e36209d42418e0e77863abb17d: the launch-side claim view is present, its four cases hold, a pointer on a host this one cannot probe stays a claim, and the declared mutation turns two cases red with the tree released into _trash. The guard as found

Two readers decide a launch's fate, and both read the launch-side view rather than the wide one:

  • _own_pointer_yields_its_tree (reckon/crew/routing.py, line 1149) yields a same-run pointer's tree only when its phase is in WAITING_REQUEST_PHASES (queued, awaiting-upstream, blocked-upstream, held) or when local_liveness proves the worker gone on this host. A verdict this host cannot prove — a run launched on another node over the shared crew home — is no evidence either way and stays a claim.
  • _launch_pointer_worktrees (line 1167) reads every live pointer exactly as the wide view _live_pointer_worktrees does, except that the launching run's own pointer is kept unless that predicate yields it.
  • The claims fed to _inspect_workspace by _launch_tree_verdict (line 2330) and the guard in _remove_worktree (line 2522) read that view. gc, _save_and_release_worktree and promotion release keep the wide view unchanged, and no path naming changed, so _launch_worktree_path (line 2303) and gc.py's confinement are untouched.
