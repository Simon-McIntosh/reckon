A second launch of a run never releases the tree its first launch holds

A worktree path is named for its session and node, not for its run, so a duplicate launch of one run reaches the tree the first launch is using. Re-verified at base 364e934266454a84533877bd02b9a916463893e2: the launch-side claim view is present, its four cases hold, and the declared mutation turns it red. This node needed no product change, so it carries the verification the section was reopened for rather than a second implementation of a working guard.

The guard as found

The defect still reproduces when the guard is disabled, which is what the negative control below shows. With it in place, the two readers that decide a launch's fate judge a same-run pointer as a claim:

  • _own_pointer_yields_its_tree (reckon/crew/routing.py) yields the tree only when the pointer's phase is in WAITING_REQUEST_PHASES (queued, awaiting-upstream, blocked-upstream, held) or local_liveness proves the worker dead on this host; an unpoven verdict on another host stays a claim.
  • _launch_pointer_worktrees reads every live pointer as _live_pointer_worktrees does, keeping the launching run's own pointer unless that predicate yields it.
  • The claims fed to _inspect_workspace by _launch_tree_verdict and the guard in _remove_worktree read that view; gc, _save_and_release_worktree and promotion release keep the wide view, and no path naming changed.
