A second launch of a run never releases the tree its first launch holds

A worktree path is named for its session and node, not for its run, so a duplicate launch of one run reaches the tree the first launch is using. The wide live-claim view drops the launching run's own pointer, so the duplicate read that tree as a disposable leftover and released it into _trash under a running worker. A launch-side view keeps a same-run pointer as a claim unless its phase still waits (WAITING_REQUEST_PHASES) or its worker is provably gone on this host, and it is read only where a launch decides a tree's fate.

What changed

  • reckon/crew/routing.py: new _launch_pointer_worktrees beside _live_pointer_worktrees. It reads every live pointer as that view does, except a pointer whose run is LAUNCH_RUN_ID: that pointer is skipped only when _own_pointer_yields_its_tree says a launch may replace its tree — the phase is in WAITING_REQUEST_PHASES, or local_liveness proves a dead worker on this host. An unpoven verdict (a pointer launched elsewhere on a shared crew home) stays a claim.
  • The two sites that decide a launch's fate read the new view: the claims passed to _inspect_workspace by _launch_tree_verdict, and the guard in _remove_worktree. gc, _save_and_release_worktree and promotion release keep _live_pointer_worktrees, and no path naming changed.
  • tests/test_a_second_launch_keeps_a_live_worktree.py (new): in a synthesised repository and crew home it cuts a tree with _create_worktree, publishes a live pointer for run X naming it, and relaunches at the same session and node under LAUNCH_RUN_ID = X. Four cases: working refuses naming the run and leaves the same inode with an empty _trash; starting refuses the same way; queued lets the launch proceed to a new tree; working with a dead local pid lets the retry replace the tree.
