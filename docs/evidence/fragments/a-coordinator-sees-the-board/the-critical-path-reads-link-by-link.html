Each link of the critical path says what it is doing and what holds it

What changed. build_roadmap's critical_path carried a list of section refs and nothing about them, so a coordinator holding the path still had to look each ref up to learn whether the head was being worked on, waiting on a peer or standing behind a gate. Each link now also carries a row: ref, plan, section, its primary_state, and holds — every open gate and every unmet wait on that link.

The primary state is the first that applies, in the plan's order: in flight (with the run_id on the section), ready-idle (with the plan's coordinator, read from the ledger by crew.plan_coordinator.resolve_plan_coordinators and never re-derived here), gated (with the gate id). A link none of those describes reports waiting with the ref it waits on, and reports no primary state when no hold explains it, rather than a fifth state invented in the roadmap.

The rows are in path order, so the head — the deepest prerequisite the chain forces — is first. critical_path.head names it and critical_path.head_note says it in words, naming the coordinator when the head is idle. critical_path.sections still holds the ordered refs it always did: ready_set_view, project_brief, crew.queue_order and graph_target read that list as strings, and changing its shape would have meant editing four modules outside this node's scope and silently clearing the ready-set's critical_path flag. No view and no refusal family is added; the read is one call on the roadmap row the path already had.
