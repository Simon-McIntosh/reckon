A resumed worker is not ended as a delivery it has not made

A run resumed after it wrote a done manifest keeps that manifest path. The launch supervisor ends a worker whose manifest reads a done word once it has rested, so the new worker's first edit to any other field made the stale delivery look fresh and the worker was ended as delivered.

Change

  • One function in reckon/crew/resumption.py, _reset_delivered_manifest_status, sets a manifest's status word to in-progress when it reads a status in the supervisor's done set (complete, failed), keeping the delivered text beside it under manifest.md.attempt-<n>.asdelivered so a status repair's manifest.md.asdelivered is never overwritten. A status outside the done set is left as it is.
  • Two launch functions call it: _resume and change_lane. The CLI crew resume and the MCP resume action call _resume instead of copying its launch steps, so the reset has two callers rather than four. Their exit codes and payloads are unchanged.

Measure

tests/test_a_resumed_worker_is_not_ended_as_delivered.py passes (6 passed), logged under the run directory with the literal command, its revision and an EXIT=0 line.

  • A complete manifest resumed through crew resume, the stub editing a non-status field, is not signalled within the shortened quiet period plus grace; the manifest reads in-progress and the attempt-named copy holds the delivered text.
  • The same holds through _resume and through change_lane.
  • A resumed stub that writes complete is still ended as delivered.
  • A blocked manifest keeps its word and is not kept as a delivery.
  • The live view classifies the working stub as running.

The declared negative control — remove the status reset — is executed and logged under the run directory: the first case fails with the runner's FAILED line and a non-zero EXIT.
