A resume never launches beside a live attempt

The launch of a resumption is not atomic with the check that licenses it. resume_plan reads the pointer, composes the plan and returns; the caller spawns the process; only then does record_resumption fold the new attempt onto the pointer. A second door that reads the pointer inside that window sees a run whose recorded process has ended and starts a worker beside one already starting — one run, two writers. The section's own incident is this window met twice: run r-20261012T042612803730-proto-read-route was auto-resumed by the wait sweep at 10:07:30Z, and a coordinator's resume at 10:08:49Z launched a second attempt beside it; the backend refused the second worker, the pointer recorded that refusal as the attempt's exit, and the run read as ended while the first worker was still working.

The pointer now carries a resume_launch_in_flight mark while a launch is between its check and its recorded attempt, and both doors refuse against it — the same refusal the launcher itself gives, so the dry-run prediction and the launch stay word for word alike. The mark holds the launcher's own pid, so a launcher that ends without recording leaves a mark no live process answers for and the refusal cannot outlive the attempt. An advice a refused resume carried is kept beside the run and delivered into the next resume's prompt, because the caller that composed it is gone by the time the launch it lost to records anything.

The same window has a second half, and it needed a second fix. A launch that meets a live attempt used to publish its own attempt marker and retire the canonical worker.json and exit.json before the backend was ever asked to start — reporting a working run as halted and unlinking the only record of its worker. The launch now reads the incumbent's liveness first, from the run's own worker record as well as the pointer, and is refused before the marker or either record is written. The live reproduction is nova's r-20261014T044136316062-forward-solve-options, measured 2026-10-14T08:18Z: one wait-lift started two supervisors 1 s apart (1280598, 1280599), their launches came 25 s later one pid apart, the loser (1282902) died on the backend's own active-writer refusal with its failure recorded as attempt-8-exit.json, and the pointer then named the dead supervisor at attempt 9 — so the run read halted while the winning worker kept working. Read-only inspection only; that run directory was not modified.

The gate is the importer population of reckon/crew/resumption.py, reckon/crew/dispatch_sessions.py and reckon/crew/dispatch_launch.py, and the cases added here cover the four the section names: a resume during a launch in flight starts nothing, names the live attempt and its process, and keeps its advice; the next resume carries that kept advice; a sweep over a run whose attempt is alive resumes nothing; and a launch meeting a live attempt leaves the pointer's phase and pids, the worker record and the classification unchanged. The negative control reapplies the named cause — the marker's reader answers nothing — and the guarded case fails.
