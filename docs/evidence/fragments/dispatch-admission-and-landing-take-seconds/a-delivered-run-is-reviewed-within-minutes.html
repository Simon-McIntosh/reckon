Two intervals, not one: the request a crew makes and the launch it waits for

The defect. A delivered run cannot land until it is reviewed, and the request that starts the review is made by the crew. The stage receipts already dated each handoff, but nothing read them as the two intervals the measure turns on: the delivery to the request, and the request to the launch. Read as one figure, a late request and a slow launch are indistinguishable, and a run whose request was never made at all appears only as a review that is missing.

What landed. reckon/crew/recovery_review_dispatch.py reads the first instant of each of the four stages from the run's own receipts (review_stage_instants) and reports them as review_request_census: one row per delivered run with request_lag_seconds and launch_lag_seconds kept apart, the median and 90th percentile of each, and an obligations list holding every delivered run with no request after REVIEW_REQUEST_DEADLINE_SECONDS (600 s), each carrying the reason its own record gives — the reflex's recorded dispatch, the refusal its dispatch rule would return, or the session no armed follower serves. reckon/crew/resumption.py runs that reading on the pass that makes the requests and carries the obligations on the sweep's report, so a sweep that could not request a review says which run and why. The obligation is also written into the review pass's owed rows, which is the record the station keeps per session and renders as a duty: the reason a coordinator is shown is the reason the census found, not a second account of it. The percentile the census quotes is the run-time profile's own rule, and a request receipted before the delivery it belongs to is counted with the unrecorded requests rather than quoted as a zero-length interval or mistaken for a request nobody made.

The harness. tests/test_a_delivered_run_is_reviewed_within_minutes.py builds the fixture repository and a temporary crew home, delivers a scoring run by the watcher's own writer, and holds a stand-in station tick in its refresh stage while the follower's sweep requests the review. It asserts the sweep's own report names the run as dispatched, the review's pointer exists, and the receipt's request instant is no later than 120 s after the delivery's — then reads the same instants back through the census, records the review's admission and start the way the fleet's own writer does, and asserts the request-to-launch interval against those receipts, so a stage the census stops mapping leaves that interval unknown and reddens the case. The second case withholds the request's precondition — its session has no armed follower — and reads no obligation at 599 s and one at 601 s whose reason names that session. A third case reads a recorded refusal as the reason rather than as no dispatch at all. The census itself is measured against a two-run sample of known size, so the median names the near lag and the 90th percentile the far one; an out-of-order receipt pair, a reviewer whose id carries no prefix but whose pointer says it is one, the review's inherited priority, and the duty row the obligation reaches are each a case of their own.

Gate. The node's ten tests pass at the head (the head arm's log reads 68 passed in 47.3 s at f4a8ef887b, its command named on the manifest's after_suite line). The armed suite arms — the node's test file beside the two importer files at the head, and the two importer files alone at the base revision — are recorded in the manifest's after_suite and baseline_suite fields with their own commands, revisions and logs; both report 0 failures.

Negative control. With the sweep's review pass made to wait for the tick — the pass gated on a marker the held tick never writes — the in-window case fails (FAILED tests/test_a_delivered_run_is_reviewed_within_minutes.py::test_a_delivered_run_is_requested_inside_the_window_while_a_tick_is_held, 3 failed, 7 passed, EXIT=1), beside the case that reads the inherited priority and the case that follows the obligation to the duty row, both of which depend on the same pass. So the cases measure the request's independence rather than restating it. The log is named on the manifest's negative_control_log line.

The live census. Read over the live crew home on 2026-11-17 at 21:45Z: 39 run receipt files, 31 with a delivery recorded, 23 of them not themselves reviews. Of those 23, 5 carry a review request's instant and 9 carry a recorded dispatch with no instant, because the receipts landed today and older dispatches predate them: the recorded fact without the clock reading is reported apart, never as an obligation. The request lag's median is 96.7 s; its 90th percentile is 917.1 s over five samples, which is the largest member of a sample too small to establish a fleet percentile — the receipt population is hours old. The launch lag is reported apart from it: median 124.1 s, 90th 147.5 s over four launches, which is the split this section exists to expose — the requests that were made were made inside the window, and the launches came after it. 9 delivered runs owe an obligation, each with its reason: a live pointer that is gone, an attempt whose resume has not delivered yet, and a review the resume superseded. What is not here. The request's priority is inherited from the run it reviews by a-session-spends-a-priority-budget §3, which owns the ordering the inheritance reaches; this node's census reads the receipts it will write and does not restate the rule.
