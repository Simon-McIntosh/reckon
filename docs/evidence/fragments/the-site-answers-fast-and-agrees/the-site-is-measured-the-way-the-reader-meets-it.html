The miss the home view owns is §17's. The shell's scripts are fetched on every load because /_ui/*.js and /_runtime/*.js answer through _send with Cache-Control: no-store, no ETag and no gzip, so the home view transfers 1.17 MB cold and 897 KB warm against the 500 KB the gate allows. Every other surface is far inside its budget, and each of those is served through a path §14 already revisioned; the home view's load is the shell scripts §17 owns. (An earlier pass of this record named §6; the surface was measured correctly then and the section that owns it is §17.)

The plan-agreement check reads all thirty. Ten plans are drawn at random per project from the rows the plan list actually renders, each plan's served HTML is parsed by the site's own reader and its figure is compared with the bar the row shows. All thirty agree. Two of them (playable-forward-solve and the-crew-surface-is-one-tool-and-a-few-verbs) sit on an exact half point, which the shelf rounds up and the parse keeps at 62.5; the bar is an integer percent, so agreement is a deviation of half a point or less and every row is inside it.

The first pass's 409s were a defect in this probe, not the site. The probe built /<project>/plans/<href> while the index row's href already begins with the artifact kind — plans/<slug> for a live plan — so it asked the server for /<project>/plans/plans/<slug>, which the server refuses with 409 Conflict. A row whose key is an archived plan's (plan:archive:<slug>) fell through the same way. Twenty-three of the thirty reads failed on that doubled path, not on browser contention; the same URLs answer 200 once the path is formed correctly. The probe now requests /<project>/<href> and samples only the rows the index can resolve. Corrected here: the first pass's retry_failures and follow_ons attributed the 409s to load, which was wrong.

The negative control and its verdict. The same probe ran against a temporary reckon serve on port 18766, started from the plan's base revision b98f7a160 (the commit before the plan's first section merged as 46e5138f2), extracted from the object store into the run's scratch directory. There the plan list never shows a non-zero bar at all (None for nova and reckon), the graph does not populate within 30 s for those two, the home view's warm load is 850 KB, and power_convertor's figure first screen transfers 2.66 MB warm with a 6.1 s cold draw — four of the six gate lines fail. Its verdict rests on the progress, view and byte lines, none of which the URL defect touched, so the control was not re-run: the fix changes only the plan-agreement line, which the control does not need to demonstrate.
