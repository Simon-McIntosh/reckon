Discovery, the checks summary and the fleet rollup answer from stored results

Each of the three derived routes now reads the last result it stored and answers it with an age header, while one generic child process recomputes on a miss. The child is started at most once per key, stores its result, and a parent waiter publishes it: a fleet-scoped key as a fleet event on every open change stream, a discovery key to the tree it belongs to. The change watch reads the stored discovery and starts a child only on a miss, spawning discovery for the tree that moved plus one rollup for the fleet, so two projects changing at once start one rollup child rather than one each.

The stored-result interface is one key, one child, one published result. A key is a tuple — ("discover", project), ("checks", project), ("rollup",) — and the store is a single JSON document per key under the configuration home, versioned so a reader can tell which result it is holding. Discovery, checks and rollup all reach it through the same two entry points: read the last result, or start the child that will replace it.

A refresh child is a process of its own, and nothing ended it when its server did: a term signal stops the interpreter without running the release that a normal exit runs, so the child kept deriving and wrote its stored result into the served home while the owner of that home was removing it — the removal failing with Directory not empty against a directory the child had just repopulated. The server now stops every running child on the way out of main, before the exec that replaces the image, and a term signal unwinds the same path a Ctrl-C already took, so the release runs either way. Each child is asked to terminate, given a bounded time to go, and killed if it will not: no refresh child outlives the process that started it. The case that pins it runs a served process whose child writes into the served home shortly after it starts and then holds the interpreter, terminates the server, and requires the child's pid to be gone and the write never to land.

The stored-result machinery — the store path, the read and write, the per-key child registry and lock, the spawn, the parent waiter, the publish step, the opt-in switch and the child's entry point — now lives in reckon/route_results.py, so the module that serves a route is no longer the module that refreshes its result. serve.py keeps the handlers and calls into the new module; route_results reaches serve's derivations inside the functions that need them, as change_streams does, so neither imports the other at module level.
