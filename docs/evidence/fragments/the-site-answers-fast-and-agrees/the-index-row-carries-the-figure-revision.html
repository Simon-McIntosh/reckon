The index row carries the figure revision

A page's first paint builds its figure and thumbnail URLs from the row /_index/<project> already serves, so the row now carries the revision of the figure's bytes. Nothing asks for a URL before it can name one.

The revision is <inode>-<size>-<mtime_ns> in hex, and it has one owner — file_memo.file_revision — that the index row and the file and thumbnail routes all call, so the token a URL carries and the token the response validates against are the same value by construction. A figure entry written before the field existed is rebuilt rather than served without it (metadata_index._row_is_complete).

The gate is tests/test_a_figure_revision_is_fetched_once.py: 10 passed, EXIT=0. It reads a row from /_index/sample, computes the expected token itself from os.stat, and finds the figure and its thumbnail answered Cache-Control: max-age=31536000, immutable. An entry persisted without the field is refreshed to the correct revision. A figure that cannot be rasterised answers exactly one Cache-Control header — the immutable one, where a duplicated no-store previously rode beside it.

The declared negative control — drop the revision from the index row — reddens the first-paint case: 2 failed, EXIT=1. The importer population is unchanged against base except for tests/test_metadata_index_survives_restart.py::test_the_index_endpoint_serves_only_row_fields, which pins ROW_FIELDS and lives outside this node's write scope; the same eleven environmental failures (playwright, browser) fail at base and head alike.
