A landing's commit and its rollback both wait out a held index lock

Change. The landing's staging git add already waited out a briefly held .git/index.lock; the git commit that followed it did not, so a peer promotion holding the lock for a moment refused a landing whose writes were already staged. In reckon/crew/promotion_scope.py the commit step of _commit_landing_writes now runs its git commit --only through reckon.crew.merge._run_waiting_out_a_held_index_lock, the helper staging already used, with this module's own _INDEX_LOCK_RETRY_ATTEMPTS and _INDEX_LOCK_RETRY_INTERVAL_SECONDS rather than merge's defaults, and records each retry on the run's landing.json as commit_retry. The second half is what the failed commit left behind. After a refusal _restore_landing_writes ran one git restore --source=HEAD --staged --worktree per path and fell straight to its index-free fallback, which declines to clear a path the index still stages while the lock is held — so two forward writes stayed staged in the shared index for any path-less commit to sweep up. Each path's restore now runs through the same helper under the same bound, and records restore_retry when a run_id is supplied, so a lock that frees while the rollback is retrying unstages the forward writes and returns their tracked content to HEAD. No second wait loop and no new bound was added; the fallback is reached only once a lock has outlasted the bound, which is the refusal that names the paths a coordinator must restore.

Test. tests/test_a_promotion_commit_survives_a_held_index_lock.py drives _commit_landing_writes against a temporary repository, taking a real .git/index.lock at the boundary each case is about and releasing it off a landing-record entry rather than a fixed delay, so no case depends on timing. The lock is taken by a stub over _stage_landing_writes that calls the real staging and then writes the lock, which puts it after the git add and before the git commit; the first case asserts no stage_retry was recorded, which is what shows the lock was met by the commit and not by staging. Each case also requires that the retry it relies on was observed while the lock file still existed, so a slow setup cannot stand in for a wait.

The lock is held past the commit's bound and released one second after the commit step gives up; the rollback's own bound of 12 attempts at 0.5 s is what waits the remaining second out. ruff check and ruff format --check report no findings on either staged path. Negative control. The two controls this section names were applied together and reverted: the commit's _run_waiting_out_a_held_index_lock wrapper replaced by a single direct _git call, and the rollback's likewise. test_a_commit_waits_out_a_lock_taken_after_staging then reddens because the landing refuses instead of committing, and test_a_rollback_waits_out_a_lock_that_outlasted_the_commit reddens at assert 1 == 12 — the commit made one call rather than using its whole bound, and the forward write is left staged. The task that did not depend on either wait, test_a_lock_held_past_both_bounds_refuses_naming_every_path, still passes, which is what shows the controls redden the cases that measure the waits rather than the harness. Log logs/negative_control.log, last line EXIT=1, both failing ids named above.

Follow-ons. None outside this node's scope. One thing a later reader should know: the restore bound is per path, so a lock held for the whole restore spends one bound per landing write rather than one for the whole rollback. That bounds a refusal's wait at n × 5.5 s for n writes, which is what the existing per-path restore structure already implied; it is left as it stands because collapsing it to one call per rollback is a change to what a restore reports per path, not to the wait this section closes.
