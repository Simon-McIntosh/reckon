A landing's commit and its rollback both wait out a held index lock

Change. The landing's staging git add already waited out a briefly held .git/index.lock; the git commit that followed it did not, so a peer promotion holding the lock for a moment refused a landing whose writes were already staged. In reckon/crew/promotion_scope.py the commit step of _commit_landing_writes now runs its git commit --only through reckon.crew.merge._run_waiting_out_a_held_index_lock, the helper staging already used, with this module's own _INDEX_LOCK_RETRY_ATTEMPTS and _INDEX_LOCK_RETRY_INTERVAL_SECONDS rather than merge's defaults, and records each retry on the run's landing.json as commit_retry. The second half is what the failed commit left behind. After a refusal _restore_landing_writes ran one git restore --source=HEAD --staged --worktree per path and fell straight to its index-free fallback, which declines to clear a path the index still stages while the lock is held — so two forward writes stayed staged in the shared index for any path-less commit to sweep up. The rollback now issues one git restore over every tracked write and one git rm --cached over every write HEAD never carried, both inside a single step run through the same helper under the same bound, so a lock that frees while the rollback is retrying unstages the forward writes and returns their tracked content to HEAD. Because both index operations are one step, a rollback of any number of writes spends one bound rather than one per path: a lock held for the whole rollback costs the same 5.5 s whether it reverts one write or ten. No second wait loop, no new bound and no new landing-record entry was added — only the commit's retries are appended to landing.json, so the record's existing step vocabulary is unchanged — and the index-free fallback is reached only once a lock has outlasted the bound, which is the refusal that names the paths a coordinator must restore. A single write HEAD never carried still has a restore attempted before its index drop, so the rollback's git receipts keep showing both steps even though only the drop can settle such a path.

Test. tests/test_a_promotion_commit_survives_a_held_index_lock.py drives _commit_landing_writes against a temporary repository, taking a real .git/index.lock at the boundary each case is about and releasing it off a landing-record entry rather than a fixed delay, so no case depends on timing. The lock is taken by a stub over _stage_landing_writes that calls the real staging and then writes the lock, which puts it after the git add and before the git commit; the first case asserts no stage_retry was recorded, which is what shows the lock was met by the commit and not by staging. Each case also requires that the retry it relies on was observed while the lock file still existed, so a slow setup cannot stand in for a wait. A fourth case seeds three tracked landing writes, holds the lock for every attempt and counts the rollback's git restore calls: it requires exactly the attempt bound and not the bound multiplied by three, which is what makes the one-bound claim falsifiable — a per-path wait records three times as many calls and reddens it.

Negative control. Follow-ons. None outside this node's scope. A rollback that has to fall back to the index-free path still reports per path, so a coordinator reading the refusal learns which writes were settled and which were not; the wait is one bound for the rollback as a whole, and the fallback's per-path work is not a wait.
