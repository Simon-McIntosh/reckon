A landing write outlasts a briefly held index lock

What changed. A landing's staging git add, its git commit and the rollback git restore all run through reckon.crew.merge._run_waiting_out_a_held_index_lock, and the bound they passed was reckon/crew/promotion_scope.py's own 12 attempts 0.5 s apart — about six seconds. A peer session's commit keeps the shared checkout's .git/index.lock for seconds at a time, so the retry ran out first and a promotion discarded minutes of reads over a lock that was about to free. The bound is now 130 attempts 0.5 s apart: a spacing span of 64.5 s, sized to outlast a lock held for a minute, and reached by every step that writes the shared index.

A refusal says why it gave up. When the staging or commit step uses up its bound while the lock is read as still held, the refusal now names how long the lock had existed and the bound it outlasted, in the form Another writer has held the checkout's index lock for <age>s, past this landing's 64.5s retry bound (130 attempts 0.50s apart). The age is read at the moment the step gives up, before the rollback runs, because the rollback spends a bound of its own and can see the lock released by the time the refusal is raised. A staging or commit failure that left no lock behind keeps git's own message with no clause added.

Measured

Both cases hold the lock from a second process, so the lock and its release are not artefacts of the landing's own git calls. The first holds it for 20 s while the promotion reaches its staging step; the landing commits, its record lists the retries in order, and the commit is recorded as committed. The second holds it well past the bound; the landing refuses, the refusal names the lock's age and the 64.5 s bound, and the rollback that follows leaves nothing staged and the plan file at its HEAD content.
