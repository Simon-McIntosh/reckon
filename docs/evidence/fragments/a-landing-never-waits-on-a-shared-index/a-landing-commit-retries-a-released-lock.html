The race the wait could not see

A peer committing in the shared checkout holds .git/index.lock for milliseconds. That is long enough to refuse a landing's git add or staging retry and short enough that the lock is usually gone by the time the wait helper asks whether the file is still on disk. The helper decided whether to retry from the file alone, so a call that had just been refused by the lock was returned after one attempt, and the landing lost a race it had already been told to wait out.

The defect reproduces at the base revision 251cb1cd, driven by this node's own test against the base helper. A second process takes the lock, the step's real git add is refused by it, and the holder releases the lock within 50 ms of that refusal. The helper returns after one attempt: AssertionError: the released lock is retried once / assert [1] == [1, 2], in logs/negative-control.log.

The change

git names the lock it could not take — fatal: Unable to create '<git-dir>/index.lock': File exists — so the failure itself says which lock refused it. Whether a failed call waits is now decided by the failure as well as by the file. A failure naming this checkout's index.lock is retried to the same bound even when the lock has already been released. A failure naming another checkout's lock is not this one's to wait for and returns at once, and a failure naming no lock still waits while this checkout genuinely holds one, because a git call can be refused by a lock it does not name.

The bound is the caller's, unchanged: the promotion passes 130 attempts 0.5 s apart, the ledger and the merge pass DEFAULT_ATTEMPTS, and a lock this checkout keeps held for the whole call is still tried exactly to that bound and then refused with the retries counted, so the new condition cannot turn a permanent lock into a wait that never ends. reckon/crew/merge.py is the only product file changed.

The new condition says nothing about whether the call succeeded, and a call that succeeded must never be run twice. Judged by the lock alone, a step that returned zero while a peer held the lock at the check was executed again: land_merge's git merge --ff-only would fast-forward a second time over the head it had just moved, promotion_scope's git commit --only would report the commit it had just made as nothing to commit and drive the rollback at the same site, and the ledger's commit step reached the same false failure. The wait is therefore asked only about a failed result — result.returncode != 0 and _failed_on_this_index_lock(lock, result) — and a case pins it: a step returning success while the instrument holds the lock is run once, with no retry recorded.

Measure

The test is tests/test_a_landing_commit_retries_a_released_lock.py, five cases over a throwaway repository with the lock held by a second process so every failure is git's own. A released lock is retried and the retried call is the one that stages the write, with the retry recorded through on_retry. A lock held for the whole call is tried exactly to the bound (five attempts, four retries recorded) and refuses. A call that returns success is run once and not retried, even though the instrument holds this checkout's lock throughout. A failure with any other cause — an unknown revision — returns after one attempt. A failure naming another checkout's index.lock returns after one attempt.

At the head c9d5bfef74 the gate reports 60 passed, exit 0 (logs/after-arm.log). The base arm, the same command resolved over the base tree, which does not carry the new test file and so names the two files it does hold, reports 55 passed, exit 0 (logs/base-arm.log).

The negative control is the base revision of the helper driven by the head's test: 1 failed, 3 passed, exit 1, and the failing id is the released-lock case (logs/negative-control.log). The three that pass at both revisions are the cases that assert the unchanged refusals, so the control isolates the one behaviour the change adds. For the guard the raised revision efeb0d0d — whose condition no longer reads the return code — is driven by the same test file: 1 failed, 4 passed, exit 1, and the failing id is the successful-call case (logs/negative-control-repair.log). Reverting the guard therefore fails exactly the check the review named, and the other four cases pass at both revisions.

Every test file importing reckon/crew/merge.py was run at both revisions over its own tree: 21 files at base, the same 21 plus the new test at head. Both arms name the same 18 failure ids and the pass count moves from 115 to 120 at the repair head, the five new cases and nothing else. Those 18 ids are pre-existing in this checkout: they are the landing-gate tests that reach the configured measurement partition without providing a recording scheduler, they fail identically at the base revision and with SLURM_JOB_ID unset, and none of them imports the changed behaviour this node touches.

Every log is under the run directory, starts with the revision, the tree, the imported module's absolute path and the literal command, and ends in EXIT=. Ruff check and ruff format --check report no findings on reckon/crew/merge.py and the new test, which also closed one pre-existing indentation deviation in a call the formatter rewrote.
