A red primary no longer blocks a repair

_require_repair_gate in reckon/crew/pending_landing.py refused a merge repair unless the gate's exit status was 0 and its log ended EXIT=0. A run whose gate files were already red on the primary branch could therefore never land through its pending landing, however clean its own change: the monitor plan's review-cell run hit exactly this on 15 November, with 26 failure ids at primary e79530ca9f and the same 26 at the primary merged with the repaired head.

Reproduced at base 3bc474f9263c: a repaired head whose gate log names FAILED tests/test_charged.py::test_charge at that same id on the primary arm is refused with repair gate did not pass, and the refusal names neither the primary nor an id — the two facts the operator needs to decide whether the redness is theirs. The panel below is that reading.

The change

A gate that exited zero still passes on its own receipt. Nothing about the green path changed: the log must be readable, record its exit status, record the declared command and name the repaired revision, and then it lands. The monitor plan's case is the red path, and only that path gained a comparison.

A red gate is now judged against the same command's own arm at the primary revision the merge conflict names. The arm is the fresh manifest's baseline_suite, which is the arm a run records for the revision it measured before its change; a repair round records it at the primary revision the conflict record carries, so the two sides are one command at two revisions rather than two spellings of a guess. The arm must name that primary revision, must not declare its run incomplete, must name a readable log, and the command its log records must be the gate's own. Each condition is refused by name rather than defaulted, because an arm measured somewhere else is not the comparison the refusal reports.

The failing ids come from the two logs through review.gate_log_failure_ids, and the difference through review.failure_ids_covered — the reader that already decides added failures for a delivery, so one test written as a bare summary name on one side and as a qualified node id on the other is not counted as two. The refusal names the added ids and both logs.

_delivered_repair already resolved the conflict's main_revision; it now passes it to the gate. The gate takes it as an optional argument, so a caller holding no conflict record gets the old absolute reading rather than a comparison against nothing.

Measure

At the base revision 3bc474f9263c, this node's test file carried into a tree of that revision beside the two importer files reports 3 failed, 60 passed, exit 1. The two failures the node is measured by are the red-primary repair refused and the added id not named; the third is the arm-at-another-revision case, which cannot be named before the argument exists. The two cases pinning unchanged behaviour — a gate log naming another revision still refused, and a green gate needing no primary arm — pass there, which is what makes them pins.

At the head the same three files report 63 passed, exit 0. Both arms run as PYTHONPATH=. .venv/bin/python -m pytest -p no:cacheprovider -q over the tree under test; the base arm runs in a clone of the base revision because the new test file is carried into it, and its log names the revision, the tree, the imported module path and the working directory on its header lines.
