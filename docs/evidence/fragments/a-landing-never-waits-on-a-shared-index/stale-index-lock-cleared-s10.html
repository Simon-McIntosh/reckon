A lock no live writer owns is cleared instead of refusing forever

What changed. A shared checkout is written from several hosts, so a lock left by a writer that died is invisible to every other host's retry: nothing on this host held for long enough to see it move, and nothing will ever remove it. reckon.crew.merge._run_waiting_out_a_held_index_lock reaches its bound, finds the lock still present, and now judges it before refusing. The lock is stale only when all three hold: its mtime is at least STALE_INDEX_LOCK_AGE_SECONDS (600 s) old; its (st_size, st_mtime_ns) signature has not changed across the whole retry window; and no process on this host has the file open, read by walking /proc/<pid>/fd. A stale lock is unlinked, the attempt retried once, and the landing's own record carries one line naming its age and the removal.

A refusal keeps its age, and an unreadable process table proves nothing. A lock any process holds, one younger than the bound, or one whose size or mtime moved refuses exactly as before, and the message now names the lock's age: the checkout's index.lock stayed held for N attempts (aged Ns); nothing was written. _processes_holding returns None when /proc cannot be read, and _stale_index_lock_age_seconds treats that as "not provably free", so an unreadable process table can never be the reason a lock is cleared.

Why one retry is enough. A writer that is alive but slow would have changed the signature during the window, and is refused by the unchanged-signature condition before age is even consulted. A file that has not moved in ten minutes with no local holder is a dead writer's, and the one retry exists only to let the step succeed now that the path is free; if it does not, the step's own result is returned and the refusal path runs as before.

Recorded, not silent. land_merge passes an on_stale_removed callback into every wait it starts, including the stale-landed-copy sweep, and the report carries stale_index_lock_removed: a list of lines of the form removed <lock> after <Ns> unchanged with no process on this host holding it. The callback keeps the helper's (result, retries) return unchanged for its other callers, and the retry it spends is counted, so the reported remaining attempts do not overstate the work left.

Measured

Four cases run against a temporary repository whose origin is a bare repo in the test's own tree. Case one ages a lock eleven minutes and leaves it untouched and unheld: the landing merges, the lock is gone, and the record names the removal with an age in the six hundreds of seconds. Case two holds the lock from a live child process: the landing refuses and the lock survives. Case three touches the lock's mtime during the retry window: the landing refuses and the lock survives. Case four ages a lock five minutes: the landing refuses, the lock survives, and the message carries aged 30Xs.

The negative control is decisive because each removed condition is the only thing standing between the test and a wrong answer: without the holder check the live child looks like nobody, and without the signature check a lock that is being rewritten looks unchanged. Both cases then clear a lock they must keep, and both remove-cases still pass because their deadlines were never what those two conditions proved.

Scope of the record. Only land_merge records the removal. The other promotion-path callers of the same helper clear a stale lock but emit no line, because reckon/crew/promotion_scope.py is outside this node's write scope; the helper accepts the callback and today they pass none.
