Two promotions of one implementation

A run that has already been promoted once can be promoted again by a second caller before its head is on the branch. The second promotion reaches a ledger row another writer already wrote, and the code that answers that case re-raised out of the pointer removal instead of returning to the caller’s landing step. The caller then reported “the ledger row for run … is already written; do not re-promote” and never ran the merge, so the reviewed head stayed off main while the pointer was left marked pending_landing_repair. The row was written; the work was not landed.

The race was reproduced directly at base revision 63b51b8337c4: two crew complete --land promotions of one reviewed head, the second starting after the other writer’s ledger row exists, with the station rewriting the live pointer to promotion-requested while the promotion runs. The call exits 1 with the message above; the head is not an ancestor of main and the pointer still names the run.

The change

The pointer comparison that raised was comparing the whole pointer, including phase. A phase is not part of the identity of an attempt: the station rewrites it to promotion-requested while the attempt it belongs to is still running, so a mark made during a promotion reads as a race. The comparison now names four fields — attempt, attempt_kind, pid and pid_start_time, the fields that say which attempt wrote the pointer — and a pointer a newer attempt wrote is still kept, which is what a resume depends on.

A promotion that finds the other writer’s row now finishes the landing itself. It records the merge it owes in the pending-landing store, retires the pointer when the pointer still belongs to its own attempt, and returns to the caller, whose landing step merges the reviewed head and clears the pending record on success — the same merge the winning writer would have run. That branch never raises: the run is either landed and retired in this call, or left with a pending record and a live pointer that the next landing pass completes.

A pointer a newer attempt wrote is left exactly as that attempt wrote it. Marking it for repair sends that attempt into the repair-only branch on its next complete call, where it looks for a pending record of its own and finds the record this promotion wrote for the attempt it read — so the newer attempt cannot finish, and the marker was written by a call that went on to succeed. The pointer is retired only when its four identity fields still name the attempt this promotion read, whether or not the station has rewritten its phase; when they name another attempt, the pointer is untouched and the caller still lands the reviewed head.

The merge recorded for the landing pass cites the head the promotion resolved before it wrote anything, rather than the manifest or the worktree as they stand when the record is written. A resume that advances the tree between the two cannot make a later pass merge a revision the original review never covered. A pending record that already exists is never replaced, so a second writer’s record survives this promotion’s attempt to record its own.

Four code paths compared a live pointer under its lock and removed it while it still matched what they had read: the promotion removing the attempt it checked, a review run retiring a pointer that moved, the raced promotion retiring the pointer its row already covers, and the landing pass releasing a mark it had made. Each carried its own absent case, its own unreadable case and its own unlink failure, so the four guards had already diverged before this work and a change to one left the others behind. pending_landing now owns that comparison once, as retire_pointer_if, returning retired, absent or held, and all four reach it. The attempt identity is likewise one vocabulary there: attempt_identity names the attempt and ignores the phase a station rewrite moves, and marked_identity is the identity a stored mark was written with, so marks already on disk keep the fields they carry.

A pointer that is gone by the time the raced promotion retires it now reports success rather than falling through to a marking path that cannot mark anything. That fall-through was the fourth defect in this area: with nothing to read, the marking path failed, and the promotion re-raised a message claiming its pointer had been kept and marked although no mark was written. The mark-failure path that remains says what it did: the promotion is recorded and the merge is left to the landing record, naming the state it actually left behind.

Measure

The cases are tests/test_a_raced_promotion_still_lands.py, over a temporary origin, checkout, worktree and crew home. Two real crew complete --land --wait promotions of one reviewed head run against it: the first is paused after its ledger write and before its landing step, and the second starts in that window. Five cases sit on that harness: the station rewriting the live pointer to promotion-requested during the second promotion; a resume taking the run over as attempt four; the record citing its reviewed head and never replacing one already on disk; a ledger row that appears between the promotion’s read and its append; and a pointer reclaimed between the promotion’s read and its retirement.

The resume that starts inside the second promotion is written from the promotion’s own commit step, which is the moment the attempt this promotion read stops being the attempt on disk. The pointer is then attempt four with no pending_landing_repair on it, the reviewed head still lands, and neither call raised. Without the identity check the promotion retires a pointer that is no longer its own and the newer attempt’s next call finds no run.

The append-race case hides the other writer’s row from the promotion’s early read and from its landing preconditions, so the append is the first thing to meet the row that is already written. The second promotion then exits 0, the reviewed head is an ancestor of main, and no pointer and no pending record are left behind. Forcing the raced argument on that call site to False turns this one case red and leaves the other four green: exit 1 with “the ledger row … is already written; do not re-promote … its pointer is kept, marked pending_landing_repair”, which is the refusal the argument removes.

The reclaimed-pointer case removes the pointer between the promotion’s read of it and its retirement, so the retirement finds nothing to compare. The call exits 0, the head lands, and no pointer comes back. Narrowing the retirement’s absent case back to a fall-through turns this one case red and leaves the other four green, with the refusal that reported a pointer kept and marked when nothing had been marked.

At the base revision 63b51b8337c4, the two importer files report 55 passed, exit 0. The head’s test file carried into a tree of that revision fails all five of its cases — 5 failed, exit 1 — the two promotion cases with the ledger-row refusal and the pointer kept as pending_landing_repair, the record case because the base module has no way to accept a reviewed head, and the two new cases with the missing argument and the absent-pointer fall-through.

At the head 443e786f88c8 the same file with those two importer files reports 60 passed, exit 0, imported from the tree under test’s own reckon/crew/promotion.py. Both arms run as PYTHONPATH=. .venv/bin/python -m pytest -p no:cacheprovider -q from the tree under test, so each arm resolves its command over its own revision; each log opens with the revision, the tree, the literal command, the imported module path and the working directory, and ends with EXIT=.

Every test file that imports either changed module — 118 files, named in the arm’s own command line — runs as its own arm at each revision. At the base revision they report 65 failed, 25 errors and 776 passed; at the head, 55 failed, 8 errors and 803 passed. Compared by test id the head adds none: all 60 of its failures are present in the base arm’s 87, and the difference runs the other way. The base arm’s log carries one run: an earlier attempt of the same arm, aborted by its harness timeout without a summary, is kept beside it as gate-base-importers.aborted.log under the header it was written with, so the retained reading is reproducible from its own file.

Negative control

Reverting the source of the repair commit in a tree of the head, with the cases kept, leaves the reclaimed-pointer case red and the other four green — 1 failed, 4 passed, exit 1 — so the cases measure the source change and not the harness around it. The two targeted arms above go further and each isolate one branch: forcing the raced argument false reddens the append-race case alone, and narrowing the absent-pointer branch reddens the reclaimed-pointer case alone. Every one of those failures is the refusal quoted in the case it belongs to.
