A discharged refusal

A merge repair tells a worker to merge the current shared branch into its worktree, and crew merge --head then runs the promotion's dry run against that head. The dry run filled the run's citations from base..HEAD in the run's own tree. Every commit the merge had brought in from the shared branch was inside that range, and the citation guard in reckon/crew/promotion_evidence.py refuses a citation that is not a commit the run made beyond its base. A peer forks its branch before the run's base and lands it on the shared branch afterwards, so the shared branch reaches commits that do not descend from the run's base; the run's merge pulls them in, and the dry run refuses with cites <sha>, which is not a commit this run made beyond its base. The dry run went past the guard only when the coordinator retyped the run's own commits with --commit, so the repair advice led straight to a refusal.

Reproduced at base revision 622ef4617d73 over a temporary primary checkout, a peer worktree, the run's worktree and a temporary crew home: the peer's branch forks before the run's base and lands on the shared branch, the run commits its own work and merges the shared branch in, and the dry run with no commit supplied reports would_promote: false with exactly that refusal, naming the peer's commit c1a0573194.

The change

The citations are no longer the plain base..HEAD range. reckon/crew/merge.py gains commits_between, which lists a range oldest first and leaves out the reachable commits of one revision named as excluding; the inference in reckon/crew/promotion.py passes the shared branch's revision there, so a run cites its own commit and its own merge of the shared branch, and not the commits the merge brought in. The guard is untouched: the fix is in what the inference cites, not in what a promotion may present as its work.

The shared revision is read through recovery_classification._primary_branch_revision, the reader the classification sweep already uses, so a sweep over many live runs asks git once per checkout instead of once per row. A record naming no readable checkout answers empty and the inference falls back to the plain range, because an unreadable shared branch is not evidence that its commits belong to the run.

The range is memoised against the tree's own head, the base, the manifest's citations and now the shared revision. A landing that moves the shared branch changes the key, so the citations are re-read rather than answered from a read taken before that landing.

A run that merged nothing is unaffected and a run citing a commit from any other branch is still refused: only the shared branch's own history is subtracted, so a merge of an unrelated branch still leaves that branch's commit in the inferred citations and the guard still names it.

Measure

The cases are tests/test_a_run_that_merged_primary_lands.py. The first fails at the base revision with the refusal quoted above and passes at the head, citing the run's commit and its merge and not the peer's commit. The second, the pin on what must not move, is green at both revisions: with an unrelated branch merged in as well, that branch's commit is still cited and the dry run is still refused for it.

Both arms run as PYTHONPATH=. .venv/bin/python -m pytest -p no:cacheprovider -q over the files this node's write scope resolves to on each arm's own tree, so the base arm's command drops the test file this node adds: it names only tests/test_staged_write_inventory.py and tests/test_every_shared_home_lock_holds_across_nodes.py. At the base revision 622ef4617d73 that arm reports 58 passed, exit 0. At the head 48c4b4b22d42 the arm adds this node's file and reports 60 passed, exit 0. Both logs open with the revision, the tree, the imported module path, the working directory and the literal command, and end with EXIT=.

The seventeen existing test files that import reckon.crew.merge, import reckon.crew.promotion_evidence or call complete_dry_run were run at the head as well. They report four failures and nothing else, and each of those files was then run at the base revision 622ef4617d73, where the same four fail the same way: one in tests/test_complete_reports_every_refusal.py, three across tests/test_every_review_round_is_committed.py and tests/test_promotion_keeps_every_round.py, all of them the gate-log refusal for a cited log carrying no terminal EXIT= line. That refusal lies outside this node's scope and was not touched.

The negative control applies the declared mutation — inferring the citations from base to head again — and the first case goes red with the peer's commit named in the refusal, 1 failed, 1 passed, exit 1, while the pin on what must not move stays green. The cases measure the source change, not the harness around it.
