One predicate names a followup that hides work, and the roadmap reports it

A followup is a pointer when its invocation sends the reader somewhere dispatchable — another plan, another mount's plan, a sprint, or its own plan's section the plan declares implementable. Anything else names work no surface can schedule, and until now the roadmap said nothing about it. One predicate now answers that question, and the roadmap reports each followup that hides work as a warn-severity wiring finding.

What changed

  • reckon/followup_pointers.py is new. classify_followup(plan, followup, *, project, declarations, sprint_ids) parses the followup's invocation — its prompt, or recommends_skill when the prompt holds none — in the grammar /reckon-VERB TARGET with an optional §N, and returns a FollowupVerdict(pointer, reason). Reasons for hiding work: no-section, section-not-implementable, host-complete, unparseable; for pointers: other-plan, other-mount, sprint, implementable-section. §2 maps to the section identity s2.
  • reckon/roadmap.py gains _followup_work_findings, called beside _unwired_plan_findings over every plan the roadmap inventories — completed plans included — through the existing _finding helper: code followup-hides-work, severity warn, message and extra naming the plan, the followup id and the reason. No other module re-derives the classification.
  • A discovery-shaped inventory row carries neither followups nor section_declarations, so _plan_followups reads both from the plan file when the row lacks them — the same fallback _plan_declarations already takes — so the finding appears on every composition path with a docs dir, not only the one that attaches followups to rows.
  • host-complete is judged before the section: a followup on a completed plan hides work wherever it points inside its own plan, because the roadmap never dispatches a completed plan. A followup naming any other plan is a pointer regardless of this plan's status.

The gate

tests/test_a_followup_that_hides_work_is_found.py writes five plans into a temporary docs directory in the store's own layout and reads them back through parse_plan. The predicate's answer and reason are asserted for the five cases; the roadmap's findings are asserted as exactly the three that hide work. Two further cases cover the recommended-skill fallback and a sprint target. A sixth drives the MCP roadmap tool, the function behind roadmap(project, view='summary'), over a mounted temporary docs directory and asserts the summary's finding counts carry the warn.
