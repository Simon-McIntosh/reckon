The resume sweep lifts a run only once something observed the worker end

What changed. _launcher_refusal — the sweep's only process guard — refused a process the local table answered for and nothing else. A run whose liveness nothing established was therefore lifted as though it were dead: a worker on another login node, or a pointer that recorded no process at all, fell through to a resume. That is the one recovery mistake that costs more than it recovers, because two workers then write one run.

The lift now requires an observed end, read through the vocabulary the row already states rather than a second one. An observation is exactly one of two things: a pid checked on this host and found dead (local_liveness returning proven), or the supervisor's exit record, which outlives a pointer nobody updated and stays readable on a machine that never launched the worker. Both compose to process gone under _process_reading; every other reading withholds the lift and names itself in the refusal. The exit record folds into the reading exactly as classify_pointer folds it — alive is asked first, an earlier attempt's record does not apply to a living worker — so a recorded end cannot read as ended on the row and as unknown at the sweep. The gate is consulted ahead of both sweep modes, so a dry run's would_resume stays the statement the real sweep acts on rather than diverging from it.

Measured

The new file tests/test_resume_sweep_needs_an_observed_death.py parks three runs in a temporary crew home and runs the sweep once. Each park is genuine — the condition each declares is met by the fixture's own file, through the default vector, so the lift stage is reached by the condition rather than by a stub. The run with the supervisor's exit record is lifted (r-observed-exit), the run whose pid this host checked and found dead is lifted (r-observed-dead-pid), and the run launched on another host with no exit record is left in place with liveness unknown named in its refusal (r-unobserved-liveness). A fourth case holds a real live child on this host and keeps the existing refusal, still has a live process; observe or stop it before resuming.

Against the base revision 89890b94 the same file fails on exactly one case — the unknown-liveness one — because that run was lifted; the recorded-exit and dead-pid cases already passed there, which is what says the two observations were not newly invented but newly required. The negative control removes the observed-end gate from a scratch copy (restore the guard that refuses only a proven-live process in a scratch copy; the unknown-liveness case must be lifted and fail), and the same case fails again with r-unobserved-liveness appearing in the lifted list. Both red logs are in the run directory's record and both end in an EXIT= line.

What is not delivered, and why

The head arm of the declared gate adds twelve failing ids. They are the fixtures of the old contract: test_crew_recover.py, test_wait_shapes.py, test_external_wait.py, test_a_met_wait_is_ready_not_abandoned.py, test_crew_wait_stanza_validation.py, test_dry_run_predicts_the_launcher.py and test_wait_marker_is_not_a_stub.py build live pointers with no launcher_host, no pid and no exit record, and assert that the sweep lifts them. Every one of them is a run whose end nothing observed, so the strict reading of the change withholds the lift — the same reading the new file's third case pins. Repairing them means giving each fixture an observed end (a dead pid on this host, or an exit record), and those files are outside this node's declared write scope, so the repair is reported rather than performed. The narrowing that would make them green again — refusing only a record that names a foreign launcher host — was rejected: it would leave the class of runs the row's promise is about still lifted on a reading that was never taken, which is the defect this change exists to remove.
