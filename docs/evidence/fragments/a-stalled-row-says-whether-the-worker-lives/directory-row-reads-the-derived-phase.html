The crew directory row reads the derived phase

The classifier and the live view derive a run's phase from the run's own newest stream, so a worker that has been thinking and editing for an hour reads working rather than the pre-spawn label its launcher wrote. The directory row still copied the pointer's stored phase, and the CLI verb and the MCP directory view both render that row — so one live run read as working in one surface and starting in another, and the two surfaces had agreed before the derivation landed.

What landed

  • reckon/crew/directory.py:84 — the row's phase is the classifier's phase, which _run_row already computes at line 70 for the row's classification and process_alive (reckon/crew/directory.py:65). The stored pointer field remains as the fallback, so a record the derivation cannot speak to keeps the label its launcher wrote rather than an empty word.
  • tests/test_directory_row_reads_the_derived_phase.py — two cases: a live pointer whose stored phase is starting and whose stream carries one assistant record reads working in the row, read through the MCP directory view and through reckon crew directory; a stream holding only system records keeps starting.
  • tests/test_working_reads_working_at_once.py:283 — the mtime comparison in the resume-stream case is replaced by an assertion naming the stream the derivation selects.

The assertion that guarded nothing

The resume-stream case asserted resume.stat().st_mtime >= stream.stat().st_mtime — two files the case itself had just written, so no change to the code under test could fail it. It is replaced by an assertion naming the file the derivation actually reads, with the pointer's own stream aged back so that choice is established rather than left to the reader's mtime tie-break (which is by path, and would pick stream.jsonl on a tie, hiding the record):

found = recovery._record_newest_stream(pointer)
assert found is not None and found[0] == resume, found
assert not recovery._stream_holds_assistant_record(stream), stream

The second line states why the case discriminates at all: the launch stream holds no assistant record, so a reader that opened that file would report the run as still starting. The transition assertion beside it is unchanged and remains the behavioural guard.

The cases stand their world up in a temporary config home

The fixture points RECKON_HOME at a directory inside the case's own tmp_path and asserts the resolved crew home is inside it before and after the case, so nothing here reads or writes the operator's ~/.config/reckon. The CLI case reads its row by running reckon crew directory --run <id> through CliRunner, which resolves the same temporary home — a CLI that reached the real home would find no such live run and fail the row lookup rather than pass on a stale row.
