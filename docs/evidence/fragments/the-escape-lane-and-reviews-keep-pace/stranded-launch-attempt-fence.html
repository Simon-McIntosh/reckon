A released launch is fenced by the attempt it abandoned, not by its run

The admission pass already writes a stranded launch of a queued request back as that request under the same run id, and records a release the launch reads before it reserves. That record named the run alone, so the request's own next attempt was refused at its reservation for the whole fence, an hour, for a launch it never made. The record now carries the attempt the release took — claim_registered_at, holder_pid and holder_host from the claim it removed (_released_attempt, reckon/crew/admission/launching.py) — and refuse_a_released_launch compares that name with the run's live claim (_names_the_released_attempt, reckon/crew/dispatch_refusals.py). A launch of the same run presenting a different claim is a later attempt and is admitted, but only for a release that recorded the re-queue (mark_launch_requeued): a launch the release gave back authorises no second attempt, so a fresh dispatch of that run id still waits out the whole fence. No claim at all is the released attempt's own run, so a slow original resuming before any later attempt is still refused, and a record that names no attempt holds for the whole fence too.
