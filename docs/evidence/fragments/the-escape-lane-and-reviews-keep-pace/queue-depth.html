Proposed sections

Each carries its own done-when. They are ordered so the two that change what a coordinator can see land first.

The pane shows the fleet's depth beside the session's own

The stat block currently counts the follower's own rows, so a coordinator reading 2q cannot tell a fleet with four queued requests from one with forty. Add a fleet cell to the same block: the pane draws the session's own five counters unchanged and a sixth group for the fleet's queued, awaiting-upstream and held counts plus the unloaded implementable section count, computed in Python from queued_placements and open_run_index.read_rows — the two owners the depth already reads through, with no third reader added. The cell is drawn only when the fleet figure differs from the session's own figures, so an idle fleet leaves the block as it is.

Done when. A test drives the pane from a temporary crew home holding 6 queued, 4 awaiting-upstream and 3 held requests across two sessions and asserts the block carries the session's own counts in their existing cells and the fleet's 6/4/3 in the new group, and that both are computed from one snapshot; the same test shows the group absent when the fleet holds no request outside the session. It fails at the base revision, where the block prints no fleet figure.

A queue-depth view serves the census to every reader

The census in this fragment was assembled by a one-off script. A view makes it durable: reckon crew view queue-depth returns, per mounted project, the implementable, in-flight, loaded and unloaded section counts and the queued requests with their refusal class, read through the same owners and derived in Python so an agent read and the pane answer from one function, as the SPA-renders-does-not-derive rule requires.

Done when. A test builds a temporary crew home and two mounted projects, one with an unloaded implementable plan and one queued request refused on its plan review, and asserts the view reports unloaded: 1 with the refusal class on the request and unloaded: 0 for the project with a live run on its only section; and the pane's fleet cell of the previous section equals the view's totals on the same fixture. It fails at the base revision, where the view does not exist.

A launched request's pointer keeps its plan and section

Any reader that joins on pointer["plan"] sees one in-flight section where the fleet runs 37. Either the launch carries the two fields forward or every reader must remember the node block; the first is cheaper and stops the next census repeating this mistake. The plan and section are already in node.plan and node.section at launch, so the fix is to write them onto the pointer the launch publishes.

Done when. A test queues a request, launches it through an admission pass against a temporary crew home, and asserts the pointer it publishes carries plan and section equal to its node's; a second case asserts a census over the same snapshot reports the same loaded-section count before and after the launch. It fails at the base revision, where the launched pointer reads plan: null for 44 of 45 working pointers and for all 4 observed queued-to-launched transitions.

Every session is told which of its ready plans it has not loaded

82 plans carrying 224 implementable sections name no coordinator session at all, so no reader can tell an abandoned plan from one whose session simply has not dispatched it. The duty belongs on the session that owns the plan: the obligations view names, per session, each implementable plan it owns with no queued and no live run, and the reason none is queued (never dispatched, refused at dispatch, refused at admission with its class). Ownership comes from the plan's coordinator registration, already written for a dispatched plan, so no new store is added.

Done when. A test builds a temporary crew home with two sessions and three plans — one with a queued request, one owned but never dispatched, one owned by the other session — and asserts the view names the never-dispatched plan for its own session, does not name it for the other, and does not name the queued plan as unloaded; and that a plan with no recorded owner is reported in a fleet-level list rather than silently dropped. It fails at the base revision, where no view names an undispatched plan.

A request whose brief is gone is re-queued or dropped with a record

Seven requests are refused on every pass because the brief file the request names no longer exists (42 pointer-rows, 43 more under retry-backoff). Each waits forever and consumes a queue place, and the refusal is recorded again on every pass. The pass that reads a missing brief rebuilds it from the node block the request still carries — the same block this census reads — or, where the block cannot rebuild it, drops the request with a recorded reason naming the lost brief path. Either way the request stops being refused on every pass, and the class is reported once rather than accumulating.

Done when. A test places two queued requests in a temporary crew home, one whose brief path is absent and one whose node block can rebuild its brief, and asserts one admission pass re-queues the rebuildable request with a present brief and drops the other with a record naming the missing path; a second pass records neither as refused again. It fails at the base revision, where brief missing on disk is recorded for the same request on every pass (measured: 7 distinct requests, 42 pointer-rows).
