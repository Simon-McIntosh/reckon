The boundary check reads two trees for a fenced run

The defect

Every dispatch records a snapshot of every worktree registered in the repository, and every promotion takes it again, at one git status per tree. A fenced worker runs read-only outside its own worktree, so the scan over the other trees looks for a write the operating system already refused. The cost is one git status per registered worktree on every launch and every promotion, on a registry that grows with the fleet.

What changed

  1. reckon.crew.routing._boundary_tree_roots names the two trees a fenced run's boundary check reads: the run's own worktree and the repository's main checkout. The main checkout stays in the set as a second line behind the fence, because a write there goes live for every session on the repository.
  2. The launch records whether the fence was composed, read from the composed launch plan's own argv rather than from the request to compose one: record["fenced"] = _plan_composed_the_fence(plan) in the dispatch record and the supervisor spec. A cli launch whose plan carries the fence wrapper records True; an in-harness launch, which composes no plan here and no fence argv, records False.
  3. Both dispatch-side snapshot writes (dispatch.dispatch for the inline launch and dispatch._write_boundary_tree_snapshot for the supervisor and delegated lanes) pass the two roots when the record is fenced.
  4. promotion._repository_tree_boundary_violations reads the recorded fact: a record whose fenced is True scans the two roots, and any other record keeps the full scan of every registered worktree.

Callers of the two routing functions

Base line numbers from the dispatch brief, head in parentheses.

  • _repository_tree_snapshot — dispatch.dispatch inline launch (base dispatch.py:5061, head dispatch.py:5068); dispatch._write_boundary_tree_snapshot supervisor and delegated lanes (base dispatch.py:6835, head dispatch.py:6875); promotion._repository_tree_boundary_violations at promotion (base promotion.py:2233, head promotion.py:2244); promotion._worktree_audit single-tree audit (base promotion.py:4162, head promotion.py:4172).
  • _tree_state — only inside routing._repository_tree_snapshot (base routing.py:578, head routing.py:590), one git status per resolved tree.

Evidence

tests/test_boundary_check_reads_two_trees.py (8 passed under the root .venv python) drives a temporary repository with fifty registered worktrees and a git shim on PATH counting status calls:

  • a cli dispatch whose launch plan carries the fence records fenced true and snapshots 2 trees; an in-harness dispatch records fenced false, snapshots the full registry, and its promotion makes that many status calls — both driven through dispatch itself, not a seeded record;
  • a fenced snapshot holds 2 trees and makes 2 status calls; an unfenced one holds 51 and makes 51;
  • a fenced promotion makes 2 status calls and an unfenced one 51;
  • a record without the fenced field keeps the full scan of 51;
  • a fenced run driven through the crew complete entry point opens no peer worktree, while the unfenced positive control opens 49;
  • a fenced run that wrote the main checkout is still refused, naming that tree.
  • negative control: routing the fenced branch through the full scan makes the fenced run's promotion take 51 status calls and the test fails (assert 51 == 2).

The importing-test-file suite over reckon.crew.routing, reckon.crew.promotion and reckon.crew.dispatch ( pytest -n 8, separate --basetemp per arm) shows 33 failed / 1076 passed / 2 skipped at head against 33 failed / 1070 passed / 2 skipped at base. One id differed each way: tests/test_crew.py::test_shadow_inherits_primary_time_budget_instead_of_role_default red at head only, and tests/test_no_member_dispatch_runs_alone.py::test_two_unnamed_reviews_launch_with_disposable_members red at base only. Both pass serially on both arms (suite-flake-check.log). The head-side id matches the shared fixed manifest path the suite plan's section 2 records as making test_shadow_* ids race under xdist: the canonical node helper pins manifest_path to /tmp/node-a-manifest.md, so a concurrent test writing a terminal manifest there inside this test's dispatch-to-complete window makes promotion read a foreign manifest and refuse. It is pre-existing xdist flake, not this change.
