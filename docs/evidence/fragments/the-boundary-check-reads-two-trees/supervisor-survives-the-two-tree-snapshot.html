The supervisor's boundary baseline reads every registered tree

The defect

The two-tree boundary change narrowed the per-run supervisor's baseline to the run's own worktree and the main checkout. That baseline then completes in milliseconds instead of crossing the registered worktrees, so a supervisor whose worker exits at once spawns, collects it and writes its completion exit record inside dispatch's two-second survival window. Dispatch reads that record and refuses the launch, so a dispatch no longer returns once its supervisor runs.

Root cause

reckon/crew/dispatch.py:6915 _supervisor_tree_snapshot read the captured fenced fact and passed it to _write_boundary_tree_snapshot, which reduced a fenced run's baseline to two trees via _boundary_snapshot_roots (reckon/crew/routing.py:562 _boundary_tree_roots). The supervisor is not the fenced process: its baseline is the record of the trees before any worker write, so it must stay complete. The narrowing belongs to the comparison.

What changed

  • _supervisor_tree_snapshot takes the full-registry baseline again, as the delegated lane and every run without the fence fact already do.
  • The supervisor spec no longer carries fenced; it was read only to narrow the supervisor's own baseline.
  • Unchanged: promotion's comparison still reads the two trees for a fenced record (_repository_tree_boundary_violations), and the inline baseline dispatch takes for a lane it launches itself still reads two.
