Dispatch returns when its supervisor finished the launch

The defect

A fenced run's supervisor now takes its boundary snapshot over exactly two trees, its own worktree and the main checkout. That snapshot completes in milliseconds, so a supervisor whose worker exits at once spawns, collects it and writes its completion exit record inside dispatch's two-second survival window. _confirm_supervisor_survived read that record as a refusal, so a dispatch whose supervisor reached its run and launched its worker was refused anyway — a dispatch that launched was reported as one that never did.

What changed

  1. reckon/crew/dispatch.py _supervisor_launched_worker reads the supervisor's completion exit record and answers whether it names a worker: a record with a worker_pid is the receipt of a launch that happened, while a launch failure or a pre-spawn stop writes the same record with no worker pid and a detail.
  2. _confirm_supervisor_survived returns the run id when that record is present, and refuses only a supervisor that exits inside the window without it — one that could not find its run or whose spawn failed. The two-tree supervisor baseline is unchanged.
  3. tests/test_dispatch_returns_without_worker.py keys case one's scan-gate hold on the trees a fenced supervisor actually scans — its own worktree and the main checkout, both under the case's base — and skips calls made by the dispatch process itself, so dispatch's own pre-return calls are charged but never held. Case one now observes the two-tree scan: the snapshot holds exactly the run's own worktree and the main checkout, and the supervisor's charged status calls name exactly those two trees.
  4. tests/test_boundary_check_reads_two_trees.py adds a case that drives the supervisor's own spec path: a fenced spec snapshots two trees and an unfenced one the whole registry, so the section's supervisor clause is tested and not only stated.

Measure

  • Base 57ccb6fe: test_dispatch_returns_once_its_supervisor_runs fails — CrewError: the supervisor ... exited within 2s of starting: the supervisor exited without recording a detail. After the rework it passes 5 of 5 isolated runs.
  • tests/test_boundary_check_reads_two_trees.py: 9 passed (8 kept plus the new supervisor-spec case).
  • test_dispatch_returns_without_worker.py: 7 passed, including the completion-acceptance case and the refusal case.
  • Negative control: with the completion-record acceptance removed, test_dispatch_* in the dispatch-returns module fails 1 failed, 6 passed — the completion-acceptance id fails with the supervisor-exit refusal, while the held-scan case is unaffected.
