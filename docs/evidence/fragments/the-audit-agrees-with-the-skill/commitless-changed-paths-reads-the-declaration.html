commitless-changed-paths-reads-the-declaration — the changed_paths absence, read at a path boundary

A commitless run declares its unchanged repository in two fields: commits says none … and changed_paths says none under the repository; the sole deliverable is the report. The commits declaration was already honoured by reading the raw field, but the changed_paths declaration was recognised only through the manifest list's prose shape — none followed by whitespace or the end of the parsed item. A declaration word followed by sentence punctuation therefore survived as a path, and a review was refused with “the manifest field 'commits' is missing” until the coordinator blanked the field by hand.

The first fix read changed_paths through the same helper commits uses. Review found that fix unsafe. The commits field's boundary accepts any non-word character after the absence word, which is right for a commit value — a revision can never read as a path — but wrong for this field. changed_paths: none.txt opens with the letters none and then a full stop, so it was read as a declaration while _changed_paths_inside_repository resolved the same field to ('none.txt',). A review that genuinely changed a file called none.txt (or nil.rs, -x.csv) then promoted with no commit and no scope in the ledger, where the dispatch base had refused the same manifest. The two fields cannot share one boundary, because only one of them can hold a path.

Review found a second gap in that value, one layer further in. A manifest field whose value is exactly one absence word — none, nil, n/a, - — is emptied by parse_manifest before any boundary is consulted, so the guard returned at its first clause and the file-existence check was never reached. A repository that really contained a changed file named none (or nil, n/a, -) with changed_paths: none and commits: none was therefore read as a declaration and promoted with no commit and no scope. The fix decides from the raw field text before the parsed list is consulted: for a commitless role, a stripped changed_paths value that is a single token naming a file in the promoted revision's tree is a path, and the run then needs the commit that contains it, as for any other changed path.

Negative control. The declared mutation — drop the raw-text existence check so a bare changed_paths value is read only from the parsed list — reddens the bare-value case first: the repository that really contains a changed file called none, with changed_paths: none and commits: none, promotes under the mutation where the head refuses it. The red log is negative-control-changed-paths.log under the run directory, whose first line repeats the declared mutation verbatim, 4 failed and 4 passed over the targeted cases.

Landing note. The behaviour is carried by reckon/crew/promotion.py: _opens_with_a_path_absence_word holds the tighter boundary, _changed_path_entries reads the raw field text so a bare value is seen before the parsed list is consulted, _path_exists_in_run_tree holds the existence check, and _changed_paths_declare_no_paths composes them with the prose and committing-role readings. _commitless_raw_field is the shared role gate, _commits_field_declares_absence keeps the permissive boundary, and the docstrings state which rule each field follows and why they differ.
