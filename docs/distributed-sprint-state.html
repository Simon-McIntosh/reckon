§1 — Why the index is a monolith

docs/state/reckon/index.json currently combines the active-sprint pointer, every sprint definition and item, milestones, timeline, blockers, project rollups, and one shared version counter. It is necessary today because those fields have no other canonical store, but it creates large MCP payloads and makes unrelated edits contend on the same optimistic-concurrency version.

The replacement must decompose state before deleting the index. Separate sprint files are the central change, accompanied by explicit homes for milestones, blockers, timeline events, and minimal project configuration. Plan lifecycle state remains in plan HTML.

§2 — Target resource model

Each sprint should be a semantic document under docs/sprints/, carrying its own status, dates, theme, ordered plan references, summary, and version. At most one sprint may have status=active; the active sprint can therefore be derived and audited rather than duplicated in a central pointer.

Milestones should likewise be independently addressable under docs/milestones/. Blockers need stable records with owner and next action. Timeline entries are append-only events and should not force a rewrite of every sprint. A small project manifest may remain for mount identity and presentation settings, but it must not aggregate mutable sprint contents or computed inventory.

§3 — MCP and concurrency

MCP should read or edit one resource at a time: a named sprint, milestone, blocker, timeline event stream, or project manifest. Project discovery composes those resources into a view without persisting the rollup. Each file owns its own version, so adding a timeline event cannot conflict with editing sprint membership.

Sprint membership references stable plan identities. Current plan state is resolved live from plan HTML instead of duplicating status, progress, decisions, or followups into the sprint file. Human-facing reads should show titles and state; machine identifiers remain available for edits and links.

§4 — Safe migration

A migration command must split the existing index atomically into typed resources, validate referential integrity, compare the composed result to the old view, and retain a recoverable snapshot. During a compatibility window, reads may compose old or new state, but writes must target only one format to prevent divergence.

The index-json-fate decision in reckon-ci-build should close only after this replacement is implemented and verified. Until then, deleting the index would lose S5 and S6 definitions, timeline history, and concurrency state.

§5 — Done-when

  1. Sprints are independently stored, versioned, discoverable, and editable.
  2. Milestones, blockers, timeline, and minimal project configuration have explicit non-monolithic stores.
  3. Project discovery composes a clear live view without persisting rollups.
  4. An idempotent migration proves state parity and preserves rollback evidence.
  5. Concurrent edits to different resources do not conflict; conflicting edits to one resource still return 412.
  6. The old index is retired only after fleet migration and audit pass.

§ Decisions

What format should each sprint resource use?

Semantic HTML keeps sprint state inspectable, versioned, and consistent with Reckon's HTML-first storage and existing document tooling.

How should the active sprint be selected?

Deriving the unique active sprint removes duplicated mutable state; audit enforces that at most one sprint is active.

What mutable state, if any, may remain in the project manifest?

The project manifest retains mount identity and presentation settings only; mutable sprint contents and computed rollups live in independently versioned resources.
