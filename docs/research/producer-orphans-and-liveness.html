What happened

The lead noticed twice, by looking at GPU utilisation, that a background worker had died while the fleet monitor still reported it running. Investigating that produced three defects, of which the monitor's silence was the least severe.

Defect 1 — the suite arms producers and never disarms them

reckon crew dispatch arms a project's producer detached, deliberately, so that ending the dispatching process does not orphan it. That is correct for a coordinator. It is wrong under a test: a test that dispatches arms a producer against its own fixture project, the test ends, and the producer survives — detached, by design, with nothing left that knows it exists.

The fixture points RECKON_HOME at a pytest temp tree, so these producers write to a config home that is deleted when the test tree is cleaned. They then poll a directory that no longer exists, forever. Named by the test that spawned them:

The accumulation rate is the part that matters. The oldest is 8.5 days old and four were spawned within the last eight minutes, by a worker running the suite as its gate. Every full-suite run adds more. This session's own done-whens demanded a full suite per node for several hours, so the orchestrator was the largest recent contributor to a leak it then discovered.

Two further traces of the same root cause, both in the real config home rather than a temp one: watch/does-not-exist-xyz-….lock and watch/empty-probe-xyz-….lock. Those names are test inputs, so at least one path arms against the real config home rather than the fixture's.

Remedy. A test must never arm a real producer. Dispatch already has the seam — --no-watch and the watch_override it records — so the fixture should take it by default, and arming should refuse outright when the resolved config home is a pytest temp tree. Belt and braces, because the first is a convention and the second is a bound check.

Defect 2 — the field the dispatch guard trusts disagrees with the machine

crew list reported watcher pid: None for reckon while its producer was running and had emitted four transitions in the preceding twenty minutes. This is not cosmetic: watcher_live and session_attached are what the dispatch guard reads to decide whether to refuse with watcher-required, so a guard meant to protect against an unheard fleet is deciding on a value that does not match reality — in whichever direction it is wrong.

The likely mechanism, offered as the next thing to check rather than as a conclusion: the registry is a written record keyed by a seat lock, and a producer whose supervisor died keeps running while its record is cleared or reclaimed. The code already carries a comment describing exactly that case for the opposite failure — a stale seat that outlives its session. The two together suggest the record and the process have no reliable binding in either direction.

Defect 3 — a long-lived producer cannot receive a fix

The producer imports reckon.crew.recovery at startup and runs for hours. Both detector fixes merged tonight — the terminal-manifest protection and the widened stall gate — are therefore inert on any seat armed before them. The reckon CLI is otherwise live for peers, because each invocation is a fresh process; the producer is the one component where that is untrue, and nothing in its output distinguishes a seat running current code from one running last week's.

This inverts the usual reasoning about a fix landing: merging a detection change does not deploy it. It also means the observations that motivated tonight's two fixes cannot be used to validate them, since the seat that failed to report was running the code the fixes replaced.

Remedy. A producer should record the version it is running, and a seat whose version differs from the installed one should be replaced at the next arming rather than reused — the arming path already replaces a stale seat under a lock, so the staleness test simply gains a second criterion.

The shape all three share

Each defect is an instance of the pattern this fleet keeps producing: the component that knows stays silent, and something downstream asserts the opposite. A detached producer knows it is running and no registry records it. A registry asserts no watcher while one runs. A seat runs superseded code and reports the same as one that does not. In each case the display is not merely incomplete — it is confidently wrong, which is why a person watching GPU utilisation outperformed the tooling twice in one evening.
