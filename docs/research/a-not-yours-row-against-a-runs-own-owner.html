Where the not-yours obligation row comes from

A coordinator saw its own held run named in its obligations with the reason “Not this session's run: owner session 0f4fa699”, which is its own session id. No code compares a session to derive that sentence: it is operator prose stored in the run's deferral and copied onto the row verbatim. The run appears repeatedly beside it for a different reason — a sweep list that appends one entry per pass and never collapses by run id.

The finding in one paragraph

The phrase is not emitted by an owner comparison. It is the free-text reason of a stored deferral (an acknowledgement) recorded on the run's live pointer, and reckon/crew/obligations.py:1899 copies that stored string onto the row. What is behind it is a factual claim that is no longer true: the pointer's own session is 0f4fa699-2444-4d93-b978-9931302ff6f8, the same id the reason names as “not this session”. The repeated listing is a separate mechanism, described under the repetition, and that one does belong in this repository.

The repetition: a sweep list that appends without dedupe

The six identical sweep-failed rows are raised one per entry in a stored list. The list is built in reckon/crew/resumption.py:3153: 

block["failed"] = [*(block.get("failed") or ()), *owed]

owed carries one entry per owed review request on this pass, keyed by run id; nothing compares an entry's run id against the entries already stored. Each subsequent pass appends its own entry for the same run again, and reckon/crew/station_obligations.py:272 (reckon/crew/station_obligations.py:277) turns every entry into a duty row. The row text is built from the same census, at reckon/crew/resumption.py:3146, which is where “the review pass requested no review for this delivered run within 600 s” comes from.

The same shape was observed independently on 2026-11-21 for session 5b10be66-c69b-456f-9a85-3840909f1723, whose single run r-20261114T144505738776-icm-iron-field-source was listed six times in one obligations read. That rules out anything specific to the held run: any run whose review request is owed across several passes accumulates one row per pass.

Does a repair belong in this repository?

The phrase: no. No code emits it, so there is nothing in reckon/ to repair. It is prose an operator recorded, and it is now stale: the pointer's own session is the id the reason calls somebody else's. The remedy is to release the deferral, not to change code — which the plan's instruction forbids for this run, so this record leaves the record in place.

The repetition: yes, it belongs in this repository. One run should owe one row: a coordinator reading seven identical duties for one run owes a turn to a single fact, and the count grows for as long as nobody acts on it. The repair is at reckon/crew/resumption.py:3153, where the owed entries for one pass are appended to the stored list without collapsing entries by run id.

Endpoint for a new section of work-of-a-lost-session-is-raised-not-left:

§25 — A run's owed review is raised once, however many sweeps have seen it. Deliverable: the sweep's owed list carries at most one entry per run id, so the obligations view names a deferred run once, however many passes have found its review outstanding; the last-seen detail and age for that run survive, and a completed sweep replaces rather than grows the list. Done when a test covering a run owed a review across two passes lists it once, and two runs owed on one pass yield two rows. Negative control: at the base revision the same two-pass case lists the run twice.
