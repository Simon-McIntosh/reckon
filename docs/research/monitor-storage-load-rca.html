§1 — Summary

On 2026-10-22 the fleet node 98dci4-clu-2068 (fleet job 1291586, 28 cores) ran at a load average of 37–39. A storage review from a power_convertor session found every task blocked on storage belonged to reckon's monitor: 20 crew follow and crew watch processes, 5.1 cores of continuous CPU, and GPFS waits (cxiWaitEventWait) behind them. The filesystem itself was healthy (a listing in 5 ms, a stat in 8 ms); the contention was the monitor's own.

The cause is structural, not one bug. Every consumer re-derives the whole fleet from the shared filesystem on every pass: each follower and each producer re-reads every live pointer, re-reads worker streams its cache cannot hold, and stamps shared lease files, so the work scales with sessions × projects × live runs × stream size. The redesign replaces that with one node-local station that reads each fact once and serves every consumer from a SQLite database on /dev/shm. A prototype run against the live crew home read 5.1 MB/min in total where today's processes read about 4 GB/min, and a subscriber spent 3 ms of CPU over 40 polls with no GPFS reads.

From the handoff by the session that drove the monitor, these are the properties the lead relies on:

§6 — Design: one station reads each fact once

Principle. Each fact is read once, by one process, on the node where it changes, and every consumer reads the derived answer. Bytes on the shared filesystem are read only when their stat identity moves or past an offset already consumed.

StoreWhereWhy
Station database: pointer mirror, stream offsets and fold state, events, cursors, obligationsSQLite in WAL mode under the node-local runtime root ($XDG_RUNTIME_DIR, then /run/user/<uid>, then /dev/shm, the order the session host already uses)Derived and rebuildable; read many times a second; WAL needs shared memory and so must never be on GPFS.
Event partitionsOne SQLite file per UTC day beside the station database, attached for reads, the oldest unlinked after a retention windowRotation by unlinking a file costs nothing and keeps the history bounded.
Live pointers, manifests, streams, ledger, reviews, evidenceGPFS, unchanged Durable truth: survives the allocation and is visible from login nodes. Writers are not changed; the station only reads them.
Exported snapshot (obligations, live board)GPFS, one small file per project, written by atomic replace only when it changesLogin-node sessions, hooks run there and the SPA cannot see node-local storage.
Reload imagesNode-local runtime rootOnly the station reloads; images are rebuilt from git, so no cross-node lease is needed.

Process model. One station per node that runs workers, held by a node-local lock, serves every project on the node. It is the database's only writer. It stats the live directory and each live pointer and stream every tick, parses a pointer only when its identity moved, reads a stream only past its stored offset and folds the new records with reckon's own observe_stream carrying the stored fold state, runs the classifier once per changed run, writes each transition once with its audience (a session, or every pane) and its duty, and runs the review reflex and settle detection once. A follower becomes a subscriber: it checks PRAGMA data_version, and when it moved, selects its session's rows after its cursor, so a row is delivered exactly once per pane by construction. Hooks and crew view query the same database on the node, and read the exported snapshot elsewhere.

Failure modes. When the allocation ends the station database goes with it; the next station rebuilds from GPFS, which the prototype measured at 170 MB and 5.5 s. A station that dies leaves subscribers reading a data_version that does not move; every row and snapshot carries the station's heartbeat time, so a reader reports a stale station rather than a quiet fleet. Concurrent readers never block the writer under WAL.

Why SQLite. Indexed reads of exactly the rows a reader needs, change detection at the cost of a shared-memory read, and transactions in place of the lock files, lease stamps and temporary-and-rename records that make up today's coordination. It is in the standard library, so it adds no dependency.

§11 — The cutover measure on 2026-10-29: the station alone is far above the bound

The station was dispatched to retire the per-project producer seats, the producer user units and the follower snapshot path, on the condition that it carry every row they carry and cost the node less than they do. The second half of that condition is not met. The station carries every row — §5’s list included — but it does not yet read each fact once at a cost the node can afford, so the retirement is withheld and the producers stay.

The measure is §2’s instrument, unchanged: a 60 s window of per-process /proc/<pid>/io deltas, /proc/<pid>/stat utime and stime deltas, and six samples of process state 10 s apart. The process set is selected on adjacent argv tokens (crew station, crew watch, crew follow), never on a substring of the whole command line, because a substring match selects the shell that launched the watch whose own argv contains the pattern. The station ran alone as crew station --interval 1, with its own runtime root and a copy of the crew home carrying 71 live pointers.

Read volume scales with the number of live runs, and its slope is the cost that matters: 126 MB/min at five live runs, and 1,067, 1,160 and 1,069 MB/min in three windows over about seventy. Against a bound of 20 MB/min the station is five times over at five runs and more than fifty times over at seventy, and the three large arms agree on that within a tenth. CPU follows the same shape but not the same proportion: 42 % of one core at five runs, and 57 %, 82 % and 92 % at seventy depending on what else the node is doing, so it is reported as a range and every arm is more than ten times the 5 % bound. The D-state samples that fail the third part of the bound appeared in two windows out of three and sat on two different waits: the contended window waits on the runtime root’s own journal (xlog_wait_on_iclog) and one quiet window waits on the file server where the streams live (cxiWaitEventWait), so the station blocks on storage in both places it reads from. None appeared in the third, which is why this part of the bound is recorded as intermittent rather than constant.

A separate probe says where the bytes go. On a cold runtime root one store tick over five live runs reads 8.2 MB and one whole station tick reads 91 MB, or 83 MB when the store is already warm; every later tick reads 0.07 MB. The store’s stream ingest is therefore already incremental — a tick whose streams have not grown reads nothing at all — and the cost is the classification pass. It replays a run’s whole stream whenever the run’s pointer file signature moves, and a live run’s signature moves continuously, so the whole-stream read is paid every tick for every run that is doing anything. The fix that would meet the bound is in that pass: classify from the folded state the store already keeps, so a moved pointer reads only the bytes its stream appended.

The before figures cannot be plotted beside these. §10 counted file syscalls per second rather than bytes, so the producers’ 6,312, 3,323 and 875 calls per second and the fourteen followers’ 310 each are a reading of a different quantity. What the two readings do share is the shape: in both, the cost is paid per run per tick, and the redesign has moved it from the followers into the station rather than removing it.
