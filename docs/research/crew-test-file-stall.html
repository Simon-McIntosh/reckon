This document records why tests/test_crew.py cannot complete in a bounded run on the login node, each value measured rather than described. It answers the four questions §4 of suite-failures-have-an-owner asks (the revision, the bound, the point it reaches, single test vs interaction, buffering), and additionally records the compute-node result that the plan's measure treats as the alternative leg: the file does complete within a stated bound on a compute node. §2 — What the stall is, observed from both sides

Login node. A whole-file run with per-test SETUP/CALL/TEARDOWN stamps issued 78 CALL stamps and 77 TEARDOWN stamps, then sat in the 78th test (node id above) with neither completion nor a further stamp until the bound killed it (run B, 300 s; run G 90 s buffered identical). The missing TEARDOWN is the tell: one test entered and never left. faulthandler stacks from the isolated run D show the hang's shape — the main thread blocked in ThreadPoolExecutor.__exit__→shutdown→join (waiting on the watcher thread), and the watcher thread inside crew.watch→_watch_event→classify_pointer, never reaching the release that the test sets only after the dispatch completes.

Compute node. The same file at the same revision completes in 29.35 s / 32.16 s (two runs), with 11 failed / 193 passed and the identical 11 failure ids. The stalling test passes there in 0.16 s. So the file is not incapable of completing; the login-node environment intersects it at exactly one test.

Timing-dependence. Under strace overhead the isolated test finished in 19.09 s but FAILED with AssertionError at test_crew.py:1812 (assert release.wait(timeout=5)) — the watch/dispatch path on the login node is slow enough (> 5 s) to trip the test's own internal watchdog in one timing, and slow forever (join on a thread in classify_pointer) in the other. The mechanism separating these two intervals on the shared login host (candidates: /proc scans, subprocess spawn latency, FIFO/stream reads) is not further bisected here — that is beyond this node's fence — but the observation is pinned to the single test either way.

§3 — Consequences

The plan's §4 measure asked that the file either complete within a stated bound or have its inability characterised. The answer is both legs at once: on the compute node it completes within 300 s (11 failed / 193 passed at this revision, 29–32 s); on the login node it is a single-test stall at ordinal 78 that unbuffered output does not move. A delta over this file therefore still requires the named-subset discipline §4 demands — but the reason is now the login-node stall, not a general inability, and the compute node offers a full-file delta within a bound for anyone who walls the run off there.
