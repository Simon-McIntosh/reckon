Root cause analysis · fleet node 98dci4-clu-2018, job 1277272

What loaded the fleet node

The fleet node was never leaking processes. It was carrying test suites and compute jobs whose every Python process opened a thread pool as wide as the node, so a few dozen processes became four to six thousand threads. Two events that matter most — the failed kill that drained the node on 3 October and a D-state storm two hours later — left no process table, because the sampler only photographs the node on task count, Python count and memory.

Method

The evidence is what the fleet already writes to shared storage, read from the login node after the fact:

  • ~/.local/state/fleet/health/1277272-98dci4-clu-2018.tsv: one fleet-health sample a minute since 28 September, 12,789 rows when read. Columns used: load, the user's thread count (ps -L -u $USER), the node-wide count of processes in D state, available memory, and a timed stat of the home directory.
  • The eight process-table snapshots the sampler wrote beside it on 5 and 6 October, each written when an alert threshold was crossed.
  • sacct for the job's steps and scontrol show node for the drain reason and its timestamp.
  • A census of every Claude pane, crew run and service on the node, taken on 7 October and kept under ~/.local/state/fleet/migration/.

Two counts in the samples are easy to misread. The task column counts threads of this user, which is what the fleet's soft RLIMIT_NPROC of 6,000 also counts. The D-state column counts processes of every user on the node, kernel threads included, so it is not the same population as the task column.

Where the "under pressure" note comes from

fleet-health raises an alert when the user's thread count exceeds 4,000, Python processes exceed 1,000, or available memory falls below 12,000 MB. It writes the alert to alerts.log, saves a process table, and puts the same line in ~/.local/state/fleet/notice. fleet-attach prints that notice once, on the next attach, and moves it to notice.seen. So the note seen when attaching is the most recent alert, which may be hours old: the last one before this analysis was written at 6 October 08:04 UTC, reading 4,035 tasks.

What the pressure was made of

Every snapshot shows between 227 and 271 processes, so the thread count did not grow by spawning. It grew because each heavy Python process carries a thread pool sized to the node's 28 cores. Measured on 7 October, an imas-codex serve process holds 57 threads and an imas-codex pytest process 55 to 61. Thirty such processes are about 1,700 threads before anything else on the node is counted, and they compete for 28 cores.

The snapshot records no thread count per process, so the per-process share of the 4,000 to 5,700 threads has to be inferred from the processes measured afterwards rather than read from the table.

The drain

Slurm drained the node at 15:54:13 on 3 October with the reason Kill task failed: a cancelled step's processes did not exit within the kill timeout. The only step of job 1277272 that ended near that moment is 1277272.1549, a sandboxed crew worker cancelled by this user and recorded as ending at 15:54:15. The match is by timing; the node's own slurmd log is not readable from here. Processes that cannot be killed are usually in uninterruptible sleep, and by 5 October none remained.

A drain does not end a running job. It stops the scheduler placing new jobs on the node, so the fleet has kept working, and steps 1560 onwards have started inside the allocation since. The node leaves service when job 1277272 ends, and returns only when an administrator resumes it.

The D-state storm

From 17:29 to 17:33 on 3 October the node-wide D-state count rose from 79 to 468 and load reached 459. During the same minutes the kernel's count of processes blocked on I/O stayed at 2 to 3 and a stat of the home directory took 7 ms, so this was not a GPFS stall of the ordinary kind. It cleared by 17:34. No process table exists for it, so neither the processes nor their wait channels are known. It is recorded here as unattributed, not as explained.

What it was not

  • Not a spawn leak. The two leaks previously measured on this fleet each reached about 7,500 Python processes. These episodes never exceeded 271 processes of any kind.
  • Not a lost node. The controller answered all 7,406 pings from 2 October on, and slurmd never took longer than 912 ms to answer.
  • Not memory exhaustion, with one near miss: available memory fell to 12.9 GB on 6 October at 07:00 against a job limit of 120 GB on a 128 GB node.

Defects found

DefectMechanismConsequence
The sampler cannot name a stall fleet-health saves a process table only on threads, Python processes or memory, and the table it saves has no thread count or wait channel The drain and the D-state storm are unattributable
Thread pools are as wide as the node Nothing in the fleet environment caps OpenMP, BLAS, numexpr or XLA threads, and nothing bounds how many heavy test runs share the node Load to 176 on 28 cores; 5,731 of the 6,000 threads after which every new process of this user on the node fails to start
The supervisor leaves zombies fleet_supervisor collects exited children only between FIFO requests, and requests are rare An imas-ambix service child started on 2 October has been left defunct under the supervisor
A service lock is node-local The lock that keeps one copy of a declared service lives in the runtime directory under /tmp A second supervisor on another node would start a second imas-ambix agent ingest and publish-watch
Dispatch cannot be paused crew drain only reports; reflex reviews, repairs and crew recover launch on their own Asking coordinators to stop does not stop every launch
The worker reservation cannot be moved ensure_reservation replaces the record only when its job has left the queue Workers cannot be pointed at a new allocation while the old one runs
The status warning reads backwards fleet-node status says the allocation ends when the drain completes The drain completes when the allocation ends, so the warning overstates the urgency
Node-local scratch is unbounded Workers leave scratch files at the top of /tmp 8,111 top-level entries of this user, plus 645 MB under /tmp/claude-39486, all lost when the node is left
A login-node timer runs on the fleet node An ssh login starts the user's systemd on the compute node, which starts reckon-paid-lanes.timer; reckon.service correctly refuses through its host condition Probably a second publisher of the metered-lane document; the login node's copy was not checked
