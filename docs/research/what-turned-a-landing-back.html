What turned a landing back

A promotion of review run r-20261018T171142922335-review-of-census-proposal-coverage-f7ed7e9d8ef6 committed its landing 2321fba57 into nova's shared checkout on 2026-10-18 and then left the checkout holding a reversed copy of that same commit: HEAD carried the landing, while the index and the working tree held the pre-landing content at the tracked plan file and were staged as deletions at the three paths the commit created. This document gives the sourced timeline, names the mechanism the code makes possible, and reproduces the state in a throwaway repository.

HEAD moved exactly twice in the window (entries 7079 and 7080 of .git/logs/HEAD) and carried 2321fba57 throughout the interval between them, so the reversal happened while HEAD already carried the landing.

What the code and two experiments fix

  • The state is exactly the rollback. The reverted state is what _restore_landing_writes (reckon/crew/promotion_scope.py:1672) leaves when it runs while HEAD still resolves to the commit before the landing: its git restore --source=HEAD --staged --worktree (lines 1697-1706) returns a tracked path to that commit's content in index and working tree, and a path the landing created is dropped from the index and unlinked (_restore_one_landing_write, lines 1737, 1741).
  • The landing commit reads the working tree and holds the shared index lock. Measured in a scratch repository: git commit --only -- <paths> — what _commit_landing_writes (promotion_scope.py:1916) and ledger._commit_state_write (reckon/ledger.py:2321) run — records the working-tree content of the named paths, and holds .git/index.lock from before the pre-commit hook until after HEAD moves. A concurrent git restore --staged fails on that lock.
  • Run at the landed HEAD the rollback changes nothing. With HEAD carrying the landing, --source=HEAD restores the landing content and HEAD:<path> resolves for the created files, so _restore_one_landing_write returns before unlinking. So the rollback is only an actor when it resolves a pre-landing HEAD.

Taken together these fix the shape of the actor: a rollback that resolved a HEAD before the landing while a landing commit of the same run committed the landing's own content. A git commit on the shared index holds that lock from reading its paths until after it moves HEAD, and git restore --staged needs the same lock, so if reckon's rollback is the actor then the committing process used another index file — which is why the reproduction below stages the landing through a private GIT_INDEX_FILE.

Candidates still standing, and the record that would separate them

  1. reckon's own rollback (_restore_landing_writes, promotion_scope.py:1672) resolving a pre-landing HEAD. It is reached from a refused stage or commit in _commit_landing_writes (lines 1953 and 1980), from a refused review-record store in reckon/crew/promotion.py:1334, and from a refused release in reckon/crew/promotion_release.py:615 and :646. One way to reach it is a second promotion of the same run: the run's ledger row reads promoted_by: review-self, so the review sweep's promote_review_run_itself (reckon/crew/recovery_review_acceptance.py:416) promoted it, and that sweep confines itself to one session only when its process holds a follower registration (_sweeping_session, reckon/crew/recovery_repair_dispatch.py:1000). Any other sweeping process handles every session's review runs, so two sweepers — for example on two hosts — can promote one review run at once. This is the leading candidate; the reproduction models it.
  2. A peer git command acting on an index it read before the landing (the session's git pull). Ruled out by .git/logs/HEAD: neither the pull nor the later git merge --no-commit wrote a reflog entry, so neither moved HEAD, and the reversal was already complete when those commands ran.
  3. Another path, in reckon or outside it, that restores files from a snapshot rather than from HEAD (an editor or tool reverting to a saved copy). Not separable from (1) by any record I can read.

The record that would separate (1) from (2)/(3) is a log of a second promotion of this run in the interval, or a receipt of the index lock. Neither survives: the run directory holds no landing-failure record, and the event that would name it — the per-path rollback report — rides only on the exception _landing_refusal carries (LANDING_ROLLBACK_ATTRIBUTE, promotion_scope.py:1762), which the incident never saw. §2 of the plan is what adds that record: a landing that reads the paths already staged before it stages, naming the commit it reverses.

The reproduction

scripts/reproduce_landing_reversion.py builds a four-path stand-in for the checkout and runs two arms. The reverted arm does not model the rollback, it calls it: it imports _restore_landing_writes from reckon.crew.promotion_scope with the worktree on PYTHONPATH, so the run exercises the production function, and it prints the module and the copy of it that was imported.
