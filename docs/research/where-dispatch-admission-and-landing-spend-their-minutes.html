Where dispatch, admission and landing spend their minutes

A dispatch preview spent most of its wall time checking live scope claims. A declaration reply rebuilt the roadmap twice. Reusing one pointer population made promotion ordering 7.6 times faster, while no local-copy store reader approached the writer’s 120-second retry ceiling.

4. Post-write roadmap rebuild

The reported “every write rebuilds the roadmap” premise is too broad at this revision. The tool adds readiness only for state operations naming a section declaration; metadata and text edits return review debt without readiness (reckon/mcp_edit_plan.py:2358). On a one-plan temporary docs root with isolated config, a real summary write took 4.276886 s and returned version 411. A declaration-shaped no-op took 9.237146 s, returned the same version, and still answered readiness=ready. These copied-root timings are not live-project performance claims.

The 366.960-second audit is an upper envelope of work affected by that owner, not 366.960 seconds of new savings this node can claim.
