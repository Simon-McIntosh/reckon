What Abandoned Means in Practice

A run reads abandoned when its process is gone and nothing is eligible for promotion. The open question, raised against two live panes, was whether that label lands on runs that in fact finished and only failed to write a manifest. This is the measurement: 270 abandoned transitions, 224 distinct runs, five projects.

§— The claim under test

The monitor showed dispatched → abandoned beside "the process is gone without a complete manifest". Read as a claim about the worker, that looks like a false positive: the worker may have finished and simply failed to leave a record the classifier accepts. Read as a claim about the process, it is exact.

recovery.py reaches abandoned only on positive proof of death. The arm requires a terminal stored phase, alive is False from the process table, no non-terminal manifest, and — since commit recovery.py:1660 — zero commits beyond the recorded base. So the classification is defensible by construction, and the question this document answers is a different one: did the runs it labelled have work to show?

§— The population, and what "resolves" means

The sample is every to_state=abandoned row in ~/.config/reckon/crew/watch/*.events: 270 transitions over 224 distinct run ids (32 runs were re-abandoned after a retry) across five projects — nova 99, reckon 80, imas-codex 69, imas-efit 19, imas-ambix 3. Nine of the 270 are baseline rows (inventory written when a follower attaches) and 261 are genuine transitions.

A run "resolves" if its run directory (~/.config/reckon/crew/runs/<run_id>) survives and, for the commit question, if its worktree survives. The worktree path and the recorded base come from the run directory's own prompt.txt (all 224 yield a path) and, where the worker wrote one, its manifest.md; the base is corroborated against the per-project crew ledger docs/state/<project>/crew.json.

The headline count. Of the runs whose worktree still resolves and whose base can be resolved, 33 of 48 — 68.8% — hold commits beyond the recorded base. Taken alone that would answer the plan's question in the direction the lead suspected. The next section is why it does not.

§— Two independent instruments, and where each one lies

Three sources record whether a run delivered, and they cover different populations. None is complete, and two of them over-count unless read carefully.

SourceCoverageWhat it showsIts failure mode
Worktree commits past base 55 / 224 runs 33 runs delivered committed work A reused worktree path accumulates peer merges; base..HEAD then counts another run's commits
Per-project crew ledger commits[] 196 / 224 runs 102 runs recorded ≥1 commit; 108 reached gate: passed Survives worktree cleanup but only covers runs the coordinator later promoted — absence is not evidence of failure
Run-directory manifest.md 143 / 224 runs 80 written inside the run's own window; 21 of those record status: complete The file is rewritten by a later resume, so an mtime after the abandon time proves nothing about the run that was abandoned

The reused-worktree confound, measured

A worktree directory is named for its node, and node names recur across waves, so a worktree path is reused. Then base..HEAD counts whatever the branch has accumulated since — including the coordinator's own promote(...) merges of other runs. Measured on r-20260915T134345728165-the-reconstruction-keeps-its-settings: the worktree shows 84 commits past its base, yet its ledger row records zero commits and gate: not-run, and the range is full of peer promotion merges. Restricting to commits whose committer date falls inside the run's own dispatched_at → abandoned_at window removes the confound and drops the count from 33 to 24.

The manifest-age trap

A run-directory manifest that says complete is only evidence about that run if it was written during the run. Of 143 manifests, 63 were written after the abandonment — by a resume or a later attempt at the same node — and read as completion only if their age is ignored. The 80 written inside the dispatch→abandon window are the usable set, and 21 of those say complete: the worker had already recorded a finished node before the label landed.

§— The population spans two classifier generations

The decisive caveat. The arm that refuses abandoned when a run holds commits past its base did not exist for most of this sample. It landed in e662009c, fix(crew): never classify a run abandoned while its work survives, at 2026-09-14T21:57Z. Before it, a dead process with a complete-but-unread manifest and commits in the tree could be labelled abandoned exactly as the lead observed.

GenerationTransitionsRunsRuns holding commits past base

After e662009c53385 with commits past base; 2 inside their own window

The falsifier. If the guard holds, no post-guard run should carry commits past its base. Measured: 15 of 38 post-guard runs still show commits from some source, and of those only 2 hold a commit dated inside their own window (r-20260914T192229213809-msc-compile-host-memory, 3 commits, ledger gate: passed; and r-20260914T221330292225-borrowed-figure-is-not-the-lanes-own, 1 commit, ledger gate: passed). The other 13 owe their counts to peer merges on a reused path or to commits recorded after the abandonment, at promotion. So the guard is not shown to be broken, and it is not shown to hold universally either: two post-guard runs delivered committed work inside their own window and were still labelled abandoned. The arm reads record['worktree'] and record['base_sha'] from the live pointer, so a pointer that lacks either field, or one whose worktree was cleaned before the sweep, defeats the guard by returning zero — a mechanism consistent with both survivors and not yet distinguished from a chained-attempt artefact.

§— Answer

The measurement does not establish that the name is wrong. It establishes three things instead:

  • Half the population is unmeasurable. 169 of 224 runs (75.4%) have no worktree left, so for the large majority the work is neither present nor absent — there is nothing to count. A verdict drawn from the resolvable minority is a verdict about the minority.
  • A substantial minority demonstrably finished. 21 runs wrote status: complete inside their own window before being labelled abandoned, and 24 hold commits dated inside that window. Those are runs whose worker finished; the label described the process, not the work.
  • The sample is contaminated by an older classifier. 217 of 270 transitions predate the commits-beyond-base guard. Pooling them with the 53 that postdate it compares two different predicates under one word.

The honest reading is that abandoned has been an accurate statement about the process and an unreliable statement about the work, most sharply in the generation before the guard landed. Whether it remains unreliable now cannot be settled from this population; it needs a prospective sample — every abandoned run from a date after e662009c measured while its worktree still exists.

Deliberately not claimed. No repair is proposed and no rename is proposed; the question was only whether the work was finished. The per-project ledger's commits[] count (102 runs) is reported as a cross-check, not as the measure: it covers only runs the coordinator later promoted, so it under-counts and its gaps are silent.

§— Reproducing

The census reads three sources and writes one table:

# population
grep -h '"to_state": "abandoned"' ~/.config/reckon/crew/watch/*.events \
  | python3 -c 'import sys,json; ...'   # 270 transitions, 224 run ids

# per-run resolution
#   worktree + base  <- crew/runs/<run_id>/{prompt.txt,manifest.md}
#   base corroborated <- Code/<repo>/docs/state/<project>/crew.json
#   base..HEAD        <- git -C <worktree> rev-list --count <base>..HEAD
#   own window        <- git -C <worktree> log --format=%cI --no-merges <base>..HEAD
#   found: 55/224 worktrees resolve, 33/48 with commits past base, 24 in own window

Every figure in this document is reproducible from those three sources at the revision named in the evidence record; the per-run table is carried there alongside the aggregates.
