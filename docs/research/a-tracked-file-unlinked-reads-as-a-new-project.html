§1 — What happened

At 20:04:10 on 2026-09-21 a routine promotion wrote docs/state/reckon/crew.json as a new store at version 1, replacing 1,263 run records and 350 roster members with a single row. It raised no error. crew complete returned {"already_promoted": false, …} — indistinguishable from a successful append. Five further promotions from four sessions then appended to the empty store, so the loss grew by a row each time until the hold.

Every live surface agreed with the empty store. crew member list returned {"members": [], "ok": true}; crew(view="drain") counted against it. All confident, well-formed and wrong. Only git held the history.

§2 — Three defects, each alone survivable

The chain needed all three. Each was found by a different session, and none of the three could see the whole of it alone.

The causal chain, in the order it fired.
DefectEffect
1 A failure raised after the ledger append does not say the append happened. crew complete printed could not stage the landing writes and exited 0, with the row already written. Invited a retry. Produced a duplicate row.
2 _restore_landing_writes (promotion.py:1626) infers this path was created by this promotion from git restore returning non-zero, then unlinks it. With index.lock held, git restore exits 128. Unlinked the tracked ledger and plan file together — the call site passes both in one list, which is why those two and no others.
3 load() returns an empty store at version 0 for an absent path, because an absent ledger is the ordinary state of a project that has run no workers yet. Every guard passed relative to that empty view; the atomic write landed the fresh store cleanly.

Defect 2 is the sharp one: the failure that triggers the rollback and the failure of the rollback have one shared cause — a held index — so the destructive branch fires exactly where its premise is least true. The docstring already names the hazard (Recovery is best-effort because the refusal that triggers it … can itself block these git calls) and unlinks anyway.

No guard failed. Against an empty store, current_view is 0 == 0; the roster guard finds nothing to drop; the run-count guard compares 1 < 0. Each behaved exactly as written.

§4 — Recovery, and what it cost

Restored from dde1292f with the post-reset promotions re-applied: 1,263 + 4 = 1,267 runs, 350 members, 20 holds, version 2008 — set above both the last good 2007 and the empty store's 7 so a stale writer raises VersionConflict rather than racing. Validated through reckon's own envelope reader: zero duplicate run ids, zero duplicate member ids.

Four rather than five, because one post-reset row was a duplicate — the same run promoted twice, the copies differing only in store_write. The shadow SQLite store had refused the second write with a UNIQUE violation at the time, so a second authority independently rejected the row the dedupe dropped.

No work was lost. Every commit was in git throughout; what was lost was the ledger's account of it, for one hour and fifty-five minutes.

Landed by ordinary git commit, never through crew complete, because the defect being repaired lives on the promote path: promoting the repair runs the repair's own target.

§6 — The repairs

The rollback asks HEAD instead of inferring. Unlink only when a direct query says HEAD does not carry the path, never from an unrelated return code. The test that must fail against today's code asserts a path PRESENT in HEAD survives a restore that failed for an unrelated reason — written the obvious way round, that a path absent from HEAD is dropped, it passes while preserving the defect.

A failure after the append names it: the ledger row for the run is already written; do not re-promote. One clause, and attempt 1 would have stopped there.

A promotion never creates a ledger. Appending to a project's history and initialising a new project are different operations and should not share a path; initialising becomes an explicit argument rather than a fallback from absence. The same collapse applies to a malformed envelope, which is read as an empty project today.

Sequencing, agreed across three sessions: restore, then fix, then resume — and the ledger repair is not a licence to resume. Only the rollback repair is: after it, a deletion stops being catastrophic, but without it files still vanish silently and the next contended git add starts round three.

Three stops on one chain, and that matters more than any one of them. Each defect alone was survivable: the retry invitation only mattered because a file could be deleted; the deletion only mattered because an absent ledger read as a new project; the absence only mattered because nothing said the row was already written. Fixing one would have left a two-link chain that looks fixed until it is not — and the next occurrence would have presented differently enough that the fix in place would have been read as evidence the cause was elsewhere. Three independent stops is the difference between this not recurring and this recurring in a shape nobody recognises.

Every claim here was verified in the running module rather than at HEAD, by two sessions independently, because a change is not in effect until the code that executes carries it. Both modules resolve from the main checkout rather than a worktree, which is the way that check usually fails on this workstation. The tests were re-run rather than read off a manifest. That is the same discipline the incident was about: a record that says a thing, and the thing being true, are different facts.

§7 — How it was found

Not by any surface. Every live read agreed with the empty store; the promotion that caused it reported success; the two sessions that promoted afterwards had no reason to suspect anything. It was found by a session comparing the committed file against git history, and the causal chain was assembled from three sessions' partial views — one holding the deleter's mechanism, one the absent-read half, and one the transcript showing why a retry was the correct response to the message it was given.

Each session was wrong about part of it. A mid-write window was proposed and withdrawn when the envelope write proved already atomic. Eight hypotheses died across the day. The account here survived because each was checked against the artifact rather than argued.

§8 — The repairs held in the field, and one of them shipped a regression

The chain was validated the same evening by an event nobody arranged. A live promotion hit a genuine .git/index.lock collision on the real ledger, with a plan file in the same rollback list — the original trigger, unforced, on the production path. Every repair fired:

ArtefactState after the failure
docs/state/reckon/crew.jsonpresent, mode 600, 1275 rows / 350 members
the plan HTML in the same paths listpresent, mode 644 — the restore having written it
the promotion's errornamed the written row and said not to re-promote, rather than inviting the retry

Provenance of the table above: the row and member counts and the file modes were read at that moment by the session whose promotion hit the lock, not by this record's author. They are corroborated rather than re-measured — a later independent reading of the same ledger gives 1277 runs against the same 350 members, consistent with two promotions having landed in between. A third session reproduced the same outcome four times independently, also reported rather than observed here. That is all three defects exercised together under the original trigger, which no constructed test could have arranged — a synthesised contention is one the author designed and therefore already understood. What still failed was the landing commit, so the row was committed by hand and pushed; the row is the thing that must not be lost.

The third repair shipped a regression, and its shape is the incident's own one level up. Making append_run refuse an absent ledger closed the fail-open read, but the guard keyed on file absence — which is true both of a ledger that was deleted and of a project that never had one. Those are the two cases this incident turns on, and the guard could not tell them apart. The file is not there stood in for this project has no history, exactly as restore returned non-zero had stood in for the path is absent from HEAD.

It also closed with no door. The refusal named allow_create=True as the remedy; no production caller passes it, no command-line flag exposes it, and nothing in the package creates a project's first crew.json. So a genuinely new project's first promotion refused, and the refusal pointed the operator at a Python keyword argument they could not reach. Existing projects were unaffected because their files exist, which is why no fleet noticed. Measured over the same fifteen promotion and ledger test files:

Those 108 were not failures the fail-open had been concealing. They were correct behaviour the guard now forbade, across a candidate set of ninety-two files — every test that promotes into a synthesised repository. The standing rule is to measure what a suite was resting on before closing a fail-open guard; the rule that was missing is to ask what legitimate case the closed guard forbids, and whether its remedy can be reached by anyone.

Correction, appended rather than edited. The base row above was measured once. A second measurement of the same revision 73392943 over the same thirteen files, by the node that carried the repair, reported 10 failed / 229 passed — totals agreeing at 239, so two tests flipped between two runs of one revision. The base is not stable at that resolution and the 8 should not be cited on its own. The delta survives, because the repair node took both of its counts from one instrument in one run and an independent verification at the merged head e1f73a40 reports 10 failed / 246 passed with a failure set identical to base: 0 added. The 108 the guard introduced are gone. A delta measured with one instrument across both sides survives a flaky denominator; the denominator quoted alone does not — which is this record's own subject, a true reading standing in for a stable fact.

The fix asks git whether the ledger path was ever tracked in the repository receiving the promotion. Tracked-then-unlinked is this incident; never-existed is a new project. That beats adding an operator flag, because a flag can be passed wrongly and a tracked-ness query cannot — and it is the sentence this record is named for, turned into a question the code asks instead of an inference it draws.
