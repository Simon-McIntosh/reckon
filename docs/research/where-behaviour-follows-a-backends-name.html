§1 — What happened, and what this record is

At 07:32Z on 20 November the configured local backend moved from one name to another in front of the same model server. The admission service was declared under the old backend's name, and it stopped admitting every request not queued under that name. The lane sat idle for twelve hours with work queued. The comparison was corrected the same evening.

The ruling that followed is wider than that one comparison: a worker's reflexes, hooks, shims, fences and the services that act on its run must be the same whichever harness a lane is set up with. This record answers the first half of that ruling only: it finds the places where behaviour still follows a backend's name or a harness dialect, and does not change them.

The deliverable is a list, not a fix. Each row gives a path and line at one named revision, what is decided there, and which of the four permitted harness differences it falls under, or that it falls under none.

§3 — The four differences that are permitted, and how a row is classified

Four differences between harnesses are permitted because the harness's own interface forces them, and no others: the launch argv, the layout of the harness home, the stream format a run writes, and the model identifier. A row is classified into one of those four, or into none.

The distinction that matters is between speaking a harness's interface _backends.py and the fence tables do, and deciding a worker's treatment from the name of the harness serving it. A flag, a home path or a stream grammar is the first. A hook that is only seeded on one harness, an instruction file a worker is given, or a gate that holds by name at all, is the second.

§5 — What the rows say

The generator reports the table it wrote: 111 rows, of which 4 fall under the launch argv, 22 under the layout of the harness home, 12 under the stream format, 73 under none, and none under the model identifier. Each line is listed once, under the difference that line itself decides.

The rows that fall under none group into four mechanisms, and they are the ones worth reading next to §1's ruling:

  • Inbox delivery is not one mechanism. The hook is seeded into a run home for the claude dialect only (reckon/_worker_fence.py:417), a codex run instead carries hook and trust overrides on its argv (reckon/_backends.py:1471 for the composition, reckon/crew_run_commands.py:2989 for the reachability test), and every other dialect is refused outright (reckon/crew_run_commands.py:3026). So a message reaches a worker by three different routes, chosen by the harness.
  • Fence protections differ. The MCP exclusion file is written for claude and omp and for no other dialect (reckon/_worker_fence.py:600), so a worker on any other harness is fenced with no exclusion list at all. The same file's MCP settings seeding is claude-only (reckon/_worker_fence.py:422).
  • A worker is given a different instruction set. reckon/agent_context.py:20, :28 and :37 give three harnesses three instruction layouts, and reckon/agent_context.py:378 reads a configuration file only for one.
  • A lane's identity, billing, reservation and admission are all read from a backend's name. The report's lane (reckon/velocity.py:200), the unmetered set (reckon/ledger.py:127), the reservation family (reckon/crew/dispatch_picker.py:1082), the picker's offer exclusion (reckon/crew/picker/snapshot.py:1715) and the gate itself. None of these is a launch argv, a home layout, a stream grammar or a model identifier, so none of them is one of the four permitted differences: they are the case the plan calls none, and the one that caused the twelve-hour stall is among them.

§6 — The negative control

One site was known before the search began, so it tests whether the search is the search this record claims. The admission service's lane gate holds a queued pointer by comparing its backend name with the lane it is draining. D10 returns it:

Line 159 is the hold that stopped admitting on 20 November. Line 732 is the correction made the same evening: the drainer serves the local lane when its name is the configured local_backend, or when the two declare the same lane document. The name comparison survives at 732 as one of two admissions and no longer as the only one. Both lines are in the table.

§7 — Candidates examined and excluded, and modules that do not branch on a name

Two candidates were examined and are not behaviours:

  • reckon/velocity.py:97 — "nova": "main" is a project name in the report's project table, not a backend.
  • reckon/crew/fleet_migrate.py:232 — "claude": records is a dictionary key holding the collected records, not a branch on a name.

The search's opposite half matters as much: the worker's own shims and guards do not branch on a harness name. reckon/worker_shims/git, reckon/worker_git_shim.py, reckon/host_shims/{salloc,sbatch,srun}, reckon/nested_launch.py, and the hooks under reckon/hooks/ (inbox, stop, walk guard, message guard, git guard, native-agent guard) contain no dialect or backend-name comparison at all. Whatever the harness, they behave the same. That is the shape the rest of the worker's treatment should take, and it is the reason the list above is short: the difference is in the launch, the home and the stream, and in the few decisions those surfaces were allowed to leak into.

§8 — Reading this record again, and the check that keeps it true

The greps in §2 reproduce the candidate set; run them at the revision named there and the same 97 distinct lines come back. What each of those lines decides is the middle column, and the classification question applied to every row is whether the line translates a harness interface or decides a worker's treatment. Each row's path and line was resolved against revision e689315bb74ca1efdd63eee69d7a55ed9b235a0e before this table was written, so every row is a line that existed at that revision.

The table is checked rather than trusted. docs/research/where-behaviour-follows-a-backends-name.check.py reads this document, takes the revision from its plan-measured-at meta and the row count from plan-row-count, resolves every row with git show <revision>:<path>, and exits non-zero naming each row that no longer resolves, or that has fallen past the end of its file, or whose line has gone blank. It also fails when the table's row count disagrees with the meta. Run it after any edit to this document: 

python docs/research/where-behaviour-follows-a-backends-name.check.py

A row that stops resolving is the signal that the code moved; a row that still resolves but no longer decides what its sentence says is the signal that the decision changed, and only a reader can catch that. The check holds the half a machine can hold.

When a later change removes a branch, the row that named it no longer resolves. That is a useful signal rather than a stale record. The record states the revision it was measured at so a reader can tell a moved line from a changed decision.
