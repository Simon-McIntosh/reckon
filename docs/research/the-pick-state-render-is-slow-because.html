Research input

Why the pick's state render is slow

The run-time profile read accounts for 99.5% of timed read duration in state renders over two seconds; the same read accounts for 41.0% in renders under 0.1 seconds.

Window and attribution

The counter ran for more than a working day before this analysis. I read /home/ITER/mcintos/.config/reckon/crew/state-read-timings.jsonl and /home/ITER/mcintos/.config/reckon/crew/pick-timings.jsonl from 2026-10-14 00:22:00 UTC through 2026-10-16 05:55:00 UTC. The interval contains 6,785 timed-read rows and 2,723 completed pick windows. Read durations are individual calls; render durations are the enclosing state_render_ms stage.

Each read row records its finish time and duration. I subtracted the duration to obtain its start, then joined both timestamps to one pick's conservative state-stage window. The lower bound is started_at + snapshot_ms + capability_ms; the upper bound is started_at + latency_ms − questions_render_ms − jev_ms. The context estimate is measured inside the snapshot, so it is not added again. This window encloses the render while allowing untimed setup and composition. A row was accepted only when exactly one pick window contained it. A pick was retained only when its accepted rows included exactly one local_lane_load, list_live and template_load marker. Thus the attribution does not silently assign overlapping picks to one another.

Of the 6,785 rows, 6,607 had one candidate window, 110 had none and 68 had multiple; 1,254 picks formed complete, unique read groups containing 6,555 rows. The other picks cannot be treated as zero-read renders: some had no counter rows or no complete unambiguous group. All figures below use only those 1,254 groups. The ms and at fields contain no project, cache-hit flag or pick identifier, so the window join is the strongest attribution these logs permit.

The slow read

Across the joined picks, _cached_run_time_profile is the dominant read. It was called 2,793 times in 1,254 renders; its median call was 5.687 ms, but its 90th percentile was 413.024 ms. The slowest calls reach seconds. The three other named reads have much smaller tails. Percentages of render time divide each read's summed duration by the summed render duration for that population. They do not total 100% because prompt composition and other work are outside these four timers.

Cause and limit of the evidence

reckon/crew/picker/lane_context.py calls _cached_run_time_profile for foreign projects with live local workers. Its persisted cache key includes the project's ledger aggregate, runs directory, SQLite index and calendar day. A changed source key or absent cache entry invokes run_time_profile, which calls ledger.runs over a 14-day window. That path checks split run-file metadata before reading its index; on this shared filesystem, a single project can have hundreds or thousands of files (3,846 in reckon's runs directory and 1,228 in imas-codex's at inspection). A new dispatch process cannot reuse the preceding process's in-memory memo. Frequent run promotions invalidate the shared profile and put that ledger work back in the render's synchronous path.

This is the code path that explains a 5 ms common case beside multi-second calls and why the profile read alone dominates the slow renders. The counter did not record whether a particular call missed its cache, which project it read, or the time spent in metadata checks versus parsing. Those details remain an instrument gap; the timing result identifies the expensive read, and the code identifies the plausible slow path rather than proving that every slow call took it.

Proposed follow-on and expected effect

Move profile recomputation off the pick's critical path. Publish a small, validated profile snapshot when a project's ledger changes; let the pick read that snapshot with its source stamp and age. If the source has moved, serve a bounded last-good snapshot with its age disclosed, or report an unknown return time when it is too old. The render should never rebuild a foreign ledger profile synchronously. The follow-on must verify that changed ledger data eventually refreshes the snapshot and that stale or absent data is labelled, so the picker does not mistake an old figure for a current one.

An illustrative replay capped every profile call at 20 ms while leaving every other measured duration unchanged. For the 1,254 joined picks, the render's 90th percentile falls from 2,708 ms to 118 ms; the share of picks whose own elapsed time exceeds the dispatcher's 5 s bound falls from 192/1,254 (15.31%) to 112/1,254 (8.93%), a 6.38-point reduction. A 50 ms cap gives a 144 ms render 90th percentile and the same 8.93% over-bound share. These are conditional estimates of removing synchronous profile stalls, not post-fix measurements. The dispatcher also performs work before pick(); this log cannot predict its actual fallback rate from the pick duration alone.
