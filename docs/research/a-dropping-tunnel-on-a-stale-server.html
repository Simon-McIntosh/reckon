§1 — What happened

On the morning of 1 October the plan reader showed two banners on a research document in mctb: authored plan HTML failed — network error and structured plan state failed — network error. Project pages for other repositories also stopped loading. The document, mctb-htscl-loop-configuration, had just been edited, so it was suspected of carrying an HTML error that broke the site.

It did not. Neither failing request reached the server. Two things were wrong at once. The SSH tunnel from the user's machine was dropping and reconnecting, and a fetch made while it was down fails before any server sees it. The server behind the tunnel was also running code from 29 September, 190 commits to reckon/ behind the client it was serving. So every project page fell back to the slow discovery path, taking 6 to 14 seconds, long enough for a dropped tunnel to kill the request in flight.

Not a cause: the document (valid in every committed version, §3.3), a server crash (the unit never restarted and served no 5xx response all morning), or the parser (20 ms on every version, with both the old and the current code).

§3 — Root cause

§3.1 — The failing requests never reached the server

The server logs every request the moment it sends a status line. Between 22:40:51 and 06:23:58 no request for the document's HTML (/mctb/research/<slug>.html) or its state (/plan/mctb/research/…) from the user's browser appears in the log, though page shells, discovery and figure requests from the same browser do. A fetch that is answered with any status, even an error, leaves a log line, and so does one whose client leaves mid-response (a broken-pipe traceback, five of them this morning). These two left nothing. They failed before reaching the server.

The user's SSH connection from the same address logged in seven times between 05:31 and 06:17 and lost three sessions at 06:09:05 and 06:14:15. The tunnel to port 8765 runs inside one of those connections. While it is down, the local end of the forward refuses or drops the browser's connection, and the browser reports exactly a fetch with no response. The laptop side was not observable from here, so this is the explanation that fits every server-side observation, not a direct capture. Two controls support it. At 06:21, while the stale server was still running, a fresh browser through a fresh tunnel loaded the same plan cleanly. At 06:23:58 the user's own load succeeded in full once the connection settled, before anything had been changed.

§3.2 — Every page took the slow path, so drops landed on requests in flight

The login-node service had run since 29 September 17:57:48. In that time 190 commits touched reckon/. Client JSX and CSS are compiled per request from the working tree, but the Python server is not reloaded. So the browser was running the current client against a server two days older. The current client asks /_index/<project> for its first paint, and the old server has no such route: all 16 /_index requests this morning returned 404, and 112 figure thumbnail requests did the same. The client handles the 404 by falling back to full discovery, so nothing errored. But every project page waited on /_discover, which took 14 s for imas-ambix. A request that takes 14 s across a tunnel that drops every few minutes is one the user sees fail. After the restart the same index answers in 7 ms for mctb and 2.0 s for imas-ambix on a cold build.

This is the second time. SPA project render fault (2 September) found Nova's empty surface to be the same split: an unrestarted server emitting an old entry point beside current shell modules. That RCA named the mechanism ("server and parse code are not hot-reloaded") but nothing changed what deploys the server, so the condition came back with a different symptom.

§6 — Can reckon check a document's compliance by itself?

Yes, and the checker already exists. reckon audit-doc (also python -m reckon.doccheck) checks the render contract: required meta, sections that are never closed, relative image paths, literal markdown in rendered bodies. It exits 1 on any error. Measured here it passed the real mctb document and failed all four broken specimens: an empty file, a binary file, a file truncated mid-section, and one with mismatched closing tags.

What is missing is the trigger. Today only the reckon-create skill's text asks an agent to run it, which depends on an agent remembering to. That is the kind of check that fails. The server, meanwhile, never lets a malformed document take a project down: discovery kept listing the good document beside all four broken ones. But it is silent about them. The empty and binary files disappeared from the listing without a word, the truncated one listed as if whole, and plan-impl="abc" read as 0.

The recommended pattern ties the existing checker to moments that always happen:

MomentMechanismWhat it catches
Commit (blocking) A check-only git pre-commit hook in each mounted repository, installed by reckon sync. It runs reckon audit-doc on the staged blobs of docs/**/*.html only (read with git show :<path>, so it checks what is committed rather than the working file) and never edits anything. Every author — human, agent, any harness — at the one step all of them take.
Edit (advisory) A post-write harness hook on docs/**/*.html, added to the fragment reckon hooks install already manages. The agent sees the error in the turn it wrote it, before it reaches a commit.
Read (visible) Discovery computes each document's check verdict in Python and carries it in the index row. The reader badges a non-compliant document, and reckon audit lists them across every mount. Documents written before the hooks existed, committed with the hook bypassed, or edited outside git; and the silent drops above.

With the commit and read bindings in place, no agent needs to remember anything. The edit binding only makes the feedback earlier. One caveat about this incident: none of the three would have prevented it, because the document was valid. They prevent the failure that was suspected, not the one that occurred.

§7 — Follow-up work

Two follow-ups landed the same day and are live on the login-node server, restarted at 08:34.

ChangeWhat it doesCommits
The server reports when it runs older code than disk At start the server records every module of the package (stat identity and hash). GET /_server compares that with disk and returns the host, the pid and a one-sentence verdict. A touch that leaves the bytes alone is not drift. The shell shows the server's sentence and the restart command in a banner under the top bar, and reckon service status ends with code: current, stale — … or unknown — nothing answered. On a scratch server, changing one module after start produced the banner on the next page load. f7019d73c, d32d59c1c
Every document carries a render-contract verdict without anyone running a check The read-time binding from §6. The server keeps one verdict per live document (the audit-doc check), keyed on every file the check read, and computes missing ones in a niced child process. GET /_checks/<project> lists the failing documents; the reader shows a document's errors, collapsed under one line with the audit-doc command; the list marks a failing row; and reckon audit lists failures across mounts without changing its exit code. A first full pass checked 1,523 documents in about three minutes and found 32 failing in 8 projects, 17 of them in imas-efit. 3d5ed27b4, b193c4168
Persisted index rows stay valid on every host Found while building the above: GPFS reports a different device number for the same file on each host (41 on the compute node, 65 on the login node), so 0 of 1,223 imas-efit index rows written by the server matched when read from the compute node. Every reader re-parsed the whole project and rewrote the index. Rows now compare without the device number, and the verdict store does the same. c208f7a3c

Still open. A server that restarts itself when its code changes (exit when the package moves and the new code imports cleanly; Restart=always brings it back) would remove the manual step. It costs a restart and cold caches on every landed change, so it is a decision for the lead. The commit-time binding from §6 (a check-only pre-commit hook installed by reckon sync) and the edit-time harness hook are not built; with the read-time verdict live, they would move the signal earlier rather than create it. The 32 failing documents are listed by reckon audit and have not been repaired.
