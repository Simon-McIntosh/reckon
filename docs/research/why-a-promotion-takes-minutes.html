§1 — Summary

On 2026-11-10, every crew complete on the fleet node took between 4.6 and 15 minutes. That included promotions of plan-review runs, which write no code and run no gate. One promotion was killed by its 900 s timeout. It left its run live and its lock held, and that shut the plan's review gate until the promotion was run again by hand. Promotion sits between every review round and the next one, so its cost is paid once per round. Across two power_convertor plans that day that came to roughly 25 review rounds. The slow promotion was the main reason the crew panel showed no work in flight that evening while both coordinators were busy.

No single bug is the cause. The promotion path reads whole populations from GPFS when it needs one run's data, and it does this in more than one place:

  • the harness home of every run directory in the crew home (22,350 of them);
  • every per-run ledger file of the project (2,332 for power_convertor, 7,752 for reckon).

Each walk costs a few minutes when GPFS is contended. On this node it was contended, with load averages of 131–139 and about 20 tasks in cxiWaitEventWait. These walks have been found one at a time: each was found with py-spy after a coordinator noticed a slow promotion. Two were fixed last night (§61 and §62 of a-read-answers-inside-its-deadline). A third (§63) is landing as this is written. A fourth, the ledger snapshot, was seen in a py-spy dump of §63's own landing and has not been filed yet.

Fixing §63 alone will not make promotions fast. What makes them stay fast is a guard on the whole crew complete path that fails when its filesystem calls grow with the run population (§5, R3). The guard should come with a smaller population (R4) and with promotion taken off the review critical path (R5).

§3 — Root causes

RC1: whole-population reads in a per-run operation. A promotion acts on one run, yet two stages of _complete_locked read every run.

  • _harvest_lane_receipt calls read_rollout_receipt without the run_id the function already accepts, so _locate_rollout searches every run's harness home for the one session the promoting run owns. The fix is four lines: ad1e6697d0, landing as §63.
  • ledger.load rebuilds its cache key by statting every per-run ledger file. The comment at ledger.py:1180 gives the reason: "directory mtime cannot detect an in-place edit". The key is correct, but its cost grows with the project's whole history and is paid on every load.

The two walks have the same shape as the held-worktree fallback scan fixed last night in §61 and §62.

RC2: the populations have no bound. the-crew-home-has-a-bound §5 (the existing backlog is reclaimed) is deferred, so the crew home holds 22,350 run directories. One-file-per-run ledgers grow by every run a project has ever made. Any O(N) walk therefore gets slower every day, including walks not found yet.

RC3: contended GPFS multiplies the cost. A stat that costs about 250 µs on a quiet filesystem costs milliseconds to tens of milliseconds behind 20 blocked tasks. On 2026-11-10 the fleet node ran at load 131–139: heavy suites ran inside the fleet job, and the monitor read GPFS. The lead's directive the same day moved heavy work to partitions, which lowers the multiplier but leaves the walks in place. Every walk in RC1 is a small cost multiplied by N and by this factor.

RC4: promotion is on the critical path of every review round. _standing_plan_review refuses a new compose while any review pointer of the plan is live, including one whose report is already stored. So each round costs reviewer time plus promotion time. A design review and a content review also exclude each other. The numbers on 2026-11-10:

  • ripple-inception-risk ran 9 content rounds and 1 design round, at 25–35 minutes per round, of which 5–8 minutes was promotion;
  • iter-supply-test-integrity ran 16 content rounds.

Answering findings already works before promotion: c71ae21b answered all three round-8 findings while that run's crew complete was still running. The gate is the only thing that waits.

RC5: a slow promotion is easily killed and leaves state behind when it is. Coordinators call crew complete with shell or MCP timeouts sized for a fast verb. A kill mid-promotion leaves the run live and the promotion lock in ~/.config/reckon/crew/locks/, so the compose refuses with "a plan review is already in flight as a live run". Separately, ledger._commit_state_write commits once and raises when a peer holds .git/index.lock. That is the-crew-does-its-own-bookkeeping §29, and it is what left §63's own plan declaration uncommitted in the reckon checkout at 21:50.

§4 — Why these walks were found one at a time

Each walk is invisible in tests because test crew homes hold a handful of runs, and invisible on a quiet filesystem because N × 250 µs is still under a second. A walk shows up only when N is large and the filesystem is contended at the same time. A coordinator then notices it as a slow verb, and someone has to py-spy it. §63's test proves that one function does not scale with the population. Nothing tests that crew complete as a whole does not, so the ledger snapshot walk passed every check and showed up only in a profile of the fix for the previous walk.
