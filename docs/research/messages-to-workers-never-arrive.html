Research input

Messages to workers never arrive

A coordinator can address a crew worker by name, is told the send succeeded, and the worker never receives anything — in 3,949 runs, not once. The approval hold that swallows the message is the mechanism; the defect is that the channel is advertised as available at all.

What was observed

A sprint-review coordinator checked in on four measurement runs and judged that three of them were about to submit a batch job without committing the benchmark script first. It sent each worker a one-line instruction — commit the benchmark before submitting the job — by peer message, addressing them by the names its own session listing had shown.

All three sends returned success. Each was then reported held: the recipient's session has different permission-mode settings, so their user must approve it before Claude sees it. One later reported expired without approval. The coordinator read the holds as belt-and-braces redundancy — the briefs already said to commit first — and moved on. That reading was reasonable and wrong: no worker received anything, and none ever could have.

What the recipients actually are

The three recipients resolve to process ids 1354598, 1362438 and 1369929. Every one is the same shape: 

claude … -p --output-format stream-json --verbose \
       --effort high --dangerously-skip-permissions \
       --add-dir …/.reckon-worktrees/…/<node>

Measured from the process table and /proc:

PropertyMeasured valueConsequence
controlling terminal ? — none, on all three no interactive surface exists
file descriptor 0 …/runs/<run>/prompt.txt stdin is a regular file, already consumed
file descriptor 1 …/runs/<run>/stream.jsonl stdout is an append-only log, read by tooling
parent process 1 detached; no shell, no session leader
permission mode bypassPermissions differs from an ordinary coordinator's mode

These are headless print-mode processes. There is no user attached to any of them, so an approval gate in front of their inbox is a gate nobody can open.

The measurement

The holds could have been an intermittent condition — a busy recipient, a slow approval. They are not. Every delivered peer message arrives in the recipient's transcript wrapped in a cross-session-message element, so the marker is countable on both sides.

PopulationFilesOccurrences of the marker
Interactive session transcripts (positive control) 244 11,939
Crew worker run streams, every run on this host 3,949 0

The control is what makes the zero mean anything: an absent signal and a mis-aimed instrument return the same empty result, so the same grep was first required to find the case known present. It finds 11,939 of them. Against every crew worker stream ever written on this workstation it finds none, in zero files.

The delivery rate of this channel is not low. It is zero, and it has been zero for the life of the fleet.

Why a coordinator uses a channel that has never worked

Three surfaces agree that the channel is available, and nothing contradicts them until the message has already expired.

  1. The session listing advertises workers as peers. A crew worker appears in it as cca-wall-at-cell-pitch-5a · interactive · busy — the same row shape, and the same word interactive, as a genuine coordinator session sitting at a terminal. Of 31 peers listed during this analysis, roughly twenty were headless workers. Nothing in the row distinguishes them. Confirmed independently from a second coordinator session on the same host, which found the same proportion — about twenty of its thirty-four rows — and its own three in-flight workers listed among them as interactive. On a busy host the peer list is mostly workers, and the genuinely addressable sessions are the minority.
  2. The send reports success. The call returns success: true with a message id. That is literally true — the message reached the recipient's socket — and it is read, reasonably, as delivery.
  3. Reckon's own instructions say to do it. The orchestration reference tells a coordinator, on finding evidence but no report, to message the worker and tell it to write the deliverable to the named path. The workstation-wide recovery order for a silent worker reads manifest file → on-disk logs → message the worker → only then redispatch. Neither names a mechanism, because at the time they were written the only mechanism in view was the peer channel.

So the coordinator followed a written instruction, using a surface that listed the recipient and a call that confirmed the send. Every available signal said the message landed. This is the failure shape this repository has recorded repeatedly and under several names: a protection, a record or a channel that reports success while doing nothing, where the silent clearance is worse than a loud refusal.

One direction is built; the other is advertised

The worker-to-coordinator direction was analysed and repaired previously: run state is pull-only, and turning a worker's file change into something a coordinator hears takes a pointer, a producer, an event stream and a session-local follower. That chain now exists, and dispatch refuses to launch without the last link armed.

The reverse direction has no chain at all. It has a name in a listing and a call that returns success.

What exists instead, and the case it does not cover

There is a real coordinator-to-worker channel: reckon crew resume --run <id> --advice "…". It continues the worker's own session so the advice reaches something that still remembers what it tried. It is the right answer to a worker that has stopped and asked for help, and it is what the recovery order should have named.

It does not cover the case that produced this incident, and this was measured rather than inferred. Invoked against a run whose process is alive — reproduced against a synthetic pointer in a temporary configuration home, so no real fleet was touched — resume exits 1 with an empty stdout and this on stderr: 

Error: run '<run-id>' still has a live process;
       observe or stop it before resuming

So resume is refused for exactly the state the coordinator was in. Two details matter for the repair. The refusal names the reason but no alternative command — observe or stop is prose, not something a caller can run — and unlike a budget hold it carries no structured error key, so a programmatic caller cannot distinguish it from any other failure. The four runs here were mid-turn and healthy. The coordinator did not want to recover them; it wanted to change what they did next, before they did it.

For that — an instruction to a live worker, delivered while it is still working — there is no channel, refused or otherwise. The useless one was used because it was the only one that appeared to exist.

Finding

Two defects, and they are separable.

The advertised channel. Headless workers are listed as interactive peers and accept sends that return success, while their measured delivery rate is zero. This is a false clearance: it costs a coordinator a real decision every time it is believed. The remedy is for the attempt to fail loudly and name the working alternative, not for it to be held pending an approval that cannot come.

The missing channel. Reckon has no way to put an instruction in front of a live worker. Resume covers the stopped worker; nothing covers the working one. Until that exists, the written recovery order contains a step no mechanism implements — a rule with no check, which is the condition this repository treats as equivalent to having no rule at all.

The second is why the first is dangerous. An advertised channel is merely wrong; an advertised channel standing in for a capability the system genuinely lacks is what makes a coordinator believe a fleet was steered when it was not.

A sibling, measured the same morning

The defect has a twin in a different surface, found while this document was being written and recorded here because it is the same shape rather than because it belongs to the same repair. The roster reports free members; nothing reports the endpoint those members run on. At 07:10:17Z on this workstation, 43 live run pointers held 37 live processes, 34 of them on a single self-hosted deployment, while crew member list reported 38 free members and no signal at all about the lane behind them.

Five coordinators had each sized a fleet against their own dependency graph width, which is the correct local rule. Nobody was wrong. The surface that would have prevented it does not exist to be consulted, so calling it a coordination failure misnames it: it is a missing signal.

What the governing quantity actually is came from the session that owns the deployment, and it corrects the obvious reading — including the one first written here. It is not a worker-count ceiling. The lane was serving 190 tokens per second aggregate while performing 22,557 tokens per second of prefill, of which 18,863 was recomputing prefixes the engine had already built; the cache turned over completely in 98 seconds while a single reply took 54 seconds plus tool time, so each session's cached prefix was evicted on the same timescale as its own turn gap, and the recomputation was what evicted the next session's. Draining the fleet from 36 concurrent requests to 20 moved the aggregate from 198 to 190 tokens per second. Shedding workers raises per-worker throughput and does almost nothing for total output.

That was corroborated here without being sought: this fleet watched the lane fall from 34 live workers to 19 over two hours while its own remaining nodes held steady at roughly one tool call every four minutes, neither speeding up nor slowing down.

The correction sharpens the point rather than softening it. The quantity that governs is cache residency — concurrent requests multiplied by mean context against the pool, where the safe bound is (pool × 0.5) / mean context because the pool must hold reusable prefixes as well as active contexts. Mean context ranged from 15,000 to 167,000 tokens in one day, which moves that bound from about 31 concurrent requests to about 7. So the roster's free-member count is not merely the wrong number to read, it is a number that cannot be corrected by scaling: no fixed worker count is right for more than one node mix.

Three instruments agree, which is worth stating because each was pointed at the question independently and one refutes the framing its own author had been circulating. The deployment reported aggregate throughput moving from 198 to 190 tokens per second as concurrent requests fell from 36 to 20. A second fleet counted its own tool calls per ten-minute bucket across the drain and found 13.9 rising to 16.5 — a nineteen percent gain in per-worker rate where halving a binding constraint should have roughly doubled it. A third watched its nodes hold a constant rate while the lane fell from 34 live workers to 19. Correlation between a large fleet and slow workers was real; the cause read into it was not, and the counterfactual that settles it was being recorded by the nodes themselves the whole time.

The remedy has the same shape as the defect, one level down, and this is the part worth carrying. A dispatch-time cap computed as above needs a published figure for the lane's headroom. That figure does not exist: asked for this lane, the pre-flight check answers headroom: unknown with a null utilisation and the detail no rate-limit event in the stream yet, and it correctly declines to hold the lane, because absence of a signal must never be read as exhaustion. So the budget fence cannot fence this lane at all, and the cap that would replace the missing roster signal is itself waiting on a missing lane signal. A remedy that consumes an unpublished input is not yet a remedy — it is the same false clearance with a formula in front of it.

What makes it the same defect is the substitution. A free roster member is a real, measurable quantity, and it is not the quantity that governs whether a worker makes progress — exactly as a successful send is real and is not delivery. Admission is not delivery, and a free member is not free capacity. In both cases a coordinator reads the available number, acts on it correctly, and is wrong.

The consequence is measured and it is not cosmetic. A starved worker and a hung one are indistinguishable from every surface the system offers: one node here ran 12 tool calls in 55 minutes and another 35 in 63, making real progress in each, while three coordinators independently opened raw event streams by hand to establish that their workers were not stalled. One was about to kill two of them. The failure mode is a coordinator destroying good work, and what prevented it three times that morning was coincidence.

One qualification belongs beside any such figure, and it is the reason this paragraph carries a timestamp. A concurrency count relayed without its observation time is the defect one layer up: a figure of 21 measured at 07:03 was passed on and read at 08:00, by which point the true count was 43. The number that matters is never the count alone but the count beside the moment it was taken.

Method and limitations

Process facts read from ps and /proc/<pid>/fd while the three runs were live. Marker counts taken over every stream.jsonl under the crew run directory and every session transcript under the harness project directory on this host, on 2026-09-15.

The resume behaviour was reproduced directly: a synthetic live pointer whose pid was a real sleeping process, under a temporary configuration home, with the real pointer directory afterwards confirmed to hold no trace of the probe.

Limitations worth stating. The count covers this workstation only, and a stream is truncated when a run is promoted, so a delivered message in a long-since-archived run would not be counted — the positive control bounds how wrong that could be, but does not eliminate it. The permission-mode explanation for the hold is the harness's own stated reason, not an independently verified cause. Resume was measured through the command-line surface only; the equivalent action on the tool surface may report differently, and resume against a pid that has become a zombie takes a different path in the liveness check and was not exercised.
