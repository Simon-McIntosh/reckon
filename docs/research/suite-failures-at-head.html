§1 — What was measured

Revision bafcd4cc on main, clean tree. Host 98dci4-clu-2058 inside fleet allocation job 1277272 (28 cores), TMPDIR=/tmp, Python 3.14.2, pytest 9.1.1.

The serial run cannot complete in a bounded job. pytest tests/ in one process reached 14% after 30 minutes at about 21% CPU and was stopped. The suite was therefore run as one pytest process per test file, 406 files, 16 at a time, 900 s per file:

timeout 900 .venv/bin/python -m pytest -p no:cacheprovider -q -rfE --basetemp=<per-file dir> tests/<file>.py

A first pass shared pytest's default base temp directory across the 16 concurrent processes. pytest keeps only the three newest pytest-N directories, so concurrent processes can delete each other's temp dirs mid-run. Every red file was therefore re-run with its own --basetemp. The failure set below comes from that isolated re-run.

§2 — Root causes confirmed from the code and history

Four clusters account for more than half the failures, and each traces to a commit that closed a guard deliberately without updating the tests that were passing only because the guard was open. All four are stale expectations: the shipped behaviour is intended, so the tests move to it (the locked decision carried from Every Suite Failure Has An Owner).

The rest, about 70 node ids, are individual contract drifts. Each is diagnosed by the node that owns its file. They include: a committed plan.schema.json behind its generator; a skill file over its token budget and missing two sentences the contract tests pin; a public-surface snapshot; a review checklist item call_sites with no VERDICT emission in the prompt; a fleet state stopped not covered by the attention buckets; backend headroom parsing that now reads unifiedWindows; session-reuse lookups returning None; and figure-topic scope conflicts that no longer raise. That last one is the likeliest real defect in the set. Two are environmental on this node: test_spa_module_scope needs a headless browser, and test_doctor reads host configuration.

§3 — Repair partition

Every red file belongs to exactly one repair node, so no two nodes write the same test file. A node diagnoses each failure in its files, classifies it as stale expectation, product defect, test isolation or environment, and repairs it. A repair needing a product source file outside the node's paths is reported rather than made, because several nodes may reach the same module.
