Explainer

Reckon Onboarding

Three surfaces install independently, and only one of them is needed to do agent work: the skills teach an agent the workflow, the MCP server lets it write plan state, and the docs server renders the surface for a human. A project must be registered before either server can see it.

§1 — What installs once, and what repeats

Two of the steps are host-wide and done once; one is per-repository and repeats every time a new project joins. Conflating them is the usual first-run mistake — people re-link the skills for each project, or register a project once and expect a second repository to appear on its own.

§2 — Prerequisites

A checkout and uv. Everything else is driven from the checkout, and every command below can be run from any directory by naming the project explicitly, which is what makes this work without installing anything onto the path. 

git clone git@github.com:Simon-McIntosh/reckon.git ~/Code/reckon
cd ~/Code/reckon && uv sync

The distribution is named reckon-plans; the import package and the console command are both reckon. Invoke it as uv run --project ~/Code/reckon reckon <command>. The skills all use that form, so a path install is a convenience rather than a requirement. Python 3.12 or newer.

§3 — The skills

The skills are what make an agent use the plan system correctly rather than hand-editing HTML: they carry the state-writeback rules, the followup contract and the fan-out boundary. They are the only one of the three surfaces that needs no server at all.

Link them, do not copy them. A symlink means an edit in the checkout is live in every runtime immediately, and it cannot drift; a copy is a second source of truth that goes stale silently. Note that the reckon install-skills subcommand copies, and reaches only the Claude directory — the linking step in reckon-sync is the one that produces symlinks across all three runtimes.

DirectoryRuntime that reads it
~/.claude/skills/Claude Code
~/.codex/skills/Codex
~/.agents/skills/Shared agent runtimes

Run Step S of ~/.claude/skills/reckon-sync/SKILL.md, which enumerates skill directories by the presence of a SKILL.md rather than by a name list. That detail matters: a fixed list silently skips a skill added later, which is exactly how reckon-roadmap stayed unlinked after it was written.

Seven skills install. reckon-sync sets up a repository, reckon-create authors a plan or doc, reckon-edit amends one and records outcomes, reckon-ship executes the work a plan describes, reckon-sprint manages sprint and roadmap state, and reckon-status and reckon-roadmap read without writing.

§4 — The MCP server

The MCP transport brokers versioned writes to plan state. It is what lets an agent resolve a followup or lock a decision without the HTTP server running, and registration is per client rather than per host.

For Claude Code:

claude mcp add reckon --scope user -- \
  uv run --project ~/Code/reckon reckon mcp

For Codex, add a table to ~/.codex/config.toml. Append it rather than rewriting the file, and re-parse afterwards to confirm the result is still valid TOML: 

[mcp_servers.reckon]
command = "uv"
args = ["run", "--project", "/home/<user>/Code/reckon", "reckon", "mcp"]

A registration is worth smoke-testing before trusting it, because a wrong command fails silently at client start rather than loudly. Feed the server one initialize frame and read the reply: 

printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"smoke","version":"0"}}}' \
  | uv run --project ~/Code/reckon reckon mcp

A registration added to a running session is not live in that session — the client connects its MCP servers at start, so restart or reconnect before expecting the tools.

§5 — Registering a repository

One idempotent command per repository. It registers the project in mounts.json, copies the shared stylesheets, writes the SPA entry point, creates the state directory and symlinks it into the config home: 

uv run --project ~/Code/reckon reckon sync <repo>/docs
# override the project key, which defaults to the docs parent directory name:
uv run --project ~/Code/reckon reckon sync <repo>/docs --project my-key

mounts.json is re-read on every request, so a newly registered project needs no server restart. Plans are discovered live from their <meta name="plan-*"> tags too — sync is for setting up a repository and for pulling in new shared assets after a reckon upgrade, not for adding a plan.

The config home resolves as RECKON_HOME, then ~/.config/reckon, then ~/docs-server for a legacy install. The CLI resolves it, so no step here needs to compute it.

Re-sync existing projects after upgrading reckon. A project's index.html is a rendered copy of the checkout's template, so it does not follow the checkout when the asset pipeline changes. A project left un-synced across such a change keeps requesting modules that no longer exist and renders a blank page with no error, and because every request it does make returns 200 the failure looks like anything but a stale entry point. The check is cheap, so bind it to the upgrade rather than trusting memory: 

python3 - <<'PY'
import json, pathlib
home = pathlib.Path.home()
config = next((p for p in (home / ".config/reckon", home / "docs-server") if p.is_dir()), None)
mounts = json.loads((config / "mounts.json").read_text())
for project, docs in mounts.items():
    index = pathlib.Path(docs) / "index.html"
    text = index.read_text() if index.is_file() else ""
    stale = "text/babel" in text or "unpkg.com" in text
    print(f"{project:24} {'STALE - re-sync' if stale else 'current'}")
PY

§6 — The docs server

The HTTP server renders the SPA and serves shared assets and compiled UI modules. Agent work does not need it: the skills read plan HTML from disk and the MCP writes it. It is what a human uses to read and act on plans, and what the crew surface reports into. 

uv run --project ~/Code/reckon reckon serve            # port 8765
uv run --project ~/Code/reckon reckon serve --port 8766

A foreground serve dies with its terminal. For a persistent deployment install it as a systemd user service, which enables lingering so it survives logout: 

uv run --project ~/Code/reckon reckon service install
uv run --project ~/Code/reckon reckon service restart   # after changing reckon code

Registered projects are then at /<project>/. Because the server compiles the JSX itself and serves each module as /_ui/<name>.js, a Python change needs the process restarted before any reader sees it, while a JSX change is live on the next page load.

§7 — Verify, and what the check does not cover

uv run --project ~/Code/reckon reckon doctor

It confirms the skills are present, that mounts.json is readable with every mounted directory existing, and that an MCP registration exists.

Two gaps are worth knowing, because a green report is easy to over-read. The MCP check looks in the Claude Desktop config and the Codex config, and not in ~/.claude.json where Claude Code keeps its own registration — so it passes on a Codex-only registration while Claude Code has no reckon tools, and conversely a working Claude Code registration alone does not satisfy it. And the skills check tests presence, not that a skill is a symlink rather than a stale copy. Neither is caught by the command, so check both directly when a client unexpectedly has no tools.

§8 — First plan

With a repository registered, author through the skills rather than by editing HTML: /reckon-create <slug> for a plan, or the same command with reckon-type=doc for a non-plan document — a review, an incident report, an explainer such as this one. /reckon-status reads across everything without writing, and is the cheapest way to confirm a fresh install sees what you expect.

Validate anything authored before relying on it. The validator catches the failures that otherwise surface as a silently wrong render, such as a relative image source or literal markdown in a field the surface passes through as raw HTML: 

uv run --project ~/Code/reckon reckon audit-doc <repo>/docs/plans/<slug>.html
