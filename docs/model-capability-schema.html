§1 — Problem and boundary

Reckon currently stores haiku, sonnet, and opus in plan metadata, sprint items, followups, prompts, schemas, examples, and UI tags. Those names describe one provider’s product families rather than the ability a task requires. They also age poorly: a newer lower-cost model can outperform an older premium model, while high-risk work may still require orchestrator-level judgment regardless of nominal family.

This plan replaces provider names in persisted state with a model-neutral capability request. Provider and model selection remains a runtime concern. Historical values must continue to parse during migration, but newly authored state must not depend on a vendor taxonomy.

§2 — Proposed contract

The schema should separate a compact capability class from explicit risk and execution requirements. A likely shape is capability.class for broad scheduling plus optional fields such as reasoning, context, tool_autonomy, verification, and risk. The runtime advertises comparable worker capabilities, and the dispatcher selects the least costly worker that satisfies every hard requirement.

Relative policies such as “one below the orchestrator” remain useful defaults, but they must operate on runtime-advertised capability order rather than hard-coded model identifiers. Solver work, security changes, migrations, conflict synthesis, and other elevated-risk tasks can set explicit floors.

§3 — Migration and compatibility

Migration covers PlanState.tier, followup and sprint-item tiers, HTML data-tier, prompt templates, schema enums, MCP operations, SPA facets, audit rules, skills, fixtures, and existing plan HTML. Legacy values must map deterministically to neutral classes on read, emit an audit warning, and be rewritten only through an explicit migration command or ordinary state edit.

The migration must distinguish capability from effort: effort=L describes work size, while capability describes the minimum worker ability and safeguards. It must also avoid pretending that a single ordinal captures all requirements; the selected representation must leave room for structured constraints.

§4 — Done-when

  1. A versioned, provider-neutral capability schema is published for plans, sprint items, and followups.
  2. Dispatch matches task requirements to runtime-advertised workers with deterministic fallback and risk escalation.
  3. Legacy Anthropic-family values remain readable and have tested migration diagnostics.
  4. Skills, prompts, docs, MCP schemas, UI labels, and fixtures contain no provider names as capability enums.
  5. Round-trip, mixed-version, absent-worker, and high-risk escalation tests pass.

§ Decisions

What should be persisted as the task’s capability requirement?

A compact neutral class supports scheduling while structured requirements preserve risk, verification, context, autonomy, and reasoning constraints that cannot be represented by one ordinal.

How should existing haiku/sonnet/opus values migrate?

Legacy provider-family values remain readable with deterministic mapping and audit diagnostics; rewriting occurs only through explicit migration or ordinary state edits.
