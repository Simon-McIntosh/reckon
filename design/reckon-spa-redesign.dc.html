The complaint

“The inflight bar is useful, but could be designed in a cleaner way — does the user need to know the exact worker hash?”

What changed
No hash by default. Identity is member · §section · elapsed — the three things you act on. pid, worktree and log sit behind Run ⌄ — and even there the run id is a tail (…fleet-watch) with copy id beside it, since the full 42-character hash is something you paste, never read.
Elapsed became a budget. A bare duration says nothing; 10m 26s of 20m with a hairline meter is exactly the overrun signal that let two nodes sit unnoticed for 55 minutes.
The saturated bar is gone. An --accent-3 plate with a keyline, not a solid blue slab — it no longer outweighs the plan title above it.
Runs stack. One header, one row per run, section as the key. An overrun or NEEDS-HELP: run takes the warn treatment and the only real button on the surface — Resume.
“codex-m” was my invention, and that was the bug. The -m meant nothing. In ledger.py a member is a roster row of id · harness · role · session_id, and the id is whatever string you passed to crew member add --member — arbitrary by design, and auto-generated as session-… for ephemeral seats. Leading with it puts a name with no meaning in the loudest slot.
So the identity now leads with what actually dispatched the work: harness (codex-cli, claude-code) and the agent it ran (gpt-5.6 sol) — both already on the run record as backend and agent. Role and effort follow, and the member id trails as @lead — a session handle, not a name.
The @ earns its keep on ephemeral seats: @session-9c2f reads instantly as a throwaway that will be reaped, while @lead is a registered seat holding a long-lived session you can resume into.
The header lost its slab. Grey bar, hairline rule, warn-coloured “1 needs help” — the run rows carry the colour, the header just counts them.
Scope: this band is one plan, so it is one repo. It only ever shows runs against the plan you're reading — the repo tag in the header names which. Fleet-wide is Crew (1f), where every run leads with its own repo tag.
The cross-repo case gets one line, not a second view. When the plan's sprint has runs in other repos, a thin lane under the header counts them per repo (S13 elsewhere · nova 1 ● · imas-codex 2 ●) and links to Crew — so you learn the sprint is live elsewhere without the band pretending to own those runs.

The complaint

“The dropdown is overly verbose… I typically have it set to just created and rarely edited. It would be useful to see an edited timestamp on all plan interactions.” · “I don't find myself using the left hand scroll bar — an indication that the design could be better.”

What changed
Six sort options became two. Created / Edited as a segmented control — one click, no menu, state visible without opening anything. Status, progress, priority and title move under ⋯; they were never the default.
Edited is always shown. Today fmtPlanDate only prints the date for the sort you chose. Now every row carries edited … whatever the sort — same-day rows show the time, older rows the date.
Rows say something. One line of plan description replaces the — · 0% · dash soup, and in-flight surfaces here too, so the list doubles as the fleet view.
The rail stopped scrolling. Sprints became a chip grid, statuses a 2-up grid, archive left entirely — it now fits without its own scroll region.
Projects became first-class — and the rail only lists live ones. No tickboxes, no greyed-out rows: visibility is set once in Manage, and a hidden project vanishes from the rail, the switcher and every surface. Mounts stay registered; the SPA just stops carrying repos you aren't developing. The set persists per browser.
Two scopes, stated once. Focus (one project, set by clicking a row) drives Plans, Sprints and Graph — those are per-repo objects, and interleaving them would repeat the mistake evidence made. Crew and Overview span every visible project, because that's where you want the whole fleet at once.
Open question for you: should a cross-repo sprint (1d) force multi-project scope while it's active, or stay under focus with a repo badge? I've drawn the latter.

“We have duplicated the wiring for evidence and research docs, they do not block or enable. We need to design another visibility surface.” · “I don't like it interleaved with our plans — an evidence doc is not a plan.”

What changed
Docs leave the plan list. No archived rows in the middle column, no Archive 39 button competing with the status filters, no evidence:archive: nav keys in the plan stream.

The complaint

“The content given on the sprint plans (why now, done when) is FAR too verbose. All plan cards should come with a brief description and nothing else — forcing more into the pills makes them too large and hides other information.”

What changed
The two justification pills are gone. A card is title + one description line. why_now and done_when still exist in the sprint contract — they render in the plan, and in the generated prompt, where they're read once.
Five cards fit a column. The current board shows barely one; the whole sprint is now visible without scrolling a column.
What survived is what you picked: status dot, progress, in-flight, repo badge. Gate summary and the D n / ! n counters moved to the card's hover state — they were noise at rest.
The repo badge earns its place on a cross-repo sprint: three repos on one board, legible at a glance.
Resolve, rethought
The old button was a number with no noun. Resolve 8 didn't say what the 8 were, where they lived, or what they cost you — and in the code the answer is specific: open decisions block prompt generation (graph.jsx: “resolve before generating prompt”). The button hid its own consequence.
It becomes a queue with the consequence attached. One row per decision — plan, the actual question, who raised it, how long it's been sitting — and Generate prompt sits next to it visibly disabled, so cause and effect are adjacent instead of two clicks apart.
Two verbs, because there are two outcomes. Lock records the answer on the plan; Defer to run marks it as decidable during the work — which the prompt builder already supports (“surfaced in the prompt, to resolve during the work”) but the UI never offered. Deferring unblocks dispatch without pretending the question is answered.
The count dropped from 8 to 3 because 8 conflated open decisions with unreviewed evidence and stale gates. Only decisions actually hold a wave; the rest were never yours to resolve here.

The complaint

“The navigation of the sprints is 'clunky'. It is hard to get an overview of the sprints and how they depend on one another without scrolling left and right < >.”

What changed
Sprints get a home view. < > stepped through one sprint at a time and never showed a second one; the gantt puts every sprint on one screen with its real window.
Dependency is drawn, not implied. Handoff ties (S7 feeds S8; S15 feeds S16) are hairlines between bars — a blocked handoff is a red tick, so “what is S16 waiting on” is answered without opening S16.
Overview / Board is a toggle, not a different page. Click a bar to drop into 1d; the arrows survive there for step-through, where they make sense.
Progress reads as a fraction (16/16, 0/5 · 1 ●), not a percentage — items shipped is what you track at sprint scale.
It won't clog at S40. The chart is a window on an unbounded timeline, not a list of everything: a configurable horizon (4w / 8w / 6m / all) centred on today, scrolling in both directions, with the date axis re-scaling rather than the rows multiplying.
Anything closed folds itself. Sprints with nothing open collapse into one dashed lane (S1–S6 · 41/41) that expands on click — so the row count tracks live work, which stays roughly constant, instead of project age, which never stops growing.
Rule of thumb behind it: vertical space is spent on sprints that can still change, horizontal space on the horizon you asked for. Old sprints stay reachable, never resident.

The question

“Should we consider a G* label for all of our graphs so that we could reckon-ship a particular graph like we can do for sprints?”

The proposal
Yes — and it's a resource, not a view. docs/graphs/G3.html beside docs/sprints/, independently versioned, so reckon ship G3 is the same code path as shipping a sprint.
Sprint cuts by time; G cuts by dependency. A sprint answers “what are we doing for two weeks”; a G answers “what has to be true for this capability to exist”. Both are shippable, both generate prompts, and a plan can belong to several Gs but one sprint.
Shipping a G means its closure shipped — every plan it transitively depends on, across repos. That's the check the Graph tab can't express today.
Wiring is explicit, not implied by position. Left-to-right is the convention — columns are dependency depth from the G's roots — but position alone was doing too much work, so every edge is now drawn: a hairline with a ▶ head, dashed into unstarted work, red where the edge is blocking. The fan-in below the lane shows a node feeding two upstream siblings, which a pure left-to-right row can't express.
Depth, not time. Stated on the chart, because the sprint gantt next door is time — two horizontal axes meaning different things is exactly the kind of thing that degrades quietly.
Agreed on scope: this is a sketch, not a spec. Wiring it for real needs a docs/graphs/ resource type, a G membership field on plans, closure computation and a ship path — a follow-up chain, not a UI change. Say the word and I'll write those plans.
